# 自己レビュー

**「別の目で見る」ことには予想以上の価値がある**（開発者の指示。2026-08-24）。
自分が書いた直後のコードは、書いた本人には正しく見える。

このスキルは [CLAUDE.md](../../../CLAUDE.md) §4 の工程を実行するためのもの。
**まとまった実装の区切りごとに必ず通す。** 省かない。

**コードだけの話ではない。ADR・設計文書・リサーチの追加と変更も、マージ前にこの工程を通す。**
`designcheck` も `lint_docs.py` も**書いてある内容の矛盾は見ない**（見るのはフロントマター・
リンク・日付という「形」だけ）。**文書の中身を守るのは人の目しかない。**

## 手順

### 0. テストが緑であることを確かめてから始める

レビューは「動くもの」に対して行う。壊れている状態でレビューを頼むと、
指摘が「壊れている」に集中して、本当に見てほしい観点が薄まる。

### 1. レビュー対象を決める

`git log --oneline main..HEAD` で、このブランチで何をしたかを確認する。
**変更したファイルを列挙する。** 対象が曖昧だとレビューも曖昧になる。

差分ではなく**既にあるもの全部**を洗うとき（文書の一括レビューなど）は、
対象を「`docs/` 配下の全文書と `CLAUDE.md`」のように**範囲で**書き、
**全部読むこと**を依頼文に明記する。目次だけ見て答えられると意味が無い。

### 2. 観点を分けて投げる

`Plan` エージェント（**書き込めない**）を使う。修正は自分で行う。
**1 人に「全部見て」と頼まない。1 人 1 観点。**

**観点はレビュー対象に対して必要なだけ立てる**（2 つに限らない）。
ただし**同時に走らせるのは 3 人まで**（開発者の指示。2026-09-10。[30 §6](../../../docs/30_作業のルール.md)）。
4 観点以上あるときは**波に分けて 3 人ずつ**流す。観点を削って人数を合わせない。

観点は、その実装で**壊れたら困るもの**から選ぶ。

| 観点 | 何を見せるか | いつ立てるか |
|---|---|---|
| **会計ドメインと帳簿** | 不変条件・制度要件・帳簿としての整合。`docs/10`・`docs/11`・`docs/research/`・DDL | 会計ロジックに触れたら必ず |
| **設計とテスト** | 依存の向き・責務・**テストの十分性**。`docs/decisions/`・テストコード | コードに触れたら必ず |
| **CLB と DB の静かな失敗** | `qa/01` の型に当てはまる形が新たにないか。デザイン JSON・スクリプト・SQL | CLB デザインや SQL に触れたら |
| **画面と文言** | 利用者が実際に読むもの。[`docs/21_画面の原則`](../../../docs/21_画面の原則.md)・レイアウトのデザイン JSON・トーストとエラーの文言 | **画面か利用者向けの文言に触れたら必ず** |
| **利用者の作業** | [`docs/06_利用者の作業` §4](../../../docs/06_利用者の作業.md) の観点。読ませるのは 06 と [`docs/02_ペルソナ`](../../../docs/02_ペルソナ.md) | **画面・文言・導線に触れたら必ず**（06 §4） |
| **公開前の混入** | 絶対パス・秘密・ライセンス未確認の資産（CLAUDE.md §5） | 公開・マージの前 |
| **文書の整合** | 複数の文書・複数の箇所で内容が食い違っていないか。`docs/00_ドキュメント規約/`・`docs/README.md`（索引と保留リスト）・`docs/research/`・[`docs/32_調査のルール`](../../../docs/32_調査のルール.md) | **ADR・設計文書・リサーチを足したり直したりしたら必ず** |
| **文書と実物の一致** | 文書の**事実の主張を 1 つずつ実物に当てて検算させる**。csproj・フォルダ・クラス名・デザイン JSON・**保存の関門のコード（`*Gate.cs`）が本当にそれを検査しているか** | **「現在形の正典」を名乗る文書を足したり直したりしたら必ず** |

**「文書と実物の一致」の観点は、ADR から正典を集約する回で必ず立てる**（2026-09-13。
[qa/02](../../../docs/qa/02_自己レビュー記録/2026-09.md) のラウンド 85。**ADR の表は「当時の姿」なので、
写した瞬間に古い**——実物とずれた 5 件は全部、ADR から写した行だった）。
依頼文には**開いて突き合わせるファイルを列挙**し、「読んで筋が通っているか」ではなく
**実物を開くこと**を明記する。

**レビュアには、触れた領域の原則とルールを必ず読ませる**（開発者の提案。2026-08-29。
**原則を知らないレビュアには「書いてあることの矛盾」しか見えず、
「守るべきものを守っていない」が見えないから**）。画面に触れたなら
[21_画面の原則](../../../docs/21_画面の原則.md)、リサーチを足したなら
[32_調査のルール](../../../docs/32_調査のルール.md)——とくに §3「どこまで調べたかを必ず書く」。

### 3. 依頼文の雛形

**雛形は [依頼文の雛形.md](依頼文の雛形.md) の A にある。そのままコピーして `{}` を埋める。**
リポジトリのパスは**依頼文に直接書く**（サブエージェントは作業ディレクトリを引き継がない）。
ただし**この文書には絶対パスを書かない**（公開リポジトリ。[CLAUDE.md §5](../../../CLAUDE.md)）。

### 4. テスト観点には、必ず次のブロックを入れる

**カバレッジ 100% でも漏れる**ことは、実際に何度も起きている（[qa/03](../../../docs/qa/03_テストで漏らした実例.md)）。
設計・テストの依頼文には、次を**そのまま**入れる。

「往復」と「縮退」の 2 行は、実際にこれで重大な不具合が 2 件見つかったから入れている
（[qa/03](../../../docs/qa/03_テストで漏らした実例.md) の L-01・L-02・L-04）。

**入れるブロックは [依頼文の雛形.md](依頼文の雛形.md) の B にある。要約せず、そのまま入れる。**

### 5. 文書の観点には、必ず次の 6 つを立てる

**6 つは互いに独立なので、1 人 1 観点で投げる**（同時 3 人までなので波に分ける。6 観点なら 2 波）。
依頼文の「見てほしい観点」に、次のブロックを**そのまま**入れる。

**(1) 決定の重複** — 決定が二重管理されていて、片方が古くなる型

**(2) 制度記述とリサーチの不一致** — 調べた内容と設計文書がずれる型

**(3) 未決の決定化** — 保留が決定にすり替わる型

**(4) 記載の矛盾** — 単純に書いてあることが合っていない型（開発者の指示。2026-08-25）

**(5) 事実と判断の混在** — 何が確かめた事実で何が意見かが読み手に決まらない型（開発者の指示。2026-08-25）

**(6) 他者に通じる表現か** — Claude の中でだけ通じる言い回しが説明なしに使われる型（開発者の指示。2026-09-19・20。docs/00 §4-13）

**(5) は他の観点の土台である。** 事実と判断が混ざっていると、
(2) の「リサーチと食い違っていないか」も (3) の「未決が決定になっていないか」も判定できない。
[docs/11](../../../docs/11_消費税設計.md) の冒頭が
「制度そのものの説明と出典はリサーチにある。本書は**設計上の決定**だけを書く」と定めているのは
この分離のことである。

**(1) と (4) は似て見えるが、直し方が違うので分ける。**
(1) は「決定が 2 か所にある」構造の問題で、直すには**片方を消してリンクにする**。
(4) は「書いてあることが合っていない」事実の問題で、直すには**どちらが正しいかを決める**。
1 人にまとめて投げると、後者が前者に吸収されて見落とされる。

**(4) にどちらが正しいかを判断させない。** それは決定であって、レビュアの仕事ではない。

**(6) は lint がほとんど判定できない。** 形は正しいまま意味が通じないので、**読む人にしか見つからない**。
**規則を書いた回・用語を作った回は必ず立てる**（docs/00 §4-13）。

**6 つのブロックは [依頼文の雛形.md](依頼文の雛形.md) の C-1〜C-6 にある。要約せず、そのまま入れる。**

### 6. 指摘を取捨する

**レビューは意見であって仕様ではない。** そのまま全部反映しない。

- **目指す水準は対象で違う**（[30 §4-1](../../../docs/30_作業のルール.md)）。
  **[CLAUDE.md §2](../../../CLAUDE.md) の「会計ロジックの不具合の絶無を期す」ための仕組みは妥協せず 100%、
  それ以外は 70〜80%** である。
  **後者で「技術的には直せるが割に合わない」指摘は、直さずに字で残す**——
  **直した回数ではなく、残した判断が記録に要る**
- **直す → レビューし直す → また直す、を無条件に繰り返さない。** 波を重ねるほど指摘は細かくなる。
  **次の波を回すかは、上の水準に照らして決める**
- **複数のレビュアが独立に挙げたもの（★）は特に信用できる。** 優先して直す
- **重大な指摘は、直す前に裏を取る**（SQL で実データを見る・実機で再現する）。
  レビュアも誤読する。実例: 「原仕訳の候補が 50 件までで古い伝票を選べない」という指摘は、
  実際には候補ダイアログに検索条件が付いていて選べた（qa/02 R3-07）
- **とくに「因果」の主張は `git log -S` / `git log -p` で当たってから採る。**
  「A が B に期限を預けていた」「C を書き直したときに落ちた」「以前は X だった」の型である。
  **行番号が付いていても裏取りにはならない**——それは「その行にそう書いてある」しか保証しない。
  **当たらない主張を規則の実例に使わない**（実際に、裏を取らずに採った因果を
  規約の正典へ実例として書き、同じ作り話を 3 か所へ複写した）
- 直す・直さない・後回しにする、を自分で決める
- 直したら[検証](../../../docs/31_検証のルール.md)（31 §1）をやり直す

### 7. 記録する

**後から理由を聞かれるものだけ**を [qa/02](../../../docs/qa/02_自己レビュー記録.md) が指す年月のファイルに書く。

- **直さないと決めたもの**（理由つき）
- **後回しにしたもの**（いつやるか。開発者に聞きたいことは明示する）
- 直した軽微な指摘は書かない。コミットが記録している

**新しく作り込んだ不具合とその見逃し方**は [qa/03](../../../docs/qa/03_テストで漏らした実例.md) に書く。
qa/02 が「レビューの採否」、qa/03 が「漏れの型」で、役割が違う。

**そして、再発防止の置き場を決める**——判定は [30 §9](../../../docs/30_作業のルール.md) が持つ。
**qa/02 に再発防止を書いて終わりにしない。** qa/02 には**行き先を指すだけ**にする。

**その回に Claude のメモリへ書いたことがあれば、ここで行き先を決める**
（規則は [30 §9-1](../../../docs/30_作業のルール.md)）。

### 8. 機械で守れないかを考える

**qa/03 に 1 件増えたら、それを機械で守れないか毎回考える。**
守れたら qa/03 から「機械で守れるようにしたもの」の表に移す。
**カタログが短くなっていくのが健全な状態**である。

- 規約テスト（`Conventions/`）で守れないか
- DDL の制約・トリガで守れないか（アプリを迂回しても効く）
- フィクスチャの既定値を安全側にすることで消せないか
- 型で表現不能にできないか

### 9. 検査（lint・規約テスト・計器）を作った回は、その検査をレビューに掛ける

**壊れた検査は赤で止まらない。** 壊れた lint は「違反 0 件」、壊れた計器は「生き残り 0 件」と言う——
**赤で止まらないので、流した本人には分からない**（2026-09-13 の制約ノックアウトで実際に起きた。
初回の報告は**トリガ 54 点のうち 38 点ぶん水増し**されていた。[qa/02 のラウンド 88](../../../docs/qa/02_自己レビュー記録/2026-09.md)）。

**検査を足した回は、次の 6 つを観点として立てる。**

1. **この検査が「最良の報告」を返す経路を数える。** ビルド失敗・対象 0 件・フィルタの綴り違い・
   例外で全件終了——**どれも「問題なし」に倒れないか**
2. **除外表・許可表は両側から守っているか。** 「書いた名前が実在するか」だけでは、
   **書き忘れは 1 件も見つからない**。**逆向き**（表に無いのに除外されるべきものがある）を検査する
3. **対照実験があるか。** **何も壊していない状態で緑になること**を、その道具自身が毎回確かめているか
4. **表明が、検査対象と同じ定数から作られていないか。**
   定数を自分自身と比べる表明は、**その定数を壊すと期待値も一緒に壊れて釣り合う**。
   **言ってほしい字面そのものを検体に書く**（2026-09-15 に 3 つの道具で独立に踏んだ。
   [qa/02 のラウンド 98・102・103](../../../docs/qa/02_自己レビュー記録/2026-09.md)）
5. **「報告」も検体に入っているか。** 判定の関数をどれだけ厳しく当てても、
   **印字する側がそれを捨てれば誰も気づかない**。
   **入口（`main`）を純関数に割り、終了コードと出る行を固定する**（同 ラウンド 103）
6. **母数を「数」で釘付けしない。「どの組か」を字で書く**（Claude の判断。2026-09-16。
   **3 回続けて同じところで破られた**——[qa/02 のラウンド 115・116・117](../../../docs/qa/02_自己レビュー記録/2026-09.md)。
   0 判定・「1 件」・「4 件」と強くしても、**別の数え方で同じ数になる書き換えが毎回通った**）。
   **書くのは「本番で見ている組の一覧」そのもの**で、**違反があっても数が変わらないこと**と
   **入力が空なら 0 になること**まで見る。**赤くなりようのない組は、母数に混ぜない**
   ——混ぜると、赤くなりうる組が全部消えても沈黙する。
   **その字は「撃とうとした名前」ではなく「通った表明」から作る**（2026-09-22。[qa/02 のラウンド 145](../../../docs/qa/02_自己レビュー記録/2026-09.md)）
   ——名前を先に積むと、**検体の中身を別物に差し替えても一覧が変わらない**（レビュアが実測した）

**否定の検体は「別の理由で同じ結果になる」形に気をつける**——
通っていても、守りたいものを守っていないことがある。

## 10. 同じ規則を別の対象へ広げた回は、前の回の指摘を**検体ごと**写す

**実装は「同じ形にする」と意識して写すのに、検体は新しく書き下ろしてしまう。**
その結果、**前の回に★重大として直した穴が、新しい検体でそのまま再発する**
（Claude の判断。2026-09-16。[qa/02 のラウンド 119](../../../docs/qa/02_自己レビュー記録/2026-09.md)——
ラウンド 118 で直した 2 つが、規則を 3 つのマスタへ広げた翌回にそろって再発した。
[qa/03 の L-54](../../../docs/qa/03_テストで漏らした実例.md)）。

- **前の回の qa/02 のラウンドを開き、★重大の検体を 1 つずつ写す。**
  カバレッジもミューテーションも鳴らない——**変異が検体の穴と同じ向きに書かれる**からである
- **変異には「前の回に却下された実装」も入れる**（「まとめる鍵を違反コードにする」など）。
  実装を壊す向きだけを書くと、却下された形は撃てない
- **フィクスチャの「2 つ目」には、なぜ 2 つ要るのかを書く**——書いていないと、次の回に読んでも分からない

## やらないこと

- **1 人のレビュアに全観点を投げる**（観点が薄まる）
- **観点を削って同時実行の上限に合わせる**（上限は同時実行の話。観点は波に分けて全部流す）
- **4 人以上を同時に走らせる**（上限は [30 §6](../../../docs/30_作業のルール.md)）
- **文書だけの変更だからとレビューを省く**（lint は書いてある内容の矛盾を見ない）
- **書き込めるエージェントにレビューさせる**（レビューと修正を混ぜない）
- **指摘を全部反映する**（レビューは意見）
- **重大指摘を裏取りなしで直す**（誤指摘に合わせてコードを壊すことがある）
