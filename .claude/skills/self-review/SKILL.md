# 自己レビュー

**「別の目で見る」ことには予想以上の価値がある**（開発者の指示。2026-08-24）。
自分が書いた直後のコードは、書いた本人には正しく見える。

このスキルは [CLAUDE.md](../../../CLAUDE.md) §3-2-1 の工程を実行するためのもの。
**まとまった実装の区切りごとに必ず通す。** 省かない。

## 手順

### 1. レビュー対象を決める

`git log --oneline main..HEAD` で、このブランチで何をしたかを確認する。
**変更したファイルを列挙する。** 対象が曖昧だとレビューも曖昧になる。

### 2. 2 人に投げる（同時 2 人まで）

`Plan` エージェント（**書き込めない**）を使う。修正は自分で行う。
**1 人に「全部見て」と頼まない。** 観点を分けることに意味がある。

観点の組み合わせは、その実装で**壊れたら困るもの**から選ぶ。定番は次の 2 つ。

| 観点 | 何を見せるか |
|---|---|
| **会計ドメインと帳簿** | 不変条件・制度要件・帳簿としての整合。`docs/04`・`docs/06`・`docs/research/`・DDL |
| **設計とテスト** | 依存の向き・責務・**テストの十分性**。`docs/decisions/`・テストコード |

ほかに、必要に応じて「CLB と DB の静かな失敗」「公開前の混入」。

### 3. 依頼文の雛形

**そのままコピーして、`{}` を埋める。** とくに末尾の 3 点は毎回入れる。
リポジトリのパスは**依頼文に直接書く**（サブエージェントは作業ディレクトリを引き継がない）。
ただし**この文書には絶対パスを書かない**（公開リポジトリ。CLAUDE.md §5）。

```
あなたは{専門}に厳しいレビュアです。**読むだけで、ファイルを一切変更しないでください。**

リポジトリ: {リポジトリのルートの絶対パス}（ブランチ `{ブランチ}`）

## レビュー対象
`git log --oneline main..HEAD` の {N} コミット。{何をしたか 1 行}。
- {変更したファイルを列挙}

## 前提として読むもの
- {関連する ADR・設計文書・リサーチ}

## 見てほしい観点（これだけに集中）
1. {観点 1}
2. {観点 2}
...

## 出力の形式
**重大度順**に `[重大] / [中] / [軽微]` で列挙し、ファイル名と行を必ず添えてください。
各項目は「何が・どこで・なぜ問題か・どう直すべきか」を 3〜5 行で。
**一般論ではなく実際のコードを根拠に。** 良い点の列挙は不要です。
```

### 4. テスト観点には、必ずこの 3 つを入れる

**カバレッジ 100% でも漏れる**ことは、実際に何度も起きている（[qa/03](../../../docs/qa/03_テストで漏らした実例.md)）。
設計・テストの依頼文には、次を**そのまま**入れる。

```
2. **テストが十分か。カバレッジ 100% に騙されていないか。** 具体的に:
   - 通っているが**何も表明していない**テスト、表明が弱いテスト
   - **カバレッジを埋めるためだけ**に見えるテスト（ADR-0012 が禁止）
   - 抜けている重要なケース（境界・異常系・往復・並行）
   - **書いた値が読み戻せることを検査しているか**（NULL のまま通っていないか）
   - **テストデータが縮退していないか**（区別すべき 2 つが同じ値になっていないか）
   - テストの前提が本番と食い違っている箇所。フィクスチャが本番の配線を複製していないか
```

**この 4 行目と 5 行目は、実際にこれで重大な不具合が 2 件見つかったから入れている。**
[qa/03](../../../docs/qa/03_テストで漏らした実例.md) の L-01・L-02・L-04 がその実例。

### 5. 指摘を取捨する

**レビューは意見であって仕様ではない。** そのまま全部反映しない。

- **両方のレビュアが独立に挙げたもの（★）は特に信用できる。** 優先して直す
- 直す・直さない・後回しにする、を自分で決める
- 直したら[検証](../../../CLAUDE.md)（§4）をやり直す

### 6. 記録する

**後から理由を聞かれるものだけ**を [qa/02](../../../docs/qa/02_自己レビュー記録.md) に書く。

- **直さないと決めたもの**（理由つき）
- **後回しにしたもの**（いつやるか。開発者に聞きたいことは明示する）
- 直した軽微な指摘は書かない。コミットが記録している

**新しく作り込んだ不具合とその見逃し方**は [qa/03](../../../docs/qa/03_テストで漏らした実例.md) に書く。
qa/02 が「レビューの採否」、qa/03 が「漏れの型」で、役割が違う。

### 7. 機械で守れないかを考える

**qa/03 に 1 件増えたら、それを機械で守れないか毎回考える。**
守れたら qa/03 から「機械で守れるようにしたもの」の表に移す。
**カタログが短くなっていくのが健全な状態**である。

- 規約テスト（`Conventions/`）で守れないか
- DDL の制約・トリガで守れないか（アプリを迂回しても効く）
- フィクスチャの既定値を安全側にすることで消せないか
- 型で表現不能にできないか

## やらないこと

- **1 人のレビュアに全観点を投げる**（観点が薄まる）
- **3 人以上を同時に走らせる**（トークン上限。波に分けて 2 人ずつ）
- **書き込めるエージェントにレビューさせる**（レビューと修正を混ぜない）
- **指摘を全部反映する**（レビューは意見）
