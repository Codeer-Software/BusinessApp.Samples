# 自己レビュー

**「別の目で見る」ことには予想以上の価値がある**（開発者の指示。2026-08-24）。
自分が書いた直後のコードは、書いた本人には正しく見える。

このスキルは [CLAUDE.md](../../../CLAUDE.md) §3-2-1 の工程を実行するためのもの。
**まとまった実装の区切りごとに必ず通す。** 省かない。

**コードだけの話ではない。ADR・設計文書・リサーチの追加と変更も、マージ前にこの工程を通す。**
`designcheck` も `lint_docs.py` も**書いてある内容の矛盾は見ない**（見るのはフロントマター・
リンク・日付という「形」だけ）。**文書の中身を守るのは人の目しかない。**

## 手順

### 0. テストが緑であることを確かめてから始める

レビューは「動くもの」に対して行う。壊れている状態でレビューを頼むと、
指摘が「壊れている」に集中して、本当に見てほしい観点が薄まる。

### 1. レビュー対象を決める

`git log --oneline main..HEAD` で、このブランチで何をしたかを確認する。
**変更したファイルを列挙する。** 対象が曖昧だとレビューも曖昧になる。

差分ではなく**既にあるもの全部**を洗うとき（文書の一括レビューなど）は、
対象を「`docs/` 配下の全文書と `CLAUDE.md`」のように**範囲で**書き、
**全部読むこと**を依頼文に明記する。目次だけ見て答えられると意味が無い。

### 2. 観点を分けて投げる

`Plan` エージェント（**書き込めない**）を使う。修正は自分で行う。
**1 人に「全部見て」と頼まない。1 人 1 観点。**

**観点はレビュー対象に対して必要なだけ立てる**（2 つに限らない）。
ただし**同時に走らせるのは 2 人まで**（トークン上限。開発者の許可があるときだけ増やす）。
3 観点以上あるときは**波に分けて 2 人ずつ**流す。観点を削って人数を合わせない。

観点は、その実装で**壊れたら困るもの**から選ぶ。

| 観点 | 何を見せるか | いつ立てるか |
|---|---|---|
| **会計ドメインと帳簿** | 不変条件・制度要件・帳簿としての整合。`docs/04`・`docs/06`・`docs/research/`・DDL | 会計ロジックに触れたら必ず |
| **設計とテスト** | 依存の向き・責務・**テストの十分性**。`docs/decisions/`・テストコード | コードに触れたら必ず |
| **CLB と DB の静かな失敗** | `qa/01` の型に当てはまる形が新たにないか。デザイン JSON・スクリプト・SQL | CLB デザインや SQL に触れたら |
| **公開前の混入** | 絶対パス・秘密・ライセンス未確認の資産（CLAUDE.md §5） | 公開・マージの前 |
| **文書の整合** | 複数の文書・複数の箇所で内容が食い違っていないか。`docs/00_ドキュメント規約.md`・`docs/README.md`（索引と保留リスト）・`docs/research/` | **ADR・設計文書・リサーチを足したり直したりしたら必ず** |

### 3. 依頼文の雛形

**そのままコピーして、`{}` を埋める。**
リポジトリのパスは**依頼文に直接書く**（サブエージェントは作業ディレクトリを引き継がない）。
ただし**この文書には絶対パスを書かない**（公開リポジトリ。CLAUDE.md §5）。

```
あなたは{専門}に厳しいレビュアです。**読むだけで、ファイルを一切変更しないでください。**

リポジトリ: {リポジトリのルートの絶対パス}（ブランチ `{ブランチ}`）

## レビュー対象
`git log --oneline main..HEAD` の {N} コミット。{何をしたか 1 行}。
- {変更したファイルを列挙}

## 前提として読むもの
- {関連する ADR・設計文書・リサーチ}
- docs/qa/01_CLB静かな失敗.md（実際に踏んだ CLB の穴）
- docs/qa/03_テストで漏らした実例.md（過去に見逃した形。同じ形を探してほしい）

## 見てほしい観点（これだけに集中）
1. {観点 1}
2. {観点 2}
...

## 出力の形式
**重大度順**に `[重大] / [中] / [軽微]` で列挙し、ファイル名と行を必ず添えてください。
各項目は「何が・どこで・なぜ問題か・どう直すべきか」を 3〜5 行で。
**一般論ではなく実際のコードを根拠に。** 良い点の列挙は不要です。
```

### 4. テスト観点には、必ず次のブロックを入れる

**カバレッジ 100% でも漏れる**ことは、実際に何度も起きている（[qa/03](../../../docs/qa/03_テストで漏らした実例.md)）。
設計・テストの依頼文には、次を**そのまま**入れる。

```
2. **テストが十分か。カバレッジ 100% に騙されていないか。** 具体的に:
   - 通っているが**何も表明していない**テスト、表明が弱いテスト
   - **カバレッジを埋めるためだけ**に見えるテスト（ADR-0012 が禁止）
   - 抜けている重要なケース（境界・異常系・往復・並行）
   - **書いた値が読み戻せることを検査しているか**（NULL のまま通っていないか）
   - **テストデータが縮退していないか**（区別すべき 2 つが同じ値になっていないか）
   - テストの前提が本番と食い違っている箇所。フィクスチャが本番の配線を複製していないか
```

「往復」と「縮退」の 2 行は、実際にこれで重大な不具合が 2 件見つかったから入れている
（[qa/03](../../../docs/qa/03_テストで漏らした実例.md) の L-01・L-02・L-04）。

### 5. 文書の観点には、必ず次の 5 つを立てる

**5 つは互いに独立なので、1 人 1 観点で投げる**（同時 2 人までなので波に分ける。5 観点なら 3 波）。
依頼文の「見てほしい観点」に、次のブロックを**そのまま**入れる。

**(1) 決定の重複** — 決定が二重管理されていて、片方が古くなる型

```
1. **同じ決定が複数の文書に書かれ、片方が古くなっていないか。**
   - ADR や設計文書が、他の文書の決定を「再掲」している箇所（リンクで済むはずのもの）
   - 決定の本体がどこにあるか、読者に決まらない箇所
   - 再掲の片方だけが更新されて食い違っている箇所
   規約は docs/00 §4-6「同じ事実を 2 箇所に書かない」。
```

**(2) 制度記述とリサーチの不一致** — 調べた内容と設計文書がずれる型

```
2. **設計文書の制度の書きぶりが `docs/research/` と食い違っていないか。**
   - 税率・控除割合・閾値・金額・期限・適用開始日
   - 制度の適用範囲（誰に・いつから・いくらまで・何を除くか）
   - リサーチの「未確認・要追跡事項」に載っているのに、設計文書が断定している箇所
   - 出典 URL と確認日が無い制度記述（docs/00 §4-9）
```

**(3) 未決の決定化** — 保留が決定にすり替わる型

```
3. **保留のはずのものが、決定として書かれていないか。**
   - docs/README.md や各文書の保留リストに載っている項目が、別の文書では断定形で書かれている
   - ADR の「決定」に、開発者の承認を得ていない内容が混ざっている
   - その断定を前提にして、後続の文書が組み立てられている連鎖
```

**(4) 記載の矛盾** — 単純に書いてあることが合っていない型（開発者の指示。2026-08-25）

```
4. **複数の文書、または同じ文書の複数の箇所で、内容が食い違っていないか。**
   決定に限らない。「書いてあることが単純に合っていない」箇所を探してほしい。
   - 数値・範囲・条件・日付
   - 表と本文、表と表
   - 用語（ADR-0017 の呼び分け、docs/00 §4-7 の「ユーザー」「開発者」）
   - 章番号・見出し番号の重複や欠番、他文書からの参照先のずれ
   - スコープの記述（docs/03 が決めた範囲と、他の文書が前提にしている範囲）

   **どちらが正しいかは判断しないでください。** 食い違っている 2 箇所を並べて示すところまでで結構です。
```

**(5) 事実と判断の混在** — 何が確かめた事実で何が意見かが読み手に決まらない型（開発者の指示。2026-08-25）

```
5. **事実と、それ以外（判断・推測・提案）が明確に分かれているか。**
   - 一次情報で確認した事実と、そこから導いた判断が、地の文で混ざっている箇所
   - 出典のない断定（「〜である」と書かれているが、根拠がどこにも無い）
   - 「〜と思われる」「〜のはず」で書いた推測が、別の文書では事実として扱われている
   - 市販ソフトの仕様（事実）と、それに合わせる／合わせないの判断が区別されていない箇所
   - リサーチ文書に判断が混ざっている／設計文書に未検証の制度記述が混ざっている
   規約は docs/00 §4-9（制度・法令の記述には出典と確認日を付ける）。
```

**(5) は他の 4 つの土台である。** 事実と判断が混ざっていると、
(2) の「リサーチと食い違っていないか」も (3) の「未決が決定になっていないか」も判定できない。
[docs/06](../../../docs/06_消費税設計.md) の冒頭が
「制度そのものの説明と出典はリサーチにある。本書は**設計上の決定**だけを書く」と定めているのは
この分離のことである。

**(1) と (4) は似て見えるが、直し方が違うので分ける。**
(1) は「決定が 2 か所にある」構造の問題で、直すには**片方を消してリンクにする**。
(4) は「書いてあることが合っていない」事実の問題で、直すには**どちらが正しいかを決める**。
1 人にまとめて投げると、後者が前者に吸収されて見落とされる。

**(4) にどちらが正しいかを判断させない。** それは決定であって、レビュアの仕事ではない。

### 6. 指摘を取捨する

**レビューは意見であって仕様ではない。** そのまま全部反映しない。

- **複数のレビュアが独立に挙げたもの（★）は特に信用できる。** 優先して直す
- **重大な指摘は、直す前に裏を取る**（SQL で実データを見る・実機で再現する）。
  レビュアも誤読する。実例: 「原仕訳の候補が 50 件までで古い伝票を選べない」という指摘は、
  実際には候補ダイアログに検索条件が付いていて選べた（qa/02 R3-07）
- 直す・直さない・後回しにする、を自分で決める
- 直したら[検証](../../../CLAUDE.md)（§4）をやり直す

### 7. 記録する

**後から理由を聞かれるものだけ**を [qa/02](../../../docs/qa/02_自己レビュー記録.md) に書く。

- **直さないと決めたもの**（理由つき）
- **後回しにしたもの**（いつやるか。開発者に聞きたいことは明示する）
- 直した軽微な指摘は書かない。コミットが記録している

**新しく作り込んだ不具合とその見逃し方**は [qa/03](../../../docs/qa/03_テストで漏らした実例.md) に書く。
qa/02 が「レビューの採否」、qa/03 が「漏れの型」で、役割が違う。

### 8. 機械で守れないかを考える

**qa/03 に 1 件増えたら、それを機械で守れないか毎回考える。**
守れたら qa/03 から「機械で守れるようにしたもの」の表に移す。
**カタログが短くなっていくのが健全な状態**である。

- 規約テスト（`Conventions/`）で守れないか
- DDL の制約・トリガで守れないか（アプリを迂回しても効く）
- フィクスチャの既定値を安全側にすることで消せないか
- 型で表現不能にできないか

## やらないこと

- **1 人のレビュアに全観点を投げる**（観点が薄まる）
- **観点を削って同時実行の上限に合わせる**（上限は同時実行の話。観点は波に分けて全部流す）
- **3 人以上を同時に走らせる**（トークン上限。開発者の許可があるときだけ）
- **文書だけの変更だからとレビューを省く**（lint は書いてある内容の矛盾を見ない）
- **書き込めるエージェントにレビューさせる**（レビューと修正を混ぜない）
- **指摘を全部反映する**（レビューは意見）
- **重大指摘を裏取りなしで直す**（誤指摘に合わせてコードを壊すことがある）
