# 依頼文の雛形と、そのまま入れるブロック

> **[`self-review` スキル](SKILL.md)が貼る文面だけを置く。**
> **どれをいつ使うか・なぜそのまま入れるかは SKILL.md の §3〜§5 が持つ。**
> **ここに規則も理由も書き足さない**——書くと同じことが 2 か所になり、片方が古くなる
> （[00 §4-6](../../../docs/00_ドキュメント規約/本文.md)）。
> 見出しに番号を使わないのは、`§3` が SKILL.md の節だけを指すようにするためである。

## A. 依頼文

```
あなたは{専門}に厳しいレビュアです。**読むだけで、ファイルを一切変更しないでください。**

リポジトリ: {リポジトリのルートの絶対パス}（ブランチ `{ブランチ}`）

## レビュー対象
`git log --oneline main..HEAD` の {N} コミット。{何をしたか 1 行}。
- {変更したファイルを列挙}

## 前提として読むもの
- {関連する ADR・設計文書・リサーチ}
- {画面・文言に触れたなら docs/21_画面の原則.md／リサーチを足したなら docs/32_調査のルール.md}
- docs/qa/01_CLB静かな失敗.md（実際に踏んだ CLB の穴）
- docs/qa/03_テストで漏らした実例.md（過去に見逃した形。同じ形を探してほしい）

## 見てほしい観点（これだけに集中）
1. {観点 1}
2. {観点 2}
...

## 出力の形式
**重大度順**に `[重大] / [中] / [軽微]` で列挙し、ファイル名と行を必ず添えてください。
各項目は「何が・どこで・なぜ問題か・どう直すべきか」を 3〜5 行で。
**一般論ではなく実際のコードを根拠に。** 良い点の列挙は不要です。
```

## B. テスト観点

```
2. **テストが十分か。カバレッジ 100% に騙されていないか。** 具体的に:
   - 通っているが**何も表明していない**テスト、表明が弱いテスト
   - **カバレッジを埋めるためだけ**に見えるテスト（ADR-0012 が禁止）
   - 抜けている重要なケース（境界・異常系・往復・並行）
   - **書いた値が読み戻せることを検査しているか**（NULL のまま通っていないか）
   - **テストデータが縮退していないか**（区別すべき 2 つが同じ値になっていないか）
   - テストの前提が本番と食い違っている箇所。フィクスチャが本番の配線を複製していないか
```

## C-1. 決定の重複

```
1. **同じ決定が複数の文書に書かれ、片方が古くなっていないか。**
   - ADR や設計文書が、他の文書の決定を「再掲」している箇所（リンクで済むはずのもの）
   - 決定の本体がどこにあるか、読者に決まらない箇所
   - 再掲の片方だけが更新されて食い違っている箇所
   規約は docs/00 §4-6「同じ事実を 2 箇所に書かない」。
```

## C-2. 制度記述とリサーチの不一致

```
2. **設計文書の制度の書きぶりが `docs/research/` と食い違っていないか。**
   - 税率・控除割合・閾値・金額・期限・適用開始日
   - 制度の適用範囲（誰に・いつから・いくらまで・何を除くか）
   - リサーチの「未確認・要追跡事項」に載っているのに、設計文書が断定している箇所
   - 出典 URL と確認日が無い制度記述（docs/00 §4-9）
```

## C-3. 未決の決定化

```
3. **保留のはずのものが、決定として書かれていないか。**
   - docs/README.md や各文書の保留リストに載っている項目が、別の文書では断定形で書かれている
   - ADR の「決定」に、開発者の承認を得ていない内容が混ざっている
   - その断定を前提にして、後続の文書が組み立てられている連鎖
```

## C-4. 記載の矛盾

```
4. **複数の文書、または同じ文書の複数の箇所で、内容が食い違っていないか。**
   決定に限らない。「書いてあることが単純に合っていない」箇所を探してほしい。
   - 数値・範囲・条件・日付
   - 表と本文、表と表
   - 用語（ADR-0017 の呼び分け、docs/00 §4-7 の 4 語——利用者・開発者・Claude・CLB 開発元）
   - 章番号・見出し番号の**重複**、他文書からの参照先のずれ
   - **`削除` が置かれた欠番は正常**（docs/00 §4-12）。指摘しない。
     **番号が飛んでいるのに `削除` が無いもの**は、**その番号を指す参照が他にあるときだけ**挙げる
     （番号を振らずに書いてきた文書は昔からあるので、欠番それ自体は欠陥ではない）
   - スコープの記述（docs/03 が決めた範囲と、他の文書が前提にしている範囲）

   **どちらが正しいかは判断しないでください。** 食い違っている 2 箇所を並べて示すところまでで結構です。
```

## C-5. 事実と判断の混在

```
5. **事実と、それ以外（判断・推測・提案）が明確に分かれているか。**
   - 一次情報で確認した事実と、そこから導いた判断が、地の文で混ざっている箇所
   - 出典のない断定（「〜である」と書かれているが、根拠がどこにも無い）
   - 「〜と思われる」「〜のはず」で書いた推測が、別の文書では事実として扱われている
   - 市販ソフトの仕様（事実）と、それに合わせる／合わせないの判断が区別されていない箇所
   - リサーチ文書に判断が混ざっている／設計文書に未検証の制度記述が混ざっている
   規約は docs/00 §4-9（制度・法令の記述には出典と確認日を付ける）。
```

## C-6. 他者に通じる表現か

```
6. **他者が読んで、同じ意味に解釈できない表現が無いか。**
   ここでいう他者とは、このリポジトリを参照する人々（一般的な意味でのソフトウェア開発者）である。
   - このリポジトリの中だけで意味を持つ言葉が、説明なしに使われている箇所
     （例: 「保護対象」「語彙」「関門」——初めて出てくる場所に 1 行の説明があるか）
   - 日常語を辞書と違う意味で使っている箇所（例: 撤退の意味の「引く」）
   - 隠れた前提や文脈を伴う表現（前提を共有していない人には別の意味に読める箇所）
   - 見出しの比喩・省略（見出しだけを読んで何の話か分からないもの）
   - 「それが何か」を書かず、リンク先に意味を預けている箇所
   次の範囲にある用語は指摘しない（一義的なので避ける必要が無い。docs/00 §4-13 の表）。
     CLB: Designer/ClaudeCodeForDesigner/ の仕様リファレンスが定義している語
     法令・税制: 法学・税制の教科書、e-Gov、官公庁公式サイトで引ける語
     会計・簿記: 一般的な簿記の教科書で引ける語
     ASP.NET・C#: Microsoft の公式リファレンスで引ける語
   規約は docs/00 §4-13。
```
