## 1. 置き場

### 1-1. 層は 4 つ、置き場は 3 つ

| 層 | 責務 | 見分け方 | 置き場 |
|---|---|---|---|
| **ドメイン** | 型・不変条件・検証・計算 | DB も時計も認証も要らずに書ける | `BusinessApp.AccountingCore` |
| **アプリケーション** | 業務の流れ。ドメインとインフラを順に使い、**何を断るかを判定する** | 会計の規則を知っている | `AccountingCore.Server` の `<機能>/Application/` |
| **インフラ** | 永続化・外部との通信。**DB の読み書きはここ** | **SQL を書く** | 同 `<機能>/Infrastructure/` |
| **プレゼンテーション** | API・保存の入口・入力の正規化・枠組みの言葉の置き換え・**断りを見せる順序** | 外の世界（HTTP・CLB・画面）の形式を知っている | **CLB の画面**と、同 `<機能>/Presentation/` |

**いちばん大切なのはドメイン層の純粋性である**（開発者。[ADR-0050](decisions/0050-会計コアの層はドメイン・アプリケーション・インフラ・プレゼンテーションの4つで読み機能フォルダの下で分ける.md)）。
アプリケーション層のためのプロジェクトは作らない——**同じプロジェクトに置き、フォルダで分ける**。

### 1-2. プロジェクト

**取引先部品（`BusinessApp.Partners*`）の構成は [13 §0](13_取引先設計.md) が、
テストと道具のプロジェクトは [ADR-0012](decisions/0012-テスト方針とカバレッジのゲート.md) が持つ**（ここには書かない）。

| プロジェクト | 何を置くか | 参照してよい相手 |
|---|---|---|
| `BusinessApp.AccountingCore` | 会計コアのドメイン層 | **`BusinessApp.Partners` ただ 1 本。NuGet ゼロ** |
| `BusinessApp.AccountingCore.Server` | 会計コアのアプリケーション・インフラ・サーバ側プレゼンテーション | `AccountingCore`・取引先部品・`ServerSupport`・CLB |
| `BusinessApp.AccountingCore.Client` | CLB スクリプトへ登録するサービス（**いま 0 ファイル**。下） | `AccountingCore` |
| `BusinessApp.ServerSupport` | 会計でも取引先でもない、この DB と関門の作法 | **なし**（NuGet も参照もゼロ） |
| `BusinessApp.Server` | **HTTP の殻**（`Controllers/`）と **CLB の配線**（`Services/`）。ASP.NET Core のホスト | `AccountingCore.Server`・`BusinessApp.Client` |
| `BusinessApp.Client` / `.Client.Shared` | Blazor WASM のホスト。CLB の起動と、Extras のサービス・エンドポイント URL の一元定義 | `.Client` → `.Client.Shared`。会計コアは参照しない |

- **`ServerSupport` が何を持つかは、その csproj の冒頭のコメントが数える**（ここに写さない）。
  **先回りの共通化をしない**——2 つ以上の部品が実際に使うものだけをここへ出す
- **`BusinessApp.Server` と `BusinessApp.Client` は CLB テンプレート由来で、カバレッジにも
  ミューテーションにも載らない**（[ADR-0012 §3](decisions/0012-テスト方針とカバレッジのゲート.md) の `Include` の外）。
  **ここに書いた行は誰にも検査されない。** だから殻と配線だけを置き、判断は `AccountingCore.Server` へ押し戻す
- **`AccountingCore.Client` には、いま 1 ファイルも無い。** CLB スクリプトから**自前のサーバ処理**を
  呼ぶ経路は Extras の `WebApiService.Post`（§4）ただ 1 つで、**クライアント側で `AccountingCore` を
  呼ぶ実装はまだ 1 本も無い**（WASM にも載っていない）。§3 の 1 行目の規則が、まだ一度も試されていないためである

### 1-3. フォルダは機能が先、層が後

- **サーバ層**は `AccountingCore.Server/<機能>/<層>/`（例 `Journals/Application/JournalPoster.cs`）。
  **ちょうど 3 段**で、**層フォルダの直下にファイルを置く**（`Journals/Application/Amendments/X.cs` は赤になる）。
  機能をまたぐものは `Shared/<層>/`。**層を先にしない**——機能フォルダの最初の名前で判定する
  サーバ層の `ModuleDependencyTests` を壊すからである
- **ドメイン層**は `AccountingCore/<機能>/`。**層フォルダを持たない**（全部が 1 つの層だから）。
  共有カーネルは `Shared/`。**ルート直下にソースを置かない**——依存の検査を素通りする
- **名前空間はフォルダに一致させる。** 違うと、同じ層のふりをして `using` 無しに別の層の型が使える
- **テストは鏡写しにする**（`TestLayoutConvention`）
- **この 2 つの規則が当たるのは会計コアの 2 プロジェクトだけである。**
  取引先部品と `ServerSupport` は平置きのまま（末尾の保留リスト）
- **CLB の `Design/Modules/` のトップレベルは「アプリ（部品）」である**——書き方は
  [`../Designer/Project.md`](../Designer/Project.md) のフォルダ規約が持つ

**機能を 1 つ足すときの順序**——①ドメイン層の `ModuleDependencyTests` の表に行を足し、
②`AccountingCore/<機能>/` を作る（**表とフォルダは相等比較なので、①②は 1 コミットで揃える**）。
③サーバ層に `<機能>/<層>/` を作る。**その機能が取引先部品を名指しするなら、
サーバ層の `ModuleDependencyTests` の表にも理由つきで足す**（使わなくなったら消す。残すと赤になる）。
④テストを鏡写しに置く。

## 2. どの層に置くか

**§1-1 の表を上から当てて、最初に当たったところへ置く。**

### 2-1. 保存の関門は 2 種類に割れる

**形式の検査ならプレゼンテーション、業務の判定ならアプリケーション**
（開発者の直感を当てはめたもの。[ADR-0050](decisions/0050-会計コアの層はドメイン・アプリケーション・インフラ・プレゼンテーションの4つで読み機能フォルダの下で分ける.md) の決定 5）。

| 関門 | 見ているもの | 層 |
|---|---|---|
| `AccountingSubmitPipeline` | CLB の保存に関門をつなぐ入口（組み立て） | Presentation |
| `BlankTextNormalizer` | 空文字を NULL に寄せる（入力の正規化） | Presentation |
| `SaveFailureMessage` | 枠組みの言葉を利用者の語に置き換える | Presentation |
| `JournalSubmitRequirements` | DDL が受け取れる形か（1 行で判定できる形式） | Application（`JournalSubmitGate` の中で呼ぶため） |
| `JournalSubmitGate`・`MasterSubmitGate`・`MasterMeaningGate`・`CompanyProfileSubmitGate` | 計上の検証・意味の凍結・コードの重複——**業務の判定** | Application |

**判定の知識そのものはドメインが持ち、関門はそれを当てるだけである。**
`JournalSubmitRequirements` が形式の検査なのに Application に居るのは、
Presentation に置くと Application → Presentation の逆流になるからである。

### 2-2. 迷いやすい置き場（実装で決めたもの）

| 置くもの | 層 | なぜ |
|---|---|---|
| 守る対象の記述子（`GuardedMaster`・`GuardedColumn`・`OneWayColumn`・`CodedMaster`・`CodedParent`） | Infrastructure | 表・列・呼び名を束ね、インフラの口が生の文字列を受けないための型 |
| **どのマスタを守るか・どのマスタがコードを持つかの一覧** | Application | **型はインフラ、一覧は業務の判定** |
| 差し戻しの例外（`JournalPostingRejectedException` ほか） | Application | 違反を全件運ぶのは、業務の判定の結果だから |
| `JournalDuplication`（純粋関数の会計補助） | Application | ドメインを借りて写す欄を決めるのは業務の流れの一部で、外の世界の形式に触れない |
| `LedgerSnapshotWriter` | Infrastructure（**明示された例外**） | 帳簿へ写す規則と利用者向けの断りを持つので、§1-1 の「DB を読み書きする側」に収まらない。**差し戻しの例外を投げず `Violation` を返す**（投げるのは `JournalPoster`）——Infrastructure が Application の例外型を知らないための形 |

### 2-3. CLB スクリプト（`*.mod.cs`）に置いてよいもの

**画面上の値の出し入れと、C# サービス・Web API の呼び出しだけ。**
金額計算・税額計算・状態遷移の判断を書かない（[ADR-0008](decisions/0008-CLBとCSharpライブラリの責務分担.md)）。

**本来なら画面が持つロジックも、テストできる `AccountingCore.Server` に置く**
（[ADR-0050](decisions/0050-会計コアの層はドメイン・アプリケーション・インフラ・プレゼンテーションの4つで読み機能フォルダの下で分ける.md) の決定 2）。
CLB スクリプトはツリーウォーク型インタプリタで静的検査が効かない、というのがこのプロジェクトの制約である。
**スクリプトに条件分岐と計算が増え始めたら、C# へ移すべきロジックが漏れているサインである。**

## 3. どこで実行するか

| 処理 | 実行場所 | 理由 |
|---|---|---|
| 1 伝票の検証・税額計算（入力中の即時フィードバック）<br>**規則だけ。まだ一度も当たっていない**（§1-2） | **クライアント**（`AccountingCore` を WASM に載せる） | 往復なしで応答する。同じライブラリなのでサーバと結果が一致する |
| 保存時の不変条件の強制 | **サーバ**（`AccountingSubmitPipeline`） | クライアントの制御は迂回できる。**最終の関門は必ずサーバ** |
| 保存に紐づかない、画面から呼ぶ処理（取消・訂正・複製） | **サーバ**（Web API。§4） | 1 操作を 1 トランザクションで包める |
| **明細を並べる帳簿**（行数が減らない） | **クエリモジュール**（SQL ＋ CLB 標準の一覧） | 降ろした先で送り返す形にならないので、往復の無駄が起きない |
| **集計帳票**（畳んで初めて意味が出る） | **サーバ完結**（Web API ＋ `AccountingCore`） | 明細を全件降ろすと件数に比例して重い。畳む規則が会計そのもの |
| 単純な一覧・検索 | **CLB 標準の一覧ページ**（`ListLayouts` / `SearchLayouts`） | CLB が最も得意とする領域。自前で作り直さない |

**「畳むか、畳まないか」が帳簿と帳票の境目である**（[ADR-0022](decisions/0022-明細を並べる帳簿はクエリモジュールで作る.md)）。
仕訳帳・総勘定元帳・補助元帳・税区分別の明細は前者、試算表・月次推移・B/S・P/L・税額集計は後者。
**集計帳票はまだ 1 本も無い。** 最初の 1 本はフェーズ 3 の税区分別集計表で、そのとき
[04 §5](04_実装計画と現在地.md) の未決事項「集計帳票の API の形」を決める。

### 3-1. 一覧の作り分け

**判断は 1 つである**——「一覧の中身が CRUD モジュールの素の姿と違うならクエリモジュール」
（[ADR-0027](decisions/0027-入力の一覧はラップモジュールとクエリモジュールで作る.md)）。
**違うなら、次は「一覧の周りに自分で画面を組むか」で分かれる。**

| 一覧の中身 | 作り方 | 実物 |
|---|---|---|
| 素の姿で足りる | CLB 標準の一覧ページ | マスタと設定の各画面 |
| 素の姿と違い、**検索欄やボタンを自分で並べたい** | **ラップモジュール**（表示専用・`DbTable` 空）**＋ クエリモジュール** | `JournalEntryBoard` ＋ `JournalEntryList` |
| 素の姿と違うが、**一覧をそのまま出せばよい** | **クエリモジュール単体**（フレームに直に登録するか、親の詳細に `ListField` で埋め込む） | `PartnerRegistrationList` |
| 明細 1 行 ＝ 1 レコードの帳簿 | **クエリモジュール** | `JournalBook`・`GeneralLedger` |

**ラップモジュールは PageFrame に `ModulePageType: "Detail"` で登録し**、詳細を担う CRUD モジュールは
同じフレームの `OtherPageModuleDesigns` に登録する（登録漏れは押した先が静かに真っ白になる。
**`lint_design.py` の F-17 がフレームのリンク・`AnchorTagField`・スクリプトの 3 経路で見ている**）。

### 3-2. 明細を並べる帳簿に置いてよい計算

**「表示のためのちょっとした加工」まで。** 行数が減らないものに限る——
相手勘定科目（複数なら「諸口」）と期間内累計がそれに当たる。
**畳む計算を SQL に書かない。**

## 4. 画面から呼ぶサーバ処理（Web API）

| 置き場 | 置くもの | 実物 |
|---|---|---|
| `*.mod.cs` | 呼んで、結果で画面を動かすだけ | `WebApiService.Post` → `NavigationService.NavigateTo` |
| `BusinessApp.Server/Controllers` | **HTTP の殻だけ。** 認証・経路・データソース名の解決 | `JournalsController` |
| `<機能>/Presentation/` | **入口。** 識別子の解釈・トランザクション・結果への写像・画面との受け渡しの型 | `JournalAmendmentEndpoint` |
| `<機能>/Application/` | 業務の手順（ドメインとインフラを順に使う） | `JournalAmendmentService` |
| `<機能>/Infrastructure/` | DB の読み書き | `JournalEntryStore` |
| `AccountingCore` | 会計の判断（純粋関数） | `JournalCorrection` |

**約束ごと**（[ADR-0016](decisions/0016-画面から呼ぶサーバ処理はWebAPIに置く.md)）

- **`[Authorize]` と `[AutoValidateAntiforgeryToken]` を必ず付ける**
- **トランザクションは入口（`<機能>/Presentation/`）が張る。** コントローラではない——
  そこは検査の外なので、**張っていることを誰も確かめられなくなる**
- **コントローラの本体は 1〜2 行に保つ。** 増えたら入口へ押し戻す
- **成否は HTTP の状態コードではなく、本文の `status`（`ok` / `rejected`）で表す。**
  業務の差し戻しは 200、想定外は 500。
  **CLB の `WebApiService` は 2xx 以外の応答本文を読めない**ので、400 で返すと差し戻しの理由が利用者に届かない
- **URL は `/api/<名詞の複数形>/<動詞>`**（`/api/journals/correct`）

## 5. 依存の向き

### 5-1. 部品のあいだ——会計コア → 取引先の一方通行

**規則の正典は [ADR-0029 §2](decisions/0029-所有は相手抜きで存在するかで導き粒度は決断で決める.md)**（相手抜きで存在するかで導く）。
**逆流を作らない。** C# はコンパイラが禁じ、両側から機械が見ている。
**CLB のモジュール参照にも同じ向きを当てる。**
**どのフォルダが取引先部品を名指ししてよいかは、サーバ層の `ModuleDependencyTests` が理由つきで持つ**
（一覧を文書に写さない。§6）。取り出すときの手順は [13 §0](13_取引先設計.md)。

### 5-2. 会計コアのモジュールのあいだ

**向きは「参照を持つ側が下位」になるように決める。** 逆向きは許可しない。
**機能どうしが双方向に参照したくなったら、それは共有カーネル（`Shared`）へ切り出す信号である**——
表に循環を書き足す選択肢は無い。

**許可の表そのものは `ModuleDependencyTests` が持つ。ここには写さない**——
写すと片方だけが直り、しかも**文書の表には検査が付かない**。あの表は
向き・実フォルダとの一致・循環の 3 つを同時に見ている（[ADR-0013](decisions/0013-機能単位のモジュール分割と依存方向.md) の決定 3）。

### 5-3. 層のあいだ

| から | へ | 可否 |
|---|---|---|
| Presentation | Application・Infrastructure・ドメイン | **可**。Infrastructure へは**組み立て・権限の関門・トランザクションの境界**のため（業務の判定は書かない） |
| Application | Infrastructure・ドメイン | **可**。**インフラの具象をそのまま使う**（インターフェースで反転しない） |
| Infrastructure | ドメイン | **可**。Application・Presentation は**参照しない** |
| Application | Presentation | **不可** |

**反転を入れないのは、置き換える相手がいないからである**（DB は SQLite 1 つ）。
**純粋ドメインにリポジトリのインターフェースを置かない**——必要なデータは呼び出し側が読んで渡す
（[ADR-0013](decisions/0013-機能単位のモジュール分割と依存方向.md) の決定 5）。
**渡す型も具象にする。** 同じ理由で MediatR・CQRS も入れない。

**層の名前の直後に `.` か `;` が続けば、コメントの中でも「参照」と数える**——
「呼ぶ」と書いたら呼んでいる、と扱う。**書き分けたいなら、層の名前を出さずに書く。**

## 6. 機械が見ているもの

**一覧をここに書かない。正典は検査のコードそのものである**（[21 §6](21_画面の原則.md) と同じ理由——
検査を足すたびに書き直すことになり、**しかも文書に書いた表には検査が付かない**）。
