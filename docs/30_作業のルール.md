# 作業のルール

> Claude が本リポジトリで作業するときの約束。**2026-09-06 に [CLAUDE.md](../CLAUDE.md) から切り出した**
> （最上位の指示書には「どうしても一番初めに読ませたいこと」だけを残す方針のため）。
> **§1 の「決め方」の表と §3 は、自律作業のときに効く**（[CLAUDE.md §0-5](../CLAUDE.md) で読み直す）。
> それ以外は、開発者が横にいる作業でも同じである。[CLAUDE.md §0-1](../CLAUDE.md) で常に読む。

## 1. 判断——自律と質問

- **原則として自律的に動き、仕様の意思決定まで自分で行う。** 判断に迷ったら、止めるより**根拠を ADR に残して前進する**
- ただし**後戻りコストの大きい根本設計・不可逆な操作・要件の重大な曖昧さ**は遠慮なく質問する
- **開発者が意見を問いかけてきたときは、回答のみ行い実装を始めない**（[CLAUDE.md §4](../CLAUDE.md)）

**選択肢が複数あるときの決め方**（実装・テスト・レビューのいずれでも同じ）

| 状況 | どうするか |
|---|---|
| 明らかにベストプラクティスが 1 つに定まる | **判断理由を残して選び、進む。** 聞かない |
| 正解が 1 つではない／開発者の意見を聞いたほうがよい | 聞く。ただし**聞く時期を選ぶ**（下 2 行） |
| ↳ 後から聞いても支障がない | **文書に保留として残し、まとめて聞く**（[00 §4-4](00_ドキュメント規約/本文.md) の保留リスト） |
| ↳ 後からだと手戻りが大きい／すぐ聞きたい | **手を止めてすぐ聞く** |

## 2. サイクル

1. **状態を読む** — [05_実装計画と現在地](05_実装計画と現在地.md) の「次にやること」
2. **設計する** — 該当する ADR とリサーチを確認する。CLB は `Docs/AppPatterns/` と `_samples/` を正典に複製する
3. **作る**
4. **検証する** — [31_検証のルール](31_検証のルール.md)
5. **自己レビューする** — §5。**まとまった実装の区切りごとに必ず入れる**
6. **記録する** — 現在地・ADR・仕様書を更新する。CLB の改善は [CLB改善提案](CLB改善提案/README.md) にその場で追記（発見日と CLB バージョン必須）
7. **コミットする** — §7

## 3. 3 回で引く

**同じ問題の修正に 3 回以上失敗し、かつ新しい手がかりが何も得られていないなら、そこで追うのをやめる。**
分かっていることを文書に残し、残りのタスクへ移り、後で開発者に報告する（開発者の指示。2026-08-24。
**環境側の問題は開発者が触ると解決することが多く、Claude が追い続けても時間だけが減るから**）。

- 判断の基準は回数ではなく**進展の有無**である。試すたびに新しい情報が出ているなら続けてよい。
  「同じところで同じように失敗している」なら止める
- **とくに CLB とブラウザ操作は、開発者が自分で触ると解決することがかなりある**（前回プロジェクトでも、
  拡張機能では動かないが手で操作すると動いた事例があった）。環境側の問題を延々と追わない
- 残すのは「何をしようとして、何が起きて、何を試したか」。次に誰が見ても同じ場所から始められる形にする

## 4. 最小修正ではなく、最善の修正——ゼロベースで考える

**修正するとき、既存のものを正として最小の差分を探す癖がある**（Claude に限らず AI 全般に）。
**その癖を疑い、ゼロベースで最善の形を考えて直す**（開発者の指示。2026-09-06。
**最小修正は既存の誤りを温存し、つぎはぎを重ねるほど後から直せなくなるから**）。
**前提は、不具合を作り込まないための検証が十分にあること**——[31](31_検証のルール.md) の関門が緑で、
自己レビュー（§5）を通す。守りがあるから大きく直せる。

**実例**（2026-09-05）。20 に「一時ファイル」「検証を育てる」の 2 節を置いたのは
「行き先が無いから」だった。**行き先を作る**という発想が無かった。翌日に 30・31 を起こして移した。

- 「今あるものをどう直すか」ではなく「**今から作るならどうするか**」を先に描き、差分はそのあとで取る
- 直す範囲を狭める理由が「壊すのが怖い」なら、**怖さの正体は検証の不足**である。検証を足してから直す
- ただし**開発者の決定をゼロベースの対象にしない**。決定を変えたいなら ADR で提案する（§1）

## 5. 自己レビュー（工程として省かない）

**手順・観点・依頼文の雛形は [`self-review` スキル](../.claude/skills/self-review/SKILL.md) が持つ。**
まとまった実装の区切りで、そのスキルを起動する。**文書だけの変更でも省かない**
（[CLAUDE.md §4](../CLAUDE.md)）。

## 6. サブエージェント

- **同時 2 人まで**（トークン上限。開発者の許可があるときだけ増やす）。3 人以上には**波に分けて 2 人ずつ**流す
- ブラウザ操作・大量ファイルの精読・SQL 結果の大量閲覧は積極的に委譲する
- 各サブエージェントには「自分が作ったタブ以外を触るな」を明記する
- ブラウザを 2 並列にするときは**同じ利用者アカウントで動かす台本を組み合わせる**（クッキー壺が 1 つのため）

## 7. Git

- **ブランチを切って作業する。** `main` に直接コミットしない（**止めるフックは無い**。文書で守る）
- ブランチ名は一般的な慣行に従う（`feat/...` `fix/...` `docs/...` `chore/...` `refactor/...`）
- コミットメッセージは **Conventional Commits**。意味のある単位で
- マージは **`--no-ff`**（Fast-Forward しない）
- **`git push` は行わない**（開発者が行う。`.claude/settings.json` の deny で機械的にも禁止している）
- コミット前フック（段の正典は [tools/README](../tools/README.md)）が緑でないコミットは作らない。`--no-verify` を使わない

## 8. 一時ファイル・一時フォルダを作らない

**作ると必ず消すことになり、削除のたびに開発者の確認で作業が止まる。** 作らない方法を先に探す。

- **DB の検査・投入**: `sql` CLI に `--query` を渡し、`--out` を省いて標準出力で受ける
  （PowerShell からは `ProcessStartInfo.ArgumentList`。`Start-Process -ArgumentList` は引用符が壊れる）
- **スキーマのテスト**: インメモリ SQLite（`:memory:`）。接続を閉じれば消える
- **DDL の適用**: `Designer/ddl/` の追跡ファイルをそのまま `--file` に渡す

やむを得ず作るならスクラッチパッドの**同じパスを上書きし続ける**（増やさない・消さない）。
**削除処理をスクリプトに紛れ込ませて確認を迂回しない。**
