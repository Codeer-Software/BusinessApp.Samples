# 作業のルール

> Claude が本リポジトリで作業するときの約束。**2026-09-06 に [CLAUDE.md](../CLAUDE.md) から切り出した**
> （最上位の指示書には「どうしても一番初めに読ませたいこと」だけを残す方針のため）。
> **§1 の「決め方」の表と §3 は、自律作業のときに効く**（[CLAUDE.md §0-5](../CLAUDE.md) で読み直す）。
> それ以外は、開発者が横にいる作業でも同じである。[CLAUDE.md §0-1](../CLAUDE.md) で常に読む。

## 1. 判断——自律と質問

- **原則として自律的に動き、仕様の意思決定まで自分で行う。** 判断に迷ったら、止めるより**根拠を ADR に残して前進する**
- ただし**後戻りコストの大きい根本設計・不可逆な操作・要件の重大な曖昧さ**は遠慮なく質問する
- **開発者が意見を問いかけてきたときは、回答のみ行い実装を始めない**（[CLAUDE.md §4](../CLAUDE.md)）

**選択肢が複数あるときの決め方**（実装・テスト・レビューのいずれでも同じ）

| 状況 | どうするか |
|---|---|
| 明らかにベストプラクティスが 1 つに定まる | **判断理由を残して選び、進む。** 聞かない |
| 正解が 1 つではない／開発者の意見を聞いたほうがよい | 聞く。ただし**聞く時期を選ぶ**（下 2 行） |
| ↳ 後から聞いても支障がない | **文書に保留として残し、まとめて聞く**（[00 §4-4](00_ドキュメント規約/本文.md) の保留リスト） |
| ↳ 後からだと手戻りが大きい／すぐ聞きたい | **手を止めてすぐ聞く** |

## 2. サイクル

1. **状態を読む** — [04_実装計画と現在地](04_実装計画と現在地.md) の「次にやること」
2. **設計する** — 該当する ADR とリサーチを確認する。CLB は `Docs/AppPatterns/` と `_samples/` を正典に複製する
3. **作る**
4. **検証する** — [31_検証のルール](31_検証のルール.md)
5. **自己レビューする** — §5。**まとまった実装の区切りごとに必ず入れる**
6. **記録する** — 現在地・ADR・仕様書を更新する。CLB の改善は [CLB改善提案](CLB改善提案/README.md) にその場で追記（発見日と CLB バージョン必須）
7. **コミットする** — §7
8. **再発防止の置き忘れが無いかを確かめる** — §9（**本体は「気づいた時点で」**。ここは最後の網）

## 3. 3 回で引く

**同じ問題の修正に 3 回以上失敗し、かつ新しい手がかりが何も得られていないなら、そこで追うのをやめる。**
分かっていることを文書に残し、残りのタスクへ移り、後で開発者に報告する（開発者の指示。2026-08-24。
**環境側の問題は開発者が触ると解決することが多く、Claude が追い続けても時間だけが減るから**）。

- 判断の基準は回数ではなく**進展の有無**である。試すたびに新しい情報が出ているなら続けてよい。
  「同じところで同じように失敗している」なら止める
- **とくに CLB とブラウザ操作は、開発者が自分で触ると解決することがかなりある**（前回プロジェクトでも、
  拡張機能では動かないが手で操作すると動いた事例があった）。環境側の問題を延々と追わない
- 残すのは「何をしようとして、何が起きて、何を試したか」。次に誰が見ても同じ場所から始められる形にする

## 4. 最小修正ではなく、最善の修正——ゼロベースで考える

**修正するとき、既存のものを正として最小の差分を探す癖がある**（Claude に限らず AI 全般に）。
**その癖を疑い、ゼロベースで最善の形を考えて直す**（開発者の指示。2026-09-06。
**最小修正は既存の誤りを温存し、つぎはぎを重ねるほど後から直せなくなるから**）。
**前提は、不具合を作り込まないための検証が十分にあること**——[31](31_検証のルール.md) の関門が緑で、
自己レビュー（§5）を通す。守りがあるから大きく直せる。

**実例**（2026-09-05）。20 に「一時ファイル」「検証を育てる」の 2 節を置いたのは
「行き先が無いから」だった。**行き先を作る**という発想が無かった。翌日に 30・31 を起こして移した。

- 「今あるものをどう直すか」ではなく「**今から作るならどうするか**」を先に描き、差分はそのあとで取る
- 直す範囲を狭める理由が「壊すのが怖い」なら、**怖さの正体は検証の不足**である。検証を足してから直す
- ただし**開発者の決定をゼロベースの対象にしない**。決定を変えたいなら ADR で提案する（§1）

## 5. 自己レビュー（工程として省かない）

**手順・観点・依頼文の雛形は [`self-review` スキル](../.claude/skills/self-review/SKILL.md) が持つ。**
まとまった実装の区切りで、そのスキルを起動する。**文書だけの変更でも省かない**
（[CLAUDE.md §4](../CLAUDE.md)）。

## 6. サブエージェント

- **同時 2 人まで**（トークン上限。開発者の許可があるときだけ増やす）。3 人以上には**波に分けて 2 人ずつ**流す
- ブラウザ操作・大量ファイルの精読・SQL 結果の大量閲覧は積極的に委譲する
- 各サブエージェントには「自分が作ったタブ以外を触るな」を明記する
- ブラウザを 2 並列にするときは**同じ利用者アカウントで動かす台本を組み合わせる**（クッキー壺が 1 つのため）

## 7. Git

- **ブランチを切って作業する。** `main` に直接コミットしない（**止めるフックは無い**。文書で守る）
- ブランチ名は一般的な慣行に従う（`feat/...` `fix/...` `docs/...` `chore/...` `refactor/...`）
- コミットメッセージは **Conventional Commits**。意味のある単位で
- マージは **`--no-ff`**（Fast-Forward しない）
- **`git push` は行わない**（開発者が行う。`.claude/settings.json` の deny で機械的にも禁止している）
- コミット前フック（段の正典は [tools/README](../tools/README.md)）が緑でないコミットは作らない。`--no-verify` を使わない
- **コミットは前景で流す。** バックグラウンドに送らない（`timeout` を伸ばして待つ）。
  フックは数分かかるが、**その間に別のファイルを直して `git add` すると、
  走っているコミットが後の変更まで飲み込む**（インデックスは 1 つしかない）。
  実際に 2 コミットが 1 つに融合した（2026-09-06。[qa/02](qa/02_自己レビュー記録.md) のラウンド 40）。
  **機械で守る案（フックが番兵を置き、`PreToolUse` が編集を拒む）は採らない**——
  番兵が消え損ねると**すべての編集が止まる**一方、防げる失敗はコミットメッセージの不正確さで、
  **関門の失敗のほうが重い**（§9 の「上が使えない理由」）

## 8. 一時ファイル・一時フォルダを作らない

**作ると必ず消すことになり、消し忘れれば成果物にごみが残り、消すときに取り違えれば要るものが消える。**
作らない方法を先に探す（**この理由は Claude が置き直したものである**。2026-09-07。
元の理由は「削除のたびに開発者の確認で作業が止まる」だったが、§10 でその前提が消えた。
**規則そのものを残してよいかは開発者に確認する**——[README](README.md) の保留リスト）。

- **DB の検査・投入**: `sql` CLI に `--query` を渡し、`--out` を省いて標準出力で受ける
  （PowerShell からは `ProcessStartInfo.ArgumentList`。`Start-Process -ArgumentList` は引用符が壊れる）
- **スキーマのテスト**: インメモリ SQLite（`:memory:`）。接続を閉じれば消える
- **DDL の適用**: `Designer/ddl/` の追跡ファイルをそのまま `--file` に渡す

やむを得ず作るならスクラッチパッドの**同じパスを上書きし続ける**（増やさない・消さない）。
それでも消す必要が出たときは §10 の `trash` を使い、
**削除を他のコマンドに紛れ込ませて関門を迂回しない。**

## 9. 問題に気づいたら、再発防止を「効く場所」に置く

**不具合・作業ミス・見落としに気づいたら、必ず再発防止を検討する。**
そして**次に同じ状況になった人が必ず読む場所に書く。** 記録した気になって終わらない。

置き場は「**その文書を、次に同じ状況の人が読むか**」で決める。上から順に強い。
**下へ降りるときは、上が使えない理由を、置いた先に 1 行で添えること**（§7 の Git の項が実例）。

| 置き場 | いつ効くか | 例 |
|---|---|---|
| **機械の関門（成果物）** | 毎回。忘れられない | コミット前フックの段・規約テスト・DDL の制約・型 |
| **機械の関門（作業）** | Claude が道具を呼ぶたび | `.claude/settings.json` の `PreToolUse`（`tools/claude/`）。**作業ミスを止められるのはここだけ** |
| **その作業の文書** | その作業をするとき | Git は §7、マイグレーションは [`Designer/migrations/README`](../Designer/migrations/README.md)、CLB は [qa/01](qa/01_CLB静かな失敗.md) |
| **必読の文書** | 毎タスク | 判断・工程は本書、文書の書き方は [00](00_ドキュメント規約/README.md) |

- **「留意事項の一覧」を新しく作らない。** 事故のたびに 1 行増える表は数年で誰も読まないし、
  **その作業をするときに開かれない**ので効かない。**集めずに散らす。**
  増えてよいのは**判定基準**（この表のような、書けば増えないもの）だけで、
  **事例のカタログは既にある 2 つ**（[qa/01](qa/01_CLB静かな失敗.md)・[qa/03](qa/03_テストで漏らした実例.md)）**で足りる**
- **置き場が無いのは、その作業の文書がまだ無いという合図**である（§4 の「行き先を作る」）
- **どう機械へ寄せるかの具体案**（規約テスト・DDL・フィクスチャ・型）は `self-review` スキル §8、
  **検証そのものの見直し**は [31 §4](31_検証のルール.md) が持つ。ここは**置き場の決め方**だけを持つ

## 10. 消すときは `trash`（ごみ箱送り）を使う。`rm` を使わない

```powershell
pwsh -NoProfile -File tools/claude/trash.ps1 <パス> [<パス> ...]   # 複数可・ワイルドカード可
pwsh -NoProfile -File tools/claude/trash.ps1 -DryRun <パス>        # 何が消えるかだけ見る
```

**`rm` を使わないこと・`rm` を deny にすることは開発者の指示**（2026-09-07。
**確認プロンプトで自律作業が止まる。かといって無制限の削除は許可したくない**、という理由）。
**そこから「ごみ箱送りなら確認を待たずに実行してよい」を導いたのは Claude である**——
戻せる削除にすれば許可と安全が両立する（経緯は [ADR-0044](decisions/0044-削除はごみ箱送りに一本化しrmを機械で止める.md)）。

- **削除にあたるコマンドは、当たり先によらず機械で拒まれる**（`rm`・`Remove-Item`・
  `shutil.rmtree`・`[IO.File]::Delete` など。
  **語彙の正典は `tools/claude/guard_delete.py` の正規表現**であって、この箇条書きではない）。
  **拒むときは代わりのコマンドが理由文で示される**
- **コミットしていない変更を消す git（`clean`・`reset --hard`・`stash drop`・`checkout -- `）も拒まれる。**
  **ここまで含めたのは Claude の判断である**（開発者が言ったのは `rm` まで。2026-09-07。
  **「Git で戻せないものを守る」と決めた以上、git 自身の破壊コマンドを外す理由が無いから**）。
  **副作用がある**——`git clean -n` のような空打ちや、1 ファイルだけの `git checkout -- ` も止まる。
  要るときは開発者に相談する
- **消せないものがある**——Git で戻せないもの（稼働 DB・追跡外の環境設定・`.git/`）は
  `trash` 経由でも拒む。**一覧と載せる基準の正典は
  [`tools/claude/protected_paths.json`](../tools/claude/protected_paths.json) の 1 ファイル**で、
  フックと `trash` の両方がそれを読む。**消す必要が出たら開発者に頼む**
- **ごみ箱から戻すのはエクスプローラで行う**（`trash` に復元機能は無い）。
  消したものは溜まっていくが、**誰がいつ空にするかは決まっていない**（[README](README.md) の保留リスト）
- **「戻せる」には穴が 2 つある。** ①ごみ箱の容量を超えるものは完全削除になるとされ、`trash` は拒めない
  （未確認。[README](README.md) の保留リスト）。
  ②**関門が取りこぼした削除は、開発者への確認ではなくそのまま実行になる**（同じく保留リスト）。
  **だから「機械が止めてくれる」に寄りかからない**
- 追跡ファイルを消すのは怖がらなくてよい——ただし**コミット済みであれば**である。
  **コミットしていない変更は git でも戻せない**
