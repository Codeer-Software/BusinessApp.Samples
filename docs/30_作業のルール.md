# 作業のルール

> Claude が本リポジトリで作業するときの約束。**2026-09-06 に [CLAUDE.md](../CLAUDE.md) から切り出した**
> （最上位の指示書には「どうしても一番初めに読ませたいこと」だけを残す方針のため）。
> **§1 の「決め方」の表と §3 は、自律作業のときに効く**（[CLAUDE.md §0-5](../CLAUDE.md) で読み直す）。
> それ以外は、開発者が横にいる作業でも同じである。[CLAUDE.md §0-1](../CLAUDE.md) で常に読む。

## 1. 判断——自律と質問

- **原則として自律的に動き、仕様の意思決定まで自分で行う。** 判断に迷ったら、止めるより**根拠を ADR に残して前進する**
  （**「最終判断」との線は [34 §1-1](34_開発者とClaudeの分担.md) が持つ**——**実装は最終判断ではない**）
- ただし**後戻りコストの大きい根本設計・要件の重大な曖昧さ**と、**[34 §1](34_開発者とClaudeの分担.md) の 6（影響重大 かつ 不可逆か高リスク）に当たる操作**は遠慮なく質問する
- **何が開発者の担当で、それ以外は Claude が確認なしに行うか——その境界は [34](34_開発者とClaudeの分担.md) が持つ**
  （**開発者が書いて全体を承認した文書である**。2026-09-20）。
  **境界に当たらないことで手を止めない。** 順番は、①34 §1 の表のどれかの行に当たるか
  → ②**3（仕様の最終判断）なら [34 §1-1](34_開発者とClaudeの分担.md)、6（影響重大 かつ 不可逆か高リスク）なら [34 §1-2](34_開発者とClaudeの分担.md)、
  8（関門を緩める）なら [34 §1-3](34_開発者とClaudeの分担.md)** → ③下の表。
  **開発者の担当ではないのに関門が塞いでいるものは [34 §2-2](34_開発者とClaudeの分担.md)**（そこにあるものだけは頼む）
- **止まったら、何に止められたかを記録する**（qa/04 か qa/02）。**「止められた」とだけ書かない**——
  実例はコミット `ffcd5a03`（2026-09-16）で、本文が「止まった」と受動態で書いてあるだけだった。
  当たる `ask` は `.claude/settings.json` に無く、**明文の無いところでの Claude の判断だったと読むしかなかった**（推定）。
  **主体（規則か・機械か・自分の判断か）を必ず書く**
- **開発者が意見を問いかけてきたときは、回答のみ行い実装を始めない**（[CLAUDE.md §4](../CLAUDE.md)）
- **自律作業の途中は、区切りごとに開発者へ報告しなくてよい**（開発者の指示。2026-09-20。
  逐語は「途中の作業一段落の段階での開発者への報告は不要です」——**禁止ではなく免除である**）。
  **区切りごとに `main` へマージするのは今までどおり**（§7-1 の 6 条件）。
  **理由は開発者が述べていない。Claude の読みでは、報告のたびに自走が切れるからである**（[34 §0](34_開発者とClaudeの分担.md) と同じ形）。
  **以下は Claude の敷衍**——報告するのは**自律作業そのものを終えるとき**である。
  **手が止まるときは別で、そのときに言う**——[34 §2-2](34_開発者とClaudeの分担.md) に当たって進めないとき、
  §3 で追うのをやめたとき、[34 §1](34_開発者とClaudeの分担.md) の担当に当たったとき

**選択肢が複数あるときの決め方**（実装・テスト・レビューのいずれでも同じ）

| 状況 | どうするか |
|---|---|
| 明らかにベストプラクティスが 1 つに定まる | **判断理由を残して選び、進む。** 聞かない |
| 正解が 1 つではない／開発者の意見を聞いたほうがよい | 聞く。ただし**聞く時期を選ぶ**（下 2 行） |
| ↳ 後から聞いても支障がない | **[05_開発者への問い](05_開発者への問い.md) に書き、作業の区切りで聞く**（§11。Claude が時期を決めて自分で起こす保留は [00 §4-4](00_ドキュメント規約/本文.md) の保留リスト） |
| ↳ 後からだと手戻りが大きい／すぐ聞きたい | **手を止めてすぐ聞く** |

## 2. サイクル

**回の始めから終わりまでの順番と道具の打ち方は [`cycle` スキル](../.claude/skills/cycle/SKILL.md) が持つ。**

1. **状態を読む** — [04_実装計画と現在地](04_実装計画と現在地.md) の「次にやること」
2. **設計する** — 該当する ADR とリサーチを確認する。CLB は `Docs/AppPatterns/` と `_samples/` を正典に複製する
3. **作る**
4. **検証する** — [31_検証のルール](31_検証のルール.md)
5. **自己レビューする** — §5。**まとまった実装の区切りごとに必ず入れる**
6. **記録する** — 現在地・ADR・仕様書を更新する。CLB の改善は [CLB改善提案](CLB改善提案/README.md) にその場で追記（発見日と CLB バージョン必須）
7. **コミットする** — §7
8. **再発防止の置き忘れが無いかを確かめる** — §9（**本体は「気づいた時点で」**。ここは最後の網）

## 3. 3 回で中断する

**同じ問題の修正に 3 回以上失敗し、かつ新しい手がかりが何も得られていないなら、そこで追うのをやめる。**
分かっていることを文書に残し、残りのタスクへ移り、後で開発者に報告する（開発者の指示。2026-08-24。
**環境側の問題は開発者が触ると解決することが多く、Claude が追い続けても時間だけが減るから**）。

- 判断の基準は回数ではなく**進展の有無**である。試すたびに新しい情報が出ているなら続けてよい。
  「同じところで同じように失敗している」なら止める
- **とくに CLB とブラウザ操作は、開発者が自分で触ると解決することがかなりある**（前回プロジェクトでも、
  拡張機能では動かないが手で操作すると動いた事例があった）。環境側の問題を延々と追わない
- 残すのは「何をしようとして、何が起きて、何を試したか」。次に誰が見ても同じ場所から始められる形にする

## 4. 最小修正ではなく、最善の修正——ゼロベースで考える

**修正するとき、既存のものを正として最小の差分を探す癖がある**（Claude に限らず AI 全般に）。
**その癖を疑い、ゼロベースで最善の形を考えて直す**（開発者の指示。2026-09-06。
**最小修正は既存の誤りを温存し、つぎはぎを重ねるほど後から直せなくなるから**）。
**前提は、不具合を作り込まないための検証が十分にあること**——[31](31_検証のルール.md) の関門が緑で、
自己レビュー（§5）を通す。守りがあるから大きく直せる。

**実例**（2026-09-05）。20 に「一時ファイル」「検証を育てる」の 2 節を置いたのは
「行き先が無いから」だった。**行き先を作る**という発想が無かった。翌日に 30・31 を起こして移した。

- 「今あるものをどう直すか」ではなく「**今から作るならどうするか**」を先に描き、差分はそのあとで取る
- 直す範囲を狭める理由が「壊すのが怖い」なら、**怖さの正体は検証の不足**である。検証を足してから直す
- ただし**開発者の決定をゼロベースの対象にしない**。決定を変えたいなら ADR で提案する（§1）

### 4-1. 仕組みをどこまで作り込むかは、対象で変わる

**本節が扱うのは「仕組み」の水準だけである。** 会計コアそのものをどこまで作るかは
[CLAUDE.md §1・§2](../CLAUDE.md) が持つ（「会計コアだけは完璧に作る」「会計ロジックの不具合の絶無」）。

**開発者の方針**（2026-09-18）。

| 対象 | 目指す水準 |
|---|---|
| **[CLAUDE.md §2](../CLAUDE.md) の「会計ロジックの不具合の絶無を期す」ための仕組み**（自動テスト等） | **妥協せず 100%** |
| **利用者が「必ず行う作業」をこのアプリで行える仕組み**（物差しは [06](06_利用者の作業.md)。**どの作業が「必ず」かは 06 の必須の列**（開発者が確認。2026-09-18）。範囲は [ADR-0065](decisions/0065-UI改善はCLBの標準の範囲で行い必ず行う作業ができないときだけ外へ出る.md)） | **妥協せず 100%**（開発者の決定。2026-09-18。逐語は「それができないなら会計アプリとして使い物になりませんから」。**会計ロジックではないが同じ側**） |
| **それ以外**（Claude の危険な操作を制御する仕組み・「必ず」ではない作業の使いやすさなど） | **70〜80%** |

**分かれ目は「アプリのコードか、道具か」ではない。**
**「会計ロジックの不具合の絶無を期す」は本プロジェクトの絶対方針**であり（[CLAUDE.md §2](../CLAUDE.md)）、
**そのための仕組みかどうか**で分かれる（開発者の言葉。2026-09-18）。

**理由**（逐語）——

> （完璧なゴールを品質100%として）80%くらいまでは、費やしたコストに応じて品質が順調に高まり、
> ゴールに近づいていく。しかし、80%から100%にするためには果てしない努力やコストがかかる。
> 0%から80%にするために費やしたコスト以上のコストがかかることも珍しくない。

> 端的に言って、費用対効果が悪いのです。よって、「だいたい80%はカバーできた。残りの20%は、
> 技術的に不可能ではないが、コストに照らして割に合わないのでここでやめよう。そういう判断をしたことを、
> ドキュメントに残すにとどめよう。」という判断が合理的・正解である場合があります。

**以下は Claude の敷衍。**

- **§4 との関係。** §4 は「**どう**直すか」の規則で、本節は「**どこまで**やるか」の規則である。
  §4 の「最善の修正」は、最小差分を避ける話であって、際限なく磨く許可ではない
- **「100%」が何の 100% かは [ADR-0012](decisions/0012-テスト方針とカバレッジのゲート.md) が持つ**——
  **数値の正典はそちら**である。**ミューテーションの下限はラチェットで 100% ではなく**、
  同 ADR は「100% は下限であって、十分性ではない」とも書いている。**本節はその数値を動かさない**
- **上の行を狭く取らない。** 「帳簿の数字を作る計算」だけではない——
  **不変条件**（[10 §1](10_会計ドメイン設計.md)）・**仕訳の不変性を守る関門**（[ADR-0004](decisions/0004-優良な電子帳簿への準拠と仕訳の不変性.md)）・
  **制度要件のトレーサビリティ**も、数字を直接作らなくても「会計ロジックの不具合」の側である。
  だから [qa/05](qa/05_観点網羅の計器.md) の観点網羅の計器・[31 §6](31_検証のルール.md) の掃引・
  ADR-0012 のゲートは、**`tools/` にあっても上の行**に属する
- **そこでやめると決めたときは「できない」ではなく「割に合わないのでやめた」と書く**——
  技術的に可能かどうかと、やるかどうかは別である。**書き残さずにやめるのは、見落としと区別が付かない。**
  置き場は 3 つで、**道具の性質に属するもの**（この綴りは見ない等）はその道具の「限界」の欄、
  **なぜその水準で止めたかの経緯**が要るものは ADR、
  **後で拾う気があり、いつ拾うかが決まるもの**だけ保留リスト（[00 §4-4](00_ドキュメント規約/本文.md) は期限を要求する）
- **コストは「直す手」だけではない。** レビューの波・検証のやり直し・機械の作り込みが乗る。
  **指摘が出たから直す、を無条件に続けない**——本節に照らして取捨する（[`self-review` スキル](../.claude/skills/self-review/SKILL.md) §6）
- **70〜80% の側でも、緑の嘘だけは残さない**——「守っている」と書いた機械が守っていない状態は、
  カバー率の問題ではなく**報告が偽である**（[qa/03 の L-56](qa/03_テストで漏らした実例.md)）。
  **カバーしないと決めた範囲は、カバーしたことにしない。**
  だから [31 §1](31_検証のルール.md) の「壊してすべてで赤くなるか」と
  `self-review` スキル §9 の 6 観点は、**70〜80% の側でも省かない**——
  **あれは水準の話ではなく、報告が偽にならないための手**である
- **どちらに属するか迷ったら開発者に聞く。** 聞き方は §1 の表——
  後から聞いても支障が無ければ [05](05_開発者への問い.md) に書いて区切りで聞き（§11）、手戻りが大きければ止めて聞く
- **「70〜80%」を測る指標は作らない。** 測れる形にした瞬間に**それが新しいゲートになり**、
  「割に合わないことをやめる」という本節の目的を裏切る

## 5. 自己レビュー（工程として省かない）

**手順・観点・依頼文の雛形は [`self-review` スキル](../.claude/skills/self-review/SKILL.md) が持つ。**
まとまった実装の区切りで、そのスキルを起動する。**文書だけの変更でも省かない**
（[CLAUDE.md §4](../CLAUDE.md)）。

## 6. サブエージェント

- **同時 3 人まで**（開発者の指示。2026-09-10。逐語は「上位プランの契約をしたので、サブエージェントは同時に3台までOKとします」、同じ日に「今後、サブエージェントは常に同時に3人までOK」）。4 人以上には**波に分けて 3 人ずつ**流す
- ブラウザ操作・大量ファイルの精読・SQL 結果の大量閲覧は積極的に委譲する
- 各サブエージェントには「自分が作ったタブ以外を触るな」を明記する
- ブラウザを 2 並列にするときは**同じ利用者アカウントで動かす台本を組み合わせる**（クッキー壺が 1 つのため）

## 7. Git

- **ブランチを切って作業する。** `main` に直接コミットしない（**止めるフックは無い**。文書で守る）。
  **`git checkout -b` は単独の呼び出しで打ち、`git branch --show-current` で確かめてから作業に入る**
  （[33 §1](33_失わないためのルール.md) の守りは呼び出し全体を拒むので、`&&` で繋ぐと**ブランチ作成ごと実行されない**ことがある）
- ブランチ名は一般的な慣行に従う（`feat/...` `fix/...` `docs/...` `chore/...` `refactor/...`）
- **ブランチの主題は「規則 ＋ それを適用しきること」で取る**（開発者の指摘。2026-09-06。
  **途中で止めた状態は、どちらの終点よりも悪いから**。実例は同日のコミット
  `docs: 略称への統一を最後まで通し、裸の条番号に法令名を添える` の本文——
  記法の規則を強制にした回に略称の統一を別扱いにしたので、
  **同じ法令が 1 ファイルの中に 3 通りで残った。残っていたのは 19 か所で、量は理由にならなかった**）。
  **以下は Claude の敷衍**（[00 §4-11](00_ドキュメント規約/本文.md)）——
  止める理由は「やると壊れるから」であるべきで、本当に切るべきなのは**別の決定が要るとき**である
- **1 つの論点について開発者との議論が続く間は、1 つの作業ブランチにコミットを重ね、論点が閉じてから `main` へマージする**（開発者の指示。2026-09-19。
  逐語は「1つの論点について話し合いが続く中でのドキュメント修正については、mainにマージせず1つの作業ブランチ内でコミットを重ねたほうが分かりやすい」。
  それまでは開発者と話して文書を直すたびにマージしていた）。**§7-1 の 6 条件はマージのときに数える**
- コミットメッセージは **Conventional Commits**。意味のある単位で
- マージは **`--no-ff`**（Fast-Forward しない）
- **`main` へのマージは Claude が行う。開発者への確認は要らない**（開発者の決定。2026-09-15。
  **開発者は理由を述べていない。** Claude の見立てでは、**自律作業中に未マージのブランチが
  積み上がると、次の作業が古い `main` から切られる**のを避けるためである）。
  **ただし §7-1 の 6 条件が全部そろっていること。1 つでも欠けたらマージしない**
- **`git push` は行わない**（開発者が行う。`.claude/settings.json` の deny で機械的にも禁止している）
- コミット前フック（段の正典は [tools/README](../tools/README.md)）が緑でないコミットは作らない。`--no-verify` を使わない
- **コミットは前景で流す。** バックグラウンドに送らない（`timeout` を伸ばして待つ）。
  フックは数分かかるが、**その間に別のファイルを直して `git add` すると、
  走っているコミットが後の変更まで飲み込む**（インデックスは 1 つしかない）。
  実際に 2 コミットが 1 つに融合した（2026-09-06。[qa/02](qa/02_自己レビュー記録/2026-09.md) のラウンド 40）。
  **機械で守る案（フックが番兵を置き、`PreToolUse` が編集を拒む）は採らない**——
  番兵が消え損ねると**すべての編集が止まる**一方、防げる失敗はコミットメッセージの不正確さで、
  **関門の失敗のほうが重い**（§9 の「上が使えない理由」）

### 7-1. `main` へマージしてよい条件（6 つ）

**開発者の決定**（2026-09-15）。**全部そろって初めてマージする。**

| # | 条件 |
|---|---|
| 1 | **そのブランチで行うべきタスクが完了している**（主題の取り方は §7 の「規則 ＋ 適用しきること」） |
| 2 | **C# コードを追加・修正したなら、単体テストも実装が完了している** |
| 3 | **ソースコードを編集したなら（コメントだけの編集を除く）、[実機操作テスト](qa/04_実機操作テスト.md)を行い完了している** |
| 4 | **主タスクに付随する作業（関連する文書の更新など）も完了している** |
| 5 | **自己レビューと、その指摘の修正が完了している**（[`self-review` スキル](../.claude/skills/self-review/SKILL.md)） |
| 6 | **機械的検証が全部通っている**（コミット前フックの全段。段の正典は [tools/README](../tools/README.md)） |

**以下はすべて Claude の敷衍**（[00 §4-11](00_ドキュメント規約/本文.md)。
**開発者が述べたのは上の表の 6 行だけで、範囲も順序もここから先は Claude が当てはめた**）。

- **「途中で止めたブランチはマージしない」は 1 の言い換えである**
- **2 の範囲は [ADR-0012 §1](decisions/0012-テスト方針とカバレッジのゲート.md) が持つ。**
  同 ADR は **`*.mod.cs`（CLB スクリプト）と `.Client` にゲートを課さない**と決めている
  ——どちらも**条件 3 の実機で受ける**。**ゲートの外にある C# を足した回**（`BusinessApp.Server`・
  `Client.Shared`・各 CLI）**と、新しい csproj を足した回**は、条件 2 が独自に効く場面である
  （**分割でゲートを持ち出し忘れると、テストは全部緑のまま検査の外へ落ちる**。[ADR-0025 §6](decisions/0025-取引先を部品として分ける.md)）

## 8. 一時ファイルは、リポジトリの中に作らない（スクラッチパッドは自由に使う）

**リポジトリの中に作らない。理由は削除の手間ではない**（2026-09-07 に開発者と決め直した）。

1. **写しは正典から乖離する。** DDL を一時ファイルに写して流すと、
   次に `Designer/ddl/` が変わったとき、テストは**古い写しを見続ける**
2. **手数が増える。** 書く → 流す → 読む → 消す の 4 手が、下のやり方ならどれも 1 手で済む

- **DB の検査・投入**: `sql` CLI に `--query` を渡し、`--out` を省いて標準出力で受ける
  （PowerShell からは `ProcessStartInfo.ArgumentList`。`Start-Process -ArgumentList` は引用符が壊れる）
- **スキーマのテスト**: インメモリ SQLite（`:memory:`）。接続を閉じれば消える
- **DDL の適用**: `Designer/ddl/` の追跡ファイルを**そのまま** `--file` に渡す

**スクラッチパッドは自由に使ってよい。片づけも要らない。**
セッションごとの使い捨てで、リポジトリにも `git status` にも現れず、**消す必要が無い**
（したがって `rm` も `trash` も出番が無い）。上の 2 つの理由がどちらも当たらないので、
**同じパスを上書きし続ける必要も無い**。
**長い文字列や日本語を含むスクリプトは、シェルのヒアドキュメントで壊れるので、
スクラッチパッドにファイルとして書いてから渡す**——コミットメッセージなら `git commit -F <ファイル>`、
スクリプトなら `python <ファイル>`。**3 行を超える文字列は、ヒアドキュメントを試さず最初からこれにする。**
**エスケープ（`\0`・`\t`・`　`）を含む検体を書いたら、書いたファイルを読み直して確かめる**
——狙った字が**本物の制御文字に化ける**ことがある（[qa/03 L-20](qa/03_テストで漏らした実例.md)）。

**一括置換をしたら、置換した行を目で読み直す。** 壊れるのは置換そのものより**副作用**である——
太字の入れ子・閉じ括弧の欠落・述語の欠落は、どれも「帰属の札だけ差し替えた」結果で、
**`lint_docs.py` は括弧の対も強調記号も見ない**（2026-09-20 に 8 か所・6 か所を一度に作り込んだ。
[qa/02](qa/02_自己レビュー記録/2026-09.md) のラウンド 138）。

**スクリプトが途中で落ちたら、書けたところまでを数えてから流し直す。**
**前半のファイルには既に書かれている**ので、同じスクリプトを直して流し直すと**前半が二重に当たる**
（同日に 30 §1 へ同じ 5 行が 2 回入った。同ラウンド）。
**置換の関数を「既に当たっていれば飛ばす」形にしておく**と踏まない。

## 9. 問題に気づいたら、再発防止を「効く場所」に置く

**不具合・作業ミス・見落としに気づいたら、必ず再発防止を検討する。**
そして**次に同じ状況になった人が必ず読む場所に書く。** 記録した気になって終わらない。

置き場は「**その文書を、次に同じ状況の人が読むか**」で決める。上から順に強い。
**下へ降りるときは、上が使えない理由を、置いた先に 1 行で添えること**（§7 の Git の項が実例）。

| 置き場 | いつ効くか | 例 |
|---|---|---|
| **機械の関門（成果物）** | 毎回。忘れられない | コミット前フックの段・規約テスト・DDL の制約・型 |
| **機械の関門（作業）** | Claude が道具を呼ぶたび | `.claude/settings.json` の `PreToolUse`（`tools/claude/`）。**作業ミスを止められるのはここだけ** |
| **スキル**（`.claude/skills/`） | その作業を始めたとき | [`cycle`](../.claude/skills/cycle/SKILL.md)（回の始めと終わり）・[`self-review`](../.claude/skills/self-review/SKILL.md)・[`live-test`](../.claude/skills/live-test/SKILL.md)（実機）・[`research`](../.claude/skills/research/SKILL.md)（制度調査）。**関門ではない**——起動するかは判断である |
| **その作業の文書** | その作業をするとき（**開くのも判断**） | Git は §7、マイグレーションは [`Designer/migrations/README`](../Designer/migrations/README.md)、CLB は [qa/01](qa/01_CLB静かな失敗.md) |
| **必読の文書** | 毎タスク | 判断・工程は本書、文書の書き方は [00](00_ドキュメント規約/README.md) |

**スキルと「その作業の文書」の差は、思い出す手がかりの多さだけである**
——どちらも起動・通読は判断で、**関門ではない**。
スキルを上に置いたのは `description` がその状況の語で書かれているぶん当たりやすいからで、
**起動させたい文書からリンクする**のは変わらない（[00 §7](00_ドキュメント規約/README.md)）。
**スキルの中身は手順と雛形にし、規則と事実は文書へリンクする**（写すと [00 §4-6](00_ドキュメント規約/本文.md) の二重管理）。
**機械にできることはスキルに書かない**（上 2 段のほうが強い）。

- **「留意事項の一覧」を新しく作らない。** 事故のたびに 1 行増える表は数年で誰も読まないし、
  **その作業をするときに開かれない**ので効かない。**集めずに散らす。**
  増えてよいのは**判定基準**（この表のような、書けば増えないもの）だけで、
  **事例のカタログは既にある 2 つ**（[qa/01](qa/01_CLB静かな失敗.md)・[qa/03](qa/03_テストで漏らした実例.md)）**で足りる**
- **置き場が無いのは、その作業の文書がまだ無いという合図**である（§4 の「行き先を作る」）
- **書く前に、それが既にどこにあるかを数える。** 「無い」と思って書いたものの多くは、
  別の場所に別の言葉である。**先に `git grep` で当たり、あるなら書かずにリンクする**——
  再発防止のつもりで**二重管理を増やす**のがいちばん多い失敗である
  （[qa/02 のラウンド 99](qa/02_自己レビュー記録/2026-09.md)）
- **どう機械へ寄せるかの具体案**（規約テスト・DDL・フィクスチャ・型）は `self-review` スキル §8、
  **検証そのものの見直し**は [31 §4](31_検証のルール.md) が持つ。ここは**置き場の決め方**だけを持つ

### 9-1. Claude のメモリは置き場に数えない

**Claude のメモリは、リポジトリの外にある一時記憶である。ここに作業のルールを置かない。**
**置いてよいのは、公開リポジトリの追跡ファイルに書けないものだけ**——
たとえば開発者個人に関する事実（[CLAUDE.md §5](../CLAUDE.md)）。
**それ以外は、リポジトリのどこかに降ろしてから書く。**
**秘密（接続文字列・API キー・パスワード）はメモリにも書かない**——
メモリはモデルに送られ会話ログに残るので、[CLAUDE.md §5](../CLAUDE.md) の禁止はここにも及ぶ。

**開発者の指示**（2026-09-15）。理由も開発者の言葉である——
**リポジトリの場所が変わればメモリは消え、他の人が `git clone` しても引き継がれない。
メモリはどこまでいっても一時記憶に過ぎない。**

**以下は Claude の敷衍**（[00 §4-11](00_ドキュメント規約/本文.md)）。
**上の表が「次に同じ状況になった人が必ず読む場所」と言うとき、開発者もその「人」である**——
**開発者が読めない規則は、改善も否認もできない**（§11 の「明文化していないと改善もできない」）。
**リポジトリの外にあるので、機械の関門も別の目も届かない**
——腐っても、誤って引いていても、鳴るものが無い。
**一時的な手控えに使うのは構わないが、回の終わりに行き先を決める**（`self-review` スキル §7）。

## 11. 開発者の確認が要ることは [05_開発者への問い](05_開発者への問い.md) に書く

**05 は「開発者の確認を要すること」をまとめた文書である**（開発者の決定。2026-09-19。
**答えを待って止まるものだけではない**——**Claude が自分で決めて実装し、後から諮るもの**も同じ場所に置く。
[34 §1-1](34_開発者とClaudeの分担.md) の表の一番下の行（自律作業中に起こった仕様の疑問）がその形である。
**開発者の理由は「いまも『決まらないと止まるもの: 止まらない』と書いた問いがたくさん並んでいる」**——
05 は既にそう使われている、ということである。
**以下は Claude の敷衍**——**置き場を決めないと「後から諮る」が消える**）。
**後から諮るものは、「決まらないと止まるもの」の欄に実装済みである旨を書き、
本文に既に実装した内容と判断の理由を書く**——
**開発者が「それでよい」と答えたらそのまま、別案を採ったらやり直す。**

**開発者の答えが無いと先へ進まないことは、会話の箇条書きではなく [05](05_開発者への問い.md) に書く**
（開発者の指示。2026-09-10。逐語は「**開発者に聞きたくなったら、それをどこかのドキュメントにまとめてほしい**」。
理由も開発者の言葉——**会話の中の問いは短文の箇条書きになり、判断材料が少なく検討が難しい。文書なら Claude が落ちても残り、
開発者は自走中の Claude を止めずに並行して検討できる**）。

**開発者が指示したこと**（2026-09-10。最後の 1 つは 2026-09-12。逐語の要約）:

- **1 問に書くこと**——どこの機能に関する問いか・いまどういう状況か（何に困っているか・何の情報が足りないか）・
  どんな選択肢があるか・Claude の推奨案・いつまでに決める必要があるか（決まらないと何ができないか）。
  「以上は例示。問いごとに必要な情報を書けばよい」。**不具合なら、どのページでどの操作をすると再現するかまで**
- **急ぎの順に並べる**（「上から順に回答を考えていく」）。**行数の目安にこだわらない**
- **回答欄は置かない**——自走中に開発者が書き込むと Git の差分に混ざる。
  開発者は「自分の回答を Claude に伝えて、議論して結論を出したい」ので、書き込んで Claude が気づいたときに読んで終わり、という運用はしない
- 開発者は Claude の作業が一段落したときに答える。対話か、長ければファイルに書いて見せるかは問いによる。
  **Claude が毎セッションの冒頭に 05 を読む規則は要らない**
- どうしてもすぐ答えが要るなら、そこで手を止めて聞く
- 結論が出て ADR や設計書にまとめたら、その問いは消す
- 運用の規則をどこかに書いておく——**明文化していないと改善もできないから**
- **問いの中で条文に触れるときは、法令名を必ず添える**（開発者の指示。2026-09-12。逐語は「単に附則と言われても困ってしまいます。質問の際は法令名も書いてください」
  「法令はソースコードと同じかそれ以上に厳密に表記をお願いします」）

**Claude の敷衍**（規則に落とすために足したもの。うまくいかなければ変える）:

- **[80 §3](80_参照法令一覧.md) の「条番号だけを裸で置かない」は、文書だけでなく 05 の問いと会話の返信にも当てる**（上の 2026-09-12 の指示を規則に落としたもの。表の中でも各行に法令名を添える）
- **書く前に、既に決まっていないかを確かめる。** 論点の語で ADR・設計文書・qa/02 の後の回を引き、
  問いには「既に決まっていること」を逐語つきで書いて、まだ決まっていない部分だけを問う
  （**2026-09-10 の初版で、ADR-0037 と ADR-0046 決定 8 が決めたことを 2 問も未決として書いた**。[qa/02 ラウンド 74](qa/02_自己レビュー記録/2026-09.md)）
- **問いができた時点で書く。** 自走中でも止まらない。
  **ただし「後から諮るもの」だけは、実装した回の区切りで足す**（まだ決めていないうちは書けない）。
  報告では「**05 に n 問足した。うち m 問は事後の確認**」とだけ言う
- **すぐ答えが要るときも、05 に書いたうえで手を止めて聞く**（§1 の「後からだと手戻りが大きい」）
- **回の着手前に、その回を期限とする問いが 05 に残っていないかを数える**（§2 の 1「状態を読む」の一部）。
  残っていれば §1 の「手を止めてすぐ聞く」へ倒す——期限を過ぎて着手すると、同じ画面を 2 度直すことになる
- **消すのは Claude。** 答えが「いまのまま」でも、その論点を負う文書に「開発者の決定。日付。理由」を書き
  （未承認の印があれば消し）、それから問いを消す。番号 `Q-nn` は使い回さない
- **消した番号を指す参照が残っていないかは `lint_docs.py` が見る**（error）。**番号を使い回さないから、
  無い番号は必ず腐った参照である。** 閉じたことを述べる行は「**旧 Q-nn**」と書けば当たらない
- **Claude が時期を決めて自分で起こす保留は、いままでどおり各文書の末尾の保留リスト**（[00 §4-4](00_ドキュメント規約/本文.md)）。
  05 に載せるのは**開発者の確認が要るもの**——「答えれば進むもの」と「先に実装して後から諮るもの」の両方である。
  **「してほしいこと」（作業の依頼）も、開発者の手が要るなら 05 に載せる**。
  **同じ論点を両方に書かない**——負う文書の側には論点の名前と `05 の Q-nn` だけを残す
