# 初見ユーザーUXテスト（2026-07-14）

> **手法**: アプリの実装知識を持たない AI エージェントに「初めて社内システムを触る社員」のペルソナを与え、業務ミッションだけを渡してブラウザで実際に操作させる。マニュアル無し・画面の表示だけが頼り。エージェントが詰まった箇所・迷った箇所・質問した内容＝**画面の説明が足りない箇所**として収集する（ユーザー発案 7/13）。
> **制約と読み方**: エージェントは人間より文字を丁寧に読む傾向があるため、「エージェントが詰まった＝人間も高確率で詰まる」は成り立つが、逆は保証されない（改善ポイントの検出器であって証明ではない）。
> 対応状況の凡例: ✅=本セッションで対応済み ／ 📋=バックログ（要ユーザー判断） ／ 💬=仕様どおり（説明改善のみ検討）

## Phase 4: 経理（山田太郎・販売チェーン一気通貫）

**結果**: 見積 Q-26-004 → 受注 SO-26-004 → 検収 A-26-004 確定（売上仕訳 No.60）→ 請求書 → 入金消込（No.61）→ 売掛残0 → SES精算プレビュー（PRJ-005 控除 700,000／PRJ-003 超過 845,000）まで**7タスク完遂**。「メニューが業務フロー順」「検収確定トーストに仕訳番号・金額」「入金候補が未消込請求書のみ」「番号体系・採番」は市販ソフト比でも高評価。

### 「請求書を作成が無反応」の調査結果（最重要事項）

エージェントは検収画面の「請求書を作成」が3回無反応と報告し、請求書を手作成して迂回した。**親エージェントが実機で再現調査した結果、アプリは正常**:
- ボタンは disabled=false（有効）。JS クリックで INV-26-010 が正常作成され、請求書詳細へ遷移・トーストも表示
- 既請求ガード（「この検収の請求書は既に作成済みです」）も正常動作
- 真因は**ブラウザ自動操作の座標クリックが Blazor ボタンで空振りする既知現象**（Project.md 記録済み）。人間のマウス操作では起きない
- 事後処理: 診断で作った INV-26-010 は削除し、手作成の INV-26-009 を検収 A-26-004 に紐付けて（SQL）チェーンを整合させた。二重請求ガードの効きも確認済み

ただしこの誤認の背景にある指摘は正当: **確定済み検収の主要アクション「請求書を作成」がグレー（Secondary）で「無効に見える」**こと（下表 U4-1）。

### 教育係への質問と回答
1. 「請求書を作成」は経理で使える仕様か → 使える（上記のとおり正常動作。誤認は自動操作起因）
2. 検収と手作成請求書の紐付け欠落 → 親が SQL で修復済み（今後の実運用では U4-2 の改修が必要）
