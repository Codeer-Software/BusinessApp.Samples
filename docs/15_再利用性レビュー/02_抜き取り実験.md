# 抜き取り実験（構成A・構成C を実際に作った記録）

読解だけでは「疎結合か」に答えられないので、**別ワークツリー（`review/reusability`）で実際に部品を抜いた**。
本体リポジトリ・本体 DB には一切触れていない（DB はコピー・デプロイ先もワークツリー内）。

ベースライン: designcheck 0 / check_navigation error 0 warn 3 / lint_design 0 / DB 参照切れ 0。

**designcheck 0 / check_navigation error 0 warn 0 / lint_design 0 / DB 参照切れ 0** で通過。
削除 60 ファイル・編集 7 ファイル・DB オブジェクト 26 個。

### 途中で踏んだもの

**(a) テーブルの素朴な DROP は FK 制約で失敗する。**
`docs/10 §4` の手順 6 は「（任意）不要になったテーブルの DROP」としか書いておらず、
対象一覧も削除順序も無い。実際には `PRAGMA foreign_keys=OFF` か、依存を解いた順序が要る。

**(b) 静的検査を全部通ったあとで、基盤機能が壊れていた。**

```
UPDATE partners SET name = ... ;
→ SQLite Error 1: 'no such table: main.vendor_invoices'
```

`partners`（基盤マスタ）の UPDATE トリガが、外した営業・購買のテーブルの表示ラベルを
書きに行くため。**エンドユーザーから見ると「取引先の会社名を直せない」**、
しかもエラー文は購買のテーブル名で、原因の見当がつかない。
`trg_partners_name_label` と `trg_partners_name_label_vi` を DROP すると解消した。

## 構成C: 会計＋営業（請求・入金。SES 精算を除く）

### やったこと

| # | 作業 | 量 | 気づいた検査 |
|---|---|---|---|
| 1 | `Modules/{Expense,Timesheet,Purchasing,Management}` 削除／PageFrame 8 枚削除 | 27 モジュール | — |
| 2 | `Sales/Receipt` から**相殺入金**（購買依存）を除去 | **.cs 14 箇所＋.json フィールド 2＋選択肢 1** | designcheck は 4 箇所のみ |
| 3 | `Sales/SesBilling` `SesRunPlan` 削除（工数依存）＋フレーム登録 1 件 | 2 モジュール | **designcheck**（フレーム登録） |
| 4 | `Shell/Notification` の経費分岐除去 | 1 ブロック | **designcheck** |
| 5 | `Shell/PortalSidebar` `PortalHome` の削除 | 4 ファイル | check_navigation（一部） |
| 6 | `PortalQueueData` 6 列→3 列 | 2 ファイル | 指摘なし |
| 7 | `PortalAlertData` **174 行→19 行に書き直し**／.json 6 欄削除 | 2 ファイル | 指摘なし |
| 8 | DB: テーブル 10・ビュー 3・トリガ 1 を DROP | 14 個 | トリガのみ試作検査が検出 |

### 結果

**designcheck 0 / check_navigation error 0 warn 2（既存）/ lint_design 0 / DB 参照切れ 0** で通過。

### 分かったこと

**(a) 「営業を選ぶと購買と工数がついてくる」。**
文書が例外と認める 2 本（相殺入金・SES 精算）が、そのまま構成C の追加コストになる。
どちらも「機能を捨てる」判断が要る＝**純粋な削除作業ではなく仕様判断**。

**(b) designcheck の findings を正としてはいけない。**
`docs/10 §3.3` は「箇所の特定は行番号でなく designcheck の findings を正とする」と書いているが、
Receipt の実測は **designcheck 4 箇所に対し、実際に直した箇所は 17**（スクリプト 14・フィールド 2・選択肢 1）。
designcheck が見るのは型参照とフィールド定義だけで、

- `if (Method.Value == "offset")` の条件分岐（8 箇所）
- 入金方法の選択肢 `"相殺,offset"`（JSON 直書き）
- 取消時の巻き戻し・完了メッセージ

は見ない。**designcheck の findings だけ潰すと、「相殺」が選べるのに登録できない入金画面になる。**

**(c) 契約 SQL は「書き方」次第で機械削除できるかどうかが決まる。**
`PortalQueueData` は 1 列＝独立した副問い合わせだったので、列単位で機械的に削れた。
`PortalAlertData` は CTE 連鎖（`months` → `pay` → `cash_now` → `flows` → `cash_final` …）で
部品をまたいで絡んでおり、**列を削るのではなく全体を書き直す**しかなかった。

**(d) 正規表現でのブロック除去は壊れる。**
PortalHome のネストしたブロックを regex で消したところ括弧が 1 つ合わなくなり、
designcheck が `型、または名前空間の定義、またはファイルの終わりが必要です` を出した。
ツール化するなら**構文を理解する削除**（JSON は構造操作・スクリプトはブロック単位）が要る。

## 副産物: 導入初手の罠

`Designer/Design/designer.settings.Development.json.sample` は**コメント付き JSON** で、
「このファイルをコピーして `<REPO_ROOT>` を置換する」と書いてある。
しかしコメントを残したままだと**接続が黙って失敗**し、designcheck が
「テーブル 'xxx' がデータソースに存在しません」を **73 件**出す（設定が読めない、とは言わない）。
テンプレートを受け取った人が最初に踏む罠。

```

# ワークツリー内に LocalData/{db,designs,storages} を作り、本体 DB をコピー
# designer.settings.Development.json をワークツリー内のパスで作る（コメントを入れない）

python Designer/tools/check_navigation.py --design-dir Designer/Design
python Designer/tools/lint_design.py --design-dir Designer/Design --ddl-dir Designer/ddl
python docs/15_再利用性レビュー/_prototype/check_db_dangling.py <worktree>/LocalData/db/business-app_v1.db
```

サーバの実機起動は行っていない（本体の 5085 番・本体 DB・`LocalData/designs` を共有するため。
起動する場合は `ASPNETCORE_URLS` / `ConnectionStrings__BusinessAppSQLite` / `DesignFileDirectory` /
`FileStorages__0__Directory` の 4 つを環境変数で振り替える必要がある）。
