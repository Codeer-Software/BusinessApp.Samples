# 依存方向の原則（提案）

> **本書は提案であり、まだ規約ではない。** 採用するなら `docs/10_部品アーキテクチャ` §1・§3 を
> 本書の内容で置き換え、本書は役目を終える（`expires`: docs/10 への取り込み完了時）。

再利用性の核心は**依存方向が一方向であること**である。双方向の依存（循環）は、
どちらの部品も単独で取り出せなくする点で最悪であり、実測でもそのとおりだった——
[01_依存の実測](01_依存の実測.md) で見つかった逆流 2 件は、**どちらも双方向の輪**であり、
[02_抜き取り実験](02_抜き取り実験.md) で実害が出たのもその 2 件だけである。

## 1. レイヤ定義（実測に合わせた修正版）

現行の `docs/10 §1` との違いは 1 点、**`Shell/` を性格の違う 2 つに割る**こと（[03 の P11](03_改善提案.md#p11)）。

| レイヤ | 名前 | 部品 | 何を知ってよいか |
|---|---|---|---|
| **L0** | 基盤 | `Shell/`（通知・パスワード変更）・`MasterSystem/`・`MasterBusiness/` | **何も知らない**（同レイヤの下位マスタのみ） |
| **L1** | 会計 | `Accounting/`・`FinancialReports/`・`Bank/` | L0 |
| **L2** | 業務 | `Sales/`・`Purchasing/`・`Expense/`・`Timesheet/` | L0・L1 |
| **L3** | 集約 | `Management/`・**`Portal/`**（`PortalHome`・`PortalSidebar`・`Portal*Data`） | L0〜L2（**DB 語彙でのみ**・§3） |
| — | 合成ルート | `PageFrames/*.frm.json` | すべて（下記） |

**`PageFrames` は合成ルート（composition root）として扱う。** どのモジュールを組み合わせるかを
宣言する場所であり、ここが全レイヤを参照するのは正しい。逆に言えば、
**部品どうしを繋ぎたくなったら、まずフレームで繋げないかを考える**。

`Bank/` を L1 に置くか任意部品にするかは [03 の P10](03_改善提案.md#p10) の論点。

### なぜ Shell を割るのか

実測すると、`Shell/` の中身は依存方向が正反対の 2 種類だった。

| 中身 | 部品から使われるか | 部品を知っているか | 実際のレイヤ |
|---|---|---|---|
| `Notification`・`PasswordChange` | **使われる**（経費が通知を送る） | 知っている（要修正・P9） | L0 であるべき |
| `PortalHome`・`PortalSidebar`・`Portal*Data` | **どの部品からも使われない**（実測で利用元ゼロ） | 7 部品すべてを知る | **L3** |

つまり現在の `Shell/` は L0 と L3 を兼ねている。図の上では最下層に見えるのに実体は最上位にあり、
これが「Shell を触ると何が壊れるか」を直感に反させている
（抜き取り実験では 3 構成とも**手直しの大半が Shell に集中**した）。

フォルダを割っても**依存の実体は 1 ミリも変わらない**。変わるのは、
図と実装が一致し、上向きの参照が `Portal/` に隔離されることである。

## 2. 禁止（例外なし）

1. **下位レイヤが上位レイヤのモジュール型を参照すること**
   （`new X()` / `ModuleSearcher<X>` / キャスト / `<X>`）
2. **同一レイヤの部品どうしが相互に参照すること**（循環）
3. **下位テーブルに仕掛けたトリガが、上位部品のテーブルを読み書きすること**
   — 静的検査に映らないため最も危険。実例 `trg_partners_name_label`（[03 の P1](03_改善提案.md#p1)）

現行で 1 に違反しているのは `Shell/Notification → Expense/ExpenseRequest` の 1 件、
3 に違反しているのは `partners` のラベル保守トリガ 2 本。**この 3 本ですべてである。**

## 3. どうしても上位を知りたくなったら

CLB では**古典的な依存性逆転（インターフェースを下位に置き、実装を上位から注入する）はできない**。
スクリプトにインターフェースの概念が無く、モジュール型は自動生成のプロキシで、
DI コンテナにも手が届かない。確認した範囲では**イベント／コールバック機構も無い**
（承認エンジンが申請モジュールを逆参照しているのは、完了を通知する手段が他に無かったためである）。

代わりに、**「抽象を文字列やデータで表し、具体は上位が供給する」**という形で同じ効果が得られる。
本アプリには既に成功例がある。

| # | 手段 | 下位が持つ「抽象」 | 具体を供給するのは | 実例 | 強さ |
|---|---|---|---|---|---|
| ① | **データ契約（弱リンク）** | 種別文字列＋ID の列 | 上位が書き込む | `journal_entries.source_type` / `source_id` | **最強**。下位は上位の存在すら知らない |
| ② | **URL 文字列での遷移** | 遷移先を文字列で持つ | 上位（またはフレーム） | `NavigationService.NavigateTo("/Accounting")` | 強い。ただし綴り誤りは `check_navigation.py` でしか気づけない |
| ③ | **値の登録（レジストリ）** | 汎用の受け皿列 | 上位が登録する | 提案 P9 の `notifications.link_url` | 強い |
| ④ | **DB 語彙での読み取り** | （抽象なし） | — | `Portal*Data` の契約 SQL | **弱い。上向き依存が残る** |

**① が本アプリで最も成功している設計判断である。** `journal_entries` が `invoices(id)` への FK を
持っていたら会計が営業を知ることになり、「会計だけ取り出す」は成立しなかった。
文字列 1 本で方向を守っている。

**④ は集約層（L3）に限って許す。** ポータルと経営管理は「全部を横断して見る」ことが仕事なので、
上位が下位を知るのは定義どおり正しい。ただし**モジュール型ではなく DB 語彙（テーブル・列）で読む**こと。
型で読むと部品を消した瞬間にデザインが壊れ、DB 語彙なら SQL の該当部分を削るだけで済む。

### 原則（1 行）

> **下位が上位を知る必要が出たら、型ではなくデータで持つ。**

通知（P9）も承認（P3）も、この 1 行を当てれば逆流が消える。
承認については、CLB にコールバックが無い以上「承認完了時に申請側を呼ぶ」は諦め、
**申請側が承認履歴を読みに行く**向きに変えることになる（制御の逆転ではなく、依存の除去で解く）。

## 4. どう守るか

規約は破られたことに気づけて初めて規約になる。本レビューの試作
（`_prototype/deps_json.py` / `deps_script.py` / `deps_sql.py` / `deps_ddl.py`）は、
110 モジュールの依存グラフを機械抽出できるところまで動いている。

これに**許可された辺の宣言**（レイヤ定義）を与えれば、逆行を error として落とせる。

```
# 構想: Designer/tools/check_layers.py
#   L0 = Shell MasterSystem MasterBusiness
#   L1 = Accounting FinancialReports Bank
#   ...
#   同レイヤ間・上向きの型参照を error、DB 語彙の上向き読み取りは L3 のみ許可、
#   下位テーブルのトリガから上位テーブルへの書き込みを error
```

新しい逆流が入った瞬間に落ちるので、レビューのたびに人が見張る必要が無くなる。
ツール化は [03 の P7](03_改善提案.md#p7)（DB 参照切れ検査）と同じ枠組みに載る。

## 5. オニオン／クリーンアーキテクチャとの対応

語彙を接続しておく。厳密な一致ではなく、判断の拠り所として。

| 一般的な呼び方 | 本アプリでの対応 |
|---|---|
| ドメイン／エンティティ（最内） | **L1 会計**（複式簿記の不変条件。法令で決まり、ほぼ変わらない） |
| ユースケース／アプリケーション | **L2 業務**（商流・申請。会社ごとに違い、最も直される） |
| インターフェースアダプタ／UI | PageFrame・各モジュールのレイアウト |
| インフラ | L0 基盤マスタ・認証・通知の器 |
| 合成ルート | **PageFrames** |

一般的なオニオンと違うのは、**マスタ（L0）が最内ではなく最外に近い位置に置かれている**こと。
会計が科目・税区分マスタを参照するので L0 は L1 より下になる。これは業務アプリでは自然で、
「安定していて汎用的なものほど下」という**安定依存の原則**には合致している。

守るべき本質は層の名前ではなく、次の 1 点に尽きる。

> **揮発性の高いもの（各社でカスタマイズされる業務）が、安定したもの（会計・マスタ）に依存する。逆は無い。**

本アプリはこの一点を、最も重要な軸（会計 ⇔ 業務）で既に達成している。
残っているのは横断機能（通知・承認）の 3 本だけである。
