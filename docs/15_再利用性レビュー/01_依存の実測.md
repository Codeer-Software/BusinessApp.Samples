# 依存の実測（部品間の結合を全件抽出した結果）

対象: モジュール 110 本（JSON・スクリプト・クエリ SQL）／PageFrame 14 枚／DDL 80 本／サーバ側 C#。
抽出方法は `_prototype/` の解析スクリプト（JSON は `ModuleName`/`Module`/`TopPageModule`/`ModuleUrlSegment`
の 4 キーのみ、スクリプトは `new X()` / `<X>` / `as X` / キャストの型参照のみ、SQL は `FROM`/`JOIN` の実表名）。

## 1. 結論: 依存の向きはほぼ守られている

**110 モジュール規模で「下方向のみ」の違反は 2 件だけ。** これは相当に良い数字である。

| 違反 | 実体 | 文書の記載 |
|---|---|---|
| Shell → 経費（型参照） | `Shell/Notification.mod.cs` の `ModuleSearcher<ExpenseRequest>`（通知の遷移先解決） | 未記載 |
| 基盤マスタ → 営業・購買（DB トリガ） | `trg_partners_name_label` / `_vi` が `partners` の UPDATE で quotes/sales_orders/acceptances/invoices/vendor_invoices を書く | 未記載 |

`docs/10 §3.3` が「例外は 3 つだけ」と宣言している横結合は、**実測でも 3 つだけ**だった
（営業→購買の相殺入金／営業→工数の SES 精算／経費→会計の少額資産）。
ただし工数側の相手は文書の `TimeEntry` ではなく `TimeEntryAdmin`（軽微な記述ずれ）。

## 2. 会計コアは業務を知らない（最重要の良い点）

`Accounting/` から業務部品への参照は**ゼロ**（JSON・スクリプト・SQL のいずれも）。
業務→会計の起票は次の弱リンクだけで成立している。

```sql
journal_entries.source_type TEXT   -- 'expense' / 'invoice' / 'receipt' / 'bank' ... FK なし
journal_entries.source_id   INTEGER
```

会計側が解釈する `source_type` は `cashbook` / `depreciation` / `import` / `template` / `bank` の
**会計・銀行自身の値だけ**で、業務部品の値を分岐に使っている箇所は無い。
つまり業務部品を全部外しても、会計は `source_type` が NULL の伝票を淡々と扱うだけで動く。

**この 1 点が「会計だけ取り出せる」の根拠**であり、実験（[02](02_抜き取り実験.md)）で裏付けられた。

## 3. 結合は SQL 層に集中している

型参照は綺麗だが、**テーブルを直接読む SQL** は部品をまたぐ。集中しているのは 2 箇所。

| 読み手 | 読む先 | ファイル |
|---|---|---|
| Shell（ポータル） | 会計・銀行・経費・営業・購買・工数・経営管理の 7 部品 | `Portal{Todo,Queue,Alert,Kpi}Data.Query.sql` の 4 本 |
| 経営管理 | 会計・営業・購買・経費・工数の 5 部品 | `{BudgetVsActual,CashFlowForecastData,CostAllocation,ProjectProfit}.Query.sql` の 4 本 |

これは `docs/10 §3.2` が「契約」として意図的に許容した設計で、**判断としては妥当**
（部品のモジュール型を参照せず、DB 語彙だけで読む）。ただし削除コストはここに集中する。
なお `PortalKpiData` は会計のテーブルしか読まないため、**どの構成でも無改修で動く**。

## 4. 基盤に混ざっているもの（部品を外しても残る）

基盤モジュールの利用元を逆引きした結果、**特定の 1 部品からしか使われていない基盤モジュール**が 6 本ある。

| 基盤モジュール | 置き場所 | 使う部品 | 構成A で残ると |
|---|---|---|---|
| ApprovalFlowTemplate / ～Member / ～Order | MasterSystem | 経費のみ | MasterAdmin に「承認テンプレート」が残る |
| ApprovalRouteRule | MasterSystem | 経費のみ | MasterAdmin に「承認ルート判定」が残る |
| ExpenseCategory | MasterSystem | 経費のみ | MasterBusiness に「経費科目」が残る |
| DepartmentMember | MasterSystem | 経費のみ（承認の walk-up 解決） | 組織マスタとしては必要なので残ってよい |

**承認一式が経費部品の中にあり、承認マスタだけが基盤にある**という捩れが本質。
`ApprovalFlow`（エンジン）・`ApprovalInbox`・`ApprovalHistory`・`MyApplication` は `Expense/` に置かれている。
結果として「会計＋営業に承認を足す」が現状の構造では**できない**。

## 5. 基盤テーブルに部品固有の列が生えている

| 基盤テーブル | 生えている列 | 由来部品 | 画面に出るか |
|---|---|---|---|
| `projects` | `ses_monthly_rate` `ses_lower_hours` `ses_upper_hours` `ses_deduct_rate` `ses_excess_rate` | 営業（SES 精算） | **出る**（`MasterBusiness/Project` に入力欄 5 つ＋説明ラベル 3 つ） |
| `partners` | `bank_code` `branch_code` `account_type` `account_no` `payee_kana` | 購買（FB 振込） | 出ない（モジュールがフィールド化していない） |
| `app_users` | `has_sales_access` `can_use_expense` `can_use_timesheet` | 各部品 | 出る（権限チェックボックス） |

`projects` の SES 欄は、営業を外した構成で**誰も使わない入力欄がエンドユーザーに見える**状態になる。
`app_users` の機能フラグは「基盤が上位部品の名前を知る」形だが、権限モデルの性質上ある程度は不可避
（ただし部品を足すたびに基盤の DDL 改修が要る点は設計上の負債）。

## 6. サーバ側 C# は結合していない

`BusinessApp.Server/Services/` は AI・パスワードポリシー・ライセンス等の基盤のみ。
業務固有は `Controllers/InvoiceCheckController.cs`（インボイス番号の国税庁照合）1 本だけで、
これは取引先マスタ（基盤）の機能。**C# 層は部品の取り外しに影響しない。**

## 7. DDL は部品で割れていない

`Designer/ddl/` は `000_auth.sql` 〜 `670_project_department.sql` の**時系列マイグレーション 80 本**。
うち **27 本が複数部品にまたがる**（例: `280_select_labels.sql` は MasterBusiness と Sales、
`590_vendor_invoice_project.sql` は会計・購買・基盤マスタの 3 部品）。

したがって「会計部品のスキーマ一式」を取り出す手段が無い。
テンプレートを受け取った会社は、使わない部品のテーブルを作る DDL も全部流すことになる。
（[03 の P5](03_改善提案.md#p5) で改善案）
