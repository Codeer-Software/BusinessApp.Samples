# カスタマイズ性と部品の切り方

[03_改善提案](03_改善提案.md) が「不要な部品を外せるか」を扱うのに対し、本書は
**「部品は残すが自社に合わせて直す」ときの直しやすさ**と、**そもそもの部品の区切りが妥当か**を扱う。

## カスタマイズしやすさについて（取り外し以外の観点）

**良い点**: 税率・税区分・閾値（`system_thresholds`）・科目の役割（`accounts.account_role`）は
マスタ化されており、ハードコードを避ける規律が効いている。**この方向をさらに広げるべき**。

**気になる点**:

- **選択肢がモジュール JSON 直書き**（`Candidates: ["銀行振込,bank", "現金,cash", "相殺,offset"]`）。
  部品構成で増減する選択肢は、マスタか enum に寄せると取り外しが機械化できる。
- **1 モジュールのスクリプトが長い**（`Receipt` 614 行・`JournalEntry` 500 行超）。
  「ノーコードで大半」という訴求に対し、実際に手を入れる導入先は数百行を読むことになる。
  緩和策として、長いスクリプトの先頭に**カスタムポイントのコメント規約**
  （「自社ルールで変えるならここ」）を置くと、テンプレートとしての価値が上がる。
- **エラー文言に科目コードが埋まっている**（「買掛金(2000)の科目がありません」）。
  科目マスタを変えた導入先で文言だけ嘘になる。

## 部品の切り方そのものについて

現在の 7 部品は業務単位として妥当。ただし **「承認」「通知」「案件」は横断機能**であり、
レイヤの上下だけでは表現できない。本レビューで見つかった歪みは 3 つともここに集中している。

横断機能は「低い所に置けば上位を知る必要が出て逆流し（通知）、高い所に置けば他部品から使えなくなる（承認）」
という同じ病気の裏表である。解き方は [05_依存方向の原則 §3](05_依存方向の原則.md)。

| 横断機能 | 現状 | 提案 |
|---|---|---|
| 承認 | 経費部品の中 | 独立部品へ（P3） |
| 通知 | 基盤にあるが経費を型で知る | URL 保存で依存を消す（P9） |
| 案件 | 基盤マスタ（正しい）だが SES 属性が混入 | 部品固有属性を追い出す（P4） |
