# 改善提案（再利用性・優先度つき）

**P7・P8 は実装済み（2026-08-18）。残りは提案まで。** 着手する場合は上から順に。
大きいもの（P3）は ADR を起こしてから。

| # | 提案 | 効果 | 規模 |
|---|---|---|---|
| [P1](#p1) | 上向きに書く DB トリガを部品側へ移す | 部品を外すと基盤が壊れるのを止める | 小 |
| [P8](#p8) | 設定ファイル雛形からコメントを外す | 導入初手の罠を消す | **済** |
| [P5](#p5) | DDL を部品別スキーマとして取り出せるようにする | **テンプレート配布の前提条件** | 中 |
| [P7](#p7) | DB オブジェクトの参照切れ検査を正式化 | 静かな失敗を機械検出 | **済** |
| [P6](#p6) | 削除手順書を実測ベースで書き直す | 手順どおりで壊れないようにする | 小 |
| [P9](#p9) | 通知の遷移先を「URL 保存」に変える | Shell→経費の型参照が消える | 小 |

## P1. 上向きに書く DB トリガを部品側へ移す {#p1}

**問題**: `trg_partners_name_label` / `trg_partners_name_label_vi`（`280_select_labels.sql` /
`360_receipt_offset.sql`）は、基盤マスタ `partners` の UPDATE で営業・購買のテーブルを書く。
部品を外すと**取引先の名称変更が実行時エラーで失敗する**（[02](02_抜き取り実験.md) で実測）。
designcheck・check_navigation・lint_design のどれも検出しない。

**なぜ今の形になったか**（尊重すべき判断）: 請求書は 4 経路で INSERT されるため、
ラベル保守をアプリ層に置くと経路ごとに漏れる。トリガなら経路を問わず整合する（`280` のコメント）。
この判断自体は正しい。問題は**トリガの置き場所**であって、トリガを使うこと自体ではない。

**提案**: トリガを「どのテーブルに仕掛けるか」ではなく **「どの部品の都合か」で置き場所を決める**。
`trg_partners_name_label` は営業の都合なので営業部品の DDL に置く（P5 の部品別スキーマとセット）。
部品を外す＝その部品の DDL を流さない／DROP する、に一元化される。

**併せて規約化**: 「基盤テーブルに仕掛けるトリガが上位部品のテーブルを書く場合、
そのトリガは上位部品の DDL に置く」。これだけで同型の再発が止まる。

**検出は P7 で担保**（試作ツールは構成A で 6 件・構成C で 1 件を正しく検出し、
全部入りでは 0 件＝誤検出なし）。

## P8. 設定ファイル雛形からコメントを外す {#p8}

**状態: 実装済み（2026-08-18）**

`Designer/Design/designer.settings.Development.json.sample` はコメント付き JSON で、
「コピーして使え」と書いてある。コメントを残すと接続が黙って失敗し、
designcheck が「テーブルが存在しません」を 73 件出す（設定が読めないとは言わない）。

**やったこと**: `designer.settings.Development.json.sample` からコメントを外し、
注意書きを `"_README"` キーに移した（**未知のキーは読み込み時に無視されることを実測**——
`_README` を入れた設定で designcheck が 0 で通ることを確認済み）。
セットアップの正典 `LocalData/README.md`（ADR-0025）にも罠の説明を追記した。

サーバ側の `appsettings.Development.json.sample` は**変更していない**。
ASP.NET Core の JSON 設定プロバイダはコメントを許容する（`JsonCommentHandling.Skip`）ため、
こちらは罠にならない。

## P5. DDL を部品別スキーマとして取り出せるようにする {#p5}

**問題**: `Designer/ddl/` は時系列マイグレーション 80 本で、27 本が複数部品にまたがる。
「会計だけのスキーマ」を取り出す手段が無い＝**テンプレートとして渡すものが無い**。

**提案**: 現行スキーマの**スナップショットを部品別に生成**する。

```
Designer/ddl/
  migrations/   ← 既存の 000〜670（開発環境を追随させる履歴。そのまま残す）
  schema/
    00_base.sql        基盤・マスタ（MasterSystem / MasterBusiness / Shell）
    10_accounting.sql  会計（Accounting / FinancialReports）
    15_bank.sql        銀行明細（P10 で任意部品化するなら分ける）
    20_sales.sql       営業
    30_purchasing.sql  購買
    40_expense.sql     経費精算＋承認（P3 なら承認を別ファイルへ）
    50_timesheet.sql   工数
    60_management.sql  経営管理
```

テーブル→部品の対応は**モジュールの `DbTable` から機械的に得られる**
（`_prototype/deps_ddl.py` が既にやっている）。生成ツールを作れば、
以後スキーマを変えても再生成できる。ビュー・トリガ・インデックス・初期データも同じ振り分けに従う。

**導入先の手順が「使う部品の SQL を上から流すだけ」になる**のが狙い。

## P7. DB オブジェクトの参照切れ検査を正式化 {#p7}

**状態: 実装済み（2026-08-18）**。`Designer/tools/check_db_dangling.py` として昇格し、
`CLAUDE.md` §5 の検証ループ表と `docs/README.md` の静的検査行に登録した。

```
python Designer/tools/check_db_dangling.py            # 既定の DB
python Designer/tools/check_db_dangling.py <db>       # DB を指定
```

検証:

| 対象 | 期待 | 結果 |
|---|---|---|
| 本体 DB（全部入り） | 0 件 | **0 件**（誤検出なし） |
| `vendor_invoices` を落としたコピー | 検出 | `trg_partners_name_label_vi` を **1 件検出**（終了コード 1） |
| 抜き取り実験・構成A | 検出 | 残ったビュー 3 本を **6 件検出** |
| 抜き取り実験・構成C | 検出 | 残ったトリガ **1 件検出** |

**部品削除以外でも効く**（テーブル改名時の取り残し検出）。

本ツールで拾えない範囲（`run_all.ps1` への組み込み・クエリ SQL の実表検証）は
[README の保留リスト](README.md#保留リスト)に積んだ。

## P6. 削除手順書を実測ベースで書き直す {#p6}

`docs/10 §4` の現行手順は 4 点で実態と合わない。

| 現行 | 実測 |
|---|---|
| 「箇所の特定は designcheck の findings を正とする」（§3.3） | Receipt は designcheck 4 箇所に対し**実際は 17 箇所**。条件分岐・選択肢は見ない |
| ビュー・トリガに言及なし | 構成A で 3 ビュー・2 トリガの取り残しが実行時に効いた |
| テーブル DROP の順序に言及なし | 素朴な DROP は FK 制約で失敗する |
| Portal\*Data は「該当 SELECT 部を削る」 | `PortalAlertData` は CTE が絡み、削るのではなく書き直しになる |

**提案**: 手順を 4 層に分け、各層に検査コマンドを紐づける。

1. **デザイン層** — モジュール／フレーム削除 → `designcheck`（型参照・フレーム登録）
2. **遷移層** — サイドバー・ポータルの導線削除 → `check_navigation.py`
3. **契約層** — `Portal*Data` の SQL と出力列 → （P2 で機械化するまでは目視チェックリスト）
4. **DB 層** — テーブル・ビュー・トリガ（FK 順序に注意）→ `check_db_dangling.py`

さらに「部品が持ち込んだ**選択肢・条件分岐**」を層 1 の目視項目として明記する
（`Candidates` の値、`== "offset"` のような文字列比較）。

## P9. 通知の遷移先を「URL 保存」に変える {#p9}

**問題**: `Shell/Notification.mod.cs` の `ResolveLinkUrl` が受信者の権限を見て
経費のフレーム URL を組み立てており、その過程で `ModuleSearcher<ExpenseRequest>` を使う。
**基盤が上位部品を型で知る唯一の箇所**で、部品を足すたびにここへ分岐が増える。

**提案**: 通知レコードに解決済み URL（または「宛先ごとの URL」）を保存し、送信側＝部品側が作る。
`notifications` に `link_url TEXT` を足し、`Notification.Send()` の引数に加える。
Shell 側は保存された URL に飛ぶだけになり、型参照も分岐も消える。

**注意**: 現行の分岐は「同じ通知でも受信者の権限で遷移先が違う」問題を解いている（ADR-0069）。
送信側は宛先ユーザーを知っているので**送信時に宛先ごとの URL を決められる**はず。
移行時は既存通知（`link_url` が NULL）へのフォールバックが要る。

## P2. ポータル契約 SQL を部品ごとに分ける {#p2}

**問題**: `Portal{Todo,Queue,Alert,Kpi}Data` の 4 本が 7 部品を読む。
`PortalQueueData` は 1 列＝独立副問い合わせなので機械的に削れたが、
`PortalAlertData` は CTE 連鎖で絡み、174 行を 19 行に**書き直す**羽目になった。

**提案（本命）**: 契約モジュールを**部品ごと**に割る。

```
Shell/PortalKpiData          （会計のみ・現状どの構成でも無改修で動く）
Shell/PortalQueueAccounting  （会計・銀行）
Sales/PortalQueueSales       （定期請求・SES）※所有は部品側でもよい
Expense/PortalQueueExpense
Management/PortalAlertCash   （資金ショート予測の重い CTE はここに隔離）
...
```

部品を外す＝そのモジュールを消す＋`PortalHome` の該当ブロックを消す、で完結する。
`PortalHome` は「存在するモジュールだけ読む」形に整える。

**代償**: ポータルのクエリ本数が 4 → 8〜10 に増える（いずれも 1 行返す軽いクエリ）。
`docs/13 §3` の契約表もモジュール単位に組み替える必要がある。

**軽い代替案**（本命が重いと判断する場合）: SQL の書き方だけ規約化する。
「契約 SQL は 1 列 1 独立副問い合わせ。部品をまたぐ CTE 連鎖を作らない」＋
`-- @part:Sales` のマーカーコメント。これだけで `PortalAlertData` も機械削除の対象になる。

## P4. 基盤テーブルから部品固有の属性を追い出す {#p4}

`MasterBusiness/Project`（基盤マスタ）に SES 精算条件の入力欄が 5 つ＋説明ラベル 3 つある。
営業を外した構成では**誰も使わない欄がエンドユーザーに見える**。

**提案**: 1:1 の拡張モジュールに移す。`Sales/ProjectSesTerms`（テーブル `project_ses_terms`）を作り、
案件マスタからは外す。列 `projects.ses_*` は移行して DROP。

`partners` の振込 5 列（`bank_code` 等）は**画面に出ていない**ので優先度は低い。
ただし部品別スキーマ（P5）を作るときは購買側に振り分ける。

## P10. 銀行明細取込を任意部品に格上げ {#p10}

`Bank/` は現在レイヤ1（会計）の一部だが、実測の依存は Accounting・MasterBusiness・MasterSystem のみで、
**外すのは容易**（`PortalQueueData` の `bank_pending` 列と Accounting フレームのリンクだけ）。

「会計は要るが銀行明細の自動取込は要らない」という導入先は現実にあり得るので、
任意部品に格上げしておくと構成の自由度が上がる。`docs/10 §1` の表を 1 行変えるだけで済む。

## P3. 承認を独立部品にする {#p3}

**問題**: 承認エンジン一式（`ApprovalFlow` `ApprovalFlowMember` `ApprovalHistory` `ApprovalInbox`
`MyApplication`）が `Expense/` の中にあり、承認マスタ（テンプレート・ルート判定）だけが
`MasterSystem/` にある。この捩れのため、

- 構成A（会計のみ）では **MasterAdmin に使われない承認マスタ画面が残る**
- **「会計＋営業」に承認を足せない**（エンジンが経費部品の中にあるため）

**提案**: `Approval/` を独立部品（レイヤ1、任意）として切り出す。

- 移す: `ApprovalFlow` `ApprovalFlowMember` `ApprovalHistory` `ApprovalInbox` `MyApplication`
  ＋ `ApprovalFlowTemplate*` `ApprovalRouteRule`（MasterSystem から）
- 切る: `ApprovalFlow → ExpenseRequest` の逆参照。`approval_flow` は既に汎用の申請参照を持てる形なので、
  **申請モジュール名＋ID の文字列**で扱い、承認完了後の処理は申請側が承認履歴を読んで行う向きに変える
- 経費は「承認部品の利用者」になる。営業の受注稟議・購買の発注承認にも同じエンジンを載せられる

**規模は大きい**（ADR 必須）。ただし構成③（会計＋営業）を公式にサポートすると決めた以上、
「営業に承認を付けたい」という要望は高確率で来る。そのときに作り直すより、
部品として切っておくほうが安い。

**先行して安くできること**: 承認マスタ（テンプレート・ルート判定）だけでも `Expense/` 側に寄せれば、
構成A で MasterAdmin に残る不要画面は消える。エンジンの汎用化は後回しにできる。
