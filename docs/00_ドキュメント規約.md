# ドキュメント規約

> 本リポジトリの `.md` 文書すべてに適用する。**唯一の入口は [README.md](README.md)**（何をするときに何を読むか）。
> 本書はその索引が成立し続けるための約束事を定める。

## 1. なぜこの規約があるか

長期開発では文書が増え続け、**どれが正か分からなくなり**、読む側（人間・Claude Code の両方）の
コンテキストを圧迫する。量そのものは問題ではない。読まなくていい文書を読まずに済むなら、
`historical` はいくら増えてもコストにならない。

したがって本規約の目的は 2 つだけである。

1. **読まなくていい文書を、開いて数行で判別できること**
2. **`current` の本文が、常に「今どうなっているか」だけを語っていること**

フロントマターはその手段であって目的ではない。

## 2. 適用範囲

- 対象: **Git 追跡下の `.md` すべて**（`docs/` 配下＋`CLAUDE.md`・`README.md`・
  `Designer/Project.md`・`LocalData/README.md`・`tools/README.md`）
- 対象外:
  - `Designer/CLAUDE.md` と `Designer/ClaudeCodeForDesigner/` … **デザイナが再生成する生成物**。
    手で直しても次のワークスペース更新で失われる（前者は追跡下にあるが対象外）
  - Git 追跡外のファイル全般（`Designer/LocalEnvironment.md`・`LocalData/` 配下など）
  - ベンダー同梱ファイル（`BusinessApp/` 配下）

## 3. フロントマター

全対象文書の先頭に YAML フロントマターを置く。

```yaml
---
title: 会計ドメイン設計              # 見出しと同じでよい
status: current                     # current | superseded | historical（3値のみ）
scope: 会計コア                      # 対象領域（部品名 / 業務名 / 全体）
audience: [開発]                    # 開発 | 運用 | 営業 | テスト（複数可）
updated: 2026-08-23                 # 内容を変えた日
supersedes: []                      # この文書が置き換えた文書のパス
related: [decisions/0004-仕訳の不変性.md]
---
```

### 3-1. 必須フィールド

| フィールド | 規則 |
|---|---|
| `title` | 短い名詞句。見出しと揃える |
| `status` | `current` / `superseded` / `historical` の 3 値のみ（§3-2） |
| `scope` | 対象領域。部品名（会計コア・証憑 …）／`全体` |
| `audience` | `開発` `運用` `営業` `テスト` から 1 つ以上 |
| `updated` | **内容を変えたときだけ**更新する。体裁変更では動かさない |

### 3-2. `status` の判定

**`status` が肝である。`current` 以外は「読まなくていい」と最初の数行で判断できる。**

| 値 | 意味 | 中身の扱い |
|---|---|---|
| `current` | 現在の仕様・計画・手順。読めば今の姿が分かる | **常に現在形に保つ**（§4） |
| `superseded` | 後継がある。`related` に後継を必ず書く | **消さない・直さない**（判断の経緯が失われる） |
| `historical` | 当時の記録として価値がある（リサーチ・実施記録・レポート） | **消さない・直さない**（記録なので現在形化しない） |

`superseded` と `historical` の違いは「後継があるか」。

### 3-3. ADR（`decisions/`）の特則

ADR は判断ログなので原則として書き換えない。`status` は決定の生死で決める。

| 状況 | `status` |
|---|---|
| 決定が現在も有効（大半） | `current` |
| 後継 ADR が決定を覆した | `superseded`（`related` に後継 ADR） |
| 検討して見送った記録 | `historical` |

**一部だけ覆された ADR は `current` のまま**とし、本文冒頭の「状態」行に部分 supersede を明記する。

### 3-4. 任意フィールド

| フィールド | 使う文書 | 意味 |
|---|---|---|
| `verified: 2026-08-23` | `tests/` 配下 | **最後に実機で通した日**。`updated`（文書を直した日）とは別物 |
| `growth: append` | 台帳・ログ型 | 追記専用で必ず育つ文書。行数警告を免除する代わりに分割方針を本文に持つ |
| `expires: <終了条件>` | 一時文書 | 移行計画・レポートなど、役目を終える予定があるもの（§4-4） |

## 4. 本文の書き方

### 4-1. `current` の文書は常に現在形に書き換える

追補・読み替え表・注記で積み上げない。**過去との差分ではなく、今どうなっているかを書く。**

### 4-2. ヘッダに更新履歴を積まない（禁止）

```
✗ > 更新: 2026-08-23 ADR-0005 を反映 ／ さらに更新: 2026-09-01 UI 改訂
```

これは**ファイル内読み替え表**であり、本文が旧記述のまま取り残される事故を必ず起こす。

- 変更の**経緯**は ADR に書く → `related:` でリンクする
- 変更の**日付**は `updated:` が持つ
- 本文は**書き換える**

### 4-3. 古い情報は消す。追記で肥大化させない

**既定の更新方法は「追記」ではなく「書き換え」である。** 文書を触るたびに、
「この文書に、もう事実でない記述・重複した記述が残っていないか」を確認して**消す**。

- **消すことをためらわない。** すべて Git 管理下にあり、履歴からいつでも復元できる。
  「念のため残す」は肥大化の最大の原因である
- **追記が正しいのは 2 種類だけ** — ADR（判断ログ）と、`growth: append` を付けた台帳・ログ型文書。
  それ以外の文書に追記していたら、それは書き換えを怠っているサインである
- **定期棚卸し**: フェーズの区切り・大きな機能追加のたびに、`current` の文書を一覧し
  「250 行を超えたもの」「もう `historical` でよいもの」「同じ事実を二重に書いているもの」を洗い出して整理する
- **実装の経過を記録する文書を作らない。** 何をしたかは git log、なぜそうしたかは `decisions/`、
  CLB の踏み抜きは `qa/` と `11_CLB改善提案/` が既に持っている。「実装履歴」文書はそれらの劣化コピーになり、
  受け皿がある限り必ずリポジトリ最大の文書に育つ

### 4-4. 「後で直す」を本文に書かない

保留は本文ではなく**保留リスト**に積む。置き場所は対象ディレクトリの `README` 末尾。書式:

```
- 2026-08-23 ADR-0007: 04_会計ドメイン設計 に補助元帳の節を追加（未了）
```

読み替え表との違いは、**これが解消される前提の一時リスト**であること。
`lint_docs.py` は `current` 文書の未処理マーカーを警告する。除外されるのは、保留リストの節、
コードブロックの中、行末に `lint-docs:ignore` を書いた行、および `decisions/` と `research/`
（自身の未確認事項を本文で列挙するのが正しい姿の文書）。

### 4-5. 一時文書には終了条件を書く

移行計画・レポートのように**役目を終える予定がある文書**は、作る時点で `expires:` に終了条件を書く。
条件を満たしたら即 `historical` にする。

### 4-6. 同じ事実を 2 箇所に書かない

書くならリンクする。とくに**マスタ化された値**（税率・控除割合・閾値）を複数の文書に直書きすると、
マスタを変えた瞬間に全部が嘘になる。コードで「制度値をハードコードしない」と定めているのと
同じ規律を文書にも適用する。

### 4-7. 呼称は「ユーザー＝エンドユーザー」「開発者＝作る側」

**「ユーザー」はこのアプリの使用者（顧客の経理担当・経営者・税理士）だけを指す。**
作る側（リポジトリの開発者・Claude Code）を「ユーザー」と呼ばない——指すときは「開発者」と書く。
正典は `CLAUDE.md`。既存文書の混在は一括置換せず、触った文書から直す。

### 4-8. 公開リポジトリに書いてはいけないもの

このリポジトリは GitHub のパブリックリポジトリへ公開する。

- **絶対パスを書かない。** リポジトリ直下は `<REPO_ROOT>` と表記する
- **ユーザー名・ホスト名・個人のメールアドレスを書かない**
- **接続文字列・API キー・トークン・パスワードを書かない**（秘密は .NET User Secrets）
- 検査: `python tools/docs/lint_secrets.py`（コミット前に流す）

### 4-9. 制度・法令の記述には出典と確認日を付ける

税率・控除割合・期限・要件を書くときは、**必ず一次情報（国税庁・e-Gov・財務省・ASBJ 等）の URL と
確認日**を併記する。記憶や推測で書かない。制度は毎年変わるため、出典と確認日が無い記述は
半年後に信用できなくなる。

## 5. 1 文書 1 責務・行数

- 目安は **250 行**。超えたら分割を検討する（機械的な上限ではなく、警告として出す）
- **台帳・ログ型（`growth: append`）は行数警告の対象外**。代わりに**最初から分割方針を持たせる**
  （月別・番号帯別）
- **「引くもの」は行数の対象外。** `decisions/`（ADR）と `research/`（制度リサーチ）は
  必要なときに 1 本だけ開く文書であり、通読しない。行数警告からも管理指標からも除く
- 管理指標は「**毎回・頻繁に読む `current` の総行数**」とする（上記を除いた合計）

## 6. 検証（`tools/docs/lint_docs.py`）

```
python tools/docs/lint_docs.py            # 規約違反の検査（error / warn）
python tools/docs/lint_docs.py --stats    # current の行数など指標
```

検査項目:

| 種別 | 内容 |
|---|---|
| error | フロントマターが無い／`status` が 3 値以外／必須フィールド欠落／`supersedes`・`related` のリンク先が実在しない |
| error | `superseded` なのに `related` が空／ADR の実ファイルと `decisions/README.md` の行が食い違う |
| warn | `current` で 250 行超（`growth: append` は除く）／`docs/*.md` が `README.md` の索引に載っていない |
| warn | `current` の冒頭 20 行に `更新:` `追補:` が積まれている／`current` の本文に未処理マーカーが残っている |

## 7. 運用（毎回の作法）

1. 文書を追加・改名したら **`README.md` の索引**を更新する（lint が突合する）
2. 判断をしたら **ADR** を起こし、`decisions/README.md` に 1 行足す（lint が突合する）
3. 後回しにするものは**保留リスト**へ（§4-4）
4. コミット前に `python tools/docs/lint_docs.py` と `python tools/docs/lint_secrets.py` を流す
5. **マージ前に別の目を通す**（[CLAUDE.md](../CLAUDE.md) §3-2-1）。
   **lint はフロントマターとリンク切れしか見ない。** §4-6 の重複も、
   文書どうしの矛盾も、機械では捕まらない
