# ドキュメント規約

> 本リポジトリの `.md` 文書すべてに適用する規約。**唯一の入口は [README.md](README.md)**（何をするときに何を読むか）。
> 本書はその索引が成立し続けるための約束事を定める。

## 1. なぜこの規約があるか

文書が 200 本・25,000 行を超え、コンテキストを圧迫している。ただし**量そのものは問題ではない**。
読まなくていい文書を読まずに済むなら、`historical` はいくら増えてもコストにならない。実際の問題は 3 つだった。

1. **どれが正で、どれが読み替え済みかが文書の外にしかない。** 本文が旧前提のまま「別表で読み替える」運用になっていた。
2. **タスク起点の索引が無い。** `README.md` が文書の一覧であって案内になっていなかった。
3. **1 文書の責務が肥大している。** 毎回の起点である進捗台帳が 1,000 行を超えていた。

したがって本規約の目的は 2 つだけである。**「読まなくていい文書を判別できること」**と**「本文が現在形であること」**。
フロントマターはその手段であって目的ではない。

## 2. 適用範囲

- 対象: **Git 追跡下の `.md` すべて**（`docs/` 配下＋`CLAUDE.md`・`Designer/CLAUDE.md`・`Designer/Project.md`・`README.md`・`LocalData/README.md`）
- 対象外:
  - `Designer/ClaudeCodeForDesigner/` … デザイナが `ai-refresh` で再生成する生成物（Git 追跡外・手で編集しない）
  - Git 追跡外のファイル全般（`Designer/temporary/`・`Designer/LocalEnvironment.md` など）
  - ベンダー同梱ファイル（`BusinessApp/**/open-iconic/README.md` など）

## 3. フロントマター

全対象文書の先頭に YAML フロントマターを置く。

```yaml
---
title: 部品アーキテクチャ          # 見出しと同じでよい
status: current                   # current | superseded | historical（3値のみ）
scope: 全体                       # 対象領域（部品名 / 業務名 / 全体）
audience: [開発]                  # 開発 | 運用 | 営業 | テスト（複数可）
updated: 2026-08-16               # 内容を変えた日
supersedes: []                    # この文書が置き換えた文書のパス
related: [decisions/0040-部品アーキテクチャとPageFrame再編.md]
---
```

### 3-1. 必須フィールド

| フィールド | 規則 |
|---|---|
| `title` | 短い名詞句。見出しと揃える |
| `status` | `current` / `superseded` / `historical` の 3 値のみ（§3-2） |
| `scope` | 対象領域。部品名（経費精算・会計 …）／業務名／`全体` |
| `audience` | `開発` `運用` `営業` `テスト` から 1 つ以上 |
| `updated` | **内容を変えたときだけ**更新する。体裁変更・フロントマター追加では動かさない |

### 3-2. `status` の判定

**`status` が肝である。`current` 以外は「読まなくていい」と最初の数行で判断できる。**

| 値 | 意味 | 中身の扱い |
|---|---|---|
| `current` | 現在の仕様・計画・手順。読めば今の姿が分かる | **常に現在形に保つ**（§4） |
| `superseded` | 後継がある。`related` に後継を必ず書く | **消さない・直さない**（判断の経緯が失われる） |
| `historical` | 当時の記録として価値がある（リサーチ・実施記録・レポート・移行の対応表） | **消さない・直さない**（記録なので現在形化しない） |

`superseded` と `historical` の違いは「後継があるか」。後継が特定できるなら `superseded`、
単に当時の記録なら `historical`。

### 3-3. ADR（`decisions/`）の特則

ADR は判断ログなので原則として書き換えない。`status` は決定の生死で決める。

| 状況 | `status` | 補足 |
|---|---|---|
| 決定が現在も有効（大半） | `current` | 現行仕様の根拠として引かれる |
| 後継 ADR が決定を覆した | `superseded` | `related` に後継 ADR |
| 検討して見送った・実装に反映されていない記録 | `historical` | |

**一部だけ覆された ADR は `current` のまま**とし、本文冒頭の「状態」行に部分 supersede を明記する
（ADR-0007・0041 が既にこの形をとっている。踏襲する）。`related` に後継を書く。

### 3-4. 任意フィールド

| フィールド | 使う文書 | 意味 |
|---|---|---|
| `verified: 2026-08-17` | `tests/` 配下 | **最後に実機で通した日**。`updated`（文書を直した日）とは別物。腐りの検出に使う（§7）。**初期値は実施日の記録が無いため最終更新日から機械的に置いた**——以後は実際に通した日で更新する |
| `growth: append` | 台帳・ログ型 | 追記専用で必ず育つ文書。行数警告を免除する代わりに分割方針を本文に持つ（§5） |
| `expires: <終了条件>` | 一時文書 | 移行計画・読み替え表・レポートなど、役目を終える予定があるもの（§4-4） |
| `modules:` / `verifies:` / `screens:` | `tests/20_体験シナリオ/` | そのシナリオが触るモジュール・画面（§6） |

## 4. 本文の書き方

### 4-1. `current` の文書は常に現在形に書き換える

追補・読み替え表・注記で積み上げない。**過去との差分ではなく、今どうなっているかを書く。**

### 4-2. ヘッダに更新履歴を積まない（禁止）

```
✗ > 更新: 2026-08-13 ADR-0053 を反映 ／ さらに更新: 2026-08-17 UI 改訂で入力の道筋が変わった
```

これは**ファイル内読み替え表**であり、本文が旧記述のまま取り残される事故を必ず起こす
（実例: `tests/20_体験シナリオ/01_経費精算/01` でヘッダが否定した旧 UI が本文に残っていた）。

- 変更の**経緯**は ADR に書く → `related:` でリンクする
- 変更の**日付**は `updated:` が持つ
- 本文は**書き換える**

`lint_docs.py` は `current` 文書の冒頭 20 行に `更新:` `さらに更新:` `追補:` があれば警告する。

### 4-3. 「後で直す」を本文に書かない

保留は本文ではなく**保留リスト**に積む。置き場所は対象ディレクトリの `README` 末尾。書式:

```
- 2026-08-16 ADR-0064: 05_購買_支払/01・03 に案件欄の記述を追加（未了）
```

読み替え表との違いは、**これが解消される前提の一時リスト**であること。
`lint_docs.py` は `current` 文書の `TODO` `未了` `後述` を警告する。

### 4-4. 一時文書には終了条件を書く

移行計画・読み替え表・監査レポートのように**役目を終える予定がある文書**は、作る時点で
`expires:` に終了条件を書く。条件を満たしたら即 `historical` にする。

> 実例: `tests/19_部品再編2026-08_読み替え表.md` は 2026-08-09 に役目を終えていたが、
> 終了条件が書かれていなかったため 8 日間「まだ読む必要があるかもしれない文書」として残り続けた。

### 4-5. 同じ事実を 2 箇所に書かない

書くならリンクする。とくに**マスタ化された値**（承認ルートの金額境界・`PAY_DUE_SOON_DAYS` などの閾値・
税率）を複数の文書に直書きすると、マスタを変えた瞬間に全部が嘘になる。
コードで「閾値をハードコードしない」と定めているのと同じ規律を文書にも適用する。

### 4-6. 呼称は「ユーザー＝エンドユーザー」「開発者＝作る側」

**「ユーザー」はこのアプリの使用者（顧客）だけを指す。** 作る側（リポジトリの開発者・Fable）を
「ユーザー」と呼ばない——指すときは「開発者」と書く。正典は `CLAUDE.md` §0-1。
既存文書の混在は一括置換せず、触った文書から直す。

## 5. 1 文書 1 責務・行数

- 目安は **250 行**。超えたら分割を検討する（機械的な上限ではなく、警告として出す）。
- **台帳・ログ型（`growth: append`）は行数警告の対象外。** 追記専用の文書に「短くしろ」は無理筋なので、
  代わりに**最初から分割方針を持たせる**（月別・番号帯別）。例: 実装履歴は `05_history/2026-08.md`。
- **管理指標は「毎回・頻繁に読む `current` の総行数」**とする。`decisions/` は `current` でも
  この指標から除く（参照時に 1 本だけ引く文書であり、通読しないため）。`lint_docs.py --stats` が出す。

## 6. テスト文書の約束

### 6-1. 体験シナリオは触るモジュールを宣言する

`tests/20_体験シナリオ/` の全ファイルはフロントマターに次を持つ。

```yaml
modules: [Purchasing/VendorInvoice, Purchasing/PaymentSchedule]   # データを作る・変える
verifies: [Accounting/JournalBook, Shell/PortalHome]              # 確認のために開くだけ
screens: ["購買・支払 > 仕入先請求書", "会計業務 > 帳簿 > 仕訳帳"]
```

**なぜ要るか**: 機能を直したとき「どの体験シナリオが影響を受けるか」を知る手段が、無ければ全本を読むことしかない。
放置すれば台本が腐り、台本を追った人が「画面が違う」に出くわしたとき
**それが台本の腐りなのか実装のバグなのか区別できなくなる**。体験シナリオは説明書ではなく**回帰テストの網**なので、
腐ると検知能力そのものを失う。

宣言があれば `lint_docs.py --impact` が影響範囲を機械的に出せる（§7）。
`verifies:` も必ず書く——確認に使う画面が変わっても台本は腐るため。
閲覧だけのシナリオ（権限ツアー等）は `modules:` が空でよいが、**両方が空は許さない**。

### 6-2. 台本の更新は層で分ける

| 層 | いつ直すか |
|---|---|
| ① 導線・画面名・項目名 | **機能変更と同じコミットで直す。** 数行で済み、間違っていると台本が能動的に嘘をつく |
| ② 期待値（金額） | その場で、ただし**実際に通した分だけ**（全本を再実行しない） |
| ③ 大規模な設計変更 | 実装完了までまとめる。ただし**着手時に影響ファイル一覧を残す**（`--impact` の出力を貼る） |

### 6-3. 期待値は揮発性で置き場所を変える

腐りやすいものを、更新コストが高い媒体に置かない。

| 層 | 例 | 置き場所 |
|---|---|---|
| **不変条件** | 貸借一致／ヘッダ合計＝明細合計／繰越の整合 | `qa/20_不変条件SQL/`（SQL） |
| **導出関係** | 請求額＝検収明細の合計／仕訳貸方＝税抜＋税 | 文書（相対表現） |
| **絶対値** | 12,800 円／No.84／Σ借方 25,813,055 | 原則書かない（下記の例外のみ） |

**絶対値を書いてよいのは「その数字自体が仕様を表しているとき」だけ。**

- 書く: 税の端数処理の結果・経過措置 80%・少額資産の 10 万/20 万/30 万・年額按分の 1/12
- 書かない: 現在の DB の状態（仕訳総数・残高・未読件数）・採番結果

採番・仕訳番号は既に**相対表現**（「その時点の最終番号 +1」）と決まっている。同じ方針を金額にも適用する。
**ドキュメントは"道筋"を書く。数字は SQL が守る。**

## 7. 検証（`Designer/tools/lint_docs.py`）

```
python Designer/tools/lint_docs.py              # 規約違反の検査（error / warn）
python Designer/tools/lint_docs.py --stats      # current の行数など指標
python Designer/tools/lint_docs.py --impact HEAD~1   # 変更が影響する体験シナリオ
python Designer/tools/lint_docs.py --stale      # verified より後にモジュールが変わった台本
```

検査項目:

| 種別 | 内容 |
|---|---|
| error | フロントマターが無い／`status` が 3 値以外／必須フィールド欠落／`supersedes`・`related` のリンク先が実在しない |
| error | `superseded` なのに `related` が空／`tests/20_体験シナリオ/` に `modules:` が無い／宣言されたモジュールが実在しない |
| error | ADR の実ファイルと `decisions/README.md` の行が食い違う |
| warn | `current` で 250 行超（`growth: append` は除く）／`docs/*.md` が `README.md` の索引に載っていない |
| warn | `current` の冒頭 20 行に `更新:` `追補:`／`current` に `TODO` `未了` `後述` |

## 8. 運用（毎回の作法）

CLAUDE.md §4 のサイクルに組み込む。

1. 機能を変えたら **`lint_docs.py --impact HEAD~1`** を流し、影響する体験シナリオの①層を**同じコミットで**直す
2. 実機で通した台本は `verified:` を更新する
3. 文書を追加・改名したら `README.md` の索引を更新する（`lint_docs.py` が突合する）
4. 判断をしたら ADR を起こし、`decisions/README.md` に 1 行足す（`lint_docs.py` が突合する）
5. 後回しにするものは保留リストへ（§4-3）
