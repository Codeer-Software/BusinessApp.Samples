# ISSUE-0006: 検収確定の仕訳が明細の税区分に関わらず一律 `SALES_10` を書く

- 起票: 2026-08-17（バグ狩り BUG-0127 を独立文書に切り出したもの）

  再挑戦の内容と根拠は **§5** に書いた。
- ユーザー判断（2026-08-17）: **「残タスクとして埋もれない場所に残す。自分でもコードを見る」**

> **この文書は「次に触る人が同じ道を辿らないため」に書いてある。**

## 1. 何が起きているか

`Sales/Acceptance.mod.cs` の `RecalcFromLines`（`:304-335`）は **ADR-0050 のとおり明細の税区分ごとに
グループ化し、税率ごとに 1 回だけ端数処理して正しい税額を出している**。ここは無傷である。

壊れているのは**仕訳行に付ける税区分タグ**だけ。`Confirm_OnClick` が生成する仕訳は、
売上行にも税行にもコード直書きの `SALES_10` を貼る。

```
Acceptance.mod.cs:559-564   cs.AddEquals(c => c.Code.Value, "SALES_10");
Acceptance.mod.cs:616       売上行に salesTaxCatId を設定
Acceptance.mod.cs:625       税行に salesTaxCatId を設定
```

### 実害

| 状況 | 何が狂うか |
|---|---|
| 軽減 8% の明細を含む検収 | 税額は 8% で正しく計算されるのに**仕訳が 10% 区分**になり、消費税集計表・科目別税区分表の税率別内訳が狂う |
| 非課税売上／免税売上だけの検収 | 税額 0 で税行が出ないのに**売上行が「課税売上 10%」に分類され、課税売上高が過大**になる（課税売上割合・簡易課税判定にも波及） |
| 経理が `SALES_10` をリネーム・無効化 | `salesTaxCatId` が null になり、`Accounting/JournalEntry.mod.cs:214` の `MarkRemainingLinesOutOfScope()` が**売上行を黙って「対象外」に落とす**＝課税売上が消費税集計から丸ごと消える |

### 現時点で顕在化しているか

**していない。** 実 DB の検収 9 件・`acceptance_lines` 15 行はすべて `SALES_10` で、混在は 0 件。
生成済みの仕訳（No.71 / No.84 等）は結果的に正しい。

**ただし潜在ではない。** `tax_categories` に `SALES_8`（軽減）・`SALES_EXPORT`（免税）が
`is_active=1` で実在し、**明細のドロップダウンから選べる**（実測）。選んだ瞬間に踏む。

## 2. 直そうとして何が起きたか（撤回の記録）

**2026-08-17 に実装 → 3 回診断 → 3 回とも外す → 撤回。**

税区分ごとに「貸方 売上行 ＋ その消費税行」を生成する方式に書き換えたところ、

```
je.Lines.AddRows(lineCount) が実行時に
Value cannot be null. (Parameter 'source')
```

で落ち、**検収の確定が全件失敗する状態になった**（＝売上計上ができない P0 リグレッション）。

| コミット | 内容 |
|---|---|
| `af6591d` | 実装 |
| `abd34da` | 修正試行 1 |
| `10cb85a` | 修正試行 2 |
| **`a7936c5`** | **撤回（元の実装に戻した）** |

**税区分タグの正しさより、売上計上が動くことを優先した判断である。**

### 最も重要な教訓

**`designcheck` は 3 回とも 0 件、不変条件も全緑のまま素通りした。画面でボタンを押すまで誰も気づけなかった。**
CLB スクリプトの実行時エラーは静的検査に一切かからない。

### 外した診断（同じ道を辿らないために）

詳細は `docs/12_CLB改善提案/01_機能改善提案.md` の **FB-053**。**原因は未特定のまま**である。
推測を「既知の罠」として書き残すほうが有害なので、そこには「原因未特定」と正直に書いてある。

**分かっている事実は 1 つだけ**:

> 動いている 6 箇所はいずれも `AddRows` の引数を**1 文で確定**させている（リテラルか三項演算子）。
> **`for` ループ内で行数を積み上げているのは、失敗した実装だけ**である。

> **2026-08-18 追記: この見立ては外れている。** `FixedAsset.mod.cs:739` と
> `ExpenseRequestAccounting.mod.cs:344` は、どちらも**ループで積み上げたリストの `.Count`** を
> `AddRows` に渡していて正常に動く（前者は 8/18 に実機で確認済み）。
> 差は引数の作り方ではなく、**行の中身をどう持っていたか**にあったと考えられる。

## 3. 再挑戦するときの手がかり

### 案 A: 行数を 1 文で確定させる

失敗した実装と動いている 6 箇所の唯一の差分がここなので、まずこれを試す価値がある。
税区分の種類数を先に数え、`AddRows(kinds * 2)` のように**1 式で**渡す。
**ただし原因が未特定なので、これで直る保証は無い。**

### 案 B: 税区分ごとに伝票を分ける（1 検収 = n 伝票）

各伝票の行数が 2 か 3 で確定するので、**既存の動いている形のまま書ける**。
代償は伝票が増えること——1 枚の検収に対して複数の売上仕訳が立つ設計判断になる。

### 案 C: 複数税率をサポートしないと明示する（**現時点の推薦**）

明細の税区分が 1 種類のときだけ従来どおり動かし、複数のときは**確定時にエラーで止める**。
実務では税率ごとに検収を分けてもらう。

**推薦する理由**: 現在の実害は「**気づけないこと**」である。黙って誤った税区分を書き続けるより、
「この検収は税率が混在しているので分けてください」と正直に止めるほうが安全で、実装も小さい。

### 案 D: あきらめる

税区分タグの誤りを**既知の制約として文書化するだけ**にする。
税額そのものは正しいので、消費税の納付額は狂わない。狂うのは**内訳の表示**である。

## 5. 再挑戦（2026-08-18）

**案 A を選び直した。ただし前回と違うのは「書き方」である。**

行の内容を**プリミティブの並行リスト**に組んでから、`AddRows(dcList.Count)` で一度に行を確保し、
添字で埋める。

```csharp
var dcList   = new List<string>();   // 借方/貸方
var accList  = new List<object>();   // 科目 id
var amtList  = new List<int>();      // 金額
var catList  = new List<object>();   // 税区分 id（借方 売掛金は null → 対象外に落ちる）
var taxFlag  = new List<bool>();     // 消費税行か
var parentList = new List<int>();    // 税行の親行番号
...
je.Lines.AddRows(dcList.Count);
```

**この形はこのリポジトリで唯一実績のある形**である（`FixedAsset.mod.cs:739` の処分仕訳、
`ExpenseRequestAccounting.mod.cs:344` の経費仕訳）。モジュール型のオブジェクトをコレクションに
持ち回らず、プリミティブだけで組み立てる点が要である。

### 仕訳の形

```
借方 売掛金        税込合計        （税区分なし → 対象外）
貸方 売上高        区分Aの税抜額    税区分 = 区分A
貸方 仮受消費税    区分Aの税額      税区分 = 区分A・is_tax_line・parent = 上の行
貸方 売上高        区分Bの税抜額    税区分 = 区分B
貸方 仮受消費税    区分Bの税額      税区分 = 区分B・is_tax_line・parent = 上の行
```

伝票は **1 検収 = 1 伝票**のまま（案 B は採らない）。

### 端数の扱い

ヘッダの税額は **税率ごとに 1 回**端数処理する（ADR-0050）。仕訳は**税区分ごと**に分けるので、
同じ税率の区分が 2 つあると切り捨ての和が 1 円ずれうる。
**差額は先頭の課税区分の税行で吸う**——こうすればヘッダと仕訳の税額が必ず一致し、不変条件 C03 が保たれる。

### まだやっていないこと

**実機検証。** `designcheck` は 8/17 の失敗時も 3 回とも 0 件だった。
**画面で「検収を確定」を押し、①10% 単独 ②8% 軽減を含む混在 ③非課税のみ、の 3 通りを確認するまで
「直った」と言わないこと。** 失敗したら §4 の作法どおり、まず動く状態に戻す。
