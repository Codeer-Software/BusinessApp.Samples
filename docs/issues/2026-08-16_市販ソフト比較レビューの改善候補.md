# 市販ソフト比較レビューで見つかった改善候補（2026-08-16 起票）

> 出所: `docs/14_市販ソフト比較レビュー.md`。市販 4 社（freee 会計／マネーフォワード クラウド会計／
> 弥生会計／勘定奉行クラウド）の公式ドキュメントと、よろずの実機（`http://localhost:5085`）を
> 突き合わせて出た「負け」のうち、**見送り（`docs/03_機能スコープ.md` §7）ではないもの**を改善候補として起票する。
>
> **実装はしない。** ユーザーが優先度を見て GO を出したものだけ着手する（CLAUDE.md §4）。
> 比較レビューは 1〜3 章（基盤マスタ／会計／営業業務）まで完了。4 章以降で見つかったものは本ファイルに追記する。
>
> **章と記号の対応**: A=会計／B=基盤マスタ／S=営業業務（以降 P=購買／E=経費精算／T=工数管理／M=経営管理を予定）

## 優先度の考え方

| 優先度 | 意味 |
|---|---|
| **最高** | デモで必ず触られる導線にあり、無いと「会計ソフトの代替」を名乗れない |
| **高** | 実運用に入った初月に必ず不満が出る。乗り換えの障害になる |
| **中** | あると効率が上がるが、無くても業務は回る |
| **低** | 見送り済み事項の再検討、または規模の割に効果が薄いもの |

## 見送り済みで、本レビューでも「触らない」と再確認したもの

`docs/03_機能スコープ.md` §7 の判断を覆す必要は無いと判断した。営業トークでの説明の仕方だけ 14 章に書いた。

| 項目 | 市販ソフトの状況 | 据え置きの理由 |
|---|---|---|
| 銀行 API による明細自動取得 | MF 2,300 以上／弥生 Next 2,500 以上の金融機関と連携 | 認証・契約が必要でデモ環境では実現不能。CSV 取込・ルール・残高照合は実装済みで、API は導入時に足す領域 |
| 消費税申告書の様式出力 | 弥生 26 は全グレード、奉行は標準機能 | 数字は消費税集計表で合っている。様式転記は税理士／別ツールの領域 |
| 電子申告（e-Tax / eLTAX） | 奉行は標準、freee は別製品 freee 申告 | 同上。税理士連携領域 |
| 電子帳簿保存法の完全準拠（JIIMA 認証相当） | 4 社とも対応をうたう | タイムスタンプ・事務処理規程は運用領域。ただし**検索性は実装するとしていた**ので J-3・J-6 は候補に残す |

## A. 会計部品（14 章 §2.4）

### A-1. 試算表 → 元帳 → 伝票のドリルダウンが無い 〔優先度: 最高 / 見積: 中〕

**実測（2026-08-16）**: 合計残高試算表（`/Accounting/TrialBalance`）の科目行をクリックしても何も起きない。
総勘定元帳（`/Accounting/GeneralLedger`）の「伝票No」列もプレーンテキストで、振替伝票に飛べない。

**なぜ効くか**: 勘定奉行クラウドは「**会計数字の根拠をクリックで確認できます**」を確認作業の看板機能として
[機能一覧](https://www.obc.co.jp/bugyo-cloud/kanjo/function/list)に掲げている。
残高 → 明細 → 伝票を降りるのは経理が月次で必ず行う動作で、**市販ソフトからの乗り換え時に最初に不満が出る場所**。
逆に言うとデモで最も効く改善でもある。

**実装の見通し**: 試算表の科目行 → 総勘定元帳（勘定科目と期間を検索条件として引き継ぐ）、
元帳の伝票No → 振替伝票の詳細、の 2 本のリンク。同一部品内なので `GetModuleDataUrl` で解決できるはず。
遷移先の妥当性は `Designer/tools/check_navigation.py` で静的検査すること。

### A-2. 合計残高試算表に部門・案件の絞り込みが無い 〔優先度: 高 / 見積: 小〕

**実測**: 合計残高試算表の検索条件は **日付（自）／日付（至）の 2 つだけ**。
一方、総勘定元帳には 補助科目（任意）／部門（任意）／案件（任意） がある。**同じ部品の中で非対称**。

**なぜ効くか**: 残高試算表を部門で見るのは市販ソフトの標準機能。
MF は「[残高試算表で部門ごとに金額が確認できる](https://biz.moneyforward.com/support/account/guide/office02/of07.html)」、
弥生はプロフェッショナル以上、奉行は部門別推移表・対比表を標準で持つ。
そして**部門別損益はペルソナの痛点 #1（案件別の損益がリアルタイムに見えない）の入口**なので、
勝ち筋の補強にもなる。

**実装の見通し**: `FinancialReports/TrialBalance` の Query SQL と検索フィールドの拡張。
元帳側に同じ絞り込みが既にあるので、SQL の書き方を流用できる可能性が高い。
なお **MF は部門別の決算書（BS/PL）は作れない**と明記しているので、
試算表レベルまで対応すれば市販ソフトに追いつく。BS/PL の部門別は別途判断。

### A-3. 仕訳に取引先の項目が無く、金額でも検索できない（電帳法の検索要件） 〔優先度: 高 / 見積: 大〕

**実測**: 振替伝票のヘッダは 伝票番号・取引日・会計年度・伝票種別・摘要・状態、
明細は 貸借・勘定科目・補助科目・部門・プロジェクト・税区分・税入力・金額・摘要。
**取引先の項目はヘッダにも明細にも無い**（`Accounting/JournalEntry.mod.json`・`JournalLine.mod.json` でも確認）。
検索条件は 振替伝票一覧が 取引日・摘要・状態、仕訳帳が **日付のみ**。

**なぜ効くか**: 国税庁は電子取引データについて
「取引年月日その他の日付・取引金額・主要な記録項目を検索条件にできること、日付・金額は範囲指定できること、
2 以上の記録項目を組み合わせられること」を求めており
（[Ⅱ 適用要件【基本的事項】](https://www.nta.go.jp/law/joho-zeikaishaku/sonota/jirei/07denshi/02.htm)）、
実務では「**日付・金額・取引先**で検索できること」と要約される。
**よろずは仕訳側でこの 3 点検索が成立しない。**
`docs/03_機能スコープ.md` §5 の横断要件は「証憑: 仕訳・経費申請へのファイル添付（日付・金額・取引先で検索可能
= 電帳法の実務土台）」と書いているので、**仕様として宣言済みなのに未実装**という位置づけになる。

**設計上の論点（ADR を起こしてから着手すべき）**:
- 取引先を **仕訳ヘッダに置く**か **明細に置く**か。弥生は補助科目で代替する文化、freee は取引先タグ、
  奉行は取引先マスタを持つ。よろずは補助科目を持っているので、
  「売掛金の補助科目＝取引先」で運用する道もある（その場合は補助科目の自動生成が論点になる）。
- 業務部品からの自動仕訳（検収・請求・入金・仕入先請求書）は取引先を知っているので、
  項目さえ作れば埋めるのは容易。手入力の振替伝票だけが任意入力になる。

### A-4. 弥生インポート形式（25 列 CSV）での仕訳エクスポートが無い 〔優先度: 高 / 見積: 中〕

**実測**: 「仕訳インポート」（汎用 CSV 取込）はあるが、エクスポートは帳票の Excel 出力のみ。
Excel 出力は「読む」ためのもので、税理士のソフトには取り込めない。

**なぜ効くか**: 弥生は導入社数の絶対王者で、**会計事務所連携の事実上の標準**。
弥生は仕訳日記帳から「弥生インポート形式」で書き出す
（[仕訳データを書き出す（エクスポート）方法](https://support.yayoi-kk.co.jp/faq_Subcontents.html?page_id=18042)）。
MF・freee・奉行は「税理士をメンバーに招待してリアルタイム共有」で応戦しており、
よろずも同じ手（税理士にアカウントを発行する）は使えるが、
**顧問税理士が弥生を使っている場合の出口が無い**のは実運用で効く。
中小 IT 企業の顧問税理士が弥生であるのはむしろ普通。

**仕様は公開されている**（[仕訳データの項目と記述形式](https://support.yayoi-kk.co.jp/subcontents.html?page_id=18545)）:
25 列・1 仕訳 1 行・カンマ区切りで、
識別フラグ／伝票No./決算／取引日付／借方勘定科目／借方補助科目／借方部門／借方税区分／借方金額／借方税金額／
貸方勘定科目／貸方補助科目／貸方部門／貸方税区分／貸方金額／貸方税金額／摘要／番号／期日／タイプ／生成元／
仕訳メモ／付箋1／付箋2／調整。必須は 識別フラグ・取引日付・借方/貸方勘定科目・借方/貸方税区分・借方/貸方金額・タイプ・調整。

**実装の見通し**: 科目名・税区分名のマッピングをマスタ化すれば、
弥生以外の形式（MF・freee の取込 CSV）にも展開できる汎用のエクスポート基盤になる。
複合仕訳（3 行以上）を 1 行 1 仕訳の形式にどう落とすかが最大の論点（弥生は「諸口」を使う）。

### A-5. 定型仕訳の明細に補助科目・プロジェクトを持てない 〔優先度: 中 / 見積: 小〕

**実測**: `Accounting/JournalTemplateLine` の項目は 行・貸借・勘定科目・**部門**・金額（税込）・税区分・税入力・摘要。
振替伝票の明細には 補助科目・プロジェクト があるのに、定型仕訳の明細には無い。

**なぜ効くか**: 案件付きの定型仕訳（外注費の案件配賦、SES 原価の計上など）が作れない。
また補助科目が無いため、口座を指定した定型（「メインバンク普通預金からの家賃引落」など）も作れず、
起票後に手で直すことになる。ペルソナは受託・SES が中心で**案件を付ける仕訳が日常**なので、
定型仕訳の価値が半減している。

### A-6. 仕訳への証憑（ファイル）添付が無い 〔優先度: 中 / 見積: 中〕

経費申請には領収書の添付欄（`ExpenseRequest.Receipt`）があるが、仕訳側には無い。
A-3 とセットで電帳法の実務土台になる。単独でやっても検索できないので、A-3 の後に。

### A-7. 摘要辞書が無い 〔優先度: 中 / 見積: 小〕

**実測**: よろずの辞書機能は定型仕訳のみ。

**市販ソフト**: 弥生は **仕訳辞書・伝票辞書・摘要辞書・かんたん取引辞書の 4 本立て**
（[概要](https://support.yayoi-kk.co.jp/subcontents.html?page_id=17804&grade_id=Std)）。
仕訳辞書は貸借一致が必須だが、**伝票辞書は貸借の一致しない仕訳も登録できる**（片側だけのテンプレ）。
辞書と帳簿を並べて表示し、辞書からアイコンをドラッグして投入する導線まで用意されている。
弥生会計 Next にも「辞書管理（仕訳辞書、伝票辞書）」がある。

摘要辞書は入力補完だけの軽い機能なので、費用対効果は良い。

### A-8. 前期比較の試算表（前年同月対比）が無い 〔優先度: 低 / 見積: 小〕

MF の「前期比較表」、弥生会計 Next の「残高試算表（前期比較）」に相当。
月次推移表があるので優先度は低い。

## B. 基盤・マスタ部品（14 章 §1.4）

### B-1. 取引先マスタに住所・支払条件が無い 〔優先度: 高 / 見積: 中〕

**実測**: 取引先マスタの項目は 取引先コード・取引先名・ふりがな・適格請求書登録番号・
得意先・仕入先・免税事業者・有効 だけ。**郵便番号・住所・電話・担当者名・敬称・締日・支払サイトが無い。**

**なぜ効くか**: 市販ソフトは会計本体と請求書アプリを分けており、住所などは請求側の製品
（弥生請求 Next・MF クラウド請求書・freee 請求書）が持つ。
**よろずは請求書も同じアプリで出す**ので、無いことが直接効く。具体的には:
- 請求書 PDF に宛先住所を印字できない
- 締日・支払サイトから支払期限を自動計算できない（現状は都度入力のはず）
- 支払予定表・資金繰り予測の期日精度が入力依存になる

**次の作業**: 3 章（営業業務）で請求書 PDF の実装を実際に見て、
どの項目が本当に要るか（宛名の敬称、部署名、担当者名など）を確定してから起票し直す。

### B-2. 案件マスタに契約金額・予定期間が無い 〔優先度: 高 / 見積: 中〕

**実測**: 案件マスタの項目は 案件コード・案件名・取引先・種別（受託/SaaS/SES/社内）・状態・有効。
種別＝SES のときだけ SES 契約条件（月額・精算幅・控除/超過単価）が現れる。
**契約金額（請負金額）・予定期間・担当部門・PM が無い。**

**なぜ効くか**: 勘定奉行クラウド［個別原価管理］の案件・プロジェクト管理は
**「請負金額や進捗管理、予定期間などを一元管理」**すると明記している
（[案件・プロジェクト管理](https://www.obc.co.jp/bugyo-cloud/kanjo-kobetsu/function/project)）。
よろずの案件損益は**実績しか見せられず、予算対比・進捗率・完成基準の判定材料が無い**。
ここは CLAUDE.md §1 で「市販ソフトが弱く CLB が強い」と位置づけた領域そのものなので、
**負けているのではなく勝ち筋が伸ばし切れていない**という性質の候補。優先度を高くする理由。

**設計上の論点**: 受託の契約金額は受注（SalesOrder）が持っているので、
案件マスタに二重で持つのか、受注から集計するのかを決める必要がある。
複数受注が 1 案件にぶら下がる（追加開発・フェーズ分割）ケースがデモ DB に実在する
（PJ-2026-101「販売管理システム構築」＋「追加開発（フェーズ1・2）」）ので、集計側が自然かもしれない。
→ 7 章（経営管理）で案件損益の画面を見てから結論を出す。

### B-3. 案件のサブプロジェクト（工程単位の原価集計） 〔優先度: 低 / 見積: 大〕

奉行［個別原価管理］は「サブプロジェクトの管理もできるため、工程管理など」より詳細な管理ができるとしている。
ペルソナ（55 名・受託 4 件・SES 8 名）の規模では過剰の可能性が高い。要件確認が先。

## S. 営業業務部品（14 章 §3.4）

### S-1. 複数請求の一括入金（合算入金）を消し込めない 〔優先度: 高 / 見積: 中〕

**実測（2026-08-16）**: 入金画面（`/SalesBilling/Receipt/{id}`）の項目は
入金日・入金方法（銀行振込/現金/相殺）・**請求書（単一選択のドロップダウン）**・入金額（税込）・
相殺する仕入請求・備考。**1 入金 = 1 請求書**の構造になっている。

**なぜ効くか**: 同じ取引先の複数の請求がまとめて 1 本で振り込まれるのは実務では日常。
現状は入金を請求書ごとに分割して登録するしかなく、通帳の 1 行と入金レコードが 1 対 1 で対応しない。
MF クラウド債権管理はこの問題を「**消込組合せレコメンド**（複数請求・一括入金でも請求と入金を自動で紐づけ）」で
正面から解いている（[機能一覧](https://biz.moneyforward.com/receivable-management/function/)）。

**設計上の論点（ADR 案件）**: 入金を「入金 1 : 消込明細 n」に分解する必要がある。
既存の `receipts` は請求書 ID を直接持ち、消込仕訳は `journal_entries.source_type='receipt'` で紐づいている
（ADR-0051）ため、**売掛残高・資金繰り予測・ポータルの期限超過アラートの 3 か所も同時に影響を受ける**。
自動照合まで作らなくても「取引先を選ぶ → 未消込の請求書が並ぶ → チェックして金額を配分」で実務の大半は解ける。

### S-2. 銀行明細から入金消込への導線が無い 〔優先度: 高 / 見積: 中〕

**実測**: `Designer/Design/Modules/Bank/` 配下に `Receipt` への参照が 1 件も無い。
銀行明細の一括起票は仕訳を作るが、営業側の入金消込とは繋がっていない。

**なぜ効くか**: 市販ソフトは「入金事実の自動取得 → 請求との自動照合」に最も投資している。
MF は機械学習による自動照合、奉行は「国内ほぼすべての金融機関のインターネットバンキングと連携し、
入金事実を自動取得」（[債権・入金管理](https://www.obc.co.jp/bugyo-cloud/akikura/function/deposit)）。
よろずは実口座 API を持たないので**自動取得では勝てない**が、
**CSV で取り込んだ明細は既に手元にある**。同じアプリの中に銀行明細と売掛残高の両方があるのに
繋がっていないのは、A×B 一体化モデル（企画概要 §2.1）の穴。

**実装の見通し**: 銀行明細の入金行 → 金額・日付・摘要（振込人名）から候補の請求書を提示 → 選んで消込。
既存の仕訳ルール（`Bank/MatchingRule`）と同じ発想でマッチング候補を出せる。**S-1 の後**（消込明細の構造が先）。

### S-3. 売掛の年齢表・滞留一覧・督促導線が無い 〔優先度: 高 / 見積: 小〜中〕

**実測**: 売掛残高（`/SalesBilling/ReceivableBalance`）は請求書ごとの残額一覧。
**取引先別の集計行も、経過月数別の年齢表も、督促の導線も無い。**

**市販ソフト**: MF クラウド債権管理は **請求残高年齢表**（「発生の経過月数ごとに表示する管理帳票」）、
**滞留明細一覧**（入金予定日超過データの抽出）、**メール・チャット連携で営業担当者へ自動通知**、
営業ユーザー向けの閲覧専用ライセンスまで持つ。

**実装の見通し**: 取引先別サマリ＋経過月数区分（〜30日／31-60／61-90／91日〜）のピボット。
督促は作業合意（メール送信は口だけ）に照らし、**通知基盤（`Shell/Notification`）で営業担当へ通知**まで。
ポータルには既に「期限超過の売掛」アラートがあるので、そこからの遷移先として作るのが自然。

### S-4. 前受金（着手金・過入金）の起票が手動 〔優先度: 中 / 見積: 中〕

**実測**: 過入金はブロックされ、
`入金額 … が請求残額 … を超えています。過入金分は前受金(2100)として振替伝票で起票してください`
というエラーが出る（`Sales/Receipt.mod.cs`）。

**なぜ効くか**: ペルソナは「中〜大型案件は中間検収あり。**前受金・仕掛品が発生する**」（`docs/02` §2）。
着手金のある受託案件で毎回、経理が振替伝票を手で起こすことになる。
MF クラウド債権管理は「前受金自動仕訳: 入金日と売上日の比較による判定・振替処理」を持つ。

### S-5. 仕掛品（未成業務支出金）の期末振替が無い 〔優先度: 中 / 見積: 大〕

**実測**: 勘定科目 1200「仕掛品」・5030「仕掛品振替高」は存在するが、
`Designer/Design/Modules/` 全体で「仕掛品」の出現はキャッシュ・フロー計算書の SQL 1 件のみ。
**計上・振替の機能は無く、手動の振替伝票のみ。**

`docs/03_機能スコープ.md` B'-3 は「受託の検収基準売上＋**前受金・仕掛品管理**」を掲げているので、
**宣言済みで未実装**という位置づけ。期をまたぐ受託案件で原価と売上の期間対応が崩れる。

**着手前にやること**: 未検収案件に紐づく原価（工数配賦の人件費＋外注費）を集める必要があるため、
**7 章（経営管理）で案件損益・人件費配賦の実装を見てから設計を判断する。** S-4 とセットで ADR を起こす。

### S-6. 請求書のメール送付・共有 URL が無い 〔優先度: 中 / 見積: 中〕

**実測**: 請求書の出力は Excel / PDF のダウンロードのみ。送付は利用者が自分で行う。

**市販ソフト**: MF クラウドインボイスは「メール・郵送・Web 配信の中から取引先に合わせた送付方法が選択可能」、
弥生請求 Next は共有 URL リンク、freee 請求書はメール送付。

**判断が要る点**: 作業合意でメール送信は「口だけ（アダプタのみ・実環境未検証）」と決めている。
それに照らすと **共有 URL の発行**（トークン付きの閲覧専用ページ）のほうが実装しやすく、デモでも実演できる。
ただし認証外の公開ページを作ることになるので、**ユーザーの判断を仰いでから**着手すべき。

### S-7. 取引先の締日・支払サイトから支払期限を自動計算する 〔優先度: 中 / 見積: 小〕

請求書の支払期限は現在ただの入力欄。**B-1（取引先マスタの拡充）とセット**で、
月末締め翌月末払いなどの条件から自動計算する。支払予定表・資金繰り予測の期日精度にも効く。

### S-8. 入金一覧の検索に取引先・請求書番号を追加 〔優先度: 低 / 見積: 小〕

現状は 入金日範囲・消込状態のみ。件数が増えると目視で探すことになる。

### S-9. 納品書 〔優先度: 低 / 対応不要の可能性が高い〕

よろずの営業伝票は 見積・受注・検収・請求書 の 4 種で納品書が無い。
市販ソフトは 見積 → 納品 → 請求 が標準の流れだが、**ペルソナは受託開発・SES・SaaS で物品の納品が無く、
検収書が納品書の役割を果たす**。要求が出るまで作らない。
