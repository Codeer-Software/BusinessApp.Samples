## 1. 現状の問題

### 1.1 データと画面の全体像（前提）

- 明細は 1 テーブル `bank_statement_lines` に集約され、`status` 列で区別される:
  `preview`（プレビュー）→ `pending`（未起票）→ `journalized`（起票済）／`excluded`（対象外）
- 「明細取込」画面は表示専用モジュール（BankImport）で、同テーブルを status で絞った 2 つのリスト（プレビュー / 未起票）を持つ。
- 「明細一覧」は**全状態**の明細が並ぶ通帳ビュー（未起票だけが残る画面ではない）。

### 1.2 不具合（実測＋コード根拠）

| # | 症状 | 根本原因 |
|---|---|---|
| B-1 | プレビュー/未起票リストの行削除が保存されない（保存を押すと復活） | 行削除はメモリ上の行リストから消えるだけ。保存処理 `SaveListEdits()` は「いまメモリにある行」を1行ずつ Submit する方式なので、**消えた行を DELETE する者がいない**。リロードで DB から復活する |
| B-2 | プレビューで削除・編集しても「この内容で登録」に反映されない（削除した行が登録され、編集前の値で登録される） | `ConfirmImport_OnClick` は**画面のリストを見ずに DB を直接検索**（status='preview' 全行）して pending に遷移させる。メモリ上の編集・削除は完全に無視される |
| B-3 | プレビューリストの編集を保存する手段がそもそも無い | `SaveListEdits()` は未起票リスト（PendingLines）だけを対象にしており、**プレビューリスト（PreviewLines）用の保存経路が存在しない** |
| B-4 | 「AIで相手科目を推定」を押すと保存ボタンなしで DB が更新される | 推定結果を行に代入して**その場で `Submit()`** している |
| B-5 | 状態セレクトが自由編集できる | 一覧の「状態」列が編集可能なドロップダウン（候補は全4値）。**手で「起票済」にすると仕訳が無いのに起票済になる**など、状態機械を UI から破壊できる。ADR-0026 の全アプリ規約にこの画面だけ違反 |
| B-6 | 明細の原本列まで編集できる | 一覧レイアウトで**日付・摘要・出金・入金・残高も編集可能**。明細は銀行データの写し（原本）であり、書き換えると残高照合の意味が崩壊する |
| B-7 | 「対象外」にすると行き止まり | 対象外行を未起票に戻す正規の手段が無い（明細一覧は削除ボタンのみ・詳細画面なし） |
| B-8 | 明細一覧の物理削除が無条件 | **起票済の明細も削除できる**。仕訳が残って照合が壊れ、重複キー解放で同じ明細を再取込→再起票（二重仕訳）できる |
| B-9 | ボタンの配置が操作対象と対応していない | どのリストに効くボタンか読み取れない |
| B-10 | 明細一覧の説明文が誤り | 「未起票の明細がここに残り、一括起票で仕訳になると消えます」は**取込画面内の未起票リストの説明**であり、全状態が表示され続ける明細一覧には当てはまらない。実際にユーザーが「未起票だけの画面」と誤解した |
| B-11 | 未確定データが本番テーブルに混入 | プレビュー（未登録の作業中データ）が確定済み明細と同じ `bank_statement_lines` に status 違いで同居しており、明細一覧・照合など全参照箇所が「preview を除外し忘れると壊れる」構造 |

一言でまとめると、**「メモリと DB の同期規律・状態機械・原本保護・確定/未確定の分離がいずれも設計されていない」**。個別修正ではなく作り直す。

## 2. あるべき仕様（v3）

### 2.0 業務フロー（この設計の背骨）

```
① 明細取込   : 銀行 CSV を貼り付け、「通帳どおり正しく取り込めているか」だけを確認して登録する
② 一括起票   : 未起票明細に相手科目を確定させ（ルール・AI・手動）、対象外を分別し、まとめて起票する
③ 明細一覧   : 取り込んだ全明細（未起票・起票済・対象外）の通帳ビュー。監査・トレーサビリティと例外操作
（残高照合・仕訳ルールは現行どおり）
```

- **科目の確定は①でなく②で行う**（ユーザー決定 2026-07-21）: 取込担当は明細の正確さだけに集中し、会計判断（科目・対象外）は起票の場でまとめて行う。プレビューに科目列は置かない。
- 「未起票明細一覧」という独立画面は**作らない**（明細一覧の状態絞り込みで足りる。既定絞り込みも設けない）。

### 2.1 データ設計: プレビューは別テーブルに分離する（B-11 の恒久対策）

**新テーブル `bank_statement_preview`** を設け、`bank_statement_lines` には**登録済み（確定）明細だけ**を入れる:

- `bank_statement_preview`: id / bank_account_id / line_date / description / amount_out / amount_in / balance / dedup_key / imported_at（科目・状態列は持たない）
- `bank_statement_lines`: 現行から **status='preview' を廃止**し、`pending / journalized / excluded` の3値に。
- 「この内容で登録」= プレビューテーブル → 本番テーブルへの**移送**（INSERT status='pending' ＋ プレビュー行 DELETE）。
- 重複キー判定: 取込時は「本番 ∪ プレビュー」の dedup_key と突合。プレビューで原本列を修正したらキーを再計算する。
- 移行: 既存 DB に preview 行が残っていれば移行時に削除する（未登録の作業中データなので破棄が安全。件数を移行ログに出す）。

**メモリのみ案を採らない理由**: 画面遷移・リロードで作業が全損する（数百行の編集途中で誤 F5 が致命傷）。他担当者の作業中プレビュー検知（放置警告）も不可能になる。CLB の一覧編集 UI は DB バックの行で最も安定して動く、という実装上の理由もある。**別テーブル案は「本番を汚さない」というメモリ案の利点を保ちつつ、作業の永続性を残せる折衷**であり、これを推奨する。

### 2.2 状態機械（v3・唯一の正）

```
（CSV取込）→ bank_statement_preview ──「この内容で登録」──→ pending ──「候補科目で一括起票」──→ journalized
                │                                            │  ↑                                    │
                │ 行削除＋保存 / 全て取り消す                  │  │「未起票に戻す」                      │「起票を取り消す」
                ↓                                            ↓  │（明細一覧の詳細）                    （明細一覧の詳細・仕訳も削除）
              （破棄・キー解放）                            excluded
                                                pending/excluded の削除は明細一覧の詳細から（キー解放）
```

| 遷移 | 誰が | どこで | 備考 |
|---|---|---|---|
| → プレビュー | システム | 【明細取込】取込ボタン | 重複キーで既存スキップ |
| プレビュー → pending | システム | 【明細取込】「この内容で登録」 | 暗黙保存＋移送 |
| プレビュー → 破棄 | ユーザー | 【明細取込】行削除＋保存 / 全て取り消す | キー解放＝貼り直し可 |
| pending → excluded | ユーザー | 【一括起票】「対象外」チェック＋保存 ／【明細一覧】詳細「対象外にする」 | 一括は起票画面、単発は詳細 |
| excluded → pending | ユーザー | 【明細一覧】詳細「未起票に戻す」 | 誤操作の差し戻し（B-7 解消） |
| pending → journalized | システム | 【一括起票】実行 | 仕訳リンク付与 |
| journalized → pending | ユーザー | 【明細一覧】詳細「**起票を取り消す**」 | **紐づく仕訳を削除**して戻す（下記） |
| pending / excluded → 削除 | ユーザー | 【明細一覧】詳細「この明細を削除」 | キー解放。取込ミスの後始末用 |

- **「起票を取り消す」（journalized → pending）を新設する**。仕訳を残したまま状態だけ戻す操作は認めない（二重起票の道）——取り消すなら**紐づく仕訳ごと削除**する。これは検収の「確定を取り消す」・入金の「入金を取り消す」と同型のパターンで、アプリ全体の規律（docs/tests/06 冒頭「仕訳を生んだ操作の取消は該当仕訳も削除。締め済み期間は不可＝赤伝対応」）に一致する。締め済みガード・確認ダイアログ（仕訳 No 明示）・明細→親の順の削除、すべて既存実装の知見で安全に作れる。**起票済→対象外の直接遷移は設けない**（起票取消で pending に戻してから対象外にすれば足りる。遷移は最小に）。
- 「状態」列はどの画面でも**表示専用**（B-5 解消）。
- excluded も残高照合の材料である（明細として存在する事実は変わらない）ことを削除ダイアログで注意喚起。

### 2.3 画面仕様

#### 【明細取込】（BankImport 改）— 受入検査だけを行う

```
口座選択 ／ 明細CSV貼り付け欄
  └─ [明細を取り込む]
── プレビューリスト（bank_statement_preview） ──────
列: 口座・日付・摘要・出金・入金・残高（科目・状態・推定元の列は無し）
編集可: 日付・摘要・出金・入金・残高（文字化け等の受入修正。登録後は原本として凍結）
行削除: ○（保存で確定）
  └─ [プレビューの変更を保存] [この内容で登録] [全てのプレビューを取り消す]
```

- 「この内容で登録」は**暗黙に「変更を保存」を実行してから**移送する（B-2 解消。画面で消した行・直した値がそのまま登録される）。
- 未登録プレビューの放置警告（他担当者の作業検知）は現行仕様を維持（プレビューテーブルの残件で判定）。
- LimitCount は null（全件表示）。

#### 【一括起票】（BankPosting 新設）— 科目の確定と起票を行う

```
絞り込み: 口座（任意）
── 未起票明細リスト（status='pending' 全件） ──────
列: 口座・日付・摘要・出金・入金・相手科目（候補）〔編集可〕・推定元・「対象外」チェック〔編集可〕
（原本列・それ以外は表示専用。行削除なし）
  └─ [変更を保存] [ルールを適用] [AIで相手科目を推定] [候補科目で一括起票]
件数サマリ: 起票対象（候補設定済み） n 件 ／ 候補未設定 m 件 ／ 対象外チェック中 k 件
```

- **ルール適用・AI 推定はどちらもメモリのみ**（保存するまで DB は変わらない。B-4 解消）。対象は「候補が未設定の行」（メモリ上の現在値で判定——手入力を上書きしない）。ルールは決定的な辞書引き、AI は不確実な推定、という位置づけの差はあるが、**操作の作法は揃える**（どちらも押す→リストに候補が入る→保存 or 起票で確定）。
- **[候補科目で一括起票] は暗黙に「変更を保存」を実行してから**、候補設定済みの pending を起票する（このリストで直した候補・付けた対象外チェックが反映されてから実行される）。確認ダイアログに件数を明示。
- 対象外チェック行は保存時に excluded へ遷移しリストから消える（一気にチェックを付けて一括で外せる）。
- この画面に行削除は無いため、保存は「全行 Submit ＋チェック行の状態遷移」だけの単純な処理で済む（差分同期が必要なのはプレビューだけになる）。
- 締め済み期間ガード・二重起票ガード・税行方式の仕訳生成・日付順の伝票採番は現行 PostAll のロジックを踏襲。

#### 【明細一覧】（BankStatementLine）— 通帳ビュー（監査）＋例外操作

- **全状態（未起票・起票済・対象外）の通帳ビュー**。既定の絞り込みは設けない（ユーザー決定）。検索: 口座・状態・日付。
- 説明文を正しいものに差し替える（B-10 解消）: 「取り込んだ銀行・カード明細の一覧です。状態（未起票・起票済・対象外）で絞り込めます。起票済の明細は仕訳とリンクしています」
- 一覧は**全列表示専用・削除ボタン廃止**（B-6/B-8 解消）。相手科目候補の編集は一括起票画面に一本化（二箇所編集は保存規律を再び曖昧にする）。
- **詳細画面を新設**: 行クリックで遷移し、状態に応じたボタン（ADR-0026 パターン）:
  - pending: 「対象外にする」（赤）／「この明細を削除」（赤・キー解放の注意書き）
  - excluded: 「未起票に戻す」（青）／「この明細を削除」（赤）
  - journalized: 「起票を取り消す」（赤・「仕訳 No.x を削除して未起票に戻します」の確認・締め済み期間は拒否して赤伝へ誘導）＋仕訳 No の表示
- 詳細画面の単発操作は確認ダイアログ＋**即 DB 反映**（対象が1件で明確なため。一覧の一括編集と規律を分ける）。

### 2.4 保存セマンティクス（各ボタンの DB への作用）

原則: **DB を書くのは「保存」「登録」「起票」「取消系」だけ**。ルール適用・AI 推定はメモリのみ。

| 画面 | ボタン | DB への作用 |
|---|---|---|
| 明細取込 | 明細を取り込む | プレビューテーブルへ INSERT のみ（未保存の編集がある場合は警告 §2.6） |
| 明細取込 | プレビューの変更を保存 | 差分同期（編集反映＋削除行 DELETE＋キー再計算） |
| 明細取込 | この内容で登録 | 暗黙保存 → 本番へ移送（INSERT pending ＋プレビュー DELETE。登録時ルール適用は Q-a） |
| 明細取込 | 全てのプレビューを取り消す | プレビュー全行 DELETE（確認ダイアログ） |
| 一括起票 | 変更を保存 | 全行 Submit（候補反映）＋対象外チェック行を excluded へ |
| 一括起票 | ルールを適用／AIで相手科目を推定 | **なし**（メモリのみ） |
| 一括起票 | 候補科目で一括起票 | 暗黙保存 → 候補設定済み pending を起票・仕訳リンク付与 |
| 明細一覧（詳細） | 対象外にする／未起票に戻す／起票を取り消す／この明細を削除 | 即時（確認ダイアログ付き。起票取消は仕訳削除を含む） |

### 2.5 差分同期の実装方式（プレビューリスト用・B-1 の恒久対策）

1. リストをリロードするたびに、ロード済み行の ID 集合をスクリプト変数に記録（スナップショット）。
2. 保存時に「スナップショットにあるが、いまメモリに無い ID」＝削除された行 → 1行ずつ `Delete()`（子なしテーブルなので物理削除が確実。Project.md 2026-07-19 知見）。
3. メモリに残っている行は 1 行ずつ `Submit()`（未変更行は無害）。
4. 同期後にリロードし、スナップショットを取り直す。

- DB 全行との突き合わせにしない（ページングで表示されていない行を誤削除する事故を防ぐ）。LimitCount null と併用。
- v3 ではこの複雑さが**プレビューテーブルに閉じる**（本番テーブルに対する削除同期は存在しない——本番の削除は詳細画面の単発操作のみ）。

### 2.6 細部仕様

- **未保存変更の警告**: 「明細を取り込む」実行時にプレビューの未保存変更を検知したら確認ダイアログ（検知が CLB API で困難なら「取込時に必ず暗黙保存」に倒す。実装時に実測して決める）。
- **推定元（rule/ai/手入力）**: 候補を手修正したら推定元を「手入力」にする（manual を候補値に追加。TEXT 列のため DDL 変更不要）。
- **重複キー（dedup_key）**: 現行方式を維持。**既存列であり本番テーブルへの新カラム追加は不要**（新設するのはプレビューテーブル側の同名列のみ）。値は原本情報から `日付|摘要|出金額|入金額|同一内容の連番` で組み立てる文字列（例: `2026/7/15|AWS ｸﾗｳﾄﾞﾘﾖｳｷﾝ|55000|0|0`。同じ日・同じ摘要・同じ金額の明細は出現順の連番で区別。残高は銀行の再出力で変わりうるため**キーに含めない**）。銀行 CSV は過去分込みで再出力されるのが普通なので、このキー一致で「取込済みスキップ」する＝取込の冪等性の要。突合は口座単位。削除＝キー解放＝再取込可能、を削除ダイアログに明記。
- **権限**: 現行どおり経理・sysadmin のみ。
- **残高照合**: 仕様変更なし。プレビュー分離により照合対象が構造的に「確定明細のみ」になる（現行の preview 除外条件が不要になる）。
- **明細一覧の CSV ダウンロード・冪等スキップ**: 仕様変更なし。
