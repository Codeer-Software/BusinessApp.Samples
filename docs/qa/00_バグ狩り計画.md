# 徹底バグ狩り 実行計画

> 目的: 「よろず」に眠っている不具合を、**機械的に・網羅的に**発見し、修正する。
> 副目的: 今回の作業で **恒久的な検証基盤**（デザインリンタ・不変条件SQL・バグ台帳）を残し、以後のバグ混入を継続的に防ぐ。
> 起案: 2026-08-16。実行方針は §7 のユーザー決定に従う。

---

## 1. 前提となる実測事実（推測ではない）

長時間の自律運用を設計するにあたり、Claude Code 自身の能力を**実測**した。以下は 2026-08-16 時点の事実。

| 論点 | 結果 | 根拠 |
|---|---|---|
| ヘッドレス `claude -p` からのブラウザ操作 | **不可**（ツールが渡らない） | 実測: `TOOL_NOT_AVAILABLE` |
| サブエージェント（バックグラウンド含む）からのブラウザ操作 | **可能** | 実測: 別エージェントが `list_connected_browsers` を実行成功 |
| 同時サブエージェント数 | 既定 20（`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`）、ネスト3段 | 公式doc |
| 親セッションに返るもの | **最終テキストのみ**（ツール出力・読んだファイルは親の文脈に載らない） | 公式doc |
| 複数ブラウザ（Braveプロファイル） | 同時接続と `select_browser` による切替は可能。ただし**切替のたび人間の選択が必要**な規約がツールに組み込まれており、無人運転では使えない | ツール仕様＋実測（現在1台接続） |
| アプリの同時ログイン制限 | **存在しない**。素の Cookie 認証。制約は「ブラウザプロファイル＝クッキー壺が1つ」だけ | `CookieAuthentication.cs` / `AccountController.cs` 実読 |
| クラウド Routines | ローカルFSに触れない（毎回 clone）→ **本件では使えない** | 公式doc |
| `/loop` | セッションが生きてアイドルのときだけ発火・7日で失効 | 公式doc |

### ここから導かれる設計方針

1. **ブラウザ作業はサブエージェントに丸投げする。** スクショもページテキストもオーケストレータの文脈に載らないため、対話セッション1本で長時間の実機検証が回せる。
2. **Brave の複数プロファイルは使わない。** アプリ側に同時ログイン制限が無く、真の同時性が要る検証（楽観ロック・競合）は HTTP セッションを別に握れば足りる。プロファイルを増やすと切替のたびに人間を呼ぶことになり、無人運転が壊れる。
3. **夜間はブラウザ不要レーンだけをヘッドレスで回す。** 実機レーンは対話セッションを必要とするため、時間帯で使い分ける。

## 3. アーキテクチャ — 4レーン制

**核心: 静的解析とSQLで「仮説」を大量生産し、ブラウザは仮説の検証にだけ使う。**
ブラウザ時間が唯一の希少資源なので、そこを彷徨わせない。

| レーン | 内容 | 並列度 | ブラウザ | 夜間ヘッドレス |
|---|---|---|---|---|
| **A: 静的監査** | 103モジュール×56スクリプトを CLB 既知の失敗＋会計ドメイン知識で読む | 10〜20 | 不要 | 可 |
| **B: データ不変条件** | 複式簿記・帳票・消込の整合性をSQLアサーション化 | 高 | 不要 | 可 |
| **C: 実機探索** | 台本実行＋敵対的探索。バックグラウンド・サブエージェントが担当 | 要実測(1〜3) | 必須 | 不可 |
| **D: 修正＋回帰** | 修正→designcheck→deploy→再起動→再検証→コミット | 直列 | 一部 | 可 |

## 4. 発見手法（12種）

### 静的レーン（A）

1. **CLB「静かな失敗」の全数リンタ化** — `HorizontalAlignment: Left/Right`（既定に化ける）、生成列、`date('now')` の UTC ずれ、新規に効かない `IsUpdateProtected`、try-finally 非対応、無言で保存を止める `OnValidateInput`、効かない `AllowEmptySearch`、`SearchValues` 単複、Boolean 初期値未チェック。**FB-001〜046 と過去の実測教訓を機械可読なルールに落とし、`Designer/tools/lint_design.py` として永続化する。**
2. **スクリプト意味監査** — 各 `.mod.cs` を対応する設計書（`04_会計ドメイン設計` / `07_経費精算設計` / `08_請求入金設計`）とペアでサブエージェントに読ませ、具体的な問いに答えさせる。
   - 端数処理は税率ごとに1回か（ADR-0049/0050）
   - `OnDataChanged` の無条件上書きは無いか（既知 A-1 の真因パターン。ADR-0053）
   - 再入・多重発火は
   - 締め期間ガードは
   - 取消の連鎖は完全か（ADR-0035）
3. **状態機械の網羅監査** — 伝票ごとに 状態×操作×権限 の行列を JSON から機械生成し、孤児状態・戻れない状態・取消漏れを検出（ADR-0026 が oracle）。
4. **権限×画面の全数マトリクス** — 15フレーム×103モジュール×26ユーザーを静的展開し、`docs/10` §5・`docs/13` と突き合わせる。「経理限定のはずが一般に見える」「直URLで入れる」を洗う（既知 C-6 の類型）。`check_navigation.py` を汎用化して取り込む。
5. **ADR ドリフト検査** — 63本の決定が現在も守られているかを機械的に照合。
6. **ドキュメント vs 実装** — 設計書に書いてあるのに実装が違う／無いものを検出。

### データレーン（B）

7. **不変条件スイート** — 実行可能な会計整合性アサーション集。
   - Σ借方 = Σ貸方（全体＋伝票ごと）
   - 伝票番号の一意性・欠番
   - 総勘定元帳 = 試算表 = BS・PL
   - 資産 = 負債 + 純資産／当期純利益 = 繰越利益の増分
   - C/F 期末残高 = BS 現預金
   - 請求書合計 = 明細合計（税率別に1回端数処理）
   - 消込残高 ≥ 0、消込フラグと消込仕訳の存在が一致（ADR-0051）
   - 償却累計 ≤ 取得価額、償却仕訳と台帳の一致
   - 予算実績の実績 = 仕訳集計
   - 孤児FK、税区分NULL（ADR-0052）、締め済み期間への仕訳追加
8. **差分不変条件** — 操作の前後で DB スナップショットを取り「この操作ではこの表だけがこう変わるはず」を検証。**目視では見つからない副作用**（他部門の行が動く等）を機械的に捕まえる。
9. **二重実装の照合** — ADR-0060 が自認するポータル件数の二重実装（`portal_billing_count_check.sql`）を毎回自動実行。

### 実機レーン（C）

10. **台本実行** — 体験シナリオ51本＋E2E分岐121個を、1本=1サブエージェントで実行。期待値は既存 E2E 文書が持っている。
11. **敵対的探索** — 台本に無いことをやる。0円・マイナス・巨大値・全角数字・超長文字列・日付逆転・締め日ちょうど・権限外URL直打ち・**二重サブミット**・**ブラウザ戻る**・リロード中断。Blazor はこの辺が壊れやすい。
12. **コンソール／ネットワーク常時監視** — 全シナリオ中の JS 例外・失敗リクエストを収集。無言の失敗を可視化する。

### 既存資産の統合

13. **未対応の改善候補 49件を再評価** — 「改善候補」の中にバグ性の高いものが混ざっている（C-6 権限ゲート無し、C-7 承認テンプレに同一人物が2段、P-1/M-1 案件損益に外注費が乗らない）。バグ台帳に統合して優先度を付け直す。

## 5. コンテキスト管理 — 「オーケストレータは読まない」規律

| 原則 | 実装 |
|---|---|
| オーケストレータはファイルを読まない・画面を見ない | 全作業をサブエージェントに委譲。返却は**構造化20行以内**に制限する |
| 状態は全部ファイル | `docs/qa/` に台帳・ランブック・進捗。次セッションはここだけ読めば再開できる |
| 生ログは分離 | `docs/qa/30_レポート/` に書かせる。オーケストレータは読まない |
| 交代の合図 | コンテキスト60%で handoff を書き、`PushNotification` でユーザーを呼ぶ（所要30秒） |
| 夜間 | ブラウザ不要の A・B・D レーンをヘッドレス連鎖で自動継続 |

### 成果物のファイル構成

```
docs/qa/
  00_バグ狩り計画.md      ← 本書（背景・方針・なぜそう決めたか）
  01_作業指示書.md        ← 新セッションが最初に読む唯一の入口（実行手順の正典）
  02_バグ台帳.md          ← BUG-nnnn（状態機械つき）
  03_進捗.md              ← 「次にやること」ポインタ
  10_チェックリスト/      ← CLB既知の静かな失敗・画面共通チェック
  20_不変条件SQL/         ← 実行可能アサーション＋ runner
  30_レポート/            ← 各バッチの生ログ（オーケストレータは読まない）
  90_最終報告.md          ← 完了時に作成
```

本書（00）は**なぜそう決めたか**を残す文書、`01_作業指示書.md` は**何をどうやるか**の実行正典。
新セッションは 01 だけ読めば作業を開始できる。

## 7. 運用の決定事項（2026-08-16 ユーザー決定）

| 論点 | 決定 |
|---|---|
| ブラウザ操作の権限 | **`.claude/settings.local.json` に操作系ツールを追記**（Git 追跡外・ADR-0038 の方針どおり） |
| セッション交代 | **通知で呼ぶ＋夜はヘッドレス**。コンテキスト60%で handoff → `PushNotification`。不在中は A・B・D レーンを自動継続 |
| 修正の範囲 | **「設計変更またはその検討を要するもの」以外は全て自律修正**（2026-08-16 ユーザー指示で拡大）。表示・UX の不整合も含む |
| 検証用 DB | **現 DB を作業台にする＋スナップショット運用** |

### 優先度の定義

優先度は**着手順を決めるためのもの**であり、修正するか否かの線引きではない。
線引きは「設計変更またはその検討を要するか」の一点（§7.1）。

| 度 | 定義 | 扱い |
|---|---|---|
| **P0** | お金が間違う（仕訳・税・残高・帳票の数字）／統制が破れる（権限・締め）／データが壊れる | 最優先で修正＋回帰アサーション追加 |
| **P1** | 機能が動かない・業務が詰まる | 修正＋回帰アサーション追加 |
| **P2** | 表示・UX の不整合、驚きのある挙動 | 修正（まとめて波で流してよい） |
| **P3** | 改善提案（現状でも業務は回る） | 設計判断を含むものは台帳止め。含まないものは修正してよい |

### 7.1 自律修正と台帳止めの線引き

**自律的に修正してよい**（＝上記のほぼ全て）:
既存の設計意図どおりに動いていないもの。計算違い・ガード漏れ・条件式の誤り・状態遷移の穴・
表示崩れ・ラベル不統一・書式（右詰め・カンマ）の乱れ・検索既定の誤り・権限判定の抜け など。

**台帳に積んで GO を待つ**（＝着手しない）:
- データモデルを変えるもの（列・テーブル・親子構造の追加改廃）
- 画面構成・導線・フレーム着地を変えるもの
- 業務フロー／承認ルートの意味を変えるもの
- 新機能の追加
- **ADR を書く必要がある判断**（＝これが最も分かりやすい判定基準）

迷ったときの自問: **「この修正は ADR に残す必要があるか？」「他の画面の作り方に波及するか？」**
どちらかが Yes なら台帳止め。

## 8. ガードレール

- 修正のたび `designcheck` を 0件にする → `deploy.ps1` → **`.mod.cs` を触ったらサーバ再起動** → 再検証
  （2026-08-16 にこれを怠って実データを生成し復旧した教訓）
- 作業前に DB スナップショット。シナリオ単位で復元
- 1バグ1コミット（Conventional Commits）
- **同じバグを3回直して直らなければ止めて相談**（既存の作業合意）
- 設計変更を伴う大物（例: 経費の明細行化）は着手せず台帳に積む
- サブエージェントの報告は鵜呑みにせず、P0/P1 は**必ず自分で再現条件を確認**してから修正に入る

## 9. 未解決の実験（P0 で最初に潰す）

1. **ブラウザ並列の可否** — 複数サブエージェントが別タブを同時操作できるか。拡張のスクショが「アクティブタブ」依存なら直列化する。可否で P3 の所要が 2〜3 倍変わる。
2. **CLB スクリプトの実行場所** — クライアント（WASM）側で走るなら、HTTP 直叩きは業務ロジックを迂回する。データ投入の近道としては使えるが「テストにならない」。用途を確定させる。
3. **ヘッドレス連鎖の権限** — `claude -p --allowedTools` で A・B・D レーンが人手なしに完走できるか。
