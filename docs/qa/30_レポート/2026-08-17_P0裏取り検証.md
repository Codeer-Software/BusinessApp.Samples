## 検証1: 減価償却の年度インデックスが逆符号 — 条件付き成立（帰結は主張と逆）

### 実際の場所

`Designer/Design/Modules/Accounting/FixedAsset.mod.cs:148-156`（主張の「154 付近」と一致）。

```csharp
int YearIndex(var acq, var yearStart, var yearEnd)
{
    if (acq >= yearStart && acq <= yearEnd) return 1;
    if (acq > yearEnd) return 0;
    var years = yearStart.Year - acq.Year;
    if (acq.Month >= yearStart.Month) { years = years; } else { years = years - 1; }
    return years + 1;
}
```

### 成立条件

会計年度は 4/1 開始（実データで確認。下記 SQL-1）。`yearStart.Month = 4` なので、
**取得月が 1〜3 月の資産**でのみ破綻する。取得月が 4〜12 月なら暦年差の補正が正しく効く。

例: 取得 2026-01-15、第17期（2025-04-01〜2026-03-31）に取得。

| 対象年度 | `YearIndex` | 期待 | 償却額 |
|---|---|---|---|
| 第17期（取得年度） | 1（`acq` が範囲内の早期 return） | 1 | 初年度月割 |
| 第18期 2026-04-01〜 | `years = 2026-2026 = 0` → 月 1 < 4 で −1 → **0** | 2 | **0 円**（「償却額はありません」で静かに素通り） |
| 第19期 2027-04-01〜 | `years = 1` → −1 → **1** | 3 | **初年度月割を再計上** |
| 第20期 | 2 | 4 | 年額 |

`if (acq.Month >= yearStart.Month)` の分岐は、**開始月より前＝前年度**という関係が
「取得日が期首より前」のときに限って逆になっている（1〜3 月は当該年度の後半なので減算してはいけない）。

### 主張の帰結は誤り（ここが報告者と食い違う）

報告は「償却累計が取得価額に到達しない」とするが、**実際は取得価額を超えて償却する**。
`straight_line` の累計式（`accumulated = firstYearAmount + annual*(k-2)`）は
「初年度月割を 1 回だけ計上した」前提だが、上表のとおり初年度月割は**2 回**計上される。
残高クランプ（`remaining = cost - 1 - accumulated`）はこの式にしか従わないため、
最終的な累計は `cost - 1 + firstYearAmount` になり、**簿価が `1 - firstYearAmount` とマイナスに沈む**。

取得価額 460,000 円・耐用年数 4 年・1 月取得（初年度 3 か月＝28,750 円）で試算すると:

| 年度 | 償却額 |
|---|---|
| 取得年度 | 28,750 |
| 2 年目 | **0** |
| 3 年目 | **28,750**（初年度の再計上） |
| 4〜6 年目 | 115,000 × 3 |
| 7 年目 | 86,249（残高クランプ） |
| 合計 | **488,749**（取得価額 −1 の 459,999 に対し **+28,750 の過大償却**、償却期間も 1 年延びる） |

`declining_200`（126 行の `k2`）も同じ `YearIndex` を使うため、同様に 2 年目 0 円・3 年目やり直しになる。

### 実データの裏

**あり（ただし現時点の被害は 0 件）**。固定資産は 2 件のみで、いずれも 7 月取得＝1〜3 月に該当しない。
生成済みの償却仕訳も理論値と一致する（SQL-2）:

- 資産1 開発用ワークステーション: 150,000 円 / 4 年 / 2026-07-14 取得 → 第18期 28,125 円
  （= 150,000÷4 × 9/12。7 月取得の月割 9 か月。正しい）
- 資産2 ノートPC ×2: 460,000 円 / 4 年 / 2026-07-08 取得 → 第18期 86,250 円
  （= 460,000÷4 × 9/12。正しい）

### 修正の見当

`YearIndex` を「取得日が属する会計年度の期首」を `fiscal_years` から引いて年数差を取る実装に置き換える
（`ModuleSearcher<FiscalYear>` で `start_date <= acq <= end_date` を解く）。暦年差＋月比較の近似はやめる。

## 検証2: 翌期繰越が補助科目・部門を捨てる — 不成立（読み手がいない）

### 実際の場所

`Designer/Design/Modules/Accounting/FiscalYear.CarryOverSql.sql:8-9`（主張どおり）。
`sub_account_id` / `department_id` に定数 `NULL` を入れ、集計も `accounts a` 単位でしか行っていない。
**コード上の事実としては主張は正しい。**

### なぜ「補助元帳の期首残高が消える」が成立しないか

1. **補助元帳はもともと期首残高を出さない。** `GeneralLedger.Query.sql:2-5` に
   「絞り込みあり: opening_balances は科目単位でしか持たないため期首残高を含めず、
   期中発生分のみの累計を表示する」と明記され、実装も `:15-16` で
   `@sub_account_id`/`@department_id`/`@project_id` のいずれかが非 NULL なら期首残高に 0 を掛けている。
   つまり**繰越前の年度でも補助元帳に期首残高は出ない**。「翌期で消える」という因果が成立しない。
2. **`opening_balances.sub_account_id` / `department_id` を読むクエリが 1 本も無い。**
   `opening_balances` を参照する 15 ファイル（TrialBalance / BalanceSheet / MonthlyTrend /
   CashFlowStatement / EquityChange / CashBalance / CashBook / BankReconciliation /
   PortalKpiData / PortalAlertData / GeneralLedger / CashFlowForecastData ほか）を確認したところ、
   いずれも `GROUP BY account_id` か `WHERE account_id = ?` の科目単位で、
   補助科目・部門で絞る箇所は存在しない。捨てられた値には消費者がいない。
3. 部門別損益は PL 科目ベースで、そもそも BS の期首残高を使わない。

### 実データの裏

**あり**。`opening_balances` は 20 行（第18期 6 行・第19期 14 行）で、
**`sub_account_id` が非 NULL の行 0 件・`department_id` が非 NULL の行 0 件**（SQL-1）。
失われている実データは無い。

### 残る（P0 ではない）事実

`OpeningBalance.mod.json` には `SubAccount` / `Department` フィールドがレイアウト上に置かれており、
**人は入力できる**。入力しても誰も読まず、繰越で NULL に潰れる——
「入れられるが効かない欄」であり、ADR-0054（有効フラグは効く場所が無いなら名乗るな）と同じ型の問題。
補助科目別の期首残高を本当に持たせるなら、繰越 SQL より先に**読み手（補助元帳の期首残高）**を作るのが筋。
優先度は P2 相当。

## 検証3: 検収確定の仕訳が明細の税区分を無視する — 確定（ただし税額そのものは正しい）

### 実際の場所

`Designer/Design/Modules/Sales/Acceptance.mod.cs:559-564`（`SALES_10` の id を 1 個だけ引く）と、
それを使う **`:616` / `:625`**（売上行と消費税行の `TaxCategory` に一律代入）。

### ADR-0050 が定めていること／守られていること

ADR-0050 の適用範囲表は `Acceptance` について「**検収明細の税区分ベースに（税額自動セット）**」と定める。
この**税額計算は正しく実装済み**——`RecalcFromLines()`（`:304-335`）が明細の `TaxCategoryRef` から
税率ごとにグループ化し、グループごとに 1 回だけ切り捨てている。`TaxAmount` の値は ADR 準拠。

破れているのは**仕訳行への税区分の付け方**で、ADR-0050 の文言が直接カバーしていない部分:

- 借方 売掛金 = 税込総額（税区分なし → `MarkRemainingLinesOutOfScope`）
- 貸方 売上 = 税抜合計、**税区分は明細に関係なく `SALES_10`**
- 貸方 仮受消費税 = `RecalcFromLines` の税額（正しい）、**税区分は `SALES_10`**

### 成立条件と影響

**検収明細に `SALES_10` 以外が 1 行でも混ざったとき**に、消費税集計表が狂う。
`TaxSummary.Query.sql:41-59` は `journal_lines.tax_category_id` で `GROUP BY` するため:

- 例 A（非課税が混在）: 課税 100,000 + 非課税 100,000 → 税額 10,000 は正しいが、
  集計表は **課税売上 200,000 / 非課税売上 0** と読む。
  `TaxSummary.Query.sql:61-67` の**課税売上割合が 100% に化け**、
  本来「個別対応方式が必要」の判定が「全額控除できます」に反転しうる。
- 例 B（8% 混在）: 10% 100,000 + 8% 100,000 → 税額 18,000 は正しいが、
  集計表は「課税売上 10% の売上 200,000・税額 18,000」と表示する（税率別内訳が破綻。
  申告書の税率別区分が作れない）。

**帳簿の金額（BS・PL・売掛金・入金消込）は正しい。壊れるのは税区分別の集計＝申告の基礎資料だけ。**

### 実データの裏

**あり（現時点の被害は 0 件）**。`acceptance_lines` 15 行は**全て `SALES_10`**（9 検収・混在 0 件。SQL-3）。
いま帳簿に載っている検収仕訳の税区分は結果的に正しい。混在検収を 1 本作った瞬間に顕在化する潜在バグ。

### 修正の見当

明細を税区分でグループ化し、**税区分ごとに売上行＋消費税行のペアを作る**
（`RecalcFromLines` の税率グループ化ロジックをそのまま流用できる）。
`ParentLineNo` は各グループの売上行を指す。

## 検証4: 「変更を保存」が画面外の下書きを削除する — 確定（主張より範囲が広い）

### 実際の場所

`Designer/Design/Modules/Accounting/CashEntry.mod.cs:129-150`（`SaveListEdits`。主張どおり）。
呼び出し元は `Save_OnClick`（`:115-124`）と `PostAll_OnClick`（`:199`）。

```csharp
foreach (var row in DraftList.Rows) { ... aliveIds.Add($"{t.Id.Value}"); }
var s = new ModuleSearcher<CashEntryDraft>();
s.AddEquals(e => e.Creator.Value, CurrentUser.Id.Value);   // ← DB 側は全件
foreach (var row in s.Execute())
    if (!aliveIds.Contains(...)) t.Delete();               // ← 画面に無ければ削除
```

画面側は `DraftList.Rows`、DB 側は `Creator` 一致の**全件**。この非対称が本体。

### 成立条件（主張より広い）

`CashEntry.mod.json:417-448` の `DraftList` は **`LimitCount: 200` かつ `PagerPosition: "Bottom"`**。
CLB の `LimitCount` は「**1 ページあたりの表示件数**」で、`Rows` は
「**現在のページの行リスト**」（`ClaudeCodeForDesigner/_field_catalog.md:4549, 4700`）。したがって:

- 下書きが 201 件以上あると 2 ページに割れ、**表示していないページの下書きが丸ごと消える**。
  主張の「201 件目以降が消える」は正しいが、正確には
  **2 ページ目を開いた状態で保存すると 1 ページ目の 200 件が消える**——どのページにいても、
  そこに載っていない全ページが消える。
- 確認ダイアログは無い（`DiscardAll_OnClick:162` にはあるが `Save_OnClick` には無い）。
  事後に `変更を保存しました（N 行を削除）` のトーストが出るだけで、削除は取り消せない。
- `PostAll_OnClick` も起票前に `SaveListEdits()` を呼ぶ（`:199`）ので、
  **一括起票でも画面外の下書きが起票されずに消える**（確認ダイアログの文面は「N 件を一括で起票します」で、
  削除には触れていない）。

### 副次的に見つかった同根の不具合

`RefreshSummary`（`:408-448`）も `DraftList.Rows` を回すため、
**未起票件数・入出金合計・「起票後の見込み残高」が現在ページ分しか集計しない**。
201 件目以降があるとき、画面の見込み残高は静かに過小になる。

### 実データの裏

**あり（現時点の被害は 0 件）**。`cash_entry_drafts` は **0 行**（SQL-1）。
下書きは起票時に削除される運用なので、常時 200 件超が滞留するのは
「月中に現金取引をため込んで月末にまとめて起票する」使い方をしたときに限られる。ただし
**一度起きたら復旧手段が無い（下書きは削除のみ・履歴なし）**ため、確率が低くても P0 として妥当。

### 修正の見当

削除対象を「画面が担当している範囲」に限定する——
`DraftList.Rows` ではなく**ロード時点の id 集合**を持たせて差集合を取るか、
`CanDelete` の行削除を即時 `Delete()` に変え、`SaveListEdits` から DB 全件走査を消すのが筋。
少なくとも `LimitCount` を `null` + `PagerPosition: "None"` にしないなら、現行実装は成立しない。
