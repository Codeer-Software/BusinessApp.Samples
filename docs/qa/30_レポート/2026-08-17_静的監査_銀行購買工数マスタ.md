# 所見

## P0

### F-01 [P0] 同一内容の明細の 2 件目以降が「重複」として静かに捨てられる

- **場所**: `Designer/Design/Modules/Bank/BankImport.mod.cs:181-195`（`SavePreviewEdits` の連番再計算）
  ／ `:215`（`ConfirmImport` が先頭で `SavePreviewEdits` を呼ぶ）／ `:240-249`（重複判定と `p.Delete()`）
- **症状**: 本番 `bank_statement_lines` に `日付|摘要|出金|入金|0` が既にある状態で、同じ内容の明細が
  もう 1 件現れる CSV を貼ると:
  1. `Import_OnClick` は既存キーと突合して 1 件目をスキップし、2 件目に `…|1` を振ってプレビューへ入れる（正しい）
  2. 「この内容で登録」が最初に呼ぶ `SavePreviewEdits` が、**プレビュー内の行だけ**を走査して連番を振り直し、
     この行を `…|0` に戻す（本番側の既存行を数えていない）
  3. 直後の重複ガードが `…|0` を既存と判定し、**`p.Delete()` でプレビュー行を無言削除**する
- 結果として、本物の入出金 1 件が帳簿に載らない。ユーザーに出るのは結果ラベルの「重複スキップ n 件」だけで、
  何が捨てられたかは表示されない。残高照合では「差異」として遅れて表面化する。
- **根拠**: `SavePreviewEdits` の `baseKeys` は `PreviewLines.Rows` のみを走査（`:181-193`）。
  一方 `Import_OnClick` の `existKeys` は本番＋プレビューの両方を見る（`:70-85`）。**同じキーを 2 つの規則で作っている**のが真因。
- **確度**: 確定（コード）／実害の再現は 要実機確認
- **補足**: `SavePreviewEdits` の連番は口座も跨いで通し番号になる（プレビューリストに口座の絞り込みが無い＝
  `BankImport.mod.json` の `PreviewLines.SearchCondition.Condition` が空）。口座が 2 つ以上になると、
  同一内容の明細が別口座に並んだだけでキーがずれ、次回の再取込で重複と判定されなくなる（逆方向の事故）。

## P1

### F-02 [P1] 一括起票の確認ダイアログで「キャンセル」しても保存は済んでいる

- **場所**: `Modules/Bank/BankPosting.mod.cs:174`（`SaveListEdits()`）→ `:195`（`MessageBox.Show`）
- **症状**: `PostAll_OnClick` は暗黙保存を**確認ダイアログより先**に実行する。ユーザーが件数を見て
  「キャンセル」を押しても、候補科目の確定と `対象外 → excluded` の遷移はすでに DB に入っており、
  チェックした行は一覧から消えたままになる。ADR-0062（不可逆・一括操作は確認してから）に反する。
- **根拠**: 同ファイルの実行順。対照的に `BankImport.ConfirmImport_OnClick` は `:206` でダイアログ →
  `:215` で保存の正しい順になっている（同じアプリ内で規律が割れている）。
- **確度**: 確定

### F-03 [P1] ルール適用が 2 実装に分裂し、登録時経路だけ部門を写さない

- **場所**: `Modules/Bank/BankImport.mod.cs:262-279` と `Modules/Bank/BankPosting.mod.cs:82-98`
- **症状**: `MatchingRule` は ADR-0056 に沿って `DepartmentRef` を持つ。
  `BankPosting.ApplyRules` は科目と部門の両方を写すが、`BankImport.ConfirmImport` は**科目しか写さない**。
  登録時に自動適用（ISSUE-0003 Q-a 案 1）された行は部門が空のまま未起票になる。
  そして `ApplyRules` は「候補が既に入っている行」を飛ばす（`BankPosting.mod.cs:78`）ため、
  一括起票画面で［ルールを適用］を押しても**部門は埋まらない**。損益科目の行は
  `PostAll` の `:279-283` で「部門未選択でスキップ」され続け、1 行ずつ手で部門を選ぶまで起票できない。
- **根拠**: 2 つのルール適用ループの差分（`BankPosting` 側だけに `rule.DepartmentRef` の転記がある）。
- **確度**: 確定

### F-04 [P1] FB データは出力後の状態遷移が無く、二重出力を防げない

- **場所**: `Modules/Purchasing/FbExport.mod.cs`（`Generate_OnClick` 全体）
- **症状**: 生成処理に `Submit()` が 1 つも無い。全銀テキストを組み立てて `FbText` に表示するだけで、
  対象の仕入先請求書に「FB 出力済み」の痕跡が一切残らない。翌日もう一度ボタンを押せば同じ内容が再生成され、
  そのまま銀行に取り込めば二重振込になる。出力履歴も無いため、事故が起きても後から追えない。
- **根拠**: 同ファイルに DB 書き込みが存在しない（読み取りは `ModuleSearcher` のみ）。
- **確度**: 確定

### F-05 [P1] FB は「受領」の未払を黙って落とし、対象期間も選べない

- **場所**: `Modules/Purchasing/FbExport.mod.cs:46`（`AddEquals(Status, "accrued")`）
- **症状**: 支払予定表は `received`（受領）と `accrued`（未払計上済）の両方を未払として並べる
  （`PaymentSchedule.Query.sql:17`）が、FB は `accrued` だけを拾う。
  **支払予定表で「⚠ 期限超過」と警告されている請求書が、FB データには入らないまま黙って通り過ぎる。**
  実データで `received` が 2 件・44,000 円ある（読み取り専用 SELECT で確認）。
  さらに `DueDate` による絞り込みが無く、期限が数ヶ月先の `accrued` も全部 1 本のファイルに混ざる
  （振込指定日は 1 つしか持てないので、期日どおりの支払ができない）。
- **根拠**: 上記 2 ファイルの WHERE 条件の差、および `vendor_invoices` の status 別集計（SELECT）。
- **確度**: 確定

### F-11 [P2] 残高照合は「口座」ではなく「帳簿科目」で集計するため、同一科目の複数口座で壊れる

- **場所**: `Modules/Bank/BankReconciliation.Query.sql:31-38`
- **症状**: `ledger_balance` は `jl.account_id = t.ledger_account_id` で仕訳を合計する。
  複数の `bank_accounts` が同じ `ledger_account_id`（例: 1020 普通預金）を指すことを
