### 問いへの回答（依頼された 8 問への直接回答）

| # | 問い | 結論 |
|---|---|---|
| 1 | 端数処理は税率ごとに 1 回か | **○ 正しい。** Quote / Acceptance / Invoice の 3 本とも「税率ごとに本体を合計 → 1 回だけ切り捨て」。明細ごとに丸めて足している箇所は無い。ただし**検収→請求の写しには実データのずれが 1 件ある**（F-01）。丸め方式が切り捨て固定でマスタ化されていない点は F-19 |
| 2 | `OnDataChanged` の無条件な数量×単価上書き | **請求書では潰れているが、3 か所に残存。** Invoice は `AcceptanceLineRef == null` でガード済み。**SalesOrder / Quote は無条件上書き（F-12）**、**Invoice の手入力行（＝合算請求書の全行）も実質無条件（F-10）** |
| 3 | 状態遷移の巻き戻し | **入金予定は巻き戻る。売掛残も巻き戻る。売上仕訳だけ巻き戻らない。** その非対称が GL と補助簿の恒久的なずれを生む（F-05、実データ 110,000 円）。さらに **void 済み請求書が検収を永久ロック（F-06）**、**確定の 2 段 Submit 失敗でデッドロック（F-07）** |
| 4 | 分割検収 | **行単位の残額計算は正しい。** ただしヘッダ額の保存が効かない疑い（F-02）と、下書き検収同士は残額を食い合う（F-16） |
| 5 | 締め済み期間ガード | **仕訳を触る 3 経路（検収確定／確定取消／発行取消）はすべてガードあり。** 請求書の発行・取消は仕訳を触らないので不要。抜けは無い |
| 6 | 権限 | **Invoice の `UserWriteCondition` が空（F-13）**。読みは経理限定なのに書きが無条件。部門をまたぐ編集は 4 伝票とも `DataWriteCondition` 空で素通り（F-17、ADR-0031 が「割り切り」と明記済み） |
| 7 | null / 0 件 / 未設定 | **`Invoice.RecalcTotal` が遅延ロードで 0 円を永続化しうる（F-08）**、帳票 11 行目以降の黙殺（F-14）、支払期限 NULL（F-15） |
| 8 | 二重サブミット | **ガードはすべて「DB 検索 → 生成」で、その間にロックが無い。** 検収確定・請求書作成・受注変換の 3 経路が理論上二重生成しうる（F-09）。実挙動はローディングオーバーレイ次第＝要実機確認 |

## 2. P0 所見

### F-01 [P0/確定] 検収 1,200,000 円に対し 2,000,000 円で発行済みの請求書が現存する

- **場所**: データ（`invoices` id=29 / `acceptances` id=13）。関連コード `Modules/Sales/Acceptance.mod.cs:711-733`、`Designer/ddl/471_acceptance_lines.sql:52-60`
- **症状**: `INV-26-017`（status=`issued`）の請求額は税抜 2,000,000 円。対応する検収 `A-26-009` の検収額は 1,200,000 円で、売上仕訳 No.84 は「売掛金 1,320,000 / 売上 1,200,000 / 仮受消費税 120,000」。**請求額（税込 2,200,000）と計上済み売掛金（1,320,000）が 880,000 円乖離**している。顧客に 80 万円多く請求している状態。
- **根拠**（SELECT の実測値）:

  | 検収 | 明細 order_amount | 明細 amount | ヘッダ amount |
  |---|---|---|---|
  | A-26-009 (id 13) | 2,000,000 | 1,200,000 | 1,200,000 |

  | 請求書 | status | acceptance_id | 明細 acceptance_line_id | 明細 unit_price | 明細 amount | ヘッダ amount |
  |---|---|---|---|---|---|---|
  | INV-26-017 (id 29) | issued | 13 | 15（= A-26-009 の明細） | 2,000,000 | 2,000,000 | 2,000,000 |

  受注 `SO-26-009` の明細合計は 2,000,000。つまり**この請求書は ADR-0049 以前のロジック（受注明細をコピー）で作られたまま**。移行 DDL `471_acceptance_lines.sql` は `invoice_lines.acceptance_line_id` を張るだけで **`invoice_lines.amount` を検収額に是正していない**（52-60 行目の UPDATE は `acceptance_line_id` のみ）。
- **現行コードは同じ請求書を新たには作らない**（`CreateInvoice_OnClick` は検収明細を写す）。しかし**残存データが未修復**で、しかも発行済みなので画面上は閲覧専用。開けば `UpdateOverAcceptanceWarning` が赤字警告を出すが、誰も開いていない。
- **確度: 確定**（DB 実測）

### F-02 [P0/要実機確認] 検収の `Amount` / `TaxAmount` が `IsUpdateProtected: true` のため、保存済み検収の再計算が DB に反映されない

- **場所**: `Modules/Sales/Acceptance.mod.json:113`（Amount）／`:131`（TaxAmount）、`Modules/Sales/Acceptance.mod.cs:304-335`（`RecalcFromLines`）
- **症状**: 検収を保存したあとに明細金額を直しても（分割検収の按分見直し、受注の選び直し）、`RecalcFromLines` はメモリ上の `Amount` / `TaxAmount` を更新するが、**`IsUpdateProtected: true` はサーバ側でも更新を拒む**ため DB のヘッダ額は古いまま。次に画面を開き直すと古い額が復活し、`Confirm_OnClick` はその古い `Amount.Value` で売上仕訳を切る（`Acceptance.mod.cs:566-568`）。明細合計と売上計上額が食い違う。
- **根拠**:
  - `_specs/_FieldCommon.md:119`「`true` にすると、**レコード作成後は値を変更できなくなる**（読み取り専用になる）。新規作成時は編集可能」＋ `Docs/CommonMistakes.md:461`「**サーバーサイドでもチェックが入り、API 経由での更新も防止される**」
  - ADR-0062 は「導出値は `IsViewOnly` で読み取り専用にする。`IsUpdateProtected` は**併用してよい**」と書いており、レイアウト側の `IsViewOnly: true` は入っている（`Acceptance.mod.json:1210`）が、**`IsUpdateProtected` を外していない**。ADR-0062 §影響の「既に保存されている不整合データがあれば、明細を 1 度触れば再計算される」という救済策は、この設定のままでは**成立しない**。
  - 対照: 請求書の `Amount` / `TaxAmount` は `IsUpdateProtected: false` ＋レイアウト `IsViewOnly: true`（`Invoice.mod.json:1126` / `:1147` / `:2412`）＝ ADR-0062 の意図どおりの形。**検収だけが違う。**
  - 現 DB では 9 件すべてヘッダ額＝明細合計で一致（＝まだ誰も保存後に明細を編集していない）。**潜在。**
- **なぜ P0 か**: 売上計上額そのものが誤る経路であり、しかも画面上は「正しい額に見える」（メモリ上は再計算済み）ため気づけない。
- **確度: 要実機確認**（更新が「黙って落ちる」のか「Submit が false を返す」のかで症状が変わる。後者なら F-07 のデッドロックに化ける）

### F-03 [P0/確定] 検収確定の仕訳が、明細の税区分に関わらず一律 `SALES_10` を書く

- **場所**: `Modules/Sales/Acceptance.mod.cs:559-564`（税区分の解決）、`:616` / `:625`（売上行・税行への設定）
- **症状**: `RecalcFromLines` は明細ごとの税区分で税率別に集計する（軽減 8%・非課税・免税を正しく扱う）のに、`Confirm_OnClick` が生成する仕訳は**売上行にも税行にもコード直書きの `SALES_10`（課税売上 10%）を貼る**。
  - 軽減 8% の明細を含む検収 → 税額は 8% で計算されるのに仕訳は 10% 区分 → **消費税集計表・科目別税区分表の税率別内訳が狂う**。
  - 非課税売上／免税売上（輸出）だけの検収 → 税額 0 で税行なし、しかし**売上行が「課税売上 10%」に分類される** → 課税売上高が過大になり、課税売上割合・簡易課税判定にも波及。
- **根拠**:
  - `Acceptance.mod.cs:561` `cs.AddEquals(c => c.Code.Value, "SALES_10");` ← **唯一の残存ハードコード**（Quote / Invoice は `DefaultFor='sales'` でマスタから引いており、ADR-0050 の「コードに税区分を直書きしない」に従っている）。
  - `tax_categories` マスタには `SALES_8`(軽減) / `SALES_EXEMPT`(非課税) / `SALES_EXPORT`(免税) が `is_active=1` で実在し、明細のドロップダウンから選べる（実測）。**到達可能。**
  - さらに `SALES_10` を経理がリネーム・無効化すると `salesTaxCatId` が null になり、`MarkRemainingLinesOutOfScope()`（`Accounting/JournalEntry.mod.cs:214`）が売上行を**黙って「対象外」に落とす** → 課税売上が消費税集計から丸ごと消える（静かな失敗）。
- **現 DB の状態**: 検収 9 件はすべて 10% のみのため、生成済み仕訳（No.71 / No.84 等）は結果的に正しい。**潜在だが、税区分マスタが揃っている以上いつでも踏める。**
- **確度: 確定**（コードとマスタの実測）

### F-04 [P0/確定] 合算請求書に載せた検収でも「確定を取り消す」が通り、売上仕訳だけが消える

- **場所**: `Modules/Sales/Acceptance.mod.cs:155-215`（`CancelConfirm_OnClick`）、ガードは `:163` のみ
- **症状**: 確定取消のガードは `FindExistingInvoiceNo()`（＝`invoices.acceptance_id` に自分を指す請求書があるか）だけ。**`BilledInvoiceRef`（合算先請求書、`acceptances.billed_invoice_id`）を見ていない**。複数検収を手動請求書にまとめる正規フロー（ADR / ISSUE-0002 の合算請求）では `acceptance_id` は張られないため、**請求済みの検収でも確定取消が通り、売上仕訳（売掛金・売上・仮受消費税）が削除される**。請求書は残ったまま。
- **結果**: 顧客に請求している売上が帳簿から消え、**売掛金だけが補助簿（売掛残高一覧）に残って GL と合わなくなる**。
- **根拠**: `:163-168` は `FindExistingInvoiceNo()` の結果しか見ない。一方で `UpdateButtons`（`:98`）は `billedNo != null` でも「請求書作成」ボタンを隠す＝**設計者は合算を「請求済み」と認識している**のに、取消側だけがそれを見ていない。`FindBilledInvoiceNo()` は `:378` に既に存在するので、ガードに 1 行足せば塞げる。
- **現 DB**: `billed_invoice_id` が入った検収は 0 件（＝合算請求フローがまだ使われていない）ため未発生。**潜在。**
- **確度: 確定**（コード）

## 3. P1 所見

### F-05 [P1/確定] 請求書 void は売掛残高からは消えるが売上仕訳は残り、GL と補助簿が恒久的にずれる

- **場所**: `Modules/Sales/Invoice.mod.cs:67-88`（`Void_OnClick`）、`Modules/Sales/ReceivableBalance.Query.sql:48`
- **症状**: `ReceivableBalance.Query.sql` は `WHERE i.status <> 'void' AND i.status <> 'draft'` で void を除外する。一方 `Void_OnClick` は売上仕訳を消さない（コメントで「貸倒れは振替伝票で別途」と明示）。**二重発行・宛先ミスで void にした場合は貸倒れではない**ので、誰も振替伝票を起こさない。結果、GL の売掛金にだけ残高が残る。
- **根拠（実データ）**: `INV-26-005`（status=`void`、`acceptance_id=2`）に対応する売上仕訳 No.32（`journal_entries` id=34、status=`posted`）が現存。入金レコードは 0 件。**110,000 円（税込）が GL 売掛金に残り、売掛残高一覧には出ない。**
- **設計としては ADR に記載のある割り切りだが、①画面が何も警告しない ②残高照合の手順に接続していない ため、実運用では必ず取り残される。最低でも void 時に「売上の取消が必要なら振替伝票を」と案内すべき。
- **確度: 確定**（DB 実測）

### F-06 [P1/確定] void 済み請求書が検収を永久ロックする（再請求も確定取消もできない）

- **場所**: `Modules/Sales/Acceptance.mod.cs:143-151`（`FindExistingInvoiceNo`）、参照元 `:98`（ボタン表示）と `:163`（取消ガード）
- **症状**: `FindExistingInvoiceNo()` は `AcceptanceRef == this.Id` の請求書を**状態で絞らずに**拾う。請求書を void にしても検収からは「請求書 INV-xx 作成済み」に見えたままで、
  - 「請求書を作成」ボタンが出ない（`:98` の `invoiceNo == null` 条件）→ **再請求できない**
  - 「確定を取り消す」も `:166` で弾かれる → **下書きに戻して直すこともできない**

  → その検収は**どの導線からも先へ進めない詰み状態**になる。void 請求書は削除導線が無い（`DeleteInvoice` は draft のみ、`CancelIssue` は自動生成分のみ）ため、自力では回復不能。
- **根拠（実データ）**: `INV-26-005` は void、`acceptances` id=2（`A-26-002`、confirmed）が現にこの状態。**発生済み。**
- **確度: 確定**（コード＋DB）

### F-07 [P1/要実機確認] 検収確定の 2 段 Submit — 仕訳生成後にステータス更新が失敗すると復旧不能

- **場所**: `Modules/Sales/Acceptance.mod.cs:636-641`
- **症状**: `je.Submit()`（仕訳）成功 → `this.Submit()`（ステータス）失敗、というシーケンスで
  - 仕訳は `posted` で存在、検収は `draft` のまま
  - 再度「確定」を押すと `:499-502` の二重生成ガードが「既に生成済みです」で拒否
  - 「確定を取り消す」は `:162` の `Status.Value != "confirmed"` で拒否

  → **仕訳だけが宙に浮き、画面からはどちらにも動かせない孤児状態。**
- **根拠**: `:641` は失敗時に `Toaster.Error("...（仕訳は生成済みです）")` と出すだけで、生成した仕訳をロールバックしない。同型の 2 段 Submit は `Quote.mod.cs:484-489` / `:557-562`（受注・契約は作られたのに見積が accepted にならない）にもある。
- **F-02 との合わせ技**: `IsUpdateProtected` が Submit を `false` で落とすなら、**この失敗は例外ではなく日常経路になる。**
- **確度: 要実機確認**（`Submit()` が失敗する条件の実測が要る）

### F-08 [P1/要実機確認] `Invoice.Detail_OnAfterInit` の `RecalcTotal()` が、明細の遅延ロード次第で請求額を 0 円に書き換えうる

- **場所**: `Modules/Sales/Invoice.mod.cs:22`（init から無条件呼び出し）、`:371-383`（`RecalcTotal` が `Amount` / `TaxAmount` を上書き）
- **症状**: `RecalcTotal()` は `Lines.Rows`（メモリ）を合計して**DB 列である `Amount` / `TaxAmount` を書き換える**。この 2 つは `IsUpdateProtected: false` なので、その後に走る状態遷移（`Void` / `Unvoid` / `RevertToDraft` はいずれも `this.Submit()` する）で**そのまま保存される**。もし init 時点で `Lines.Rows` が空なら請求額が 0 円で確定する。
- **根拠**: 同じファイルの `PrintInvoice`（`:558-562`）が **「明細は DB から取り直す（メモリ行の遅延ロード対策）」** とコメント付きで `ModuleSearcher` に切り替えている＝**作者自身が `Lines.Rows` の遅延ロードを実測で踏んでいる**。にもかかわらず `RecalcTotal` は `Lines.Rows` を信じ、しかも書き込む先が永続列。Quote / SalesOrder の `TotalAmount` は `DbColumn: ""`（非永続）なので同じ形でも実害が無く、**Invoice だけが危険**。
- **現 DB**: 請求額と明細合計が食い違う請求書は 0 件（＝まだ踏んでいない）。
- **確度: 要実機確認**（遅延ロードが起きる条件の再現が要る）

### F-09 [P1/要実機確認] 二重サブミットのガードがすべて「DB 検索 → 生成」で、間にロックが無い

- **場所**: `Acceptance.mod.cs:499-502`（確定）／`:676-682`（請求書作成）／`Quote.mod.cs:437-442`（受注変換）
- **症状**: いずれも「既に在るか」を `ModuleSearcher` で調べてから生成する。連打・回線遅延で 2 リクエストが並ぶと**両方がガードを通過**し、仕訳 2 本／請求書 2 通／受注 2 件ができる。加えて採番（`NextAcceptanceNo` / `NextInvoiceNoForCreate` / `NextOrderNoForConvert`）も「最大値 +1」なので**同じ番号が 2 件**になり、`Acceptance.mod.cs:740-742` の「作った請求書を番号で引き直して遷移」が別物を開く可能性がある。
- **根拠**: DB 側に一意制約が無い（`ddl/110_billing.sql` に `UNIQUE(invoice_no)` 等が無い）。`invoice_no` の重複は現時点 0 件（実測）。
- **緩和**: `using var loading = LoadingService.StartLoading(0)` のオーバーレイが実質的な連打防止になっている可能性が高い。**そこが唯一の防波堤**という構造は残る。
- **確度: 要実機確認**

### F-10 [P1/確定] 合算請求書の手入力明細は、数量×単価で金額を無条件に上書きされる

- **場所**: `Modules/Sales/Invoice.mod.cs:361-364`
- **症状**: ガードは `l.AcceptanceLineRef.Value == null && l.UnitPrice.Value != null` → **「検収明細から写した行**でなければ**上書きする」**。合算請求書（複数検収を手動請求書にまとめる正規フロー）の明細は手入力なので `AcceptanceLineRef` が NULL で、**全行が上書き対象**。分割検収の按分額（数量 1 × 単価 2,000,000 だが請求は 1,200,000）を入力しても、次に別の行を触った瞬間 2,000,000 に戻る。
- **根拠**: これは ADR-0049 が潰したはずの「改善候補 A-1 の真因」と**同じ形**が、検収由来でない経路に残っているもの。コメント（`:358-360`）も「手で足した行だけ、入力の手間を省くために数量×単価を自動で入れる」と、上書きが常時走ることを前提にしている（初回だけではない）。
- **確度: 確定**（コード）

## 4. P2 所見

### F-11 [P2/確定] `inLinesHandler` 再入ガードの内側で DB 検索している（Quote / SalesOrder / Invoice）

### F-12 [P2/確定] 受注・見積の明細は数量×単価を無条件上書きし、一式・値引き行を表現できない

### F-16 [P2/確定] 分割検収の残額計算は「確定済み」だけを引くため、下書き検収同士が同じ残額を食い合う

### F-17 [P2/確定] 4 伝票とも `DataWriteCondition` / `DataReadCondition` が空で、他部門の伝票を編集できる

### F-18 [P2/確定] 検収明細の税区分だけ「仕入側を除外」フィルタと必須指定が抜けている

## 5. P3 所見

### F-19 [P3/確定] 端数処理が「切り捨て」固定で、マスタ化されていない

- **場所**: `Invoice.mod.cs:456`、`Quote.mod.cs:302`、`Acceptance.mod.cs:332` — いずれも `(int)(base * rate / 100)`
- **内容**: 税率ごとに 1 回丸める点は正しい（インボイス制度の要件を満たす）が、**丸め方は切り捨て固定**。事業者は切上げ・四捨五入も選べるため、CLAUDE.md の「税率・税区分・閾値はマスタ化してハードコードしない」に照らすと `tax_rates` か `tax_categories` に丸め方式の列を持たせるのが筋。
- 併せて、`(int)` はゼロ方向丸めなので**負値（値引き明細・赤伝）では切り上げになる**非対称がある。

### F-20 [P3/確定] 明細の数量が INTEGER で、0.5 人月・1.5 時間を表現できない

- **場所**: `ddl/110_billing.sql:26`（`quote_lines.qty INTEGER`）ほか 4 テーブル、`ddl/471_acceptance_lines.sql:14`
- **内容**: ペルソナ（IT 受託／SES）では「0.5 人月」「1.5 人日」が日常。現状は数量 1・単価に金額を寄せる運用で回避するしかない。単価×数量の見え方が業務実態と合わない。

-- (1) 検収ヘッダ額 vs 明細合計

  FROM invoices i WHERE i.status = 'void' OR i.acceptance_id IS NOT NULL;   -- INV-26-005(void) / INV-26-017(2,000,000)
SELECT invoice_no, COUNT(*) c FROM invoices GROUP BY invoice_no HAVING c > 1;   -- 0 件

SELECT je.journal_no, jl.line_no, jl.dc, a.code, jl.amount, tc.code, tc.taxation_type, jl.is_tax_line
