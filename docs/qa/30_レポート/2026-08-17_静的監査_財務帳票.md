# 所見（重要度順）

## P0

### F-01 [P0] 期首残高が前期末から乖離しても、どの帳票にも検知手段が無い（第19期の 4 帳票が同時に 8,936,588 円ずれている）

- **場所**:
  `BalanceSheet.Query.sql:23-28` ／ `CashFlowStatement.Query.sql:66-70` ／
  `EquityChange.Query.sql:14-19` ／ `MonthlyTrend.Query.sql:59-63`
- **症状**: 4 帳票とも期首を `opening_balances`（当年度分）だけから取り、
  **前期の期末残高と突き合わせていない**。繰越が実行された後に前期へ仕訳を足しても、
  当年度の期首は古いスナップショットのまま更新されない。
  そして **`opening_balances` は年度内で Σ=0 に閉じているため、当年度の BS は完璧に貸借一致する**。
  つまり「前期末 ≠ 当期首」という誤りを示すシグナルが、7 帳票のどこにも出ない。
- **実測（第18期 → 第19期）**:

  | | 金額 |
  |---|---:|
  | 第18期 繰越利益剰余金 期末（貸方） | 750,000 |
  | 第18期 当期純利益 | 7,139,362 |
  | **本来の第19期 期首（貸方）** | **7,889,362** |
  | **実際の第19期 期首（借方）** | **1,047,226** |
  | **差額** | **8,936,588** |

  科目別の乖離も同時に発生している（売掛金 6,232,000／普通預金 3,665,110／仮受消費税 942,000 ほか計 11 科目）。
  第19期の期首残高は `Σ balance = 0`・資産合計 5,868,985 で**それ自体は完全に整合**しており、
  これは `docs/tests/11_E2Eテストシナリオ/README.md` §4 が**第18期**に期待していた値（BS 合計 5,868,985・
  当期純損失 1,797,226）と一致する。**繰越実行時点の第18期を凍結したコピーが、そのまま第19期の期首として残っている。**
- **影響**: 第19期の 貸借対照表・キャッシュ・フロー計算書・株主資本等変動計算書・月次推移表(BS) が
  同時に誤る。しかも 4 帳票すべてが「内部的には正しい」ため、目視でも検算行でも発見できない。
- **提案**: 7 帳票のどれか（BS が自然）に「前期末残高 − 当期首残高 = 0」の検算行を足す。
  または `docs/qa/20_不変条件SQL` 側に前期末＝当期首の不変条件を追加する。
  **繰越処理そのものの修正は本監査の対象外**（`FiscalYear` 側）。
- **確度**: 確定

## P1

### F-02 [P1] C/F の「現金及び現金同等物の期首残高」が前期の期末残高と結びついていない

- **場所**: `CashFlowStatement.Query.sql:66-70`（`cash_open`）・`:119-120`（期首・期末の表示行）
- **症状**: `cash_open` は当年度の `opening_balances` から現預金帯（コード 1000〜1099）を拾うだけで、
  前年度の C/F の期末残高との連続性を検証していない。C/F は本来「前期末 → 当期末」の連続性が
  帳票の骨格そのものなので、ここが切れると帳票の意味が失われる。
- **実測**: 第18期 期末現金 = 5,150,000 ＋ 2,375,720 = **7,525,720**（BS の現預金と一致・恒等式も成立）。
  一方 第19期 期首現金 = **3,810,610**。**同じ DB の連続する 2 期で 3,715,110 の断絶**がある。
- **根拠**: 恒等式自体は健全（実測で `営業CF 2,662,084 ＋ 投資CF △286,364 ＋ 財務CF 0 = Δ現預金 2,375,720` が
  厳密に一致）。壊れているのは開始点だけ。
- **確度**: 確定（F-01 の C/F における現れ方。別建てにしたのは、C/F だけは「期首・増減・期末」を
  1 枚に印字しており、前期との接続を帳票内で示せる唯一の場所だから）

### F-03 [P1] 月次推移表だけが仕訳を `fiscal_periods` 経由で拾うため、期間行に載らない日付の仕訳が黙って落ちる

- **場所**: `MonthlyTrend.Query.sql:21-30`（`mv` の `JOIN per p ON date(e.entry_date) BETWEEN …`）
- **症状**: BS・PL・C/F は `e.fiscal_year_id` だけで仕訳を集める。月次推移表は
  **`fiscal_year_id` に加えて「その年度の `fiscal_periods` のいずれかの期間に日付が入っていること」**を
  要求する（INNER JOIN）。両方の条件は DB で保証されていない——
  `journal_entries` に `entry_date` と `fiscal_year_id` の整合制約は無く（`ddl` の
  `CREATE TABLE journal_entries` に CHECK も FK 複合制約も無い）、`fiscal_periods` は
  `UNIQUE(fiscal_year_id, period_no)` だけで年度全体を覆う保証も無い。
- **影響**: 期間行の隙間に落ちた仕訳は月次推移表からだけ消える。
  結果として **PL の年間合計 ≠ 月次推移表の Total 列**、および **BS 検算行（負債・純資産合計）が
  資産合計と一致しなくなる**。しかもエラーにならず、金額が小さく減るだけ。
- **実測**: 現データでは該当 0 件（`fiscal_year_id` と日付が食い違う確定仕訳 0 件／
  どの期間にも載らない確定仕訳 0 件／第18期の期間は 12 行で年度を隙間なく被覆）。
  したがって **今は症状が出ていない**。
- **確度**: 確定（コードと DDL から。現データでは未発現）

### F-04 [P1] 月次推移表の月列が 12 固定なのに、期間の取得側は 12 に制限していない（決算期変更で合計が壊れる）

- **場所**: `MonthlyTrend.Query.sql:14-20`（`per`。`WHERE fiscal_year_id IN (SELECT id FROM yr)` のみ）と
  出力側の `m01`〜`m12` 固定列（`:107-119` ほか各 UNION ブロック）
- **症状**:
  - PL の Total 列は `SUM(r.amt)`＝**全期間の合計**。一方、画面に出る列は第1〜12月だけ。
    13 期間以上の年度（決算期変更に伴う 13〜18 ヶ月の変則決算期）では、
    **第13月以降の金額が Total には入るが列には出ない → 12 ヶ月を足しても Total に合わない。**
  - BS の Total 列は `SUM(CASE WHEN b.period_no = 12 THEN …)` の**決め打ち**なので、
    13 期間の年度では「期末残高」ではなく「第12月末残高」を出す（列名は「合計/期末」）。
  - 逆に 12 未満の短い決算期では、余った列が空白のまま並ぶ。
- **根拠**: `fiscal_periods.period_no` に上限の CHECK は無い（DDL のコメントに「1〜12（期首月=1）」と
  あるだけ）。SQL 冒頭の設計コメント `-- 先頭行（sort_key '00-…'）は暦月ヘッダ（… 決算期変更に自動追随）` は
  **暦月ラベルにしか当てはまらず、列数と Total には当てはまらない**。
- **実測**: 現データは 3 年度とも `fiscal_periods` が 12 行ちょうど。よって未発現。
- **確度**: 確定（コードと DDL から。現データでは未発現）

### F-05 [P1] 株主資本等変動計算書だけ、対象仕訳の絞り込みが `entry_date` 範囲（他 6 本は `fiscal_year_id`）

- **場所**: `EquityChange.Query.sql:20-27`（`mv`）・`:29-38`（`ni`）
- **症状**: `mv` と `ni` は **`fiscal_year_id` をまったく見ず**、
  `date(e.entry_date)` が年度の開始〜終了に入っているかだけで仕訳を選ぶ。
  BS・PL・C/F・月次推移・消費税 2 本はすべて `e.fiscal_year_id` を基準にしている。
  両者が一致する保証は DB に無い（F-03 と同じ根）。
- **影響**: 同じ年度を選んでいるのに、株主資本等変動計算書だけが別の仕訳集合を見る。
  当期純利益欄が BS・PL と食い違い、期末純資産が BS の純資産合計と合わなくなる。
- **実測**: 現データでは一致（`fiscal_year_id` と日付が食い違う確定仕訳 0 件。
  第18期の当期純利益は BS 基準・PL 基準・EquityChange 基準の 3 通りすべてで 7,139,362）。
- **確度**: 確定（コードから。現データでは未発現）

## P2

### F-06 [P2] 対象年度を選ばずに開くと、7 帳票すべてが無言で「今日を含む年度」を表示する（セレクトは空欄のまま）

- **場所**: 各 `*.Query.sql` の `yr` / `fy` CTE（`COALESCE(@fiscal_year_id, (SELECT id FROM fiscal_years WHERE date(start_date) <= date('now','localtime') AND …))`）と、
  7 本の `SearchLayouts[""].OnSearchInitialization`
- **症状**:
  1. `OnSearchInitialization` は **MonthlyTrend の `Search_OnInitialization` だけ**で、そこも設定するのは
     表示帳票（PL/BS）のみ。**年度の初期値を入れている帳票は 1 つも無い。**
     `FiscalYearRef` は `EmptyCandidateType: "Null"` なので空候補も選べる。
  2. 結果として、開いた直後の画面は「対象年度: （空欄）」なのに、中身は今日を含む年度のデータ。
     ユーザーからは「全年度の累計」にも「まだ何も絞っていない」にも見える。
  3. **今日がどの年度にも入らない場合**（決算期の切り替え漏れ・年度マスタの未整備）、
     内側の SELECT が NULL を返し `id = NULL` で 0 行になる。BS は
     「資産合計 0 / 負債・純資産合計 0」の 2 行、PL と C/F は**段階利益行・小計行がすべて 0 で描画される**——
     エラーでも空表でもなく、**もっともらしいゼロの財務諸表**が出る。
- **確度**: 確定（1・2 はコードと JSON から。3 は SQL の評価から。ゼロ表示の見え方は要実機確認）

### F-07 [P2] 月次推移表(PL) は、同じ表の中で「空白」と「0」が混ざる

- **場所**: `MonthlyTrend.Query.sql:126-137`（科目行）・`:145-157`（区分小計）と
  `:166-178` 以降の段階利益行（`plm` 経由）
- **症状**: 科目行・区分小計は `SUM(CASE WHEN r.period_no = 1 THEN r.amt END)` で、
  その月に取引が無ければ **NULL＝空白セル**。一方、段階利益行は `plm` を通り、
  `plm` が `per LEFT JOIN plrow` ＋ `COALESCE(…, 0)` で全 12 期間を 0 埋めしているため **0 と表示される**。
- **実測（第18期・現データで発現中）**: 確定仕訳は 2026-06／07／08 と 2027-03 にしかなく、
  売上は第4月（10,315,000）と第5月（1,550,000）だけ。
  したがって **売上高の行は 10 ヶ月が空白、売上総利益の行は同じ月が 0** になる。
- **確度**: 確定（金額は実測。セルの見え方は要実機確認）

### F-08 [P2] 科目別税区分表の「税込対価」列は税込ではない（税額は仮払／仮受消費税の行に分離される）

- **場所**: `TaxDetailByAccount.Query.sql:56-57`（`gross_amount`）・`TaxDetailByAccount.mod.json` の
  `GrossAmount.DisplayName = "税込対価"`
- **症状**: 消費税は `is_tax_line = 1` の別行として **仮払消費税(1900) / 仮受消費税(2200) の科目に**立つ
  （`journal_lines` の設計どおり）。本表は科目 × 税区分でグループ化するので、
  費用・収益科目の行には税行が 1 本も入らない。結果、
  **費用科目の行は「消費税額 = 0」「税込対価 = 本体金額」**になり、税額だけが 1900 / 2200 の行に独立して並ぶ。
- **実測（第18期・課税仕入 10%）**:

  | 科目 | 本体金額 | 消費税額 | 「税込対価」表示 |
  |---|---:|---:|---:|
  | 旅費交通費 | 51,546 | 0 | 51,546 |
  | 地代家賃 | 450,000 | 0 | 450,000 |
  | 外注費 | 500,000 | 0 | 500,000 |
  | 仮払消費税 | 0 | 165,853 | 165,853 |

- **影響**: 本表の目的（`TaxDetailByAccount.Query.sql:1-13` に明記された「税区分の付け間違いを見つける」）
  に対しては本体金額列で十分機能するが、「税込対価」という列名が
  **その科目の税込取引額だと読ませてしまう**。消費税集計表（税区分単位なので税行も同じグループに入る）
  では同じ列が本当に税込になるため、2 帳票で同名列の意味が違う。
- **確度**: 確定

### F-09 [P2] 貸借対照表の当期純利益は損益科目の**期首残高も**取り込む（損益計算書は取り込まない）

- **場所**: `BalanceSheet.Query.sql:11-41`。`bal` CTE は BS/PL を区別せず全科目に
  `opening_balances` を LEFT JOIN しており、`ni` はその `bal` の PL 部分を集計している
- **症状**: 損益計算書（`ProfitLoss.Query.sql:10-20`）は `journal_lines` だけを見て期首を見ない。

### F-12 [P2] 消費税集計表の控除方式判定は、閾値マスタが引けないと「個別対応方式が必要」と**断定して**表示する

- **場所**: `TaxSummary.Query.sql:69-77`（`th`。2 つの `LIMIT 1` スカラサブクエリ）・
  `:114-118`（判定の `CASE WHEN … >= th.ratio_min AND s.taxable <= th.sales_cap THEN … ELSE …`）
- **症状**: `th` が行を引けないと `ratio_min` / `sales_cap` は NULL になる。
  SQL の三値論理では `x >= NULL` は NULL＝真ではないので、**必ず ELSE 側**、すなわち
  「個別対応方式または一括比例配分方式が必要です」が出る。
  エラーにも「判定できません」にもならず、**課税売上割合 100% の会社にも誤った判定を断定して見せる。**

  正しく解決でき、第18期の表示は `99.99%（全額控除できます）`（課税売上 12,865,000 / 非課税売上 620）。
  `valid_to` は真の NULL（`typeof = 'null'`）なので `IS NULL` 判定も効いている。**今は正しい。**
- **提案**: `ratio_min IS NULL OR sales_cap IS NULL` のときは「判定できません（閾値マスタ未設定）」を出す。
- **確度**: 確定
