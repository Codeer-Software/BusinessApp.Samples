# 権限条件の全数監査 — 全モジュールのアクセス制御

- 実施日: 2026-08-17
- 手段: **静的読解のみ**（`*.mod.json` の機械走査＋関連 `*.mod.cs`・仕様書の読解。
  DB 書き込み・サーバ起動・deploy・designcheck・commit・SELECT はいずれも未実施）
- 対象: `Designer/Design/Modules/**/*.mod.json` **全 104 本**
- 判定基準: `docs/10_部品アーキテクチャ.md` §2/§5（権限モデル・フレームゲート）、
  `docs/03_機能スコープ.md` B-8（経理限定）、`docs/decisions/0026`（削除ではなく無効化）、
  `Designer/ClaudeCodeForDesigner/_specs/ModuleDesign.md`・`_specs/QueryAndSql.md`・

- **修正は一切行っていない。** 本書は指摘のみ。

## 0. 前提にした CLB の権限セマンティクス（正典からの引用要約）

監査の判定はこの 5 点に依存する。いずれも CLB 仕様リファレンスに明記がある。

1. **条件が空 = 制限なし**（全ログインユーザーが通る）。空は「未設定」ではなく「全開放」を意味する。
2. **新規作成は読み取り権限を要求しない。更新・削除は要求する**
   （`Docs/AppPatterns/auth_personal_data.md`。SQL の `UPDATE … WHERE` に `SELECT` 権限が要るのと同じ規則）。
   → `UserReadCondition` だけ設定して `UserWriteCondition` が空のモジュールは、
   **「読めないが INSERT はできる」**という状態になる。
3. **`DataReadCondition` / `DataWriteCondition` は Query モジュール（`DbTable` 空＋QueryField）に効かない。**
   行の絞り込みは SQL の `WHERE` と予約パラメータ `@current_user_id` で書く。
4. **`Standalone` の ExecuteSqlField の実行には `UserWriteCondition` が要る。**
   本アプリの ExecuteSqlField は `FiscalYear.CarryOverSql`（`Timing: Update`）1 本のみで Standalone は無し。
5. **スクリプト（`*.mod.cs`）は WASM 側で走るためサーバ側の防御ではない。**
   `IsVisible` / `IsViewOnly` / `Toaster.Error` によるガードは、`ModuleDataIO` 経路（URL 直指定・API）を素通りする。
   サーバで効くのは `CanCreate/CanUpdate/CanDelete` と 4 条件だけ。

## 1. 走査結果（網羅の証跡）

| 指標 | 本数 |
|---|---|
| 走査したモジュール総数 | **104** |
| うち `DbTable` を持つ（実テーブル書き込み経路あり） | 63 |
| うち表示専用（`DbTable` 空。Query／集計／ボード） | 41 |
| 4 条件すべて空 | **13** |
| 一部のみ設定 | **91** |
| 4 条件すべて設定 | **0** |

「4 条件すべて設定 = 0」は異常値ではない。ほとんどのモジュールは 4 条件のうち 1〜2 本しか必要としない
（例: 参照マスタは読み取り全開放が正しく、行レベル条件も不要）。**空であること自体は穴ではない。**
本監査は「そのモジュールが扱うデータの機微性・業務上の必要性」と突き合わせて判定した。

その結果:

- **穴と判定したモジュール: 28 本**（内訳は §2。既知の `ExpenseRequest` を含む）
- **防御が妥当と判断したモジュール: 76 本**

妥当と判断した代表例と理由:

| 分類 | 例 | 空でよい理由 |
|---|---|---|
| 参照マスタ（読み取り全開放） | `Partner` `Project` `Department` `DepartmentMember` `TaxCategory` `TaxRate` `ExpenseCategory` `SystemThreshold` `AccountLookup` `FiscalYearLookup` | 全画面の Select/Link 候補として全員が読む必要がある。書き込みは `HasAccountingAccess` / `IsSysAdmin` で閉じている |
| `AppUser` の読み取り | `MasterSystem/AppUser` | CLB 仕様上 `AppUser` に読み取り条件を付けると `CurrentUser`・LinkField 表示が全部壊れる（`_specs/Authentication.md` の明示的な警告）。**パスワードは `PasswordHashField` で `hash`/`salt` 列が書き込み専用＝読み戻されない**ため、機微列の露出は無い |
| 経理限定の帳票・Query | `FinancialReports/*` `Accounting/GeneralLedger` `Management/*` `Purchasing/PaymentSchedule` ほか | `UserReadCondition: HasAccountingAccess`（一部 `IsApprover OR`）で読み取りを閉じており、`DbTable` が空なので書き込み経路が存在しない |
| 行レベルで自分に閉じた個人ビュー | `Expense/MyApplication`（`Creator=自分`）`Expense/ApprovalInbox`（`CurrentApprover=自分`）`Shell/Notification`（`RecipientUser=自分`） | `DataReadCondition` で正しく絞っている。**この 3 本が「正しい実装の見本」** |
| 取引先の機微列の分離 | `MasterBusiness/Partner`（読み全開放）と `PartnerBank`（同じ `partners` テーブル・経理限定） | 口座番号・銀行コードは `PartnerBank` 側にしか置いておらず、モジュールのフィールド構成で列を分離できている。**設計として正しい** |

### 観点 V5（ADR-0041 の職務分掌）の結果: **違反なし**

業務モジュールの `UserReadCondition` / `UserWriteCondition` を全数確認したところ、
**`IsSysAdmin` を OR で足しているものは 1 本も無い**。`IsSysAdmin` を条件に使うのは
`AppUser` / `Department` / `DepartmentMember` / `ApprovalFlowTemplate*` / `ApprovalRouteRule` /
`PasswordPolicy` の**書き込み**のみで、これは組織・ガバナンスマスタの管理者領分そのもの。
admin は `HasAccountingAccess` 等の業務フラグを持たない限り業務データを読めない。ADR-0041 は守られている。

## 2. 所見（全 17 件）

重要度: P0=承認・金銭の統制が破れる / P1=他人の機微データ露出・帳簿の不正投入 / P2=統制の抜け・完全性 / P3=軽微

### [P0][観点 V1・V3] 承認フロー本体に一切の権限条件が無く、自己承認できる

- 場所: `Designer/Design/Modules/Expense/ApprovalFlow.mod.json`
  （`UserReadCondition` / `UserWriteCondition` / `DataReadCondition` / `DataWriteCondition` すべて空・`CanUpdate: true`）
- 症状: 任意のログインユーザーが、他人の申請に紐づく `approval_flow` 行を読み、
  `Status` を `Pending` → `Approved` に直接書き換えられる。承認権限の判定は
  `ApprovalFlow.mod.cs` の `UpdateButtons()` にある
  `ApproveButton.IsVisible = isPending && HasWaitingMemberForCurrentUser()` **だけ**で、これは WASM 側の表示制御。
- 根拠: 前提 5（画面ガードはサーバ防御ではない）＋前提 1（空=全開放）。
  承認済み＝経費精算の支払実行に直結するため、金銭の統制が破れる。
- 確度: **確定**（条件が空であることと、承認判定がスクリプトにしか無いことは静的に確定）

### [P0][観点 V1・V3] 承認の段・承認者行も無条件で書き換えられる

- 場所: `Designer/Design/Modules/Expense/ApprovalFlowOrder.mod.json`・
  `Designer/Design/Modules/Expense/ApprovalFlowMember.mod.json`（ともに 4 条件すべて空・`CanCreate/CanUpdate/CanDelete: true`）
- 症状: 上位の `ApprovalFlow.Status` を触らずとも、`approval_flow_member.Status` を `Waiting` → `Approved` に、
  `ApproverUser` を自分に、`approval_flow_order.Status` を `Skipped` にする等で承認段を消化・迂回できる。
  段の追加・削除も可能なため「課長→部長の積み上げ」（ADR-0048）を任意に短絡できる。
- 根拠: 姉妹モジュール `ApprovalInbox` は `DataReadCondition: CurrentApprover=自分` で正しく絞っているのに、
  その実体テーブルを持つ 3 モジュールが全開放という**不揃い**。
- 確度: **確定**

### [P0][観点 V1・V2] 経費明細行（領収書ファイル込み）が全開放

- 場所: `Designer/Design/Modules/Expense/ExpenseRequestLine.mod.json`（4 条件すべて空・`CanCreate/CanUpdate/CanDelete: true`）
- 症状: 任意のログインユーザーが、他人の `expense_request_lines` を URL 直指定で開き、
  金額・費目・接待先（`EntertainmentGuest`）・案件・**領収書ファイル（`Receipt` FileField）**を閲覧でき、
  さらに行の更新・削除・追加ができる。親の `ExpenseRequest` 側にある「申請済みなら編集不可」のガードは
  親モジュールのスクリプトにしか無いため、**行モジュールを直接開けば承認済み申請の明細も改竄できる**。
- 根拠: 同じ経費データを扱う `MyApplication` は `DataReadCondition` で `Creator=自分` に絞っている（不揃い）。
  領収書画像は個人の機微情報（ADR-0066 で明細行に移設された）。
- 確度: **確定**（既知の `ExpenseRequest` とは別モジュール・別テーブル）

### [P1][観点 V1] 承認履歴が全件読めて、偽の履歴行を作れる

- 場所: `Designer/Design/Modules/Expense/ApprovalHistory.mod.json`（4 条件すべて空・`CanCreate: true`）
- 症状: 全社員の承認履歴（誰がいつ何を承認・却下し、どんなコメントを書いたか）を全件閲覧できる。
  加えて `CanCreate: true` かつ書き込み条件が空なので、**存在しない承認の履歴行を捏造できる**
  （`ActorUser` は `AddHistory()` がスクリプトで詰めているだけで、サーバ側の縛りが無い）。
  `CanUpdate/CanDelete` は false なので既存行の改竄・消去はできない。
- 根拠: 却下コメントは人事上の機微情報。監査証跡が改竄可能では統制の証拠にならない。
- 確度: **確定**

### [P1][観点 V3・V2] 会計コアの伝票に `UserWriteCondition` が無く、経理でない社員が仕訳を INSERT できる

- 場所: `Modules/Accounting/JournalEntry.mod.json`・`JournalLine.mod.json`
  （`UserReadCondition: HasAccountingAccess` のみ・`UserWriteCondition` 空・`CanCreate: true`）
- 症状: 一般社員は仕訳を**読めない**（読み取り条件が効く）が、前提 2 により
  **新規作成だけは読み取り権限を要求しない**ため、`journal_entries` / `journal_lines` に行を INSERT できる。
  読み戻せないので画面上は無反応だが、総勘定元帳・試算表・財務諸表はテーブルを集計するので**帳簿が汚染される**。
- 根拠: 同じ会計部品の `JournalTemplate` / `JournalTemplateLine` / `CashEntryDraft` /
  `Bank/BankStatementLine` / `MatchingRule` は `UserWriteCondition: HasAccountingAccess` を**設定している**。
  会計コアの本丸だけが抜けているのは明確な不揃い。docs/03 B-8（経理機能は経理アクセス権を持つ者だけ）とも齟齬。
- 確度: **確定**（設計上の穴。実際に INSERT が通るかの実証は 要実機確認）

### [P1][観点 V3] 期間・固定資産・開始残高も同型（`UserWriteCondition` 欠落）

- 場所: `Modules/Accounting/FiscalYear.mod.json`・`FiscalPeriod.mod.json`・`FixedAsset.mod.json`・`OpeningBalance.mod.json`
  （いずれも `UserReadCondition: HasAccountingAccess` のみ・`CanCreate: true`）
- 症状: 非経理ユーザーが会計期間・会計期・固定資産・開始残高の行を新規投入できる。
  特に `fiscal_periods` への投入は**締めガード（クローズ済み期間への起票拒否）の前提を壊す**
  ——同一年月の期レコードが二重に存在すると、期間解決の結果が投入行に依存する。
- 根拠: 上と同じ不揃い。`FiscalYear` は `CarryOverSql`（ExecuteSqlField / `Timing: Update`）も持つが、
  こちらは更新経路のため読み取り権限が要り、非経理からは起動できない（Standalone ではない）。
- 確度: **確定**（設計上の穴。実証は 要実機確認）

### [P1][観点 V3・V2] 請求書・入金にも `UserWriteCondition` が無い

- 場所: `Modules/Sales/Invoice.mod.json`・`Modules/Sales/Receipt.mod.json`
  （`UserReadCondition: HasAccountingAccess` のみ・`CanCreate: true`）
- 症状: 営業機能すら持たない社員が `invoices` / `receipts` に行を INSERT できる。
  請求書は発行・ロック（ADR-0033）と入金予定の自動作成（ADR-0032）が乗る伝票で、
  売掛残高・資金繰り予測がテーブルを直接集計するため、数字が動く。
- 根拠: 明細側の `InvoiceLine` には `UserWriteCondition: HasAccountingAccess` が入っており、
  親の `Invoice` にだけ無い（**親子で不揃い**）。同じ営業部品の
  `Quote` / `QuoteLine` / `SalesOrder` / `Acceptance` / `RecurringBilling` / `RecurringRunPlan` /
  `SesRunPlan` はすべて `UserWriteCondition` を持つ。
- 確度: **確定**（設計上の穴。実証は 要実機確認）

### [P1][観点 V1・V2] 全社員の工数が全員に読める

- 場所: `Designer/Design/Modules/Timesheet/TimeEntry.mod.json`
  （`UserReadCondition` 空・`DataReadCondition` 空・`DataWriteCondition: UserRef=自分` のみ）
- 症状: 任意のログインユーザーが `time_entries` を全件検索でき、他人が
  「どの案件に何時間・どんなメモで」入力したかを閲覧できる。書き込みは自分の行に閉じているのに、
  読み取りだけ全開放という**非対称**。
- 根拠: 姉妹モジュール `TimeEntryAdmin`（同じ `time_entries`）は
  `UserReadCondition/UserWriteCondition: HasAccountingAccess` で閉じている。
  「経理だけが横断して見る」ための別モジュールを用意している以上、staff 側は本人に閉じるのが設計意図のはず。
  スクリプト側も `OnSearchInitialization()` に
  「一覧の検索初期値: 担当者=自分（サイドバーリンク経由で発火。**権限フィルタではない**）」と自認している。
- 確度: **確定**（露出は確定。ただし「全員に見せてよい」という業務判断があるなら仕様確認が要る）

### [P2][観点 V3] 他人名義の工数登録を止めているのは WASM の `IsViewOnly` だけ

- 場所: `Modules/Timesheet/TimeEntry.mod.cs`（`Detail_OnAfterInit()`）／`TimeEntry.mod.json`（`UserWriteCondition` 空）
- 症状: スクリプトのコメントは「担当者の付け替えは経理のみ（他人名義の新規登録を防ぐ。更新・削除は
  DataWriteCondition がサーバ側で本人限定済み）」と書いているが、**新規登録を防いでいるのは
  `UserRef.IsViewOnly = true` だけ**。`DataWriteCondition` が INSERT 時の新規行に対して評価されるかは
  CLB 仕様に明記が無い。評価されないなら他人名義の工数を投入でき、原価配賦・案件損益が歪む。
- 根拠: 前提 5。コメント自身が「更新・削除は」と書いており、新規は射程外であることを示唆している。
- 確度: **要実機確認**（`DataWriteCondition` の INSERT 適用有無が分岐点）

### [P2][観点 V4] ADR-0026 が「削除ではなく無効化」と決めた 10 マスタが全部 `CanDelete: true`

- 場所: `MasterSystem/Account.mod.json`・`SubAccount`・`TaxRate`・`TaxCategory`・`AppUser`・`Department`／
  `MasterBusiness/Partner`・`Project`・`BankAccount`／`Sales/RecurringBilling`（10 本すべて `CanDelete: true`）
- 症状: ADR-0026 の横展開調査は「有効フラグを持つマスタ 10 種は**一覧削除を撤去**し
  『削除ではなく無効化（有効チェック）』に統一」と決めているが、撤去したのは**一覧レイアウトのボタンだけ**で、
  モジュールの削除経路は開いたまま。書き込み権限を持つ者（経理／sysadmin）が
  URL 直指定・API 経由で参照済みマスタを物理削除でき、ADR が防ごうとした
  「生 SQLite FK エラーの露出」および参照整合性の破壊が起きうる。
  特に `AppUser` は ADR-0043 が一覧ヘッダーに「削除はできません。退職者は有効チェックを外して無効化します」と
  明記しているのに、`CanDelete: true` のまま。
- 根拠: ADR-0026「横展開調査の結果」節と `CanDelete` の実値の齟齬。ADR-0043 の文言との齟齬。
- 確度: **確定**

### [P2][観点 V3] 定期請求契約の削除可否がスクリプト判定のみ

- 根拠: 前提 5。判定条件（作成者本人 ∨ 経理）が `DataWriteCondition` に落ちていない。
- 確度: **確定**

### [P2][観点 V3] 伝票の「draft のみ削除」（ADR-0026）もすべてスクリプト側のガード

- 場所: `Modules/Sales/Quote.mod.cs`・`Acceptance.mod.cs`・`Invoice.mod.cs`・`Receipt.mod.cs`・

- 確度: **確定**（実装状況は確定。許容するかは設計判断）

### [P3][観点 V1] 任意ユーザー宛の偽通知を作成できる

- 場所: `Designer/Design/Modules/Shell/Notification.mod.json`
  （`DataReadCondition: RecipientUser=自分` は正しいが、`UserWriteCondition` が空・`CanCreate: true`）
- 症状: 読み取りは自分宛に正しく閉じているが、作成が全開放なので、
  任意のユーザー宛に任意の本文・任意のリンク先を持つ通知を送り込める（社内フィッシングの足場）。

- 確度: **確定**

### [P3][観点 V1・V2] `PortalTodoData` だけ `UserReadCondition` が無く、全ユーザー分の件数を返す

- 場所: `Designer/Design/Modules/Shell/PortalTodoData.mod.json`（4 条件すべて空）／`PortalTodoData.Query.sql`
- 症状: SQL は `FROM app_users u WHERE u.is_active = 1` で**全有効ユーザーの行**を返し
  （承認待ち件数・申請中件数）、`@current_user_id` による絞り込みが無い。
  読み取り条件も無いので、任意のユーザーが他人の件数を取得できる。
- 根拠: 姉妹の `PortalQueueData` / `PortalKpiData` は `HasAccountingAccess`、
  `PortalAlertData` は `HasSalesAccess OR IsApprover OR HasAccountingAccess` を設定している（**不揃い**）。
  ただし SQL のコメントが「ユーザー数は小規模なので全行で問題ない」と設計意図を明示しており、
  返るのは件数（整数）だけなので機微性は低い。前提 3 のとおり Query モジュールに `DataReadCondition` は効かないので、
  直すなら `@current_user_id` を `WHERE` に足す。
- 確度: **確定**（露出は確定・影響は軽微）

### [P3][観点 V2] 既知の `ExpenseRequest` と同一テーブルを見る `ExpenseSettlementQueue` は正しく閉じている（対比のための記録）

- 場所: `Designer/Design/Modules/Expense/ExpenseSettlementQueue.mod.json`
- 症状: なし。`UserReadCondition/UserWriteCondition: HasAccountingAccess` で閉じており、
  `DataReadCondition` が無いのは「経理が全件を横断して処理する」という業務要件どおり。
- 根拠: 同じ `expense_request` テーブルを、経理向けは `UserReadCondition` で、
  本人向けは `DataReadCondition` で閉じる、という切り分けは正しい。**穴は `ExpenseRequest` 本体だけ**。
- 確度: **確定**

### [P3][観点 V4] `CanDelete: true` は全 104 本中 56 本

- 場所: 全体（内訳は §3 の表）
- 症状: 前段の 10 マスタと伝票群を除いた残りは、明細行（`*Line`）・中間データ
  （`bank_statement_preview` / `recurring_run_plan` / `ses_run_plan` / `cash_entry_drafts`）・
  組織/承認テンプレートで、いずれも削除が業務上必要か、親の `DeleteTogether` に連動する行。
  ADR-0026「残課題（低優先）」が挙げる有効フラグ無しマスタ
  （`AccountCategory` / `ApprovalFlowTemplate` / `FiscalYear` / `FiscalPeriod` / `FixedAsset` /
  `InvoiceTransitionRate` / `SystemThreshold`）の削除存置も、ADR で明示的に許容済み。
- 根拠: ADR-0026 の残課題節。
- 確度: **確定**（穴ではないが、`CanDelete` の棚卸し結果として記録）

### [P3][観点 V5] `admin`（sysadmin）による業務データ越境: 違反なし

- 場所: 全業務モジュール（`Accounting/` `Sales/` `Purchasing/` `Expense/` `Timesheet/` `Management/` `Bank/` `FinancialReports/`）
- 症状: なし。全数確認の結果、業務モジュールの読み書き条件に `IsSysAdmin` の OR は 1 本も無い。
  `IsSysAdmin` は `AppUser` / `Department` / `DepartmentMember` / `ApprovalFlowTemplate*` /
  `ApprovalRouteRule` / `PasswordPolicy` の**書き込み条件**にのみ現れる。
- 根拠: ADR-0041 の職務分掌（admin は業務画面に入れない）が、モジュール条件のレベルでも守られている。
  ただし上の P0/P1 群（条件が空のモジュール）は「全ログインユーザー」に admin も含むため、
  **条件が空である限り admin も素通りする**——V5 の実質的な違反はそこに集約される。
- 確度: **確定**

### [P3][観点 V2] `NotificationCenter` / `PortalHome` / `PortalSidebar` / `PasswordChange` の 4 条件空は妥当

- 場所: `Modules/Shell/NotificationCenter.mod.json` ほか 3 本（いずれも `DbTable` 空）
- 症状: なし。`DbTable` が空なので直接の書き込み経路が無い。
  `NotificationCenter` は `ModuleSearcher<Notification>` 経由で読むため `Notification` の
  `DataReadCondition`（自分宛）が効く。`PasswordChange` は `WebApiService.Post("/api/password/change")` で

  他人のパスワードは変更できない（ADR-0059 のとおりサーバ 1 か所判定）。
- 根拠: 実装の読解による。
- 確度: **確定**

## 4. 推奨する直し方（実装はしていない）

優先順に、方針だけ記す。実装は別タスク。

1. **P0 の 3 群**（`ApprovalFlow` / `ApprovalFlowOrder` / `ApprovalFlowMember` / `ApprovalHistory` /
   `ExpenseRequestLine`）に行レベル条件を入れる。承認系は「申請者本人 ∨ 現在の承認者 ∨ 経理」で
   `DataReadCondition`、承認操作は本来サーバ側でしか判定できないので、
   `DataWriteCondition` に落とせない部分は**サーバ拡張（`CustomizedModuleDataIO` の派生）で弾く**のが筋。
   `ApprovalHistory` は `CanCreate` をスクリプト専用にできないため、少なくとも読み取りを絞る。
2. **`UserWriteCondition` の欠落 8 本**（`JournalEntry` `JournalLine` `FiscalYear` `FiscalPeriod`
   `FixedAsset` `OpeningBalance` `Invoice` `Receipt`）に、姉妹モジュールと同じ
   `HasAccountingAccess`（`Invoice`/`Receipt` は業務に合わせて `HasSalesAccess OR` を検討）を入れる。
   **これは 1 行ずつの機械的な追加で済み、費用対効果が最も高い。**
3. `TimeEntry` に `DataReadCondition: UserRef=自分` を入れる（横断閲覧は `TimeEntryAdmin` の役目）。
   全員閲覧が業務要件なら、その旨を docs に明記して本所見を閉じる。
4. ADR-0026 の 10 マスタは `CanDelete: false` にする（ADR の決定と実装を一致させる）。
5. `PortalTodoData.Query.sql` に `WHERE u.id = @current_user_id` を足す。
6. 再発防止: `Designer/tools/` に「機微テーブルを持つモジュールの 4 条件」を検査する lint を足し、
   新規モジュール追加時に条件の抜けを機械検出する。本監査のスクリプトがその原型になる。
