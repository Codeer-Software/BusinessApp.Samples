## 確度の凡例

- **確定** = ファイル上の記述だけで結論が出るもの（条件式・呼び出しの有無・JSON の設定値）。
- **要実機確認** = コード上の欠落は確定しているが、最終的な画面挙動が CLB ランタイムの
  再描画・再初期化のタイミングに依存するもの。

## 総括

ADR-0066 の骨格（判定額＝合計／費目＝行ごと／段の合成／行ごとの端数処理／1 申請 1 伝票）は
実装と一致しており、`BuildMergedOrders` の合成規則も ADR の手続きどおりである。
一方で **明細行化にともなって「行が持つ税区分」まわりの整合が弱く**、税額を誤る経路が 3 本ある（F-01〜F-03）。
また **入力欄カード（`EditingLine`）の可視状態を更新する呼び出しが 3 経路で抜けており**、
承認後・申請中に明細を足せる穴が残っている（F-04）。行レベルの参照制御が無い点（F-05）も
`MyApplication` / `ApprovalInbox` が `DataReadCondition` を使っているのと対照的である。

## P1

### F-01 [P1][V] 費目を課税→不課税に変えても税区分が追随せず、不課税の経費に仮払消費税が立つ

- 場所: `Designer/Design/Modules/Expense/ExpenseRequestLine.mod.cs:50-53`
- 症状: 入力欄で費目「消耗品費」を選ぶと `TaxCategoryRef` に既定の「課税仕入 10%」が入る。
  そのあと費目を「諸会費」（不課税）に変えても、`ApplyCategoryDefaults` は
  `if (TaxCategoryRef.Value == null)` のときしか既定を入れないため **税区分は課税仕入 10% のまま残る**。
  `IsTaxablePurchase()` が真なので「うち消費税」のクリアも走らない。
  結果、`CalcLineTax` が税額を計算し、仕訳は `D 諸会費 9,091 / D 仮払消費税 909` になる。
  逆方向（不課税 → 課税）では税額 0 のままとなり、控除もれになる。
- 根拠: コード読み。`ApplyCategoryDefaults` の上書き条件が null 限定であること、
  `ExpenseRequest.mod.cs:399-410` の `ResolveLineTaxCategory` が「行の税区分があればそれを使う」ため
  費目と矛盾したまま仕訳生成まで到達すること。仕訳コアの同型不具合 F-01（勘定科目変更時に税区分が
  追随しない）と同じ形。ADR-0066 の B-03（不課税費目の行 → 税額 0）は「費目を先に選んだ場合」しか
  成立せず、実機検証の B 表でも B-03 は実施されていない。
- 確度: 確定

### F-02 [P1][V] インボイス経過措置の税区分を経費で使うと控除割合が適用されず、全額を仮払消費税に計上する

- 場所: `Designer/Design/Modules/Expense/ExpenseRequest.mod.cs:384-396`（`CalcLineTax`）と
  `:981-994`（税行の組み立て）
- 症状: 税区分マスタには `PUR_10_TR`「課税仕入 10%(経過措置)」`PUR_8_TR` があり（`ddl/010_tax.sql:60-61`、
  `uses_transition_deduction = 1`）、明細の税区分セレクトは `IsActive` だけで絞っているので選択できる。
  ところが経費の仕訳生成は `taxationType == "taxable_purchase"` と税率しか見ず、
  **控除割合（現行 80%、2026-10-01 以降 50%）を掛けない**。免税事業者から受け取ったレシートを
  正しく経過措置区分で入力するほど、仮払消費税が過大に計上される。
- 根拠: コード読み。同じ計算を振替伝票側は正しく行っている
  （`Modules/Accounting/JournalEntry.mod.cs:751-765` で `deductible = fullTax * transitionRate / 100`、
  控除できない分を本体額へ寄せる）。経費側だけがこの処理を持たない。
  `FinancialReports/TaxSummary.Query.sql:35-36` も経過措置を前提に集計しているため、
  帳票と仕訳が食い違う。
- 確度: 確定

### F-03 [P1][V] 少額資産の 10 万円判定を税込金額で行い、台帳には税抜で登録する（税込 10 万〜11 万が誤って資産計上）

- 場所: `Designer/Design/Modules/Expense/ExpenseRequestLine.mod.cs:75-81`
- 症状: `ApplyAssetSuggestion` は `Amount`（＝**金額（税込）**）を `SMALL_ASSET_EXPENSE`（100,000）と
  比較して固定資産計上を自動 ON にする。一方 `ExpenseRequest.mod.cs:1079-1081` は
  `baseAmount = gross - CalcLineTax(l)`（税抜）を取得価額として台帳へ登録する。
  税込 105,000 円（税抜 95,455 円）の備品は **自動 ON になり、95,455 円で資産計上される**。
  本アプリは税抜経理（仮払消費税を分離）なので、少額減価償却資産の判定も税抜で行うのが正しく、
  この 1 台は本来その期に全額損金にできる。
- 根拠: コード読み＋税務上の取扱い（少額減価償却資産の判定は採用している消費税経理方式によるため、
  税抜経理なら税抜価額で判定する）。固定資産台帳側は税抜で判定しており
  （`Modules/Accounting/FixedAsset.mod.cs:45`）、経費側だけが税込基準になっている。
- 確度: 確定

### F-05 [P1][V] 経費申請に行レベルの参照制御が無く、一般社員が他人の申請と領収書を閲覧・編集できる

### F-07 [P2][V] 承認依頼通知が「自分が作った最新のフロー」に送られるため、下書きを 2 件持つと通知が届かない

- 場所: `Designer/Design/Modules/Expense/ApprovalFlow.mod.cs:832` と `:900-909`
  （`FetchLatestOwnFlowFromDb`）
- 症状: 初回申請の通知先を「`Creator = 自分` で `Id` が最大の `approval_flow`」から引いている。

  通知はフロー B に対して送られる。B は Draft で Active な段が無いので

- 根拠: コード読み。同じファイルの `Resubmit_OnClick:1186` と `ReapproveForOverrun:1245` は
  `FetchSelfFromDb()`（実 Id 解決）を使っており、初回申請だけが「最新の自分のフロー」に頼っている。
  コメント（`:898-899`）は「同一ユーザーの同時多重申請はブラウザ操作上起こらない前提」と書くが、
  下書きの早期保存でその前提が崩れた。
- 確度: 確定

### F-08 [P2][V] 明細を触るたびに計上日を「明細の最も遅い利用日」で上書きし、手入力の計上日を捨てる

- 場所: `Designer/Design/Modules/Expense/ExpenseRequest.mod.cs:377-380`
- 症状: `RecalcFromLines()` は下書きのあいだ無条件に `ExpenseDate.Value = lastUsed` を実行する。
  経理・申請者が意図して計上日を月末（例: 2026/07/31）に置いても、

- 確度: 確定

### F-09 [P2][V] 手で外した固定資産チェックが、金額・利用日を直すと自動で ON に戻る

- 場所: `Designer/Design/Modules/Expense/ExpenseRequestLine.mod.cs:67-82`
- 症状: `ApplyAssetSuggestion` は `Amount_OnDataChanged` / `UsedDate_OnDataChanged` /
  `Category_OnDataChanged` / AI 読み取り完了のたびに走り、
  「資産性の費目 × 閾値以上 × 現在 OFF」なら ON にする。利用者が意図的に外したという記憶を持たないため、

- 根拠: コード読み。ADR-0066 の D-05 は「自動 ON を手で OFF → OFF のまま維持」を期待値としているが、
  金額・利用日を再入力しない限りしか成立しない。
- 確度: 確定

### F-10 [P2][V] 未払計上は明細合計、支払仕訳はヘッダ合計を使う二経路になっている

- 場所: `Designer/Design/Modules/Expense/ExpenseRequest.mod.cs:1004`（`total` は明細から積算）と
  `:1328`（`int amount = Amount.Value;`）
- 症状: 仕訳生成（`D 費目 / C 未払金`）の貸方は明細から積み直した `total`、
  精算（`D 未払金 / C 普通預金`）は**ヘッダの集計列**を使う。両者が乖離すると未払金が残る。
  乖離は `CommitEntry` の 2 回目の `Submit()`（`:135`）が失敗したとき、あるいは
  `Lines_OnDataChanged` の 2 回目の `Submit()`（`:333`・戻り値未検査）が失敗したときに発生しうる。
  どちらも「明細は保存済み・ヘッダ合計だけ古い」状態を作る。
- 根拠: コード読み。不変条件 D05 はこの乖離を検出できるが、支払仕訳が切られたあとでは
  未払金残高の訂正伝票が要る。同じ値を 2 通りに求めていること自体が設計上の弱点。
- 確度: 確定

### F-13 [P2][V] 「編集をやめる」がヘッダの未保存編集ごと捨てる

### F-14 [P2][Val] 経理の一括処理が無く、月数十〜数百件を 1 件ずつ 3 段階クリックする

- 場所: `Designer/Design/Modules/Expense/ExpenseSettlementQueue.mod.cs`（行アクションは `Open` のみ）、
  `ExpenseRequest.mod.cs:824`/`1257`/`1375`（仕訳生成・精算・完了はいずれも 1 件単位）

## 白と確定させた項目（次回この範囲を再走査しないため）

- **段の合成（ADR-0066 決定 2-2）** — `BuildMergedOrders`（`ApprovalFlow.mod.cs:72-145`）は
  キーの畳み込み・`order_no` 最大値による並び・同値時の `manager → director → 個人指名` を
  ADR の手続きどおりに実装している。行順に依存しない（キーの初出順ではなく seq でソートする）。
- **判定額の分割回避** — `GetJudgeAmount`（`:499-502`）は区分の分岐を持たず常に明細合計。
  ADR の追補 1（事前申請も明細合計）と一致。
- **税の端数処理の方針** — `CalcLineTax` は行ごとに 1 回だけ切り捨てる。
  ADR-0050（税率ごとに 1 回）は自社発行の請求書側の規約であり、ここに適用しないという
  ADR-0066 決定 5 の判断とコードが一致している。
- **二重生成ガード** — 仕訳（`:843-846`）・支払仕訳（`:1278-1281`）とも `source_type` + `source_id` で
  検索してから作る。固定資産も `code` で重複を弾く（無言なのは F-22）。
- **`ListField` からの行追加による幽霊明細** — `Lines` は `CanCreate: false` なので、
  行番号 NULL のまま親 FK だけ持つ行が一覧から生まれる経路は無い（`DeleteTogether: true` で
  親削除時に明細も消える）。
- **`date('now')` の UTC ずれ** — Expense 配下に SQL 直書きの日付判定は無い。
  日付はすべて `DateOnly.FromDateTime(DateTime.Today)`。
- **自己承認の回避** — `WalkUpRole`（`:404-421`）で申請者を除外し、
  `ResolveFixedApproverAvoidingSelf`（`:437-442`）で固定指名も代替に振る。
  役職段の圧縮（`:295-298`）は連続する役職段にだけ効き、個人指名段は畳まれない。
- **マスタ参照の有効性フィルタ** — 明細の費目・税区分・案件のセレクトはいずれも
  `IsActive = true` で絞っている。
