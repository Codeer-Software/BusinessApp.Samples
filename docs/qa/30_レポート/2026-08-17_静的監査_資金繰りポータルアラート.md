## 所見

### F-01 [P1][V] 期首資金が「当年度の期首残高＋当年度の posted 仕訳」しか見ておらず、繰越未実施で黙って 0 になる

- **場所**: `Modules/Management/CashFlowForecastData.Query.sql:14-31`（`cur_yr` / `cash_now`）、
  同 `:62-73`（`ap_now`）、`Modules/Shell/PortalAlertData.Query.sql:34-51,124-128,158`
- **症状**: `cash_now` は `opening_balances`（当年度分）と `journal_entries.fiscal_year_id IN cur_yr`
  の posted 仕訳だけを足す。したがって
  1. **当年度の `opening_balances` がまだ無い**（＝前期の決算確定・繰越処理を走らせていない期首直後。
     中小企業では期首から 2〜3 ヶ月ふつうに続く状態）→ 前期末の現預金がまるごと欠落し、
     期首資金が当年度の増減分だけ（多くはマイナス）になる
  2. **今日がどの `fiscal_years` にも入らない**（次年度を作り忘れている）→ `cur_yr` が 0 行 →
     `IN (SELECT ...)` が全て偽 → **期首資金 0 円・未払金 0 円**
  どちらも例外にならず、`ending < 0` が全月で立ち、画面は 4 行すべてに「⚠ 資金ショート」、
  ポータルは「⚠ 資金ショート予測: 今後4ヶ月中 4 ヶ月」を出す
- **根拠**: コード読み。`opening_balances` は繰越処理で作られる明示操作の産物（直近コミット
  `08198d5` が「繰越フラグの解除…を静かな失敗にしない」と扱っている＝手動の工程）。
  **ペルソナのどの判断で困るか**: 経営者が期首直後にポータルを見ると必ず「4 ヶ月連続ショート」と出る。
  一度でも空振りすると、本当にショートする月が来ても誰も信じない（アラートの信用の破壊は不可逆）
- **04 との関係**: 04 §1 の現状分析に**この項目は無い**。出金を 3 層に拡充しても残高の起点が
  同じなら症状は残る。**作り変えで消えない可能性が高い**
- **確度**: **確定**（コード読み。実際に警告が出るかは 要実機確認）

### F-02 [P1][V/Val] SES 案件の将来請求が入金予測に一切入っていない

- **場所**: `Modules/Management/CashFlowForecastData.Query.sql:50-61`（`rec_in`）／
  対比: `Modules/Shell/PortalQueueData.Query.sql:43-52,65-68`
- **症状**: 将来入金の見込みは `recurring_billings`（定期請求契約）**だけ**から作っている。
  SES の月次請求は同じテーブルではなく `projects`（`project_type='ses'`・`ses_monthly_rate`・
  `ses_lower_hours`/`ses_upper_hours`）に載っており、ポータルの作業キューは
  `PortalQueueData` で**両者を別々に**数えている（`recurring_pending` と `ses_pending`）。
  資金繰り予測だけが SES 側を見ていない。請求書が発行されるまで（＝当月分は翌月）SES の売上が
  入金予測にまったく現れず、**未発行の将来月は永久に 0 円**
- **根拠**: 上記 2 ファイルの参照テーブルの差。ADR-0036（SES もプラン方式）で SES が
  定期請求とは別実装になった経緯と整合。
  **ペルソナのどの判断で困るか**: 受託＋SES のソフトハウスにとって SES は**最も読みやすい安定収入**。
  それが欠けた予測は構造的に悲観側へ振れ、F-01 と重なると偽のショート警告を量産する。
  逆に「予測より入金が多い」が常態化すると、予測そのものを経営者が見なくなる
- **04 との関係**: 04 は出金の拡充が主題で、入金側の SES 欠落は §1 に挙がっていない。**残る**
- **確度**: **確定**

### F-03 [P1][V] 未払金・承認済み経費を当月に一括計上し、承認済み経費は期間で一切絞っていない

- **場所**: `Modules/Management/CashFlowForecastData.Query.sql:75-79`（`exp_now`）、`:99`（`idx = 0` 一括）
- **症状**:

    3 年前に承認されたまま精算されずに残っている申請も、今月の出金として満額計上される
  - 未払金（`ap_now`）と承認済み経費は `CASE WHEN mm.idx = 0` で**当月にだけ**載る。
    期日の情報を持っているのに使っていないので、当月に山ができ翌月以降は人件費だけになる

  （`VendorInvoice.mod.cs:3`）なので仕入先請求書との二重計上も無い
  **ペルソナのどの判断で困るか**: 「今月は苦しいが来月から楽になる」という**実在しない形**が毎月出る。

### F-06 [P2][V] 売上の既定税区分が無い／無効だと、定期請求の入金見込みが税抜のまま（約 10% 過小）

- **場所**: `Modules/Management/CashFlowForecastData.Query.sql:33-37`（`sales_rate`）、`:52`
  （`PortalAlertData.Query.sql:52-56,72` にも同じコピー）
- **症状**: `COALESCE((SELECT tr.rate_percent ... WHERE tc.default_for='sales' AND tc.is_active=1), 0)`。
  既定税区分が未設定・無効化・税率未紐付けのいずれでも `pct = 0` になり、
  `monthly_amount * (100 + 0) / 100` ＝ **税抜額が入金見込みになる**。エラーも警告も出ない
- **根拠**: コード読み。直近コミット `08198d5`（`fix(accounting,sales): 繰越フラグの解除と
  売上既定税区分の欠落を静かな失敗にしない`）で**同じ欠落を静かな失敗にしないと決めた**のに、
  この 2 本の SQL は `COALESCE(..., 0)` のまま取り残されている
  **ペルソナのどの判断で困るか**: 入金が毎月 10% 過小に出て、慢性的に悲観側の予測になる。
  ずれ幅が一定なので「なんとなく当たらない表」として放置されやすい
- **確度**: **確定**

### F-07 [P2][V] 定期請求の入金月が「請求月の翌月」固定で、取引先の支払サイトを見ていない

### F-09 [P2][V] 期日なしの仕入先請求書の扱いが、同じポータル画面の 2 つの数字で食い違う

- **場所**: `Modules/Shell/PortalAlertData.Query.sql:16-20`（`pay`）と
  `Modules/Management/CashFlowForecastData.Query.sql:80-87`（`vend_out`）
- **症状**: `pay` は `julianday(date(v.due_date)) - julianday(...)` を計算するため、
  `due_date` が NULL なら `days_left` が NULL になり、`days_left < 0` にも `>= 0 AND <= days` にも
  当たらない → **超過にもまもなくにも数えられず、アラートから消える**。
  一方 `vend_out` は `COALESCE(date(v.due_date, 'start of month'), 当月)` で**当月の出金として計上**する。
  同じ仕入先請求書が「支払期限アラート 0 件」なのに資金繰りの当月出金には載る
- **根拠**: 両 SQL の突合。`PaymentSchedule.Query.sql:21-22` は NULL 期日をソート用に
  `'9999-99-99'` へ寄せており、期日なしの請求書が実在しうる前提で作られている
  **ペルソナのどの判断で困るか**: 期日未入力の請求書は「入力漏れ」であって「支払わなくてよい」ではない。
  アラートに出ないので放置され、支払遅延として顕在化する
- **確度**: **確定**
