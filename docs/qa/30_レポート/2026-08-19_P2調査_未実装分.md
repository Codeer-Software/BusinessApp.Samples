## BUG-0057 承認テンプレートの削除で生の SQLite FK エラー

**前提は真、しかも台帳より範囲が広い。**

- FK は実際に効いている（`PRAGMA foreign_keys` = 1）。BUG-0174 の「実 DB では 0」という記述のほうが古い
- 参照は 1 本ではなく **3 本**: `approval_flow.template_id`（18 行）／`approval_route_rules.template_id`（5 行）／
  `approval_flow_template_order.template_id`（NOT NULL・全 4 テンプレが 1〜3 段を保有）
- **実際の削除 UI は PageFrame 側**（`PageFrames/MasterAdmin.frm.json` の `Left.Links[3]` ＝
  Module=`ApprovalFlowTemplate` の `ListPageDesign.ListFieldDesign.CanDelete = true`）で、
  **`DeleteTogether = false`**。つまり一覧削除は子（承認段）を連れて行かないので、
  **「使用済み」でなくても、承認段を 1 つでも持つテンプレは全部落ちる**。現 DB の 4 テンプレは全部これ

**方針**: `MasterAdmin.frm.json` の当該リンクと `ApprovalFlowTemplate.mod.json` の
`ListPageFieldDesign.CanDelete` を `false` にし（ルート直下の `CanDelete` は `true` のまま——
`this.Delete()` が拒否されるため）、詳細に「このテンプレートを削除」ボタンを新設して
`ApprovalFlowTemplate.mod.cs`（現在は存在しない）で参照を数える。先例は `Sales/SalesOrder.mod.cs`。

**実装時の落とし穴（調査で判明）**:

- **`ModuleSearcher<ApprovalFlow>` でガードしてはいけない。** `ApprovalFlow` の `UserReadCondition` は
  `CanUseExpense ∨ IsApprover ∨ HasAccountingAccess` で、この画面に入れるのは `IsSysAdmin`。
  3 つとも false の admin からは **0 件に見えてガードをすり抜ける**。過去の申請実績の有無は
  `this.Delete()` の戻り値（false）で判定する
- 子（承認段）と孫（承認者）は**深い方から明示的に消す**。`DeleteTogether` は詳細画面の 1 段目までしか当てにならない
- `ApprovalRouteRule` の参照は先に数える（消してからだと経費申請が「ルートが無い」で出せなくなる）

**同型**: 一覧削除を許している 19 か所は**全部 `DeleteTogether = false`**。
うち FK 子を持つのは `ApprovalFlowOrder`（Expense 系 3 フレーム）と `JournalTemplate`（Accounting）。
前者は「そもそもエンドユーザーに段を単独削除させる導線が要るのか」自体が設計判断。

## BUG-0168 FB の受取人名 30 桁超が無言で切れる

**前提は真。ただし現データでは未発火**（`partners.payee_kana` の最大は 14 文字）。

- `Purchasing/FbExport.mod.cs` の `PadC` が `Substring(0, n)` で超過分を捨てる。
  `MasterBusiness/PartnerBank.mod.cs` の `AccountValidationError()` は**文字種しか見ておらず長さを見ない**
- 自社側は `ConsignorKana` だけ `KanaError` を通し、`HeadBankKana` / `HeadBranchKana` は**素通し**。
  全角を入れると Shift-JIS で 2 バイトになり、**文字数 120 でも実バイト数が 120 を超える**——
  `FbExport.mod.cs:6` の「半角のみ＝バイト長=文字数」という前提が破れ、自己検証が素通りする
- **同族**: `PadN` は**上位桁**を捨てる（`t.Substring(t.Length - n, n)`）。金額 10 桁を超えると
  **まったく別の金額で振り込まれる**。ループ内の金額チェックに `amt > 9999999999` を足す

**方針**: 長さ検証は `PartnerBank.AccountValidationError()` の 1 か所に置く
（登録画面と FB 生成の両方がここを呼ぶので、基準が 2 か所に割れない）。
`Substring` による切り捨ては全デザイン中 `FbExport.PadC` の 1 か所だけ。

## BUG-0169 工数の新規作成が他人名義を防げていない

**前提は真。台帳より少し悪い。**

- `TimeEntry.mod.cs:16` は無条件ではなく `if (CurrentUser.HasAccountingAccess.Value != true) { UserRef.IsViewOnly = true; }`
  ＝**経理権限があれば TimeEntry でも他人名義を入力できる**
- `Detail_OnAfterInit:11` は `UserRef == null` のときだけ自分に寄せるので、URL や前画面から他人の値が載れば
  そのまま新規行の名義になる
- 真因は CLB の仕様: **`DataWriteCondition` は新規行に適用されない**（`_specs/ModuleDesign.md`「新規追加 … 対象外」）

**方針**: **サーバ拡張が要る**（CLAUDE.md §2 の「CLB 単体では不可能」に該当）。

- `OnValidateInput` は使えない（`lint_design.py` の CLB-004 が error・無言で保存が止まる）
- `IsViewOnly` / `OnDataChanged` は WASM 側の描画制御なので API 直叩きを止めない
- 関門を置けるのは `BusinessApp.Server/Services/CustomizedModuleDataIO` の `AddAsync` / `BulkAddAsync`
  だけ（新規と更新を区別できる唯一の場所。パスワード必須化 BUG-0395 と同じ理由でここにある）
- 代理入力の正規の入口は別モジュール `TimeEntryAdmin`（`UserWriteCondition` で経理限定）なので、
  `data.Name == "TimeEntry"` のときだけ効かせれば代理入力は邪魔しない

**同型**: `DataWriteCondition` で本人限定しているモジュールのうち、`Creator`（CLB の予約システムフィールド・
サーバが上書きするので詐称不可）ではなく**普通の列で所有者を表している**のは `TimeEntry` だけ。

**不変条件の候補**（現データは 0 件なので今すぐ緑で入る）:

```sql
SELECT t.id, t.user_id, t.creator FROM time_entries t
LEFT JOIN app_users u ON u.id = t.creator
WHERE t.creator IS NOT NULL AND t.user_id IS NOT NULL AND t.user_id <> t.creator
  AND COALESCE(u.has_accounting_access, 0) = 0;
```

## BUG-0237 `ExpenseStaff/Start` の 400 リトライ暴走

**静的には確認できなかった（ブラウザを使わない調査だったため）。まず再現を取ること。**

ただし **400 を出しうる構造欠陥を 1 件特定した**:
**`ExpenseRequest` は `UserReadCondition` が空（全員可読）なのに、
`ApprovalFlow`（`CanUseExpense ∨ IsApprover ∨ HasAccountingAccess`）を `ModuleField` で埋め込み、
一覧列に `ApprovalFlow.Status` を出している。** BUG-0259 とまったく同じ形。
3 フラグとも false なのは `admin` だけで、`/ExpenseStaff/Start` の URL 直打ちは
同日レーン C が実際にやっていた操作（FB-055 に記録あり）。状況証拠としては最も整合する。

**注意**: BUG-0259 の「全モジュールを走査し、この 1 件だけと確認済み」は
**経理限定モジュールだけを見た走査**で、`CanUseExpense` ゲートを取りこぼしていた。

**再現手順**: `admin` で DevTools の Network を開いて `/ExpenseStaff/Start` を直打ちし、
`POST /api/module_data/list` の `moduleName` を見る。400 ならそれが真因の指名。

**方針**: `ExpenseRequest.UserReadCondition` を埋め込み先と**同じ 3 つの OR** に揃える
（`CanUseExpense` 単独にしないのは、`Shell/Notification.mod.cs:63` が全ユーザー文脈で
`ModuleSearcher<ExpenseRequest>` を実行して「自分の申請か」を判定しているため）。
**リトライを止めない側は CLB ランタイムの問題**でデザインからは制御できない → 再現が取れたら FB として起票。

## BUG-0277 翌期繰越の 2 回目のダイアログ

**前提は真。** `FiscalYear.mod.cs:262` の文言は 1 回目・2 回目で完全に同一。
ただし**画面側（ダイアログ外）は ADR-0068 で改善済み**（`UpdateCarryOverStatus()` が
`not_carried` / `stale` / `current` を灰・赤・緑で出す）。台帳の記述は
「まったく気づけない」ではなく「**ダイアログでは**気づけない」に更新すべき。

**制約**: `opening_balances` に**タイムスタンプ列が無い**ので、台帳が求める「前回 yyyy/mm/dd 実行」は
現スキーマでは出せない。出せるのは「いま何行あるか」「貸借差」「当期末と一致しているか」の 3 つ。

**方針**: ダイアログの直前で翌期の `opening_balances` を数え、
`v_carryover_staleness`（画面ラベルと同じビュー）から `state` を取って文面に混ぜる。
状態取得は `FindCarryOverStatus()` に切り出して**画面ラベルとダイアログで 1 か所を共有**する
（`FindWipStatus()` と同じ作法）。`RunCarryOverForClose` からの経路（`confirm=false`）は素通り。

**同型**: 同じファイルの `WipTransfer_OnClick` は件数・金額を先に取ってダイアログに出している＝**お手本側**。
繰越だけが揃っていないという非対称。

## BUG-0300 銀行明細の相手科目候補を空に戻せない

**台帳の前提が現物と食い違う。`[要再検証]` に落とすべき。**

- 台帳の再現手順は「ID 6 で…」だが、**いまの DB では id=6 も id=7 も `suggested_account_id = NULL`**
- 機構として疑われていた側は**全部つぶれた**（すべて実測）:
  - `bank_statement_lines.suggested_account_id` は NULL 許容（`ddl/160_bank.sql:36`）
  - このテーブルにトリガーは 0 件
  - CLB の変更検知は null を正しく「変更」と見る（`ValueFieldBase.IsModified` → `IsSame`）
  - 書き込み側にも null スキップ分岐は無い（`ModuleDataIOForDb.GetWriteDbParameters` 以下）
- **ただし化石が 1 行ある**: `id=14` は `suggested_account_id=65` かつ `suggestion_source` が NULL。
  `SuggestedAccount_OnDataChanged` は「科目が null のときだけ source を null にする」ので、
  **同一 Submit で source の NULL 化だけが書かれ、科目の NULL 化が書かれなかった**場合と一致する
- 残る候補は **UI 側（`SelectField` の空候補選択が row モジュールの `Current.Value` に届いていない）**。
  実機でしか切り分けられない

**先に直せるもの（機構と無関係に確定）**: `Bank/BankPosting.mod.cs` の `SaveListEdits` は
**`Submit()` の戻り値を捨てて**おり、`Save_OnClick` は結果に関わらず必ず成功トーストを出す。
「保存されない」報告は、この成功トーストのせいで**保存されたと信じて画面を離れる**ところまで込みの被害。

**切り分け手順**: 保存の前後で必ず SELECT を見る（画面表示を根拠にしない）。
両方 NULL → 直っている／`suggestion_source` だけ NULL → id=14 と同じ片側書き込みが再現／
両方そのまま → Submit 自体が走っていない。

## BUG-0374 仕掛品の検収判定が `sales_orders.project_id` 依存

**前提は真。ただし台帳の「売上 0 の条件が保険になっている」は誤り。**

- `sales_orders` 10 件中 2 件が `project_id IS NULL`（`SO-26-002 保守料 7月分` / `SO-26-004 業務改善ツール開発`）で、
  **両方とも確定検収を持っている**。`acceptances` に `project_id` 列は無く、案件への唯一の経路が
  `sales_orders.project_id` なので、この 2 件の検収は**どの案件からも見えない**
- **保険にならない理由**: `v_project_revenue`（`ddl/720:74-84`）は `journal_lines.project_id` で集計するので、
  案件を持たない受注から起票された売上仕訳も `project_id` が NULL になる。
  → **検収判定と売上判定は独立した保険ではなく、同時に外れる**
- 現時点で実害は出ていない（`v_wip_candidate` の対象は `PJ-2026-103` 1 件のみ・これは正当）

**方針は 2 つに分ける**:

1. **検知（自律で入れて安全）**: `ddl/826` で `v_unlinked_acceptance` を新設し `v_wip_status` に 1 列足す →
   `WipStatus.Query.sql` / `.mod.json` に列を通す → `FiscalYear.mod.cs` に
   `UnlinkedAcceptanceNote(st)` を足して仕掛品の行に併記（`MissingSalaryNote` と同じ設計・BUG-0367）
2. **根治（GO 待ち）**: 「受注に案件を必須にする」は**開発者判断が要る**
   - 既存 2 行を先に埋める必要があるが、**どの案件に付け替えるかは帳簿から読めない**
     （取引先 3 の contract 案件は 4 つあり、付け替え先で案件別損益・仕掛品の金額が動く）
   - `ddl/100_sales.sql` の `quote_id` に「NULL=見積なしの受注（SES 更新等）」というコメントがあり、
     **案件を立てない受注が想定されている可能性**がある。必須化はその運用を止める業務ルール変更
   - もう一つの案「`acceptances` に `project_id` を持たせる」はデータモデル変更で
     `Acceptance` / `Invoice` / 売上仕訳まで波及する
