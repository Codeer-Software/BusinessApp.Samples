### S-01 [P0] 売上の既定税区分が無いと、定期請求・SES が「税額0円・売上行が対象外」の請求書と仕訳を無言で作る
- **場所**: `Designer/Design/Modules/Sales/RecurringRun.mod.cs:391-396`, `:516-517`, `:646-648`
  / `Designer/Design/Modules/Sales/SesBilling.mod.cs:294-299`, `:418-419`
- **症状**: `tax_categories.default_for='sales' AND is_active=1` の行が無い／無効化されると、
  `salesTaxCatId` が **null のまま実行が続く**。科目（1100/4020/2200/2110）は 1 つでも欠ければ
  `Toaster.Error` で止めるのに、税区分だけノーガード。結果:
  1. `taxPct=0` → 請求書の消費税が 0 円（`BuildPlan` のプレビューも税額 0 で「生成予定」と表示する）
  2. 売上行で `l.Account.Value = saasAccountId` が `ApplyLineDefaults` を発火させて科目既定の税区分を
     入れた**直後に** `l.TaxCategory.Value = salesTaxCatId`（＝null）で**上書きして消す**
  3. `je.MarkRemainingLinesOutOfScope()` が null 行を拾って**「対象外」に確定**させる
  → 課税売上がまるごと消費税集計表から落ち、仕入税額控除・申告額が狂う。エラーも警告も出ない。
- **根拠**: `JournalEntry.mod.cs:167-178`（「税区分をセットしない＝対象外になる、ではない。
  `ApplyLineDefaults` はスクリプト生成にも発火する」＝ADR-0053）と、上記代入順の組み合わせ。
  `InvoiceLine.tax_category_id` は NOT NULL 化されていない（`ddl/490` は `journal_lines` と
  `journal_template_lines` のみ）ため、請求書側も DB エラーにならず静かに通る。
- **確度**: 確定（コード経路）／発生条件（既定税区分の欠落・無効化）は 要実機確認
- **示唆する修正**: `salesTaxCatId == null` を科目と同じくエラーで止める。
  併せて `if (salesTaxCatId != null)` を付けて既定の上書きを避ける。

### S-02 [P0] 課金サイクルを monthly→yearly に変えると、既存の月額請求書を年額アンカーと誤認して前受収益を逆振替する
- **場所**: `Designer/Design/Modules/Sales/RecurringRun.mod.cs:238-241`（`BuildYearlyPlanRow` のアンカー検索）
- **症状**: アンカー年額請求書の検索条件が `recurring_billing_id` ＋ `billing_month` だけで、
  **`invoice_source` を見ていない**。月額で走っていた契約を経理が年額に切り替えると、
  周期起点月（＝`start_month` の応当月）に**過去の月額請求書**が居るため、それをアンカーと判定する。
  以降 `plan_kind='defer'` が毎月立ち、`D 前受収益 / C SaaS売上高` が**前受計上仕訳なしで**生成される。
  → 前受収益(2110)が貸方残なしにマイナスへ、SaaS売上高は月額請求分と二重計上。
- **根拠**: `RecurringRun.mod.cs:238-241` に `InvoiceSource` 条件が無い。生成側は
  `inv.InvoiceSource.Value = "recurring"`（月額・:446）と `"recurring_annual"`（年額・:578）を
  書き分けているので、判定側だけが区別を落としている。`BuildMonthlyPlanRow:162-165` も同じ穴（対称）。
- **確度**: 確定（コード）。実データで既に起きているかは 要実機確認（サイクル変更の運用があったかによる）
- **示唆する修正**: アンカー検索に `invoice_source='recurring_annual'` を足す。あわせて
  確定済み契約の `BillingCycle` 変更をガードするか、変更時に警告する。

### S-03 [P0] 年額契約が周期の途中で終了・無効化・期間外になると、前受収益が未償却のまま永久に残る
- **場所**: `Designer/Design/Modules/Sales/RecurringRun.mod.cs:84-122`（契約期間・status・IsActive の除外）
  / `:206-262`（`BuildYearlyPlanRow` に `EndMonth` の考慮が無い）
- **症状**: 2 通りで前受収益(2110)が閉じない。
  1. 年額請求は**契約終了月を見ずに 12 ヶ月ぶん満額**を請求・前受計上する（`EndMonth` 参照ゼロ）。
     開始 2026-04・終了 2026-09 の年額契約でも年額全額を請求してしまう。
  2. 按分振替は契約が `ended` / `IsActive=false` / 期間外になった瞬間に**契約ごと除外**され止まる。
     残った前受収益を戻す経路は他に無い（`grep 2110` の結果、2110 に触るのは RecurringRun のみ）。
  → B/S に前受収益が塩漬け、P/L に売上が計上されない。警告も残高監視も無い。
- **根拠**: `BuildPlan:84-122` の `continue`／`excluded` は契約単位で、前受残の有無を一切見ない。
  `CreateDeferJournal` を呼ぶ経路は `plan_kind` が `annual` / `defer` のときだけ。
- **確度**: 確定（コード）
- **示唆する修正**: 契約終了・無効化時に未償却残を一括振替する導線か、
  最低限「前受収益の未償却残一覧」を帳票に出して気づけるようにする。

### S-04 [P1] 相殺入金の取消は「買掛を戻す → 仕訳削除」の順で、後半が失敗すると片落ちしたまま止まる
- **場所**: `Designer/Design/Modules/Sales/Receipt.mod.cs:139-160`
- **症状**: 仕入先請求を `accrued` に戻して `Submit()` 成功後、`DeleteJournalEntryWithLines(je)` が

- **確度**: 確定（コード）。削除失敗自体の発生確率は 要実機確認
- **示唆する修正**: 順序は FK 制約上変えられないので、削除失敗時に仕入先請求を paid へ戻す
  補償を書く。戻せなければ「手当てが必要」と明示するメッセージにする。

### S-05 [P1] 消込仕訳の明細削除が途中で失敗すると、貸借の欠けた仕訳が帳簿に残る
- **場所**: `Designer/Design/Modules/Sales/Receipt.mod.cs:71-85`（`DeleteJournalEntryWithLines`）
- **症状**: 明細を 1 行ずつ `Delete()` し、途中で false が返ると**削除済みの行を戻さずに** return false。
  親の `journal_entries` は残るので、**借方だけ／貸方だけの仕訳**が posted のまま帳簿に残る。

- **確度**: 確定（コード）
- **示唆する修正**: 先に全行を読み切って削除可能性を判定する、または削除失敗時に
  「この仕訳は手で修正が必要」と伝票番号つきで明示する。

### S-06 [P1] ADR-0060 の二重実装は今も食い違う: 年額契約の按分月をポータルが数えない
- **場所**: `Designer/Design/Modules/Shell/PortalQueueData.Query.sql:31-33`
  vs `Designer/Design/Modules/Sales/RecurringRun.mod.cs:306-309`
- **症状**: 依頼の問い「両方のロジックを読み比べて条件が一致しているか」への回答は **一致していない**。
  SQL は yearly を「周期起点月（`% 12 = 0`）のみ」に限って数えるが、`BuildYearlyPlanRow` は
  周期 2〜12 ヶ月目に `plan_kind='defer'` / `status='planned'`（＝按分振替のみを生成予定）を出す。
  → 年額契約が 1 本でも走っていれば、12 ヶ月のうち 11 ヶ月は
  **画面「生成予定 1 件」・ホーム「0 件」** になる。ADR-0060 が直したズレの鏡像。
- **根拠**: SQL:31-33 の `% 12 = 0` 条件。SQL 冒頭のコメント自身が
  「月額は毎月、年額は**周期起点月のみ**対象」（:16）と、BuildPlan と違う契約を宣言している。
  一方 ADR-0060「決定 3」は「`BuildPlan` と同条件にする」と書いており、**ADR と SQL コメントが矛盾**。
  `docs/tests/portal_billing_count_check.sql` の突合（A の recurring_pending == B の planned）は
  年額の按分月に流すと必ず落ちるはずで、**チェック自体がその月には成立しない**。
- **確度**: 確定（両方のコードを読み比べた）。SES 側は同じ読み比べで**条件一致を確認**した
  （status/is_active/rate>0/mins>0/精算後 1 円以上・整数時間・下限上限が両方 non-null のときだけ控除超過。
  `ses_lower_hours` 等は `ddl/220_ses.sql` で INTEGER なので `(int)lower` の切捨ても差にならない）
- **示唆する修正**: SQL に defer 分（アンカーがあり当月の `recurring_defer` 仕訳が無い年額契約）を足すか、
  ADR-0060 と SQL コメントを「年額の按分月は数えない」で揃えて突合 SQL に例外を明記する。
  **どちらでもよいが、ADR・SQL コメント・突合 SQL の 3 点が今バラバラなのが一番まずい。**

- **症状**: 同じファイルの `:142` `:316` はモジュールをまたぐ Id 比較を

- **確度**: 要実機確認（取消は E2E で通っているはずなので、現状は一致していると推測される。
