| # | 問い | 結論 |
|---|---|---|
| 1 | 貸借が必ず一致するか | **画面経路は一致する。ただし保証は 2 か所のスクリプトだけ**。DB 制約も共有ヘルパも無く、`je.Submit()` を呼ぶ他 12 経路は無検証（F-02） |

| 3 | `OnDataChanged` の無条件上書き | 直接の上書きは無い。しかし**逆向きの欠陥**があり、科目を変えても税区分が追随せず古い既定が残って消費税が生成される（**F-01 / P0**） |

# 所見（重要度順）

## P0

### F-01 [P0] 勘定科目を変え直しても税区分が追随せず、旧科目の既定税区分のまま消費税が分離される

- **場所**: `Designer/Design/Modules/Accounting/JournalEntry.mod.cs:124-165`（`ApplyLineDefaults`）
- **症状**:
  1. 明細行で「消耗品費」を選ぶ → `ApplyLineDefaults` が科目マスタの既定「課税仕入 10%」＋`inclusive` を自動セット
  2. 入力を間違えたと気づき、同じ行の科目を「普通預金」に変更する
  3. **税区分は「課税仕入 10%」のまま残る**（普通預金の既定である「対象外」に戻らない）
  4. 確定すると `RegenerateTaxLines` が働き、`普通預金 11,000` が
     `普通預金 10,000` ＋ `仮払消費税 1,000` に分解される
  5. **借方合計・貸方合計は変わらないので貸借エラーにならず、警告も出ない**。
     内税なので「確定時に消費税 N 円が追加されます」のヒント（`UpdateTaxHint`、`exclusive` 限定）も出ない
- **影響**: 資産・負債科目に課税仕入／課税売上が立ち、消費税集計表の課税仕入額・仮払消費税残高・
  試算表の科目残高が同時に狂う。ADR-0053 で「減価償却の貸方に取得時の既定が入り課税仕入を
  114,375 円狂わせていた」のと**同じ症状を、手入力経路で再現できる**
- **根拠**（当該行）:
  ```csharp
  if (l.Account.Value != null && l.TaxCategory.Value == null)   // ← 「null のときだけ」入れる
  {
      missingAccountIds.Add(l.Account.Value);
  }
  ...
  if (l.TaxCategory.Value != null) continue;                     // ← 既に入っていれば触らない
  ```
  `JournalLine.mod.json` の `Account` フィールドは `OnDataChanged: ""`（科目単独のハンドラは無い）で、
  税区分を更新しうるのはこの `ApplyLineDefaults` だけ。したがって
  **「1 度でも税区分が入った行は、科目を何回変えても税区分が固定される」**
- **なぜ「上書きしない」設計だけでは足りないか**: ユーザーが明示的に選んだ税区分を潰さない、という
  意図自体は正しい（ADR-0053 の教訓）。しかし現状は「自動で入れた値」と「人が選んだ値」を
  区別していないため、自動で入れた値まで守ってしまっている。区別する状態（例: 直前に自動セットした
  `Account` の値を行に保持し、科目が変わったら再解決する）を持たない限り解けない
- **確度**: **確定**（コードと JSON だけで成立）。実データにこの状態の行があるかは要 SELECT

### F-02 [P1] 貸借一致の検証が 2 経路にしかなく、共有ヘルパも無い（他 12 経路の `je.Submit()` は無検証）

- **場所**: `JournalEntry.mod.cs:450-463`（唯一の検証）、`JournalImport.mod.cs:250-257`（もう 1 つ）
- **症状**: `JournalEntry` は
  `MarkAllLinesOutOfScope()` / `MarkRemainingLinesOutOfScope()` / `GenerateTaxLinesOnce()` /
  `FillMissingDepartments()` という**共有ヘルパを公開しているのに、貸借検証だけ公開していない**。
  結果、`new JournalEntry()` → `je.Submit()` を行う他モジュールは 1 件も貸借を検証していない
  （`grep 貸借 Modules/**/*.mod.cs` の結果は `JournalEntry` と `JournalImport` のみ）。
  該当経路は `CashEntry` / `FixedAsset` / `BankPosting` / `ExpenseRequest`(×2) /
  `Acceptance` / `Receipt` / `RecurringRun`(×3) / `SesBilling` / （`VendorInvoice`×2 は本監査の対象外）
- **影響**: 各経路は「借方 1 行・貸方 1 行を対で組む」実装なので現状は一致しているはずだが、
  **不一致を作った瞬間に誰も気づかない**。DB にも制約は無い（`ddl/040_journal.sql` に CHECK 無し）。
  `docs/04 §0-2`「貸借一致しない伝票は確定できない」は**アプリ層の 2 か所でしか守られていない**。
  ADR-0060 が問題にした「判定の二重実装」と同じ構図（今回は二重ではなく**未実装が 12 個**）
- **根拠**: 上記 grep と、`JournalEntry.mod.cs` に貸借検証を行う `void`/`bool` の公開ヘルパが
  存在しないこと（`UpdateTotals` は表示用フィールドを更新するだけで判定を返さない）
- **提案**: `bool ValidateBalance()` を `JournalEntry` に切り出し、`FillMissingDepartments()` と同じく
  「全経路が `Submit()` の直前に呼ぶ」規約にする。`docs/qa/20_不変条件SQL/A01` が事後に検算する仕組みは
  既にあるので、事前ガードと対にすれば守れる
- **確度**: **確定**

### F-03 [P1] 伝票番号の一意性が DB にもアプリにも無く、採番は read-max+1 が 4 か所に重複実装

- **場所**: `JournalEntry.mod.cs:811-822`（`NextJournalNo`）、`JournalImport.mod.cs:353-365`（同ロジックの写し）、
  ほか `VendorInvoice.mod.cs:557` / `RecurringRun.mod.cs:483,613` にも同名の別実装
- **症状**: `SELECT max(journal_no) + 1` 相当を読んでから `Submit()` するだけで、
  一意性の担保が**どこにも無い**。同一年度に対して 2 つの確定処理が同時に走ると同じ番号が付く
- **根拠**:
  - `ddl/040_journal.sql:39` — `journal_no INTEGER,`（制約なし）
  - `ddl/040_journal.sql:73` — `CREATE INDEX ... ON journal_entries(fiscal_year_id, journal_no)`
    → **UNIQUE ではない通常インデックス**。`Designer/ddl/*.sql` 全体を `journal_no` で grep しても
    UNIQUE を張る後続 DDL は無い
  - `docs/04 §3` は「journal_no … 年度内連番（表示用伝票番号。**年度+連番でユニーク**）」と規定
  - `docs/qa/20_不変条件SQL/A03_仕訳_伝票番号の一意性.sql` が存在する＝**事後検算の仕組みはあるが事前の制約が無い**
- **影響**: 法定帳簿の識別子が重複しうる。単独利用のデモでは顕在化しにくいが、
  「CSV インポート実行中に別ユーザーが振替伝票を確定」で普通に起きる
- **確度**: **確定**（DDL とコードのみで成立）

### F-04 [P1] CSV インポートは冪等でなく、貼り付けたまま再クリックすると全件が二重に取り込まれる

- **場所**: `JournalImport.mod.cs:16-419`（`Import_OnClick`）
- **症状**: 取込完了後、`ResultLabel.Text` は更新されるが **`CsvText.Value` はクリアされない**。
  重複判定のキー（ハッシュ・`source_id`・取込ジョブ ID）も持たない。
  「成功したか確信が持てずもう一度押す」「戻る→再表示して押す」で**全伝票が二重計上**される。
  しかも確認ダイアログ本文が自ら「まとめて取り消す導線はありません（誤りは伝票ごとに訂正が必要です）」
  と宣言しているとおり、巻き戻し手段が無い
- **根拠**: `Import_OnClick` 全体に `CsvText.Value = ""` が無く、`je.SourceId.Value` も設定していない
  （`je.SourceType.Value = "import"` のみ・`JournalImport.mod.cs:342`）。
  よって「同じ CSV が既に取り込まれているか」を判定する材料が DB 側に残らない
- **影響**: 移行データの二重計上。全帳票が狂う
- **提案**: ①成功後に `CsvText.Value = ""` にして結果だけ残す ②`source_id` に取込ロット番号を持たせ、
  同一ロットの再取込を拒否する ③少なくとも「同一日付・同一グループキー・同一金額の確定伝票が既にある」
  警告を出す
- **確度**: **確定**（コードにクリアも冪等キーも無い）

### F-05 [P1] 「部門・プロジェクトを修正する」が購買・営業フレームから真っ白になる（CLB-013）

- **場所**: `JournalEntry.mod.cs:345-355`（`DeptEdit_OnClick`）× `PageFrames/*.frm.json`
- **症状**: `NavigationService.GetModuleUrl("JournalLineDepartment")` へ遷移するが、
  `JournalLineDepartment` は **`Accounting.frm.json` にしか登録されていない**。
  `JournalEntry` は `Accounting` / `Purchasing` / `SalesBilling` の 3 フレームに登録されているため、
  購買・営業フレーム側から確定済み伝票を開いて当ボタンを押すと、
  **URL だけ変わってコンテンツが空**になる（CLB-013 の典型症状。エラーもコンソール出力も出ない）
- **根拠**（フレーム登録の実測）:
  - `Accounting.frm.json` の `OtherPageModuleDesigns`: `JournalEntry`(Auto) / `JournalLineDepartment`(Detail)
  - `Purchasing.frm.json`: `JournalEntry`(Auto) のみ
  - `SalesBilling.frm.json`: `Receipt`(Auto) / `JournalEntry`(Auto) のみ
  - `DeptEditButton.IsVisible = isPosted`（`JournalEntry.mod.cs:34`）＝**フレームを問わず確定済みなら必ず出る**
- **確度**: **確定**（静的な登録の欠落）／表示結果そのものは **要実機確認**
- **提案**: `JournalLineDepartment` を 3 フレームすべてに登録するか、
  `DeptEditButton` を Accounting フレームでのみ表示する。`Designer/tools/check_navigation.py` の
  検査 D がまさにこれを拾うはずなので、対象ファイル修正後に走らせて確認したい

### F-06 [P1] 部門修正画面は行の保存失敗を握り潰し、0 行しか保存できなくても「保存しました」と出す

- **場所**: `JournalLineDepartment.mod.cs:96-115`（`Save_OnClick`）
- **症状**:
  ```csharp
  foreach (var row in LineList.Rows)
  {
      var l = (JournalLine)row;
      if (l.Submit() == true) { saved = saved + 1; }   // ← false は無視。理由も出さない
  }
  ...
  Toaster.Success($"部門・プロジェクトを保存しました（{saved} 行）");   // ← 常に成功トースト
  BackToEntry();                                                    // ← そのまま画面を離れる
  ```
  `JournalLine.Department` は `IsRequired: false` かつ `EmptyCandidateType: "Null"`（空候補あり）なのに
  DB は `department_id INTEGER NOT NULL`（`ddl/540_department_required.sql:42`）。
  つまり**画面で部門を空に戻せてしまい、その行の `Submit()` は必ず失敗する**。
  失敗しても件数が減るだけで、成功トーストを見たユーザーは保存されたと信じて離脱する
- **付随**: 行を 1 件ずつ `Submit()` するためトランザクションが無く、
  途中で失敗すると**一部の行だけ更新された中間状態**が残る
- **根拠**: 上記コード、`JournalLine.mod.json` の `Department`（`IsRequired:false` /
  `EmptyCandidateType:"Null"`）、`ddl/540` の NOT NULL 化
- **確度**: 「失敗を握り潰して Success を出す」「非トランザクション」は **確定**。
  空候補が実際に選べるか（＝失敗を起こせるか）は **要実機確認**

### F-07 [P1] 唯一の訂正手段である赤黒訂正に支援が無く、税区分の自動セットで元伝票と 1 円単位で一致させにくい

- **場所**: `JournalEntry.mod.cs:331-342`（`Post_OnClick` のダイアログ本文）×
  `JournalEntry.mod.cs:124-165`（`ApplyLineDefaults`）× `628-809`（`RegenerateTaxLines`）
- **症状**: 確定は不可逆で、訂正は「反対仕訳を起票してください」しか案内されない（ADR-0026 の決定どおり）。
  ところが元伝票は**税抜化済み**（本体 10,300 ＋ 仮払消費税 700 のように分解されて保存されている）。
  ユーザーが反対仕訳を手で起こすとき、
  - 本体額 10,300 をそのまま入れると、科目既定の税区分が自動で入り（F-01 と同じ経路）、
    確定時に **再度**税抜化されて 9,364 ＋ 936 になる
  - 元伝票と一致させるには「税込 11,000 を内税で入れる」か「全行を対象外にする」必要があるが、
    画面はそれを案内しない（`PostedNote` の文面にも無い）
- **影響**: 赤黒訂正が**打ち消しにならず、差額が残る**。訂正のたびに消費税集計表が歪む
- **根拠**: 上記 3 か所のコード。反対仕訳を生成するボタン・ヘルパは
  `Modules/**/*.mod.cs` 全体を「赤黒 / 反対仕訳 / 訂正伝票」で grep しても存在せず、
  ヒットするのは案内メッセージのみ
- **提案**: 確定済み伝票に「この伝票の反対仕訳を作る」ボタンを付け、
  `is_tax_line` の行も含めて全行を D/C 反転・**全行 `TaxInputMode = "none"`／税区分は元行のまま**で
  複製した下書きを生成する（税の再計算をさせない）。ADR-0026 の「確定の取消は作らない」に反しない
  ——取り消すのではなく、正しい反対仕訳を作る作業を機械化するだけ
- **確度**: **確定**（コードに支援が無く、再税抜化が起きることは `RegenerateTaxLines` から自明）

### F-09 [P2] 定型仕訳からの起票が締め済み期間・締め済み年度をチェックせず、確定できない下書きを作る

- **場所**: `JournalTemplate.mod.cs:51-98`（`CreateEntry_OnClick`）
- **症状**: 本日日付で `FiscalYear` は解決するが、
  ①`FiscalYear.Status`（open/closed）を見ない ②`FiscalPeriod` をまったく解決しない。
  本日の属する月次期間が締め済みでも下書きは作られ、`JournalEntry` 画面へ遷移し、
  そこで初めて「取引日の期間は締め済みです」と言われて**確定できない下書きだけが残る**
- **根拠**: 同関数に `FiscalPeriod` の `ModuleSearcher` が無く、`fy.Status` の判定も無い。

### F-18 [P3] 消費税の端数処理は「明細行ごとに 1 回」で、ADR-0050 の「税率ごとに 1 回」とは別方式

- **場所**: `JournalEntry.mod.cs:737-784`（`RegenerateTaxLines`）
- **事実関係**:
  - 本体行 1 行につき税行 1 行を作り、`fullTax = input * ratePercent / (100 + ratePercent)`（内税）
    または `input * ratePercent / 100`（外税）で**行ごとに切り捨て**る
  - 二重丸めは無い（`deductible` を出した後の `baseAmount` は減算のみ）
  - `docs/04 §3.2` の規定（内税は税込額 ×率/(100+率) を切り捨て）には**従っている**
  - ADR-0050 が定めた「明細を税率でグループ化し、グループごとに 1 回だけ切り捨てる」のは
    見積・受注・請求（売上伝票）についての決定で、仕訳伝票は対象外
- **残るリスク**: 同一税率の課税行が 1 伝票に複数あると、
  請求書側（税率ごと 1 回）と仕訳側（行ごと 1 回）で最大数円ずれうる。
  売上仕訳は `Acceptance` / `Invoice` 側が金額を作って渡すので実際には衝突しないが、
  **手起票で同じ取引を再現すると一致しない**
- **判断**: 現状は仕様どおり。方式が 2 つある事実を `docs/04 §3.2` に注記しておくと将来の混乱を防げる
- **確度**: **確定**
