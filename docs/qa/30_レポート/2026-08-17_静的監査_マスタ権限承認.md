# 所見（重要度順）

## P0-1 承認ルートに同一人物が 2 段並ぶ（総務部の申請）— 2 段承認が実質 1 段になる

- **場所**: `Designer/Design/Modules/Expense/ApprovalFlow.mod.cs:101-104`（圧縮条件）、
  `:127-137`（固定指名段の分岐と `prevRoleApprovers = null`）、
  `:243-248` `ResolveFixedApproverAvoidingSelf`
- **症状**: 重複段の圧縮（ADR-0044 §3）は `isRoleOrder`（役職段）どうしにしか効かない。
  固定指名段（`approver_role='user'`）は**圧縮の対象にも、重複チェックの対象にもならない**。
  `ResolveFixedApproverAvoidingSelf` が避けるのは**申請者本人だけ**で、「直前の段の承認者と同じ人」は素通りする。
  実 DB の seed では 総務段の固定承認者が `soumu_kacho1`（総務部 第一課長 石川真理）であり、
  同じ `soumu_kacho1` が総務部 第一課の `manager` でもある。したがって:
  - `soumu_ippan`（総務部 第一課の member）の**交際費 3 万円未満** → テンプレート `経費_課長まで＋総務`
    → 1 段目 `soumu_kacho1` → 2 段目 `soumu_kacho1`。**同一人物が連続 2 回承認する**
  - 同じく **20 万円以上** → `経費_部長まで＋総務` → `soumu_kacho1` → 部長 → `soumu_kacho1`。
    3 段のうち 2 段が同じ人
  ADR-0010（自己承認の禁止）が守ろうとした「1 人で決裁を完結させない」という内部統制の趣旨が、
  総務部の申請では成立していない。承認 WF が市販ソフト比較の訴求点（docs/14）であるだけに痛い。
- **根拠**: 圧縮条件 `if (isRoleOrder && prevRoleApprovers != null && SameIdSet(...))` は固定段では常に false。
  固定段の else 節が `prevRoleApprovers = null`（:136）を実行するので、固定段をまたいだ比較もできない。
  実 DB（読み取り専用 SELECT）で
  `approval_flow_template` × `order` × `member` を結合した 8 行のうち
  `経費_課長まで＋総務` = `[manager, soumu_kacho1]`、`経費_部長まで＋総務` = `[manager, director, soumu_kacho1]`、
  `department_members` に `('10-1','総務部 第一課','section', manager, soumu_kacho1)` と
  `('10-1', member, soumu_ippan)` を確認した
- **確度**: **確定**（コード＋実 DB の seed の両方で成立する）
- **考えられる直し方**: `LoadFromTemplate` の第 2 パスで、段の生成直前に「直前段の承認者集合」を役職／固定を問わず保持し、
  同一集合なら段を落とす（＝圧縮の一般化）。あるいは固定指名承認者にも
  「直前段に居るなら代替へ」の解決を入れる。テンプレート側で回避する（総務段を `soumu_kacho2` にする）のは
  組織が変わると再発するので推奨しない

## P1-2 承認テンプレートは「名前」で再解決されるが `approval_flow_template.name` に UNIQUE が無い

- **場所**: `Modules/Expense/ExpenseRequest.mod.cs:31, 38-51`（id → 名前）、
  `Modules/Expense/ApprovalFlow.mod.cs:626-630`（名前 → `tmpls[0].Id`）、
  `Designer/ddl/070_approval.sql` 由来の実スキーマ `approval_flow_template(name TEXT NOT NULL)`
- **症状**: ADR-0023 は「テンプレートは **ID 参照**なので改名に強い」と書いているが、実装は
  `ルール.template_id` → `FindTemplateNameById()` で**名前に変換**し → `ApprovalFlow` が
  再度**名前で検索して `tmpls[0]` を採る**、という往復になっている。
  `ApprovalFlowTemplate` は `CanCreate=true`・`Name` に `IsRequired` も UNIQUE も無いため、
  システム管理者が UI で同名テンプレート（あるいは名前が空のテンプレート）を作れる。
  同名が 2 件あると、どちらが選ばれるかは検索順まかせで、**エラーも警告も出ない**。
  ADR-0023 が「壊れやすさの解消」として掲げた性質が、この往復のぶんだけ残っている
- **根拠**: `FindTemplateNameById` は `t.Name.Value` を返し（ExpenseRequest.mod.cs:50）、
  受け側は `ts.AddEquals(t => t.Name.Value, tmplName); ... TemplateId.Value = tmpls[0].Id.Value;`。
  実 DB の `CREATE TABLE approval_flow_template` に UNIQUE 制約なし。`ApprovalFlowTemplate.mod.json` の
  `Name` フィールドに `IsRequired` キーなし
- **確度**: **確定**（制約の不在と往復の存在）／「どちらが勝つか」は **要実機確認**

## P1-3 「有効」フラグの新規既定が入らないマスタが 6 件 — 作った直後にどこからも選べない

- **場所**: `Account.mod.json` / `TaxCategory.mod.json` / `TaxRate.mod.json` /
  `ExpenseCategory.mod.json` / `Department.mod.json` / `SubAccount.mod.json` の `IsActive` フィールド
- **症状**: この 6 モジュールには `DefaultValue` も、`IsNewData` で `true` を入れる

  画面から作った勘定科目・税区分・税率・費目・部門・補助科目は `is_active = 0` で保存される。
  そして `IsActive` は**参照フィールドの検索条件に埋め込まれている**（下記）ので、
  新しく作った科目は仕訳・期首残高・銀行明細・定型仕訳・予算のどの入力欄の候補にも出てこない。
  ADR-0054 が定型仕訳で実測した「作った直後に一覧から消える」と同型で、
  そのとき直したのは `JournalTemplate` 1 本だけだった
- **根拠**: 17 モジュール全体を機械走査して `DefaultValue` の出現が 0 件。
  `OnAfterInitialization` が設定されているのは `AppUser` / `ApprovalRouteRule` / `PasswordPolicy` の 3 つだけ。
  `IsActive.Value` を検索条件に持つ参照フィールドは 30 箇所超（`JournalLine.Account` /
  `JournalLine.TaxCategory` / `OpeningBalance.Account` / `FixedAsset.AssetAccount` /
  `BankStatementLine.SuggestedAccount` / `MatchingRule.Account` / `JournalTemplateLine.Account` /
  `BudgetEntry.AccountRef` / `ExpenseRequest.ExpenseCategoryRef` / `AppUser.所属部門` ほか）。
  対して `AppUser.mod.cs:10-13` は `IsActive` を、`ApprovalRouteRule.mod.cs:3-9` も同じ手当てをしている
  ＝この 6 件だけ手当てが漏れている
- **確度**: **確定**（CLB-017 は本リポジトリで実測済みの既知挙動。ADR-0054 §「新規作成の既定を ON にしたのは修正でもある」）

## P1-4 `tax_rates` の適用期間が全消費者で使われていない（死んだ列）— 税率改正を行追加で表せない

- **場所**: `MasterSystem/TaxRate.mod.json`（`ValidFrom` は `IsRequired=true`）、消費側は
  `Expense/ExpenseRequest.mod.cs:603-612` / `Sales/Quote.mod.cs:318-322` / `Sales/Invoice.mod.cs:472-476` /
  `Sales/Acceptance.mod.cs:370-374` / `Sales/SesBilling.mod.cs:52-56` / `Sales/RecurringRun.mod.cs:70-73` /
  `Bank/BankPosting.mod.cs:204-208` / `Accounting/JournalEntry.mod.cs:656, 719`
- **症状**: 税率の解決はすべて「税区分 → `tax_rate_id` → その 1 行の `rate_percent`」であり、
  `valid_from` / `valid_to` を見ている箇所が**ひとつも無い**（`invoice_transition_rates` は
  ちゃんと期間解決しているのと対照的）。したがって
  「2027-10-01 から 12%」を新しい `tax_rates` 行として足しても**誰も拾わない**。
  制度改正に追随するには既存行の `rate_percent` を書き換えるか税区分の参照先を差し替えるしかなく、

- **根拠**: `ModuleSearcher<TaxRate>` の全 8 箇所を確認。いずれも `rs.AddEquals(r => r.Id.Value, tcat.Rate.Value)`
  ＋ `ExecuteFirstOrDefault()` で、日付条件を付けていない。

  `AddLessThanOrEqual(ValidFrom)` / `AddGreaterThanOrEqual(ValidTo)` で期間解決している
- **確度**: **確定**（8 箇所すべて読了）

## P1-5 AppUser の 識別名／表示名／パスワード／所属部門 がどれも必須でない

- **場所**: `MasterSystem/AppUser.mod.json` の `ユーザー識別名` / `表示名` / `所属部門` / `パスワード`
  （4 つとも `IsRequired: false`）
- **症状**:
  - **識別名が空でもユーザーを作れる**。`app_users.user_name` は `NOT NULL UNIQUE` だが
    空文字は NOT NULL を通るので、1 件目は保存でき（ログインできないアカウントが生まれる）、
    2 件目で生の `UNIQUE constraint failed` トーストになる
  - **パスワードが空でも新規作成に進める**。`EnforcePasswordPolicy` は
    「空 ＝ 変更しない」として検証をスキップする（`CustomizedModuleDataIO.cs:74`）ので、
    新規でも素通りし、`app_users.hash` / `salt` の `NOT NULL` に当たる。
    利用者には「パスワードを入力してください」ではなく DB の生エラーが出る
  - **表示名が空**でも保存でき、承認フローの表示（`ApprovalFlow.mod.cs:399` の `DisplayText`）が空欄になる
- **根拠**: JSON の当該 4 フィールドに `IsRequired` が無い／`false`。
  `CustomizedModuleDataIO.cs:68-79` の早期 return。実 DDL `000_auth.sql:6-12` の `NOT NULL` 群
- **確度**: 必須指定が無いことは **確定**。空パスワードで実際に何が起きるか（NOT NULL 違反か空ハッシュ書き込みか）は **要実機確認**

## P1-6 所属部門が空のユーザーの申請は、金額に関係なく「経理 1 名の 1 段承認」に静かに落ちる

- **場所**: `Modules/Expense/ApprovalFlow.mod.cs:277-290`（`FindUserDepartment`）、
  `:193-206`（`ResolveRoleApprovers`）、`:261-274`（`FindFallbackApprover`）
- **症状**: `FindUserDepartment` は `所属部門` が null なら `null` を返す。
  `WalkUpRole(null, ...)` は while ループに入らず即空リスト → 課長段も部長段も
  `FindFallbackApprover`（経理アクセスを持つ在職ユーザーのうち **Id 最小**の 1 名）に落ちる。
  課長段と部長段が同一人物になるので P0-1 とは逆にここでは圧縮が効き、
  **20 万円の申請でも「経理の誰か 1 人が 1 回押すだけ」**になる。
  警告もトーストも出ず、承認履歴を見ないと気づけない。
  ADR-0043 が「新規ユーザー登録は所属＋権限チェックの 2 操作になる」と認めているとおり
  所属の付け忘れは起こりうるのに、付け忘れが権限の穴になる
- **根拠**: 上記 3 関数。`ResolveRoleApprovers` は `role == "manager"` のとき director へ格上げしてから
  `FindFallbackApprover` に落ちる構造で、途中に「部門未設定」を区別する分岐が無い
- **確度**: **確定**（コードのみで成立）

## P1-7 制度閾値・経過措置率は FK で守られておらず、消すと「静かに 0」になる

- **場所**: 実 DB のスキーマ（`system_thresholds` / `invoice_transition_rates` を参照する FK は 0 件）、
  `Modules/Expense/ExpenseRequest.mod.cs:951`、`Modules/Accounting/JournalEntry.mod.cs:674-684`、
  `Modules/Accounting/FixedAsset.mod.cs:50-58`
- **症状**: この 2 テーブルは他のどのテーブルからも参照されていないため、
  マスタ画面（`SystemThreshold` / `InvoiceTransitionRate` とも `CanDelete=true`）から**無条件に削除できる**。

  - `SMALL_ASSET_EXPENSE` を消す → `GetThresholdAmount` が 0 → `if (limit > 0 && ...)` が偽 →

- **根拠**: 実 DB の全テーブルに `PRAGMA foreign_key_list` を回して被参照を集計した結果、
  `system_thresholds` と `invoice_transition_rates` は被参照ゼロ。他のマスタ
  （accounts / tax_categories / departments / app_users / expense_categories / tax_rates /
  approval_flow_template / account_categories / sub_accounts）はすべて被参照あり
- **確度**: **確定**

## P2-8 消費税集計表が制度閾値を「今日」で解決している（過年度の帳票が今日の基準で出る）

- **確度**: **確定**
