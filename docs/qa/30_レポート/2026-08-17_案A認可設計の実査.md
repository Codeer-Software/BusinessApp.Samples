# 案A（対象者ごとにモジュールを分ける）認可設計の実査

経費部品の認可欠落（BUG-0211/0212/0213/0233）に対し、ユーザーが決定した「案A: 対象者ごとに
モジュールを分ける」で全要件を表現できるかを、実コードと実 DB スキーマで確かめた記録。
**本稿は調査のみ。修正は一切していない。**

## 0. 前提の再確認（実測）

現状、経費部品の認可条件は**4本すべて空**である。

- `Designer/Design/Modules/Expense/ExpenseRequest.mod.json:1697-1736` — User/Data の Read/Write すべて `Children: []`
- `Designer/Design/Modules/Expense/ExpenseRequestLine.mod.json:719-730` — 4本とも `{"ModuleName": ""}`
- `Designer/Design/Modules/Expense/ApprovalFlow.mod.json:585-621` / `ApprovalFlowOrder.mod.json:176-209` /
  `ApprovalFlowMember.mod.json:313-346` / `ApprovalHistory.mod.json:190-223` — いずれも空

一方、同じフォルダの受信箱系は既に案Aの形になっている。

- `ApprovalInbox.mod.json:255-283`（`UserReadCondition` = AppUser の `IsApprover` OR `HasAccountingAccess`）
  ＋ `:287-303`（`DataReadCondition` = `CurrentApprover.Value == CurrentUser.Id.Value`）
- `MyApplication.mod.json:275-305`（`DataReadCondition` = `Creator == CurrentUser` かつ Cancelled/Approved 以外）
- `ExpenseSettlementQueue.mod.json:204-249`（`DbTable` は `expense_request`。人ゲート＝`HasAccountingAccess` のみ、行フィルタ無し）

**`ExpenseSettlementQueue` が既に `expense_request` を指す2本目のモジュール**である点は重要で、
案Aの「同一 DbTable に対象者別モジュールを複数置く」は本アプリで前例がある。

## 1. 承認者用モジュールの行フィルタは自モジュールの列だけで書けるか

### 実測: `expense_request` に「現在の承認者」を示す列は無い

`PRAGMA table_info(expense_request)` の 32 列に、承認者を指す列は存在しない。
人を指す列は `creator` / `updater` / `payee_user`（精算対象者）の3つだけで、いずれも承認者ではない。

承認者を持つのは `approval_flow.current_approver`（`PRAGMA table_info(approval_flow)` で確認）で、
`expense_request.approval_flow_id` の先にある**別テーブル**である。

### `current_approver` は認可キーとして使えない（決定的）

`ApprovalFlow.mod.cs:512-542` `RecalculateCurrentApproverDisplay()` は、Active な段の Waiting メンバーのうち
**先頭の1人しか書かない**。

```csharp
CurrentApprover.Value = dbMembers[0].ApproverUser.Value;
return;
```

複数課長の OR 承認（`ApprovalType == "any"`、`ApprovalFlow.mod.cs:307`）では待ちメンバーが2名以上いるが、
`current_approver` には1名しか入らない。だから受信箱は `approval_flow` ではなく
**`approval_inbox_view`（メンバー行を1行=1レコードで展開したビュー）**を読んでいる。

したがって選択肢 (a)「`expense_request` に非正規化列を足す」は、`approval_flow.current_approver` を
写す限り**同じ欠陥をそのまま持ち込む**（OR 承認の第2承認者が締め出される）。
多値を1列に押し込む案（カンマ連結＋`Like`）は、条件式の右辺に置けるのが `CurrentUser.Id.Value` そのもので
区切り文字を合成できないため、`,1,` と `,11,` を区別できず成立しない。

### 結論: (b) 粗いゲートで妥協する

**推奨は (b)。** 承認者用モジュールの行フィルタは、`expense_request` 自身の列である
`settlement_status` で「下書きでない＝申請として提出済み」に絞る。根拠は3つ。

1. **正しさが壊れない。** (a) は OR 承認を壊す。(b) は壊さない。
2. **一覧の導線が既に厳密。** 承認者が申請へ入る入口は `ApprovalInbox`（`ExpenseApprover.frm.json:88`）で、
   これは `approval_inbox_view` × `DataReadCondition` により**自分が担当する行しか出さない**。
   承認者用モジュールに一覧ページを持たせず詳細のみ（`ModulePageType: "Detail"`）にすれば、
   粗くなるのは「URL 直打ちで他人の申請番号を当てた場合」だけに縮む。
3. **行単位の実行時ガードが既にある。** 承認操作そのものは `ApprovalFlow.mod.cs:723-752`
   `GetCurrentMemberForUserStrict()` が「Active な段の自分宛 Waiting メンバー」を DB から引き直して検証し、
   無ければ「承認権限がありません」で止める（`:965`）。読めることと承認できることは既に分離されている。

**ただし (b) には実機確認が要る落とし穴が1つある。** 却下は `SettlementStatus` を `draft` に戻す
（`ExpenseRequest.mod.cs:696-699`）。CLB が行条件を更新の**前像**で評価するか**後像**で評価するかが
仕様書に明記されておらず、後像評価なら「draft を除外する行条件」が却下操作自体を弾く。
安全側の逃げは `DataWriteCondition` を空（人ゲートのみ）にし、行フィルタは `DataReadCondition` だけに置くこと。
それでも仕様上「更新には `DataReadCondition` も必要」（`_specs/ModuleDesign.md:118-121`）なので、
**却下が通るかは実機で必ず確かめる**こと。

## 2. `approval_inbox_view` と `my_application_view` は何をしているか / 案Aの受け皿になるか

### 実測（`SELECT sql FROM sqlite_master WHERE type='view'`）

- **`approval_inbox_view`** — `approval_flow_member m` × `approval_flow_order o` × `approval_flow f` の3段 JOIN。
  `m.status='Waiting' AND o.status='Active' AND f.status='Pending'` で絞り、
  `m.approver_user_id` を **`current_approver`** という名前で公開する。
  1行 = 「いま自分が承認すべきメンバー行」。**OR 承認でも待ち人数ぶん行が出る**のがこのビューの要点。
- **`my_application_view`** — `approval_flow f` に `expense_request er` を左結合し、`title` / `amount` を
  `parent_module_name='ExpenseRequest'` のときだけ載せる。`f.creator`（申請者）と `f.current_approver` を公開する。
- （参考）`active_app_users` — `app_users WHERE is_active=1`。

### 案Aの受け皿として使えるか

**一覧・行フィルタの受け皿としては使える。** 実際すでにそう使われている（`ApprovalInbox` / `MyApplication` は
`CanCreate/CanUpdate/CanDelete: false` の読み取り専用モジュール）。
承認者用に「`expense_request` × `approval_flow` × Active段 × Waiting メンバー」を結合した同種のビューを新設し、
`DataReadCondition` を `current_approver == CurrentUser.Id.Value` にする手は**成立する**。
`current_approver` が自モジュール（＝ビュー）の列になるので、案Aの原理どおり「人ゲート AND 行フィルタ」で書ける。
これが1節の (a)/(b) に対する**第三の選択肢 (c)** で、OR 承認も壊さない。

**ただし書き込みの器にはできない。** SQLite のビューは INSTEAD OF トリガが無ければ更新できず、
承認操作は最低でも `expense_request.settlement_status` を書く（3節参照）。
なお本アプリには `trg_active_app_users_ins` / `trg_active_app_users_upd_password` という
**ビューへの INSTEAD OF トリガの前例がある**ので、`UPDATE expense_request SET ... WHERE id = old.id` を
書くトリガを足せば書けるようにはできる。だが多テーブル JOIN ビューへの INSTEAD OF UPDATE は
「どの列がどのテーブルへ落ちるか」をトリガ側で全部決め打ちする必要があり、
`ModuleField`（`approval_flow_id` を保存のたび書き戻す）まで面倒を見ることになる。
**初手では (b)、(c) は「承認者一覧を厳密にしたくなったとき」の伸びしろとして持っておく**のが妥当。

## 3. 申請提出時の書き込み連鎖

`ApprovalFlow.mod.cs:789-834` `SubmitButton_OnClick()` が起点。順に:

1. `parent.ValidateForApply()`（`ExpenseRequest.mod.cs:504`）— 読み取りのみ
2. `ApprovalFlow.Status = "Pending"` / `AttemptNo` / `ParentModuleName` / `ParentId` を設定（`:808-814`）
   → **`approval_flow` 既存行の UPDATE**
3. `parent.SelectTemplateIds()`（`ExpenseRequest.mod.cs:436`）— 読み取りのみ
4. `LoadFromTemplates()`（`:220-335`）→ `Orders.AddRow()`（`:300`）で **`approval_flow_order` を INSERT**、
   `newOrder.Members.AddRow()`（`:310` / `:323`）で **`approval_flow_member` を INSERT**
5. `AddHistory("Submit", ...)`（`:637-647`）→ `History.AddRow()` で **`approval_history` を INSERT**
6. `NotifyParentStatusChanged()`（`:784-787`）→ `ExpenseRequest.OnApprovalFlowStatusChanged("Pending")`
   （`ExpenseRequest.mod.cs:673-701`）が `SettlementStatus` / `DepartmentRef` / `EstimatedAmount` を設定
   → **`expense_request` 既存行の UPDATE**
7. `parent.Submit()`（`:825`）— ここまでの 2〜6 が**1回のカスケード保存**で確定する
   （`ExpenseRequest` → ModuleField `ApprovalFlow` → DetailListField `Orders` → DetailListField `Members` /
   ListField `History`）
8. `NotifyActiveApprovers(...)`（`:832` → `:841-844`）→ `new Notification().Send(...)` で **`notification` を INSERT**

### 承認フロー系の `UserWriteCondition` を承認者に絞ると申請提出は壊れるか

**壊れる。確定。** 理由は2段階ある。

- **`approval_flow` は UPDATE である**（手順2）。`_specs/ModuleDesign.md:118-121` の表どおり、
  更新には `UserReadCondition` と `DataReadCondition` が必要で、当然 `UserWriteCondition` も必要。
  申請者が承認者フラグを持たなければ、この時点で保存が拒否される。
- **INSERT 側も逃げられない**（手順4・5）。同節が「新規追加は行条件の**対象外**」と書いているのは
  `DataReadCondition` / `DataWriteCondition` の話であって、`UserWriteCondition`（人ゲート）は
  新規追加にも効く。よって `approval_flow_order` / `approval_flow_member` / `approval_history` の
  人ゲートを「承認者だけ」にすると、一般社員は自分の申請の承認段すら作れない。

かつ7の `parent.Submit()` は**単一トランザクション相当のカスケード**なので、
どれか1つが拒否されれば申請全体が失敗する。「承認履歴だけ落ちて申請は通る」という部分成功は起きない。

**逆向きの対称な破綻も同時に押さえておくこと。** 承認（`ApprovalFlow.mod.cs:985`）・却下（`:1144`）・
取消（`:1272`）・超過再承認（`:1238`）はすべて `GetParentModule().Submit()` を呼ぶ。
つまり**承認者は `expense_request` の行を UPDATE する**。
`ExpenseRequest` の `DataWriteCondition` を `Creator == CurrentUser` にした瞬間、承認操作が壊れる。
承認者用モジュールを別に立てる必要は、まさにここから来ている。

## 5. 案Aで全要件を表現できるか

### 表現できない一点

**承認フローの明細3テーブル（`approval_flow_order` / `approval_flow_member` / `approval_history`）を
「その申請の承認に関わっている人だけ」に絞る行フィルタは、案Aでも書けない。**

CLB の行条件は「自モジュールの列 × 比較 ×（定数 または `CurrentUser.*`）」しか置けない
（`_specs/SearchConditions.md:278-284`。`Exists`/`NotExists` は `IS NOT NULL`/`IS NULL` であって
**副問い合わせではない**）。この形で「関係者の集合」は表せない。

- `approval_flow_order` — 列は `id / approval_flow_id / order_no / status / approval_type`
  （`PRAGMA table_info` 実測）。**人を指す列が1つも無い**。
- `approval_flow_member` — `approver_user_id` はあるが、それが指すのは**自分の行だけ**。
  OR 承認で承認者Aが承認すると、`SkipRemainingWaitingMembers()`（`ApprovalFlow.mod.cs:1053-1077`）が
  同じ段の**B・Cの行**を `Skipped` に更新する。`ApproverUser == CurrentUser` の行フィルタは
  この正当な更新を必ず弾く。
- `approval_history` — `actor_user_id` を使うと「自分が起こした履歴」しか読めず、
  承認画面の履歴欄が空になる（業務要件と正面衝突）。

モジュール分割は「人ゲート AND 行フィルタ」の**組を増やす**操作であって、
行フィルタが表現できない集合を作り出すことはできない。よってこの3テーブルは
**人ゲート（`UserReadCondition` / `UserWriteCondition`）止まり**にせざるを得ず、
行単位の担保は `GetCurrentMemberForUserStrict()`（`ApprovalFlow.mod.cs:723-752`）という
スクリプト側のガードに残り続ける。残留リスクは「承認者フラグを持つ社員が、
URL 直打ちで他人の申請の承認段・履歴を読める」こと（書き込みは上記ガードで止まる）。

これ以外の要件——申請者は自分の申請だけ／承認者は提出済みの申請を開いて承認できる／
経理は全件を処理できる／明細と領収書は親と同じ範囲でしか見えない——は案Aで表現できる。

### 設計案

`ExpenseRequest` と `ExpenseRequestLine` を対象者別に分け、承認フロー系は分けずに人ゲートだけ張る構成。

| モジュール | DbTable | UserReadCondition | UserWriteCondition | DataReadCondition | DataWriteCondition | 用途 | 新/既 |
|---|---|---|---|---|---|---|---|
| `ExpenseRequest` | `expense_request` | （空） | （空） | `Creator == CurrentUser.Id` | `Creator == CurrentUser.Id` | 申請者の作成・編集・照会。実費確定 | 既存（条件を入れる） |
| `ExpenseRequestApproval` | `expense_request` | `AppUser.IsApprover == true` | 同左 | `SettlementStatus != "draft"` | （空。人ゲートのみ） | 承認者が開く申請詳細＋承認欄。編集不可・明細は読み取り | 新規 |
| `ExpenseRequestAccounting` | `expense_request` | `AppUser.HasAccountingAccess == true` | 同左 | （空＝全件） | （空＝全件） | 仕訳生成・精算・完了。経理ボタン群を持つ | 新規 |
| `ExpenseSettlementQueue` | `expense_request` | `HasAccountingAccess == true` | 同左 | （空） | （空） | 経理の作業受信箱（一覧のみ・読み取り） | 既存（遷移先だけ差し替え） |

★ `ExpenseRequestLine` の行フィルタには**構造的な前提が要る**。`expense_request_lines` には
`creator` に相当する列が無く（`PRAGMA table_info` 実測。19 列すべてに人を指す列が無い）、
親への FK `ExpenseRequestId` は `IdFieldDesign`（`ExpenseRequestLine.mod.json:49`）なので
リンク越しのパスも書けない。取りうる手は2つ。

- **(α) `ExpenseRequestId` を `LinkFieldDesign` に変える**（`CommonMistakes` #28 が FK に許す型は
  `IdFieldDesign` **または** `LinkFieldDesign`）。すると `ExpenseRequestId.Creator.Value == CurrentUser.Id.Value`
  という行条件が書ける可能性がある。`ExpenseRequest.mod.json:4171` が `"ApprovalFlow.Status"` という
  `ModuleField` 越しのリンクキーを実際に使っているので、リンク越しのパス自体は生きている。
  **ただし `DataReadCondition` でリンク越しのパスが使えるかは仕様書に明記が無く、要実機確認。**
- **(β) `expense_request_lines` に `creator` 列を足し**、`ExpenseRequestLine` の Field 名を予約名 `Creator` にして
  CLB の自動セットに乗せる。行条件は `Creator == CurrentUser.Id` で確実に書ける。
  既存行のバックフィル（`UPDATE ... SET creator = (SELECT creator FROM expense_request ...)`）が要る。

**(β) を推奨する。** (α) は挙動が未確認で、外すと「明細が空で表示される」という
気づきにくい壊れ方（`_specs/ModuleDesign.md:141-149`: 埋め込み子は権限不成立でも**エラーにならず空**）をする。
(β) は列を1本足すだけで確実に効き、しかも埋め込み子の行条件は「同梱フェッチでも後からの取得でも一貫して効く」
と仕様が保証している。

なお `ApprovalFlowOrder` / `ApprovalFlowMember` / `ApprovalHistory` の人ゲートに使う
`CanUseExpense`（`app_users.can_use_expense`）は、申請提出の連鎖（3節）を通すために
**申請者も満たす**必要がある。「承認者だけ」に絞ってはならない。

### 実装順序の提案

書き込み連鎖に触るものを最後に回し、読み取りだけのものから固める。

1. **`expense_request_lines` に `creator` 列を足してバックフィル**（DDL＋UPDATE のみ。画面は無変更）。
   ここで `sql` CLI と `designcheck` を通し、既存が壊れないことを確認する。
2. **`ExpenseRequestLine` に行条件を入れる**（★の (β)）。この時点で「申請者は自分の明細しか見えない／
   承認者・経理の画面では明細が空になる」状態になるはず。**空になることを実機で確認する**——
   これが「埋め込み子は権限不成立で静かに空になる」仕様を自分の目で押さえる回になり、以降の切り分けが速くなる。
3. **`ExpenseRequestLineAccounting` を作り、経理用の親から参照させる**。経理は行フィルタ無し＝最も単純なので、
   分割の型をここで確立する。
4. **`ExpenseRequestAccounting` を新設**し、`ExpenseSettlementQueue.mod.cs:6` の遷移先を差し替える。
   仕訳生成・精算・完了のスクリプトはこちらへ移す。経理の動線が閉じたことを実機で確認。
5. **`ExpenseRequest` に `Creator` 行条件を入れる**（申請者用に確定）。ここで承認者・経理が
   `ExpenseRequest` を開けなくなるので、4 が先に済んでいる必要がある。
6. **`ExpenseRequestApproval` ＋ `ExpenseRequestLineApproval` を新設**し、`ApprovalInbox.mod.cs:17` の
   遷移先を写像する。**承認・却下・取消が実際に保存できるかをここで必ず実機確認する**
   （1節末尾の「却下は `draft` に戻す」問題、3節の `GetParentModule().Submit()`）。
7. **最後に `ApprovalFlowOrder` / `ApprovalFlowMember` / `ApprovalHistory` の人ゲート**を張る。
   ここは申請提出の連鎖を壊す唯一の場所なので、他が全部緑になってから触る。
   張った直後に「新規申請 → 提出 → 承認 → 却下 → 再申請」を通しで流す。
8. `Designer/Design/PageFrames/Expense*.frm.json` の Link / `OtherPageModuleDesigns` / Start を整理し、
   `designcheck` を 0 findings にして締める。

各ステップの後に `deploy.ps1` ＋**サーバ再起動**（スクリプト変更を含むため）を挟むこと。
