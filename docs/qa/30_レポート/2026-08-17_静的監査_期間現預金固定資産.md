### F-01 [P0] `YearIndex` の月調整が逆符号で、1〜3月に取得した資産の償却が黙って壊れる

- **場所**: `Designer/Design/Modules/Accounting/FixedAsset.mod.cs:148-156`（特に 154 行）
- **確度**: 確定（純粋な算術。実行環境に依存しない）

```csharp
var years = yearStart.Year - acq.Year;
if (acq.Month >= yearStart.Month) { years = years; } else { years = years - 1; }
return years + 1;
```

3月決算（`yearStart.Month == 4`）で、取得日が 1〜3月＝**前年度に属する**とき、経過年数は
「1 少ない」のではなく「1 多い」。符号が逆である。実例:

| 取得日 | 対象年度 | 正しい年目 | 実装の戻り値 | 結果 |
|---|---|---|---|---|
| 2026-02-10 | 第18期（2026-04〜2027-03） | 2 | **0** | `CalcDepreciationForYear` の `if (k < 1) return 0;` に落ち、**償却額 0 円** |
| 2026-02-10 | 第19期（2027-04〜2028-03） | 3 | **1** | **取得年度扱い**になり `firstYearAmount = annual × 2 / 12` を再度計上 |

- **影響**: 1〜3月取得の資産（決算期末の駆け込み取得は実務で頻出）は 2 年目に減価償却費が計上されず、3 年目以降も月割の初年度額が延々と繰り返される。累計は取得価額に到達せず、資産が過大計上され続ける。
- **静かさ**: 例外もエラーも出ず、トーストは「この年度の償却額はありません（対象外または償却済み）」（`FixedAsset.mod.cs:254`）と出るだけで、正常系と区別できない。
- **`lump_sum_3yr` にも同じ経路で効く**（`FixedAsset.mod.cs:91` の `k3`）。1〜3月取得の一括償却資産は 2・3 年目が 0 円になり、取得価額の 1/3 しか損金にならない。

### F-02 [P0] 期首残高の貸借一致検証が無く、Σ≠0 のまま保存できる

- **場所**: `FiscalYear.mod.cs:19-37`（`UpdateOpeningTotal`）／`FiscalYear.mod.json` の `OpeningBalances`（`OnValidateInput` は空文字）
- **確度**: 確定（`.mod.cs` に `OnBeforeSubmit` 相当が無く、`.mod.json` の全フィールドの `OnValidateInput` が空）

`UpdateOpeningTotal()` は合計を `OpeningTotal` に出し、0 でなければ文字色を赤にするだけで、**保存を止めない**。
`docs/04` §6「導入初年度の期首残高は…**投入合計が貸借一致しないと確定不可**（複式の入口を守る）」および
§9 チェックリスト「期首残高の貸借一致検証」は**未実装**である。

- **影響**: 移行初年度の期首が最初から貸借不一致でも登録でき、以後すべての帳票が同額ずれ続ける。導出主義（ADR-0004）を採っている以上、期首は唯一の「入力された残高」であり、ここが複式の入口の統制点にあたる。
- 併せて: `OpeningBalances` の `PagerPosition` は `"Top"`（ページャあり）で、`UpdateOpeningTotal` は `OpeningBalances.Rows` しか見ない。行数がページ上限を超えるとき合計が現在ページ分だけになる可能性がある（**要実機確認**。F-05 と同型の疑い）。

### F-03 [P0] 翌期繰越が補助科目・部門を捨て、期首残高の内訳が消える

- **場所**: `FiscalYear.CarryOverSql.sql:8-9`
- **確度**: 確定（`SELECT @next_year_id, t.account_id, NULL, NULL, t.bal` と、集計側が `a.id` 単位でしか GROUP していない）

```sql
INSERT INTO opening_balances (fiscal_year_id, account_id, sub_account_id, department_id, balance)
SELECT @next_year_id, t.account_id, NULL, NULL, t.bal
```

`docs/04` §6「翌期の opening_balances を生成: BS 科目の期末残高を**科目・補助・部門単位でコピー**」に反し、
実装は**科目単位に潰して補助科目と部門を NULL で潰している**。

- **影響**: 補助元帳（`sub_accounts` 単位）の期首が翌期で全部 0 になり、取引先別の売掛・買掛内訳が年度をまたいだ瞬間に失われる。部門別 BS を作る場合も同様。
- 前期の `opening_balances` に補助・部門つきの行があっても、繰越後は 1 科目 1 行に潰れる（前期の内訳は残るので、**年度をまたぐと内訳の粒度が突然落ちる**という形で現れる）。
- なお総額は保たれるので、試算表・BS の合計は狂わない。壊れるのは内訳だけである。

### F-04 [P0] 繰越後の後始末 Submit が未検査で、`next_year_id` が残ると以後の通常保存が毎回「翌期首の洗い替え」を実行する

- **場所**: `FiscalYear.mod.cs:86-95`
- **確度**: コードは確定（戻り値未検査）。実際に残留しうるかは**要実機確認**

```csharp
NextYearId.Value = typedNext.Id.Value;
var ret = this.Submit();          // ← ここは検査している
NextYearId.Value = null;
if (ret == false) { Toaster.Error("繰越に失敗しました"); return; }
this.Submit();                    // ← 戻り値を見ていない。失敗しても成功トーストが出る
Toaster.Success($"{typedNext.Name.Value} への繰越が完了しました");
```

`NextYearId` は `DataOnlyFields` 扱いだが**実列 `fiscal_years.next_year_id` にバインドされている**（`ddl/155`）。
2 回目の Submit（NULL への書き戻し）が失敗すると値が DB に残り、`CarryOverSql` は `Timing: Update` なので
**以後その年度を保存するたびに繰越 SQL が発火し、翌期の `opening_balances` を無言で DELETE→INSERT する**。

- **影響**: 翌期の期首残高を手で調整していた場合、年度名を直した・状態を締め済みにした、といった無関係な保存で調整が消える。画面にはトーストも差分も出ない（`next_year_id` は `DataOnlyFields` なので画面に見えない）。
- ISSUE-0001 の教訓（この経路は「静かに効かない／静かに効く」の両方を起こす）が、逆向きにまだ残っている形。
- **対策の方向**: 2 回目の Submit も検査して失敗時に警告する、または SQL の no-op ガードを「`next_year_id IS NOT NULL` かつ更新直前にセットされた」ことまで含む形にする。

### F-05 [P0] 「変更を保存」が、画面のリストに載っていない自分の下書きを DB から消す

- **場所**: `CashEntry.mod.cs:129-150`（`SaveListEdits`）。`PostAll_OnClick` からも呼ばれる（199 行）
- **確度**: ロジックは確定。実害の有無は `ListField.Rows` の意味論に依存するため**要実機確認**

```csharp
foreach (var row in DraftList.Rows) { ... aliveIds.Add($"{t.Id.Value}"); }
var s = new ModuleSearcher<CashEntryDraft>();
s.AddEquals(e => e.Creator.Value, CurrentUser.Id.Value);
foreach (var row in s.Execute()) { if (aliveIds.Contains(...)) continue; t.Delete(); }
```

「画面から消えた行を DB からも消す」（ADR-0055 実装知見 4・FB-040）ための処理だが、
**`DraftList` は `LimitCount: 200` / `PagerPosition: "Bottom"`**（`CashEntry.mod.json`）である。

- `DraftList.Rows` が**現在ページ分しか返さない**なら、ページ 2 以降の下書きが「変更を保存」を押すたびに全削除される。
- 仮に全ロード分を返すとしても、**201 件目以降は `LimitCount` に落ちて `aliveIds` に入らず、必ず削除される**（こちらは確定）。
- 削除は確認ダイアログ無しで、トーストは「変更を保存しました（N 行を削除）」と出るだけ。**利用者の意図した削除と区別がつかない。**
- 同じ `DraftList.Rows` を `RefreshSummary`（408-448 行）が「起票後の見込み残高」の元にしているので、上限を超えた分は見込み残高からも黙って抜ける。

### F-06 [P1] 除却・売却が帳簿に一切反映されず、除却後も償却仕訳を生成できる

- **場所**: `FixedAsset.mod.json`（`Status` 候補 `使用中/除却/売却`・`RetiredDate` あり／ボタンは `GenerateDepButton` の 1 つだけ）、`FixedAsset.mod.cs:70-145`（`CalcDepreciationForYear` が `Status` / `RetiredDate` を一度も参照しない）
- **確度**: 確定（フィールド一覧とスクリプト全文の走査）

- 状態を「除却」にしても**除却損（8500）の仕訳は生成されない**。資産は BS に簿価のまま残り、台帳と帳簿が恒久的に食い違う。売却（8000 固定資産売却益）も同じで、売却価額を入れる欄すら無い。
- `CalcDepreciationForYear` が状態を見ないため、**除却済み・売却済みの資産に対しても翌年度の償却仕訳を生成できる**（二重生成ガードは「その年度に生成済みか」しか見ない）。除却年度の月割（期首〜除却日）も無く、除却年度は満額計上される。
- `docs/04` §7 は状態と `retired_date` を持つことまでしか規定しておらず、除却・売却の記帳フローは未定義。**設計から欠けている**ので、修正は ADR を要する。

### F-07 [P1] 200%定率法に償却保証額・改定償却率が無く、簿価が 1 円に到達しない

- **場所**: `FixedAsset.mod.cs:121-142`
- **確度**: 確定（コード内コメントも「簡易: 保証率・改定償却率は未対応」と明記）

`amount2 = book × (2 / 耐用年数)` を毎年掛けるだけなので、簿価は指数的に減衰するが**有限年で 1 円に到達しない**。
法人税法の定率法は、償却額が償却保証額を下回った年度から改定償却率による均等償却へ切り替える必要がある。

- **影響**: 耐用年数を過ぎても償却が終わらない／別表十六（二）と一致しない。「市販の財務会計専門ソフト以上」を掲げる以上、定率法は制度どおりに実装されている必要がある。
- 画面にもドキュメントにも「定率法は簡易実装です」という表示は無く、利用者は正規の定率法だと信じる。
- 併せて `int amount2 = book * rate;`（`rate` は `decimal`）の丸め（切り捨てか四捨五入か）は CLB スクリプトエンジンの型変換に依存する。**要実機確認**。円単位の金額なので 1 円ずれる。

### F-08 [P1] 当日を含む会計年度が無いと、現預金残高が黙って 0 円・出納帳が 0 件になる

- **場所**: `CashBalance.Query.sql:11-27`／`CashBook.Query.sql:7-11, 50`
- **確度**: 確定（SQL の意味論）

```sql
WITH yr AS (SELECT id FROM fiscal_years
            WHERE date(start_date) <= date('now','localtime') AND date(end_date) >= date('now','localtime'))
...
COALESCE((SELECT SUM(o.balance) FROM opening_balances o
          WHERE ... o.fiscal_year_id IN (SELECT id FROM yr)), 0) + COALESCE(..., 0) AS book_balance
```

`yr` が 0 件（＝翌年度をまだ作っていない・年度の隙間の日に開いた）だと、`IN (SELECT id FROM yr)` が常に偽になり、
`COALESCE(...,0)` が効いて **`book_balance` が全科目 0 円**になる。エラーも警告も出ない。

- 入出金起票の画面は「現預金の残高（yyyy/MM/dd HH:mm 現在）」という見出しの下に 0 円を並べる（`CashEntry.mod.cs:439`）。**「本当に残高がゼロ」と区別できない。**
- `CashBook.Query.sql` は更に悪く、`date(e.entry_date) >= COALESCE(date(@date_from), (SELECT date(start_date) FROM yr))` が
  `NULL` との比較になり **1 行も返らない**（`CashBook.mod.cs:10` の `if (fy == null) return;` で検索既定も入らないため、日付未指定の初期表示がこの経路に落ちる）。
- 年度末の翌日（例: 4/1 に第19期を未作成）に必ず踏む。**期初は経理が最も画面を開く時期**である。

### F-11 [P1] 入出金の一括起票が会計年度の締め状態を見ない

### F-17 [P2] 入出金起票の現預金行に、科目マスタの既定税区分が残りうる（ADR-0053 と同型）

## 2. 問題が無いことを確認した点（誤検知を避けるための記録）

- **繰越の代数**: 期首合計 Σ=0 は成立する。BS 科目に「期首＋当期仕訳（借方正）」を積み、`code='3100'` にだけ PL 科目の `Σ(D−C)`（＝−当期純利益）を足す式は、全仕訳が貸借一致していれば `Σ_BS + Σ_PL = 0` により合計 0 になる。符号（利益で 3100 が貸方＝負に振れる）も正しい。
- **繰越の冪等性**: `DELETE → INSERT` の洗い替えなので、何度実行しても結果は同じ。二重に走っても残高は倍にならない。
- **繰越の事故防止**: 「期首も確定仕訳も無い年度からの繰越」を止めるガード（`FiscalYear.mod.cs:62-76`）が入っており、移行初年度の期首を空データで潰す事故は塞がれている。
- **入出金起票の税行**: 相手科目の行だけを内税化し、`GenerateTaxLinesOnce()` を入力額のまま 1 回だけ呼ぶ経路は正しい。税行は本体行と同じ貸借側に付き、本体が税抜に減るので**貸借は不変**（ADR-0053 の検算どおり）。経過措置（控除不能分を本体に残す）でも貸借は保たれる。
- **ADR-0051（消込済みのみ）**: 現預金残高は「確定仕訳の集計」から導出されるため、未消込の入金が混ざる余地が構造的に無い。`CashBalance.Query.sql` / `CashBook.Query.sql` とも `e.status = 'posted'` で絞っている。
- **UTC ずれ**: 対象モジュールの SQL は全て `date('now','localtime')`。スクリプトも `DateTime.Today` / `DateTime.Now`。裸の `date('now')` は `Designer/temporary/` の検算スクリプトにしか無い（本番経路ではない）。
- **償却の二重の真実**: `fixed_assets` に償却累計・簿価の列は無く（`ddl/060`）、仕訳が唯一の真実。ADR-0004（導出主義）に沿っている。ただし**理論値と仕訳の乖離を検知する仕組みも無い**（F-01・F-06・F-07 が乖離を生む側）。
- **償却累計の上限**: 定額法（`FixedAsset.mod.cs:113-117`）と一括償却 3 年（91-94 行）は、それぞれ残存簿価 1 円・取得価額ちょうどで正しく打ち止めになる。最終年度の端数調整も入っている。
- **確定伝票の保護**: `LockPostedFields()`（`JournalEntry.mod.cs:77-85`）で個別ロック、削除は下書きのみ（824-835 行）。ADR-0026 準拠。`this.IsViewOnly` を使わない理由もコメントに残っている。
- **`OnDataChanged` の上書き**: 対象 9 モジュールの `OnDataChanged` は全て表示値の再計算のみで、永続列を上書きするものは無い。
