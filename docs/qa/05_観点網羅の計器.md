# 観点網羅の計器（計画）— SQL・DDL テストの強さを測る

> 2026-08-26 に開発者と検討し、方針の GO が出た**未実装の計画**である。
> 実装に着手するセッションは、本書を設計の起点にし、着手時に ADR を起こして
> 判断（なぜミュテーションか・どの案を採ったか）をそちらへ移す。

## 1. 問題 — SQL・DDL はテストの強さを測る計器の外にいる

`BusinessApp.Schema.Tests` は、本物の DDL を載せたインメモリ SQLite に本物の SQL を流して
検査する三層構造を持つ。

| 層 | 何を守るか |
|---|---|
| `QueryModuleTests` | クエリモジュールの宣言と SQL の**整合**（全モジュール自動） |
| `JournalBookQueryTests` など行動テスト | 値を入れて行数を数え、**条件が効くこと**（帳簿ごとに手書き） |
| `SchemaConstraintTests` など制約テスト | CHECK・UNIQUE・外部キー・トリガによる**不変条件** |

この仕組み自体は良い。問題は**テストの強さを測る計器が無い**ことである。
C# 側はカバレッジ 100% と `dotnet stryker`（[ADR-0012](../decisions/0012-テスト方針とカバレッジのゲート.md)）が
「テストされていないロジック」を機械で炙り出すが、どちらも C# の IL しか見ない。
SQL ファイル・DDL の制約・トリガはその外にあり、**観点の漏れは人の注意力だけが頼り**になっている。
実際に [qa/03](03_テストで漏らした実例.md) には「`>=` と `>` の取り違え」「`date()` の掛け忘れ」
「分岐名の綴り違い」のような、**例外にならず静かに 0 件や全件を返す**壊れ方が積まれている。

「観点を網羅できているか」は、実は 2 つの別の問いであり、それぞれに計器が作れる。

| 問い | 計器 |
|---|---|
| 書いたテストは、SQL・DDL の壊れ方を**検出できる強さ**があるか | §3 SQL ミュテーション・§4 制約ノックアウト |
| そもそも**観点リストの項目が全部テストになっている**か | §5 ID トレーサビリティ・§6 構造メタテスト |

## 2. 結論 — 4 つの計器を作る（着手順つき）

| 順 | 計器 | 概要 | 重さ |
|---|---|---|---|
| 1 | **制約ノックアウト**（§4） | DDL から制約・トリガを 1 つずつ外し、スキーマテストが赤になることを確認する | 小 |
| 2 | **ID トレーサビリティ**（§5） | 不変条件 I-nn・制度要件の ID とテストの参照を突き合わせ、未参照 ID を列挙する | 小 |
| 3 | **SQL ミュテーション B 案**（§3） | SQL に機械変異を入れ、テストの入力コーパスで原本と行セットを差分比較する | 中 |
| 4 | **構造メタテスト・独立オラクル**（§6） | 行動テストの書き忘れ検知と、集計 SQL の C# 独立実装との突き合わせ | 中 |
| 随時 | **SQL ミュテーション A 案**（§3-3） | 実テストスイートをミュータントに対して回す。区切りごとに手動実行 | 大 |

1・2 は半日で入って即座に効く。3 は設計判断（演算子表・コーパスの形）を含むので本書 §3 に従う。
4 の独立オラクルは集計系 SQL（フェーズ 3 の税集計・フェーズ 4 の試算表）が増える前に土台だけ作る。

## 3. 計器 1: SQL ミュテーションテスト（自作ミニ Stryker）

Stryker が効かないのは Stryker が C# の IL しか変異させないからで、
**ミュテーションテストという手法自体は SQL にそのまま適用できる**。
SQL は `File.ReadAllText` で読むただのテキストであり、変異の注入点は既にある。

### 3-1. ミュータントの生成（A 案・B 案で共通）

1. 原本の SQL を読む
2. **変異演算子ごとに出現箇所を列挙**する（正規表現または簡易トークン走査）
3. **1 変異点 = 1 ミュータント**。出現位置を 1 つだけ置換した SQL 文字列を作る
   （同時に 1 箇所しか変えないのがミュテーションテストの原則）

変異演算子の表は汎用セットではなく **[qa/03](03_テストで漏らした実例.md) の実績から起こす**。
初期セットの候補（確定は実装時）:

| 演算子 | 由来 |
|---|---|
| `>=` → `>`、`<=` → `<` | 境界の取り違え（qa/03 実績） |
| `date(x)` → `(x)` | `date()` の掛け忘れ（qa/03 実績） |
| CASE 分岐の候補値文字列の 1 文字置換 | 分岐名の綴り違い（qa/03 実績） |
| `AND` → `OR` | 条件の合成ミス |
| `LEFT JOIN` → `INNER JOIN` | 任意項目の行落ち |
| `IS NULL` → `IS NOT NULL` | NULL 分岐の反転 |
| `COALESCE(a, b)` → `(b)` | 写し（スナップショット）優先の崩れ |
| `DISTINCT` の削除、`ORDER BY` の列を 1 つ削る | 重複・並び順 |

注意: 正規表現ベースの置換は **SQL コメントと文字列リテラルの中にも当たる**。
コメント由来の等価ミュータントを減らすため、変異点の列挙前にコメントを除外する
（SQLite の文法なら「文字列リテラルとコメントをスキップする」だけの簡易走査で足りる）。

### 3-2. B 案 — 行セットの差分比較（常設・上界の測定）

**判定**: シード済みインメモリ DB に対し、テストが使う入力コーパスを
**原本 SQL とミュータント SQL の両方に流し、全行セットを比較**する。

- どれかの入力で結果が違う → 殺せた（今の入力群で検出可能）
- **全入力で完全一致 → 生存**。「この壊れ方は今のテストデータ・入力では原理的に見分けられない」
  ことの証明なので、シード行かパラメータの組を足す
- 変異の結果 SQL が構文エラーになったら自明に検出可能なので集計から除外する

**入力コーパスの定義が肝**である。SQL の出力を決めるのは **(DB の状態, パラメータの組)** の
ペアなので、コーパスの 1 エントリもこのペアにする。インメモリ SQLite は作り直しが一瞬なので、
エントリごとに「シード → ARRANGE SQL → 両者を流して比較」をやり直せばよい。

成立条件が 1 つある。

> **テストの入力（DB 状態の作り方＋パラメータ）が、データとして列挙できる形になっていること。**

現行の `JournalBookQueryTests` は ARRANGE を SQL 文字列（`Create(beforePosting)`）で受けており、
既にこの形をしている。**この設計規約を崩さない**ことが計器の前提になる。実装時にやること:

- コーパスの表を 1 箇所に定義し、**行動テストとミュテーションハーネスの両方が同じ表を読む**
  （`[MemberData]` の供給元を共有する）。写し漏れ・ドリフトを構造的に消すため
- `Create` の後に追加で `Execute` している行動テスト（並び順の検査など）は、
  ARRANGE を `beforePosting` 側へ寄せてコーパス化できる形に直す
- 生存ミュータントには**等価ミュータント**（挙動が本当に変わらないもの）が混ざる。
  人が仕分けて**許容リスト**（ファイル・変異点・理由）に残し、テストは
  「許容リストにない生存ミュータントが 0 件」を検査する。これで**常設のテスト**にできる

**限界も記録しておく**: B 案は「どの入力で違いが出うるか」しか見ず、
**テストがどの列をアサートしているか**は見ない。つまり測るのはテストの強さの**上界**である。
正確な測定は A 案で行う。

### 3-3. A 案 — 実テストスイートで殺す（区切りごとに手動）

環境変数（例 `SQL_MUTATION=<ファイル>:<位置>:<置換前>:<置換後>`）を `TestDatabase` の SQL 読込が
解釈して変異を当て、ドライバスクリプトがミュータントごとに `dotnet test --filter` を
子プロセスで回して**赤になること**を確認する。実際のアサーションで殺せるかを測るので正確だが、
実行時間が長い。**コミット前フックには載せず**、実装の区切り・フェーズの区切りで手動実行する。

### 3-4. A 案と B 案の関係

生成（§3-1）は共通で、**違いは殺し方の判定だけ**である。
B 案で入力の穴を常時見張り、区切りで A 案を回して答え合わせする、という補完関係で運用する。

## 4. 計器 2: 制約ノックアウトテスト

`sqlite_master` から CHECK・UNIQUE・外部キー・トリガを列挙し、**1 つずつ外した DDL** で
スキーマテスト群を流して「赤になること」を確認する。全部緑のまま生き残った制約は、
**誰もテストしていない制約**である。

- 計上済み仕訳の不変性（[CLAUDE.md §2-2](../../CLAUDE.md)）を守るトリガが本当にテストで
  見張られているかを、これで機械的に言えるようになる
- 実装の注意: トリガとインデックスは `DROP` で外せるが、**CHECK と UNIQUE は
  `CREATE TABLE` の中にあるので DROP できない**。DDL テキストから該当行を除いた変異版を
  作って DB を組み直す（§3-1 と同じテキスト変異の考え方）。インメモリなので組み直しは一瞬
- 生存の扱いは §3-2 と同じ（テストを足すか、許容リストに理由つきで残す）

## 5. 計器 3: ID トレーサビリティのメタテスト

カバレッジは「コードの網羅」しか測れないが、本当に知りたいのは「**観点（仕様）の網羅**」であり、
これは仕様側から数えるしかない。素材は既にある——不変条件には
[04_会計ドメイン設計](../04_会計ドメイン設計.md) の **I-nn** という ID が振られ、
電帳法の検索要件（規則・通達の番号）もテストの XML コメントに現れている。
つまり「カタログの ID ↔ それを引くテスト」の対応はほぼ存在していて、**突き合わせだけが人力**である。

そこを機械化する: カタログの全 ID に対しテストソース中の参照を走査し、
**未参照の ID を列挙するメタテスト**を置く。これで「観点リストに載っているのに
テストが 1 本もない」は機械が検出し、残る人力は「**カタログ自体が完全か**」だけに縮む。

- 実装の注意: ID の参照はコメントに書かれるので、走査はテストの**ソーステキスト**に対して行う
  （`lint_docs.py` がコード内の文書参照を突合しているのと同じ発想）
- 制度要件側のカタログ（規則 5 ⑤一ハ・通達 8-13〜8-15 など）は
  [電帳法リサーチ](../research/2026-08-23_電子帳簿保存法.md) から「検証可能な要件」を抜き出して
  ID 化する。フェーズ 2 の完了条件である**優良な電子帳簿のチェックシート対応表**
  （[05 §1](../05_実装計画と現在地.md)）と同じ素材なので、対応表の項目 ID をそのまま使うのが良い

## 6. 計器 4: 構造メタテストと独立オラクル

- **行動テストの書き忘れ検知**: `QueryModuleTests` は全モジュールに自動でかかるが、
  行動テストは帳簿ごとに手書きであり、新しい帳簿を足したときの書き忘れを止める仕組みが無い。
  「`*.Query.sql` 1 本につき対応する行動テストクラスが 1 つ存在する」ことを検査する
  メタテストを置く（`クエリモジュールが一つ以上ある` と同じ、空回り防止の発想）
- **集計系への独立オラクル**: 試算表・税集計のような SQL は、同じ計算を
  `AccountingCore` 側の C# でも実装し、**ランダム生成した仕訳データで両者の一致を突き合わせる**
  （プロパティベーステスト）。固定シードでは踏めない組合せ（複数税区分 × 部門 × 年度またぎ）を
  乱数が踏む。C# 側オラクルはカバレッジと Stryker の傘下に入るので、そこの品質は既存の計器で守れる

## 7. 運用 — qa/03 と計器を接続する

[CLAUDE.md §3-2-1](../../CLAUDE.md) は「qa/03 に 1 件増えたら、機械で守れないかを毎回考える」と
定めている。本計器の導入後は、この問いに標準の答えが 1 つ増える:

> **その壊れ方は、変異演算子の表（§3-1）に写せないか。**

写せたら演算子を足す。演算子表が育つほど計器の感度が上がり、カタログ（qa/03）から
「機械で守れた」として消せる件が増える。

## 8. 実装時の保留

- 演算子表の初期セットの確定（§3-1 の候補を実測で間引く・足す）
- B 案を常設テストにしたときの実行時間の実測（ミュータント数 × コーパス数 × DB 組み直し）
- 等価ミュータント許容リストの置き場所と形式（テストコード内の表か、別ファイルか）
- 集計系オラクルのランダム生成器の設計（プロパティベーステストのライブラリ選定を含む）
