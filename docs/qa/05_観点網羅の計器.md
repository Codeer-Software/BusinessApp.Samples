# 観点網羅の計器（計画）— SQL・DDL テストの強さを測る

> 2026-08-26 に開発者と検討し、**方針**の GO が出た**未実装の計画**である。
> GO の対象は「この 4 つの計器を作る」までで、細部（§8）は未決。
> 実装に着手するセッションは、本書を設計の起点にし、着手時に ADR を起こして
> 判断（なぜミューテーションか・§8 の各項をどう決めたか）をそちらへ移す。

## 1. 問題 — SQL・DDL はテストの強さを測る計器の外にいる

`BusinessApp.Schema.Tests` は、本物の DDL を載せたインメモリ SQLite に本物の SQL を流して
検査する三層構造を持つ。

| 層 | 何を守るか |
|---|---|
| `QueryModuleTests` | クエリモジュールの宣言と SQL の**整合**（全モジュール自動） |
| `JournalBookQueryTests` など行動テスト | 値を入れて行数を数え、**条件が効くこと**（帳簿ごとに手書き） |
| `SchemaConstraintTests` など制約テスト | CHECK・UNIQUE・外部キー・トリガによる**不変条件** |

問題は、この層に**テストの強さを測る計器が無い**ことである。
会計コアの C# 2 プロジェクト（`AccountingCore`・同 `.Server`）はカバレッジ 100% と
Stryker（[ADR-0012](../decisions/0012-テスト方針とカバレッジのゲート.md) §8）が
「テストされていないロジック」を機械で炙り出すが、Stryker が変異させるのは
C# のソース（Roslyn 構文木）だけで、**別ファイルにある SQL・DDL の制約・トリガはその外**にある。
そこの観点の漏れは人の注意力だけが頼りで、実際に起きかけた——
仕訳帳の法定検索は「宣言と SQL の整合」しか検査されておらず、`>=` と `>` の取り違えも
空値検索の分岐名の綴り違いも**例外にならず静かに 0 件を返す**状態だったことが、
レビューで見つかっている（[qa/02](02_自己レビュー記録.md) ラウンド 4。
その場で `JournalBookQueryTests` を足して塞いだ）。日付を文字列で比べて検査が常に外れていた
実例もある（[qa/03](03_テストで漏らした実例.md) L-12）。

本書は「観点を網羅できているか」を 2 つの別の問いに分けて捉える（この分解が本書の判断の核である）。

| 問い | 計器 |
|---|---|
| 書いたテストは、SQL・DDL の壊れ方を**検出できる強さ**があるか | SQL ミューテーション（§3）・制約ノックアウト（§4） |
| そもそも**観点リストの項目が全部テストになっている**か | ID トレーサビリティ（§5）・構造メタテスト（§6） |

## 2. 結論 — 4 つの計器を作る

着手順は次を目安とする（確定は着手時）。

| 順 | 計器 | 概要 | 重さ（見積り） |
|---|---|---|---|
| 1 | **制約ノックアウト**（§4） | DDL から制約・トリガを 1 つずつ外し、スキーマテストが赤になることを確認する | 小 |
| 2 | **ID トレーサビリティ**（§5） | 不変条件 I-nn・制度要件の ID とテストの参照を突き合わせ、未参照 ID を列挙する | 小 |
| 3 | **SQL ミューテーション B 案**（§3-2） | SQL に機械変異を入れ、テストの入力コーパスで原本と行セットを差分比較する | 中 |
| 4 | **構造メタテスト・独立オラクル**（§6） | 行動テストの書き忘れ検知と、集計 SQL の C# 独立実装との突き合わせ | 中 |
| 随時 | **SQL ミューテーション A 案**（§3-3） | 実テストスイートをミュータントに対して回す | 大 |

制約ノックアウトと ID トレーサビリティを先頭に置くのは、実装が小さい見込みで、
入れた日から既存テストの穴を報告し始めるからである。SQL ミューテーションは
設計判断（演算子表・コーパスの形・§8 の未決）を含むので、本書 §3 に従って後に置く。
独立オラクルは集計系 SQL（フェーズ 3 以降。[05 §3](../05_実装計画と現在地.md)）が増える前に土台だけ作る。

## 3. SQL ミューテーションテスト（自作ミニ Stryker）

Stryker が SQL に効かないのは変異対象が C# ソースだけだからであり、
ミューテーションテストという**手法**は SQL にも適用できると判断した。
根拠: SQL は `File.ReadAllText` で読むただのテキストなので、変異の注入点が既にある。

### 3-1. ミュータントの生成（A 案・B 案で共通）

1. 原本の SQL を読む
2. **変異演算子ごとに出現箇所を列挙**する（正規表現または簡易トークン走査）
3. **1 変異点 = 1 ミュータント**。出現位置を 1 つだけ置換した SQL 文字列を作る
   （同時に 1 箇所しか変えないのがミューテーションテストの原則）

変異演算子の表は汎用セットではなく、**このリポジトリで実際に起きた・起きかけた壊れ方の記録**
（[qa/03](03_テストで漏らした実例.md) と [qa/02](02_自己レビュー記録.md) のレビュー記録）から起こす。
初期セットの候補（確定は実装時）:

| 演算子 | 由来 |
|---|---|
| `>=` → `>`、`<=` → `<` | 境界の取り違え（qa/02 ラウンド 4 がレビューで特定した危険） |
| `date(x)` → `(x)` | 日付を文字列で比較して検査が外れた実例（qa/03 L-12） |
| CASE 分岐の候補値文字列の 1 文字置換 | 空値検索の分岐名の綴り違い（qa/02 ラウンド 4。候補と宣言の静的な整合は `QueryModuleTests` が守済みだが、SQL 内の分岐名のずれは実行しないと出ない） |
| `AND` → `OR` | 条件の合成ミス |
| `LEFT JOIN` → `INNER JOIN` | 任意項目の行落ち |
| `IS NULL` → `IS NOT NULL` | NULL 分岐の反転 |
| `COALESCE(a, b)` → `(b)` | 写し（スナップショット）優先の崩れ |
| `DISTINCT` の削除、`ORDER BY` の列を 1 つ削る | 重複・並び順 |

注意: 正規表現ベースの置換は **SQL コメントと文字列リテラルの中にも当たる**。
コメント由来の等価ミュータントを減らすため、変異点の列挙前にコメントを除外する。
「文字列リテラルとコメントをスキップするだけの簡易走査」で足りると見込むが、
SQLite には二重引用符の識別子引用などの例外があるため、**実装時に既存の全 SQL ファイルで
走査結果を目視で裏取りする**（§8）。

### 3-2. B 案 — 行セットの差分比較（常設候補・上界の測定）

**判定**: シード済みインメモリ DB に対し、テストが使う入力コーパスを
**原本 SQL とミュータント SQL の両方に流し、全行セットを比較**する。

- どれかの入力で結果が違う → 殺せた（今の入力群で検出可能）
- **全入力で完全一致 → 生存**。「この壊れ方は今のテストデータ・入力では原理的に見分けられない」
  ことの証明なので、シード行かパラメータの組を足す
- 変異の結果 SQL が構文エラーになったものは集計から除外する
  （`QueryModuleTests` が全 SQL を実行するので、実物がそう壊れれば検出される）

**入力コーパスの定義が肝**である。SQL の出力を決めるのは **(DB の状態, パラメータの組)** の
ペアなので、コーパスの 1 エントリもこのペアにする。インメモリ SQLite の作り直しは
十分速い見込みなので（実測は §8）、エントリごとに「シード → ARRANGE SQL → 両者を流して比較」を
やり直す設計とする。

成立条件が 1 つある。

> **テストの入力（DB 状態の作り方＋パラメータ）が、データとして列挙できる形になっていること。**

現行の `JournalBookQueryTests` は ARRANGE を SQL 文字列（`Create(beforePosting)`）で受けており、
既にこの形をしている。計器を成立させるにはこの形を保つ必要がある
（規約として明文化するかは着手時の ADR で決める）。実装時にやること:

- コーパスの表を 1 箇所に定義し、**行動テストとミューテーションハーネスの両方が同じ表を読む**
  （`[MemberData]` の供給元を共有する）。写し漏れ・ドリフトを構造的に消すため
- `Create` の後に追加で `Execute` している行動テスト（並び順の検査など）は、
  ARRANGE を `beforePosting` 側へ寄せてコーパス化できる形に直す必要が出る
- 生存ミュータントには**等価ミュータント**（挙動が本当に変わらないもの）が混ざる
  （C# 側 Stryker の初回実績でも「許容してよいノイズ」が出た。ADR-0012 §8）。
  人が仕分ける前提で、**仕分け結果の持ち方は未決**である——ADR-0012 §8 は Stryker に
  **ラチェット下限**方式を採り、同 §4 は「許容リストは必ず腐るので、持たなくてよい設計を選ぶ」を
  原則にしている。SQL 側を許容リスト方式にするならこの原則との折り合いの理由が要る。
  着手時の ADR で決める（§8）
- 実行時間が許せば（実測は §8）通常のテストとして常設し、コミット前フックの傘下に入れる

**限界も記録しておく**: B 案は「どの入力で違いが出うるか」しか見ず、
**テストがどの列をアサートしているか**は見ない。つまり測るのはテストの強さの**上界**である。
正確な測定は A 案で行う。

### 3-3. A 案 — 実テストスイートで殺す

SQL の読込を 1 箇所（`TestSupport` の読込ヘルパ）に集約して行動テストがそれを使う形に直し、
そのヘルパが環境変数（例 `SQL_MUTATION=<ファイル>:<位置>:<置換前>:<置換後>`）を解釈して
変異を当てる。ドライバスクリプトがミュータントごとに `dotnet test --filter` を子プロセスで回して
**赤になること**を確認する。実際のアサーションで殺せるかを測るので正確だが、実行時間は長い。

実行タイミング（コミット前フックに載せるか・区切りごとの手動か）は**実測してから着手時に決める**。
ADR-0012 §8 の Stryker も、当初「フェーズの区切りで」としたものを実測の速さを見て
開発者の判断で毎回実行へ変えた前例がある。

### 3-4. A 案と B 案の関係

生成（§3-1）は共通で、**違いは殺し方の判定だけ**である。
B 案で入力の穴を見張り、区切りで A 案を回して答え合わせする、という補完関係を想定している
（B 案をどの頻度で回せるかは §8 の実測次第）。

## 4. 制約ノックアウトテスト

DDL の制約・トリガを **1 つずつ外した**スキーマでテスト群を流して「赤になること」を確認する。
全部緑のまま生き残った制約は、**誰もテストしていない制約**である。

- 計上済み仕訳の不変性（[CLAUDE.md §2](../../CLAUDE.md)）を守るトリガが本当にテストで
  見張られているかを、これで機械的に言えるようになる
- 外し方は対象によって 2 通りに分かれる:
  - **トリガとインデックス**（二重取消・二重訂正を止める部分一意インデックス
    `ux_journal_entries_single_reversal` などを含む）は `DROP` で外せる
  - **`CREATE TABLE` の中にある CHECK・表内 UNIQUE・外部キー**は DROP できないので、
    DDL テキストから該当箇所を除いた変異版で DB を組み直す（§3-1 と同じテキスト変異の考え方）。
    `sqlite_master` に独立した行を持つのはトリガとインデックスだけなので、
    表内の制約の**列挙**にも DDL テキストの解析が要る。その実装方式は着手時に検証する（§8）
- 生存の扱い（テストを足すか、理由つきで許容するか）は §3-2 の未決と同じ枠で決める

## 5. ID トレーサビリティのメタテスト

カバレッジは「コードの網羅」しか測れないが、本当に知りたいのは「**観点（仕様）の網羅**」であり、
これは仕様側から数えるしかない。素材は既にある——不変条件には
[04_会計ドメイン設計](../04_会計ドメイン設計.md) の **I-nn** という ID が振られ、
電帳法の検索要件（規則・通達の番号）もテストの XML コメントに現れている。
一方向の機械突合も一部ある（`JournalViolationCodesTests` がコードの使う I-nn を
docs/04 の表と突き合わせている）が、**「カタログ側から見て未参照の ID を列挙する」逆方向が無い**。

そこを作る: カタログの全 ID に対しテストソース中の参照を走査し、
**未参照の ID を列挙するメタテスト**を置く。これで「観点リストに載っているのに
テストが 1 本もない」は機械が検出し、残る人力は「**カタログ自体が完全か**」だけに縮む。

- 実装の注意: ID の参照はコメントに書かれるので、走査はテストの**ソーステキスト**に対して行う
  （`lint_docs.py` がコード内の文書参照を突合しているのと同じ発想）
- 制度要件側の ID には**規則・通達の条番号を使わない**。優良な電子帳簿の要件は
  2027-01-01 に規則 5⑤ から 5④ へ移動し、国税庁の現行資料は既に改正後番号で書かれている
  （番号の出典と確認日は[電帳法リサーチ](../research/2026-08-23_電子帳簿保存法.md) §0・§14-2 に依る）。
  条番号を ID にすると施行日を境に実務資料と食い違う。**優良な電子帳簿のチェックシート対応表**
  （[40](../40_優良な電子帳簿の対応表.md) の A1〜G2）の**項目 ID を正**とする
- カタログ化する検索要件はひととおり揃える——範囲指定（通達 8-15）だけでなく
  **組合せ検索（通達 8-16）**・空値検索（通達 8-13）・記録項目（通達 8-14）まで。
  なおテストコメントの既存の引用には誤りが見つかっている（§8）

## 6. 構造メタテストと独立オラクル

- **行動テストの書き忘れ検知**: `QueryModuleTests` は全モジュールに自動でかかるが、
  行動テストは帳簿ごとに手書きであり、新しい帳簿を足したときの書き忘れを止める仕組みが無い。
  「`*.Query.sql` 1 本につき対応する行動テストクラスが 1 つ存在する」ことを検査する
  メタテストを置く（`クエリモジュールが一つ以上ある` と同じ、空回り防止の発想）
- **集計系への独立オラクル**: 試算表・税集計のような SQL は、同じ計算を
  `AccountingCore` 側の C# でも実装し、**ランダム生成した仕訳データで両者の一致を突き合わせる**
  （プロパティベーステスト）。固定シードでは踏みにくい組合せ（複数税区分 × 部門 × 年度またぎ）を
  乱数が踏みやすくする。C# 側オラクルはカバレッジと Stryker の傘下に入るので、
  そこの品質は既存の計器で守れる

## 7. 運用 — qa/03 と計器を接続する

**`self-review` スキル §8** は「qa/03 に 1 件増えたら、機械で守れないかを毎回考える」と
定めている。本計器の導入後は、この問いに標準の答えが 1 つ増える:

> **その壊れ方は、変異演算子の表（§3-1）に写せないか。**

写せたら演算子を足す。演算子表が育つほど計器の感度が上がり、カタログ（qa/03）から
「機械で守れた」として消せる件が増える。

## 8. 実装時の保留（着手時の ADR で決める・検証する）

- 演算子表の初期セットの確定（§3-1 の候補を実測で間引く・足す）
- コメント・文字列リテラルを除外する簡易走査の十分性（既存の全 SQL ファイルで目視の裏取り）
- B 案の実行時間の実測（ミュータント数 × コーパス数 × DB 組み直し）と、
  常設（コミット前フック搭載）にできるかの判断
- A 案の実行タイミング（フック搭載か・区切りごとの手動か）
- 生存ミュータントの仕分け結果の持ち方——ADR-0012 §8 のラチェット下限方式に揃えるか、
  許容リスト方式にするか（後者なら同 §4「許容リストは必ず腐る」との折り合いの理由を書く）
- 表内制約（CHECK・表内 UNIQUE・外部キー）を DDL テキストから列挙・除去する実装方式
- 集計系オラクルのランダム生成器の設計（プロパティベーステストのライブラリ選定を含む）
- テストコメントの誤参照の修正——`JournalBookQueryTests` の
  「qa/03 L-03 の型」（L-03 は観測の切り分けの話で、静かな 0 件の型ではない）と
  「組み合わせ（…通達 8-15）」（組合せ検索は 8-16）
