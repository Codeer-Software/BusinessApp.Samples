# 観点網羅の計器（計画）— SQL・DDL テストの強さを測る

> 実装に着手するセッションは、本書を設計の起点にし、着手時に ADR を起こして
> 判断（なぜミューテーションか・§8 の各項をどう決めたか）をそちらへ移す。

> 仕組みは `tools/clb/sql_mutate.py` と `tools/clb/sql_sweep.ps1`（`-Mode Tests|Rows`）、
> B 案の観測は `BusinessApp.TestSupport` の `SqlMutationProbe`。

## 1. 問題 — SQL・DDL はテストの強さを測る計器の外にいる

`BusinessApp.Schema.Tests` は、本物の DDL を載せたインメモリ SQLite に本物の SQL を流して
検査する三層構造を持つ。

| 層 | 何を守るか |
|---|---|
| `QueryModuleTests` | クエリモジュールの宣言と SQL の**整合**（全モジュール自動） |
| `JournalBookQueryTests` など行動テスト | 行を入れて読み戻し、**返った行を名指しで突き合わせる**（帳簿ごとに手書き） |
| `SchemaConstraintTests` など制約テスト | CHECK・UNIQUE・外部キー・トリガによる**不変条件** |

問題は、この層に**テストの強さを測る計器が無い**ことである。
カバレッジ 100% と Stryker（[ADR-0012 §8](../decisions/0012-テスト方針とカバレッジのゲート.md)）が
「テストされていないロジック」を機械で炙り出すが、**Stryker が変異させるのは C# のソースだけ**で、
**別ファイルにある SQL・DDL の制約・トリガはその外**にある。
そこの漏れは人の注意力だけが頼りで、実際に起きかけた——`>=` と `>` の取り違えも
空値検索の分岐名の綴り違いも**例外にならず静かに 0 件を返す**（[qa/02](02_自己レビュー記録/2026-08.md) ラウンド 4）。
日付を文字列で比べて検査が常に外れていた実例もある（[qa/03](03_テストで漏らした実例.md) L-12）。

本書は「観点を網羅できているか」を 2 つの別の問いに分けて捉える（この分解が本書の判断の核である）。

| 問い | 計器 |
|---|---|
| 書いたテストは、SQL・DDL の壊れ方を**検出できる強さ**があるか | SQL ミューテーション（§3）・制約ノックアウト（§4） |
| そもそも**観点リストの項目が全部テストになっている**か | ID トレーサビリティ（§5）・構造メタテスト（§6） |

## 2. 結論 — 4 つの計器を作る

| 順 | 計器 | 状態 | 概要 | 重さ（見積り） |
|---|---|---|---|---|
| 1 | **制約ノックアウト**（§4） | **済**（2026-09-13） | DDL から制約・トリガを 1 つずつ外し、スキーマテストが赤になることを確認する | 小 |
| 2 | **ID トレーサビリティ**（§5） | **済**（2026-09-14。不変条件・制度要件とも） | 不変条件 I-nn・制度要件の ID とテストの参照を突き合わせ、未参照 ID を列挙する | 小 |
| 3 | **SQL ミューテーション B 案**（§3-2） | **済**（2026-09-15。[ADR-0058](../decisions/0058-行セットの差分で殺す掃引は入力コーパスを持たず行動テストが流した入力をその場で当てる.md)） | SQL に機械変異を入れ、**行動テストが流した入力**で原本と行セットを差分比較する | 中 |
| 4 | **構造メタテスト・独立オラクル**（§6） | **書き忘れ検知は済**（2026-09-14。[ADR-0055](../decisions/0055-クエリモジュールには行を入れて読み戻すテストを必ず置く.md)）。独立オラクルは未着手 | 行動テストの書き忘れ検知と、集計 SQL の C# 独立実装との突き合わせ | 中 |
| 随時 | **SQL ミューテーション A 案**（§3-3） | **済**（2026-09-14。[ADR-0056](../decisions/0056-SQLミューテーションはクエリのSQLを1箇所ずつ壊し行動テストだけで赤になるかを見る.md)） | 実テストスイートをミュータントに対して回す | 大 |

**どれも入れた日から既存テストの穴を報告し始めた。**
**残るのは独立オラクルだけ**である
（集計系 SQL が増える前に土台だけ作る。フェーズ 3 以降。[04 §3](../04_実装計画と現在地.md)）。

## 3. SQL ミューテーションテスト（自作ミニ Stryker）

Stryker が SQL に効かないのは変異対象が C# ソースだけだからであり、
ミューテーションテストという**手法**は SQL にも適用できると判断した。
根拠: SQL は `File.ReadAllText` で読むただのテキストなので、変異の注入点が既にある。

### 3-1. ミュータントの生成（A 案・B 案で共通）

**1 変異点 = 1 ミュータント**。出現位置を 1 つだけ置換する
（同時に 1 箇所しか変えないのがミューテーションテストの原則）。
**手順と実装は [ADR-0056](../decisions/0056-SQLミューテーションはクエリのSQLを1箇所ずつ壊し行動テストだけで赤になるかを見る.md)
と `tools/clb/sql_mutate.py`** が持つ。

変異演算子の表は汎用セットではなく、**このリポジトリで実際に起きた・起きかけた壊れ方の記録**
（[qa/03](03_テストで漏らした実例.md) と [qa/02](02_自己レビュー記録.md) のレビュー記録）から起こす。
**A 案で採った 12 個の正典は `sql_mutate.py` の `OPERATORS`**。候補として挙げていたもの:

| 演算子 | 由来 |
|---|---|
| `>=` → `>`、`<=` → `<` | 境界の取り違え（qa/02 ラウンド 4 がレビューで特定した危険） |
| `date(x)` → `(x)` | 日付を文字列で比較して検査が外れた実例（qa/03 L-12） |
| CASE 分岐の候補値文字列の 1 文字置換（**採っていない**） | 空値検索の分岐名の綴り違い（qa/02 ラウンド 4）。**文字列リテラルの中を書き換える変異なので、伏せ字（下）と両立しない**——別の当て方が要る |
| `AND` → `OR` | 条件の合成ミス |
| `LEFT JOIN` → `INNER JOIN` | 任意項目の行落ち |
| `IS NULL` → `IS NOT NULL` | NULL 分岐の反転 |
| `COALESCE(a, b)` → `(b)` | 写し（スナップショット）優先の崩れ |
| `DISTINCT` の削除、`ORDER BY` の列を 1 つ削る | 重複・並び順 |

注意: 正規表現ベースの置換は **SQL コメントと文字列リテラルの中にも当たる**。
**当てると等価ミュータントばかり増えて、生き残りの数が意味を失う**ので、列挙の前に伏せる。
**伏せ方と裏取りの結果は [ADR-0056 決定 2](../decisions/0056-SQLミューテーションはクエリのSQLを1箇所ずつ壊し行動テストだけで赤になるかを見る.md)**、
**実装は `tools/clb/sql_mutate.py`**（`selftest` が守る）が持つ。

### 3-2. B 案 — 行セットの差分比較——**2026-09-15 に入った**

**判定と実測は
[ADR-0058](../decisions/0058-行セットの差分で殺す掃引は入力コーパスを持たず行動テストが流した入力をその場で当てる.md) が持つ**
（入力の取り方・注入と報告の渡し方・行セットの畳み方・壊れた点の扱い・生き残りと入力の数の持ち方・
計器そのものの守り・フックに載せるか）。
**仕組みの正典はコードである**——観測は `BusinessApp.TestSupport` の `SqlMutationProbe`、
掃引は `tools/clb/sql_sweep.ps1 -Mode Rows`、計器そのものの検査は `SqlMutationProbeTests`。

**入力コーパスを別に持たない。** **行動テストが流したその瞬間に、その接続とその引数で当てる**——
**コーパスは定義されるのではなく観測される**ので、写しが生まれない（ADR-0058 決定 1。
表を持つ形を採らなかった理由もそちらが持つ）。

**限界が 2 つある。**

1. B 案は「どの入力で違いが出うるか」しか見ず、**テストがどの列をアサートしているか**は見ない。
   つまり測るのはテストの強さの**上界**である。正確な測定は A 案で行う
2. **`ORDER BY` が全順序でない SQL では使えない。** 行セットは行の並びまで畳み込むので、
   **同着の行の順が実行計画の違いで入れ替わるだけでも「見分けた」に数える**
   ——**見えない点が減る向き**なので、上限だけでは気づけない。
   **`ORDER BY` を触る回は、最後まで並べたときに一意になることを確かめる**
   （いまの 4 本のうち 2 本は主キーで閉じており、残る 2 本は
   「会計年度の開始日が重複しない」前提に乗っている。ADR-0058 の帰結と [04 §5](../04_実装計画と現在地.md) の保留）

### 3-3. A 案 — 実テストスイートで殺す——**2026-09-14 に入った**

**決定と実測は
[ADR-0056](../decisions/0056-SQLミューテーションはクエリのSQLを1箇所ずつ壊し行動テストだけで赤になるかを見る.md) が持つ**
（対象・変異点の数え方・注入の仕方・回す先・判定・生き残りの持ち方・実行のタイミング）。
**仕組みの正典はコードである**——変異点は `tools/clb/sql_mutate.py`、掃引は `tools/clb/sql_sweep.ps1`、
注入は `TestDatabase.QuerySql`、計器そのものの検査は `SqlMutationTests`。

### 3-4. A 案と B 案の関係

生成（§3-1）は共通で、**違いは殺し方の判定だけ**である。駆動役も 1 本
（`sql_sweep.ps1 -Mode Tests|Rows`）——**母数の下限もモジュールの数え方も写しを作らない**。
**A 案が測るのは「実際のアサーションで殺せるか」**、B 案が測るのは**上界**。

**B 案の生き残りは、A 案の生き残りの部分集合である**——
**行が 1 行も変わらないなら、どのアサーションも気づけない**から。
**2 つの差がそのまま「見えているのに誰も見ていない」＝アサーションの穴**で、
**直し方も違う**（B 案の生き残りは検体かパラメータを足して潰し、差のほうは表明を足して潰す）。

**2026-09-15 の実測では、差は 0 だった**——**両案が 1 点の違いもなく同じ生き残りを返した**
（数と所要は [ADR-0058](../decisions/0058-行セットの差分で殺す掃引は入力コーパスを持たず行動テストが流した入力をその場で当てる.md) の実測。
**ここには写さない**）。**B 案のほうが桁で速い**ので、**ふだんは B 案を流し、区切りで A 案を回して差を見る。**

## 4. 制約ノックアウトテスト——**2026-09-13 に入った**

DDL の制約・トリガを **1 つずつ外した**スキーマでテスト群を流して「赤になること」を確認する。
全部緑のまま生き残った制約は、**誰もテストしていない制約**である。
計上済み仕訳の不変性（[CLAUDE.md §2](../../CLAUDE.md)）を守るトリガが本当にテストで
見張られているかを、これで機械的に言えるようになった。

**決定と実測は [ADR-0053](../decisions/0053-制約ノックアウトはDDLを1つずつ外し振る舞いのテストだけで赤になるかを見る.md) が持つ**
（外す単位・殺し手に数えるテスト・回す先・注入の仕方・生き残りの持ち方・実行のタイミング）。
**仕組みの正典はコードである**——`BusinessApp.TestSupport` の `SchemaKnockout`、
掃引は `tools/clb/knockout.ps1`、計器そのものの検査は `SchemaKnockoutTests`。

## 5. ID トレーサビリティのメタテスト——**2026-09-14 に、不変条件・制度要件とも入った**

カバレッジは「コードの網羅」しか測れないが、本当に知りたいのは「**観点（仕様）の網羅**」であり、
これは仕様側から数えるしかない。**カタログの全 ID に対しテストのソース中の参照を走査し、
未参照の ID を列挙する。** これで「観点リストに載っているのにテストが 1 本もない」は機械が検出し、
残る人力は「**カタログ自体が完全か**」と「**触れているテストが中身を見ているか**」に縮む。

**不変条件（I-nn）の側の決定と実測は
[ADR-0054](../decisions/0054-不変条件のIDはカタログの側から数えテストが触れていないものを報告する.md) が持つ。**
**仕組みの正典はコードである**——`InvariantTraceabilityConvention` と `InvariantTraceabilityTests`。

**制度要件の側（[40](../40_優良な電子帳簿の対応表.md) の A1〜G2）も 2026-09-14 に入った。**
**判断と実測は [ADR-0057](../decisions/0057-制度要件は済と書いた項目だけを参照必須にし条番号ではなく項目IDで引く.md) が持つ。**
**仕組みの正典はコードである**——`RequirementTraceabilityConvention` と `RequirementTraceabilityTests`。

- **条番号を ID にしない。** 優良な電子帳簿の要件は 2027-01-01 に電帳規則 5⑤ から 5④ へ移動し、
  国税庁の現行資料は既に改正後番号で書かれている <!-- lint-docs:switch-ok 改番の事実 -->
  （出典と確認日は[電帳法リサーチ](../research/2026-08-23_電子帳簿保存法.md) §0・§14-2）。
  **施行日を境に実務資料と食い違う**ので、[40](../40_優良な電子帳簿の対応表.md) の**項目 ID を正**とする
- カタログ化した検索要件は、範囲指定（電帳通達 8-15）・**組合せ検索（電帳通達 8-16）**・
  空値検索（電帳通達 8-13）・記録項目（電帳通達 8-14）である。
  **テストコメントの通達番号の取り違えは 2026-09-14 に直した**（§8 から消した）
- **項目 ID の表は節ごとに分かれ、プライム付き・1 列目が空の継続行がある**——行の拾い方は検体で固定した（ADR-0057 の決定 6）

## 6. 構造メタテストと独立オラクル

- **行動テストの書き忘れ検知**——**2026-09-14 に入った**（`QueryBehaviorCoverageTests`。
  判断と実測は [ADR-0055](../decisions/0055-クエリモジュールには行を入れて読み戻すテストを必ず置く.md) が持つ）。
  **入れた日に 1 本の穴を報告した**（`PartnerRegistrationList`）。
  **測れるのは「クラスがあるか」まで**で、中身が薄いテストは見えない——
  **書いた行動テストの十分性は、SQL を 1 箇所ずつ壊して確かめた**（§3 の自動化は同じ日に入った）
- **集計系への独立オラクル**: 試算表・税集計のような SQL は、同じ計算を
  `AccountingCore` 側の C# でも実装し、**ランダム生成した仕訳データで両者の一致を突き合わせる**
  （プロパティベーステスト）。固定シードでは踏みにくい組合せ（複数税区分 × 部門 × 年度またぎ）を
  乱数が踏みやすくする。C# 側オラクルはカバレッジと Stryker の傘下に入るので、
  そこの品質は既存の計器で守れる

## 7. 運用 — qa/03 と計器を接続する

**`self-review` スキル §8** は「qa/03 に 1 件増えたら、機械で守れないかを毎回考える」と
定めている。**SQL ミューテーション（§3。2026-09-14 に A 案が入った）の側の答えはこうである**:

> **その壊れ方は、変異演算子の表（§3-1）に写せないか。**

写せたら演算子を足す（正典は `tools/clb/sql_mutate.py` の `OPERATORS`）。
演算子表が育つほど計器の感度が上がり、カタログ（qa/03）から「機械で守れた」として消せる件が増える。

**制約ノックアウト（§4。実装済み）の側の答えはこうである**——
**その壊れ方は、DDL の制約 1 本に対応するか。** 対応するなら、**外して赤くなるテストを書く**
（`knockout.ps1 -Only <点>` で確かめる）。対応しないなら、この計器では捕まらない。

## 8. 実装時の保留（着手時の ADR で決める・検証する）

**決まった分はここから消してある。** 制約ノックアウトは 2026-09-13 に
[ADR-0053](../decisions/0053-制約ノックアウトはDDLを1つずつ外し振る舞いのテストだけで赤になるかを見る.md)、
SQL ミューテーションの A 案は 2026-09-14 に
[ADR-0056](../decisions/0056-SQLミューテーションはクエリのSQLを1箇所ずつ壊し行動テストだけで赤になるかを見る.md)、
**B 案は 2026-09-15 に
[ADR-0058](../decisions/0058-行セットの差分で殺す掃引は入力コーパスを持たず行動テストが流した入力をその場で当てる.md)**
で決まった。**B 案の回に預けていたもののうち、閉じたのは 3 件**である——
**等価ミュータントの持ち方**（本数の上限で持つ。同 決定 6）、
**等価と証明できる生き残りを生成の段階で外すか**（外さない。同 実測）、
**殺し手として数えないテストの番人**（除外表を作らず、字面を読むこと自体を禁じる。同 決定 8）。
**実行時間は実測できたが、常設の可否は閉じていない**——**開発者の答え待ちである**（下）。

**残っているのは下の 4 件**である。

- **演算子表を広げる前に、A 案の設計を決める**（2026-09-15 に論点が動いた）。
  **候補表に「同じ型の列どうしの置換」が要る**——
  **SELECT 句の列の取り違えだけが、`QueryModuleTests` と行動テストの両方を素通りできる形**なのに、
  **いまの 12 演算子は 276 点中 21 点しか `FROM` より前に立っていない**（ADR-0056 の実測）。
  **ところがこの演算子は列参照の数だけ点を立てるので、点の数が数倍になる**——
  **B 案は秒で吸収するが、A 案は 1 点 1 秒強なので持たない**（ADR-0058 の帰結）。
  **`-Mode Tests` を全点掃引のままにするか標本に落とすかが先**である。
  **演算子表に無い形は、ほかに 2 つ見えている**——**連言の削除**と **`IN` のリテラル操作**
  （どちらも掃引が構造的に報告できない穴で、見つけたのは人である）。
  **フェーズ 3 で最初のクエリモジュールを足す回に、3 つまとめて決める**
  （税区分別集計表。[04 §3](../04_実装計画と現在地.md)。**新しい SQL が入る回が、演算子表を読み直す回である**）
- **DDL の中の演算子を誰が見張るか**（[ADR-0056 決定 1](../decisions/0056-SQLミューテーションはクエリのSQLを1箇所ずつ壊し行動テストだけで赤になるかを見る.md) が送った保留）。
  **制約ノックアウトは制約を 1 本まるごと外す形しか見ない**ので、
  **`CHECK` の中の `>=` を `>` にするような歪めは 2 つの計器のあいだに落ちている**。
  **2026-09-14 に、この隙間に落ちる不具合を実際に作り込んだ**（[L-48](03_テストで漏らした実例.md)。
  トリガの `WHEN` 節の `> 4 * LENGTH(x)` が緩く、見つけたのは自己レビューで計器ではない）。
  **B 案の仕組みは使えない**——**DDL は行を返さないので、行セットで殺す判定が成り立たない**
  （ADR-0058 の帰結）。**つまり A 案の形になるので、制約ノックアウトの延長として設計するのが筋**である。
  **制約・トリガをまとめて次に触る回に決める**
- **掃引をコミット前フックに載せるか**（2026-09-15。**開発者の答え待ち**——[05 の Q-27](../05_開発者への問い.md)）。
  **実測は済んだ**（`-Mode Rows` は端から端まで 7.4 秒。ADR-0058 の実測）が、
  **載せるかは ADR-0056 決定 7 が「開発者に諮る」と約束している**
