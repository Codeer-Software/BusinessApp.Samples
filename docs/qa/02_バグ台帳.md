  - `s.AddLessThanOrEqual(e => e.EntryDate.Value, EndDate.Value);`
- **症状**: SQLite の日付比較は**文字列比較**なのに、DATE 宣言の列に時刻成分が混入している。**実測（2026-08-17）**: `fiscal_years` は seed 由来の第17期 `'2025-04-01'`・第18期 `'2026-04-01'` が**時刻なし**、画面から作られた第19期だけ `'2027-04-01 00:00:00'` と**時刻あり**。伝票側は画面経由なので `invoices.issue_date` / `sales_orders.order_date` / `acceptances.acceptance_date` / `journal_entries.entry_date` がいずれも `'YYYY-MM-DD 00:00:00'`。
  この非対称のため `'2026-08-31 00:00:00' <= '2026-08-31'` が**偽**になり、**期間の端の伝票が範囲から丸ごと落ちる**。`FiscalPeriod` の締めチェックで落ちると、**未確定伝票が残ったまま期間を締められる**（統制の穴）
- **再現**: 未調査（第19期を対象にした期間解決・締めチェックで再現するはず。DB を汚さないため実行していない）
- **判定**: 台帳止め（**根本対処は「DATE 列から時刻成分を落とす」データ移行＋入力側の正規化**でデータモデルに触る。個別箇所に回避策を足すのは、既に下記のとおり同じ回避が散在しており事態を悪化させる）
- **影響範囲**: `FiscalPeriod`（締めチェック）/ `FiscalYear`（年度解決）/ 期間解決を行う全モジュール。**同型の `ModuleSearcher` 日付比較は 20 ファイル・約 35 箇所**に及ぶ（CashBook / CashEntry / JournalBook / JournalEntry / JournalLineDepartment / JournalTemplate / BankPosting / BankStatementLine / ExpenseRequest / Acceptance / Invoice / Receipt / RecurringRun / SesBilling / FixedAsset ほか）
- **備考**: 重要な補足が 3 つ。

  2. **開発チームは既にこの罠を踏んで局所回避している**。`Sales/Receipt.mod.cs:347` に「境界日知見: **月末日は辞書順比較で失敗するため月初日で解決**」というコメント付きの回避策が実在する（`FixedAsset.mod.cs:231` も同型）。**回避策が散在していること自体が、根本未対処の証拠**
  3. `date('now')` の UTC 罠は**該当なし**。全 30 箇所が `date('now','localtime')` / `strftime(...,'now','localtime')` で JST 補正済み（素の `date('now')` はコメント行 1 箇所のみ）
