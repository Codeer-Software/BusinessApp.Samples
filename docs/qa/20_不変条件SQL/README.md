# 不変条件 SQL（会計整合性の実行可能アサーション集）

> 作成: 2026-08-17 ／ 更新: 2026-08-17（A11 の対象範囲を売上高区分に是正、NULL 比較・行番号一意性の穴を 5 本で修正）
> 対象 DB: `LocalData/db/business-app_v1.db`（データソース `BusinessAppSQLite`）
> 正典: `docs/04_会計ドメイン設計.md`（何が成り立つべきか）・`docs/decisions/`（個別の判断）

## 0. なぜこれがあるのか

近日中に **「経費申請の明細行化」** と **「資金繰り予測の拡充＋借入金管理の新設」** という大改修が入る。

**改修のあとで不整合を見つけても、「元からそうだったのか、改修で壊れたのか」は判別できない。**
基準は変更の前にしか取れない。だから改修前のいま、いまの DB で何が成立していて何が成立していないかを
実行可能な形で固定した。改修後に `run_all.ps1` を流し、§3 の基準値と突き合わせれば、
**増えた違反＝改修が壊したもの**として即座に切り分けられる。

## 1. 使い方

```powershell
# 全部流す（違反があるものだけ最後にまとめて報告する）
pwsh -File docs/qa/20_不変条件SQL/run_all.ps1

# 一部だけ・違反行の中身も見る
pwsh -File docs/qa/20_不変条件SQL/run_all.ps1 -Only 'C*' -ShowRows

# デザイナ exe を明示（既定は Designer/LocalEnvironment.md の DesignerExePath: から読む）
pwsh -File docs/qa/20_不変条件SQL/run_all.ps1 -DesignerExe 'C:\path\to\BusinessApp.Designer.exe'
```

- 終了コード: `0` 全件合格 ／ `1` 違反あり ／ `2` 実行エラーあり
- 結果 JSON は既定で一時フォルダに出る（`-OutDir` で変更可。リポジトリには残さない）
- **読み取り専用**。ここに置く SQL は `SELECT` のみ。DB を書き換えるチェックは置かない
- サーバ起動もデプロイも不要。DB を直接見るだけなので数十秒で終わる

単発で 1 本だけ流したいときは sql CLI を直接叩く:

```powershell
& "<デザイナexe>" sql "<repo>\Designer\Design" --datasource BusinessAppSQLite `
  --file "<repo>\docs\qa\20_不変条件SQL\A01_仕訳_伝票ごとの貸借一致.sql" --out "<一時フォルダ>\a01.json"
```

## 2. 書き方の規約（新しいチェックを足すとき）

1. **1 ファイル 1 チェック。** ファイル名は `<分類><番号>_<領域>_<主張>.sql`。主張は「成り立つべきこと」を肯定形で書く
   （「貸借が一致する」。「貸借が一致しない伝票」ではない）
2. **合格＝0 行、違反＝違反内容の行を返す SELECT。** ランナーは返った行数を数えるだけ。
   合格時に「OK」という行を返してはいけない
3. **冒頭コメントに 3 点を必ず書く。** 「何を保証するか」「違反時の意味（何が壊れるか）」「出典（ADR・設計書・実装ファイル）」
4. **違反行には原因追跡に足る列を載せる。** id だけ返さない。日付・金額・状態・差額を添える
5. **絶対パスを書かない。** リポジトリは GitHub 公開対象。マシン固有のパスは `Designer/LocalEnvironment.md` から読む
6. **制度値をハードコードしない。** 税率は `tax_rates` から解決する（`C02` の `std` CTE が手本）
7. **例外を許すときはコード付きで明示する。** 「評価勘定だから除外」なら除外理由と科目コードをコメントに残す（`F03` が手本）
8. **判定が二重実装になっている箇所は、実装側の定義に合わせる。** 画面の判定が正典（`C06` の消込額の定義がその例）

### 誤検出を作らないための落とし穴（実際に踏んだもの）

**誤ったアサーションは、無いより有害。** 赤が信用されなくなった時点で全部が死ぬ。
チェックを足すときは以下を必ず確認する。

| 落とし穴 | 具体例 | 対処 |
|---|---|---|
| **科目区分の取り方が広すぎる／狭すぎる** | `account_type='revenue'` には営業外収益・特別利益も入る。売上高だけを指したいなら `account_categories.code='REV'` | 「PL 全体」なら `account_type`、「売上高」「販管費」など帳票上の区分なら `account_categories` を使う |
| **`<>` は NULL を落とす** | `invoices.status` に NOT NULL 制約が無い。`status <> 'void'` だと NULL の請求書が黙って集計外になる | `COALESCE(col,'') <> 'x'` / `NOT IN` の前に COALESCE |
| **符号のある金額の SUM** | 売上値引・返品は収益科目の借方行として立つ。`SUM(amount)` では相殺されない | `SUM(CASE WHEN dc='C' THEN amount ELSE -amount END)`。件数を出す SQL でも純額列を添える |
| **LEFT JOIN による行の増殖** | 1 入金に消込仕訳が 2 本あると SUM が二重になる | 原因側を別チェック（`C07`）で検出しておく。集計は相関スカラサブクエリを優先 |
| **日付比較の非正規化** | `fiscal_years.start_date` は第19期だけ `"2027-04-01 00:00:00"`（時刻成分が混入している年度が実在する） | **全ての日付比較を `date()` で包む。** 年度の連結判定も `date(p.end_date,'+1 day')` で行う |
| **一意性を暗黙に前提する** | `parent_line_no → line_no` の解決は line_no の伝票内一意性に依存するが、DB に制約が無い | 前提そのものをチェックにする（`A05` の行番号重複） |

## 4. 違反 7 件の内容（改修前の基準値）

**修正はしていない。** ここに記録するのが目的で、直すかどうかは別の判断。

### A09（1 件）CSV 取込由来の税行に親行の紐づきが無い
伝票 26「7月電気代」（`source_type='import'`）。`is_tax_line=1` の仮払消費税 1,363 円の行に
`parent_line_no` が入っていない。`JournalEntry.mod.cs` は「CSV インポート由来は税行込みの生データが正なので畳まない」と
明記しており、**取込経路だけ税行の親子関係を作らない設計**になっている。
消費税集計表が親行の税区分に依存する集計をしている箇所があれば、取込分だけ落ちる可能性がある。
設計として許容するなら A09 に `source_type <> 'import'` の除外を足す判断もありうる（いまは足していない）。

### A11（13 件・8,015,000 円）売上行の部門が「全社共通」
確定仕訳の売上高 13 行（4000 受託開発 6 行 5,450,000 ／ 4010 SES 3 行 2,165,000 ／ 4020 SaaS 4 行 400,000）が
共通部門の受け皿に入っている。部門別 PL・予算実績でこの売上がどの部にも計上されない。
ADR-0056 は「損益科目の行には実部門が要る」としているが、`FillMissingDepartments()` の補完が
売上行にも効いている（または起票経路が部門を渡していない）。連動元は acceptance / ses / recurring 系。

> **2026-08-17 修正**: 当初は `account_type = 'revenue'` で書いていて **15 行・8,015,620 円**と報告したが、
> これは過検出だった。`revenue` 型には営業外収益（受取利息 7000）と特別利益（固定資産売却益 8000）も含まれ、
> 預金利息 2 行・620 円を巻き込んでいた。**預金利息に稼いだ部門は無く、全社共通が正しい姿**なので違反ではない。
> 対象を `account_categories.code = 'REV'`（売上高区分）に絞り、13 行・8,015,000 円が正。
> 科目コードの `'4%'` ベタ書きではなく区分マスタで解決しているので、売上科目を増やしても自動で追随する。

※参考（チェック対象外）: 費用側の全社共通は 28 行・4,539,337 円。共通費を受けて後から配賦する正当な
使い方があるため不変条件にしていない。営業外収益の全社共通は 2 行・620 円で、これは正常。

### B03（10 件）／B04（1 件・差額 8,936,588 円）第19期の期首残高が古い
第19期の期首残高は「翌期繰越を実行した時点のスナップショット」で、**その後 第18期に伝票を足しても自動追随しない**。
例: 売掛金は第18期末 7,552,000 に対し第19期首 1,320,000（E2E シナリオ完了時点の値のまま）。
`decisions/0006` の繰越方式（損益振替仕訳を作らずカラム値を焼き込む）の構造的な弱点で、
**再繰越が必要なことを誰も警告しない**。第19期の伝票が 0 件のいまは実害が出ていないだけ。

### C05（1 件）相殺入金に相殺先が入っていない
入金 id 27（2026-08-31・請求書 27・`method='offset'`）に `offset_vendor_invoice_id` が無い。
ADR-0035 は「相殺は買掛側と連動」としているので、買掛側が消えていない可能性がある。

### C08（1 件・差額 −880,000 円）売掛金元帳と売掛残高一覧が一致しない
元帳 7,552,000 に対し一覧 8,432,000。原因は C10 と同一（下記）。

### C10（1 件・超過 880,000 円）検収額を超える請求書
検収 A-26-009（税込 1,320,000）に対し請求書 INV-26-017 が税込 2,200,000。
**売上・売掛金は検収の確定でしか計上されない**ため、超過 880,000 円は請求書には載るが帳簿には存在しない。
`Invoice.mod.cs` は警告を出すがブロックしない（ISSUE-0002: 増額は変更契約として新しい受注・検収を起こす運用）。
運用ルール上は「請求書の作り方が間違っている」のだが、**アプリはそれを止めず、結果として売掛が永久にズレる**。

## 5. 書けなかったアサーション（理由つき）

| 求められたもの | 書けなかった理由 | 代わりに置いたもの |
|---|---|---|
| 総勘定元帳の残高と試算表の一致 | 集計済み残高テーブルを持たない設計（`decisions/0004`）で、両方とも `journal_lines` の集計。突合しても恒真で、バグを一切検出しない | **C08**（元帳 × 業務一覧の突合）。こちらは自明でない |
| 予算実績の実績値 = 仕訳集計 | `budget_lines` に実績列が無い。実績は画面で都度集計するため、比較対象が存在しない | **F05** で予算側の構造（期番号の範囲・行の重複）を検証 |
| 消込フラグと消込仕訳の存在が一致 | `receipts` に消込フラグ列が無い。ADR-0051 では「消込仕訳の存在」が消込済みの唯一の表現 | **C06** で請求書 status を代理フラグとして検証・**C07** で仕訳の実体を検証 |
| 締め済み会計期間に仕訳が存在しないか | 「締めた後に伝票を追加・変更したか」は DB から判定できない（締め日時の記録が無く、`updated_at` と締めの前後関係を比べられない）。締め済み期間に posted 伝票があること自体は正常 | **A07** で「締め済み期間に取り残された未確定伝票」だけ検証 |
| 償却計算の妥当性（月割・保証率・改定償却率） | 償却額の計算はスクリプト内にしかなく、期待値を DB から再現できない。`fixed_assets` に累計列も月次明細も無い | **E01** で上限（累計 ≤ 取得価額 − 1）だけ検証 |
| ~~経費申請のヘッダ = 明細合計~~ | ~~現状は 1 申請 1 明細で明細テーブルが存在しない~~ | **2026-08-17 に D05 として追加済み**（ADR-0066 の明細行化にともない） |
| 借入金の残高整合（返済予定 vs 元帳） | 借入金管理のテーブルがまだ無い（新設予定） | 新設後に H 系として追加する |

## 6. スキーマから気づいた設計上の懸念

1. **`source_type` / `source_id` は型のない外部キーで、DB 制約が一切効かない。**
   参照先テーブルが `source_type` の値ごとに違う（10 種類・F02 のコメント参照）ため、
   業務レコードを削除すると仕訳だけが残る。しかも新しい連動元を足すたびに検証側も更新が要る。
   `bank_statement_lines.journal_entry_id` のような実 FK 列と流儀が分かれているのも混乱のもと。

2. **DATE 宣言の列に時刻成分が混入している。**
   `fiscal_years.start_date` は 第17期・第18期が `2025-04-01` なのに 第19期だけ `2027-04-01 00:00:00`。
   保存経路によって形が変わるため、比較は必ず `date()` で正規化しないと壊れる。
   本集の SQL は全部 `date()` を通しているが、アプリ側の SQL に素の比較が残っていないかは別途点検が要る。

3. **翌期繰越がスナップショット方式で、陳腐化を検知する仕組みが無い。**
   前期に 1 本でも伝票を足せば翌期の期首残高は間違いになるが、警告も再計算もされない（B03/B04）。
   決算後の修正が日常的に起きる中小企業では、これは事故として顕在化する。
   最低でも「繰越実行時の前期末残高」を記録して差分を出せるようにしたい。
