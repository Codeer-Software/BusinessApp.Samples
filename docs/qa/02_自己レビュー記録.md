# 自己レビュー記録

[CLAUDE.md §3-2-1](../../CLAUDE.md) の自己レビューで出た指摘と、**採否の判断**を残す。

**指摘をそのまま全部反映しない。** レビューは意見であって仕様ではないので、
直すもの・直さないもの・後回しにするものを決める。

**ここに残すのは「後から理由を聞かれるもの」だけ**である。直した軽微な指摘は
コミットが記録しているので書かない。**直さないと決めたもの**と**後回しにしたもの**を、
理由つきで残すことに価値がある。

分割方針: 1 ラウンド 1 節。**ラウンドが 20 を超えたら**前半を番号帯ごとに別ファイルへ移す。

## 2026-08-24 ラウンド 2（仕訳の入力と計上が通った時点）

観点を分けて 2 人に読ませた。**会計ドメインと計上経路の穴**と、
**設計・依存の向き＋テストの十分性**。後者には「カバレッジ 100% に騙されていないか」を明示して問うた。

結果: 37 件（会計 14 / 設計 23）。直したものはテスト 373 件緑・
`AccountingCore` と `AccountingCore.Server` のカバレッジ 100% のまま反映した。

**この 2 件は、放っておけば必ず帳簿を壊していた。**

- **金額に小数が入る余地があった。** CLB の数値フィールドに小数桁の制限が無く、
  SQLite の `INTEGER` は `100.5` を整数に落とせず REAL のまま格納し、読み出し側の
  `Convert.ToInt64` が黙って丸めていた。借方 1000.5 / 貸方 1000.4 が
  「どちらも 1000」として貸借一致で計上され、DB には 0.1 円ずれた値が残る（I-01 が破れる）。
  画面・DDL（`typeof`）・読み出しの 3 か所すべてで塞いだ
- **最初から計上済みとして INSERT する道が DB に開いていた。** 他のトリガが UPDATE も DELETE も
  明細の追加も止めるので、**貸借不一致・明細ゼロの計上済み伝票が恒久的に残り、訂正も取消も
  できなくなる**。`BEFORE INSERT` のトリガで塞いだ

**テストの指摘で最も効いたのは次の 2 つ。**

- 本番の呼び順（`Prepare` → 保存 → `CompleteAsync`）は、並べ替えても `Prepare` を消しても
  47 件すべて緑のままだった。しかも `Prepare` を消すと関門が**完全に迂回される**。
  入口を `SubmitAsync(data, save)` の 1 本にして、順番を型で保証した
- 会計年度が初期データに 1 本しか無いので、`where fiscal_year_id = @p1` を**消しても
  100% のまま緑**だった。I-17 は製品の中核なのに DB 層では未証明だった。年度を 2 本にして検査した

### 解決済み: 「仕訳の新規画面が初期値を出さない」は**私の誤診だった**

半日をこれに溶かしたので、原因と教訓を残す。

- **実際には画面は最初から正常だった。** 開発者が手で開くと初期値も計上も問題なく動いた
- **誤診の原因**: `get_page_text` で画面を読んでいたが、**この API は `<input>` の value を拾わない**。
  伝票番号を読み取り専用に変えたあたりから、値付きで見える項目と見えない項目が混ざり、
  「全部空」と読み違えた（[qa/01](01_CLB静かな失敗.md) G-07）
- **なぜ長引いたか**: 誤った観測を疑わず、**原因の側だけを 9 通り切り分けた**
  （デザインを戻す・DB を作り直す・キャッシュを消す・C# を戻す…）。
  すべて「再現する」と出たので、そのたびに「原因は別にある」と結論した。
  **観測が間違っていれば、切り分けは何回やっても収束しない**
- **教訓**: 画面の状態を判定するときは**スクリーンショットを見る**。
  テキスト抽出は補助に留める。§3-2-0 で引く前に、**まず観測手段そのものを疑う**

なお、この過程で拡張機能の接続不良も重なった（[qa/01](01_CLB静かな失敗.md) G-08）。
Chrome とセッションの再起動で復旧した。

### 実機で確認したこと（2026-08-24）

観測手段を直したうえで、フェーズ 1 の完了条件をすべて実機で確認した。

- 新規作成で取引日・計上日・会計年度・状態に初期値が入る
- 明細の行番号・借貸が自動で入り、税区分が勘定科目の既定から入る
- 貸借不一致で計上すると**行番号つきの違反**が返り、**伝票も明細も採番も残らない**
- 貸借一致で計上すると伝票番号が付き、画面がその場で閲覧専用になる
- 金額は `typeof(amount) = 'integer'` を満たして保存されている

## 2026-08-24 ラウンド 3（一覧・検索、下書きの破棄、取消）

観点を分けて 2 人に読ませた。**会計と帳簿**（取消の正しさ・訂正への布石・法定検索）と、
**設計とテスト**（SQL の危うさ・上書き設計の穴・カバレッジに騙されていないか）。

結果: 40 件（会計 25 / 設計 15）。両者が独立に同じ 4 点を挙げた（★）。

**★ 反対仕訳の取引日が「今日」のまま計上されていた。** `JournalReversal` は
`TransactionDate = original.TransactionDate` と正しく決めていたのに、サーバが書き戻すのは
**明細と摘要だけ**で、取引日は画面の値が残っていた。docs/04 §5 で決めた
「反対仕訳の取引日は原仕訳と同じ」に正面から反する。しかも明細の課税仕入れの時点は
原仕訳から写るので、**同じ行の中で取引年月日と課税時点が矛盾**する。

**★ そしてテストがこれを構造的に隠していた。** フィクスチャの原仕訳と取消が同じ既定日付で、
取引日を一度も表明していなかった。カバレッジ 100% でも「別日で正しく写るか」は
一度も試していない。**原仕訳と取消の日付を変えたら即座に赤くなった。**

**★ 種別「訂正」が選べて、反対仕訳なしに計上できた。** 原仕訳を指したまま利用者が明細を
自由に書いた伝票が通り、原仕訳は生きたままなので**取引が帳簿に二重に載る**。
関門を種別のホワイトリストにして塞いだ。

**★ 会計年度を原仕訳から写していた。** 年度をまたぐ取消（3 月の仕訳を 4 月に取り消す）で
「作れたのに計上できない」という一番読みにくい行き止まりになる。計上日から引くようにした。

そのほか直したもの。

- **無効にしたマスタを使った仕訳が、取消も訂正もできなくなっていた。** 科目・部門・補助科目の
  無効は取消では警告に落とす（新たな計上には使えないが、取消は過去の反転である）
- 二重取消を DB でも止める（部分ユニークインデックス）。同時に 2 人が取り消すと、
  アプリの検査は両方が「まだ取り消されていない」を読んでしまう
- 検証より先に DB を書いていたので、計上済みの再取消がトリガの生 SQLite 例外になっていた
- `ReversalContext` を省略可能にしていた。既定値は「まだ取り消されていない」＝最も危険な側
- 課税仕入れの時点を時刻なしで書いていた（qa/01 A-04。その行だけ範囲検索から落ちる）
- `ReplaceLinesAsync` の 17 列が**全テストで NULL** だった。全項目を非 NULL で往復させる検査を足した

## 2026-08-25 ラウンド 4（訂正・Web API・仕訳帳）

観点を分けて 2 人に読ませた。**会計ドメインと帳簿**（訂正の正しさ・仕訳帳が帳簿として成立するか）と、
**設計とテストの十分性**（ADR の約束が守られているか・カバレッジに騙されていないか）。

結果: 33 件（会計 16 / 設計 17）。両者が独立に同じ点を挙げたもの（★）が 3 つあった。

**★ 訂正の下書きは、画面で種別を「通常」に変えられた。** 変えると種別ごとの関門が丸ごと外れ、
しかも二重訂正の検出は `correction` の行しか数えないので、**同じ原仕訳にもう 1 本訂正を計上できる**。
取引が帳簿に 2 回載る。種別は作成時に決まるものなので、下書きのうちでも変えられないようにした

**★ 無効化したマスタを使った伝票は「取消だけできて訂正できない」状態だった。**
訂正は取消を先に計上してから再計上の下書きを開くので（ADR-0015）、
再計上の検証が Error のままだと**取消だけが確定して詰む**。
「取消では止めない」の理由（訂正も取消もできない仕訳を残さない）は訂正にもそのまま当てはまる。

**★ 仕訳帳の法定検索は、一度も「効いていること」を検査していなかった。**
`QueryModuleTests` は宣言と SQL の整合しか見ず、値を入れた実行が 1 本も無かった。
`>=` と `>` の取り違えも、空値検索の分岐名の綴り違いも、例外にならず**静かに 0 件**を返す。

- 摘要の接頭辞剥がしが、**通常の仕訳の本文まで落としていた**（「伝票番号 12 の取消」と書いた
  普通の仕訳を取り消すと本文が消える）。剥がすのは原仕訳が取消・訂正のときだけにした

- 仕訳帳の取引先が、**表示は「明細優先」なのに検索だけ OR** だった。記載と違う行が返る
- 仕訳帳の並び順が年度を無視していた。年度をまたぐ取消が原仕訳より前に並ぶ

- ADR-0016 の「業務の差し戻しは 400」が実装（200 ＋ `status`）と食い違ったままだった。
  **ADR は唯一「約束」を持つ層なので、次に触る人を 400 へ引き戻す**。実測（qa/01 K-01）を根拠に改訂した
- テストデータの縮退。フィクスチャが取引日と計上日を**わざわざ同じ値**にしていたので、
  取引日を書くべき場所に計上日を書いても全テストが緑だった（qa/03 L-02 の再発）。既定でずらした
- 部分ユニークインデックスの検査が原仕訳 1 本に縮退していた。
  列を `(original_entry_id)` から `(entry_type)` に取り違えても緑になる

ミューテーションテストも回し、**実際の検査漏れが 1 件**出た。
`計上日 < 取引日` を `<=` にしても緑——「その日のうちに起票して計上する」という

### 教訓

- **関門は「鳴るか」だけでなく「何と言うか」まで表明する。** 鳴っても間違った直し方を教えるなら、
  無いよりたちが悪い（指示どおり直すと新しい違反になる）
- **偽の入力は本番と同じ形で作る。** 形が違うと、**本番では通らない経路**を検査して満足する
- **免除は足す前に実測する。** `growth: append` の免除は、実際には台帳 1 本しか通しておらず、
  代わりに「今日足す行」を無罪にしていた。**測っていたら最初から入れなかった**
