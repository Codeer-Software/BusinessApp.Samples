## 1. ミッション

**「よろず」に眠っている不具合を、機械的・網羅的に発見し、修正する。**
**同時に「ペルソナの実務で本当に使えるか」（Validation）も問い、使えない点を可視化する**（§4「発見の観点」）。

このアプリは 103 モジュール・56 スクリプト・15 PageFrame から成り、体験シナリオ 51 本と
E2E 分岐 121 個ぶんの台本・期待値が既に文書化されている。しかし**それを回す仕組みは手動しかなく、
自動テストは実質ゼロ**。台本は厚いのに検算が人力、という状態にある。

したがって本タスクの成果は二つ:

1. **発見と修正** — 眠っている不具合を洗い出し、直す
2. **恒久的な検証基盤** — 以後バグが混入したら機械が気づく状態にする
   - `Designer/tools/lint_design.py` — CLB「静かな失敗」の全数リンタ
   - `docs/qa/20_不変条件SQL/` — 実行可能な会計整合性アサーション集＋ runner
   - DB スナップショット／復元スクリプト
   - `docs/qa/02_バグ台帳.md` — BUG-nnnn 台帳

2 は 1 と同格の目的である。「今回バグを直した」より「次からバグに気づける」ほうが価値が高い。

## 2. あなた（Claude Code）の能力の実測事実

**再調査するな。2026-08-16 に実測済みである。** 推測ではなく実測結果。

| 論点 | 結果 |
|---|---|
| ヘッドレス `claude -p` からのブラウザ操作 | **不可**（ツール自体が渡らない） |
| サブエージェント（バックグラウンド含む）からのブラウザ操作 | **可能**（実測で成功） |
| 同時サブエージェント数 | 技術的には既定 20・ネスト 3 段。**ただし運用上は 3 が上限**（§5-2 の課金枠制約） |
| 親セッションに返るもの | **最終テキストのみ**。ツール出力・読んだファイルは親の文脈に載らない |
| 複数ブラウザ（Brave プロファイル） | 切替のたび人間の選択が必要 → **無人運転では使わない** |
| アプリの同時ログイン制限 | **存在しない**（素の Cookie 認証。制約はクッキー壺が1つなだけ） |
| クラウド Routines | ローカル FS に触れない → **使えない** |

### この事実から導かれる、最も重要な運用原則

> **ブラウザ作業はサブエージェントに丸投げする。**
> スクリーンショットもページテキストもあなたの文脈には載らない。
> あなたが自分でブラウザを操作すると、数十回で文脈が埋まる。**自分では操作するな。**

同じ理由で、**ファイルの精読・大量の grep・SQL 結果の大量閲覧も全てサブエージェントに投げる。**
あなたの仕事は「投げる・受け取る・台帳に書く・次を決める」だけ。

## 3. 環境と正確なコマンド

### 3.1 パスの解決

- リポジトリ直下を `<REPO_ROOT>` と表記する
- **デザイナ exe のパスは `Designer/LocalEnvironment.md` の `DesignerExePath:` 行にある**（Git 追跡外）。
  以下 `<DESIGNER_EXE>` と表記
- デザインプロジェクトのルート = `<REPO_ROOT>/Designer/Design`（以下 `<DESIGN_DIR>`）
- DB 実体 = `<REPO_ROOT>/LocalData/db/business-app_v1.db`
- データソース名 = `BusinessAppSQLite`（唯一。`AllowCliSqlAccess: true` が安全境界）

**本書に絶対パスを書かないこと**（このリポジトリは GitHub 公開対象。ADR-0038）。

### 3.2 サーバ起動 / 停止 / 起動待ち

```powershell
# 起動（http://localhost:5085）
dotnet run --project BusinessApp/BusinessApp.Server --launch-profile http

# 起動待ち
pwsh -NoProfile -File Designer/tools/wait-server.ps1 -TimeoutSec 60

# 停止（ポート 5085 の listener を落とす）
$p = Get-NetTCPConnection -LocalPort 5085 -State Listen -ErrorAction SilentlyContinue | Select-Object -First 1 -ExpandProperty OwningProcess; if ($p) { Stop-Process -Id $p -Force; "Stopped PID $p (port 5085)" } else { "No listener on 5085" }
```

**罠**: サーバを exe 直叩きする場合は CWD を `BusinessApp.Server` プロジェクトディレクトリにすること
（Content root = 起動時 CWD。リポジトリ直下だと appsettings が読めず全ログインが 500 になる）。
`dotnet run --project` 方式ならこの罠は無い。**常に `dotnet run --project` を使え。**

### 3.3 デプロイ（hot-reload）

```powershell
pwsh -NoProfile -File Designer/tools/deploy.ps1
```

`Designer/Design` 一式を zip 化して `LocalData/designs/App.zip` に置く。FileWatcher が検知して hot-reload。

> **`*.mod.cs`（スクリプト）を変更した場合と DB スキーマを変更した場合は、
> deploy だけでは反映されない。必ずサーバを再起動すること。**
> （2026-08-16 にこれを怠って実データを生成し復旧した事故がある）

### 3.4 designcheck

```powershell
& "<DESIGNER_EXE>" designcheck "<DESIGN_DIR>" --out "<出力JSON>" 2>&1 | Out-Null

**`2>&1 | Out-Null` は必須。** デザイナ exe は GUI アプリなので、パイプしないと PowerShell が
完了を待たずに戻ってしまう。`findingCount` が 0 になるまで直す。

## 4. 作業アーキテクチャ — 4 レーン制

**核心の考え方: 静的解析と SQL で「仮説」を大量生産し、ブラウザは仮説の検証にだけ使う。**
ブラウザ時間が唯一の希少資源なので、そこを彷徨わせない。

| レーン | 内容 | 並列度 | ブラウザ | ヘッドレス `claude -p` |
|---|---|---|---|---|
| **A: 静的監査** | モジュール／スクリプトを CLB 既知の失敗＋会計ドメイン知識で読む | **最大 2** | 不要 | 可 |
| **B: データ不変条件** | 複式簿記・帳票・消込の整合性を SQL アサーション化 | **最大 2** | 不要 | 可 |
| **C: 実機探索** | 台本実行＋敵対的探索 | **最大 2** | 必須 | 不可（ツールが渡らない） |
| **D: 修正＋回帰** | 修正 → designcheck → deploy → 再起動 → 再検証 → コミット | 直列（オーケストレータ自身） | 一部 | 可 |

> **右端の列は「ヘッドレス実行かどうか」だけの話であり、時刻やユーザーの在席とは無関係**
> （2026-08-17 ユーザー訂正）。**対話セッションで自走している限り、深夜でもユーザー不在でも実機は自由に使ってよい。**
> むしろユーザーが画面を見ていない時間帯のほうが、ブラウザを占有しても迷惑にならない分だけ都合がよい。

**並列度はレーンをまたいだ合計で 2 まで**（A を 2 本走らせている間に C を足さない）。理由は §5-2。
レーン D はオーケストレータ自身が担うので、この 2 人枠には数えない。

### 発見の観点 — Verification と Validation の両輪（ユーザー明示指示・2026-08-17）

**バグ狩りは「正しく作れているか」だけでなく「作るべきものになっているか」も見る。**

| 観点 | 問い | 主な出し方 |
|---|---|---|
| **Verification（検証）** | 仕様・設計どおりに動くか。計算・状態遷移・権限・整合性は正しいか | レーン A/B。既存の手法 1〜9 がこれ |
| **Validation（妥当性確認）** | **ペルソナが実務で使って役に立つか。** 市販ソフトなら当然できることができない・手順が非現実的・出力が実務で使えない | レーン C を中心に、A でも常に併走 |

Validation の判断基準は**ペルソナ**（`docs/02_ペルソナ.md`／IT 受託ソフトハウス 30〜80 名）と、
**あなた自身の会計・業務実務の知見**。必要に応じて `WebSearch`／`WebFetch` で
**市販ソフト（弥生会計・freee・マネーフォワード・勘定奉行 等）の仕様や、実務上の慣行・法制度を
幅広く調べて根拠にする**。記憶や思い込みで「これで十分」と判断しない。

Validation で見るべき典型:
- **業務が完了できるか** — 途中で詰む導線、戻れない状態、代替手段の無い制約
- **入力の現実性** — 実務でありうる形（分割検収・着手金・値引・返品・訂正）を受け止められるか
- **出力の実用性** — 帳票が税理士・銀行・監査に出せる体裁か。証跡が追えるか
- **業務量への耐性** — 月次で数百件流したときに現実的な手数か（一括操作・検索・上限）
- **誤操作からの回復** — 間違えたときに取り消せるか、被害が限定されるか

**取り扱い（重要）**: Validation 所見は §8.1 の線引きで**多くが「機能追加」＝台帳止め**になる。
それでよい。**「バグではないから」と黙って捨てるな。** 台帳に `[台帳止め]` で積み、
`03_進捗.md` の「GO 待ち一覧」に 1 行で載せる。ユーザーが判断できる形にするところまでが仕事。
既存の起票（`docs/issues/`）や `docs/14_市販ソフト比較レビュー.md` と重複する場合はそちらへ寄せ、台帳からは参照だけ張る。
なお**「実務でありえない入力を受け付けて壊れる」は Verification 側のバグ**（ガード漏れ）なので自律修正の対象。

### レーン A の具体手法

1. **CLB「静かな失敗」の全数リンタ化** — 以下を機械可読ルールにして `Designer/tools/lint_design.py` を作る。
   これは今回の最重要成果物のひとつ。
   - `HorizontalAlignment` の `Left`/`Right`（**エラーにならず既定 `Start` に化ける**。正しくは `Start/Center/End/Stretch`）
   - SQLite の生成列を CLB が認識しない（FB-046）
   - `date('now')` は UTC（JST とずれる）
   - `IsUpdateProtected` は新規作成時に効かない
   - スクリプトで try-finally が使えない
   - `OnValidateInput` が無言で保存を止める
   - `AllowEmptySearch` が効かない（ADR-0057）
   - OR 検索の既定値は `SearchValues`（複数形）。単数形だと無言で効かない
   - Boolean は新規時の初期値が未チェック（ADR-0054）
   - 検索既定は `?initialize_search=true` 付き遷移でしか効かない
   - 既知の全リストは `docs/12_CLB改善提案/01_機能改善提案.md`（FB-001〜046）にある。**サブエージェントに読ませて抽出させる**
2. **スクリプト意味監査** — 各 `.mod.cs` を対応する設計書とペアで読ませ、具体的な問いに答えさせる
   - 端数処理は税率ごとに 1 回か（ADR-0049/0050）
   - `OnDataChanged` の無条件上書きは無いか（**既知の真因パターン**。ADR-0053: `OnDataChanged` は
     スクリプト生成にも発火する＝「セットしない」は「既定が入らない」ではない）
   - 再入・多重発火は
   - 締め期間ガードは
   - 取消の連鎖は完全か（ADR-0035）
3. **状態機械の網羅監査** — 伝票ごとに 状態×操作×権限 の行列を JSON から機械生成し、
   孤児状態・戻れない状態・取消漏れを検出（ADR-0026 が oracle）
4. **権限×画面の全数マトリクス** — 15 フレーム × 103 モジュール × 26 ユーザーを静的展開し、
   `docs/10_部品アーキテクチャ.md` §5・`docs/13_ポータルと通知基盤.md` と突き合わせる。
   `Designer/tools/check_navigation.py` を汎用化して取り込む（**現状 DESIGN パスがハードコードされているので直す**）
5. **ADR ドリフト検査** — `docs/decisions/` の 63 本の決定が現在も守られているか照合
6. **ドキュメント vs 実装** — 設計書（`04_会計ドメイン設計` / `07_経費精算設計` / `08_請求入金設計`）と実装の齟齬

## 5. コンテキスト規律（絶対規則）

**これが守れないと、10 時間もたずに判断品質が崩壊する。**

### 5-2. トークン枠の管理（ユーザー明示指示・2026-08-17）

> **同時に走らせるサブエージェントは 2 人まで。レーンをまたいだ合計で数える。**
> 「10〜20 並列で投げてよい」と書いてあった旧記述は**全て無効**。§4 の表が正。

**実測（2026-08-17）**: 5 時間枠の開始 20 分で枠の 10% を消費した。内訳は
**完了した 6 エージェントで約 948,000 トークン（1 体あたり平均 158k・最大 238k）**、
オーケストレータ本体は同期間で約 20 万。**消費のほぼ全てがサブエージェントである。**
したがって効く対策は同時実行数よりも**1 体あたりの重さと総投入数**。

**守ること**:

| 規則 | 内容 |
|---|---|
| **同時 2 人まで** | レーンをまたいだ合計。3 人目を投げたくなったら、先に 1 人の完了を待つ |
| **1 体あたり 100k を目安** | 依頼文で**対象ファイルを名指し**し、`WebSearch` は**回数を明示して制限**する（例:「最大 2 回」）。探索範囲を書かないと平気で 200k 使う |
| **台帳統合は書式を分ける** | P0/P1 は 10 項目のフルブロック、**P2/P3 は「## 未対応（P2/P3・簡略）」節に 1 行の表**で足りる。統合エージェントが最も重いのはここ |
| **小さい修正は自分でやる** | 委譲すると相手がコンテキストを読み直す分だけ高くつく。1 ファイルの局所修正はオーケストレータが直接やるほうが安い |
| **同じものを二度読ませない** | 既に台帳へ統合済みのレポートを再度読ませない。レポートは「統合したら用済み」 |

**記録の規律（枠切れは予告なく来る）**:
- **バッチが 1 つ完了するたびに `03_進捗.md` を更新する。** まとめて後で書こうとするな
- 修正はコミットまでを 1 単位にする。作業ツリーに未コミットの修正を溜めない
- 枠が苦しくなってきたら、**新しいバッチを投げるより先に台帳と `03_進捗.md` を最新化する**
- **消費量の記録**: 完了通知に載る `subagent_tokens` を `03_進捗.md` の消費表に積む。
  オーケストレータは 5 時間枠の残量を直接観測できない（**自分のコンテキスト残量とは別物**）ので、
  この積み上げが唯一の手がかりになる。**30 分に一度、累計をユーザーに報告する**

**2 人が走っている間、あなたは待つ。** 空き時間に自分でファイルを読み始めるな（§5 の規律に反する）。
ただし**修正レーン（§8.3）を自分で進めるのは可**——むしろそれが待ち時間の正しい使い方である。

| 規則 | 内容 |
|---|---|
| **自分で読まない** | ファイルの精読・大量 grep・SQL 結果の閲覧・ブラウザ操作は**全てサブエージェントに委譲** |
| **返却を絞る** | サブエージェントには「所見のみ・最大 20 件・1 件 5 行以内」を必ず指示する（§6 のテンプレ） |
| **生ログは外に置く** | 詳細は `docs/qa/30_レポート/<日付>_<バッチ名>.md` に書かせる。**あなたは読まない** |
| **レポートは必ず台帳へ転記する** | **レポートは読み物・台帳は追跡台帳。** 所見をレポートに書いただけで番号を付けないと、誰も追わないまま消える。2026-08-19 にこれが 13 件溜まっているのが発覚し、うち 1 件は**全社ロックアウトの P1**（BUG-0386）だった。転記の粒度は「1 所見 1 番号」。**再現しない・成立しない所見も『再現せず』で採番して残す**——同じ所見が次の監査でまた出てくるため（BUG-0392） |
| **状態はファイル** | 記憶に頼らない。`02_バグ台帳.md` と `03_進捗.md` が唯一の真実 |
| **投入回数を数える** | `03_進捗.md` にサブエージェント投入の累計回数を記録する。**150 回を超えたら引き継ぎを検討**（§12） |
| **例外** | P0/P1 バグの修正時だけは、対象ファイルを自分で読んでよい。修正の質は文脈の節約より優先する |

```

### 6.4 並列投入のルール（2026-08-16 実測に基づく）

- **全レーン合計で同時 2 人までが絶対上限**（§5-2・ユーザー指示）。レーン A/B も例外ではない
- **ブラウザ 2 並列は技術的に安全**（§14 実験1 で 33 観測・混入ゼロ）。制約はトークン枠のほうである
  - タブの**表示内容**は隔離される（33 観測で混入ゼロ）

  - ただし **3 並列でスクリーンショットが 1 回タイムアウトした**（`Page.captureScreenshot` が 30 秒で失敗）。

- **同じファイルを触るサブエージェントを同時に走らせるな**（修正レーンは特に）

## 8. 修正ポリシー

### 8.1 線引き — ここだけ間違えるな

> **2026-08-17 にユーザーが線引きを広げた。以前の版より自律の範囲がかなり広い。**
> 「バグ修正はこのタスクの範疇。設計や仕様の判断が必要なものだけ人間が確認する」

**自律的に修正する**:

1. 既存の設計意図どおりに動いていないもの — 計算違い・ガード漏れ・条件式の誤り・
   状態遷移の穴・表示崩れ・ラベル不統一・書式（右詰め・カンマ）の乱れ・検索既定の誤り・権限判定の抜け。
   **P2（表示・UX の不整合）も対象。**
2. **仕様を変えることになるが、「明らかにこれが正解の挙動だ」と確信できるもの**
3. **UI を変えることになるが、「明らかにこれが最善だ」と確信できるもの**

つまり **「仕様変更だから」「UI 変更だから」は、それ自体では台帳止めの理由にならない。**
判断の軸は**変更の種類ではなく、確信の度合い**である。

**台帳に積む（着手しない）**:
- **業務上・会計上の判断が要るもの** — どちらの挙動が正しいかが業務ルール次第で、
  ユーザーに聞かないと決められないもの（例: 社会保険料の税区分、締め済み期間の訂正方針）
- **データモデルの改廃**（列・テーブル・親子構造）で、移行と既存データの解釈が絡むもの
- **業務フロー／承認ルートの意味を変えるもの**
- **新機能の追加**（今そこに無い業務をできるようにする。バグ修正ではない）
- **設計の選択肢が複数あり、どれが良いか根拠だけでは決まらないもの**
- Validation 所見のうち、上記に当たるもの（§4「発見の観点」）

**迷ったら台帳止めに倒してよい**（ユーザー明示）。ただし「念のため」で全部積むな——
それでは自律作業にならない。**確信できるなら直す。確信が持てないから積む。**

判断に迷ったときの自問:
- 「これを直したあと、ユーザーに『なぜそうした』と聞かれて、業務・会計・UX の言葉で
  1 分で説明して納得してもらえるか？」→ Yes なら直す
- 「正解が複数ありうるか？ 選択にユーザーの好み・業務ルールが要るか？」→ Yes なら積む

**台帳止めにしたものは ADR に相当する判断材料を書いておく**（完了時にまとめて提示するため。§7）。

### 8.2 回帰テストの義務（ユーザーの明示指示）

> **デグレは修正箇所に直接出るとは限らない。修正箇所のみならず関連箇所も網羅的にテストせよ。**

修正 1 件ごとに、以下を**必ず**実施する。省略は許されない。

1. **影響範囲マップを先に作る**（修正の前に）
   - 触ったモジュール／スクリプトを**参照している**他モジュール（Link/Lookup/写し元・写し先）
   - 共通スクリプト・共通 SQL・クエリモジュール
   - その数字が流れ込む先の**帳票**（試算表・BS・PL・C/F・月次推移・消費税集計）
   - **ポータルの件数・アラート**（ADR-0060 の二重実装に注意）
   - 通知基盤（`docs/13_ポータルと通知基盤.md`）
   - サブエージェントに「このモジュールを参照している箇所を全部挙げろ」と投げれば早い
2. **直接確認** — 修正箇所が意図どおりになったか（実機）
3. **関連箇所の確認** — 1 で洗い出した箇所を実機で確認（サブエージェントに分散させてよい）
4. **不変条件スイート全件** — `docs/qa/20_不変条件SQL/` を全部流してグリーンを確認
5. **該当ドメインの体験シナリオを最低 1 本完走**
6. **`designcheck` が 0 件**

**この 6 つが全部済むまで `[修正済]` にしてはいけない。**
台帳の「検証」欄には、実施した項目を具体的に列挙すること（「テスト済み」ではなく「何をやったか」）。

### 8.3 修正の手順

```
1. DB スナップショットを取る
2. 影響範囲マップを作る（8.2-1）
3. 修正する
4. designcheck → 0 件になるまで直す
5. deploy.ps1
6. .mod.cs / DDL を触ったなら → サーバ再起動（必須）
7. 8.2 の 2〜5 を実施
8. 回帰アサーションを 20_不変条件SQL/ に追加（可能なら）
9. 1 バグ 1 コミット（Conventional Commits）
10. 台帳を更新
```

### 9-2. 3 回直して直らなかったときの手順（ユーザー指示・2026-08-17）

> **止まってユーザーに相談しなくてよい。撤回して台帳に書き残し、バグ狩りを続ける。**
> ただし**別セッションの自分が読んで判断できるだけの情報を残すこと**が条件である。

1. **まず動く状態に戻す。** 業務が止まる修正（伝票が起票できない・保存できない等）を
   デプロイしたまま次に行かない。`git show <着手前のコミット>:<ファイル>` で
   元の実装を取り出して戻し、deploy → **サーバ再起動** → 実機で戻ったことを確認する
2. **台帳の状態を `[台帳止め（GO待ち）]` にし、以下を必ず書く**:
   - **試した診断と、それぞれがどう外れたか**（表にする。同じ道を辿らせないため）
   - **動いている実例との差分**（「この形は動く／この形は動かない」を具体的なファイル:行で）
   - **撤回したコミットハッシュ**（実装 → 修正試行 → 撤回、の順に全部）
   - **再挑戦するときの手がかり**（迂回案を最低 1 つ。「あきらめる」も選択肢として書く）
   - **実害の範囲**（今のデータで顕在化しているか、潜在か）
3. **CLB 側の問題が疑われるなら `docs/12_CLB改善提案/` に再現コードごと記録する。**
   原因が分からないなら**「原因未特定」と正直に書く**。間違った推測を「既知の罠」として
   残すほうが有害である（FB-053 がその実例）
4. **`03_進捗.md` の GO 待ち一覧に 1 行足して、次のバグに進む**

**判断の物差し**: 4 回目に行くかどうかは「新しい情報が手に入ったか」で決める。
実機のエラーメッセージが変わった・動く実例との差分が新たに見つかった、なら続けてよい。
**同じ症状に対して推測を並べ替えているだけなら止める。**

## 14. 未解決の実験（P0 で最初に潰す）

結果は `docs/qa/03_進捗.md` に必ず記録すること。**推測で進めるな。**

### 実験1: ブラウザの並列可否 — **実施済み（2026-08-16）。再実験は不要**

**結論: 並列可。2 並列を標準、3 を上限とする。**

**方法**: アプリを使わず、ローカルの静的ページ 3 枚（赤=ALPHA / 青=BRAVO / 緑=CHARLIE、
それぞれ固有マーカー文字列を表示）を用意し、サブエージェントを 2 本／3 本同時に立てて
各自のタブで `computer` スクリーンショットと `get_page_text` を交互に連射させ、
**相手のマーカーが混入しないか**とタイムスタンプの重なりを検証した。

**結果**:

| 検証 | 観測数 | 混入 | エラー |
|---|---|---|---|
| 2 並列（交互に 6 ラウンド） | 24 | **0** | 0 |
| 3 並列（`browser_batch` で連射） | 33/36 | **0** | スクショ 1 件がタイムアウト |

- **同時性は本物**: 2 並列の最終ラウンドは両者 **21 ミリ秒差**で実行された
- **タブ内容は完全に隔離される**。スクリーンショットは「アクティブタブ依存」ではなく **tabId スコープ**だった。
  他エージェントが同時にタブを作成・遷移していても、自分のタブの内容は一切変わらない
  → 表示は混ざらない。**ただしログインセッションは共有される**（上記・2026-08-17 に実測して訂正）
- **3 並列で綻びが出た**: `Page.captureScreenshot` が 30 秒でタイムアウト（36 回中 1 回）。
  さらに 1 フレームでズーム倍率が変わる描画アーティファクトを観測
- **`get_page_text` は一度も失敗せず、異物も返さなかった** → **確認は原則テキストで行い、
  スクリーンショットは「見た目の崩れ」を疑うときだけ**（文脈節約だけでなく堅牢性の理由からも）
- **`browser_batch` は最初のエラーで残りを黙って捨てる**（実測）。観測数の照合を怠ると
  「実行したつもりで実行されていない」検証が生まれる

**レーン C の所要見積り**: 2 並列で 10〜20h（直列なら 20〜40h）。

### 実験2: CLB スクリプトの実行場所 — **実施済み（2026-08-16）。確定。再調査不要**

**結論: スクリプトは 100% クライアント（Blazor WASM）側で走る。**
**したがって HTTP を直接叩く操作は「テスト」として一切使えない。**

- サーバ側にスクリプトエンジンは存在しない。Roslyn を参照しているのは WASM プロジェクトだけ
- 設計データはスクリプト込みでフロントへ配られ、インタープリタ方式で実行される
- **HTTP 直叩きで動かないもの**: `OnDataChanged` / 各種 `On*Click` / 保存前検証 /
  **仕訳の自動生成** / `IsRequired` の必須チェック（`ValidateInput()` は UI 側）
- **HTTP 直叩きでも動くもの**: 認証・CSRF、`ModuleDataIO` の権限判定
  （UserRead/Write・DataRead/WriteCondition）、パスワードポリシー検証、
  トランザクション、DB の制約・トリガー・生成列

**この結論が意味すること（重要）**:

1. **ブラウザ実機が、業務ロジックを通す唯一の経路である。** 「HTTP で速く回す」という近道は無い。
   だからこそ §14 実験1 で確認した**ブラウザ 2 並列**が効いてくる
2. **HTTP 経由でデータを作って「通った」と判断してはいけない。** 検証が丸ごと素通りし、偽陽性になる
3. **テストデータの投入は `sql` CLI の直接 INSERT のほうが正直。**
   HTTP と違い「ロジックを通していない」ことが明白で、権限・トリガーも意識して書ける。
   ただし**どちらの経路でも仕訳の自動生成は起きない**ので、複式簿記の整合は自分で担保すること
4. **P0 で HTTP セッションハーネスを作る必要は無くなった。** 作るな

### 実験3: ヘッドレス連鎖の権限 — **実施済み（2026-08-16）。全項目グリーン**

`claude -p`（`--bare` なし）は**プロジェクトの `.claude/settings.json` /
`settings.local.json` の許可を継承する**。実測結果:

| 検査 | 結果 |
|---|---|
| ファイル読み取り | ok |
| `sql` CLI 実行（読み取りクエリ） | ok |
| ファイル書き込み | ok |
| サブエージェント起動 | ok |
| サブエージェント**並列**起動 | ok |
| 権限で拒否されたもの | **なし** |

→ **夜間の無人稼働は成立する。** レーン A・B・D をヘッドレス連鎖で回してよい。
ブラウザツールだけは渡らない（§2）ので、**レーン C はヘッドレスでは動かせない**——
ただしこれは「ヘッドレスでは」であって「夜間は」ではない。
**対話セッションなら深夜でもユーザー不在でも実機は自由**（§10 の訂正を参照）。

**この実験で判明した設定の不備（修正済み）**:
`.claude/settings.local.json` の `Write(...)` ルールは**ファイル権限チェックに一致せず無効**だった
（`Edit(...)` ルールが全てのファイル編集ツールを覆う仕様）。放置すると無人運転中に
リポジトリへの新規ファイル作成で止まる。2026-08-16 に `Write` 行を削除し `Edit` 行に一本化済み。
**同時にブラウザ操作系ツール（`navigate` / `computer` / `form_input` / `tabs_create_mcp` /
`tabs_close_mcp` / `browser_batch` / `javascript_tool`）も追記済み**なので、§11 の P0-1 は完了している。
