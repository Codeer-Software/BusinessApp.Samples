# テストで漏らした実例

**実際に作ってしまった不具合と、なぜテストが見逃したか**を残す。
[qa/01](01_CLB静かな失敗.md) が CLB の踏み抜きを集めるのと同じ作法で、こちらは**自分の作り込みと検査の穴**を集める。

## この文書の使い方

- **実装するとき**: 新しいコードが下の「漏れの型」のどれかに当てはまらないかを見る
- **テストを書くとき・レビューするとき**: 型ごとの「次から効く検査」をそのまま使う
- **自己レビューのとき**: [`self-review` スキル](../../.claude/skills/self-review/SKILL.md)がここを参照する

## この文書の育て方

- **分割方針**: L-nn の番号帯で分ける。**L-40 を超えたら**前半を番号帯ごとに別ファイルへ移す

- **一般論を書かない。** 「境界値を確かめる」のような教科書的な観点は、書いた瞬間に読まれなくなる。
  **実際に踏んだ形だけ**を書く
- **1 件につき「何を作ったか・なぜ検査をすり抜けたか・次から何で捕まえるか」の 3 つ**を書く。
  原因の分析より、**次に同じ形を探せること**が目的である
- **機械で守れるようにしたら、その型はここから消す。**
  この文書が短くなっていくのが健全な状態である。
  リストに頼る範囲を減らすのが目的であって、リストを長くするのが目的ではない

## L-01 ドメインが決めた値が、永続化されずに捨てられていた

**何を作ったか**（2026-08-24・取消の実装）

`JournalReversal` が「反対仕訳の取引日は原仕訳と同じ」と正しく決めていたのに、
サーバが DB に書き戻すのは**明細と摘要だけ**だった。取引日は画面が入れた「今日」が残り、
docs/10 §5 で決めた仕様に正面から反する伝票ができていた。

**なぜすり抜けたか**

- ドメイン側のテストは**戻り値**を見ていて緑だった。**その戻り値が使われない経路**を誰も試していない
- サーバ側のテストは、原仕訳と取消の**取引日を同じ既定値**で作っていた（下の L-02 と重なる）
- 行・分岐カバレッジは 100% だった。**その行は通っている。使われていないだけ**

**次から効く検査**

- **ドメインが決めた項目のうち、いくつが実際に DB に書かれるかを数える。**
  戻り値の項目数と、書き込み SQL の列数が大きく違ったら疑う
- **「読む → 決める → 書く → 読み直して確かめる」を 1 本のテストにする。**
  戻り値で止めない
- ミューテーションテストなら機械で出る（`TransactionDate = original.TransactionDate` を消しても緑だった）

## L-02 テストデータが縮退していて、区別すべき 2 つが同じ値だった

**何を作ったか**（2026-08-24・取消の実装）

L-01 を隠していた直接の原因。フィクスチャの `InsertDraft` と `InsertReversalDraft` が
どちらも既定の取引日を `2026-08-24` にしていた。**日付を変えたら即座に赤くなった。**

**なぜすり抜けたか**

観点は持っていた（ドメイン側に「取引日は原仕訳と同じ」というテストがある）。
**観点ではなく、値の作り方の問題**だった。観点リストでは防げない種類の漏れである。

**次から効く検査**

- **フィクスチャの既定値を、意味の違うものは全部違う値にする。**
  同じ値を使いたければ、テスト側が明示的に指定しなければならない形にする
- 「A と B が同じであること」を確かめるテストは、**A と B が別々に作られているか**を必ず見る
- 日付・金額・ID など、**取り違えても型が通るもの**はとくに注意する（[ADR-0014](../decisions/0014-識別子は型を作る.md) の動機と同じ）

## L-03 観測が「起きていない」と「起きたが何も変わらなかった」を区別できなかった

**何を作ったか**（2026-08-24・計上日から会計年度を引く処理）

「計上日を変えても会計年度が変わらない」を切り分けるため、ハンドラの中で摘要に目印を書いた。
ところが**最後に `[発火] 年度=…` で上書きする**作りにしたので、

- ハンドラが発火していない → 初期化時の目印が残る
- 発火したが該当年度が無く、古い年度がそのまま → **同じ文字列**になる

の 2 つが**まったく同じ表示**になった。切り分けにならない観測を作ってしまった。

真の原因は「該当が無いときに空にする処理が抜けていた」ことで、**開発者の指摘で判明した**。

**なぜすり抜けたか**

そもそもテストの話ではなく、**デバッグの設計**の失敗。
ただし根は同じで、**「観測が 2 つの状態を区別できるか」を確かめずに観測を始めた**。

**次から効く検査**

- **目印は上書きせず、追記する。** `Description.Value += "…"` にすれば経路が全部残る
- **切り分けを始める前に「この観測で、どの仮説とどの仮説が区別できるか」を書く。**
  区別できない観測なら、観測のほうを先に直す
- [qa/02](02_自己レビュー記録.md) の「引く前に観測手段そのものを疑う」と同じ教訓。
  **同じ失敗を 1 日に 2 回している**

## L-04 書いた値を読み戻す往復を一度も検査していなかった

**何を作ったか**（2026-08-24・取消の明細書き込み）

`ReplaceLinesAsync` が明細を 18 列で INSERT するのに、
**全テストで 12 列が NULL** だった。列を取り違えても、書式を間違えても、どのテストも赤くならない。

**なぜすり抜けたか**

- 「書けた」ことしか確かめていなかった。**読み戻して同じ値かを見ていない**
- 金額と貸借は本体行で合うので、**貸借一致でも金額でも検出できない**

**次から効く検査**

- **リポジトリの書き込みメソッドには、全項目を非 NULL で埋めて往復させるテストを 1 本置く。**
  `Assert.Equal(書いた行, 読んだ行)` で record ごと比べる
- NULL 許容の列は、**NULL のときと値があるときの両方**を通す

## L-05 呼び出しの順番が、型でも検査でも守られていなかった

**何を作ったか**（2026-08-24・保存時の関門）

`Prepare` → 保存 → `CompleteAsync` の 3 行は、**並べ替えても `Prepare` を消しても 47 件全部が緑**だった。
しかも `Prepare` を消すと、検証を一切通らずに計上済みが書かれる（ADR-0004 がまるごと迂回される）。

**なぜすり抜けたか**

テストが**部品を手で繋いでいた**ので、本番の配線とずれても気づけない。
フィクスチャに「組み立て方も検証の対象である」と注記しながら、実際には複製していた。

**次から効く検査**

- **順番に意味がある処理は、公開する入口を 1 本にして順番を型で保証する**（検査ではなく設計で消す）
- **本番の組み立てとテストの組み立てを同じ関数にする。**
  フィクスチャが `new` を並べていたら疑う

## L-06 既定値が「最も危険な側」だった

**何を作ったか**（2026-08-24・取消の文脈）

`ReversalContext context = default` と省略可能にした。既定値は `IsAlreadyReversed = false`、
つまり「**まだ取り消されていない＝取り消してよい**」。呼び忘れると二重取消が通る。

テストの 9 件中 8 件がこの引数を省略していて、**既定値が安全でないことに誰も気づけない構造**だった。

**なぜすり抜けたか**

省略可能にした時点で、「呼び忘れ」がテストの対象から外れる。

**次から効く検査**

- **安全に関わる引数を省略可能にしない。** 既定値を置くなら「最も安全な側」にする
- 省略可能な引数を見たら、**省略したときに何が起きるか**を必ずテストに書く

## L-07 カバレッジの設定が、async とイテレータをまるごと計測から外していた

**何を作ったか**（2026-08-25・訂正の実装中に発覚）

カバレッジのゲートは `record` のコピーコンストラクタを穴に数えないために
`ExcludeByAttribute=CompilerGeneratedAttribute` を置いていた。**この設定は
`async` のステートマシンと `yield return` のイテレータも同時に除外する。**

結果、`AccountingCore.Server` は**計測対象が 38 クラス中 6 クラス**しかなく、
`JournalEntryStore` は同期の小さなヘルパ 1 つだけが測られていた。
ドメイン側でも `AmendmentRules`（イテレータ）が丸ごと、`JournalReversal.Validate` も測られていなかった。
**それでも表示は「100%」で、ゲートは緑だった。**

除外をやめたところ、**一度も実行されていない防御コードが 4 か所**出てきた。
そのうち 1 つは、前日のレビューで ★ が付いた「種別のホワイトリスト」の拒否分岐そのものである
（直したのに、直したことを何も検査していなかった）。

**なぜすり抜けたか**

設定を入れた時点（2026-08-23）では**実測して影響範囲を確認していた**し、その結論は正しかった。
当時のコードに `async` もイテレータも無かったからである。
**確認は「そのときのコード」に対して正しく、コードが変わった瞬間に嘘になった。**
しかも嘘になったことは、数字が下がるのではなく**上がったまま**現れる（測らない行は穴に数えられない）。

**次から効く検査**

- **「除外」設定は、何が除外されたかを数で確かめる。** カバレッジの率だけを見ない。
  レポートの**クラス数と関数名の一覧**を見れば、消えた層はすぐ分かる
- **「実測で確認済み」と書いた設定には、いつ・どのコードに対して測ったかを併記する。**
  前提が変わったときに読み手が疑える
- カバレッジ 100% が「未テストの行がゼロ」を意味するのは、**測っている行が全部のときだけ**である

## L-08 守りが 3 つあったのに、全部が「利用者に編集させている 1 列」に乗っていた

**何を作ったか**（2026-08-25・訂正）

訂正の再計上には守りを 3 つ置いた。①アプリの検証（原仕訳が取り消されているか・既に訂正されていないか）
②DB の部分ユニークインデックス（再計上は原仕訳 1 本につき 1 本）③関門の種別ホワイトリスト。

**3 つとも `entry_type = 'correction'` を条件にしていた。** そして種別は、
下書きのうちは画面で自由に変えられた。「訂正」を「通常」に変えて計上すると、
①も③も通らず、②は数えず、**同じ原仕訳にもう 1 本訂正を計上できる**。取引が帳簿に 2 回載る。

**なぜすり抜けたか**

守りを足すたびに「もう 1 枚増えた」と数えていたが、**3 枚とも同じ前提の上に立っていた**。
テストはすべて種別が正しい状態から始まっており、**前提そのものを崩すテストが無かった**。

**次から効く検査**

- **守りを数える前に、その守りが何に依存しているかを数える。** 同じ値に依存する守りは 1 枚である
- **分類に使う列は、作成後に変えられないようにする。** 「変えたいなら作り直す」で困ることはまず無い
- 利用者が編集できる項目のうち、**サーバの分岐に使っているもの**を洗い出す

## L-09 自分で書いたレシピの分岐を、最初の実践で書き落とした

**何を作ったか**（2026-08-25・テーブル作り直しマイグレーション 0004）

migrations/README の作り直しレシピ⑧は「書き戻しが 0 行だと `sqlite_sequence` に行が無いので、
そのときは INSERT にする」と自分で書いてあった。なのに最初の作り直しマイグレーションは
**UPDATE の 1 文だけ**で書いた。行を全部消した表を作り直すと、退避した採番が黙って捨てられ、
消した id が再利用される（帳簿間のリンクが別の行を指す事故の形）。

**なぜすり抜けたか**

- 同値テストは**空の DB** にマイグレーションを再生する。書き戻しは毎回 0 行コピーで、
  比較は `sqlite_master` のテキストだけ。**データと採番の往復はどの網にも乗っていなかった**
- レシピを README に書いた安心感で、写すときに読み返さなかった。
  **文章の規約は、機械が照合しない限り「書いた」と「守った」が別物**

**次から効く検査**

- **作り直しマイグレーションには「データありの再生テスト」を必ず対で書く**
  （行を入れ、末尾を消して採番を進め、適用し、全列の読み戻しと採番の非再利用を表明する。
  `MigrationEquivalenceTests` の「作り直しはデータと採番を失わない」「行が空でも採番を失わない」が型）
- レシピ⑧自体を、書き落とせない**ガード付き 2 文の形**に書き換えた（README）

## L-10 テストの土台が CLB の返り値を偽って、経路 1 本がまるごと未検査だった

**何を作ったか**（2026-08-26・計上の関門 `JournalSubmitGate`）

**新規作成の画面から直接「計上する」を押すと、必ず失敗していた。**
「下書き保存 → 開き直して計上」なら通るので、**画面を触るまで誰も気づかなかった**。
続けて 2 つ目も出た。保存そのものが失敗したときに、その理由を捨てて先へ進み、
利用者には「計上する仕訳の ID を解決できない」という**二次的な内部エラー**だけが届いていた。

原因は 1 つに繋がっている。CLB の `ModuleSubmitResult` は、
**仮 ID → 本物の ID の対応を `SourceId` / `DestinationId` で返す**（`TemporaryIdMap` には入らない）。
関門は `TemporaryIdMap` だけを見ていたので、新規行の仮 ID をいつまでも解決できなかった。

**なぜすり抜けたか**

- **テストの土台（`AccountingServer.Saving`）が `TemporaryIdMap` に詰めて返していた。**
  つまり**実装の思い込みをそのまま土台に写して**、土台と実装が同じ勘違いで握手していた。
  緑は「実装が正しい」ではなく「実装と土台が一致している」しか言っていなかった
- 実際の返り値を**一度も実機で見ていなかった**。見た瞬間に
  `src= dst= map=0 ex=SQLite Error 19` と出て、10 秒で分かった
- **失敗を表す返り値を作れる土台になっていなかった**ので、「保存が失敗したとき」を
  書こうと思っても書けなかった。**書けない検査は、無いのと同じ**

**次から効く検査**

- **外部ライブラリの返り値を偽る土台は、実機で 1 度は本物を観測してから書く。**
  土台の中に「何を観測して、いつ観測したか」を書き残す（`SubmitData.Result` の注記）
- **土台には成功だけでなく失敗も作れるようにする**（`SubmitData.Failure`）。
  失敗が作れない土台は、異常系をまるごと検査の外に置く
- **直したあと、古い実装を新しい土台にかけて赤くなることを必ず確かめる**
  （今回は 5 件が赤くなった。これを見るまで「土台を直した」と言わない）
- **画面から入る経路は全部通す。** 「新規のまま計上」と「保存してから計上」は別経路である
  （[qa/04](04_実機操作テスト.md) の記録）

## L-11 テストの土台が NULL を空文字に化けさせ、「入っていない」の表明が必ず通っていた

**何を作ったか**（2026-08-26・テストの土台 `TestDatabase.ScalarOf<T>`）

`Convert.ChangeType(command.ExecuteScalar()!, typeof(T))` と書いていた。
**`Convert.ChangeType(DBNull.Value, typeof(string))` は例外ではなく `""` を返す。**
そのため `Assert.Null(Scalar<string?>("select 写しの列 ..."))` という表明が、
**実際には値が入っていても必ず通っていた**。

**なぜすり抜けたか**

- **「無いこと」を確かめる表明だけが壊れる**ので、正常系の緑からは何も見えない。
  写しを焼く実装を書いて初めて、5 件の「入っていないはず」が全部通ってしまうことに気づいた
- 土台は `TestSupport` にあって**どのテストからも見えない**。
  ここが嘘をつくと、上に乗っているテスト全部が同じ嘘をつく（[L-10](#l-10-テストの土台が-clb-の返り値を偽って経路-1-本がまるごと未検査だった) と同じ形）

**次から効く検査**

- **土台が値を変換する場所は、NULL を必ず別扱いにする。**
  NULL を表せない型（`long` など）で NULL を読んだら**止める**（既定値の 0 を返すと、
  今度は「0 のはず」が黙って通る）
- **「無いこと」の表明を書いたら、1 度は値を入れて赤くなることを確かめる。**
  正常系の緑は、否定の表明が生きているかを何も言っていない

## L-12 CLB が日付に時刻を付けて書くので、文字列で比べていた検査が本番だけ死んでいた

**何を作ったか**（2026-08-26・登録の関門と写しの焼き込み）

**CLB は日付の列に `"2023-10-01 00:00:00"` と時刻付きで書く**（アプリ全体でそう）。
なのに「同じ日から始まる登録が 2 件」を止める検査は `valid_from = '2023-10-01'` と
**文字列で比べていた**ので、本番では**いつも外れて二重登録が黙って通っていた**。
外れても例外は出ないので、画面上は何ごともなく保存される。

同じ日に 2 件目が入ると、計上のときに「どれを写すか決められない」で**計上のほうが止まる**——
入力の誤りが、関係の無い場面で初めて音を立てる形になっていた。

**なぜすり抜けたか**

- **テストが素の `'2023-10-01'` を入れていた。** 土台が CLB と違う形で書いていたので、
  文字列の比較が一致してしまい、緑になった（L-10・L-11 と**同じ形で 3 度目**）
- 実機で 1 行入れて DB を覗いた瞬間に分かった。**保存された値を一度も見ていなかった**

**あわせて見つかったこと**

`tax_point`（課税仕入れの時点）を入力する画面が無いので**全行 NULL** だった。
「入っていなければ写さない」と書いていたため、**登録番号の写しが永久に空**になる状態だった。
取引日で引くように変えた（`LedgerSnapshotWriter.TaxPointOf`）。

**次から効く検査**

- **DB へ書く形は、実機で 1 行入れて `sql` CLI で覗いてから決める。**
  型名（`DATE`）が何を格納するかは、CLB が何を書くかとは別である
- **テストの土台に「CLB と同じ形で書く」入口を用意する**（`AccountingServer.DateLiteral`）。
  素のリテラルを直接書かせない
- **日付の比較は `date()` で包む。** 文字列の等値で日付を比べない
- **新しい列を足したら、実機で 1 件通して値が入ることを見る。**
  「入れる画面が無いので永久に空」は、単体テストでは絶対に見えない

## L-13 新しい部品を足したことで、成立していた ADR の性質が黙って壊れた

**何を作ったか**（2026-08-26・計上時に写しを焼く `LedgerSnapshotWriter`）

ADR-0018 は「**取消・訂正は原仕訳の写しをそのまま引き継ぐ**」と決め、しかも
「**（既にそうなっている）**」と添えてあった。実際そうなっていた——反対仕訳の明細は
原仕訳を写して作るので、写しも一緒に運ばれていた。

そこへ「計上のたびにマスタから引いて焼く」部品を足したところ、**取消の計上でも焼き直され**、
原仕訳の計上後に改名された相手では**同じ取引の表と裏が違う名前**になった。
帳簿の記載事項が 1 つの取引で 2 通りになり、計上済みは不変なので直せない。

**なぜすり抜けたか**

- **「既にそうなっている」と書いてある性質には、検査が付いていなかった。**
  自然に成立していた性質は、壊れるまで誰も見ない
- 新しい部品のテストは**新しい部品の観点**（写しが入るか）しか見ていなかった。
  「これまで成立していたことが、まだ成立しているか」は観点に無かった
- 実機で改名 → 取消と順に触って初めて出た。**単体テストは 1 つの計上しか見ていなかった**

**次から効く検査**

- **ADR に「既にそうなっている」と書くときは、その場でテストを 1 本足す。**
  書いた時点では本当でも、**あとから足した部品が壊す**。文書は壊れたことを教えてくれない
- **計上の経路は 3 つある**（保存の関門・取消・訂正）。計上に関わる部品を足したら、
  **3 つとも通す**。今回は取消を通す検査が 1 件も無かった
- **状態を変えてから 2 回目を通す検査を書く**（改名してから取り消す・登録を取り消してから訂正する）。
  1 回きりの検査は「引き継ぎ」を見られない

## L-14 関門が、DB に拒まれる値を作って保存へ渡していた

**何を作ったか**（2026-08-26・取引先の素性の関門）

`PartnerSubmitGate` が法人番号を正規化して書き戻すとき、**空欄も空文字にして渡していた**。
DDL の CHECK は `corporate_number IS NULL OR corporate_number GLOB '[0-9]…13 桁'` なので、
空文字はどちらにも当たらず**保存が DB で失敗する**。
起こる場面は特殊ではない——「入っている法人番号を消す」という、
[13 §1-2](../13_取引先設計.md) が想定している正規の直し方そのものである。

**関門の役目は「DDL の CHECK の手前に置く網」なのに、関門自身が網の外の値を作っていた。**

**なぜ検査をすり抜けたか**

- 関門のテストは**保存が呼ばれたかどうか**しか見ていなかった。
  本物の DDL を載せた SQLite を毎回立てているのに、**`partners` へ 1 行も書いていなかった**
- スキーマ側のテストは「12 桁」「14 桁」「数字でない」を拒むことを見ていたが、
  **空文字を試していなかった**
- 実機の台本も「壊れた番号を弾く」までで、**「入っている番号を消す」を誰も踏んでいなかった**

**次から何で捕まえるか**

- **関門を通した値を、そのまま DB に流す往復のテストを 1 本置く**
  （`関門が通した値は_DB_も受け取れる`）。関門の受理集合が DB の受理集合に収まっていることを、
  保存が呼ばれたかどうかではなく**実際に書いて**確かめる
- **DB の CHECK のテストには、必ず空文字のケースを入れる。**
  「無い」は NULL で表す（[10 §4-4](../10_会計ドメイン設計.md)）と決めているなら、
  空文字が拒まれることはその決定の裏返しである
- **値を書き戻す関門は、「空にする」経路を台本に入れる。** 壊れた値を弾くだけの台本は、
  正しい直し方が通ることを見ていない

## L-17 関門が鳴りはしたが、**示した直し方が別の壊れた文書を指していた**

**何を作ったか**（2026-08-28・自己レビューで発見。同日のコミット `1bc927f`）

「`current` の本文が `superseded` へリンクしていたら error」の関門を足したとき、指摘文に
**後継の文書名**を添えた。その後継を `related` の**先頭を無検証で**取っていた。

実データの `superseded` 4 本のうち **2 本は `related[0]` 自身が `superseded`** だった
（後継がさらに覆された組）。つまり関門は「**この壊れた文書へ張り替えよ**」と案内していた。
指示どおり直せば**新しい違反になる**。加えて後継のパスを「対象文書から見た相対」のまま出していたので、
指摘を受けた文書から見ると存在しない場所を指すこともあった。

**なぜすり抜けたか**

- **セルフテストが件数しか表明していなかった。** `len(got) != want` だけを見ていたので、
  **指摘文の中身は 1 文字も検査していない**。`SEV_ERROR` を `SEV_WARN` に書き換えても、
  行番号を消しても、後継を間違えても、**全ケースが通る**
- [L-03](#l-03-観測が起きていないと起きたが何も変わらなかったを区別できなかった) と同じ形である——
  あちらは「起きた／起きなかった」、こちらは「鳴った／正しく鳴った」を区別できていなかった
- **偽の入力だけで表明していた。** セルフテストの `Doc` は手で組み立てたもので、
  `related[0]` が `superseded` という**実データにしかない形**が 1 件も入っていなかった
- 同じ理由で、**偽の入力が本番と食い違っていた**ことにも気づけなかった——
  ADR 台帳の免除を `growth: append` の無い偽 `Doc` で表明していたが、
  本物の台帳には `growth: append` があり、**本番では到達しない経路のカバレッジだけを埋めていた**

**次から何で捕まえるか**

- **関門を足したら、件数ではなく「何と言うか」を表明する。** `severity`・指摘先・行番号・
  リンク先・**直し方の案内**を 1 ケースで全部当てる（`lint_docs.py --selftest` に入れた）
- **偽の入力だけで済ませない。実データで一度通し、見た件数を印字してラチェットにする。**
  `lint_docs.py` は「superseded 宛リンク: N 件を検査」を毎回出し、
  セルフテストが **N ≧ 1** を要求する。**0 は「違反が無い」ではなく「配線が死んだ」を疑う数字**である
- **偽の入力は、本番のデータと同じ形で作る。** フロントマターの有無・フラグの有無まで揃える
  （揃っていないと、通らない経路を検査して満足することになる）
- **関門は、足したあとに 1 回ずつ壊して鳴ることを確かめる**（L-15 の作法）。
  今回は 10 通り（格下げ・免除の追加・免除の削除・案内の劣化・戻り値の固定など）で確かめた

> **2026-08-28 追記**: この処方のうち「行番号を表明する」は、**書いた直後は空振りしていた**。
> 検体のリンクを本文 1 行目に置いていたので、行番号を `body_start + 1` に固定する壊し方と
> 区別が付かなかった（翌ラウンドのレビューで発覚。[qa/02 R20-03](02_自己レビュー記録.md)）。
> **検体は「壊れ方と区別が付く形」に作る**——先頭・末尾・単一の値を避け、
> 同じ値を 2 つ並べない。L-02（テストデータの縮退）が別の顔で出たものである。

## L-19 順序に使えない代理キーで並べ、その誤りを検体の縮退が隠した

**何を作ったか**（2026-08-30・元帳の累計を会計年度で切ったとき。自己レビューで発見）

「累計を会計年度で切る」ために、窓と並びの両方に **`e.fiscal_year_id`** を書いた。
`fiscal_years.id` は `INTEGER PRIMARY KEY AUTOINCREMENT` の**代理キー**で、年代とは無関係な挿入順である。
第 17 期のデモデータ（フェーズ 7）を後から入れると id は第 18 期より大きくなり、
**元帳が新しい年度から先に出る。** しかも列は並べ替え不可にしたので利用者は戻せない。

**なぜすり抜けたか**

- **足したテストの検体が縮退していた。** 追加した会計年度は第 19 期ひとつで、
  「後から入れた・日付も後」——**代理キー順と年代順が一致していた**。
  `ORDER BY` を `id` にしても `start_date` にしても同じ結果になる（L-02 の形）
- **「わざと壊して鳴ることを確かめる」は実行していた。** 窓と並びを 1 つずつ壊し、
  どちらも赤くなることを見ている。**鳴ったのは事実だが、鳴らした壊し方が足りなかった**——
  検体が区別できない壊し方（id か開始日か）を、そもそも試していない
- 元の SQL には `ORDER BY ... e.fiscal_year_id ...` が既にあり
  （伝票番号が年度内の連番だから年度を並びに含める、という別の目的）、
  **そこにあった書き方をそのまま前に動かした。** 目的が変わったことに気づかなかった

**次から何で捕まえるか**

- **順序キーに代理キーを使わない。** 「順番に意味がある列」（開始日・日付・コード）で並べる。
  識別子は**同一性**には使えるが**順序**には使えない——`PARTITION BY` に `id` を書くのは正しく、
  `ORDER BY` に書くのは誤り、という違いがある
- **年度・期間をまたぐ検体には、「後から入れた古い年度」を必ず 1 本入れる。**
  時系列に素直な検体だけでは、代理キーで並べる実装と区別が付かない
- **壊して鳴らすときは、「区別したい 2 つの実装」を両方作って比べる。**
  1 つ壊して赤くなったことは、検体が十分であることを何も言っていない
- **機械で守る案**: `Designer/Design/Modules/Accounting/Books/*.sql` の `ORDER BY` に `_id` で終わる列が
  現れたら警告する（`lint_design.py`）。誤検出は「識別子で並べたい正当な場面」だが、
  帳簿では思いつかない。**足すかどうかはフェーズ 2.5 の D で決める**


## L-20 正しく書いてある既存の SQL から写すときに 1 文字落ち、エスケープが何もしなくなった

**何を作ったか**（2026-08-31・新しいクエリモジュール 2 本。自己レビューで発見。**2 人が独立に指摘**）

登録番号と摘要の部分一致に、仕訳帳と同じ「利用者が打った文字をワイルドカードにしない」処理を写した。

```sql
-- 正しい（仕訳帳・総勘定元帳）
replace(replace(replace(@p_keyword, '\', '\\'), '%', '\%'), '_', '\_')
-- 写し損じ（新しい 2 本）
replace(replace(replace(@p_keyword, '\', '\'),   '%', '\%'), '_', '\_')
```

`replace(x, '\', '\')` は**何もしない**。SQL は正しく走り、例外も出ない。
壊れるのは `\` を含む語で検索したときだけで、パターンが `%\%` になり
「`\%` ＝ リテラルの %」というまったく別の問い合わせに化ける。
**利用者には「該当なし」としか見えない。**

**なぜすり抜けたか**

- **既存の正しい実装から写した**ので、目視では「同じ形」に見える。
  差は `'\\'` と `'\'` の 1 文字で、しかも**真上のコメントが正しい手順を説明している**——
  読んだ人は実装が合っていると思う
- **`QueryModuleTests` は検索欄を全部 NULL で流す。** 宣言と SQL の突き合わせも
  出力列の突き合わせも通るが、**LIKE の枝には一度も入らない**
- 実機でも見つからなかった。`\` を含むデータが無く、普通の語では正しく絞れるからである
- **道具の側の事情もある**（このリポジトリの作り方）——SQL をヒアドキュメントで書くと
  バックスラッシュが処理系ごとに食われる。**「書いたつもりの文字が入っていない」**が起きやすい

**次から何で捕まえるか**

- **機械で守った**（上の表）。`ESCAPE` を書いた回数だけ `\` の二重化があることを見る。
  逃がす対象（`%` と `_`）は書き損じても素直に「絞れない」で現れるので、
  **静かに壊れる 1 手だけ**を固定する
- **既存の実装から写したものは、写した先で 1 回動かす。** 「同じ形にした」は検査ではない
- **バックスラッシュを含む文字列を書いたら、書いたファイルを読み直して確かめる**

## L-21 「入っているか」だけを見て、DDL の `CHECK` が並べていない値を保存へ渡していた

**何を作ったか**（2026-08-30 に置いた保存の手前の網。2026-09-02 のフェーズ 2.5 の D で発見）

`JournalSubmitRequirements` は「DDL がそのまま受け取れる形か」を見る関門である。
金額と行番号には**上限と整数性**まで書いたのに、**選択肢の値は「空でないか」しか見ていなかった**。
`journal_lines.debit_credit` / `journal_entries.status` / `journal_entries.entry_type` は
どれも `CHECK (… IN (…))` を持つので、**候補外の値は DB が拒む**——
そこまで届くと、利用者には `SQLite Error 19` がそのまま出る（[qa/01 F-16](01_CLB静かな失敗.md)）。

**なぜすり抜けたか**

- **同じファイルが、同じ理由をすでに書いていた。** 金額と行番号のところに
  「画面は `Min: 1` で防いでいるが、**画面は経路の 1 本でしかない**」と書いてある。
  **選択肢にはその理屈を当てていなかった**——「選択欄だから変な値は来ない」で止まっている
- **テストが「関門を通った値を DB が受け取れるか」しか見ていなかった。**
  [L-14](#l-14-関門がdb-に拒まれる値を作って保存へ渡していた) の処方（往復）は当ててあったが、
  検体は**正しい値**だけだった。**DB が拒む値を関門に食わせる往復**を書いていない
- **カバレッジもミューテーションも緑。** 見ていない入力は、変異させる行が存在しない

**次から何で捕まえるか**

- **受理集合は列挙子から引く**（値を書き並べない）。`EnumConsistencyTests` が
  「デザイン enum・DDL の `CHECK`・C# の列挙型」の 3 者一致を守っているので、
  **列挙子を見れば DDL を見たことになる**
- **往復テストは「通る値」と「DB が拒む値」を対で書く。** 片側だけだと、
  「関門は止めるが DB は受け取れた」（＝過剰な関門）と
  「関門は通すが DB が拒む」（＝穴）の区別が付かない
- **`CHECK` を持つ列を数え、関門が見ている列と突き合わせる。**
  今回見つかったのは、DDL の `CHECK` を機械で読む検査（`EnumConsistencyTests` の網の拡張）を
  書いていて、**「この列を関門は見ているか」を人が問い直したから**である

> **2026-09-02 追記（同じ日の自己レビュー）**: **最初の直し方が間違っていた。**
> 受理集合の判定に `DbValue.ToDefinedEnum` を使ったが、あれは**DB から読んだ値を C# に直す
> 寛容な読み手**で、`ToPascalCase` を通してから名前を照合する——`"Debit"` も `"_debit"` も通す。
> DDL が受け取るのは `'debit'` だけなので、**穴は塞がっていなかった**。
> `DbValue.ToSnakeCase` で列挙子を DB の書き方に直して照合する形に替えた。
> **検体も縮退していた**——`"both"` のような綴り違いだけを試していたので、
> 「候補外を弾く実装」と「PascalCase を通す実装」を区別できなかった。
> **区別したい 2 つの実装を両方作って比べる**（L-19 の処方）が、ここでも要る。
> あわせて `tax_treatment` が同じ形で残っていたことも分かり、同時に塞いだ

## L-22 CLB の条件が届かない書き込み経路を、権限の外に置いたまま「閉じた」と書いた

**何を作ったか**（2026-08-25 の取消・訂正の Web API。2026-09-02 の自己レビューで発見）

取消・訂正は画面から Web API（`/api/journals/reverse` / `correct`）で呼ぶ（ADR-0016）。
このコントローラは `[Authorize]` だけを持ち、**`IDbAccessor` を直に使う**ので、
`JournalEntry` / `JournalLine` に付けた `UserWriteCondition` を **1 つも通らない**。
`can_access_app` が真の利用者なら誰でも——取引先だけの利用者でも——
任意の伝票に**取消を計上できた**。取消は計上済みで不変（ADR-0004）なので、**取り返しがつかない**。

同じ回に、フェーズ 2.5 の E で「`JournalEntry` / `JournalLine` を会計の役割に閉じた」と書いた。
**閉じていない経路があるのに、閉じたと書いた**のがいちばん悪い。

**なぜすり抜けたか**

- **「モジュールに条件を付けた」を「データを閉じた」と読んだ。** qa/01 F-30 が
  「このモジュールを閉じたは、このデータが読めなくなったではない」と**読み取り**について
  書いているのに、**書き込みの側で同じ読み違いをした**
- **実機の台本が API を 1 本しか叩いていない。** P-15 は `POST /api/module_data/list` を
  投げて 500 を確かめたが、**`/api/journals/*` は 1 度も投げていない**。
  「API から読めない」を確かめて「API から書けない」と読んだ
- **権限を C# で見る場所が 1 つも無かった。** `accounting_role` を読むコードは
  リポジトリ全体で 0 行で、`EnumConsistencyTests` の対応表にも
  「会計コアが役割を読む場面は無い」と書いてあった。**無いことが前提になっていた**ので、
  「ここは通らないのでは」と疑う手掛かりが消えていた

**次から何で捕まえるか**

- **「CLB の条件が効かない経路」を数える。** いま分かっているのは 2 つ——
  `IDbAccessor` を直に使う Web API と、`CustomizedModuleDataIO` の外側。
  **新しい入口を作ったら、その入口が通る関門を並べて書く**
- **権限は入口ごとに 1 か所へ集める。** 取消・訂正は `JournalAmendmentEndpoint.RunAsync` の
  1 か所で見る。操作ごとに書くと、次の操作を足した日に忘れる
- **実機の台本は「読めない」と「書けない」を別に踏む。** qa/04 に P-17 を足した
  （役割の無い利用者で `/api/journals/reverse` を投げて、伝票が増えないこと）
- **「閉じた」と書く前に、その相手に届く経路を数える。** 数えずに書いた文が
  そのまま設計文書に残ると、**次に読む人は閉じていると信じる**

## L-23 「入っている」と「無い」しか検体に無く、「空にした」を一度も通していなかった

**何を作ったか**（2026-08-24 からの保存の関門。2026-09-02 の実機操作で発見）

補助科目を一度選んでから × で消し、下書き保存すると
**保存ごと落ちて `SQLite Error 19: 'FOREIGN KEY constraint failed'`** が出た。
CLB は空にした `LinkField` を `null` ではなく**空文字**で送ってくる（[qa/01 F-33](01_CLB静かな失敗.md)）。
関門はそれをそのまま通し、`sub_account_id INTEGER REFERENCES sub_accounts(id)` へ `''` が渡っていた。

**利用者は正しい操作をしている。** 参照を空に戻すのは正規の入力であって誤りではないのに、
**その伝票はもう保存できない**——直す手立ては、消した補助科目を選び直すことだけだった。

**なぜすり抜けたか**

- **検体が 2 状態しか無かった。** 関門のテストは「値が入っている」（`Line`）と
  「フィールドが差分に載っていない」（`LineWithout`）だけを作っていた。
  CLB が実際に送る 3 つ目の状態——**フィールドはあるが空**——を一度も組み立てていない。
  `ModuleSubmitData` を自分の手で組み立てるテストは、**画面が実際に送る形を知らない**
- **必須の欄では再現しない。** `JournalSubmitRequirements` は空文字を「入っていない」と読んで
  差し戻すので、勘定科目や金額を空にしても関門で止まる。
  **素通りするのは必須でない参照だけ**で、そこを空にする検体が 1 つも無かった
- **往復のテスト（[L-14](#l-14-関門がdb-に拒まれる値を作って保存へ渡していた) の処方）も同じ検体を使っていた。**
  関門のテストと DB へ書くテストが**同じ 2 状態**を共有していたので、
  2 本あっても穴は 1 つのままだった
- **実機の台本に「一度入れた値を消す」が 1 つも無い。** 入れる・直す・行ごと消すはあったが、
  **参照欄だけを空に戻す**は無かった。**消す操作は、消せる欄の数だけある**

**次から何で捕まえるか**

- **参照欄の検体は 3 状態を並べる**——値あり・**空**・欄なし。
  「空」は画面でしか作れない状態なので、**意識して作らないと永久に通らない**
- **「利用者が消せる欄」を数える。** `IsRequired` でない `LinkField` が候補である。
  空にできる欄には**空にした往復**を 1 本書く（関門を通した結果が DB に入ることまで見る）。
  **ただし全部が踏むとは限らない**——同じ日に確かめた 3 例では、
  **`ListField` の行**（仕訳明細の補助科目）だけが空文字で届き、
  **トップレベルの欄 2 つ**（取引先の名寄せの親・伝票の取引先）は NULL で保存された
  （[qa/01 F-33](01_CLB静かな失敗.md)）。**「どの欄が踏むか」はまだ 3 例しか無い**
- **直す場所は入口に 1 か所。** `JournalSubmitGate.SubmitAsync` の先頭で
  `LinkFieldData.Value` の空文字を `null` に直す。**フィールドごと・列ごとに書かない**——
  次に空にできる欄を足した日に忘れる（[L-22](#l-22-clb-の条件が届かない書き込み経路を権限の外に置いたまま閉じたと書いた) と同じ処方）
- **`Add` と `Update` を両方通す。** 参照を空に戻す操作は**ほとんど更新で起きる**
  （一度選んだものを消すのだから、その行はもう DB にある）。
  `Add` だけ直すと、**実機で実際に踏む側が直らない**
- **機械で守れるのは「関門より下」だけ**（2026-09-02 時点）。
  空文字を入れた `ModuleSubmitData` を関門に食わせる単体テストは書ける（上の 2 項目がそれで、
  `JournalSubmitGateTests` に `Add` と `Update` の 2 本ある）。
  **書けないのは「CLB が本当に空文字を送るか」のほう**である——それは本番の画面でしか作れないので、
  **実機の台本（[qa/04](04_実機操作テスト.md) J-11）で踏むしかない**。
  **規約テストで「空にできる欄をすべて数える」ことも試みていない**——
  どの欄が踏むかがまだ分かっていないため（上）

## L-24 ツールがファイルを書き直したときに BOM が付き、コミットまで通った

**何を作ったか**（2026-09-02。同じ日のうちに自分で見つけた）

置き場所を間違えたドキュメント注釈を直すのに、Python で
`open(p, encoding="utf-8-sig")` で読んで**同じ `utf-8-sig` で書き戻した**。
読みは BOM を「あれば取る」だが、**書きは「必ず付ける」**である。
`.cs` 2 本と `.mod.json` 2 本の先頭に BOM が付いた。

**`.cs` の 2 本はそのままコミットまで通った**（`e62ab35`）。
`.mod.json` の 2 本は `lint_design.py` が JSON を読めずに落ちたので、そこで気づいた。

**なぜすり抜けたか**

- **`.editorconfig` は `charset = utf-8`（＝ BOM なし）と書いてあるのに、守らせる仕組みが無かった。**
  設定は**エディタへの申し送り**であって、検査ではない。
  **書いてあることと、守られていることは別**である
- **文字列では見えない。** `File.ReadAllText` は BOM を取り除いて返すので、
  CRLF の検査（`CarriageReturnProblems`）と同じ形では書けない。
  **バイトを見る検査が 1 本も無かった**
- **`git diff` でも見えない。** 差分は「ファイル全体が変わった」とは出ず、
  BOM の付いた行が 1 行の差分として出るだけで、目では BOM と分からない
- **JSON だけが偶然引っかかった。** `lint_design.py` は `json.load` を素の UTF-8 で呼ぶので
  BOM で落ちる。**狙って作った関門ではない**

**次から何で捕まえるか**

- **機械で守った**（上の表）。`CSharpStyleTests` の「ソースに BOM を付けない」が
  検査対象の `.cs` の**先頭 3 バイト**を見る。**検体を 1 つ食わせて、鳴ることも同じテストで見る**
- **ファイルを書き戻すときは、読みと書きで同じ符号化を指定しない。**
  `utf-8-sig` は**読み専用の道具**である。書くときは `utf-8`
- **`.mod.json` は BOM 無しである**（`lint_design.py` が素の UTF-8 で読む）。
  デザインファイルを機械で書き換える道具を作るときは、ここを最初に確かめる

## L-25 トリガが「いま所属している親」しか見ておらず、明細を計上済みへ付け替えられた

**2026-09-03。自己レビュー（CLB と DB の静かな失敗の観点）が指摘し、
インメモリ SQLite で再現して確かめた。**

**何が起きたか**

`journal_lines` の不変性を守るトリガ 2 本は、どちらも
`(SELECT status FROM journal_entries WHERE id = OLD.journal_entry_id) = 'posted'` という条件で、
**その明細が「いま」ぶら下がっている伝票の状態しか見ていなかった**。だから

```sql
UPDATE journal_lines SET journal_entry_id = <計上済みの伝票> WHERE journal_entry_id = <下書き>;
```

は**どのトリガにも当たらずに通る**。通ると、計上済みの伝票に身に覚えのない行が 1 本増える——
**貸借一致（I-01）も不変性（I-05）もその瞬間に破れ、しかも計上済みなので訂正も取消もできない。**
DDL 自身が「CSV 取込・API・スクリプト・手作業の SQL のどれからでも通る**最後の関門**」と
宣言している場所の穴である（ADR-0004）。

**なぜすり抜けたか**

- **検体が「同じ親の中での変更」しか無かった。** `JournalImmutabilityTests` は
  `UPDATE journal_lines SET amount = ...` / `SET account_id = ...` / `DELETE` を並べていたが、
  **親を変える UPDATE が 1 本も無かった**。列を並べて網羅した気になっていたが、
  **外部キーの列は「値」ではなく「所属」である**——他の列と同じ扱いでは足りない
- **逆向きは塞がっている。** 計上済みの明細を下書きへ逃がす向きは `OLD` 側の条件に当たって拒まれる
  （2026-09-03 に検体を足して固定した）。**なぜ片側だけで足りると思ったのかは分からない**——
  当時の記録が無いので、ここは推測になる
- **カバレッジもミューテーションも DDL を見ていない。** トリガは C# ではないので、
  どちらの計器も届かない範囲にある

**次から何で捕まえるか**

- **機械で守った。** トリガを 1 本足し（`trg_journal_lines_no_move_into_posted`。`NEW` 側を見る）、
  `JournalImmutabilityTests` に「下書きの明細を計上済みの伝票へ移せない」を足した。
  `SchemaShapeTests` のトリガ一覧にも名前を足してある
- **親を持つ表を作ったら、「親を付け替える UPDATE」を必ず検体に入れる。**
  **`Designer/ddl/` の `REFERENCES` を全部洗った。** `journal_lines` のほかに親を持つのは
  `partner_invoice_registrations`（親は `partners`）・`accounting_periods`（親は `fiscal_years`）・
  `sub_accounts`（親は `accounts`）・**`partners.parent_partner_id`（名寄せの親）**の 4 つ。
  **どれも「親の状態で子の可変性が決まる」形の不変を持たない**ので同じ穴は無い——
  名寄せの親はいちばん近いが、守っているのは**深さ**であって状態ではない（ADR-0028）。
  **状態で縛る親子を作った日に、この形を思い出すこと**
- **トリガの条件に `OLD` が出てきたら、`NEW` も要るかを必ず問う。**
  「変更前がどうだったか」と「変更後がどうなるか」は別の問いである

## L-26 `INSERT OR REPLACE` の暗黙の DELETE がトリガを鳴らさず、計上済みが下書きに戻せた

**2026-09-03。L-25 と同じ回の自己レビュー（設計とテストの観点）が指摘し、
インメモリ SQLite で再現して確かめた。**

**何が起きたか**

SQLite は、**REPLACE が制約充足のために消す行の DELETE トリガを、
`PRAGMA recursive_triggers` が OFF のあいだ発火しない**（既定は OFF。本リポジトリはどこでも立てていない）。
だから次の 1 文が通る。

```sql
INSERT OR REPLACE INTO journal_entries
    (id, fiscal_year_id, transaction_date, posting_date, status, entry_type, entered_at)
VALUES (<計上済みの伝票 id>, 1, '2026-05-20', '2026-05-20', 'draft', 'normal', '2026-05-20 10:00:00');
```

`trg_journal_entries_no_posted_insert` は `NEW.status = 'posted'` しか見ないので鳴らず、
既存の計上済み行は `trg_journal_entries_posted_no_delete` を**鳴らさずに消え**、同じ id の下書きに差し替わる。
明細は id が同じままぶら下がるので、**計上済みの伝票が 1 文で下書きに戻る**。
明細側も同じで、`id` をぶつければ**計上済みの明細が 1 行黙って消える**（I-01 も同時に破れる）。
実測では **`id`・冪等キー・明細の `id`・`UPDATE OR REPLACE` の 4 経路**が通った。

**なぜすり抜けたか**

- **検体が「素の DML」しか無かった。** `JournalImmutabilityTests` は `INSERT` / `UPDATE` / `DELETE` を
  並べていたが、**衝突解決の指定（`OR REPLACE`）を付けた形が 1 本も無かった**。
  SQL の「文の種類」で網羅したつもりが、**同じ文が別の意味を持つ書き方**を落としていた
- **L-25 と同じ日に見つかったのに、別の穴だった。** L-25 は「OLD しか見ていない」、
  こちらは「暗黙の DELETE を誰も見ていない」。**1 つ塞いだから安心、にならない**
- **PRAGMA の既定を確かめていなかった。** `Recursive Triggers` はどこにも書かれていない。
  **テスト用の接続（`TestDatabase`）は `Foreign Keys=True` を明示しており、
  稼働側（`appsettings.Development.json`）はそれすら書いていない**——
  **明示している設定の隣に、明示していない設定がある**。稼働側ほど当てはまる

**次から何で捕まえるか**

- **機械で守った。** 衝突そのものを拒むトリガを 4 本足し（`no_replace_posted_insert` /
  `_update` × 伝票・明細）、`JournalImmutabilityTests` に 4 経路の検体を入れた。
  **接続の PRAGMA に頼らない**——ここは「手作業の SQL からでも通る最後の関門」であり、
  接続ごとの設定は、まさにその手作業の経路で外れる
- **不変を守るトリガを書いたら、`OR REPLACE` を必ず 1 本試す。**
  `OR IGNORE` / `OR ROLLBACK` は行を消さないので同じ穴は無い
- **PRAGMA の既定値は、明示していない項目こそ確かめる。**

## L-27 「補助科目を使う」がオフの科目に補助科目を付けた明細が、計上まで通る

**2026-09-04。探索的テストで見つけ、実際に計上して確かめた**（伝票 36。計上済みなのでもう動かせない）。

**何が起きたか**

`accounts.requires_sub_account = 0` の現金に補助科目 `X001` を作り、
「現金 700 / 小口現金 700」の仕訳でその補助科目を選んで**計上できた**。

通ってしまう経路が 3 つ重なっている。

1. **補助科目マスタの勘定科目の候補が絞られていない**（105 件すべて出る）
2. **補助科目マスタに保存の関門が無い**（L-28）
3. **計上の関門も見ていない**——`JournalEntryValidator.ValidateSubAccount` は
   「補助科目が**無い**とき `RequiresSubAccount` なら拒む」と
   「**ある**とき実在と親の一致を見る」の 2 つだけで、
   **`RequiresSubAccount` が false なのに補助科目が付いている場合を見ていない**

**何が壊れるか。** 貸借も残高も合うのでデータは壊れない。壊れるのは**マスタの設定の意味**である——
`requires_sub_account` は実質「補助科目が**必須**か」だけを表し、
「補助科目を**持てる**か」は誰も守っていない。補助元帳は「補助科目が正しい親に属していること」を
前提にする（`ValidateSubAccount` のコメント）が、**その親が補助科目を持つ設計かは前提にしていない**。

**なぜすり抜けたか**

- **検体が「必須なのに無い」と「親が違う」の 2 つだけだった。** `RequiresSubAccount` は
  `true` の側しかテストされていない（`AccountingFixture` は普通預金だけを `true` にしている）。
  **真偽の片側しか踏んでいない述語は、もう片側で何が起きるかを誰も見ていない**
- **マスタどうしの整合を見るテストが 1 本も無い。** 単体の不変条件（I-01〜I-17）は
  「仕訳が正しいか」を見るもので、**「マスタの設定が仕訳に効いているか」は別の問い**である
- **画面の候補の絞りは、テストの対象外である。** `designcheck` も `lint_design.py` も
  「候補が正しく絞られているか」は見ない（見る手段が無い）

**次から何で捕まえるか**

- **`ValidateSubAccount` に「使わない科目に補助科目が付いている」を足す**（違反コードを 1 つ増やす）。
  ここが最後の砦で、画面の候補を絞っても迂回路（取込・投入 API）が残る
- **補助科目マスタの候補を `requires_sub_account = 1` で絞る**（画面での「押す前に見せる」）
- **真偽を持つマスタの設定を足したら、両側の検体を必ず置く。**
  `is_contra` / `is_company_wide` / `requires_sub_account` / `is_active` はどれもこの形

## L-28 マスタに保存の関門が無く、DB の制約に当たると全部が同じ定型文になる

**2026-09-04。探索的テストで 3 例（勘定科目・部門・自社情報）を実測。**

**何が起きたか**

会計コアの保存の関門は `JournalSubmitGate` と `CompanyProfileSubmitGate` の **2 つだけ**である
（`AccountingSubmitPipeline` の配線）。**勘定科目・補助科目・部門・税区分の 4 マスタには 1 つも無い。**
そのため DB の制約に当たった保存は、すべて `SaveFailureMessage` の定型文になる——
「保存できませんでした。入力内容を確かめ、画面を開き直してもう一度お試しください。」

実測した 3 例。

| やったこと | 出た文言 | 本来言うべきこと |
|---|---|---|
| 勘定科目に既存コード `1100` | 定型文 | 「科目コード 1100 は既に使われています」 |
| **部門で 2 つ目の「全社共通」** | 定型文 | 「全社共通の部門は 1 つだけです」 |
| 自社情報の決算月 `13` | 定型文 | 「決算月は 1〜12 の月で入力してください」 |
| **税区分で「課税売上」＋税率区分なし** | 定型文 | 「課税の区分には税率区分が要ります」 |

**4 番目は税の整合そのものである。** DDL は「課税でない区分に税率区分は付かず、課税の区分には必ず付く」を
2 本の `CHECK` で守っているが、**画面の税率区分に必須の印が無い**ので、
利用者は「入れなくてよい欄」だと思って保存し、定型文だけを受け取る（[21 §1](../21_画面の原則.md)の
「押す前に見せる」に反する。**条件つき必須は印を出し分ける必要がある**）。

**とくに 2 番目が悪い。** コードも名前も正しいのに拒まれ、
**「全社共通は 1 つだけ」という規則が画面のどこにも書いていない。**
利用者には**何を直せばよいか手がかりが無い**。

**対比**: 同じ回に確かめた**取引先部品の関門は堅い**——名寄せの親に自分自身を選ぶと
「その取引先自身を名寄せの親にはできません。別の取引先を選ぶか、空欄にしてください」、
法人番号なら「国税庁の法人番号公表サイトで確かめて入力し直してください」と、
**次の一手まで返す**。自社情報の法人番号も同じ。**足りないのは会計コアのマスタだけ**である。

**なぜすり抜けたか**

- **`SaveFailureMessage` は自ら「ここに落ちてくるのは関門が拾えなかった失敗だけで、
  それは『関門が 1 つ足りない』という合図である」と書いている。**
  合図は鳴っていたが、**鳴ったことを誰も見に行っていなかった**
- **DDL の制約はテストで検査されている**（`SchemaConstraintTests`）。
  だから「守られている」ことは確かめられていた——**「利用者のことばで守られているか」を
  誰も確かめていなかった**。関門の有無は、制約のテストからは見えない
- **画面から踏まないと分からない。** DDL の一意制約は 5 つ（`accounts.code` /
  `sub_accounts (account_id, code)` / `departments.code` / `ux_departments_company_wide` /
  `tax_categories.code`）あり、どれも C# のテストからは「利用者に何が出るか」が見えない

**次から何で捕まえるか**

- **マスタにも保存の関門を置く**（L-27 の直しと同じ回でやる）
- **DDL に制約を足したら、「その制約に当たったとき利用者に何が出るか」を必ず決める。**
  決めないなら、それは定型文になるということである
- **`SaveFailureMessage` に落ちたことを数える。** いまは `onSaveFailure` に原文を渡す口があるので、
  **開発機ではそれをログに出し、探索のたびに「関門が足りない場所」を洗い出せる**

## L-29 使っている勘定科目の「科目区分」を、警告なしで変えられる（過去の帳簿の意味が遡って変わる）

**2026-09-04。探索的テストの 2 巡目で実測（変更して保存し、元に戻した）。**

**何が起きたか**

勘定科目の詳細画面で、**計上済みの仕訳明細が既にある科目の「科目区分」を変えて保存できる。**
実測は `通信費`（`6070`。計上済みの明細 1 本）を **費用 → 資産**に変え、「更新しました」が出た。
確認も警告も出ない。**科目コード・科目名も同じように変えられる。**

**何が壊れるか。3 つある。**

1. **総勘定元帳の「期間内累計」の意味が、過去の行まで遡って変わる。**
   その画面自身が「**資産・負債・純資産の科目は会計年度をまたいで積み上げ、
   収益・費用の科目は会計年度ごとに積み直します**」と書いている。区分を変えると、
   **1 行も動かしていない過去の帳簿の数字が変わる。**
2. **不変条件 I-13（損益科目の仕訳明細には部門がある）が、取り返しのつかない形で壊れる。**
   いま**計上済みで部門を持たない資産・負債の明細が 58 本**ある（実測）。
   そのどれかの科目を収益・費用へ変えた瞬間、**58 本が I-13 違反になる**。
   **計上済みは不変（[ADR-0004](../decisions/0004-優良な電子帳簿への準拠と仕訳の不変性.md)）なので、
   もう直せない。** 区分を戻す以外に手が無い。
3. B/S・P/L（フェーズ 4）が、過去の金額を別の区分へ入れ替える。

**同じ形が税区分にもある（こちらも実測して、元に戻した）**

`journal_lines` は**税区分を FK でしか持たない**——`applied_rule_version` は制度ルールの版で、
**その税区分の「課税区分」「税率区分」そのものの写しは無い**。

実測は `TP`（`課税仕入（標準税率）`。**計上済みの明細 4 本が使っている**）の**課税区分を
「課税仕入」→「課税売上」に変えて保存**した。**「更新しました」で通る。** 確認も警告も無い。
そのとき税区分名は「課税仕入（標準税率）」のままなので、**名前と中身が食い違った状態**になる。
`IsUpdateProtected` は 4 マスタのどのフィールドにも付いていない。

**これは仕入を売上に読み替える書き換えである。** 過去の仕訳の税の扱いが遡って変わり、
[20 §2](../20_実装の原則.md) の「後日マスタを更新しても過去を再計算しない」は、
**税率の版については守られているが、税区分そのものの意味については守られていない。**
フェーズ 3（消費税）の着手前に決めること。

**なぜすり抜けたか**

- **L-28 と同じ根**（マスタに保存の関門が無い）だが、**症状が逆である**——
  L-28 は「DB が拒むのに文言が定型文」、こちらは**DB が何も拒まない**。
  だから `SaveFailureMessage` の合図すら鳴らない。**静かに通る。**
- **不変条件のテストは「仕訳を保存するとき」しか見ていない。**
  I-13 を検査するのは `JournalEntryValidator` で、**マスタを更新する経路にはどの検査も無い。**
  「明細は正しく作られた」ことは守られているが、**「あとから前提を動かされない」ことは誰も守っていない。**
- **不変条件を「保存時の検査」としてだけ書いてきた**のが本当の抜けである。
  I-13 は*仕訳と科目の関係*についての条件で、**科目の側を動かしても破れる**。

**次から何で捕まえるか**

- **勘定科目の保存の関門で、使用中の科目の区分変更を拒む**——
  「この科目には計上済みの仕訳が 12 件あります。科目区分は変えられません。
  新しい科目を作って、以後の仕訳をそちらへ記帳してください」。
  **科目コードも同じ**（帳簿の見出しが遡って変わる）。科目名は変えてよい（識別ではなく呼び名）
- **不変条件ごとに「これを破れる経路」を数える**という見方を入れる。
  I-13 なら「仕訳を保存する」「明細を移す」（L-25 で塞いだ）「**科目区分を変える**」の 3 本があった
- **DB のトリガでも守れる**（アプリを迂回しても効く）——
  `accounts` の `UPDATE` で、`category` が損益とそれ以外の間をまたぐとき、
  その科目の計上済み明細が 1 本でもあれば `RAISE(ABORT)` する

## L-30 「元の伝票」を手で入れられるのに、押すと定型文で拒まれる（どちらへ動かしても行き止まり）

**2026-09-04。探索的テストの 3 巡目で実測。**

**何が起きたか**

振替伝票の「元の伝票」は**参照欄として編集できる**（候補ダイアログも開き、× で消せる）。
しかし**利用者がここを触ってよい場面は 1 つも無い**——種別は画面で変えられず（通常のまま）、
取消・訂正の伝票はサーバが作るときに元の伝票を入れるからである。

実測は 2 方向とも行き止まりだった。

| やったこと | 何が起きるか |
|---|---|
| **通常の伝票に元の伝票 38 を入れて「計上する」** | **定型文**「保存できませんでした。入力内容を確かめ、画面を開き直して…」。伝票も伝票番号も増えない（実測。41 件・最大番号 38 のまま） |
| 訂正の下書きで元の伝票を × で消して保存 | 同じ形（`CHECK (entry_type NOT IN ('correction','reversal') OR original_entry_id IS NOT NULL)` に当たる） |

止めているのは DDL のトリガ `trg_journal_entries_original_only_for_amendment` で、
その文言は「原仕訳を指定できるのは訂正・取消だけ。」——**開発者のことばであって、利用者には出ない。**

**なぜすり抜けたか**

- **仕訳には関門がある**（`JournalSubmitGate`。この製品でいちばんよく試されている場所）。
  にもかかわらず、**「利用者が触れてはいけない欄」という観点が関門の外にあった。**
  関門が見ているのは「入った値が正しいか」で、「**そもそもこの欄を出してよいか**」は画面の話だからである
- **L-28 と同じ「定型文で拒まれる」形だが、こちらはマスタではなく仕訳で起きている。**
  「マスタに関門が無い」という括り方では拾えない
- **`JournalSubmitGate` は `SystemAssignedFields` を持っている**（`PostedBy` / `EntryNo` /
  `PartnerNameSnapshot` など、下書き保存のとき差分から外す欄）。
  **`OriginalEntry`（画面のフィールド名）はその一覧に入っていない**——「サーバが決める欄」の一覧はあったのに、
  この欄が漏れていた

**次から何で捕まえるか**

- **画面で `IsViewOnly` にする**（[21 §1](../21_画面の原則.md)「押せるのに拒まれる欄を残さない」）。
  取消・訂正では値が入って見えるだけでよい
- **関門でも拒む**（画面を迂回する経路のため）。文言は「元の伝票は取消・訂正のときにシステムが入れます。
  手で入れることはできません」
- **「サーバが決める欄」の一覧を 1 か所にする。** いま `SystemAssignedFields` と
  画面の `IsFocusSkip` / `IsViewOnly` が別々に並んでおり、**どちらかにだけ足すと今回の形になる**

## L-31 別の人が先に保存していたとき、「入力内容を確かめ」としか言わない

**2026-09-04。探索的テストの 4 巡目で実測（対照実験つき）。**

**何が起きたか**

**楽観ロックそのものは効いている。** 実測はこうである。

1. 下書き 48（`optimistic_locking = 2`）をブラウザで開く
2. **`sql` CLI で外から**「別の人が先に直した」ように書き換える
   （`description` を変え、`optimistic_locking` を 3 にする）
3. ブラウザ側で摘要を直して「下書き保存」→ **拒まれる。DB は 2 の値のまま**（＝上書きされていない）
4. **対照**: 画面を開き直して（版 3 を読んで）同じ操作をすると**成功する**（版 4 になる）

**守りは正しい。問題は文言である。** 3 で出るのは `SaveFailureMessage` の定型文——
「保存できませんでした。**入力内容を確かめ**、画面を開き直してもう一度お試しください。…」。

**入力内容は 1 つも悪くない。** 悪いのは「開いたあとに別の人が変えた」ことである。
本当は「**この伝票は、あなたが開いたあとに別の人が変更しました。画面を開き直して、
その変更を確かめてからもう一度入力してください。**」と言うべきで、
そう言わないと利用者は**同じ入力をやり直して同じ所に落ちる**か、
**同僚の変更があることに気づかないまま**になる（[21 §2-3](../21_画面の原則.md)）。

**削除との競合も同じ形である。** 下書き 45 を開いたまま CLI でその行を削除してから保存すると、
**保存は拒まれ、行は作り直されない**（緑。伝票の総数も最大 id も動かない）。
文言はやはり定型文で、ここでの正しい言い方は
「**この伝票は、あなたが開いたあとに削除されました。**」である。

**なぜすり抜けたか**

- **L-28・L-30 と根は同じ**（関門が拾えなかった失敗が全部 1 つの定型文になる）が、
  **見つけ方が違う**——版の食い違いは**送られてきた値をいくら見ても分からない**。
  保存済みの版と突き合わせて初めて分かる。だから「入力の検査」を厚くしても永久に拾えない
- **同時操作は台本に無かった。** 2 つのブラウザを並べる必要があると思われていて、
  [qa/04](04_実機操作テスト.md) にも「**ブラウザ拡張の制約**で確かめられない」と書いてあった。
  **`sql` CLI で片方を演じれば 1 つの画面で足りる**（下の「次から何で捕まえるか」）

**次から何で捕まえるか**

- **関門で版を見て、専用の文言を返す。** `JournalSubmitGate` は既に保存済みの行を読んでいるので、
  差分の `OptimisticLocking` と突き合わせる場所はある
- **同時操作の台本を「`sql` CLI で相手を演じる」形で書く。**
  ①画面で開く ②CLI で外から変える ③画面で保存して拒まれることを確かめる
  ④**開き直して同じ操作が通ることを確かめる（対照）**。
  **④が無いと「たまたま失敗しただけ」と区別できない**

## L-32 一意制約は「見た目の一意」を守らない——`1100` と `1100 `（末尾に空白）が別の科目として並ぶ

**2026-09-04。探索的テストの 5 巡目で実測（作って、無効にした）。**

**何が起きたか**

勘定科目の新規作成で**科目コードに `1100 `（末尾に半角空白）**を入れて保存すると、
**通る**（id 106）。既にある `1100`（現金）とは別の行になる。

**一覧では見分けがつかない。** 科目コードで `1100` を検索すると 2 件出て、
**どちらの科目コード欄も「1100」と表示される**（実測）。総勘定元帳の科目コード欄も同じである。

DB の値は `[1100]`（4 文字）と `[1100 ]`（5 文字）で、`UNIQUE` から見れば確かに別物である。

**どこまで広がるか**

- `accounts.code` は `TEXT NOT NULL UNIQUE` で、**書式の `CHECK` が無い**
  （DDL のコメントは「4 桁」と書いているが、守っているものは何も無い）
- **同じ形が `sub_accounts.code`・`departments.code`・`tax_categories.code`・`partners.code`
  にもある**（どれも `TEXT ... UNIQUE` で正規化なし。**DDL と関門を読んで確かめた。実測は勘定科目だけ**）
- 関門で正規化しているのは**法人番号だけ**（`CorporateNumber.Normalize`）。コードは 1 つも通っていない
- 前後の空白だけではない。**全角の `１１００`・大文字小文字違いも「別物」**になる
  （`UNIQUE` は既定で大文字小文字を区別する）

**なぜすり抜けたか**

- **`UNIQUE` があるので「重複は守られている」と思っていた。**
  守られているのは**バイト列の一意**であって、**利用者が見る一意ではない**
- **重複のテストは「同じ文字列」でしか試していない**（`SchemaConstraintTests`）。
  **「人には同じに見えるが機械には違う値」を試していない**
- L-28（マスタに関門が無い）と根は同じだが、**症状が逆で、こちらは DB が拒まない**。
  だから `SaveFailureMessage` の合図すら鳴らない

**次から何で捕まえるか**

- **関門でコードを正規化する**（前後の空白を落とす。全角英数を半角に寄せるかは開発者に聞く）。
  **正規化してから重複を見る**——正規化しても保存前に重複が見えるので、
  「科目コード 1100 は既に使われています」と返せる（L-28 の直しと同じ回）。
  **やり方はこの製品の中に既にある**——`InvoiceRegistrationNumber.Normalize`（前後の空白を落とし、
  小文字と全角数字を拒む）と `CorporateNumber.Normalize` が同じことをしている。
  **識別子を扱う欄のうち、正規化していないのはコード列だけである**（2026-09-05 に実機で確かめた。[qa/04](04_実機操作テスト.md)）
- **書式を決めて `CHECK` にする**（DDL のコメントが「4 桁」と言っているなら、そう書く）
- **一意制約のテストに「見た目が同じで機械には違う値」を必ず 1 本入れる**——
  前後の空白・全角・大文字小文字。**これは全部のコード列に効く型である**
