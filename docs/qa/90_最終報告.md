## 2. 何が原因で、どういう種類のバグが多かったか

**これが本書で最も価値のある節である。** 件数より、次の作り方を変えるのはこちらだ。

### 2-1. 圧倒的に多いのは「静かな失敗」

直した 15 件のうち **12 件が「例外もエラーも出ないまま、間違った結果が確定する」型**だった。

| 型 | 実例 |
|---|---|
| **無言でデータが消える** | 入出金の下書きが、開いていないページのぶんごと削除（BUG-0094）／同一内容の銀行明細の 2 件目が「重複」として削除（BUG-0162） |
| **無言で 0 円になる** | 売上の既定税区分が引けないと税額 0 円の請求書を一括生成（BUG-0144）／同じ欠落が SQL 側にも残っていて入金見込みが約 10% 過小（BUG-0251） |
| **無言で警告が消える** | 予算警告の閾値行が無いと比較が NULL 化してポータルの警告が行ごと消える（BUG-0250）。**「警告が無い＝健全」に見える** |
| **無言で誤った値が保存される** | 償却の年度判定が 1 年ずれて取得価額を超えて償却（BUG-0090）／繰越フラグが残って保存のたびに翌期首を洗い替え（BUG-0093）／ヘッダの導出値がサーバ側で更新拒否され古い額で仕訳（BUG-0126） |
| **無言で通ってしまう** | 合算請求済みの検収でも確定取消が通り、請求書だけが残る（BUG-0128）／別取引先の請求書を合算先にできる（BUG-0239） |

**共通する構造**: どれも `designcheck` は 0 件、不変条件スイートも全緑のまま通過する。
**静的検査で「壊れている」と分かるバグは、もうこのアプリにはほとんど残っていない。**
残っているのは「読み込めるし、動くし、数字も出る。ただし間違っている」型である。

### 2-2. 「同じことを 2 か所に書いた」が次に多い

- 生成側は `recurring` / `recurring_annual` と書き分けているのに、判定側が区別を落としていた（BUG-0145）
- 取込時は本番と突合して連番を振るのに、保存時はプレビュー内だけで振り直していた（BUG-0162）
- スクリプト側は「既定税区分が無ければ止める」と直したのに、同じ判定の SQL 側が取り残された（BUG-0144 → 0251）
- 資金繰りの 90 行の SQL が、ポータル用ファイルへ逐語コピーされている（BUG-0257）

**教訓**: **同じ概念の判定を 2 か所に書いたら、その時点で片方が腐る**。
直すときは必ず「この判定は他にどこにあるか」を先に探すこと。今回はそれで**対称の穴**を
何度も同時に塞げた（BUG-0145 の月額側、BUG-0130 の 3 経路、BUG-0251 の 2 ファイル）。

### 2-3. 権限は「条件が空か」では見つからない

最重要の発見（BUG-0259）は**権限の全数監査では見つからなかった**。
`ExpenseCategory` 自身の読み取り条件は空＝誰でも読める。しかし**その中のフィールドが
経理限定の `Account` モジュールを参照していた**ため、非経理ユーザーが検索すると
サーバが参照先の解決に失敗して 400 を返す。結果、**一般社員は経費申請を 1 件も作れなかった**
（＝経費精算が全社的に使用不能）。

**教訓**: 認可は**モジュール単位ではなくグラフで見る**。「このモジュールを読む人は、
参照先も読めるか」を問わないと同型を取りこぼす。今回は全モジュールを走査して
同型が 1 件だけであることを確認した。

### 2-4. Validation（実務で使えるか）は、Verification と別の穴を出す

計算が正しくても実務で使えない、という所見が **Val だけで 40 件以上**出た。代表例:

- 銀行の一括起票で**部門を 1 行ずつしか選べない**（月数百明細のペルソナで一括起票の意味が消える）
- 勘定科目が **70 件のフラット select**。科目コード直接入力もインクリメンタル検索も無い
- **赤黒訂正（反対仕訳の自動生成）が無い**。既存データにも手作業の訂正 2 本が残っている
- 経費の経理処理が 1 件ずつ 3 段階クリック（100 件で 600 操作超）
- 交際費の 1 人あたり 1 万円基準（令和 6 年度改正）を判定していない

**これらは「バグではない」ので放置されやすいが、テンプレートとして売る以上は
「導入したその日に不満が出る点」である。** 台帳止めとして全件記録した。

### 2-5. 自分が作り込んだリグレッションからの教訓

BUG-0127（検収仕訳の税区分）の修正で**検収確定を全件失敗させ、3 回直して 3 回とも外し、撤回した**。

- **`designcheck` 緑・不変条件全緑でも、動作は何も保証されない。** 画面で押すまで直っていない
- **症状の説明を思いついた時点で満足しない。** 3 回とも「もっともらしい説明」で満足して外した。
  動いている実例との差分を**全部**数え上げるべきだった
- 詳細は `docs/12` の **FB-053**（原因は未特定のまま。外した診断も記録した）

## 4. ユーザーの判断を待っているもの（GO 待ち）

全 110 件は `02_バグ台帳.md` の「台帳止め（GO 待ち）」表にある。**とくに判断してほしい 3 件**:

### ① 認可の穴（BUG-0211 / 0212 / 0213 / 0233・P0）

**実機で確認済み**: 非承認・非経理の一般社員が `/api/module_data/list` に任意の id を投げて
**他人の承認フロー・経費明細（領収書列を含む）を 200 で取得できる**。書き込みも**サーバ側の認可が皆無**で、
非特権ユーザーのリクエストが 403 ではなく業務ロジックまで到達する（承認ボタンが出ないのは
WASM の描画制御にすぎない）。

**CLB の条件式では要件を表現できないことを実査で確認した**——`UserReadCondition` は
AppUser に対するユーザー単位のゲート、`DataReadCondition` は自モジュール列の行単位フィルタで、
両者は AND。「自分の行 ∨ 承認者なら全部 ∨ 経理なら全部」という OR は書けない。
`Exists` は SQL の EXISTS ではなく非 null 判定なので親を辿る副問い合わせにも使えない。

**3 案と推奨は BUG-0233 に全部書いた**（推奨は案A: 対象者別モジュール分割＝既存の
`MyApplication` / `ApprovalInbox` と同じ作法）。**この 1 件を読めば判断できる。**

### ② 検収仕訳の税区分（BUG-0127・P0・3 回失敗して撤回）

あきらめる（推奨）／税区分ごとに伝票を分ける／複数税率を非サポートと明示する、の 3 択。
実データの検収 9 件はすべて 10% のみなので**現時点の帳簿は正しい**。

### ③ 翌期繰越の陳腐化（BUG-0060・P0）

第 19 期の期首残高が **8,936,588 円ずれている**（不変条件 B03/B04 が検出）。
繰越をスナップショット方式のままにして陳腐化検知を足すか、再計算方式に変えるか。
