## 2026-08-12 検収の明細化と税額計算の是正（ADR-0049/0050・改善候補 A-1 起点・ユーザー設計提案→GO）

改善候補 A-1（分割検収から作った請求書の金額が受注全額に化ける）を、
ユーザーの提案「**そもそも検収が明細行を持つべきでは**」を受けて構造ごと直した回。

- **ADR-0049 検収に明細行（`acceptance_lines`）**: 受注明細のコピーで、摘要・数量・単位・単価・受注金額・税区分は
  読み取り専用、**編集できるのは「検収金額」だけ**。各行は `sales_order_line_id` で受注明細に紐づき、
  行ごとの残額自動セット・行単位の超過判定ができる。検収額・消費税額は明細合計からの導出に変わり手入力を廃止。
  請求書生成は検収明細をそのままコピーするだけになり、**明細合計＝検収額が構造的に成立**する。
  行の追加・削除ボタンは出さない（`CanCreate/CanDelete: false`。**スクリプトからの `AddRows()` は妨げられない**ことを実機確認）
- **A-1 のもう一段深い真因**: 明細コピーを入れても金額が化けたため追ったところ、
  `Invoice.Lines_OnDataChanged` が **`金額 = 数量 × 単価` を無条件に再計算**しており、書き込んだ検収額をその場で潰していた。
  `Amount` への代入自体が同ハンドラを再帰的に呼ぶため、代入した値が同じイベント内で消える構造。
  これは検収由来に限らず**利用者が請求明細の金額を手で直しても消える**状態だった。
  自動計算を「検収に紐づかない行」だけに限定して解決
- **行単位のリアルタイム赤字警告**: 請求明細が元の検収明細の金額を超えたら、発行時ではなく**入力したその場で**
  行・超過額つきで警告する（ユーザー指定）。**ブロックはしない**（正当な増額を機械が判定できないため人に委ねる）
- **ADR-0050 税額計算を明細の税区分ベースへ**: 従来は明細の税区分を無視して合計に一律 10% を掛けていた
  （8%・非課税・免税・不課税の行にも 10% が乗る不具合）。**税率ごとに集計してから 1 回だけ端数処理**する
  インボイス制度の要求に合わせた。**税区分は必須**にし（見積・受注・請求の各明細）、
  既定値は**コードに埋めず `tax_categories.default_for` マスタ列**で決める（ユーザー指摘: 「10% が普通」は 2026 年だけの話）。
  `SALES_10` のハードコードは `RecurringRun` / `SesBilling` / 資金繰り予測 / ポータル警告からも一掃
- **移行**: `ddl/470`（既定税区分列）・`ddl/471`（`acceptance_lines` 新設＋既存 9 件の復元＋`invoice_lines.acceptance_line_id` 紐付け）。
  分割検収 1 件（A-26-009）は最終行で差額調整。**帳簿は 1 円も動かない**（売上仕訳は検収額合計で計上済みのため）
- **実機検証**: `soumu_bucho` で 10 項目を通した（残額自動セット／明細編集の自動再計算／確定仕訳／
  請求書の金額が化けない・開き直しても化けない／行単位の赤字警告／税区分 8% への追随／マスタ既定の自動セット／
  8%+10% 混在の端数処理 89,333 円／移行済み INV-26-017 への警告）。詳細は ADR-0049 末尾の表。
  検証で作った検収 2 件・請求書 2 件・仕訳 1 本は削除済みで、貸借一致・孤児レコード 0 件を確認
- **ドキュメント追随**: 体験シナリオ `02_営業_受託/03` を「明細で分ける分割検収」へ改題・全面書き換え

### 2026-08-14 — 入出金起票の作り直しと部門の必須化を決定（ADR-0055 / ADR-0056・実装前）

- **調査で分かったこと（実データ）**:

  紐づかない費用は全社共通**」。決め方は三段（人が画面にいる経路はエラーで止める／機械経路は自動解決／
  最後の保険が全社共通）で、これは税区分の
  「経路が明示 → 科目マスタの既定 → `MarkRemainingLinesOutOfScope()`」と同じ型。
  `journal_lines.department_id` を **NOT NULL** 化し既存を全社共通へ移行する
  （条件付き NOT NULL は SQLite の CHECK がサブクエリ不可のため書けない。ADR-0052 の税区分と同じ形を採る）。

  財務諸表が 1 円も動かない管理会計の軸だから許され、かつ**これが無いと部門必須化が運用に耐えない**。

- **実装時に確認すること（ADR に明記済み）**: ①明細だけ変更したとき親の `UPDATE` が走るか（走らないと

### 2026-08-17 — 経費申請の明細行化（ADR-0066・改善候補 E-1／ユーザー GO 済み）

`docs/tasks/03_経費申請の明細行化.md` を起点に、設計 → ユーザー GO → 実装 → 実機検証 → ドキュメント現行化まで実施。
**正典は `docs/decisions/0066-経費申請の明細行化.md`**（設計・追補・実機検証の表を含む）。

**決めたこと（設計の芯）**

- **段階分けはしない。**「第 1 段階は費目をヘッダ固定」案は、月末のレシートが費目混在なのが常態で実需を満たさず、
  体験シナリオを 2 回書き換えることになって総コストが増えるため採らなかった。
- **「作らない（複製で回す）」も採らない。** 複製が軽くするのは申請者の入力で、**承認回数は 1 件も減らない**。
  痛点は承認側（課長・部長 約 20 名）にあるので代替にならない。
- **承認ルート＝判定額は申請合計・費目は行ごと。** 行ごとに `approval_route_rules` を解決し、
  得られたテンプレートの段を承認者キーで畳んで 1 本の段列に合成する。
  **明細 1 行なら従来と同一の段列に帰着する**ので、既存 14 件の移行でルートは変わらない。
- **ヘッダの `amount`/`tax_amount` は新設せず、意味を「明細合計の導出値」に変えた。**
  ポータル件数・精算処理待ち・資金繰り予測・申請中ビュー・支払仕訳がこの列を見ているため、**下流を 1 行も変えずに済んだ**。
- **仕訳は 1 申請 1 伝票**（借方＝明細ごと／税行＝借方行ごと／貸方の未払金 1 行）。
  税行を行ごとにするのは、経費はレシート記載の税額が正だから（ADR-0050 の「税率ごとに 1 回」は自社発行の請求書側の規約）。

**実装中に決めた追補**（いずれも ADR-0066 に記載）

1. **事前申請も明細を持たせた。** 明細が無いと費目ベースのルート判定が効かず、
   交際費の事前申請が総務段を素通りする＝統制の穴になるため。見込み額は申請時の明細合計のスナップショットへ変更し、
   実費確定フラグ（`ddl/601`）を追加した。
2. **実費確定の再承認判定を「段構成の突き合わせ」に変更。** 明細を編集できる期間ができたので、
   金額区分の比較だけだと「実費確定中に交際費の行を足す」ケースを取りこぼす。
3. **AI 読み取りの添付は明細行へ移せない**（CLB のスクリプトから `FileGuid`/`FileSize` に到達できない）。
   行ごとの領収書は明細グリッドの添付欄を使い、AI に読ませた 1 枚はヘッダに残す形にした（FB-048）。

**DDL**: `600_expense_lines.sql`（新設＋移行）／`601_expense_actual_confirmed.sql`／`602_expense_header_tax_backfill.sql`

**実機で見つけて直した不具合 3 件**

1. **AI 読み取りで金額だけ 0 になる。** `Lines.AddRow()` が**その場で** `Lines_OnDataChanged` を発火させ、
   まだ空の行で合計が 0 に書き戻されるため、受け皿から行へ写すときには値が消えていた（ADR-0053 の実例）。
   受け皿の値を `AddRow()` より前に退避して解決。**CLB 改善提案 FB-047 として記録**。
2. 合成時の代表テンプレートが実態とずれる（3 段のルートなのに 2 段のテンプレートが記録される）→ 段数最大のものに変更。
3. 移行でヘッダの「うち消費税」が NULL のまま残る → **新設した不変条件 D05 が 11 件検出** → `ddl/602` で是正。

**検証**

- 承認ルート **13 ケース**を実機で申請（境界 4・費目混在 4・行順・同一費目・walk-up・明細 0・ルート未一致）。
  すべて期待どおり。ブロックした 3 件はテンプレート未設定・段 0・履歴なしで**中途半端な状態が残らない**。
- 仕訳は明細 5 行（課税・不課税・税額手入力・固定資産・案件別）の申請で **10 行**を SQL 検算。貸借差額 0。
  固定資産は資産の行だけ台帳へ（取得価額＝税抜本体・取得日＝行の利用日・名前＝行の摘要）。
- 事前申請 4 ケース（幅内・110% 超・**区分跨ぎ**・実費での計上）。
- **更新経路**（却下 → 明細修正 → 再申請）でヘッダ合計が DB でも更新されることを確認。
  ここは `IsUpdateProtected` を付けなかった判断の裏取りでもある（付けていれば静かな失敗になっていた）。
- 移行の同一性: 9 指標が完全一致（仕訳・固定資産・承認フロー/order/member/history は 1 行も動かない）。
- **回帰**: designcheck 0 件／`lint_design.py` error 0・warn 37（着手前と同数）／
  不変条件 SQL **32 合格・7 違反＝着手前と完全に同一**（A09=1・A11=13・B03=10・B04=1・C05=1・C08=1・C10=1）。
- **検証で作ったデータ（申請 21 件・仕訳 6 本・固定資産 1 件・通知）はすべて削除**し、
  DB の指紋が移行直後と一致することを確認。移行済みデータで一巡を試した申請 1 件も検証前の状態へ戻した。

### 【8/17 夜】E-1 の UI を作り直す（ADR-0066 の UI 改訂・4 ブロック構成）

**ユーザーからの指摘**（実機を見ての 3 点）:

1. 新規作成画面が複雑で、パッと見て何をすればいいか分からない（1 明細あたりの情報が多すぎる・14 列）
2. **AI 読み取りがほぼ機能していない**。2 枚目を読ませると 1 枚目が消え、明細が全部上書きされる
3. AI 入力しかないように見える。手作業で入れる導線が分からない

**2 の原因はこちらの前提の誤り**。「AI はヘッダの受け皿にしか書かない」と決めつけて受け皿→行のコピーを組んだが、
実際の `AITextAnalyzerField` は **`Lines` コレクションにも非決定的に書き込む**（1 回の読み取りで行が二重に増え、
2 回目で既存行を上書きしていた）。**レシート 1 枚しか試さず、2 枚目の挙動を検証しないまま
「2 行目が足される」と体験シナリオに書いた**のも失敗。プローブ（`AddRow()` を止めた実行）で抽出側の書き込みと確定させた。

**やったこと**: ユーザー提案の 4 ブロック構成を採用し、**入力欄のカードを「明細テーブルの行そのもの」**にした
（`ExpenseRequestLine` を `ModuleField`＝`editing_line_id` で埋め込む）。
**その行が AI 読み取りと領収書 FileField を自分で持つ**ので、1 回のアップロードで抽出値とファイルが同じ行に載る。
ユーザーが「最悪」と言った 2 つの状態——**入力欄で読ませてリストにもう一度アップロードし直す**／
**領収書が有限枚しか添付できない**——をどちらも回避できる。

- 入力中の行は `expense_request_id`・`line_no` とも NULL。**リストにも合計にも出てこない**。「追加」で両方が入る
- 行の削除で `line_no` を 1..N に詰め直す（`RenumberLines`）
- 既存明細の編集は**リストの行クリック → 入力欄に読み込み → 「この明細を更新」**
- 書きかけを残したまま申請・実費確定はできない（黙って捨てないための関門）
- **1 枚のレシートを複数明細に分ける**（機器 2 台を別々に固定資産登録）も成立する
- `ApprovalFlow.Initialize` の初期状態を `Pending` → `Draft`（明細追加で下書き保存されるようになったため）
- `ddl/603`（`expense_request.editing_line_id`）／不変条件 **D06** 新設

**CLB の実測知見（→ `docs/12` の FB-049〜052・FB-048 の訂正）**:
`ModuleField` は保存のたびに DB 列を自分の子の Id で上書きする（別レコードを開けない・画面外のインスタンス経由で回避）／
`NavigateTo` は同一モジュールではページを作り直さない（`Reload()` が正解）／
未保存で `Reload()` を呼ぶと例外／`AITextAnalyzerField` の書き込み範囲を制限できない／
**`FileField` はスクリプトからファイルを移せる**（FB-048 の「移せない」は誤りだった。カタログのスクリプト節を読んでいなかった）。

**検証**: 実機 19 ケース（U-01〜U-19）。**2 枚のレシートを続けて読ませても 1 枚目が無傷**であること、
それぞれに別の領収書が付くこと、1 枚を 2 明細に分けて**固定資産 2 件が別々に登録**されること、
仕訳（借方 4 行＋貸方 1 行・貸借一致）、事前申請の実費確定までを実機で通した。

**回帰**: designcheck 0 件／`lint_design.py` error 0・warn 37（着手前と同数）／
不変条件 SQL **33 合格・7 違反＝着手前と完全に同一**。検証データはすべて削除して指紋一致。

体験シナリオ 経費-11 を全面書き直し＋経費-01〜10 の入力手順を改訂／E2E 01_経費精算 4 本／
`docs/12`（FB-049〜052・FB-048 訂正）／`docs/qa/20_不変条件SQL`（D06 新設）。
