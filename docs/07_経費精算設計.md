> **更新: 2026-08-17 ADR-0066（経費申請の明細行化）を反映**: **1 申請が複数の明細（レシート 1 枚 = 1 行）を持つ**構成になった。費目・金額・利用日・案件・税区分・交際費 3 項目・固定資産・領収書は**行が持つ**。ヘッダの合計金額・うち消費税は明細からの導出値（画面では読み取り専用）、`expense_date` は「利用日」から「**計上日**（仕訳日付）」へ意味が変わった。承認ルートは「**判定額＝申請合計 / 費目＝行ごと**」で解決し、行ごとに得たテンプレートの段を重ね合わせる（§6）。事前申請も明細を持ち、見込み額は申請時の明細合計のスナップショットになった（§8）。データモデルは §2、入力ガードは §7 を参照。

## 0. 位置づけ（ユーザーの A/B モデル）

- **A＝会計コア（フェーズA）**: 市販の財務会計専門ソフト相当。**経理機能フラグ（`HasAccountingAccess`）保有者専用**。経理以外に触られてはならない（→B-8 の経理ゲート必須。現行はユーザー管理画面の「経理機能」チェックで直接付与・ADR-0043）。
- **B＝業務フロー部分**: 市販ソフトが対応しにくい「会社ごとの業務フローに合わせたアプリ」。**全社員が触る**。原課（営業部・開発部）が申請→金額や科目に応じて決裁権限者が変わる。
- **本アプリの価値は A と B の一体化**。経費精算は B の代表であり、承認完了後に A へ自動連携（仕訳）される。

### 2-1. 明細行（2026-08-17・ADR-0066 / ddl/600・601・602）

**1 申請 = 1 金額**をやめ、`expense_request_lines` を新設した。レシート 1 枚が 1 行になる。

| どこが持つか | 項目 |
|---|---|
| **明細**（`expense_request_lines`） | 利用日・費目・税区分・金額（税込）・うち消費税・案件・利用先・摘要・交際費 3 項目・固定資産フラグ・資産管理番号・領収書 |
| **ヘッダ**（`expense_request`） | 件名・目的・申請区分・支払先区分・支払先・部門（申請時スナップショット）・**計上日**・承認状態・精算ステータス・**合計金額**・**うち消費税**・見込み額・実費確定フラグ |

- **ヘッダの `amount` / `tax_amount` は新設せず、意味を「明細合計の導出値」に変えた。**
  精算処理待ち・ポータル件数・資金繰り予測・申請中ビュー・支払仕訳がこの列を見ているため、
  下流を 1 行も変えずに済んでいる（実測で確認した参照箇所:
  `Shell/PortalTodoData` `Shell/PortalQueueData` `Shell/PortalAlertData`
  `Management/CashFlowForecastData` `ddl/440_my_application_view` `Expense/ExpenseSettlementQueue`）。
  画面では読み取り専用（`IsViewOnly`・ADR-0062）。
- **`expense_date` は「利用日」から「計上日（仕訳日付）」へ。** 利用日は行が持つため、
  仕訳の日付をヘッダで 1 つ決める必要がある。既定値は**明細でいちばん遅い利用日**（下書きのあいだ追随）。
- 税額は**行ごとに確定して単純合計**する。経費はレシート記載の税額が正なので、
  「税率ごとに 1 回だけ端数処理」する ADR-0050（自社が発行する請求書の規約）は当てはまらない。
- 移行は「1 申請 → 1 明細」。既存 14 件で仕訳・固定資産台帳・承認履歴は 1 行も動いていない。
- ヘッダと明細の一致は不変条件 `docs/qa/20_不変条件SQL/D05_...sql` で機械的に検査する。

### 2-2. 申請画面は 4 ブロック（2026-08-17 夜・ADR-0066 の UI 改訂 / ddl/603）

```
（見出し無し）        件名・目的・計上日・申請区分・支払先
レシート 1 枚ぶんを入力  ← 明細 1 件分のフォーム（AI 読み取り＋領収書＋全項目）＋「この内容で明細に追加」
この申請の明細          ← 積み上がったリスト（9 列）＋ 合計金額・うち消費税・見込み額
承認                    精算ステータス・経理ボタン・承認フロー
```

見出しに番号は振らない。**枠（カード）で 4 つに区切る**ので、番号が無くても切れ目が分かる。
先頭のカードは件名・計上日を見れば何のブロックか自明なので見出しを置かない
（編集中は「レシート 1 枚ぶんを入力」→「この明細を編集」に変わる）。

**入力欄のカードは「フォーム」ではなく明細テーブルの行そのもの**（`ExpenseRequestLine` を
`ModuleField`＝`editing_line_id` で埋め込んでいる）。**AI 読み取りと領収書をその行が持つ**ので、
1 回のアップロードで抽出値とファイルが同じ行に載り、リストへの再添付が要らない。

入力中の行は `expense_request_id`・`line_no` のどちらも NULL。**リストにも合計にも出てこない。**
「この内容で明細に追加」で両方が入り、その瞬間に明細になる。行を削除すると `line_no` は 1..N に詰まる。

| 操作 | 動き |
|---|---|
| リストの行をクリック | その明細を入力欄に読み込む（見出しが「この明細を編集」に変わる） |
| この明細を更新 | 読み込んだ行を上書き保存し、入力欄を空に戻す |
| 入力内容をクリア / 編集をやめる | 入力中の内容を捨てる。確定済みの明細には触らない |

- 書きかけを残したまま**申請・実費確定はできない**（黙って捨てないための関門）。
- **1 枚のレシートを複数明細に分ける**（高価な機器 2 台を別々に固定資産登録する等）は、
  AI で 1 件目を追加 → 空になったフォームに 2 件目を手入力して追加、で成立する。
  2 件目に領収書は付かない（例外的な操作なので許容する）。
- 入力欄のカードが出るのは**下書きのあいだと、事前申請の実費確定待ちのあいだ**だけ。
- 行番号と `editing_line_id` の健全性は不変条件 `D06_...sql` で機械的に検査する。

## 3. 実装ステップ（台帳と連動）

1. **B2-1 移植品の動作確認**: サーバ起動→承認者ユーザー作成（花子=課長役・admin=申請者）→テンプレ手動1件→経費申請→承認 E2E。移植した素の状態が動くことを先に確定させる
2. **B2-2 データモデル＋フォーム拡張**（§2。2軸出し分け・費目・事実項目・交際費例外・添付）
3. **B2-3 承認ルート自動決定**（テンプレ4種 seed・SelectTemplateName 拡張・承認者の部門役職差し替え）
4. **B2-4 経理処理フェーズ**（精算ステータス・経理の仕訳生成→A連携・固定資産誘導）
5. **B2-5 実費超過再承認＋総合 E2E**

## 4. 設計判断（参照仕様からの重要な引き継ぎ）

- 経理の仕訳確定は**承認テンプレートに含めない**（承認と経理処理を分離）
- 精算対象者は既定＝申請者本人・変更可（代理申請）
- 申請日は業務項目（編集可）。監査は CreatedAt（自動）
- 利用先（店）・精算対象者（社員）・支払取引先（業者）は別項目

## 5. 申請者まわりの現行仕様（2026-08-06 レビュー第9弾で確定）

- **申請中（MyApplication）**: 実体は `my_application_view`（`approval_flow` に `expense_request` を JOIN・ddl/440）。列は 申請種別／件名／金額（税込）／状態／承認担当（代表）／申請日時。**表示は進行中＋却下のみ**——承認済・キャンセルは一覧から消える（承認済は通知と申請一覧で確認する。却下は申請者のアクション待ちのため残す）
- **申請一覧（ExpenseRequest 検索ページ）の既定検索**: 申請者=自分。**経理は既定なし**（全社の申請が見える）。全員分を見たいときは申請者条件をクリアして再検索
- **承認待ち（ApprovalInbox）**: 状態の検索条件は**廃止**（実体ビュー `approval_inbox_view` が常に「進行中で自分が担当」の行だけを返すため）。並列 OR 中は担当全員の受信箱に同じ申請が出て、1人の承認で残りは自動スキップ
- **通知**: 一覧は /Main/Notification（`Shell/NotificationCenter`・既定=未読のみ表示・「既読の通知を全て削除」あり）。サイドバー「通知 (N)」は未読件数バッジ。経費フレームの通知メニューは廃止（ここに一本化）
- **着地**: ExpenseStaff=申請／ExpenseApprover=承認待ち／ExpenseAccounting=精算処理待ち（トップ画面は全廃・ADR-0045）

## 6. 承認ルート（積み上げ方式・ADR-0048 ／ 段の合成・ADR-0066）

**判定額＝申請の合計金額（明細の合計）。費目＝行ごと。**
行ごとに `approval_route_rules` を first-match で解決し、得られたテンプレートの段を
1 本の段列に**重ね合わせて**から、その各段が申請時にコピーされる
（進行中・過去の申請は影響を受けない）。

### 段の合成（ADR-0066）

1. 各テンプレートの段を「承認者キー」でまとめる（役職段は `manager` / `director`、
   個人指名段は承認者 ID の集合）
2. 同じキーの段は 1 つに畳む
3. 並び順は「そのキーが登場したテンプレート内の `order_no` の最大値」の昇順。
   同値なら 課長 → 部長 → 個人指名

**明細が 1 行なら従来とまったく同じ段列に帰着する**ので、移行で既存申請のルートは変わらない。
`approval_flow.template_id` には代表 1 件（段数が最大のもの）を記録し、
**合成に使った全テンプレート名は申請履歴のコメントに残す**（「承認ルート（合成）: A ＋ B」）。

実機での確認例:

| 明細 | 合計 | ルート |
|---|---|---|
| 消耗品 20,000 ＋ 会議費 15,000 | 35,000 | 課長 → 部長（**各行は 3 万未満でも合計で判定**） |
| 消耗品 50,000 ＋ 交際費 10,000 | 60,000 | 課長 → 部長 → 総務（**費目の合成**） |
| 消耗品 5,000 ＋ 交際費 5,000 | 10,000 | 課長 → 総務（合成しても部長は入らない） |

金額を合計で見るのは、**申請を分割して上位承認を回避できないようにする**ため。

### テンプレートと適用条件

| 適用条件（承認ルート判定マスタ） | テンプレート | ルート（承認段） |
|---|---|---|
| 全費目 0〜29,999 | `経費_課長まで` | 課長 |
| 全費目 30,000〜199,999 | `経費_部長まで` | 課長 → 部長 |
| 全費目 200,000〜 | `経費_部長まで＋総務` | 課長 → 部長 → 総務 |
| 交際費 0〜29,999 | `経費_課長まで＋総務` | 課長 → 総務 |
| 交際費 30,000〜 | `経費_部長まで＋総務` | 課長 → 部長 → 総務 |

- テンプレート名の規約: **「〜まで」＝役職ラインの終端**（そこまでの役職段をすべて積む）、**「＋総務」＝合議段**（テンプレートで個人指名された総務担当）。
- 金額が上がると承認者が**入れ替わる**のではなく**積み上がる**。自分の課の支出は金額にかかわらず必ず課長が把握する（日本の稟議の通例。ADR-0048 の背景）。
- 少額（3 万円未満）の交際費だけ部長を飛ばすのは意図的な例外。部長を通したい導入企業は交際費の 2 ルールをどちらも `経費_部長まで＋総務` に向ければよい。

### 段の圧縮（walk-up との相互作用・ADR-0044）

役職段の承認者は walk-up（自課の課長 → 居なければ親の部の部長 → それも居なければ経理代替）で解決され、**申請者本人は必ず除外**される。その結果:

| 状況 | 実際に生成される段 |
|---|---|
| 課長が居る通常のケース | 課長 → 部長（テンプレートどおり 2 段） |
| **申請者の課が課長空席** | 課長段が部長へ繰り上がり、次の部長段と承認者集合が一致 → **段が 1 つに圧縮**され「部長のみ」 |
| **課長本人が申請** | 本人除外で同じく部長へ繰り上がり、圧縮されて「部長のみ」 |
| 部長も居ない | 経理代替 1 名 |

**「課長を飛ばす」ケースを特例として書く必要がなくなった**のが積み上げ方式の眼目。圧縮は**連続する役職段どうし**にだけ効き、個人指名段（総務段）は圧縮対象外（`ApprovalFlow.mod.cs` の `prevRoleApprovers` / `SameIdSet`）。

## 7. 入力ガードの現行仕様（2026-08-12・ADR-0051／改善候補 A-3・A-4）

- **件名は必須**（`Title.IsRequired: true`）。空件名は承認依頼の通知本文・仕訳摘要・固定資産の自動登録名に
  そのまま流れるため。CLB の必須は保存全般に効くので**下書き保存の時点から必須**。見積・請求書の件名は元から必須で、
  経費だけが例外だった。
- **「うち消費税」の検算**: 手入力があればそれを税額に採用する設計（レシート記載額の優先）は維持したうえで、

  | 条件 | 挙動 |
  |---|---|
  | 負値 | エラー（申請・実費確定を止める） |
  | 税額 ≧ 金額（税込） | エラー（同上） |
  | 税率からの計算値と ±10% を超えて乖離 | 警告のみ（申請は通る） |

  許容幅は「桁ミスは必ず捕まえ、軽減税率・非課税品の混在によるブレは通す」帯として ±10%（下限 1 円）。
  閾値は `ExpenseRequest.mod.cs` の `GetTaxDiffTolerancePercent()`（マスタ化しない）。
  判定は入力時・金額変更時・AI 読み取り完了時（気づかせる）と、申請時・実費確定時（止める）。
- **不課税・非課税の費目では「うち消費税」欄を隠し、入力済みの値もクリアする**（クリアは Info トーストで通知）。
  費目が未選択のうちは欄を出す（入力順を縛らない）。

### 7-1. 明細行化にともなう変更（2026-08-17・ADR-0066）

上記の検証は**すべて行単位**になり、メッセージに行番号が付く（「**3 行目**: 交際費は…」）。

| 検証 | 単位 | 文言の例 |
|---|---|---|
| 明細が 1 行以上あるか | 申請 | 「明細を 1 行以上入力してください（レシート 1 枚が 1 行です）」 |
| 金額（税込）・利用日・費目 | **行** | 「N 行目: 金額（税込）を入力してください」 |
| 交際費 3 項目 | **行**（その行の費目が交際費のときだけ） | 「N 行目: 交際費は相手先・参加人数・目的の入力が必須です」 |
| 「うち消費税」の負値・税込以上 | **行** | 「N 行目: 「うち消費税」… が金額（税込）… 以上です」 |
| 「うち消費税」の乖離（±10%） | **行** | 警告のみ・申請は通る |
| 領収書の未添付 | 行を数えて 1 本 | 「領収書が添付されていない明細が N 行あります…」（警告・ブロックしない） |
| 承認ルートが解決できない | 申請 | 「一致するルールがありません（費目 ○○ / 判定額 N 円）」で停止 |

- **不課税の行に残った「うち消費税」は、明細を触ったときにまとめてクリアする**
  （「消費税の対象外の費目の行があったため、「うち消費税」を N 行分クリアしました」）。
- **少額資産の自動判定も行単位**。1 申請に資産行と経費行が混在してよく、
  固定資産台帳に載るのは資産行だけ（取得価額は税抜本体、取得日は**その行の利用日**、
  名前は**行の摘要**、資産コードは未入力なら `EXP-{申請id}-{行番号}`）。

## 8. 事前申請（2026-08-17・ADR-0066 で改訂）

明細行化にともない、事前申請も**申請時に明細（費目と見込み金額）を入れる**形に変えた。
明細が無いと費目ベースのルート判定が効かず、交際費の事前申請が総務段を素通りしてしまうため。

- 見込み額（`estimated_amount`）は**申請したときの明細合計のスナップショット**。手入力ではなくなった
  （読み取り専用。再承認では上書きしないので、比較の基準が動かない）
- 承認後・実費確定前だけ**明細が編集可能**になる。実費が出たら明細を実費に直して「実費を確定」を押す
  （単独の「実費（税込）」入力欄は廃止＝実費は明細そのもの）
- 確定時の再承認判定は 2 つ。どちらかに当たれば再承認:
  1. 実費合計 > 見込み × `EXP_OVERRUN_RATE`（既定 110%）
  2. **「いま必要な承認者の段構成」が「実際に承認された段構成」と違う**
     （金額区分の跨ぎだけでなく、実費確定のあいだに交際費の行を足したようなケースも捕まえる）
- 確定済みかどうかは `expense_request.actual_confirmed` で持つ（`ddl/601`）
