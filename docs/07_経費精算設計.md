## 0. 位置づけ（ユーザーの A/B モデル）

- **A＝会計コア（フェーズA）**: 市販の財務会計専門ソフト相当。**経理機能フラグ（`HasAccountingAccess`）保有者専用**。経理以外に触られてはならない（→B-8 の経理ゲート必須。現行はユーザー管理画面の「経理機能」チェックで直接付与・ADR-0043）。
- **B＝業務フロー部分**: 市販ソフトが対応しにくい「会社ごとの業務フローに合わせたアプリ」。**全社員が触る**。原課（営業部・開発部）が申請→金額や科目に応じて決裁権限者が変わる。
- **本アプリの価値は A と B の一体化**。経費精算は B の代表であり、承認完了後に A へ自動連携（仕訳）される。

## 3. 実装ステップ（台帳と連動）

1. **B2-1 移植品の動作確認**: サーバ起動→承認者ユーザー作成（花子=課長役・admin=申請者）→テンプレ手動1件→経費申請→承認 E2E。移植した素の状態が動くことを先に確定させる
2. **B2-2 データモデル＋フォーム拡張**（§2。2軸出し分け・費目・事実項目・交際費例外・添付）
3. **B2-3 承認ルート自動決定**（テンプレ4種 seed・SelectTemplateName 拡張・承認者の部門役職差し替え）
4. **B2-4 経理処理フェーズ**（精算ステータス・経理の仕訳生成→A連携・固定資産誘導）
5. **B2-5 実費超過再承認＋総合 E2E**

## 4. 設計判断（参照仕様からの重要な引き継ぎ）

- 経理の仕訳確定は**承認テンプレートに含めない**（承認と経理処理を分離）
- 精算対象者は既定＝申請者本人・変更可（代理申請）
- 申請日は業務項目（編集可）。監査は CreatedAt（自動）
- 利用先（店）・精算対象者（社員）・支払取引先（業者）は別項目

## 5. 申請者まわりの現行仕様（2026-08-06 レビュー第9弾で確定）

- **申請中（MyApplication）**: 実体は `my_application_view`（`approval_flow` に `expense_request` を JOIN・ddl/440）。列は 申請種別／件名／金額（税込）／状態／承認担当（代表）／申請日時。**表示は進行中＋却下のみ**——承認済・キャンセルは一覧から消える（承認済は通知と申請一覧で確認する。却下は申請者のアクション待ちのため残す）
- **申請一覧（ExpenseRequest 検索ページ）の既定検索**: 申請者=自分。**経理は既定なし**（全社の申請が見える）。全員分を見たいときは申請者条件をクリアして再検索
- **承認待ち（ApprovalInbox）**: 状態の検索条件は**廃止**（実体ビュー `approval_inbox_view` が常に「進行中で自分が担当」の行だけを返すため）。並列 OR 中は担当全員の受信箱に同じ申請が出て、1人の承認で残りは自動スキップ
- **通知**: 一覧は /Main/Notification（`Shell/NotificationCenter`・既定=未読のみ表示・「既読の通知を全て削除」あり）。サイドバー「通知 (N)」は未読件数バッジ。経費フレームの通知メニューは廃止（ここに一本化）
- **着地**: ExpenseStaff=申請／ExpenseApprover=承認待ち／ExpenseAccounting=精算処理待ち（トップ画面は全廃・ADR-0045）

## 6. 承認ルート（積み上げ方式・ADR-0048／2026-08-09）

判定額（立替=実費・事前申請=見込み額→実費確定後は実費）と費目から `approval_route_rules` が first-match でテンプレートを選び、テンプレートの各段が**申請時にコピー**される（進行中・過去の申請は影響を受けない）。

| 適用条件（承認ルート判定マスタ） | テンプレート | ルート（承認段） |
|---|---|---|
| 全費目 0〜29,999 | `経費_課長まで` | 課長 |
| 全費目 30,000〜199,999 | `経費_部長まで` | 課長 → 部長 |
| 全費目 200,000〜 | `経費_部長まで＋総務` | 課長 → 部長 → 総務 |
| 交際費 0〜29,999 | `経費_課長まで＋総務` | 課長 → 総務 |
| 交際費 30,000〜 | `経費_部長まで＋総務` | 課長 → 部長 → 総務 |

- テンプレート名の規約: **「〜まで」＝役職ラインの終端**（そこまでの役職段をすべて積む）、**「＋総務」＝合議段**（テンプレートで個人指名された総務担当）。
- 金額が上がると承認者が**入れ替わる**のではなく**積み上がる**。自分の課の支出は金額にかかわらず必ず課長が把握する（日本の稟議の通例。ADR-0048 の背景）。
- 少額（3 万円未満）の交際費だけ部長を飛ばすのは意図的な例外。部長を通したい導入企業は交際費の 2 ルールをどちらも `経費_部長まで＋総務` に向ければよい。

### 段の圧縮（walk-up との相互作用・ADR-0044）

役職段の承認者は walk-up（自課の課長 → 居なければ親の部の部長 → それも居なければ経理代替）で解決され、**申請者本人は必ず除外**される。その結果:

| 状況 | 実際に生成される段 |
|---|---|
| 課長が居る通常のケース | 課長 → 部長（テンプレートどおり 2 段） |
| **申請者の課が課長空席** | 課長段が部長へ繰り上がり、次の部長段と承認者集合が一致 → **段が 1 つに圧縮**され「部長のみ」 |
| **課長本人が申請** | 本人除外で同じく部長へ繰り上がり、圧縮されて「部長のみ」 |
| 部長も居ない | 経理代替 1 名 |

**「課長を飛ばす」ケースを特例として書く必要がなくなった**のが積み上げ方式の眼目。圧縮は**連続する役職段どうし**にだけ効き、個人指名段（総務段）は圧縮対象外（`ApprovalFlow.mod.cs` の `prevRoleApprovers` / `SameIdSet`）。

## 7. 入力ガードの現行仕様（2026-08-12・ADR-0051／改善候補 A-3・A-4）

- **件名は必須**（`Title.IsRequired: true`）。空件名は承認依頼の通知本文・仕訳摘要・固定資産の自動登録名に
  そのまま流れるため。CLB の必須は保存全般に効くので**下書き保存の時点から必須**。見積・請求書の件名は元から必須で、
  経費だけが例外だった。
- **「うち消費税」の検算**: 手入力があればそれを税額に採用する設計（レシート記載額の優先）は維持したうえで、

  | 条件 | 挙動 |
  |---|---|
  | 負値 | エラー（申請・実費確定を止める） |
  | 税額 ≧ 金額（税込） | エラー（同上） |
  | 税率からの計算値と ±10% を超えて乖離 | 警告のみ（申請は通る） |

  許容幅は「桁ミスは必ず捕まえ、軽減税率・非課税品の混在によるブレは通す」帯として ±10%（下限 1 円）。
  閾値は `ExpenseRequest.mod.cs` の `GetTaxDiffTolerancePercent()`（マスタ化しない）。
  判定は入力時・金額変更時・AI 読み取り完了時（気づかせる）と、申請時・実費確定時（止める）。
- **不課税・非課税の費目では「うち消費税」欄を隠し、入力済みの値もクリアする**（クリアは Info トーストで通知）。
  費目が未選択のうちは欄を出す（入力順を縛らない）。
