# 部品アーキテクチャ仕様書

> 作成: 2026-08-02（ADR-0040/0041）・改訂: 2026-08-05（ADR-0043/0044/0045 = 3軸分離・部課階層・ポータル本格化）。
> 本書が **部品の定義・依存ルール・削除手順・カスタムポイントの正典**。
> 本アプリはテンプレートとして再利用されることを前提に、「使いたい部品だけ組み合わせる／自社に合わせて一部だけ直す」単位＝**部品**で構成される。再利用の単位は PageFrame。

## 1. 部品一覧とレイヤ

依存は**下方向のみ**許可（上のレイヤは下を知らない）。

| レイヤ | 部品 | 必須 | Modules フォルダ | PageFrame | 修正されやすさ |
|---|---|---|---|---|---|
| 0 | 基盤・マスタ | 必須 | `Shell/` `MasterSystem/` `MasterBusiness/` | Main／MasterBusiness／MasterAdmin | 低（組織・制度マスタはデータで吸収） |
| 1 | 会計 | 必須コア | `Accounting/` `Bank/` `FinancialReports/` | Accounting | **低**（法令で決まるためほぼ無修正） |
| 2 | 営業業務 | 任意 | `Sales/` | SalesStaff／SalesBilling | 中（商流は会社ごとに違う） |
| 2 | 購買業務 | 任意 | `Purchasing/` | Purchasing | 中 |
| 2 | 経費精算 | 任意 | `Expense/` | ExpenseStaff／ExpenseApprover／ExpenseAccounting | **高**（申請・承認ルールは各社カスタム前提） |
| 2 | 工数管理 | 任意 | `Timesheet/` | Timesheet／TimesheetAccounting | 高 |
| 3 | 経営管理 | 任意 | `Management/` | ManagementApprover／ManagementFull | 中（全部品を読む最上位の集約） |

- `Shell/` は共通殻: **PortalHome**（業務ポータル＝全員の着地）・**PortalSidebar**（Main の左サイドバー）・
  **Notification**（全社通知基盤・ADR-0045）・**Portal*Data**（ポータル集約の契約 SQL。§3.2）
- マスタ管理は淡々と CRUD するだけで、**各部品のロジックに依存しない**（完全な葉ノード）
- 部品別のトップページ（旧 ExpenseHome／SalesHome／AccountingHome／AdminHome）は **ADR-0045 で全廃**。
  各フレームは「一番使う業務画面」に直接着地する（§5）

## 2. 権限モデル（ADR-0043/0044 の要約 = 3軸分離）

「誰が何の画面を使えるか」「誰がどこに所属するか」「誰が誰の稟議を決裁するか」は**別の構造**で持つ:

| 軸 | 構造 | 内容 |
|---|---|---|
| 機能権限 | `app_users` の**直接フラグ**（ユーザー管理画面のチェックボックスで編集） | 営業機能（has_sales_access）／経理機能（has_accounting_access）／経費精算（can_use_expense・既定ON）／工数入力（can_use_timesheet・既定ON）／システム管理者（is_sysadmin） |
| 組織所属 | `departments`（**部課2階層**: parent_id 無し=部／有り=課。課はオプション）＋ `department_members`（ユーザー×ノード×役職 一般/課長/部長） | 兼務は行の追加。主所属= `app_users.department_id`（課 or 部）。伝票部門は**部ノードのみ**（主所属が課なら祖先の部＝キャッシュ列 `business_department_id`／`所属部`） |
| 承認構造 | `department_members` の課長/部長行 ＋ 承認テンプレート・承認ルート判定マスタ（ADR-0023） | 役職は **walk-up 解決**: 自課の課長 → 親の部 → 部長へ自動繰上げ → 経理代替（ADR-0044。自己承認回避も同じ一般則） |

- `is_approver` だけは**導出キャッシュ**（課長/部長行 ∨ 承認テンプレの個人指名。DB トリガー保守・`ddl/385` で再計算可）
- 部門メンバー行の追加/削除は**機能の見え方に影響しない**（旧「部門種別からの転記」は廃止）

| フレーム | ゲート |
|---|---|
| Main | なし（ログインユーザー全員） |
| ExpenseStaff | 経費精算フラグ（CanUseExpense） |
| Timesheet | 工数入力フラグ（CanUseTimesheet） |
| ExpenseApprover・ManagementApprover | 承認者（IsApprover） |
| SalesStaff | 営業機能 |
| SalesBilling・Accounting・Purchasing・ExpenseAccounting・TimesheetAccounting・ManagementFull・MasterBusiness | 経理機能 |
| MasterAdmin | システム管理者フラグ |

着地と導線（ADR-0042/0045）: **全員が業務ポータル（Main/PortalHome）に着地**。業務への導線は
**Main 左サイドバー（`Shell/PortalSidebar`）に一本化**（権限フラグで出し分け・変種解決は 経理 > 承認者 > 一般）。
ポータル中央は「やること・アラート・KPI」の集約（正典: docs/13）。
各フレームのサイドバー先頭の「ホーム」でいつでもポータルへ戻れる。

## 3. 部品間依存マップ

### 3.1 正規の依存（下方向・常時）

- 全部品 → 基盤・マスタ（参照マスタ: 取引先・案件・部門・科目・税制・ユーザー、通知基盤 Notification）
- レイヤ2 の各業務 → 会計（`JournalEntry` への仕訳生成、`FiscalYear`/`FiscalPeriod` の締めガード）
- 経営管理 → 会計・営業・購買・経費・工数（SQL クエリでの読取集約）

### 3.2 ポータル集約の契約（Shell → 各部品の「テーブル・ビュー」参照）

ポータルは部品の**モジュール型を参照しない**。Shell 所有の QueryField SQL（`PortalTodoData` /
`PortalQueueData` / `PortalAlertData` / `PortalKpiData`）が各部品の**テーブル・ビュー（DB 語彙）**を読む。
この SQL 群が部品→ポータルの契約であり、部品側のステータス設計・警告条件を変えるときは
**docs/13 §3 の表と該当 SQL を同時に更新**する。部品をテンプレートから外すときは該当 SELECT 部を削る。

通知は逆方向: 各部品 → 基盤 `Notification.Send()`（下方向参照。送信 API・論理リンクの閲覧時解決は docs/13 §4）。

### 3.3 オプション連携（例外は 3 つだけ・削除手順つき）

| 連携 | 実体 | 部品を外すときの手直し |
|---|---|---|
| 営業 → 購買（相殺入金） | `Sales/Receipt`: json の `OffsetVendorInvoiceRef` フィールド＋ `Receipt.mod.cs` の `VendorInvoice` 型参照一式（designcheck が正確な位置を報告する） | 購買を外す場合: Receipt の相殺入金フィールドとスクリプト該当箇所を除去 |
| 営業 → 工数（SES 精算） | `Sales/SesBilling.mod.cs` の `TimeEntry` 型参照一式（`ModuleSearcher<TimeEntry>`＋キャスト） | 工数を外す場合: SES 精算・請求（SesBilling/SesRunPlan）ごと外すか、工数集計部を除去 |
| 経費 → 会計（少額資産） | `Expense/ExpenseRequest.mod.cs` の `new FixedAsset()` | 会計は必須部品のため通常発生しない |

※箇所の特定は行番号でなく **designcheck の findings を正**とする。

既知の逆流 1 件: `ApprovalFlow → ExpenseRequest`（承認エンジンがクライアントを逆参照）。承認一式は
経費精算部品**内**に置くことで許容している。他部品に承認を広げるときはエンジンの汎用化が先（将来課題）。

## 4. 部品の外し方（テンプレート利用手順）

1. 対象部品の `PageFrames/*.frm.json` を削除
2. 対象部品の `Modules/<フォルダ>/` を削除
3. `Shell/PortalSidebar`（リンクとスクリプト）・`Shell/PortalHome`（表示項目とスクリプト）・
   `Shell/Portal*Data` の SQL から該当部品の参照を除去（docs/13 §3 の表が対象一覧）
4. §3.3 のオプション連携に該当する場合はその手直しを適用
5. `designcheck` → findingCount 0 を確認。あわせて `python Designer/tools/check_navigation.py` で
   FB-023 静的検査（リンク・スクリプト遷移先の未登録＝designcheck が検出しない「無言の真っ白」）が
   エラー 0 であることを確認 → デプロイ
6. （任意）不要になったテーブルの DROP

## 5. フレーム着地と変種マトリクス（機能追加時のチェックリスト）

**着地＝そのフレームで一番使う業務画面**（ADR-0045 でトップ全廃。TopPageModuleDesign・セグメント `Start`）:

| フレーム | 着地 |
|---|---|
| ExpenseStaff | 申請（ExpenseRequest） |
| ExpenseApprover | 承認待ち（ApprovalInbox） |
| ExpenseAccounting | 精算処理待ち（ExpenseSettlementQueue） |
| Timesheet／TimesheetAccounting | 工数入力（TimeEntry／TimeEntryAdmin） |
| SalesStaff | 見積（Quote） |
| SalesBilling | 請求書（Invoice） |
| Accounting | 仕訳/振替伝票（JournalEntryBoard） |
| Purchasing | 仕入先請求書（VendorInvoice） |
| ManagementApprover／ManagementFull | 予実対比（BudgetVsActual) |
| MasterBusiness | 取引先（Partner） |
| MasterAdmin | ユーザー管理（AppUser） |

同一部品の変種フレームはメニューを重複して持つ（CLB はリンク単位の可視条件を持たない= FB-009）。
**部品にメニューを足すときは、その部品の全変種に同じ変更を入れること。**

| 部品 | 変種 | 差分 |
|---|---|---|
| 経費精算 | ExpenseStaff ⊂ ExpenseApprover ⊂ ExpenseAccounting | Approver=＋承認待ち／Accounting=＋精算処理待ち |
| 工数管理 | Timesheet／TimesheetAccounting | Accounting=＋工数管理（経理）、案件一覧は Staff のみ |
| 営業業務 | SalesStaff ⊂ SalesBilling | Billing=＋請求書・入金・定期請求の実行・SES精算・請求（取引先一覧は Staff のみ） |
| 経営管理 | ManagementApprover ⊂ ManagementFull | Approver=予実対比・予算明細のみ |
| マスタ | MasterBusiness／MasterAdmin | 交差なし（業務・会計マスタ／組織・承認ガバナンス） |

新しいフレーム（部品）を足すときは
① `Shell/PortalSidebar` にリンク（表示条件＋変種解決）を追加し
② ポータルに出す「やること・アラート」があれば docs/13 §3 の表と `Portal*Data` SQL・`PortalHome` に追加し
③ 新フレームのサイドバー先頭に「ホーム」リンク（→ Main/PortalHome）を置く。

## 6. カスタムポイント（導入企業が触る場所）

| やりたいこと | 触る場所 |
|---|---|
| 部品を外す | §4 の手順 |
| 誰にどの業務を見せるか | **ユーザー管理のチェックボックス**（営業・経理・経費精算・工数入力・システム管理者） |
| 部・課の新設・分割・統合 | 部門マスタのみ（親部門で課を表現。権限には影響しない） |
| 誰が誰の稟議を決裁するか | 部門メンバーマスタの課長/部長行（walk-up 解決が自動で追随）＋承認テンプレート・承認ルート判定（ADR-0023） |
| sysadmin を従来型スーパーユーザーに戻す | 各フレームの `UserReadCondition` に `IsSysAdmin == true` の OR を追加（＋モジュール条件も同様） |
| 税率・制度・閾値の変更 | 税制マスタ・制度閾値マスタ（MasterBusiness。支払期限警告日数 PAY_DUE_SOON_DAYS も含む。ハードコード無し） |
| サイドバーのリンク構成・変種解決 | `Shell/PortalSidebar.mod.cs`（表示条件と遷移先が集約されている） |
| ポータルの表示項目 | docs/13 §3 の表 → `Shell/PortalHome.mod.cs`・`Shell/Portal*Data.Query.sql` |

## 7. 実装規約（この構成を壊さないために）

- 新モジュールは部品のフォルダに置き、**下方向以外の参照を作らない**。やむを得ない横断は §3.3 に追記して
  「オプション連携＋除去手順」をセットで文書化する
- スクリプトの画面遷移: 同一部品内は `GetModuleUrl`/`GetModuleDataUrl`（現在フレーム解決）、
  部品跨ぎ・変種固定の遷移はフレーム名を明示した NavigateTo。**フレーム素の URL（`/{Frame}`）は
  そのフレームの既定業務画面（TopPageModuleDesign）に着地する**（旧 `/{Frame}/Top` 規約は ADR-0045 で廃止）。
  遷移先の妥当性は `Designer/tools/check_navigation.py` が静的検査する
- 他部品の情報をポータルに出したいときは §3.2 の契約 SQL に載せる（モジュール型参照は不可）。
  集計・帳票としての横断は経営管理（レイヤ3）の仕事
- 通知は各部品から `new Notification().Send(...)` で送る（基盤への下方向参照。URL を焼き込まない）
- 権限判定はフラグ列（`HasSalesAccess`/`HasAccountingAccess`/`CanUseExpense`/`CanUseTimesheet`/
  `IsApprover`/`IsSysAdmin`）のみを使う。部門名・ユーザー名でのハードコード判定は禁止
- 伝票の部門は**部ノード**（`NodeType='dept'`）に限定し、既定値は `CurrentUser.所属部.Value` を使う
