## 0. 最初に読むもの

## 1. なぜやるか

### 問題 1: 2 つのテスト文書群が同じ事実を持っている

| 文書群 | 本数 | 行数 | 建前の役割 |
|---|---|---|---|
| `tests/11_E2Eテストシナリオ/` | 35 | 約 4,100 | 期待値の正典（金額・仕訳番号まで固定）・分岐 ID の台帳 |
| `tests/20_体験シナリオ/` | 52 | 約 8,800 | 人が読んで順に触れる操作台本 |

実際には **20 が 11 の分岐 ID を参照タグとして持ち、手順も期待値も重複して書いている**。
同じ事実が 2 箇所にあるので、直すコストも腐るコストも 2 倍払っている
（規約 §4-5「同じ事実を 2 箇所に書かない」への違反）。

**重複を完全になくすことはできない**——両者は目的が違うので、ある程度の重なりは正しい。
やりたいのは**目的を明確にし、内容を綺麗に分け直すこと**（2026-08-17 ユーザー指示）。

- **11_E2E = 「E2E テスト」のための網羅的ドキュメント**
- **20_体験シナリオ = 「ユーザーが機能を体験する」ためのシナリオドキュメント**

### 問題 2: 腐りやすい絶対値が、更新コストの高い markdown に置いてある

各台本が「仕訳の最終番号は No.83」「請求書 14 件」「Σ借方＝25,813,055」「未読 52 件」といった
**その時点の DB スナップショット**を本文に固定で書いている。他の台本を 1 本流すだけで嘘になる。

現に `python Designer/tools/lint_docs.py --stale` は **35 本**を「verified より後に
モジュールが変わった」として挙げる。数字の腐りはこれに輪をかけて速い。

**ドキュメントは"道筋"を書く。数字は SQL が守る**——これが規約 §6-3 で定めた方針。
不変条件 SQL は既に 40 本あり、`run_all.ps1` で一括判定できる。器はできている。

## フェーズ A: 役割を分けて、重複を整理する

### A-1. 両者の境界を決めて README に明記する

決めること（提案。妥当なら採用し、変えるなら理由を ADR に残す）:

| | 11_E2E | 20_体験シナリオ |
|---|---|---|
| 読者 | 回帰テストを回す人・実装者 | アプリを初めて触る人・デモする人・UX を見る人 |
| 粒度 | **分岐 1 つ = 1 エントリ**（ID・前提・操作・期待値） | **実務の一本道 1 つ = 1 ファイル**（物語 → 手順 → 期待結果） |
| 期待値 | **仕様を表す数字**（税の端数・閾値・段数）を持つ | 持たない。**11 の分岐 ID を参照する** |
| 手順の詳しさ | 最小限（どの画面で何をするか。1 行で足りる） | 詳しい（クリックする場所・トーストの文言・つまずいたときは） |
| 網羅性の責任 | **こちらが持つ**（分岐 ID の抜けを検査できる状態にする） | 持たない（代表的な道筋だけ通す） |

**要は「11 は what/期待値、20 は how/体験」に寄せる。**

### A-2. 重複している記述を片側に寄せる

1. 各章（経費・販売・購買・会計コア・銀行・案件経営管理・特殊取引・決算・帳票検証）について、
   11 と 20 の記述を突き合わせ、**同じことを書いている箇所**を洗い出す
2. **手順の細部は 20 へ寄せ、11 からは落とす**（11 は「どの分岐を・何を期待するか」に絞る）
3. **期待値の数字は 11 へ寄せ、20 からは落として参照タグにする**
4. 20 の各ステップに付いている分岐 ID（`EXP-R02` など）が **11 に実在するか**を機械的に確認する
   （存在しない ID を参照していたら、11 に足すか 20 の記述を直す）

### A-3. 分岐 ID の台帳を作る

11_E2E に**分岐 ID の一覧表**（ID → 一行説明 → 定義ファイル → それを通る 20 のファイル）を置く。
これがあると「この分岐はどこで検証されるのか」が 1 画面で分かる。
`lint_docs.py` に「20 が参照する ID が 11 に実在するか」の検査を足せるとなお良い。

## フェーズ B: 期待値を揮発性で置き直す

### B-1. 絶対値を 3 層に仕分ける

規約 §6-3 の表に従い、テスト文書に出てくる数字を分類する。

| 層 | 例 | 行き先 |
|---|---|---|
| 不変条件 | 貸借一致／ヘッダ合計＝明細合計／繰越の整合 | `qa/20_不変条件SQL/`（SQL） |
| 導出関係 | 請求額＝検収明細の合計／仕訳貸方＝税抜＋税 | 文書に相対表現で残す |
| 絶対値（仕様） | 税の端数処理の結果・経過措置 80%・少額資産 10/20/30 万・年額按分 1/12 | **文書に残す** |
| 絶対値（DB の現在値） | 仕訳総数・残高・件数・採番結果 | **文書から消す** |

**線引きの原則: その数字自体が仕様を表しているときだけ書く。**

### B-2. `tests/20_体験シナリオ/README.md` §4「実行前の DB 前提」を SQL 化する

いまは仕訳 75 本・請求書 14 件・未読 52 件…という表が書いてある。**これは書いた瞬間から腐る。**

- `qa/20_不変条件SQL/` に `Z01_現在のDB状態.sql`（仮）を置き、
  会計年度・締め状態・仕訳数・貸借合計・各伝票の件数と最新番号を 1 回のクエリで出せるようにする
- README §4 は「**実行前にこれを流して現状を見よ**」という 3 行に置き換える
- 各台本の「前提」表にある同種の数字も同じ扱いにする

### B-3. 台本内の絶対値を相対表現に直す

採番・仕訳番号は既に相対表現（「その時点の最終番号 +1」）になっている。**同じ扱いを金額にも広げる。**

- 「Σ借方＝Σ貸方＝25,813,055」→「**Σ借方＝Σ貸方**（値は `run_all.ps1` の A01 が判定する）」
- 「発行済・未入金が 8 通」→「発行済・未入金の請求書が**複数通**」
- ただし **B-1 で「仕様」に分類した数字は消さない**（消すと計算バグを検知できなくなる）

### B-4. 消した検知能力を SQL で埋める

絶対値を消すと、その数字が守っていた検査も消える。**消しっぱなしにしない。**
消した期待値ごとに「これは何を守っていたか」を考え、必要なら不変条件 SQL を足す。

## 進め方（段階を分けてコミットする）

1. A-1 境界を決めて両 README に明記 → コミット
2. A-2 章ごとに重複を整理（**章単位でコミット**。1 コミットで全章やらない）
3. A-3 分岐 ID の台帳を作る → コミット
4. B-1 仕分けの結果を一覧にして残す（どの数字をどこへ動かすかの計画）→ コミット
5. B-2 DB 前提の SQL 化 → コミット
6. B-3/B-4 台本の絶対値を相対化しつつ、必要な不変条件 SQL を足す（**章単位でコミット**）→ コミット

各段階のあと `python Designer/tools/lint_docs.py`（error 0）と
`docs/qa/20_不変条件SQL/run_all.ps1` を流す。SQL を足したら本数も README に反映する。

## 特に注意すること

- **検知能力を落とさない。** 数字を消すのが目的ではなく、腐らない場所へ動かすのが目的。
  B-4 を飛ばすと「読みやすくなったが何も検知しなくなった文書」になる。
- **20 の物語・つまずいたときは・確認ポイントは削らない。** ここが体験シナリオの価値。
  削るのは重複した期待値と、DB の現在値だけ。
- **`verified:` を更新するのは実際に実機で通したときだけ。** 文書を直しただけでは動かさない。
- 大きな設計判断（11 の役割を変える等）は **ADR を起こしてから**着手する。
