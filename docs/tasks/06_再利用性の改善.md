### 5-1. P9 — 通知の遷移先を「URL 保存」に変える

`Shell/Notification.mod.cs` の `ResolveLinkUrl()` が受信者の権限を見て経費のフレーム URL を組み立てており、
その過程で `ModuleSearcher<ExpenseRequest>` を使う（**基盤が上位部品を型で知る唯一の箇所**）。

**やること**: 遷移先 URL を**送信時に決めて保存する**。送信側は宛先ユーザーを知っているので宛先ごとの
URL を作れる。基盤は保存された文字列に飛ぶだけになり、型参照も分岐も消える。

1. **DDL**（`Designer/ddl/` に新規ファイル・番号は既存の最大 +10）

   ```sql
   ALTER TABLE notifications ADD COLUMN link_url TEXT;
   ```

2. **既存通知を移行する**（フォールバックを残すと型参照が消えないので、**全部埋める**）

   ```sql
   UPDATE notifications SET link_url = CASE
     WHEN link_module IS NULL OR link_id IS NULL THEN NULL
     WHEN link_module = 'ExpenseRequestApproval'
       THEN '/ExpenseApprover/ExpenseRequestApproval/' || link_id
     WHEN link_module = 'ExpenseRequest' THEN CASE
       WHEN EXISTS (SELECT 1 FROM expense_request e
                     WHERE e.id = CAST(notifications.link_id AS INTEGER)
                       AND e.creator = notifications.recipient_user)
            THEN '/ExpenseStaff/ExpenseRequest/' || link_id
       WHEN (SELECT has_accounting_access FROM app_users u
              WHERE u.id = notifications.recipient_user) = 1
            THEN '/ExpenseAccounting/ExpenseRequestAccounting/' || link_id
       WHEN (SELECT is_approver FROM app_users u
              WHERE u.id = notifications.recipient_user) = 1
            THEN '/ExpenseApprover/ExpenseRequestApproval/' || link_id
       ELSE '/ExpenseStaff/ExpenseRequest/' || link_id
     END
     ELSE NULL END;
   ```

   **`link_id` は TEXT・`expense_request.id` は INTEGER なので CAST が要る。**
   `expense_request` の作成者列名（`creator`）は実機で確認してから流すこと。

3. **`Notification.mod.json`** に `LinkUrl`（`link_url`）フィールドを足す
4. **`Notification.mod.cs`**
   - `Send(recipientUserId, title, body, linkUrl)` にシグネチャを変更（`linkModule`/`linkId` は廃止）
   - **`ResolveLinkUrl()` を削除**し、`Open_OnClick()` は `LinkUrl.Value` に飛ぶだけにする
   - `link_module`/`link_id` 列は残してよい（監査用）。ただし新規書き込みはしない
5. **`Expense/ApprovalFlow.mod.cs`** — 呼び出し側が URL を組み立てて渡す。
   宛先ごとのモジュール解決（`ToApproverModule` 付近・940 行台）は**そのまま使える**。
   これは経費部品の中の話なので、部品→基盤の下方向参照のまま。

**検証**: `deps_script.py` で `Shell -> Expense` が消えること。通知を実際に送って開けること
（承認者宛・申請者宛・経理宛の 3 通り）。旧通知（移行済み）も開けること。

### 6-1. P5 — 部品別スキーマを生成できるようにする

`Designer/ddl/` は時系列マイグレーション 80 本で **27 本が複数部品にまたがる**＝「会計だけのスキーマ」を
取り出せない。**方針（判断済み・§9-1）**: マイグレーションは**残す**。二本立てにする。

```
Designer/ddl/
  migrations/   ← 既存の 000〜（既存環境を追随させる履歴。そのまま移動するだけ）
  schema/       ← 配布用の正典。**機械生成**する
      00_base.sql        Shell / MasterSystem / MasterBusiness
      10_accounting.sql  Accounting / FinancialReports
      15_bank.sql        Bank
      20_sales.sql       Sales
      30_purchasing.sql  Purchasing
      40_expense.sql     Expense（承認一式を含む）
      50_timesheet.sql   Timesheet
      60_management.sql  Management
      70_portal.sql      Portal（契約 SQL が読むビューがあれば）
```

**二重管理にならないのは生成するから。** 手で書いてはいけない。

**生成ツール `Designer/tools/gen_part_schema.py` を作る**:

- 現行 DB の `sqlite_master` から `CREATE TABLE / VIEW / TRIGGER / INDEX` を取り出す
- **テーブル → 部品**の対応はモジュールの `DbTable` から機械的に得る（`_prototype/deps_ddl.py` に実装済み）
- **モジュールを持たないテーブル**（`company_profile` `department_managers` `temporary_files` `active_app_users` 等）は
  ツール内の**手動マッピング表**で振り分ける。表に無いものが出たら**エラーで止める**（黙って捨てない）
- **トリガは「書き込む先の部品」に置く**。これが P1 の解決になる（下記 6-2）
- 出力順は依存順（FK の参照先が先）

**検証（必須）**: まっさらな SQLite に `schema/` を全部流し、現行 DB と `sqlite_master` を突き合わせて
**差分ゼロ**を確認する。差分が出たら生成ツールが不完全。
