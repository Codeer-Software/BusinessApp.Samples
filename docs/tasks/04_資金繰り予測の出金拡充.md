## 1. なぜやるか

**資金繰り予測の出金側が実質空っぽになっている。**

`CashFlowForecastData.Query.sql` の出金の源は次の 4 つだけ:

- **当月のみ**の未払金残高（勘定科目 2020 の当年度 GL 残高）
- **当月のみ**の承認済み未仕訳の経費（`expense_request.settlement_status = 'approved'`）
- 仕入先請求書の未払い分（`vendor_invoices.status IN ('received','accrued')`。支払期限の月へ計上）
- 月次人件費（`monthly_salaries` に行がある月だけ）

したがって次のものが**一切入らない**:

| 入っていないもの | ペルソナでの重さ |
|---|---|
| 家賃・通信費・水道光熱費などの**定期固定費** | 毎月確実に出ていく。家賃だけで月 15 万円 |
| **社会保険料** | 給与とほぼ同額規模の固定支出 |
| 法人税・消費税の**納税** | 痛点 #5 の片翼 |
| **賞与** | 痛点 #5 のもう片翼 |
| **借入金の返済** | 勘定科目に 短期借入金(2300)・長期借入金(2400) はあるが返済予定を持つ場所が無い |

実機（2026-08-16）でも **2026-09 以降の出金予定が 0 円**で、
入金だけが積み上がって残高が増え続ける絵になっていた。

**ペルソナ痛点 #5 は「資金繰りが経営者の勘。賞与月・納税月の残高不安が常にある」**（`docs/02` §5）。
**痛点のど真ん中が予測の外にある。**

> **補足（`docs/14` の判定でどう書いたか）**: この画面は説明文で
> 「未回収請求書・定期請求・承認済み経費・未払金・仕入先請求書（支払期限月）・月次人件費から
> 現預金残高の推移を予測します」と**入力の範囲を明記している**。誤解を招く作りではないので、
> 不具合ではなく機能不足として扱っている。

## 3. 設計で決めること（**ここを出してユーザーに確認する**）

### 3-1. 予定をどこに持つか（2 案）

**案 A: 定型仕訳を流用する（軽い・推奨）**

`Accounting/JournalTemplate`（定型仕訳）には既に家賃・給与・社保などが登録されている想定。
ここに **「毎月の資金繰り予定に含める」フラグ**（と、必要なら発生日＝毎月何日）を足し、
資金繰りの SQL が定型仕訳明細の**現預金科目の貸方合計**を月次の固定出金として拾う。

- 利点: 新しいマスタを作らない。**すでに正しい金額と科目がある**ものを使える。「ハードコードしない」方針にも合う
- 欠点: 賞与・納税のような**毎月でない**支出を表現できない。定型仕訳の責務がやや広がる
- 現状の `JournalTemplate` の項目は 定型コード・定型名・メモ・**表示（ShowInList）**・明細。
  明細は 行・貸借・勘定科目・部門・金額（税込）・税区分・税入力・摘要。**案件と補助科目は持てない**
  （これは別件 `docs/14` A-5）

**案 B: 支出予定マスタを新設する（汎用・重い）**

`cash_outflow_plans`（仮）に 名称・金額・支払月の指定（毎月／指定月／複数月）・勘定科目・部門・有効 を持たせる。

- 利点: 賞与（6 月・12 月）・納税（法人税は決算 2 ヶ月後、消費税は中間納付あり）・
  借入返済（元利均等・回数指定）まで素直に表現できる
- 欠点: 作るものが増え、**入力を維持する運用コスト**が発生する

**案 A+B の折衷**: 毎月の固定費は案 A（定型仕訳）、賞与・納税・借入返済は案 B（予定マスタ）。
**推奨はこの折衷**だが、まず**ユーザーに「どこまで作るか」を確認する**こと。

### 3-2. 借入金の返済をどう扱うか

勘定科目に 短期借入金・長期借入金 はあるが、**返済予定を持つ場所が無い**。
弥生はプロフェッショナル以上で「借入金管理」を持つ。

- 借入金マスタ（借入先・借入日・元本・利率・返済回数・返済日）を作れば元利均等の予定表を自動生成できる
- ただし**デモデータに借入金の残高が無い**（実機の試算表で確認すること）。
  ペルソナに借入を設定するかどうかから決める必要がある → **ユーザー確認事項**

### 3-3. 期間

現行は **当月から 4 ヶ月固定・検索条件なし**（SQL の再帰 CTE が `idx < 3`）。
賞与（6 月・12 月）と納税（3 月決算なら 5 月申告）を織り込むなら**4 ヶ月では視野に入らない**。

- **6〜12 ヶ月へ広げる**。期間を検索条件にするか、固定で 12 ヶ月にするかを決める
- 検索条件を足すなら `docs/14` §7 で指摘した「検索条件が無い」という負けも同時に解消する
- **注意**: 範囲検索の既定は NULL 行を落とす（ADR-0057）。期間指定を足すときの落とし穴

### 3-4. 二重計上をしないこと（**最重要の検算**）

現行 SQL は既に二重計上を避ける工夫をしている。**同じ罠を踏まないこと**:

- 仕入先請求書を請求書ベースで拾うため、**買掛金の GL 残高は加算していない**
- 未回収額の控除は**消込済みの入金だけ**（ADR-0051。発行時の自動作成分を引くと全請求書が残額 0 になる）

固定費を足すときの新しい罠:

- **家賃の定型仕訳から予定を作りつつ、同じ家賃が仕入先請求書にも登録されていると二重**になる
- **給与の定型仕訳と `monthly_salaries` が二重**になる（現行は `monthly_salaries` を使っている）
- **納税予定と、未払法人税等・未払消費税等の GL 残高が二重**になる

→ **どの経路で拾うかを 1 つに決め、SQL のコメントに明記する**こと（現行 SQL がそうしている）。

## 5. 特に注意すること

- **`date('now')` は UTC**。現行 SQL は `date('now','localtime')` を使っている。**必ず踏襲する**。
- **スクリプト変更後は deploy ＋サーバ再起動してから実機検証する。**
- **ポータルのアラートと対で保守する**（ADR-0060）。資金繰りの判定を変えるなら
  `Shell/PortalAlertData.Query.sql` の該当箇所も見る。`docs/13` §3 の表が対象一覧。
- 税率をハードコードしない。現行 SQL は売上の既定税区分（`tax_categories.default_for='sales'`）から
  税率を引いている。**同じ流儀を守る**。
- 確認ダイアログは「不可逆か一括」のときだけ（ADR-0062）。
