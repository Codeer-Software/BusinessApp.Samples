## 1. なぜやるか — 何が起きているか（実測値つき）

**資金繰り予測の出金側が構造的にほぼ空で、入金だけが積み上がり残高が単調増加する絵になっている。**

実機 DB（2026-08-16 実測）で裏を取った内訳:

| 事実 | 実測値 |
|---|---|
| 定型仕訳には固定費が**登録済み** | T01 事務所家賃 165,000／T02 給与 3,000,000（うち預金支出 2,550,000）／T03 社会保険料 420,000。**資金繰り SQL はこれを一切見ていない** |
| 月次人件費 `monthly_salaries` | 当年度（FY2）に **`period_no=4`（2026年4月）の 9 行しかない**。5 月以降は人件費すら 0 円 |
| 未払金（2020）の GL 残高 | **当月（idx=0）に一括で載せるだけ**。翌月以降は 0 |
| 承認済み経費 | 同じく当月一括。会計期間で絞っていない |
| 未払消費税等（2210） | FY2 の決算仕訳（2027-03-31）で **241,211 円**を貸方計上済み → 納付は 2027-05。**予測に出ない** |
| 未払法人税等（2220） | 同じく **70,000 円**。**予測に出ない** |
| 借入金 | 短期(2040)・長期(2500) とも**残高 0**。返済予定を持つ場所も無い |
| 現預金科目の判定 | SQL が `code IN ('1000','1010','1020')` を**ハードコード**。`accounts.is_cash_equivalent=1` は **1000/1010/1020/1030（定期預金）の 4 つ**で、**定期預金を取りこぼしている** |
| 予測期間 | 再帰 CTE が `idx < 3` で**当月＋3ヶ月固定**・検索条件なし |

**ペルソナは 3 月決算。** 法人税・消費税の確定納付は 5 月、賞与は 6 月・12 月。**4 ヶ月窓では痛点 #5 の当事者イベントが構造的に視野の外にある。**

> **補足（`docs/14` の判定でどう書いたか）**: この画面は説明文で入力の範囲を明記しているため、
> **不具合ではなく機能不足**として扱っている。

### 現行 SQL の資産（壊してはいけない工夫）

現行 SQL は既に二重計上を丁寧に避けている。**この水準を落とさないこと。**

- 仕入先請求書を請求書ベースで拾うため、**買掛金の GL 残高は加算していない**
- 未回収額の控除は**消込済みの入金だけ**（ADR-0051。発行時の自動作成分を引くと全請求書が残額 0 になる）
- 定期請求の未生成将来分は `NOT EXISTS` で「まだ請求書が無い月」だけを拾っている
- 税率は売上の既定税区分（`tax_categories.default_for='sales'`）から引いている（ハードコードしない）
- 「今日」は `date('now','localtime')`（`date('now')` は UTC。**必ず踏襲する**）

## 2. 設計の背骨 — 予測の出金は 3 層に分かれる

この 3 層モデルが本タスクの全設計の土台。**層ごとに正しいデータ源が違う**ので、1 つの仕組みで賄おうとしないこと。

| 層 | 中身 | 金額・期日の性質 | データ源 |
|---|---|---|---|
| **① 確定債務** | 買掛金・未払金・承認済み経費・未払税金 | 両方とも確定済み | **帳簿**（現行の延長） |
| **② 経常反復** | 給与・社保・家賃・通信費 | 反復は確実、金額は緩やかに変動 | **定型仕訳＋起票実績** |
| **③ イベント** | 賞与・労働保険料・設備投資・借入返済・補助金入金 | 都度決まる。帳簿に手がかりが無い | **予定マスタ／借入金マスタ** |

**規律: 帳簿から導けるものは、絶対に予定マスタに手入力させない。** これがマスタの肥大化と二重計上を防ぐ唯一の歯止め。

### 貫く原則: アプリは税額を計算しない

税制改正に対する最大の防御は「計算しないこと」。本タスクでは**課税所得×税率のような税額計算を一切実装しない**。金額は決算仕訳が確定させた**残高**、または**前年の納税実績**から取る。

これにより、**2026年4月1日以後開始事業年度から適用される防衛特別法人税**（ペルソナは 3 月決算なので第19期から対象・初年度は中間納付なしで確定申告のみ＝**2027年5月納付**）が上乗せされても、それが未払法人税等に含めて計上される限り、**アプリの改修はゼロで予測に反映される**。逆に税率で予測する機能を作っていたら、2026年4月に即座に壊れていた。

> **この原則は既に一度このアプリを救っている。** インボイス経過措置は当初「80% → 2026年10月から50% → 2029年10月終了」だったが、令和8年度税制改正で「80% → **70%** → 50% → 30%」の 4 段階に**スケジュールごと書き換えられた**。本アプリは `invoice_transition_rates`（期間付きマスタ）で持っていたので**行を足すだけで済んだ**。率をコードに埋めていたら、2026年10月から静かに誤った税額を出し始めていた。

## 3. 確定した設計（ユーザー承認済み・2026-08-17）

### 3-1. 現預金の定義をフラグへ寄せる

`code IN ('1000','1010','1020')` のハードコードを **`accounts.is_cash_equivalent = 1`** に置き換える（ADR-0063 で入った列）。

- **効果**: 定期預金(1030)の取りこぼしが直る。将来の科目追加にマスタ変更だけで追随できる
- **注意**: これは**数字が変わる変更**。定期預金の残高が 0 なら見た目は変わらないが、実測して差分を確認すること
- `PortalAlertData.Query.sql` 側も同時に直す

### 3-2. 層② 経常反復 — 定型仕訳フラグ ＋ 直近実績の平均（案 A-2）

**`journal_templates` に「資金繰りに含める」フラグを 1 本足す。** 金額は**登録額ではなく起票実績の平均**を使う。

#### なぜ定型仕訳の「現預金科目の貸方」で正しいのか（実務の裏付け）

実務の資金繰り表は、人件費欄に**手取り額**を入れ、預り金（源泉所得税・住民税）と社会保険料は**実際に納付する月**の別欄に立てる。給与計上月と現金が出る月がズレるため。

```
T02 給与の支払   D 給料手当 3,000,000 / C 預り金 450,000 / C 普通預金 2,550,000
T03 社会保険料   D 法定福利費 280,000 / D 預り金 140,000 / C 普通預金 420,000
```

**「現預金科目の貸方合計」を拾えば、T02 からは手取り 2,550,000、T03 からは納付額 420,000 が正しい月に取れる。** 預り金 450,000 は現預金の貸方ではないので二重に載らない。**複式簿記の構造が資金繰り表の作法を自動的に満たしている。**

#### 実装ルール（罠が多いので厳守）

| ルール | 理由 |
|---|---|
| **現預金科目の「貸方 − 借方」の純額**を取る | 入金側の定型仕訳（借入実行など）があっても符号で正しく扱える |
| 金額は **`source_type='template'` かつ `source_id=定型ID` の `status='posted'` 仕訳から、起票実績のある直近 3 回の月合計の平均** | 更新運用ゼロで最新に追随する。「直近3ヶ月の実績平均」は経営者にも説明できる |
| **月に複数回起票された場合は、月ごとに合計してから平均**する | 月2回払いの給与を単純平均すると半額になる |
| **起票の無い月は平均の母数に入れない** | 0 円の月を混ぜると平均が下がる |
| 実績が 1 件も無ければ**定型仕訳の登録額**にフォールバック | 新規登録した定型がいきなり 0 円にならない |
| **当月に既にその定型から起票済みなら、当月の予定は出さない** | 実績（現預金残高に反映済み）と予定の二重計上を防ぐ。既存の `rec_in` の `NOT EXISTS` と同じ形 |
| **`draft` の仕訳は含めない** | 未確定の金額を予測に混ぜない |

- 索引は `Designer/ddl/480_journal_source_index.sql` が既にある（`source_type`/`source_id`）
- **定型仕訳側に「支払日」は持たせない。** 月次予測に日は不要（YAGNI）。日次資金繰りに拡張するときに初めて必要になる
- **定型仕訳側の繰返しは「毎月」だけ。** 年次のもの（労働保険料など）は層③の予定マスタへ回す。これでフラグ 1 本で済み、定型仕訳の責務が広がりすぎない

#### `monthly_salaries` は資金繰りから外す

**実務上も正しい判断。** このマスタは原価配賦（案件別損益）のための道具で、資金の出方を語る資格がない:

1. **手取りではない**（会社負担社保込みの発生ベースの概算コスト）
2. **社保の定型仕訳と二重になる**（会社負担社保がこの中に入っている）
3. **支払月がズレる**（原価配賦は当月の労務費、現金は翌月末）

### 3-3. 層① 税金 — 残高を納付月に置く ＋ 前年実績のフォールバック

#### 基本: 未払税金の残高を納付月に置く

- `未払法人税等(2220)`・`未払消費税等(2210)` の残高を、**会計年度末 + 申告期限月数**の月に出金として置く
- 残高が消えれば（＝納付すれば）予定も自動で消える。**二重計上ガードが構造的に不要**

#### 弱点と対策（**これが最重要の設計上の気づき**）

**未払法人税等は決算で初めて計上される。期中は残高 0。** つまり「今日が 2026年8月、第19期の決算は 2027年3月、納付は 2027年5月」というとき、**残高ベースだけでは 12 ヶ月窓に納税が現れないケースが多い。**

→ **前年の納税実績をフォールバックに使う**:

> **未払税金の残高があればそれを納付月に置く（確定値）。無ければ、前年同月の納税実績（現預金の貸方で、相手科目が未払法人税等・未払消費税等の仕訳）を置く（見込み値）。**

- **税制改正に強い**: 税額を計算していない。実績が変われば翌年自動で追随する（1 年遅れ）
- **説明できる**: 「前期はこの月にこれだけ払った」は実務の資金繰り表でも定石
- **確定値と見込み値は画面上で区別する**（§3-7）

#### 申告期限はマスタ化する

コードに「2ヶ月」と書かない。**`company_profile` に列を足す**（単一行のマスタが既にある）:

- `tax_filing_months`（既定 2） — 決算日の翌日から申告・納付までの月数
- `tax_filing_extension_months`（既定 0） — 申告期限延長の特例（法人税は 1 ヶ月、消費税も令和2年度改正で延長可）

**ここが唯一残る制度依存。だからこそマスタ化する。**

### 3-4. 層③ 資金繰り予定マスタ（新設）

**「たまにある入出金」を人が入れる唯一の場所。入力しなければ何も起きない（予測は現状のまま）。**

- **入金側も持つ**（符号あり）。補助金・助成金・保険の満期返戻金・増資は帳簿から拾えない
- **当月は出さない**（ユーザー決定）。過去月＝実績、**翌月以降＝予定**。これで実績との二重計上が**構造的に起きない**。消込チェックのような手作業を要求しない
  - **帰結**: 当月に賞与があっても予測には出ない。**画面に注記を出すこと**（「予定は翌月以降を表示します」）
- 想定される中身: 賞与／労働保険料（年1回・分割なら 7・10・1月）／税理士・社労士の顧問料の年払い／設備投資（PC 入替・サーバ更新）／退職金／保険料の年払い／社宅更新料／補助金・助成金の入金

### 3-5. 借入金マスタ（新設）— ペルソナに借入を設定する

**ユーザー決定: 機能もデモデータも作る。**

#### なぜ必要か

- IT 受託は構造的に資金ギャップが大きい: 支払サイト 60〜90 日、開発期間中の入金ゼロ、**人件費だけが先に出る**、仕様変更による検収遅延。ソフトウェア業の倒産は 2024 年に **223 件と過去最多**
- 従業員 55 名・年商 8.5 億で売上 60% が検収基準の受託。**運転資金の借入枠を持っていないほうが考えにくい**
- 痛点 #5 の「受託の入金は検収ずれで凸凹が激しい」は、まさにこの構造の記述。**その凸凹を吸収する手段が借入**
- 弥生は**プロフェッショナル以上でようやく「借入金管理」**。標準で持つことは営業的にも効く（`docs/14` の「市販の"機能が多い"は上位グレードの束」という営業の核と整合）
- 返済は**毎月確実に出ていく固定額**。資金繰り予測の主役の一人

#### 作る範囲: レベル 2（借入金マスタ ＋ 返済予定表の自動生成 ＋ 返済仕訳の起票）

- **元利均等・元金均等の両方に対応する。** 中小企業の信用保証協会付き融資は元金均等も多い。計算式は単純で、片方しかないほうが不自然
- **据置期間（元本据置・利息のみ）に対応する。** 実務でよくある
- **証書貸付に限定する。** 当座貸越は「枠」であって返済予定が無い別概念。手形貸付も今回は対象外
- 借入先は**取引先マスタとは別**に持つ（金融機関は仕入先ではない）
- 既存科目で足りる: 短期借入金(2040)・長期借入金(2500)・支払利息(7500)

#### 二重計上ガード

**返済予定表の各行に `status`（planned / posted）を持たせ、資金繰りは `planned` かつ将来日付の行だけを拾う。** 起票した瞬間に `posted` になり、その分は現預金残高に反映済みなので予測から落ちる。定型仕訳と同じ思想。

### 3-6. 期間は 12 ヶ月固定

- 賞与（6・12 月）と確定納税（5 月）を確実に窓に入れるには 12 ヶ月が要る。実務の資金繰り表も年間が定番
- **検索条件は付けない。** 12 ヶ月固定にすれば「見たい範囲が見えない」という `docs/14` §7 の指摘の実体が解消する。かつ範囲検索の NULL 落ち（ADR-0057）の罠を踏まない
- **年度またぎに注意**（§6 の実装上の罠を参照）

### 3-7. 内訳を出す ＋ 経常収支と財務収支を分ける

**内訳の無い予測は「勘」を別の「勘」に置き換えただけ。** 経営者が知りたいのは「なぜこの月が凹むのか」であって、合計額ではない。実務の資金繰り表は必ず**経常収支・財務収支（・投資収支）**を分ける。

現行は `月／期首資金／入金予定／出金予定／期末資金／警告` の 6 列しかない。これを拡張する:

```
月 / 期首資金
  【経常収入】 売上入金 / その他収入
  【経常支出】 人件費 / 固定費 / 仕入・外注 / 経費・未払金 / 税金
  【財務収支】 借入実行 / 借入返済
期末資金 / 警告
```

- **行＝月のまま、列に内訳を足す**（実務の資金繰り表は行＝項目・列＝月だが、月が今日基準で動くため CLB のグリッドで列を動的にするのは筋が悪い。将来の課題とする）
- **確定値と見込み値を区別する**（税金の列。ツールチップか注記で「前年実績からの見込み」と分かるようにする）
- チャートは**積み上げ棒**にすると凹みの理由が一目で分かる
- **C/F 計算書（`FinancialReports/CashFlowStatement.Query.sql`）の 財務活動区分と定義を揃える**こと

### 3-8. ポータルアラートを対で保守する（ADR-0060）

**`Shell/PortalAlertData.Query.sql` は資金繰りロジックを丸ごと複製している**（当月+3ヶ月・期末資金<0 の月数）。

- 期間・出金の定義を変えたら**必ず両方を直す**。片方だけ直すと、ポータルの「資金ショート n 件」と資金繰り画面が矛盾する
- **12 ヶ月に広げるとアラート件数が増える可能性が高い。** ポータルの見え方が変わることを承知のうえで進め、`docs/13_ポータルと通知基盤.md` §3 の表を更新する
- **できれば複製を解消する**（片方が他方を参照する形にできないか検討する。CLB のクエリモジュールの制約次第）

## 4. データモデル（実装の出発点。DDL は `Designer/ddl/` へ）

> **採番前に必ず `Designer/ddl/` の最新番号を確認すること。** 2026-08-17 時点の最新は **590**（並行セッションが使用中）。

## 5. 二重計上をしないこと（**最重要の検算**）

**同じ支出を 2 つの経路で拾わないこと。どの経路で拾うかを 1 つに決め、SQL のコメントに明記する**（現行 SQL がそうしている）。

| 支出 | **拾う経路（これだけ）** | 拾わない経路 | ガードの仕組み |
|---|---|---|---|
| 給与（手取り） | 定型仕訳 T02 の現預金貸方 | `monthly_salaries` | `monthly_salaries` を SQL から削除 |
| 社会保険料 | 定型仕訳 T03 の現預金貸方 | `monthly_salaries` の法定福利込みコスト | 同上 |
| 家賃・通信費等 | 定型仕訳の現預金貸方 | 仕入先請求書 | **同じ家賃が仕入先請求書にも登録されていないか実データで確認する** |
| 当月分の固定費 | （起票済みなら**出さない**） | — | `source_type='template'` のその月の存在チェック |
| 買掛金 | 仕入先請求書（`received`/`accrued`） | 買掛金の GL 残高 | 現行どおり |
| 未払金 | 未払金の GL 残高（当月一括） | — | 現行どおり |
| 法人税・消費税 | 未払税金の**残高**（無ければ前年実績） | 予定マスタへの手入力 | **予定マスタに税金を入れさせない運用規律** |
| 借入返済 | `loan_repayments` の `planned` 行 | 予定マスタ・定型仕訳 | `status` で起票済みを除外 |
| 賞与等 | 予定マスタ | — | **当月は出さない**ので実績と重ならない |

**検算のやり方**: 実装後、12 ヶ月分の各月について、上表の各経路の金額を個別に SQL で出し、画面の出金合計と手計算で一致させる。**「だいたい合っている」で終わらせないこと。**

## 6. リスクとデグレ対策（**隠さず全部書く**）

### 6-1. 【最大】デモデータに借入を入れると財務諸表の期待値が全面的に変わる

**現在の期首残高（実測）**:

| 会計年度 | 借方合計 | 貸方合計 | 行数 |
|---|---|---|---|
| FY2（2026-04-01〜、当年度） | 5,750,000 | 5,750,000 | 6 |
| FY3（2027-04-01〜、繰越済み） | 6,916,211 | 6,916,211 | 14 |

FY2 期首の中身は 現金 10 万／小口現金 5 万／普通預金 500 万／敷金 60 万 ／ 資本金 500 万／繰越利益剰余金 75 万 の 6 行だけ。

**影響**:

- 期首残高に借入金を足すと**貸借が崩れる**ので、借方に同額の相手科目が必要
- **FY2 と FY3 の両方**の `opening_balances` を直す必要がある（FY3 は繰越済み）
- 貸借対照表・キャッシュ・フロー計算書・試算表の期待値が変わる
- **影響を受けるドキュメント**:
  - `docs/tests/11_E2Eテストシナリオ/09_帳票検証/基本シナリオ.md`（BS/PL/CF の期待値）
  - `docs/tests/11_E2Eテストシナリオ/全仕訳台帳.md`
  - `docs/tests/11_E2Eテストシナリオ/00_初期設定/基本シナリオ.md`（期首残高の登録手順）
  - `docs/tests/11_E2Eテストシナリオ/08_決算/*`（繰越）
  - `docs/tests/20_体験シナリオ/08_決算_年度/03_翌期繰越と新年度.md`

**ユーザー承認済み**（「期待値の作り直しも仕方ない」）。ただし**§8 に金額規模の未決事項がある**。

### 6-2. 【要注意】C/F 計算書の財務活動区分は、これまで一度も検証されていない

`CashFlowStatement.Query.sql` には既に「短期借入金の純増減額」「長期借入金の純増減額」の行があるが、**借入残高が 0 だったので常に 0 が表示されていた**。借入を入れると**初めて数字が入る**。

- これは**デグレではなく、未検証コードパスの露出**。バグが見つかる可能性が高い
- **見つかったら「今回の作業で壊した」ではなく「以前から潜在していた」と切り分けて報告すること**
- 逆に言えば、本タスクは C/F 計算書の正しさを初めて検証する機会でもある

### 6-3. 【要注意】ポータルのアラート件数が変わる

12 ヶ月に広げると「資金ショート」の判定対象月が 4 → 12 に増える。**件数が増えるのは仕様変更であって不具合ではない**が、ポータルの見た目が変わる。`docs/13` §3 の表を更新すること。

### 6-4. 【要確認】期首資金に未来日付の posted 仕訳が入っている

`cash_now` は当年度の posted 仕訳を**日付で絞らずに全部**足している。実測すると **2027-03-31 付の決算仕訳が既に posted**。

- その決算仕訳は現預金を動かさない（未払税金の計上だけ）ので**現時点では影響が無い**はずだが、**他に未来日付の現預金仕訳が無いか必ず確認すること**
- 原理的には `e.entry_date <= date('now','localtime')` で絞るべき。**直すなら、直す前後の期首資金を実測して差分を報告すること**

### 6-5. 【実装の罠】年度またぎ

12 ヶ月に広げると予測期間が**翌会計年度に入る**。

- **`cur_yr` の絞りは維持すること。** `opening_balances` は FY3 の分も既に登録されているので、年度で絞らずに合計すると**期首残高が二重に載る**
- 期首資金は「今日時点の残高」を **1 回だけ**計算し、以降は増減の累積で進める（現行と同じ方式）。この方式なら年度またぎでも壊れない
- 定期請求・未回収請求書の拾い方も年度をまたいで正しいか確認する

### 6-6. 【既存の割り切り】未払金・承認済み経費の「当月一括」

支払期日の情報が無いため当月に全額を置いている。**12 ヶ月に広げると、当月だけ異常に凹む絵が目立つようになる。**

- **現行の挙動を維持する**（支払期日が分からない以上、当月に置くのが安全側）
- ただし**内訳（§3-7）を出せば「当月に未払金が一括で載っている」ことが読み取れる**ので、誤解は生まれない。内訳を出すことがこの割り切りの緩和策にもなっている

### 8-1. 借入の金額規模 — 期首 BS が想定より小さいことが分かった

ユーザーは当初「運転資金 5,000万〜1億円・5年・元利均等・年利1.5%前後」で OK と判断したが、**その後の実測で期首 BS の総額が 575 万円しかないことが判明した**（§6-1）。年商 8.5 億という設定と全く釣り合っていない（デモデータは仕訳数を絞った結果）。

ここに 5,000 万の借入を入れると、**BS 上「借入金が総資産の 9 割」という異常な絵**になる。選択肢:

| 案 | 内容 | 評価 |
|---|---|---|
| **(a) デモデータ規模に合わせる**（例: 1,000万・5年） | 借入額を BS の規模に合わせる | **推奨。** 借入「機能」を見せるのに額の大小は関係ない。作業範囲が資金繰りに収まる |
| (b) 期首 BS 全体を年商 8.5 億に見合う規模へ作り直す | 本来あるべき姿 | 資金繰りタスクの範囲を大きく超える。**別タスクとして issue 化すべき** |
| (c) 5,000万を入れて BS の不整合は許容 | — | 「市販ソフト以上」を名乗るデモとして苦しい |

**あわせて、借入金の相手科目（借方）を何にするか**も決める必要がある:

| 案 | 借方 | 評価 |
|---|---|---|
| **(ア) 仕掛品(1200)** | 「借りた金は人件費に消えて仕掛品になっている」 | **推奨。** IT 受託のリアルそのもの（ペルソナ §2 に「仕掛品（未成業務支出金）が発生」と明記）。**現預金残高が変わらないので、既存の資金繰り・資金ショート警告の絵が保たれ、デグレ範囲が最小になる** |
| (イ) 普通預金 | 「借りた金が手元にある」 | 自然だが、**現預金が厚くなり資金ショート警告が出なくなる**。既存シナリオの期待値が全面的に変わる |
| (ウ) 期中の借入実行仕訳にする | 期首残高を触らない | 「創業 18 期目の会社が今期初めて借りる」は少し不自然。ただし「運転資金の追加調達」としては自然 |

### 8-2. 消費税・法人税の中間納付 — **見送り判断の再考をお願いしたい**

ユーザーは「予測でそこまでする必要はない」と判断済み。**その判断を尊重するが、事実として次を伝えたい**（不都合な情報を隠さないため）:

- **中間納付額は税額を計算しない。** 「前期の確定税額 ÷ n」で機械的に決まる。**税率も税制も関係なく、前年実績から導ける**——§3-3 のフォールバックとまったく同じ考え方で自動化できる
- 回数の閾値は改正されうるが、**閾値マスタにすれば追随できる**（`system_thresholds` や `full_deduction_thresholds` の前例がある）
  - 消費税: 前期の確定消費税額（国税分）が 48万円超で年 1 回／400万円超で年 3 回／4,800万円超で年 11 回
  - 法人税: 前期の確定税額が 20万円超で予定申告。事業年度開始後 6 ヶ月経過日から 2 ヶ月以内（3 月決算なら **11 月末**）
- **年商 8.5 億のペルソナは、実務上ほぼ確実に中間納付の対象**。消費税は少なくとも年 3 回、法人税も 11 月末に発生する
- 見送ると、**「実データから自動で積み上げる」という本アプリの売りが、税金については片肺になる**（確定納付は自動、中間納付は手入力）

→ **改めて「入れる／入れない」の判断をお願いしたい。** 入れない場合も、予定マスタに手入力できるので致命的ではない。

### 8-3. デモデータの定型仕訳を増やすか

現在の定型仕訳は**家賃・給与・社保の 3 本だけ**。実務なら通信費・水道光熱費・リース料・駐車場・保険料・クラウド利用料などもある。

- **推奨: 5〜8 本に増やす。** 低リスク・高効果で、資金繰りの内訳が一気にリアルになる
- ただし**同じ費用が仕入先請求書にも登録されていないか確認すること**（§5 の二重計上）
