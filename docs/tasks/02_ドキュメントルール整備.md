## 1. なぜやるか（問題の正確な定義）

ドキュメントが増えてコンテキストを圧迫している（**2026-08-16 時点で 183 ファイル・20,523 行**）。

ただし、**原因はメタデータの不足ではない**。本当の問題は次の 3 つ:

1. **「今どれが正で、どれが読み替え済みか」が文書の外にしかない。**
   例: E2E テストシナリオは本文が旧前提のまま「19_読み替え表で読み替える」運用になっている。
   読む側は 2 つの文書を突き合わせないと現在の仕様が分からない。
2. **「何をするときに何を読めばいいか」が索引になっていない。**
   `docs/README.md` は文書の一覧であって、タスク起点の案内になっていない。
3. **1 文書の責務が肥大している。** `05_実装計画と進捗台帳.md` は 854 行あり、
   毎回の実行の起点なのに全体を読まないと現在地が分からない。

したがって「フロントマターを付ける」だけでは目的を達しない。
**status による現行/廃止の明示**と**本文の現在形化**が本丸。

## 2. 決めること（ルール）

### 2-1. フロントマター（全 `.md` に必須）

```yaml
---
title: 部品アーキテクチャ
status: current          # current | superseded | historical
scope: 全体              # 対象領域（部品名 / 業務名 / 全体）
audience: 開発           # 開発 | 運用 | 営業 | テスト
updated: 2026-08-16
supersedes: []           # この文書が置き換えた文書のパス
related: [decisions/0040-....md]
---
```

- **`status` が肝**。`current` 以外は「読まなくていい」と最初の数行で判断できる。
  - `current` … 現在の仕様・計画
  - `superseded` … 後継がある（`related` に後継を書く）。**中身は消さずに残す**
  - `historical` … 当時の記録として価値がある（ADR・リサーチ・テスト実施記録）
- ADR は原則 `historical`（不変の判断ログ）。ただし **状態が「採用」で現行仕様を規定しているものは `current`**。
- `updated` は**内容を変えたときだけ**更新する（フロントマター追加だけでは更新しない）。

### 2-1b. 体験シナリオには「使うモジュール／画面」を必ず宣言させる（**追加要件・2026-08-17**）

`docs/tests/20_体験シナリオ/` の全 51 本のヘッダ（フロントマターでもよい）に、
**そのシナリオが触るモジュール名と画面名**を書く。例:

```yaml
modules: [Purchasing/VendorInvoice, Purchasing/PaymentSchedule, Accounting/JournalEntry]
screens: [購買・支払 > 仕入先請求書, 購買・支払 > 支払予定表, 会計業務 > 帳簿 > 仕訳帳]
```

**なぜ要るか（これが無いと運用が回らない）**

機能を直したとき「どの体験シナリオが影響を受けるか」を知る手段が、いま**51 本を読むことしかない**。
その結果、直さずに放置 → 台本が腐る → 台本を追った人が「画面が違う」に出くわしたとき
**それが台本の腐りなのか実装のバグなのか区別できない**、という事故が起きる。
体験シナリオは単なる説明書ではなく**回帰テストの網**なので、腐ると検知能力そのものを失う。

宣言があれば `grep -l "Purchasing/VendorInvoice" docs/tests/20_体験シナリオ/**/*.md` で
影響範囲が機械的に引ける。**これが「機能を直したらその場で台本も直す」という運用の前提条件**になる。

**あわせて決めること（2026-08-17 のユーザーとの議論より）**

- 台本の更新は**層で分ける**:
  - **① 導線・画面名・項目名** … 機能変更と同じコミットで直す（数行で済み、間違っていると台本が能動的に嘘をつく）
  - **② 期待値（金額）** … その場で、ただし**実際に通した分だけ**（51 本を再実行しない）
  - **③ 大規模な設計変更**（例: E-1 経費申請の明細行化）… 実装完了までまとめる。ただし**着手時に影響ファイル一覧を残す**
- 採番・仕訳番号は既に**相対表現**（「その時点の最終番号 +1」）と決まっている（`tests/20/README` §2）ので、
  ②の churn は金額だけに限定されている。**この設計は維持する。**
- どうしても後回しにするときは「後で直す」ではなく**保留リストに積む**
  （`tests/20/README` 末尾か専用ファイルに `- 2026-08-16 ADR-0064: 05_購買_支払/01・03 に案件欄の記述を追加（未了）` の形）。
  `tests/19_部品再編2026-08_読み替え表` との違いは、**これが解消される前提の一時リスト**である点。

### 2-2. `docs/README.md` を唯一の入口にする

一覧ではなく**タスク起点の索引**にする。例:

```markdown
## 何をするときに何を読むか
| やること | 読むもの |
|---|---|
| 新しい機能を検討する | 03_機能スコープ → 10_部品アーキテクチャ |
| モジュールを 1 本足す | 10_部品アーキテクチャ §5 → Designer/Project.md |
| 会計の正しさを確かめたい | 04_会計ドメイン設計 §9 |
| アプリを触って改善点を探す | tests/20_体験シナリオ/README |
| 判断の経緯を知りたい | decisions/README |
```

そのうえで `CLAUDE.md` からの文書参照は**この索引 1 本に集約**し、CLAUDE.md を痩せさせる。

### 2-3. 「現行仕様」と「経緯」を物理的に分ける（**一番効く**）

- **仕様書は常に現在形に書き換える。** 追補・読み替え表で積み上げない。
- 経緯は ADR（`decisions/`）に置き、仕様書からはリンクで参照する（既存ルール）。
- **具体的な作業**: `tests/19_部品再編2026-08_読み替え表.md` の内容を
  E2E テストシナリオ本文にマージし、19 は `status: historical` にする。
  同様の「追補で読み替え」構造が他にないか全文書を走査する。

### 2-4. 1 文書 1 責務・行数の目安

- 目安: **250 行**。超えたら分割を検討する（機械的な上限ではない）。
- 最優先の分割候補: `05_実装計画と進捗台帳.md`（854 行）
  → 「現在地と次にやること」（短い・毎回読む）と「完了済みの履歴」（長い・普段読まない）に分ける。

## 3. 検証

`Designer/tools/` に軽いチェックスクリプトを置く（`designcheck` とは別物）:

- 全 `.md` にフロントマターがあるか
- `status` が 3 値のいずれかか
- `supersedes` / `related` のリンク先が実在するか

## 4. 進め方（段階を分けてコミットする）

1. **ルールを決めて文書化**（`docs/00_ドキュメント規約.md` を新設）→ コミット

## 5. 特に注意すること

- **中身を消さない。** `superseded` にするだけで、削除はしない（判断の経緯が失われる）。
- **フロントマターを付けただけで満足しない。** 目的は「読まなくていい文書を判別できること」と
  「本文が現在形であること」。3 の解消が終わって初めて効果が出る。
- **`Designer/ClaudeCodeForDesigner/` は対象外**（デザイナが再生成する生成物・Git 追跡外）。
- `CLAUDE.md` / `Designer/CLAUDE.md` / `Designer/Project.md` は docs/ の外だが、
  索引との整合が必要なので 7 で必ず見直す。
