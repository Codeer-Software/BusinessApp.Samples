## 1. 不変条件（P0。すべて自動テストで検査する）

会計コアが常に守る性質。破れたら製品として成立しない。

**この表に挙げたものが `I-nn` で、それ以外の差し戻しは `E-` で始まる**（`JournalViolationCodes`）。
**一覧はここが持つが、I-03・I-04・I-11〜I-13 の規則の本体は [15_記帳の枠組み](15_記帳の枠組み.md) にある。**
**摘要を必須にした規則は足していない**（Claude の判断。2026-09-08。規則より前に計上された伝票がその性質を破っているから）——
**同じ論法は I-17 にも効くので、足すかどうかは [04 §5](04_実装計画と現在地.md) の未決**である
（法定記載事項を欠く違反が `E-` で、法定でない部門必須が `I-13` なのは重みが逆に見える）。

| # | 不変条件 |
|---|---|
| I-01 | 計上済み仕訳は、伝票単位で借方合計＝貸方合計 |
| I-02 | 計上済み仕訳の全体でも借方合計＝貸方合計 |
| I-03 | 仕訳明細は、有効な会計期間に属する |
| I-04 | 締め済み期間に、仕訳を計上・訂正・取消できない |
| I-05 | 計上済み仕訳は、変更も削除もされない（レコードが不変） |
| I-06 | 訂正・取消は、原仕訳を一意に特定する情報を持つ |
| I-07 | 元帳の残高＝当該科目の仕訳明細の集計（残高キャッシュを持たない） |
| I-08 | 試算表・B/S・P/L・部門別 P/L は、同じ仕訳集合から再現できる |
| I-09 | 部門別 P/L の全部門合計＝全社 P/L |

| I-16 | 制度ルールの版を変えても、過去の仕訳の計算結果は変わらない |
| I-17 | 伝票番号は欠番を埋め直さず、再利用しない |

## 2. 日付を 1 つに潰さない

会計では「日付」が複数ある。1 つの列にまとめると、必ずどこかで意味が壊れる。

| 概念 | 意味 | 誰が決めるか |
|---|---|---|
| **取引日**（`transaction_date`） | 取引が行われた日。帳簿の「取引年月日」 | 利用者 |
| **計上日**（`posting_date`） | 会計期間への帰属を決める日。通常は取引日と同じ | 利用者（既定は取引日） |
| **入力年月日**（`entered_at`） | システムに記録された日時。**利用者は変更できない** | システム |
| **課税仕入れの時点**（`tax_point`） | 消費税の経過措置・税率の判定基準日。役務は完了日、資産は引渡日 | 利用者（既定は取引日） |
| **計上した日時**（`posted_at`） | 下書きを計上に進めた時刻。**帳簿への帰属を決める「計上日」とは別物**で、こちらは処理の時刻 | システム |
| **証憑日** | 請求書等の日付。会計コアは参照キーとして持つのみ | 外部 |

**入力年月日は「通常の業務処理期間の経過後の入力の事実を確認できる」という優良な電子帳簿の要件
（電帳規則 5 ⑤一イ(2)）そのもの**であり、取引日とは絶対に共用しない。

### 2-1. 計上日は取引日より前にできない

**取引が起きる前に帳簿へ載せることはできない**ので、`計上日 >= 取引日` を計上時に検証する。
逆に取引日が過年度であることは正常なので検証しない（遅れて起票した取引を当期に計上する）。

発生主義で会計期間が開いていれば両者は一致するのが基本で、ずれるのは**計上日が後ろになる向きだけ**である。

| 類型 | 取引日にする日 |
|---|---|
| 消耗品購入（掛） | 納品日。請求書の到着日でも支払日でもない |
| 請負（受託開発） | 検収日 |
| 準委任（SES） | 役務完了日（月末）。翌月の請求書の日付ではない |
| SaaS 年額前受の月次按分 | 按分する月の末日 |

いずれも消税法の帳簿記載事項②「課税仕入れを行った年月日」と同じ日である（請求書の日付は証憑日として別に持つ）。

> **落とし穴**: 準委任で請求書の日付を取引日にすると計上日と逆転する。取引日の入れ方が誤っており、
> 放置すると経過措置の割合判定（`tax_point`）と法定検索も同時に狂う。**逆転を弾けば入力時点で気づける。**

## 3. 金額の持ち方

- **`decimal` を使う。浮動小数点を使わない**（CLB スクリプトの数値も `decimal` に統一される）。
  **金額は整数円**で、円未満は端数処理の結果としてのみ発生する
- 仕訳明細は **借方／貸方を符号ではなく区分で持つ**（`debit_credit`）。金額は常に正
- 税抜経理なので、本体行の金額は**税抜**。消費税額は**税行**として別明細に持つ（[11](11_消費税設計.md)）

## 4. 仕訳のモデル

### 4-1. 構造

**伝票ヘッダ（`journal_entries`）1 件に、仕訳明細（`journal_lines`）が複数ぶら下がる。**
**消税法 30 ⑧の法定記載事項を満たすのは明細**（§4-2）、**法税規則 55 ① の「内容」を持つのは伝票の摘要**（§4-2-1）。
伝票番号は計上時に採番して**会計年度の中で一意**にする（I-17。台帳は `journal_entry_sequences`）。

**1 枚の伝票には、1 つの取引だけを記す**（開発者の決定。2026-09-08。逐語は「**伝票は 1 取引を 1 伝票とする**」。
理由と検討した選択肢は [ADR-0045](decisions/0045-振替伝票1枚には1つの取引だけを記す.md)）。
**こう決めると、伝票の取引年月日と摘要がその取引の「年月日」と「内容」の欄になり、
摘要を必須にした関門（§4-2-1）で欄が 1 つ確保される**（理由の当てはめは Claude）。

- **運用の約束であって、機械は判定しない**（Claude の敷衍）。1 枚に何件書かれているかを製品は見ない
- **当たるのは取引を記す伝票だけである**（**Claude の読み**——取消・期首残高・決算振替・繰越は
  帳簿の上の振替なので法税規則 54・55 が数える「取引」に当たらない。訂正の再計上は当たる）。
  **取引を記さない伝票への当てはめは [05 の Q-13](05_開発者への問い.md) で聞いている**

**列の正典は [`Designer/ddl/`](../Designer/ddl/README.md)（`005_journals.sql`）である。本書は列の一覧を持たない**——写すと必ず腐る（実際に 3 箇所ずれていた）。本書が持つのは**列の背後にある決定**だけである。

| 何を決めているか | どこ |
|---|---|
| 日付を 4 つに分ける（取引日・計上日・入力年月日・課税仕入れの時点） | §2 |
| 金額は整数円、借方／貸方は符号ではなく区分で持つ | §3 |
| 取引先を明細に「名前の写し」ごと持つ | §4-2 |
| 「無い」は NULL 1 通りで表す | [20 §7](20_実装の原則.md) |
| 種別（`entry_type`）と、訂正・取消が原仕訳を指すこと | §5 |
| 損益科目の明細には部門が要る | [15 §4](15_記帳の枠組み.md) |
| 他部品からの投入に要る 3 つの列 | §10 |
| 消費税の列（税区分・用途区分・課税仕入れの時点・適用した版・消費税行） | [11](11_消費税設計.md) |
| 計上時に写して固定するもの（取引先名・登録番号） | [ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md) |

**会計期間は列に持たない。** 計上日から都度解決する（[15 §2](15_記帳の枠組み.md)）。
**会計年度（`fiscal_year_id`）は列に持つ。** **画面は計上日から決めて選ばせない**（`IsViewOnly`）が、
**画面以外の経路があるので計上の関門が食い違いを弾く**（§5）——通すと別の年度の番号列から伝票番号が出て I-17 が壊れる。
訂正・取消では**年度が原仕訳と変わることがある**（計上日だけが後ろにずれるため）。

**伝票の種別（`entry_type`）は 6 つ**——通常・訂正・取消・期首残高・決算振替・繰越。**作成時に決まり、あとから変えられない**（変えられると種別ごとの関門が丸ごと外れる。qa/03 L-08）。
**取引先は伝票と明細の両方が持ち、明細の値が伝票の既定値を上書きする**（§4-2）。

### 4-2. なぜ取引先を明細に「名前の写し」ごと持つのか

消税法 30 ⑧の帳簿の法定記載事項は**仕訳明細が満たす**必要があり、FK だけだと取引先の改名で過去の帳簿の記載が変わる。だから**FK と名前の写しを両方持つ**。
写す仕組みは [ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)、取引先側は [13](13_取引先設計.md)。

### 4-2-1. 仕訳帳の記載事項——「内容」は法定である（摘要を必須にする）

> 青色申告法人は、仕訳帳には、取引の発生順に、**取引の年月日、内容、勘定科目及び金額**を
> 記載しなければならない。
>
> ——法税規則 55 ①（**要旨**。逐語は e-Gov。リサーチにあるのは帳簿別の要約表である）

**出典と版は [仕訳と伝票の用語リサーチ §1](research/2026-08-25_仕訳と伝票の用語.md)**（令和 8 年 7 月 31 日施行分。e-Gov）。**2026-09-05 に開発者が同じ条文を示し、読み方が一致した。**

**「内容」は勘定科目とは別に挙がっている。** 勘定科目・金額は明細が、年月日は伝票が持つが、
**「内容」を持つ欄は伝票の摘要である**——明細の「内容」（`item_description`）は消税法 30 ⑧③の
「資産又は役務の内容」で、**別の要件に応える別の欄**である（§4-2）。
**どの記載事項をどの欄で満たすかは Claude の当てはめで、現在形は [40 §4-1](40_優良な電子帳簿の対応表.md) が持つ**。

**摘要 1 つで足りるのは、1 枚に 1 つの取引しか記さないからである**（前提は §4-1）。
**したがって摘要は必須である**（開発者の決定。2026-09-05）。計上の関門（`JournalEntryValidator`）が空の摘要を止め、
DDL のトリガが**関門を通らない経路**（いまは `sql` CLI と手作業の SQL。CSV 取込と投入 API はフェーズ 6）を止める。**空白だけも「入っていない」とみなす。**

**関門が守るのは「空でないこと」だけである**（開発者の決定。2026-09-08。逐語は
「**それ以上のチェックは困難でしょうし、逆にユーザビリティを阻害することになりかねません**」）。
**書かせることまでが機械の仕事で、何を書くかは利用者に委ねる**（Claude の補足）——
**何が「内容」かを機械が判定する手立ては思い付かず、判定を誤れば正しい仕訳を止める**（中身が本当に「内容」かは見ていない）。

**二層の広さは同じにする**（関門は `string.IsNullOrWhiteSpace`、トリガは同じ符号位置を `trim` で落とす）。
**トリガが狭いと、関門が走らない経路でだけ「関門なら弾く値」が帳簿に載る。広いと**、関門を通った値を DB が拒み、
利用者に枠組みの言葉が出る（[qa/01 F-16](qa/01_CLB静かな失敗.md)）。**だから `JournalDescriptionGuardTests` が両方向で突き合わせる。**

- **規則より前に計上された伝票が残る**（開発機に 2 件。明細の「内容」も空なので**仕訳帳のその行には「内容」が 1 つも無い**）。
  **計上済みは不変**（[ADR-0004](decisions/0004-優良な電子帳簿への準拠と仕訳の不変性.md)）**なのでもう直せない**——**本番で同じことが起きたら記載事項を欠いた行が永久に残る**ので関門を置いた。
  **帳簿はその行も探せなければならない**（下の電帳通達 8-13）
- **[電帳通達 8-13](40_優良な電子帳簿の対応表.md)（記録事項が無い記録も検索できること）とは衝突しない**——
  あちらは「空の記録を探せること」を求めるだけで、「空にできること」を求めていない。
  **明細の「内容」を必須にしないのは、欠けたときの帰結が違うから**である——55 ① は記帳の義務で、
  欠けると帳簿そのものが要件を満たさない。消税法 30 ⑧③ は仕入税額控除の要件で、欠けると
  **その仕入れの控除が受けられない**（[11 §8](11_消費税設計.md)。扱いはフェーズ 3）

**必須にするのは計上のときだけ。下書き保存では求めない**（開発者の決定。2026-09-05）。

**理由は、それで法税規則 55 ① を満たせるからである**——条文が求めるのは**帳簿への記載**で、
**計上の関門が止めれば記載事項を欠いた行は帳簿に載らない**。打ちかけの伝票にまで強制する利益が無い。
**「下書きは帳簿ではない」という理屈は使わない**——[40 §5-1](40_優良な電子帳簿の対応表.md) の
**開発者未確認の当てはめ**で、同節が「この読みを前提にした断定を他の文書へ広げない」と自ら禁じているからである。

**印は最初から出す**（押した瞬間に初めて知る形にはしない。[21 §1](21_画面の原則.md)）。

**摘要と明細の内容の上限は、どちらも 200 文字である**（**開発者の決定**。2026-09-13。逐語は「摘要と内容は200文字くらいほしい気がします」。
市販の中心と一致する。[リサーチ](research/2026-09-13_市販会計ソフト比較_文字の欄の上限.md)）。**短くしない**——経過措置の旨と回収特例の住所を明細の「内容」に書く運用である（[11 の保留リスト](11_消費税設計.md)）。
**上限で入力を止めず、プレースホルダで見せて関門が断る**（守り方は [12 §2-2](12_マスタ台帳.md)）。**実装はこれから**——マスタと取引先の 8 欄は 2026-09-14 に入ったが、**伝票の 2 欄は次の回**である（[04 §1](04_実装計画と現在地.md) の C）。

## 5. 訂正モデル

[ADR-0004](decisions/0004-優良な電子帳簿への準拠と仕訳の不変性.md) の具体化。電帳通達 8-9 が示す「直接訂正・削除できないシステム＋反対仕訳」方式を採る。

| 状態 | できること |
|---|---|
| `draft` | 自由に編集・削除できる（まだ帳簿ではない） |
| `posted` | **変更・削除できない**。動かせるのは訂正・取消だけ（**複製は下の表**——帳簿を動かさないので、この行に当たらない） |

| 操作 | 生成されるもの |
|---|---|
| **取消** | 原仕訳の貸借を反転した `reversal` 伝票 1 本。`original_entry_id` に原仕訳 |
| **訂正** | `reversal` 伝票 ＋ 正しい内容の `correction` 伝票。どちらも `original_entry_id` を持つ |
| **複製** | 同じ内容の `normal` の**下書き** 1 本。**`original_entry_id` は持たない**（訂正モデルの操作ではない） |
| **訂正のやり直し** | 取消済みで再計上の無い原仕訳に、`correction` の**下書き** 1 本（取消は作り直さない）。「訂正する」が兼ねる（[ADR-0052](decisions/0052-訂正のやり直しは訂正するが兼ね取消済みで訂正の無い原仕訳には再計上の下書きだけを起こす.md)。Claude の判断。開発者は未承認） |

**複製は訂正モデルの操作ではない**——帳簿を 1 行も動かさず、原仕訳との関係も作らない**新しい記帳**である。
ここに並べてあるのは、利用者から見て取消・訂正と隣り合う同じ並びのボタンだからにすぎない。
**元にできる種別は、取消・訂正の対象にできる種別と同じ**（通常と訂正。取消伝票は元にできない——
取り消された原仕訳を複製すればよい）。何を写すかは [ADR-0048](decisions/0048-伝票の複製は取引の内容だけを写す.md)、
**会計補助（ステートレス）である**ことは [ADR-0049](decisions/0049-会計補助はステートレスなものだけを作り会計コアのドメイン層には置かない.md) が持つ。

- **反対仕訳の取引日は、原仕訳と同じにする**（訂正に気づいた日ではない）。
  帳簿の「取引年月日」は取引そのものを説明する欄であって、訂正作業の日ではないからである。
  原仕訳の期間が締まっていれば計上日だけが後ろにずれるので、[§2-1](#2-1-計上日は取引日より前にできない) と矛盾しない
- 反対仕訳の作り方は**総額方式**（貸借を入れ替える）を採る。純額方式・同一科目のマイナス金額も
  法令上は認められるが（電帳一問一答 令和 8 年 7 月版 問 26）、総額方式が最も読みやすい
- **7 日以内の訂正は履歴を残さなくてよいという緩和（電帳通達 8-10）には依存しない**——
  緩和には内部規程とシステムの両方が必要で、条件の管理コストが利益を上回る
- 表示上は原仕訳・反対仕訳・再計上をグループにして見せてよいが、**データは畳まない**
- **取消が済んでいて再計上（下書きを含む）の無い原仕訳には、「訂正する」で再計上の下書きだけを起こせる**
  （訂正の下書きを消した後の受け皿。判定は入口の `JournalAmendmentService` が持ち、計上の関門は
  計上済みの再計上だけを見る。[ADR-0052](decisions/0052-訂正のやり直しは訂正するが兼ね取消済みで訂正の無い原仕訳には再計上の下書きだけを起こす.md)。Claude の判断。開発者は未承認）

**計上の関門**（**保存の関門**が見る。`JournalSubmitGate`。[ADR-0008](decisions/0008-CLBとCSharpライブラリの責務分担.md)）
- **原仕訳が取り消されていない `correction` は計上できない**（通すと取引が二重に載る）
- **二重取消・二重訂正は、アプリと DB の両方で止める**
- **取消の明細と摘要はサーバが原仕訳から作る**（利用者に入力させない）。訂正は取消を計上したうえで、
  **原仕訳を写した下書き**を開いて利用者に直させる（[ADR-0015](decisions/0015-訂正は取消と再計上の組で表し更新履歴方式を採らない.md)）
- **画面から「取り消す」「訂正する」「複製する」を押したときの入口だけは Web API** である
  （[ADR-0016](decisions/0016-画面から呼ぶサーバ処理はWebAPIに置く.md)）。**取消・訂正はどの経路でも上の関門を通る。
  複製は計上しないので**、関門に当たるのは複製した下書きを計上するときである

## 10. 他部品からの仕訳投入

会計コアが公開する唯一の書き込み経路。

- 投入元は `source_component` ＋ `source_document_id` ＋ `idempotency_key` を必ず付ける
- 会計コアは**投入された仕訳にも同じ検証を通す**（貸借一致・期間・部門・税区分）——「外部からだから信用する」経路を作らない
- 投入された仕訳も計上後は不変。訂正は反対仕訳による
