# 会計ドメイン設計

> **複式簿記の正しさはこの文書で担保する。** 実装より先にここを確定させる。
> 消費税の計算設計は [11_消費税設計](11_消費税設計.md) に分けてある。

## 1. 不変条件（P0。すべて自動テストで検査する）

会計コアが常に守る性質。破れたら製品として成立しない。

| # | 不変条件 |
|---|---|
| I-01 | 計上済み仕訳は、伝票単位で借方合計＝貸方合計 |
| I-02 | 計上済み仕訳の全体でも借方合計＝貸方合計 |
| I-03 | 仕訳明細は、有効な会計期間に属する |
| I-04 | 締め済み期間に、仕訳を計上・訂正・取消できない |
| I-05 | 計上済み仕訳は、変更も削除もされない（レコードが不変） |
| I-06 | 訂正・取消は、原仕訳を一意に特定する情報を持つ |
| I-07 | 元帳の残高＝当該科目の仕訳明細の集計（残高キャッシュを持たない） |
| I-08 | 試算表・B/S・P/L・部門別 P/L は、同じ仕訳集合から再現できる |
| I-09 | 部門別 P/L の全部門合計＝全社 P/L |
| I-10 | B/S の当期純利益＝P/L の当期純利益 |
| I-11 | 期首残高は貸借一致し、B/S 科目のみで構成される |
| I-12 | 翌期首残高＝前期末残高（繰越後） |
| I-13 | 損益科目の仕訳明細には部門がある |
| I-14 | 同一の外部伝票を二重に計上しない（冪等性キーで一意） |
| I-15 | 税集計は、対象の仕訳明細へドリルダウンできる |
| I-16 | 制度ルールの版を変えても、過去の仕訳の計算結果は変わらない |
| I-17 | 伝票番号は欠番を埋め直さず、再利用しない |

## 2. 日付を 1 つに潰さない

会計では「日付」が複数ある。1 つの列にまとめると、必ずどこかで意味が壊れる。

| 概念 | 意味 | 誰が決めるか |
|---|---|---|
| **取引日**（`transaction_date`） | 取引が行われた日。帳簿の「取引年月日」 | 利用者 |
| **計上日**（`posting_date`） | 会計期間への帰属を決める日。通常は取引日と同じ | 利用者（既定は取引日） |
| **入力年月日**（`entered_at`） | システムに記録された日時。**利用者は変更できない** | システム |
| **課税仕入れの時点**（`tax_point`） | 消費税の経過措置・税率の判定基準日。役務は完了日、資産は引渡日 | 利用者（既定は取引日） |
| **計上した日時**（`posted_at`） | 下書きを計上に進めた時刻。**帳簿への帰属を決める「計上日」とは別物**で、こちらは処理の時刻 | システム |
| **証憑日** | 請求書等の日付。会計コアは参照キーとして持つのみ | 外部 |

**入力年月日は「通常の業務処理期間の経過後の入力の事実を確認できる」という優良な電子帳簿の要件
（電帳規則 5 ⑤一イ(2)）そのもの**であり、取引日とは絶対に共用しない。

### 2-1. 計上日は取引日より前にできない

**取引が起きる前に帳簿へ載せることはできない**ので、`計上日 >= 取引日` を計上時に検証する。
逆に取引日が過年度であることは正常なので検証しない（遅れて起票した取引を当期に計上する）。

発生主義で会計期間が開いていれば、両者は一致するのが基本である。ずれるのは
**計上日が後ろになる向きだけ**（締めた後に請求書漏れが発覚した、前期の取引が決算後に判明した）。

| 類型 | 取引日にする日 |
|---|---|
| 消耗品購入（掛） | 納品日。請求書の到着日でも支払日でもない |
| 請負（受託開発） | 検収日 |
| 準委任（SES） | 役務完了日（月末）。翌月の請求書の日付ではない |
| SaaS 年額前受の月次按分 | 按分する月の末日 |

いずれも消費税法の帳簿記載事項②「課税仕入れを行った年月日」と同じ日である。
請求書の日付は証憑日として別に持つ。

> **落とし穴**: 準委任で請求書の日付（6/10）を取引日にすると、計上日 5/31 と逆転する。
> 取引日の入れ方が誤っており、放置すると経過措置の割合判定（`tax_point`）と法定検索の結果も
> 同時に狂う。**逆転を弾くことで入力時点で気づける。**

## 3. 金額の持ち方

- **`decimal` を使う。浮動小数点を使わない**（CLB スクリプトの数値も `decimal` に統一される）
- **金額は整数円**。円未満は端数処理の結果としてのみ発生し、保存時には整数
- 仕訳明細は **借方／貸方を符号ではなく区分で持つ**（`debit_credit`）。金額は常に正
- 税抜経理なので、本体行の金額は**税抜**。消費税額は**税行**として別明細に持つ（[11](11_消費税設計.md)）

## 4. 仕訳のモデル

### 4-1. 構造

**伝票ヘッダ（`journal_entries`）1 件に、仕訳明細（`journal_lines`）が複数ぶら下がる。**
帳簿の法定記載事項を満たすのは**明細**であり（§4-2）、伝票番号は計上時に採番して
**会計年度の中で一意**にする（I-17。採番の台帳が `journal_entry_sequences`）。

**列の正典は [`Designer/ddl/`](../Designer/ddl/README.md)（`005_journals.sql`）である。本書は列の一覧を持たない**——
写すと必ず腐る（実際に 3 箇所ずれていた。2026-08-26）。本書が持つのは**列の背後にある決定**だけである。

| 何を決めているか | どこ |
|---|---|
| 日付を 4 つに分ける（取引日・計上日・入力年月日・課税仕入れの時点） | §2 |
| 金額は整数円、借方／貸方は符号ではなく区分で持つ | §3 |
| 取引先を明細に「名前の写し」ごと持つ | §4-2 |
| 「無い」は NULL 1 通りで表す | §4-4 |
| 種別（`entry_type`）と、訂正・取消が原仕訳を指すこと | §5 |
| 損益科目の明細には部門が要る | §9 |
| 他部品からの投入に要る 3 つの列 | §10 |
| 消費税の列（税区分・用途区分・課税仕入れの時点・適用した版・消費税行） | [11](11_消費税設計.md) |
| 計上時に写して固定するもの（取引先名・登録番号） | [ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md) |

**会計期間は列に持たない。** 計上日から都度解決する（§7）。
**会計年度（`fiscal_year_id`）は列に持つ。** 画面の初期値は計上日から入れるが、
**いまは利用者が変えられる**ので、**計上の関門が「計上日の属する年度」との食い違いを弾く**（§5）。
食い違いを通すと別の年度の番号列から伝票番号が出て、I-17 の一連番号が壊れる。
訂正・取消では計上日だけが後ろにずれるので、**年度が原仕訳と変わることがある**。

**伝票の種別（`entry_type`）は 6 つ**——通常・訂正・取消・期首残高・決算振替・繰越。**作成時に決まり、あとから変えられない**（変えられると種別ごとの関門が丸ごと外れる。qa/03 L-08）。
**取引先は伝票と明細の両方が持ち、明細の値が伝票の既定値を上書きする**（§4-2）。

### 4-2. なぜ取引先を明細に「名前の写し」ごと持つのか

消税法 30 ⑧の帳簿の法定記載事項は**仕訳明細が満たす**必要がある。
FK だけだと取引先の改名で過去の帳簿の記載が変わるので、**FK と名前の写しを両方持つ**。
写す仕組みは [ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)、取引先側は [13](13_取引先設計.md)。

### 4-2-1. 仕訳帳の記載事項——「内容」は法定である（摘要を必須にする）

> 青色申告法人は、仕訳帳には、取引の発生順に、**取引の年月日、内容、勘定科目及び金額**を
> 記載しなければならない。
>
> ——法税規則 55 ①

**出典は [仕訳と伝票の用語リサーチ §1](research/2026-08-25_仕訳と伝票の用語.md)**
（e-Gov `https://laws.e-gov.go.jp/law/340M50000040012`。確認日 2026-08-25。
**令和 8 年 7 月 31 日施行分**であることは 2026-08-26 に同じく e-Gov で確認）。
**2026-09-05 に開発者が同じ条文を示し、読み方が一致した。**

**「内容」は勘定科目とは別に挙がっている。** 勘定科目・金額は明細が持ち、年月日は伝票が持つが、
**「内容」を持つ欄は伝票の摘要である**——明細の「内容」（`item_description`）は
消税法 30 ⑧③の「資産又は役務の内容」で、**別の要件に応える別の欄**である（§4-2）。

**したがって摘要は必須にする。** いまは空のまま計上でき、**実際に空のまま計上済みの伝票が
2 件ある**（伝票番号 1・12。明細の「内容」も空なので、**仕訳帳のその行には「内容」が 1 つも無い**）。
2026-09-04 の探索的テストで見つけ、2026-09-05 に決着した（[qa/04](qa/04_実機操作テスト.md)）。

- **計上済みは不変（[ADR-0004](decisions/0004-優良な電子帳簿への準拠と仕訳の不変性.md)）なので、
  その 2 件はもう直せない。** 開発機のデータだから実害は無いが、
  **本番で同じことが起きたら記載事項を欠いた行が永久に残る**
- **[電帳通達 8-13](40_優良な電子帳簿の対応表.md)（記録事項が無い記録も検索できること）とは衝突しない。**
  あちらは「空の記録を探せること」を求めるだけで、「空にできること」を求めていない。
  取引先・部門・補助科目・明細の内容は引き続き空になりうる

**必須にするのは計上のときだけ。下書き保存では求めない**（開発者の決定。2026-09-05）。

**理由は、それで法税規則 55 ① を満たせるからである。** 条文が求めるのは**帳簿への記載**であり、
**計上の関門が空の摘要を止めれば、記載事項を欠いた行は帳簿に載らない**。
打ちかけの伝票にまで強制すると「あとで書く」ができなくなり、入力の邪魔になるだけである。

**「下書きは帳簿ではない」という理屈は、ここでは使わない**——それは
[40 §5-1](40_優良な電子帳簿の対応表.md) の**開発者未確認の当てはめ**であり、
同節が「**確認を取るまで、この読みを前提にした断定を他の文書へ広げない**」と自ら禁じている。

**印は最初から出す。** 押した瞬間に初めて知る形にはしない（[21 §1](21_画面の原則.md)）。

### 4-3. 帳簿間の相互関連性

優良な電子帳簿の要件（電帳規則 5 ⑤一ロ）。**伝票番号（`entry_no`）を一連番号として全帳簿で共有**し、
仕訳帳 ⇔ 総勘定元帳 ⇔ 補助簿 ⇔ 固定資産台帳を相互に辿れるようにする。

**実装（2026-08-26）**: 仕訳帳と総勘定元帳の伝票番号の列が、その伝票へのリンクになっている。
どちらも**伝票番号の範囲でも引ける**——電帳通達 8-14 (注) の「一連番号等で検索できるとき」の経路である。
**伝票番号は会計年度の中の連番**なので、年度をまたいで引くと同じ番号が複数出る。
1 本に絞るには会計年度と組み合わせる。

集計転記をする箇所（決算振替など）は、摘要に**集計対象と集計範囲**（対象・期間・条件）を記録する。

### 4-4. 空の値は 1 通りに持つ（空値検索の前提）

検索機能は「記録事項がない電磁的記録」も探せなければならない（電帳通達 8-13。[リサーチ](research/2026-08-23_電子帳簿保存法.md) §3.5）。そのために**「無い」は NULL で表し、空文字を保存しない**。混在すると空値検索が `is null or = ''` になり、書き漏らした側が静かに取りこぼす。
CLB は未入力も「入力して消した」場合も NULL で保存する（2026-08-25 実測）。取込・投入 API に備えて、
**保存の関門は受け取った空文字を NULL に寄せてから渡す**（`PartnerSubmitGate` が最初の実装。qa/03 L-14）。
**帳簿のクエリ側は空文字も拾う二重の守り**を残す（`is null or = ''`）——
関門を通らない経路（CSV 取込・投入 API。フェーズ 6）が入るまで、法定検索を守るのはこちらである。

## 5. 訂正モデル

[ADR-0004](decisions/0004-優良な電子帳簿への準拠と仕訳の不変性.md) の具体化。国税庁の電帳通達 8-9 が示す
「直接訂正・削除できないシステム＋反対仕訳」方式を採る。

| 状態 | できること |
|---|---|
| `draft` | 自由に編集・削除できる（まだ帳簿ではない） |
| `posted` | **変更・削除できない**。訂正・取消のみ |

| 操作 | 生成されるもの |
|---|---|
| **取消** | 原仕訳の貸借を反転した `reversal` 伝票 1 本。`original_entry_id` に原仕訳 |
| **訂正** | `reversal` 伝票 ＋ 正しい内容の `correction` 伝票。どちらも `original_entry_id` を持つ |

- **反対仕訳の取引日は、原仕訳と同じにする**（訂正に気づいた日ではない）。
  帳簿の「取引年月日」は取引そのものを説明する欄であって、訂正作業の日ではないからである。
  原仕訳の期間が締まっていれば計上日だけが後ろにずれるので、[§2-1](#2-1-計上日は取引日より前にできない) と矛盾しない
- 反対仕訳の作り方は**総額方式**（貸借を入れ替える）を採る。
  純額方式・同一科目のマイナス金額も法令上は認められるが（電帳一問一答 令和 8 年 7 月版 問 26）、
  総額方式が最も読みやすく、集計時の符号の扱いが単純になる
- **7 日以内の訂正は履歴を残さなくてよいという緩和（電帳通達 8-10）には依存しない。**
  常に履歴を残す。緩和には内部規程とシステムの両方が必要で、条件の管理コストが利益を上回る
- 表示上は原仕訳・反対仕訳・再計上をグループにして見せてよいが、**データは畳まない**

**計上の関門**（**保存の関門**が見る。`JournalSubmitGate`。[ADR-0008](decisions/0008-CLBとCSharpライブラリの責務分担.md)）
- **原仕訳が取り消されていない `correction` は計上できない**（通すと取引が二重に載る）
- **二重取消・二重訂正は、アプリと DB の両方で止める**
- **取消の明細と摘要はサーバが原仕訳から作る**（利用者に入力させない）。訂正は取消を計上したうえで、
  **原仕訳を写した下書き**を開いて利用者に直させる（[ADR-0015](decisions/0015-訂正は取消と再計上の組で表し更新履歴方式を採らない.md)）
- **画面から「取り消す」「訂正する」を押したときの入口だけは Web API** である
  （[ADR-0016](decisions/0016-画面から呼ぶサーバ処理はWebAPIに置く.md)）。どちらの経路も上の関門を通る

## 6. 勘定科目

| 属性 | 内容 |
|---|---|
| コード | 4 桁。体系は資産 1xxx / 負債 2xxx / 純資産 3xxx / 収益 4xxx / 費用 5xxx〜 |
| **科目区分** | 資産・負債・純資産・収益・費用。**部門の要否判定と決算振替がこれに依存する**（必須） |
| 決算書表示区分 | B/S・P/L のどの区分に並べるか（流動資産／固定資産／売上高／販売費及び一般管理費 …） |
| 既定税区分 | 入力時の初期値。**「値が入っていない行の穴埋め」に使わない**（前回の実測で事故った） |
| 補助科目の要否 | 補助科目を持つ科目か |
| 現預金科目か | 出納帳・資金の集計に使う |
| 固定資産科目か | 固定資産台帳の計上先候補を絞る |
| **評価勘定か** | 減価償却累計額・貸倒引当金・売上値引戻り高・期末棚卸高のように、**通常残高が科目区分と逆**の科目。科目区分だけから借方残／貸方残を決めると必ず誤る |
| 有効／無効 | 入力候補に出すかどうか。**過去データの表示・検索は妨げない** |

補助科目は必ず 1 つの勘定科目に属する。**明細の補助科目が、その明細の勘定科目に属しているか**を
計上時に検証する（属していない補助科目を許すと補助元帳が壊れる）。

**科目区分と決算書表示区分は別物である。** 表示区分は「財務諸表のどこに並べるか」であって、
科目の性質ではない。台帳の対象や部門の要否は科目区分で判定する。

### 6-1. 通常残高がどちら側か（この規則の正典）

残高・累計を借方と貸方のどちらを正で出すかは、**科目区分と評価勘定の組**で決まる。
**「科目区分が 資産 または 費用」と「評価勘定である」が食い違うなら借方側**、揃うなら貸方側。

| | 評価勘定でない | 評価勘定 |
|---|---|---|
| 資産・費用 | **借方**（現金・雑費） | **貸方**（減価償却累計額・貸倒引当金） |
| 負債・純資産・収益 | **貸方**（買掛金・売上高） | **借方**（売上値引戻り高） |

**科目区分だけで決めると、評価勘定の 2 通りが必ず逆になる。** 最初の実装は総勘定元帳の
「期間内累計」で、`GeneralLedgerQueryTests` が 4 通りを固定している。
**フェーズ 4 の試算表は 2 つ目の実装**なので、そのときこの表と突き合わせる（ADR-0022 の帰結）。

## 7. 会計期間と締め

会計年度（`fiscal_years`）の下に月次期間（`accounting_periods`）が並び、**どちらも締め状態を持つ**。
会計年度は**優良な電子帳簿の適用開始日**（`premium_ledger_from`）も持つ。
列は [`Designer/ddl/`](../Designer/ddl/README.md)（`002_periods.sql`）が正典（§4-1 と同じ理由）。

- **会計年度は 12 か月とは限らない。** 設立初年度・解散年度・事業年度の変更で 1 年未満になり、
  法人が節税等の目的で意図的に短くすることもある（開発者の指摘。2026-08-27）。
  **月次期間が 12 個ある前提を、どこにも置かない**——期間の生成も、按分も、年換算も
  **`start_date` と `end_date` から数えた月数**で導く。制度の判定にも効く
  （全額控除の 5 億円判定は年換算が要る。[11 §7](11_消費税設計.md)）。
  **年換算は制度ごとに条文を見る。一律に当てない**——経過措置の相手方別上限は**しない**（[11 §5](11_消費税設計.md)）
- **期間の解決は「対象日の月初日」で行わない。** 日付は `YYYY-MM-DD 00:00:00` に正規化して範囲比較する（[qa/01](qa/01_CLB静かな失敗.md) A-04）。前回プロジェクトが月初日方式で回避していた問題は、書式を正規化すれば起きない
- 締めは**月次 → 年度**の順。締め前チェック（貸借不一致・下書きの残存・部門未設定・税区分未設定）を通す
- 再オープンは権限者のみ。**理由と実行者と日時を必ず記録**する
- **優良な電子帳簿は「課税期間の初日から」全帳簿で要件を満たす必要がある**（電帳法 8 ④・電帳令 2）。
  年度の途中から有効化できないので、`premium_ledger_from` が年度の開始日と一致しない場合は警告する

## 8. 期首残高と繰越

- 期首残高は**マスタではなくデータ**（[12_マスタ台帳 §3](12_マスタ台帳.md) にも載せない）。
  科目・補助科目・部門の単位で持ち、**貸借一致を検証する**
- 導入初年度の期首残高は利用者が入力する。2 年目以降は繰越処理が生成する
- 繰越は「前期末の B/S 科目残高を翌期首へ移し、P/L 科目の残高を繰越利益剰余金へ振り替える」
- **前期を後から訂正したときのために、繰越は再実行できる**（暫定繰越）。
  前期を締めた時点で確定させる。暫定と確定を区別し、前期に変更があったら陳腐化を検知する

## 9. 部門

[ADR-0010](decisions/0010-部門は単一階層とし損益科目でのみ必須にする.md) のとおり単一階層。
「全社共通」を 1 件持つ。**損益科目の明細では必須、貸借科目の明細では任意。**

**部門は会計が生んだ集計軸であり、人事組織とは一致させない**
（[ADR-0029 §2](decisions/0029-所有は相手抜きで存在するかで導き粒度は決断で決める.md)。将来 人事部品ができても統合しない）。

### 9-1. システム生成仕訳の部門付与ルール（実装より先に確定させる）

人が入力しない仕訳にも部門は要る。**後付けすると破綻する**ので、生成経路ごとにルールを定める。

| 生成経路 | 対象科目 | 部門の決め方 |
|---|---|---|
| 消費税行 | 仮払・仮受消費税等（B/S 科目） | **親行から引き継ぐ**（任意項目だが、税集計を部門別に見るために引き継ぐ） |
| 期首残高 | B/S 科目のみ | **不要**（損益科目が現れないため構造的に問題が起きない） |
| 決算振替（損益 → 繰越利益剰余金） | 損益科目 ＋ 純資産科目 | 損益科目側は**振り替える元の明細の部門を引き継ぐ**。純資産側は任意 |
| 繰越（翌期首残高の生成） | B/S 科目のみ | **不要**（期首残高と同じ） |
| 減価償却仕訳 | 減価償却費（損益科目） | **固定資産が部門を持つ**。台帳から引き継ぐ |
| 他部品からの投入 | 任意 | **投入元が指定する。** 損益科目に部門が無ければ検証で弾く（穴埋めしない） |

**「部門が空なら全社共通で埋める」保険を全経路に置く設計にはしない。** それは
「値が入っているのに意味がない」状態を作り、誰も気づかないまま部門別損益が嘘になる。
全社共通は**利用者が意図して選ぶ**ときだけ使う。

## 10. 他部品からの仕訳投入

会計コアが公開する唯一の書き込み経路。

- 投入元は `source_component` ＋ `source_document_id` ＋ `idempotency_key` を必ず付ける
- 会計コアは**投入された仕訳にも同じ検証を通す**（貸借一致・期間・部門・税区分）。
  「外部からだから信用する」経路を作らない
- 投入された仕訳も計上後は不変。訂正は反対仕訳による
