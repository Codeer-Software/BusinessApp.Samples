# CLB の高く評価している点（GOOD-xxx）

> 改善提案と対で「維持・強化してほしい設計」を記録する。本プロジェクト（複式簿記の財務会計アプリをほぼノーコード＋少量 C# で構築）での実感ベース。

### GOOD-001 DataWriteCondition のサーバ強制と UI への自動反映
行レベルの書込条件（例: 工数は本人の行のみ）を 1 箇所書くだけで、サーバ側で強制されると同時に**他人の行の削除ボタン非表示・詳細の読み取り専用化まで UI が自動で追随**する。内部統制の実装コストが劇的に低く、顧客デモでの訴求点にもなった。FB-010 は「UserWriteCondition もこの水準に揃えてほしい」という要望である。

### GOOD-002 UserReadCondition とメニュー表示の連動＋直 URL のサーバブロック
読取権限の無いモジュールはサイドバーから自動で消え、URL 直打ちも「不正なアクセスです」で止まる。「見えないだけで叩けば通る」穴が構造的に無い。3 ロールの権限設計が宣言だけで完成した（当時の構成。2026-08-02 再編後の部門メンバーシップ型権限も同機構で実現 → `docs/10_部品アーキテクチャ.md`）。

### GOOD-003 QueryField（SQL 直書き帳票）の自由度
試算表・BS/PL・キャッシュ・フロー計算書・月次推移表・資金繰り予測まで、**会計帳票のすべてを QueryField の SQL だけで構築できた**。ウィンドウ関数・CTE・再帰 CTE も通る。「宣言的 UI ＋ 生 SQL」の組合せは業務システムの現実解として非常に強い。

### GOOD-004 designcheck CLI
デザイン JSON の読込妥当性をヘッドレスで検証できるため、AI エージェントによる自律開発ループ（編集 → designcheck → デプロイ → 実機確認）が成立した。findingCount=0 を機械的なゲートにできる。FB-018 はこれをもっと欲しいという要望。

### GOOD-005 zip 監視による hot-reload デプロイ
`Designs.Cookie\App.zip` を置くだけで稼働中サーバに反映される仕組みは、CI 的な自動デプロイと相性が良い（仕様が文書化されればなお良い → DOC-011）。

### GOOD-006 AITextAnalyzerField の設計
「ファイル添付＋AI 抽出＋フィールド自動充填」が 1 コントロールで完結し、**プロンプト（Remarks）をデザイン側に持てる**ため、抽出ルールの調整がノーコード領域でできる。Select/Link 候補の解決まで面倒を見てくれる。モック Provider があるおかげで API キー無し環境でも開発・デモが回るのも実務的。

### GOOD-007 ExcelReport（テンプレート差込）と Excel 一括ダウンロード/アップロード
実物の請求書 Excel をテンプレートにして FindCellByText 差込 → Excel/PDF 出力、という流れが素直。一覧の Excel DL/UL（予算の一括登録に使用）も業務アプリの定番要求をカバーしている。

### GOOD-008 認証・承認フローのサンプル（PatternShowcaseAuth）の正典性
承認ワークフローという最難関領域を、サンプルの複製・改変から出発できた。「ゼロから作らせない」ドキュメント戦略（AppPatterns / Samples / Defaults）は AI 開発との相性が特に良い。

### GOOD-009 designcheck が URL セグメント重複を検出してくれた（2026-07-19）
ロール別フレーム再編で TopPageModuleDesign とサイドバーリンクが同一モジュール（Home）を指した際、「URLセグメント重複」として4フレームぶん正確に指摘され、実機で踏む前に修正できた。フレーム大規模再編のような構造変更でも designcheck → 0件 が信頼できるゲートとして機能している。
