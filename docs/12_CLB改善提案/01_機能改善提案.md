# CLB 機能改善提案（FB-xxx）

> 「静かな失敗」（エラーにならず壊れる）を最優先に並べている。各項目の「出典」は本リポジトリ内の実測記録。
> 環境: Codeer.LowCode.Blazor 1.2.51.0 / net8.0 / SQLite。

## A. 静かな失敗を防ぐ（最優先群）

### FB-001【高】ExecuteSqlField のパラメータ解決が「フィールド名」ではなく「DB 列名」
- **事象**: SQL 内の `@プレースホルダ` は Parameters に指定したフィールドの **DbColumn 名**で解決される。フィールド名（例 `NextYearId`）で書くとバインドされず、SQLite の「Must add values for the following parameters」で **Submit 全体がロールバック**する。フィールド名＝列名のときは偶然動くため、命名が食い違ったときだけ突然壊れる。
- **困った点**: 真因特定まで数日を要した（当初は「ボタンから発火しない」に見えた）。エラーがどのフィールドの問題か示さない。
- **提案**: ①フィールド名でも解決する（または両対応） ②少なくとも designcheck で「SQL 内の @名 が Parameters の DbColumn と一致するか」を検証する ③実行時エラーに「@名 ↔ 利用可能パラメータ一覧」を含める。
- 出典: `docs/issues/ISSUE-0001`（解決済み）・Project.md 2026-07-08。

### FB-002【高】ModuleSearcher の OrderBy/OrderByDescending でラムダに `.Value` を忘れると「エラーにならずソートが無効」になる
- **事象**: `searcher.OrderByDescending(e => e.JournalNo)` は例外にならず**ソートされない**。`.Value` 付きが正。`Limit(1)` と組み合わせた採番ロジックで常に同じ番号が返り、伝票番号が 4 件重複した。
- **提案**: AddEquals 系と同様に Variable 規約違反を**実行時例外**にする（または式解析で designcheck 検出）。「動くけど並ばない」は採番・最新取得の定番バグ源。
- 出典: Project.md 2026-07-06（実測）。

### FB-003【高】DateField への DateTime 代入が「UI には表示されるのに保存されない」
- **事象**: スクリプトで DateField.Value に DateTime を代入すると画面表示は正しいが、保存データに値が乗らず NOT NULL 違反になる。`DateOnly.FromDateTime()` が必須。
- **提案**: 型不一致の代入をコンパイルエラーまたは即時例外にする（暗黙変換を入れるのでも可）。「見えているのに保存されない」は発見が遅れる。
- 出典: Project.md 2026-07-07（BankImport で実測）。

### FB-004【高】表示専用モジュール（DataSourceName 空）の `this.Submit()` が無反応（例外なし）
- **事象**: 戻り値も例外も無く、単に何も起きない。ListField の行保存は `row.Submit()` が正解だが、それに気づく手掛かりがない。
- **提案**: データソース未バインドのモジュールで Submit を呼んだら例外（または明示の false＋ログ）。
- 出典: Project.md 2026-07-07。

### FB-005【高】レイアウトに出ていないフィールド・ChildModule の `.Value` が遅延ロードで null になる
- **事象**: DataOnlyFields や画面に出ていない LinkField の値が、実行タイミングによって null（例: 申請者の部門引継ぎが欠落）。ChildModule の Status もメモリを信用できず、確実に値が要る処理はすべて ModuleSearcher で DB から取り直すコーディング規約を敷いて回避した。
- **提案**: ①スクリプトから使うフィールドを確実にロードする明示 API（`await this.EnsureLoaded(f => f.Creator)` のような） ②未ロード値へのアクセスを null でなく例外にするオプション。静かな null はロジックの歯抜けを生む。
- 出典: Project.md 2026-07-06（2 件）。

### FB-006【中】新規未保存の子行 Id（`@temporary:GUID`）を数値検索条件に渡すと FormatException（サーバ 500）
- **事象**: 新規生成直後の子行 Id を条件に ModuleSearcher で検索すると落ちる。クライアントで例外が握り潰される経路もあり、発見が遅れた。
- **提案**: ModuleSearcher 側で temporary Id を検出して明示エラー（または空結果）にする。あわせて「クライアントで握り潰される例外」を開発者コンソール等に必ず出す。
- 出典: Project.md 2026-07-08。

### FB-007【中】TEXT 宣言の日付列で DateOnly が MM/dd/yyyy 文字列化され比較・ソートが破綻する
- **事象**: DDL で DATE でなく TEXT と書くと、CLB が InvariantCulture 書式で保存し辞書順比較が壊れる。DatabaseGuidelines に記載はあるが、踏むと DROP→再作成が必要で被害が大きい。
- **提案**: ①日付系フィールドがマップされた列の型を designcheck で検証 ②TEXT 列でも ISO 8601（yyyy-MM-dd）で書き込む。
- 出典: Project.md 2026-07-05（030 で実測・全 DDL 是正）。

### FB-008【中】日付検索パラメータの書式が seed 由来の素の DATE 文字列と混在し、境界日（月末）の比較が辞書順で偽になる
- **事象**: `end_date >= @日付` が「@日付 = end_date と同日」で失敗し、月末日付の伝票が「対応する月次期間がありません」になる。全スクリプトを「月初日で期間解決する」方式に統一して回避した。
- **提案**: CLB が日付パラメータ・日付列書き込みを常に同一の正規形（date() 適用相当）に揃える。アプリ側の回避（月初日方式）はマニュアルにも載せてほしい（→ DOC-007）。
- 出典: Project.md 2026-07-06/07-07（実発現を確認）。

### FB-030【高】モジュール `IsViewOnly = true` で ButtonField の OnClick が発火しなくなる（1.2→1.3 の挙動変更・エラーなし）
- **事象**: 「確定済みデータは閲覧専用＋取消ボタンだけ残す」パターン（`this.IsViewOnly = true` ＋ ボタン IsVisible 制御）が、CLB 1.2.51 では動いていたのに 1.3.4 では**ボタンをクリックしてもハンドラが呼ばれなくなった**。ボタンは disabled 見た目にならず通常表示のまま・コンソールエラーもネットワーク要求も無しで、単に無反応（実測: 見積の「下書きに戻す」・検収の「確定を取り消す」・入金の「入金を取り消す」が全滅）。
- **回避策（実測で有効）**: モジュールを ViewOnly にした後、操作させたいボタンだけ `Button.IsViewOnly = false;` を明示する（フィールド個別設定がモジュール設定に勝つ）。
- **提案**: ①ViewOnly でクリック不能になるならボタンを disabled 表示にする（見た目と挙動の一致） ②またはボタンは既定で ViewOnly の影響外にする（1.2 挙動へ戻す） ③リリースノートに挙動変更として明記。
- 出典: 2026-07-20 実測（CLB 1.3.4/1.3.6 アップグレード後にユーザーレビューで発覚。Quote/Acceptance/Receipt を個別解除で修正）。

### FB-031【高】列挙型の旧値がデシリアライズエラーにならず既定値に化ける（HorizontalAlignment "Right" → Start）
- **事象**: 1.3 系で `HorizontalAlignment` の値名が `Left/Center/Right` から `Start/Center/End/Stretch` に変わったが、旧値を含む JSON は**エラーにも designcheck の指摘にもならず、既定値 Start（左寄せ）として静かに解釈**される。さらにデザイナで保存すると旧値 "Right" が "Start" に**固定化**され、右寄せ意図が失われる（実測: ラベル右寄せ 11 箇所がデザイナ保存で左寄せ化）。
- **回避策**: リポジトリ全体で旧値を新値へ一括変換した（Right→End / Left→Start、73 箇所）。
- **提案**: ①旧値名を正しい新値へマップする後方互換コンバータ（Right→End） ②未知の列挙値は designcheck で警告する ③破壊的リネームはリリースノートに明記。
- 出典: 2026-07-20 実測（commit 4251148）。

### FB-032【中】一覧の Excel ダウンロードが数値列も文字列セルで出力する
- **事象**: `CanBulkDataDownload` の Excel 出力は、NumberField（Format 指定あり・SQL も数値型を返すクエリモジュール）でも**全セルを共有文字列（`t="s"`）で書き出す**（貸借対照表の出力 xlsx を解析して実測。2026-07-21）。ダウンロード後にユーザーが SUM 等の集計・再計算をしようとすると全列が文字列で使えず、Excel 側で手動の型変換が必要になる。
- **提案**: フィールド型が数値・日付の列はネイティブ型のセル（`t` 省略＋数値書式）で出力する。表示フォーマット（#,0）は Excel の表示形式（numFmt）へマップするのが理想。
- 出典: 2026-07-21 ユーザーレビュー指摘 → xlsx 実測（フィールド定義・クエリ側は数値で正しく、フレームワークの Excel ライタ起因と特定）。

### FB-033【中】LinkFieldNames のリンク先参照フィールドを検索レイアウトに置くと「描画はされるが候補が空」になる（エラーなし）
- **事象**: `LinkFieldNames` に `SalesOrderRef.PartnerRef` のようなパス（SelectField マスタ参照経由）を登録し、SearchLayout の `FieldLayoutDesign.FieldName` にそのパスを指定すると、**designcheck は 0 件で通過し、検索画面にドロップダウンも描画される**が、参照先モジュールの候補が検索コンテキストではロードされず**空のまま**（値を選べない＝実質検索不能）。エラー・警告・ログなし。
- **提案**: (1) 検索コンテキストでも参照フィールドの候補をロードして「親の参照先で絞る」検索を成立させる（子文書を親の属性で検索する需要は業務アプリで頻出）、または (2) 非対応なら designcheck が「検索レイアウトにリンク先参照フィールドは配置できません」を検出してエラーにする。
- 出典: 2026-07-23 実測（ランタイム 1.3.4）。検収（Acceptance）に受注経由の取引先・案件・部門検索を試作した際に発見。回避策として当該検索は見送り（親側の属性を子へ非正規化すれば可能だが今回は不採用）。

## B. 権限・ナビゲーション

### FB-009【中】メニュー項目（PageFrame の Link）にロール等の可視条件を設定できない
- **事象**: メニューの表示/非表示は「遷移先モジュールの UserReadCondition」に完全連動する。「モジュール自体は読める必要がある（他画面のセレクト参照・スクリプト参照のため）が、メニューには出したくない」ケースが表現できない。
- **実測した回避策（2026-07-10 のページフレーム分割で確立・有効）**: ①フレーム単位の UserReadCondition と「入口リンクの Module を権限を代表する画面にする」ことで大半は表現できる ②入口専用の表示専用モジュール（例: 読取= sysadmin の AdminHome）を作れば任意ロールの入口を作れる ③セレクト参照だけ必要なモジュールは非機微列だけの Lookup モジュール（例: FiscalYearLookup）に分離する。ただしいずれも「モジュールを増やす」回避であり、リンク単位の条件があれば不要。
- **提案**: PageFrame の Link 単位に UserReadCondition（または表示条件式）を設定できるようにする。
- 出典: 2026-07-10 ページフレーム分割（docs/decisions/0019）。

### FB-023【高】フレーム跨ぎリンクは「遷移先フレームに同一 Module×URL セグメントの登録」が無いと画面が静かに真っ白になり、designcheck が検出しない
- **事象**: PageLink の `PageFrame` に別フレームを指定した場合、遷移先 URL のセグメント解決は**遷移先フレームに登録されたページ定義**（Links／TopPageModuleDesign／OtherPageModuleDesigns）で行われる。遷移先フレームに該当 Module×セグメントの登録が無いと、サイドバーだけ描画されコンテンツが**エラーなしで真っ白**になる（実測: Main→AdminFrame の入口リンク Module=AdminHome、AdminFrame 側は TopPage（セグメント Top）としてのみ登録 → /AdminFrame/AdminHome が白画面）。CommonMistakes #38 の亜種だが、**designcheck はフレーム内の登録漏れもフレーム跨ぎの不整合も検出しない**。
- **提案**: ①designcheck に「PageFrame 跨ぎリンクの遷移先登録チェック」を追加（Link.PageFrame≠空のとき、遷移先フレームのページ定義に Module×セグメントが存在するか） ②実行時も真っ白でなく「ページ定義がありません」を表示する。
- 出典: 2026-07-10 ページフレーム分割で実測（OtherPageModuleDesigns への登録で解消）。あわせて「同一フレーム内の URL セグメント重複」は designcheck が検出してくれた（TopPage と Link の Module 重複）——この検出は有用だった。

### FB-010【中】UserWriteCondition の UI 連動が「フィールドの読み取り専用化」で止まり、ボタンは残る
- **事象**（2026-07-09 の sysadmin 権限再編で実測して精緻化）: UserWriteCondition を満たさないユーザーが既存レコードの詳細を開くと、**フィールドは自動で読み取り専用になる**（この連動自体は素晴らしい）。しかし①一覧の「新規作成」ボタンは表示されたままで、新規作成画面にも遷移できる ②詳細の「登録」ボタンも表示されたまま——「入れないのにボタンはある」という UX の非対称が残る。1.3.4 でも同様（ListPageDesign にも権限連動のプロパティは無いことをリフレクションで確認）。
- **提案**: UserWriteCondition を満たさないユーザーには、新規作成ボタン（PageFrame Link 側）と SubmitButton・一覧の削除ボタンも自動非表示にする（フィールド読み取り専用化と同じ水準に揃える）。
- **本アプリでの対処（2026-07-11・設計としてはむしろ推奨形）**: 「読めるが書けない画面」を作らない構成に変更した——マスタの**編集画面は編集権限のあるロール専用フレームに置き**（取引先・案件 → 会計フレーム）、他ロールには**閲覧専用の確認ページ**（CanCreate/Update/Delete=false・詳細遷移なし・DetailLayouts 空の一覧専用モジュール）を提供する。データ読取権限はセレクト参照のため全員のまま＝「画面の到達可否」と「データの読取可否」を分離する。この二枚看板パターンは AppPatterns に載せる価値がある（→ DOC 側にも提案余地）。
- 出典: ユーザー実操作レビュー（2026-07-09、2026-07-11 に「そもそもマスタを直接見せない」方針で確認ページ分離を実装）・sysadmin/経理の権限差の実機確認（勘定科目画面）。

### FB-011【低】検索条件のラベルは「手動でラベル列を並べる」しかなく、既定では無ラベルになる
- **事象（調査で判明）**: 検索レイアウトに LabelField の列を置けばラベルは実現できる（正典 AllFieldsSearch がこのパターン）。ただし**既定の検索フォームは無ラベル**で、「どの欄が何の条件か分からない」UI が簡単にできてしまう。本アプリでは全 32 モジュール・78 ラベルをスクリプトで一括挿入して解決した（フィールドの DisplayName + 「：」を自動付与）。
- **提案**: ①検索レイアウトの項目に「DisplayName を自動でラベル表示する」オプション（デザイナのワンチェック）を用意する ②少なくとも SearchConditionGuidelines にラベル付与の推奨パターンを明記する（→ DOC-015）。
- 出典: ユーザー実操作レビュー（2026-07-09）→ 2026-07-10 全画面一括対応済み。

### FB-012【中】CanCreate:false が「UI の新規作成」と「スクリプトからの生成」を同時に塞ぐ
- **事象**: スクリプトで new→Submit するモジュールは CanCreate:true が必須（false だとサーバが "This module data cannot be created" で拒否）。「ユーザーには新規作成させないが、システムは生成する」（自動仕訳・自動採番台帳など）が素直に書けず、PageFrame Link の UseNavigateToCreate:false ＋ ListField の CanCreate:false の組合せで UI 側だけ塞ぐ回避をしている。
- **提案**: モジュール権限を「UI 操作」と「スクリプト（サーバ内）操作」で分離する、またはスクリプト実行コンテキストには CanCreate を適用しないオプション。
- 出典: Project.md 2026-07-07。

### FB-013【中】読取ゲート付きモジュールへの代理作成で Submit の戻り値から成否が判定できない
- **事象**: DataReadCondition（自分宛のみ）が付いた通知モジュールに他ユーザー宛レコードを new→Submit すると、INSERT は成功しても戻り値が true にならない（Submit 後の再読込が読取条件で 0 件になるため）。再検索による確認も同じ理由で不可能。
- **提案**: Submit の戻り値を「書込の成否」と「再読込の可否」に分離する（例: 結果オブジェクトに Inserted/Reloaded を分けて返す）。
- 出典: Project.md 2026-07-08（通知の誤警告トースト不具合の真因）。

### FB-014【低】承認フロー枠の「申請種別」がモジュール名の生文字列（例: ExpenseRequest）で表示される
- **事象**: フロー系 UI に出る ParentModuleName がモジュールの内部名のまま。SelectField の Candidates で日本語マップする回避をした。
- **提案**: モジュールの DisplayName を解決して表示する（または表示名解決のヘルパを提供）。
- 出典: docs/05 2026-07-08（回避実装済み）。

## C. データ構造・親子モジュール

### FB-015【高】多段ネストの子レコードは FK が後埋めされるため、FK 列に NOT NULL を付けるとネスト生成が失敗する
- **事象**: 親子孫（承認フロー→順番→メンバー）の一括 Submit で、子の FK が INSERT 時点では NULL。DDL で NOT NULL を付けていると壊れる。「FK 列に NOT NULL 禁止」という DB 設計規約で回避したが、参照整合性を DDL で守れないのは本末転倒感がある。
- **提案**: ネスト Submit を「親 INSERT → FK を埋めて子 INSERT」の順に 1 トランザクションで行い、NOT NULL 付き FK を許容する。
- 出典: Project.md 2026-07-05（approval_flow_member で実測）。

### FB-016【中】子行が 1 件も無い親では ChildModuleField が実体化されず、UI・スクリプトとも沈黙する
- **事象**: 子モジュールの UI やボタンが出ない・OnAfterInitialization も走らない・未保存の子のフィールドを外部から参照すると「〜操作が存在しません」。スクリプトで「保存済み親に新しい子を付ける」には、子を単独 Submit→実列バインドの NumberField で FK リンク→子の状態を初回扱いにする、という 3 点セットが必要だった。
- **提案**: ①子 0 件でも子モジュールを初期化するオプション ②スクリプトから「親に子を生成して紐づける」公式 API。
- 出典: Project.md 2026-07-08（経費申請の複製機能で確立）。

### FB-017【中】ExecuteSqlField をスクリプトから実行できない（全メンバー ScriptHide）
- **事象**: ボタン → 任意 SQL 実行をやるには「Timing:Update ＋ 非バインドのフラグ列 ＋ SQL 側 NULL ガード ＋ ボタンでフラグセット→Submit」という擬似パターンが必要（翌期繰越で使用）。
- **提案**: スクリプトから安全に呼べる実行 API（実行可否は designer.settings 側の権限で制御）。
- 出典: Project.md 2026-07-05。

## D. 開発体験・検証

### FB-018【中】designcheck の検証範囲を意味レベルへ拡張してほしい

### FB-024【中】サイドバーの Logout が通常メニューと同列に並び、誤クリックしやすい（確認も出ない）
- **事象**: 標準サイドバーは Links の直後に Logout が同じ見た目・同じ密度で並ぶ。メニュー項目のつもりでクリックすると**確認なしで即ログアウト**する（ユーザー実操作レビューで指摘）。
- **提案**: ①Logout をサイドバー下端に分離配置する標準スタイル（または SideBarDesign にオプション） ②ログアウト前の確認ダイアログ（オプションで可）。
- **本アプリでの回避策（2026-07-11 実装・実機確認済み）**: `data-system="logout"` が付与されているおかげで両方ともアプリ資産だけで実現できた——①app.css で `[data-system=sidebar]` を flex 化し logout の nav-item に `margin-top:auto` + `position:sticky; bottom:0`（**CLB 本体 CSS が後勝ちするため `!important` が必要**な点は注意） ②index.html に capture フェーズの click リスナで自前の確認オーバーレイを挟む（OK 時のみ再クリック）。`data-system` 属性の整備は回避策を可能にしている良設計（GOOD 側にも通じる）。
- **追記（2026-07-19）**: ②の確認ダイアログはユーザー方針（index.html への自前 JS を持たない・確認ダイアログ自体を廃止）により撤去した。①の CSS 分離配置は継続。**標準機能としての Logout 分離配置の提案は引き続き有効**。
- 出典: ユーザー実操作レビュー（2026-07-11）。

### FB-025【低】ホーム（ダッシュボード）のショートカットをエンドユーザーが自分で構成できる仕組みがほしい
- **背景**: 業務アプリの定番として「ホームによく使う画面へのショートカットボタンを並べる」構成を採ったが、どの画面をよく使うかはロールでは決まらない（同じ経理でも人によって銀行明細取込中心／帳票中心と分かれる）。現状はロール別の固定セットをアプリ側で作り込むしかなく、ボタンが増えるほど全員に無関係なボタンが混ざる。ユーザーレビューでも「**ホーム画面のボタンを自分で設定できれば最高**」との要望が出た（2026-07-11）。
- **提案**: ユーザー単位のショートカット（お気に入り）機構。例: ①PageFrame の Link に「お気に入り登録可」フラグを付け、CLB がユーザー別の選択状態（DB テーブル）を管理 ②ホームに置ける「お気に入り一覧」標準フィールド（AnchorTag の動的リスト）を提供。一覧のユーザー列カスタマイズ（CanCustomizeColumns）と同系統の「ユーザー別 UI 状態の永続化」であり、既存機構の延長で実現できるはず。
- **アプリ側の現状**: ロール別固定ショートカット（全員=経費申請・工数入力、経理はさらに振替伝票・銀行明細取込・月次推移表・資金繰り予測）。ユーザー別にするには専用テーブル＋動的 AnchorTag 生成の作り込みが必要で、今回は見送った。
- 出典: ユーザー実操作レビュー（2026-07-11）・ADR-0021。

### FB-026【低】読取ゲート付き Detail 型ページへの直 URL アクセスが「不正なアクセスです」トースト＋Blazor 未処理例外（黄色バー）になる
- **事象**（2026-07-13 全ロール×全画面の巡回チェックで実測）: フレームには入れるがモジュールの UserReadCondition を満たさないユーザーが、Detail 型ページ（例: 承認者ロールで経理専用の /Budget/BudgetEntry）を直 URL で開くと、「不正なアクセスです」トースト（正しい防御）と同時に **「An unhandled error has occurred. Reload」の黄色バー**が出て SPA が停止する（リロードで復帰）。一覧型（ListPage）の同条件やフレームゲート（「ページフレームへのアクセス権限がありません」）は例外なく綺麗にブロックされるのと非対称。

- 出典: 2026-07-13 巡回チェック（承認者×/Budget/BudgetEntry で再現。同型の他画面も同挙動と推定）。

### FB-027【中】CLB 標準 UI の文言が英語固定でローカライズ手段がない
- **事象**（2026-07-16 レビュー第4弾で棚卸し）: 日本語アプリでも以下が英語のまま表示される。
  - 一覧の削除確認ダイアログ: 「削除しますか？」＋ **Yes / No** ボタン（本文は日本語なのにボタンだけ英語）
  - サイドバー最下部のログアウトリンク: **Logout**
  - 権限エラー等の一部トースト: **No permission to read module** 系
  - Blazor 標準の黄色バー: **An unhandled error has occurred. Reload**（これは Blazor 側だが、テンプレートの index.html 既定文言として CLB テンプレにも波及）
- **アプリ側で回避できた分**: Logout 表記と黄色バーは index.html の DOM 差し替え（MutationObserver）で日本語化した。ただし削除確認の Yes/No とサーバ発トーストは Blazor コンポーネント内部のため**アプリ側から安全に差し替える手段がない**。
- **追記（2026-07-19）**: MutationObserver による Logout 日本語化はユーザー方針（index.html への自前 JS を持たない）により撤去し、現在は英語 "Logout" 表記のまま運用している。**アプリ側の回避手段を放棄したため、本提案（ローカライズ API）の重要度はむしろ上がった**。
- **提案**: ①文言リソースの差し替え API（リソースファイル or AppSettings での辞書指定） ②少なくとも削除確認ボタンを「はい/いいえ」にするか MessageBox.Show と同様にラベル指定可能にする。業務アプリの納品先はエンドユーザーが非エンジニアであり、部分的な英語は「未完成品」の印象を与える。
- 出典: 2026-07-16 実測（請求書一覧の削除確認・サイドバー・権限トースト）。

### FB-028【高】子持ちモジュールの「検索インスタンス」に対する Delete() が子の FK 制約で失敗する（DeleteTogether が効かない）
- **事象**（2026-07-19 実測）: `ModuleSearcher<JournalEntry>` で取得したインスタンスに `Delete()` を呼ぶと、子（journal_lines）が FK で親を参照しているため **SQLite Error 19: FOREIGN KEY constraint failed** で失敗し `false` が返る。UI 経由の削除では `DeleteTogether: true` の子が先に消えるが、**スクリプトからの検索インスタンス削除にはカスケードが適用されない**。戻り値を確認しないと「トーストは成功・DB には残存」の静かな失敗になる（実際に踏んだ）。
- **回避策（本アプリで確立）**: 明細を `ModuleSearcher` で列挙して1行ずつ `Delete()`（各戻り値を検証）→ 最後に親を `Delete()`。さらに削除対象を FK 参照している他テーブルの列（例: vendor_invoices.accrual_entry_id）は**先に null にして Submit** してから削除する。
- **提案**: ①検索インスタンスの Delete() にも DeleteTogether のカスケードを適用する ②少なくともマニュアル（Scripts.md の Module API）に「Delete() は bool? を返す・子持ちモジュールでは子を先に消す必要がある」を明記する。
- 出典: docs/05 2026-07-19（未払計上取消の実装で実測）。

### FB-029【中】FK 制約違反が生の SQLite エラー文のままトースト表示される
- **事象**: 参照されている行の削除などで「SQLite Error 19: 'FOREIGN KEY constraint failed'.」がそのままエンドユーザーに表示される（2026-07-14 の承認テンプレート削除でも同事象を記録済み）。防御としては正しいが、非エンジニアには意味不明。
- **提案**: DB 例外を人に読める形へ変換するフック（例: FK 違反→「使用中のため削除できません」）または例外メッセージの差し替えポイントの提供。
- 出典: 2026-07-19 実測（仕入先請求書の削除ガード）・2026-07-14（ADR-0023 検証）。

### FB-034【高】PageFrame の UserReadCondition がログインユーザーのレコードの列しか参照できない（関連テーブルで権限を表せない）
- **事象**（2026-08-02 部品アーキテクチャ再編・ADR-0041 で直面）: フレームゲートは `CurrentUserModule`（AppUser）のフィールド条件のみで、**リンク先・関連テーブル（例: 部門メンバー表・部門マスタの種別）を条件に使えない**。「営業種別の部門にメンバー行を持つユーザーにだけ営業フレームを見せる」という自然な権限表現が直接は書けない。
- **回避策（本アプリで確立）**: AppUser にゲート用キャッシュ列（has_sales_access 等）を持ち、メンバーシップ表・部門種別からの導出を **DB トリガーで経路非依存に転記**する（select_label と同じ定石）。一括再計算 SQL（ddl/385）も常備。
- **提案**: ①UserReadCondition で関連モジュール経由の条件（EXISTS 相当）を書けるようにする ②または「ログインユーザーの権限セット」を返すスクリプトフック（サーバ側で評価）を用意する。キャッシュ列方式は動くが、テンプレート利用者に「なぜこの列があるのか」の説明コストが常に付く。
- 関連: FB-009（リンク単位の可視条件が無い）。この 2 つが揃うと「部品×対象者でフレームを分ける」設計の JSON 重複が大きく減る。
- 出典: ADR-0041・ddl/380（トリガー実装）。

### FB-035【高】表示専用モジュール（DbTable 無し）の Detail でボタンが pointer-events:none になりクリック不能（静かな失敗）
- **事象**（2026-08-02 実測・ADR-0042 の業務ポータルで直面）: `DbTable: ""`・CanCreate/Update/Delete 全て false の表示専用モジュールを Detail ページで開くと、モジュールがビュー専用扱いになり、**ButtonField がインラインstyle `pointer-events: none;` 付きで描画される**。見た目は通常のボタン（disabled でも半透明でもなく cursor:pointer のまま）なのにクリックだけが無反応で、コンソールにもエラーが出ない。designcheck でも検出されない。
- **回避策（本アプリで確立）**: `Detail_OnAfterInit` の先頭で `IsViewOnly = false;` を明示する（PortalHome.mod.cs）。
- **提案**: ①表示専用モジュール（DbTable 無し）の Detail はビュー専用の既定を「操作可」にする（ボタンを置く＝押させたい意図が明白）②少なくともビュー専用時のボタンは disabled 見た目（半透明＋not-allowed）にして「押せないことが見て分かる」状態にする。「見た目は有効・実は無反応」が最悪の形。
- 出典: ADR-0042（業務ポータル実装）。
- **追記（2026-08-14・ADR-0056）**: 同じ現象が **DbTable を持つ通常モジュール**でも起きる。
  スクリプトで `this.IsViewOnly = true`（確定済み伝票を閲覧専用にする用途）にすると、
  そのモジュールの **ButtonField もすべて `pointer-events: none` になり押せなくなる**。
  「閲覧専用にしたいのは入力項目であって、操作ボタンではない」場面（確定済み伝票から
  サブ画面へ飛ばすボタンなど）で詰む。回避策は**入力項目を 1 つずつ `IsViewOnly` にする**ことだが、
  レイアウトに項目を足したとき列挙を更新し忘れると**編集できてしまう**——安全側の既定と逆になる。
  提案: モジュールの `IsViewOnly` は**値を持つフィールドにだけ効かせ、Button/Anchor は対象外**にする
  （または `IsViewOnly` に「ボタンを含めるか」の指定を設ける）。

### FB-036【中】rename-module が PageFrame のレガシー `TopPageModule` プロパティを追従しない
- **事象**（2026-08-02 実測）: `rename-module`（RoleDispatch→PortalHome）で `TopPageModuleDesign.Module` は追従したが、同じ frm.json に併記される**旧形式の `TopPageModule` プロパティは旧名のまま残った**。designcheck も findings 0 のまま検出しない。今回はランタイムが TopPageModuleDesign を優先していたため実害前に気づけたが、旧プロパティを読む経路があれば静かに壊れる。

- **提案**: ①rename-module のリファクタリング対象に `TopPageModule` を追加 ②またはレガシープロパティ自体を廃止（読み書きしないなら designcheck で「不一致」を警告）。
- 出典: ADR-0042（Main.frm.json:135 で実測）。

### FB-037【中】IsVisible=false のフィールドは固定幅カラムが空のまま残りレイアウトに穴が空く
- **事象**（2026-08-02 実測）: スクリプトで `Btn.IsVisible = false` にすると field-layout は描画されないが、**Width 指定の grid-column 自体は空 div（幅 150px 固定）として残る**。折り返し行にボタンを並べる「タイル」構成では、権限で非表示にしたタイルの位置に空白が並び、「ボタンが中途半端な位置に浮く」見た目になる（業務ポータルで実測。ExpenseHome の旧切替ボタンにも潜在していた）。
- **回避策（本アプリで確立）**: app.css で対象モジュールをスコープし、中身の無いカラムを畳む: `[data-module="PortalHome"] .grid-column:not(:has(.field-layout)) { display: none; }`。
- **提案**: ①フィールド非表示時にカラムごと畳む opt-in（例: GridColumn.CollapseWhenFieldHidden）②または「可視フィールドだけを詰めて並べる」フロー系行の提供。権限でボタン数が変わる画面はこのアーキテクチャの定石なので、CSS 回避なしで組めるようにしたい。
- 関連: FB-009/FB-034（権限による出し分けの表現力）。
- 出典: ADR-0042（業務ポータル実装）。

### FB-038【中】サイドバーのモジュール置換（SideBarDesign.ModuleName）で描画されるモジュールに `data-module` 属性が付かない
- 現象: 通常の詳細ページは ルート div に `data-module="X"` が付き CSS スコープに使えるが、`Left.ModuleName` によるサイドバー置換は ModuleRenderer 経由の描画になり、識別属性が GUID の `data-name` のみになる（2026-08-05 実測・1.3.16）。
- 影響: サイドバー内モジュール専用の CSS（リンク色・非表示行の畳み込み等）を書くとき、`data-module` でスコープできず、サイドバー容器のクラス（デスクトップ `.sidebar`／モバイル複製 `.sidebar-nav`）×`.field-layout` という間接的なセレクタに頼ることになる。CLB 内部クラス名への依存はバージョンアップで壊れやすい。
- 提案: ModuleRenderer 描画（サイドバー/ヘッダー置換・ModuleField 埋め込み）でも一貫して `data-module="モジュール名"` を付与してほしい。
- 回避策: 本アプリでは `.sidebar .field-layout a` / `.sidebar-nav .field-layout a` でスコープ（app.css）。
- 関連: FB-031 系（DOM 構造の安定識別子）。

### FB-039【高】スクリプトの `ref` / `out` 引数が呼び出し元に伝わらない（静かな失敗）
- **事象**（2026-08-14 実測・ADR-0055 の入出金起票で直面）: モジュールスクリプトで `int PostOne(Draft d, ref int tax)` のように `ref` 引数を定義し、呼び出し元で `var tax = 0; PostOne(d, ref tax);` としても、**メソッド内で `tax` に代入した値が呼び出し元に反映されない**（ゼロのまま戻る）。コンパイルエラーにも実行時エラーにもならず、コンソールにも何も出ない。結果として「消費税額の合計が常に 0」＝表示から情報が静かに欠落した。
- **困った点**: C# として自然な書き方が黙って壊れるため、原因の特定に時間がかかる。DB もログも正常で、値だけが落ちる。
- **回避策（本アプリで確立）**: 戻り値の受け渡しはモジュールレベル変数で行う（`int lastPostedTax = 0;` を宣言し、メソッドはそこへ書き、呼び出し元が読む）。
- **提案**: ①`ref`/`out` をサポートする ②できないなら**スクリプト保存時（または designcheck）で「`ref`/`out` は未サポート」とエラーにする**。「書けてしまうが効かない」が最悪の形。
- 出典: ADR-0055（CashEntry.mod.cs のコメントに実測を記録）。

### FB-040【中】ListField の行削除（CanDelete）はメモリ上の操作で、DB には反映されない
- **事象**（2026-08-14 実測）: 表示専用モジュール（`DbTable: ""`）にホストした ListField で `CanDelete: true` にすると行のゴミ箱ボタンが出て、押すと**画面からは消える**。しかし DB は変わらないため、`Reload()` や画面再訪で**行が復活する**。親テーブルを持つ通常の明細（親の Submit で保存）と違い、表示専用ホストには保存契機が無いので当然ではあるが、UI 上は「削除できたように見える」。

- **回避策（本アプリで確立）**: 「変更を保存」ボタンで **DB 側の行と画面の行を突き合わせ、画面から消えた行を明示的に `Delete()` する**（CashEntry.mod.cs の `SaveListEdits`）。
- **提案**: ①表示専用ホストの ListField では `CanDelete` を無効（またはデザイン時に警告）②あるいは行削除時に「保存するまで確定しない」ことが分かる表示（取り消し線・保留マーク）にする。
- 関連: FB-035（表示専用モジュールの既定挙動）。
- 出典: ADR-0055（入出金起票の下書きグリッド）。

### FB-041【中】日付列を `TEXT` で作ると日付が地域書式で書き込まれ、SQL の日付関数が黙って壊れる
- **事象**（2026-08-14 実測・SQLite）: 新テーブルの日付列を `entry_date TEXT NOT NULL` で作り DateField を割り当てたところ、CLB は **`"08/14/2026"`（US 書式）** で書き込んだ。同じアプリの既存テーブル（`DATE` 宣言）は `"2026-08-14 00:00:00"` で入るため、**同じ型のフィールドなのに列の宣言型で保存書式が変わる**。SQLite の `date()` はこの書式を解釈できず NULL を返すので、期間比較・ソートを含む集計 SQL が**エラーにならずに全滅**する。
- **困った点**: CLB 経由の読み書きは往復で一致するため画面上は正常に見え、SQL 側だけが静かに壊れる。発見は帳票の値がおかしいことからの逆算になる。
- **回避策**: 日付列は必ず `DATE`、日時列は `DATETIME` で宣言する（既存テーブルに合わせる）。
- **提案**: ①保存書式を列の宣言型に依存させず ISO 8601 に固定する ②または designcheck で「DateField が TEXT 列にマップされている」を警告する。
- 出典: ADR-0055（`ddl/530_cash_entry_drafts.sql` のコメントに実測を記録）。

### FB-043【中】範囲検索が NULL 行を必ず落とすため、「未設定＝継続中」を表す列で既定条件が作れない
- **事象**（2026-08-14 実測・ADR-0057）: 日付・数値の範囲検索は `>= SearchMin` / `<= SearchMax` を
  発行するため、その列が NULL の行は**必ず除外される**。業務では「終了月が未設定＝まだ続いている」
  「有効期限なし＝無期限」のように **NULL が「上限なし」を意味する**列が普通にあり、
  そういう列に対して「終了月が空欄 または 今月以降」＝**進行中のものだけ**という
  最も自然な既定フィルタが、検索フォームでは表現できない。
- **試したこと**: 共通プロパティ `AllowEmptySearch`（既定 `false`・カタログの説明は「空検索を許可」の
  一行のみ）が NULL 包含のフラグではないかと考え、終了月が 過去 / 未来 / NULL の 3 件で実測した。

  | 終了月 | From = 当月で検索 | 検索欄を空にして検索 |
  |---|---|---|
  | 過去 | 除外 | 表示 |
  | 未来 | 表示 | 表示 |
  | **NULL** | **除外** | 表示 |

  範囲条件自体は効いている（過去が落ちる）のに NULL は落ちる。空欄検索でも全件出るので
  「空欄のとき `IS NULL` を条件にする」でもない。**範囲検索フィールドに対しては観測可能な効果が無い。**
  検索レイアウトの `Operator: "Or"` も、OR で繋ぐ相手（IS NULL 条件）を作れないため解決にならない。
- **回避策**: 「終了しているか」を状態列として持たせ、`SearchValues` の既定値で除外した（ADR-0057）。
  `end_month` から導出できる事実を状態としても持つことになり、**情報が二重化する**。
  もう一つの回避策は一覧の Query モジュール化だが、一覧と詳細が分かれ新規作成導線の作り直しが要る。
- **提案**: ①範囲検索フィールドに「未設定も含める」オプション（`IncludeNullInRangeSearch` 等）を足す
  ②または検索 UI に「未設定を含む」チェックを出す。①だけでも「NULL＝上限なし」の業務列が救われる。
- **あわせて**: `AllowEmptySearch` は挙動が文書化されておらず（カタログは名称のみ）、
  範囲検索フィールドでの意味が不明のまま。→ DOC-017 参照。
- 出典: ADR-0057「実測: `AllowEmptySearch` は範囲検索の NULL 包含に使えない」。

### FB-044【高】フィールドの `OnValidateInput` が false を返すと、保存が「無言で」止まる
- **事象**（2026-08-16 実測・ADR-0059）: `PasswordFieldDesign` の `OnValidateInput` に
  「サーバへ問い合わせて条件を満たさなければ `SetError` して `false` を返す」ハンドラを付け、
  条件を満たさない値で `SubmitButton` を押したところ、**保存は止まったが画面には何も出なかった**。
  `.invalid-feedback` も描画されず、トーストも出ず、`fetch` も飛ばない（＝サーバへ行っていない）。
  利用者から見ると「登録ボタンを押しても何も起きない」。
- **困った点**: 止まっていること自体は正しいのに、**理由が一切表示されない**。
  ハンドラが呼ばれているのか、`SetError` が効いていないのか、そもそも登録されていないのかを
  切り分ける手段が画面上に無く、通信の有無を JS で覗いて初めて「クライアント側で止まっている」と分かった。
- **回避策**: `OnValidateInput` を使わず、`OnDataChanged`（フォーカスが外れたときに発火・挙動が安定）で
  ラベルに赤字を出し、**実際の関門はサーバ側**（`ModuleDataIO` の override）に置いた。
  サーバ側で `LowCodeException.Create(メッセージ)` を投げると、その文言が**そのままトーストに出る**
  （「更新に失敗しました」と 2 本並ぶ）ので、利用者には理由が伝わる。
- **提案**: ①`OnValidateInput` が `false` を返したとき、`SetError` の有無にかかわらず
  「入力エラーがあります」相当を必ず表示する（無言で止めない）
  ②`SetError` がどのフィールド型で描画されるのかを明記する（`PasswordField` は
  確認欄と共有の `.invalid-feedback` を持つため、スクリプトからの `SetError` との関係が不明）
  ③`OnValidateInput` の発火タイミング（入力中／フォーカスアウト／Submit 時）を仕様化する。
- 出典: ADR-0059（パスワードポリシーの適用先として最初に試した方式）。

### FB-046【中】CLB は SQLite の生成列（GENERATED ALWAYS AS）を認識しない
- **事象**（2026-08-16 実測・ADR-0061）: 一覧に「税込金額」を出すため
  `ALTER TABLE invoices ADD COLUMN gross_amount INTEGER GENERATED ALWAYS AS (...) VIRTUAL` を追加し、
  その列を `DbColumn` に指定したところ、**designcheck が
  「カラム 'gross_amount' が 'BusinessAppSQLite.invoices' に存在しません」**と報告した。
  `sql` CLI からは普通に SELECT でき、値も正しい。
- **原因の推定**: スキーマ取得が `PRAGMA table_info` を使っているため。
  SQLite は生成列を `table_info` に含めず、`PRAGMA table_xinfo` でしか返さない。
- **困った点**: 「同じ行の 2 列から導ける値」は生成列が最も安全（定義上ズレようがない）なのに使えず、

- **回避策**: 実列＋`AFTER INSERT` / `AFTER UPDATE OF` トリガー（`ddl/550`）。
- **提案**: スキーマ取得を `table_xinfo` に変え、生成列を「読み取り専用の列」として扱う
  （INSERT/UPDATE の列リストから自動的に除外する）。
- 出典: ADR-0061。

### FB-047【高】`ListField.AddRow()` がその場で `OnDataChanged` を発火させ、行に値を入れる前に集計が走る
- **事象**（2026-08-17 実測・ADR-0066）: ヘッダ＋明細の構成で、明細 `ListField` の
  `OnDataChanged` に「明細から合計を再計算してヘッダへ書き戻す」処理を置いていた。
  スクリプトから
  ```csharp
  var row = Lines.AddRow();      // ← ここで OnDataChanged が同期的に発火する
  row.Amount.Value = Amount.Value;   // ヘッダの受け皿から写す
  ```
  と書くと、`AddRow()` の時点で**まだ空の行**を含めて集計が走り、
  ヘッダの合計が 0 に書き戻される。その直後に読む `Amount.Value` は 0 なので、
  **写したはずの金額が消える**。
- **困った点**: エラーも警告も出ない。画面には行が 1 行増えているので「動いている」ように見え、
  金額だけが 0 になる。原因が「自分のハンドラが自分の入力を消していた」ことなので、
  ハンドラ・受け皿・AI 抽出のどこが悪いのかの切り分けに時間がかかった。
  今回は AI 抽出フィールド（`AITextAnalyzerField`）が書いたヘッダの値を明細行へ移す処理で踏んだ。
- **回避策**: `AddRow()` を呼ぶ**前に**必要な値をローカル変数へ退避してから行へ書く。
  ```csharp
  var stagedAmount = Amount.Value;   // 先に退避
  var row = Lines.AddRow();
  row.Amount.Value = stagedAmount;
  ```
- **提案**: ①`AddRow()` に「イベントを発火させない」オーバーロード
  （`AddRow(bool notify = true)`）を用意する、または
  ②`SuspendNotifyStateChanged()` と同様に**イベント抑止のスコープ**を用意する
  （`using var _ = Lines.SuspendEvents();`）。
  ③少なくとも「`AddRow()` は `OnDataChanged` を同期的に発火させる」ことをマニュアルに明記する。
- 関連: 同種の罠として既に ADR-0053（`OnDataChanged` はスクリプトからの生成にも発火する）がある。
  **発火すること自体は仕様として妥当**なので、抑止する手段が無いことが問題。
- 出典: ADR-0066「実装中に判明した設計上の追補」・`Modules/Expense/ExpenseRequest.mod.cs` の `AiImport_Completed`。

### FB-049【高】`ModuleField` が DB 列を一方的に上書きするため、スクリプトから「別のレコードを開く」ことができない
- **事象**（2026-08-17 実測・ADR-0066 の UI 作り直し）: `ModuleFieldDesign`（`DbColumn: editing_line_id`）で
  子レコードを 1 件埋め込む画面で、**同じ列を指す `NumberField` を並置して**
  スクリプトから別レコードの Id を入れ、`Submit()` した。

  EditingLineIdRaw.Value = 別の行の Id;   // 同じ editing_line_id 列
  this.Submit();                          // ← ModuleField が自分の子の Id で上書きする
  ```
  結果、DB に書かれるのは **`ModuleField` が抱えている子の Id**（未保存なら新規採番された Id）で、

- **困った点**: 「埋め込んだフォームに、一覧で選んだ既存レコードを載せ替える」という
  ごく普通の操作が、素直には実現できない。`ChildModule` は読み取り専用、

  var s = new ModuleSearcher<ExpenseRequest>();
  s.AddEquals(e => e.Id.Value, this.Id.Value);
  var other = (ExpenseRequest)s.ExecuteFirstOrDefault();
  other.EditingLineIdRaw.Value = 開きたい行の Id;
  other.Submit();        // 画面の ModuleField を経由しないので上書きされない
  this.Reload();         // 読み直すと ModuleField がその行を載せる
  ```
- **提案**: ①`ModuleField.Load(object id)`（DbColumn を張り替えて子を読み直す）を用意する、または
  ②`DbColumn` を持つ `ModuleField` でも「同じモジュール・同じレイアウトのまま Id だけ差し替える」
  `SetModule` の限定形を許す。③少なくとも「`ModuleField` は保存時に自分の子の Id を DbColumn へ書く」ことを
  マニュアルに明記する（同じ列を別フィールドから触れることは実際にできてしまうため）。
- **あわせて確認できたこと**: `DbColumn` を `null` にすると、次の保存で**新しい空の子が作られる**。
  「入力欄を空に戻す」用途にはこれが使える（意図した仕様かは不明だが実測では安定していた）。
- 出典: ADR-0066「UI の作り直し」の実測知見 1・2、`Modules/Expense/ExpenseRequest.mod.cs` の `PointEditingLineTo`。

### FB-052【中】`AITextAnalyzerField` の書き込み範囲を制限できない（`ListField` にも書く）

### FB-053【高】`AddRows()` の多重定義解決が外れて実行時に落ちる（原因特定済み・designcheck は緑）

- **症状**: `je.Lines.AddRows(lineCount)` が実行時に
  `[lineCount] je.Lines.AddRows(lineCount); Value cannot be null. (Parameter 'source')` で失敗する。
  この文言は LINQ の `Enumerable.Count(null)` が出すもの。**`designcheck` は緑のまま素通りし、
  画面でボタンを押して初めて落ちる。** 例外文言は生の C# のまま利用者に出る。
- **状態: 2026-08-18 に原因を特定した。** 別の機能（仕掛品の期末振替）で同じ例外が再現したので、
  同じ画面・同じ行で書き方だけを変えて 3 通り試した。

| # | 書き方 | 結果 |
|---|---|---|
| 1 | `AddRows(rows.Count * 2)` — `rows` は **`List<WipCandidate>`（モジュール型）** | **落ちる** |
| 2 | `var n = rows.Count * 2; AddRows(n);` | **落ちる** |
| 3 | `AddRows(dcList.Count)` — `dcList` は **`List<string>`** | 動く |

  **`AddRows` には `AddRows(int count)` と `AddRows(List<Module> src)` の 2 つの多重定義がある。**
  引数の静的な型が int に決まらないと**リストを受ける側に流れて null が渡る**——
  例外のパラメータ名が `'source'`（リスト引数の名前）なのはそのためだと考えられる。

  **`.Count` そのものは壊れていない。** モジュール型のリストでも比較や表示には普通に使える
  （このリポジトリの経費・承認まわりで実際に動いている）。壊れるのは **`AddRows` に渡したときだけ**。

  **2026-08-17 の見立て「引数は 1 文で確定させる」は外れ。** 変数に受けても落ちる（試行 2）し、
  逆に `List<string>` の `.Count` ならループで積み上げたものでも動く（試行 3）。

**外した診断（同じ道を辿らないための記録）**

| # | 診断 | 直し方 | 結果 |
|---|---|---|---|
| 1 | 数値リテラルとメンバアクセスを 1 つの式に混ぜると壊れる（`1 + catKeys.Count + taxLineCount`） | `.Count` を単独で受けてから足す | **同じ行で同じ例外** |
| 2 | `.Count` を受けた変数を `AddRows()` に渡すと壊れる | `var lineCount = 1;` から加算だけで組み立てる | **同じ行で同じ例外** |
| 3 | `for` ループ内で `lineCount` を再代入している点が違う（動く 6 箇所はいずれも 1 文で確定させている） | 未検証 | — |

**動いている形（このコードベースの実績。迷ったらこれを真似る）**

- `je.Lines.AddRows(2)` — リテラル
- `je.Lines.AddRows(dcList.Count)` — **その場で**メンバアクセスを渡す（4 箇所）
- `var lineCount = (tax > 0) ? 3 : 2;` → `AddRows(lineCount)` — **1 文で確定する三項演算子**（6 箇所）
- `var lineCount = 2; if (useDiff) { lineCount = (diffTax > 0) ? 4 : 3; }` — 分岐での再代入（`Receipt:467`）

**動かなかった形**

- 税区分ごとに行数が変わるため、`for` ループの中で `lineCount = lineCount + 1;` を繰り返す形
  （`Sales/Acceptance.mod.cs` の売上仕訳生成。**3 回試して 3 回とも失敗し、実装を撤回した**）

- **なぜ重いか**: 静的検査に一切出ない。**「designcheck が緑」は動作を何も保証しない。**
  しかも落ちるのは業務の根幹（この例では売上計上）で、利用者には意味不明な英語の例外が出るだけ。
- **提案**: ①**多重定義の解決を直す**か、`AddRows(int)` と `AddRows(List<Module>)` の名前を分ける
  （例: `AddEmptyRows(int)`）。同名のままだと、引数の型が曖昧なスクリプトで必ず踏む
  ②少なくとも「リスト側の多重定義に null が渡った」ときは、
  **どの多重定義に解決したかを含む業務文言**にする（今の例外は原因を何も語らない）
  ③可能なら designcheck か実行前検証で検出する
- **こちら側の対処**: `lint_design.py` に **CLB-039** を追加した。
  `AddRows(...)` の引数が `List<モジュール型>` の `.Count` 由来（1 段の変数経由も追う）なら error。
  わざと壊して発火することを確認済み
- **出典**: 2026-08-17 のバグ狩り。BUG-0127（検収仕訳の税区分）の修正で作り込み、
  実機検証 3 回で発覚・撤回。**この間ずっと「検収を確定（売上計上）」が全件失敗していた。**
  2026-08-18 に仕掛品の期末振替（BUG-0016）で再現し、真因を特定して両方とも解決した（ISSUE-0006 §6）。

### FB-059【高】整数どうしの割り算が小数になる（動的値を代入した変数の型が変わる）

- **症状**: スクリプトで

  ```csharp

  foreach (var e in entries) { minutes = minutes + e.Minutes.Value; }
  var hours = minutes / 60;   // C# なら整数除算のつもり
  ```

  と書くと、`hours` が **160.98333333333333333333333333** になる。

- **提案**: ①`var` に代入した変数の型がどう決まるかをリファレンスに明記する
  （とくに「動的値との演算で型が変わる」こと） ②できれば C# と同じ型規則にする
  ③せめて `int` に代入できない値を暗黙に丸めるときは警告を出す
- **回避策**: **切り捨てを期待する割り算は必ず `int` で受ける**。

- **出典**: 2026-08-19 のバグ狩り。体験シナリオ SES-02（精算幅の切り捨て境界）で発見（BUG-0410）。

### FB-060【高】`ModuleSearcher` の日付比較が「時刻付き文字列」で行われ、時刻なしの行が境界で落ちる

- **症状**: SQLite の `DATE` 列に対する `AddGreaterThanOrEqual(e => e.SomeDate.Value, d)` は、
  パラメータを **`'YYYY-MM-DD 00:00:00'`** として渡す。SQLite の日付比較は文字列比較なので、
  列に `'YYYY-MM-DD'`（時刻なし）で入っている行は
  `'2026-09-01' >= '2026-09-01 00:00:00'` が**偽**になり、**範囲の下端で黙って消える**。
  逆向き（`end_date >= 対象日`）でも、列が時刻なしだと**上端で期間解決が失敗する**。
- **なぜ困るか**: **同じ列に 2 つの書式が入りうる**のが問題の芯。
  CLB 経由の保存は時刻付き、`sql` CLI や seed の DDL からの投入は時刻なしになりやすく、
  **同じテーブルの中で「拾える行」と「拾えない行」が混ざる**。
  エラーも警告も出ないので、「期末日の伝票が集計から抜ける」「締めチェックが下書きを見落とす」
  という形でしか気づけない。実際このリポジトリでは
  **20 ファイル・約 35 箇所に「月初日で解決する」という対症療法**が積み上がっていた。
- **提案**: ①`DATE` 列の比較はパラメータ側も日付だけにする（あるいは列側を `date()` で正規化して比較する）
  ②少なくともリファレンスに「`DATE` 列の期待書式」を明記する
  ③デザイナの `designcheck` で「DATE 列に書式の混在がある」を検出できるとなお良い
- **回避策**: **DB 側の書式を CLB が書く形（`YYYY-MM-DD 00:00:00`）に揃える**。
  このリポジトリでは `Designer/ddl/811_normalize_date_columns.sql` で正規化し、
  不変条件 `F06_日付_DATE列の書式が揃っている` で再発を検出している（ADR-0074）。
  **時刻を落とす方向に揃えると逆に全部の下端比較が壊れる**ので注意。
- **出典**: 2026-08-19 のバグ狩り。`FiscalPeriod` の締め前チェックを計測器にして実測（BUG-0066）。

  利用者にも開発者にも原因が伝わらない（このリポジトリでは検収の新規作成で発現した）。
- **提案**: ①`DeleteAllRows()` が未保存行を削除キューに入れないようにする
  ②直せないならリファレンスに「未保存行を含む `ListField` では `DeleteAllRows()` を使わない」と明記する
- **回避策**: 行を控えてから `DeleteRow` で 1 行ずつ消す。
  ```csharp
  var rows = new List<object>();
  foreach (var row in Lines.Rows) { rows.Add(row); }
  foreach (var r in rows) { Lines.DeleteRow(r); }
  ```
- **出典**: 2026-08-19 のバグ狩り。検収の新規作成で受注を選び直すと保存できない件（BUG-0238）を実機で再現・修正。

### FB-062【中】`ModuleSearcher.Execute()` の戻り値を `List<object>` 引数で受けると、スクリプトが無言で死ぬ

- **症状**: 判定ヘルパを

  ```csharp
  bool RequiresDepartment(List<object> accounts, object accountId) { … }
  ...
  var accounts = new ModuleSearcher<Account>().Execute();
  if (RequiresDepartment(accounts, id)) { … }
  ```

  と書くと、**呼び出した時点でスクリプトが止まる**。例外メッセージもトーストもコンソール出力も出ず、
  そのメソッドが書き換えるはずだったラベルが**空のまま画面が描画される**。
  `List<string>` を渡す形に変えると通る。`List<自作モジュール型>` の引数は動く実績がある
  （`FiscalYear.PostOneWipJournal(… List<WipCandidate> rows …)`）ので、
  `Execute()` の戻り値の実体型と `List<object>` の食い違いが原因と思われる。
- **なぜ困るか**: **失敗が画面に出ない。** ラベルが空・集計が更新されない、という結果だけが残るので、
  「データが無いのかな」と誤解する。`designcheck` も緑のまま通る。
- **提案**: ①`Execute()` の戻り値型をリファレンスに明記する
  ②スクリプト実行時の例外を握り潰さず、少なくとも開発時はトーストかコンソールに出す
  （**これが一番効く**。この種の「無言の死」はこのリポジトリで何度も踏んでいる）
- **回避策**: `Execute()` の結果を引数で持ち回らない。必要なら `List<string>` などに詰め替えて渡す。
- **出典**: 2026-08-19 のバグ狩り。一括起票のサマリ判定を直す途中で踏んだ（BUG-0223）。

### FB-063【中】標準の「登録」ボタン（`SubmitButtonFieldDesign`）に `OnClick` が無く、検証を挟めない

- **症状**: CLB 標準の登録ボタンは `SubmitButtonFieldDesign` で、`OnClick` を持たない。
  押すと**スクリプトを一切通らずに保存される**。保存前に検証を挟みたい場合は、
  `ButtonFieldDesign` に置き換えて `OnClick` から自分で `this.Submit()` を呼ぶしかない。
- **なぜ困るか**: 検証ハンドラを書いても、**ボタンの型を変えないと一切呼ばれない**。
  実際このリポジトリでは、取引先口座の 5 項目整合検証（`Register_OnClick`）が実装済みなのに
  画面が標準ボタンのままで、**銀行コードだけ入れた部分入力の口座が保存できていた**（BUG-0045）。
  「書いたのに呼ばれない」ので `designcheck` も緑のまま通る。
- **提案**: ①`SubmitButtonFieldDesign` に保存前フック（`OnValidating` 等）を持たせる
  ②またはリファレンスに「標準ボタンはスクリプトを通らない」と明記する
- **回避策**: 検証が要る画面では `ButtonFieldDesign` ＋ `OnClick` ＋ `this.Submit()` にする。
  このリポジトリでは `lint_design.py` の **CLB-041**（`.mod.json` から参照されていないハンドラを検出）
  で機械検査している。
- **出典**: 2026-08-19 のバグ狩り。取引先口座の検証が効いていなかった件（BUG-0045）。
