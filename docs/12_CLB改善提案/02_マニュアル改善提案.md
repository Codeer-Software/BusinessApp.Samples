# CLB マニュアル改善提案（DOC-xxx）

> 対象: Web マニュアル（Codeer.LowCode.Blazor.Manual）および AI 向けリファレンス（ClaudeCodeForDesigner）。
> 基準: **「実測しないと分からなかったこと」＝ドキュメントに書いてあるべきだったこと**。FB-xxx（機能改善）と対になる項目は、機能側を直さない場合のドキュメント要求として読んでほしい。

### DOC-001【高】ExecuteSqlField: パラメータは「DB 列名」で解決されることを明記
- `JP/db/execute_sql_field.md` に「SQL の @プレースホルダはフィールド名でなく DbColumn 名で書く」を太字で。フィールド名＝列名の例だけ載っていると罠に気づけない（対: FB-001）。あわせて「スクリプトから実行不可（全メンバー ScriptHide）」と、擬似 Standalone 実行パターン（Timing:Update＋フラグ列＋NULL ガード）を実例付きで。

### DOC-002【高】CommonMistakes に「OrderBy/OrderByDescending のラムダにも .Value が必須」を追加
- AddEquals 系の Variable 規約は記載があるが、OrderBy は漏れている。「エラーにならずソートが無効になる」「Limit(1) 採番が重複する」という症状も添える（対: FB-002）。

### DOC-003【高】スクリプトの値取得の大原則「レイアウトに出ていないフィールドの .Value を信用しない」を Scripts ガイド冒頭へ
- DataOnlyFields・ChildModule の値は遅延ロードで null があり得ること、確実に要る値は ModuleSearcher で DB から取り直すこと。これは本プロジェクトで最も繰り返し踏んだ罠で、承認フロー・部門引継ぎ・通知など実害 4 件以上（対: FB-005）。

### DOC-004【高】DatabaseGuidelines に「FK 列に NOT NULL を付けない（ネスト生成は FK 後埋め）」を追加
- 親子孫の一括 Submit の内部動作（親→子の順で INSERT、FK は後埋め）を図解し、REFERENCES は可・NOT NULL は不可と明記（対: FB-015）。

### DOC-005【中】「表示専用モジュール（DataSourceName 空）の制約一覧」を独立ページに
- this.Submit() は無反応（行保存は row.Submit()）、CanCreate の意味、検索・一覧の挙動差。表示専用モジュールは操作画面（取込・一括実行系）の定石パターンなのに、制約がどこにもまとまっていない（対: FB-004）。

### DOC-006【中】Fields リファレンスの DateField に「スクリプト代入は DateOnly 必須」を明記
- DateTime を代入したときの症状（表示は正しいが保存されない）も書く（対: FB-003）。

### DOC-007【中】日付比較のベストプラクティス「期間・年度の解決は境界日を避けて月初日で行う」を追加
- CLB の日付書き込み書式（`YYYY-MM-DD HH:MM:SS`）と seed の素の DATE 文字列が混在すると、辞書順比較で境界日（月末＝end_date 同日）の `>=` が偽になり得る。QueryField・スクリプト双方の注意として。あわせて「自作 SQL の日付比較・GROUP BY は `date(列)` で正規化」も（対: FB-008）。

### DOC-008【中】ChildModuleField の実体化条件を明記
- 「子行が 0 件の親では子モジュールの UI・スクリプトが一切動かない」「未保存の子のフィールドを外部から参照するとエラー」「スクリプトで親に子を後付けする 3 点セット（単独 Submit→実列 FK リンク→初回状態値）」（対: FB-016）。

### DOC-009【中】認証まわりの内部動作を運用ガイドに
- ①認証のデータソースは `app.clprj` の CurrentUserModuleDesignName（=ユーザーモジュール）の DataSourceName から解決される ②ユーザーテーブルが空なら初回起動時に admin/admin を自動作成 ③antiforgery トークンはユーザー束縛で、`POST /api/account/logout` 後に login.html へ直行すると 400 になる（`/` を一度 GET すれば回復。通常フローは影響なし）。自動テスト・運用切替時に必要な知識。

### DOC-010【中】PDF 出力の環境要件（フォント）をセットアップガイドに
- `CustomFontResolver` が `FontFileDirectory` から `{フェイス名}.ttf` を読むこと、無いと Object reference エラーで**全 PDF 出力が失敗**すること、日本語には NotoSansJP.ttf 配置が必要なこと、PdfSharp 6.2.3 は TTC 不可・可変フォント TTF 可であること。新環境セットアップの必須手順なのにどこにも書かれていない。

### DOC-011【中】zip デプロイ（FileWatcher 取込）の仕様を明記
- エントリ名は `\` 区切り・ディレクトリエントリ無し・app.clprj はルート直下・designer.settings*.json は含めない、hot-reload の反映条件（スクリプト変更・スキーマ変更はサーバ再起動）。GUI「送信」を使わず CI/CLI からデプロイしたい開発者向け（対: FB-022）。

### DOC-012【低】ブラウザ自動テストの注意集（テスト容易性ガイド）
- ①検索フォームの SelectField は JS の value 設定＋change dispatch では Blazor に伝わらないことがある（実クリック＋キーボード操作が確実） ②Blazor ボタンは座標クリックが空振りすることがある（JS の btn.click() が確実） ③`<input type=date>` は JS で value 設定＋input/change dispatch ④トーストを判定材料にしない（DB・ログで判定）。CLB アプリの E2E 自動化をする全開発者が同じ穴を踏むはず。

### DOC-013【低】CanCreate とスクリプト生成の関係を明記
- 「スクリプトで new→Submit するモジュールは CanCreate:true 必須」「UI の新規作成だけ塞ぐには PageFrame Link の UseNavigateToCreate:false ＋ ListField の CanCreate:false」（対: FB-012）。

### DOC-015【中】SearchConditionGuidelines に「検索条件にはラベルを付ける」推奨パターンを追加
- 既定の検索フォームは無ラベルで、複数条件を並べると識別不能になる。正典 `AllFieldsSearch` の「LabelField 列＋検索フィールド列」パターンを、推奨レイアウトとしてガイドラインに明記してほしい（対: FB-011）。LayoutGuidelines の「入力欄ラベルは placeholder で代用して削る」原則との使い分け（詳細フォームは placeholder 可・検索行はラベル推奨、等）も整理されると迷わない。

### DOC-014【低】QueryField の SQL 制約に SQLite 固有の落とし穴を追記
- compound SELECT（UNION）+ ORDER BY に式を書くとエラーになるためサブクエリで包む、集約 SELECT の行ゲートは WHERE でなく HAVING（集約は WHERE 全滅でも 1 行返る）など、帳票 SQL で実際に踏んだもの。

### DOC-016【中】`_specs/PageFrame.md` の「サブフレーム」記述が実装と乖離（入れ子ではなくフレーム切替）
- PageFrame.md 末尾の「PageLink の `PageFrame` プロパティに別のフレーム名を指定することで、サブフレーム（ネストされたナビゲーション構造）を実現できる」という一文は誤解を招く。実体は**フレーム切替**であり、遷移後の URL 解決は遷移先フレームの登録（Links/TopPageModuleDesign/OtherPageModuleDesigns）で行われる（FB-023 の真っ白事故の遠因）。`PageFrameDesign` に子フレームを持つプロパティは存在せず、URL も `/{Frame}/{Module}` の 1 フレームセグメント固定。
- **提案**: 「サブフレーム」の語を「フレーム切替リンク」に改め、①アクティブなフレームは常に 1 枚 ②切替先に Module×セグメントの登録が必要 ③階層表現はメニューの `/` 区切りで行う、を明記する。
- 出典: 2026-08-02 部品アーキテクチャ再編（ADR-0040）の事前調査。

### DOC-017【中】`AllowEmptySearch` の挙動が説明されていない（名称だけで意味が読み取れない）
- 全フィールド共通プロパティ `AllowEmptySearch`（`_specs/_FieldCommon.md`・既定 `false`）の説明が
  カタログ・仕様書とも「**空検索を許可**」の一行だけで、何が起きるのかが分からない。
  「検索欄が空でも条件を発行する（＝空の値にマッチさせる）」とも
  「範囲条件に空欄の行も含める」とも読め、**フィールド型ごとの意味も書かれていない**。
- 範囲検索フィールド（Date/DateTime/Number/Time）で `true` にして実測したところ、
  観測可能な効果が無かった（FB-043 の実測表）。**実測しないと分からなかった＝ドキュメント提案**。
- **提案**: ①「どのフィールド型で」「検索欄が空のとき／値があるとき」に何が起きるかを型別に書く
  ②範囲検索フィールドでは効かない（または効く）ことを明記する
  ③使いどころの例を 1 つ載せる。効果が無い型では designcheck で警告してもよい。
- 出典: ADR-0057（2026-08-14 実測）。
