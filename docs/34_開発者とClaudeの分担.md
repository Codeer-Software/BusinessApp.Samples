# 開発者と Claude の分担

> **何を開発者が担い、それ以外を Claude が確認なしに行うか**の境界を持つ文書。
>
> **本書は、開発者が書いて全体を承認した**（2026-09-19 に開発者が書き直し、2026-09-20 に
> 「**この文書の内容は全て、開発者承認済みです**」と述べた）。**だから行ごとに「誰が言ったか」と日付を書かない**
> ——**全文が開発者の指示である [CLAUDE.md](../CLAUDE.md) と同じ形**である。
> **後から Claude が足した行には「Claude の敷衍」**——開発者の承認を得ていない、Claude が足した補足のこと——
> **と印を付ける。本書では、承認されたらその印を消す**（本書には日付と帰属が無いので、
> [00 §4-11](00_ドキュメント規約/本文.md) の「日付と理由に替える」は当たらない）。
>
> 迷ったときの決め方は [30 §1](30_作業のルール.md)、消す・戻す・上書きの判断は [33](33_失わないためのルール.md)、
> 開発者に決めてもらうことの書き方は [30 §11](30_作業のルール.md)。**ここは境界だけ。**

## 0. なぜ境界を書くか

**境界が書かれていないと、Claude は「不可逆に見える操作」の手前で止まる**——
**止まるたびに自走が切れる。** だから境界を 1 か所に書き、**それ以外は行う**。

## 1. 開発者が担うこと

開発者が担当することは次のとおり。
ただし、開発者が承認した上で実作業のみ Claude に任せることはある
（**実例**: `deny` の控えを広げた回——「今回は Claude が行ってください」。**一回限りの委任であって、担当が移ったわけではない**。[33 §1](33_失わないためのルール.md)）。

| # | 開発者が担うこと | 補足・いまのプロジェクトでの具体例 |
|---|---|---|
| 1 | **機密情報の管理と利用**（`Designer/LocalEnvironment.md` に定めた開発用アカウントの ID・パスワードは機密情報に含まれない。） | .NET User Secrets・接続文字列・API キー・本物の資格情報（[CLAUDE.md §5](../CLAUDE.md)）。**開発用アカウントは含まれない**——同ファイルに開発者が書いたアカウントについて、**アカウントの登録・ログイン・ログアウトを Claude が行ってよい**（規則と理由は [31 §3](31_検証のルール.md)） |
| 2 | **ローカル環境やプロジェクトリポジトリ外に関する整備** | デザイナ exe・`.claude/settings.local.json`・`Designer/LocalEnvironment.md`・新環境のセットアップ（[README](../README.md)）・依存の導入（Playwright 等——`Designer/CLAUDE.md`）。**開発者が決めるのは、これらのファイルに何を書くかである**——どのアカウントを使うか、パスワードは何か、デザイナ exe がどこにあるか、といった**環境ごとに違う値**。**Claude がこれらのファイルを新しく作れないのは別の話**で（関門が塞いでいる）、§2-2 が持つ |
| 3 | **プロジェクトのゴールやスコープ、要件、仕様等に関する最終判断** | [01](01_企画概要.md)・[02](02_ペルソナ.md)・[03](03_機能スコープ.md) と、ADR の「開発者の決定」。**最終判断に至るまでの調査・素案作成・提案等は Claude が積極的に行うこと。** 実装との線は **§1-1** |
| 4 | **法令及び税制に関する最終判断** | 条文の当てはめ・制度の解釈（[CLAUDE.md §2](../CLAUDE.md)・[32](32_調査のルール.md)）。**最終判断に至るまでの調査・素案作成・提案等は Claude が積極的に行う**。Claude は `docs/research/` に一次情報を集め、読みを「Claude の読み」と印して諮る |
| 5 | **リモートリポジトリへのプッシュその他のプロジェクトの外部公開に関する作業** | `git push`（[30 §7](30_作業のルール.md)。**`.claude/settings.json` の `deny` が機械でも禁じている**）・公開設定・外部サービスへの送信 |
| 6 | **影響重大 and (不可逆的 or 高リスク) な作業** | **控えを取っても戻せないものを消す・控えを取らずに上書きする**こと（例: `.git/`・追跡外の環境設定・`LocalData/storages`。**関門が守っているファイルの一覧は [`protected_paths.json`](../tools/claude/protected_paths.json) だが、6 に当たるのはそのうちの一部である**）、**コミットしていない作業を捨てる git**、**reflog そのものを消す git**（`reflog expire`／`delete`／`drop`・`gc --prune`。**戻す手段のほうが消えるので不可逆である**）。**git の禁止の一覧と理由は [33 §1](33_失わないためのルール.md)。** **開発用 DB**——いまサーバが使っている DB（`LocalData/db`）と、その控え（`LocalData/backup`）——**は当たらない**（§1-2。運用は [33 §2](33_失わないためのルール.md)）。**判定は §1-2** |
| 7 | **Claude in Chrome では再現しないブラウザ上の細かな挙動の確認など、Claude が実施できない作業** | [30 §3](30_作業のルール.md) の「3 回で中断する」で残したもの・[qa/01 の G 節](qa/01_CLB静かな失敗.md) の型。**Claude が「できない」と決めつけない**——試して残った分だけを頼む |
| 8 | **機械的関門を緩める決定** | 本プロジェクトで要となる品質と開発上の安全を機械的関門が保護している。その基準を下げる決断は開発者のみが行うとする。 **何が「緩める」に当たるかは §1-3**。**締める向きは Claude が行う**（§2-1）。 |

### 1-1. 仕様の最終判断と、実装との線（表の 3 の解説）

**最終判断に至るまでの調査・素案作成・提案等は Claude が積極的に行う。**
これは「仕様については全て開発者に諮り、開発者が了承するまで実装しない」ことを**意味しない**。
**実装は最終判断ではない。**

| どういう仕様か | Claude はどうするか |
|---|---|
| **ゴール・スコープ・要件を変更しうる検討事項** | ADR・[05](05_開発者への問い.md) に案を作り、**判断を仰いでから**進む |
| **実装前に確認すべき仕様**（下） | 同じく、**実装前に**判断を仰ぐ |
| **それ以外の、自律作業中に起こった仕様の疑問** | 検討事項と判断の理由を適切に文書へ残したうえで、**Claude 自身が最適と考える案で実装する。そのうえで [05](05_開発者への問い.md) に書いて後から諮る**（[30 §11](30_作業のルール.md)） |

**「実装前に確認すべき仕様」とは。**

- 法令解釈を要する仕様。
- 複数の選択肢があり、ベストプラクティスを容易に決めきれない、あるいはどれも選ぶ妥当な理由があり開発者が決断するよりない仕様。
- 実装後に仕様を変更するとコストが大きい仕様。
- 等。

**聞くと決めたあとの「いつ聞くか」は [30 §1](30_作業のルール.md) の表が持つ**（手を止めてすぐ聞くか、[05](05_開発者への問い.md) に書いて作業の区切りで聞くか）。

### 1-2. 「影響重大 and (不可逆的 or 高リスク)」の見方（表の 6 の解説）

**まず影響重大かを見る。影響重大でなければ、不可逆でも高リスクでも Claude が行う。**
影響重大であって、なおかつ不可逆か高リスクのどちらかに当たるときだけ、開発者の担当になる。

#### 影響重大

- 重要な情報が含まれるなど。
- 開発用 DB は重要な情報ではない。それは開発用に過ぎない。
    - もし、「今の DB には検証で活用できる多数のレコードを登録しており、消えると手戻りが大きい」などの理由があるなら、当該 DB のスナップショットを取るなどすべきである。
    - **開発用 DB を「重要な情報が含まれ、消えると被害が大きい」状態にしてはならない。**

#### 不可逆

- 一度実施するとその作業前の状態に戻ることができないこと。
- ほかの場所への退避、ごみ箱への移動、git で戻せる操作は不可逆には当たらない。

#### 高リスク

- 失敗の可能性と失敗したときの被害の大きさで判定する。
    - 失敗する可能性が高いなら高リスク。
    - 失敗する可能性は低いが万が一失敗したときの被害が甚大であるなら高リスク。

### 1-3. 機械的関門を「緩める」とは（表の 8 の解説）

**機械的関門とは、危ない操作を機械が自動で拒む仕組みのこと**である——
`tools/claude/` のフックと、`.claude/settings.json` の許可・禁止の設定と、コミット前フックの検査。
**以下、本書ではこれを「関門」と呼ぶ。**

> **（2026-09-21 追記。Claude）他の文書では、本書の「機械的関門」「関門」を「操作制限」と書く**——
> 「関門」が保存の直前の検査（`*SubmitGate`）を指す語と同じ字だったためである（[81 §1](81_略語と記号.md)）。
> **語の選択は開発者の確認待ちで、本書の本文の字は変えていない。**

**緩めるとは、関門を弱めること・許可を広げることをいう。**

| 緩める操作 | 何が起きるか |
|---|---|
| **`.claude/settings.json` の `allow` に道具を足す** | **その道具を使うときの確認が出なくなる。** フックは `allow` と関わりなく毎回走るが、**その道具の消し方・上書きの仕方が `guard_delete.py` の語彙**（拒む語の一覧）**に無ければ、確認もなく通る**。**2026-09-16 に `iconv` と uv を足したときがその実例で、どちらも当時は語彙の外だった**（**同じ回に語彙へ入れて塞いだ**ので、いまは穴ではない。[33 §1](33_失わないためのルール.md)） |
| **`deny` から行を外す** | **削除の語と git の形については、フックが落ちたときの控えが無くなる。** ただし**`git push` と秘密ファイルの `Read`（`secrets.json`・`.pfx`・`.snk`）については、`deny` が唯一の関門**である——**フックは `Write` と `Bash`／`PowerShell` しか見ない**ので、外すと関門そのものが消える |
| **[`protected_paths.json`](../tools/claude/protected_paths.json) から行を外す** | そのファイルが消せる・上書きできるようになる（一覧と、載せる／載せない基準もこのファイルが持つ） |
| **コミット前フックの検査を 1 つ外す** | その検査が毎回の関門から落ちる（検査の一覧は [tools/README](../tools/README.md)） |
| **カバレッジの下限を下げる** | [ADR-0012](decisions/0012-テスト方針とカバレッジのゲート.md) の行・分岐 100%。**数値の実体は各テストの `.csproj` の `<Threshold>`** である |

**ミューテーションテストの下限**（数値の実体は `tools/git-hooks/pre-commit`）**だけは別で、Claude が動かす**。
[ADR-0012 §8](decisions/0012-テスト方針とカバレッジのゲート.md) が、割れたら **(a) テストを足して戻す**のが先で、
戻せないときに **(b) 生き残りを読んで、許容と判断した理由とともに下限を動かす**——という手続きを、
**Claude の作法として**定めているからである（生き残りの一覧を残すことまで決めている）。

**締める向き**——穴を塞ぐ・拒む語を足す・`--selftest` の試験例を足す——**は Claude が行う**（表の 8・§2-1）。

**ただし、この向きを機械が完全に支えるわけではない**（Claude が `guard_delete.py` を読んで書いた。
**実際に語を消して `--selftest` を走らせてはいない**）。
**多くの語は `deny` の控えや `ALLOWED_TOOLS` の覚え書きと双方向に結ばれているので、語を消すと `--selftest` が赤くなる。**
**どこからも名指しされていない語**（`Set-Content`・`Rename-Item` など）**だけは、試験例ごと消せば緑のまま通る。**

## 2. それ以外は、Claude が確認なしに行う

**§1 に当たらないあらゆることは、Claude が自律的に・開発者の確認なしに行う**。

### 2-1. 開発者が個別に許した作業の例

- **ごみ箱送りと、いまサーバが使っている DB の退避と復元**（[33 §1](33_失わないためのルール.md)）。
  **ただしごみ箱の中身を消すのは開発者である**（同。**関門は拒んでいないので §2-2 ではない**）
- **開発用アカウントの登録・ログイン・ログアウト**（[31 §3](31_検証のルール.md)）
- **デプロイ・サーバ再起動・ブラウザ操作**（[31 §2](31_検証のルール.md)・`Designer/CLAUDE.md`）
- **関門（`tools/claude/`・`.claude/settings.json`）を直すこと・締めること**
  （[33 §1](33_失わないためのルール.md)。直したら `guard_delete.py --selftest` を通す。**緩めるのは §1 の 8**）
- **`main` へのマージ**（[30 §7](30_作業のルール.md)。6 条件がそろっていれば）

**新しく書くのは境界だけである。** 許されることを一つひとつ数え上げない。書くのは次の 3 つだけ——
①**§1 に当たるもの** ②**当たるかどうかの判断が分かれるもの** ③**当たらないと分かった操作の作法**
（「どう行うか」。[33 §2](33_失わないためのルール.md) がその形）。
**個別の規則にまだ「開発者に確認する」と書いてあって §1 に当たらないものを見つけたら、その規則を直す**
（[30 §9](30_作業のルール.md) の「効く場所に置く」）。

### 2-2. §1 に当たらないが、いま関門が塞いでいるので開発者に頼むもの

**ここにあるのは開発者の担当ではない。** 開発者の字を借りれば、
**「リスクがなく開発者としては許容する対象だが、機械が経路を塞いでいる」**ものである
（開発者が 2026-09-19 に §1 の 2 へ自分で書いた句。**関門を直せばここから消え、§2-1 の側へ移る**）。

| 塞がっていること | 何が塞いでいるか |
|---|---|
| **関門が守っているファイルを新しく作ること**（`Designer/LocalEnvironment.md`・`.claude/settings.local.json` など） | `Write` をフックが拒み、`Edit` は既にあるファイルにしか使えない。`.sample` からの複製も行き先の名前で拒まれる（実測と綴りは [33 §1](33_失わないためのルール.md)） |
| **いまサーバが使っている DB（`LocalData/db`）・その控え（`LocalData/backup`）・デプロイの成果物（`LocalData/designs`）を消すこと** | **フックと `trash` の両方**が拒む（[33 §1](33_失わないためのルール.md)）。**§1-2 では Claude の担当**（作り直せる・控えから戻せる）なのに塞がっている |
| **同じものの名前を変えること** | **フックの上書きの語彙**（`mv`・`Rename-Item` など）**が、保護対象の名前と一緒に出ると拒む**（[33 §1](33_失わないためのルール.md)。**`trash` は改名に関与しない**） |

**守っているファイルの一覧と、載せる／載せない基準は
[`tools/claude/protected_paths.json`](../tools/claude/protected_paths.json)** が持つ。
**この表は、実際に塞がれて手が止まったものを書き足していく。**

**開発者が意図して拒むと決めた git は、ここには入らない**——
`branch -D`・`update-ref`・`reflog expire` など（逐語と理由は [33 §1](33_失わないためのルール.md)）。
**要るときは開発者に声をかける**（同）。

**「できない」と決めつけない**——関門が見ている語は網羅ではないので、**試して塞がれた分だけを頼む。**

## 3. 開発者が Claude に期待すること

1. **会計・簿記・経理に係る実務に関する豊富な知識と、それに基づく設計等の判断。**
2. **ソフトウェア開発に係る無数の知見と、それに基づく設計・実装・検証等の遂行能力及びそれらのプロセスの改善策。**
3. **Claude（あるいは AI 一般）に係る知識と、それに基づく最適なルール・ドキュメント等の整備。**
4. **法令に関する論理的検討**（法令解釈の最終確認先及び最終判断者は開発者だが、Claude も豊富かつ高度な法解釈能力・論理的思考力を有しており、自ら検討できる。**ただし、記憶には頼らず最新の根拠を調査すること。**）**。**
5. **インターネットを用いた広範な調査力。**
6. **高速に・24 時間働き続けることのできるそのスピードと作業量。**
7. **以上に掲げた知識及びそれら以外のあらゆる知識に基づく開発者への積極的な提案。**

### 3-1. Claude がこれをどう受けるか

- **1・2 は「判断してよい」の裏づけである**——[30 §1](30_作業のルール.md) の「ベストプラクティスが 1 つに定まるなら聞かない」は、
  この期待に立っている。**ただし §1 の 3・4（最終判断）は開発者のもの**で、Claude は案と根拠を作る
- **3 は、規則を Claude が書き起こして諮ってよいということである**——
  起こした規則には「Claude の敷衍」と印し、**開発者が承認したら、その文書の作法に従って印を落とす**
  （日付と理由を残す文書ではそちらへ替える。[00 §4-11](00_ドキュメント規約/本文.md)）
- **4・5 は「自分で調べて検討せよ」であって、「記憶で決めてよい」ではない**——
  4 の但し書きのとおり、制度・法令は `docs/research/` を先に読み、無ければ調べて記録してから実装する
  （[CLAUDE.md §2](../CLAUDE.md)・[32](32_調査のルール.md)）。**それでも迷ったら §1 の 4 で開発者に聞く**
- **7 は、気づいたら言う**——問いは [05](05_開発者への問い.md)、判断の経緯は ADR、作業の改善は [30 §9](30_作業のルール.md)。
  **「聞かれていないから言わない」を採らない**
