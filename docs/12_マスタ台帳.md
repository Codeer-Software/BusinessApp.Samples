# マスタ台帳 — 何を・誰が・どう持つか

> **各マスタの仕様の現在形は、この表が正典である。** なぜそうなのかは各セルが指す ADR が持つ。
> かつては三層分類（①制度ルール／②会計設定／③会計マスタ）で括っていたが、
> **層に押し込むのをやめ、マスタごとに各軸の仕様を並べる形にした**
> （[ADR-0029 §6](decisions/0029-所有は相手抜きで存在するかで導き粒度は決断で決める.md)。
> 経緯は当時の ADR-0006 → ADR-0019。どちらも `superseded`）。

## 1. 軸の読み方

| 軸 | 意味 | 決めているもの |
|---|---|---|
| **所有** | どの部品のものか。「会計をやめても存在するか」で導く | [ADR-0029 §2](decisions/0029-所有は相手抜きで存在するかで導き粒度は決断で決める.md) |
| **誰が編集するか** | 役割の名前で書く（旗の実装は別問題） | 軸の形は [ADR-0034](decisions/0034-役割は部品ごとの直交な軸で持ち軸の中は階段にする.md)。個別の割り当ての経緯は ADR-0026 の理由節 |
| **更新のきっかけ** | 何が起きたら変わるか（頻度は見込み。決定ではない） | — |
| **過去の仕訳を守る仕組み** | マスタを変えても計上済みが動かない理由 | 制度値の版固定は [20 §2](20_実装の原則.md)、写しの焼き込みは [ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md) |
| **初期データ** | 出荷時に何が入っているか | [seed/README](../Designer/seed/README.md) |

**削除はどのマスタもさせない。無効化する。** `is_active` は「**入力時の候補に出すか**」の意味であり、
過去データの表示・検索を妨げない。フラグの名前もその意味に合わせる
（経緯は当時の ADR-0006 → ADR-0019。論理削除列の不在は `SchemaShapeTests` が機械で守る）。
例外は**インボイス登録**（終わりの日付で残す。[14](14_適格請求書発行事業者の登録.md)）と
**制度ルール**（無効化ではなく版の交代）。

**オフにされる科目の下に残る補助科目は、勘定科目の保存の側で数える。**

関門が確かめると、名前も「有効」も直せなくなるからである。見つける SELECT は [qa/04](qa/04_実機操作テスト.md) の MST-42 の行。
**DB のトリガは無い**（関門だけが守る。[ddl/README](../Designer/ddl/README.md) の二重防御の表。置くかは下の保留リスト）。

**取引先を要する科目は 2026-09-08 に入った**（計上の関門 ＋ DDL のトリガ。マイグレーション 0020〜0022。
**現在形は [15 §1-2](15_記帳の枠組み.md) が持つ**）。

### 2-1. コードの書式

**コードを持つのは 6 つの表である**——`fiscal_years` / `tax_categories` / `accounts` /
`sub_accounts` / `departments` / `partners`。**6 つとも同じ規則に従う**
（理由と経緯は [ADR-0047](decisions/0047-マスタのコードは空白を落とす以外書き換えず字種で断る.md)）。

| | 規則 |
|---|---|
| 字種 | **半角英数字・ハイフン（`-`）・アンダーバー（`_`）だけ。** 全角・空白・他の記号・かな漢字は断る |
| 記号の位置 | **先頭と末尾に置けない。記号を連続させられない** |
| 長さ | **1〜20 文字** |
| 前後の空白 | **黙って落とす**（Unicode の空白すべて）。落として空になったら「必須」で断る |
| 大小 | **保存は入力のまま。同一性の判定だけ大小を無視する**——`A100` があれば `a100` は登録できない |

**断りは、関門も DDL のトリガも、条件ごとに 1 つずつ言う。** 順は **空 → 字種 → 先頭 → 末尾 → 連続 → 長さ** で、
最初に当たった 1 つだけを言う（関門については開発者の指示。2026-09-08。逐語「即エラー。次へ進まない」。
**トリガへ同じ順を当てるのは Claude の敷衍**。2026-09-10。マイグレーション 0029・0031）。欄の呼び名は画面のラベル
（「科目コード」「年度コード」など。[21 §2-6](21_画面の原則.md)）。
**調だけは違う**——関門は利用者向けの「です・ます」、**DDL の `RAISE` は「だ・である」**（他の表のトリガと同じ。
届くのは取込・`sql` CLI・SQL の直打ちで流す人だけで、アプリの画面には関門の文言が先に出る。**Claude の判断。2026-09-10**）。

**書き換えるのは前後の空白だけである。** 全角英数を半角へ寄せることも、英字を大文字へ寄せることもしない
（[21 §0](21_画面の原則.md) の境目——**利用者が入れたつもりのものを変えない**）。
**記号を落として突き合わせもしない**（`10-01` と `1001` は別のコード）。

**守りは 2 段である**（[ADR-0038 §4](decisions/0038-使用中のマスタは意味を変えられない.md) と同じ形）——
**利用者の言葉で断る保存の関門が本体**、**DDL のトリガが最後の守り**（届く相手は上の段落）
（`CHECK` ではない。既存の表に後から足せないため。[ADR-0047](decisions/0047-マスタのコードは空白を落とす以外書き換えず字種で断る.md) の追記）。
**大小を無視した重複は `UNIQUE ... COLLATE NOCASE` の索引**が止める。
**3 か所に同じ事実が要る**（C# の関門・DDL のトリガ・CLB のプレースホルダ）ので、**機械で突き合わせる**——
**長さは 3 者一致**（`FieldLengthConsistencyTests`。プレースホルダは上限の数が含まれることを見る）、**字種と形は関門とトリガの 2 者一致**
（`MasterCodeGuardTests` が符号位置を総当たりする）。**字種と形はプレースホルダを突き合わせていない**（[20 §4](20_実装の原則.md)）。

**使用中のコードは変えられない。** 上の表の 4 マスタに加え、**取引先も同じ扱いである**
（[ADR-0047](decisions/0047-マスタのコードは空白を落とす以外書き換えず字種で断る.md) の決定 9）。

### 2-2. 文字の欄の上限

**マスタと取引先の文字の欄には、上限を置く**（2026-09-13 の決着。**問い（旧 Q-20）は [05](05_開発者への問い.md) から消した**）。
**伝票の摘要と明細の内容は [10 §4-2-1](10_会計ドメイン設計.md) が持つ**（どちらも 200 文字。マスタではないので、§3 の線に従って本書には載せない。**守り方と数え方はここと同じ**で、2026-09-14 に一緒に入った）。

| 欄 | 上限 | 決めた理由 |
|---|---|---|
| **勘定科目・補助科目・部門・税区分・会計年度の名前** | **30 文字** | **Claude の判断**（開発者が「それ以外はあなたの案でかまいません」と委ねた。2026-09-13）。**問いに置いていた案は 60 文字だったが、リサーチを受けて 30 に改めた**——市販は 20〜40 が中心で、freee と MF が 30。**摘要と同じ桁で設計している社は 1 社も無い**（[リサーチ §2](research/2026-09-13_市販会計ソフト比較_文字の欄の上限.md)） |
| **取引先の名前** | **100 文字** | 同上。**案は 60 文字だったが 100 に改めた**——クラウド系は 255〜300、オンプレ系は 32〜60 と割れており、**法人の正式名称が入る余地**を採りつつ一覧が崩れない側に寄せた |
| **勘定科目・補助科目のカナ** | **60 文字** | **開発者の決定。2026-09-16**。**読みは表記より長い**——「株式会社」4 字の読みは「カブシキガイシャ」8 字なので、**名前を上限いっぱいまで書いた科目が、その読みを入れられない**形にしないために名前の 2 倍を採る。**市販ソフトのカナの上限は調べていない**（旧 Q-26 に明記して諮った） |
| **取引先のカナ** | **200 文字** | 同上（名前 100 の 2 倍）。**2026-09-16 までは名前と同じ 100 だった** |
| **自社情報の会社名** | **100 文字** | 同上（問いの添え書きは「取引先と揃える」）。**「自社も取引の相手方になりうる」は Claude の言い換え**（2026-09-16） |
| **自社情報のカナ** | **200 文字** | 同上（取引先のカナと揃える） |
| **自社情報の代表者名** | **30 文字** | 同上（問いには値だけ）。**「人名 1 つ分」は Claude の言い換え**（2026-09-16）。マスタの名前と同じ数だが、動く理由が違う |
| **自社情報の住所** | **200 文字** | 同上（問いの添え書きは「取引先の所在地と揃える」）。**同じ数でも定数は別にしてある**——動く理由が違う（相手方の住所と自社の住所）ので、片方だけ動かす決定が来た日に分割から始めずに済む（**Claude の判断。2026-09-16**） |
| **自社情報の電話番号** | **20 文字** | 同上。**書式は置かない**——内線・国番号・区切り記号の形が割れる |
| **取引先の所在地** | **200 文字** | **案のまま。** **1 列で持つ**と決めてある（[13 §1-2](13_取引先設計.md)）ので、市区町村・番地と建物名を 2 欄に分ける社（freee は各 255）より 1 欄あたりを長く採る |

**会計年度を含めたのは開発者の決定である**（2026-09-20。旧 Q-11。もとは Claude の判断。2026-09-14）。
**旧 Q-20 の問いは「マスタの名前（勘定科目・補助科目・部門・税区分・取引先・会計年度）」と書いていた**が、
決着を写したこの表は 4 つしか挙げていなかった。**答えの逐語は追跡外の答えファイルにあり、いま残っていない**ので
どちらとも決められず、**含める側に倒した**——他の 4 マスタと同じ数で、外す理由が見当たらないからである。
作成の画面はまだ無い（§1 の表。フェーズ 4）が、**守りを先に置く**（コードの関門と同じ）。
**欄は `Name` ではなく `Label` である。**

**郵便番号だけは、長さではなく書式の規則を置く**（**開発者の決定。2026-09-16**）——
日本の郵便番号は 7 桁で、区切りを入れて **`123-4567` の 8 文字ちょうど**にしかならないので、
「N 文字以内」という形の規則が当たらない。**規則の正典はここ（§2-2）で、その写しが `PostalCode`（C#）と `012_text_length.sql` の `GLOB` である。**
**写し同士の一致は `FieldLengthConsistencyTests` が見る**——法人番号より強く、**プレースホルダの字そのものと `ShouldTrimAfterEdit` まで**突き合わせる
（**数そのものがこの文書と合っているかは機械が見ていない**——定数を変えて 3 者を緑にしたまま、この表だけを嘘にできる）。
**空白を落とす以外は書き換えない**（**Claude の判断。2026-09-16**。[ADR-0047](decisions/0047-マスタのコードは空白を落とす以外書き換えず字種で断る.md) の線）
——「1234567」に「-」を足して直すことはしない。

**上限で入力を止めない**（[21 §1](21_画面の原則.md)）。**プレースホルダで見せ、関門が「いま何文字あるか」まで言って断る。**
守りは §2-1 と同じ 2 段（関門が本体・DDL が最後の守り）で、**3 者一致を `FieldLengthConsistencyTests` が見る**
（**上の表の欄 × 3 者を毎回突き合わせる**。**数は書かない**——足すたびに腐る。DDL は `Designer/ddl/012_text_length.sql`、C# の定数は `MasterTextLength`）。
**上限は「その欄を触った保存」でだけ効く**——DDL の更新トリガは `BEFORE UPDATE OF <列>` なので、
**上限を決める前から入っていた長い行も、その欄に触らない限り直せる**。

**前後の空白は落として保存する**（[21 §0](21_画面の原則.md)「利用者の意図でない混入の除去は黙って直してよい」）。
**画面（`ShouldTrimAfterEdit`）と関門の両方で落とし、関門は落とした姿を差分に書き戻す**——
比べるときだけ落とすと、**関門が数えた長さと DDL が数える長さが食い違う**（[qa/03 の L-14](qa/03_テストで漏らした実例.md)）。

**数えられない値は、長さより先に断る。** SQLite の `LENGTH()` は
**BLOB ではバイト数を返し、TEXT では途中の U+0000 で止まる**ので、
**どちらもすり抜けの経路になる**（[qa/03 の L-48](qa/03_テストで漏らした実例.md)）。
関門も DDL も、**U+0000 を含む値を「使えない字」として断る**。

**「文字」は Unicode の符号点で数える**（**Claude の判断。2026-09-13**）——**全角と半角を区別しない**。
市販でも freee・MF・弥生 Next が「全角・半角を問わず」で、半角換算の桁数を使うのはデスクトップ製品だけである。
**バイト数で数えない**——利用者には何文字入るのかが分からなくなる。

**その代わり、見た目 1 字でも 2 と数える字が残る**——結合文字（か＋濁点）・異体字セレクタ（葛＋VS17）・
国旗の絵文字は、**見た目は 1 字でも符号点は 2 つ**である。**書記素で数える手立てが SQLite に無い**ので、
**2 つの守りが同じ数を返すこと**を優先した。

### 2-2-1. 長さの上限を置かない文字の欄

**次の欄には「N 文字以内」の規則を置かない。** 理由は 3 通りある——
**①置かないと決めた**（公表名）・**②長さではなく書式の規則で守る**（郵便番号・法人番号）。
**どれも数え落としではない**（`FieldLengthConsistencyTests` の除外の表が理由つきで持ち、
**デザインを総当たりして漏れを赤くする**）。**未決のものは、いまこの表に 1 つも無い。**

| 欄 | なぜ置いていないか |
|---|---|
| インボイス登録の**公表名** | **公表システムの写し**で、長さは相手が決める（[14](14_適格請求書発行事業者の登録.md)。**開発者の決定。2026-09-16**——「置かない」と決めた） |
| **自社情報の郵便番号** | 長さではなく**書式**の規則である（上の §2-2）。**法人番号と同じく、桁ちょうどの欄は「N 文字以内」の表に載せない** |
| **法人番号**（取引先・自社情報） | 13 桁ちょうど。別の規則で、上の §2-2 の下で突き合わせている |
