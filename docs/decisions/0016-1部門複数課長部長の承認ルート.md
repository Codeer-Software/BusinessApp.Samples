# 0016: 1部門に複数の課長・部長を許す承認ルート（department_managers 方式・OR 承認）

- 状態: 採用 / 日付: 2026-07-08 / 契機: ユーザー正式要望「実務では1部門複数課長は避けられない。部長も複数化する（通常運用で1人にすればよいだけ）」
- 先行: ADR-0015（バックログ・設計スケッチ）を本 ADR で実装に昇格。ADR-0007（動的解決）・ADR-0010（自己承認禁止）を一般化して継承。

## 決定

### 1. 役職の持ち方: `department_managers` 中間テーブルへ完全移行

```sql
department_managers(id INTEGER PK AUTOINCREMENT,
                    department_id INTEGER REFERENCES departments(id),
                    user_id INTEGER REFERENCES app_users(id),
                    role TEXT)  -- 'manager'(課長) | 'director'(部長)
```

- 既存 `departments.manager_user / director_user` のデータは seed で移行し、**列は物理削除せず使用停止**（SQLite の DROP COLUMN 制約を避ける。モジュール・スクリプトからの参照は全て除去し、二重管理は発生させない）。
- 部門マスタ画面は単一リンク2個 → **役職者の子リスト（DepartmentManager 子モジュール、DeleteTogether）** に置き換え。

### 2. 承認セマンティクス: 同一 Order 展開 ＋ OR 完了（approval_type）

- ルート解決（LoadFromTemplate）で `approver_role='manager'|'director'` を**該当役職の全員**を同一 Order のメンバーとして展開する。
- `approval_flow_order` に **`approval_type TEXT`（'all' 既定 / 'any'）** を追加。役職展開で複数名になった Order は `'any'`（**1人が承認すれば次段へ**）。1名なら従来どおり。
- 完了判定 `IsOrderCompleted` は**メモリ Rows 依存を廃し DB ベース**に書き換える（既知バックログ「並列承認の DB 化」と同一作業）。直前にメモリで Approved にした Member は DB 未反映のため、**判定時に当該 Member Id を Approved とみなすオーバーライド**を行う。
- Order 完了時、同 Order の残 Waiting メンバーは **Skipped** にする（二重承認防止・履歴の可読性）。
- **却下は従来どおり1人の却下でフロー全体が却下**（OR 承認でも実務上これが自然。差し戻し→再申請で回復可能）。
- 制約（設計上の前提）: **役職解決メンバーは Order 内で単独**であること（固定承認者との混載不可）。既存テンプレ4種は全て満たす。テンプレを増やす際はこの前提を守る。

### 3. 自己承認禁止（ADR-0010）の一般化

「候補集合から申請者を除外 → 残0名なら格上げ → それも0名なら経理代替」:
1. 役職候補（例: 課長2名）から申請者本人を除外。**残があればそのまま**（申請者が課長の1人でも、もう1人の課長が承認すればよい）
2. 課長候補が0名になったら部長候補（申請者除外）へ格上げ
3. それも0名なら経理ロールの他ユーザー（Id 最小）を代替承認者に（従来どおり）
4. 固定承認者（総務）が本人の場合も従来どおり経理代替

### 4. 承認待ち一覧（ApprovalInbox）のメンバーベース化

現状は `approval_flow.current_approver`（代表1名）との一致で絞るため、**2人目以降の課長の受信箱に案件が出ない**。SQLite **VIEW** で作り替える:

```sql
CREATE VIEW approval_inbox_view AS
SELECT m.id, f.parent_module_name, f.parent_id, f.status,
       m.approver_user_id AS current_approver, f.creator, f.created_at
FROM approval_flow_member m
JOIN approval_flow_order o ON o.id = m.approval_flow_order_id
JOIN approval_flow f ON f.id = o.approval_flow_id
WHERE m.status='Waiting' AND o.status='Active' AND f.status='Pending';
```

- 列名を旧テーブルに合わせるため **ApprovalInbox モジュールは DbTable の差し替えのみ**（DataReadCondition は既存の CurrentApprover==自分 がそのまま効く）。読み取り専用モジュールのため VIEW で問題ない（designcheck で実証確認する）。
- 「自分の番のものだけが出る」（Active Order の Waiting メンバーのみ）という業務的意味も明確になる。
- `approval_flow.current_approver` は**画面表示・検索用の代表者**（最初の Waiting メンバー）として存続。

### 5. 二重承認の多層防御

- 承認ボタン可視判定（HasWaitingMemberForCurrentUser）と実行時検索（GetCurrentMemberForUserStrict)は **Active な Order のメンバーのみ**を対象にする（Order 状態を DB で確認）。Skipped 化が万一漏れても承認は通らない。

## 却下した代替案

- **departments に manager_user2 等の列追加**: 人数上限が構造に埋まる。論外として不採用。
- **AND 承認（全課長の承認が必要）**: 実務の「どちらか1人が見れば良い」に反する。approval_type='all' として機構は残す（将来テンプレで選択可能）。
- **受信箱を C# 拡張やスクリプトで動的絞り込み**: VIEW の方が宣言的で、CLB の DataReadCondition 機構に自然に乗る。

## レビュー反映（2026-07-08 夜・3視点サブエージェントレビュー後の追加決定）

1. **ルート解決・自己承認除外は「申請者」基準に統一**: 従来は操作者（CurrentUser）基準だったため、実費超過の再承認（ReapproveForOverrun）を経理等が代行すると (a) 代行者の部門で誤解決 (b) 申請者本人が承認者に入る自己承認の穴があった（レビュー指摘・既存からの持ち越し）。申請者 = フローの最初の Submit 履歴の ActorUser（未申請なら操作者）として解決する。
2. **却下・キャンセル経路の Skipped 化も DB ベースに統一**（承認経路と同じ #60 対策）。
3. **ID 等値判定は文字列正規化（IsSameId）に統一**: LinkField/SelectField/IdField 由来の型差で比較が silent no-op になるリスクを排除。
4. **役職解決に実在チェック**: 物理削除されたユーザーの department_managers 残骸行を除外（1人役職の部門でフローが永久停滞する事故の防止）。
5. **`department_managers` に UNIQUE(department_id, user_id, role)**（251_department_managers_unique.sql）。重複行はマスタ保存時に DB エラーで拒否される。
6. **役職者の候補は Role≠general に絞る**: general ロールを課長登録すると承認ボタンは出るのに受信箱・件数は見えない（UserReadCondition）片手落ち状態になるため、候補から除外。
7. **ホームの承認待ち件数はロールゲート付き**: ApprovalInbox は UserReadCondition 付きのため、approver/accounting 以外では検索しない（一般社員のホーム破壊の予防）。

## 既知の限界（v1 で許容・記録）

- **承認テーブルのサーバー強制の書き込みゲートは無い**: approval_flow/order/member と expense_request の状態列は、CLB の宣言的条件（User/DataWriteCondition）では「申請者が他人の承認メンバー行を作成でき、承認者が自分の行だけ更新できる」という状態遷移を表現できない。承認・却下の権限判定はクライアント（WASM スクリプト）実行であり、API を直接叩く悪意ユーザーの自己承認改ざんは防げない。**社内利用（ペルソナ=30〜80名のソフトハウス）の信頼境界では許容**とし、厳格化する場合はサーバ拡張（C# のカスタム保存 API）が必要——バックログに記録。なお会計コア（仕訳等）は B-8 の経理ゲートで保護済み。
- **真の同時承認（コミット前の同時実行窓）は防げない**: 楽観ロック無しの last-write-wins。stale 画面（先行コミット後）の二重承認は Active Order ゲートで防御済み。ブラウザ運用では発生頻度が低く v1 許容。
- **並列相方への承認依頼通知は取り消されない**（開いても承認ボタンは出ない。E-08 で仕様確認）。

## 検証条件（必須）

- 過去に遅延ロード起因（#60）の重大バグを2度修正した領域。**S-01〜S-03 の完全回帰＋複数役職者の新シナリオ**（2人課長の並列承認・申請者=課長の1人・1人が却下・受信箱の両者表示と承認後の消滅）を**ブラウザ実機**で全件確認する。テストケースは専任サブエージェントが設計（docs/08_テストケース_複数役職者.md）。
