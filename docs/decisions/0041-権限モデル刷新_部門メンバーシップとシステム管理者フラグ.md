# ADR-0041: 権限モデル刷新 — ロール廃止、部門メンバーシップ×システム管理者フラグへ

- 日付: 2026-08-02
- 状態: 採用（実装・実機検証済み・旧 role 列は廃止完了）
- 関係: ADR-0040（部品アーキテクチャ）と対。ADR-0016（複数部門長）・ADR-0023（承認ルートマスタ化）の機構は無改修で継承
- DDL: `Designer/ddl/380_membership_permissions.sql`（導入）・`385_recompute_permission_cache.sql`（一括再計算）・`390_drop_role.sql`（旧列廃止）

## 背景

旧 `AppUser.Role.Value`（general/approver/accounting/sysadmin の単一選択）は、性質の違う 3 つの軸
——①部門機能（経理部だから会計をする）②職位（部門長だから承認する）③IT 管理職能——を 1 カラムに
押し込んだ人工物だった。そのため「営業部の一般と開発部の一般で見え方を変える」「A 部では承認者・
B 部では一般」という実務の状態を表現できず、部品アーキテクチャ（ADR-0040）とも噛み合わなかった。
ユーザーレビューで「ロール前提を捨て、所属部×権限でゼロベースに再設計する」方針が確定した。

## 決定

### 1. 手で管理する「真実」は 2 つだけ

| 真実 | 実体 | 内容 |
|---|---|---|
| 部門メンバーマスタ | `department_members`（旧 department_managers に「一般 member」を追加して昇格） | ユーザー × 部門 × 権限（member／manager=課長／director=部長）。兼務・「A部承認者/B部一般」は行の追加で表現 |
| システム管理者フラグ | `app_users.is_sysadmin` | 所属と独立（情シス部所属≠管理者、が実務）。自分自身の解除はロックアウト防止ガードで禁止 |

承認ルート解決（ADR-0016）は manager/director 行だけを読むため、member 行の同居は承認機構に影響しない
（実測: 課長2名の OR 並列ルートが正しく生成され、member 行は混入しない）。

### 2. 見え方はメンバーシップから導出（手入力の見え方設定を作らない）

CLB のフレームゲート（UserReadCondition）はログインユーザーの AppUser 列しか参照できないため、
**ゲート用キャッシュ列**を AppUser に持ち、**DB トリガーが経路非依存で転記**する（select_label と同じ定石。
CLB Submit・sql CLI・デモ掃除 SQL のどこから書いても追随する）:

- `has_sales_access` = 営業種別の部門にメンバー行がある
- `has_accounting_access` = 経理種別の部門にメンバー行がある
- `is_approver` = どこかの部門に課長/部長行がある

部門マスタに **部門種別**（dev/sales/accounting/other）を追加。参照するのは転記トリガーのみで、
フレーム定義は部門名を知らない——組織改編（部の新設・分割・種別変更）はマスタ変更だけで追随する。
キャッシュ列は `IsUpdateProtected: true`＋レイアウト非表示（AppUser 一覧に閲覧列のみ）。
整合が疑わしいときは `ddl/385` でいつでも全再計算できる（列は捨てられるキャッシュ）。

### 3. 職務分掌 — sysadmin は「経理の上位互換」をやめる

- sysadmin が入れるのは MasterAdmin（ユーザー・部門・部門メンバー・承認テンプレ・承認ルート）のみ。
  業務フレームへの OR 同乗を全廃 → 「経理にはできて sysadmin にはできないこと」（仕訳・請求・入金・支払・会計マスタ保守）が明確になった
- 会計ドメインマスタ（勘定科目・科目表示区分・補助科目・費目・税率・税区分・経過措置・制度閾値）の
  書込権限を sysadmin → 経理へ移管（税率を情シスが触る会社は無い）
- 内部統制上の意味: 旧 sysadmin は「架空取引先の登録→口座登録→仕訳→振込データ作成」を単独で完結できた。
  新モデルはこの単独完結を構造的に排除する（J-SOX の IT 全般統制で説明可能な形）
- 従来型スーパーユーザーに戻したい企業向けのカスタムポイント: 各フレームの UserReadCondition に
  `IsSysAdmin == true` の OR を 1 つ足すだけ（docs/10 §カスタムポイント）

### 4. 着地の優先順位（RoleDispatch）

sysadmin → MasterAdmin ／ 経理 → Accounting ／ 承認者 → ExpenseApprover ／ 営業 → SalesStaff ／
それ以外 → ExpenseStaff。一般・承認者系の 5 フレーム（ExpenseStaff/ExpenseApprover/Timesheet/SalesStaff/
ManagementApprover）には「マイページ」リンク（同一フレーム内 RoleDispatch）があり、自分のホームへ戻れる
（経理系 7 フレームは静的な相互リンクで完結するため持たない）。

## 移行

- 並走方式: 新権限基盤を追加してフレームと全モジュール権限条件（96 条件・82 モジュール）・スクリプト 14 ファイルを切替え、
  全実機検証の通過後に `role` 列を廃止（`ddl/390`）。active_app_users ビューと seed 用トリガーは
  role なしで再作成し、空 DB の初期 admin に is_sysadmin=1 を付与（seed の INSERT は user_name/hash/salt のみ、実装確認済み）
- 既存 27 ユーザーの移行はメンバー行の自動生成＋一括転記（`ddl/380`）。部門種別は
  総務部=accounting／営業部・SaaS事業部=sales／開発1・2部=dev／全社共通=other
- 検証で確認した事実: メンバー行の UI 編集（部門詳細）→キャッシュ即時転記の往復／
  権限外フレームの直 URL 拒否／role 列廃止後のログイン・振り分け正常

## 影響・注意

- **テストアカウントの読み替え**が必要（旧「ロール」列は消えた）: `docs/tests/19` 参照
- CLB への改善提案: フレーム条件が関連テーブルを参照できない制約が本キャッシュ列の存在理由（FB-034）
- 承認テンプレートの個人指名承認者が課長/部長行を持たない場合、「承認タスクは届くが承認者フレームが
  見えない」状態になりうる（メンバーマスタの運用衛生で回避。将来はテンプレメンバーも is_approver 算定に含める拡張余地あり）
