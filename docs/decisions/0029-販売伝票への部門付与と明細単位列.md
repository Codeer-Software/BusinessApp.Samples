# 0029: 販売伝票への部門付与（＋明細の単位列）

- 日付: 2026-07-23
- 状態: 採用・実装済み
- 起点: ユーザーレビュー第7弾（見積・受注・請求書・売掛残高を取引先・案件・部門で検索したい／見積書に単位列がほしい）

## 決定1: 部門は「案件」ではなく「伝票」が直接持つ

見積（quotes）・受注（sales_orders）・請求書（invoices）・定期請求契約（recurring_billings）に
`department_id INTEGER REFERENCES departments(id)` を追加する（ddl/330）。案件（projects）には部門を持たせない。

### 理由

1. **仕訳明細との相似**: このアプリの分析軸の正は journal_lines であり、部門と案件は独立した2軸
   （両方持つ・片方だけ・どちらも無し、が全て有効）。伝票も同じ構造にすることで齟齬が生じない。
   工数入力・人件費配賦・案件損益は案件軸の機能であり、案件が部門を持たなくても影響しない。
2. **発行時点スナップショット**: 案件経由の導出だと案件の主管部門変更が過去伝票へ遡及する。
   伝票が直接持てば発行時点の所属が固定される（ddl/270 経費申請の部門スナップショットと同じ思想）。
3. **部門横断案件を自然に表現できる**。

### 運用

- 任意入力（NULL=全社/共通）。新規作成時は**作成者の所属部門を初期値**にする（各 mod.cs）。
- コピー伝搬: 見積→受注（変換）／受注→請求書（検収の請求書作成）／契約→請求書（定期実行）。
- **売上仕訳への伝搬**: 検収確定・定期実行（月額売上・年額前受・按分振替）の仕訳明細に伝票の部門をセット
  → 総勘定元帳の部門絞り込み（既存機能）で部門別売上が取得できる。SES 精算経由は部門ソースが無いため v1 では未設定。
- 既存データは作成者（creator）の現所属部門でバックフィル。creator 無しの seed 契約は営業部で補完。
- 組織変更への耐性: ID 参照＋無効化運用（改名=マスタ変更が全画面反映／消滅・合併=無効化で過去伝票は保全／
  分割=旧部門のまま保存が発行時点の事実）。部門系譜の付け替え分析は対応外（市販中小向けソフトと同じ割り切り）。
- 入力ドロップダウンは部門マスタ参照（表示順ソート）。経費申請の前例に合わせ IsActive では絞らない
  （検索用途で無効部門の過去実績も探せることを優先）。

## 決定2: 検索条件の拡充

- 見積・受注・請求書: 取引先・案件・部門のドロップダウン検索を検索レイアウト2行目に追加。
- 売掛残高（クエリ）: @partner_id / @project_id / @department_id（NULL=絞り込みなし）＋状態・支払期限。
  状態は既定「入金済を除く」（サイドバー経由の OnSearchInitialization で設定）。
- **検収は見送り**: 受注経由（リンク先参照）の検索は CLB 非対応と実測で判明（描画されるが候補が空＝静かな失敗。
  FB-033）。ユーザー指示により非正規化（検収への列コピー）は行わず現状維持。

## 決定3: 明細の「単位」列（ddl/320）

quote_lines / sales_order_lines / invoice_lines に `unit TEXT` を追加（自由入力。式・人月・か月・時間 等）。
明細コピーの全経路で引き継ぎ、定期・SES 生成分は「式」。見積書・請求書の帳票テンプレートに単位列を挿入
（数量の右）。定期契約の見積は専用モジュールを作らず、既存見積の明細記載（単価の単位を摘要・単位列で明示）
＋備考（契約期間・サイクル等）で表現する。

## 影響

- ddl/320・330、販売系モジュール・スクリプト、帳票テンプレート2種、総勘定元帳の部門別売上が有効化。
- テスト計画と実施結果: docs/tests/16。
