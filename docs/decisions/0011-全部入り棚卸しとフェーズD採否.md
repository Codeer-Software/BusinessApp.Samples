# 0011: 「全部入り」棚卸しによるスコープ拡張（フェーズ D の採否）

- 状態: 採用 / 日付: 2026-07-06

## 背景

計画フェーズ A/B/B'/C の全機能が実装・実機検証済みとなった時点で、ユーザーと「**今作っていないが、『全部入り』『中小企業が満足する』と言うために追加すべき機能は無いか**」をゼロベースで棚卸しした（社長指示の原点=「市販ソフトの仕様は全部参考に、完璧なものを」への総点検）。市販ソフト（弥生会計・freee・マネーフォワード。MF は最上位プラン機能も含む）の機能表と突き合わせ、候補ごとに 価値×実装コスト×検証可能性 で採否を判断した。

制約: Fable との作業期限が 2026-07-07 まで。ISSUE-0001 の調査より新機能実装を優先する（ISSUE-0001 はユーザーが後日単独で対応可能なため）。

## 決定（採用 — フェーズ D として実装。番号は優先順）

| # | 機能 | 採用理由 |
|---|---|---|
| D-1 | **月次推移表**（PL/BS の12ヶ月横並び） | 市販ソフト必須帳票で経営者・税理士が最頻使用するのに現状は年度スナップショットのみ。既存の仕訳集計 SQL のピボットで作れて費用対効果が全候補中最高 |
| D-2 | **銀行・クレカ明細 CSV 取込 → 自動仕訳 → 残高照合** | freee/MF が市場を取った核心機能。実務の仕訳の大半は銀行・カード明細から生まれるのに現状の仕訳入口は手入力・経費・請求・AI 領収書のみ。ルールベース（摘要パターン→科目のマッチングルールをマスタ化）＋ルール未該当は既存 Azure OpenAI 基盤で科目推定→確認して一括起票。**残高照合（銀行残高 vs 帳簿預金残高の突合）を一体設計する**（→ ADR-0012）。API 連携ではなく CSV 取込（→ 不採用欄） |
| D-3 | **キャッシュ・フロー計算書**（間接法・簡易） | BS・PL・株主資本等変動まであって C/F だけ無い＝財務三表が揃っていない。中小に作成義務は無いが「全部入り・複式簿記も全部」の指示に対する形式的な穴。間接法なら既存データから導出でき、資金繰り予測（C-2）と併せて資金管理の物語が完成する |
| D-4 | **定型仕訳（仕訳辞書）** | 毎月の家賃・給与・社保など「科目は同じで金額だけ変わる」繰り返し仕訳のテンプレ登録→ワンタッチ起票。実務満足度に直結する割に実装が最軽量 |
| D-5 | **仕訳 CSV インポート**（汎用） | ①他ソフトからの移行導線（「弥生は要らない」と言うには弥生から乗り換えられる必要がある。Excel 出力23画面に対し取込が予算のみという非対称は導入提案で必ず突かれる）②**給与データ取込を兼ねる**（→ 不採用欄「給与専用取込」） |
| D-6 | 買掛・支払管理（請求書受領→未払計上→支払予定表→支払消込） | 売る側（見積→…→消込）は完備だが買う側が経費精算のみ。IT 受託の最大コストは外注費・SES 仕入でありペルソナ物語の残る穴。資金繰り予測の「発生予定経費」の精度も上がる。**優先度は D-1〜D-5 の後（余力枠）** |

## 決定（不採用・後回し — 理由付き）

| 項目 | 判断 | 理由 |
|---|---|---|
| 銀行 API 連携（明細の自動取得） | 不採用（継続） | 銀行との認証・契約が必要な外部依存でデモ環境では実現不能。CSV 取込（D-2）で実務価値の大半を回収 |
| 振込データ作成（全銀フォーマット FB データ） | **後回し**（D-6 の後続としてバックログ化） | ①依存が逆: FB データの源泉は支払予定であり、買掛・支払管理（D-6）より先に作ると出力すべきデータが無い（例外は経費精算の社員振込のみで訴求が小粒） ②取引先・社員の銀行口座マスタ整備が必要 ③固定長 Shift-JIS・半角カナの規約ものだが、この環境では実銀行に取り込む検証手段が無く「仕様書と目視で合ってるはず」までしか到達できない（実機検証主義に照らし品質保証が弱い） |
| 給与データ専用の取込機能 | 不採用（D-5 に吸収） | 給与計算ソフト（弥生給与・MF 給与・freee 人事労務）は例外なく会計ソフト向け仕訳 CSV 出力を持つ。受け側に必要なのは給与専用機能ではなく汎用の仕訳 CSV インポート。給与仕訳は定型パターンなので D-4（定型仕訳）＋ D-5 で中小実務の9割をカバー |
| 給与計算・年末調整そのもの | 不採用（継続） | 別製品ドメイン（03 §7 の既存判断を維持） |
| 法人税申告書・勘定科目内訳明細書 | 不採用（継続） | 税理士連携領域。「申告は税理士、日常会計は本アプリ」の線引きを維持 |
| 電子帳簿保存法の完全準拠・簡易課税 | 不採用（継続） | 既存判断を維持（ペルソナの年商規模なら原則課税） |

## 影響

- `03_機能スコープ.md` に §8 フェーズ D を追加、§7 見送り表を更新。
- 実装順序: D-1 → D-2 → D-3 → D-4 → D-5 →（余力）D-6。詳細は `05_実装計画と進捗台帳.md`。
- D-2 の構造設計は ADR-0012 に分離（残高照合を後付けにしない設計判断）。
