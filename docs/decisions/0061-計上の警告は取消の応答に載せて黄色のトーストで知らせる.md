# ADR-0061 計上の警告は、取消の応答に載せて黄色のトーストで知らせる

## 状況

**計上の検証は「止める（Error）」と「止めない（Warning）」を持っている**が、
**Warning はどこにも届かない。**

**実物を開いて確かめた**（2026-09-16）。

**警告に落とす規則は 2 つある**（`JournalEntryValidator`）。

| 重さの規則 | 警告になる種別 | 当たる検査 |
|---|---|---|
| `ReversalOnlySeverity` | **取消だけ** | 伝票の取引先の実在・有効／`E-PARTNER-REQUIRED`（取引先を要する科目）／`E-SUBACCOUNT-REQUIRED`・`E-SUBACCOUNT-NOT-ALLOWED`（補助科目の 2 値） |
| `InactiveSeverity` | **取消と訂正の両方** | 明細の取引先の実在・有効／`E-ACCOUNT-INACTIVE`／`E-DEPARTMENT-INACTIVE`／`E-SUBACCOUNT-INACTIVE` |

**つまり警告は取消だけのものではない。訂正の再計上でも出ている**（[15 §1-3](../15_記帳の枠組み.md) の表も、明細の取引先を訂正で「止めない」と書いている）。

**そして、捨てているのは 4 段ある。**

1. **`JournalPoster.PostAsync` が `PostingResult.Violations` を捨てる。**
   返すのは `result.PostedEntry` だけで、同じ場所の注記が
   「戻り値に `with` で足しても誰も読まず、表明の無い契約になるだけである」と書いている（2026-08-25 の自己レビュー）。
   **警告の出どころはここである**——`JournalPosting.Post` が `JournalEntryValidator` の違反を載せている
2. **`JournalAmendmentService.PostDraftAsync` が、その戻り値ごと捨てる**
3. **`AmendResult.Ok(...)` は `Violations` を空の配列で作る**
   （`AmendResult` には `violations` の欄が既にある。**ただし「差し戻しの内訳」として定義されており、
   `AmendViolation` は `Code`・`Message`・`LineNo` だけで重さを運ばない**）
4. **`JournalEntry.mod.cs` の `Amend()` は、成功したら `Toaster.Success(done)` を出すだけ**で、
   応答の `violations` を読んでいない

**`JournalReversal.Reverse` の違反ではない**——あちらが作るのは `AlreadyReversed` と
`AmendmentRules.ValidateOriginal` だけで、**どれも Error なので成功経路には 1 件も残らない**。

**つまり、無効にした科目・部門・補助科目・取引先のまま取消や訂正が通っても、利用者は何も知らされない。**
自己レビュー（[R69-13](../qa/02_自己レビュー記録.md)）が「既存の穴を取引先で 1 種類広げた」と指摘して、
[05](../05_開発者への問い.md) の旧 Q-12 として開発者に諮ってあった。

**画面まで届ける経路は 2 つで、通る道が違う**——
取消と、訂正の取消部分は Web API（`JournalAmendmentEndpoint`。[ADR-0016](0016-画面から呼ぶサーバ処理はWebAPIに置く.md)）、
訂正の再計上は「計上する」の標準の保存経路（`this.Submit()` → `AccountingSubmitPipeline`）である。
**サーバ側で警告を拾う場所は、どちらも `JournalPoster` の 1 か所である。**

## 決定

**開発者の決定である**（2026-09-16。Claude が 3 案を示して A を選んだ。
逐語は「**あなたの推奨どおりAで行きましょう。**」）。**A の本文は次のとおりだった**——

> **A. 「取り消す」の応答に載せ、画面で黄色のトーストにする**——Web API の応答に `warnings` を足し、
> `JournalEntry.mod.cs` がトーストにする。利用者がその場で気づく。帳簿は変えない。
> **取消しか覆わない**——訂正の再計上（保存の成功）に文言を載せる経路は未計測。

1. **取消の応答に警告を載せ、画面で黄色のトーストにする。**
   帳簿は変えない（計上済みの伝票に列を足さない）

**知らせ方の既定も開発者が決めた**（同日。逐語は
「**基本はCLBの通知機能を使う方針でいいと思ってます。それがどうしてもふさわしくないならダイアログなどを検討する、
という順番で考えましょう。**」）。

2. **知らせは CLB の通知機能を既定とする。**
   **ダイアログを検討するのは、トーストがどうしてもふさわしくないときだけ**である。
   **逐語の「CLB の通知機能」を `Toaster`、「ダイアログなど」を `MessageBox` と読んだのは Claude である**
   （CLB の仕様は `Designer/ClaudeCodeForDesigner/Docs/AppPatterns/dialog_patterns.md`）

**以下は Claude の敷衍で、開発者は述べていない。**

3. **使うのは `Toaster.Warn` である**（`Success`・`Info`・`Warn`・`Error` の 4 種のうち。
   **本製品は既に `Toaster.Warn` を使っている**——`JournalEntry.mod.cs` の「この伝票は計上済みです。」）。
   **規則そのものは [21 §2-7](../21_画面の原則.md) に置いた**（この ADR は取消への当てはめだけを持つ）
4. **訂正の再計上の側も、同じ `JournalPoster` で拾う。**
   **決めていないのは「画面まで届ける手立て」だけ**である——
   標準の保存経路（`this.Submit()`）に**成功時の文言を載せられるかは未計測**なので、
   **実測してから決める**（[qa/01](../qa/01_CLB静かな失敗.md) の型——**想像で決めない**）

## 理由

**以下は Claude の整理である。** 開発者が述べたのは A を選んだことと、通知を既定にすることである。

- **警告のほとんどは、利用者がその場でできることが 2 つしかない**——「マスタを有効に戻す」か「気にしない」。
  作業を止める価値が無いので、ダイアログではなくトーストが合う
- **ただし `ReversalOnlySeverity` の 3 つは違う**（`E-PARTNER-REQUIRED`・`E-SUBACCOUNT-REQUIRED`・
  `E-SUBACCOUNT-NOT-ALLOWED`）。**これらは原仕訳がそもそも相手方や補助科目を欠いている場合**なので、
  **有効に戻す相手が存在しない**。とくに `E-PARTNER-REQUIRED` の取消行は**相手方を欠いたまま帳簿に載る**——
  [15 §1-2](../15_記帳の枠組み.md) が「摘要と違い、書いて救えない」と書いているとおりで、計上済みは不変（I-05）である。
  **消えるトースト 1 枚では、その事実がどこにも残らない**（帰結 7）
- **帳簿は変えない。** 計上済みの伝票に列を足すと、[ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md) の不変性は保てるが**スキーマが動く**。
  **帳簿に出す価値のある情報になった時点で考え直す**

## 検討したが採らなかった案

| 案 | 中身 | 採らなかった理由 |
|---|---|---|
| **B. 計上済みの伝票に注記として残す** | 列を足し、詳細と帳簿に出す | 取消と訂正の**両方の経路を覆え、消えない**が、**スキーマが動く**。帳簿に出す価値が立ってから（**ただし理由の 2 つ目が、B が覆っていた穴を残す**） |
| **C. サーバのログにだけ書く** | ログ出力 | 実装は最小だが、**利用者には届かない**（いまと同じ） |

## 帰結

**以下は Claude の敷衍で、開発者は述べていない。実装はフェーズ 4**
（[04 §5](../04_実装計画と現在地.md) が期限を持つ。**ここには期限を書かない**）。

1. **`JournalPoster.PostAsync` が `PostingResult.Violations` も返す。**
   **戻り値を変えると `this.Submit()` の経路とも共有している**ので、
   `JournalSubmitGate` 側の呼び出しも同時に直す
2. **`JournalAmendmentService.PostDraftAsync` が上へ運び、`ReverseCoreAsync` と `CorrectCoreAsync` の
   両方が `AmendResult.Ok(...)` に載せる**（訂正の取消部分も同じ応答に乗る）
3. **`AmendResult.violations` の意味を広げる。**
   いまの注記は「差し戻しの内訳」で、`AmendViolation` は重さを運ばない。
   **`status: "ok"` の応答に警告を載せるなら、重さを運ぶか、注記と画面の約束を書き換える**
4. **`JournalEntry.mod.cs` の `Amend()` が、成功したときに `violations` を読んで `Toaster.Warn` を出す。**
   **`Toaster.Warn` は `Toaster.Success` の後に出す**——
   **`Success` は表示中のトーストを消してから出す**（CLB の実装と仕様書の両方で確かめた。2026-09-16）ので、
   **先に警告を出すと黙って消える**（[qa/01](../qa/01_CLB静かな失敗.md) の静かな失敗の型）
5. **遷移をまたいでトーストが残るかは未計測である**——
   `Amend()` は `Toaster.Success` の直後に画面を遷移させる。**実機で測る**
6. **警告が複数のときの出し方は [21 §2-4](../21_画面の原則.md) が既に決めている**
   （改行を入れず「（2 件）。①…②…」で区切る。**開発者の決定**。2026-09-10）。
   **新しく決めるのは「トーストを何枚出すか」だけ**で、
   [21 §2-6](../21_画面の原則.md) の判断基準（1 つにできるならそのほうがよい。費用で測る）を当てる
7. **`E-PARTNER-REQUIRED` の取消だけは、トースト 1 枚では足りない**（理由の 2 つ目）。
   **法定記載事項を欠く行が帳簿に永久に残る**ので、**記録に残す手を別に決める**（ログか注記）。
   **[40 §6](../40_優良な電子帳簿の対応表.md) に積んだ**
8. **`JournalEntryValidator` の注記（「警告は、いまはどこにも届かない。届け先は未決である」）を、
   この ADR へのリンクに書き換える**（[qa/02 R69-13](../qa/02_自己レビュー記録.md) が 15 §1-3 と対で入れた記録である）
