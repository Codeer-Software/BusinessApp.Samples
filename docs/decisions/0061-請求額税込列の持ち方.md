# ADR-0061: 請求書一覧の「請求額（税込）」を実列＋トリガーで持つ

- 日付: 2026-08-16
- 状態: 採用
- 関連: ADR-0050（税額計算）／`ddl/280_select_labels.sql`（同型のトリガー保守列）

## 背景（問題）

請求書一覧が「請求書番号／発行日／取引先／件名／状態」だけで金額を持たず、
「いくらの請求か」を見るには 1 件ずつ開く必要があった。

実務で請求書一覧を眺める目的は **入金と突き合わせる／未回収の総額を掴む** なので、
欲しいのは**税込**の金額。ところが `invoices` は `amount`（税抜）と `tax_amount` を別々に持ち、
税込の列が無い。

## 選択肢

| 案 | 内容 | 得失 |
|---|---|---|
| A | 税抜（`amount`）をそのまま列に出す | 最短。ソート・検索も効く。ただし実務が突き合わせたい数字ではない |
| B | 一覧の行スクリプトでラベル列を作る | 保存列を増やさない。**ソート・検索ができない** |
| C | 生成列（`GENERATED ALWAYS AS ... VIRTUAL`） | 定義上ズレようがなく理想的 |
| **D** | 実列＋DB トリガー保守 | 保存列は増えるが、経路非依存で整合する |

当初はユーザーと B で合意していたが、実装前に C を試したところ
**CLB のスキーマ照合から生成列が見えなかった**（`designcheck` が
「カラム 'gross_amount' が 'BusinessAppSQLite.invoices' に存在しません」。
`PRAGMA table_info` は生成列を返さず `table_xinfo` が要るため）。
C が使えないと分かった時点で、B の制約（ソート不可）を受け入れる理由が無くなった。

## 決定

**D を採用**。`invoices.gross_amount`（INTEGER）を実列として持ち、
`AFTER INSERT` と `AFTER UPDATE OF amount, tax_amount` のトリガーで
`COALESCE(amount,0) + COALESCE(tax_amount,0)` を書き込む（`ddl/550`）。

アプリ層のフックではなくトリガーにする理由は `select_label`（ddl/280）と同じ:
**請求書は 手動作成 / 検収から作成 / SES 一括生成 / 定期請求実行 の 4 経路で INSERT される**ので、
mod.cs 側のフックだと経路ごとに保守が要り、必ず漏れる。トリガーなら経路を問わず整合する。

モジュール側は `IsUpdateProtected: true` + `IgnoreModification: true` の NumberField で**読むだけ**にし、
一覧では件名の次に右詰め（`amount-cell`）で表示する。ソートも効く。

## 影響

- 既存 45 件は移行時に一括で埋めた。
- トリガーは `UPDATE OF` で監視列を限定しているため、トリガー自身の `UPDATE`（`gross_amount` のみ）では再発火しない。
- 検証: 金額を書き換えて `gross_amount` が追随し、戻すと元に戻ることを実データで確認済み。

## 備考（将来の罠）

- **CLB は SQLite の生成列を認識しない**（実測）。他の「同じ行から導ける値」を足したくなったときも
  生成列は使えないので、トリガー保守列にする。
- 税込を使う場所が増えたら（帳票・検索条件など）この列を使い回す。
  逆に、税抜が要る場所で誤ってこの列を使わないよう、表示名は必ず「請求額（税込）」と明示する。
