# ADR-0032 認証部品の `app_users` を正典に迎え入れ、役割の列を間借りする

## 状況

[ADR-0026 §1](0026-画面は役割で分け玄関のページフレームを置く.md) が、役割の列を
**`app_users` に間借りする**と決めた（`is_sysadmin` / `accounting_role` / `partner_role`、
のちに `can_access_app` を追加）。**列の定義は各部品が所有し、その部品がマイグレーションを出す**、
というのがその形である。

ところが、それを実装しようとすると**置き場所が無かった**。

- **`app_users` は本プロジェクトが作ったテーブルではない。** CLB の Cookie 認証が使うもので、
  形は CLB 仕様リファレンス `_specs/Authentication.md` が決めている。
  `Designer/ddl/` にも `Designer/migrations/baseline/` にも入っていない
- **`migrate.ps1 -Verify` は `app_users` を「管轄外」として比較していない**
  （`SchemaVerifyCli` が「正典が持つオブジェクト」だけを管轄とする）
- したがって `ALTER TABLE app_users ADD COLUMN ...` というマイグレーションは、
  **同値検査（`MigrationEquivalenceTests`）が baseline から再生したときにテーブルが無くて落ちる**

**別テーブルに逃がすことはできない。** CLB の権限条件は
**ログインユーザーのレコードの列しか参照できず、関連テーブルを辿れない**
（[qa/01 F-21](../qa/01_CLB静かな失敗.md)）。役割を `app_user_roles` のような表に持つと、
そもそも権限条件が書けない。

## 決定

**`Designer/ddl/007_auth.sql` を作り、`app_users` を正典に迎え入れる。**

- **本体の列（`id` / `user_name` / `name` / `hash` / `salt` と索引）は CLB のものなので変えない。**
  正典に書くのは**稼働 DB から写した現物**であって、本プロジェクトが決めた形ではない
- **間借りの列（役割 4 本）は末尾に置く。** `ALTER TABLE ADD COLUMN` と同値のテキストになる
  （[migrations/README](../../Designer/migrations/README.md) の規約）
- **マイグレーションは「無ければ作ってから足す」**（`CREATE TABLE IF NOT EXISTS` ＋ `ALTER TABLE`）。
  稼働 DB では CREATE が何もせず、baseline からの再生では CREATE が効く。どちらも同じ姿になる
- **役割の付与（DML）はマイグレーションに書かない。** migrations/README が
  「データ行の同値の網が入るまで DML マイグレーションは書かない」と定めているうえ、
  **新しい DB では空振りする**——`admin` は CLB がサーバ起動時に作るので、
  マイグレーションを当てる時点ではまだ居ない。**最初の 1 人に `is_sysadmin` を立てるのは導入の手順**である

## 理由

**正典が知らない列は、誰も守れない。**
間借りしたまま `app_users` を管轄外に置き続けると、
**役割の列が欠けていても・型が違っても、同値検査も `-Verify` も素通りする。**
役割の列が欠けるということは、**権限条件が誰にも当たらなくなる**——
つまり全開放（[qa/01 F-18](../qa/01_CLB静かな失敗.md)）に静かに戻る。
これは「守りが 1 枚も無い状態に、警告なしで落ちる」形であり、本プロジェクトが最も避けたい壊れ方である。

**「所有」と「正典に書くこと」は別である。**
[ADR-0025 §5](0025-取引先を部品として分ける.md) が「DB は分けない。物理の同居と論理の所有は別」と
決めたのと同じ整理を、もう 1 段進めたものにあたる——
**物理のスキーマは 1 つの正典が持ち、論理の所有は部品ごとに持つ。**
`007_auth.sql` の中で、本体の列と間借りの列をコメントで分けているのはそのためである。

**代案「同値検査も管轄で分ける」を採らなかった。**
`SchemaSnapshot.SplitByJurisdiction` は既にあるので、
同値検査にも当てて `app_users` を無視させることはできた。
しかしそれは**「守れない範囲を広げる」方向**であり、上の理由の逆を向いている。

## 帰結

- **`app_users` が管轄内に入った。** `migrate.ps1 -Verify` が比較するオブジェクトは 33 → 38 に増えた
  （2026-08-31 実測）。今後、CLB が本体の列を変えたら**この検査が鳴る**——
  鳴ったら正典を現物に合わせて直す（CLB 側が正しい）
- **`can_access_app` の既定は真**にする。CLB はユーザーテーブルが空のとき `admin` を自動で入れるので、
  偽を既定にすると**その `admin` が生まれた瞬間に締め出される**
- **役割の既定は「何もできない」**（bool は偽、役割は NULL）。安全側である
- **最初の 1 人に `is_sysadmin` を立てる手順が要る。** 新しい DB では、サーバを 1 度起動して
  `admin` を作らせてから付与する。手順は [seed/README](../../Designer/seed/README.md)、
  開発機のデモ用アカウントは [ADR-0031](0031-デモ用の利用者アカウントは開発用のseedに置く.md) の `dev/`
- **`AppUser` モジュールのフィールド名は日本語のまま**（認証部品の資産）。
  新しい 4 本は本プロジェクトが足すので PascalCase 英語にする（`Designer/Project.md` の命名規約）
