# ADR-0001 会計コア単体を部品として作る

> **2026-08-27 追記**: [ADR-0025](0025-取引先を部品として分ける.md) により、本プロジェクトの中で
> 作ってきた取引先マスタを独立のアプリ部品に格上げした。作る機能の範囲は広がっていない
> （既存実装の再包装。ADR-0025 §7）が、決定の「1 部品のみ」と理由の「依存の向きが常に
> 『他部品 → 会計コア』」は当時の姿である。現在の依存規則は
> [ADR-0024 §4](0024-部品の分割は束ねる相手抜きで使われる場面があるかで決める.md)。
> **会計コアを完璧に作り、周辺業務を作らないという芯は変わっていない。**

## 状況

前回プロジェクト（`BusinessApp_old`）は「財務会計を中心に、経費精算・販売・購買・工数管理まで
全部入り」を目標にした。結果として各領域が相互依存し、切り離せなくなり、バグが大量に入り込んで
収拾がつかなくなった。

一方で Codeer.LowCode.Blazor（CLB）の売りは、機能を単一責任で小さく分け、レゴブロックのように
組み合わせられることである。前回の作り方はその売りと逆行していた。

## 決定

**本プロジェクトで作るのは「会計コア」1 部品のみとする。** 会計コアだけを、他の会計ソフトの
代替として通用する水準まで作り込む。

目的は次の 3 つを同時に満たすことである。

1. **CLB の技術デモ** —「CLB でここまで作れる」
2. **実用**（対象ペルソナが freee 等の代替として実際に使える）
3. **部品**（他の部品と組み合わせて製品化できる形で作る）

会計コアの外にある業務（経費精算・販売・購買・工数・承認フロー・証憑管理など）は、
**本プロジェクトでは作らない**。必要になれば別の部品として、別のプロジェクトで作る。

## 理由

- 「相互依存で切り離せなくなる」ことが前回の最大の失敗要因であり、その原因は
  **同時に複数領域へ着手したこと**にある。1 部品に絞れば構造的に発生しない
- 会計コアは他部品に依存しない（依存の向きが常に「他部品 → 会計コア」）ため、
  最初に作る部品として適している
- 「完璧に作る」は範囲を絞らないと成立しない。会計ソフトは正しさの証明コストが極めて高く、
  範囲が広がるほどテスト資産が薄まる

## 帰結

- **スコープ拡大の圧力に対しては、原則として「別部品」と答える。** 例外を認めるのは
  ADR で明示的に判断したときだけ（[ADR-0024](0024-部品の分割は束ねる相手抜きで使われる場面があるかで決める.md) の基準に従う）
- 対象ペルソナが使う機能であっても、**会計コアの責務でないものは含めない**
  （例: 経費精算の申請画面。ただし「経費精算部品が投入した仕訳を受け入れる」ことは会計コアの責務）
- 他部品との連携点（仕訳の投入 API・外部伝票を特定する情報の保持）は、
  **利用者が居なくても最初から設計に含める**。これは会計コアが部品であるための条件だからである
- 「会計コアだけでは製品にならない」は承知のうえで進める。製品化は複数部品の組み合わせで行う
