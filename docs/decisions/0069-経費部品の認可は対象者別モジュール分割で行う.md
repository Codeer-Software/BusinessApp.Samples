# ADR-0069: 経費部品の認可は対象者別モジュール分割で行う

- 日付: 2026-08-17
- 状態: 採用（実装中）
- 起点: BUG-0211 / BUG-0212 / BUG-0213 / BUG-0233。一般社員が他人の経費申請・明細
  （領収書ファイル込み）・承認フローを**読めて書ける**。実測で `/api/module_data/list` が
  認証済みなら誰にでも任意 id の他人レコードを 200 で返した

## 前提の確認（よくある誤解）

**CLB はサーバー側で認可を判定している。** `Submit` 受信時に強制するので、スクリプトから
`Module.Submit()` を呼んでも回避できない（`_specs/ModuleDesign.md:162-163`）。
**穴が開いているのは機構が無いからではなく、条件を書いていないから**である
（`"ModuleName": ""` ＝条件なし＝全許可）。経費部品の 6 モジュールは 4 条件すべてが空だった。

## CLB の認可条件でできること・できないこと

認可条件は 4 つあるが、性質は 2 種類しかない。

| つまみ | 見る対象 | 決めること |
|---|---|---|
| `UserReadCondition` / `UserWriteCondition` | **ログイン中ユーザー自身**（`AppUser`）の列 | この人はこのモジュールに触れてよいか＝**人単位のゲート** |
| `DataReadCondition` / `DataWriteCondition` | **自モジュールの列だけ**。右辺に `CurrentUser.Id.Value` を置ける | この人はどの行を扱えるか＝**行単位のフィルタ** |

**2 つは AND でしか結合しない。** よって経費に本来かけたい
「自分が申請した ∨ 自分が今の承認者 ∨ 経理なら全部」という **OR は 1 モジュールでは書けない**。
`Exists` / `NotExists` は SQL の `EXISTS` ではなく単なる非 NULL 判定なので、
親を辿る副問い合わせの逃げ道も無い（`_specs/SearchConditions.md:283-284`）。

## 決定

**同じテーブルに対象者別のモジュールを複数定義し、各モジュールに「人ゲート AND 行フィルタ」を
1 組ずつ与える。和（OR）はモジュール分割で作る。**

これは本アプリが既に採っている作法である（`MyApplication` / `ApprovalInbox` / `TimeEntryAdmin`）。
穴が開いているのは、この作法を経費部品に徹底していない箇所である。

| 対象 | 人ゲート | 行フィルタ |
|---|---|---|
| 申請者用 | なし（全員） | `Creator == CurrentUser.Id` |
| 承認者用 | `IsApprover == true` | 自分が承認者である申請だけ（ビュー経由・下記） |
| 経理用 | `HasAccountingAccess == true` | なし |

副次的な効き目として、**更新・削除は読み取り権限を要求する**ので（SQL の `UPDATE` に `WHERE` が
あるとき `SELECT` 権限も要る、と同じ規則）、読みを絞れば書きも自動的に絞られる。

### 明細行には `creator` 列を足す

`expense_request_lines` の 19 列に人を指す列が無く、親 FK が `IdFieldDesign` なので
リンク越しの条件も書けない。**`creator` 列を追加してバックフィルする。**

### 承認者の行フィルタはビューで作る

`approval_inbox_view` と同型で `expense_request` を結合したビューを作り、
`current_approver == CurrentUser.Id` を「自モジュールの列」に見せる。
SQLite のビューは読み取り専用だが、本アプリには `active_app_users` への INSTEAD OF トリガの前例がある。

**非正規化列を持つ案は却下した。** `approval_flow.current_approver` は
`ApprovalFlow.mod.cs:529` で待ちメンバーの先頭 1 人しか入らず、
OR 承認（`ApprovalType="any"`）の第 2 承認者を締め出す。この列を `expense_request` に写せば
同じ欠陥を持ち込むことになる。

## 案Aで表現できない一点（ユーザー指示により記録する）

**承認フローの明細 3 テーブル（`approval_flow_order` / `approval_flow_member` /
`approval_history`）を「その申請の承認に関わっている人だけ」に絞る行フィルタは、案Aでも書けない。**

理由は 2 つ:

1. `approval_flow_order` に**人を指す列が 1 つも無い**。行フィルタの材料が存在しない
2. `approval_flow_member.approver_user_id` は自分の行しか指さないが、
   **OR 承認は仲間の行を `Skipped` に更新する**。「自分の行だけ書ける」に絞ると承認そのものが動かない

したがってこの 3 テーブルは、**人ゲート（`IsApprover == true` ∨ 経理）までで止める。**
一般社員の自己承認は塞がるが、**承認者どうしの越権（担当外の申請を承認する）は条件では塞げない**。
これは承認履歴（`approval_history`）で追跡する統制に委ねる。
完全に塞ぐならサーバ拡張（案B）が要るが、**この一点のためだけに C# を持ち込むかは別途判断する**。

## 実装上の落とし穴（実査で確定した事実・踏むと必ず壊れる）

1. **`ExpenseRequest` に `Creator == CurrentUser` の `DataWriteCondition` を入れた瞬間に承認が壊れる。**
   承認・却下・取消・再承認はすべて `GetParentModule().Submit()` で親を UPDATE している
   （`ApprovalFlow.mod.cs:985 / 1144 / 1238 / 1272`）。承認系の書き込みは承認者用モジュール経由に
   付け替える
2. **承認フロー系の `UserWriteCondition` を承認者に絞ると申請提出が壊れる。**
   提出は `approval_flow` を UPDATE し `order`/`member`/`history` を INSERT する単一カスケード
   （`ApprovalFlow.mod.cs:789-834`）。**行条件は新規追加に効かないが、人ゲートは新規追加にも効く**
3. **埋め込み子は権限不成立で「エラーにならず静かに空」になる**（`_specs/ModuleDesign.md:141-149`）。
   明細が消えても画面は正常に見えるので、分割は 1 段ずつ実機で確認する
4. **承認者用・経理用を `ExpenseRequest` の複製にしない。** JSON 4,215 行・スクリプト 1,427 行を
   3 重管理することになる。承認者用は「ヘッダ読取＋明細読取＋承認欄」、経理用は
   「経理ボタン＋仕訳生成」に絞った薄いモジュールにする
5. **却下は `settlement_status` を `draft` に戻す**（`ExpenseRequest.mod.cs:696-699`）。
   行条件を前像で見るか後像で見るかは仕様書に記載が無いので、却下できるかは実機で確かめる

## 実装の結果（2026-08-18）

段階 1〜8 をすべて実装し、実機で確認した。**サーバ拡張（案B）は採らない**という開発者判断
（2026-08-18）に従い、CLB の条件式で書ける範囲で締めている。

| 段階 | 実装 | 実機 |
|---|---|---|
| 1-2 明細に `creator` と行条件 | 済 | ○（ただし**書き込み条件が見る列を画面に読み込ませる**必要があった＝BUG-0323） |
| 3-4 経理用モジュール | 済 | ○ |
| 5 申請者用に行条件（読み＋書き） | 済 | ○ 一般社員の一覧が 14 件 → 自分の 7 件に。他人の id を直打ちしても中身が出ない |
| 6 承認者用モジュール | 済 | ○ 明細が見える・承認/却下/取消が保存される |
| 7 承認フロー 3 テーブルの人ゲート（`CanUseExpense`） | 済 | 提出のカスケードが通ることを確認 |
| 8 フレーム整理 | 済 | `designcheck` 0 |

**閉じた P0**: BUG-0048 / 0213 / 0234。

**閉じなかったもの（CLB の条件式では書けない）**:
- **承認者どうしの越権**（担当外の申請を承認できる）= BUG-0211 / 0212
- **承認者が担当外の申請の明細を読める** = BUG-0322

`CanUseExpense` の人ゲートで弾けるのは、実データでは **`admin` だけ**である
（ほかの有効ユーザーは全員 `can_use_expense=1`）。それでも張る価値はある——
将来「経費を使わないユーザー」を作ったときに自動で締まるし、
**設計の意図をデザインファイルに残せる**（条件が空だと「まだ考えていない」と区別がつかない）。

残る越権は**承認履歴による事後追跡**に委ねる。塞ぐにはサーバ拡張が要るが、
「この一点のために C# を持ち込むか」は**採らない**と決めた（ミッションの CLB 最優先を優先）。

> 補足: 人ゲートを `CanUseExpense` にしたのは、**提出のカスケードを申請者が通す必要がある**ため。
> `IsApprover` にすると申請者が `approval_flow_order` / `member` / `history` を INSERT できず、
> **申請そのものが動かなくなる**（行条件は新規追加に効かないが、人ゲートは効く）。
> 承認エンジンを経費以外（休暇申請など）へ広げるときは、この人ゲートを
> 「経費」ではなく「この承認エンジンを使ってよい人」の意味に読み替える必要がある。

## 帰結

- 参照差し替えは最小構成で **22 系統**（JSON 8・スクリプト 11・PageFrame 3）
- `parent_module_name` は DB に保存された値（常に `"ExpenseRequest"`）なので、
  申請者と承認者で遷移先モジュールを変える写像は**スクリプトで書く**しかない
  （`ApprovalInbox.mod.cs:17` / `MyApplication.mod.cs:15` / `ApprovalFlow.mod.cs:812`）
- この決定は経費部品で先に完成させ、**他部品（購買・営業）の同型の穴へ横展開する型とする**
