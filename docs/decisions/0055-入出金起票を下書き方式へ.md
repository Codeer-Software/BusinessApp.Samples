# ADR-0055: 入出金起票を「下書き＋一括起票」方式へ改める

- 日付: 2026-08-14
- 状態: 採用・実装済み（実機検証 2026-08-14。**決定 4 は実装中に修正した**——下記「決定 4」参照）
- 関係: ADR-0012（銀行明細取込＝ステージング方式。**本 ADR はその方式を再利用する**）／
  ADR-0026（確定済み伝票は編集・削除できない）／ADR-0053（入出金起票の消費税行生成）／
  ADR-0056（部門の必須化。入出金起票にも部門欄が要る）／
  `docs/tests/20_体験シナリオ/06_会計_仕訳と帳簿/04_定型仕訳と入出金起票.md`

## 背景: 「入力フォーム」であって「帳簿」ではない

入出金起票は、日付・現預金科目・入出金・相手科目・金額・摘要を入れて「起票する」を押すと、
**下書きを経ずにその場で確定仕訳を作る**画面である。会計ソフトとして見ると 3 つの弱点がある。

### 1. 打ち間違いを直す手段が赤伝しかない

市販ソフトの出納帳入力は「**一覧そのものが入力欄**」で、残高が横に走り、打った行をその場で直せる
（弥生会計・マネーフォワード・勘定奉行の出納帳入力、freee の取引登録）。本アプリは入力専用フォームで、
しかも確定まで一気に進むため、訂正は赤伝しかない。**小口現金のように打ち間違いが多い領域で最も痛い差**である。

### 2. 現預金科目の候補が JSON にハードコードされている

`CashEntry.mod.json` の `Candidates` に `現金,1000` / `小口現金,1010` / `普通預金,1020` が直書きされている。
勘定科目マスタに口座科目（例: 普通預金(B銀行)）を足しても**この画面には出てこない**。
CLAUDE.md §3 の「税率・税区分・閾値・勘定科目などはマスタ化してハードコードしない」に反している。

### 3. 相手科目に現預金科目が並ぶ

相手科目のドロップダウンは有効な全勘定科目で、`普通預金 → 普通預金` のような無意味な仕訳も作れる。

> なお ADR-0053 で「相手科目の候補を**税区分で**絞る案」を採らなかったのは、CLB の `SearchCondition` が
> 関連先の関連先（`accounts` → `tax_categories.taxation_type`）を条件にできないためである。
> **`accounts` 自身の列でなら絞れる**ので、本 ADR の決定 2 は当時の判断と矛盾しない。

## 決定 1: 下書き行テーブルを持ち、一括起票する

**銀行明細取込（ADR-0012）と同じステージング方式にする。** 入力しても即座には仕訳を作らず、
下書き行として溜め、「起票する」でまとめて仕訳に変換する。

| 論点 | 決定 | 理由 |
|---|---|---|
| 下書きの置き場 | **DB のテーブル**（`BankStatementLine` と同じ） | 画面を離れても消えない。打ちかけて離席しても失わない |
| 行が持つもの | 日付・現預金科目・入出金・相手科目・**部門**・金額・摘要を**1 行が全部持つ** | どんな入出金でも積めるようにするため。科目や方向を揃える制約は付けない |
| 伝票の単位 | **下書き 1 行 = 仕訳 1 本** | 日付も相手科目も違う行を 1 伝票にまとめる理由がない。銀行の一括起票も明細ごとに 1 伝票 |
| 採番のタイミング | **一括起票の実行時**（行ごとに採番） | 下書きの時点では番号を持たない |
| 起票時のエラー | 行ごとに判定し、締め済み・年度なし等は**その行だけスキップ**して結果に件数を出す | 銀行の「起票 n 件 / スキップ n 件 / 失敗 n 件」と同じ |
| 税行 | 従来どおり行ごとに 1 回だけ生成（ADR-0053） | 下書きを経ても税行の生成は確定の 1 回きり、という規律は変わらない |

画面上部の「日付・現預金科目・入出金」は**フォームの状態ではなく「次に足す行の初期値」**になる。
現行の「起票後も相手科目が残る」連続入力の工夫は、下書き方式では
**「直前の行をコピーして新しい行を足す」**で実現する（弥生の出納帳も直前行の日付を引き継ぐ）。

一覧は科目を混ぜて全行表示し、現預金科目を**列**として持つ。科目で絞る検索は付けるが**既定は全表示**——
絞りを既定にすると「打ったはずの行が見えない」事故が起きる。

## 決定 2: 下書き行は作成者を持ち、自分の行だけを見る

**銀行明細と下書き行は性質が違う。**

| | 銀行明細（`BankStatementLine`） | 入出金の下書き行 |
|---|---|---|
| 実体 | 銀行から取り込んだ**事実**。会社の共有物 | 誰かが**打ちかけているメモ**。個人の作業領域 |
| 他人が触ってよいか | よい（誰が起票しても同じ結果） | **だめ**（A さんが確認中の行を B さんが確定してしまう） |

ペルソナ（従業員 30〜80 名）では「小口現金は総務、預金は経理主任」のような分担が普通に起こるため、
「同時に 1 人しか操作しない」前提は採らない。**下書き行に作成者を持ち、自分の行だけを表示・起票する。**

副作用として、**打ちかけたまま長期離脱した人の行を誰も掃除できない**。
対策はポータルの経理作業キューに「▶ 未起票の入出金: N 件」を**全社分**で出す（存在は見える）に留める。
掃除が必要になったら「全員の未起票を表示」チェックを後から足せばよく、最初から作り込まない。

## 決定 3: 残高は「基準時刻付き」と「起票後の見込み」の 2 段で出す

**「常に正しい今の残高」は原理的に作れない**（他人が同時に打てば変わる）。これは市販ソフトも同じで、
出納帳の残高は画面を開いた時点のスナップショットである。重要なのは**表示が古いことに気づけること**なので、

```
小口現金   帳簿残高              80,000 円 （15:30 現在）  [更新]
           この下書きを起票すると  78,900 円 （-1,100）
```

- **基準時刻を添える**。起票直後は自動で取り直す
- **見込み残高を併記する**。小口現金の実査は「金庫の現物と帳簿を合わせる」作業なので、
  実務で見たいのは「今日の分を記帳し終えたらいくらになるか」＝下段。**市販ソフトに無い親切**であり、
  下書き方式にするからこそ出せる値

## 決定 4: 現預金科目をマスタで決める（相手科目は「同じ科目だけ」禁じる）

勘定科目マスタ（`accounts`）に**現預金科目フラグ**（`is_cash_equivalent`）を持たせ、
**現預金科目の候補をフラグ true の科目から引く**（JSON の `Candidates` ハードコードを廃止）。
対象は C/F 計算書が「現金及び現金同等物」として扱う 1000〜1099 帯と同じ 4 科目
（現金・小口現金・普通預金・**定期預金**）。口座科目を増やしてもフラグを立てるだけで画面に出る。

> **当初案の修正（実装中に判明）**: 「相手科目からは現預金科目を**すべて**除く」と書いていたが、
> これは誤りだった。**現預金どうしの振替が実務で頻出**する——小口現金の補充（普通預金 → 小口現金）は
> E2E 基本シナリオ 4-6 の題材そのもので、定期預金への預け入れも同じ形になる。全部除くとこれらが
> 永久に処理できなくなる。
>
> 無意味なのは「**現預金科目とその相手科目が同じ**」ケース（普通預金 → 普通預金）だけなので、
> **候補は絞らず、追加・起票の検証で同一科目を弾く**（「相手科目に同じ現預金科目は選べません」）。
> 候補を絞る代わりに検証で止める形は ADR-0053 で採った判断と同じ筋である。

## 決定 5: 部門を持たせる（ADR-0056 の適用）

下書き行は部門を持ち、**相手科目が損益科目なら部門を必須**にする（追加時にエラーで止める）。
仕訳に落とすときは**損益科目の行にだけ**部門を刻み、BS 側（現預金行）と税行は
`JournalEntry.FillMissingDepartments()` の保険が埋める（税行は親行から継承）。

## 確定後の取消は本 ADR のスコープ外にする

検討の過程で「直前の起票を取り消すボタン（対象の仕訳を削除）」を先に作る案があった。
このアプリは既に **4 経路（仕入先請求書の未払計上取消・支払取消、銀行明細の起票取消、入金消込の取消）で
「業務操作の取消＝仕訳を削除」を実装している**ので、入出金起票にも同じ形を持たせること自体は規律に沿う。

しかし**下書き方式にすると、起票前に何度でも直せるため確定後に消したいケースが激減する**。
先に取消を作ると履歴リストを 2 回作ることになるので、**下書き方式を先に入れ、取消は必要になってから**とする。
実装する場合の条件も検討済みなので記録しておく——経理のみ／**仕訳の期間がオープンなときだけ**
（締め済みなら赤伝に誘導）／確認ダイアログ／対象は履歴一覧から選ばせる（`source_type='cashbook'` には
`source_id` が無いため「直前」を機械的に特定できず、最新 1 件を拾う実装は他人の仕訳を消しうる）。

## 採らなかった案

- **下書きを全員で共有する（銀行明細と同じ扱い）**: 打ちかけを他人が確定する事故が構造的に起きる
- **下書きをセッション（メモリ）で保持する**: 離席・リロード・画面遷移で消える。
  打ち間違いに気づくのは残高照合のときで、それは別の日になることが多い
- **確定後の取消ボタンだけを足して現行フォームを維持する**: 上記のとおり二度手間になる
- **相手科目を税区分（非課税・不課税・対象外）で絞る**: ADR-0053 で却下済み。
  「会議費を現金で払った」という普通の取引が処理できなくなる

## 影響

- **体験シナリオ 06-04 のステップ 6〜10 が全面書き換え**になる。E2E の CSH-01〜05 も同様
- 「起票する」を押した瞬間に採番される、という現行の性質が変わる（**一括起票時に採番**）
- 下書きテーブルの DDL 追加。既存の仕訳データへの影響は無い（移行不要）

## 実装で分かったこと（「実装時に確認すること」の結果）

1. **行追加は `CanCreate` を使わず、入力欄＋「明細に追加」ボタンにした。** ユーザーの想定
   （「入力しても即仕訳にならず、下にプレビューとして積まれる」）とも一致し、追加前に検証を挟めるため。
2. **自分の行だけに絞るのは `Variable: "CurrentUser.Id.Value"` 一発でよかった**——隠しフィールドは不要。
   `FieldVariableMatchCondition` が「現在ログインユーザー」を直接参照でき、これは CLB の標準機能。
3. **見込み残高は軽い。** 帳簿残高は専用のクエリモジュール（`CashBalance`）が SQL 側で集計し、
   下書きの増減は画面が持っている行から足すだけなので、`OnDataChanged` ごとの再計算で問題なかった。
   **クエリモジュールの行にスクリプトから値を書くと、そのまま表として描画される**（未検証だったが動いた）。
4. **`ListField` の行削除は DB に届かない**（メモリ上の操作）。「変更を保存」で
   DB 側と画面側の行を突き合わせ、消えた行を明示的に `Delete()` する形にした（FB-040）。
5. **`ref` / `out` 引数は呼び出し元に伝わらない**（例外も出ない）。消費税額の受け渡しが黙って 0 になり、
   モジュールレベル変数に変更した（FB-039）。
6. **日付列は `DATE` で宣言する。** `TEXT` で作ると CLB が `08/14/2026` 形式で書き込み、
   SQLite の `date()` が NULL を返して SQL 側が静かに壊れる（FB-041）。

## 実機検証（2026-08-14 / soumu_bucho）

| 確認 | 結果 |
|---|---|
| 現預金科目の候補 | マスタのフラグから 4 科目（現金・小口現金・普通預金・定期預金）。ハードコード廃止を確認 |
| 部門ガード | 会議費（損益）で部門なしのまま「明細に追加」→「部門を選択してください（損益科目の仕訳には部門が必要です）」でブロック |
| 連続入力 | 追加後に**金額と摘要だけ**クリアされ、日付・科目・入出金・部門は残る。フォーカスは金額へ戻る |
| グリッド編集 | 金額 1,100 → 3,300 に直して「変更を保存」→ DB に反映（3,300） |
| 行削除 | ゴミ箱で消して**保存すると DB からも消える**（「変更を保存しました（1 行を削除）」）。保存前に再読込すると復活する＝仕様どおり |
| 残高の 2 段表示 | 小口現金 帳簿 100,000 ／ 未起票 −1,100 ／ 見込み 98,900。基準時刻付き |
| 一括起票 | 「起票 1 件（No.89〜89） ／ うち消費税 100 円 ／ スキップ 0 件 ／ 失敗 0 件」 |
| 生成仕訳（会議費 1,100・課税仕入 10%） | D 小口現金 1,100（対象外・全社共通）／ C 会議費 1,000（課税仕入・**開発1部**）／ C 仮払消費税 100（税行・**開発1部**＝親行から継承）。貸借一致 |
| 起票後 | 下書きは 0 件になり、残高が確定側に移る |

検証で作った伝票・下書きは削除済み。**DB はクリーン**（仕訳 202 行・76 伝票・部門なし 0 行・下書き 0 件）。
