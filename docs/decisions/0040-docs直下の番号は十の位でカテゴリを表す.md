# ADR-0040 docs 直下の番号は、十の位でカテゴリを表す

## 状況

`docs/` 直下で番号を持つ 18 のエントリ（`.md` が 16 本と、ディレクトリが 2 つ）は、
**足した順の連番**で番号を持っていた。
その結果、番号と内容が入り乱れた——09 と 10 と 15 が「原則」、04 と 06 と 07 と 08 が「設計」、
16 と 17 が「ルール」で、間に企画・進行管理・適合の証明が挟まっていた。

**[docs/README](../README.md) の地図は、改番前まで「番号は連番であって読む順ではない。役割で読む。」と
断り書きを置いていた**（本 ADR で書き換えたので、いまは残っていない）。
番号から役割が引けないので、毎回いちばん上の索引を開かないと、どの文書が何を持つのか分からなかった。
**この断り書き自体が、番号が役に立っていない証拠だと読んだ**（Claude の判断）。

**放置するほど高くつく。** 文書を指す参照は追跡下の 196 ファイルに散っており、
文書が増えるたびに改番の代金も上がる。

## 決定

**十の位をカテゴリにする**（開発者の決定。2026-09-06。
**番号と内容が入り乱れていて、番号から役割が引けなかったから**）。
帯は **0x 全体・1x 設計・2x 原則・3x ルール・4x 適合・8x 参照・9x その他**の 7 つ。

**帯の中身の定義と番号の付け方は [00 §8](../00_ドキュメント規約/README.md) が持つ。**
ここに写さない——**規則が育った日に ADR だけが嘘になる**からである
（ADR は書き換えない文書。[00 §3-3](../00_ドキュメント規約/フロントマター.md)）。

**開発者が決めたのは次の 5 つである。**

1. 十の位をカテゴリにすること
2. **参照（8x）を後ろに置き、9x を「その他」の受け皿にすること**（開発者の指示）
3. **`CLB改善提案/` から番号を外すこと**（開発者の指示。「番号をなくすのがベストの気がします」）
4. 0x の中身（規約・企画・ペルソナ・スコープ・現在地）
5. **4x「適合」を新設すること**（下の節。開発者が「それ用のカテゴリを新たに作るべきではないか」と問い、
   Claude が文書の主旨を調べて答え、開発者が「新設してください」と決めた）

**それ以外の細部は Claude が決めた**——各文書をどの帯のどの番号に置くか、帯の中の並び、
[00 §8-1](../00_ドキュメント規約/README.md) の採番規則。**開発者は未承認である。**

### 4x「適合」を新設した理由

**優良な電子帳簿の対応表は、設計でも検証でもない。**
制度の事実の正典は電帳法リサーチ、設計の正典は 10・11・12、実機確認の記録は qa/04 が持つ。
この文書が持つのは「国税庁の要件 → 製品のどの機能が満たすか」の 1 対 1 の対応、
つまり**外部の要求と成果物のトレーサビリティ**だけである。
§5「この表を書いて決めたこと」で設計判断が落ちてくるのは副産物である
（実例は 40 §5-1——計上前の下書きを保存等の対象から外す当てはめは、この表を書く過程で出た）。

既存のどの帯にも入らないので、帯を作った。将来ここに入りうるのは、
インボイス制度の適合表、法人税・所得税の帳簿要件の対応表など。

## 理由

- **番号から役割の見当がつく。** 地図を開かずに当たりを付けられる
- **新しい文書の置き場所が自明になる。** 「どの帯か」を先に決めれば番号は決まる
- **帯そのものが成長の余地である。** 帯の中は連番で空けない

## 代償

**カテゴリが動いたら番号も動く。** 連番にはこの引っ越しコストが無い。
今回買ったのは「並び順の分かりやすさ」で、代金は**1 文書を別の帯へ移すたびに数十〜百数十か所の書き換え**である
（実績は下の追記）。

だから**一度きりにするための条件**を [00 §8-1](../00_ドキュメント規約/README.md) に付けた。
条件の中身はそちらが持つ（**ここに写すと、規則が育ったとき ADR だけが嘘になる**。
ADR は書き換えない文書である——[00 §3-3](../00_ドキュメント規約/フロントマター.md)）。

## 実施のしかた（記録）

**危ないのは「番号だけで指す形」である。** 札に `04 §5` と書いて
`04_会計ドメイン設計.md` へ張った参照は、改番でファイルが消えるのでリンク検査が鳴る。
鳴らないのは `docs/04 §1`・`04 §5` のような短縮形で、
**旧番号が実在する別の文書に着地するため、リンク検査も節の実在検査も素通りする。**
そこで次の順で守りを作ってから改番した。

1. **参照の形を実データから全数洗い出した**（推測でパターンを並べない）。
   書き方は 5 系統あり、そのうち**裸の番号**（`08 が現在形を持ち`）は
   形では文書参照と判定できない——`節が 15 を超えたら` と区別が付かないため。
   **候補を全部あぶり出して 1 件ずつ読み、参照か数量かを判定した**
2. **参照を「番号ではなく題名」で解決した表**を作った。題名は改番で動かないので、
   正しく書き換えられていれば表は 1 行も変わらない。これを 14 回の改番すべてで突き合わせた
3. **`lint_docs.py` の節参照検査を、リンクを張れない 3 つの形まで広げた**
   （`docs/10 §1`・`docs/21_画面の原則.md §2`・`21 §3`。それまで 400 件以上が素通りだった）。
   指し先は作業ツリーの実体から引くので、**その番号の文書が無ければ鳴る**——
   ただし鳴るのは**上の 5 形で書かれた参照のうち、検査の対象ファイルにあるもの**に限る
   （[00 §6](../00_ドキュメント規約/README.md)）。
   `08 が現在形を持ち` のような**散文の裸の番号は、どの形にも当たらないので鳴らない**
4. **1 文書 1 コミット**。番号の衝突を避けるため、
   **空いている番号へ先に逃がしてから、空いた番号を埋める**順にした
   （2x → 3x → 4x → 8x → 番号なし → 1x → 0x）

**`Designer/migrations/` は触っていない。** 適用済みのマイグレーションは
`migrate.ps1` が SHA-256 で照合し、1 バイトでも変わると「適用後に編集されている」と移行を拒む
（[ADR-0020](0020-スキーマは現在形の正典で持ち変更は差分で配る.md)）。
**だからあの 10 本には旧番号のコメントが残る。それが正しい。**
`lint_docs.py` も同じ理由でここを検査から外している。
**自己レビューで見つかった**——改番の道具は「追跡下のテキスト全部」を見ており、
凍結という概念を知らなかった。**解決表の突合はここを鳴らせない**（表から見れば正しく書き換わっているため）。

**`qa/` の記録文書の中の番号も、遡って書き換えた。** 規則の本体は [00 §3-3](../00_ドキュメント規約/フロントマター.md) が持つ
（`qa/` の扱いは本 ADR の回に足した。**Claude が提案し、マージの前に開発者が承認した**）。
`qa/02_自己レビュー記録.md` だけで 158 行が書き換わっている。

**サブエージェントに解決表そのものを敵対的にレビューさせた**（開発者の指示。2026-09-06。
**機械的チェックに漏れがあれば全て漏れるから**）。重大な穴が 3 件見つかった——
判定表が桁を持たず同じ行の `R18-08` まで書き換えていた（しかも検算は緑のまま通る）、
番号から題名を引く表が静的で改番後に別文書へ解決していた、
同じ字を 2 系統が拾って置換が必ず衝突していた。
**どれも改番を始めてからでは気づけない形だった。**

> **2026-09-06 追記**: **自己レビューの指摘を受けて、調査の原則を 2x から 3x へ移した**（15 回目の改番）。
> **21 ファイル・40 か所**。あわせて**題名を「調査のルール」に改めた**（58 か所）——
> 3x に置いて題名が「原則」のままだと後から混乱するため（どちらも開発者の決定）。
> **これが「1 文書を別の帯へ移す代金」の実測値である。**
> 上の「14 回の改番すべてで突き合わせた」は本文を書いた時点の回数で、いまは 15 回である。
