# ADR-0040 docs 直下の番号は、十の位でカテゴリを表す

## 状況

`docs/` 直下の 18 文書は、**足した順の連番**で番号を持っていた。
その結果、番号と内容が入り乱れた——09 と 10 と 15 が「原則」、04 と 06 と 07 と 08 が「設計」、
16 と 17 が「ルール」で、間に企画・進行管理・適合の証明が挟まっていた。

**[docs/README](../README.md) の地図が「番号は連番であって読む順ではない。役割で読む。」と
断り書きを置いていたのが、その敗北宣言である。** 番号から役割が引けないので、
毎回いちばん上の索引を開かないと、どの文書が何を持つのか分からなかった。

**放置するほど高くつく。** 参照はこの時点で 197 ファイル・のべ 2,300 か所を超えており、
文書が増えるたびに改番の代金も上がる。

## 決定

**十の位をカテゴリにする。**

| 帯 | 意味 |
|---|---|
| **0x** | 全体 — 文書そのものの約束と、プロジェクトの輪郭と現在地 |
| **1x** | 設計 — 何がどうあるべきか（What） |
| **2x** | 原則 — 成果物が満たすこと |
| **3x** | ルール — Claude がどう動くか |
| **4x** | 適合 — 外部の要求と、自分たちの成果物の対応づけ |
| **8x** | 参照 — 通読せず、必要なときに 1 本だけ開くもの |
| **9x** | その他（空。受け皿） |

**番号を付けるのは「読む文書」だけ**とし、`CLB改善提案/` からは番号を外して
`decisions/`・`research/`・`qa/` と同じ「たまっていくもの」に揃えた。

規則の本体は [00 §8](../00_ドキュメント規約/README.md) が持つ（帯の定義・番号の付け方）。

### 4x「適合」を新設した理由

**優良な電子帳簿の対応表は、設計でも検証でもない。**
制度の事実の正典は電帳法リサーチ、設計の正典は 10・11・12、実機確認の記録は qa/04 が持つ。
この文書が持つのは「国税庁の要件 → 製品のどの機能が満たすか」の 1 対 1 の対応、
つまり**外部の要求と成果物のトレーサビリティ**だけである。
§5「この表を書いて決めたこと」で設計判断が落ちてくるのは副産物で、
落ちた判断は ADR へ出ていく（[ADR-0037](0037-計上済みの伝票は画面でも計上時の姿を見せる.md) が実例）。

既存のどの帯にも入らないので、帯を作った。将来ここに入りうるのは、
インボイス制度の適合表、法人税・所得税の帳簿要件の対応表など。

## 理由

- **番号から役割の見当がつく。** 地図を開かずに当たりを付けられる
- **新しい文書の置き場所が自明になる。** 「どの帯か」を先に決めれば番号は決まる
- **帯そのものが成長の余地である。** 帯の中は連番で空けない

## 代償

**カテゴリが動いたら番号も動く。** 連番にはこの引っ越しコストが無い。
今回買ったのは「並び順の分かりやすさ」で、代金は「将来 2,300 か所の書き換え」である。

だから**一度きりにする条件**を [00 §8-1](../00_ドキュメント規約/README.md) に付けた——
帯を増やさない、「その他」が 2 本を超えたら分類を見直す、
番号を動かすときは [§4-12-1](../00_ドキュメント規約/本文.md) の手順で参照を洗う。

## 実施のしかた（記録）

**旧番号は別の実在文書に着地するので、機械のリンク検査も節の実在検査も鳴らない。**
`docs/04 §1` は改番後も「実在する別の文書の §1」を指してしまう。
そこで次の順で守りを作ってから改番した。

1. **参照の形を実データから全数洗い出した**（推測でパターンを並べない）。
   5 系統に整理でき、そのうち**裸の番号**（`08 が現在形を持ち`）は
   形では文書参照と判定できない——`節が 15 を超えたら` と区別が付かないため。
   候補 215 件を 1 件ずつ読んで判定した
2. **参照を「番号ではなく題名」で解決した表**を作った。題名は改番で動かないので、
   正しく書き換えられていれば表は 1 行も変わらない。
   これを 14 回の改番すべてで突き合わせた（2,334 行が完全一致）
3. **`lint_docs.py` の節参照検査を、リンクを張れない 3 つの形まで広げた**
   （`docs/10 §1`・`docs/21_画面の原則.md §2`・`21 §3`。それまで 400 件以上が素通りだった）。
   指し先は作業ツリーの実体から引くので、**番号が消えたときの取り残しは必ず鳴る**
4. **1 文書 1 コミット**。番号の衝突を避けるため、
   **空いている番号へ先に逃がしてから、空いた番号を埋める**順にした
   （2x → 3x → 4x → 8x → 番号なし → 1x → 0x）

**サブエージェントに解決表そのものを敵対的にレビューさせた**（開発者の指示。2026-09-06。
**機械的チェックに漏れがあれば全て漏れるから**）。重大な穴が 3 件見つかった——
判定表が桁を持たず同じ行の `R18-08` まで書き換えていた（しかも検算は緑のまま通る）、
番号から題名を引く表が静的で改番後に別文書へ解決していた、
同じ字を 2 系統が拾って置換が必ず衝突していた。
**どれも改番を始めてからでは気づけない形だった。**
