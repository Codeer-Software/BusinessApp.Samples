# ADR-0065 UI 改善は CLB の標準の範囲で行い、「必ず行う作業」ができないときだけ外へ出る

## 状況

**「利用者にとって使いやすいか」を測る仕組みが工程に無かった**（開発者の指摘。2026-09-18）。
[21](../21_画面の原則.md) は画面 1 枚の中の作法、台本（[qa/04 §3](../qa/04_実機操作テスト.md)）は機能ごとの「拒む・見せる・残る」（Claude の要約）、
探索的テストは「壊す」向きで、**「経理担当として普通に 1 か月使えるか」はどれも測っていない**。
[02](../02_ペルソナ.md) にも、利用者が日次・月次・年次に何をどの頻度で行うかは書かれていなかった。

物差しを作るなら、**どこまで直すか（水準）と、何を使って直してよいか（範囲）**を先に決めないと、
直すたびに迷う。とくに範囲は、いまの取消・訂正・複製が Web API とスクリプトで作られている
（[ADR-0016](0016-画面から呼ぶサーバ処理はWebAPIに置く.md)）ので、線の引き方によっては既存の機能が線の外へ出る。

## 決定

**開発者の決定**（2026-09-18。番号は Claude が振った）。

1. **利用者の作業の物差しは、別の文書に作る**（[06_利用者の作業](../06_利用者の作業.md)）。[02](../02_ペルソナ.md) に入れない——02 が肥大化するから
2. **追記するものと、そうでないものは分ける**
3. **UX の指摘（壊れていないが使いにくい）の行き先は、物差しの側**（Claude の案を採った）
4. **水準——「必ず行う作業」は 100% 側、それ以外は 70〜80% 側**（[30 §4-1](../30_作業のルール.md) の表が持つ。逐語もそちら）
5. **範囲——「必ず行う作業」ができないなら、CLB 標準機能以外を使ってでも直す。それ以外は CLB 標準機能でできる範囲の改善で構わない。**
   理由は逐語——「①今回のアプリは CLB でできることを見せるためのアプリであること ②CLB 標準機能以外で実現するためにはコストが増大するが、目的に照らしコストに見合わないこと」
6. **「CLB 標準機能」の線**——Claude の案に「概ね OK」として、次を付け足した（逐語に近い要約）。
   デザイナで書けるものと、それが呼ぶ Web API は標準内。ただし**スクリプトで行うのはプレゼンテーション層の処理のみ**で、
   **複雑なロジック（テストしなければ正確性を担保できないもの）をスクリプトで書くのは不可**。
   自作 Razor コンポーネントと JS での上書きは標準外。**CSS は、デザイナでも `app.css` を編集できるので、
   「ちょっとしたデザイン調整のために CSS をいじる」ことくらいは許容したい**。
   **留保**——「付け足すことであいまいになっちゃいましたが…。何かうまい言葉でまとめられたら、まとめてください」
7. **物差しの 1 行の粒度は、Claude の案を承認**——利用者が「やろう」と思って始め、終わったと確かめられる 1 つの作業
8. **Extras は標準の内側。Codeer が提供する拡張機能のようなものは CLB 標準とみなす**（同日。開発者は理由を述べていない。
   Claude が 05 の旧 Q-39 で「標準内」と推奨した理由は、CLB でできることを見せる目的に照らして Codeer が配っているものは CLB の側と読めるから——
   開発者はそれを Extras 単体から「Codeer が提供する拡張機能のようなもの」へ広げた）

**当てはめは Claude**（[00 §4-11](../00_ドキュメント規約/本文.md)）——決定 2 の「そうでないもの」は書き換える文書と読み、
**物差し（各作業のいまの状態）は書き換え、確かめた回の記録は [qa/04 §4](../qa/04_実機操作テスト.md) が指す年月のファイルに追記する**。

### 線引きのまとめ（Claude の言葉。決定 6 の留保を受けて）

**作るのは CLB、整えるのは CSS、計算と検証は C#。**

| | 標準内 | 標準外 |
|---|---|---|
| **画面を作る** | デザイナで作れるもの——デザイン JSON・レイアウト・クエリモジュール・**Extras など Codeer が提供する拡張**（決定 8）・それが呼ぶ Web API | 自作 Razor コンポーネント／CLB の外に画面を持つ |
| **画面を動かす** | スクリプト（`*.mod.cs`）に置いてよいものは [22 §2-3](../22_層と実行場所.md) のとおり。C# へ移す線は [20 §1](../20_実装の原則.md)・[ADR-0008](0008-CLBとCSharpライブラリの責務分担.md) | JS で CLB の描画や振る舞いを上書きする |
| **見た目を整える** | `app.css` での**ちょっとしたデザイン調整**（デザイナからも編集できる） | — |

**以下は Claude の敷衍（開発者未確認）**——まとめる過程で足した判定の言葉と、線の外側の 3 つ。

- **迷ったときの判定——「CLB が描いた物を、CLB の外の仕組みで置き換えたり動かしたりしていないか」。**
  置き換える・動かすなら標準外、整えるだけなら標準内。この言葉にしたのは、**既存の取消・訂正・複製を線の内側に残すため**である
  （Web API を呼んで結果で画面を動かすだけ——[22 §3](../22_層と実行場所.md) の表——で、スクリプトは計算をしていない）
- **CSS は「整える」まで。** CLB の要素を隠して別の物を出すなど、**振る舞いを変えるためには使わない**——それは「置き換える」側である
- **標準外を使うのは「必ず行う作業」（[06 §3](../06_利用者の作業.md)）が標準内ではできないときだけ**で、使ったら**なぜ標準内で足りなかったか**を ADR に残す

## 理由

**開発者の理由は決定 5 の逐語①②である。**

**以下は Claude の敷衍。**

- **このアプリは CLB の技術デモでもある**（[CLAUDE.md §1](../../CLAUDE.md) の目的①）。標準の外で作った使いやすさは、CLB で作れることの証明にならない
- **「必ず」だけを 100% にするのは、[30 §4-1](../30_作業のルール.md) の分かれ目と同じ考え方に読める**——
  会計ロジックの不具合と同じく、**できなければ誰も使わない**ものは費用対効果の外に置き、それ以外は 80% で止める

## 検討したが採らなかった案

**開発者に示したのは「02 に入れる」だけである。** 他は Claude が並べた対案で、退ける理由は決定 5・6 から Claude が導いた。

| 案 | 中身 | 採らない理由 |
|---|---|---|
| 物差しを 02 に入れる | ペルソナの §5 を作業まで展開する | 02 が肥大化する（開発者） |
| すべて CLB 標準の範囲に限る | 標準外を一切使わない | 「必ず行う作業」ができないときに、できないまま出荷することになる（決定 5 の裏返し） |
| 制限を置かない | 使いやすさのために何でも使う | 決定 5 の理由①②に反する。独自実装が増えるほど [qa/01](../qa/01_CLB静かな失敗.md) の型の静かな失敗が増える |
| 線を「ファイルの種類」で引く | `*.mod.cs` と `app.css` は内、それ以外は外 | スクリプトに計算を書く道が開く（決定 6・[ADR-0008](0008-CLBとCSharpライブラリの責務分担.md) に反する）。**何をするかで引かないと、種類だけでは守れない** |

## 帰結

1. [06_利用者の作業](../06_利用者の作業.md) を作った。**必須の印と頻度は開発者が確認した**（2026-09-18。Claude の素案から §2-3 の 4 行と W-38（減価償却）を必須に上げた。理由は述べていない。必須と頻度を別の列にしたのは開発者の提案を Claude が採ったもの）
2. [30 §4-1](../30_作業のルール.md) の表に「必ず行う作業」の行を足した
3. 工程 3 か所（設計・実機・自己レビュー）で 06 を引く。**規則は [06 §4](../06_利用者の作業.md) だけが持ち、スキルはそこを指す**
4. **「必ず」の作業が標準内でできない実例は、まだ 1 つも無い。** 出たときにこの ADR の当てはめとして ADR を起こす
5. **CSS の「整える」の実例は `app.css` が持つ。** 整える以上のことを CSS でしたくなったら、それは標準外の合図である（Claude の判断）
6. 決定 4 の水準は、UX の指摘を取捨するときの基準になる（[`self-review` スキル](../../.claude/skills/self-review/SKILL.md) §6）
