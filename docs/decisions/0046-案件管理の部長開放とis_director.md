# ADR-0046: 案件管理の部長開放と is_director キャッシュ

- 日付: 2026-08-06
- 状態: 採用（レビュー第9弾で実装）
- 関係: ADR-0043（3軸分離——本 ADR はその適用例）・ADR-0044（部課階層）・FB-034（条件は AppUser 列のみ参照可）

## 背景

案件（Project）の登録・変更は経理専用だったが、実務で案件を起こすのは現場の長であり、
部長にも開放したい（ユーザー要望 2026-08-06）。「部長である」という組織事実から権限を導く設計を
どう置くか（キャッシュ列 / 権限フラグ自動ON / 役職×権限マトリクス / キャッシュ分離テーブル）を
比較検討し、ユーザー合意の上で本方式に確定した。

## 決定

三段論法の各段を「正しい家」に置く:

| 知識 | 置き場所 |
|---|---|
| このユーザーは部長である（組織の事実） | `department_members` の director 行（真実）→ `app_users.is_director`（FB-034 制約による写像キャッシュ。トリガー保守=ddl/450・再計算=ddl/385） |
| 部長には案件編集権限がある（認可ポリシー） | Project モジュールの **UserWriteCondition**（経理 ∨ IsDirector。CLB の全ポリシーが集まる宣言的な場所） |
| ゆえに編集できる（評価） | CLB ランタイム |

- **開放範囲は基本情報まで**（名称・取引先・種別・状態）。SES 精算条件（単価・精算幅）は損益直結の
  経理項目のため、非経理にはスクリプトで読取専用（`Project.mod.cs`）
- 導線: 工数フレーム（Timesheet）の「案件一覧」を読取専用ビュー（ProjectView・廃止）から
  Project 本体に差し替え。一般社員は閲覧のみ（書込条件で自動的に読取専用）、部長・経理は編集可
- `is_manager` は作らない（YAGNI——消費者が現れたら同型で追加）。`is_approver` は
  個人指名を含む独立した事実のため存続（冗長ではない）
- 課長にも開放したい導入企業のカスタム: `is_manager` キャッシュを同型で追加し
  Project の条件に OR を足す（docs/10 §6 の作法）

## 検討して退けた代替案（要約。詳細は 2026-08-06 の設計対話）

- **can_edit_project をトリガーで自動 ON**: 真実でもキャッシュでもない中間物になり、ポリシーが
  トリガー SQL という最も見えない場所に埋まる
- **役職×権限のマッピングテーブル**: FB-034 がある限りキャッシュ列は結局必要で、得るのは対応表の
  データ化のみ。対価（権限マトリクス管理画面）が ADR-0041/0043 で捨てた複雑さの再導入になる。
  ポリシーが本当にマトリクス化したら再検討（ADR-0043 の「目安5〜6本」と同じ脱出口）
- **キャッシュ専用テーブルへの分離**: CurrentUser モジュールの差し替え＋96条件の書き換えという
  大工事を、機能ゼロの純化のために払うことになる

## 影響

- AppUser 詳細・一覧に「部長」を自動判定表示（承認者と同格）
- docs/10 §2 のキャッシュ群・§6 カスタムポイントに追記
