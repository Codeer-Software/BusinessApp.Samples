# ADR-0013 機能単位のモジュール分割と依存方向

> **2026-08-27 追記**: [ADR-0025](0025-取引先を部品として分ける.md) が `Partners` を
> 会計コアの機能フォルダから独立部品へ出すと決めた。実装後、本文中のモジュール一覧・依存の図・
> §3 の参照ゼロ検査の記述は当時の姿になる（新しい構成の正典は ADR-0025 §2。
> 依存表の正典は当時からコード `Conventions/ModuleDependencyTests.cs` であり、
> 本文 §3 の図は概略である）。本 ADR の決定——層はプロジェクト参照で・機能は名前空間フォルダで
> 割る、会計コアの機能ごとに csproj を分けない——は変わっていない。

## 状況

[ADR-0008](0008-CLBとCSharpライブラリの責務分担.md) は**層**（純粋ドメイン／サーバ／クライアント／CLB）を
決めたが、**それぞれの層の中をどう割るか**は決めていない。

最初の実装は `Primitives / Masters / Calendar / Journals / Rules / Validation` という
**「モノの種類」による分割**になっていた。この形は、機能が増えると 1 つの機能が
6 フォルダに散る。会計コアはこの先、元帳・試算表・消費税・固定資産・決算まで伸びる。

## 決定

### 1. 層はプロジェクト参照で、機能は名前空間フォルダで割る

**層（横）は済んでいる。** `AccountingCore` ← `.Server` / `.Client` という
プロジェクト参照が依存の向きを**コンパイラに守らせている**。これはオニオン／ヘキサゴナルの
中心的な要求そのものであり、用語や層の追加は要らない。

**足りないのは機能（縦）の分割**なので、そちらを名前空間フォルダで入れる。

```
BusinessApp.AccountingCore/
  Shared/            共有カーネル。金額・端数処理・有効期間・借方貸方・制度ルールの仕組み・違反の型
  Accounts/          勘定科目
  Periods/           会計年度・会計期間・締め
  ConsumptionTax/    税区分・用途区分・経過措置
  Journals/          仕訳（モデル・計上の関門）
  （以降）Departments / Partners / Ledgers / Closing / FixedAssets
```

**3 つのプロジェクトで同じ機能フォルダ名を使う。** 1 つの機能を触るとき開く場所を固定する。

> **用語の注意**: プロジェクト名の `Server` / `Client` は 2 通りの意味で使われている。
> `BusinessApp.Server` / `.Client` は**ホスト**（ASP.NET Core / Blazor WASM）、
> `AccountingCore.Server` / `.Client` は**会計コアの層**である。文脈で読み分ける。

| 層 | 置くもの |
|---|---|
| `AccountingCore/Journals/` | 型・不変条件・検証（純粋） |
| `AccountingCore.Server/Journals/` | 採番・保存・サーバ側の関門・帳票 API |
| `AccountingCore.Client/Journals/` | CLB スクリプトから呼ぶサービスの登録 |
| CLB モジュール名 / DB テーブル名 | `Journal*` / `journal_entries` |

### 2. 機能ごとに csproj を分けない

分ければコンパイル時に依存を強制できるが、採らない。

- `AccountingCore` は **WASM に載る**ので、アセンブリが増えるとダウンロード量と起動時間に
  直接効く（[ADR-0008](0008-CLBとCSharpライブラリの責務分担.md) の明示的な制約）
- 開発者 1 人で 10 プロジェクトは摩擦が大きい

名前空間フォルダ ＋ 後述の依存テストで、コストの 1 割で効果の 9 割を取る。

### 3. 依存の向きを表で定義し、テストで強制する

会計は本質的に相互参照が多く、「モジュール間の依存ゼロ」は成立しない。
目指すのは**向きを一方通行に固定する**ことである。

```
Shared
  ← ConsumptionTax                （税区分。勘定科目を知らない）
    ← Accounts                    （勘定科目は「既定税区分」を持つ）
  ← Periods
  ← Departments / Partners
      ← Journals                  （マスタと制度の上に載る）
```

向きは**参照を持つ側が下位**になるように決める。勘定科目は既定税区分を持つが、
税区分は勘定科目を知らないので `Accounts → ConsumptionTax` である。逆向きを許可しない。

表は `Conventions/ModuleDependencyTests.cs` が持ち、次を検査する。

- 許可されていないモジュールを参照していないか
- **実フォルダと表が一致しているか**（フォルダを増やしたら表の更新を強制する）
- 表に循環が無いか／表の参照先が実在するか
- `AccountingCore.csproj` に `PackageReference` も `ProjectReference` も無いか（依存ゼロの明文化）

### 4. 依存の検出は「文字列の出現」で行う。外部ライブラリを使わない

ソースファイルの中に `BusinessApp.AccountingCore.<他モジュール>` が現れたら、
他モジュールへの参照とみなす。

- `using` ・ `using static` ・エイリアス・完全修飾の**すべてがこの 1 つの規則で捕まる**。
  C# は他名前空間の型を、いずれかの形で名前空間ごと書かなければ参照できない
- IL 解析（`System.Reflection.Metadata` でメソッド本体を追う）は 10 倍複雑で、間違えても気づけない
- **アーキテクチャ検査ライブラリを入れない。** この規則は 20 行で書けて読んで分かる。
  外部ライブラリは、規則の単純さに対して依存とメンテ追従のコストが見合わない

副作用として、XML ドキュメントコメントで他モジュールの型を完全修飾しても違反になる。
これは**望ましい副作用**として受け入れる（型名だけで書けば済む）。

### 5. 純粋ドメインにリポジトリのインターフェースを置かない

教科書どおりのオニオンなら「ドメインが `IJournalRepository` を定義し、インフラが実装する」となるが、
**採らない。** 現在の設計は、ドメインが I/O という概念を持たず、必要なデータは呼び出し側が
読んで渡す形（`IAccountLookup` ・ `PostingContext`）である。

> **2026-08-26 追記**: `IAccountLookup` は実装に無い。3 行下の「渡す型は具象にする」に合わせて
> インターフェースをやめ、具象の `AccountCatalog` を渡す形にした（qa/02 R1-14）。

これはリポジトリ注入より**強い**疎結合であり、テストに DB もモックも要らない。
リポジトリを足すのは実質的な退化になる。同じ理由で MediatR・CQRS も入れない。

**渡す型は具象にする。** 会計マスタは全件を先に読める規模（科目 100 件程度）で、
差し替える実装も無い。メモリ上の値の集まりに `IXxx` を被せるのは、テストを楽にせず
読みにくくするだけである（[ADR-0012](0012-テスト方針とカバレッジのゲート.md) §6）。
`Find` だけのインターフェースは「リポジトリの最小形」であり、
帳票が列挙と並び替えを要求した時点で作り直しになる。

## 理由

- **1 機能が 1 フォルダに収まっていること（高凝集）と、依存の向きが一方通行であること（疎結合）が
  本質**であって、オニオンの層の名前や、モジュールごとのアセンブリ分割は手段にすぎない
- **今やるべき理由**: 20 ファイルの時点なら移動は 30 分で終わる。
  [ADR-0012](0012-テスト方針とカバレッジのゲート.md) の配置規約テストがあるので、
  ソースとテストの片方だけ動かせば落ちる。フェーズ 4 で 200 ファイルになってからでは着手しない判断になる
- 依存の表をコードに置くと、**設計の意図がレビュー可能な形で 1 箇所に集まる**。
  文書だけの規約は破られても気づけない

## 帰結

- 新しい機能を作るときは、まず `ModuleDependencyTests` の表に行を足す。
  足さずにフォルダを作るとテストが落ちる
- 機能どうしが双方向に参照したくなったら、それは**共有カーネルへ切り出す信号**である。
  表に循環を書き足す選択肢は無い（テストが落ちる）
- 他部品からの仕訳投入（[04 §10](../04_会計ドメイン設計.md)）は `Journals` の公開 API として置き、
  部品の境界をコード上でも 1 箇所に見えるようにする
- 将来 `AccountingCore.Server` が肥大したら `.Application` を割る余地は残る。
  そのときもフォルダ単位で移せばよいので、今は分けない
