# ADR-0076: 仕訳が取引先を持つ（電子帳簿保存法の検索要件）

- 日付: 2026-08-19

## 背景

電子帳簿保存法は、電子取引データを保存するときに **「取引年月日」「取引金額」「取引先」の
3 項目で検索できること**を求めている（検索要件）。証憑をアプリに添付する（BUG-0006/0023）だけでは
要件を満たさない——添付しただけの証憑は「探せない証憑」だからだ。

このアプリの仕訳は、着手時点で **3 項目のうち取引年月日しか持っていなかった**:

- **取引先**: `journal_entries` に列そのものが無い。取引先名は摘要の文字列（「入金 INV-26-004」など）に
  埋もれていて、`LIKE` でも取引先では引けない
- **取引金額**: 金額は `journal_lines` 側にあり、一覧の「金額」列（借方合計）は表示専用で検索できない

つまり「アルタイル商事との 70 万円以上の取引を出せ」に答えられない。税務調査で最初に来る質問がこれである。

## 決定

**`journal_entries.partner_id` を持ち、仕訳を生成するすべての経路で自動的に埋める。
振替伝票一覧で取引先・金額（範囲）でも検索できるようにする。**

### 1. データモデル

`journal_entries.partner_id INTEGER REFERENCES partners(id)`（NULL 可・索引つき。`ddl/816`）。

**NULL 可にする**のが要点。銀行明細・現金出納・定型仕訳・仕訳インポート・減価償却・仕掛品振替・
手入力の振替伝票には、そもそも取引先マスタに載る相手がいない。ここを必須にすると
「相手がいないのに何か選ばされる」画面になり、嘘のデータが増える。
**取引先が特定できる経路だけ埋め、それ以外は空**——これが正しい状態。

### 2. 自動で埋める（人に入力させない）

仕訳の生成経路は 22 か所ある。そのうち生成元が取引先を持っているのは次の 14 か所で、
すべてスクリプトで引き継ぐ:

| 生成元 | 引き継ぐ取引先 |
|---|---|
| 検収 → 売上計上 | 受注の取引先 |
| 入金消込（単票／合算） | 消込先の請求書の取引先 |
| 請求書の赤伝・値引 | 請求書の取引先 |
| 仕入先請求の計上・支払 | 仕入先 |
| 定期請求（SaaS 月額・年額前受・按分振替・打ち切り） | 契約の取引先 |
| SES 請求 | 案件の取引先 |
| 経費の計上・支払 | **支払先が取引先のときだけ**（社員への精算は取引先ではない） |
| 確定伝票の取消（赤伝・ADR-0075） | 元伝票から引き継ぐ |

手入力の振替伝票には取引先の選択欄を置く（任意）。**入力を強制しない**——
仕訳の 4 分の 1 は相手が取引先ではないので、必須にすると入力が形骸化する。

既存の仕訳は生成元から遡って埋め戻す（`ddl/817`・54 件）。
過去分が探せないなら検索要件を満たしたことにならない。

### 3. 検索

振替伝票一覧に「取引先」（部分一致）と「金額」（借方合計の範囲）を足す。
金額は明細の集計値なので `HAVING` で絞る。一覧にも取引先列を出す
——検索できても一覧に出ないと「これで合っているか」が確認できない。

## 影響

- 仕訳を生成する新しい経路を足すときは、**取引先を引き継げるなら必ず引き継ぐ**。
  引き継がないと過去の仕訳だけ検索に出ない、という穴が静かに空く
- 部門別・案件別と違い、`partner_id` は**集計には一切使っていない**（検索と表示のためだけ）。
  売掛残高や案件損益がこの列を見に来ると二重の真実になるので、そうしない

## 代替案と却下理由

- **摘要に取引先名を必ず書く運用にする** — 表記ゆれで検索に漏れる（「（株）」「株式会社」「アルタイル」）。
  マスタへの参照でないので、取引先名を直しても過去の仕訳には追随しない
- **`journal_lines` に持たせる** — 1 伝票の中で相手が変わることは（このアプリの生成経路では）無い。
  行に持たせると検索が `EXISTS` になり、伝票単位の「取引先」という概念もぼやける
- **取引先を必須にする** — 上述のとおり、相手がいない仕訳が全体の 4 分の 1 ある
