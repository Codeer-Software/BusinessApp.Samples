# ADR-0024 部品の分割は「束ねる相手抜きで使われる場面があるか」で決める

## 状況

[ADR-0002](0002-部品の定義と分割の判断基準.md) はアプリ部品の分割基準を
「**その部品だけを使う利用者が現実に存在するときに限る**」と定めた。

この基準を取引先マスタに当てると「分けない」になる。取引先台帳**だけ**を使う会社は
現実にはまず考えられない（見立て。取引先台帳だけなら Excel で足りる）からである。

一方 [ADR-0019](0019-マスタは会計が生んだ概念かで分ける.md) は取引先を「会計の外の実体」と
整理した。経費精算・販売・購買のどの部品も同じ取引先を使い、会計をやめても取引先は存在し続ける。
つまり**会計コア抜きの組（販売＋取引先など）で使われる場面は現実にある**のに、
旧基準は「単独で使われるか」しか問わないため、この**共有される部品**を判定できない。

開発者が取引先の部品化を提起した際（2026-08-27）、基準の側が判断を誤らせることが確認された。
基準そのものを改める。

## 決定

### 1. 部品の 2 階層（ADR-0002 から変更なし）

| 用語 | 定義 | 実体 |
|---|---|---|
| **アプリ部品** | 単独でデプロイでき、それだけで業務価値を持つ CLB のデザイン単位 | モジュール群（`*.mod.json`）＋ PageFrame ＋ DB テーブル群 ＋ 付随する C# ライブラリ |
| **コード部品** | .NET プロジェクト単位。アプリ部品の内部で使う | `*.csproj` 1 つ |

1 つのアプリ部品は複数のコード部品を持ってよい。複数のアプリ部品が同じコード部品を共有してもよい。
ただし依存の方向は常に下位から上位のみであること。

### 2. アプリ部品の分割基準（ここを改めた）

**アプリ部品として分けるのは「その機能が、いま束ねようとしている部品抜きで使われる現実の場面が
存在する」とき。**

旧基準の「その部品だけを使う利用者が現実に存在する」は、この場面の 1 つ（単独利用）にすぎない。
十分条件を必要条件と書いていたのが旧基準の誤りである。

| 機能 | 会計コア抜きで使われる場面 | 判定 |
|---|---|---|
| 証憑管理 | 電子取引データの保存だけしたい会社が現実にいる（単独利用） | 分ける（本プロジェクトでは作らない） |
| 承認フロー | 経費精算だけに承認を敷く場面がある。そもそも会計の責務ではない | 分ける（本プロジェクトでは作らない） |
| **取引先** | **販売・購買・経費精算のどれもが会計抜きで取引先を使う。複数部品が同じ取引先を共有する** | **分ける**（[ADR-0025](0025-取引先を部品として分ける.md)） |
| 減価償却 | 会計抜きで固定資産台帳だけ使う会社はいない | 分けない（会計コアに含める） |

表の「場面」の列は、確認された事実だけでなく**市場の見立てを含む**（判断の材料である）。

判定に迷ったら [ADR-0019](0019-マスタは会計が生んだ概念かで分ける.md) の問い
「**会計をやめても、その概念は存在し続けるか**」を先に当てる。存在し続けるもの（会計の外の実体）は
他部品も同じものを使うので、本基準でも「分ける」に落ちる（取引先ではどちらの基準も同じ答えになった）。

### 3. コード部品の分割基準（ADR-0002 から変更なし）

**コード部品として分けるのは、次のいずれかに当てはまるとき。** 分割コストが低いので積極的に分ける。

- 依存の向きを一方向に固定したい
- 単独でテストしたい（とくに制度依存が重く、境界値テストを大量に書く領域）
- 別のアプリ部品からも使う見込みがある
- 実行場所が違う（純粋計算 / サーバ専用 / クライアント専用）

### 4. 部品間の依存規則（向きの決め方を一般化した）

旧規則は「会計コアは他のどの部品も知らない」と書いた。これは**会計コアより上位の部品が
存在しない**ことを暗黙の前提にしていたが、ADR-0019 が「会計の外の実体」（取引先。
[13 §1-1](../13_取引先設計.md) の整理では会計コアより上位）を認めた時点で、
この前提は成立しなくなっていた。向きの決め方そのものを書く。

- **依存の向きは「単独で成り立つ側が上位、相手を要る側が下位」。** 下位が上位に依存し、
  上位は下位を知らない
  - 取引先は誰も知らない。会計コアは取引先を知ってよい。周辺業務（経費精算・販売・証憑・承認）は
    会計コアと取引先を知ってよい。会計コアは周辺業務を知らない
  - 会計コア → 取引先の依存は、本設計の下では不可避でもある。仕入税額控除の帳簿記載事項①
    「課税仕入れの相手方の氏名又は名称」（消税法 30 ⑧。
    [消費税リサーチ §8](../research/2026-08-23_消費税インボイス制度.md)）の写しを、
    計上時にサーバがマスタから引くと決めている（[ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md)）
- 下位部品は上位部品の**公開された連携点**だけに依存する。会計コアへの仕訳投入は公開 API を通し、
  **会計コアのテーブルを直接 INSERT しない**（変更なし）
- **上位部品のテーブルを下位部品が読むこと（SELECT・JOIN・外部キー）は、同じ DB に同居する限り
  許す。書き込みは所有部品の関門だけを通す**（今回明文化。会計の帳簿が取引先を JOIN で引く、
  仕訳の明細が `partners` へ外部キーを張る、はこの形である）
- 会計コアは、投入元が誰かを知らないまま、**元伝票を特定する情報を保持し続ける**
  （他部品からの追跡と、電子帳簿保存法上の保存要件——帳簿間の相互関連性ほか。
  [電帳法リサーチ §3.4](../research/2026-08-23_電子帳簿保存法.md)——の両方に必要。変更なし）

## 理由

- **旧基準は共有部品を判定できない。** 取引先に当てると「分けない」という誤った答えが出ることが
  部品化の検討（2026-08-27）で確認された（誤った決定が下される前に基準を改めている）。
  「単独利用者がいるか」は分ける理由の 1 つであって、唯一の理由ではない
- ADR-0002 の芯——「分けられるものは全部分ける」に逃げない、
  **分割の理由は「別々に使われる」という事実**であって整理整頓の美学ではない——は変えていない。
  変えたのは「別々に使われる」の判定方法だけである
- 依存規則の一般化は ADR-0019 の帰結の清算である。「会計の外の実体」を認めながら
  「会計コアは何も知らない」と言い続けることはできない。向きの原理（独立して成り立つ側が上位）を
  書けば、取引先にも将来の共有部品にも同じ規則で答えが出る

## 帰結

- [ADR-0002](0002-部品の定義と分割の判断基準.md) は `superseded`。**本 ADR が現在の正典である**
- 取引先への適用は [ADR-0025](0025-取引先を部品として分ける.md)
- ADR-0002 の個別判定は引き継ぐ——固定資産・減価償却はアプリ部品として会計コアに**含め**、
  コード部品としては**分ける**。証憑管理・承認フローはアプリ部品として**分ける**（本プロジェクトでは
  作らない）。会計コアは「仕訳が外部証憑を参照するための識別情報」だけを持つ
- 今後の分割判断は §2 の基準で行い、判断が自明でなければ ADR を起こす
