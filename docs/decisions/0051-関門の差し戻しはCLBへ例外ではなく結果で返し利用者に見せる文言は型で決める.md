# ADR-0051 関門の差し戻しは CLB へ例外ではなく結果で返し、利用者に見せる文言は型で決める

## 状況

保存の関門（[ADR-0008](0008-CLBとCSharpライブラリの責務分担.md)）は、差し戻しを例外（`JournalPostingRejectedException` ほか 5 種）で投げ、
ホストの例外ハンドラ（`UseExceptionHandlerSendToFront`）が `Message` をそのまま HTTP 500 の本文にして、CLB がトーストに出していた。
この形には 2 つの問題があった。

1. **トーストが 2 枚出る**——関門の文言に続けて、CLB 自身の定型文「更新に失敗しました」が出る
   （[qa/02 R25-08](../qa/02_自己レビュー記録.md)。2026-08-30 に見つけ、消す手が分からず保留のまま 2026-09-10 まで来た）。
2. **開発者向けの文言も同じ経路で画面に出る**——例外ハンドラは型を見ないので、`InvalidOperationException` の
   「仮 ID … に本物の ID が 2 つ対応している」「仕訳 … が見つからない」もそのまま利用者に届く（[qa/02 R57-35](../qa/02_自己レビュー記録.md)）。
   読めない型（`UnreadableFieldException`）だけは入口が定型文に差し替えていたが、それ以外は野放しだった。

CLB は保存の失敗を **`ModuleSubmitResult.ExceptionMessage`** で報告する仕組みを持つ（[qa/01 F-16](../qa/01_CLB静かな失敗.md)）。
2026-09-10 に実機で確かめた（1.3.20。[qa/01 F-42](../qa/01_CLB静かな失敗.md)）：**関門の差し戻しをこの形で返すと、CLB はその文言だけを 1 枚のトーストにし、
その保存で書いた分（下書きの UPDATE）を巻き戻す**。摘要を変えてから「計上する」を押して差し戻された後、DB の摘要と版は動いていなかった。

## 決定

**Claude の判断（2026-09-10）。開発者は未承認**——R25-08 は「消す手が分かっていない」保留で、開発者に諮った記録は無い。
本 ADR は見つけた手を記録し、開発者の判断を待つ。

### 1. 差し戻しは CLB へ例外ではなく結果で返す

保存の入口 `AccountingSubmitPipeline` に **`SubmitAsResultAsync`** を置き、本番の入口（`CustomizedModuleDataIO`）はこれだけを呼ぶ。
関門が投げた差し戻しは `ModuleSubmitResult.ExceptionMessage` に文言を載せた結果 1 件に変換する。関門は今までどおり例外を投げてよい——
変換は入口の 1 か所で行う。

### 2. 利用者に見せてよい文言かどうかは型で決める

`BusinessApp.ServerSupport` に基底 **`RejectedException`** を置き、利用者に見せてよい差し戻しはすべてこれの派生にする
（仕訳・マスタ・自社情報・取引先・登録番号の 5 種。規約テスト `RejectedExceptionConventionTests` が名前で見つけて基底に乗っていることを確かめる）。
入口は **この型の例外だけを利用者の語として返し、それ以外の例外は定型文（`SaveFailureMessage.Text`）に差し替えて原文をログへ回す**。
文言の中身を見て利用者向けかを判定することはしない——判定できないからである。

### 3. 例外のまま返す `SubmitAsync` は残す

テストと `DbTransactionScope`（Web API の経路）は例外で巻き戻す前提で組まれている。`SubmitAsync` は差し戻しを例外のまま返し、
`SubmitAsResultAsync` がそれを包む。テストは差し戻しを `Assert.ThrowsAsync` で見続けてよい。

## 理由

- **1 枚にできる手が、CLB の仕様の中にあった。** 例外で返すかぎり CLB の 1 枚は消せないが、結果で返せば CLB は自分の定型文を出さない（実測）
- **巻き戻しも CLB が引き受ける**（実測）。関門が保存の後で差し戻す経路（計上）でも、下書きの保存は残らない
- **型で線を引けば、関門を足す人が「画面に出る文言か」を毎回考えなくてよい。** 差し戻しは基底に乗せる、それ以外は何を投げても定型文になる

## 帰結

- 関門の差し戻しと想定外の失敗が、**親（伝票・マスタの行）の差分がある保存では 1 枚のトースト**になる。
  **明細だけを直した保存（親の差分が無い。[qa/01 F-41](../qa/01_CLB静かな失敗.md) ②）では CLB の「更新に失敗しました」が 1 枚残る**——
  結果に行ごとの `SourceId` を付けて返しても変わらなかった（2026-09-10 実測 1.3.20。[qa/01 F-42](../qa/01_CLB静かな失敗.md)）。
  ここは [CLB 改善提案 FB-017](../CLB改善提案/01_機能改善提案.md) に送り、R25-08 は「明細だけの保存」に絞って閉じる
- 開発者向けの例外文言が画面に出る経路は、保存の入口からは消える（R57-35 を閉じる）。Web API の経路は
  [ADR-0016](0016-画面から呼ぶサーバ処理はWebAPIに置く.md) のとおり 200 以外を画面側が定型文にするので、もともと出ない
- `UnreadableFieldException` を入口で `InvalidOperationException` に包み直していた分岐は消える（`SubmitAsResultAsync` が受ける）
- 実機の台本（[qa/04](../qa/04_実機操作テスト.md) の C-03）の「2 枚目が出る」は「出ない」に変わる（C-05 は明細だけの保存なので残る）。[04 §5](../04_実装計画と現在地.md) の未決を閉じる
- **CLB が結果を見て巻き戻す挙動は実測に依る**（1.3.20）。版を上げたら [qa/01 F-42](../qa/01_CLB静かな失敗.md) の手順で踏み直す

## 検討したが採らなかった案

- **ホストの例外ハンドラで型を見て差し替える**——ハンドラはカバレッジにもミューテーションにも載らない（[ADR-0012 §3](0012-テスト方針とカバレッジのゲート.md)）。
  差し替えの規則を検査の外に置くことになる。しかも 2 枚出るのは変わらない
- **関門が例外ではなく結果を返す形に書き直す**——全関門と数百のテストが例外で組まれている。入口の 1 か所で変換すれば同じ効果が出る
- **CLB 改善提案に送る**——CLB の仕様の中で解けたので送らない
