# ADR-0059: パスワードポリシーのマスタ化と、利用者自身のパスワード変更

- 日付: 2026-08-16
- 状態: 採用
- 関連: ADR-0024（API キーの User Secrets 化）／ADR-0041（権限モデル）／`_specs/Authentication.md`

## 背景（問題）

ユーザーからの指摘 2 件を調べたところ、どちらも「無い」ことが確認された。

1. **パスワードの制限が一切無い。**
   CLB の `PasswordField` は入力をハッシュ化するだけで、長さ・文字種の検証を持たない
   （ハッシュ化はサーバの `CustomizedModuleDataIO` → `PasswordHashHelper.ApplyPasswordHash`）。
   本リポジトリ側にも検証は無く、**1 文字でも「a」でも通る**状態だった。
   「中小企業が実運用できる」を掲げるアプリとして、これは通せない。

2. **利用者が自分のパスワードを変更できない。**
   `パスワード` フィールドを持つモジュールは `AppUser`（システム管理＞ユーザー管理）だけで、
   この画面はシステム管理者専用。一般利用者は管理者に依頼するしかなく、
   **管理者が新しいパスワードを知ってしまう**運用になっていた。

### 設計上の制約（ここが判断の分かれ目）

- **`AppUser` に `UserWriteCondition` を付けられない。** `AppUser` は `CurrentUser` のソースなので、
  読み書きを制限するとマイプロフィール・`LinkField` 表示・他モジュールの参照が全部壊れる
  （CLB の仕様。`_specs/Authentication.md` に明記）。
  つまり「自分の行だけ更新できる」という制約を **CLB 側では表現できない**。
- **現在のパスワードの照合はハッシュ照合**なので、CLB スクリプト（WASM）では原理的に不可能。
- 認証テーブルは `appsettings.json` の `PasswordCheckUserTableInfo` で
  `active_app_users`（ビュー）を指している（ddl/290・390）。SQLite のビューは
  `INSTEAD OF` トリガーが無いと更新できず、`INSERT` 用はあるが `UPDATE` 用は無かった。

## 選択肢

### ポリシーの持ち方
| 案 | 得失 |
|---|---|
| A. 定数としてコードに埋める | 実装は最短。ただし社内規程は会社ごとに違い、NIST SP 800-63B のように推奨自体が改訂される。CLAUDE.md §3「閾値をハードコードしない」に反する |
| **B. マスタ化（採用）** | 「御社のポリシーに合わせられます」と言える＝デモの訴求にもなる。開発中だけ緩めることもできる |

### 検証をどこに置くか
| 案 | 得失 |
|---|---|
| C. CLB スクリプトだけ | 実装は軽いが、API を直接叩けば素通り。一括取込（`BulkAddAsync`）も通らない |
| D. サーバだけ | 安全だが、入力中に条件が分からず体験が悪い |
| **E. サーバが唯一の判定・クライアントは呼び出すだけ（採用）** | 判定の実装が 1 か所。画面は「条件の説明文」と「保存前の先出し検証」を API 経由で受け取る |

### 自己変更画面の作り
| 案 | 得失 |
|---|---|
| F. `AppUser` を自分の行だけ編集させる | 上記のとおり `UserWriteCondition` が使えず、制約を表現できない |
| **G. DB に紐づかない表示専用モジュール＋専用 API（採用）** | 更新対象がサーバ側で本人に固定され、他人の行を書き換える経路が構造的に存在しない |

## 決定

1. **`password_policies` テーブル（1 行固定）を新設**（ddl/560）。項目は 4 つ:
   - `min_length` … 最小文字数
   - `required_kinds` … 英大文字 / 英小文字 / 数字 / 記号 のうち最低何種類（0〜4。0 で制限なし）
   - `allow_same_as_user_name` … ユーザー識別名と同じ文字列を許すか
   - `forbid_reuse_current` … 現在のパスワードと同じものへの変更を禁止するか

   画面は `PasswordPolicy` モジュール（システム管理＞セキュリティ＞パスワードポリシー。
   システム管理者のみ・`CanCreate:false` / `CanDelete:false`）。

2. **判定の実装はサーバの `PasswordPolicyService` 1 か所**。呼び出し元は 2 つ:
   - `CustomizedModuleDataIO`（Add / BulkAdd / Update）… **CLB 経由の全パスワード書き込みが必ず通る点**。
     システム管理者のユーザー管理も、CSV の一括取込もここを通る。
   - `PasswordController`（`/api/password/change`）… 利用者自身の変更。

   クライアント側には判定を複製しない。画面が受け取るのは
   **`GuidanceText()` が作る説明文**（＝検証と同じ場所で生成されるので、文言と実装がズレない）と、
   保存前の先出し検証 `/api/password/validate` の結果だけ。

3. **自己パスワード変更は `PasswordChange` モジュール（表示専用・`DbTable: ""`）＋ `/api/password/change`**。
   - 更新対象は Cookie 認証の `NameIdentifier`＝ログイン中の本人に固定。リクエストで対象ユーザーを指定できない。
   - 現在のパスワードの照合を必須にする（`PasswordHashHelper.VerifyHash`）。
   - 導線は左サイドバー（`PortalSidebar`）に全員向けで追加する。
     **ただし「パスワードの変更」を直接置かず、`Settings`（設定）フレームを 1 枚かませる**
     （2026-08-16 ユーザー指摘: 業務メニューと同じ高さに生で並ぶのは怖い）。
     サイドバーは「設定」→ `/Settings`、フレーム内のメニューは「アカウント/パスワードの変更」。
     `Settings` フレームはゲートなし（全員）で、着地は ADR-0045 の方針どおり
     部品トップを作らず主画面（パスワードの変更）に直接置く。
     今後の利用者ごとの設定（表示設定・通知の受け取り方など）はこのフレームに足す。

4. **ビューへの `INSTEAD OF UPDATE OF hash, salt` トリガーを追加**（ddl/570）。
   `app_users` を直接名指しすれば動くが、それでは「認証テーブルは設定で差し替えられる」という契約が壊れる。
   INSERT と同じくビュー側にトリガーを置き、サーバは常に `PasswordCheckUserTableInfo` のテーブル名だけを見る。

5. **開発 DB の初期値は緩くする**（2026-08-16 ユーザー指示）:
   `min_length=4` / `required_kinds=0` / `allow_same_as_user_name=1` / `forbid_reuse_current=0`。
   開発中は ID とパスワードが同じ状態のほうが扱いやすいという判断。
   **本番想定の推奨値は 12 / 3 / 禁止 / 禁止** で、これは画面から切り替えられる（切り替えられること自体がデモの訴求）。

## 影響

- 既存ユーザーのパスワードには遡及しない（検証は「新しく書き込むとき」だけ走る）。
  ポリシーを厳しくしても、既存の弱いパスワードでログインはできる。
  これを塞ぐなら「初回ログイン時の変更強制」が要る（→ 未実装。バックログ）。
- `AppUser` のパスワード欄を空のまま保存すると、これまでどおりパスワードは変更されない
  （検証もハッシュ化もスキップ）。
- `password_policies` テーブルが無い環境では既定値（12 / 3 / 禁止 / 禁止）にフォールバックし、
  ログインとユーザー管理は動き続ける。

## 残る弱点（正直に記録する）

- **既存の平文相当の弱いパスワードは残る**（上記）。
- **`AppUser` は認証済みユーザーなら API 経由で書き込めてしまう**（`UserWriteCondition` を付けられないため）。
  今回の変更でパスワードだけは `CustomizedModuleDataIO` の検証を必ず通るようになったが、
  「他人の表示名や権限フラグを API 直叩きで書き換える」経路自体は塞げていない。
  これは CLB の `CurrentUser` モジュールの構造的な制約で、本アプリ固有の実装ミスではない。
  塞ぐならサーバ側で `AppUser` への書き込みを sysadmin に限る追加ガードが要る（→ バックログ）。
- **パスワード再利用の履歴（過去 N 世代の禁止）は持たない。** 現在との一致だけを見る。
