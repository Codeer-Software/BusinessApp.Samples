# 0034: 定期請求実行のプラン方式（プレビューと実行のロジック共通化）

- 日付: 2026-07-26
- 状態: 採用・実装済み
- 起点: ユーザー要望「対象月を選ぶと生成対象の契約と金額がリストで見えると分かりやすい。
  ただしプレビューと実行でロジックが別に存在するのは設計として極めて危うい——共通化できないか」

## 課題

「定期請求の実行」は対象月＋実行ボタン＋結果1行のみの画面で、売上計上を伴うバッチを
「何が起こるか見えないまま」押す構造だった。素朴にプレビューを足すと、生成対象の判定
（期間・年払い周期・冪等・金額）がプレビュー用 SQL と実行用スクリプトに二重化し、
両者のズレが「プレビューと結果が違う」不信を生む。

## 決定: プラン（実行指示書）を介した一本化

判定ロジックを **`BuildPlan(対象月)` の1関数に集約**し、その出力（プラン行）を
プレビュー表示と実行の両方が消費する。

```
BuildPlan(対象月)  … 唯一の判定ロジック。recurring_run_plan へ全行洗い替えで書き出す
  ├─ プレビュー   … 対象月変更・画面初期化で BuildPlan → 一覧（PlanLines）はテーブルを表示するだけ
  └─ 実行        … ボタン押下で BuildPlan を再実行（最新データで再判定）→ status='planned' の行を
                    plan_kind（monthly/annual/defer）に従って機械的に消費。実行側は判定を持たない
```

- **プラン行** = 契約・取引先・部門・種別（月額/年額）・請求額（税抜）/消費税/按分振替額・
  状態（生成予定/生成済み/対象外）・内容（理由文）・請求書番号＋実行用の機械項目
  （plan_kind・周期起点月・周期内月番号・アンカー年額請求書 id）。
- **状態の網羅**: 月額の生成予定/生成済み/void 停止、年払いの
  「年額請求＋前受＋按分（起点月）」「按分振替のみ（n/12ヶ月目）」「起点月未実行」「void 停止」、
  下書き契約・無効化契約の対象外（理由つき）。
- 実行が終わったプラン行は状態を「生成済み」に更新し、仕訳 No・請求書番号を書き戻す
  （実行直後の画面がそのまま結果一覧になる）。
- ボタン名は実態に合わせ「対象月の請求書**・仕訳**を一括生成」に変更。

## 採用理由

- プレビューと実行がどちらも BuildPlan しか通らないため、**両者がズレる余地が構造的にない**
  （ユーザー指摘の二重化リスクへの回答）。
- プレビュー表示後に他ユーザーがデータを変えても、実行は押下時点の BuildPlan 再実行が正なので
  会計データはズレない（画面の古さは情報の鮮度の問題に留まる）。
- 銀行明細取込 v3（ISSUE-0003）で確立した「未確定の作業データは専用テーブルに分離」パターンの応用。
  一覧の表示は CLB の ListField ＋ 明示 Reload()（Project.md 2026-07-21 の知見）で素直に組める。

## 実装

- テーブル: `recurring_run_plan`（ddl/350。全ユーザー共有の一時領域・BuildPlan のたび洗い替え。
  同時プレビューは後勝ちだが上記のとおり実害なし）
- モジュール: `RecurringRunPlan.mod.json`（一覧専用・経理/sysadmin のみ・SelectField で
  契約/取引先/部門の名前解決）、`RecurringRun.mod.cs`（BuildPlan/実行の全面改修）
- 会計処理（仕訳の形・科目・冪等判定・入金予定の自動作成）は ADR-0033 までの仕様と完全に同一。
  変更したのは「判定の置き場所」と UI だけ。

## 検証（2026-07-26 実機）

- 2026-07（生成済み月）: 按分振替 1/12 生成済み・月額生成済みが番号つきで表示
- 2026-09（未生成月）: 月額2件=生成予定、年払い2件=按分振替のみ（2/12・3/12）、金額・部門とも期待値どおり
- 実行: 請求書2＋仕訳4（前受按分 D2110/C4020、売上 D1100/C4020+C2200）＋入金予定2を生成、
  一覧が全行「生成済み（仕訳 No つき）」に更新、サマリ表示も正
- 対象外: 下書き契約・無効化契約が理由つきで表示されることを確認
- 検証は DB バックアップ→復元方式で実施（デモデータは無変更）
