# ADR-0038 使用中のマスタは、意味を変えられない

## 状況

**計上済みの仕訳が使っているマスタの「意味を決める列」を、警告なしで変えられた**
（2026-09-04 の探索的テストで実測。[qa/03 L-29](../qa/03_テストで漏らした実例.md)）。
実測したのは 2 つで、どちらも「更新しました」で通り、確認も警告も出なかった。

- 勘定科目 `通信費`（計上済みの明細 1 本）の**科目区分**を 費用 → 資産
- 税区分 `TP`（計上済みの明細 4 本）の**課税区分**を 課税仕入 → 課税売上。
  このとき税区分名は「課税仕入（標準税率）」のままで、**名前と中身が食い違った状態**になる

**壊れるものが 3 つある。**

1. **総勘定元帳の「期間内累計」の意味が、過去の行まで遡って変わる。**
   その画面自身が「資産・負債・純資産の科目は会計年度をまたいで積み上げ、
   収益・費用の科目は会計年度ごとに積み直します」と書いている
2. **不変条件 I-13（損益科目の仕訳明細には部門がある）が、取り返しのつかない形で壊れる。**
   計上済みで部門を持たない資産・負債の明細が**58 本**あり（2026-09-04 実測）、
   そのどれかの科目を収益・費用へ変えた瞬間に I-13 違反になる。
   **計上済みは不変（[ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md)）なのでもう直せない**
3. 過去の仕訳の**税の扱い**が遡って変わる。[20 §2](../20_実装の原則.md) の
   「後日マスタを更新しても過去を再計算しない」は、**税率の版については守られているが、
   税区分そのものの意味については守られていない**

**根は「不変条件を保存時の検査としてだけ書いてきた」ことである。**
I-13 を検査するのは `JournalEntryValidator` で、**マスタを更新する経路にはどの検査も無い**。
明細は正しく作られたが、**あとから前提を動かされないことは誰も守っていなかった。**

## 決定

**計上済みの仕訳明細が 1 本でも参照しているマスタの行は、意味を決める列を変えられない**
（開発者の決定。2026-09-05。**過去の帳簿の数字が遡って変わり、しかも計上済みは直せないから**）。

### 1. 「使用中」は、計上済みの明細があること（開発者の決定。2026-09-05）

**下書きしか参照していない行は変えてよい。** 下書きは直せるからである。
下書きが違反状態になったときは、**計上の関門が拾う**（それが関門の仕事である）。

### 2. 変えられない列と、変えてよい列

**分ける基準は「過去の記録の意味が変わるか」である**
（個々の列への当てはめは Claude が行い、**開発者が承認した。2026-09-08**——
Claude が材料として示したのは、下の表の「なぜ」の欄そのものである）。
**守っている列の現在形は [12 §2](../12_マスタ台帳.md) の表が持つ。ここに置くのは「なぜその列か」の理由である。**

| マスタ | 変えられない | なぜ |
|---|---|---|
| 勘定科目 | `code` | 帳簿の科目コード欄が遡って変わり、外部との突合（取込・申告ソフト）が壊れる |
| | `category`（科目区分） | 累計の積み方（年度をまたぐか積み直すか）と部門の要否（I-13）が決まる |
| | `is_contra`（評価勘定） | **累計の符号そのもの**——`(category IN ('asset','expense')) <> (is_contra = 1)` で借方側か貸方側かが決まる（[10 §6-1](../10_会計ドメイン設計.md)）。入れ替えると過去の累計が全部反転する |
| | `requires_sub_account`（§3 で `uses_sub_account` に改名する） | **どちらの向きも壊れる**。オン→オフは既存の明細の補助科目が宙に浮き、オフ→オンは補助科目を持たない過去の明細が違反になる |
| 補助科目 | `code`・`account_id` | 親の付け替えは **A 科目の補助元帳に穴が空き、B 科目に他人の補助科目が生える**（取引先の `RejectRepoint`。[13 §3-4](../13_取引先設計.md) と同じ形） |
| 部門 | `code`・`is_company_wide` | 「全社共通」は部門別集計での扱いが他と違う枠なので、付け外しで過去の集計の意味が変わる（[10 §9-1](../10_会計ドメイン設計.md)） |
| 税区分 | `code`・`taxation_type`・`rate_kind` | 過去の仕訳の税の扱いが遡って変わる（状況で実測した） |

**変えてよい列**は、4 マスタとも `name`・`is_active`・`display_order`
（`name_kana` があるのは勘定科目と補助科目だけで、部門・税区分の表には無い）。
勘定科目の `default_tax_category_id` と税区分の `default_tax_treatment` も変えてよい——
**入力の初期値でしかなく、計上済みの明細が持つ値は動かない**
（[12](../12_マスタ台帳.md) の「値が入っていない行の穴埋めに使わない」）。

**この表は網羅ではない。** ここに出ていない列（勘定科目の `statement_section`・
`is_cash_equivalent`・`is_fixed_asset`、各表の `created_at` 系）は**まだ決めていない**。
使う実装が入る回に決める——決算書の表示区分は**フェーズ 4**（試算表・決算書）、
現預金科目と固定資産科目のフラグは**フェーズ 4・5**。
**「実装がまだ無い」は「意味が変わらない」ではない**ので、そのとき §2 の基準に当てて判断し直す。

#### 2-1. 名前を変えると、過去の帳簿の表示は変わる（写しを持たないため）

**取引先名だけが写しを持ち、勘定科目名・補助科目名・部門名・税区分名は持たない**
（`journal_lines.partner_name_snapshot` と `journal_entries.partner_name_snapshot` のみ）。
だから科目を改名すると、**過去の帳簿の科目名の表示も変わる。**

**それでよいと考えている。** 取引先名を写したのは**本プロジェクトの選択**である——
消税法 30 ⑧の①相手方の氏名又は名称は**取引先コード等の記号・番号でも差し支えない**
（無条件。消税基本通達 11-6-1。[11 §8](../11_消費税設計.md)・
[ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md) の注記）。
それでも名称で写すのは、**コードだけでは帳簿を読む人が相手を特定できない**からで、
**相手方は取引の当事者そのもの**だから当時の名前で残すほうが読める。
一方、法税規則 55 ① が仕訳帳に求める「勘定科目」は**自社が付けた分類**であり
（条文と出典は [10 §4-2-1](../10_会計ドメイン設計.md)）、
求められているのは**どの科目に記帳したか**という識別で、その識別は `id` と `code` が担っている。

**ただし、これは Claude の読みであって確かめていない。**
市販ソフトが科目名の写しを持つかどうかは**未調査**である（[32 §2](../32_調査のルール.md)）。
**コード体系の調査（B-2 の前にやる）と同じ回で見る。**

> **2026-09-08 追記**（Claude。判断は変わっていない。事実だけが動いた）。
> **弥生会計は科目名の写しを持たない**ことを確かめた——改名すると過年度を含む既存の仕訳の表示が変わる
> （[マスタのコード体系のリサーチ §4](../research/2026-09-08_市販会計ソフト比較_マスタのコード体系.md)）。
> **確かめたのは 1 社だけ**である。本 ADR の読み（科目名は写さない）は、市場の主流と同じ側にあった。

### 3. 補助科目は 2 値。オフなら「持てない」

**`requires_sub_account` を `uses_sub_account` に改名する**（開発者の決定。2026-09-05）。

- **オンの科目だけが補助科目を持て、そのとき必須。オフの科目は持てない**
- 3 値（使う／使える／使わない）にしない。**「持てるが任意」の実務上の需要が思い当たらず**、
  一部の明細だけ補助科目なしを許すと「全補助科目の合計＝科目の残高」が崩れるため

**改名する理由**は、上の決定でこの列の意味が「必須か」から「**使うか**」に変わるからである。
画面のラベルは既に「補助科目を使う」で、**DB の列名だけが「要求する」と言っていた**。
[qa/03 L-27](../qa/03_テストで漏らした実例.md) の穴（オフの科目に補助科目を付けた明細が計上できた）は
関門が無かったことが原因で名前のせいではないが、**読み違えられる名前を残す理由も無い**。

### 4. 関門で拒み、DDL のトリガでも拒む（開発者の決定。2026-09-05）

**2 層に置く。** 関門は利用者のことばで断り、トリガは**アプリを迂回する経路**
（取込・CLI・API）への最後の守りになる。

**トリガを置く先例は [L-25・L-26](../qa/03_テストで漏らした実例.md)** だが、
**あちらは関門を置いていない**——画面から踏めない経路だけの話だったからである。
**こちらは画面から踏めるので、関門のほうが本体で、トリガは追加の守りである。**

文言はこの形にする——**何件あるか**と**次に何をすればよいか**を入れる。
**数える単位は「仕訳明細」である**（伝票ではない。[ADR-0017](0017-仕訳と伝票の呼び分け.md) の呼び分け）。

> この科目には計上済みの仕訳明細が 12 行あります。科目区分は変えられません。
> 新しい科目を作って、以後の仕訳をそちらへ記帳してください。

**断りの文言の作法は [21 §2-6](../21_画面の原則.md) が持つ**——この文例をもとに Claude が起こし、
**開発者が承認した**（2026-09-08）。
**上の文例はこの ADR を書いた時点の形で、その作法には従っていない**——
「勘定科目」を「科目」と呼び、「仕訳」を単独で出している（[ADR-0017](0017-仕訳と伝票の呼び分け.md)）。
**実装の文言は 21 §2-6 に従う。**

> **2026-09-07 追記**（Claude。実装して分かった事実）。
>
> §1・§2・§4 を実装した（docs/04 §1 の A-1）——関門は `MasterMeaningGate`、
> トリガは `trg_accounts/sub_accounts/departments/tax_categories_meaning_frozen_when_posted`（マイグレーション 0011）。
> 同日の自己レビュー（[qa/02 ラウンド 45](../qa/02_自己レビュー記録.md)）で、レビュアのサブエージェントが `INSERT OR REPLACE` と
> `UPDATE OR REPLACE … SET id` が上の 4 本を迂回することをインメモリ SQLite で再現した（[qa/03 L-26](../qa/03_テストで漏らした実例.md) と同じ型）。
> `trg_*_no_replace_used_insert/update` の 8 本を足し（マイグレーション 0012）、`MasterMeaningGuardTests` に固定した。
> **id を指定しない `INSERT` は止めない。**

## 却下した案

| 案 | 却下の理由 |
|---|---|
| 変更を許して監査ログに残す | **遡って帳簿の数字が変わることを記録しても、数字は直らない。** 記録は「何が起きたか」を答えるが、「帳簿が正しいか」には答えない |
| マスタを版で持ち、過去の帳簿は当時の版を見る | **会計ソフトとしては正しい設計**だが、全マスタに有効期間を入れる工事になる。**いま直そうとしているのは探索的テストで見つけた穴**（[04 §1](../04_実装計画と現在地.md) の A-1）であって、マスタの持ち方の作り直しではない。**将来これを採るなら、この ADR を superseded にする** |
| 画面だけで止める（`IsUpdateProtected`） | **画面からの保存は拒まれるが、API を直に叩く経路は未確認である**（[qa/01 F-26](../qa/01_CLB静かな失敗.md) が「守りとして数えてよいとはまだ書けない」と断っている）。**確かめていないものを守りに数えない** |

## 帰結

- **不変条件は「保存時の検査」だけでは守れない。** 不変条件ごとに**それを破れる経路を数える**
  という見方を入れる。I-13 なら「仕訳を保存する」「明細を移す」（L-25 で塞いだ）
  「**科目区分を変える**」（この ADR）の 3 本があった
- **[12 マスタ台帳](../12_マスタ台帳.md) が、守っている列の現在形を持つ**（§2 は「なぜその列か」の理由）
- 移行のために、**直す前のデータがどう振る舞うか**を確かめる標本を開発用 seed に置く
  （オフの科目に補助科目が付いた計上済み明細など）。**seed は生の SQL で入れるので関門を通らない**が、
  **意味の凍結のトリガは `UPDATE` にだけ張り、`REPLACE` 対策の `BEFORE INSERT` が中断するのは
  「その id を計上済みの明細が既に使っている」ときだけである**ので、標本の投入（`INSERT`）は止まらない
  ——id を指定しない `INSERT` では、`BEFORE INSERT` の時点の `NEW.id` が**実在しない値**になり、
  どの明細とも一致しないからである（**SQLite 3.53.1 で実測。`-1` が入る**。
  **仕様上は未定義**なので、値そのものには依存しない書き方にしてある）
