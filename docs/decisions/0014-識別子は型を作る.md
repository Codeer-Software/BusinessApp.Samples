# ADR-0014 識別子は型を作る

## 状況

DB の主キーは `INTEGER`（long）＋自動採番が CLB の規約であり、動かせない
（`Designer/ClaudeCodeForDesigner/Docs/DatabaseGuidelines.md`）。一方で最初の実装は
ドメインの識別子を `string` にしていた。DDL を書いた時点でこの不整合が確定したため、決着させる。

会計コアでは `account_id` / `sub_account_id` / `department_id` / `partner_id` / `tax_category_id` /
`journal_entry_id` / `fiscal_year_id` / `accounting_period_id` が、**同じ形で大量に流れる**。

## 決定

### 識別子ごとに型を作る。生の `long` や `string` を引き回さない

```csharp
public readonly record struct AccountId(long Value);
```

TypeScript のブランド型に相当するもので、**ロジックは持たない**。目的は 1 つだけ、
「別の種類の識別子を渡したらコンパイルが通らない」ことである。

素の `long` だと `Find(departmentId)` のような取り違えがコンパイルを通り、
**数字は出るが中身が違う**という最悪の壊れ方をする。集計・帳票では気づくのが数か月後になる。

置き場所は**その識別子が指す実体を持つモジュール**（[ADR-0013](0013-機能単位のモジュール分割と依存方向.md)）。
`AccountId` は `Accounts/`、`TaxCategoryId` は `ConsumptionTax/` に置く。

### 検証（正の値かどうか）は入れない

`Value > 0` を強制するコンストラクタは**書かない**。

- 識別子を採番するのは DB（`INTEGER PRIMARY KEY AUTOINCREMENT`）であり、負の値や 0 は現実に来ない
- 「未設定」は `default`（`Value` が 0）になるが、これは**コンストラクタを通らない**ので
  ガードでは検出できない。ガードは検出できないものに対する見せかけの安心になる
- 「実在する科目か」は `IAccountLookup.Find` が null を返すことで判る。
  こちらの方が `> 0` よりはるかに強い検査であり、実際に検証で使っているのはこちらである

> **2026-08-26 追記**: `IAccountLookup` は実装に無い。具象の `AccountCatalog.Find` が同じ役を担う（qa/02 R1-14）。

### 未設定の表し方

| 状況 | 表し方 |
|---|---|
| 任意項目（補助科目・部門・取引先） | `SubAccountId?` のように null 許容にする |
| まだ保存していない伝票 | `JournalEntry.Id` を `JournalEntryId?` にして null |
| 必須なのに入っていない | `default`（`Value == 0`）。検証が弾く |

`JournalLine.TaxCategoryId` は必須だが `required` だけでは `default` を防げないので、
`JournalEntryValidator` が `== default` を違反として報告する。

### 識別子とコードを混同しない

`AccountDefinition` は `Id`（DB の主キー）と `Code`（利用者が見る 4 桁の科目コード）を**両方**持つ。
最初の実装は両者を同じ `string` に潰していた。科目コードは利用者が変えうるので、
仕訳が参照するのは必ず `Id` の側である。

## 理由

- **取り違えは静かに壊れる。** 型が違えばコンパイラが止める。会計ロジックの不具合の絶無を期す
  （CLAUDE.md §1）以上、コンパイラに検出させられるものは全部させる
- **コストがほぼゼロ。** `readonly record struct` は 1 行で書け、等値比較・`ToString`・
  ハッシュが自動で付く。ボクシングも起きない
- **WASM に載る**ことを考えても、`long` 1 つ分の構造体なので実行時コストは無い

## 帰結

- 新しいテーブルを足したら、対応する識別子の型も足す。**生の `long` を公開 API に出さない**
- DB との境界（`AccountingCore.Server`）で `long` ↔ 識別子型の変換が要る。
  変換は境界の 1 か所に閉じ込め、ドメインの内側に生の `long` を持ち込まない
- CLB スクリプトからは数値として見えるので、`AccountingCore.Client` のサービス境界でも同じ変換を行う
- 識別子の型はロジックを持たないので、**専用のテストファイルを作らない**。
  実際に使う場所のテストで覆われる（[ADR-0012](0012-テスト方針とカバレッジのゲート.md) の
  「カバレッジを埋めるためのテストを書かない」）
