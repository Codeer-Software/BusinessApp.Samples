# 0012: 銀行明細取込＝ステージング＋仕訳リンク方式（残高照合を一体設計）

- 状態: 採用 / 日付: 2026-07-06

## 背景

D-2（銀行・クレカ明細 CSV 取込→自動仕訳）の構造として、最短実装は「CSV を読んで即仕訳を生成する」変換処理だが、ユーザーから残高照合（MF 最上位プランの機能: 銀行残高・入出金明細と帳簿の預金勘定・仕訳の突合）の要望が出た。残高照合を後付けしようとすると「どの明細がどの仕訳になったか」の対応関係が失われており作り直しになるため、取込の構造を先に決める必要がある。

## 選択肢

1. **直接変換方式**: CSV → 仕訳を即生成。明細は保存しない。実装最小だが、取込済み判定（重複取込防止）も照合もできない
2. **ステージング＋仕訳リンク方式**: 明細を `bank_statement_lines`（ステージングテーブル）に保存し、生成した仕訳の id をリンク列に持つ。仕訳生成は「取込」と「起票」の2段階
3. 照合専用の突合テーブルを別途持つ（明細と仕訳を多対多で対応付け）

## 決定

**選択肢2（ステージング＋仕訳リンク方式）を採用。**

- 明細 CSV は口座マスタ（bank_accounts: 口座⇔勘定科目・補助科目の対応）を指定して `bank_statement_lines` に取り込む（日付・摘要・入金額・出金額・残高・取込元ファイル・重複判定キー）
- 仕訳化は明細行ごとに: マッチングルール（摘要パターン→相手科目・税区分のマスタ）→ 該当なしは AI 科目推定 → ユーザー確認 → 一括起票。生成仕訳の id を明細行の `journal_entry_id` に記録
- 残高照合は画面1枚: 明細側の残高列 vs 総勘定元帳の預金残高の日次比較＋**未起票明細一覧（＝差異の原因リスト）**

## 根拠

- 残高照合・重複取込防止・「未起票明細」の可視化が、リンク列1本からすべて導出できる（残高導出主義 ADR-0004 と同じ思想: 状態を二重に持たず対応関係から導く）
- 経理実務の月次締めでは銀行勘定調整表の突合が必須であり、照合できない取込は市販ソフト代替として片手落ち
- 選択肢3（多対多）は「複数明細→1仕訳」等の高度な消込に必要だが、v1 では 1明細→1仕訳 で実務の大半を回収できる。多対多はリンク列を対応テーブルに昇格すれば移行可能で、後戻りコストが小さい

## 影響

- DDL: `bank_accounts`・`matching_rules`・`bank_statement_lines`（journal_entry_id リンク付き）
- CSV パースは CLB の Excel/ファイル基盤で足りない場合のみ C# 拡張（§2 の原則どおり最小限）
- AI 科目推定は C-1 の Provider 切替基盤（Mock/Claude/AzureOpenAI）を再利用する
