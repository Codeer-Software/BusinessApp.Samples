# ADR-0023: 承認ルート判定のマスタ化（approval_route_rules）

- 日付: 2026-07-14
- 状態: 採用・実装済み（境界値16ケース実機検証済み）
- 関連: ADR-0007（承認ルートの動的解決——テンプレート選択の部分を本 ADR が supersede）、ADR-0016（複数課長 OR 承認）

## 背景（ユーザー指摘 2026-07-13）

「20万円以上なら経費_部長＋総務」のような**条件→テンプレートの対応がどこにも見えない**というユーザーの疑問から、対応表が `ExpenseRequest.mod.cs` の `SelectTemplateName()` に**テンプレート名の文字列直書き**で存在することが露見した。問題点:

1. **柔軟性がない**: 金額の閾値（EXP_APPROVAL_MID/HIGH）は制度閾値マスタにあるが、「どの区分でどのテンプレートを使うか」「区分をいくつに分けるか」はコード修正が必要
2. **壊れやすい**: テンプレートを改名すると申請時に「承認テンプレートが見つかりません」で停止する（名前文字列で結合していた）
3. **見えない**: 管理者がルーティング全体を一覧できる画面がない

ユーザー要件: 「この範囲の金額」「この費目」なら「このテンプレート」をマスタで管理する。分岐条件は金額上限・下限（下限最低0・上限は無制限あり）と費目。**絶対に不具合を入れてはならない場所**なので境界値等の網羅テストを行い、新規作成したテンプレートでも正しく動くことを実証すること。

## 決定

### 1. データモデル: `approval_route_rules`（ddl/260）

| 列 | 意味 |
|---|---|
| priority | **小さい順に評価し、最初に一致した行を採用**（first-match） |
| expense_category_id | 費目（NULL=全費目に一致）。費目指定ルールは汎用ルールより小さい優先度にする運用 |
| min_amount / max_amount | 判定額の範囲。**両端とも「その額を含む」**。min の最低は 0、max NULL=上限なし |
| template_id | 適用テンプレート。**ID 参照**（改名に影響されない） |
| note / is_active | 説明・有効フラグ（無効行はスキップ） |

- 判定額の定義は従来どおり（立替=実費、事前申請=見込み額→実費確定後は実費。`GetJudgeAmount()` 不変）
- seed は旧ロジックの完全移行: 交際費 0〜29,999→課長＋総務／交際費 30,000〜→部長＋総務（優先度10・20）＋全費目 0〜29,999→課長のみ／30,000〜199,999→部長のみ／200,000〜→部長＋総務（優先度100・110・120）。交際費ルールは `is_entertainment=1` の費目ごとに SQL で生成
- **EXP_APPROVAL_MID/HIGH は廃止**（制度閾値から DELETE・090 の seed も撤去）。EXP_OVERRUN_RATE（実費超過110%）はルート選択ではなく再承認発火条件なので存続

### 2. 実装の要点（リスク最小化）

- **変更は `SelectTemplateName()` の中身のみ**。「テンプレート名の文字列を返す」契約を維持したため、承認エンジン本体（ApprovalFlow.mod.cs——申請・再申請・実費超過再承認・OR承認・自己承認回避）は**1行も変更していない**。ルールの template_id → 名前は都度 DB 解決（改名安全）
- 新モジュール `ApprovalRouteRule`（管理画面）: **読取=全員**（申請者のスクリプトがルールを読むため。「参照マスタに読取ゲートを付けない」原則＝レビュー第3弾の教訓）／**書込=sysadmin**。メニューはマスタ管理（システム）＞承認ルート判定（承認フローテンプレートの直後・相互に説明文で誘導）
- 一致ルールなし／参照テンプレート消失時は明示エラートースト（「承認ルート判定に一致するルールがありません」等）を出し申請をブロック（静かな失敗をしない）

## 発見・改善メモ

- **使用済みテンプレートの削除は FK 制約で拒否される**（approval_flow.template_id が参照）。参照整合性としては正しいが、生の「SQLite Error 19: FOREIGN KEY constraint failed」トーストが出る。「使用中のため削除できません」に翻訳するのは将来課題（CLB 側の削除フックの問題として docs/12 候補）
- 同一優先度が複数ある場合の順序は不定。seed は10刻みで採番し、運用でも優先度の一意を推奨（画面説明文に記載済み）

## 影響

- 社内規程の変更（決裁金額の変更・特定費目の特別ルート・新テンプレートの追加）が**マスタ編集だけ**で完結する。「改正に強い」原則（CLAUDE.md §3）の承認ドメインへの適用が完成
- docs/tests/06・07・09・11（承認ルート関連）と ADR-0007 の該当箇所を更新済み

## 追記: 2026-08-09（ADR-0048）

**ADR-0048 でテンプレートの中身が積み上げ方式になった（ルール割り当ては不変）。** 本 ADR で決めた `approval_route_rules` の 5 行——どの費目・どの金額帯でどのテンプレートを使うか——は **1 行も変更していない**。変わったのは各テンプレートが持つ承認段の構成と名前だけ:

| 旧テンプレート名 → 新名称 | 旧ルート → 新ルート |
|---|---|
| 経費_課長のみ → `経費_課長まで` | 課長（変更なし） |
| 経費_部長のみ → `経費_部長まで` | 部長 → **課長 → 部長** |
| 経費_課長＋総務 → `経費_課長まで＋総務` | 課長 → 総務（変更なし） |
| 経費_部長＋総務 → `経費_部長まで＋総務` | 部長 → 総務 → **課長 → 部長 → 総務** |

- 本 ADR の設計（テンプレートを **ID 参照**で結合し、名前文字列に依存しない）のおかげで、**改名しても既存ルールは無傷**だった。上の 3 の目的「壊れやすさの解消」が実地で効いた形。
- 上記「3. 検証」の 16 ケース表は**当時のテンプレート構成での実測記録**であり、現行の期待値ではない（例: R-01/02 の「部長のみ」は現在「課長 → 部長」になる）。現行の承認ルート表は `docs/07_経費精算設計.md` §6、現行の E2E 期待値は `docs/tests/11_E2Eテストシナリオ/01_経費精算/分岐_承認ルート.md` が正。
