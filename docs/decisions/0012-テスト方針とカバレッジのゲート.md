# ADR-0012 テスト方針とカバレッジのゲート

> **2026-08-27 追記**: [ADR-0025](0025-取引先を部品として分ける.md) §6 により、取引先の分割の
> 実装後はゲートを敷く対象プロジェクトが増える（§1 の表・§3 の Include は当時の姿。
> 新しい対象の正典は ADR-0025 §6）。テスト方針そのものは変わっていない。

## 状況

[ADR-0009](0009-専門家レビューの代替手段.md) は「期待値の根拠を何に置くか」を決めた。
決まっていないのは**どこまで検査すれば手を止めてよいか**と、**テストをどこに置くか**である。

会計ロジックの不具合は製品として致命的（CLAUDE.md §1）なので、
「テストを書いたつもりで、実は通っていない行が残っている」状態を機械的に検出したい。

実測（2026-08-23、テスト 56 件時点）では行 81.1% / 分岐 74.1% で、
未到達の約 19% は**すべて本物の未テストロジック**だった。生成コードのノイズではない。

## 決定

### 1. 会計コアは行・分岐とも 100% をゲートにする

| プロジェクト | ゲート |
|---|---|
| `BusinessApp.AccountingCore` | **行 100% / 分岐 100%**。割れたらビルドを落とす |
| `BusinessApp.AccountingCore.Server` | **行 100% / 分岐 100%**（2026-08-24 追加） |
| `BusinessApp.AccountingCore.Client` | 数値ゲートを課さない。画面に近く、実機検証のほうが効く |
| CLB スクリプト（`*.mod.cs`） | 対象外。実機検証で確かめる（そもそも薄く保つのが [ADR-0008](0008-CLBとCSharpライブラリの責務分担.md)） |

**`.Server` にも同じゲートを敷いた理由**（当初は「数値ゲートを課さない」としていた）。

- ここは **DB と CLB に触る層で、静かに壊れる場所そのもの**である。列名の綴り違い・
  NULL の取り違え・トリガとの噛み合わせは、型検査でもレビューでも落ちない
- 本物の DDL と初期データを使い捨ての SQLite に流す土台（`BusinessApp.TestSupport`）を
  作ったので、**「DB があるから書けない」という言い訳が消えた**。偽の問い合わせで固めるのではなく、
  本物の SQL を本物のスキーマに流す
- 実際、この層は実装中に 3 回続けて壊れた（[qa/01](../qa/01_CLB静かな失敗.md) C-12・F-11〜F-13）。
  **一度壊れた場所は、また壊れる**

### 2. 100% は下限であって、十分性ではない

**100% が意味するのは「未テストの行がゼロ」だけである。** 目的は不具合をなくすことであって、
数字を満たすことではない。十分性は [ADR-0009](0009-専門家レビューの代替手段.md) の
3 種のテスト（ゴールデン・境界・性質）と、[11 §9](../11_消費税設計.md) の観点が受け持つ。

したがって次を**禁止**する。

- **ゲッターを呼ぶだけのテスト**、`ToString` を舐めるだけのテストなど、カバレッジを埋めるためのテスト
- カバーできない行を通すためだけの `[ExcludeFromCodeCoverage]`

**不正な入力に対する挙動を固定するテストは、埋め合わせではない。** 未知の列挙値を渡すと
例外になる、といった検査は「誤った値を黙って通さない」という実際の振る舞いを守っている。

カバーできない行が出たら、**まずその行が要るのかを疑う**。使われていない公開メソッドは、
テストを書く前に消すか、使う場所を作るかのどちらかである。

### 3. 計測の設定

ゲートはテストプロジェクトの `.csproj` に埋め、**`dotnet test` を打つだけで計測と判定が走る**ようにする。
別コマンドにすると流し忘れる。

| 設定 | 理由 |
|---|---|
| `Include=[BusinessApp.AccountingCore]*` / `[BusinessApp.AccountingCore.Server]*` | 対象は会計コアだけ。テストの土台（`TestSupport`）も CLB 由来のコードも数えない |
| `SkipAutoProps=true` | 未設定の `init` プロパティを穴に数えない |
| `Threshold=100` / `ThresholdType=line,branch` / `ThresholdStat=total` | 割れたら MSBuild エラーで落ちる |

**`ExcludeByAttribute` は置かない**（2026-08-25 改訂）。

当初は `record` のコピーコンストラクタを除くために
`ExcludeByAttribute=CompilerGeneratedAttribute` を置いていた。2026-08-23 の実測では
「除外されるのはコピーコンストラクタ 8 個だけ」で正しかったが、**この設定は
`async` のステートマシンと `yield return` のイテレータも同時に除外する**。
当時のコードにその 2 つが無かったので副作用が見えなかっただけである。

`AccountingCore.Server`（ほぼ全てが `async`）を足した時点で、**計測対象は 38 クラス中 6 クラスに落ち、
`JournalEntryStore` は同期の小さなヘルパ 1 つしか測られていなかった**。
それでも「100%」と表示され、ゲートは緑だった。除外をやめたところ、
**一度も実行されていない防御コードが 4 か所**出てきた（qa/03 L-07）。

- **設定の影響範囲を「そのときの実測」で固定しない。** コードの性質が変われば結論も変わる
- 除外をやめた代償として、`with` を一度も使わない `record` のコピーコンストラクタが穴に残る。
  これは `Conventions/GeneratedCopyConstructorTests` が 1 本だけ触れる
  （§2 の「カバレッジを埋めるためのテストを書かない」に対する、理由つきの唯一の例外）。
  **閾値を下げて逃げない。** 下げると、これから増える本物の穴まで一緒に隠れる

### 4. ユニットテストは対象と同じ場所・同じ名前に置く

```
src : BusinessApp.AccountingCore/Primitives/Yen.cs
test: BusinessApp.AccountingCore.Tests/Primitives/YenTests.cs
      名前空間も BusinessApp.AccountingCore.Tests.Primitives に揃える
```

- **1 ソースファイル ＝ 1 テストファイル**。ソース側も 1 ファイル 1 公開型に保つ。
  ただし**その型と一体の小さな付随型は同居してよい**——`XxxExtensions`、および
  引数・戻り値としてしか現れない `record`（`CorrectionContext`・`AmendmentAvailability`・
  `AmendResult` など）。**別ファイルに散らすと、対になっている型どうしが離れて読めなくなる。**
  同居してよいのは「その型を読むときに一緒に読むもの」だけで、
  独立した振る舞いを持つ型は分ける（2026-08-26 に明文化。実装は最初からこの形だった）
- テスト専用のフォルダ（`Fixtures/` `Golden/` `Conventions/`）は対象外

**この規約はコンベンションテスト（`Conventions/TestLayoutTests.cs`）が機械的に検査する。**
検査は「テスト → ソース」の**一方向だけ**にする。許容リストは必ず腐るので、持たなくてよい設計を選ぶ。

**逆方向は機械では守れない。** 逆方向（テストの無いソース）はカバレッジが受け持つ建前だが、
`record` のデータ型は `SkipAutoProps` と生成メンバの除外により**計測対象の行がほとんど無い**ので、
テストファイルが無くても 100% は緑になる。データだけの型に専用のテストを作らないのは
妥当な判断（[ADR-0014](0014-識別子は型を作る.md) の識別子型も同じ）なので、
**「ロジックを持つ型には専用のテストを置く」を人が守る規約**として残す。

### 5. `Golden/` に置くのは通しの設例だけ

[ADR-0009](0009-専門家レビューの代替手段.md) は「設例 1 件 = ファイル 1 つ」を定めた。
これを**帳票・申告書レベルの、入力一式と期待値一式を持つ設例**に限って適用する。
控除割合を 1 つ引くような設例は、対象型のユニットテストに出典つきで書く。

ファイルを分ける目的は「設例の入力と期待値を 1 箇所で追えるようにすること」であり、
値が 1 つの設例には効かないためである。

### 6. テストしやすさを設計の判断材料にする

- **依存はインターフェースで受け取る**（`IAccountLookup` が例）。ただし
  **抽象を置くのは I/O 境界と、実装が差し替わる場所だけ**にする。
  メモリ上の値の集まりに `IXxx` を被せるのは、テストを楽にせず読みにくくするだけである

  > **2026-08-26 追記**: 上の例に挙げた `IAccountLookup` は、**それ自体が「被せてはいけない側」だった**ので
  > 実装から消した（qa/02 R1-14）。いまは具象の `AccountCatalog` を `PostingContext` に載せて渡している。
  > 残っているインターフェースは `IEffectiveDatedRule` 1 本だけである。
- **時刻は引数か `TimeProvider` で受け取る。** `DateTimeOffset.UtcNow` を直接呼ばない。
  入力年月日（[10 §2](../10_会計ドメイン設計.md)）はシステムが決める値なので、
  テストから固定できないと検証できない
- **検証は違反を全件返す純粋関数**にする。例外で打ち切らない

### 7. CI は置かず、コミット前フックで検査する

開発者が 1 人で、Claude はコミットのみ・push は開発者が行う運用（[30 §7](../30_作業のルール.md)）では、
GitHub Actions は**壊れた状態が積まれてから気づく**ことになる。代わりに
`tools/git-hooks/pre-commit` で `lint_secrets` → `lint_docs` → `lint_design` → `dotnet test`（カバレッジ込み）を流す。

> **2026-08-26 追記**: その後、稼働 DB との同値検査（ADR-0020）・ミューテーション（§8）・
> 削除ガードを足して**現在は 7 段**である。段の一覧は [`tools/README`](../../tools/README.md) が持つ
> （ここに写すと必ず腐るため）。
>
> **2026-09-06 追記**: 凍結ファイルの検査を足して **8 段**になった。
> **上の「現在は 7 段」がまさに腐った**——段数は数えずに `tools/README` を引くこと。

- フックは `.git/hooks` ではなく **`tools/git-hooks/` に置いて追跡する**。
  clone 後に `git config core.hooksPath tools/git-hooks` で有効にする
- `--no-verify` で迂回できることは承知の上で、**規律の代替ではなく「うっかり」を防ぐ装置**とする
- **フックは作業ツリーを検査する（ステージ内容ではない）。** 一部だけステージしてコミットすると、
  緑になったコミットが緑である保証は無い。`git stash` を挟む実装は失敗時に作業を失う危険があり、
  得より損が大きいので採らない。**部分コミットをするときは人が確認する**

### 8. ミューテーションテストをコミット前に毎回流す（2026-08-24 追加）

カバレッジ 100% は「未テストの行がゼロ」しか言わない。**「壊したら気づくか」**は
ミューテーションテスト（Stryker.NET）で測る。コードに機械的な変異（`<=` → `<`、行の削除、
`||` → `&&` など）を入れてテストを走らせ、**緑のまま生き残った変異＝検査していない場所**を出す。

- **コミット前フックで毎回流す**（会計コア約 30 秒＋サーバ約 1 分。
  当初は「フェーズの区切りで」としたが、この速さなら毎回で運用できる、という
  開発者の判断で常時化した。耐え難く遅くなったら、そのとき見直す）
- 手で流すときはテストプロジェクトのディレクトリで
  `dotnet stryker --project {対象}.csproj`（グローバルツール `dotnet-stryker`）。
  レポートは `StrykerOutput/`（Git 追跡外）に出る
- **スコアの下限はラチェットである。** 生き残りには**許容してよいノイズ**が混ざるため、
  下限は「現状の生き残り」のすぐ下に置き、割れたら (a) テストを足して戻すか
  (b) 生き残りを読んで、許容と判断した理由とともに下限を動かす。**黙って下げない**
  - 許容: 違反・例外の**文言**（テストはコードで表明し、文言に依存しない方針のため）／
    `ThrowIfNull` 等の防御ガード／等価な変異（並び替えが結果に影響しない箇所など）
  - 許容しない: 境界（`<=` ↔ `<`）・条件・返り値・書き込みの変異が生き残ったら、
    それは [qa/03](../qa/03_テストで漏らした実例.md) 行きの実漏れである
- **ラチェットを動かすコミットでは、生き残りの一覧を残す**（開発者の指示の系。2026-09-02 に規則化）。
  フックは `--reporter progress` なので**画面に数字しか出ず、あとから「何が生き残っていたか」を
  読み直せない**——上げた回の根拠が「そのとき見た」だけになる（[qa/02 R28-18](../qa/02_自己レビュー記録.md)）。
  下限を動かす回だけ `--reporter json` を 1 回流し、生き残りを
  [qa/02](../qa/02_自己レビュー記録.md) にそのラウンドの記録として貼る
  - **上げた理由は「実測がそうだった」と書く。** 「文言まで表明したから」は誤りである——
    上の許容リストが**文言の変異をノイズと決めている**ので、文言のテストはスコアを動かさない
- 初回（2026-08-24）の実績: カバレッジ 100% の状態で**実漏れが 3 件**出た。
  境界 0 の縮退（qa/03 L-02 の変種）、重大度を全部警告にしても緑、採番ガードの `||` → `&&`。
  修正後のスコアは会計コア 76.7% / サーバ 93.8% で、下限は 75 / 92 に置いた
  （**2026-08-26 追記**: その後ラチェットを回して**現在の下限は 76 / 94**。値の正典は `pre-commit`）

## 理由

- **`AccountingCore` は外部依存ゼロの純粋ライブラリなので、到達不能なコードが原理的に存在しない。**
  100% に届かないなら「テストしていないロジック」か「要らないコード」のどちらかで、どちらも直すべきである
- **95% のような中途半端な閾値は 5% の逃げ道を作る。** そこに溜まるのは防御コードと稀な分岐、
  つまり最も危ない場所である
- **実際に効いている。** 100% へ埋める過程で、`FiscalCalendar.IsPostable` と
  `JournalEntryValidator` の判断が食い違う欠陥（会計期間はあるのに会計年度が無いとき、
  前者は計上不可・後者は素通し）を検出した。設例ベースのテストでは見つからない類である

## 帰結

- テストを増やすほど「テストしやすい設計」に寄る。**寄らないなら設計が悪いというサイン**として扱う
- 新しい公開型を足したら、同じ場所・同じ名前のテストファイルを作る。作らなければコミットが落ちる
- カバレッジが 100% を割ったコミットは作れない。**割ったまま先へ進む選択肢を残さない**
- 検証ループ（[31 §1](../31_検証のルール.md)）の「C# ロジック」は、`dotnet test` 1 本でテスト・カバレッジ・
  配置規約の 3 つを見ることになる
