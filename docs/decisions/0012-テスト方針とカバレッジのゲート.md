# ADR-0012 テスト方針とカバレッジのゲート

## 状況

[ADR-0009](0009-専門家レビューの代替手段.md) は「期待値の根拠を何に置くか」を決めた。
決まっていないのは**どこまで検査すれば手を止めてよいか**と、**テストをどこに置くか**である。

会計ロジックの不具合は製品として致命的（CLAUDE.md §1）なので、
「テストを書いたつもりで、実は通っていない行が残っている」状態を機械的に検出したい。

実測（2026-08-23、テスト 56 件時点）では行 81.1% / 分岐 74.1% で、
未到達の約 19% は**すべて本物の未テストロジック**だった。生成コードのノイズではない。

## 決定

### 1. `AccountingCore` は行・分岐とも 100% をゲートにする

| プロジェクト | ゲート |
|---|---|
| `BusinessApp.AccountingCore` | **行 100% / 分岐 100%**。割れたらビルドを落とす |
| `.Server` / `.Client` | 数値ゲートを課さない。「サーバの関門を必ず通る」ことを結合テストで担保する |
| CLB スクリプト（`*.mod.cs`） | 対象外。実機検証で確かめる（そもそも薄く保つのが [ADR-0008](0008-CLBとCSharpライブラリの責務分担.md)） |

### 2. 100% は下限であって、十分性ではない

**100% が意味するのは「未テストの行がゼロ」だけである。** 目的は不具合をなくすことであって、
数字を満たすことではない。十分性は [ADR-0009](0009-専門家レビューの代替手段.md) の
3 種のテスト（ゴールデン・境界・性質）と、[06 §9](../06_消費税設計.md) の観点が受け持つ。

したがって次を**禁止**する。

- **ゲッターを呼ぶだけのテスト**、`ToString` を舐めるだけのテストなど、カバレッジを埋めるためのテスト
- カバーできない行を通すためだけの `[ExcludeFromCodeCoverage]`

**不正な入力に対する挙動を固定するテストは、埋め合わせではない。** 未知の列挙値を渡すと
例外になる、といった検査は「誤った値を黙って通さない」という実際の振る舞いを守っている。

カバーできない行が出たら、**まずその行が要るのかを疑う**。使われていない公開メソッドは、
テストを書く前に消すか、使う場所を作るかのどちらかである。

### 3. 計測の設定

ゲートはテストプロジェクトの `.csproj` に埋め、**`dotnet test` を打つだけで計測と判定が走る**ようにする。
別コマンドにすると流し忘れる。

| 設定 | 理由 |
|---|---|
| `Include=[BusinessApp.AccountingCore]*` | 対象は純粋ドメインだけ |
| `SkipAutoProps=true` | 未設定の `init` プロパティを穴に数えない |
| `ExcludeByAttribute=CompilerGeneratedAttribute` | `record` のコピーコンストラクタを除く |
| `Threshold=100` / `ThresholdType=line,branch` / `ThresholdStat=total` | 割れたら MSBuild エラーで落ちる |

`CompilerGeneratedAttribute` の除外は**実測で影響範囲を確認済み**である。
除外されるのは `record` のコピーコンストラクタ 8 個だけで、**ラムダは 1 つも除外されない**
（2026-08-23 実測）。ラムダが消える設定なら、LINQ 述語だらけの検証コードで数字が嘘になるため採れない。

### 4. ユニットテストは対象と同じ場所・同じ名前に置く

```
src : BusinessApp.AccountingCore/Primitives/Yen.cs
test: BusinessApp.AccountingCore.Tests/Primitives/YenTests.cs
      名前空間も BusinessApp.AccountingCore.Tests.Primitives に揃える
```

- **1 ソースファイル ＝ 1 テストファイル**。ソース側も 1 ファイル 1 公開型に保つ
  （`XxxExtensions` だけは対象の型と同居してよい）
- テスト専用のフォルダ（`Fixtures/` `Golden/` `Conventions/`）は対象外

**この規約はコンベンションテスト（`Conventions/TestLayoutTests.cs`）が機械的に検査する。**
検査は「テスト → ソース」の**一方向だけ**にする。許容リストは必ず腐るので、持たなくてよい設計を選ぶ。

**逆方向は機械では守れない。** 逆方向（テストの無いソース）はカバレッジが受け持つ建前だが、
`record` のデータ型は `SkipAutoProps` と生成メンバの除外により**計測対象の行がほとんど無い**ので、
テストファイルが無くても 100% は緑になる。データだけの型に専用のテストを作らないのは
妥当な判断（[ADR-0014](0014-識別子は型を作る.md) の識別子型も同じ）なので、
**「ロジックを持つ型には専用のテストを置く」を人が守る規約**として残す。

### 5. `Golden/` に置くのは通しの設例だけ

[ADR-0009](0009-専門家レビューの代替手段.md) は「設例 1 件 = ファイル 1 つ」を定めた。
これを**帳票・申告書レベルの、入力一式と期待値一式を持つ設例**に限って適用する。
控除割合を 1 つ引くような設例は、対象型のユニットテストに出典つきで書く。

ファイルを分ける目的は「設例の入力と期待値を 1 箇所で追えるようにすること」であり、
値が 1 つの設例には効かないためである。

### 6. テストしやすさを設計の判断材料にする

- **依存はインターフェースで受け取る**（`IAccountLookup` が例）。ただし
  **抽象を置くのは I/O 境界と、実装が差し替わる場所だけ**にする。
  メモリ上の値の集まりに `IXxx` を被せるのは、テストを楽にせず読みにくくするだけである
- **時刻は引数か `TimeProvider` で受け取る。** `DateTimeOffset.UtcNow` を直接呼ばない。
  入力年月日（[04 §2](../04_会計ドメイン設計.md)）はシステムが決める値なので、
  テストから固定できないと検証できない
- **検証は違反を全件返す純粋関数**にする。例外で打ち切らない

### 7. CI は置かず、コミット前フックで検査する

開発者が 1 人で、Claude はコミットのみ・push は開発者が行う運用（CLAUDE.md §3-4）では、
GitHub Actions は**壊れた状態が積まれてから気づく**ことになる。代わりに
`tools/git-hooks/pre-commit` で `lint_secrets` → `lint_docs` → `lint_design` → `dotnet test`（カバレッジ込み）を流す。

- フックは `.git/hooks` ではなく **`tools/git-hooks/` に置いて追跡する**。
  clone 後に `git config core.hooksPath tools/git-hooks` で有効にする
- `--no-verify` で迂回できることは承知の上で、**規律の代替ではなく「うっかり」を防ぐ装置**とする
- **フックは作業ツリーを検査する（ステージ内容ではない）。** 一部だけステージしてコミットすると、
  緑になったコミットが緑である保証は無い。`git stash` を挟む実装は失敗時に作業を失う危険があり、
  得より損が大きいので採らない。**部分コミットをするときは人が確認する**

## 理由

- **`AccountingCore` は外部依存ゼロの純粋ライブラリなので、到達不能なコードが原理的に存在しない。**
  100% に届かないなら「テストしていないロジック」か「要らないコード」のどちらかで、どちらも直すべきである
- **95% のような中途半端な閾値は 5% の逃げ道を作る。** そこに溜まるのは防御コードと稀な分岐、
  つまり最も危ない場所である
- **実際に効いている。** 100% へ埋める過程で、`FiscalCalendar.IsPostable` と
  `JournalEntryValidator` の判断が食い違う欠陥（会計期間はあるのに会計年度が無いとき、
  前者は計上不可・後者は素通し）を検出した。設例ベースのテストでは見つからない類である

## 帰結

- テストを増やすほど「テストしやすい設計」に寄る。**寄らないなら設計が悪いというサイン**として扱う
- 新しい公開型を足したら、同じ場所・同じ名前のテストファイルを作る。作らなければコミットが落ちる
- カバレッジが 100% を割ったコミットは作れない。**割ったまま先へ進む選択肢を残さない**
- 検証ループ（CLAUDE.md §4）の「C# ロジック」は、`dotnet test` 1 本でテスト・カバレッジ・
  配置規約の 3 つを見ることになる
