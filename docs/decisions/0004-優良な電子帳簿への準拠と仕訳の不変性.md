# ADR-0004 優良な電子帳簿への準拠と仕訳の不変性

## 状況

「他の会計ソフトの代替になる」ことを目標にする以上、**優良な電子帳簿の要件を満たさない製品を
ユーザーがわざわざ選ぶ理由がない**。優良な電子帳簿には次の 3 要件がある。

1. 訂正・削除の履歴の確保
2. 帳簿間の相互関連性の確保
3. 検索機能の確保（取引年月日・取引金額・取引先／範囲指定／2 項目以上の組み合わせ）

このうち ① は、**データモデルの根幹**を決める。後から追加することが構造的にできない。

## 決定

**優良な電子帳簿の要件充足を必須要件とする。** 訂正・削除の履歴の確保は、国税庁が認める方式のうち
**「データを直接訂正・削除できないシステムとし、訂正・削除は当初データを特定する情報を付加した
反対仕訳の入力により行う」方式**を採用する。

具体的には次を会計コアの不変な前提とする。

| 対象 | 規則 |
|---|---|
| 計上済み（posted）の仕訳 | **一切変更・削除できない**（UPDATE / DELETE を発行しない） |
| 訂正 | 原仕訳を特定する情報を持つ**反対仕訳**を起こし、正しい内容で**再計上**する |
| 取消 | 原仕訳を特定する情報を持つ**反対仕訳**のみを起こす |
| 下書き（draft）の仕訳 | 自由に編集・削除できる（計上前は帳簿ではない） |
| 仕訳の識別子 | 計上時に採番し、以後**不可逆**（欠番を埋め直さない・再利用しない） |
| 入力年月日 | システムが自動付与し、**利用者が訂正・削除できない** |
| 通常の業務処理期間の経過後の入力 | その事実を記録する |

**この規則を迂回する経路を作らない。** CSV 取込・API・管理画面・スクリプトのいずれからも
計上済み仕訳を書き換えられないようにし、**サーバ側で強制**する（クライアント側の制御だけに頼らない）。

## 理由

- 3 つの認められる方式（履歴を別テーブルに残す／訂正削除できないシステム＋反対仕訳／
  7 日以内の例外運用）のうち、**反対仕訳方式が最も検証しやすく、会計的にも正しい**。
  「履歴テーブルに残す」方式は、履歴の欠落・改ざんを防ぐ仕組みを別途作る必要があり、
  かつ「帳簿の記録が書き換わる」こと自体が会計の慣行に反する
- 不変（immutable）にすると、**残高＝仕訳の集計**という関係が壊れなくなる。
  更新を許すと「集計済みの残高キャッシュとの不整合」「締め後の遡及変更」といった
  会計ソフト最悪の不具合クラスが構造的に発生しうる
- 不変前提はテストを劇的に単純にする。「ある時点の帳簿」が入力の関数として決まるため、
  ゴールデンテストが安定する

## 帰結

- **UI の設計が変わる。** 「編集」ボタンではなく「訂正」「取消」という操作になる。
  利用者にとって不慣れな面があるため、訂正の導線は特に丁寧に作る
- **赤伝（反対仕訳）が帳簿に残る。** 仕訳帳・総勘定元帳には原仕訳・反対仕訳・再計上の 3 本が並ぶ。
  これは制度上正しい姿だが、「一覧が見にくい」という要求が必ず出る。
  **表示上の集約（訂正済みの伝票をグループ化して見せる）で対応し、データは畳まない**
- **検索要件**（取引年月日・取引金額・取引先／範囲／組み合わせ）を、仕訳帳・総勘定元帳・
  補助簿のすべてで満たす必要がある。CLB の検索レイアウトで実現する
- **帳簿間の相互関連性**のため、仕訳に一貫した識別子を持たせ、元帳・補助簿・試算表から
  仕訳へドリルダウンできるようにする。他部品から投入された仕訳は、
  元伝票を特定する情報（部品名＋外部伝票 ID）を保持する
