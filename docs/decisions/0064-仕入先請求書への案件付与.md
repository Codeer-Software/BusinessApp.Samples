# ADR-0064: 仕入先請求書に案件を持たせ、生成する仕訳の全明細へ引き継ぐ

- 日付: 2026-08-16
- 状態: 採用
- 関連: ADR-0029（伝票が部門を持つ）／ADR-0056（損益科目の行には部門が要る）／
  `docs/14_市販ソフト比較レビュー.md` §4・§7（この問題を見つけた比較レビュー）／
  `docs/issues/2026-08-16_市販ソフト比較レビューの改善候補.md` P-1・M-1

## 背景（問題）

**案件別損益（`Management/ProjectProfit`）の原価に、外注費・SES 仕入がまったく乗っていなかった。**

案件別損益の「直課費用」は次の SQL で集計している（`ProjectProfit.Query.sql`）:

```sql
SELECT l.project_id, SUM(CASE WHEN l.dc = 'D' THEN l.amount ELSE -l.amount END) AS direct_cost
FROM journal_lines l ... WHERE a.account_type = 'expense' AND l.project_id IS NOT NULL
```

**SQL は正しい。データ側に案件が入らないのが原因だった。**
`Purchasing/VendorInvoice`（仕入先請求書）に案件の列が無く、
「未払計上」ボタンが作る仕訳の明細は `project_id` が必ず NULL になっていた。

### 実測（2026-08-16・デモ DB）

| 確認したこと | 結果 |
|---|---|
| 確定仕訳の**費用科目**の明細で案件が付いている行 | **36 行中 3 行だけ**（旅費交通費 1・新聞図書費 1・減価償却費 1 ＝ 経費精算と固定資産の経路のみ） |
| 確定仕訳の**収益科目**の明細で案件が付いている行 | 18 行中 14 行（売上側は業務からの自動仕訳が案件を持つ） |
| 外注費 500,000 円（基幹システム改修 6 月分・仕訳 No.6） | **`project_id` が NULL** |

結果として「基幹システム改修」は売上 1,250,000 に対し直課費用 8,000（旅費交通費のみ）となり、
**粗利が 50 万円過大**に出ていた。

### なぜ重いか

ペルソナ（`docs/02`）の売上は受託 60%・SES 25% で、**外注費と SES 仕入が最大コスト**。
痛点 #2 は「工数原価が会計とつながっていない。人件費の案件配賦がどんぶり」。
CLAUDE.md §1 と企画概要 §2 は「市販ソフトでは見えない案件別損益」を最大の売りに据えている。

つまり**いちばん見せたい数字がいちばん狂っていた**。しかも画面は
「案件別の損益（売上・直課費用・配賦人件費・粗利）を確認できます」としか書いておらず、
原価が欠けていることをどこにも断っていない——**もっともらしい数字が黙って出る**状態だった。

## 決定

**仕入先請求書のヘッダに案件（`project_id`・任意）を持たせ、
未払計上仕訳と支払仕訳の「全明細」へ引き継ぐ。**

- 先例は `ddl/200_expense_project.sql`（経費申請への案件選択）。**同じ形に揃える**。
- 引き継ぐ範囲は**全明細**（費用行・仮払消費税行・買掛金行、および支払仕訳の買掛金行・預金行）。
  - 案件別損益が見るのは費用科目と収益科目だけなので、資産・負債の行に案件が入っても数字は動かない。
  - 一方で**総勘定元帳を案件で絞ったときに、その案件の入出金まで追える**という実利がある。
  - 経費精算（`ExpenseRequest.GenerateJournal`）も全明細に付けており、流儀が揃う。
- `.Value` はレイアウト状態によって未ロードのことがあるため、
  null なら DB から取り直す（`ResolveProjectId()`。経費精算と同じ対処）。
- 「この請求書を複製」は案件と部門もコピーする（反復的な外注の月次請求で毎回選び直さずに済む）。
- 一覧に「案件」列を足す（部門列の隣）。

### 既存データの是正

デモ DB の仕入先請求書 5 件のうち案件性があるのは `VG-2026-071`（外注費・基幹システム改修）だけで、
残り 4 件（消耗品費・広告宣伝費・雑費）は社内経費なので案件が無いのが正しい。
`ddl/590_vendor_invoice_project.sql` で `VG-2026-071` と、そこから生成済みの仕訳
（未払計上 No.6 / 支払 No.7）の全明細に `PRJ-001` を遡って入れた。

**適用後**: 基幹システム改修の直課費用が **8,000 → 508,000 円**。

## 退けた案

| 案 | 退けた理由 |
|---|---|
| **仕入先請求書を明細行化し、行ごとに案件を持たせる** | 1 枚の請求書に複数案件が載るケース（外注先からの月次請求）を扱えるので理想。ただし未払計上仕訳の生成・複製・既存データ移行・体験シナリオ 4 本に波及し、**E-1（経費申請の明細行化）と同規模の設計変更**になる。ヘッダ 1 本でも本件の欠陥（案件別損益に原価が乗らない）は解消するので、**まずここまでを入れ、明細行化は残件として P-1 に残す** |
| 費用科目から案件を推測する | 外注費だからといって案件が一意に決まらない（社内案件・複数案件）。推測は誤配賦を生むだけ |
| 仕訳を手で直す運用にする | 自動生成された仕訳を毎回手で直すのは、業務と会計の一体化という企画の芯（`docs/01` §2.1）と正面から矛盾する |
| 案件を必須にする | 社内経費の請求書（消耗品費・印刷代など）は案件を持たないのが正しい。必須にすると全社共通のダミー案件を作ることになり、集計を汚す |

## 影響

| 対象 | 影響 |
|---|---|
| `Management/ProjectProfit` | **直課費用に外注費・SES 仕入が乗るようになる**（本件の目的） |
| `Accounting/GeneralLedger` | 案件で絞ったときに買掛金・預金の動きも見えるようになる |
| `Purchasing/PaymentSchedule`・`FbExport`・`Management/CashFlowForecastData` | 影響なし（いずれもヘッダの金額しか見ていない） |
| `Sales/Receipt`（相殺入金） | 影響なし（買掛金の消込は金額ベース） |
| 体験シナリオ `05_購買_支払/01`・`03` | 案件欄が増えたので画面説明を追記 |

## 残件

**1 枚の請求書に複数案件を載せられない。** 外注先からの月次請求で案件が 3 つあるときは、
請求書を 3 件に分けて登録する必要がある。明細行化は
`docs/issues/2026-08-16_市販ソフト比較レビューの改善候補.md` の P-1 に残件として記載した。
