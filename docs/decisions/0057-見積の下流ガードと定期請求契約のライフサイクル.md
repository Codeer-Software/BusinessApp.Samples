# ADR-0057: 見積の下流ガードの対称化と、定期請求契約のライフサイクル整備

- 日付: 2026-08-14
- 状態: 採用
- 関係: `docs/issues/2026-08-09_体験シナリオ執筆中に見つかった改善候補.md` C-1 / C-8 / C-9 ／
  ADR-0026（状態遷移のボタン一元化）／ADR-0027（ボタン2色規約）／ADR-0032（入金予定の自動作成）／
  ADR-0033（定期請求由来の請求書は「発行を取り消す」）／ADR-0051（未確定入金の除外）

## 背景

体験シナリオ執筆中に見つかった改善候補の C セクション（ガードや導線の穴）のうち、
定期請求契約まわりの 3 件をまとめて扱う。調査の過程で**既存バグが 1 件**見つかったので併せて是正する。

### C-1: 1 つの見積から、定期請求契約と受注の両方を作れてしまう

見積から作れる下流は `SalesOrder`（受注）と `RecurringBilling`（定期請求契約）の 2 つだけだが、
ガードが非対称だった。

| ハンドラ | 受注を確認 | 契約を確認 |
|---|---|---|
| `ConvertToRecurring_OnClick`（契約にする） | ✅ | ✅ |
| `ConvertToOrder_OnClick`（受注にする） | ✅ | ❌ |
| `RevertToDraft_OnClick`（下書きに戻す） | ✅ | ❌ |

「契約にする」だけが両方を見ており、他の 2 つは受注しか見ていない。単なる書き忘れである。

このため 2 クリックで二重変換が成立した。①契約にする → ②下書きに戻す（受注が無いので通る）→
③受注にする（受注が無いので通る）。**同じ取引が定期請求と検収→請求の両経路で二重に売上計上されうる。**
デモ DB の Q-26-009「請求クラウドサービス」が実際にこの状態（下書きなのに確定済の契約を持つ）だった。

### C-8: 定期請求契約に削除導線が無い

`RecurringBilling.mod.json` は `CanDelete: true` だが、詳細レイアウトに削除ボタンが無く、
一覧側も両フレームで `ListFieldDesign.CanDelete: false`。**許可はあるのに導線がゼロ**で、
一度作った契約は永久に残った。見積（下書きのみ）・受注（検収が無いときのみ）には削除ボタンがあり、
定期請求契約だけが抜けていた。

あわせて `Revert_OnClick`（下書きに戻す）が請求実績を見ておらず、ダイアログも
「生成済みの請求書・仕訳には影響しません」と**請求実績があっても戻せることを明示していた**。
下書きは一般ユーザーも編集できるため、これは「確定済の変更は経理のみ」という権限が
ボタン 1 つで抜けられることを意味する。

### C-9: 一覧に検索条件が無く、行数が増え続ける

販売系モジュールで唯一 `SearchLayouts` の `Rows` が空だった（他は 6 条件前後）。
一覧は `LimitCount: 50` の Id 降順なので、契約が 50 件を超えると古いものへ到達できない。

## 決定

### 1. 見積の下流は「1 つだけ」を不変条件にし、3 ハンドラを対称化する（C-1）

`Quote.mod.cs` に `FindDownstreamLabel()` を置き、変換系・巻き戻し系のすべてがこれで判定する。
`RevertToDraft_OnClick` の `accepted` 限定はやめ、**状態に関わらず**下流の有無を見る
（旧ガードをすり抜けて draft のまま下流を持つデータが既に存在したため）。

### 2. 削除は「下書き かつ 請求書 0 件」、権限は作成者本人＋経理（C-8）

| 操作 | 条件 |
|---|---|
| 削除 | `draft` かつ請求書が **1 件も無い**（取消済み含む） |
| 下書きに戻す | **取消（void）でない**請求書が 1 件も無い |

判定を分けた理由:

- **削除**は `invoices.recurring_billing_id` の外部キーが現実の制約。取消済みの行が残っていても
  物理削除は失敗するので、void も数える（数えないと生の SQLite エラーが画面に出る）
- **下書きに戻す**は業務判断。`RecurringRun` は void を「未請求」とみなして再生成の対象に戻すので、
  巻き戻しの可否も同じ流儀に揃える

権限を作成者本人にも広げたのは、下書きは一般ユーザーも作れるため。自分が作ったものを
自分で片付けられないのは不便で、かつ下書きは実行対象外なので実害がない。

なお定期請求由来の請求書には「下書きに戻す」が無く、巻き戻し手段は「発行を取り消す」＝**物理削除**
（ADR-0033）。したがって「請求書を全部消せば契約も消せる」状態には戻れる＝袋小路にはならない。

### 3. 契約に `ended`（終了）状態を足す（C-9）

**「終了しているか」は本来 `end_month` から導出できる事実であり、状態として持つのは情報の重複である。**
それでも状態を持たせたのは、CLB の検索フォームでは
**「終了月が空欄 または 今月以降」という NULL を含む OR 条件を書けない**ためで、これは実測で確認した
（下記「実測」）。導出のまま既定フィルタを掛けるには一覧を Query モジュール化するしかなく、
一覧と詳細の分離・新規作成導線の作り直しというコストに見合わないと判断した。

二重の真実にしないため、**「終了にする」は `end_month` の設定を必ず伴う**（空欄なら当月を自動セットし、
確認ダイアログで明示する）。これで `end_month` が正・`status` は「経理が終了処理を済ませた印」と
役割が分かれる。残るズレは「終了月が過ぎているのに終了処理をしていない」＝掃除していないだけで、
矛盾ではない。

**「終了を解除」に業務上の制限は設けない**（契約更新・再開は普通に起きる）。ただし無言の失敗を 2 つ潰す:

- 終了月が過去のまま解除すると `RecurringRun` の期間判定で毎月スキップされ続け、
  プランにすら現れない → **警告を出す**（データは勝手に書き換えない。利用者の意図が読めないため）
- 解除すると終了期間中の未生成月も対象に戻る → **確認ダイアログで明示する**

既定検索は「下書き＋確定済」（`Status.SearchValues` に複数値、`AllowOrSearch: true`）。
サイドバー経由の `?initialize_search=true` でのみ発火し、チェックボックスとして条件が見えている。

### 4. 下書き契約が資金繰り予測とポータルに載っていたのを是正する（既存バグ）

`recurring_billings` を売上見込みに使う SQL 3 本のうち、**2 本が `status` を見ていなかった**。

| SQL | 修正前 | 判定 |
|---|---|---|
| `PortalQueueData.Query.sql` | `is_active = 1 AND status = 'confirmed'` | 正しい |
| `PortalAlertData.Query.sql` | `is_active = 1` のみ | **下書きを拾う** |
| `CashFlowForecastData.Query.sql` | `is_active = 1` のみ | **下書きを拾う** |

見積から「定期請求契約にする」で作った下書きは `is_active = 1`・`start_month = 翌月`・
`monthly_amount = 見積の税抜合計` が入るので、**経理が確定していない金額が入金見込みに載る**。
2 本に `status = 'confirmed'` を追加した（`ended` も同時に除外される）。

## 実測: `AllowEmptySearch` は範囲検索の NULL 包含に使えない

C-9 の設計を決める前に、全フィールド共通プロパティ `AllowEmptySearch`（既定 `false`・
カタログの説明は「空検索を許可」の一行のみ・本プロジェクトでの使用実績ゼロ）の意味を実測した。
`EndMonth` に `true` を立て、終了月が 過去 / 未来 / NULL の 3 件で検証:

| 契約の終了月 | 終了月 From = 2026-08 で検索 | 検索欄を空にして検索 |
|---|---|---|
| 2026-03（過去） | 除外 | 表示 |
| 2027-03（未来） | 表示 | 表示 |
| **NULL** | **除外** | 表示 |

範囲条件自体は効いている（過去が落ちている）のに **NULL 行は落ちる**。空欄検索でも全件出るので
「空欄のとき `IS NULL` を条件にする」でもない。**範囲検索フィールドに対しては観測可能な効果が無い。**

→ 詳細は `docs/12_CLB改善提案/` に記録。

## 影響

- 二重変換が塞がり、同じ取引が二経路で計上される事故が構造的に起きなくなった
- 請求実績のある契約を下書きに戻せなくなり、確定済の権限がボタンで抜けられる穴が塞がった
- 終了した契約が一覧の既定から外れ、契約が増えても一覧が使い物になる
- 下書き契約の金額が資金繰り予測・ポータル警告に混ざらなくなった

デモ DB の実害も是正した: `quotes.id = 13`（Q-26-009）を `draft` → `accepted`
（確定済・請求実績ありの契約を持つ以上、こちらが正しい状態）。

## 見送ったもの

- **一覧の Query モジュール化**（`ReceiptList` 方式）。モデルを導出のまま保てるが、
  一覧と詳細が分かれ新規作成導線の作り直しが必要で、得るものに見合わない
- **終了月を過ぎた契約の `is_active` 自動オフ**。列も状態も増えないが、「一時停止」と「終了」を
  同じスイッチに同居させることになり、かつシステムが黙ってチェックを外すのは驚きが大きい
- **削除後の一覧遷移に `?initialize_search=true` を付ける**。見積・受注の削除と挙動を揃えた
  （削除直後は全件が見える）。付けるなら 3 モジュールまとめて別途
