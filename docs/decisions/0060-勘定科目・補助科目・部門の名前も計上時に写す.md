# ADR-0060 勘定科目・補助科目・部門の名前も、計上時に写す

## 状況

**取引先の名前は計上時に写している**——[ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md)（帳簿の記載事項は計上時に写して固定する）と
[ADR-0037](0037-計上済みの伝票は画面でも計上時の姿を見せる.md)（計上済みの伝票は画面でも計上時の姿を見せる）である。
**しかし勘定科目・補助科目・部門の名前は写していない。**

**実物を開いて確かめた**（2026-09-16）。

- `journal_lines` が持つ写しは **`partner_name_snapshot` と `registration_no_snapshot` の 2 本だけ**である
  （`Designer/ddl/005_journals.sql`）。科目・補助科目・部門は**識別子だけ**を持つ
- 写しを書くのは `LedgerSnapshotWriter`（計上の経路）で、**取引先しか見ていない**
- **名前は変えてよい列である**（[ADR-0038 §2](0038-使用中のマスタは意味を変えられない.md)）。
  DDL のトリガが止めているのは**コード**と**意味を決める列**で、**名前の更新は止まらない**

**つまり、科目を改名すると、計上済みの伝票の画面も帳簿の表示も遡って変わる。**

**さらに、名前が法定記載事項に当たりうる**（2026-09-06 に気づいた。**Claude の読み**。現在形は [40 §4-1](../40_優良な電子帳簿の対応表.md)）。
法税規則 別表二十四は、
（六）その他の債権債務・（十二）その他の収入・（十四）その他の経費について
「**それぞれ適当な名称を付して区分し**」を求め、（二）当座預金について「**預金の口座別に**」を求める
（逐語は [対象帳簿リサーチ §2](../research/2026-09-06_優良な電子帳簿の対象帳簿と記載事項.md)）。
**本製品はその「名称を付して区分」を勘定科目・補助科目で満たしている**ので、
**名前が動くと、過去の帳簿の区分の見え方も動く。**

## 決定

**開発者の決定である**（2026-09-16。Claude が 3 案を示して A を選んだ。
逐語は「**移さないと、のちにマスタを改名した時に、計上済みの伝票の表示が変わるというのがさすがに気持ち悪いです。**」）。
**A の本文は次のとおりだった**——

> **A. 取引先と同じ扱いにする**——明細に科目名・補助科目名・部門名の写しを足し、計上時に焼く。
> 画面も ADR-0037 と同じ切り替え。帳簿と伝票が計上時の姿で揃い、改名の影響が消える。
> 列が 3 つ増え、マイグレーションと帳簿クエリの書き換えが要る。

1. **仕訳明細に、勘定科目名・補助科目名・部門名の写しを持つ。**
   計上時にサーバが書く（取引先の写しと同じ扱い。[ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md) の 3 つの原則をそのまま当てる）
2. **計上済みの伝票の画面でも、写しを見せる**（[ADR-0037](0037-計上済みの伝票は画面でも計上時の姿を見せる.md) を明細にも当てる）

**以下は Claude の敷衍で、開発者は述べていない。**

3. **[ADR-0038 §2](0038-使用中のマスタは意味を変えられない.md) の「名前は変えてよい」は変えない。**
   写しがあるので、改名しても過去の帳簿は動かない。**誤字の訂正ができなくなるほうが困る**
4. **検索はマスタの識別子で、表示は写しで行う**（取引先と同じ。正典は
   [ADR-0037 §4](0037-計上済みの伝票は画面でも計上時の姿を見せる.md)「検索は識別子で行う。写しにするのは表示だけ」）。
   **改名しても、同じ科目で引き続き引ける**（帳簿クエリは既に識別子で絞っている）

## 理由

**開発者が述べた理由は 1 つだけである**——「**改名すると計上済みの伝票の表示が変わるのが気持ち悪い**」。
**理由 1 はその言い換えで、理由 2・3 と各項の 2 文目以降は Claude の整理である。**

1. **帳簿と伝票が、計上時の姿で揃う。** 取引先だけを写して科目を写さないと、
   **同じ 1 行の中で「計上時の姿」と「いまの姿」が混ざる**
2. **名前が法定記載事項に当たりうる以上、動かないほうが安全である**（状況）。
   **当たらないと言い切れないなら、写す側に倒す**
3. **ADR-0038 の線を名前まで広げる案（写さない・改名を止める）を採ると、誤字の訂正もできなくなる。**
   ADR-0038 が止めているのは「**過去の記録の意味が変わる**」変更であって、名前はそこに入れていない

## 検討したが採らなかった案

| 案 | 中身 | 採らなかった理由 |
|---|---|---|
| **B. 写さない** | 改名を「意味を変える」に当たるとして止める | **誤字の訂正もできなくなる。** [ADR-0038 §2](0038-使用中のマスタは意味を変えられない.md) は名前を「変えてよい列」に置いている |
| **C. コードだけを写す** | 名前は写さず、コードで区分を固定する | 列は小さいが、**名前が動く問題は残る**（帳簿に出るのは名前である） |

## 帰結

**以下は Claude の敷衍で、開発者は述べていない。実装はフェーズ 4 である**
（[12](../12_マスタ台帳.md) の論点として、マスタに手を入れる回。**期限は [40 §6](../40_優良な電子帳簿の対応表.md) が持つ**）。
**1〜5 は 2026-09-16 に実物を開いて確かめた。**

1. **`journal_lines` に列を 3 本足す。** 手順は [ADR-0020](0020-スキーマは現在形の正典で持ち変更は差分で配る.md) と
   [`Designer/migrations/README`](../../Designer/migrations/README.md) の 4 段
   （`ddl/` を直す → 差分を書く → 同値の網 → 稼働 DB へ当てる）
2. **`JournalSubmitGate.SystemAssignedFields` に 3 つを足す。**
   いまここは `PartnerNameSnapshot` を保存から落としていて、同ファイルの注記が
   「守っているのは画面ではなく**画面を通らない経路**」と書いている。
   **足さないと、Web API を直に叩くだけで任意の名前を法定記載事項の欄へ焼ける**（計上済みは不変なので直せない）。
   **`RegistrationNoSnapshot` がこの一覧に入っていないのも同じ回で塞ぐ**
3. **写しを書く経路は 2 本ある。** [ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md) の原則は 4 つで、
   **4 つ目が「取消は原仕訳の写しをそのまま引き継ぐ。訂正の再計上は焼き直す」**である。
   実物の `LedgerSnapshotWriter.BurnAsync` は**取消なら伝票の名前だけ引き継いで即 return** し、明細に 1 行も書かない
   ——取消の明細の写しは `JournalReversal.Reverse` の `line with { … }` が原仕訳から運んでいる。
   **3 本足すときは `JournalLine` のプロパティと `JournalEntryStore` の INSERT の列にも足す。**
   **落とすと取消の明細だけ写しが NULL になる**（[qa/03 L-13](../qa/03_テストで漏らした実例.md) の型——同じ取引の表と裏で名前が違う）
4. **帳簿のクエリは `COALESCE(写し, 現在のマスタ名)` にする。**
   **取引先が既にそうしている**（`GeneralLedger.Query.sql`・`JournalBook.Query.sql` の
   `COALESCE(l.partner_name_snapshot, lp.name, ep.name)`）。
   **[ADR-0037](0037-計上済みの伝票は画面でも計上時の姿を見せる.md) の帰結が「この列より前に計上された伝票は写しが空である。埋め直さない」と既に決めている。**
   `account_id` は `NOT NULL` なので**古い行が空になることはない**——残るのは
   **同じ科目の元帳に、改名前の写しと改名後の現在名が混ざる**ことだけである
5. **相手勘定科目（`counter_account_name`）は別に直す。**
   `GeneralLedger.Query.sql` の副問い合わせは**反対側の行の `accounts.name`** を `MIN` で出しており、
   クエリ自身の注記が「**法税規則 55 ② の法定記載事項**」と書いている。
   **その行に足した写し 1 本では出せない**ので、他行の写しを引く形に変える。
   **`COUNT(DISTINCT o.account_id)` の数え方は変えない**——写しの文字列で数えると、改名で「諸口」が揺れる
6. **税区分名は写さない。**
   [ADR-0038 §2-1](0038-使用中のマスタは意味を変えられない.md) は税区分名も同列に並べていたが、
   **税区分は制度の写しであって自社が付けた分類ではなく、仕訳には適用した版を固定する**（I-16。[12](../12_マスタ台帳.md)）。
   **名前が動いても、どの税区分で計算したかは版が持っている**（**Claude の判断**）
7. **写しの列には上限を置かない。** 取引先の写し（`partner_name_snapshot`・`registration_no_snapshot`）にも
   長さのトリガが無く、[12 §2-2](../12_マスタ台帳.md) の 8 欄にも入っていない。
   **置くと危ない**——上限のトリガは `BEFORE UPDATE OF <列>` なので**上限より前から入っている長い名前は生き残る**。
   その名前を写す計上が上限に当たると、**写しが書けないのではなく計上そのものが落ちる**
   （`JournalLineRules.ShortenCopiedText` と `JournalReversal` の注記が、まさにこの型で
   「永久に取り消せなくなる」のを避けている）。**置くならその詰め方を写しにも当てる**
8. **→ 2026-09-16 に当てた**（[ADR-0062](0062-明細の取引先は行ごとに選べるようにし伝票の取引先は既定値にする.md)。`DataOnlyFields` と `OnAfterInitialization` を配線し、`ListField` の行ごとに表示を差し替えられることを実機で確かめた——記録は qa/04 の 2026-09-16 の節）。**この 8 と、次の 9 は、当てる前の記録である。**

   **決定 2（明細の画面でも写しを見せる）は、まだ当てられない。**
   取引先のヘッダは `JournalEntry.mod.cs` が `Partner.DisplayText` を差し替えて実現しているが、
   **[ADR-0037](0037-計上済みの伝票は画面でも計上時の姿を見せる.md) は「伝票の画面の明細行には取引先の列が無い」として明細を帳簿に任せていた**。
   **`ListField` の行ごとに表示だけを差し替えられるかは未計測である**——**実機で測るまで、決定 2 は明細に当たらない**
9. **`JournalLine.mod.json` の `DataOnlyFields` は、**実際に画面のスクリプトから読むときに要る
   （**一覧レイアウトの側**。[qa/01 F-34](../qa/01_CLB静かな失敗.md) が 2026-09-03 に踏んだのは
   「`ListField` の行から、レイアウトに出していないフィールドをスクリプトで読むと必ず空」という形である）。
   **いまの `PartnerNameSnapshot` は `DataOnlyFields` に入っていないが何も壊れていない**——読むスクリプトが無いからである。
   **決定 2 を当てる回に、読む側と一緒に足す**
10. **[ADR-0038 §2-1](0038-使用中のマスタは意味を変えられない.md) に追記する。**
    同節は「写しを持たないので過去の帳簿の科目名の表示も変わる。**それでよいと考えている**」と書いており、
    本 ADR はそれを覆す。**ただし同節は「これは Claude の読みであって確かめていない」と自ら印を付けている**ので、
    **開発者の決定を部分的に覆す場合には当たらない**（[フロントマター §3-3](../00_ドキュメント規約/フロントマター.md) の
    `superseded` の規則は、開発者が決めた ADR の決定を覆すときのものである）。
    **同節が既に採っている「日付つき追記」の形で足す**
11. **[40 §4-1](../40_優良な電子帳簿の対応表.md) に当てはめを足す。**
    「名前が別表二十四の『名称を付して区分し』に当たりうる」という読みは、
    [ADR-0042](0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の帰結により
    **40 §4-1 の表が現在形を持つ**ことになっているが、**いまその表に無い**。
    **この読みは Claude のままである**（開発者に諮っていない）
