# ADR-0049: 検収に明細行を持たせる

- 日付: 2026-08-11
- 状態: 採用
- 関係: ADR-0008（売上計上は検収基準）・ADR-0029（明細の単位列）・ADR-0050（税額の行単位化）・
  `docs/issues/2026-08-09_体験シナリオ執筆中に見つかった改善候補.md` A-1

## 背景

見積・受注・請求書はいずれも明細行を持つのに、**検収だけが合計金額（`amount` / `tax_amount`）しか持たなかった**。
この非対称が実害を生んでいた。

検収から請求書を作るとき、金額は検収額を渡す一方で**明細は受注明細をそのままコピー**していた。
請求書の `RecalcTotal()` は明細合計で金額を上書きするため、**分割検収で作った請求書を画面で開いた瞬間に
請求額が受注全額に戻る**（改善候補 A-1）。金額と明細が別々の根拠を持っていたことが原因である。

対症療法として「検収由来の請求書では再計算しない」「明細を按分する」などが考えられたが、
いずれも**金額と明細が食い違いうる状態そのものは残る**。

## 決定

**検収に明細行（`acceptance_lines`）を持たせる。**

- 検収明細は**受注明細のコピー**。摘要・数量・単位・単価・税区分は受注明細から引き継ぎ、**読み取り専用**とする
  （検収は「いくら受け入れたか」を記録する行為であり、品目や単価を書き換える場ではない）
- **編集できるのは金額だけ。** 部分検収は「この行はいくらぶん受け入れたか」で表現する
- 各行は `sales_order_line_id` で**受注明細に紐づく**。これにより受注明細ごとの検収済み累計が出せ、
  残額の自動セットと超過判定が行単位でできる
- 検収額（`acceptances.amount`）は**明細合計から導出**する（手入力をやめる）。
  税額は明細の税区分から計算する（ADR-0050）
- 請求書の生成は**検収明細をそのままコピー**するだけになる。按分ロジックは不要

### なぜこれが A-1 の根治になるのか

請求書の明細が検収明細のコピーになるため、**明細合計＝検収額が構造的に成立する**。
`RecalcTotal()` が何度走っても答えが変わらない。特別扱いもフラグも要らず、破綻の余地が消える。
「金額を守るために再計算を止める」のではなく、「**再計算しても正しい状態を作る**」という解決になっている。

### 実装中に判明した、もう一段深い真因（2026-08-12）

明細をコピーする実装を入れて実機で試したところ、**それでも請求明細の金額が受注額に戻った**。
追ってみると `Invoice.Lines_OnDataChanged` が明細グリッドの変更のたびに

```csharp
if (l.UnitPrice.Value != null) l.Amount.Value = l.Qty.Value * l.UnitPrice.Value;
```

を無条件に走らせており、スクリプトが書き込んだ検収額を**その場で 数量×単価 に戻していた**。
`Amount` への代入自体がこのハンドラを再帰的に呼ぶため、代入した値が同じイベントの中で消えていた。

A-1 の真因はここにある。`Detail_OnAfterInit` の `RecalcTotal()` は合計を再計算するだけで、
**明細の金額を壊していたのはこの自動計算**だった。しかもこれは検収由来の請求書に限らず、
**利用者が請求明細の金額を手で直しても同じように消える**——単価と食い違う金額をそもそも保持できない状態だった。

対策として、自動計算を**手で足した行（`acceptance_line_id` が NULL の行）だけ**に限定した。
検収明細から写した行にとっては金額（＝検収金額）が正であり、数量×単価は導出根拠ではない。
手入力行の入力補助という本来の役割は残る。

### 実務との整合

部分検収は本来「金額」ではなく「行」で起きる。「要件定義と基本設計は受け入れたが開発はまだ」というのが
現場の姿であり、金額の按分はそれを会計に写した結果にすぎない。従来は結果だけを持ち原因を持っていなかった。

副次的に、受注残の管理が行単位でできるようになり、売上計上の仕訳も行ごとの税区分で切れるようになる。

## データモデル

```sql
CREATE TABLE acceptance_lines (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    acceptance_id       INTEGER REFERENCES acceptances(id),
    line_no             INTEGER,
    sales_order_line_id INTEGER REFERENCES sales_order_lines(id),  -- 受注明細への紐づき
    description         TEXT,      -- 以下 5 列は受注明細のスナップショット（読み取り専用）
    qty                 INTEGER,
    unit                TEXT,
    unit_price          INTEGER,
    order_amount        INTEGER,   -- 受注明細の金額（残額計算・超過判定の基準）
    amount              INTEGER,   -- 今回検収する金額（唯一の編集対象）
    tax_category_id     INTEGER REFERENCES tax_categories(id)
);

ALTER TABLE invoice_lines ADD COLUMN acceptance_line_id INTEGER REFERENCES acceptance_lines(id);
```

`order_amount` を持つのは、一覧に「受注 / 検収 / 残」を並べて見せるため。
CLB の一覧はテーブル結合をしないので、スナップショットとして保持するのが実装上も自然。

`invoice_lines.acceptance_line_id` は、請求明細がどの検収明細から来たかを保持する。
行の並べ替えや追加が起きても対応が壊れないため、**行単位の超過警告**（別途）が正確にできる。
手動請求書・定期請求・SES の明細では NULL。

## 既存データの移行

デモ DB の検収 9 件を、紐づく受注の明細から復元する（実測で方針を確定した）。

| 件数 | 状況 | 移行 |
|---|---|---|
| 8 件 | 検収額 ＝ 受注明細合計 | 受注明細をそのままコピー（金額も受注どおり） |
| 1 件（A-26-009） | 検収額 1,200,000 ＜ 受注明細合計 2,000,000（分割検収） | 受注明細をコピーし、**最終行で差額を調整**して合計を検収額に合わせる |

「最終行で調整」を一般則とする。分割検収がどの行に対するものだったかは記録が残っていないため、
合計を保つことを優先する。**帳簿（売上仕訳）は検収額の合計で計上済みなので、移行で金額は 1 円も動かない。**

## 影響

- 検収画面: 受注を選ぶと明細が展開される。検収額は明細合計の自動計算になり手入力できなくなる
  （従来「検収額を減らして値引き」ができたが、今後は**行の金額を下げる**形になる。より正確）
- 検収明細には**行の追加・削除ボタンを出さない**（`ListField.CanCreate/CanDelete: false`）。
  摘要・数量・単価が編集不可なので手で足した行は意味を持てない。
  なお `CanCreate: false` は UI のボタンを消すだけで、スクリプトからの `AddRows()` は従来どおり保存される（実機で確認）
- 請求書生成: 受注明細ではなく検収明細をコピーする
- 請求明細の「金額 = 数量 × 単価」自動計算は、検収に紐づかない行に限定された（上記「もう一段深い真因」）
- 体験シナリオ `02_営業_受託/03_分割検収と請求金額の罠.md` は「罠」が解消されるため書き換えが必要
- 11_E2E の RCV-09（検収額の手修正＝値引き）は行単位の操作に変わる
