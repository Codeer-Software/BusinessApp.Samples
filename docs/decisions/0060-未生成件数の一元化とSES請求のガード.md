# ADR-0060: ポータルの「当月未生成」を画面の判定に揃える／SES 請求のガードを足す

- 日付: 2026-08-16
- 状態: 採用
- 関連: ADR-0034（定期請求のプラン方式）／ADR-0036（SES のプラン方式）／ADR-0045（ポータル）

## 背景（問題）

ユーザーから「ホームの『定期請求・SES の当月未生成: 3 件』をクリックしたら
定期請求の実行画面が開いたが全件生成済みだった。SES は 2 件未生成。どうやっても件数が合わない」
という指摘。実データで追ったところ、**3 件は全部 SES**（定期請求は 0 件）で、
さらに **SES 画面は 2 件しか出していない**（3 件目は「請求額 0 円以下」で除外）という
二重のズレだった。原因は 3 つ。

1. **導線が 1 本しかない。** 定期請求と SES はモジュールが別（`RecurringRun` / `SesBilling`）なのに、
   ポータルは件数を合算して `RecurringRun` にだけ飛ばしていた。SES の未生成は見に行っても見つからない。
2. **判定が二重実装で食い違っていた。** 画面側は `BuildPlan()` が唯一の判定、
   ポータル側は `PortalQueueData.Query.sql` がそれを SQL で再現したもので、除外条件が同期していなかった
   （定期請求の「金額 0 円」、SES の「精算後の請求額 0 円以下」）。
3. **SES の判定自体にバグがあった。** `BuildPlan` は `is_active` しか見ておらず、
   `status`（進行中/完了/中断）を見ていなかった。**完了にした SES 案件が毎月の生成予定に残り続ける。**

さらに調査中に見つけた 2 件:

- **工数実績が 0 分の月でも請求額が出てしまう。** 精算幅つきの契約は実績 0h だと下限まるごと控除で
  計算され、たとえば月額 800,000／下限 140h／控除 5,000 なら 100,000 円が「生成予定」になる。
  実務でこれが起きる原因はほぼ常に**工数の入力漏れ**で、そのまま実行すると誤請求になる。
  実データでも SES 3 件すべてが当月 0 分だった。
- **`date('now')` は UTC。** SQLite の `'now'` は UTC なので JST とは 9 時間ずれ、
  毎月 1 日の 0:00〜9:00 は「前月」を数える（実測: UTC 2026-08-15 / ローカル 2026-08-16）。
  画面側は `DateTime.Today`（ローカル）なので、月初の朝だけホームと画面が 1 ヶ月ずれる。

## 選択肢（判定の一元化をどうするか）

| 案 | 得失 |
|---|---|
| A. ポータルの件数をプランテーブル（`recurring_run_plan` / `ses_run_plan`）から数える | 判定は完全に 1 本になる。しかしプランテーブルは**全ユーザー共有の一時領域で、画面を開いたときにしか作られない**（ADR-0034）。誰も画面を開いていない間は空／古い値になり、ポータルが嘘をつく |
| B. ポータル表示時にプランを作り直す | 常に正しいが、`BuildPlan` は N+1 で重く、しかも**他人がプレビュー中のプランを壊す**（共有の一時領域なので） |
| C. 判定を SQL に一元化し、`BuildPlan` が SQL を読む形にする | 理屈は正しいが、年払いの周期判定・前受按分・除外理由の文言まで SQL に移す必要があり、C# より読みにくく壊しやすい。今回の不具合に対して割に合わない |
| **D. SQL 側を BuildPlan と厳密に揃え、「対で保守する契約」として明示する（採用）** | 二重実装は残るが、実データ上の乖離は消える。契約をコメント・ADR・突合 SQL の 3 点で縛る |

## 決定

1. **ポータルの行を分ける。** 「定期請求の当月未生成」と「SES 請求の当月未生成」を別行にし、
   それぞれ `RecurringRun` / `SesBilling` へ遷移する。

2. **`SesBilling.BuildPlan` にガードを 2 つ足す**（画面が正典なので、まずこちらを直す）:
   - `status != 'active'` の案件は「完了しているため対象外」「中断しているため対象外」で除外
   - **対象月の工数実績が 0 分の案件は「未入力のため対象外（工数を入力してから実行してください）」で除外**

3. **`PortalQueueData.Query.sql` を `BuildPlan` と同条件にする**（金額 0 円の除外、SES の
   `status` + `is_active`、実績あり、精算後の請求額が 1 円以上）。
   SQL の先頭に「この SQL と BuildPlan は対で保守する契約」であることを明記し、
   突合の検証 SQL（`docs/tests/portal_billing_count_check.sql`）へのリンクを置く。

4. **実績 0 分を請求対象から外した副作用を、別の作業として可視化する。**
   そのままだと「請求が出てこない理由」が画面から消えて黙って落ちる。
   ポータルに「▶ SES の当月工数が未入力: N 件（入力されるまで請求を作れません）」を追加した。
   **請求を作る作業と、工数を入れてもらう作業は別物**なので行も分ける。

5. **全 Query SQL の `date('now')` を `date('now','localtime')` に統一**（15 ファイル）。

## 影響

- 当月（2026-08）は SES 3 件すべてが「工数実績が未入力」で対象外になり、
  ポータルの請求キューは消えて代わりに「工数が未入力: 3 件」が出る。画面と件数が一致した（実機確認済み）。
- **完了・中断した SES 案件が請求されなくなる**。これまで請求されていた可能性があるので、
  過去に生成した SES 請求書のうち完了案件のものは目視確認したほうがよい（今回は該当なし）。
- 月初の朝 9 時前に見たときの帳票・アラートの日付ズレが解消する。

## 残る弱点（正直に記録する）

- **判定は 2 か所にある**（`BuildPlan` と件数 SQL）。片方だけ直せばまたズレる。
  縛りは「SQL 先頭の契約コメント」「この ADR」「突合の検証 SQL を実機検証のチェックリストに入れる」の 3 点のみで、
  仕組みとして強制はできていない。**SES の精算式（下限控除・上限超過）は特に危ない**——
  式を変えるときは必ず両方を直すこと。
