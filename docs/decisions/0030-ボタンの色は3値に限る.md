# ADR-0030 ボタンの色は 3 値に限り、押せないボタンを灰色にしない

## 状況

[21_画面の原則](../21_画面の原則.md) §4 は当初「ボタンの色は 2 色」（青＝通常操作／赤＝破壊的）としていた。
これは **Claude の判断**で、根拠を持っていなかった（[qa/02 R21-13](../qa/02_自己レビュー記録.md)）。

開発者が 2 つの反例を挙げた（2026-08-30）——**押せないボタンを示す灰色**と、**黄色を使いたくなる場面**。
そのうえで「**前回プロジェクトでルールを決めていたはずなので調べてほしい**」と指示があった。

**前回プロジェクトには同名の論点の ADR があった**（`BusinessApp_old` の ADR-0027
「ボタン色規約の一新」。2026-07-19。**本リポジトリの追跡外**なので、以下に必要な事実を写す）。
きっかけは開発者自身の指摘である。

> 「灰色ボタンと青色ボタンの使い分けが分からない。**灰色は押してはいけないのかと思う。**
> 使い分けをユーザーが理解できないなら分けるべきでない」

そのときの実態調査——**6 色が混在**していた（Primary 46 / Secondary 19 / Info 6 / Success 5 /
Danger 3 / Warning 2）。**同じ「保存」が、見積の画面では青、検収の画面では灰**だった。
歴史的経緯の堆積で体系が無かった。

## 選択肢

### A. 3 値だけ（青＝前進／赤＝巻き戻し／灰＝ダイアログのキャンセル専用）

- **長所**: 利用者が色から意味を読み取れる。青が複数並んでも迷わない
- **短所**: 「主・副」「重要度」を色で表せない

### B. 主ボタン＝青／副ボタン＝灰（従来型）

- **短所**: **「灰＝押すべきでない」と読まれることが実地で確認された**（上の開発者の指摘）。
  副次アクションが押されなくなる

### C. 意味で色を分ける（Success＝完了系・Warning＝注意系を使う）

- **短所**: **作り手の意図であって利用者の読解と一致しない。**
  前回プロジェクトの**初見 UX テストで読解されなかった**

## 決定

### 1. A を採る。ボタンの色は 3 値だけ

**現在形の規則は [21 §4](../21_画面の原則.md) が持つ**（更新され続けるものを判断ログに置かない）。
本 ADR が決めているのは「**3 値に絞る**」ことと、その理由である。

**CLB の `ButtonVariant` は 18 値ある**（`Outline*` 9 種・`Text` を含む。CLB 1.3.20）。
**禁止する色を数え上げない**——ホワイトリストの 3 値以外は使わない、とだけ決める。
数え上げると CLB が値を増やすたびに腐る。

### 2. 押せないボタンを灰色にしない

灰色は選択肢 B が捨てた読まれ方（押してはいけない）を持つので、**無効の表現には使わない**。
**(a) 非表示にして理由をラベルで示す**か、**(b) アクション色のまま半透明にする**。
(b) の数値は [`Designer/Project.md`](../../Designer/Project.md) が持つ。

**そもそも「押せるのに必ずエラーになる」状態を作らない**のが先である（[21 §1](../21_画面の原則.md)）。

### 3. 前回プロジェクトの結論をそのまま引き継ぐ

**適切でない例が実際に出るまで尊重する**（開発者の決定。2026-08-30。
**悩んだ末の選択であり、作り直す根拠がまだ無いから**）。

## 理由

**決め手は「作り手の意図」ではなく「利用者の読解」である。**
選択肢 B も C も、作り手の中では筋が通っている（副次だから灰、注意だから黄）。
どちらも**実地で読まれなかった**——B は開発者自身が、C は初見 UX テストが示した。

**本プロジェクトはまだこの実測を持っていない。** 引き継ぐのは前回プロジェクトの結果であり、
**対象ペルソナ**（[02](../02_ペルソナ.md)）で測り直したものではない。
覆すときは新しい ADR を起こす。

## 帰結

- **`Warning`（黄）が 1 件残っている**——振替伝票の「訂正する」（`CorrectButton`）。
  掃除は[05](../05_実装計画と現在地.md) のフェーズ 2.5
- **「訂正する」を青と赤のどちらにするかは、この ADR を書いた時点では決めていなかった。**
  訂正は誤りを直す**前進**だが、押した瞬間に**取消を 1 本計上するので元に戻せない**。
  前回プロジェクトの ADR も「訂正」を名指ししていない

  > **2026-08-30 追記**: **開発者が「赤」と決めた**（2026-08-30。
  > **訂正が実際にすることは取消の計上そのものだから**）。
  > **前回プロジェクトからの引き継ぎではなく、本プロジェクトの新しい判断**である
  > （§3 の「適切でない例が実際に出るまで尊重する」の対象外——前回は「訂正」を決めていない）。
  > **当てはめの現在形は [21 §4](../21_画面の原則.md) が持つ**（一般則には広げていない）。
- **`Variant` の値は機械で見られる**（デザイン JSON のキーを読むだけ）。
  [05](../05_実装計画と現在地.md) のフェーズ 2.5 の D に積んである
- 差し戻しの見た目は本 ADR の対象外
  （[ADR-0023](0023-利用者への差し戻しは1種類の見た目で見せる.md) がトースト 1 種類と決めている）
