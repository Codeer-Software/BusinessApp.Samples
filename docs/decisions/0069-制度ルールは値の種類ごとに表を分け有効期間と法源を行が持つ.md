## 状況

**フェーズ 3 に入る。** [20 §2](../20_実装の原則.md) は「制度値をハードコードしない。
税率・控除割合・閾値・耐用年数は**有効期間つきのルールデータ**として持つ」と決めており、
[12 §2](../12_マスタ台帳.md) は制度ルールの行を
「**有効期間つきの版**（`valid_from` / `valid_to`）＋ **必ず法源・出典 URL を持つ**。
行を UPDATE せず新版を INSERT」と書いている。
配り方は [ADR-0020](0020-スキーマは現在形の正典で持ち変更は差分で配る.md)（ベンダーがマイグレーションで配る）が決めた。

**まだテーブルが 1 つも無い。** `tax_categories` は 2026-08 に作ったが、
**税率の数値はそこに持たない**と DDL のコメントが明記しており（`003_consumption_tax.sql`）、
仕訳明細には `applied_rule_version`（[10 §1](../10_会計ドメイン設計.md) の I-16）の列だけが空で待っている。

**持つ値は 1 種類ではない。** フェーズ 3 で要るだけでも 3 つあり、**引き方も値の形も違う。**

| 値 | 引く鍵 | **引く日** | 値の形 | 正典 |
|---|---|---|---|---|
| 税率 | 税率区分（標準・軽減・旧 8%） | **課税資産の譲渡等をした日・課税仕入れを行った日**（`tax_point`。**Claude の当てはめ**——`Designer/ddl/005_journals.sql` の `tax_point` の列注記が「経過措置・税率の判定基準日」と書いているのに乗っている。**明文の決定は無い**。[11 §1-1](../11_消費税設計.md)）。**返還等の行は未決**（[11 の保留リスト](../11_消費税設計.md)） | 率（国税分）と分数（地方分） | 値は [税率リサーチ](../research/2026-09-23_消費税の税率と地方消費税の税率.md)、形は [11 §1-1](../11_消費税設計.md) |
| 経過措置の控除割合 | 無し（期間だけ） | **課税仕入れの日**（`tax_point`）**そのもの。取引日で代えない** | 百分率 | [同 §1-1](../research/2026-08-23_消費税インボイス制度.md) |
| 相手方別上限額 | 無し（期間だけ） | **会計年度の開始日**（制度は課税期間の開始日。会計年度＝課税期間の前提で揃えている——[11 §5-8](../11_消費税設計.md)） | 金額（税込） | [同 §1-3](../research/2026-08-23_消費税インボイス制度.md) |

**[11 §5-8](../11_消費税設計.md) は「割合は `tax_point` で、上限額の版は会計年度の開始日で取る。
取る日が違うので、同じ判定にまとめない」と既に書き分けている。**

**引く日を「基準日」と書いてはならない**（[11 §5-2](../11_消費税設計.md) の 4 つの日付の表）——
**基準日は「`tax_point`、無ければ取引日」**で、**割合は `tax_point` そのもの**である。
**取引日で代えると、引渡が 9/30・取引日が 10/05 の仕入れが 80% ではなく 70% になる**
（境目は 2026・2028・2030・2031 の各 9/30）。
**2026-09-23 に一度この表と本文に「基準日」と書き、自己レビューで直した。**

**引く側の要件は 2026-09-18〜20 に定まった**（同 ADR）——
**割合は行ごとの「経過措置を適用する」の指定で効き**（決定 3）、
**上限額は一の者ごと・年度ごとの累計を計上時の関門が見る**（決定 4）。
**累計が負のときは残り枠が上限額を超える**（決定 12）ので、
**表が答えるのは「その日に有効な上限額」までで、残り枠の計算は表の外にある。**

## 決定

### 1. 値の種類ごとに表を分ける。汎用の 1 表にしない

`rule_type` と `value` を持つ 1 つの表に畳まない。**種類ごとに列と CHECK を書ける表を作る。**

- **CHECK が書けなくなる。** 控除割合は 0〜100 の整数、上限額は正の整数円、税率は分子と分母——
  **1 列に畳むと「その値として妥当か」を DB が言えない。**
  本プロジェクトの DDL は CHECK で意味を守る作りで通してきた（`003`・`005`）
- **引く鍵が違う。** 税率は税率区分で引き、控除割合と上限額は期間だけで引く。
  **汎用表にすると「鍵が要る種類」と「要らない種類」が同じ列を共有し、NULL の意味が種類ごとに変わる**
- **引く日が違う。** 上の表のとおりである。**同じ関数で引けないものを、同じ表に入れる理由が無い**

**代償は、有効期間と法源の列が表ごとに繰り返されること**である。
**受け入れる**——本プロジェクトの DDL は `created_at` / `updater` / `optimistic_locking` も表ごとに書いており、
**繰り返しより「その表を読めば意味が分かる」を採ってきた**。

### 2. 期間は法令が書いた字のまま持つ。両端を含む

`valid_from` と `valid_to` は **どちらもその日を含む**。`valid_to` が NULL なら「以後ずっと」。

- **法令と国税庁の資料が閉区間で書いている**（「令和5年10月1日から令和8年9月30日**まで**」）。
  **半開区間に直すと、±1 日の解釈をデータに焼き込むことになる**——
  [14 §4](../14_適格請求書発行事業者の登録.md) が `valid_to` をやめた理由と同じ筋である
- **DDL のコメントに「両端を含む」と書く。** 書かないと、引く側が半開のつもりで書いた日に静かにずれる

### 3. 版の字（`version`）は行が持ち、仕訳明細に写す

`applied_rule_version`（`journal_lines`）に入れる字を、**ルールの行が `version` 列として持つ**。

- **形は `<種類>:<鍵>:<valid_from>`**（実データは `tax_rate:standard:2019-10-01`）。
  **真ん中の `<鍵>` は、行を引くときに使う列の値**（税率の表なら `rate_kind`）である。
  **期間だけで引く表では、真ん中を入れない**（実データは `transition_purchase_rate:2026-10-01`）。
  **連番にしない**——連番は「どの版か」を人が読んで確かめられない。
  **真ん中を入れるかどうかは表ごとに決まる**——税率は区分でも引くので、入れないと 3 区分の版が同じ文字列になる
  （**真ん中は 2026-09-23 に Claude が足した**。帰結を見よ）
- **仕訳に写した字から、その行を引き直せる**（I-16 の「過去を再計算しない」を、字で追えるようにする）

### 4. 法源は「条文の指し」と「出典 URL」と「確認日」の 3 つを持つ

[12 §2](../12_マスタ台帳.md) が「必ず法源・出典 URL を持つ」と決めているので、列にする。

- `legal_basis`——条文の指し（[80 §3](../80_参照法令一覧.md) の記法）
- `source_url`——一次情報の URL
- `confirmed_on`——**法源を最後に確かめた日**（[32 §3](../32_調査のルール.md)）。
  **開発者が原文を示して確認した日も含む**——[80 §2-1](../80_参照法令一覧.md) の出典の列と同じ意味である。
  **「URL を開いた日」に限ると、開発者確認で埋めた行に書く日が無くなる**

**3 つとも NOT NULL にする。** 出典の無い制度値を入れられる口を、最初から開けない。

### 5. 制度が変わったら、既存行を書き換えず新しい期間の行を INSERT する

[12 §1](../12_マスタ台帳.md) の「制度ルールは無効化ではなく版の交代」をそのまま守る。
**`is_active` を持たない**——期間が有効・無効を決めるので、フラグは 2 つ目の真実になる。

**「UPDATE しない」の射程は制度の変更である。**
**配った値そのものの誤りを直すときは UPDATE する**——
**同じ期間の行を 2 本持てない**（`version` の UNIQUE・**引くときに使う列と `valid_from` の複合の一意索引**
——**複合にしたのは 2026-09-23 に Claude**——・重なりのトリガが同時に効く）ので、
訂正に INSERT の道は無い。**そのとき版の字は変わらないので、何をいつ直したかはマイグレーションの記録が持つ。**

**計上済みの税額は、どちらでも動かない**（反対仕訳でしか動かせない。[ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md)）。
**版で引き直したときの説明だけが変わる**——**そこは受け入れる**。
**稼働 DB を手で書き換えても、次のコミットで `migrate.ps1 -Verify` が正典との差を言う**（`VendorRows`）。

**版の字は期間から導く**（DB のトリガが強制する）ので、
**版が指す日と、その版が実際に効いた期間が食い違ったまま仕訳に焼ける道は塞いである**。

## 帰結

- **`tax_categories.rate_kind` が税率表の鍵になる。** 税区分は「標準か軽減か」だけを持ち、
  その日に何 % かは税率表が答える——`003` のコメントが最初からそう書いていた形に、実体が追いつく
- **経過措置の 2 つ（控除割合・上限額）は別の表になる。**
  同じ「経過措置」でも引く日が違うので、まとめない（決定 1）
- **できたのは経過措置の控除割合と税率の 2 表である**（`transition_purchase_rates`・`tax_rates`。どちらも 2026-09-23）。
  **相手方別上限額の表は、この 2 回では作らなかった**（制度の事実は揃っている。**未決なのは設計である**）——
  **十億円は独立した規定ではなく [附則 52 ①（現行版）](../research/2026-09-11_インボイス経過措置の附則条文.md) のかっこ書きそのもの**で、
  **射程は 80% の行と同じ 2023-10-01 起点**である。
  **切り替わりは [同 附則 90 ③（令和8年法律第12号）](../research/2026-09-11_インボイス経過措置の附則条文.md)**——
  「令和八年十月一日**以後に開始する課税期間**から適用し、同日前に開始した課税期間については、**なお従前の例による**」。
  **つまり「課税期間の開始日が 2026-10-01 より前なら十億円、以後なら一億円」で確定している。**
  **残っているのは、会計年度の開始日で引く表（[11 §5-8](../11_消費税設計.md)）にしたとき、
  十億円の行の `valid_from` をどこに置くか**である——**2023-10-01 を含む課税期間は、
  1 年の事業年度なら最も早くて 2022-10-02 に始まる**。
  **2026-09-23 に一度「リサーチに無いので調べる」と書いたが、それは誤りだった**（自己レビューで見つけた。
  **同じ附則 52 ① の射程から 80% の行の 2023-10-01 を導いておきながら、上限額では同じ導出を拒んでいた**）
  > **2026-09-24 追記（事実の訂正）**: **上の「制度の事実は揃っている」「射程は 80% の行と同じ 2023-10-01 起点」「課税期間の開始日が 2026-10-01 より前なら十億円」「2022-10-02 に始まる」は、条文の改正履歴と合わない**（附則 90 ③ の逐語は正しい）。
  > **事実**: 十億円のかっこ書きは、所税法等一部改正法（令和6年法律第8号）が 2024-10-01 に所税法等一部改正法（平成28年法律第15号）附則 52 ① へ足したもの（Claude が e-Gov で 2 つの版を突き合わせた。逐語は [条文リサーチ §8](../research/2026-09-11_インボイス経過措置の附則条文.md)）。
  > **Claude の読み**（開発者は未確認）: それより前に開始した課税期間には上限が無い。**2026-09-23 の取り下げ（「調べる」を誤りとした）が、誤りだった。** 読みと表の形は [05](../05_開発者への問い.md) の Q-62 で諮っている
- **税率の表は 2026-09-23 に作った**（`Designer/ddl/015_tax_rates.sql`。形は [11 §1-1](../11_消費税設計.md)）。
  **決定 2・4 はそのまま当たった。決定 1・3・5 は、当てる中で広げた**——
  **同じ「有効期間つきの表」でも、鍵も終わり方も値の形も違う**。
  **①鍵は税率区分＋日付**（014 は日付だけ）**②終期なしの行が普通である**（`standard`・`reduced` は条文が期限を書いていない。
  **`legacy_8` の NULL は Claude の当てはめで、開発者は未承認**——旧税率そのものを外す予定（[Q-54](../05_開発者への問い.md)）。
  014 は必ず終期がある。**決定 2 が「NULL なら以後ずっと」と既に書いており、そこは広げていない**）
  **③値は 2 つあって形が違う**（国税は対価に対する率、地方は消費税額に対する分数）。
  **①に合わせて、2026-09-23 に Claude が決定 3 の版の文字列へ「引くときに使う列」の部分を入れ、
  決定 5 の一意索引をその列との複合にした**（**決定 2・4 は字のまま当たった**）。
  **合計税率（10%・8%）は持たずに導く**（国税 ×（分母＋分子）÷ 分母）。
  **万分率**（1 万分のいくつか。7.8% ＝ 780）**の整数で導く**ので、
  [消費税リサーチ §5-4](../research/2026-08-23_消費税インボイス制度.md) の
  **税込側の換算率（100/110・10/110・7.8/110 等）が整数の分数のまま組み立てられる**
  ——小数に直すと丸めが入るからである。**割り切れない行は DDL の CHECK と `TaxRate` の両方が断る**。
  **積上げの 78/100 だけは、この表から導いてはいけない**——
  **[消費税リサーチ §5-2](../research/2026-08-23_消費税インボイス制度.md) は率によらない固定値として書いているが、
  旧税率 8% に 78/100 と 0.7875 のどちらが当たるかは確かめていない**（消税令 46 を開いていない。
  [税率リサーチ §3](../research/2026-09-23_消費税の税率と地方消費税の税率.md)）。
  **条文と切り替わった日は [税率リサーチ](../research/2026-09-23_消費税の税率と地方消費税の税率.md) が持つ**
- **`journal_lines.applied_rule_version` は 1 列しかないが、課税仕入れの行は版を 2 つ要する**
  （税率の版と控除割合の版）。**2026-09-23 の自己レビューで見つけた宿題である**——
  いま片方を書けばもう片方が消えるので、**課税仕入れの行では I-16（過去を再計算しない）を満たせない**。
  **版を仕訳に書く回に、複数持てる形へ直す**（種類つきの子表か、種類ごとの列）。
  **あわせて、税額計算方式も明細に固定するかを決める**——
  **方式は課税期間ごとの会計設定で後から変えられる**（[11 §3](../11_消費税設計.md)）ので、版だけでは数が再現しない。
  **端数処理の設定の粒度はまだどこも決めていない**（[11 §4](../11_消費税設計.md) は「用途ごとに分ける」までである）
- **ベンダーが配る行は `REPLACE` の暗黙の DELETE から守る**（`Designer/ddl/016`。2026-09-23）。
  **014 は 0039 で配って以来この穴を抱えていた**——`INSERT OR REPLACE` で控除割合 80% の行が
  消えて別の行に置き換わることを実測した。**行までベンダーが配る表では、行の上書きも不変条件である**
- **行の同値検査は同じ回に入れた**（2026-09-23。`BusinessApp.TestSupport/VendorRows.cs`）——
  **行を配る前に、行の同値検査を先に入れた**。[ADR-0020](0020-スキーマは現在形の正典で持ち変更は差分で配る.md) が
  「フェーズ 3 まで保留」としたものである。
  **`MigrationEquivalenceTests` が「seed ≡ baseline+migrations」を、`migrate.ps1 -Verify` が
  「seed ≡ 稼働 DB」を見る。** **比べるのは意味の列だけ**で、代理キーと監査列は見ない
  （**新しく作った DB は 1 から、配達で足した DB は続きから `id` を振る**）
