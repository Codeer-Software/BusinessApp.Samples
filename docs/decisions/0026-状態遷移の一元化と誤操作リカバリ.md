# ADR-0026: 状態遷移の一元化と誤操作リカバリ（逆遷移）の設計

- 日付: 2026-07-19
- 状態: 採用・実装済み
- 関連: ADR-0027（ボタン色規約）、ADR-0008（検収基準売上）、docs/04（仕訳データモデル）

## 背景（ユーザーレビュー 2026-07-19）

1. 見積の「状態」を直接「受注」に変更できるが、受注レコードは作られない（ドロップダウン直接編集が遷移ロジックを素通りする）
2. 受注の「状態」を空欄にして保存できる（IsRequired なし・直接編集可）
3. 一覧の削除ボタンで状態を問わず行を削除できる（下書き以外も消せる）
4. 「状態を遷移し間違えたとき、どう戻すか」が機能ごとに未設計（ユーザー指示: 全機能を見直し仕様を考えて作る）

## 決定1: 状態フィールドの三原則

1. **ワークフロー状態はすべて表示専用**（詳細レイアウトの Status 列に `IsViewOnly: true`）＋ `IsRequired: true`。遷移は**ボタン経由のみ**（遷移ロジック・ガード・仕訳生成が必ず通る）
2. **一覧の行削除ボタンは文書系モジュールから全面撤去**（モジュール側 `ListPageFieldDesign.CanDelete: false` とフレーム側 Link の両方）。削除は**詳細画面の赤ボタン**（状態条件付き・確認ダイアログ付き・`this.Delete()`）のみ — ExpenseRequest の 7/16 パターンを全文書に展開
3. **押しても必ずエラーになるボタンは見せない**（状態・ロール・データ条件で `IsVisible` を切替。例: 請求書作成済みの検収では「請求書を作成」を消して「INV-xx 作成済み」ラベルを表示）

### 例外（状態セレクトの直接編集を維持するもの）

- **FiscalYear / FiscalPeriod**: 締め・再オープンは「状態変更そのものが業務操作」であり、E2E・デモ台本でこの操作系が確立済み。ガード（draft 残存警告・締め済み起票ブロック）も実装済み
- **Project.status / 各マスタの is_active**: ワークフローではなくマスタ属性
- **BankStatementLine**: 状態は取込ワークフローが機械管理（詳細では表示専用化のみ実施。一覧の🗑は「未起票明細の掃除」としてドキュメント化済みの挙動なので維持）

## 決定2: 逆遷移（誤操作リカバリ）の全機能設計

方針: **会計事象（仕訳）を生んでいない遷移は無条件で戻せる／仕訳を生んだ遷移は「仕訳を削除して戻す」を期間 open の場合のみ許可**（締め済みは赤伝＝決算修正仕訳へ誘導）。仕訳削除は生成時と同じ `source_type`+`source_id` で特定するため取り違えがない。取消系ボタンは全て赤（Danger）＋確認ダイアログ＋経理ロール限定（仕訳を伴うもの）。

| 機能 | 前進遷移 | 逆遷移（新設） | ガード |
|---|---|---|---|
| 見積 Quote | 送付済にする／受注にする（受注生成）／失注にする | **下書きに戻す**（sent/rejected→draft、accepted→draft） | accepted からは受注が存在する限り不可（先に受注削除） |
| 受注 SalesOrder | 完了にする | **進行中に戻す**（closed→open） | — |
| 検収 Acceptance | 検収を確定（売上仕訳生成）／請求書を作成 | **確定を取り消す**（confirmed→draft、売上仕訳を削除） | 請求書作成済みは不可（先に請求書削除）／仕訳期間が締め済みは不可（赤伝誘導） |
| 請求書 Invoice | 発行する | **下書きに戻す**（issued→draft） | 入金レコードあり・partial/paid は不可（先に入金取消）／定期・SES の生成仕訳ありは不可（赤黒訂正へ） |
| 入金 Receipt | 入金を確定（消込仕訳生成） | **入金を取り消す**（消込仕訳を削除→未確定へ。請求書ステータスを「消込仕訳が残る入金の合計」で再計算） | 仕訳期間が締め済みは不可 |
| 仕入先請求書 VendorInvoice | 未払計上（仕訳生成）／支払登録（仕訳生成） | **未払計上を取り消す**（accrued→received）／**支払を取り消す**（paid→accrued）いずれも該当仕訳を削除 | 各仕訳の期間が締め済みは不可 |
| 振替伝票 JournalEntry | 確定 | （確定の取消は作らない＝**赤黒訂正**が正） | 下書きのみ詳細から削除可 |
| 経費精算 | 既存の承認フロー | 既存（却下→差し戻し・キャンセル・実費超過再承認）で設計済み | — |
| 銀行取込 | プレビュー→登録→一括起票 | 既存（プレビュー取消・行🗑・手修正） | — |

### 削除の許可条件（詳細画面の赤ボタン）

| モジュール | 削除できる条件 |
|---|---|
| Quote | draft のみ |
| SalesOrder | 検収が存在しないこと（確認ダイアログで見積が accepted のまま残る旨を案内） |
| Acceptance | draft のみ |
| Invoice | draft かつ入金・生成仕訳なし |
| Receipt | 未確定（消込仕訳なし）のみ |
| VendorInvoice | received（仕訳未生成）のみ |
| JournalEntry | draft のみ（確定済みは赤黒訂正） |

## 実装メモ

- 仕訳の削除は `ModuleSearcher<JournalEntry>` で `source_type`+`source_id` により特定し `je.Delete()`（Lines は `DeleteTogether: true` でカスケード）。検索インスタンスへの Submit が効くことは実証済み（docs/05 B4-4）で、Delete も同じ Module API
- 期間ガードは仕訳の `entry_date` の**月初日**で FiscalPeriod を解決（境界日の辞書順比較の罠を回避する既知パターン）
- 既存データの状態空欄は 0 件を確認（補修不要）
- 補助: 検収で請求書作成済みの場合の案内ラベル（InvoiceDoneLabel）、確定後の保存ボタン非表示化も本 ADR の原則3に基づく

## 残課題（→ 横展開調査で扱う）

- マスタ系（Partner/Project/Account 等）の一覧削除: 参照整合（使用中マスタの削除）の方針が未設計。「削除ではなく無効化」への統一を検討
- FixedAsset・FiscalYear の一覧削除ボタンも同様に要検討
