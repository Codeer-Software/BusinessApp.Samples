# ADR-0021 C# は読みやすさを損なわない範囲で最新の記法に揃える

## 状況

対象は .NET 8（C# 12）。コードは primary constructor・コレクション式・record など
新しい記法を既に多く使っているが、古い書き方（文字列連結・`Environment.NewLine` の連結）と
読みにくい新記法（`is { }`）が混在している。

**開発者の指示（2026-08-25）**: C# 12 までのできるだけ新しい記法を使う。
見本として `JournalPostingRejectedException.cs` を開発者自身が改稿した。
あわせて **`is { }` は非常に分かりにくいので使わない**。

## 決定

### 1. 目的は読みやすさである。新しさそれ自体ではない

新しい記法でも読みにくくなるもの（`is { }` が代表）は採らない。
迷ったら「初見の読み手が意味を一意に取れるか」で決める。

### 2. 記法の対応表

| 場面 | 使う | 使わない |
|---|---|---|
| null 検査＋値の取り出し | **型パターン** `x is int v` / `x is string s` | `x is { } v`（**禁止**。null 検査に見えない） |
| null 検査のみ | `is null` / `is not null` | `== null` / `!= null`（演算子の多重定義に左右される） |
| 文字列の組み立て | **補間** `$"{...}"` | `+` の連結 |
| 複数行の文字列 | **raw string literal** `$"""..."""` | `Environment.NewLine` の連結 |
| コレクションの生成 | **コレクション式** `[...]`・スプレッド `[.. xs]` | `new List<T> { ... }`・`ToArray()` の羅列 |
| 依存の受け取り | **primary constructor** | フィールド代入だけのコンストラクタ |
| 型が左辺で明らかな生成 | target-typed `new()` | 型名の繰り返し |
| 条件分岐で値を返す | **switch 式**・パターンマッチ | if-else の連鎖で代入 |
| 名前空間 | file-scoped（既に全域） | ブロック形 |

**raw string literal の改行はソースファイルの改行そのもの**であり、
`Environment.NewLine`（Windows では CRLF）ではない。しかも作業コピーの改行は
クローンごとの `core.autocrlf` 設定に依存する。
そこで 2 つで守る: ① `.gitattributes` に `*.cs text eol=lf` を敷いて**ソースの改行を LF に固定**する
（導入済み。§4-3）。②**利用者向け文言の改行は raw literal の改行（＝LF）に統一し、
`Environment.NewLine` を混ぜない**。`string.Join` で行を束ねるときも `"\n"` を使う
（表示先はブラウザで、LF で足りる。混ぜると 1 つの文言の中で改行コードが割れる）。

### 3. スコープ

- **対象**: 自作の C#（`AccountingCore` 系・`TestSupport`・`Schema.Tests`・`SchemaVerifyCli`）。
  ここにはビルドの関門（§4-1）を敷く
- **対象外**: **CLB スクリプト（`*.mod.cs`）**。ツリーウォーク型インタプリタが対応する
  範囲しか書けない（[ADR-0008](0008-CLBとCSharpライブラリの責務分担.md)）。新記法を持ち込まない
- **必要最小限に留める**: CLB テンプレート由来のプロジェクト（`BusinessApp.Server`・
  `BusinessApp.Client`・`BusinessApp.Client.Shared`・`BusinessApp.Designer`・
  `BusinessApp.LicenseRegisterCli`）。**ビルドの関門は敷かない**——テンプレート更新との差分を
  無用に増やさないため。ここに置いた自作コードは §4-2 の規約テストが守る

**`BusinessApp.Server` には自作部分が 3 本ある**（テンプレート取り込み以降の差分）。

| ファイル | 何か | 行き先 |
|---|---|---|
| `Controllers/JournalsController.cs` | 取消・訂正の Web API（[ADR-0016](0016-画面から呼ぶサーバ処理はWebAPIに置く.md)） | **移動済み**（2026-08-26）。残るのは認証・経路・データソース名の解決だけ |
| `Services/CustomizedModuleDataIO.cs` | 計上の関門の入口 | **移らない。** CLB の `ModuleDataIO` の override なのでホスト側にしか置けない |
| `Services/ExceptionHandlerUtils.cs` | 例外の文面を組み立てて画面へ返す | 移らない。§2 の改行の規則だけ規約テストが見る |

**関門を敷かない理由は「やがて空になるから」ではない。** 自作部分は残り続ける。
テンプレート更新との差分を無用に増やさないためである。

**そのうえで例外が 1 つある。`BusinessApp.Server` は「利用者に見せる文言を組み立てる層」でもある**
（`UseExceptionHandlerSendToFront` が例外の文面を組み立てて画面へ返す）。
ビルドの関門は敷かないが、**改行コードの規則（§2）だけは規約テストが見る**。
実際、一斉見直しで例外の中身を LF にした結果、つなぎ目だけが CRLF で残っていた。

**`BusinessApp.AccountingCore.Client` は現時点で `.cs` を 1 本も持たない。**
表にも `.editorconfig` にも載っているが、守るものがまだ無い（実装が入った時点で効き始める）。

### 4. 機械で守る

守り方は 2 つある。**どちらでも守れないものは、規約に書いても守られない。**

#### 4-1. ビルドの関門（`.editorconfig` ＋ `EnforceCodeStyleInBuild`）

`TreatWarningsAsErrors` と組で強制になる。
`EnforceCodeStyleInBuild` は**対象 8 プロジェクトすべてに新しく足した**。
`TreatWarningsAsErrors` は 5 本が既に持っていたので、無かった 3 本
（`Schema.Tests`・`AccountingCore.Tests`・`AccountingCore.Server.Tests`）に足した。

**`option = value:warning` の severity はビルドでは効かない**（2026-08-25 実測）。
たとえば `csharp_style_namespace_declarations = file_scoped:warning` だけを書くと、
エディタには波線が出るのに**ビルドは素通りする**。止めたい規則は
`dotnet_diagnostic.IDEnnnn.severity = warning` を**規則 ID ごとに明示的に**書かなければならない。

これは**「機械で守っているつもりで、実は何も見ていない」**という壊れ方をする。
気づいたのは、規約に反する形をわざと書いて**警報が鳴るかを確かめた**ときである。
以後、機械の関門を足したら**必ず一度わざと壊して鳴ることを確かめる**。

そこで `.editorconfig` は 2 段構成にしてある。

| 段 | 何を書くか | 効き目 |
|---|---|---|
| `[*.cs]` | **好みの表明**（どちらの書き方が正か） | エディタの提案。ビルドは見ない |
| `[BusinessApp/BusinessApp.{対象}/**.cs]` | **規則 ID ごとの severity** | ビルドの関門 |

対象外（CLB スクリプトと CLB テンプレート由来のプロジェクト）は、
**下段のパスに含めない**ことで外してある。除外の指定を書かない分だけ壊れにくい。

**2 段は独立ではない。片方だけ触らないこと。**
下段の severity は「どの規則を報告するか」しか決めず、**何を正とするかは上段が決める**。
上段の option を消す・`false` にすると、下段は warning のまま何も報告しなくなる——
`dotnet_diagnostic.IDE0290.severity = warning` が primary constructor を要求するのは
`csharp_style_prefer_primary_constructors = true` があるからで、これを `false` にすると
IDE0290 は逆に「primary constructor をやめろ」と言う。**規則を足すときも消すときも両方を直す。**

**強制しないと決めた規則**（理由つきで `.editorconfig` に残す）

- **IDE0305**（LINQ の終端の `.ToList()` / `.ToArray()` を `[.. 式]` にする）。
  複数行の連鎖の頭に `[..` が来ると開き括弧と閉じ括弧が遠く離れ、
  「ここで実体化する」という意図も読み取りにくくなる。§1 の基準で落とした（対象は 19 か所）。
  **配列リテラルの `new[] { ... }` → `[...]`（IDE0300）は強制する。** 別の規則である
- IDE0045 / IDE0046（三項演算子への寄せ）。条件が長いと一行が読めなくなる
- `var` の使い分け（本 ADR の表に無い）・式形式メンバの強制

#### 4-2. 規約テスト（`CSharpStyleConvention`）

ビルドで表現できないものを、読んで検査する。判定と表明はどちらも
`BusinessApp.AccountingCore.Tests/Conventions/` にある（**テストの土台に置かない**——
共有すると Roslyn の DLL 9 MB が `SchemaVerifyCli` の出力にまで載る）。

**正規表現ではなく構文木（Roslyn）で見る。** 最初は正規表現で書いたが、
自己レビュー（2026-08-26）で次が分かった。

- `x is{}`（空白なし）を取りこぼす。C# は `is` と中かっこの間に空白を要求しない
- 行ごとに当てていたので、**改行をまたぐ書き方**を取りこぼす
- コメントと文字列を消してから当てるために手書きの字句スキャナを持っていたが、
  補間文字列の穴の中の引用符（`$"{s.Split('"')[0]}"`）で走査がずれ、**行末まで消えていた**。
  消しすぎは「違反 0 件」に化けるので、取りこぼしより危ない

構文木なら、コメントと文字列リテラルはそもそも式ではないので**誤検知が原理的に起きず**、
空白と改行の入れ方にも左右されない。字句スキャナ約 200 行が消えた。
`Microsoft.CodeAnalysis.CSharp` はリポジトリ内の他プロジェクトと同じ版（4.9.2・MIT）で、
**テストプロジェクトにだけ足す**（`AccountingCore` の依存ゼロは保つ）。

**① 禁止形**

| 見るもの | 範囲 | 構文上の判定 |
|---|---|---|
| `is { }` | **リポジトリ内のすべての `*.cs`**（CLB スクリプトを含む） | 型も位置パターンも無く、中身が空のプロパティパターン。`is string { }` や `is { Length: 0 }` は当たらない |
| `== null` / `!= null` | ビルドの関門を敷いたプロジェクト | 等値・非等値の二項演算で、左右のどちらかが `null` リテラル。**括弧とキャストは剥がす**（`x == (object)null` は多重定義を迂回するために人が書く形で、この規則が禁じたいものそのもの）。`x == default` は見ない——値型どうしの正しい比較が実在し、意味解析なしでは区別できない |
| **`#if` / `#elif` / `#else`** | **リポジトリ内のすべての `*.cs`** | 条件付きコンパイルの中は**構文木から消える**ので、そこに書かれた禁止形は検査を素通りする。分岐の網羅という難問を持ち込むより、使わない。**理屈は適用範囲の広い側にこそ当てはまる** |
| `Environment.NewLine`、および**リテラルの中の CR** | `AccountingCore`・`AccountingCore.Server`・`BusinessApp.Server`（§3 の例外） | `NewLine` という名前そのものを疑う（字面で `Environment` と比べるだけでは `global::` 付き・`using static`・別名 using が抜ける）。CR は**補間文字列・文字リテラル・UTF-8 リテラルまで**見る——ここが唯一の網で、ファイルの実バイトを見る検査には当たらない |
| **構文を読めなかったこと** | 禁止形を 1 つ以上当てるとき | 構文が壊れていればどの禁止形にも当たらず、見た目は「きれい」になる。**読めなかったことを「違反 0 件」と混同しない** |

**② 関門そのもの**

| 見るもの | なぜ要るか |
|---|---|
| csproj が `TreatWarningsAsErrors` と `EnforceCodeStyleInBuild` を宣言しているか（**強制対象の表に載るものだけ**） | XML として読む。文字列の部分一致だと、コメントアウトした宣言や `Condition` つき `PropertyGroup`（＝特定の構成でしか効かない宣言）を「有る」と数える |
| **`NoWarn` / `WarningsNotAsErrors` が IDE の規則を抑制していないか**（csproj ＋ **`Directory.Build.props` など暗黙に読み込まれる設定**） | 宣言を残したまま `<NoWarn>IDE0055</NoWarn>` を 1 行足せば関門は死ぬ。**「必要なプロパティが有る」ことは「関門が効いている」ことを意味しない。** 必要プロパティの側は集約されると誤検知（＝安全側）だが、**抑制の側は逆向きに壊れる**ので非対称に見る |
| `.editorconfig` の強制セクションの見出しと表が一致しているか（両方向） | ここがずれると、csproj も表も正しいのにビルドが素通りする |
| **規則の実効 severity**（Roslyn に**リポジトリ内のすべての `.editorconfig`** を解釈させて引く） | **見出しの照合だけでは、中身の severity 行が全部消えても・後ろに広いセクションを足して打ち消しても緑になる。** ルート 1 本だけを見ると、下の階層に 3 行置いて打ち消せる。対象外のプロジェクトで警告に**ならない**ことも同時に見る |
| **上段の option の値**（何を正とするか） | severity は「報告するか」しか決めない。`csharp_style_namespace_declarations` を `block_scoped` にすると、IDE0161 は warning のまま**逆のこと**を言う。**6 行反転しただけで 10 個のビルドエラーが消えたのにテストは全部緑だった** |
| **警告になっている規則の数が下限を割っていないか** | 名指しで守るのは代表の 10 件だけで、`.editorconfig` にはその 4 倍以上ある。**名指ししていない分を全部消しても検査は緑になる** |
| どちらの表にも載っていないプロジェクトが無いか（実体は **`BusinessApp.slnx`**） | ビルドされるのはソリューションに載っているものであって、フォルダの有無ではない |
| **強制対象の件数が下限を割っていないか** | 3 つの表を揃えて動かせば、整合したまま関門だけが消える。ミューテーションスコアと同じラチェットを置く。**下げるときは qa/02 に理由を書いて下げる** |
| `.gitattributes` が **1 本だけ**で、その中の**最後の**指定が `eol=lf` か。C# に CR が無いか | §4-3 |

**③ 検査が空回りしていないこと**

- **禁止形を実際に食わせて、当たることを確かめる。** 通す経路は本番と同じ関数である
  （テストだけが通る別の道を作らない）
- **判定はすべて「入力を受け取って結果を返す」形にする。** そうしないと
  「壊した入力を食わせて赤になる」検査が書けず、**中身を空にしても緑のまま**になる
  （実測した時点の 6 つの検査のうち、5 つがそうだった）
- **判定と読み取りを混ぜた「薄い皮」を作らない。** ディスクから読むものは
  「**どこを読むか**」だけを持ち、判定を持たない。皮に判断が残ると、そこは中身を空にしても
  緑のまま通る——実際、走査範囲を 1 語変えると `Designer/*.mod.cs` が黙って対象外になった
- 規約を説明する doc コメント・SQL の中の文字列・似て非なる正しい記法が、
  **当たらないこと**も対で表明する。誤検知は「規約を書けなくなる」形で効いてくる
- 場所の解決を間違えると 1 本も読まないまま緑になるので、
  **この検査自身のソースと `*.mod.cs` を見つけられること**を表明する

**見ていないもの**（承知のうえで残す）

- `*.razor` の中の C#。切り出す手間に見合わない（現状 6 本・違反 0 件）
- `Directory.Build.props` に集約したプロパティ。csproj 自身しか見ないので、
  集約すると「無い」と報告される。**安全側に倒れている**ので、集約したくなった時点で直す

#### 4-3. 改行コード

`.gitattributes` に `*.cs text eol=lf` を足し、raw string literal の改行を LF に固定した。
リポジトリ側は既に LF なので、この変更で差分は出ない（変わるのは作業コピーだけ）。

**リポジトリ内のテキストの改行は 1 種類に揃える。** `* text=auto` を `* text=auto eol=lf` に広げた。
`.cs` だけを固定すると、`.sql` や `*.mod.json` は clone した機の設定で CRLF になり、
**C# の raw string literal（LF 固定）とファイルから読んだテキストを突き合わせる検査**が
機械によって結果を変える。追跡ファイルに CRLF を要求する種類（`.bat` / `.cmd`）は 1 本も無い。
`*.cs` の行を残してあるのは、規約テストが**この 1 行の存在**を検査するためでもある。

**ただし `.gitattributes` が効くのは checkout のときだけ**で、既に CRLF で持っている作業コピーは
`git add --renormalize` か再 checkout をするまで直らない。IDE0055 も改行コードを見ない。
しかも**その行を消しても、この機の作業コピーは LF のままなので CRLF 検査は緑を返す**——
壊れが出るのは別のマシンが clone した後である。そこで §4-2 の規約テストが
「`.gitattributes` にこの行が有ること」と「C# に CR が無いこと」を**両方**見る。

### 5. 挙動を変えないことの担保

一斉見直しは「挙動を変えないリファクタリング」として行い、既存の全ゲート
（テスト・カバレッジ 100%・ミューテーション・`designcheck`・`-Verify`）を通し、
主要画面の実機確認で締める（[ADR-0012](0012-テスト方針とカバレッジのゲート.md)）。
記法の置き換えで意味が変わりうる箇所（演算子の多重定義・改行コード・遅延評価）は、
機械的に置換せず 1 か所ずつ読む。

## 理由

- **早いほど安い。** 後回しにするほど直す箇所が増える（開発者の指摘）。
  全ゲートが緑で機能作業が仕掛かっていない今が、挙動を変えないリファクタリングの最安のタイミング
- **規約は書いた時点から効く。** 一斉見直しを先にやれば、以後のすべてのタスクの差分が
  安定した記法の上に乗り、レビューのノイズが減る
- `is { }` の禁止は好みの問題ではなく読み手のコストの問題である。`is int v` は
  「int が入っていたら取り出す」と読めるが、`is { }` は null 検査であることが字面から読めない

## 帰結

**一斉見直しは実施済み（2026-08-25〜26）。** テスト 703 件・カバレッジ 100%・
ミューテーション・`designcheck`・`-Verify` がすべて緑。
**実機確認は開発者が行った**（トーストの表示。下記）。

- 開発者の見本（`JournalPostingRejectedException.cs`）は 2 点を規約に揃えて取り込んだ:
  ① `is not null and int lineNo` → `is int lineNo`（同義。型パターンが null を通さないため、
  規約の推奨形は短い方にした。**開発者と合意済み**）
  ② raw string literal の中の `string.Join(Environment.NewLine, ...)` → `string.Join("\n", ...)`
- `is { }` は 32 か所を型パターンに置き換えた。**うち 2 か所で `using` が足りずビルドが落ちた**——
  型名が字面に出ることの効果がそのまま出た形である
- 利用者に見せる文言の `+` 連結 4 か所は 1 つの補間文字列に、
  テストの SQL の `+` 連結 4 か所は raw string literal にした。
  **触った文言 5 本には完全一致の表明を置いた**——部分一致では、日付をはさんだ後半（＝つないだ側）と
  行を束ねる改行そのものが無防備なままになる。
  **値を埋め込む文言（補間の穴があるもの）は完全一致で固定する。地の文だけの文言は部分一致でよい**
- **改行そのものについては、この ADR の前提が 1 つ崩れた。**
  開発者の実機確認（2026-08-26）で、**CLB のトーストは改行を表示に出さない**ことが分かった
  （LF でも CRLF でも同じ。[qa/01](../qa/01_CLB静かな失敗.md) D-12）。
  §2 の改行の規則そのものは正しい（ソースの改行が clone ごとに変わるのを防ぐ）が、
  **「複数行の文言を作って見せる」という使い方は成立しない**。
  文言の組み立てを 1 行前提に直すかは[保留リスト](../README.md) 9 で決める
- **機械の関門は、足したら一度わざと壊して鳴ることを確かめる。**

  検査の中身を空にしても大半が落ちない／**severity を守っても上段の option を反転すれば関門が消える**。
