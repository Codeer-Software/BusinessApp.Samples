# ADR-0070 明細にも楽観ロックの版を持たせ、明細だけの保存でも伝票の版を進める

## 状況

**2026-09-25 に、同じ下書きを 2 つのタブで開き、同じ明細の金額をそれぞれ直して保存すると、あとの保存が黙って勝った**
（下書き id 264 の明細 484。タブ B が 1000 → 2000 で保存したあと、画面が 1000 のままのタブ A が 1000 → 3000 で保存すると、断られずに 3000 が残った——
[qa/04 の記録](../qa/04_実機操作テスト/2026-09.md) の 2026-09-25）。**先に保存した人に知らされないまま、金額が置き換わる。**

**分かっていた事実が 2 つある**——
①**明細の表 `journal_lines` に版（楽観ロックの版番号）の列が無かった**（この回より前の `Designer/ddl/005`。[qa/01](../qa/01_CLB静かな失敗.md) の F-41 ③ の 2026-09-10 の実測でも、明細の × の差分の版は `null` だった）。
伝票の表 `journal_entries` には `optimistic_locking` があり、CLB の `OptimisticLockingFieldDesign` がその伝票の差分を持つ保存のたびに進める（[qa/04 の記録](../qa/04_実機操作テスト/2026-09.md) の 2026-09-25 の CNC-01——摘要の保存で版 0 → 1）
②**明細だけの保存は、伝票の差分を 1 つも持たない**（F-41 ②）ので、伝票の版は進まず、突き合わせも起きない。
保存の関門（`JournalSubmitGate`）は明細について「まだ在るか」だけを見ていた。
**上書きが通ったのは、この 2 つが重なったからだと読む**（Claude の読み。**直したあとは止まった**——2026-09-25 の実機。qa/04 の CNC-07）。

**同じ根から、ほかに 2 つの形が出る**（2026-09-25 の自己レビューで挙がった。Claude の読み）——
③先に保存した人が明細だけを直したあと、**古い画面**（先に保存した人の保存より前に開き、開き直していない画面）**のまま計上する・伝票を削除する・摘要を直して保存する**と、関門は伝票の版で比べるしかなく（伝票の版は動いていない）、見ていない明細の変更の上に書く
④先に保存した人が**計上した**あと、古い画面のまま明細だけを直すと、計上は明細の版を進めないので関門を通り、**計上済みの行を変えさせない DB のトリガ（[ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md)）に当たる**。

## 観測（2026-09-25。Claude がブラウザで送信の中身を捉えた）

**CLB の振る舞いとしての正典は [qa/01](../qa/01_CLB静かな失敗.md) の F-41 ③ で、ここは決めた時点で見たことの控えである。**
**決定 1〜3 のコードを配り（決定 4・5 を足す前）、明細 1 行の下書き（id 255）で確かめた**（`window.fetch` を包んで送信の本文を読んだ——qa/01 の G-16。**ブラウザ側の観測で、サーバが受け取った形のダンプではない**）。

- **明細の更新の差分に `OptimisticLocking` が載る**
- **明細の × の削除（`ModuleDeleteInfo`）に版が載る**（`DecimalValue`）——F-41 ③ の「版は `null`」は、欄が無かった頃の実測だった
- **保存のあと、CLB は伝票と明細を読み直す**（`api/module_data/list` を伝票と明細に 1 本ずつ打ち、`OptimisticLocking` を取り直す）
- **開き直さずに同じ明細をもう一度保存しても、断られなかった**（金額 600 → 700。明細の版は 1 → 2、伝票の版は 0 のまま）

**確かめていないこと**——**CLB 自身が古い版の明細の更新を拒むか**（関門が先に断るので、実機では見えない）。**関門が進めた伝票の版を画面が次の保存に載せるかは、送信の本文では見ていない**（実機の合否からの読みは帰結の最後）。

## 決定

**決定 1〜6 は Claude の判断である**（2026-09-25。開発者の承認は得ていない——[05](../05_開発者への問い.md) の Q-68 で後から諮っている）。**断りの文言の正典は `JournalLineRules` とそのテスト**で、下の字は決めた時点の写しである。

1. **`journal_lines` に `optimistic_locking INTEGER NOT NULL DEFAULT 0` を足す**（`Designer/ddl/005`・マイグレーション `0046`）
2. **明細のモジュール（`JournalLine`）に、予約名 `OptimisticLocking` の欄を置き、`IncrementVersion: true` にする**——伝票と同じ形
3. **保存の関門は、変える・消す明細の版を保存済みの版と突き合わせ、食い違う明細の数を入れた 1 文で断る**
   ——「明細 N 行が、あなたが開いたあとに別の人に変更されています。画面を開き直して、その変更を確かめてから、もう一度操作してください。」
   **版の欄が無いか新規の形なら判定しない**、**読めない型なら止める**（伝票の版と同じ）
4. **明細だけを変えた保存（伝票の差分が無い保存）が成功したら、関門がその伝票の版を 1 つ進める**——③を塞ぐ。
   **伝票の差分がある保存の伝票は進めない**（CLB が進めるので 2 つ進む）。**下書きにしか当てない**。**進める伝票は保存の前に決める**
   （保存のあとの差分では、新しい伝票の明細の親が本物の識別子に書き換わっているかもしれず、作ったばかりの伝票の版を進めてしまう）
5. **開いたあとに伝票が計上されていたら、何を直した保存でも、同時操作の断りとしては「計上されました」の 1 通にする**——④を塞ぐ（入力の要件の断りは別に並びうる）。
   「この伝票は、あなたが開いたあとに計上されました。計上した伝票は変えられないので、画面を開き直して、直すときは「訂正する」を使ってください。」
   **伝票の版が食い違った保存でも、計上されていればこちらを言う**（「もう一度操作して」と言っても、開き直した伝票は閲覧専用）。
   **削除は計上済みを版より先に見る**——古い版の削除なら「この伝票は、あなたが開いたあとに計上されました。計上した伝票は削除できないので、画面を開き直して、取り消すか訂正してください。」（古い下書きの画面には取消・訂正のボタンが無い）、今の版なら前からある「伝票番号 N は計上済みです。…」
6. **伝票が消えていたか、変えられていたか、計上されていたら、明細のことも行番号の重なりも言わない**——開き直すか一覧へ戻れば、明細も番号も見直せる。**明細を足すだけの保存で番号が重なる形には効かない**（帰結の「2 つのタブで同じ下書きに明細を足すと」）。
   **消えた伝票に明細を足す保存は「削除しました」と断る**（見ないと外部キーに当たる）

## 理由

**比べた案**（2026-09-25。Claude の判断）——

| 案 | 効き方 | 扱い |
|---|---|---|
| **明細に版を持たせる（決定 1〜3）** | 明細の版が差分に載り、保存のたびに進む（観測）。関門が食い違いを利用者の語で言う | **採った**——同じ明細の上書き（状況の①②）は、明細の版でしか見分けられない |
| **明細の保存で伝票の版を進める（決定 4）** | 伝票の版が「明細を含む伝票全体」の版になる | **採った（決定 1〜3 と組で）**——これだけでは、あとから明細だけを保存する側の差分に伝票の版が載らないので、**明細どうしの上書きは止まらない**。③は塞ぐ |
| 関門が、画面が開いたときの値と保存済みの値を突き合わせる | 版の列が要らない | **採らなかった**——画面が開いたときの値は差分に載らない（CLB は触った欄の新しい値しか送らない——qa/01 F-12）ので、突き合わせる相手が無い |

**決定 4 を関門でやる理由**——CLB は伝票の差分が無い保存で伝票の行に触れない（F-41 ②）ので、**同じ要求の中で CLB と伝票の版を取り合うことが無い**。
DB のトリガで明細の変更に合わせて伝票の版を進める形は採らなかった——CLB が伝票と明細の両方を持つ保存で、明細を先に書くと伝票の版の突き合わせが外れうる（**順序は実測していない**。Claude の読み）。

**明細の削除で CLB 自身が版を見るかは確かめていない**（2026-09-25 の自己レビューで、CLB 1.3.20 の DLL の呼び出し先を読んだ担当は「物理削除は識別子だけで消す」と読んだ）。**だから決定 3 は削除も数える。**

## 帰結

- **実機の台本に CNC-07〜CNC-10 を足し、CNC-05 の期待を決定 4 に合わせた**（[qa/04 §3-7](../qa/04_実機操作テスト.md)）
- **伝票の版の意味が変わった**——「伝票の欄の版」から「明細を含む伝票全体の版」へ。書くのは CLB と、明細だけの保存のあとの関門である（`Designer/ddl/005` の注記）
- **明細の版は、その明細の差分が載った保存でだけ進む**。サーバが明細を書く経路（取消・訂正・複製の下書きを作る・計上のときの写し）は、新しい行を `DEFAULT 0` で入れるか、既存の行の版の列に触れないので、開いている画面の版と食い違わない（2026-09-25 の自己レビューでコードを読んで確かめた）
- **古い画面のまま、先に保存された明細とは別の明細だけを直す保存は通る**——先に保存された明細には触れないので上書きは起きず、保存のあと CLB が明細を読み直すので、画面に先の変更が出る（Claude の読み。実機では確かめていない）
- **伝票の `updated_at` は、明細だけの保存では動かない**（決定 4 は版だけを進める）——「いつ直したか」に明細の変更は残らない。**受け入れる**（Claude の判断——下書きを直した時刻は帳簿の記載事項ではなく、計上の日時は `posted_at` が持つ）
- **2 つのタブで同じ下書きに明細を足すと、行番号の重複の断りで行き止まりになりうる**（Claude の読み。実機では確かめていない）——[04 §5](../04_実装計画と現在地.md) に積んだ
- **画面を通らない経路（API・取込）の取りこぼし**（2026-09-25 の自己レビュー。Claude の読み）——明細の親を別の伝票に付け替える更新は、移る先を見ず、版も進めない。取込で計上済みの伝票に明細を足すと、開いていないのに「開いたあとに計上されました」と言う。**取込を設計する回**（フェーズ 6）に合わせて決める（[04 §5](../04_実装計画と現在地.md) に積んだ）
- **決定 4 で関門が進めた伝票の版は、画面が次の保存に載せていると読む**（Claude の読み。2026-09-25 の実機の合否から。送信の本文は見ていない）——明細だけの下書き保存のあと「同じ画面のまま」計上が通った（[qa/04 の記録](../qa/04_実機操作テスト/2026-09.md) の BOK-04。担当が手順に足した手）。台本どおりに流したなら、1 つのタブで開き直さずに明細だけの保存のあと摘要の保存・計上・削除も通った（同じ記録の CNC-08 の ③⑦⑧。担当の報告は開き直したかを書いていない）。**前提は、伝票の差分を持つ保存に伝票の版が載ること**（qa/01 F-41 ④）——載らなければ関門は判定せずに通すので、通っただけでは載ったとは言えない
