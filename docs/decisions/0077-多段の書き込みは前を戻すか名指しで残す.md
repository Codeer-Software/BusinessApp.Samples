# ADR-0077: 多段の書き込みは「前を戻す」か「名指しで残す」

- 日付: 2026-08-19

## 背景

**CLB のスクリプトにトランザクション境界は無い。** `Submit()` も `Delete()` も 1 レコード単位で、
複数レコードにまたがる更新を「まとめて成功／まとめて失敗」にする手段が用意されていない。

このアプリには多段の書き込みが多い。たとえば:

- **検収の確定**: 売上仕訳を作る → 検収を `confirmed` にする
- **見積の受注化**: 受注を作る → 見積を `accepted` にする
- **相殺入金の取消**: 仕入先請求の支払リンクを外す → 消込仕訳を消す（FK の都合でこの順しかない）
- **仕訳の削除**: 明細を 1 行ずつ消す → 伝票本体を消す（親単独の `Delete()` は子がいると静かに失敗する）

どれも**後半が失敗すると、前半だけが済んだ状態が残る**。そして残り方が悪い:

- 検収は「仕訳は posted・検収は draft」——「確定」は二重生成ガードに拒否され、
  「確定を取り消す」は `confirmed` でないと拒否される。**画面からどちらにも動かせない孤児**
- 相殺入金は「消込仕訳は残ったまま、買掛が未払で復活」——
  **ADR-0035 が防ごうとした「相殺済みの買掛を二重に振り込む」状態そのもの**
- 仕訳削除は「借方だけ／貸方だけの伝票が posted のまま帳簿に残る」

しかも従来のコードは、いずれも `Toaster.Error("〜に失敗しました（仕訳は生成済みです）")` と
出すだけで終わっていた。**何が起きたかは書いてあるが、何をすればいいかが無い。**

## 決定

**多段の書き込みで後半が失敗したら、前半を戻す。戻せないなら、残ったものを名指しで伝える。**

### 1. 戻せるなら戻す（補償）

「作りたてで誰も参照していないもの」は消せる。消せば操作前の状態に戻り、ユーザーは**もう一度押せばよい**。

| 経路 | 後半が失敗したとき戻すもの |
|---|---|
| 検収の確定 | 生成した売上仕訳を削除 |
| 見積 → 受注 | 作成した受注を削除 |
| 見積 → 定期請求契約 | 作成した契約を削除 |
| 相殺入金の取消 | 仕入先請求を `paid` に戻す（外した支払リンクを張り直す） |

メッセージは「**〜を取り消しました。もう一度〜を押してください**」。次の行動が書いてある形にする。

### 2. 戻せないなら、伝票番号を添えて名指しで伝える

補償自体が失敗することもある（DB エラーが続いているなら当然ありうる）。そのときは:

- **成功トーストを出さない**（これが一番まずい壊れ方——「保存された」と信じて離脱する）
- **何が残っているかを具体的に書く**——「伝票 No.84 は貸借が合っていない状態で帳簿に残っています」
- **誰に言えばいいかを書く**——「経理に連絡し、この伝票番号を伝えてください」

### 3. 消し始める前に「消せるか」を確かめる

仕訳の削除は `JournalEntry.DeleteWithLines()` に 1 本化し、
**明細を 1 行も消す前に、その伝票を指している他の表を調べる**。
`journal_lines` を参照する表は無い（`Designer/ddl/` を全数確認）ので、
削除が途中で落ちる現実的な原因は銀行明細（`bank_statement_lines.journal_entry_id`）と
仕入先請求の支払リンク（`vendor_invoices.payment_entry_id`）の 2 つだけ。
先に断れば、貸借の欠けた伝票を作らずに済む。

### 4. 最後の網は不変条件スイート

それでも壊れた状態が残ったら、`A01_仕訳_伝票ごとの貸借一致` が拾う。
**「気づかないまま流れる」ことだけは起きない**——これが方式として成立している根拠。

## 影響

- **削除の実装を書き写さない。** `DeleteWithLines` は正典であって、コピーではない。
  書き写した結果、同じ部分失敗が **7 か所**に増えていた（Receipt / BankStatementLine /
  VendorInvoice / Acceptance / Invoice / RecurringBilling / FiscalYear）。
  台帳（BUG-0148）が挙げていたのは 2 か所だけで、grep して初めて 7 か所と分かった
- 新しく多段の書き込みを書くときは、**後半の失敗パスに補償を書くまでがワンセット**

## 代替案と却下理由

- **削除した行を控えておき、失敗したら作り直す** — 却下。`journal_lines` は列が多く、
  1 つでも写し漏らすと**静かにデータが変わる**。しかも補償自体が失敗しうる状況で
  「新規作成」に頼るのは筋が悪い
- **サーバ側に C# の拡張サービスを置き、トランザクションで囲む** — 却下（今は）。
  CLB 単体でできる範囲を示すのがこのアプリの主旨（CLAUDE.md §2）で、
  上の 4 つで実害は塞げている。**トランザクションが本当に要る所が出たら、そこだけ拡張する**
