# ADR-0022 明細を並べる帳簿はクエリモジュールで作り、集計帳票はサーバ完結にする

## 状況

総勘定元帳を作るにあたって、**同じものについて 2 つの文書が違うことを言っていた**。

- [ADR-0008](0008-CLBとCSharpライブラリの責務分担.md) の「実行場所の決め方」の表:
  **「帳票・集計（試算表・元帳・B/S・P/L・税集計）は<u>サーバ完結</u>」**
- [05_実装計画と現在地](../05_実装計画と現在地.md) の着手順:
  **「総勘定元帳・補助元帳。<u>仕訳帳と同じクエリモジュールの形</u>」**

仕訳帳（`JournalBook`）は既にクエリモジュールで作ってあり、明細 1 行が 1 レコードで出る。
元帳はその仕訳帳を勘定科目ごとに並べ替えたものなので、**どちらの形でも作れてしまう**。
どちらを選ぶかは、この先の試算表・B/S・P/L・税集計の作り方まで決める。

## 決定

**「畳むか、畳まないか」で分ける。**

| | 作り方 | 例 |
|---|---|---|
| **明細を並べる帳簿**（行数が減らない） | **クエリモジュール**（SQL ＋ CLB 標準の一覧） | 仕訳帳・総勘定元帳・補助元帳・税区分別の明細 |
| **集計帳票**（畳んで初めて意味が出る） | **サーバ完結**（Controller ＋ `AccountingCore`） | 試算表・月次推移・B/S・P/L・税額集計 |

ADR-0008 の表のうち**「元帳」の行だけを本 ADR が上書きする**。他の行（試算表・B/S・P/L・税集計）は
そのまま有効である。

> **2026-08-26 追記**: [00 §3-3](../00_ドキュメント規約/フロントマター.md) はその後
> **「一部でも覆された ADR は全体を `superseded` にし、引き継いだ新 ADR を起こす」**に変わった。
> 本 ADR と ADR-0008 はその規約より前に書かれているので、**今回限りの例外**として
> ADR-0008 を `current` のまま据え置いている（開発者の判断）。次からはこの形にしない。

### 明細を並べる帳簿に置いてよい計算

**「表示のためのちょっとした加工」まで**。元帳では次の 2 つがそれに当たる。

| 計算 | なぜ SQL でよいか |
|---|---|
| **相手勘定科目**（複数なら「諸口」） | 同じ伝票の反対側の行を見るだけ。行数は減らない。法人税法施行規則 55 ② の法定記載事項なので省けない |
| **期間内累計** | 窓関数 1 つ。並んでいる行に沿って積むだけで、畳んでいない |

**符号の規則（通常残高がどちら側か）と、損益科目かどうかの判定は
[04 §6](../04_会計ドメイン設計.md) と `AccountCategory` が正典**である。
科目区分だけでは決まらない——評価勘定は逆になる。フェーズ 4 で試算表を C# に作るときは、
**同じ規則の 2 つ目の実装になる**ので、04 §6 と `GeneralLedgerQueryTests` の 4 通りを見比べて揃える。

## 理由

- **ADR-0008 が「サーバ完結」を選んだ決め手は往復の無駄である。** 原文は
  「クライアントへ明細を全件降ろしてから再送する二重往復を避ける」。
  元帳は明細をそのまま出す帳簿なので、降ろした先で送り返す形にならない。当たらない
- **SQL に書いたロジックも、このリポジトリではテストできる。**
  `JournalBookQueryTests` は本物の DDL を載せた使い捨て SQLite に**本物の SQL を流して**
  振る舞いを固定している。「テストしたいから C#」にはならない
  （元帳も `GeneralLedgerQueryTests` で同じ形にした）
- **CLB の一覧が持っているもの**——ページング・列幅・検索欄・遷移——を自前で作り直す理由が無い。
  `ProCodeField` で描き直せば、帳簿 1 つにつき同じものを書くことになる
- **集計帳票は逆である。** 全科目 × 全期間を畳んでから見せるので、明細を降ろす形にすると
  件数に比例して重くなり、しかも畳む規則（科目区分・評価勘定・決算書表示区分・端数処理）が
  会計そのものである。ここは `AccountingCore` に置いてゴールデンテストで守る

## 帰結

- 帳簿を足すときは `Designer/Design/Modules/Accounting/Books/` に SQL ＋ `*.mod.json` を置く。
  `QueryModuleTests` が宣言と SQL のずれを自動で拾い、**振る舞いは帳簿ごとにテストを書く**
- **並び順は帳簿の意味の一部である。** 元帳は科目ごと・取引日順に累計が積み上がるので、
  一覧の列で並べ替えさせない（`CanUserSort: false`）
- 元帳の累計は**期首残高を含まない**（フェーズ 4 で入る）。含まないことが分かる名前
  （「期間内累計」）で出し、フェーズ 4 で「残高」に変える

  > **2026-08-30 追記——元帳の累計を会計年度で切った。**
  > 上の表の「窓関数 1 つ・畳んでいない」という性質は変わっていない（窓の区切りが細かくなっただけ）。
  >
  > - **切ると決めたのは開発者**（2026-08-28。理由は「**損益科目**の累計が決算をまたいで積み上がる」）
  > - **その理由を損益科目に限って当て、貸借科目は切らないことにしたのは Claude**（2026-08-30。
  >   一律に切ると現金の累計が手許現金でも残高でもない数になる。[qa/02](../qa/02_自己レビュー記録.md) の R24-03）。
  >   並び順と年度の列も同じ回の Claude の判断である（R24-01・R24-04）
  >
  > **現在形の規則は `Designer/Design/Modules/Accounting/Books/GeneralLedger.Query.sql` が持つ**（ここには写さない）。
  > **仕訳帳は別の順序である**——あちらは「取引の発生順に」記載する帳簿だから（法規 55 ①）。
  >
  > **フェーズ 4 で期首残高を入れるときに見直しが要る**（R24-18）。
  > ①繰越を流すまで貸借科目の元帳が 0 から始まる ②窓の区切りは計上日由来の年度なのに、
  > 窓の中の並びは取引日なので、期首残高の伝票より前に並ぶ行が出る。
- **この決定の反対側（サーバ完結）が最初に試されるのは、フェーズ 3 の税区分別集計表**である。
  そのとき [05 §5 の未決事項](../05_実装計画と現在地.md)「集計帳票の API の形」を決める。
  フェーズ 4 の試算表はその 2 つ目になる

  上の表のとおり税額集計も集計帳票なので、先に来るのはフェーズ 3 である）
