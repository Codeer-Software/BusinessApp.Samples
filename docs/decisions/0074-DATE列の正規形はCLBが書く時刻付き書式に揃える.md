# ADR-0074: DATE 列の正規形は「CLB が書く時刻付き書式」に揃える

## 背景

SQLite の日付比較は**文字列比較**である。この DB の `DATE` 宣言列には 2 つの書式が混在していた。

| 書き手 | 書式 | 例 |
|---|---|---|
| アプリ（CLB の保存） | `YYYY-MM-DD 00:00:00`（19 文字） | `2026-09-01 00:00:00` |
| seed の DDL | `YYYY-MM-DD`（10 文字） | `2026-09-01` |

2026-08-19 時点で 37 列・405 行のうち **92 行が時刻なし**だった
（`fiscal_periods` 24 行・`time_entries` 19 行・`fiscal_years` 4 行 ほか）。

混在そのものは 2026-07-05 から把握していたが、当時の記録は
「辞書順比較は成立する（自作 SQL だけ `date()` で正規化すればよい）」という**誤った理解**で、
そのあと踏んだ「月末日の期間解決が失敗する」現象（2026-07-06 / 07-07）とも噛み合っていなかった。
結果として **20 ファイル・約 35 箇所に「月初日で解決する」という対症療法が散在**した。

## 実測して確定した事実（2026-08-19）

`FiscalPeriod.Status_OnDataChanged`（締める前に下書き伝票を数える処理）を計測器に使い、
`journal_entries.entry_date` の書式だけを変えて件数の変化を見た。

| 列の値 | 検索条件 | 結果 |
|---|---|---|
| `2026-09-01`（時刻なし） | `EntryDate >= 2026-09-01`（期間の開始日） | **落ちる** |
| `2026-09-01 00:00:00` | 同上 | 拾う |
| `2026-09-15`（時刻なし） | 同上（範囲の内側） | 拾う |

つまり **CLB が `ModuleSearcher` の日付比較に渡すパラメータは `YYYY-MM-DD 00:00:00` 側**である。
`'2026-09-01' >= '2026-09-01 00:00:00'` は辞書順で偽になるため、
**時刻なしの行だけが、範囲の下端で黙って消える**。

同じ理屈が期間解決の上端にも効く。`end_date >= 対象日` で `end_date` が
`2026-09-30`（時刻なし）・対象日が `2026-09-30`（パラメータは時刻付き）だと偽になり、
**「取引日に対応する月次期間がありません」**になる。これが 2026-07-07 に踏んだ現象の正体だった。

## 決定

**`DATE` 宣言列の正規形を `YYYY-MM-DD 00:00:00`（CLB が書く形）とする。**

- 既存データは `Designer/ddl/811_normalize_date_columns.sql` で一括正規化する（冪等）
- 不変条件 `F06_日付_DATE列の書式が揃っている` で 10 文字の値を検出する
- 今後 seed DDL に日付リテラルを書くときは **` 00:00:00` を付ける**

### 「時刻を落とす」方向に揃えてはいけない

台帳 BUG-0066 の当初の見立ては「DATE 列から時刻成分を落とす」だったが、これは**逆**である。
パラメータ側が時刻付きである以上、列を時刻なしに揃えると
**すべての下端比較（`>= 開始日`）が境界日で壊れる**。実測前に着手していたら大事故だった。

### 「月初日で解決する」既存の回避策はそのまま残す

正規化で不要になったが、**外すと再発時に気づけない**。
回避策は 2 重の安全弁として維持し、新規コードでも月初日方式を続ける
（`Designer/Project.md` の該当知見も更新済み）。

## 影響

- `Modules/` 配下の `.sql` と不変条件 SQL は日付比較を必ず `date()` / `strftime()` で正規化しており、
  この変更の影響を受けない（2026-08-19 に全文検査）
- 表示は CLB が `DateTime` としてパースするので変わらない
- 実機で試算表・ポータル・仕訳帳の再描画を確認、不変条件 45/45 緑
