# ADR-0027 入力の一覧はラップモジュールとクエリモジュールで作る

## 状況

開発者が「**振替伝票の一覧で、取り消された伝票がひと目で分かるようにしたい**」と挙げた
（2026-08-28）。例として「1 列増やして『取り消されています（取消伝票：xx）』と出す」。

いまの一覧は `JournalEntry`（CRUD モジュール）の標準一覧ページで、この列は作れない。
**「取り消されているか」が逆引きだから**である——取消伝票のほうが `original_entry_id` で
原仕訳を指しており、原仕訳の行は自分が取り消されたことを知らない。

[ADR-0022](0022-明細を並べる帳簿はクエリモジュールで作る.md) は**帳簿**（仕訳帳・総勘定元帳）を
クエリモジュールで作ると決めたが、**入力のための一覧**は対象外だった。

## 決定

### 1. 振替伝票の一覧を、ラップモジュール ＋ クエリモジュールで作り直す

CLB のマニュアル（`designer/page_types.md`「CRUD だけど一覧表示を完全にコントロールしたい」）が
示す形をそのまま採る。**前回プロジェクトが同じ構成で動かしている**（`JournalEntryBoard`）。

| モジュール | 役割 |
|---|---|
| `JournalEntryBoard` | **表示専用**（`DbTable` 空）。PageFrame には **`ModulePageType: "Detail"`** で登録する。DetailLayout に `SearchField` ＋「新規作成」ボタン ＋ `ListField` を並べる |
| `JournalEntryList` | **クエリモジュール**。SQL で取消・訂正の有無を `LEFT JOIN` で引き、列に出す |
| `JournalEntry` | **今のまま CRUD。** 詳細（起票・計上・訂正・取消）を担う。フレームの `OtherPageModuleDesigns` に登録する |

- **新規作成**は `NavigationService.GetModuleDataUrl("JournalEntry", "-")` へ遷移するボタンで作る。
  `-` が新規作成を表すことは**本プロジェクトで確認済み**（`/Main/JournalEntry/-` で作成画面に入れた。
  2026-08-28。[qa/04](../qa/04_実機操作テスト.md)）。**この 2 引数版は現在のフレームで解決される**ので、
  フレームが 5 枚になる本 ADR の後は、どのフレームから押されるかに注意する
- **行から詳細へ**は `AnchorTagField`（`Target: "Url"` ＋ `Module: "JournalEntry"` ＋
  `IdVariable`）の列で作る。仕訳帳の `EntryLink` と同じ形
- **下書きの削除は詳細画面に移す。** 標準一覧の削除アイコンが無くなるため。
  **これはクエリモジュール化の副作用で、利用者の操作が 1 つ動く**——
  開発者に諮っていない（[05 §5](../05_実装計画と現在地.md) で確認する）
  → **2026-08-28 開発者が承認**（「OK です。問題ありません」）

### 2. 「取り消されている」は SQL で引き、伝票の行には持たせない

`journal_entries` に `reversed_by_entry_id` のような列を**足さない**。
計上済みの行を UPDATE することになり、`trg_journal_entries_posted_no_update` が拒む。
**この 1 列のために [ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md) の最も強い守りを緩めない。**

出す内容は「取消・訂正の有無と、その伝票番号」とする。文言は利用者の語で書く
（[21_画面の原則 §2](../21_画面の原則.md)）。**画面で「仕訳」と単独に書かない**
（[ADR-0017](0017-仕訳と伝票の呼び分け.md)）。

### 3. 詳細画面にも「取り消されています」を出す

`/api/journals/availability` がすでに「訂正・取消ができるか」と理由を返している。
**取消伝票の番号を返す項目を足し、詳細画面に出す。** 一覧と詳細で同じ事実が見える。

### 4. 削除の実装は前回プロジェクトの形に従う

- **`this.Delete()` の戻り値を必ず検査する。** 子（明細）を持つ親の削除は、子側の失敗で
  `false` を返して**静かに終わる**（[qa/01 C-03](../qa/01_CLB静かな失敗.md)）
- **締めガードを入れる。** 会計年度・会計期間が締め済みなら削除させない
- 削除後は一覧（`JournalEntryBoard`）へ戻る

## 理由

**逆引きを表現する手が他に無い。**

| 案 | なぜ採らないか |
|---|---|
| `journal_entries` に取消先の列を足す | 計上済みの UPDATE になる。DDL のトリガが拒む（§2） |
| CRUD モジュールに計算列を足す | `QueryField` はクエリモジュール（`DbTable` 空）専用で、CRUD と混ぜられない |
| 行ごとのスクリプトで引く | `ListLayouts[""].OnAfterInitialization` は行ごとに発火するが（[qa/01 D-11](../qa/01_CLB静かな失敗.md)）、行数ぶんの `ModuleSearcher` は N+1 になる |
| 種別と原仕訳の列で読み取らせる（現状） | 取消伝票の**行**を見れば分かるが、原仕訳の行からは分からない。開発者の要求はそこ |

**性能上の理由も同じ向きを指している。** 前回プロジェクトは
「`JournalEntry` モジュール直の一覧は行ごとに重量級モジュール一式を構築して**表示に約 4 秒**かかっていた」
と実測して、この構成に移している（**前回プロジェクトの実測**。
`BusinessApp_old/Designer/Design/Modules/Accounting/JournalEntryBoard.mod.cs` のコメント。2026-07-20。
**同名のファイルを本プロジェクトにも作るので、引用元を取り違えないこと**）。
**本プロジェクトでは計測していない**（伝票がまだ数十件）。**年間 3,000〜4,000 仕訳**
（[05](../05_実装計画と現在地.md) フェーズ 7）を入れれば同じことが起きると**見込んでいる**。

**ADR-0022 と衝突しない。** あちらは「**明細 1 行 ＝ 1 レコード**の帳簿はクエリモジュールで作る」。
こちらは「**伝票 1 件 ＝ 1 レコード**の入力用一覧も、標準一覧では足りなければクエリモジュールにする」。
どちらも「一覧の中身が CRUD モジュールの素の姿と違うならクエリモジュール」という同じ判断である。

## 帰結

- **仕訳帳の伝票番号リンクと同じ導線が 2 つになる**（仕訳帳から・振替伝票の一覧から）。
  行き先は同じ `JournalEntry` の詳細なので矛盾しない
- **`JournalEntry` をフレームの `OtherPageModuleDesigns` に登録し忘れると、
  リンクを押した先が静かに真っ白になる**（[qa/01 F-17](../qa/01_CLB静かな失敗.md)）。
  [ADR-0026 §6](0026-画面は役割で分け玄関のページフレームを置く.md) の静的検査がこれを見る<!-- lint-docs:ignore 経緯 -->（現在形は [ADR-0035 §3](0035-フレームは役割と部品の組で分け玄関を1枚置く.md)。2026-09-01 注記）
- クエリモジュールには `DataReadCondition` が効かない（[qa/01 F-23](../qa/01_CLB静かな失敗.md)）。
  絞りは SQL の `WHERE` に書く。いまは行レベルの秘匿が無いので影響しない
- **この一覧は帳簿ではない**（下書きを含む）。法定検索は仕訳帳が担うという
  [ADR-0022](0022-明細を並べる帳簿はクエリモジュールで作る.md) の整理は変わらない
