# ADR-0044 削除はごみ箱送りに一本化し、`rm` を機械で止める

## 状況

**開発者は「`rm` は確認プロンプトで自律作業が止まるので使わないでほしい」と繰り返し伝えてきたが、
Claude はそれでも `rm` を書いてしまう**（開発者の見立て: 学習した情報に `rm` が無数にあるため）。
`rm` は `.claude/settings.json` の `ask` にあったので、書くたびに確認の待ちが入っていた。

かといって**開発者は `rm` を無制限に許可することもしたくない**（逐語）。
完全削除は戻せず、**取り違えたときの損失が「作業が止まる」よりはるかに重い**からである。

つまり問題は「許可するか・禁じるか」の二択に見えて、**どちらも受け入れられない**という形をしていた。

**開発者が指示したこと**（2026-09-07）——素案（`LocalData/trash.ps1`）を確認し、
追跡ファイルとして適切な場所へ置き、**一番使いやすいように自由に改良してよい**。
`CLAUDE.md` に追記し、`settings.json` で `rm` を `ask` ではなく `deny` にし、必要な文書修正を行う。
**条件が 1 つ示された**——「**このリポジトリをクローンした人が Claude Code を使うとき、支障なく動く**こと」。

**同日、実装を見た開発者が続けて決めたこと**——ごみ箱送りは**確認不要**
（「でないと作った意味がない」）。git の破壊コマンドまで拒むのは可
（「**これらをしたいなら声をかけてくれればいい**」）。削除の語彙の拡張は可。
**追跡外の開発用設定を確認なしに編集することが妥当な状況は思い浮かばない。**
**そして「どっちかというと `Write`（上書き）が怖い。`trash` よりずっと怖い」**——
`Write` にも正典を効かせること。
**スクラッチパッド配下の `rm` の扱いだけは「私が承認することでもない」として Claude に委ねられた。**

## 決定

1. **削除は `tools/claude/trash.ps1`（ごみ箱送り）に一本化する。**
2. **ごみ箱送りは、開発者の確認を待たずに実行してよい**（開発者の指示）。
3. **削除にあたるコマンドは、当たり先によらず機械で拒む。**
   **本体は `PreToolUse` フック**（`tools/claude/guard_delete.py`）で、拒むときに代わりのコマンドを示す。
   **`.claude/settings.json` の `deny` は控え**——deny は前方一致の文字列規則でしかなく、
   `find … -delete` のような形を表現できないので、**止められるのはフックの一部だけ**である。
4. **コミットしていない変更を消す git のコマンドも拒む**（`clean`・`reset --hard`・`stash drop`・
   `checkout -- `）。**「Git で戻せないものを守る」と決めた以上、git 自身の破壊コマンドを外す理由が無い**。
   **代償**として `git clean -n` の空打ちや 1 ファイルだけの `git checkout -- ` も止まる。
   **要るときは開発者に声をかける。**
5. **スクラッチパッド配下の `rm` の例外は廃止する**（開発者が判断を委ねた）。
   **例外は `allow` でしか書けず、`allow` は権限判定そのものを飛ばす**（**2026-09-08 追記: この断定は誤りである**——実験したところ、**`deny` はフックの `allow` より強かった**（[リサーチ §4](../research/2026-09-08_使用中SQLiteの複製とフックのallow.md)）。**ただし `deny` に載っていない当たり先は守られない**ので、「`allow` を増やすほど抜け道の隠れる面積が広がる」という決定 5 の理由自体は変わらない。関門を `ask` に載せない判断は[ADR-0046](0046-稼働DBの退避と復元を戻せる道具に閉じる.md) の決定 8）。**
   `allow` を出す形を増やすほど**抜け道が隠れられる面積が広がる**（実際、この回に見つかった
   バイパスはその経路にあった）。**そもそも [30 §8](../30_作業のルール.md) で
   スクラッチパッドは片づけないと決めたので、どちらのコマンドも出番が無い。**
6. **戻すのが現実的でないものは、ごみ箱送りでも拒む。**
   **一覧と載せる基準の正典は `tools/claude/protected_paths.json` の 1 ファイル**で、
   フックと `trash` の両方が読む。
7. **`trash` は自分でも保護判定を持つ。** フックはコマンド文字列しか見られず、シェルを解釈しない。
   **パスを解決したうえでの本当の境界は、実際に消す側にしか置けない**
8. **保護対象への `Write`（全上書き）を拒む**（開発者の指示）。**拒むのはフックだけである**
   （権限規則では書き分けられない。理由は帰結）。
   **上書きは削除より強い**——ごみ箱は前の中身を残すが、上書きは残さない。
   しかも `Write` は中身を照合しないので、**想定と違うファイルでも黙って通る**。
   **判定の起点は、worktree から実行されたときは本体のリポジトリも含む**——
   `trash` が先に塞いだ穴（決定 7）が `Write` 側に残っていた（自己レビューで実証。2026-09-08）
9. **保護対象の名前が出る上書きのコマンドも拒む**（`sed -i`・`Copy-Item`・`> ファイル` など）。
   **`Write` ツールだけ塞いでも、同じことがシェルからできる**
10. **`Edit` は拒まず、確認（`ask`）にとどめる。**
    照合があるので**取り違えでは壊れない**が、**照合を通す字は読めば手に入るので、
    意図すれば空にもできる**（自己レビューで判明）。
    拒まないのは、**追跡外の環境設定を直すのが正当な作業**で、塞ぐと自律作業が止まるからである。
    **新しく作るときは雛形から複製する**（`Edit` は既存にしか当たらず、`Write` は拒まれるため）
11. **両方に自己検査を置き、コミット前フックで流す**（`--selftest` / `-SelfTest`。
    段の並びは [tools/README](../../tools/README.md) が持つ）
12. **残る 2 つの穴は、埋めないまま自律作業へ進む**（開発者の決定。2026-09-08）——
    ①**ごみ箱の容量超過は未確認のまま**、②**白紙の許可は絞らない**。
    **Claude が示した材料と、残る危険は、帰結と「採らなかった案」が持つ。**
    **①は、正典に「ごみ箱に入りきらないほど大きいもの」の行を初めて足すときに確かめ直す**
    ——材料がその 1 行で失効するからである

## 理由

- **約束で守れなかったものは、機械に置く**（[30 §9](../30_作業のルール.md) の「機械の関門（作業）」。
  **作業ミスを止められるのはここだけ**である）
- **「戻せる」ことが、許可と安全を両立させる。** 禁止でも放任でもなく、**失敗の代償を下げる**方向で解いた
- **拒むだけでは同じことが起きる。** 「使うな」と言われても代わりが無ければまた書く。
  だから**フックの理由文に、そのまま実行できるコマンドを書いた**——`rm` を書いた次の一手が `trash` になる
- **正典を 1 つにした理由。** 守る対象の表を Python と PowerShell に書き写すと、
  片方だけ直したときに**守っているつもりで素通り**になる。1 ファイルを両方が読む形にして、
  「正典に載っているのに止まらない」を自己検査が鳴らすようにした

### 採らなかった案

**別名の案は開発者の提案**である（下表の 1 行目）。開発者は判断を Claude に委ね、
上の条件を示した。**却下に異議は出ていない**（2026-09-07）。
**最終行だけは開発者自身の却下である**（2026-09-08）。

| 案 | 採らなかった理由 |
|---|---|
| **`rm` を `trash` の別名にする**（開発者の提案） | **示された条件（クローンした人の環境で動く）を満たせない。** 別名はシェルのプロファイルに置くしかなく、リポジトリに入らない。**この repo はそもそも `pwsh -NoProfile` で呼ぶ規約**（[tools/README](../../tools/README.md) のコマンド例）なので、プロファイルに置いても読まれない。Bash ツールと PowerShell ツールで別々に用意する必要もある |
| **`npm` の `trash-cli` を使う**（開発者が試行） | 開発者の環境で期待どおり動かせなかった（開発者の報告。2026-09-07。**原因は未調査。製品側の問題とは限らない**）。加えて、**この repo には追跡下の `package.json` が 1 つも無い**——依存が 1 つ増えるのではなく、Node の基盤ごと持ち込むことになる |
| **`SHFileOperation` を直接呼ぶ** | エラーダイアログを完全に抑止できる利点はあるが、**構造体の宣言を誤ると静かに完全削除する**（未確認。危険側に倒した）。実測では `Microsoft.VisualBasic.FileIO` でもダイアログは出なかった（下記）ので、**枠組みに載っているほうを採る** |
| **`trash` に復元機能を持たせる** | ごみ箱から戻す動詞（シェルの verb）は**表示言語で名前が変わるとされ**（未確認）、機械で当てにできない。戻すのは人がエクスプローラで行えばよく、**当てにできない復元があるより、無いほうが誤解が無い** |
| **`Edit` も拒む** | **追跡外の環境設定を直す道が無くなる**（デザイナ exe のパスが変わったときの保守は正当な作業である）。照合がある分 `Write` より弱い危険なので、**拒まずに確認にとどめた**（決定 10）。**`Edit` の `deny` は `Write` も同時に塞ぐ**（帰結の「上書きの控えは、拒否ではなく確認である」） |
| **白紙の許可を、リポジトリのスクリプト起動だけに絞る**（`Bash(python:*)` → `Bash(python tools/…)` の形） | **採らない**（開発者の決定。2026-09-08）。**Claude が示した材料**は、**絞れば `python -c` や `sed -i` が許可に当たらなくなって穴は狭まるが、同じ道具を使う正当な作業まで毎回確認が挟まり、自律作業が止まる**ことだった。**すり抜けた削除・上書きが無確認で実行される状態は残る**（帰結） |

**実測したこと**（Claude。2026-09-07。1 回計測）——別のプロセスが `FileShare.None` で開いたファイルを
`Microsoft.VisualBasic.FileIO` に `UIOption.OnlyErrorDialogs` で消させたところ、
**ダイアログは出ず、1.4 秒で例外**になった。**測っていないのは、ごみ箱の容量超過時と権限拒否時**である。

## 帰結

- **削除で作業が止まらなくなる。** 代わりに**ごみ箱に消したものが溜まる**——空にするのは開発者が行う
- **削除でないコマンドが巻き添えで拒まれる。** 判定は引用の中を区別しないので、
  `grep "Remove-Item"` のような**検索や文書編集が、語に触れただけで止まる**
  （この ADR を書いた回だけで 4 回起きた）。**過剰検出側へ倒した代償**であり、
  逃げ方は語の表記を変えて書き直すこと。理由文にその案内を入れてある
- **`trash` は Windows 専用である。** 本リポジトリ自体が Windows 前提
  （[README](../../README.md) の「セットアップ（新環境）」）なので、他の OS 向けの経路は用意していない
- **「戻せる」が崩れる置き場がある。** ネットワーク・リムーバブルにはごみ箱が無いとされるので
  `trash` が拒む（固定ドライブかどうかで代用しており、**同値そのものは未検証**）。
  **ごみ箱の容量を超える巨大なファイルは拒めない**——消してみるまで分からないためである。
  **完全削除になるのかは未確認のままで進める**（開発者の決定。2026-09-08）。
  **Claude が示した材料**は、正典に載る「ごみ箱に入りきらないほど大きいもの」の行が
  決定の時点で 1 つも無かったことである。
  **それでも穴は残る**——`trash` は**正典に載っていない大きなファイル**も素通りでごみ箱へ送るので、
  **「戻せるから確認は要らない」（決定 2）という前提が、大きなファイルでだけ崩れる**
- **上書きは「止めきった」わけではない。** 閉じたのは `Write` ツールと、
  **保護対象の名前がコマンドに出る**形だけである。名前を出さずに上書きする形は通る
- **上書きの控えは、拒否ではなく確認である。** 削除するコマンドは `deny` にも並べてあるが、
  **`Write` は `deny` に書けない**——ファイルの権限判定が参照するのは `Edit(パス)` と `Read(パス)` だけで、
  `Write(パス)`・`NotebookEdit(パス)`・`MultiEdit(パス)`・`Glob(パス)` は
  **受け付けられたうえで一度も参照されず**、起動のたびに警告が出る。
  そして `Edit(パス)` の 1 行は `Write`・`NotebookEdit` にも当たるので、
  **「`Write` は拒み、`Edit` は確認」を権限規則で書き分けることはできない**
  （`Edit` を `deny` にすれば `Write` も塞げるが、それは決定 10 を捨てることになる）。
  したがって**上書きを拒むのはフックだけ**で、フックが起動しなければ `ask` の確認（決定 10 の行）に落ちる。
  **規則は `deny` → `ask` → `allow` の順に評価され、先に当たった 1 つが結論を決める**ので、
  `allow` の裸の `Write` より `ask` の `Edit(パス)` が先に当たる
  （出典: Claude Code 公式ドキュメント「Configure permissions」。2026-09-08 に Claude が確認。
  **起動時の警告が出ること・消えたことは開発者が実機で確認**）。
  **`MultiEdit` はどちらも覆わない**（フックの `matcher` にも無い。いまのセッションには配られていない）
- **フックの限界は残る。** コマンド文字列への正規表現なので、変数に入れてから消す形はすり抜ける。
  **これは「うっかり」を止める装置であって、悪意を止める装置ではない。**
  しかも**すり抜けた先は「開発者への確認」ではなく、そのまま実行である**
  （`Bash(python:*)` のような白紙の許可があるため。**その許可は絞らないと決めた**——採らなかった案）。
  **したがって自律作業でも、すり抜けた削除・上書きを止める人はいない**
- **`lint_secrets.py` の SEC-003 を 1 行だけ免除した**（`trash.ps1` の、
  ごみ箱の無い置き場を拒めているかを確かめる検体。架空のホスト名・共有名）。
  **ファイル単位ではなく行単位で外してある**——`trash.ps1` はネットワーク共有を扱う道具なので、
  ファイルごと外すと本物のホスト名が将来素通りする
