# ADR-0029 所有と依存は「相手抜きで存在するか」で導き、部品の粒度は決断で決める

## 状況

分割の基準が 2 本の ADR に分かれていた。

- [ADR-0024](0024-部品の分割は束ねる相手抜きで使われる場面があるかで決める.md) —
  アプリ部品として分けるのは「**束ねる相手抜きで使われる**場面があるとき」
- [ADR-0019](0019-マスタは会計が生んだ概念かで分ける.md) —
  マスタの所有は「**会計をやめても存在し続けるか**」で決める

開発者が両者の包含関係を指摘した（2026-08-28）——**「A 抜きで B が使われる」なら
「A 抜きで B が存在する」**。つまり 0024 の基準は 0019 の問いの強い形であり、
**同じ原理の 2 つの現れ**である。別々の ADR に置くと、片方だけを直して食い違う。

さらに ADR-0019 は **2 つの論点を 1 本に抱えていた**——「所有をどう決めるか」と
「会計マスタごとの仕様（誰が編集・版・削除）」である。後者は更新され続ける現在形であり、
書き換えない約束の ADR に置いた結果、[ADR-0026](0026-画面は役割で分け玄関のページフレームを置く.md) が<!-- lint-docs:ignore 経緯 -->
権限を決めたときに表と食い違い、[00 §3-3](../00_ドキュメント規約/フロントマター.md) により全体を
`superseded` にするしかなくなった。**仕様書に書くべきものを ADR に書くと、
しょっちゅう編集する必要が生じる**（開発者の指摘。2026-08-28）。

両者を 1 本に併せ、マスタごとの現在形は仕様書 [12_マスタ台帳](../12_マスタ台帳.md) へ出す。

## 決定

### 1. 部品の 2 階層（ADR-0024 §1 を引き継ぐ）

| 用語 | 定義 | 実体 |
|---|---|---|
| **アプリ部品** | 単独でデプロイでき、それだけで業務価値を持つ CLB のデザイン単位 | モジュール群（`*.mod.json`）＋ PageFrame ＋ DB テーブル群 ＋ 付随する C# ライブラリ |
| **コード部品** | .NET プロジェクト単位。アプリ部品の内部で使う | `*.csproj` 1 つ |

1 つのアプリ部品は複数のコード部品を持ってよい。複数のアプリ部品が同じコード部品を共有してもよい。
依存の方向は常に下位から上位のみである（向きの決め方は §2）。

### 2. 所有と依存の向きは「相手抜きで存在するか」で導く。ここは正確に導出する

判定は 1 つの問いで決まる。

> **A をやめても、B は存在し続けるか。**

存在し続けるなら、B は A のものではない。A はそれを**使うだけ**で、定義しない。
取引先・利用者アカウントは会計をやめても存在する（会計の外の実体）。勘定科目・部門・会計期間は消える
（会計の概念。**部門は会計が生んだ集計軸であり、人事組織とは一致させない**——
将来 人事部品ができても統合しない）。

**答えが「そもそも A が決めていない」になるものがある**（ADR-0019 の第三の枝を引き継ぐ）——
消費税率・経過措置の控除割合・耐用年数は**法令が決める値**である。これらは「制度ルール」と呼び、
**その写し（マスタの行）は、使う部品が持つ**（会計の税率は会計部品が持つ。
**所有の割当はここで新しく定めた**——ADR-0019 は分類を立てただけで、所有は書いていなかった）。
ただし値を決めるのは法令なので**利用者は編集できない**（持ち方は [12](../12_マスタ台帳.md)）。

**依存の向きはこの問いから機械的に決まる**（ADR-0024 §4 を引き継ぐ）。

- **単独で成り立つ側が上位、相手が要る側が下位。** 下位が上位に依存し、上位は下位を知らない
  - 取引先は誰も知らない。会計コアは取引先を知ってよい。周辺業務（経費精算・販売・証憑・承認）は
    会計コアと取引先を知ってよい。会計コアは周辺業務を知らない
- 会計コア → 取引先の依存は、本設計の下では**不可避**でもある。仕入税額控除の帳簿記載事項①
  「課税仕入れの相手方の氏名又は名称」（消法 30 ⑧。
  [消費税リサーチ §8](../research/2026-08-23_消費税インボイス制度.md)）の写しを、
  計上時にサーバがマスタから引くと決めている（[ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md)）
- 下位部品は上位部品の**公開された連携点**だけに依存する。会計コアへの仕訳投入は公開 API を通し、
  **会計コアのテーブルを直接 INSERT しない**
- **上位部品のテーブルを下位部品が読むこと（SELECT・JOIN・外部キー）は、同じ DB に同居する限り
  許す。書き込みは所有部品の関門だけを通す**（会計の帳簿が取引先を JOIN で引く、
  仕訳の明細が `partners` へ外部キーを張る、はこの形である）
- 会計コアは、投入元が誰かを知らないまま、**元伝票を特定する情報を保持し続ける**
  （他部品からの追跡と、**優良な電子帳簿の要件**（規則 5 ⑤一ロ。[ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md) で
  準拠すると自ら決めた）——帳簿間の相互関連性ほか——の両方に必要。
  [電帳法リサーチ §3.4](../research/2026-08-23_電子帳簿保存法.md)）

**この導出を間違えると依存が逆流する**（例: 取引先の画面が会計の権限を参照する。
[ADR-0026](0026-画面は役割で分け玄関のページフレームを置く.md) の権限の軸も同じ理由で部品ごとに分ける——現在形は [ADR-0034](0034-役割は部品ごとの直交な軸で持ち軸の中は階段にする.md)。2026-09-01 注記）。<!-- lint-docs:ignore 経緯 -->

### 3. アプリ部品として実際に分けるかは「束ねる相手抜きで使われる場面があるか」で判断する

**§2 の問い（存在の独立）が所有を決め、こちらの問い（利用の独立）が「切り出す価値」を決める。**
使われるなら存在するので、こちらは §2 より強い証拠である（開発者の整理。2026-08-28）。

| 機能 | 会計コア抜きで使われる場面 | 判定 |
|---|---|---|
| 証憑管理 | 電子取引データの保存だけしたい会社が現実にいる（単独利用） | 分ける（本プロジェクトでは作らない） |
| 承認フロー | 経費精算だけに承認を敷く場面がある。そもそも会計の責務ではない | 分ける（本プロジェクトでは作らない） |
| **取引先** | **販売・購買・経費精算のどれもが会計抜きで取引先を使う。複数部品が同じ取引先を共有する** | **分ける**（[ADR-0025](0025-取引先を部品として分ける.md)） |
| 減価償却 | 会計抜きで固定資産台帳だけ使う会社はいない | 分けない（会計コアに含める。コード部品としては分ける） |

「場面」の列は、確認された事実だけでなく**市場の見立てを含む**（判断の材料である）。
「その部品だけを使う利用者がいるか」（旧 ADR-0002）は場面の 1 つ（単独利用）にすぎない。

### 4. どこまで細かく割るかは決断である

§2 の問いを機械的に適用すれば、会計の中もいくらでも割れる——
**貸借対照表抜きで仕訳は存在する**（開発者の例え。2026-08-28）。しかし分けない。
「**まとめてよく使うから、ひとくくりにして会計機能として作ろう**」と**決断した**からである
（開発者の整理。2026-08-28。決断そのものは [ADR-0001](0001-会計コア単体を部品として作る.md) が
当時「会計コア 1 部品のみ」として下している。凝集の判断は
[02_ペルソナ](../02_ペルソナ.md) と [03_機能スコープ](../03_機能スコープ.md) に従う）。

- **上位と下位の関係（§2）は正確に導出する。** ここを決断で曲げてはならない——曲げると依存が逆流する
- **切る位置（§3・本節）は決断である。** 分けることも分けないことも、理由を添えて ADR に残す

### 5. コード部品の分割基準（ADR-0024 §3 から変更なし）

次のいずれかに当てはまるとき分ける。分割コストが低いので積極的に分ける。

- 依存の向きを一方向に固定したい
- 単独でテストしたい（とくに制度依存が重く、境界値テストを大量に書く領域）
- 別のアプリ部品からも使う見込みがある
- 実行場所が違う（純粋計算 / サーバ専用 / クライアント専用）

### 6. マスタの所有も §2 の問いで決める。マスタごとの現在形は 12 が持つ

- **取引先は会計のマスタではない**（会計の外の実体。設計は [07_取引先設計](../07_取引先設計.md)）
- **利用者アカウント・権限は認証部品のもの。** 会計コアは `AppUser` を使うだけで、持たない
  （画面を役割で分けるための旗の扱いは [ADR-0026](0026-画面は役割で分け玄関のページフレームを置く.md)。現在形は [ADR-0034](0034-役割は部品ごとの直交な軸で持ち軸の中は階段にする.md)。2026-09-01 注記）<!-- lint-docs:ignore 経緯 -->
- **部門は会計のもの**（§2 の例のとおり。単一階層は [ADR-0010](0010-部門は単一階層とし損益科目でのみ必須にする.md)）
- **各マスタの仕様（誰が編集する・更新のきっかけ・版と履歴・削除・初期データ）は
  [12_マスタ台帳](../12_マスタ台帳.md) が現在形の正典である。** ADR には置かない
- **三層分類（①制度ルール／②会計設定／③会計マスタ）は分類としては廃止する。**
  「**層に分けることにあまり意味はない。分類の軸を洗い出し、各マスタの仕様を表にするのがよい**」
  （開発者。2026-08-28）。
  「制度ルール」（ベンダーが配布し利用者は編集できない・有効期間つきの版で持つ）という**言葉**は
  引き続き使う。当時の三層の表は ADR-0019 §1 にある

## 理由

- **2 つの基準は同じ原理の現れだった。** 「使われる ⇒ 存在する」の関係に気づいた以上、
  別々の ADR に置き続けると、片方だけが更新されて食い違う
- **導出と決断を分けると、議論が短くなる。** 「上下関係はどちらか」は答えが 1 つに決まる
  （§2 の問い）。「切るか」は割り切りであり、理由を残せばよい（§4）。
  混ぜると「取引先は分けるのに固定資産は分けないのは矛盾では」という不毛な問いが生まれる
- **仕様書に書くべきものを ADR から出す。** ADR-0019 の三層の表は「更新するのは誰か」を含み、
  権限の設計（ADR-0026）が動くたびに古くなった。現在形は仕様書（12）が持ち、
  ADR は「なぜそう決めたか」だけを持つ——
  [05 §1](../05_実装計画と現在地.md) の「実行場所の設計文書」と同じ整理である
- **1 ADR 1 論点。** 複数の論点を抱えた ADR は、片方が覆されたときに丸ごと写し直しになる。
  ADR-0019 がその実例になった（[decisions/README](README.md) に規則として足した）

## 帰結

- [ADR-0019](0019-マスタは会計が生んだ概念かで分ける.md) と
  [ADR-0024](0024-部品の分割は束ねる相手抜きで使われる場面があるかで決める.md) は `superseded`。
  **本 ADR が分割と所有の現在の正典、[12_マスタ台帳](../12_マスタ台帳.md) がマスタごとの仕様の正典**
- 系譜: 部品の基準は ADR-0002 → 0024 → 本 ADR。マスタの分類は ADR-0006 → 0019 → 本 ADR ＋ 12
- ADR-0024 の個別判定を引き継ぐ——固定資産・減価償却はアプリ部品として会計コアに**含め**、
  コード部品としては**分ける**。証憑管理・承認フローはアプリ部品として**分ける**（本プロジェクトでは
  作らない）。会計コアは「仕訳が外部証憑を参照するための識別情報」だけを持つ
- [ADR-0026](0026-画面は役割で分け玄関のページフレームを置く.md) と ADR-0019 §1 の<!-- lint-docs:ignore 経緯 -->
  「誰が編集するか」の食い違いは、**12 が現在形を 1 か所で持つことで解消した**
- 今後の分割判断は §3・§4 で行い、判断が自明でなければ ADR を起こす。
  **新しいマスタを足すときは、まず「会計をやめても存在するか」（§2）を問い、12 に行を足す**
