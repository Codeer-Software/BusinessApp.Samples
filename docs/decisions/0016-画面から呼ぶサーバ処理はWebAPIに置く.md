# ADR-0016 画面から呼ぶサーバ処理は Web API に置く

## 状況

訂正（[ADR-0015](0015-訂正は取消と再計上の組で表し更新履歴方式を採らない.md)）で、
**保存に紐づかないサーバ処理**が初めて必要になった。
「訂正する」ボタンは、押した時点で取消を計上し、再計上の下書きを作って開く。
これは「利用者が保存を押した」という契機を持たないので、
これまでの唯一の関門（`CustomizedModuleDataIO.SubmitAsync`）には乗らない。

[docs/05 §5](../05_実装計画と現在地.md) の未決事項 #4
「CLB スクリプトから呼ぶサーバ処理の置き場（[ADR-0008](0008-CLBとCSharpライブラリの責務分担.md) と
[ADR-0013](0013-機能単位のモジュール分割と依存方向.md) が噛み合っていない）」が、ここで期限を迎えた。

## 選択肢

### A. Web API のコントローラを足し、スクリプトから HTTP で呼ぶ

`BusinessApp.Server` に薄いコントローラを置き、中身は `AccountingCore.Server` に書く。
スクリプトは Extras の `WebApiService.Post(...)` で叩く。

- **長所**
  - **会計の判断が 1 行もスクリプトに乗らない**（ADR-0008 のとおり）。
    スクリプトがするのは「この伝票を訂正して」と頼み、返ってきた下書きを開くことだけ
  - サーバ側は**普通の C# として単体テストできる**。今回も 100 件のテストで固めた
  - **フェーズ 6 の「他部品からの仕訳投入 API」と同じ土台**になる。
    投入 API を作るときに、認証・トランザクション・エラーの返し方を作り直さなくてよい
- **短所**
  - HTTP の層が 1 つ増える（認証・CSRF・エラーの整形）。
    ただし本アプリは既に Cookie 認証と CSRF トークンを持ち、
    `ModuleDataController` ほか 5 本のコントローラが同じ形で動いている。**新しい仕組みではない**

### B. CLB スクリプトだけで完結させる

スクリプトが取消の伝票を組み立てて `Submit()` し、続けて訂正の下書きを組み立てて `Submit()` する。
明細の写しは、保存の関門が「訂正の下書きなら原仕訳の明細を入れる」と決めて行う。

- **長所**: HTTP の層が増えない。新しい入口を守る必要がない
- **短所**
  - **「1 操作」が 2 回の保存になる。** 片方が成功して片方が失敗する状態を、
    スクリプト側で巻き戻せない（トランザクションはサーバの保存 1 回ごとに閉じる）。
    取消だけが計上されて訂正の下書きが無い、という中途半端な結果が残りうる
  - **「下書きを保存したら黙って明細が湧く」という暗黙の挙動**が 1 つ増える。
    静的検査が効かない層に、保存の副作用で状態が変わる規則を足すことになる
  - 順番と組み立てがスクリプトに乗るので、**会計の判断がスクリプトに漏れる**（ADR-0008 に反する）

### C. `ExecuteSqlField` / `QueryField` でサーバ側 SQL を直接叩く

- **短所**: 検証も採番も通らない計上経路が生まれる。[ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md) の
  「規則を迂回する経路を作らない」に正面から反する。**検討に値しない**

## 決定

### A を採る。画面から呼ぶサーバ処理は Web API のコントローラに置く

決め手は**トランザクションの粒度**である。訂正は「取消を計上する」「再計上の下書きを作る」の
2 つで 1 操作であり、**途中で失敗したときに取消だけが残ってはいけない**。
1 回の HTTP 呼び出しの中で 1 つのトランザクションを張れる A だけがこれを満たす。

### 置き場の規則（未決事項 #4 の決着）

| 層 | 置くもの | 例 |
|---|---|---|
| `AccountingCore` | 会計の判断（純粋関数） | `JournalCorrection` |
| `AccountingCore.Server` | DB を触る手順。**機能フォルダに置く**（ADR-0013） | `JournalAmendmentService`（`Journals/`） |
| `BusinessApp.Server/Controllers` | **HTTP の殻だけ。** 認証・トランザクション・エラーの整形 | `JournalsController` |
| `*.mod.cs` | 呼んで、結果で画面を動かすだけ | `WebApiService.Post` → `NavigationService.NavigateTo` |

**コントローラに業務のロジックを書かない。** 書いた瞬間にテストできない場所へ判断が移る。
コントローラの本体は 1〜2 行（サービスを呼ぶ）に保ち、増えたらサービス側へ押し戻す。

### 約束ごと

- **`[Authorize]` と `[AutoValidateAntiforgeryToken]` を必ず付ける。** 既存のコントローラと同じ。
  会計コアの API を認証なしで開けない
- **トランザクションはコントローラが張る。** 例外が出たら丸ごと巻き戻す。
  サービスは張らない（呼び出しを組み合わせる余地を残す）
- **業務の差し戻しは 200、想定外は 500。** 成否は HTTP の状態コードではなく
  **本文の `status`**（`ok` / `rejected`）で表し、差し戻しでは違反コードの配列を添える。
  画面はコードで分岐でき、文言はそのまま出せる。
  それ以外の例外は既存の `UseExceptionHandlerSendToFront` に任せる（500 ＋ 本文にメッセージ）。

  **当初は 400 と決めていたが、実装した日に取り消した**（2026-08-25）。理由は 2 つある。
  ① **CLB の `WebApiService` は 2xx 以外の応答本文を読めない**（[qa/01](../qa/01_CLB静かな失敗.md) K-01）。
  400 で返すと利用者に見えるのは CLB が出す「Invalid Error Code400」だけで、
  差し戻しの理由を伝えるというこの API の目的がまるごと果たせない。
  ② 「取り消せない」「既に訂正されている」は**要求が正しく届いて処理された結果**であって、
  通信や書式の失敗ではない。状態コードで業務の結果を表さないほうが筋が通る。

  **フェーズ 6 の投入 API（他部品が相手）で同じ形にするかは、そのとき決め直す。**
  相手が CLB のスクリプトでないなら 400 のほうが素直である
- **URL は `/api/journals/...`。** 名詞は複数形、操作は動詞（`reverse` / `correct`）

## 帰結

- 未決事項 #4 は解消した。[docs/05 §5](../05_実装計画と現在地.md) から落とす
- フェーズ 6 の「他部品からの仕訳投入 API」は、この形をそのまま広げればよい
- **CLB のスクリプトから HTTP を叩けることに依存する。** これは Extras の
  `WebApiService`（`ExtrasClientInitializer` が登録）が提供しており、
  同じ経路を `Toaster` も使っている。Extras を外すことになったら本 ADR を見直す
