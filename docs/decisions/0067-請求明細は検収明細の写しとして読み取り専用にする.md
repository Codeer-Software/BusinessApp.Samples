# ADR-0067: 請求明細は検収明細の写しとして読み取り専用にする

- 日付: 2026-08-17
- 状態: 採用（実装はバグ狩りの P0 修正で行う）
- 関連: ADR-0049（請求書は検収明細の写し）／ADR-0050（税は明細の税区分ベース）／
  ADR-0062（導出値は読み取り専用にする）／ADR-0008（売上計上は検収基準）／
  ISSUE-0002 §0 原則A（増額は差分文書の追加で表現する）
- 起点: 不変条件 `C10_請求_検収額を超える請求が無い.sql` が「赤で正常」の状態にあり、
  検査として機能していなかった（`docs/qa/03_進捗.md` §4 の要判断項目）

## 背景（問題）

不変条件 C10 は「検収に紐づく請求書の税込請求額が、その検収の税込確定額を超えないこと」を検査する。
しかし `Sales/Invoice.mod.cs` の `UpdateOverAcceptanceWarning()` は**警告するだけでブロックしない**。
つまり現行設計では超過は「あり得る状態」であり、**C10 は赤いまま正常**という矛盾した状態にあった。

赤いまま放置される検査は、やがて誰も見なくなる。どちらかに倒す必要があった。

### 超過が起きると何が壊れるか

売上・売掛金は**検収の確定でしか計上されない**（ADR-0008）。検収額を超えて請求すると、
**超過分は請求書に載るのに帳簿には一切現れない**。結果:

- 総勘定元帳の売掛金 ≠ 売掛残高一覧の残額合計（不変条件 C08 の違反）
- 入金があっても消し込めない残額が永久に残る

### 実務では「検収額を超える請求」はありうるのか

ありうる。ただし**類型ごとに正しい置き場所が違い、「検収に紐づけた請求書を膨らませる」形が
正当になるケースは無い**。

| 類型 | 実務での頻度 | 正しい置き場所 | 検収紐づけ請求書を超過させるべきか |
|---|---|---|---|
| マイルストーン請求（着手金・中間金） | **受託開発で最も一般的** | 検収と無関係の請求。会計上は**前受金**（→ ISSUE-0005） | いいえ（検収がまだ無い） |
| 実費・立替の上乗せ（旅費・機材の pass-through） | SES・準委任でよくある | **検収の明細に含める** | いいえ |
| 追加作業・仕様変更 | 頻繁 | **変更契約として新しい受注・検収を起こす**（ISSUE-0002 S2） | いいえ |
| 消費税・端数の差 | — | そもそも超過ではない（比較の仕方の問題） | いいえ |
| 遅延損害金・違約金 | 稀 | 別請求（営業外収益） | いいえ |

### いま超過を作れてしまう経路

請求書は**下書きのあいだ伝票全体が編集可能**なので、経理が明細金額を手で増やせば超過を作れる
（`qa/02_バグ台帳.md` BUG-0059 の「今も同じ状態を作れる」）。
現 DB の違反 1 件 `INV-26-017` は 2026-08-11 作成＝ADR-0049/0050 修正の前日のデータ残骸だが、
**経路が生きている以上、データを消しても再発する**。

## 選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| 1 | C10 を警告レベルに落とす | **不採用**。壊れた状態（帳簿に現れない売掛）を検知しなくなる。C08 の破れも道連れになる |
| 2 | 保存時にブロックする（超過ならエラーで止める） | **不採用**。ISSUE-0002 S6（締め済み期間の訂正）で詰む——検収を後から減額修正すると既存の請求書が超過状態になり、編集をブロックされると直せない。ADR-0062 の「止めるのは不可逆か一括のときだけ」にも反する |
| 3 | **請求明細の金額を編集させない**（検収由来なら読み取り専用） | **採用** |
| 4 | 実装は今のまま（警告のみ）、違反データだけ片付ける | 不採用。BUG-0059 の経路が生きているので再発する |

## 決定

### 決定 1: 検収に紐づく請求書の明細金額は読み取り専用にする

ADR-0049 は「**請求書は検収明細の写し**」と定めた。写しなら、それは**導出値**である。
ADR-0062 は「**導出値は読み取り専用にする**」と定めている。この 2 つを素直につなぐ:

> **`acceptance_id` を持つ請求書の明細金額（および税額に効く項目）は、画面で編集させない。**

- 分割して請求したい → **検収を分ける**（ISSUE-0002 S4 の分割検収。既に手順がある）
- 増額したい → **変更契約として新しい受注・検収を起こす**（ISSUE-0002 S2 / 原則A）
- 減額したい → **検収額を修正する**（ISSUE-0002 S3。検収額が売上計上額）

**警告もブロックも要らなくなる**——超過を作る入口が無くなるため。
`UpdateOverAcceptanceWarning()` は当面残してよい（既存データや将来の抜け道に対する保険）。

### 決定 2: C10 は error のまま残す

警告レベルには落とさない。決定 1 により**構造的に緑を維持できる**ようになるので、
赤が出たら「本当に何かが壊れている」を意味する検査になる。

### 決定 3: 検収に紐づかない請求書（手動の合算請求書）は対象外

`acceptance_id` が NULL の請求書は C10 の検査対象外であり（SQL が `JOIN acceptances` のため）、
明細金額の読み取り専用化の対象にもしない。**ただしこの経路には別の穴がある**——
手動請求書は仕訳を一切作らないため、売掛金が帳簿に載らない。着手金の受け皿として使うと
C08 が壊れる。→ **ISSUE-0005** で別途扱う。

## 影響

- **実装**: `Sales/Invoice`（＋ `Sales/InvoiceLine`）で、`AcceptanceRef` があるときに明細の
  金額・数量・単価・税区分を読み取り専用にする。定期請求・SES の自動生成分は既に発行後ロック済み。
  **バグ狩りの P0 修正の 1 件として実施する**（`docs/qa/01_作業指示書.md` の手順・回帰 6 点セットに従う）
- **データ**: 現 DB の違反 1 件 `INV-26-017` は旧バグの残骸。実装後に片付けて C10 を緑にする
- **不変条件**: C10 のコメントに本 ADR を出典として追記する
- **仕様書**: `docs/08_請求入金設計.md` に現行仕様（What）として反映する
- **体験シナリオ**: `tests/20_体験シナリオ/02_営業_受託/03_明細で分ける分割検収.md` が
  「請求額の行単位赤字警告」を扱っている。実装後は**警告が出せなくなる**ので台本の①層を直す
  （`lint_docs.py --impact` で影響範囲を確認すること）
- **ユーザーへの影響**: 「請求書で金額を微調整する」運用ができなくなる。値引きは検収額の修正、
  増額は変更契約——どちらも既存の運用規約どおりなので、**新しい制約ではなく既存規約の強制**である

## 備考

- 本 ADR は「超過をどう扱うか」の問いに対し、**警告するかブロックするかの二択ではなく
  「そもそも入力させない」**という第3の道を採った。ADR-0062 で確立した
  「導出値は読み取り専用」の規約が、そのまま答えになっている
- 判断の材料は `docs/qa/03_進捗.md` §4（要判断）とユーザーとの議論（2026-08-17）
