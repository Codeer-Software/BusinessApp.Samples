# ADR-0034 役割は部品ごとの直交な軸で持ち、軸の中は階段にする

## 状況

[ADR-0026](0026-画面は役割で分け玄関のページフレームを置く.md) は役割・画面・権限を 1 本で決めていたが、
[ADR-0033](0033-読み取りはそのアプリの役割を持つ人だけに開く.md) が §3 の「読み取りは原則として絞らない」を
覆したため、[00 §3-3](../00_ドキュメント規約/フロントマター.md)（一部だけを覆すときも元 ADR は全体を
`superseded` にする）により全体が `superseded` になった。

**生きている決定は、分けて引き継ぐ**（開発者の決定。2026-09-01。
**「文書を綺麗に保つことはメリットがたくさんあると思っています。
今後楽をするためにも、今分けておきたいです」**——逐語）。
分け方は Claude の判断で、節の数（6）ではなく**問いの数で切った**——
①役割をどう表すか（本 ADR）②画面をどう構えるか（[ADR-0035](0035-フレームは役割と部品の組で分け玄関を1枚置く.md)）
③権限をどこに書くか（[ADR-0036](0036-権限は到達と書き込みに書き分け守りは保存の関門に置く.md)）
④読み取りを誰に開くか（[ADR-0033](0033-読み取りはそのアプリの役割を持つ人だけに開く.md)）。

本 ADR が引き継ぐのは **0026 §1（追記で確定した現在形）**である。
決定に至る往復と棄却案（Boolean 3 フラグ案・`role` 単一列・組織からの導出）は 0026 に凍結されている。

## 決定

**開発者が決めた骨格**（2026-08-28。0026 §1 の追記に記録された回答の写し。**鉤括弧内のみ逐語**で、構成と太字は Claude のもの）:

> ① 権限の軸は**機能（部品）ごと**に分け、軸どうしは**直交**——「システム管理」と「経理」の権限は独立で、
> `IsSysAdmin` を業務側の条件に混ぜない
> ② **軸の中は階層**——経理は 経理責任者 ⊃ 経理担当 ⊃ 帳簿閲覧（帳簿閲覧の利用はフェーズ 4）。
> 上位は下位の画面も閲覧・編集できる。**「責任者は担当を含む」をデータではなく規則として持つ**
> （責任者に担当のフラグも立てる方式はやめる）
> ③ **取引先は独立の権限の軸**（編集 ⊃ 閲覧 ⊃ なし）。理由も開発者自身のもの——
> 「経理権限で取引先を触れるようにすると、取引先の情報を取得・編集するときに**利用者の会計権限を
> 確認する必要が生じる。これは依存方向が逆**」。
> 経理（責任者・担当）は編集、経営（フェーズ 4）は閲覧、システム管理者は「なし」

（`IsSysAdmin` は当時検討していた Boolean フラグ案の名で、確定した列は `is_sysadmin`——下の実装形。
追記④「列の持ち方の確定」も実装形で決着済み。原文は 0026 §1 の追記にある）

実装形（開発者が 2026-08-28 に承認）:

- **列は `app_users` に 3 本**——`is_sysadmin`（bool）・
  `accounting_role`（NULL＝なし / `viewer` / `staff` / `manager`）・
  `partner_role`（NULL＝なし / `viewer` / `editor`）。TEXT ＋ CHECK。
  **既定は「何もできない」**（bool は偽、役割は NULL）
- **1 機能 1 列**——「役割は 1 つ」がデータの形と一致し、
  無意味な組み合わせ（責任者かつ担当）が構造的に作れない
- **条件は OR-of-Equal**（担当の画面は `staff` または `manager`）。`>=` 比較は CLB で未確認なので使わない
- **まだ使わない値も CHECK には今から入れる**（`viewer`。SQLite の CHECK 変更はテーブル作り直しになるため）
- **列の定義（値・意味・CHECK・マイグレーション）は各部品が所有し、`app_users` に間借りする**
  （物理の同居と論理の所有は別——[ADR-0025 §5](0025-取引先を部品として分ける.md) と同じ判断）。
  役割を足すときは**その部品がマイグレーションを出す**（認証部品のコードは触らない）

## 理由

- **直交にする理由は依存の向きである**（上の開発者③）。軸を混ぜると、部品を取り出すときに
  他部品の権限を知らないと動けなくなる。向きの規則は [ADR-0029 §2](0029-所有は相手抜きで存在するかで導き粒度は決断で決める.md)
  （この参照は設計側が添えたもの——0026 §1）
- **`role` 単一列は前回プロジェクトが作って捨てた**——あれは**直交な機能を 1 列に詰めた**失敗であり、
  **1 機能内の全順序を 1 列で持つ**のは別物である
- **組織（部門の所属）から権限を導出しない**——前回プロジェクトは導出のせいで
  「営業機能を使わせるために**虚偽の組織行**を登録する」状態を作り、翌月に直接付与へ戻している

## 帰結

- **OR の書き忘れ**（責任者が担当の画面に入れない）は `lint_design.py` の検査が見る
  （「使われている値より上位が欠けていないか」。実装済み——フェーズ 2.5 の D）
- **読み取りにもこの軸を使う。** 既定と例外の立て方は [ADR-0033](0033-読み取りはそのアプリの役割を持つ人だけに開く.md)
- **`admin` は `is_sysadmin` だけ真にする**（開発者の決定。2026-08-28）。会計は触れない。
  軸が直交であることの帰結として説明できる（Claude の注記）。
  デモ用の経理・取引先の役割は [ADR-0039 §5](0039-開発用アカウントの資格情報はGit追跡外に置く.md) の seed が付与する
- 閲覧のみの役割（経営・顧問税理士）を実際に使うのはフェーズ 4（[05](../05_実装計画と現在地.md)）
- **どのマスタを誰が編集するかの現在形は [12_マスタ台帳](../12_マスタ台帳.md) が 1 か所で持つ**（ここに写さない）
