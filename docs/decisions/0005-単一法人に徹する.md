# ADR-0005 単一法人に徹する

## 状況

開発者が 2026-08-20 に用意した検討メモ（品質保証の整理。リポジトリ外）のドメインモデルは `Tenant / LegalEntity` を中核に置いている。
一方、対象ペルソナは単一法人・単一拠点である（[ADR-0003](0003-対象ペルソナ.md)）。

「将来の複数法人化に備えて、全テーブルに `legal_entity_id` 列を持たせ、値は常に 1 に固定しておく」
という**器だけ作る**選択肢がある。これを採るかを決める必要がある。

## 決定

**器は作らない。会計コアは単一法人・単一会計単位に徹する。**
全テーブルに `legal_entity_id` を持たせることはしない。

ただし、**「自社（会計単位）」という概念の置き場所だけは 1 レコードのテーブルとして持つ**。
`company_settings`（設定値の入れ物）ではなく `legal_entities`（1 行・`id = 1`）とする。

> **2026-08-26 追記**: 実装したテーブル名は **`company_profile`** である（`Designer/ddl/001_organization.sql`。
> `CHECK (id = 1)` で 1 行を担保）。判断は変わっていない——名前だけが実装時に変わった。

複数法人を扱う必要が生じた場合は、**アプリのインスタンス（DB）を法人ごとに分ける**ことで対応する。

## 理由

### 器を作らない理由

- **「使わない機能は含めない」という本プロジェクトの原則に真っ向から反する。**
  全テーブルに使われない列が付き、全クエリに実質無意味な条件が付き、
  CLB のモジュール定義・テストデータ・designcheck のすべてに重みが乗る
- **節約になる量が小さい。** 複数法人化するときに変わるのは列だけではない。
  勘定科目体系の共有／法人別、会計期間の独立、締めの単位、権限、
  法人間取引の消去——**設計そのものが変わる**。列だけ用意してあっても大した助けにならない
- **後から追加が構造的に不可能なものではない。** 列追加とバックフィルは大変だが可能である。
  YAGNI の例外にしてよいのは「後から追加できないもの」に限る。本プロジェクトでそれに当たるのは
  仕訳の不変性（[ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md)）であり、そこは実際に例外扱いしている
- **DB を分ける方式のほうがテナント分離として強い。** 会計データの越境は最悪の事故であり、
  アプリ内で `WHERE legal_entity_id = ?` を全経路に徹底するより、
  そもそも同じ DB に他社データが無いほうが安全である

### 「自社」を 1 行のテーブルにする理由

- 法人名・住所・適格請求書発行事業者の登録番号（T 番号）・決算期・消費税の課税方式は、
  **どのみち必要**である。置き場所は要る
- 設定値の Key-Value ではなく**型のある 1 行のテーブル**にすると、CLB のモジュールとして
  素直に扱え（1 レコードの詳細画面）、列に型と制約が付く
- 将来複数法人化するときは「1 行 → N 行」になるだけで、概念の置き場所を新設せずに済む。
  子テーブルへの FK 追加は必要だが、それは器を作っていても同じ作業である。**列は増えないのに
  概念だけ用意できる**ので、コストがほぼゼロで済む

## 帰結

- 会計コアのテーブルに `legal_entity_id` / `tenant_id` は付けない
- `legal_entities` は 1 行しか持たない前提で設計する（UI は「事業所情報」の詳細画面 1 枚）
- 複数法人の要求が出たら、その時点で改めて ADR を起こす。既定の答えは
  「インスタンス（DB）を分ける」であり、それで足りない要件（法人間取引の消去・連結）が
  出て初めてデータモデルの変更を検討する
