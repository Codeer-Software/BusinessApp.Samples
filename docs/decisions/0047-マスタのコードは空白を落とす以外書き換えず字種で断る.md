# ADR-0047 マスタのコードは、空白を落とす以外は書き換えず、字種で断る

## 状況

**`1100` と `1100 `（末尾に半角空白）が、別の勘定科目として保存できた**
（[qa/03 L-32](../qa/03_テストで漏らした実例.md)。2026-09-04 の探索的テストで実測）。
`UNIQUE` はバイト列の一致しか見ないので、**画面で見分けの付かない 2 行が並ぶ。**

コードを持つのは **6 つの表**である——`fiscal_years` / `tax_categories` / `accounts` /
`sub_accounts` / `departments` / `partners`。どの表にも**書式の決まりが無い**
（DDL は `TEXT NOT NULL` と `UNIQUE` だけ）。

**市販ソフトを先に調べたが、答えは出なかった**
（[マスタのコード体系のリサーチ](../research/2026-09-08_市販会計ソフト比較_マスタのコード体系.md)。
半角と明記していたのは 2 社、全角を弾くと書いた社は 0 社、**入力時に正規化するかを書いた資料は 1 本も無い**）。
**だから自分たちで決めるしかない**（[04 §5](../04_実装計画と現在地.md) が「B-2 の実装の回」を期限にしていた未決事項）。

取りうる形は 3 つあった。

| | どうするか | 代償 |
|---|---|---|
| (a) | **寄せて正規化する**（全角英数を半角へ・英字を大文字へ・空白を落とす） | 利用者が打った字が黙って変わる。写像の関数を持つことになる |
| (b) | **前後の空白だけ落とし、残りは字種で断る** | 全角で打った利用者は打ち直しになる |
| (c) | 何も見ない（現状） | 見分けの付かない行が並ぶ。**L-32 がそれである** |

**この論点は 2026-09-08 より前の別セッションでも話し合われていた**が、
**リポジトリにも git log にも記録が残っていなかった**（開発者の記憶にはあった）。
本 ADR は決定そのものと同じくらい、**決定を残すこと**を目的にしている（[30 §9](../30_作業のルール.md)）。

## 決定

**(b) を採る。** 以下 1〜9 は**開発者が承認した**（2026-09-08。逐語は理由の節に引く）。

1. **字種は、半角英数字・ハイフン（`-`）・アンダーバー（`_`）に限る。**
   他の記号・空白・全角・かな漢字は**断る**
2. **先頭と末尾に記号を置けない。** 記号は英数字に挟まれた位置にだけ置ける
3. **記号を連続させられない**（`10--01` は断る）
4. **長さは 1〜20 文字**
5. **前後の空白は黙って落とす**（半角・全角・タブ・改行——Unicode の空白すべて）。
   **落として空になったら「必須」で断る**
6. **全角英数は、半角へ寄せずに断る**（開発者の指示。2026-09-08）。
   **正規化と呼べる書き換えは 5 の空白だけ**である
7. **保存するのは入力されたままの字**（大小を潰さない）。
   **同一性の判定だけ英字の大小を無視する**——`A100` があるとき `a100` は登録できない
8. **記号を落として突き合わせない。** `10-01` と `1001` は別のコードである
9. **取引先のコードも、使用中は変えられない**（他の 4 マスタと揃える。[ADR-0038](0038-使用中のマスタは意味を変えられない.md)）

**以下 10〜12 は Claude の決めで、開発者は述べていない。**

10. **検査の順は、トリム → 空（必須）→ 字種 → 先頭末尾の記号 → 記号の連続 → 長さ → 重複**。
    **1 つの欄については、最初に当たった 1 つだけを返す**（開発者の「即エラー。次へ進まない」に従う）。
    **別の欄の違反は、これまでどおり同時に返す**
11. **見えない字（ゼロ幅空白・BOM・制御文字）は、字種違反として断る。**
    ただし文言で**位置を言う**（「n 文字目に、目に見えない文字が入っています」）——
    見えない字に「使えない文字があります」とだけ返すと、利用者は直しようがない
12. **同じ規則を 6 つの表すべてに当てる。**
    会計年度（`fiscal_years`）は作成の画面がまだ無い（フェーズ 4）が、
    **規則は先に置く**——[20 §5](../20_実装の原則.md) の「使われないコードを残さない」に当たらない。
    置くのは**分岐ではなく制約**であり、DDL の `CHECK` は最初の 1 行から毎回働く

## 理由

**字種と形**（決定 1〜4）。**開発者の逐語**（2026-09-08）——

> 字種として、原則として記号は禁止ですが、ハイフンとアンダーバーは許可したいです。
> スペースの代わりに区切りたいことはしばしばあると思います。
> ただし、文字列の先頭でのハイフンとアンダーバーは禁止です。

**末尾と連続の禁止は Claude が足し、開発者が承認した**（逐語「末尾のハイフンとアンダーバー禁止、
記号の連続禁止、長さは1文字以上20文字以下。全てOKです」）。**理由は先頭を禁じたのと同じ**である——
`1100-` と `1100`、`10--01` と `10-01` は**画面で見分けが付かない**。
L-32 が末尾の空白で起きたのと同じ型の事故が、記号でも起こる。

**20 という数に制度的な根拠は無い**（Claude の見立て。一覧の列幅と CSV の実務）。
勘定科目は 4 桁・部門は 2 桁で運用しており、市販ソフトの上限は 3〜20 文字に散らばっている
（[リサーチ §1](../research/2026-09-08_市販会計ソフト比較_マスタのコード体系.md)）。

**寄せずに断る**（決定 6）。**開発者の指示。2026-09-08。逐語**——

> よくよく考えると、そもそも半角英数字しか入力を認めないのだから、
> 全角英数が入っていたら寄せるんじゃなくてエラーでいいと思いました。

**この形は [21 §0](../21_画面の原則.md) が既に引いていた境目と一致する。**
同節は「前後の空白を落とすような**利用者の意図でない混入の除去**は黙って直してよい。
**境目は『利用者が入れたつもりのものを変えるか』**」と定めている。
**全角で打った `１１００` は、利用者に見えていて、打ったつもりで打った字**である。
だから黙って書き換える側ではなく、同節の「**拒めるなら拒む**」側に入る。

**しかも、この製品には同じ骨格の先例が 2 つある。**
`InvoiceRegistrationNumber.Normalize` と `CorporateNumber.Normalize` は、
どちらも `Trim()` **だけ**で、全角数字は `ContainsAnyExceptInRange` が弾く。
**寄せる形を採ると、識別子 3 種のうちコードだけが別の骨格になっていた。**

**大小**（決定 7）。**開発者の逐語**（2026-09-08）——

> 英字の大小…保存は入力のまま。同一性チェックは大小無視。OKです。理由もよく分かりました。
> 「a100」でも「A100」でも登録できる。しかし、「A100」を既に作ってあったなら、「a100」はもう登録できない。

**大小を潰して保存しない理由**は決定 6 と同じで、**画面に出る字が変わるから**である。
**大小を区別したまま重複を許さない理由は、SQLite の中で規則が割れるから**である——
`UNIQUE` は既定でバイト列を見る（大小を区別する）が、**`LIKE` は ASCII 英字の大小を区別しない**。
帳簿の法定検索は `LIKE` を使うので、区別する形を採ると
**「`A100` と `a100` の両方を作れるのに、コードで検索すると両方ヒットする」**という食い違いが生まれる。
**字種を半角英数に絞ったので、`COLLATE NOCASE` が ASCII しか畳まない制限とちょうど噛み合う。**

**記号を落として突き合わせない**（決定 8）。**落とすと、利用者が意図して入れた区切りが消えて、
無関係なコードと衝突する**（`10-01` と `1001` が同じものになる）。
**区切りとして許した以上、区切りは意味を持つ。**

**取引先のコードを凍結する**（決定 9）。**開発者の逐語は「取引先コードも凍結しましょう」**である。
**Claude が指摘したのは非対称のほう**——`MasterMeaningGate.Guarded` は
勘定科目・補助科目・部門・税区分の 4 マスタで `code` を凍結しているのに、
**取引先だけが抜けていた**（意図か漏れかは記録から判別できなかった）。
**帳簿には取引先の名称と登録番号を焼き込んでいる**（[ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md)）ので、
コードを変えても過去の記載は動かない。**それでも揃えるのは、
「科目コードは変えられないのに取引先コードは変えられる」理由を利用者に説明できないから**である。

## 帰結

- **現在形の正典は [12_マスタ台帳](../12_マスタ台帳.md) の表**である。**本 ADR に写さない**
  （[ADR の書き方](README.md)——更新され続ける現在形は仕様書に置く）
- **重複定義になるので、機械で突き合わせる**（[20 §4](../20_実装の原則.md)）。
  字種と長さは **C# の関門・DDL の `CHECK`・CLB の `MaxLength`** の 3 か所に要る。
  **20 §4 の表の「桁の書式」の行は、いま「守れていない」と書いてある**——
  この回で `EnumConsistencyTests` と同じ形のテストを足し、その行を閉じる
- **DDL でも全部表せる。** 字種は `code NOT GLOB '*[^0-9A-Za-z_-]*'`、先頭と末尾は
  `code GLOB '[0-9A-Za-z]*'` と `code GLOB '*[0-9A-Za-z]'`、連続は `code NOT GLOB '*[-_][-_]*'`、
  長さは `length(code) BETWEEN 1 AND 20`。**関門が本体・DDL が最後の守り**という
  [ADR-0038 §4](0038-使用中のマスタは意味を変えられない.md) の二重防御をそのまま踏襲する

  > **2026-09-09 追記**: **実装は `CHECK` ではなくトリガで置いた**（`Designer/ddl/008_master_code_format.sql`）。
  > **判断は変わっていない**——DDL で表せることも、二重防御にすることも上のとおりである。
  > 変わったのは機構だけで、理由は 2 つ。**① `CHECK` を後から足すには表を作り直すしかない**
  > （`accounts` は `journal_lines` から参照され、既にトリガも持っているので、作り直しは危険に見合わない）。
  > **② トリガなら断りの文言を返せる**——`RAISE(ABORT, ...)` に語を置ける。
  > **ただし、その文言がアプリの利用者に届くわけではない**（**2026-09-09 の自己レビューで確かめた訂正**）——
  > `SaveFailureMessage.ToUserLanguage` が DB から上がった文言を**中身を見ずに**定型文へ差し替えるので、
  > **届くのは `sql` CLI と取込で流す人にだけ**である。**それでも文言を置く価値はそこにある**
  > （関門を迂回する経路こそ、このトリガが守る相手だからである）。
  > 条件そのものは上の `GLOB` をそのまま `WHEN` 節に置いてある。
  > **大小を無視した重複は `UNIQUE ... COLLATE NOCASE` の索引**で止める（列の `UNIQUE` は残した）。
- **取引先の関門は、部品をまたぐ**（**Claude の判断。開発者は未承認**）。
  「使用中」は**計上済みの仕訳明細が参照しているか**という会計の事実だが、
  依存は会計コア → 取引先の一方通行である（[ADR-0025 §4](0025-取引先を部品として分ける.md)）。
  **取引先部品から会計コアを名指しできない**ので、**取引先側が問い合わせ口（インタフェース）を定義し、
  会計コア側の実装をホストが差し込む**形にする。**実装の回に確かめる**

  > **2026-09-09 追記**: **実装は問い合わせ口ではなく、会計コア側の関門（`MasterMeaningGate`）が
  > 取引先の行も見る形にした。** 「使用中」は会計の事実なので、判定ごと会計コアに置くほうが素直である
  > （取引先だけを載せたホストには仕訳が無いので、凍結する対象も無い）。
  > **代償は、取引先だけのホストでこの関門が 1 つ足りなくなること**で、
  > `SaveFailureMessage` と同じ形の「持ち出し忘れ」になる（[ADR-0025 §6](0025-取引先を部品として分ける.md)）。
  > **`PartnerSubmitPipeline` の「足りなくなるもの」の段落に書き足した**ので、そのときに気づける。
  > **数える単位も違う**——取引先は伝票にも明細にも入るので、**振替伝票の枚数**で数える
  > （明細だけを数えると、伝票にだけ取引先を入れた計上済みの伝票を取りこぼす）。
- **CSV 取込（フェーズ 6）でも、全角のコードは寄せずに落ちる**（行単位エラー）。
  他社ソフトから出した CSV に全角が混じっていると取り込めない。
  **これは意識して払う代金である**——黙って寄せて、元帳のコードが取込前と変わっているほうが重い。
  **取込を作る回にこの決定を蒸し返さない**
- **既存データの始末は 2 行だけ**（2026-09-08 に稼働 DB を実測）。
  `accounts` に `1100 `（末尾に空白）が 1 行、`partners.name_kana` に空文字が 1 件。
  **`1100 ` は `TRIM` できない**——seed の現金（`1100`）と `UNIQUE` で衝突する。
  探索的テストで手作りした検証用の行で、**計上済みの明細からの参照は 0 行・ぶら下がる補助科目も 0 件**なので、
  **行ごと消す**（開発者の逐語「1100の空白は消したほうがいいですね」。始末はマイグレーション。
  **DB を作り直さない**——[ADR-0020](0020-スキーマは現在形の正典で持ち変更は差分で配る.md) の
  「差分で配る」経路は製品そのものであり、開発機で作り直して済ませる癖が付くと、
  本番でしか起きない移行の失敗を出荷まで一度も踏まないことになる）
- **`COLLATE NOCASE` を後から付けても、既存行は 1 つも弾かれない**
  （大小を無視した重複は 2026-09-08 の実測で 0 件）
- **覆るとき**（寄せる形に決め直すとき）**に動くのは、関門と DDL の `CHECK` と、
  既に保存されたコードである。** 寄せる規則は**過去のデータを書き換えないと一貫しない**——
  そのとき使用中のマスタのコードを書き換えることになり、
  [ADR-0038](0038-使用中のマスタは意味を変えられない.md) の凍結と正面からぶつかる。
  **だから覆すなら早いほうがよい**（行が少ないうちに）
