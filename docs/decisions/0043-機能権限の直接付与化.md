# ADR-0043: 機能権限の直接付与化 — 3軸分離（機能権限／組織所属／承認構造）

- 日付: 2026-08-05
- 状態: 採用（本 ADR 起票と同セッションで実装）
- 関係: ADR-0041 の §2「見え方はメンバーシップから導出」を **supersede**（§1 の部門メンバーマスタ・§3 の職務分掌・§4 は存続）。ADR-0044（部課階層）・ADR-0045（ポータル本格化）と同時決定
- 起点: ユーザーレビュー 2026-08-05「ユーザーごとに機能の権限有無そのものを指定していない。営業部の部門メンバーにすることで営業機能が使えるのは間接的すぎる」

## 背景

ADR-0041 は旧 Role 単一列を廃止した正しい改革だったが、**機能の見え方（フレームゲート）まで組織所属から導出した**ことで新たな歪みを生んだ:

1. **権限を変えたいのに組織の事実を偽る必要がある。** 開発1部の課長に営業機能を使わせるには「営業部のメンバー」という虚偽の組織行を登録するしかない（シードに実例あり: `kaihatsu1_kacho1` が営業アクセスのためだけに営業部 member 行を持つ）。以後、営業部のメンバー一覧は「営業部で働く人」に答えられない
2. **因果が3段間接**（メンバー行→部門種別→トリガー→キャッシュ列）で、管理者が「なぜこの人に経理画面が見えるのか」を画面から遡れない。ユーザー管理画面の 営業/経理/承認者 列が編集不能なのもこの帰結
3. **`dept_type` は権限概念の密輸品。** 参照者は転記トリガーのみで、組織マスタに権限設定が紛れている
4. 経費精算・工数管理は「全社員機能」としてゲート無しだが、実務では外したいユーザーがいる
   （SES 協力会社要員=工数のみ／顧問税理士=経理閲覧のみ／退職前アカウント 等）。特別扱いが並列でない

## 決定

**「誰が何の画面を使えるか」「誰がどこに所属するか」「誰が誰の稟議を決裁するか」は別の関心なので、別の構造に持たせる。**

| 軸 | 構造 | 内容 |
|---|---|---|
| 1. 機能権限 | `app_users` の直接フラグ（真実・チェックボックスで編集） | 下表の5本 |
| 2. 組織所属 | `departments` + `department_members` | 純粋な組織の真実（ADR-0044 で部課階層化） |
| 3. 承認構造 | `department_members` の課長/部長行 + 承認テンプレ/ルートマスタ | ADR-0016/0023 を継承（ADR-0044 で walk-up 化） |

### 1. 機能権限フラグ（軸1）

| 列 | 意味 | 既定 | 由来 |
|---|---|---|---|
| `has_sales_access` | 営業機能 | OFF | 既存キャッシュ列を**列名そのまま真実に昇格** |
| `has_accounting_access` | 経理機能 | OFF | 同上 |
| `can_use_expense` | 経費精算 | **ON** | 新設（全社員機能のオプトアウト型） |
| `can_use_timesheet` | 工数入力 | **ON** | 新設（同上） |
| `is_sysadmin` | システム管理 | OFF | 既存のまま（データとしては並列。UI では「業務機能」と「システム管理」をグループ分け表示） |

- **移行初日の各ユーザーの権限値は現キャッシュ値をそのまま引き継ぐ**（誰の見え方も変わらない）
- 列名・フィールド名を変えないため、**フレームゲート 96 条件・82 モジュール・スクリプト14ファイルは無修正**
- sales/accounting の転記トリガーは削除。`dept_type` 列は廃止（唯一の消費者が消えるため）
- 部門メンバー行の追加/削除は今後、機能の見え方に**一切影響しない**

### 2. `is_approver` だけはキャッシュのまま（導出継続）

「承認者フレームが見えるか」は付与するものではなく**決裁権を持つことの帰結**。直接フラグにすると
「承認者チェック ON だが決裁権がどこにもない」孤児状態を作れてしまう。導出条件はこの機会に拡張:

```
is_approver = どこかの部門に課長/部長行がある
           ∨ 承認テンプレートの個人指名承認者である（ADR-0041 既知課題の解消）
```

`approval_flow_template_member` への INSERT/UPDATE/DELETE トリガーを追加し、個人指名承認者にも
承認者フレームが見えるようにする。

### 3. フレームゲートの変更

| フレーム | 旧ゲート | 新ゲート |
|---|---|---|
| ExpenseStaff | なし（全員） | `CanUseExpense` |
| Timesheet | なし（全員） | `CanUseTimesheet` |
| 他 12 フレーム | 変更なし（列名不変のため条件式も不変） | — |

admin シードは `can_use_expense=0` / `can_use_timesheet=0` とし、PortalHome 等にあった
「isAdmin なら経費/工数ボタンを隠す」**ハードコード特例を全廃**する（全てフラグで説明できる状態へ）。
職務分掌（sysadmin は業務画面に入らない）の思想と 2 アカウント運用の推奨は ADR-0041 §3 のまま。

### 4. ユーザー管理画面（UX 同時是正）

- 詳細（新規/編集）に権限チェック群を配置: 「業務機能」グループ（営業・経理・経費精算・工数入力）と
  「システム管理」（システム管理者）。承認者は**読み取り専用表示**＋「部門の課長/部長・承認テンプレートの
  指名から自動判定（部門管理で編集）」の注記
- 一覧ヘッダー文を更新（「削除はできません。退職者は有効チェックを外して無効化します」を明記）
- 自分自身の sysadmin 解除禁止ガード（ロックアウト防止）は存続

## 検討して退けた代替案

- **権限テーブル（user_id×権限キー）+ キャッシュ転記**: 「権限追加時にテーブル変更不要」が狙いだが、
  CLB のゲートは CurrentUser（AppUser）の列しか参照できない（FB-034）ためキャッシュ列追加は結局必要で、
  スキーマ変更は消えない。得るもの（付与履歴）に対し管理画面・トリガー・シードの複雑化が見合わない。
  フラグが増殖して権限マトリクスの様相を呈したら（目安 5〜6 本超）その時に移行 ADR を起こす（列→行転記は機械的）
- **疑似部門（「営業機能利用者」グループ）**: 部門別損益・承認ルートを汚染する。組織マスタに権限概念を残す点で本末転倒
- **RBAC（ロール×権限マトリクス）**: 30〜80名・権限5本の規模では層が1枚増えるだけ。ADR-0041 が
  ロールを廃止した理由がそのまま当てはまる

- docs/10 §2「権限モデル」・§6 カスタムポイント（「誰にどの業務を見せるか」→ ユーザー管理のチェックボックスへ）を改訂
- docs/tests/19 に読み替えを追記（`kaihatsu1_kacho1` の営業部 member 行は組織上の兼務としては残すが、
  営業アクセスの根拠はフラグに移る）
- 「部門を営業種別にすれば全員に営業画面が見える」という一括付与の便利さは失われる（新規ユーザー登録が
  所属+権限チェックの2操作になる）。権限初期値のサジェストは間接性の再導入になるため実装しない
