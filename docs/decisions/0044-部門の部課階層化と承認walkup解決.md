# ADR-0044: 部門の部課階層化と承認役職の walk-up 解決

- 日付: 2026-08-05
- 状態: 採用（本 ADR 起票と同セッションで実装）
- 関係: ADR-0016（複数課長 OR 承認——機構は継承、適用範囲を「同一ノードの同格役職」に正す）・
  ADR-0023（承認ルートマスタ化——無改修で継承）・ADR-0043（3軸分離の軸2/軸3を本 ADR が具体化）
- 起点: ユーザーレビュー 2026-08-05
  「kaihatsu1_ippan の課長決裁が『第一課長 OR 第二課長のどちらか』になる。実務では自分の課の課長が決裁するはず」
  「課長職不存在の部門では部長が決裁する、が実現できるか」

## 背景

1. **組織軸の解像度不足。** departments はフラットで「課」を持たず、開発1部の 2 人の課長は
   「同一部門の manager 行 2 本」でしかない。ADR-0016 の OR 承認は「本当に同格の課長が複数いる部門」を
   想定した機構だが、「別々の課を持つ課長たち」に誤適用され、実務（自分の課の課長が決裁）と乖離していた。
   シードのユーザー名（第一課長/第二課長）には課の概念があるのに、構造には無い
2. **課長不在の部門は申請がブロックされる。** `ResolveRoleApprovers` は役職 0 人の部門で空リストを返し、
   申請自体が「承認者を決定できません」で止まる。空席期間中はその部門の課長決裁申請が全部止まる。
   一方「自己承認回避」の場合に限り manager→director→経理代替の格上げが既に存在する（特例扱い）

## 決定

### 1. departments を自己参照 2 階層にする（課はオプション）

```sql
ALTER TABLE departments ADD COLUMN parent_id INTEGER NULL REFERENCES departments(id);
ALTER TABLE departments ADD COLUMN node_type TEXT NOT NULL DEFAULT 'dept';  -- 'dept'(部) | 'section'(課)
```

- 課（section）の親は必ず部（dept）。まずは 2 階層に限定（深い階層は将来拡張）
- **課は使いたい部門だけ使う**。課を持たない部門は従来どおり部直属の member/manager で運用できる
- 所属（member 行）と課長（manager 行）は課ノードに付く。部長（director 行）は部ノードに付く。
  部直属の member/manager も許容（課を持たない部門・部付きスタッフ）
- 主所属 `app_users.department_id` は所属ノード（課 or 部）を指す
- 兼務は従来どおり複数ノードへの member 行

### 2. 会計の部門ディメンションは「部」に固定

- 伝票（経費申請・仕訳・請求等）の部門は**部ノードのみ**。部門 SelectField の候補は `node_type='dept'` で絞る
- 申請者の主所属が課の場合、伝票部門は**課→親の部を自動導出**
- 部門別損益・予算・原価配賦・E2E 検算値は**一切無傷**（課別損益は将来の rollup 拡張とし今回スコープ外）

### 3. 承認役職の walk-up 解決（課長不在の繰上げが構造の帰結になる）

`ApprovalFlow.mod.cs` の役職解決を「所属ノードから上へ辿って最寄りの該当役職」に一般化する:

```
ResolveRoleApprovers(申請者, role):
  start = 申請者の主所属ノード（課 or 部）
  role == manager（課長決裁）:
    start から親方向に walk-up し、各ノードで manager 行の候補（申請者本人を除外）を収集。
    最初に見つかったノードの候補を返す（複数なら同一ノード内 OR = ADR-0016 継承）
    どのノードにも居なければ → director 解決へ格上げ（課長不在の自動繰上げ）
  role == director（部長決裁）:
    start から親方向に walk-up し、各ノードで director 行の候補（申請者本人を除外）を収集。
    最初に見つかったノードの候補を返す
    どのノードにも居なければ → 経理代替 1 名（既存フォールバック）。それも無ければ申請ブロック（明示エラー）
```

- **自己承認回避（ADR-0010/0016）は walk-up に統一**される: 候補から本人を除外した結果が空なら
  そのまま上へ辿る＝旧「格上げ特例」が一般則に吸収される
- **重複段の圧縮**: 格上げの結果、直前の承認段とメンバー集合が同一になる段は生成しない
  （例: 課長段が部長に格上げされ、次段も部長 → 部長 1 段に圧縮。同一人物の連続 2 回承認を防ぐ）
- 承認テンプレート・承認ルート判定マスタ（ADR-0023）・Order 生成・OR 承認・再承認・履歴は**無改修**。
  変更は役職解決関数（`ResolveRoleApprovers`/`ResolveDeptRoleAll`/`FindUserDepartment`）に局所化する

### 4. 挙動変更の明示（読み替え対象）

| ケース | 旧挙動 | 新挙動 |
|---|---|---|
| 課所属の一般が課長決裁 | 部内の全課長 OR | **自分の課の課長のみ** |
| 課長不在（空席）の課で課長決裁 | 申請ブロック | 部の課長 → 居なければ部長へ自動繰上げ |
| 部長本人が課長決裁の申請 | 部内の課長が承認 | 部に manager 不在なら部長代理へ（director から本人除外） |
| 課長本人が課長決裁の申請 | 部長へ格上げ（自己承認回避） | 同じ結果（walk-up の帰結として） |

### 5. シード組織の再編

5 つの有人部門すべてに 第一課/第二課 を新設し、ユーザー名と構造を一致させる:

- `*_kacho1` → 第一課の manager、`*_kacho2` → 第二課の manager
- 一般（`*_ippan`）→ 第一課の member、`kaihatsu2_shinjin` → 開発2部第二課の member
- 部長・部長代理 → 部ノードの director のまま
- `kaihatsu1_kacho1` の営業部 member 行は**組織上の兼務として存続**（営業アクセスの根拠は ADR-0043 のフラグへ移行済み）
- 全社共通（コスト部門）は課なしのまま

## 検討して退けた代替案

- **課を別テーブル（sections）**: 組織の真実が 2 テーブルに割れ、所属・役職の表現が二重化する。自己参照 1 本が一貫
- **`app_users.manager_id`（個人上司チェーン）**: 複数課長 OR の退行・空席時の断線・兼務（部門ごとに上司が違う）で破綻。
  組織変更のたびに個人単位の張り替えが必要になる点も部門経由に劣る
- **起案者が承認者を編集**: 自分の稟議のルートを自分で決められるのは内部統制の穴（ADR-0041 §3 の J-SOX 説明可能性と矛盾）。却下
- **フラット維持＋不在時繰上げのみ**: 最小コストだが「部内全課長 OR」の実務乖離が残る。
  組織階層に承認が正しく追随するのは市販ソフト比較の訴求点でもあり、ミッション（実運用レベル）に照らして階層化を採る

## 検証条件（実装時の受け入れ基準）

承認エンジンの役職解決は「絶対に不具合を入れてはならない場所」（ADR-0023 のユーザー要件）のため、
境界値の実機検証をワンセットにする:

1. 課所属の一般 → 自課の課長のみ（隣課の課長が混入しない）
2. 課長空席（manager 行を一時削除）→ 部長へ自動繰上げ
3. 部長も不在 → 経理代替、それも無ければ明示エラーで申請ブロック
4. 課長本人の申請 → 部長へ（自己承認回避 × 階層）
5. 部直属 member の申請（課なし部門）→ 部の課長/部長で従来どおり
6. 兼務者の申請 → 主所属側のルートで解決
7. 同一課に manager 2 名 → 同一ノード OR（ADR-0016 回帰）
8. 重複段の圧縮（課長段が部長に格上げ＋次段部長 → 1 段）
9. 再承認（実費超過 → RebuildOrdersFromTemplate 経路）でも同じ解決になる
