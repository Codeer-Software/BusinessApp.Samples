# 0007: 承認ルート＝テンプレ4種×役職の動的解決（approver_role 方式）

- 状態: 採用（**テンプレート選択ロジックの部分は ADR-0023 が supersede**——「費目×金額→テンプレート」の対応はスクリプト直書きから approval_route_rules マスタへ移行し、EXP_APPROVAL_MID/HIGH 閾値は廃止。役職の動的解決＝本 ADR の核は存続） / 日付: 2026-07-05

## 背景
経費精算の承認ルートは「費目×金額で決裁権限者が変わる」（references/経費精算.md、ユーザーの A/B モデルの核）。承認エンジン（PatternShowcaseAuth 移植）のテンプレートは承認者を**固定ユーザー**で持つため、「申請者の所属部門の課長/部長」という相対指定ができなかった。

## 選択肢
1. **テンプレメンバーに `approver_role` 列（manager/director/指定ユーザー）を追加し、申請時に部門マスタで解決** ← 採用
2. 部門ごとにテンプレートを複製（開発1部用・営業部用…）
3. 承認ルートをスクリプトに直書き（テンプレートを使わない）

## 決定
選択肢1。`approval_flow_template_member.approver_role` を追加し、`ApprovalFlow.LoadFromTemplate` が申請時に `app_users.department_id` → `departments.manager_user / director_user` で実ユーザーに解決する。総務は組織上1名なので**固定ユーザー指定**のまま。テンプレは4種（課長のみ／部長のみ／課長＋総務／部長＋総務）で、選択は `ExpenseRequest.SelectTemplateName()` が費目×金額（事前申請は見込み額）で行う。

## 根拠
- 「実際の業務では」部門が増えるたびにテンプレを複製するのは破綻する（選択肢2）。役職で書けば部門マスタの整備だけで全部門に効く。
- テンプレート駆動を維持することで、承認段数や並列承認の追加が**データ変更だけ**でできる（選択肢3はこの利点を失う）。
- 金額閾値（3万/20万）は `system_thresholds`（EXP_APPROVAL_MID/HIGH）でマスタ化し、社内規程の改定に設定変更で追随できる。

## 影響・実装メモ
- 解決失敗（所属部門なし・役職未設定）は申請をブロックし、Orders を一切作らない（事前検証パス）。
- 申請時にテンプレートを**再解決**する（Initialize 時は金額・費目が未入力のため仮値。申請ボタンで SelectTemplateName を呼び直す）。
- 交際費は金額によらず総務併載＋相手先/人数/目的の必須チェック（`ValidateForApply` 契約メソッド。親モジュールは SelectTemplateName と ValidateForApply を実装する）。
- **実測バグ修正**: 2段テンプレの1段目承認で `AdvanceToNextOrder` がメモリの `Orders.Rows` の遅延ロード空値を読み、フロー全体を誤って Approved にしていた → DB 検索ベースに修正（`RecalculateCurrentApproverDisplay` も同様に補強）。ChildModule の Status/LinkField はメモリを信用しない（Project.md 知見 #60 系）。
