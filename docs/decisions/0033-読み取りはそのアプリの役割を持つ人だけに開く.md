# ADR-0033 読み取りは、そのアプリの役割を持つ人だけに開く

## 状況

**権限の軸は 2026-08-28 に開発者が決めている**——アプリ（部品）ごとに直交・軸の中は階段・
取引先は独立の軸（決定の記録の現在形は [ADR-0034](0034-役割は部品ごとの直交な軸で持ち軸の中は階段にする.md)。
原文は 0026 §1 の追記）。

**ところが、同じ ADR の §3 は「データを読めるか」だけをこの軸の外に置いた。**
「**原則として絞らない**」と決めており、理由は CLB の性質だった——
`LinkField` / `SelectField` で参照されるマスタは読み取りを閉じると参照側が壊れる、
`AppUser` にはそもそも読み取り条件を付けられない（[qa/01 F-20](../qa/01_CLB静かな失敗.md)）。

**つまり ADR-0026 は、内部で食い違ったまま置かれている。**
§1 の追記が「軸は直交」と言い、§3 が「読み取りは軸を見ない」と言っている。

**実装もその食い違いを写している。** 帳簿のクエリモジュール 2 本は
[qa/02 R27-04](../qa/02_自己レビュー記録.md) で会計の役割に閉じたが、
`JournalEntry` / `JournalLine` / `PartnerInvoiceRegistration` の `UserReadCondition` は空＝全開放で、
**F-18 のとおりなら、`is_sysadmin` だけの `admin` や取引先だけの利用者が、API から下書きを含む
全伝票を読める**（同 R29-10。1.3.20 では未実測——E の実機確認 [qa/04 P-15](../qa/04_実機操作テスト.md) で確かめる）。

## 決定

**開発者が決めたのは、次のとおりである**（2026-08-31。逐語）。

> - 「**「読み取りは原則として絞らない」というのも、これはもはや原則ではないと思います。
>   必要最小限の読み取りにすべきです。**」
> - 「**経理アプリの何らかの権限（責任者・担当（編集）・閲覧）を何も持たないならば、
>   経理アプリのデータを読み取れないべきです。この関係は全アプリと権限とについて同じです。**」
> - 「**そして 1 アプリ内でも、経理責任者だけが閲覧できるものは、経理担当者は閲覧できません。**」
> - 「**ただし、そうするとアプリが動作できなくなる場合にのみ、やむを得ず読み取り権限を付与する
>   …という判断順序ではないか**」
> - 取引先については「**「経理担当であれば取引先の閲覧権限がなくても取引先を読み取らせる」
>   ことはしない」という整理も十分にありな気がします**」

**この最後の 1 つを採ることを Claude が推し、開発者が「あなたの整理でいいと思います」と承認した。**

**以下は、それを実装できる形にした Claude の判断である**（2026-08-31）。

1. **既定は「そのアプリの役割を 1 つも持たない利用者は、そのアプリのデータを読めない」**
2. **アプリの中は階段。** 上位は下位が読めるものを読める。
   **下位は上位専用のものを読めない**
3. **①②で壊れる箇所は、数え上げて 1 件ずつ「読ませる」以外で直せないかを先に見る**——
   **欄をそもそも出さない**か、**その権限を要求する**
4. **どうしても読ませるしかないものだけ、理由を書いて例外にする**

**②の「上位専用」はデータの層で言う**（Claude の判断）。画面の到達可否ではない
（それはフレームと玄関が決める。[ADR-0036 §1](0036-権限は到達と書き込みに書き分け守りは保存の関門に置く.md)）。
**入力に要る候補（勘定科目・部門・税区分）は「上位専用」ではない**——
編集が上位の役割に置かれたマスタでも、経理担当が伝票を起こすのに要るので読める
（誰が編集するかの現在形は [08_マスタ台帳](../08_マスタ台帳.md)）。

## 理由

**軸を直交と決めたのに、読み取りだけ軸を見ないのは、決めた形が守られていないということである。**
「経理担当 ⇒ 取引先閲覧」を入れると、取引先アプリの読み取り権限は独立した軸ではなくなり、
`partner_role OR accounting_role` になる。次に部品が増えれば同じ例外を要求してきて、
積み上がった先に残るのは**飾りの軸**である。これは開発者が 2026-08-28 に述べた
「**依存方向が逆**」そのものが、読み取りの側で起きるということでもある。

**2 つの案は、失敗の仕方が違う。**

| | 失敗の形 | 気づけるか |
|---|---|---|
| **直交を貫く**（採用） | 経理担当にしたのに取引先の閲覧を付け忘れる | **設定漏れ。利用者アカウントの画面に、付いている役割がそのまま出ている** |
| 例外を入れる | 何も壊れない。ただし権限モデルが嘘になる | **気づく機会がない** |

**設定漏れは直せる。モデルの嘘は直せない。**

**ただし「気づける」を過信しない。** 決定③のとおり**欄をそもそも出さない**実装にすると、
「候補が空で気づく」という手掛かりは消える。**気づきの担保は、利用者アカウントの画面と、
役割の組み合わせを検査する仕組みのほうに置く**（何を検査するかは下の帰結）。

**ADR-0026 §3 の観察は、いまも捨てない。** マスタを閉じると参照側が壊れる**かもしれない**ことは、
[qa/01 F-20](../qa/01_CLB静かな失敗.md) が書いている——**`AppUser` については CLB 仕様リファレンスが
明示的に警告しており、マスタ全般は同型の危険からの外挿である。どちらも 1.3.20 では確かめていない**
（qa/01 は F-18〜F-24 を前回プロジェクト由来の未確認として括っている）。誤っていたのは**射程**のほうで、
その観察から「だから**原則として**絞らない」を引き出したのが広すぎた。
**壊れるのは候補を出す欄であって、データを読むこと一般ではない。**

## 「読めない」は層によって意味が違う

**この節が、実装する人に読んでほしいところである。**
読み取りには 3 つの層があり、`UserReadCondition` が効くのは 1 番目だけである。

| 層 | 例 | 読み取り条件は効くか |
|---|---|---|
| **モジュール経由の読み取り** | 一覧・`ModuleSearcher`・`LinkField` / `SelectField` の候補 | **効く**（クエリモジュール自身にも効く） |
| **クエリモジュールの SQL が JOIN した先** | `JournalEntryList` が `partners` を JOIN して取引先名を出す | **効かない**（[qa/01 F-30](../qa/01_CLB静かな失敗.md)。**設計を読んで判ったもので、実測ではない**）。絞るなら SQL の `WHERE` に書く |
| **焼き込んだ写し**（帳簿の記載事項） | `partner_name_snapshot`（[ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md)） | **関係しない。もう会計コア自身のデータである** |
| **焼き込んだ写し**（記載事項ではないもの） | `registration_no_snapshot`——**法定記載事項ではない**。CSV の入出力と監査追跡が「当時の値」を要求するから持つ（[07 §4](../07_取引先設計.md)）。帳簿には印字しない | 同上 |

したがって——**取引先マスタを読めない経理担当でも、帳簿には取引先名が出る。**

**これは漏れではない**（Claude の判断）。ただし**制度は、この判断を支えない**——
帳簿の記載事項①は「課税仕入れの相手方の氏名又は名称」だが、
**取引先コード等の記号・番号で差し支えない（無条件）**（基通 11-6-1。
[消費税リサーチ §8](../research/2026-08-23_消費税インボイス制度.md)）。
制度が求めるのは記帳と保存であって、**氏名・名称そのものを帳簿に出すことでも、
社内の誰に読ませるかでもない。**

**支えているのは本プロジェクトの決定のほうである。** [ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md) が
「記載事項は計上の時点で写して固定する」と決めた（取引先の改名で過去の帳簿の記載が変わらないため）。
**写した値はもう会計コアのデータ**なので、会計の役割で読めてよい——
**「取引先マスタを読む権限」と「帳簿に載っている取引先名を読むこと」は別物**である。

**そして、写しが無い経路は例外として立てる**（決定④）。

- **振替伝票の一覧**（`JournalEntryList`）は**下書きを含むので写しが無く**、
  `partners` を JOIN した名前がそのまま出る。**下書きは帳簿ではない**（[04 §5](../04_会計ドメイン設計.md)）ので、
  上の理屈は当たらない。**この 1 件は「入力の一覧は会計の役割で読む」という例外**として置く——
  伝票を起こす人が、自分が入れた取引先の名前を見られないほうがおかしいからである
- **仕訳帳・総勘定元帳**は `COALESCE(写し, JOIN)` で、**新規の計上では写しが必ず入る**
  （`LedgerSnapshotWriter` が焼く。帳簿は `status = 'posted'` だけを出す）。
  ただし**写しを入れる前（2026-08-26 より前）に計上した行は NULL のままで、埋め直せない**
  （計上済みは不変。ADR-0004）。**残っているかは確かめていない**——E の着手時に数える

## 帰結

- **ADR-0026 §3 の「読み取りは原則として絞らない」は、本 ADR が置き換える。**
  0026 は全体を `superseded` にし、生きている決定は 0034〜0036 と本 ADR が論点ごとに引き継いだ
  （2026-09-01。規則・経緯・開発者の言葉は [ADR-0034 の状況節](0034-役割は部品ごとの直交な軸で持ち軸の中は階段にする.md)）
- **会計側は `Partner` モジュールを 5 か所で参照している**——`JournalEntry.Partner` と
  `JournalLine.Partner`（`LinkField`）、**帳簿 2 本と振替伝票の一覧の検索欄**（`SelectField`）。
  「入力の候補 1 か所」ではない。**取引先を読めない利用者に対しては、この 5 か所すべてを
  出し分ける**必要がある
- **`Partner` を閉じるまで、「取引先を読めない経理担当」は存在しない。**
  いま `Partner.UserReadCondition` は空である。**閉じる順序を決めるのは実装の仕事**で、
  本 ADR が決めたのは既定である
- **`viewer` を効かせないと運用できない。** 「取引先を読ませるが編集させたくない経理担当」に
  `partner_role = viewer` を付けることになる。いま `viewer` はどの条件にも現れない
  （[qa/02 R27-16](../qa/02_自己レビュー記録.md)）
- **いまの静的検査は、この既定を守れない。** `lint_design.py` の D-22 は
  「**使われている値より上位**が欠けていないか」しか見ないので、
  `staff OR manager` と書けば `viewer` を足し忘れても緑になる。
  **①を機械で守れる形は、`UserReadCondition` が空でないことを見るところまで**である
  （書き込み条件を見る D-24 の読み取り版。例外は許可表に理由つきで置く）。
  **「軸の全ての値が OR で入っている」という形にはできない**——決定②と衝突する。
  たとえば帳簿閲覧（`viewer`）に、仕訳帳は開いても下書きを含む振替伝票の一覧までは開かない、
  という判断がありうる（Claude の見立て。`viewer` をどのモジュールまで開くかの確定はフェーズ 4——
  [05 §5](../05_実装計画と現在地.md)）。**「どの役割まで開くか」はモジュールごとの判断であって機械には決まらない**
- **候補が空の欄を残さない。** [21 §1](../21_画面の原則.md) は
  「選べないものを候補に出さない」「押せるのに拒まれるボタンを残さない」と決めており、
  **読めない相手の候補欄はその系**である。21 に 1 項目として足す
- **計上は壊れない。** 登録番号を引く `PartnerRegistrationStore` も、名称を読む `PartnerStore` も
  **取引先部品のクラスで、素の SQL で読む**（モジュールの権限を通らない）。
  会計コアはそれを呼ぶだけなので、取引先モジュールを閉じても計上は動く
- **`AppUser` だけは閉じられない**（[qa/01 F-20](../qa/01_CLB静かな失敗.md)）。
  役割の列が全利用者から読めることは [ADR-0032](0032-認証部品のapp_usersを正典に迎え入れる.md) の帰結のまま
- **`UserReadCondition` が空のモジュールは 13 本ある**——状況節に挙げた入力の 3 本、
  マスタ・設定の 9 本（`Partner` / `Account` / `Department` / `SubAccount` / `TaxCategory` /
  `CompanyProfile` / `FiscalYear` / `AccountingPeriod` / `AppUser`）、
  そして**玄関の `PortalHome`**。
  **`PortalHome` は決定④の例外として開けたままにする**——玄関はどの役割の人も着地する画面で、
  ここを閉じるとルート URL の着地先が無くなる。**他の玄関 4 枚は役割で閉じてある**
- **どれをいつ閉じるかは [05](../05_実装計画と現在地.md) が持つ**——ADR に予定を焼き付けない
