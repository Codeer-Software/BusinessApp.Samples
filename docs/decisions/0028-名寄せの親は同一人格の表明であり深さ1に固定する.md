# ADR-0028 名寄せの親は同一人格の表明であり、深さ 1 に固定する

## 状況

開発者が取引先の「名寄せの親」を実機で触り、3 つの穴を見つけた（2026-08-28）。

1. **種別が違っても親にできる。** 法人を個人事業者の親にできてしまう
2. **連鎖も循環も作れる。** C の親が B、B の親が A にでき、さらに A と B が互いを親にできる
3. **無効にした取引先が候補に出ない**ので親に選べない。一方で、**親になっている取引先を
   無効にすることはできる**。どちらの整理を採っても、いまの実装は破れている

[07 §1-5](../07_取引先設計.md) は「連鎖と循環はフェーズ 3（解決の規則と一緒に作る）」と送っており、
[07 §2-2](../07_取引先設計.md) は解決の順序だけを決めていた。**規則の本体が未定のまま
画面だけが先に出ている**状態である。

## 決定

**名寄せの親は「この 2 者は同じ事業者である」という表明であり、それ以外の意味を持たない。**
[07 §2-1](../07_取引先設計.md) のとおり、名寄せが要る理由は
経過措置の控除限度額が「**一の免税事業者等ごと**」の集計だから（[06 §5](../06_消費税設計.md)）という 1 点に尽きる。
以下はすべてここから導く。

### 1. 種別が確定していて違う組は、保存の関門が止める

- 両方の `entity_type` が入っていて、かつ異なるなら**エラー**にする
- **片方でも未分類（NULL）なら通す**

### 2. 親は必ず根である（深さ 1 の森に固定する）

保存の関門が 2 つを止める。

- 選んだ**親が、さらに親を持っている**
- **自分が既に誰かの親になっている**のに、自分に親を付けようとしている

この 2 つで**循環は構造的に消える**（深さ 2 以上が作れないため）。

**同じ規則を DDL のトリガにも置く**（[ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md) の
「最後に守るのは DB」と同じ形）。行をまたぐので `CHECK` では書けないが、
`BEFORE INSERT / UPDATE` のトリガなら書ける。自己参照を拒む `CHECK` は現状のまま残す。

### 3. 無効にした取引先も、親にできる

`ParentPartner` の候補から `IsActive = true` の絞り込みを**外す**。

逆向き（親になっている取引先を無効にできないようにする）は**採らない**。
子を全部付け替えないと無効化できなくなり、実務が止まる。

### 4. 取引先の一覧に「名寄せの親」の列を出す

### 5. 法人番号を持つ取引先に親を設定することは、止めない

解決の順序は「法人番号 → 親 → 自分」なので、法人番号があれば親は**参照されない**。
[07 §2-2](../07_取引先設計.md) が決めたとおり、食い違いは**フェーズ 3 の解決処理が警告する**。
入力の時点では止めない。

## 理由

### 種別違いを「止める」にした理由

**種別が違えば別人格である。**「一の免税事業者等」として合算してはならない。
とくに**法人成り**（個人事業者が法人化する）は現実によく起き、しかも「同じ人だ」と感じやすいので、
**誤って束ねられる確率がいちばん高い組み合わせ**である。制度上の判断ではなく、
法人と個人が別の人であるという事実に近い。

一方、[07 §2-1](../07_取引先設計.md) が「未確認」と断っている**相続・合併・屋号違い**は、
いずれも**種別が同じまま**なので、この規則に妨げられない。

**「警告して通す」を採らなかった。** いまの `PartnerSubmitGate` は例外を投げる（止める）機構しか持たず、
警告を出すには Web API を 1 本足すか画面にロジックを書くことになる。
そして誤りの実害は「経過措置の限度額が過大に計算される」という**画面に何も出ない**形なので、
止める側に倒すのが本プロジェクトの流儀に合う。種別を直せば通るので詰まない。

**未分類を通すのは [07 §1-2](../07_取引先設計.md) との整合**である。あちらは
「種別の必須は画面で守り、DB は NULL 可にする。**その行を直そうとした時点で分類を求める**」と決めている。
未分類の行を親にした瞬間に止めると、触っていない行に分類を強制することになる。

### 深さ 1 に固定した理由

**連鎖を許すと、解決処理が union-find になる。** 循環の検知が必要になり、
検知したときに「誰が代表か」を決める規則がもう 1 つ要る。**代表が実行時に決まると、
同じデータで集計結果が変わりうる**。

深さ 1 でも用途は満たせる。名寄せに必要なのは「グループの代表を 1 つ決めること」だけで、
支店 → 本店・屋号 → 本体はどちらも深さ 1 である。グループの統合が要るなら、
子を付け替えるという明示的な操作になる（対象ペルソナの取引先は数十件）。

**単純な仕様にしておくほうが、最終的に不具合が少ない**（開発者の判断。2026-08-28）。

### 無効でも親にできるとした理由

`is_active` の意味は [ADR-0019](0019-マスタは会計が生んだ概念かで分ける.md) が定義している——
「**入力時の候補に出すか**の意味であり、過去データの表示・検索は妨げない」。

**名寄せの親は入力時の候補ではない。** 屋号を変えた個人事業者の旧レコードを無効にする、
支店ごとのレコードのうち本店をもう使わないので無効にする——どちらも**親が無効であることが正常**である。

## 帰結

- **`PartnerSubmitGate` に検査が 2 つ増える**（種別の一致・親の深さ）。
  どちらも他の行を読むので `PartnerStore` に問い合わせが増える。
  差分に無い項目は保存されている値で補う（既存の検査と同じ作法。[07 §1-5](../07_取引先設計.md)）
- **`partners` にトリガが 2 本増える。** テーブルの作り直しになる
  （[migrations/README](../../Designer/migrations/README.md) のレシピ）。
  **`display_order` の削除と同じ 1 本のマイグレーションでまとめる**——どちらも同じテーブルを触る
- **親と子のどちらを直す場合も検査が要る。** 「親に親を付ける」「子を持つ行に親を付ける」
  「親の種別を変えて食い違わせる」の 3 方向すべてを、自動テストと実機の台本に入れる
- [07 §1-5](../07_取引先設計.md) の「連鎖と循環はフェーズ 3」という保留は**解消する**
- フェーズ 3 で解決処理を書くとき、**入力側で深さ 1 が保証されている**ので、
  解決は「法人番号があればそれ、無ければ親、無ければ自分」の 1 段で済む
