# 0015: 承認ルートの役職管理 — 部門マスタ方式を維持（1部門複数課長はバックログ・設計スケッチ付き）

- 状態: 採用（現状維持）/ 日付: 2026-07-07 / 契機: ユーザー質問「役職の設定場所が分かりにくい」「1部門に課長が複数いる場合は？」

## 現状の構造（質問への回答）

- **ユーザーの role=approver** は「承認ボタンを押す権限があるか」
- **部門マスタの 課長/部長（manager_user/director_user）** は「承認ルートが誰に回るか」
- 承認ルート解決（ADR-0007）は申請者の所属部門から課長/部長を引く。役職はユーザー画面には表示されない

## 分かりにくさへの見解

二重管理を避けるため「ルートの担い手＝部門の属性」に一本化した設計は維持する（ユーザー画面からも設定できるようにすると、同じ事実を2画面で編集でき整合バグの温床になる）。**改善余地はユーザー画面に「この人が課長/部長を務める部門」の読み取り専用表示を足すこと**（編集は部門マスタに誘導）——小粒バックログとする。

## 1部門に課長が複数いる場合（現状は非対応）

departments.manager_user が単一列のため **v1 は1部門1課長**。実務では複数課長（どちらか1人が承認すれば良い OR 承認）が一般的という指摘はそのとおり。

### 対応する場合の設計スケッチ（バックログ）

1. `department_managers(department_id, user_id, role='manager'|'director')` 中間テーブルを新設（既存列は互換のため残すか移行）
2. ルート解決（ApprovalFlow.LoadFromTemplate）で該当役職の**全員を同一 Order のメンバーとして展開**（構造上 ApprovalFlowMember は複数メンバー/Order に対応済み）
3. **完了判定を OR 型に**: 現在の IsOrderCompleted は「全員承認（AND）」かつメモリ Rows 依存（既知の罠）。`approval_type='any'|'all'` を Order に持たせ、DB ベースで判定に書き換える（磨きバックログ「並列承認の DB 化」と同一作業）
4. 自己承認禁止（ADR-0010）は「候補から申請者を除外し、残0名なら格上げ」に一般化

影響範囲は承認フローの中核であり、過去に遅延ロード起因の重大バグを2度修正した領域。**着手時は承認シナリオ（S-01〜S-03）の完全回帰を必須**とする。
