# ADR-0020 スキーマは現在形の正典で持ち、変更は差分で配る

## 状況

スキーマの正典は `Designer/ddl/`（番号順の SQL）で、`Schema.Tests` がその**ファイルそのもの**を
インメモリ SQLite に適用して検査している。一方、**稼働 DB への反映は手作業**である。
実際に 005 へトリガを 3 本足したとき、同じ内容を `sql` CLI で手でも当てた。
**「DDL ファイルの内容」と「稼働 DB の姿」を同期させているのは人間の記憶**であり、
ずれても `designcheck` も `dotnet test` も検出しない（テストはインメモリ DB を使うので常に緑）。

さらに 2 つの要求が控えている。

- **制度ルールの配布**。当時の規則（ADR-0006 → 0019。現 `superseded`）は「制度ルールの更新は
  マイグレーションで配布する。行を UPDATE せず、新版を INSERT して旧版に `valid_to` を入れる」
  だった（**現在形は [12_マスタ台帳](../12_マスタ台帳.md) の制度ルールの行**が持つ。内容は同じ）
- **デモデータと配布**（フェーズ 7）。素の DB から再現可能に構築できる必要がある

## 決定

### 1. 置き場は 3 つ。正典は現在形、マイグレーションは配達物

| 置き場 | 役割 | 増減 |
|---|---|---|
| `Designer/ddl/` ＋ `Designer/seed/` | **現在形の正典**。その場で書き換える。読み手はここだけ読む。**新規 DB はここから直接作る**。`Schema.Tests` の検査対象（従来どおり） | 育つだけ |
| `Designer/migrations/`（新設） | **既存 DB への配達物**。`0001_add_posted_by.sql` のような**単一連番**。DDL と DML（制度ルールの行）を混在させ、種類はファイル名で示す。**適用済みファイルは編集禁止**（チェックサムで機械強制） | 増えるが、**全 DB が適用済みの分は掃除で消せる** |
| `Designer/migrations/baseline/`（新設） | **同値テストの起点**。`ddl/` の凍結コピー ＋ `VERSION`（どこまで畳んだか）。**手で編集することは決してない**。掃除のたびに現在の `ddl/` のコピーで置き換えて**前進する** | 増えない |

**履歴を再生しない。** 新規 DB は正典から直接作るので、マイグレーションは「歴史」ではなく
「配達物」である。古い差分を永遠に動く状態に保つ義務を負わず、
「今のスキーマ」を知るために差分の鎖をたどる必要もない。

### 2. ランナーは `tools/clb/migrate.ps1`。DB アクセスは `sql` CLI のみ

| コマンド | 内容 |
|---|---|
| `-Adopt` | 稼働 DB に `schema_migrations(version, name, checksum, applied_at)` を作り、現時点を刻む（一度だけ） |
| `-Apply` | 未適用のマイグレーションを番号順に、**1 本 1 トランザクション**で適用する |
| `-Status` | 適用済み／未適用の一覧を出す |
| `-Verify` | `ddl/` からインメモリに作った正解と稼働 DB の `sqlite_master` を突き合わせ、ずれを報告する |

自前で DB 接続しない（`AllowCliSqlAccess` の安全境界を迂回する経路を増やさない）。
既製ツール（DbUp・FluentMigrator 等）も使わない。必要な機能が上の 4 つだけで、
得るものより「自前で DB を開く経路が増える」損のほうが大きい。

### 3. 網は 2 つ。同値テストはコミット前、`-Verify` は稼働 DB

| 網 | いつ | 何を捕まえるか |
|---|---|---|
| **同値テスト**（`Schema.Tests` に追加） | コミット前（フック） | 「`baseline/` ＋ 未掃除のマイグレーション」を再生した DB が「`ddl/` ＋ `seed/`」から作った DB と一致するか。**正典を書き換えたのにマイグレーションを書き忘れた・間違えた**を、稼働 DB に触る前に捕まえる |
| **`-Verify`** | 適用後・随時（コミット前フックでも毎回） | 稼働 DB そのもののずれ。SQLite はトリガも含めて全定義が `sqlite_master` に載るので、**テーブル再構築（SQLite の制約変更は表の作り直しが要る）でトリガを 1 本落とした**という一番ありそうな事故を検出できる |

同値で比較するのは**スキーマ全体**と、**利用者が編集できないテーブルの行**（＝制度ルール。
[12_マスタ台帳](../12_マスタ台帳.md) の「誰が編集するか」列＝ベンダーの行がそのまま対象を決める）。
勘定科目のような利用者が育てるマスタは初期投入専用（既存 DB へ再配布しない）なので対象外。

制度ルールの行の正典は `seed/` 側に置き、既存 DB へは同じ内容をデータマイグレーションで配る。
「同じ事実を 2 か所に書かない」（規約 §4-6）に対しては、**機械が一致を強制する二重は許す**という
既存の型に従う（区分値を DDL・CLB の enum・C# の列挙型の 3 か所に持ち、
`EnumConsistencyTests` が一致を強制しているのと同じ）。

### 4. 掃除の規則

- 存在するすべての DB が適用済みのマイグレーションは、**もう二度と実行されない。消してよい**
- 消すときは必ず **baseline の前進とセット**で行う。`baseline/` を現在の `ddl/` のコピーで
  置き換え、`VERSION` に畳んだ番号を刻み、それ以前のファイルを消す
- 制度ルールの行を持つようになった後の掃除では、baseline にその行の写し（INSERT）も含める
- ランナーは、適用済みの最大番号が `VERSION` 未満の DB を
  「この DB は古すぎる」と止める（旧バージョンで途中まで適用してから来る）
- `schema_migrations` の行は消さない（何をいつ適用したかの記録として安い）

### 5. 制度ルールはデータマイグレーションで配る。編集 UI は作らない

利用者が制度データ（税率・控除割合・耐用年数）を編集する UI は作らない。

- 値の正しさはアプリには検証できない（形式や期間の重複は検査できても、70% が正しいかは
  法令にしかない）。編集させた瞬間、正しさの責任が利用者へ移り、
  ゴールデンテスト（[ADR-0009](0009-専門家レビューの代替手段.md)）が守る範囲の外に出る
- 追記専用・法源・出典の規律を UI で強制する機械は、年 1 回程度の事象に対して重すぎる
- **利用者が正当に変えたいものは既に②会計設定にある**ように三層の境界が引かれている。
  「この制度値を変えたい」が出たら、それは UI の不足ではなく**その値の分類の誤りのシグナル**である

配布の実態は「アプリの更新の中に SQL が入っている」。利用者が SQL を目にすることはない。
将来、アプリ更新とデータ更新を分離したくなったら「署名つきルールパックの取込画面」があり得るが、
それは編集 UI ではなく**ベンダー配布物の受け口**であり、データモデル（有効期間つきの行）は
同じなので、今の決定は分離を妨げない。閲覧専用の画面は従来どおり作る。

### 6. 作らないもの

- **Down（巻き戻し）**。実務でほぼ使われず、書いても検証されない。「あるのに動かない」が一番危険。
  開発中は DB を捨てて作り直し、本番相当はバックアップから戻す
- **履歴の完全再生**（§1）と**既製ツール**（§2）

## 理由

- **手作業の継続**を退けるのは、状況に書いたとおり。ずれをどの検査も検出しない
- **履歴再生方式**（マイグレーションの束だけを正典にする）を退けるのは 3 点。
  ①古い差分を永遠に保守する義務が生まれる ②「今のスキーマ」を読むのに鎖をたどることになる
  ③`Schema.Tests` の「DDL ファイルそのものを検査するので写し間違いが起きない」性質が壊れる
- **編集 UI** を退ける理由は決定 §5 のとおり

## 帰結

- **着手順が変わった。** マイグレーションの仕組みを最初のタスクとして実装した（2026-08-25）。
  `posted_by` が最初の実マイグレーションになる（[docs/04 §2](../04_実装計画と現在地.md)）
- **実測（2026-08-25・CLB 1.3.20）**: `sql` CLI はトランザクションで包まない。`--file` も `--query` も
  文ごとの autocommit で、エラーで停止するが、それまでの文はコミット済みのまま残る
- **決定（2026-08-25）**: 当初案の「BEGIN/COMMIT をマイグレーション側に書く規約」は採らず、
  **ランナーが包む**。ランナーはマイグレーション本体と `schema_migrations` への記録を
  1 つの BEGIN/COMMIT に入れた SQL を `--query` で流す（トランザクションは SQL 文中の
  BEGIN/COMMIT で成立させる）ので、**適用と記録がずれない**（ファイル側に書く方式では、
  本体が成功して記録だけ失敗する窓が残る）。ファイル側のトランザクション文は
  同値テストとランナーの両方が拒む
- **同値比較の実装（2026-08-25 確定）**: 比較は `sqlite_master` の**正規化テキスト
  （コメント除去＋引用外の空白の圧縮）の完全一致**とする（`TestSupport/SchemaSnapshot.cs`）。
  pragma による構造比較にしないのは、pragma に CHECK 制約が載らないため。
  テキスト一致を成り立たせる書き方の規約は [migrations/README](../../Designer/migrations/README.md) が持つ
- **`-Verify` の管轄（2026-08-25 確定）**: 稼働 DB は他部品（認証の `app_users`）と同居しているので、
  検証は「正典が持つオブジェクト」と「正典のテーブルに付いているオブジェクト」に限る。
  他部品のテーブルには口を出さない（[ADR-0029 §2](0029-所有は相手抜きで存在するかで導き粒度は決断で決める.md) の境界を検証にも当てる）
- **要確認（フェーズ 3 まで）**: 「市販ソフトは制度改正をベンダー更新で配り、利用者に
  税率マスタを編集させない」という前提はまだリサーチしていない（[22_調査の原則 §2](../22_調査の原則.md)）。
  制度ルールのテーブルを作る前に確認する
- 制度ルールのテーブルはまだ存在しない。データマイグレーションが実際に走るのはフェーズ 3 から。
  **フェーズ 3 まで保留なのはデータ行の同値検査**（スキーマ側の網は実装済みで、`-Verify` は
  「未適用のマイグレーションが残っていないか」の検査までは行う。書き込まれた**行の中身**が
  正典どおりかは確かめられない）。行の同値の具体形と、`-Adopt` の採用前検査への
  組み込みはそのとき固める
