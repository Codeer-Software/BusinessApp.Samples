# ADR-0015 訂正は取消と再計上の組で表し、更新履歴方式を採らない

## 状況

訂正（`correction`）の実装を前に、2 つの問いが未決だった。

1. 訂正は「取消 1 本 ＋ 再計上 1 本」の 2 本組になる（[10 §5](../10_会計ドメイン設計.md)）。
   **2 本が対であることをどう持つか。** 計上済みの行は変更できないので、
   列を足すなら訂正の行が生まれる前でなければならない、という時間制約があった
2. そもそも [ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md) の
   「計上済みは不変・訂正は反対仕訳」でよいのか。**国内クラウド会計の主流は
   「直接書き換え ＋ 改ざんできない更新履歴」であり**、開発者からも
   「更新履歴が保存される仕様でもいいのでは」という意見が出た

[市販ソフトと英語圏 ERP の調査](../research/2026-08-24_訂正と取消のデータ設計.md)を行い、決着させる。

## 選択肢

### A. 不変帳簿 ＋ 反対仕訳（ADR-0004 の路線を貫く）

計上済みは変更・削除できない。訂正は取消（貸借反転）と再計上の 2 本を帳簿に足す。

- **長所**
  - **要件の充足が帳簿そのもので完結する。** 国税庁は「反対仕訳に当初の仕訳を特定できる
    情報が付加されていれば、訂正又は削除の履歴の確保の要件を満たす」と明言している
    （[調査 §1](../research/2026-08-24_訂正と取消のデータ設計.md)。
    **2026-08-27 追記**: 出典は**電帳一問一答 令和 8 年 7 月版 問 26**で確定した。
    この一問一答は毎年改定されるので、引くときは版を確かめる）。**履歴テーブルが不要**
  - **守りが DB にある。** トリガと部分ユニークインデックスで、画面・CSV 取込・API・手 SQL の
    どこから来ても壊れない。すでに実装・検証済みで、取消は実機まで通っている
  - **集計が単純。** 取消も再計上もただの仕訳。除外フラグを見る集計が 1 つも無い
  - 英語圏 ERP（SAP・Odoo・NetSuite）の主流方式
    （**2026-08-26 追記**: ここに TKC FX も挙げていたが、TKC は**巡回監査後にロックされる**方式で、
    下の選択肢 D に当たる。A の味方として数えない——[調査 §2](../research/2026-08-24_訂正と取消のデータ設計.md)）
- **短所**
  - **帳簿が賑やかになる。** 計上後の軽微な打ち間違いでも赤黒 2 本が恒久的に残る
  - 一覧の可読性は表示上のグルーピングで補う必要がある

### B. 直接書き換え ＋ 更新履歴（freee・マネーフォワード・弥生の方式）

計上済みも編集できる。全変更を履歴テーブル（変更前後のスナップショット）に自動記録し、
履歴は利用者が訂正・削除できないようにする。

- **長所**
  - **UX が良い。** 帳簿が綺麗に保たれ、国内クラウド会計の利用者の期待に合う
  - 法的にも成立する（弥生・PCA 等がこの方式で JIIMA の優良電子帳簿認証を取得している）
- **短所**
  - **安全性が「全書き込み経路で履歴を書くこと」に丸ごと乗る。** 画面・CSV 取込（フェーズ 6）・
    API（フェーズ 6）・スクリプトのどれか 1 経路で書き漏らすと、**静かに要件違反**になり、
    実地調査まで気づけない。CLB 層は静的検査が効かないので、この失敗モードは
    本プロジェクトの最大の弱点とちょうど噛み合う
  - 現行の守り（DB トリガ）を撤去することになる。最後の砦を失う
  - 実装が大きい。履歴テーブル（伝票＋明細のスナップショット）・改ざん防止・履歴閲覧画面・
    全書き込み経路のフック・テスト一式。ADR-0004 以降に作ったものの作り直しを含む

### C. 版チェーン（PCA 方式）

旧版を「二重線付き」で残し、新版が旧版を参照する。

- **長所**: 帳簿上で履歴が見え、現行版は綺麗
- **短所**: **集計のたびに「現行版のみ」のフィルタが要る。** 除外を書き漏らした集計が
  静かに残高を狂わせる——総額方式がわざわざ避けた事故がそのまま戻ってくる。実装も大きい

### D. 折衷（開いている期間は直接編集＋履歴、締め後は反対仕訳。TKC のロック方式）

- **長所**: UX と堅牢性の折衷
- **短所**: 対象が締め前に限られるだけで、**B の機構一式（履歴・改ざん防止・全経路フック）が
  そのまま必要**。2 方式の並存で複雑さはむしろ増える

## 決定

### A を貫く。更新履歴方式（B）は採らない

決め手は合法性ではない（B も合法である）。**失敗モードの質**である。

- A の失敗モードは「直せない」。**うるさく失敗する**ので必ず気づく
- B の失敗モードは「履歴の書き漏らし」。**静かに失敗し**、実地調査まで表面化しない。
  CLB という静的検査の効かない層を挟む本構成で、これは受け入れられない

**この選択は可逆である。** A で運用して実利用者の訂正 UX に不満が実証されたら、
D（開いている期間の直接編集）を後から足せる。逆に B で始めて A に戻ると履歴の空白が残り、
事実上戻れない。**A は片道ドアではない側の選択**でもある。

UX の不利は次で軽減する。①下書きのうちは自由に編集・削除できる（すでにそう）。
②訂正を 1 操作にする（下記）。③原仕訳・取消・再計上を画面でグルーピングして見せる。

### 再計上（correction）に列を足さない。対のリンクは持たない

訂正の 2 本は、どちらも `original_entry_id` で**原仕訳を**指すだけにする。

- 法が求めるのは「取消 → 原仕訳」の参照 1 本だけ（[調査 §1](../research/2026-08-24_訂正と取消のデータ設計.md)）
- 調査した実装（SAP・Odoo・NetSuite・Xero・QuickBooks ほか）に、
  **「再計上が取消を指す」列を持つものは 1 つも無かった**。Odoo は訂正を 1 操作で提供しながら、
  新しい伝票に外部キーを付けていない
- 鎖にすると「取消だけして再計上しない」「再計上を 2 回やり直す」が表現できず、
  鎖が壊れたときの回復手段が無い
- まとめて見せたいときは `id = 原 or original_entry_id = 原` で集まる

**これで「訂正の行が生まれる前に列を足さないと」という時間制約は消えた。**

### 訂正の操作仕様（フェーズ 2 で実装）

1. 計上済み伝票の「訂正する」→ サーバが**取消を計上**し、**原仕訳の内容を写した
   correction の下書き**を作って開く
2. 利用者が下書きを直して計上する。correction の中身は利用者が決める
   （取消と違い、サーバは上書きしない）
3. 途中で放棄して「取消だけ」が残るのは**正当な状態**（単なる取消と同じ）
4. **誤って取り消したときの復旧**は、correction を単独で計上する
   （取消は既にあるので、正しい内容＝原仕訳と同じ内容を入れ直せば元に戻り、
   原仕訳への参照で経緯が辿れる）
5. **取り消せる種別に correction を加える**（今は normal のみ）。
   訂正を間違えたときに、その訂正を取り消せないと詰むため

### 総額方式で固定する。方式フラグは持たない

純額方式（赤伝＝同じ科目にマイナス）も法令上は認められるが、作らない。
切り替え可能にすると集計・帳票・税集計に方式分岐が増える。
赤伝を求める実務が実証されたら本 ADR を改訂する
（そのときは方式を仕訳に保存する。後から解釈を変えられない値のため）。

## 帰結

- 訂正はいつでも着手できる（スキーマ変更なし）
- 履歴テーブル・履歴閲覧画面・改ざん防止機構は**作らない**（設計がまるごと 1 つ減る）
- 市販クラウド会計と UX が異なることは意識的な選択である（[32_調査のルール §2](../32_調査のルール.md)）。
  対象ペルソナに税理士が含まれ、TKC も**巡回監査後は**直接訂正できない点で近い
  （**2026-08-26 追記**: 当初「税理士業界標準の TKC が同方式」と書いたが、
  「業界標準」に出典が無く、TKC は条件付きなので限定を戻した）
- 取消理由（`reversal_reason`）は本 ADR の範囲外
  （[qa/02](../qa/02_自己レビュー記録.md) R3-09。監査ログの設計と一緒に扱う）
