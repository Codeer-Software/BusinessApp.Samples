# ADR-0050 会計コアの層は、ドメイン・アプリケーション・インフラ・プレゼンテーションの 4 つで読み、機能フォルダの下で分ける

## 状況

[ADR-0013](0013-機能単位のモジュール分割と依存方向.md) は層を**プロジェクト参照**で（`AccountingCore` → `AccountingCore.Server`）、
機能を**名前空間フォルダ**で割った。`AccountingCore.Server` は「採番・保存・サーバ側の関門・帳票 API」の置き場で、
その中に**永続化**（`JournalEntryStore` ほか）・**業務の流れ**（`JournalAmendmentService`・`JournalPoster`）・
**外との境界**（`JournalAmendmentEndpoint`・`AccountingSubmitPipeline`）が同じフォルダに並んでいた。

[ADR-0049](0049-会計補助はステートレスなものだけを作り会計コアのドメイン層には置かない.md) で複製を
「ドメイン層からアプリケーション層へ」移したとき、**「アプリケーション層」という語がこのリポジトリのどこにも定義されていない**
ことが自己レビューで指摘された（[qa/02 R64-07](../qa/02_自己レビュー記録.md)）。0049 は暫定で
「アプリケーション層は `AccountingCore.Server`」と書いたが、同じプロジェクトにインフラも API もあるので、
その定義では「`AccountingCore.Server` に置く」以上のことを言えていない。

開発者が 2026-09-10 に、オニオンアーキテクチャの 4 層でこのプロジェクトを読み直す整理を示した。本 ADR はそれを記録する。

## 決定

**以下は開発者の整理である**（2026-09-10）。Claude の提案を採った部分は、それぞれの節で分けて書く。

### 1. 層は 4 つ。置き場は 3 つ

| 層 | 責務 | 置き場 |
|---|---|---|
| **ドメイン層** | 型・不変条件・検証。純粋で、DB も時計も知らない | `AccountingCore` |
| **アプリケーション層** | オーケストレーション——業務の流れに沿って、ドメインとインフラを適切に使う | `AccountingCore.Server` の機能フォルダ配下 `Application/` |
| **インフラ層** | 永続化・外部との通信。DB を読み書きする側 | `AccountingCore.Server` の機能フォルダ配下 `Infrastructure/` |
| **プレゼンテーション層** | 利用者と外の世界に面する側——画面と、サーバの API・保存パイプラインの入口 | **CLB**（画面）と、`AccountingCore.Server` の機能フォルダ配下 `Presentation/` |

**いちばん大切なのはドメイン層の純粋性である**（開発者）。アプリケーション層のためのプロジェクトは作らない
（オーバーエンジニアリング。開発者の判断）——**アプリケーション層はインフラ層と同じプロジェクトに置き、フォルダで分ける**。

**インフラ層は「外部と通信する」ものだけではない。** DB の読み書きはインフラである
（開発者は当初「インフラ層は今のところ無い」と見ていたが、`JournalEntryStore` ほか 7 本の永続化を挙げられて訂正した。
2026-09-10。Claude の指摘を開発者が採用）。

### 2. CLB は薄い UI に徹し、本来 UI が持つロジックも `AccountingCore.Server` に置く

CLB スクリプトはテストが組めない（[ADR-0008](0008-CLBとCSharpライブラリの責務分担.md)）ので、
**本来ならプレゼンテーション層（画面）に置くべきロジックも、テストできる `AccountingCore.Server` に置く。**
CLB には本当に薄い、利用者インターフェースだけを書く。**これは本プロジェクトの制約であり、ルールである**（開発者）。
サーバ側のプレゼンテーション層が「API を持つ」以上の仕事をしているのは、このためである。

### 3. フォルダは機能が先、層が後

`AccountingCore.Server/<機能>/<層>/` の形にする（例：`Journals/Application/JournalPoster.cs`）。
**層を先にしない**——[ADR-0013](0013-機能単位のモジュール分割と依存方向.md) の「3 つのプロジェクトで同じ機能フォルダ名を使う」と、
機能フォルダの最初の名前で判定する `ModuleDependencyTests` を壊さないため（Claude の提案を開発者が採用）。
機能をまたぐもの（保存パイプラインの入口・トランザクション・役割の読み出し）は `Shared/<層>/`。
テストは同じ形で鏡写しにする（`TestLayoutConvention` が要求する）。

### 4. 依存の向きは、軽く機械で守る

| から | へ | 可否 |
|---|---|---|
| Presentation | Application・Infrastructure・ドメイン | 可（Infrastructure へは**組み立て**のため。業務の流れを書いてはいけない） |
| Application | Infrastructure・ドメイン | 可。**インフラの具象をそのまま使う**（インターフェースで反転しない。[ADR-0013 の決定 5](0013-機能単位のモジュール分割と依存方向.md) と同じ判断——ここで反転まで入れるのはオーバーエンジニアリング） |
| Infrastructure | ドメイン | 可。**Application・Presentation を参照しない** |
| Application | Presentation | **不可** |

規約テスト（`LayerDependencyTests`）が、名前空間の出現でこれを検査する（[ADR-0013 の決定 4](0013-機能単位のモジュール分割と依存方向.md) と同じ手法。
Claude の提案を開発者が採用。「軽く」の意味は、反転を要求しない・組み立てのための参照を許す、の 2 つ）。

### 5. 保存の関門は、形式の検査ならプレゼンテーション、業務の判定ならアプリケーション

開発者の直感——**NestJS の `@UseGuards`・`@UsePipes` はプレゼンテーション層で、「リクエストの形式が正しいか」を見る役目はそこにある。
ただし「正しい形式とは何か」の知識はアプリケーション層やドメイン層にあり、Guard や Pipe はそれを利用する**（2026-09-10。「内容を見ての個別判断」と付言）。

これを当てはめると、関門は 2 種類に分かれる（Claude の当てはめ）。

| 関門 | 見ているもの | 層 |
|---|---|---|
| `BlankTextNormalizer` | 空文字を NULL に寄せる（入力の正規化） | Presentation（Pipe） |
| `SaveFailureMessage` | 枠組みの言葉を利用者の語に置き換える | Presentation |
| `AccountingSubmitPipeline` | CLB の保存に関門をつなぐ入口 | Presentation（組み立て） |
| `JournalSubmitRequirements` | DDL が受け取れる形か（1 行で判定できる形式） | **Application**——`JournalSubmitGate` の中で呼ばれるので、Presentation に置くと Application → Presentation の参照になる。形式の知識はドメインの `JournalLineRules` が持ち、ここはそれを当てるだけ |
| `JournalSubmitGate`・`MasterSubmitGate`・`MasterMeaningGate`・`CompanyProfileSubmitGate` | 計上の検証・採番・意味の凍結・コードの重複——**業務の判定** | Application |

`JournalDuplication`（純粋関数。会計補助）は Application。ドメインを借りて写す欄を決めるのは業務の流れの一部で、外の世界の形式には触れない。

### 6. 「アプリケーション層に置く」の意味

[ADR-0049 の決定 5](0049-会計補助はステートレスなものだけを作り会計コアのドメイン層には置かない.md) の暫定の定義
（「アプリケーション層は `AccountingCore.Server`」）は本 ADR に置き換える。会計補助（ステートレス）は `Application/` に置く。

## 理由

- **ドメイン層の純粋性を最優先にする**（開発者）。アプリケーション・インフラ・プレゼンテーションの 3 つが同じプロジェクトに
  同居しても、ドメインが汚れなければ会計ロジックのテストは守れる
- **フォルダで分ければ、読む人が層を間違えない。** 同じフォルダに永続化と業務の流れが並ぶと、
  「ドメイン層に置かなくてよいはず」（ADR-0049）の判断がしにくい
- **反転を入れないのは、置き換える相手がいないから。** DB は SQLite 1 つで、差し替えの予定が無い

### 7. 実装で決まった置き場（Claude の当てはめ。2026-09-10）

- **`GuardedMaster`・`GuardedColumn`・`OneWayColumn`・`CodedMaster`・`CodedParent` は `Masters/Infrastructure/`。**
  表・列・呼び名を束ねる記述子で、Infrastructure の口（`MasterUsageStore`・`MasterCodeStore`）が生の文字列を受けないための型である。
  **どのマスタを守るか・どのマスタがコードを持つか（一覧）は Application の関門が持つ**——型はインフラ、一覧は業務の判定
- **`LedgerSnapshotWriter`（Infrastructure）は差し戻しの例外を投げず、断り（`Violation`）を返す。** 投げるのは `JournalPoster`（Application）。
  Infrastructure が Application の例外型を知らないための形で、動きは変わらない（断りがあれば 1 行も書かない）
- **コメントの中の言及も「参照」と数える**（`<see cref>` は `using` を要するので、逆向きの言及は `<c>` で書く）。
  「呼ぶ」と書いたら呼んでいる、と扱う——書き分けたいなら層の名前を出さずに書く

## 帰結

- `AccountingCore.Server` の 25 ファイルを `<機能>/<層>/` に移し、名前空間もフォルダに合わせる。テストも鏡写しに移す
- `LayerDependencyTests` を足す。壊して赤くなることを確かめる
- [ADR-0013](0013-機能単位のモジュール分割と依存方向.md) の「将来 `.Application` を割る余地は残る」はそのまま——割るときはフォルダ単位で移せる
- [docs/20 §1](../20_実装の原則.md) に層の語を足す。ADR-0049 の決定 5 は本 ADR を指す形に直す

## 検討したが採らなかった案

- **アプリケーション層のプロジェクトを作る**——オーバーエンジニアリング（開発者）
- **層を先にしたフォルダ**（`Application/Journals/`）——ADR-0013 と `ModuleDependencyTests` を作り直すことになる
- **インフラをインターフェースで反転する**——[ADR-0013 の決定 5](0013-機能単位のモジュール分割と依存方向.md) と同じ理由で採らない
