# ADR-0006 マスタの三層分類

## 状況

「マスタ」と一括りにされているものの中に、**性質がまったく違うもの**が混ざっている。
前回プロジェクトでは「システム管理者が変更するマスタ」と「経理担当者が変更するマスタ」を
権限で分けていたが、権限の違いの裏にはより本質的な区別がある。

また「会計期間はマスタか」「期首残高はマスタか」という問いにも答えを出す必要がある。

## 決定

マスタを**更新のきっかけ**で 3 層に分類し、それぞれ扱いを変える。

| 層 | 内容 | 更新するのは誰か | 更新のきっかけ | 有効期間 |
|---|---|---|---|---|
| **① 制度ルール** | 消費税率、経過措置の控除割合、少額特例の閾値、みなし仕入率、法定耐用年数、償却率 | **ベンダー**（利用者は閲覧のみ） | 法令改正 | **必須**（`valid_from` / `valid_to`） |
| **② 会計設定** | 事業所情報、会計期間、消費税の課税方式・経理方式・控除方式、期首残高 | 経理責任者（年 1 回程度） | 期首・制度選択の変更 | 会計期間単位 |
| **③ 会計マスタ** | 勘定科目、補助科目、税区分の割当、取引先、部門 | 経理担当者（随時） | 業務 | 状態フラグ（有効／無効） |

### 層ごとの規則

**① 制度ルール**
- **利用者は編集できない**（画面に編集 UI を出さない。参照のみ）
- 必ず有効期間・法源・出典 URL を持つ
- **仕訳に適用したルールの版を固定して保存する。** 後日マスタを更新しても過去の仕訳を再計算しない
- 更新はマイグレーション（DDL/DML）で配布する。C# 側にハードコードしない

**② 会計設定**
- 会計期間（`fiscal_years` / `accounting_periods`）は**マスタではなく状態を持つ台帳**として扱う。
  締め状態（open / closed）が動くため、静的な参照データとは性質が違う
- **期首残高はマスタではなくデータ**である。金額を持ち、貸借一致の検証対象で、
  繰越処理で生成される。仕訳とは別テーブルに置くが、扱いは仕訳に準じる

**③ 会計マスタ**
- 削除ではなく**無効化**する（過去の仕訳が参照しているため）
- 有効／無効フラグは「**入力時の候補に出すか**」の意味であり、
  過去データの表示や検索を妨げない。フラグの名前もその意味に合わせる

## 理由

- **①と③を同じ「マスタ」として扱うと必ず事故る。** 利用者が税率を編集できる作りにすると、
  過去の仕訳が黙って再計算されるか、編集した本人しか理由を知らない値が帳簿に残る。
  制度値は「マスタ」ではなく**ベンダーが配布するルールデータ**である
- **②を①③から分ける理由**は更新頻度と影響範囲である。会計設定を変えると帳簿全体の
  解釈が変わる（経理方式の変更・控除方式の変更）ため、期首以外での変更は原則として認めない
- 「期首残高をマスタに置く」設計は貸借一致の検証を素通りさせる。
  **金額を持つものは全てデータとして扱い、同じ検証を通す**

## 帰結

- 制度ルールは C# のコード部品（`AccountingCore`）が**読み取り専用で参照**する。
  税率・控除割合の判定は「取引日（または課税仕入れの時点）で有効な版を引く」形に統一する
- 会計マスタの画面は経理担当者向け、会計設定の画面は経理責任者向けに分ける。
  制度ルールは参照専用の画面のみ（「いま何が適用されているか」を説明するため）
- **ユーザー・権限は会計マスタに含めない。** これは認証部品の責務であり、会計コアの外側である
  （既存の `AppUser` を利用する）
- 制度ルールのテーブルは、**マイグレーションで更新されることを前提にした構造**にする
  （行を UPDATE せず、新しい版を INSERT して旧版に `valid_to` を入れる）
