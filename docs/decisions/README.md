# ADR（意思決定ログ）

判断の**経緯**を残す場所。仕様書が「今どうなっているか」を書くのに対し、ADR は
「**なぜそう決めたか・他に何を検討したか**」を書く。

## 書き方

- 1 件 1 ファイル。ファイル名は `NNNN-短い決定文.md`（4 桁ゼロ埋め・番号は連番）
- 見出しは `状況` → `決定` → `理由` → `帰結` の 4 節を基本にする
- **決定文はタイトルに書く。**「〜について」ではなく「〜する」と言い切る
- 起こしたら**本ファイルの表に 1 行足す**（`lint_docs.py` が実ファイルと突合する）
- ADR は原則として**書き換えない**。覆すときは新しい ADR を起こし、旧 ADR の `status` を
  `superseded` にして `related` に後継を書く（規約 §3-3）
- **1 件 1 論点。** 複数の論点を抱えた ADR は、片方が覆されたときに丸ごと写し直しになる
  （実例: ADR-0019。所有の軸とマスタごとの仕様を 1 本に抱え、後者が動いた瞬間に全体を
  `superseded` にするしかなくなった）。**更新され続ける現在形は仕様書に置き、ADR には理由だけを置く**

## ADR を起こす基準

次に当てはまるなら起こす。

- 後から変えると高くつく（データモデル・依存の向き・不変条件）
- 選択肢が複数あり、どれを選んだかを後で説明する必要がある
- 「なぜこうなっていないのか」を将来必ず聞かれる

逆に、自明な実装判断や、仕様書に書けば足りることは ADR にしない。
