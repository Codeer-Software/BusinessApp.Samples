# ADR-0037 計上済みの伝票は、画面でも計上時の姿を見せる

## 状況

**計上済みの伝票の詳細が、取引先欄に「いまのマスタの名前」を出していた**（2026-09-02 の実機で発見。
[qa/04](../qa/04_実機操作テスト.md) の記録）。同じ伝票を帳簿で見ると**計上時の写し**が出るので、
**取引先を改名したあとは、2 か所で名前が違って見える。**

[ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md) が固定すると決めたのは
**帳簿の記載事項**（消法 30 ⑧。明細が満たす。[10 §4-2](../10_会計ドメイン設計.md)）までで、
**伝票詳細の参照欄の見せ方は決めていない。** どちらを出すかは、
**帳簿の正典性**（写し）と**マスタへの導線**（現在名）のどちらを重く見るかの判断である。

## 決定

**計上済みの伝票を見せる画面は、計上時の姿を見せる**（開発者の決定。2026-09-02。
**同じ伝票の取引先名が場所によって違うと、どちらが正典なのか利用者に分からなくなるから**）。

### 1. 伝票の取引先は、計上済みなら計上時の写しを出す

**`journal_entries.partner_name_snapshot` を足し、計上時にサーバが焼く。** 画面の欄は、
下書きならマスタを引く欄（`LinkField`）、計上済みなら写しの欄（`TextField`）に入れ替える。

**伝票の画面の明細行には、取引先の列が無い**——`ListField` が描くのは `JournalLine` の
**一覧レイアウト**で、そこに列を置いていないからである（詳細レイアウトにはある。qa/01 F-34）。
データとしては明細も取引先を持ち、明細の値が伝票の既定値を上書きする（[10 §4-1](../10_会計ドメイン設計.md)）。
**利用者が改名の影響を見たのは、伝票ヘッダの欄である。**
明細の写し（`journal_lines.partner_name_snapshot`）は帳簿が読むもので、
[ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md) が既に決めている。

**列を分けるのは、役割が違うからである。** 明細の写しは**帳簿の法定記載事項**
（消法 30 ⑧。[10 §4-2](../10_会計ドメイン設計.md)）で、伝票の写しは**画面が計上時の姿を見せる**ためのもの。
伝票の取引先は明細の既定値でもあるが、**全明細が自分の取引先を持つ伝票では明細から復元できない**ので、
伝票の側にも持つ。

### 2. 反対仕訳は原仕訳の写しを引き継ぐ

焼き直すと、原仕訳の計上後に改名された相手で**同じ取引の表と裏が違う名前になる**。
明細で実際に起きたこと（[qa/03 L-13](../qa/03_テストで漏らした実例.md)）を、伝票の側でも避ける。

### 3. 振替伝票の一覧も、計上済みは写しを出す

**入力の一覧は帳簿ではない**（[ADR-0017](0017-仕訳と伝票の呼び分け.md)）——下書きを含み、
「いま探す」ための道具である。だから当初は現在名のままにする案だったが、
**同じ伝票を一覧と詳細で見て名前が違うのは、この ADR が直そうとしている食い違いそのもの**なので、
`COALESCE(e.partner_name_snapshot, p.name)` で揃える。**下書きは現在名**——
まだ写しが無く、入力の途中だからである。

### 4. 検索は識別子で行う。写しにするのは表示だけ

帳簿の取引先の検索は取引先の識別子で引く（`COALESCE(l.partner_id, e.partner_id)`）。
**改名しても同じ取引先で引ける**という点で、写しの文字列で引くより強い。
[40 の D1](../40_優良な電子帳簿の対応表.md) はこの形で満たしている。

## 理由

- **計上済みの伝票は不変である**（[ADR-0004](0004-優良な電子帳簿への準拠と仕訳の不変性.md)）。
  レコードが不変なのに**画面の表示だけが時とともに変わる**のは、不変性の約束に対する裏切りに見える
- **写しは既にある。** 明細の `partner_name_snapshot` は計上時にサーバが焼いており
  （[ADR-0018](0018-帳簿の記載事項は計上時に写して固定する.md)）、帳簿はそれを読んでいる。
  伝票詳細だけが読んでいなかった
- **導線は失われない。** 改名した取引先を追いたいときは、下書きの伝票・振替伝票の一覧・
  取引先マスタのどれからでも辿れる。**計上済みの伝票詳細だけが辿れなくなる**が、
  そこは「当時どう記帳したか」を見る画面である

## 帰結

- **計上済みの伝票詳細から取引先マスタへ飛べなくなる。** 欄が `LinkField` ではなくなるため。
  必要になったら、写しの隣に「いまの取引先を見る」導線を別に置く（欄の値を現在名に戻すのではなく）
- **この列より前に計上された伝票は写しが空である。** 埋め直さない——
  計上時点の名前が分からない以上、いまのマスタ名で埋めるのは嘘になる。
  **画面も一覧も現在名へ落ちる**（`COALESCE(写し, 現在名)` と同じ見方に揃えてある）。
  **取消も同じ**——原仕訳の写しが空なら、取消の写しも空になる
- **`registration_no_snapshot` は画面に出さないまま**である。帳簿の記載事項ではなく、
  判定の根拠の記録だから（[07 §4](../07_取引先設計.md)）
- **この規則は取引先以外にも当てはまりうる。** 勘定科目・補助科目・部門を改名すると、
  計上済みの伝票と帳簿の表示が動く。**いまは写しを持っていない**ので同じ問題が残る——
  帳簿の法定記載事項ではないので急がないが、[12_マスタ台帳](../12_マスタ台帳.md) の論点として扱う
- **写しは利用者から受け取らない。** 保存の関門が `PartnerNameSnapshot` を捨てる
  （`PostedBy` / `PostedAt` / `Creator` / `Updater` と同じ扱い）。
  通すと、帳簿と食い違う名前を画面に出せてしまう
