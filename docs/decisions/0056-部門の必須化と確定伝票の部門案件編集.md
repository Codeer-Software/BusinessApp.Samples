# ADR-0056: 部門を必須化する（全社共通・NOT NULL）／確定済み伝票でも部門・案件は編集可にする

- 日付: 2026-08-14
- 状態: 採用（実装前。実機検証は実装後に追記する）
- 関係: ADR-0052（**税区分で同じ問題を同じ形で解いた。本 ADR はその対称形**）／
  ADR-0009（案件損益＝管理会計レイヤ）／ADR-0026（確定済み伝票は編集・削除できない。**本 ADR で一部緩める**）／
  ADR-0029・ADR-0031（販売伝票への部門付与）／ADR-0044（部門の部課階層）／ADR-0055（入出金起票にも部門欄が要る）

## 背景: 部門別 P/L はほとんど機能していない

「部門別損益」を売りにしているが、実データを数えると次の状態だった（2026-08-14 時点・仕訳 202 行）。

| 科目区分 | 明細行 | 部門あり | |
|---|---:|---:|---|
| **費用** | 38 | **9** | **76% が部門なし** |
| **収益** | 18 | **3** | **83% が部門なし** |
| 資産 | 103 | 12 | |
| 負債 | 43 | 11 | |

部門が付いている費用 9 行は**すべて経費精算由来**である。起票経路ごとに見ると、

| 経路 | 部門なしの行 |
|---|---|
| 経費精算 | 0 / 21（唯一の完全実装） |
| 銀行明細取込 | **32 / 32** |
| 仕入先請求書 | **9 / 9** |
| SES 精算 | **9 / 9** |
| 定型仕訳 | **8 / 8** |
| 入出金起票 | **6 / 6** |
| 振替伝票（手入力） | 34 / 37 |

つまり「穴が 1 つある」ではなく、**売りにしている機能が動いていない**。
`BudgetVsActual.Query.sql` が `COALESCE(d.name, '(部門未設定)')` で未設定行を可視化しているのは、
本来「移行期の逃げ道」であって定常状態ではない。

### 税区分でまったく同じ問題を解いている

ADR-0052 で「**`NULL`（未設定）という表現を廃止し、BS 科目にも『対象外』を明示して `NOT NULL` 化する。
同じ意味を 2 通りで表現していたのが根だった**」と決めた。部門もいま同じ形をしている——
`NULL` が「全社共通のつもり」なのか「入れ忘れ」なのか区別できない。
**税区分でその表現をやめたのなら、部門も同じ結論になるのが設計の筋である。**

## 決定 1: 規約を 1 本に決める

> **損益科目の行には必ず部門を付ける。BS 科目の行は任意。部門は「部」レベル。
> 特定部門に紐づかない費用は「全社共通」に付け、空にはしない。**

- **損益／BS の判定は `accounts.account_type`**（`expense` 33 科目・`revenue` 7 科目が損益、
  `asset` / `liability` / `equity` が BS）
- **「部」レベル**（`departments.node_type = 'dept'`）。課（`section`）は付けない。
  経費精算が申請者の所属**部**を付けている既存規約の踏襲
- **「全社共通」は既に存在する**（`departments` code `00`・部長も課も持たない）。新設は不要で、使われていなかっただけ

### BS を「付けない」ではなく「任意」にした理由

当初案は「BS 科目には付けない」だったが、実データで**資産 12 行・負債 11 行に既に部門が入っている**
（経費精算が仮払消費税・未払金まで含む全行に部門を入れているため）。
厳格に「付けない」とすると既存挙動を壊し、総勘定元帳で未払金を部門絞り込みしていた経路も後退する。
**必須にするのは損益科目だけ、BS は任意**とすれば壊すものが無く、部門別 P/L の目的は達せる。

### 部門別 BS を目指さない理由

部門別 P/L は部門が欠けていても「(部門未設定)」に出るだけで他部門の数字は読めるが、
**部門別 BS は 1 行でも欠けると資産合計 ≠ 負債・純資産合計になり、帳票として成立しない**。
中途半端が許されない。そして中小 IT 企業に「開発1部の現金」「開発1部の普通預金」という概念は無く、
口座を部門別に分けてもいない。部門別に見たい BS 項目は実質**固定資産**と**売掛金・買掛金**だけだが、
**このアプリはその 2 つを仕訳の部門に頼っていない**——固定資産は固定資産台帳の部門欄、
売掛残高は請求書の部門（`ReceivableBalance.Query.sql` は `invoices.department_id` で絞っている）。

部門別 BS が欲しくなったら「BS 行にも部門を必須にする」だけなので、後戻りにはならない。

## 決定 2: 部門の決め方は三段。経路によって挙動を変える

判断基準は「**その場に人間がいて、部門を知っているか**」の一点。

| | 経路 | 挙動 |
|---|---|---|
| **① 人が画面にいる** | 入出金起票・振替伝票・仕入先請求書・銀行の一括起票 | **エラーで止める**（損益科目の行のみ必須） |
| **② 機械的に決まる** | 経費精算（申請者の部）・検収/請求（伝票の部門）・SES/定期請求（契約の部門）・償却（資産の部門） | **自動で入れる**。ここでエラーを出すと業務が止まる（人は既に画面を離れている） |
| **③ ②で解決できない残り** | 元データに部門が無い場合 | **全社共通で補完し、結果表示で明かす** |

これは税区分で既に採っている構造（各経路が明示 → 科目マスタの既定 → `MarkRemainingLinesOutOfScope()` の保険）
と同じ形で、コードの型も揃う。

**③の自動補完には「入れ忘れに気づかない」副作用がある**（全社共通が不自然に膨らんでも誰も気づかない）。
補完したときは結果表示に出す（例:「部門未指定の 2 行を全社共通で計上しました」）。

### 収益側も同時に埋める

費用だけ埋めると「費用は正しいのに売上が歪む」部門別 P/L になり、かえって誤読を生む。
SES 精算・定期請求・検収/請求の**売上行**に部門を入れるところまでを 1 セットにする。
ADR-0029 で用意した伝票の部門欄が、仕訳生成時に明細へ転記されていないだけの可能性が高い（実装時に確認）。

## 決定 3: `journal_lines.department_id` を NOT NULL にする

「**損益科目の行だけ NOT NULL**」は列制約では書けない。判定に `accounts.account_type` が要るが、
**SQLite の `CHECK` 制約はサブクエリを書けない**ためである。選択肢は 2 つあった。

| 案 | 中身 | 判断 |
|---|---|---|
| **A（採用）** | `department_id` を**全行 NOT NULL** にし、意味を持たない行には「全社共通」を入れる | 税区分と完全に同じ形。列制約 1 つで済み、DB を替えても移植できる |
| B | トリガーで「損益科目なら NOT NULL」を強制 | 条件は正確に表現できるが DB 依存。ADR-0041 でトリガーを使っているので禁じ手ではないが、A で足りる |

A を採る。決定 1 の「BS は任意」は、この場合**「UI では入力を求めないが、保存時に全社共通で埋まる」**を意味する。

**DB 制約は「入力を促す」役目を果たさない。** NOT NULL にすると全部が何かで埋まるので、
「全社共通を選んだ」のか「入れ忘れて埋まった」のかは DB から区別できなくなる。
**決定 2 ①のエラーとセットでないと意味がない**——制約は壊れたデータを入れないための保険、
入力の正確さは UI の責任、という分担である。

### 既存データの移行

`NOT NULL` 化には既存 `NULL` の解消が前提なので、**遡及補正は必須**（当初は「やらない」としていたが撤回する）。

- `ddl/` にマイグレーションを追加し、既存の `department_id IS NULL` を**全社共通**に寄せる
- 金額は 1 円も動かないが、**予実対比の「(部門未設定)」行が消えて全社共通に移る**。
  E2E の 06_案件・経営管理／09_帳票検証の該当箇所を追随させる

## 決定 4: 確定済み伝票でも「部門・案件」は編集可にする（摘要は不可）

| 項目 | 確定後 |
|---|---|
| 日付・勘定科目・金額・貸借・税区分 | **ロック維持**（訂正は赤黒訂正） |
| **部門・案件（プロジェクト）** | **編集可** |
| 摘要 | **ロック維持**（本 ADR のスコープ外） |

### なぜ部門・案件だけ緩めてよいか

**部門と案件は仕訳の構成要素ではない。** 複式簿記の仕訳を成立させるのは 日付・勘定科目・金額・貸借 で、
部門と案件は「その仕訳をどう分類して見たいか」という**分析の軸**にすぎない。
証拠として、**部門や案件を後から変えても BS・PL・試算表・消費税集計表は 1 円も動かない**。
動くのは部門別 P/L・案件損益・予実対比だけである。財務諸表が不変な項目を後から直せることは、
帳簿の信頼性を損なわない。

**摘要は違う。** 摘要は取引の内容を示す**法定帳簿の記載事項**であり（消費税の仕入税額控除では
「相手方の氏名・年月日・内容・金額」の帳簿記載が要件）、自由に後から書き換えられると
**証憑と帳簿の整合を後付けで作れてしまう**。本アプリは行レベルの変更履歴を持たない
（`journal_lines` に更新者・更新日時の列が無い）ので、**履歴なしで摘要だけ書き換え可能にするのは
最も危ない組み合わせ**になる。摘要の訂正は赤黒訂正で足りる。

### そもそもこの機能が無いと部門の必須化が運用に耐えない

決定 3 で既存行を全社共通に寄せ、決定 2 ③で自動補完も全社共通に落とす。つまり
**「本当は開発1部なのに全社共通で記帳された行」が必ず生まれる。**
直す手段が赤黒訂正しかないと、部門だけの誤りのために伝票を 2 本増やし、
財務諸表に何の影響もない訂正で帳簿が膨らむ。**この機能があるからこそ
「まず全社共通で埋めて、後から精度を上げる」という移行が成り立つ。**

### 市販ソフトとの関係

市販ソフト（弥生会計・freee・マネーフォワード・勘定奉行）は**確定後の仕訳を全項目修正できる**。
日本の会計ソフトは**修正主義**（帳簿を直接直す）が主流で、制限は「期間の締め・決算確定」「権限設定」
「電子帳簿保存法の優良な電子帳簿を適用する場合の訂正・削除履歴の保存」でかける。

つまり **ADR-0026 の「確定済みは一切編集不可」は市販ソフトより厳しい**。
本決定は「市販ソフトに無い機能を足す」のではなく、**行き過ぎた厳しさを筋の通る範囲で 1 段緩める**ものである。

### 条件

1. **締め済み期間はロック**。月次締めは「部門別 P/L を確定して配った」という意味を持つため、
   締めた後に部門が変わると配布済みの報告と食い違う。直すなら期間を再オープンする（既存の規律と一貫）
2. **経理のみ**（他の会計操作と同じゲート）
3. **変更ログは持たない**。金額にも科目にも履歴が無いのに部門にだけ履歴があるのは構造としていびつで、
   全項目の履歴は電帳法対応として別途まとめて検討する

### 監査証跡はヘッダの更新者・更新日時で足りる

`Creator` / `CreatedAt` / `Updater` / `UpdatedAt` は CLB の**予約名のシステムフィールド**で、保存時に自動セットされる。
実データを見ると、**76 伝票のうち `created_at ≠ updated_at` は 5 本だけ**で、
5 本とも「振替伝票を**下書き保存 → あとで確定**した」ものだった（自動起票の 60 本以上は一度も更新されていない）。
つまり `updated_at` は現状すでに「**人が手で介入した印**」として機能しており、
部門・案件の編集をそこに載せても意味が一貫する。

**限界（許容する）**: 変更前の値は残らない。`updater` は「最後に触った人」で上書きされるため、
下書きを確定した人の情報は消える（ただし `creator`＝起票者は残るので責任の所在は追え、
現状も「確定した人」は保持していないので新たに失うものはない）。

**あわせて、伝票詳細に「最終更新: 2026-08-14 15:30 山田太郎」を表示する。**
今は DB にあるだけで画面から見えないため、記録が意味を持つようにする。

## 採らなかった案

- **`NULL` のまま「(部門未設定)」で可視化を続ける**: 「全社共通のつもり」と「入れ忘れ」が区別できない状態が続く。
  ADR-0052 で税区分について否定した表現を、部門にだけ残す理由がない
- **一律で自動補完する（エラーを出さない）**: 人が画面にいる経路まで補完すると、
  全社共通が膨らんでも誰も気づかない。入力の正確さは UI が担うべき
- **一律でエラーにする**: 経費精算・償却など人が画面にいない経路で業務が止まる
- **摘要も編集可にする**: 法定帳簿の記載事項であり、行レベルの変更履歴が無い現状では危険
- **BS 科目にも部門を必須にする**: 部門別 BS を作らない限り実益がなく、入力コストだけが増える

## 実装時に確認すること

1. **子リスト（明細）だけを変更したとき、親レコードの `UPDATE` が走るか。**
   仕様書は「保存時に自動セット」と書いているが、親の値が 1 つも変わらない場合に
   親行の `UPDATE` が発行されるかは書かれていない。走らなければ `updated_at` が動かず決定 4 の前提が崩れる。
   **実測で確認する**（走らない場合は保存時にスクリプトで `UpdatedAt` を明示代入する等で対応）
2. **確定済み伝票でフィールド単位に編集可否を分けられるか。** 現在は `this.IsViewOnly = true` で丸ごとロックしている。
   分けられない場合は、専用の「部門の後付け」画面（部門が全社共通の行を検索して一括で振り分ける）にする——
   既存 100 行超の振り分け作業にはむしろそちらが便利なので、最終的には両方あってもよい
3. **売上行に部門が載っていない原因**（伝票の部門欄が明細へ転記されていないだけか、そもそも欄が無いか）
