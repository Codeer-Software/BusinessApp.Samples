# ADR-0067 マージコミットは、木がブランチ先端と同じなら木から決まる段を流さない

## 状況

**git はマージが自動でコミットするとき `pre-commit` を呼ばない。**
置かないと「`main` に入る瞬間だけ、どの段も通らない」ので、2026-08-27 の自己レビューの指摘で
`pre-merge-commit` を置き、**同じ段へ丸ごと委譲**していた（[tools/README](../../tools/README.md)）。

**2026-09-20 に開発者が問うた**（逐語）——

> コミット前フックは必要ですが、マージコミット前には走らさなくてもいいと思いますが、どうでしょうか。
> なぜなら、作業ブランチにおける最終コミット時点でのチェックと同じだと思うからです。
> （マージコミットの途中で編集を行わない限り。）

**Claude が 2 つ実測した**（2026-09-20）。

- **フックの所要は全段で 382 秒**。うち**ミューテーションが 302 秒**（79%）で、
  残りの段は合計 80 秒である（内訳は [tools/README](../../tools/README.md) の段の表の順）
- **`main` から辿れるマージ 154 本のうち、150 本（97.4%）は「マージコミットの木」と「取り込んだブランチ先端の木」が同一**だった。
  **違ったのは 4 本**で、内訳は **`main` が先へ進んでいた合流が 2 本**（`7b13349d`・`4c43a891`）と、
  **`main` は先祖なのに木が違うもの**（＝**マージコミットの中で編集している**）**が 2 本**（`33f2ff82`・`03e142e3`）である

**つまり開発者の読みは 97.4% で正しく、例外は実在した。**
そして**同じか違うかは、`pre-merge-commit` が 2 つの木を比べれば判定できる**（[30 §9](../30_作業のルール.md) の表で、成果物を自動で検査する仕組みが最も強い置き場）。

**本書の 2 つの語。** **木**＝git の tree（そのコミットに入るファイルの中身の全体）。**木から決まる段**＝入力が木の中身だけで決まる段
（lint・テスト・ミューテーション等。`migrate.ps1 -Verify` は稼働 DB を読むので違う）。**軽い経路**＝木から決まる段を飛ばして
`migrate.ps1 -Verify` だけを流す側。

## 決定

**開発者の決定**（2026-09-20。発端は上の開発者の問いで、Claude の案を開発者が採った。実装は 2026-09-21）。
**Claude の読み**——検査を 1 つ外すわけではない（`pre-commit` の段は変わらない）が、機械が見る契機を減らす向きなので
[34 §1](../34_開発者とClaudeの分担.md) の 8「品質測定基準を下げる決定」に当たると読み、開発者に諮った。[34 §1-3](../34_開発者とClaudeの分担.md) の箇条で型が近いのは「全件を流す契機を減らす」である。

1. **`pre-merge-commit` は、これからコミットする木（`git write-tree`）と、取り込むブランチ先端の木を比べる。**
   **先端は `GITHEAD_<sha>` 環境変数から取る**——**`MERGE_HEAD` はこのフックからは見えない**（下の帰結）
2. **同じなら、木から決まる段を流さない。** そのブランチの最終コミットの `pre-commit` が、**同じ木を全段で検査済み**だからである
3. **違うなら全段を流す。判定できないときも全段へ倒す**——**取り込む先端を 1 つに決められない**（`GITHEAD_*` が 0 個・2 個以上）・
   **これからコミットする木を書けない**・**先端の木を引けない**の 3 つがそれに当たる。**判定できないものを「同じ」に倒さない**
4. **木が同じでも `migrate.ps1 -Verify` だけは流す。** **稼働 DB は木の中に無い**ので、
   ブランチの最終コミットから時間が空くとずれうる（[ADR-0064](0064-稼働DBのスキーマはmigrateだけで動かし適用の記録はコミットごとに突き合わせる.md) の「コミットごとに突き合わせる」を保つ）
5. **飛ばしたときは、何を飛ばしたか（段の一覧の在り処）・かわりに流す段・2 つの木のハッシュを印字する。**
   **黙って飛ばさない**——「守っている」と書いたフックが守っていない状態は、カバー率ではなく**報告が偽**である（[30 §4-1](../30_作業のルール.md)）

## 理由

- **重複が 97.4% で、重い段がその 79% を占める。** 浮く時間は 1 マージあたり約 6 分である
- **このフックが見る例外は 2 本である**（`7b13349d`・`4c43a891`。**`main` が先へ進んでいた合流**）。
  **状況節の 4 本のうち残り 2 本は、このフックを通らない**（帰結）。**この 2 本では、どの親の木でもない木が履歴に入る**
  ——リンク切れ（`lint_docs.py`）や、別々のブランチで足したテストと DDL の噛み合わせは、**そこでしか見えない**
- **「`main` が先祖か」ではなく、木そのものを比べる。** **木が同じことが、そのまま「同じ木を全段で検査済み」という根拠になる**
  ——先祖関係からその根拠へ至るには、**どの経路でその木ができたか**を推論しなければならない

## 検討したが採らなかった案

| 案 | 採らない理由 |
|---|---|
| **一律に `pre-merge-commit` を外す**（`pre-commit` へ委譲しない） | **`main` が先へ進んでいた合流の 2 本が素通りになる**（実測で 154 本中 2 本＝1.3%）。**残り 2 本は `pre-commit` が受ける**ので素通りしない |
| **「`main` が先祖なら飛ばす」で判定する** | **結論は木の比較と同じになるが、根拠が間接になる**——「先祖だから木も同じはず」は、**マージの中で編集していない**ことを前提にした推論である。木を比べればその推論が要らない |
| **検査済みの木の台帳を持ち、木が台帳にあるときだけ飛ばす** | **作り込みすぎ**（[30 §4-1](../30_作業のルール.md) の 70〜80% の側）。台帳なら「その木が `pre-commit` を通った」と言えるが、rebase・cherry-pick・`--no-verify` の先端を作らないのは [30 §7](../30_作業のルール.md) の規則の側で守っている。**その規則が破られたときに拾えなくなる**ことは、下の帰結に書いて引き受ける |

## 帰結

- **`pre-merge-commit` は委譲だけの 2 行ではなくなる。** 段の正典は [tools/README](../../tools/README.md) のままで、
  **軽い経路に何が残るか**（`migrate.ps1 -Verify` だけ）**も同じ表の下が持つ**
- **取り込む先端は `GITHEAD_<sha>` で決まる。`MERGE_HEAD` は使えない**——**git がこのフックを呼ぶ時点では書かれていない。**
  **git が `MERGE_HEAD` を書くのは「マージが止まったあと」**（衝突・`--no-commit`・**フックが拒んだとき**）で、
  **止まったマージを締めくくる `git commit` は `pre-commit` が受ける**（全段が流れる）。
  **衝突したときは、このフックがそもそも呼ばれない**（git がそこで止まる）。
  **`GITHEAD_*` は git がマージ戦略へ渡すもので、`githooks(5)` の約束ではない。** 渡されなくなれば 0 個になり、**安全側（全段）へ倒れる**。
  **上の状況節が数えた「マージコミットの中で編集した 2 本」（`33f2ff82`・`03e142e3`）は、この `pre-commit` の側の経路である**
  ——**このフックは通らない**（だから決定 3 の「違うなら全段」に、その形は現れない）
- **`MERGE_HEAD` で判定していた初版は、本物のマージでは軽い経路へ一度も入らなかった**
  （2026-09-21 の実装から 2026-09-22 に直すまでの 2 マージ——`da43ebf9`・`3485fa86`——は、
  木が同一なのにどちらも全段の 382 秒を流した。**実装日の clone で軽い経路を通したのは、手で `MERGE_HEAD` を置いて直接呼んだときだけ**である）。
  **壊れていたのは判定の入口**（`MERGE_HEAD` の行数を数えていた）**で、それを見逃したのは自己検査の作り方**である
  ——検体を `git merge --no-commit` で作って**このファイルを直接呼んで**いた。**それは git がこのフックを呼ばない経路**で、
  `MERGE_HEAD` があるのもその経路だけだったので、**壊れていることを一度も言わなかった**
  （**型と実測は [qa/03 の L-63](../qa/03_テストで漏らした実例.md) が持つ**）
- **判定は `PRE_MERGE_COMMIT_EXPLAIN=1` で、何も流さずに印字だけさせられる。**
  **`EXPLAIN` はマージも止める**（軽い経路でも 0 を返さない）——**返すと、印字だけのつもりで撃ったマージが
  `migrate.ps1 -Verify` を飛ばしたまま成立する**。**スクリプト自身の終了コードは 全段=10／軽い経路=11 だが、
  `git merge` 経由で見えるのは git の 1** である。
- **自己検査（`PRE_MERGE_COMMIT_SELFTEST=1`）は、使い捨てのリポジトリで撃つ。**
  **本物の `git merge` に呼ばせる検体**（木が同一・`main` が先へ進んでいた合流・オクトパス・衝突）と、
  **git には作れないので写しを直接呼ぶ検体**（マージの外・先端の木を引けない）、
  **隔離**（下）と**ハーネスの対照実験**からなる。**撃った検体は名前で釘付けする**（数で数えない）。
  **経路だけでなく、そこへ倒れた理由の字も見る**——**理由を見ないと、別の理由で全段へ落ちていても緑になる**（それが初版の壊れ方である）。
  **コミット前フックの「失うことを止める道具の自己検査」の段が毎回流す**
- **自己検査は、外側のマージから引き継いだ `GITHEAD_*` と git のローカル環境変数を落としてから撃つ。**
  **全段へ倒れたマージは `exec` で `pre-commit` を起こし、`pre-commit` はこの自己検査を流す**——
  `exec` は環境を保つので、落とさないと内側の検体が「外側の 1 個＋内側の 1 個」を見て**全件赤になり、マージが止まる**
  （2026-09-22 に実測。自己レビューの指摘で見つかった。検体「隔離」が見張る）
- **軽い経路が `migrate.ps1 -Verify` を実際に流して緑になるのは、この直しを `main` へ取り込むマージが最初である。**
  **自己検査は `EXPLAIN` で撃つので、そこには到達しない**（使い捨てのリポジトリには稼働 DB も `LocalEnvironment.md` も無い）。
  **到達しない 2 行**——`migrate.ps1 -Verify` の実行と、全段へ倒れたときの `pre-commit` への委譲——は、
  **字が在ることだけを検体で見ている**（消されたときに黙らないため）
- **失うもの**: rebase の衝突解決・cherry-pick・revert・am・`--no-verify` で作られたブランチ先端は `pre-commit` を通っていない。
  これまではマージの全段がその唯一の網だったが、木が同じなら今後は当たらない。**それらを作らないのは [30 §7](../30_作業のルール.md) の規則が守る**
- **[30 §7-1](../30_作業のルール.md) の条件 6（機械的検証が全部通っている）の意味は変わらない。**
  **Claude の読み**（開発者未承認。30 §7-1 の末尾に同じ断りで置いてある）——
  **条件 6 は、ブランチの最終コミットで全段が通っていることを指す。** マージはそれを配るだけである
- **コミットの側（`pre-commit`）は 1 段も緩めていない。**
