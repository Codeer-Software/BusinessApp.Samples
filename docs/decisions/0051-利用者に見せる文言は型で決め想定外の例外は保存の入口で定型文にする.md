# ADR-0051 利用者に見せる文言は型で決め、想定外の例外は保存の入口で定型文にする

> **2026-09-10 追記**: 帰結の「トーストの 2 枚出しは閉じない——開発者に諮る」は同日に閉じた。**2 枚のまま受け入れる**
> （開発者の基準に Claude の見積りを当てた。決定は [21 §2-6](../21_画面の原則.md)）。本文は当時のまま。

## 状況

保存の関門（[ADR-0008](0008-CLBとCSharpライブラリの責務分担.md)）は差し戻しを例外で投げ、ホストの例外ハンドラ
（`UseExceptionHandlerSendToFront`）が `Message` をそのまま HTTP 500 の本文にして、CLB がトーストに出す。
例外ハンドラは**型を見ない**ので、関門の外で起きた `InvalidOperationException` の「仮 ID … に本物の ID が 2 つ対応している」
「仕訳 … が見つからない」も同じ経路で利用者に届く（[qa/02 R57-35](../qa/02_自己レビュー記録.md)）。
読めない型（`UnreadableFieldException`）だけは入口（`AccountingSubmitPipeline`）が定型文に差し替えていたが、
それ以外の例外は野放しだった。文言の中身を見て「利用者向けか」を判定することはできない。

**この回で分かったこと**（2026-09-10 実測 1.3.20。[qa/01 F-42](../qa/01_CLB静かな失敗.md)）。差し戻しに 2 枚のトーストが出る
（関門の文言に CLB の「更新に失敗しました」が続く。[qa/02 R25-08](../qa/02_自己レビュー記録.md)）のは、
**例外で返すか結果で返すかではなく、画面のボタンの種類で決まる**——標準の `SubmitButtonFieldDesign`（「下書き保存」「登録」）は
自分の定型文を重ね、スクリプトの `this.Submit()` / `this.Delete()`（「計上する」「削除」）は重ねない。
2026-09-02 の記録（[qa/04](../qa/04_実機操作テスト.md)）が「計上するは関門の文言だけ、取引先の登録は 2 枚」と書いていたのが、その事実だった。

## 決定

**Claude の判断（2026-09-10）。開発者は未承認。**

### 1. 利用者に見せてよい文言かどうかは型で決める

`BusinessApp.ServerSupport` に基底 **`RejectedException`** を置き、利用者に見せてよい差し戻しはすべてこれの派生にする
（仕訳・マスタ・自社情報・取引先・登録番号の全 5 種。規約テスト `RejectedExceptionConventionTests` が 2 部品の例外の派生を全数取って、
基底に乗っていることを確かめる）。

### 2. 保存の入口は、差し戻し以外の例外を定型文に差し替える

`AccountingSubmitPipeline.SubmitAsync` は **`RejectedException` はそのまま投げ、それ以外の例外はすべて `SaveFailureMessage.Text`
（定型文）の `InvalidOperationException` に差し替えて原文をログへ回す**。読めない型・DB の生の失敗・`ArgumentNullException` も同じ。
入口の引数の欠けだけは、関門に入る前に `ArgumentNullException` で止める（呼び手の誤り）。

### 3. 差し戻しは例外のまま CLB へ渡す（結果で返す形は採らない）

`ModuleSubmitResult.ExceptionMessage` に文言を載せて返す形も動く（CLB はその保存で書いた分を巻き戻す。実測）が、採らない。
理由は「検討したが採らなかった案」に書く。

## 理由

- **型で線を引けば、関門を足す人が「画面に出る文言か」を毎回考えなくてよい。** 差し戻しは基底に乗せる、それ以外は何を投げても定型文になる
- **入口の 1 か所で差し替えれば、関門ごとに置き場所を考えなくてよい**（`SaveFailureMessage` を入口に置いたのと同じ理由）
- **例外で巻き戻す形は、CLB にもテストにも共通の前提**である。`DbTransactionScope`（Web API の経路）も、テストの土台（`AccountingServer.SubmitAsync`）も、
  例外で巻き戻る前提で組まれている（58 本のテストがそれを表明している）

## 帰結

- 開発者向けの例外文言が画面に出る経路は、保存の入口から消える（R57-35 を閉じる）。Web API の経路は、画面のスクリプトが
  200 以外を定型文にする（`JournalEntry.mod.cs` の `Amend`。[qa/01 K-01](../qa/01_CLB静かな失敗.md)）ので、もともと出ない。
  Web API の経路は決定 2 の外（[ADR-0016](0016-画面から呼ぶサーバ処理はWebAPIに置く.md) が持つ。`JournalAmendmentEndpoint` が
  捕まえるのは `JournalPostingRejectedException` だけで、他の部品の差し戻しがこの経路に乗った日に基底で受ける形へ広げる）
- **トーストの 2 枚出し（R25-08）は閉じない。** 原因が分かった——標準の `SubmitButtonFieldDesign` の仕様である。
  アプリ側の手は「標準の保存ボタンをやめ、スクリプトのボタンで `ValidateInput()` → `Submit()` する」（「計上する」と同じ形）だが、
  画面の作りの決定なので開発者に諮る（[04 §5](../04_実装計画と現在地.md)）。CLB 側へは [FB-017](../CLB改善提案/01_機能改善提案.md)
- 定型文の経路（想定外の例外）は画面から踏めないので、テストだけが守る（`AccountingSubmitPipelineTests`）

## 検討したが採らなかった案

- **差し戻しを `ModuleSubmitResult.ExceptionMessage` で返す**——一度実装して自己レビューで戻した（[qa/02 ラウンド 71](../qa/02_自己レビュー記録.md)）。
  ① トーストは 1 枚にならない（枚数はボタンで決まる。「計上する」で 1 枚だったのは以前からで、実測 1 回を別のボタンに一般化した誤り——
  [qa/03 L-43](../qa/03_テストで漏らした実例.md)）。② 巻き戻しを「CLB が結果を見て巻き戻す」という CLB 固有の挙動に頼ることになり、
  例外で巻き戻す前提のテストと本番の機構が食い違う（qa/03 L-05・L-10 の型）。③ `DbTransactionScope` で包んで呼ぶと差し戻しが確定する罠になる
- **ホストの例外ハンドラで型を見て差し替える**——ハンドラはカバレッジにもミューテーションにも載らない（[ADR-0012 §3](0012-テスト方針とカバレッジのゲート.md)）。
  差し替えの規則を検査の外に置くことになる
- **関門が例外ではなく結果を返す形に書き直す**——全関門と数百のテストが例外で組まれている
