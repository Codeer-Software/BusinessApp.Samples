# 会計ドメイン設計

> **複式簿記の正しさはこの文書で担保する。** 実装より先にここを確定させる。
> 消費税の計算設計は [06_消費税設計](06_消費税設計.md) に分けてある。

## 1. 不変条件（P0。すべて自動テストで検査する）

会計コアが常に守る性質。破れたら製品として成立しない。

| # | 不変条件 |
|---|---|
| I-01 | 計上済み仕訳は、伝票単位で借方合計＝貸方合計 |
| I-02 | 計上済み仕訳の全体でも借方合計＝貸方合計 |
| I-03 | 仕訳明細は、有効な会計期間に属する |
| I-04 | 締め済み期間に、仕訳を計上・訂正・取消できない |
| I-05 | 計上済み仕訳は、変更も削除もされない（レコードが不変） |
| I-06 | 訂正・取消は、原仕訳を一意に特定する情報を持つ |
| I-07 | 元帳の残高＝当該科目の仕訳明細の集計（残高キャッシュを持たない） |
| I-08 | 試算表・B/S・P/L・部門別 P/L は、同じ仕訳集合から再現できる |
| I-09 | 部門別 P/L の全部門合計＝全社 P/L |
| I-10 | B/S の当期純利益＝P/L の当期純利益 |
| I-11 | 期首残高は貸借一致し、B/S 科目のみで構成される |
| I-12 | 翌期首残高＝前期末残高（繰越後） |
| I-13 | 損益科目の仕訳明細には部門がある |
| I-14 | 同一の外部伝票を二重に計上しない（冪等性キーで一意） |
| I-15 | 税集計は、対象の仕訳明細へドリルダウンできる |
| I-16 | 制度ルールの版を変えても、過去の仕訳の計算結果は変わらない |
| I-17 | 伝票番号は欠番を埋め直さず、再利用しない |

## 2. 日付を 1 つに潰さない

会計では「日付」が複数ある。1 つの列にまとめると、必ずどこかで意味が壊れる。

| 概念 | 意味 | 誰が決めるか |
|---|---|---|
| **取引日**（`transaction_date`） | 取引が行われた日。帳簿の「取引年月日」 | 利用者 |
| **計上日**（`posting_date`） | 会計期間への帰属を決める日。通常は取引日と同じ | 利用者（既定は取引日） |
| **入力年月日**（`entered_at`） | システムに記録された日時。**利用者は変更できない** | システム |
| **課税仕入れの時点**（`tax_point`） | 消費税の経過措置・税率の判定基準日。役務は完了日、資産は引渡日 | 利用者（既定は取引日） |
| **証憑日** | 請求書等の日付。会計コアは参照キーとして持つのみ | 外部 |

**入力年月日は「通常の業務処理期間の経過後の入力の事実を確認できる」という優良な電子帳簿の要件
（規則 5 ⑤一イ(2)）そのもの**であり、取引日とは絶対に共用しない。

## 3. 金額の持ち方

- **`decimal` を使う。浮動小数点を使わない**（CLB スクリプトの数値も `decimal` に統一される）
- **金額は整数円**。円未満は端数処理の結果としてのみ発生し、保存時には整数
- 仕訳明細は **借方／貸方を符号ではなく区分で持つ**（`debit_credit`）。金額は常に正
- 税抜経理なので、本体行の金額は**税抜**。消費税額は**税行**として別明細に持つ（[06](06_消費税設計.md)）

## 4. 仕訳のモデル

### 4-1. 構造

```
journal_entries（伝票ヘッダ）
├── id                     PK
├── entry_no               伝票番号（計上時に採番・不可逆・一意）
├── transaction_date       取引日
├── posting_date           計上日（会計期間の決定に使う）
├── fiscal_period_id       FK → accounting_periods
├── status                 draft | posted
├── entry_type             normal | correction | reversal | opening | closing | carryover
├── original_entry_id      FK → journal_entries（訂正・取消のとき必須）
├── description            摘要
├── partner_id             FK → partners（伝票単位の取引先。明細で上書きできる）
├── source_component       投入元の部品名（手入力は null）
├── source_document_id     元伝票を特定する情報
├── idempotency_key        外部投入の重複防止（UNIQUE）
├── entered_at             入力日時（システム自動・変更不可）
├── posted_at              計上日時（システム自動・変更不可）
└── creator / updater      CLB のシステム予約名

journal_lines（仕訳明細）
├── id                     PK
├── journal_entry_id       FK → journal_entries
├── line_no                行番号
├── debit_credit           debit | credit
├── account_id             FK → accounts
├── sub_account_id         FK → sub_accounts（任意）
├── department_id          FK → departments（損益科目では必須）
├── partner_id             FK → partners（明細単位。帳簿の法定記載事項①）
├── partner_name_snapshot  取引先名の写し（検索と法定記載事項のため）
├── amount                 金額（税抜・正の整数）
├── tax_category_id        FK → tax_categories
├── tax_treatment          税区分の用途区分（課税売上対応 / 共通対応 / 非課税売上対応）
├── tax_point              課税仕入れの時点
├── applied_rule_version   適用した制度ルールの版
├── is_tax_line            消費税行か
├── parent_line_no         税行が対応する本体行
├── item_description       資産又は役務の内容（帳簿の法定記載事項③）
├── book_only_deduction    帳簿のみ保存で控除する類型（該当する場合）
└── evidence_ref           証憑を特定する情報（証憑部品への参照キー）
```

### 4-2. なぜ取引先を明細に「名前の写し」ごと持つのか

消費税法 30 ⑧の帳簿の法定記載事項（相手方の氏名又は名称・年月日・資産又は役務の内容・支払対価の額）は
**仕訳明細が満たす**必要がある。また優良な電子帳簿の検索要件は「取引先」を検索条件にできることを求め、
**検索項目に値がない（空白）レコードを検索できること**まで含む（通達 4-9）。

マスタへの FK だけだと、取引先の改名で過去の帳簿の記載が変わってしまう。
**FK（現在の取引先を指す）と名前の写し（そのときの記載）を両方持つ**。

### 4-3. 帳簿間の相互関連性

優良な電子帳簿の要件（規則 5 ⑤一ロ）。**伝票番号（`entry_no`）を一連番号として全帳簿で共有**し、
仕訳帳 ⇔ 総勘定元帳 ⇔ 補助簿 ⇔ 固定資産台帳を相互に辿れるようにする。

集計転記をする箇所（決算振替など）は、摘要に**集計対象と集計範囲**（対象・期間・条件）を記録する。

## 5. 訂正モデル

[ADR-0004](decisions/0004-優良な電子帳簿への準拠と仕訳の不変性.md) の具体化。国税庁の通達 8-9 が示す
「直接訂正・削除できないシステム＋反対仕訳」方式を採る。

| 状態 | できること |
|---|---|
| `draft` | 自由に編集・削除できる（まだ帳簿ではない） |
| `posted` | **変更・削除できない**。訂正・取消のみ |

| 操作 | 生成されるもの |
|---|---|
| **取消** | 原仕訳の貸借を反転した `reversal` 伝票 1 本。`original_entry_id` に原仕訳 |
| **訂正** | `reversal` 伝票 ＋ 正しい内容の `correction` 伝票。どちらも `original_entry_id` を持つ |

- 反対仕訳の作り方は**総額方式**（貸借を入れ替える）を採る。
  純額方式・同一科目のマイナス金額も法令上は認められるが（一問一答 問26）、
  総額方式が最も読みやすく、集計時の符号の扱いが単純になる
- **7 日以内の訂正は履歴を残さなくてよいという緩和（通達 8-10）には依存しない。**
  常に履歴を残す。緩和には内部規程とシステムの両方が必要で、条件の管理コストが利益を上回る
- 表示上は原仕訳・反対仕訳・再計上をグループにして見せてよいが、**データは畳まない**

## 6. 勘定科目

| 属性 | 内容 |
|---|---|
| コード | 4 桁。体系は資産 1xxx / 負債 2xxx / 純資産 3xxx / 収益 4xxx / 費用 5xxx〜 |
| **科目区分** | 資産・負債・純資産・収益・費用。**部門の要否判定と決算振替がこれに依存する**（必須） |
| 決算書表示区分 | B/S・P/L のどの区分に並べるか（流動資産／固定資産／売上高／販売費及び一般管理費 …） |
| 既定税区分 | 入力時の初期値。**「値が入っていない行の穴埋め」に使わない**（前回の実測で事故った） |
| 補助科目の要否 | 補助科目を持つ科目か |
| 現預金科目か | 出納帳・資金の集計に使う |
| 固定資産科目か | 固定資産台帳の計上先候補を絞る |
| **評価勘定か** | 減価償却累計額・貸倒引当金・売上値引戻り高・期末棚卸高のように、**通常残高が科目区分と逆**の科目。科目区分だけから借方残／貸方残を決めると必ず誤る |
| 有効／無効 | 入力候補に出すかどうか。**過去データの表示・検索は妨げない** |

補助科目は必ず 1 つの勘定科目に属する。**明細の補助科目が、その明細の勘定科目に属しているか**を
計上時に検証する（属していない補助科目を許すと補助元帳が壊れる）。

**科目区分と決算書表示区分は別物である。** 表示区分は「財務諸表のどこに並べるか」であって、
科目の性質ではない。台帳の対象や部門の要否は科目区分で判定する。

## 7. 会計期間と締め

```
fiscal_years（会計年度）
├── id / label（「第 18 期（2026 年度）」）
├── start_date / end_date
├── status         open | closed
└── premium_ledger_from   優良な電子帳簿の適用開始日

accounting_periods（月次期間）
├── id / fiscal_year_id
├── start_date / end_date（月初日・月末日）
└── status        open | closed
```

- **期間の解決は「対象日の月初日」で行わない。** 日付は `YYYY-MM-DD 00:00:00` に正規化して
  範囲比較する（[qa/01_CLB静かな失敗](qa/01_CLB静かな失敗.md) A-04）。
  前回プロジェクトが月初日方式で回避していた問題は、書式を正規化すれば発生しない
- 締めは**月次 → 年度**の順。締め前チェック（貸借不一致・下書きの残存・部門未設定・税区分未設定）を通す
- 再オープンは権限者のみ。**理由と実行者と日時を必ず記録**する
- **優良な電子帳簿は「課税期間の初日から」全帳簿で要件を満たす必要がある**（法 8 ④・令 2）。
  年度の途中から有効化できないので、`premium_ledger_from` が年度の開始日と一致しない場合は警告する

## 8. 期首残高と繰越

- 期首残高は**マスタではなくデータ**（[ADR-0006](decisions/0006-マスタの三層分類.md)）。
  科目・補助科目・部門の単位で持ち、**貸借一致を検証する**
- 導入初年度の期首残高は利用者が入力する。2 年目以降は繰越処理が生成する
- 繰越は「前期末の B/S 科目残高を翌期首へ移し、P/L 科目の残高を繰越利益剰余金へ振り替える」
- **前期を後から訂正したときのために、繰越は再実行できる**（暫定繰越）。
  前期を締めた時点で確定させる。暫定と確定を区別し、前期に変更があったら陳腐化を検知する

## 9. 部門

[ADR-0010](decisions/0010-部門は単一階層とし損益科目でのみ必須にする.md) のとおり単一階層。
「全社共通」を 1 件持つ。**損益科目の明細では必須、貸借科目の明細では任意。**

### 9-1. システム生成仕訳の部門付与ルール（実装より先に確定させる）

人が入力しない仕訳にも部門は要る。**後付けすると破綻する**ので、生成経路ごとにルールを定める。

| 生成経路 | 対象科目 | 部門の決め方 |
|---|---|---|
| 消費税行 | 仮払・仮受消費税等（B/S 科目） | **親行から引き継ぐ**（任意項目だが、税集計を部門別に見るために引き継ぐ） |
| 期首残高 | B/S 科目のみ | **不要**（損益科目が現れないため構造的に問題が起きない） |
| 決算振替（損益 → 繰越利益剰余金） | 損益科目 ＋ 純資産科目 | 損益科目側は**振り替える元の明細の部門を引き継ぐ**。純資産側は任意 |
| 繰越（翌期首残高の生成） | B/S 科目のみ | **不要**（期首残高と同じ） |
| 減価償却仕訳 | 減価償却費（損益科目） | **固定資産が部門を持つ**。台帳から引き継ぐ |
| 他部品からの投入 | 任意 | **投入元が指定する。** 損益科目に部門が無ければ検証で弾く（穴埋めしない） |

**「部門が空なら全社共通で埋める」保険を全経路に置く設計にはしない。** それは
「値が入っているのに意味がない」状態を作り、誰も気づかないまま部門別損益が嘘になる。
全社共通は**利用者が意図して選ぶ**ときだけ使う。

## 10. 他部品からの仕訳投入

会計コアが公開する唯一の書き込み経路。

- 投入元は `source_component` ＋ `source_document_id` ＋ `idempotency_key` を必ず付ける
- 会計コアは**投入された仕訳にも同じ検証を通す**（貸借一致・期間・部門・税区分）。
  「外部からだから信用する」経路を作らない
- 投入された仕訳も計上後は不変。訂正は反対仕訳による
