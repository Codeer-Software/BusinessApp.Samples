# 企画概要 — CLB 統合業務基盤アプリ「よろず（Yorozu）」

> 作成: 2026-07-05 / 更新: 2026-08-02（部品アーキテクチャ再編 ADR-0040/0041 反映）・2026-08-09（全ドキュメント現行化スイープ。ADR-0043/0044/0045/0046＝3軸分離・部課階層・ポータル本格化・案件の部長開放を反映） / 管理: Fable（Claude Code）
> 上位文書: ルート `CLAUDE.md`（ミッションブリーフ）。本書はそれを企画として具体化したもの。

## 1. 何を作るか

**ASP.NET + Codeer.LowCode.Blazor（CLB）製の、中小 IT 企業向け「全部入り」財務会計アプリケーション。**

複式簿記の仕訳から財務諸表（BS/PL）作成までを備えた市販会計ソフト（弥生会計・freee 等）の**代替**であり、さらに市販ソフトが弱い**プロジェクト別損益・受託×SaaS の売上管理**を統合した、IT 受託業に特化した会計基盤。

- 名称は **よろず（Yorozu）**。表示形は「**よろず - 統合業務基盤アプリ**」。万屋（よろずや）の「よろず」＝あらゆること・何でも扱う、の意で、**「全部入り」というミッションの芯と意味が一致する**（ADR-0047・2026-08-09）。ひらがな 3 文字で読み間違いがなく、会計にも営業にも購買にも寄っていないため部品が増えても名前が古びない。表記は**ひらがなを正**とする（カタカナ「ヨロズ」は自動車部品の上場企業と衝突するため使わない）。
  - 旧名称は **帳合（ちょうあい / Chōai）**。フェーズ A（会計コア）の段階で付けた会計用語で、守備範囲が業務全体へ広がった 2026-08-09 に改称した（経緯と退けた案は ADR-0047）。

## 2. なぜ作るか（CLB の売り込み）

このアプリ自体が CLB のセールス材料。伝えたいメッセージは2つ:

1. **「CLB はここまでできる」** — 会計という「堅い・複雑・正確性必須」の業務ドメインを、大半ノーコード（JSON/スクリプト/SQL）+ 少量の C# で実装できることの実証。
2. **「テンプレートとして御社で使える」** — 聴衆（=ソフトハウス）が自社の経理にそのまま導入でき、さらに「顧客案件のベースにできる」と感じる完成度。

### 訴求の設計

| 聴衆が見るもの | 感じてほしいこと |
|---|---|
| 仕訳入力〜試算表〜BS/PL が動く | 「会計コアが本当に動いている。デモ玩具ではない」 |
| プロジェクト別損益・工数原価 | 「うちの会社のこの痛みが解決される」（自分ごと化） |
| AI 領収書読み取り→仕訳提案 | 「新技術との統合も CLB 上で自然にできる」 |
| 実装の中身（JSON/スクリプト） | 「この規模でもコードはこれだけ？ 自社でも保守できる」 |

### 2.1 A×B 一体化モデル（ユーザーの言葉による芯・2026-07-05）

- **A＝会計コア（フェーズA）**は市販の財務会計専門ソフトに相当する部分で、**経理担当だけが触る**。
- **B＝業務フロー部分（フェーズB/B'）**は「市販ソフトが対応しにくい、会社ごとの業務フローに合わせたアプリ」。原課（営業部・開発部）が申請すると**金額や科目に応じて決裁権限者が変わる**ような部分で、**全社員が触る**。
- 市販ソフトでは A と B が分断される（B は Excel・紙・別システム）。**本アプリは A と B が一体化しており、B の業務が完了すると A に自動連携される**——これが CLB だからこそ作れる核心価値。
- 帰結として、A 部分は経理機能フラグ（HasAccountingAccess）を持つユーザー専用にゲートする（認可必須。→ 機能スコープ B-8、権限モデルの正典は `10_部品アーキテクチャ.md`）。

## 3. 到達目標

- **「これがあれば弥生会計や freee は要らない」と言えるレベル**（中小 IT 企業の実運用範囲において）。
- 共存・補助ツールではなく**代替**。複式簿記・消費税・月次/年次締め・固定資産・財務諸表まで含む。
- 加えて市販ソフトには無い管理会計（案件別損益・繰延収益・資金繰り予測）で「市販ソフト**以上**」を主張する。

## 4. スコープの骨格（詳細は `03_機能スコープ.md`）

- **フェーズ A**: 会計コア（科目・仕訳・元帳・試算表・BS/PL・消費税・締め・固定資産）
- **フェーズ B**: 周辺業務（取引先・経費精算＋承認・請求/入金・出納帳・予算・権限・通知。通知はその後、経費部品の持ち物から基盤=Shell/Notification へ昇格し全社通知基盤になった＝ADR-0045）
- **フェーズ B'**: IT 受託特化の管理会計（プロジェクト別損益・繰延収益・SES 稼働請求）
- **フェーズ C**: 差別化（AI 領収書→仕訳提案・資金繰り予測・インボイス番号照合）

## 5. 技術方針

- **可能な限り CLB**（モジュール JSON / スクリプト / SQL / クエリ / チャート）。C#/ASP.NET はサーバ経由 LLM・外部 API 等「CLB 単体で不可能な所」だけ。この比率自体が訴求。
- **税率・税区分・閾値・勘定科目はすべてマスタ化**し、税制改正に設定変更のみで追随（根拠: `research/2026-07_税制・会計制度リサーチ.md`）。
- 認証は既存の Cookie 認証（AppUser）を土台にする。権限は**3軸分離**（ADR-0043/0044）: ①機能権限＝`app_users` の**直接フラグ5本**（営業機能/経理機能/経費精算/工数入力/システム管理者。ユーザー管理画面のチェックボックスで編集）、②組織所属＝部課2階層の `departments`＋`department_members`、③承認構造＝課長/部長行からの **walk-up 解決**（自課の課長→部長へ自動繰上げ→経理代替）。部門メンバー行の増減は画面の見え方に影響しない（正典: `10_部品アーキテクチャ.md`）。
- DB は会計専用 SQLite を新設（→ `decisions/0001`）。

## 6. 成功条件（デモとしての完成の定義）

1. サンプル会社1期分のデータで、**仕訳入力→試算表→BS/PL が正しい数字で通る**（貸借一致・繰越整合）。
2. 経費申請→承認→自動仕訳→月次締めの一連の業務フローが**ログインユーザーの機能権限フラグ別に**動く（承認は自課の課長からの walk-up 解決）。
3. 案件別損益ダッシュボードが受託/SES/SaaS 混在で**「市販ソフトでは見えない数字」**を見せる。
4. AI 領収書読み取りが実キーで動き、「撮影→仕訳」の驚きを提供する。
5. 上記すべてが CLB デザイン（JSON+スクリプト）中心で、C# 拡張は少数ファイルに収まっている。
