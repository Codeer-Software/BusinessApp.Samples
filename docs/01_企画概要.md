# 企画概要 — CLB 財務会計アプリ「帳合（ちょうあい / Chōai）」

> 作成: 2026-07-05 / 管理: Fable（Claude Code）
> 上位文書: ルート `CLAUDE.md`（ミッションブリーフ）。本書はそれを企画として具体化したもの。

## 1. 何を作るか

**ASP.NET + Codeer.LowCode.Blazor（CLB）製の、中小 IT 企業向け「全部入り」財務会計アプリケーション。**

複式簿記の仕訳から財務諸表（BS/PL）作成までを備えた市販会計ソフト（弥生会計・freee 等）の**代替**であり、さらに市販ソフトが弱い**プロジェクト別損益・受託×SaaS の売上管理**を統合した、IT 受託業に特化した会計基盤。

- 名称は **帳合（ちょうあい / Chōai）**。江戸商人の「帳簿を突き合わせ勘定を合わせる」の意で、複式簿記の核心を指す言葉。主要会計製品との名称衝突が無いことを確認済み（2026-07-05 リサーチ。当初案 Ledgerix は海外サービスと衝突するため変更）。同音「寵愛」=愛されるアプリの掛詞。画面タイトル等はリソース化し変更容易にしておく。

## 2. なぜ作るか（CLB の売り込み）

このアプリ自体が CLB のセールス材料。伝えたいメッセージは2つ:

1. **「CLB はここまでできる」** — 会計という「堅い・複雑・正確性必須」の業務ドメインを、大半ノーコード（JSON/スクリプト/SQL）+ 少量の C# で実装できることの実証。
2. **「テンプレートとして御社で使える」** — 聴衆（=ソフトハウス）が自社の経理にそのまま導入でき、さらに「顧客案件のベースにできる」と感じる完成度。

### 訴求の設計

| 聴衆が見るもの | 感じてほしいこと |
|---|---|
| 仕訳入力〜試算表〜BS/PL が動く | 「会計コアが本当に動いている。デモ玩具ではない」 |
| プロジェクト別損益・工数原価 | 「うちの会社のこの痛みが解決される」（自分ごと化） |
| AI 領収書読み取り→仕訳提案 | 「新技術との統合も CLB 上で自然にできる」 |
| 実装の中身（JSON/スクリプト） | 「この規模でもコードはこれだけ？ 自社でも保守できる」 |

## 3. 到達目標

- **「これがあれば弥生会計や freee は要らない」と言えるレベル**（中小 IT 企業の実運用範囲において）。
- 共存・補助ツールではなく**代替**。複式簿記・消費税・月次/年次締め・固定資産・財務諸表まで含む。
- 加えて市販ソフトには無い管理会計（案件別損益・繰延収益・資金繰り予測）で「市販ソフト**以上**」を主張する。

## 4. スコープの骨格（詳細は `03_機能スコープ.md`）

- **フェーズ A**: 会計コア（科目・仕訳・元帳・試算表・BS/PL・消費税・締め・固定資産）
- **フェーズ B**: 周辺業務（取引先・経費精算＋承認・請求/入金・出納帳・予算・権限・通知）
- **フェーズ B'**: IT 受託特化の管理会計（プロジェクト別損益・繰延収益・SES 稼働請求）
- **フェーズ C**: 差別化（AI 領収書→仕訳提案・資金繰り予測・インボイス番号照合）

## 5. 技術方針

- **可能な限り CLB**（モジュール JSON / スクリプト / SQL / クエリ / チャート）。C#/ASP.NET はサーバ経由 LLM・外部 API 等「CLB 単体で不可能な所」だけ。この比率自体が訴求。
- **税率・税区分・閾値・勘定科目はすべてマスタ化**し、税制改正に設定変更のみで追随（根拠: `research/2026-07_税制・会計制度リサーチ.md`）。
- 認証は既存の Cookie 認証（AppUser）を土台に3ロール（一般社員／承認者／経理）+ 経営閲覧。
- DB は会計専用 SQLite を新設（→ `decisions/0001`）。

## 6. 成功条件（デモとしての完成の定義）

1. サンプル会社1期分のデータで、**仕訳入力→試算表→BS/PL が正しい数字で通る**（貸借一致・繰越整合）。
2. 経費申請→承認→自動仕訳→月次締めの一連の業務フローが**ログインユーザーのロール別に**動く。
3. 案件別損益ダッシュボードが受託/SES/SaaS 混在で**「市販ソフトでは見えない数字」**を見せる。
4. AI 領収書読み取りが実キーで動き、「撮影→仕訳」の驚きを提供する。
5. 上記すべてが CLB デザイン（JSON+スクリプト）中心で、C# 拡張は少数ファイルに収まっている。
