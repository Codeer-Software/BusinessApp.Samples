# 体験シナリオ 工数-02: 案件マスタの権限（一般=閲覧／部長=基本情報／経理=SES 条件まで・ADR-0046）

> 作成: 2026-08-09 ／ 所要時間: 約30分 ／ 影響: 案件 `a`（テスト残骸）の種別・SES 契約条件を一時変更／`PRJ-007` の有効フラグを一時 OFF／**開発2部の部門メンバーに director 行を一時追加**（承認ルートにも波及するため後片付け必須）。仕訳・工数は増えない
> 主役: **kaihatsu2_shinjin**（開発2部 第二課 一般 高橋健）→ **kaihatsu2_bucho**（開発2部 部長 加藤正雄）→ **soumu_bucho**（総務部 部長 山田太郎・経理）→ **admin**（システム管理者）。パスワードはユーザー名と同じ。
> 同じ 1 つの案件画面が、見る人によって「読むだけ」「基本情報だけ書ける」「全部書ける」に変わる。その境界を 4 視点で体験し、最後に**権限そのものを組み替えて**切り替わる瞬間を見る。

## 物語

案件マスタは、工数入力・SES 精算・案件損益のすべての入口にある共通マスタである。誰でも編集できてはいけないが、経理だけに閉じると現場が動けない。
そこで **ADR-0046** は「**基本情報は部長にも開き、損益に直結する SES 精算条件だけは経理に閉じる**」という線を引いた。
その線を、一般社員 → 部長 → 経理 の順に実際に触って確かめ、最後に admin が部門メンバーの役職行を 1 行足すだけで線が動くことを見届ける。

## 前提

| 項目 | 内容 |
|---|---|
| 書込条件（ADR-0046） | 案件（Project）の `UserWriteCondition` = **経理機能 ∨ 部長（`is_director`）**。読取は全員 |
| `is_director` の出どころ | **部門メンバーの「役職＝部長」行から DB トリガーで導出されるキャッシュ**。ユーザー管理のチェックボックスではない（機能権限とは別軸・ADR-0043） |
| SES 契約条件 5 項目 | `SES 月額基本料金` / `精算下限(h)` / `精算上限(h)` / `控除単価(円/h)` / `超過単価(円/h)`。**種別が SES のときだけ表示**され、**経理のみ編集可**（部長は読み取り専用） |
| 画面の場所 | 一般・部長 → 工数管理（**Timesheet**）> **案件一覧**／経理 → 業務マスタ（**MasterBusiness**）> **案件**（経理の工数管理は TimesheetAccounting で、案件一覧は無い） |
| 使う案件 | `a`（名称 `b`・**テスト残骸**。README §4）を種別切替の実験台に／`PRJ-004 ECサイト構築`（受託）／`PRJ-005 保守運用SES 高橋`（SES）／`PRJ-007 在庫管理システム開発（完了）`（状態＝完了・有効ON） |
| 既知の UX 非対称 | CLB の `UserWriteCondition` は**フィールドの読み取り専用化までしか UI に連動せず、「新規作成」「登録」ボタンは残る**（→ `docs/12_CLB改善提案/01_機能改善提案.md` FB-010）。本シナリオではこれも観察対象にする |

## ステップ 1: 一般社員は閲覧のみ（高橋健）

**kaihatsu2_shinjin** でログイン → サイドバー「**工数管理**」→ 工数入力に着地 → サイドバー「**案件一覧**」。

- **確認ポイント（読取は全員）**: 一般社員でも **12 件すべてが見える**。コード・案件名・区分・状態で検索もできる。案件は工数入力のプルダウンの元データなので、読取を絞る意味がない。

`PRJ-004 ECサイト構築` の行を開く。

- **期待結果**: 詳細画面の**全項目がグレーアウト（読み取り専用）**。案件コード・案件名・取引先・種別・状態・有効のどれにもカーソルが入らない。
- **確認ポイント（FB-010 の非対称）**: それでも画面下部に「**登録**」ボタンが**残っている**。一覧にも「**新規作成**」ボタンが出ていて、押せば新規作成画面にも入れてしまう。
- 試しに新規作成画面で 案件コード `TMP-001` ／ 案件名 `権限テスト` ／ 種別 `受託` ／ 状態 `進行中` を入れて「**登録**」を押す。
  - **期待結果**: **保存されない**（サーバ側の書込条件で拒否される）。一覧に戻っても `TMP-001` は増えていない。
  - **設計上の含意**: 権限の実体は**サーバ側で強制**されているので穴は無い。「押せるのに何も起きない」のは UI 連動が追いついていないだけ——CLB への改善要望として記録済み（FB-010）。

## ステップ 2: 部長は基本情報を編集できる（加藤正雄）

ログアウト（サイドバー最下部の Logout）→ **kaihatsu2_bucho**（開発2部 部長）でログイン → サイドバー「**工数管理**」→ 「**案件一覧**」。

- **確認ポイント**: 見えている一覧はステップ 1 とまったく同じ（読取は全員同条件）。違うのは開いた後。

`PRJ-004 ECサイト構築` を開く。

- **期待結果**: **基本情報 6 項目が編集できる**。

| 項目 | 状態 |
|---|---|
| 案件コード | 編集可（DB でユニーク） |
| 案件名 | 編集可 |
| 取引先 | 編集可。**候補の絞り込みが無い**——`株式会社シリウス設計`（取引終了・無効）も選べてしまう |
| 種別 | 編集可（`受託 / SES / SaaS / 社内`） |
| 状態 | 編集可（`進行中 / 完了 / 中断`） |
| 有効 | 編集可（チェックボックス） |

- 案件名を `ECサイト構築（部長編集テスト）` に変えて「**登録**」→ **保存できる**。一覧の名称も変わる。
- **すぐ元に戻す**: 案件名を `ECサイト構築` に戻して「登録」。

次に SES 案件 `PRJ-005 保守運用SES 高橋` を開く。

- **期待結果**: 種別が SES なので **SES 契約条件のブロックが表示される**（「　SES 契約条件（月額・精算幅）」「精算幅 下限〜上限(h)」「控除／超過単価(円/h)」の 3 ラベルと 5 つの入力欄）。
- **確認ポイント（ADR-0046 の核心）**: 基本情報は編集できるのに、**SES 契約条件 5 項目だけが読み取り専用**でグレーアウトしている。
- **なぜこの線か**: 単価と精算幅は **SES 請求金額＝売上に直結**し、案件損益の粗利も動く。案件の当事者である部長が自分で単価を触れる状態は職務分掌上まずい、という判断（`Project.mod.cs` の冒頭コメントに同じ理由が書いてある）。

## ステップ 3: 経理は全部編集できる（山田太郎）

ログアウト → **soumu_bucho** でログイン → サイドバー「**業務マスタ**」→ 取引先に着地 → サイドバー「**案件**」。

- **確認ポイント（導線の違い）**: 経理の「工数管理」は **TimesheetAccounting**（工数入力 / 工数管理（経理））で、**案件一覧が無い**。経理は案件を「マスタ管理」の文脈で **業務マスタ > 案件**から触る。同じ Project モジュールの別の入口。

`PRJ-005 保守運用SES 高橋` を開く。

- **期待結果**: **SES 契約条件 5 項目も含めてすべて編集可能**。値を書き換えられる状態になっている（実際には変更しないこと——SES 精算の金額が変わる）。
- **確認ポイント**: ステップ 2 と同じ画面・同じレイアウトで、**グレーアウトの有無だけが違う**。1 つのモジュールに「経理∨部長」の書込条件と、スクリプト側の「非経理なら SES 5 項目を読み取り専用」を重ねて実現している（三段論法の各段を正しい家に置く＝事実はキャッシュ・ポリシーは条件式・例外はスクリプト）。

## ステップ 4: 種別を SES に切り替える／戻しても値は消えない（山田太郎）

実験台には**テスト残骸の案件 `a`（名称 `b`・種別 受託）**を使う（実データを汚さないため）。業務マスタ > 案件 で `a` を開く。

1. **種別を `SES` に変更する**。
   - **期待結果**: 保存する前に、**その場で SES 契約条件のブロックが出現する**（`ProjectType_OnDataChanged` が発火してフィールドの表示を切り替えている）。
2. 契約条件を入力する。

| 項目 | 入力値 |
|---|---|
| SES 月額基本料金 | `500,000` |
| 精算下限(h) | `140` |
| 精算上限(h) | `180` |
| 控除単価(円/h) | `3,000` |
| 超過単価(円/h) | `4,000` |

   → 「**登録**」。
3. **種別を `受託` に戻して「登録」**。
   - **期待結果**: SES 契約条件のブロックが**画面から消える**。
4. もう一度 **種別を `SES` に戻す**。
   - **期待結果（本ステップの狙い）**: ブロックが再表示され、**さっき入力した 500,000 / 140 / 180 / 3,000 / 4,000 がそのまま残っている**。
   - **設計意図**: 表示を切り替えているだけで**値は消していない**（`Project.mod.cs` のコメント「値は消さない（種別を誤って切り替えても入力済みの契約条件が失われないように）」）。種別の誤操作 1 回で契約条件が飛ぶ事故を防ぐ、という UX 優先の割り切り。
   - **裏返しの注意**: 「受託に戻したのに SES の単価が DB に残り続ける」ということでもある。案件を SES から他種別へ本当に変更するときは、**契約条件を手で空にしてから**種別を変えるのが安全（SES 精算の対象は「有効かつ種別 SES」なので、種別が受託なら精算はされないが、データとしては残る）。

→ 後片付け（手順は末尾）で、種別を `受託` に・5 項目を空に戻す。

## ステップ 5: 「状態＝完了」と「有効オフ」はまったく違う（山田太郎）

案件には似て非なる 2 つのスイッチがある。どちらが効くのかを実際に見る。

まず現状を確認する。業務マスタ > 案件 で `PRJ-007 在庫管理システム開発（完了）` を開く。

- **確認ポイント**: **状態＝`完了`／有効＝ON**。

サイドバー「ホーム」→「**工数管理**」→ 「**工数入力**」→ 「新規作成」→ 案件のプルダウンを開く。

- **期待結果**: **`在庫管理システム開発（完了）` が候補に出る。** 状態が「完了」でも候補からは消えない。
- **確認ポイント（状態は飾り）**: `進行中 / 完了 / 中断` の **状態を見ている処理は現状どこにも無い**（表示専用）。「完了にしたから、もう工数は付かないはず」という思い込みが最も危ない。

業務マスタ > 案件 に戻り、`PRJ-007` の「**有効**」チェックを**外して**「登録」。

- 再び 工数管理 > 工数入力 > 新規作成 の案件プルダウンを開く。
  - **期待結果**: **`在庫管理システム開発（完了）` が候補から消える。** 有効フラグだけが実際の絞り込みに効いている。
  - **併せて**: SES 精算の対象からも外れる。ただし **案件損益には 0 行のまま出続ける**（無効化しても消えない）。
- **すぐ元に戻す**: `PRJ-007` の「有効」を ON に戻して「登録」。

- **運用上の結論**: 「もう工数を付けさせたくない」なら**有効を外す**。「実績として記録は残すが業務上は終了」の意思表示が**状態＝完了**。この 2 つを混同すると、締めた案件に工数が付き続けて案件損益が動く。

## ステップ 6: 権限そのものを組み替える（admin — director 行の追加と削除）

ここまでの「一般＝閲覧／部長＝編集」の線は、**部門メンバーの役職行 1 行**で決まっている。それを動かしてみる。

ログアウト → **admin** でログイン。

- **確認ポイント（職務分掌）**: admin のサイドバーは「通知」と「**システム管理**」だけ。経費も工数も営業も会計も無い（**業務画面には入れない**・ADR-0041）。

サイドバー「**システム管理**」→ ユーザー管理に着地 → サイドバー 組織 > 「**部門**」→ `開発2部` を開く。

- **確認ポイント**: 詳細下部に「**部門メンバー（組織所属・承認ルートの正。役職: 一般/課長/部長）**」の一覧がある。現在は 加藤正雄（部長）・吉田直樹（部長）などが並ぶ。

部門メンバーに **1 行追加**する。

| 項目 | 入力値 |
|---|---|
| 社員 | `開発2部 一般 高橋健` |
| 役職 | `部長` |

→ 「**登録**」。

- **期待結果**: 行が保存され、**DB トリガーで `app_users.is_director` が高橋健に立つ**（同時に `is_approver` も立つ）。
- **⚠ 副作用の警告（後片付けが必須な理由）**: この 1 行は権限だけでなく**承認ルートにも効く**。開発2部の申請に対する部長段に高橋健が加わり、既存の部長 2 名と **OR 並列**になる（誰か 1 人の承認で段が完了）。デモ用の組織構造が変わってしまうので、確認したら必ず消すこと。

ログアウト → **kaihatsu2_shinjin**（高橋健）で**再ログイン**（フラグはログイン時に解決されるので、開いたままのセッションでは変わらない）。

- **期待結果（本ステップのゴール）**: サイドバー「**工数管理**」→ 「**案件一覧**」→ `PRJ-004 ECサイト構築` を開くと、ステップ 1 ではグレーアウトしていた**基本情報 6 項目が編集できるようになっている**。
- **同時に確認**: `PRJ-005 保守運用SES 高橋` を開くと、**SES 契約条件 5 項目は読み取り専用のまま**（部長になっただけでは経理項目は開かない＝ステップ 2 と同じ状態）。
- **ついでに**: ポータルに「▶ あなたの承認待ち: N 件」の区画が出るようになり、サイドバーに「**経営管理**」（承認者なので ManagementApprover）が現れる。**役職行 1 行で 3 つのことが同時に変わった**——これが「権限＝部門メンバーシップ」という設計の効き方。

**元に戻す**: ログアウト → **admin** → システム管理 > 組織 > 部門 > `開発2部` → 部門メンバーの高橋健（部長）の行を**削除**して「**登録**」。

- ログアウト → **kaihatsu2_shinjin** で再ログイン → 案件一覧の詳細が**再びすべてグレーアウト**に戻り、サイドバーから「経営管理」が消え、ポータルの「あなたの承認待ち」区画も消える。

## 後片付け

**soumu_bucho**（経理）と **admin** で、触ったものを元に戻す。

1. **部門メンバーの director 行（最重要）**: **admin** → システム管理 > 組織 > 部門 > `開発2部` → 高橋健（部長）の行が**削除済み**であることを確認する。残っていると承認ルートが変わったままになる。
2. **案件 `a` の種別と SES 契約条件**: **soumu_bucho** → 業務マスタ > 案件 > `a` を開く → 種別が `受託` でなければ一度 `SES` にして **5 項目（500,000 / 140 / 180 / 3,000 / 4,000）をすべて空に消し** → 種別を `受託` に戻して「登録」。
   - （`a` はもともとテスト残骸なので、DB を掃除する方針なら案件ごと削除してもよい。ただし工数・仕訳が紐づいていないことを確認してから。）
3. **`PRJ-007` の有効フラグ**: 業務マスタ > 案件 > `PRJ-007 在庫管理システム開発（完了）` の「**有効**」が **ON** に戻っていることを確認する。工数入力の案件プルダウンに再び出れば OK。
4. **`PRJ-004` の案件名**: ステップ 2 で変更した場合、`ECサイト構築` に戻っていることを確認する。
5. **確認**: 工数管理 > 工数入力 > 新規作成 の案件プルダウンに 12 件中の有効案件が揃い、案件損益（経営管理 > 案件損益）の区分表示がシナリオ前と同じになっていれば原状復帰。

## つまずいたときは

- **「登録」を押しても保存されない／何も起きない**: 書込条件（**経理 ∨ 部長**）を満たしていない。ボタンだけ残るのは既知の UX 非対称（FB-010）で、バグではなくサーバ側で正しく弾かれている状態。
- **部長なのに編集できない**: `is_director` は**部門メンバーの「役職＝部長」行**から導出される。ユーザー管理のチェックボックス（営業/経理/経費/工数/システム管理者）とは別軸。部門マスタの該当ノードにその人の部長行があるかを admin で確認する。**部長行を足した直後は再ログインが必要**。
- **SES 契約条件の欄が出てこない**: 種別が `SES` になっていない。種別を SES にすると保存前でもその場で現れる。
- **SES 契約条件が読み取り専用のまま**: 経理機能フラグの無いユーザー（部長を含む）。soumu_bucho で操作する。
- **種別を戻したのに SES の単価が残っている**: 仕様（値は消さない）。本当に消したいなら種別を SES にして 5 項目を空にしてから戻す。
- **案件が工数入力のプルダウンに出ない**: 「**有効**」が OFF。**状態＝完了は関係ない**（完了でも候補に出る）。
- **一般社員に案件一覧が見えてしまう**: 仕様（読取は全員）。案件は工数入力の参照元なので読取は絞っていない。書けないことがサーバで担保されている。
- **admin で業務画面に入れない**: 仕様（職務分掌・ADR-0041）。admin は組織・ユーザー・承認ガバナンス専用で、経費・工数フラグも OFF。業務の検証は soumu_bucho 等で行う。
