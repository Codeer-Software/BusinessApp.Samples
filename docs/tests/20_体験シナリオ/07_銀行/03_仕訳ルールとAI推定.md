# 体験シナリオ 銀行-03: 仕訳ルールと AI 推定（優先度・適用方向・全角半角・手入力の保護）

> 所要時間: 約25分 ／ 影響: 仕訳ルール 3 本＋銀行明細 7 行を追加し、**末尾の後片付けで全部削除する**。仕訳は 1 本も作らない（起票まで進めない）ので帳簿は前後で無変化
> 主役: **soumu_bucho**（総務部 部長 山田太郎・経理）。パスワードはユーザー名と同じ。
> 「摘要から相手科目を当てる」仕組みの中身を開けて見る回。ルールが**どういう順で・どういう条件で**当たり、当たらなかった残りを AI がどう埋め、人の手入力がどう守られるかを 1 画面で見比べる。

## 物語

山田太郎は毎月の銀行明細に同じ摘要が並ぶことに気づいた。「これ、辞書に登録しておけば毎回選ばなくて済むのでは？」
ところが試しに作ってみると、同じキーワードのルールを 2 つ作ってしまったり、入金の明細に出金用のルールを当ててしまったり、全角で書いた「ドコモ」が半角の「ﾄﾞｺﾓ」ルールに当たらなかったり——辞書を育てるには当たり方の癖を知る必要がある。ルールで拾いきれなかった摘要は AI に下書きさせ、最後は人が確定する。

## ステップ 1: 既存のルールを眺める

**soumu_bucho** でログイン → サイドバー「**会計業務**」→ 銀行 > **仕訳ルール**。

- **確認ポイント**: 一覧の列は **優先度 / 摘要キーワード / 適用方向 / 相手勘定科目 / 有効 / 部門**。**優先度の昇順**に並んでいる（この並び順がそのまま評価順）。
- **確認ポイント（部門列）**: ルールは相手科目だけでなく**部門も持てる**（ADR-0056。損益科目の行には部門が必須なので、当たった瞬間に明細の部門まで埋めておける）。seed の 12 件は**部門が空**なので、当たった行の部門は一括起票画面で人が選ぶことになる。
- **確認ポイント**: 「振込」だけが**入金のみ**で、残りは出金のみ。銀行明細の「振込」は入金なら売掛金の回収、出金なら支払で意味が真逆になるため、**方向でルールを分けるのが基本形**。

## ステップ 2: 必須 4 項目のガードを見る

「**新規作成**」を押す。

- **確認ポイント（初期値）**: 「**有効**」チェックが**最初から ON** になっている。ここが OFF 始まりだと「作ったのに当たらないルール」を量産するので、新規作成時だけ自動で ON にしている。
- 何も入れずにいきなり「**登録**」を押す。

- **期待結果**: 保存されず、**優先度・摘要キーワード・適用方向・相手勘定科目の 4 項目**が必須エラーになる（メモと有効は任意）。
- **確認ポイント**: 優先度欄のプレースホルダは「**小さいほど優先（例: 10）**」、摘要キーワード欄は「**摘要に含まれる文字列（例: AWS）**」。この 2 行がルールの意味論をほぼ全部説明している。

## ステップ 3: ルールを 3 本作る

同じ「新規作成」から、以下の 3 本を順に作る（1 本ごとに「登録」→ 一覧に戻って「新規作成」）。**キーワードはすべて同じ `ﾃｽﾄｹｲﾋ`**（半角カナ）にするのがポイント。

| # | 優先度 | 摘要キーワード | 適用方向 | 相手勘定科目 | 部門 | メモ |
|---|---|---|---|---|---|---|
| R1 | `50` | `ﾃｽﾄｹｲﾋ` | 出金のみ | 消耗品費 | `全社共通` | `BNK03 負け組（優先度が大きい）` |
| R2 | `20` | `ﾃｽﾄｹｲﾋ` | 出金のみ | 雑費 | `全社共通` | `BNK03 勝つはず（優先度が小さい）` |
| R3 | `10` | `ﾃｽﾄｹｲﾋ` | 入金のみ | 雑収入 | `全社共通` | `BNK03 入金専用` |

- **確認ポイント（部門は任意だが入れておく）**: 部門はルールの必須項目ではないが、相手科目が損益科目なら**起票時に必ず要る**（ADR-0056）。ルールに入れておけば当たった瞬間に明細の部門まで埋まり、一括起票で選び直さずに済む。
  **2026-08-19 まではここが効いていなかった**（取込のルール適用が部門をコピーしていなかった＝BUG-0407）。
  修正後は、次のステップで一括起票を開いたとき **R1〜R3 が当たった行の「部門」列に `全社共通` が入っている**。

- **期待結果**: 一覧が **15 件**になり、R3（10）→ R2（20）→ R1（50）の順に、既存ルールの間に挟まって並ぶ。
- **確認ポイント**: 「同じキーワードのルールを複数作っても、システムは何も警告しない」。矛盾は**優先度と方向でしか解決されない**——だからこそ次のステップで挙動を確かめる価値がある。

## ステップ 4: テスト明細を取り込んで、登録時のルール適用を見る

**画面**: 会計業務 > 銀行 > **明細取込**（取込先口座は MB01 が自動選択）

以下を貼って「**明細を取り込む**」。**残高列は書かない**（本書はルールの当たり方が主題で、照合は扱わない。残高を合わせる手順は 銀行-01／銀行-02 が担当）:

```
日付,摘要,出金額,入金額
2026/08/28,BNK03 ﾃｽﾄｹｲﾋ ｼﾊﾗｲ,3300,
2026/08/28,BNK03 ﾃｽﾄｹｲﾋ ﾆｭｳｷﾝ,,3300
2026/08/28,BNK03 ﾄﾞｺﾓ ｹｲﾀｲﾘﾖｳｷﾝ,5500,
2026/08/28,BNK03 ドコモ ケイタイリヨウキン,5500,
2026/08/28,BNK03 ｼﾞﾑﾖｳﾋﾝ 消耗品費 ﾊﾗｲ,1100,
2026/08/28,BNK03 ﾅｿﾞﾉﾋｷｵﾄｼ,2200,
2026/08/28,BNK03 ﾅｿﾞﾉﾆｭｳｷﾝ,,4400
```

- **期待結果**: 「プレビュー **7** 件 / 重複スキップ 0 件 / スキップ行（ヘッダ・明細以外） **1** 行」。

→ 内容を確認して「**この内容で登録**」→ 確認ダイアログ「プレビュー中の明細をまとめて銀行明細に登録します。登録後は「取込をやめる」では戻せません。よろしいですか？」→「**登録する**」。

- **期待結果**: 「**7 件を未起票の明細として登録しました（ルール適用 3 件 / 重複スキップ 0 件）。科目の確定と起票は「一括起票」で行います**」。
- **確認ポイント**: **ルールが当たるのは「この内容で登録」の瞬間**（＋一括起票画面の「ルールを適用」ボタン）。取込＝プレビューの段階では科目は付かない。

## ステップ 6: 手で入れた科目は「ルールを適用」でも上書きされない

1. `BNK03 ドコモ ケイタイリヨウキン`（全角の行）の「相手科目（候補）」ドロップダウンで **通信費** を選ぶ。
   - **期待結果**: その行の「推定元」が **`manual`** に変わる。サマリが「起票対象 4 件 ／ 候補未設定 3 件」になる。
2. 「**ルールを適用**」を押す。

- **期待結果**: 結果ラベル「**ルール適用: 0 件（保存または一括起票で確定されます）**」＋トースト「**ルールに一致する明細がありませんでした**」。
- **確認ポイント（保護の証明）**: 全角行の推定元は **`manual` のまま**で、科目も通信費のまま。ボタンの対象は「**候補が空**かつ対象外チェックが付いていない行」だけなので、**ルール・AI・手入力のどれで入った候補も、あとからルールに塗り替えられることはない**。
- **確認ポイント**: いま候補が空なのは `ｼﾞﾑﾖｳﾋﾝ`・`ﾅｿﾞﾉﾋｷｵﾄｼ`・`ﾅｿﾞﾉﾆｭｳｷﾝ` の 3 行。どれもキーワードを含まないので 0 件になった。有効なルールが 1 件も無い状態で押すと、メッセージは「有効な仕訳ルールがありません」に変わる（今回は 15 件あるので出ない）。

## ステップ 7: AI で相手科目を推定する（モック）

「**AIで相手科目を推定**」を押す。

- **期待結果**: 結果ラベル「**AI 推定: 対象 3 件 / 反映 3 件（保存または一括起票で確定されます）**」＋トースト「AI が 3 件の相手科目を推定しました」。
  **プロバイダが Mock のときだけ**、両方に「**（モック応答）**」が挟まる。
  印が付かなかったら**実 API を呼んでいる**——前提表と BUG-0408 を参照。
- **期待結果（モックの当て方）**:

  | 摘要 | AI が入れる科目 | モックの規則 |
  |---|---|---|
  | `BNK03 ｼﾞﾑﾖｳﾋﾝ 消耗品費 ﾊﾗｲ` | **消耗品費** | 摘要に**勘定科目名（2 文字以上）がそのまま含まれていれば、その科目**を選ぶ |
  | `BNK03 ﾅｿﾞﾉﾋｷｵﾄｼ` | **雑費** | 判断材料が無い**出金**は雑費 |
  | `BNK03 ﾅｿﾞﾉﾆｭｳｷﾝ` | **売掛金** | 判断材料が無い**入金**は売掛金 |

  **実 API（AzureOpenAI）で動かした 2026-08-19 の実測でも、この 3 行は同じ科目になった**——
  システムプロンプトがモックと同じ方針（判断できなければ出金は雑費・入金は売掛金）を明示しているため。
  ただし**実 API は毎回同じ答えとは限らない**ので、期待値としては「モックのとき」を正とする。

- **確認ポイント**: 3 行とも推定元が **`ai`**。サマリは「未起票 7 件 ／ 起票対象 7 件 ／ 候補未設定 0 件 ／ 対象外チェック中 0 件」。
- **確認ポイント（対象の定義）**: AI の対象も「**候補未設定**かつ対象外チェックなし」の行だけ。もう一度押すと対象が 0 件になり、トースト「**AI 推定の対象（相手科目候補が未設定の明細）がありません**」が出る（押して確かめてよい）。
- **確認ポイント（「（モック応答）」の意味）**: この 5 文字は **AI プロバイダが Mock 設定である印**。Claude／AzureOpenAI に切り替えると消え、実際のモデルが摘要と科目候補一覧を読んで推定する（サーバ側で**候補一覧に実在するコードだけを通す検証**をしてから返すので、存在しない科目が入ることはない）。デモでは「AI は下書き、確定は人間」という役割分担を口頭で添えると刺さる。
- **確認ポイント（保存規律）**: ここまで**まだ DB には何も書かれていない**。ブラウザを閉じれば推定結果は消える。ルールも AI もメモリ上の下書き、というのが銀行部品の一貫した規律。

3. **原状確認**: 仕訳ルールが **12 件**、明細一覧（状態=未起票）が **0 件**。仕訳帳・試算表は本書の前後で無変化。

- **確認ポイント（ルールの行削除）**: 削除の確認は **CLB 標準の「削除しますか？」＋ Yes / No**（英語のまま。FB-027）。
  削除しても一覧右上の件数表示は**古いまま**（`(1-12 /15件)` のように残る）。行数の方が正しく、再検索で直る。
- **2026-08-19 の実機確認**: 全 8 ステップが台本どおりに再現した（BUG-0407 の部門コピーだけが当時未修正）。
  後片付け後は明細 13 行・ルール 12 件・最終伝票 No. 変化なし。

## つまずいたときは

- **`BNK03 ﾃｽﾄｹｲﾋ ｼﾊﾗｲ` に消耗品費（R1）が入る**: R2 の優先度が R1 より大きくなっていないか（数字が**小さい方が勝つ**）。または R2 の「有効」が OFF になっている（無効ルールは評価対象外）。
- **入金の行に雑費（R2）が入る**: R2 の適用方向が「入出金両方」になっている。方向を「出金のみ」に直す。
- **`ドコモ`（全角）に通信費が自動で入ってしまう**: 全角キーワードのルールを別途作っていないか（既存 12 件は半角）。ルール一覧の摘要キーワード列を見て確認する。
- **AI 推定で「AI 推定サービスに接続できませんでした」**: サーバが起動していないか、`AISettings` が Mock 以外でキーが未設定。Mock に戻せば実キー無しで動く。
- **AI の反映件数が対象件数より少ない**: モデルが返したコードが勘定科目マスタに存在しない場合、サーバ側の検証で捨てられる（Mock ではまず起きない）。残った行は手で選べばよい。
- **ルールを消したのに一覧から消えない**: 行削除は一覧の保存操作とセット。削除後に一覧を再検索して確認する。
- **明細が消せない**: 状態が「起票済」になっていないか（本書では起票しない想定）。起票済なら先に詳細画面の「起票を取り消す」で未起票に戻す（→ 銀行-04）。
