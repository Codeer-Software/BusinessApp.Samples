# 体験シナリオ マスタ-01: ユーザーと機能フラグ（3軸分離を体で覚える）

> 作成: 2026-08-09 ／ 所要時間: 約20分 ／ 影響: **ユーザー 1 名を新規追加**（ユーザーには削除導線が無いため、最後は「有効」を外して無効化する。行は DB に残る＝完全消去は任意の SQL 作業）
> 主役: **admin**（システム 管理者）＋ 途中で作る **taiken_user**（体験 太郎）。パスワードは全員ユーザー名と同じ。
> 「画面が見えるかどうか」は**ユーザーのチェックボックスだけ**で決まり、**部門メンバー行では決まらない**——ADR-0043 の 3 軸分離を、チェック 1 個の ON/OFF で目に見える形で確かめる。

## 物語

株式会社アルタイルシステムズに中途入社の「体験 太郎」が着任した。まずは全社員共通の機能（経費精算・工数入力）だけで立ち上げ、
配属が営業まわりと決まった時点で営業機能を足す。試用期間の扱いを間違えたので、最後は一度アカウントを止める。
情シス担当（admin）は、その一連を**ユーザー管理画面のチェックボックスだけ**で完結させられることを確認する。

## 前提

| 項目 | 内容 |
|---|---|
| 権限の 3 軸（ADR-0043） | ① **機能権限** = `app_users` の直接フラグ（この画面のチェックボックス）／② **組織所属** = 部門メンバー行（→ マスタ-02）／③ **承認構造** = 役職行＋テンプレート（→ マスタ-03）。**①だけがサイドバーの出し分けを決める** |
| 新規ユーザーの既定 | 有効 = ON、**経費精算 = ON、工数入力 = ON**、営業機能・経理機能・システム管理者 = OFF（全社員機能はオプトアウト型） |
| 承認者・部長 | **読み取り専用**。DB トリガーが役職行・テンプレート指名から自動転記する（この画面では触れない） |
| 削除 | ユーザーに削除導線は無い。退職は「有効」を外す運用 |
| 影響 | 新規ユーザー 1 名。既存ユーザー・組織・伝票は一切変更しない |

---

## ステップ 1: admin のポータルを見る（職務分掌の確認）

**admin** でログイン。

- **期待結果**: 全員と同じ**業務ポータル**（Main/PortalHome）に着地する。中央は「こんにちは、システム 管理者 さん」＋日付と、最下部の「**ユーザー・組織・承認ルートの管理はこちら →**」くらいしか出ない。
- **確認ポイント**: サイドバーは「**よろず／通知／システム管理／Logout**」だけ。経費精算・工数管理すら出ない（admin は `CanUseExpense`・`CanUseTimesheet` も OFF）。
  承認待ち・進行中の申請・経理の作業キュー・アラート・経営ダッシュボードは**行ごと消えている**（0 件の項目は見出しごと消える設計）。
  これが職務分掌（ADR-0041）——**管理者は業務データを見ない**。

サイドバー「**システム管理**」→ MasterAdmin フレームの着地画面「**組織/ユーザー管理**」。

- **確認ポイント**: 画面上部の説明文が読める。
  > ユーザーの登録・編集ができます。業務機能の権限（営業・経理・経費精算・工数入力）はチェックボックスで指定します。承認者は部門の課長/部長・承認テンプレートの指名から自動判定。削除はできません — 退職者は「有効」を外して無効化します。
- 一覧の列: ユーザー識別名／表示名／所属部門／営業機能／経理機能／経費精算／工数入力／部長／承認者／システム管理者／有効。
  **列見出しをクリックすると並べ替えできる**ので、「経理機能」で並べて経理保有者（総務部の 5 名）を数えてみるとよい。

## ステップ 2: 新規ユーザーの既定値を確かめる

「**新規作成**」を押し、**まだ何も入力せずに**フォームを眺める。

- **期待結果（ここが本ステップの主目的）**:

| 項目 | 新規作成時の既定 |
|---|---|
| 有効 | **ON** |
| 営業機能 | OFF |
| 経理機能 | OFF |
| **経費精算** | **ON** |
| **工数入力** | **ON** |
| システム管理者 | OFF |

- **確認ポイント**: 経費精算・工数入力だけ最初から ON なのは「全社員が使う機能はオプトアウト型」という設計判断（ADR-0043）。
  新入社員を登録した瞬間から経費申請と工数入力ができ、**情シスが個別に許可を出す必要がない**。
- **確認ポイント（触れない欄）**: 〔承認者〕〔部長〕のチェックはグレーアウトしていて押せない。すぐ下に注意書きが出ている:
  > ※ 承認者・部長は部門の役職（課長/部長）・承認テンプレートの指名から自動判定されます（部門管理で編集）。部長は案件の登録・変更ができます
  **ここを人間が手で変えられないのが肝**。承認者の正は部門メンバーの役職行であって、このチェックはその写し（キャッシュ）にすぎない。実際に点いたり消えたりする様子は マスタ-02 で見る。

## ステップ 3: ユーザーを作る

そのまま入力する。

| 項目 | 入力値 |
|---|---|
| ユーザー識別名 | `taiken_user` |
| 表示名 | `体験 太郎` |
| 所属部門 | `開発1部 第一課` |
| パスワード | `taiken_user` |
| 有効 | ON（既定のまま） |
| 営業機能／経理機能／システム管理者 | OFF（既定のまま） |
| 経費精算／工数入力 | ON（既定のまま） |

→ 「**登録**」を押す。

- **期待結果**: 一覧に `taiken_user ／ 体験 太郎 ／ 開発1部 第一課` の行が増える。営業機能・経理機能・部長・承認者・システム管理者は空、経費精算・工数入力・有効にチェック。
- **確認ポイント**: 所属部門のドロップダウンには**部も課も両方出る**（`開発1部` と `開発1部 第一課` が別々に選べる）。ここで**課**を選ぶと、その人の承認は「自課の課長 → 部長」の順に walk-up する。部を選ぶと最初から部長段になる。
- **確認ポイント**: 「所属部」列（あれば）は自動で `開発1部` になっている。これも読み取り専用のキャッシュで、**伝票の部門の既定値**に使われる（伝票の部門は部ノードのみ）。

## ステップ 4: 作ったユーザーで入ってみる（最小権限の見え方）

サイドバー最下部の「**Logout**」→ **taiken_user / taiken_user** でログイン。

- **期待結果**: ポータルに着地。挨拶は「こんにちは、体験 太郎 さん」。
- **確認ポイント（本シナリオの山①）**: サイドバーが

  | よろず |
  |---|
  | 通知 |
  | **経費精算** |
  | **工数管理** |
  | Logout |

  の 5 つだけ。**営業業務・会計業務・購買・支払・経営管理・業務マスタ・システム管理はどれも出ない。**
- **確認ポイント**: ポータル中央は「未読の通知」の見出しすら出ない（未読 0 件）。承認待ちも進行中の申請も 0 なので行ごと消える。**「何もない画面」は壊れているのではなく、権限どおり**。
- 試しに「経費精算」を押すと ExpenseStaff フレーム（着地=申請）、「工数管理」を押すと Timesheet フレーム（着地=工数入力）に入れる。申請一覧の検索条件「申請者」には自分（体験 太郎）が既定でセットされている。
- **確認ポイント（直 URL）**: アドレスバーに `/Accounting` と直接打ち込んでも入れない（権限外は拒否される）。詳しくは `00_ポータルと通知/03_直URLゲートと着地.md`。

## ステップ 5: 営業機能に✓を入れる（3軸分離の実感どころ）

「**Logout**」→ **admin** で再ログイン → システム管理 → 組織/ユーザー管理 → `taiken_user` の行を開く。

**営業機能**にチェックを入れる → 「**登録**」。

- **期待結果**: トースト「登録しました」。一覧の営業機能列にチェックが付く。
- **確認ポイント**: **部門メンバー行は一切触っていない**。3 軸のうち①だけを動かした。

「**Logout**」→ **taiken_user** でログイン。

- **期待結果（本シナリオの山②）**: サイドバーに「**営業業務**」が増えている。押すと SalesStaff フレーム（着地=**見積**、サイドバーは 見積／受注／検収／売掛残高／定期請求契約／取引先一覧）。
- **確認ポイント**: 増えたのは「営業業務」だけ。**「経営管理」は出ない**（`IsApprover ∨ HasAccountingAccess` が条件で、営業機能では点かない）。**「業務マスタ」も出ない**（経理機能が条件）。
  ——1 つのチェックが 1 つの業務を開ける、という素直な対応になっている。

### 実機で確かめてほしいこと: 反映に再ログインは要るか

- **ログイン中のユーザーの権限を admin が変えた直後、そのユーザーの画面はいつ変わるか**を試す価値がある。
  実装ではログインユーザー情報（`CurrentUser`）が**セッションに載る**ため、**再ログインが必要な可能性が高い**。
- 手順: taiken_user でログインしたまま放置 → 別ブラウザ（またはシークレットウィンドウ）の admin で経理機能に✓ → taiken_user 側で
  ① ポータルを **F5 リロード** → サイドバーは変わるか？
  ② 変わらなければ **Logout → 再ログイン** → 変わるか？
- **結果がどちらでも仕様として妥当**（セッション方式なら再ログインが正しい）。ただし**運用手順書には「権限を変えたら本人に再ログインを案内する」と書く必要がある**ので、ここは必ず実測して記録する。
  （試したら経理機能のチェックは**必ず外して**元に戻すこと。この確認は任意ステップ）

## ステップ 6: 自分のシステム管理者は外せない（ロックアウト防止）

**admin** でログイン中に、ユーザー管理から**自分自身（admin）**の行を開く。

「**システム管理者**」のチェックを**外そうとする**。

- **期待結果**: チェックが**その場で ON に戻り**、赤いトーストが出る。
  > 自分自身のシステム管理者権限は外せません（ロックアウト防止）。別の管理者で操作してください。
- **確認ポイント**: これは保存時ではなく**チェックを外した瞬間**の判定（`IsSysAdmin_OnDataChanged`）。「登録」を押す必要すらない。
  管理者が 1 人しかいない環境で自分を降格すると、**誰もユーザー管理画面に入れなくなる**（`IsSysAdmin` が MasterAdmin フレームのゲート）ので、その事故を入口で塞いでいる。
- **確認ポイント（他人の分は外せる）**: 制限は「自分自身」だけ。`taiken_user` に一度システム管理者を付けて登録し、続けて外して登録すると**普通に外せる**。
  管理者を交代するときは「新管理者に付ける → 新管理者でログインして旧管理者から外す」という手順になる。
  （試した場合は `taiken_user` のシステム管理者チェックを**必ず OFF に戻す**）

## ステップ 7: 無効化するとログインできなくなる

ユーザー管理 → `taiken_user` を開く → 「**有効**」のチェックを**外す** → 「**登録**」。

- **期待結果**: 一覧の「有効」列が空になる。行そのものは残る（**削除導線は無い**）。

「**Logout**」→ **taiken_user / taiken_user** でログインを試す。

- **期待結果**: **ログインできない**（認証エラー）。パスワードは合っているのに弾かれる。
- **確認ポイント**: 無効化はアプリのスクリプトではなく**認証の入口（有効ユーザーだけを見るビュー）**で効いている。つまり「無効なのに直 URL で入れてしまう」抜け道が原理的に無い。
- **確認ポイント（承認への波及）**: 退職者を無効化すると、承認テンプレートに個人指名されていても**承認者として選ばれなくなる**（無効ユーザーは経理代替に振り替わる）。承認が永久に止まる事故を防ぐための仕様。この分岐は マスタ-03 でも触れる。

## つまずいたときは

- **「システム管理」がサイドバーに出ない**: システム管理者フラグを持つのは `admin` だけ。業務ユーザー（soumu_bucho 等）では出ないのが正しい。
- **新規作成時に経費精算・工数入力が OFF になっている**: 誰かが既定を変えたのではなく、**既存ユーザーを開いている**可能性が高い。既定 ON は「新規作成」のときだけ効く。
- **同じユーザー識別名で登録できてしまう／できない**: 識別名の一意性は DB 制約が受け持つ。重複させると生の DB エラーが出るので、既存の一覧で先に確認する。
- **営業機能に✓したのに「営業業務」が出ない**: ステップ 5 の「再ログインは要るか」を参照。まず Logout →再ログインを試す。それでも出なければ、チェックが保存されているか（一覧の営業機能列）を確認。
- **承認者・部長のチェックを付けたい**: この画面では**付けられない**（設計どおり）。部門メンバーに課長行／部長行を足すと自動で点く → マスタ-02 ステップ 4。
- **作ったユーザーを消したい**: UI に削除導線は無い。運用上は無効化で十分。DB から本当に消す場合は、そのユーザーが作った申請・通知・承認履歴の孤児化に注意（管理者作業）。

## 後片付け

1. `taiken_user` の「**有効**」が OFF になっていること（ステップ 7 で実施済み）。
2. `taiken_user` の「**営業機能**」チェックを**外して**「登録」（ステップ 5 で付けたもの）。ステップ 5 の実機確認で経理機能・システム管理者を試した場合も、すべて OFF に戻す。
   → これで `taiken_user` は「無効・全業務フラグ OFF（経費精算/工数入力は既定 ON のまま）」という無害な状態になる。
3. **admin 自身の設定は何も変えていない**こと（システム管理者は ON のまま。ステップ 6 は保存を伴わない）。
4. **（任意・管理者作業）**行そのものを消したい場合は DB から `app_users` の `taiken_user` を削除する。**UI からは消せない**。この体験では申請・通知を一切作っていないので、参照は無く安全に消せる。

- **既存データへの影響はゼロ**: 伝票・仕訳・承認・部門メンバーには一切触れていない。
