# 体験シナリオ マスタ-02: 部課と承認の追随（階層ガード・キャッシュ転記・walk-up の実証）

> 作成: 2026-08-09 ／ **更新: 2026-08-09 ADR-0048/0044 反映**（承認テンプレート名を新名称に。12,000 円なのでルート＝課長 1 段は不変）／ 所要時間: 約30分 ／ 影響: **課を 1 つ新規追加**（部門には削除導線が無いため、最後は「有効」を外して無効化する。行は DB に残る＝完全消去は任意の SQL 作業）。ほかに部門メンバー行の追加・削除と経費申請 1 本を作るが、**すべて元に戻す**
> 主役: **admin**（組織の編集）＋ **kaihatsu2_shinjin**（開発2部 第二課 一般 高橋健・walk-up の実証）。パスワードは全員ユーザー名と同じ。
> 組織を 1 行いじると、承認者が誰になるかが**その場で変わる**。「役職行が正・チェックは写し」という ADR-0044 の設計を、実際の経費申請で目に見える形で確かめる。

## 物語

株式会社アルタイルシステムズの総務部に、来期から「第三課」を新設することになった。情シス（admin）は部門マスタに課を足し、課長を割り当てる。
同じ日、開発2部 第二課の課長（山口健太）が長期出張に入り、課長席が空く。空席のあいだ、第二課の新人・高橋健の経費申請は誰に回るのか——
**部長へ自動で繰り上がる**ことを、実際に申請を起こして確かめる。

## 前提

| 項目 | 内容 |
|---|---|
| 組織の形（ADR-0044） | `departments` は自己参照の **2 階層**。親部門なし = **部**（`dept`）／親部門あり = **課**（`section`）。`node_type` は **DB トリガーが保守**（画面では読み取り専用） |
| 承認者の解決 | 申請者の所属ノードから**親方向へ walk-up**。最寄りの該当役職者（申請者本人は除く）**全員**。課長が居なければ**部長へ自動繰上げ**、それも居なければ**経理代替**、それも無ければ申請ブロック |
| 同格が複数 | 同一ノードに同役職が 2 名以上 → **OR 並列**（1 人の承認で段が完了。残りは Skipped） |
| キャッシュ転記 | `is_approver`（承認者）= 課長 or 部長の行がある **∨** 承認テンプレートに個人指名／`is_director`（部長）= 部長の行がある。**DB トリガーで即時**。`is_director` が ON になると**案件マスタを編集できる**（ADR-0046） |
| 使う承認ルート | 12,000 円・旅費交通費 → 承認ルート判定の優先度 100（全費目 0〜29,999）→ テンプレート「**経費_課長まで**」（manager 1 段） |
| 影響 | 課 1 つ（無効化して残る）／部門メンバー行の増減（元に戻す）／経費申請 1 本（キャンセル→削除）／承認依頼の通知 2 通（残る） |

## ステップ 1: 部門一覧を読む（部と課の見分け方）

**admin** でログイン → サイドバー「**システム管理**」→ 組織/**部門**。

- **確認ポイント**: 上部の説明文。
  > 部門と役職者（課長・部長）を管理します。役職者は経費の承認ルート解決に使われます。
- 一覧は**表示順**で並ぶ。部（親部門が空）とその配下の課（親部門あり）が交互に読める並びになっている:

| 部門コード | 部門名 | 親部門 | ノード種別 |
|---|---|---|---|
| 00 | 全社共通 | （空） | dept |
| 10 | 総務部 | （空） | dept |
| 20 | 営業部 | （空） | dept |
| 31 / 32 / 40 | 開発1部 / 開発2部 / SaaS事業部 | （空） | dept |
| 10-1 / 10-2 | 総務部 第一課 / 第二課 | 総務部 | section |
| …（各部に 第一課・第二課） | | | |

- **確認ポイント**: **「全社共通」だけは課を持たない**。伝票の部門候補は部ノードのみなので、全社共通は「どの部にも紐づかない費用」の受け皿として使う。
- 適当な課（例: **総務部 第一課**）を開いてみる。**親部門 = 総務部**、**ノード種別 = section**（グレーアウト。手では変えられない）。
  詳細の下には「**部門メンバー（組織所属・承認ルートの正。役職: 一般/課長/部長）**」のインライン一覧があり、`石川真理 / 課長`・`藤井愛 / 一般` の 2 行が入っている。
  **列は「社員」と「役職」の 2 つだけ**——これが承認ルートの唯一の入力である、という潔い設計。

## ステップ 2: 課を作る（親部門を選ぶと section になる）

一覧の「**新規作成**」→ 入力:

| 項目 | 入力値 |
|---|---|
| 部門コード | `10-3` |
| 部門名 | `総務部 第三課` |
| **親部門（部のままなら空）** | `総務部` |
| ノード種別 | （空のまま。読み取り専用） |
| 表示順 | `103` |
| 有効 | ON（既定） |

→ 「**登録**」を押す。

- **期待結果**: 一覧に `10-3 総務部 第三課` が総務部 第二課の次に並ぶ。**開き直すと ノード種別 が `section` になっている**（入力していないのに）。
- **確認ポイント（課の作り方の要点）**: 課を作る手順は「**部を先に作る → 次に課を新規作成して親部門にその部を選ぶ**」の 2 段。
  ノード種別は自分で選ぶ項目ではなく、**親部門を入れたかどうかの結果**。だから「親部門を空にすれば部、埋めれば課」という 1 つのルールだけ覚えればよい。
- **確認ポイント**: 親部門のドロップダウンには**部だけ**が出る（有効な `dept` ノードのみ）。課を選ぶことはそもそもできない＝**3 階層目を作る入口が無い**。

## ステップ 3: 2 つのガードを踏む（保存しないので安全）

ガードは「値を変えた瞬間」に効く（`ParentRef_OnDataChanged`）。**「登録」は押さないこと**——押さなければ DB は 1 バイトも変わらない。

### 3-1. 自己参照ガード

部門一覧から **総務部**（コード 10）を開く → 親部門のドロップダウンで「**総務部**」（自分自身）を選ぶ。

- **期待結果**: 選んだ値が**即座に空へ戻り**、赤いトースト。
  > 自分自身を親部門にはできません
- **確認ポイント**: 保存前に戻るので、うっかり自己参照ループを作れない。値は元の「空」に戻っているだけなので、このまま画面を離れてよい。

### 3-2. 3 階層ガード

同じ **総務部** の画面で、今度は親部門に「**営業部**」を選ぶ（＝総務部を営業部の課に格下げしようとする）。

- **期待結果**: 値が空へ戻り、赤いトースト。
  > 課を持つ部門を課にはできません（階層は部・課の2階層まで）
- **確認ポイント**: 総務部は第一課・第二課（＋いま作った第三課）を持っているので、課にすると「部 > 課 > 課」の 3 階層になってしまう。それを**子の存在を数えて**止めている。
- **確認ポイント**: 逆に**課を持たない部**（例: 全社共通）なら、このガードには掛からない。組織を整理して部を課に降格する運用は、**先に配下の課を移すか無効化してから**、という順序になる。

→ **「登録」を押さずに**、サイドバーから部門一覧に戻る。

## ステップ 4: 課長行を足すと「承認者」が自動で点く（キャッシュ転記）

部門一覧 → **総務部 第三課**（さっき作った課）を開く。

「部門メンバー」の一覧で行を追加:

| 社員 | 役職 |
|---|---|
| `総務部 一般 藤井愛` | `課長` |

→ 「**登録**」。

- **期待結果**: メンバー行が 1 行保存される。

サイドバー「**組織/ユーザー管理**」→ `soumu_ippan`（藤井愛）の行を見る。

- **期待結果（本シナリオの山①）**: **「承認者」列にチェックが付いている**。ユーザー管理画面では触れなかったはずの欄が、**部門メンバーに課長行を 1 行足しただけで自動で点いた**。
  「部長」列は空のまま（部長行ではなく課長行なので）。
- **確認ポイント**: これが `is_approver` の DB トリガー転記。**正は役職行、チェックはその写し**。だからユーザー管理画面ではグレーアウトしている。
- **確認ポイント（役職を部長にしたら）**: 同じ行の役職を「**部長**」に変えて登録すると、「承認者」と「**部長**」の**両方**が点く。
  さらに `is_director` が ON になると、その人は**業務マスタの案件を編集できるようになる**（ADR-0046。経理でなくても基本情報だけ編集可・SES 契約条件は経理限定）。
  試したら**役職を「課長」に戻して登録**しておくこと。
- **確認ポイント（機能の見え方は変わらない）**: 藤井愛のサイドバーに「経費精算」「工数管理」以外が増えることは**ない**……と言いたいところだが、**承認者になったので「経営管理」が出る**（条件が `IsApprover ∨ HasAccountingAccess`）。
  一方で**営業業務・会計業務・購買・支払・業務マスタは出ない**——これらは機能フラグ（3 軸の①）が条件で、部門メンバー行では動かない。
  **「承認まわりだけが組織に追随し、業務機能はチェックボックスだけで決まる」**——これが 3 軸分離の境目。

### 元に戻す（このステップ分）

総務部 第三課 に戻り、**藤井愛の行を削除**して「**登録**」。

- **期待結果**: ユーザー管理で藤井愛の「承認者」チェックが**消える**。
- **確認ポイント**: ただし、**承認テンプレートに個人指名されている人は行を消しても承認者のまま**（`is_approver` の条件が OR のため）。例えば石川真理（soumu_kacho1）は「経費_課長まで＋総務」「経費_部長まで＋総務」に個人指名されているので、仮に課長行を外しても承認者は点いたまま。

## ステップ 5: 課長を空席にする（walk-up の準備）

部門一覧 → **開発2部 第二課** を開く。

- **確認ポイント（現状）**: 部門メンバーは `山口健太 / 課長`・`高橋健 / 一般` の 2 行。

**`山口健太 / 課長` の行を削除** → 「**登録**」。

- **期待結果**: 第二課のメンバーは `高橋健 / 一般` だけになる（＝課長空席）。
- **確認ポイント**: 組織/ユーザー管理で `kaihatsu2_kacho2`（山口健太）を見ると、**「承認者」チェックが消えている**。彼は他に課長/部長行を持たず、テンプレートにも指名されていないため。
- **⚠ 副作用（短時間で戻すこと）**: 承認者でなくなった山口健太は、**この間だけ経費の「承認待ち」画面に入れなくなる**（ExpenseApprover フレームのゲートが `IsApprover`）。
  彼には既存の承認待ち案件が 1 件あるので、**ステップ 7 の復元まで一気に進める**こと。

## ステップ 6: 空席の課から申請する → 部長へ繰り上がる（本シナリオの山②）

「**Logout**」→ **kaihatsu2_shinjin / kaihatsu2_shinjin**（開発2部 第二課 一般 高橋健）でログイン。

サイドバー「**経費精算**」→ 申請一覧 → 「**新規作成**」:

| 項目 | 入力値 |
|---|---|
| 件名 | `walk-up 確認 タクシー代` |
| 金額（税込） | `12,000` |
| 利用日 | 本日（既定） |
| 目的 | `課長空席時の承認ルート確認` |
| 申請区分 | `立替精算（支払済み）`（既定） |
| 支払先区分 | `社員へ精算`（既定・精算対象者=自分） |
| 費目 | `旅費交通費` |

→ 「**申請**」を押す（領収書未添付の黄色い警告は出るがブロックされない）。

- **期待結果**: トースト「申請しました」。承認フロー欄が

  `(▶開発2部 部長 加藤正雄,▶開発2部 部長代理 吉田直樹)`

  の **1 段・2 名並列**になる。
- **確認ポイント（walk-up）**: テンプレートは「経費_課長まで」＝**課長 1 段**のはずなのに、部長 2 名が出た。
  解決の道筋はこう:
  1. 申請者の所属ノード = **開発2部 第二課** → 課長を探す → **居ない**（ステップ 5 で消した）
  2. 親ノード = **開発2部** → 課長を探す → **居ない**（開発2部の直属メンバーは部長 2 名だけ）
  3. 課長がどこにも居ないので **director へ自動繰上げ** → 開発2部 第二課 に部長は居ない → 親の **開発2部** に部長 2 名（加藤正雄・吉田直樹）→ **この 2 名で確定**
  「課長空席時は部長へ」という**特例を書かずに**、walk-up という 1 つの規則の帰結として解決されているのがポイント（ADR-0044）。
- **確認ポイント（OR 並列）**: カッコで括られた 2 名は **OR**（`any`）。どちらか 1 人が承認すればこの段は完了し、**もう 1 人は Skipped** になる。同一ノードの同役職は同格、という考え方。
- **確認ポイント（比較）**: 課長が居れば `▶開発2部 第二課長 山口健太` の 1 名だけになる（→ `01_経費精算/01_立替精算の一巡.md`）。**同じ申請内容・同じテンプレートでも、組織の 1 行で承認者が変わる。**
- **確認ポイント（通知）**: 加藤正雄・吉田直樹の**両方**に「承認依頼」通知が飛ぶ。並列 OR は「同時に依頼し、早い者勝ちで完了」という運用になる。

### （任意）さらに空席にするとどうなるか

開発2部の部長 2 行も消すと、**経理代替**（経理機能を持つ有効ユーザーのうち Id 最小＝総務部 部長 山田太郎）へ落ちる。それも居なければ

> 承認者を決定できません: 部門の課長/部長の設定、または自己承認の代替となる経理ユーザーを確認してください（自己承認は禁止です）

で**申請そのものがブロックされ、承認ルートの行は 1 行も作られない**（中途半端な状態を残さない）。
この確認をした場合は、**開発2部の部長 2 行を必ず復元**すること（承認が広範囲に止まる）。

## ステップ 7: 後片付け

**必ず全部やること。** 組織を戻さないと、以後のシナリオの期待値がずれる。

### 7-1. 経費申請を消す（kaihatsu2_shinjin）

1. `walk-up 確認 タクシー代` を開く → 「**キャンセル**」→ トースト「キャンセルしました」。精算ステータスが「下書き」に戻る。
2. 「**この下書きを削除**」（赤）→ 確認ダイアログ「削除する」→ 一覧から消える。

- **確認ポイント**: 「申請中」一覧からも消えていること。
- **残るもの**: 加藤正雄・吉田直樹に飛んだ「承認依頼」通知 2 通は残る（既読にするか削除するかは任意）。削除した申請の子フロー行が DB に孤児として残るのも既知（画面には出ない）。

### 7-2. 開発2部 第二課の課長を復元（admin）

**admin** でログイン → システム管理 → 組織/**部門** → **開発2部 第二課** → 部門メンバーに行を追加:

| 社員 | 役職 |
|---|---|
| `開発2部 第二課長 山口健太` | `課長` |

→ 「**登録**」。

- **期待結果**: 組織/ユーザー管理で `kaihatsu2_kacho2`（山口健太）の「**承認者**」チェックが**戻る**。彼の承認待ち画面も再び開けるようになる。
- **確認ポイント**: 復元した行は**新しい行 ID** になるが、承認解決は「社員×役職」で行うので実害は無い。

### 7-3. 総務部 第三課を無効化

部門一覧 → **総務部 第三課** → 「**有効**」のチェックを外す → 「**登録**」。

- **確認ポイント**: メンバー行はステップ 4 で削除済み（残っていたら先に消す）。
- **⚠ 元に戻せない部分**: 部門には**削除導線が無い**（一覧からも詳細からも消せない）。無効化すると親部門候補・所属部門候補・伝票の部門候補から消えるので実害は無いが、`departments` に行は残る。
- **（任意・管理者作業）**完全に消す場合は DB から `departments` の `10-3` を削除する。この体験では第三課に伝票・工数・申請を紐づけていないので、参照は無く安全に消せる。

### 7-4. 変えていないことの確認

- 総務部の親部門が**空**のままであること（ステップ 3 は保存していないので、リロードすれば元どおり）。
- 藤井愛（`soumu_ippan`）の「承認者」「部長」が**両方とも空**であること。
- 開発2部の部長 2 行（加藤正雄・吉田直樹）が残っていること。

## つまずいたときは

- **課を作ったのにノード種別が dept のまま**: 親部門が入っていない。親部門を選んで登録し直す（トリガーは保存時に走るので、開き直して確認する）。
- **親部門のドロップダウンに目的の部が出ない**: 候補は「**部ノードかつ有効**」のみ。無効化した部は出ない。
- **課長行を足したのに承認者が点かない**: 役職が「一般」になっていないか確認。転記されるのは**課長・部長だけ**。
- **課長を消したのに承認者が点いたまま**: そのユーザーが**別の部門にも役職行を持っている**か、**承認テンプレートに個人指名されている**。`is_approver` は OR 条件。
- **walk-up が部長にならず、総務部 部長 山田太郎になった**: 部長行まで消えている（経理代替に落ちた）。開発2部の部長 2 行を確認。
- **申請時に「承認ルート判定に一致するルールがありません」**: 組織ではなく**承認ルート判定マスタ**の問題 → マスタ-03。
- **同じ人・同じ部門・同じ役職の行を 2 つ作れない**: DB のユニーク制約。**別役職・別部門の兼務行は作れる**（例: A 部の一般かつ B 課の課長）。
