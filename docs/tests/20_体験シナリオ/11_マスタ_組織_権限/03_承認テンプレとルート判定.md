# 体験シナリオ マスタ-03: 承認テンプレとルート判定（構成エラー・優先度・境界値・一致なし）

> 作成: 2026-08-09 ／ **更新: 2026-08-09 ADR-0048/0044 反映**（テンプレート 4 本の新名称・積み上げ構成を前提に全面改訂。旧版が「異常」として書いていた『経費_部長のみ に課長の順番が残っている』は、**ADR-0048 で正常な仕様になった**ため記述を反転。ステップ 6 の期待結果が「部長 2 名の 1 段」→「課長 → 部長の 2 段」に変わる）／ 所要時間: 約35分 ／ 影響: **承認テンプレート 1 本とルート判定ルール 1 行を追加**（ルールは削除して片付ける。テンプレートは一度使うと FK で削除できなくなるため残る＝完全消去は任意の SQL 作業）。既存ルール 3 行を一時的に無効化して**必ず戻す**。経費申請 2 本を作り、キャンセル→下書き削除まで行う
> 主役: **admin**（承認ガバナンスの編集）＋ **kaihatsu1_ippan**（開発1部 第一課 一般 小林美咲・申請して踏む役）。パスワードは全員ユーザー名と同じ。
> 「誰が承認するか」は**テンプレート**が決め、「どのテンプレートを使うか」は**ルート判定マスタ**が決める。この 2 段構えを、正常系だけでなく**わざと壊して**理解する。

## 物語

情シス（admin）が「図書研修費は総務が直接見る」という新しい決裁ルールを追加しようとしている。
ところが最初に組んだテンプレートは構成を間違えていて、申請者（小林美咲）が「申請」を押した瞬間にエラーで弾かれる。
2 度の構成エラーを直し、金額の境界を確かめ、最後は「どのルールにも当たらない」状態まで作って、承認ガバナンスの守りの厚さを味わう。

## 前提

| 項目 | 内容 |
|---|---|
| 2 段構え | **承認フローテンプレート** = 誰が何段で承認するかの型／**承認ルート判定** = 費目×金額でどのテンプレートを使うか。両方とも システム管理 > 承認 の配下 |
| ルート判定のアルゴリズム | 優先度の**小さい順**に評価 → 無効行はスキップ → 費目指定があれば申請の費目と一致するときのみ → `下限 ≦ 判定額 ≦ 上限`（**両端を含む**・上限空欄=上限なし）→ **最初に一致した行**を採用 |
| 判定額 | 立替精算 = 金額（税込）／事前申請 = 見込み額（実費確定後は実費） |
| テンプレートはコピーされる | 申請時にテンプレートの内容が申請側へ**複製**される。**後から編集しても既存の申請には影響しない** |
| 現状のルート判定（seed 5 行） | 10: 交際費 0〜29,999 → **経費_課長まで＋総務**／20: 交際費 30,000〜 → **経費_部長まで＋総務**／100: 全費目 0〜29,999 → **経費_課長まで**／110: 全費目 30,000〜199,999 → **経費_部長まで**／120: 全費目 200,000〜 → **経費_部長まで＋総務**（割り当ては ADR-0048 でも変えていない。変わったのはテンプレート名と中身） |
| テンプレートは積み上げ（ADR-0048） | 名前の規約は「**〜まで**」= 役職ラインの終端、「**＋総務**」= 合議段。`経費_課長まで` = 課長 1 段／`経費_部長まで` = **課長 → 部長の 2 段**／`経費_課長まで＋総務` = 課長 → 総務／`経費_部長まで＋総務` = **課長 → 部長 → 総務の 3 段**。金額が上がっても承認者は**入れ替わらず積み上がる** |
| 申請者 | 小林美咲（開発1部 第一課）。**自課の課長 = 山本由美 1 名**（walk-up で解決・隣の第二課長 中村拓也は候補にならない＝ADR-0044）、部 = 開発1部（部長 田中宏・部長代理 渡辺剛の 2 名 → 部長段で OR 並列） |
| 影響 | テンプレート 1 本（残る）／ルール 1 行（削除）／既存 3 行の一時無効化（戻す）／経費申請 2 本（削除）／承認依頼の通知 数通（残る） |

> **進め方のコツ**: admin と小林美咲を何度も行き来する。**通常ウィンドウで admin、シークレットウィンドウで小林美咲**を開いておくと、ログアウトの往復が要らず快適。
> **⚠ 実行中の注意**: ステップ 7 で全費目ルールを一時的に止める。その間、**他の人が経費申請すると全部ブロックされる**。ステップ 7 と後片付けは続けて一気に行うこと。

## ステップ 1: 承認フローテンプレートを読む

**admin** でログイン → サイドバー「**システム管理**」→ 承認/**承認フローテンプレート**。

- **確認ポイント**: 上部の説明文。
  > 経費承認ルートのテンプレート（課長のみ・部長＋総務 など）を管理します。どの申請にどのテンプレートを使うかは「承認ルート判定」で設定します。

  ⚠ **この説明文の例示（「課長のみ・部長＋総務」）は ADR-0048 以前の旧名称のまま**（画面文言の追随漏れ・改善提案のネタ）。実際の seed は下記の 4 本。
- seed は 4 本（すべて「〜まで」＝積み上げ方式・ADR-0048）:

| テンプレート | 承認順番 | 使われる場面（ルート判定の seed） |
|---|---|---|
| `経費_課長まで` | 課長（1 段） | 全費目 0〜29,999 |
| `経費_部長まで` | **課長 → 部長（2 段）** | 全費目 30,000〜199,999 |
| `経費_課長まで＋総務` | 課長 → 総務（2 段） | 交際費 0〜29,999 |
| `経費_部長まで＋総務` | **課長 → 部長 → 総務（3 段）** | 全費目 200,000〜／交際費 30,000〜 |

**「経費_課長まで＋総務」** を開く。3 階層の構造が読める:

```
テンプレート「経費_課長まで＋総務」    ← ①テンプレート（名前・説明）
 ├ 承認順番 0                          ← ②順番（この単位で順に回る）
 │   └ 承認者: 決め方=申請者の部門の課長 / 必須=✓   ← ③メンバー（同一順番内は並列）
 └ 承認順番 1
     └ 承認者: 決め方=指定ユーザー / 承認者=総務部 第一課長 石川真理 / 必須=✓
```

- **確認ポイント**: 画面の説明文がルールを全部言っている。
  > 承認順番を順に追加し、各順番に承認者を並列で追加します。必須=true なら全員必須、false なら誰か1人（同順番内に必須者がいない場合）。テンプレートはコピーされて使われるので、後から編集しても既存の申請には影響しません。
- **用語の対応**:
  - **順番** = 直列（前の段が終わってから次へ）。順番は**並べ替えで自動採番**される（手で番号を打たない）。
  - **同一順番内の複数メンバー** = 並列。**必須=✓ が 1 人でも居れば「必須の人は全員」**、必須が誰も居なければ「誰か 1 人」。
  - **承認者の決め方** は 3 択: `指定ユーザー` / `申請者の部門の課長` / `申請者の部門の部長`。後ろ 2 つは申請時に**申請者の組織から動的に解決**される（→ マスタ-02 の walk-up）。
- **確認ポイント（役職は「全員 OR」に化ける）**: 「申請者の部門の課長」1 人分のメンバー行が、申請時には**申請者の所属ノードから walk-up して見つかった最寄りの該当役職者全員**へ展開される（ADR-0044）。2 名以上なら OR 並列（1 人の承認で段が完了）。
  この組織では**課長は各課 1 名なので課長段は単独**、**部長は部長・部長代理の 2 名なので部長段が OR 並列**になる。
  だから**役職メンバーは同じ順番に他のメンバーと同居できない**——次のステップで、その禁止を実際に踏む。
- **確認ポイント（積み上げの実物を見る）**: 「**経費_部長まで**」を開いて、**順番が 2 つある**ことを確認する。

  ```
  承認順番 0 → 承認者: 決め方=申請者の部門の課長 / 必須=✓
  承認順番 1 → 承認者: 決め方=申請者の部門の部長 / 必須=✓
  ```

  名前は「部長まで」だが**課長を飛ばさない**。これが ADR-0048 の積み上げ方式で、3 万円以上でも自分の課の支出は課長が把握する、という実務に合わせたもの。
  同様に「経費_部長まで＋総務」は**順番が 3 つ**（課長 → 部長 → 総務）。
  もし「経費_部長まで」の順番が **1 つ（部長だけ）** しか無ければ、その環境は `Designer/ddl/460_approval_stacked_route.sql` が未適用の古い状態（ステップ 6 の期待結果が食い違う。→「つまずいたときは」）。
- **確認ポイント（積み上げと walk-up の噛み合い）**: 課長段と部長段が同居しているおかげで、**申請者の課の課長が空席／課長本人が申請**したときに課長段が部長へ繰り上がり、次の部長段と同じ承認者集合になるため**段が 1 つに圧縮**される（「部長のみ 1 段」になる）。特例を書かずに組織の実態から導かれる、というのが ADR-0044＋0048 の眼目（walk-up 自体の体験は → マスタ-02）。

## ステップ 2: わざと壊したテンプレートとルールを作る

### 2-1. テンプレートを作る

承認フローテンプレート → 「**新規作成**」:

| 項目 | 入力値 |
|---|---|
| テンプレート名 | `体験_テストルート` |
| 説明 | `マスタ-03 体験用。使い終わったら片付ける` |

「承認順番」に**順番を 1 つ**追加し、その中の「**承認者 (この順番で承認するメンバー)**」に**2 行**入れる:

| 承認者の決め方 | 承認者 | 必須 |
|---|---|---|
| `申請者の部門の課長` | （空。役職指定では使わない） | ✓ |
| `指定ユーザー` | `総務部 第一課長 石川真理` | ✓ |

→ 「**登録**」。

- **期待結果**: 保存できてしまう。**マスタ画面はこの矛盾を止めない**（構成の妥当性は、実際に展開する申請時に判定される）。
- **確認ポイント**: 「保存できる ≠ 使える」。ここが後で効いてくる。

### 2-2. ルート判定ルールを作る

サイドバー 承認/**承認ルート判定**。

- **確認ポイント**: 上部の説明文を読む。アルゴリズムがそのまま書いてある。
  > 経費の承認ルートを決める判定ルールです。優先度の小さい順に評価し、費目と金額（下限〜上限）が最初に一致した行のテンプレートが使われます。金額の判定は税込の申請額（事前申請は見込み額）で、下限・上限とも「その額を含む」、上限が空欄なら上限なしです。どのルールにも一致しない場合、申請はエラーでブロックされます。テンプレート内の「課長」「部長」は申請者の部門の役職者全員に並列で回り、1人の承認で先へ進みます。
- 一覧は**優先度の昇順**。5 行の seed が並んでいる。

「**新規作成**」:

| 項目 | 入力値 |
|---|---|
| 優先度 | `5` |
| 費目 | `図書研修費` |
| 金額下限(円) | `0` |
| 金額上限(円) | `29999` |
| 承認フローテンプレート | `体験_テストルート` |
| 説明 | `マスタ-03 体験用` |
| 有効 | ON（**新規作成時の既定**） |

→ 「**登録**」。

- **確認ポイント**: 「有効」が最初から ON なのは意図的な既定（作ったのに効かない、という罠の予防）。
- **確認ポイント**: 優先度 5 は seed の最小（10）より小さいので、**図書研修費はこのルールに真っ先に当たる**。全費目ルール（優先度 100）にはもう届かない。

## ステップ 3: 混載エラーを踏む（役職指定は単独の段でなければならない）

「**Logout**」→ **kaihatsu1_ippan / kaihatsu1_ippan**（小林美咲）でログイン。

サイドバー「**経費精算**」→ 申請一覧 → 「**新規作成**」:

| 項目 | 入力値 |
|---|---|
| 件名 | `ルート判定テスト 技術書` |
| 金額（税込） | `29,999` |
| 利用日 | 本日（既定） |
| 目的 | `承認テンプレートの構成確認` |
| 申請区分 | `立替精算（支払済み）`（既定） |
| 支払先区分 | `社員へ精算`（既定） |
| 費目 | `図書研修費` |

→ 「**申請**」を押す。

- **期待結果**: 赤いトースト。
  > 承認テンプレート構成エラー: 役職指定の承認者は単独の承認段階にしてください
- **確認ポイント（何が起きなかったか）**: 申請は**保存すらされていない**。一覧に戻っても行は増えていないし、承認ルートの行も**1 行も作られていない**。
  テンプレート展開は「全メンバーを先に検証してから作る」二段構えになっていて、**途中で失敗しても中途半端な承認段を残さない**。承認基盤で一番大事な性質。
- **確認ポイント（なぜ禁止か）**: 「申請者の部門の課長」は申請時に**複数人へ展開される**。同じ段に固定の指名者が混ざると「課長 2 名＋石川真理の 3 人並列、必須は全員」なのか「課長のうち 1 人＋石川真理」なのか、意味が決まらない。だから**役職メンバーは単独の段**という制約にしている。
- **入力内容はこのまま残しておく**（ブラウザのタブを閉じない）。ステップ 4・5 で「申請」を押し直す。

## ステップ 4: 承認者未設定エラーを踏む

**admin** に戻る → システム管理 → 承認/承認フローテンプレート → `体験_テストルート` を開く。

1. 順番の中の「**申請者の部門の課長**」の行を**削除**する。
2. 残った「指定ユーザー」の行の**承認者を空**にする（`石川真理` を外す）。

→ 「**登録**」。

**小林美咲**の申請フォームに戻り、もう一度「**申請**」を押す。

- **期待結果**: 赤いトースト。
  > 承認テンプレートに承認者未設定のメンバーがあります
- **確認ポイント**: 混載は解消したが、今度は**指名先が空**。決め方が「指定ユーザー」なのに承認者が入っていないと、誰にも回せない。これも**申請時に**初めて発覚する（マスタ画面では保存できてしまう）。
- **確認ポイント（他の構成エラー）**: 同じ検証で拾われるものがあと 2 つある。作るのは任意:

| 状況 | メッセージ |
|---|---|
| 承認段階（順番）が 0 個のテンプレート | 承認テンプレートに承認段階がありません |
| 役職も指名も誰にも解決できない | 承認者を決定できません: 部門の課長/部長の設定、または自己承認の代替となる経理ユーザーを確認してください（自己承認は禁止です） |

## ステップ 5: 直すと通る — 費目指定が全費目に勝つ（境界の下側 29,999）

**admin** → `体験_テストルート` → 残っているメンバー行の**承認者に `総務部 第一課長 石川真理`** を設定 → 「**登録**」。

- テンプレートは「順番 1 つ・メンバー 1 人（石川真理・必須）」というシンプルな形になった。

**小林美咲**の申請フォームで、もう一度「**申請**」。

- **期待結果**: トースト「申請しました」。承認フロー欄が

  `▶総務部 第一課長 石川真理`

  の **1 段・1 名**。
- **確認ポイント（本ステップの主目的）**: **課長の山本由美は出ていない**。
  もし全費目ルール（優先度 100: 0〜29,999 → 経費_課長まで）が採用されていれば `▶山本由美` になったはず。
  **優先度 5 の費目指定ルールが先に一致して打ち切られた**——「優先度の小さい順に評価し、最初に一致した行で確定」という first-match が効いている証拠。
- **確認ポイント（費目指定と全費目の関係）**: 費目を指定した行は「その費目のときだけ候補になる特例」、費目が空欄の行は「どの費目にも当たる一般則」。
  **どちらが勝つかは優先度の数字だけで決まる**（費目指定だから強い、という暗黙のルールは無い）。seed が交際費ルールを 10・20、全費目ルールを 100・110・120 に置いているのは、**特例を上に、一般則を下に**という並べ方の慣習にすぎない。
  → 特例を作るときは「一般則より小さい優先度を付ける」ことを忘れると、**作ったのに一度も当たらないルール**ができる。
- **確認ポイント（29,999 = 境界の下側）**: いま入れた 29,999 は作ったルールの**上限そのもの**。`下限 ≦ 判定額 ≦ 上限` で**両端を含む**ので一致する。

## ステップ 6: 1 円増やすと落ちる（境界の上側 30,000）

**小林美咲**のまま、申請一覧 → 「**新規作成**」:

| 項目 | 入力値 |
|---|---|
| 件名 | `ルート判定テスト 技術書2` |
| 金額（税込） | `30,000` |
| 目的 | `境界値の確認` |
| 費目 | `図書研修費`（ステップ 3 と同じ） |

→ 「**申請**」。

- **期待結果**: 承認フロー欄が

  `▶開発1部 第一課長 山本由美 →(開発1部 部長 田中宏,開発1部 部長代理 渡辺剛)`

  の **2 段**（1 段目=課長・単独／2 段目=部長 2 名の OR 並列）。▶ が付いているのは 1 段目だけで、**部長にはまだ通知が飛ばない**（順次到達）。
- **確認ポイント（何が起きたか）**: 判定額 30,000 は作ったルール（0〜29,999）の**上限を 1 円超えた**ので不一致 → 交際費ルール（10・20）は費目違いでスキップ → 全費目 0〜29,999（100）も不一致 → **全費目 30,000〜199,999（優先度 110）で一致** → テンプレート「経費_部長まで」。
  **費目指定の特例から一般則へ、静かに落ちる**。この「フォールスルー」が意図どおりかは、ルールを作るたびに確認する価値がある。

## つまずいたときは

- **「経費_部長まで」というテンプレートが見当たらない／「経費_部長のみ」のままになっている**: `Designer/ddl/460_approval_stacked_route.sql`（ADR-0048）が未適用の環境。460 は冪等なので適用すれば改名と課長段の挿入が同時に済む。
  旧名称のままだと 30,000〜199,999 の申請が「**部長 1 段**」になり、ステップ 6 の期待結果（課長 → 部長の 2 段）と食い違う。
- **「経費_部長まで」の順番が 1 つしかない**: 改名は済んでいるが課長段の挿入が効いていない（460 の 2) 節を再実行する）。**逆に順番が 2 つあるのが現行の正**——旧版の本書はこれを「異常」と書いていたが、ADR-0048 で仕様が反転している。
  なお、seed 元の `Designer/ddl/090_approval_route.sql` は**歴史記録としてそのまま残してある**（460 が上書きする）ので、090 を読んで「部長 1 段が正」と誤読しないこと。
- **テンプレートを直したのに、進行中の申請のルートが変わらない**: 仕様。テンプレートは**申請時にコピー**されるので、既存の申請には影響しない。新しく申請し直せば新しい構成で回る。
- **「承認者を決定できません…」が出る**: テンプレートではなく**組織側**の問題（課長も部長も居ない／全員が申請者本人／経理代替も居ない）→ マスタ-02。
- **作ったルールが一度も当たらない**: 優先度が既存ルールより**大きい**（＝後回し）ため、先に一般則に当たっている。優先度の数字を小さくする。
- **金額の境界がずれる**: 下限・上限とも**その額を含む**。「30,000 円未満」を表したいなら上限は `29999`。
- **一覧の削除ボタンが見当たらない**: 削除できるのは**承認フローテンプレート**と**承認ルート判定**だけ。ユーザー・部門・取引先・勘定科目には削除導線が無い（無効化で運用する）。
- **事前申請だと判定額が違う**: 事前申請は**見込み額**で判定し、実費確定後は**実費**で判定し直す（超過時は自動で再承認）→ `01_経費精算/07_事前申請_超過再承認.md`。
