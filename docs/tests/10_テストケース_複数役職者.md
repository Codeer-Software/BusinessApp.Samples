## 1. テストフィクスチャ

### 1.1 ユーザー（既存4名＋追加2名）

| ユーザー | ログイン | ロール | 所属 | 役職（department_managers） |
|---|---|---|---|---|
| システム 管理者 | admin / admin | accounting | 開発1部 | なし（申請者役） |
| 承認 花子 | hanako / hanako | approver | 開発1部 | **課長**（既存データ移行分） |
| 部長 次郎 | jiro / jiro | approver | 開発1部 | **部長**（既存データ移行分） |

### 1.2 準備手順

1. **ユーザー追加は UI で行う**（パスワードハッシュのため SQL 直挿入は不可）: admin でログイン → ユーザー管理 → 「課長 健太」(kenta/kenta, approver, 所属=開発1部)・「部長 五郎」(goro/goro, approver, 所属=開発1部) を作成
2. **役職の追加は部門マスタ画面で行う**（それ自体が M-10 のテスト）: 部門マスタ → 開発1部 → 役職者リストに 健太=課長・五郎=部長 を追加
3. フィクスチャ検証 SQL（実施前に必ず流す）:

```sql
-- 開発1部の役職構成（期待: hanako=manager, kenta=manager, jiro=director, goro=director の4行）
SELECT dm.id, d.name AS dept, u.user_name, dm.role
FROM department_managers dm
JOIN departments d ON d.id = dm.department_id
JOIN app_users u ON u.id = dm.user_id
ORDER BY d.name, dm.role, u.user_name;
-- 申請者の所属（期待: admin/hanako/jiro/kenta/goro=開発1部, soumu=管理部）
SELECT u.user_name, d.name FROM app_users u LEFT JOIN departments d ON d.id = u.department_id;
```

### 1.3 共通検算 SQL（各ケースの「確認ポイント」で使用）

```sql
-- 最新フローの Order/Member 状態一覧
SELECT f.id AS flow, o.order_no, o.status AS order_st, o.approval_type,
       u.user_name AS approver, m.status AS member_st, m.is_required
FROM approval_flow f
JOIN approval_flow_order o ON o.approval_flow_id = f.id
LEFT JOIN approval_flow_member m ON m.approval_flow_order_id = o.id
LEFT JOIN app_users u ON u.id = m.approver_user_id
WHERE f.id = (SELECT MAX(id) FROM approval_flow)
ORDER BY o.order_no, m.id;

-- 受信箱ビューの中身（誰の受信箱に何が出ているか）
SELECT v.id, u.user_name AS approver, v.parent_module_name, v.parent_id
FROM approval_inbox_view v JOIN app_users u ON u.id = v.current_approver;

-- 通知の宛先確認（直近10件）
SELECT n.id, u.user_name AS recipient, n.title, n.is_read
FROM notifications n JOIN app_users u ON u.id = n.recipient_user
ORDER BY n.id DESC LIMIT 10;
```

> 注: テーブル・ビュー名（department_managers / approval_inbox_view / notifications）は実装時の実名に合わせて読み替えること。
