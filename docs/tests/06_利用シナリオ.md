# 利用シナリオ集（総合テスト用）

> 作成: 2026-07-06 ／ 全面追随: 2026-07-19（ADR-0026/0027/0028）／ 更新: 2026-08-02（部品アーキテクチャ再編 ADR-0040/0041 反映）／ **更新: 2026-08-09 現行化（ADR-0042〜0048）**
> **2026-08-09 現行化の要点**: ①冒頭の画面表記ブロックを**全員ポータル着地＋ Main 左サイドバー＋フレーム素 URL**に全面書き換え（`/{フレーム}/Top`・権限別の自動転送・「ほかの業務」・ホームの切替ボタンはすべて廃止＝ADR-0042/0045）。②フィクスチャ表の「権限」列を**機能権限フラグ**に（ADR-0043。部門メンバーシップは組織の事実であって見え方には影響しない）。③S-01〜S-03 の承認ルートを**積み上げ方式**（ADR-0048）＋ **walk-up＝自課の課長**（ADR-0044）に。④S-09（権限の境界）を直接フラグ・walk-up 前提に再構成。⑤**S-19 を「ホーム」から「業務ポータル」に書き換え**（docs/13 §3 の表示項目一覧＝やること 4・作業キュー 3・アラート 4・KPI・管理者案内）。⑥案件は**部長にも開放**（ADR-0046）。**業務ロジックの期待値（金額・仕訳・状態遷移・検算クエリ）は一切不変。**
> 目的: 典型的なユーザーストーリーに沿って「こんな操作をしたらこんな結果が得られる」を確認する総合テストの台本（ユーザー要望）。
> 実装済みの全機能（フェーズ A 会計コア／B 周辺業務／B' 管理会計／D 拡張）を、**一般メンバー・承認者（課長/部長）・経理・システム管理者**の4つの権限視点で網羅する。
> 各シナリオは独立して読めるが、S-01→S-19 の順に流すと「申請→承認→会計→帳票→経営分析」の一連のストーリーになる。
> **より詳細な期待値（金額・トースト文言・仕訳番号まで固定した完全版）は docs/tests/11_E2Eテストシナリオ が正**。本書は機能単位の再確認・回帰テスト用の軽量版。
> **画面表記（2026-08-09 現行・ADR-0042〜0047）**:
> - **着地**: ログインすると**権限にかかわらず全員が業務ポータル**（`/` = Main フレームの `PortalHome`）に着地する。**旧「権限に応じたホームへの自動転送」は無い**（管理者→MasterAdmin／経理→Accounting … の振り分けは廃止）。
> - **業務への移動**: **Main 左サイドバー**（`Shell/PortalSidebar`）に一本化。**「ほかの業務」リンク・「マイページ」・ホーム画面の切替ボタン・部品別ホーム（ExpenseHome／SalesHome／AccountingHome／AdminHome）はすべて廃止**。業務から業務へは「フレームのサイドバー先頭『**ホーム**』→ ポータルのサイドバー『○○』」。最上部のブランドは「**よろず** ／ 統合業務基盤アプリ」（ADR-0047・旧称「帳合」）でクリックするとポータルに戻る。**Logout はサイドバー最下部**（英語表記・確認ダイアログなしで即ログアウト）。
> - **サイドバーのリンクと表示条件**（遷移先は変種解決＝経理 > 承認者 > 一般の順で最初に該当したフレーム）: 通知（常時・未読があれば「**通知 (N)**」）→ `/Main/Notification` ／ 経費精算（`CanUseExpense`）→ ExpenseAccounting > ExpenseApprover > ExpenseStaff ／ 工数管理（`CanUseTimesheet`）→ TimesheetAccounting > Timesheet ／ 営業業務（`HasSalesAccess` ∨ `HasAccountingAccess`）→ SalesBilling > SalesStaff ／ 会計業務・購買・支払・業務マスタ（`HasAccountingAccess`）→ Accounting／Purchasing／MasterBusiness ／ 経営管理（`IsApprover` ∨ `HasAccountingAccess`）→ ManagementFull > ManagementApprover ／ システム管理（`IsSysAdmin`）→ MasterAdmin。
> - **URL**: **フレーム素の URL**（`/Accounting`・`/ExpenseStaff` など）を開くとそのフレームの**既定業務画面**に着地する。**`/{フレーム名}/Top` は全廃**（着地: ExpenseStaff=申請／ExpenseApprover=承認待ち／ExpenseAccounting=精算処理待ち／Timesheet・TimesheetAccounting=工数入力／SalesStaff=見積／SalesBilling=請求書／Accounting=振替伝票／Purchasing=仕入先請求書／ManagementApprover・ManagementFull=予実対比／MasterBusiness=取引先／MasterAdmin=ユーザー管理）。個別画面は従来どおり `/{フレーム名}/{セグメント}`（例: `/Accounting/JournalEntryBoard`）。**権限外のフレームは直 URL も「ページフレームへのアクセス権限がありません」**（Main だけはゲート無しで全員入れる）。
> - **権限**: 見え方を決めるのは **`AppUser` の機能権限フラグ 5 本**（営業機能／経理機能／経費精算〔既定 ON〕／工数入力〔既定 ON〕／システム管理者。ADR-0043）。**部門メンバーシップ（一般/課長/部長）は組織の事実と承認ルートの正であり、画面の見え方には影響しない**。導出キャッシュは `IsApprover`（課長/部長行がある ∨ テンプレートの個人指名）と `IsDirector`（部長行がある。案件の書込条件＝ADR-0046）の 2 本だけで、いずれも閲覧専用（DB トリガー保守）。
> - **メニュー表記**: 本書は「グループ/リンク」またはリンク名で書く（例:「帳簿/出納帳」「精算処理待ち」）。**通知一覧は `/Main/Notification`** に一本化（経費フレームの通知メニューは廃止・既定は未読のみ表示）。会計年度は全画面で「**第18期（2026年度）**」形式。
> 操作の原則（ADR-0026/0027）: **「状態」は全画面で表示専用**、遷移は青ボタン（前進）と赤ボタン（削除・取消・巻き戻し）だけで行う。一覧に削除ボタンは無く、削除は詳細画面の赤ボタン（状態条件つき・確認ダイアログつき）。誤操作は各画面の「〜を取り消す」「下書きに戻す」で巻き戻せる（仕訳を生んだ操作の取消は該当仕訳も削除。締め済み期間は不可＝赤伝対応）。

## S-01 経費申請（立替・少額）→ 課長承認 【一般社員・承認者】

**ストーリー**: 開発部の社員が 3 万円未満の旅費を立て替えたので精算したい。

1. kaihatsu1_ippan でログイン（**業務ポータルに着地**）→ 左サイドバー「**経費精算**」（`CanUseExpense`。このユーザーは ExpenseStaff に解決され「申請」に着地）→ サイドバー「申請」> 新規作成
2. 件名・金額（例 8,000）・利用日・費目=旅費交通費 を入力 → 申請区分は既定の「立替精算」、精算対象者は既定で本人
3. 「申請」を押す
- **期待**: トースト「申請しました」。フロー表示「状態:進行中 ✓(申請者)→(▶第一課長 山本由美)」（3万未満 → テンプレート **`経費_課長まで`** が自動選択。承認者は**申請者の自課（第一課）の課長**＝山本由美の単独。隣の第二課の中村拓也には回らない＝walk-up・ADR-0044）。精算ステータス=申請中。**山本由美に通知**（承認依頼）が作成される
4. kaihatsu1_kacho1 でログイン → **業務ポータル**の「▶ あなたの承認待ち: 1 件」または「未読の通知」に承認依頼 → 「開く」
- **期待**: 該当申請へ遷移し通知が既読化。申請内容は編集不可（グレーアウト）
5. 「承認」を押す
- **期待**: 状態=承認済・精算ステータス=承認済。**申請者に「承認されました」通知**

**バリエーション（ADR-0048 の積み上げ方式）**: 金額 3万〜20万 → **課長 → 部長**の2段（2段目は 部長 田中宏・部長代理 渡辺剛の**並列 OR**。1人の承認で先へ進む）。20万以上 → **課長 → 部長 → 総務**の3段。**金額が上がっても承認者は入れ替わらず段が積み上がる**（自分の課の支出は必ず課長が把握する）。ただし**課長が空席の課・課長本人の申請では、課長段が部長へ繰り上がって部長段と重複するため段が1つに圧縮**され「部長のみ」になる（特例を書かずに walk-up の帰結として解決される＝ADR-0044/0048）。却下するとステータスが下書きへ戻り申請者が再申請できる。

## S-02 交際費申請（例外項目＋総務併載） 【一般社員】

**ストーリー**: 取引先との会食費を精算したい。交際費はコンプライアンス上、相手先の記録と総務の確認が必須。

1. kaihatsu1_ippan で経費新規作成 → 費目=**交際費** を選ぶ
- **期待**: 「接待の相手先・参加人数・接待の目的」の3項目が**出現**する
2. 3項目を空のまま「申請」
- **期待**: 赤トースト「交際費は相手先・参加人数・目的の入力が必須です」で**ブロック**される
3. 3項目を入力して申請
- **期待**: 金額が3万未満でも**課長→総務**の2段ルート（テンプレート `経費_課長まで＋総務`。交際費は常に総務併載。総務段はテンプレートの個人指名＝soumu_kacho1）。**3万以上の交際費は 課長 → 部長 → 総務 の3段**（`経費_部長まで＋総務`）——少額の会食にだけ部長を挟まないのが意図的な例外（ADR-0048）

## S-03 事前申請 → 実費超過 → 自動再承認 【一般社員・承認者】

**ストーリー**: 出張前に見込み 25,000 円で事前申請し承認を得たが、実費は 40,000 円かかった。

1. kaihatsu1_ippan で経費新規作成 → 申請区分=**事前申請** に変更
- **期待**: 「見込み額」欄が出現（立替では非表示）
2. 費目=旅費交通費・見込み額 25,000 で申請 → 山本由美（自課の課長）が承認
3. kaihatsu1_ippan で申請を開く → 「実費（税込）」欄に 40,000 → 「実費を確定」
- **期待**: 区分跨ぎ（3万超え）＋見込み×110%超のため**自動で再承認へ**。トースト「実費が見込みを超過したため再承認を依頼しました」。ルートが**課長 → 部長の2段**（`経費_部長まで`。1段目=山本由美／2段目=部長 田中宏・部長代理 渡辺剛の並列）に再解決され、履歴に超過理由が記録される（再解決は**申請者基準**——経理が代行確定しても申請者本人が承認者に入らない）
4. 山本由美がもう一度承認 →（1段目の承認で初めて部長へ通知が飛ぶ）→ kaihatsu1_bucho（または buchodairi）が承認 → 経理処理へ進める

**バリエーション**: 実費 26,000（区分内・110%以内）なら再承認は走らず、そのまま仕訳生成可能になる。

## S-04 経理処理: 仕訳生成 → 支払 → 出納帳 【経理】

**ストーリー**: 承認済の経費を会計に取り込み、精算金を支払う。ここからは経理専用の世界（A×B 一体化の接点）。

1. soumu_bucho（経理）でログイン → ポータルの左サイドバー「**経費精算**」（経理なので **ExpenseAccounting** に解決され「精算処理待ち」に着地）→ 承認済の経費を開く
- **期待**: 「仕訳を生成」ボタンが見える（**承認者には見えない**）
2. 「仕訳を生成」
- **期待**: トーストに伝票 No と金額。仕訳は D 費目の既定科目（税抜本体）＋ D 仮払消費税 ／ C 未払金（税込）。仕訳帳・試算表に即反映。ステータス=経理処理中。**備品×10万円以上の申請は D が工具器具備品になり、固定資産台帳へ自動登録**（EXP-{id}、取得価額=税抜）。利用日の期間が締め済みなら**本日日付に自動フォールバック**（摘要に利用日を記載・トーストで通知）
3. 「精算済にする」
- **期待**: 支払仕訳（D 未払金／C 普通預金）が自動生成。会計（Accounting）の「帳簿/出納帳」（普通預金）に出金行が現れ残高が減る
4. 「完了にする」 → ステータス=完了

## S-05 販売サイクル: 見積→受注→検収→請求→入金 【営業＋経理】

**ストーリー**: 受託案件の商談から入金までを一気通貫で管理する。売上計上は検収基準（ADR-0008）。
**操作**: soumu_bucho（経理）なら営業請求・入金（SalesBilling）で全ステップを通しで実行できる。営業視点を確認する場合は 1〜3 を eigyo_ippan または kaihatsu1_kacho1（営業兼務）の SalesStaff で行う（請求書・入金のメニューは SalesBilling にのみあり、確定・消込は経理のみ）。

1. 「見積」> 新規作成: 取引先・件名・明細（数量×単価で金額自動計算・税抜合計表示）→ 保存（Q-26-xxx 採番）。「見積書を出力（Excel/PDF）」で帳票も確認できる。状態は表示専用で、下書きでは「送付済にする」「受注にする」「失注にする」「この見積を削除」のボタンが並ぶ
2. 「受注にする」

**バリエーション**: 先方が振込手数料を差し引いた入金（差額≦1,000円）は支払手数料として**自動処理**され全額消込。請求残額を超える入金は**過入金ガード**で拒否（前受金の手動起票へ誘導）。誤入金の確定は「入金を取り消す」で消込仕訳を削除し請求書ステータスを再計算できる。

**変更契約の運用規約**（詳細な検討は docs/issues/ISSUE-0002）:

1. **増額・追加スコープは「差分文書の追加」で表す**: 変更契約分を新しい見積として起こし（件名規約: 「元件名 変更契約①: 追加内容」）、「受注にする」→ **元契約と同一の案件**に紐付ける。以後は独立した受注として検収・請求まで流す（案件損益は案件単位で自動合算）。既存の受注明細を直接書き換えない——検収が登録された受注はシステム側でも編集不可。
2. **減額・値引きは検収額の手修正で表す**: 検収時に検収額を減額する（マイナス明細の受注は作らない。検収確定は金額>0のため単独検収できない）。
3. **合算請求**: 当初契約と変更契約の請求を1枚にまとめたい場合は、**手動請求書**（請求書>新規作成）に両方の明細を記載して発行する。その後、各検収の「合算先請求書」欄でその請求書を選択すると「請求書を作成」ボタンが消えて合算済みラベルに変わる（二重請求防止）。
4. **検収確定後の変更**は逆操作チェーン（入金取消→請求書取消→確定取消）で巻き戻してからやり直す。締め済み期間は赤黒訂正。

- **期待**: まず**プレビュー（未登録・専用テーブル）**に入る。原本 6 列をその場で修正・行削除でき（「プレビューの変更を保存」で確定）、「全てのプレビューを取り消す」で貼り直し可。「この内容で登録」で未起票の明細へ確定——このとき摘要に AWS/家賃/振込手数料等を含む行は**仕訳ルールで相手科目が自動セット**（推定元=rule）。同じ CSV を再取込しても**重複スキップ**
2. 「銀行/一括起票」 → 既に帳簿計上済みの明細（入金消込・経費支払など）は「対象外」にチェック →「変更を保存」
- **期待**: 対象外の行は excluded になり一覧から外れる（明細一覧の詳細画面「未起票に戻す」で差し戻せる）
3. 「AIで相手科目を推定」
- **期待**: ルール未該当の明細に AI が科目を提案（推定元=ai。実キー設定時は実 AI）。候補はドロップダウンで手修正できる（推定元=manual）。**AI・ルールの結果は「変更を保存」または起票まで DB に書かれない**
4. 「候補科目で一括起票」→ 確認ダイアログ
- **期待**: 明細ごとに仕訳が生成（課税科目は本体＋仮払/仮受消費税の税行に分解・日付は明細の日付）。明細は起票済みになり伝票No が付き、一括起票の一覧から消える
5. 「銀行/残高照合」
- **期待**: 日付ごとに 明細残高＝帳簿残高・差額0・判定「○ 一致」。未起票明細が残っていれば差額の原因として件数表示
6. 「銀行/仕訳ルール」: 新しい摘要パターン（例: 新しい取引先）をルール登録 → 次回から自動判定（優先度昇順で最初の1件だけ適用）
7. 「銀行/明細一覧」: 全状態の通帳ビュー（表示専用）。行クリックの詳細画面で 対象外化⇄差し戻し・**起票の取り消し**（紐づく仕訳ごと削除・締め済み期間は赤伝誘導）・明細の削除（キー解放）ができる

## S-14 定型仕訳で毎月の繰り返し仕訳をワンタッチ起票 【経理】（フェーズ D-4）

1. 「仕訳/定型仕訳」 → 「給与の支払」を開く（給与総額/預り金/振込額の3行構成）
2. 「この定型から伝票を起票」
- **期待**: 本日日付の**下書き伝票**が作成され、振替伝票画面へ自動遷移
3. 金額を当月の給与計算結果に修正 → 「確定」
- **期待**: 貸借一致チェック→採番→確定。家賃テンプレ（課税仕入・内税）は確定時に消費税行が自動生成される（定型には税行を持たせない＝税率改正に自動追随）

## S-15 仕訳 CSV インポート（他ソフトからの移行・給与データ取込） 【経理】（フェーズ D-5）

**ストーリー**: 移行元ソフト（弥生等）や給与ソフトが出力した仕訳データを一括で取り込む。

1. 「仕訳/仕訳インポート」 → CSV（伝票グループ,日付,借貸,科目コード,金額,税区分コード,摘要）を貼り付け → 「取り込む」
- **期待**: 伝票グループ単位で検証（科目実在・貸借一致・締め済み期間ガード）し、OK の伝票のみ確定で取込・再採番。NG 伝票は理由付きでスキップ報告。**行は無加工で取り込む**ため移行元と1円もズレない。税科目行（1900/2200）は税行として自動マークされ消費税集計の税額側に載る
2. 「下書きとして取り込む」を ON にすると draft で入る（内容を確認してから個別に確定する運用）
3. 取込後、試算表・仕訳帳で検算（Σ借方=Σ貸方）

## S-16 買掛・支払管理と支払予定表 【経理】（フェーズ D-6）

1. 購買・支払（Purchasing）の「仕入先請求書」 → 新規（仕入先・請求日・支払期限・費用科目・税込金額）→ 保存。反復請求は「この請求書を複製」で前月分から起こせる（費用科目の候補は費用・資産科目に絞られる）
2. 「未払計上（仕訳生成）」
- **期待**: D 費用科目(本体)+仮払消費税 / C 買掛金 の仕訳（請求日で発生主義計上）。状態=未払計上済。誤操作は「未払計上を取り消す」（赤）で仕訳ごと受領に戻せる
3. 「支払予定表」 → 期限順に一覧・合計行・期限超過は「⚠」/7日以内は「まもなく」
4. 「支払登録（消込仕訳）」→ D 買掛金 / C 支払口座。状態=支払済・予定表から消える（誤操作は「支払を取り消す」で仕訳ごと未払計上済に戻せる）
5. 「振込データ作成」 → 未払計上済の請求書から全銀フォーマット（120桁固定長）の総合振込データを生成・様式自己検証つき
6. 検算: 買掛金残高 = 未払計上済かつ未払いの請求額合計

## S-17 SES 精算幅の自動請求 【経理】（B'-5）

1. 業務マスタ（MasterBusiness）の「案件」（経理）→ SES 案件に契約条件（月額基本・精算幅 140〜180h・控除/超過単価）を設定
2. 工数管理（Timesheet）の「工数入力」で当該月の実績を入力（例: 190h）
3. 「SES精算・請求」（SalesBilling） → 対象月 → 「精算を計算」
- **期待**: 「基本 800,000（精算幅 140〜180h・実績 190h00m）＋ 超過 10h×4,500 = 845,000」の内訳プレビュー（請求書は未生成）
4. 「請求書を一括生成（売上仕訳込み）」→ INV（税込）＋ SES売上高の売上仕訳（全行に案件付き→案件損益へ自動反映）。再実行はスキップ（冪等）

## S-18 SaaS 年額プランの前受計上と按分 【経理】（磨き: 年払い）

1. 「定期請求契約」（SalesBilling） → 課金サイクル=年額・年額（税抜）を設定して保存（下書き）→ 経理が「確定する」（実行対象は「確定済」かつ「有効」の契約のみ）
2. 「定期請求の実行」（SalesBilling） → 起点月に実行
- **期待**: 年額請求書＋前受計上仕訳（D 売掛金税込 / C 前受収益＋仮受消費税）＋当月分の按分振替（D 前受収益 年額/12 / C SaaS売上高）
3. 翌月以降の実行 → 按分振替のみが毎月積み上がる（前受収益残高が月次で減少）。再実行は常にスキップ（冪等）

## 検算クエリ（テスト後の整合確認）

sql CLI（`BusinessApp.Designer.exe sql ... --datasource BusinessAppSQLite`）で:

```sql
-- 全 posted 仕訳の貸借一致（常に等しいこと）
SELECT SUM(CASE WHEN dc='D' THEN jl.amount ELSE 0 END) AS 借方,
       SUM(CASE WHEN dc='C' THEN jl.amount ELSE 0 END) AS 貸方
FROM journal_lines jl JOIN journal_entries je ON je.id=jl.journal_entry_id
WHERE je.status='posted';

-- 伝票番号の重複ゼロ（年度内連番）
SELECT COUNT(*) FROM (SELECT fiscal_year_id, journal_no, COUNT(*) c
FROM journal_entries GROUP BY fiscal_year_id, journal_no HAVING c > 1);

-- 売掛金残高 = 未入金請求の残額合計（導出主義の照合）
SELECT (SELECT SUM(CASE WHEN dc='D' THEN amount ELSE -amount END)
        FROM journal_lines jl JOIN journal_entries je ON je.id=jl.journal_entry_id
        JOIN accounts a ON a.id=jl.account_id
        WHERE a.code='1100' AND je.status='posted') AS 売掛金残高;

-- 期首残高の貸借一致（繰越後の翌期。0 であること）
SELECT fiscal_year_id, SUM(balance) FROM opening_balances GROUP BY fiscal_year_id;
```
