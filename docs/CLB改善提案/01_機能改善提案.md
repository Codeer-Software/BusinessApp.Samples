CLB 本体への機能改善提案。書式と運用ルールは [README](README.md) を参照する。

### FB-001【高】予約名フィールドの型違いを designcheck が検出しない

- **発見日**: 2026-08-24
- **CLB バージョン**: ランタイム 1.3.20 / デザイナ 1.3.20 / Extras 0.5.0
- **症状**: 予約名 `OptimisticLocking` を `NumberFieldDesign`、`Creator` / `Updater` を
  `NumberFieldDesign` で定義したモジュールで、一覧・詳細は正常に表示・検索できるのに、
  **更新すると必ず「更新に失敗しました」**になる。`designcheck` は `findingCount: 0`、
  `POST /api/module_data` は **200 を返し**、サーバのコンソールにも例外は出ない。
  ブラウザのコンソールに `Update failed` の 1 行が出るだけで、原因を示す情報がどこにも無い
- **なぜ困るか**: 「designcheck が緑」「HTTP 200」「サーバログに例外なし」が揃うため、
  DB 制約・データ・レイアウトのどこを疑えばよいか手がかりが無い。マスタ 5 本を作った直後に踏み、
  切り分けに 30 分以上を要した。予約名の一覧はマニュアル（CommonMistakes #42-A）に書かれているが、
  **書かれていることと、破ったときに検出されることは別**である
- **提案**: `designcheck` が「予約名 `Id` / `LogicalDelete` / `OptimisticLocking` / `CreatedAt` /
  `UpdatedAt` / `Creator` / `Updater` の Field が、規定のデザイン型になっているか」を検査してほしい。
  併せて、`OptimisticLocking` が SQLite / SQL Server / MySQL のデータソースで
  `IncrementVersion: false` のままなら警告してほしい（PostgreSQL の `xmin` 前提の既定値のため）。
  更新失敗の理由（版の不一致・型変換の失敗）がクライアントに伝わると、なお良い
- **回避策**: 予約名の Field を規定のデザイン型で作り直す。型が未決のものは Field ごと持たない
- **出典**: [qa/01_CLB静かな失敗](../qa/01_CLB静かな失敗.md) F-09

### FB-002【中】Boolean の新規作成時の初期値を宣言的に指定できない

- **発見日**: 2026-08-24
- **CLB バージョン**: ランタイム 1.3.20 / デザイナ 1.3.20 / Extras 0.5.0
- **症状**: DB 列が `is_active INTEGER NOT NULL DEFAULT 1` でも、新規作成画面のチェックボックスは
  必ずオフで始まる。そのまま登録すると 0 が入る
- **なぜ困るか**: マスタの「有効」フラグのように**既定が true であるべき項目**は珍しくない。
  気づかないと「新規作成したマスタが入力候補に出ない」という、原因の分かりにくい不具合になる。
  実害が出るのは作った直後ではなく、そのマスタを使おうとした後日である
- **提案**: `FieldDesign` に新規作成時の初期値（`DefaultValue`）を宣言的に持たせてほしい。
  少なくとも Boolean / Select / Number では、スクリプトを書かずに指定できると良い
- **回避策**: `DetailLayout.OnAfterInitialization` で `IsNewData` を見て代入する。
  値の出し入れだけなのでスクリプトに書いてよい範囲ではあるが、マスタの数だけ同じ 3 行が増える
- **出典**: [qa/01_CLB静かな失敗](../qa/01_CLB静かな失敗.md) F-10

### FB-003【中】headless CLI の標準出力が UTF-8 でなく OS のレガシーコードページで出る

- **発見日**: 2026-08-25
- **CLB バージョン**: ランタイム 1.3.20 / デザイナ 1.3.20 / Extras 0.5.0
- **症状**: デザイナ exe の `sql` サブコマンドで `--out` を省いて結果 JSON を標準出力から受けると、
  出力は UTF-8 ではなく OS のレガシーコードページでエンコードされている（日本語 Windows で
  CP932 であることを実測。ja-JP は ANSI も OEM も 932 なので、exe がどちらの系で選んでいるかは
  この環境では区別できない。他ロケールは未検証）。
  日本語（トリガの `RAISE(ABORT, '…')` の文言など）を含む結果を UTF-8 として読むと文字化けし、
  CP932 の後続バイトに 0x5C（`\`）を含む字（「仕」「訳」等）では **JSON のエスケープとして不正**になり
  パースそのものが失敗する
- **なぜ困るか**: PowerShell 7 は既定で UTF-8 として読むので、パイプで受けるとそのまま踏む。
  ASCII の結果では顕在化せず、日本語を含む行を初めて取り出したときに突然壊れるため、
  呼び出し側の JSON の組み立てを疑って時間を失う（実測では `sqlite_master` の
  トリガ定義を取り出した時に発覚）
- **提案**: headless モード（`sql` / `designcheck` など `--out` 省略時の標準出力）は
  常に UTF-8（BOM なし）で書いてほしい。JSON を名乗る出力なら RFC 8259 の既定も UTF-8 である
- **回避策**: 呼び出し側で `ProcessStartInfo.StandardOutputEncoding` に
  `CultureInfo.CurrentCulture.TextInfo.OEMCodePage` を指定して読む（`tools/clb/_designer.ps1`。
  ja-JP では ANSI/OEM どちらでも 932 になるので、この選び方は ja-JP でのみ検証済み）
- **出典**: `tools/clb/_designer.ps1` のコメント（2026-08-25 実測）

### FB-004【中】一覧から 1 件削除すると、行は減るのに件数の表示だけ古いまま残る

- **発見日**: 2026-08-26
- **CLB バージョン**: ランタイム 1.3.20 / デザイナ 1.3.20 / Extras 0.5.0
- **症状**: `ListPage` の一覧で行の削除アイコンを押して確定すると、表の行は 18 → 17 に減るが、
  右上の件数表示が `(1-17 /18件)` のまま残る。検索ボタンを押し直すと `(1-17 /17件)` に直る。
  再現手順: 一覧を開く → 任意の行を削除 → 件数表示を読む
- **なぜ困るか**: 利用者には「18 件あるはずなのに 17 件しか出ていない」と読める。
  **表示が消えるのではなく、間違った数が出る**ので、データが欠けたと誤解させる。
  自動テストで件数を判定材料にしている場合も、削除の直後だけ静かに誤判定する
- **提案**: 削除の確定後に件数も再計算してほしい（行の再取得と同じ契機で更新される形）
- **回避策**: 削除のあとに検索を打ち直す。実機テストでは、削除後の件数を判定材料にしない
- **出典**: [qa/01 D-14](../qa/01_CLB静かな失敗.md)（2026-08-26 実測）

### FB-005【低】一覧の削除確認だけボタンが英語（Yes / No）で、自前のダイアログと調子が揃わない

- **発見日**: 2026-08-26
- **CLB バージョン**: ランタイム 1.3.20 / デザイナ 1.3.20 / Extras 0.5.0
- **症状**: `ListPage` 既定の削除確認は「削除しますか？」＋ **Yes / No**。
  同じ画面から出す `MessageBox.ShowWithTitle(..., "はい", "いいえ")` は日本語なので、
  **同じ操作の流れの中で英語と日本語のボタンが混ざる**
- **なぜ困るか**: 本アプリの読み手は経理担当者と税理士で、英語のボタンを想定していない。
  文言の調子を揃える規約（本プロジェクトの [21_画面の原則 §2](../21_画面の原則.md)）を、この 1 か所だけ機械的に守れない
- **提案**: 既定ダイアログのボタン文言を指定できるようにしてほしい
  （モジュール側の設定でも、アプリ全体の既定でもよい）
- **回避策**: 見つかっていない。削除確認を自前に置き換えると、
  `ListPage` の削除機能そのものを作り直すことになる
- **出典**: [qa/04](../qa/04_実機操作テスト.md) の 2026-08-26（J-05 の実機操作で観測）


### FB-006【中】スクリプトからの `this.Submit()` が、`IsRequired` の検証を通らない

- **発見日**: 2026-08-28
- **CLB バージョン**: ランタイム 1.3.20 / デザイナ 1.3.20 / Extras 0.5.0
- **症状**: 標準の `SubmitButtonFieldDesign` はクリック時に全フィールドの `ValidateInput()` を
  走らせるが、`ButtonFieldDesign` の `OnClick` から `this.Submit()` を呼ぶと**走らない**。
  同じ画面に両方のボタンを置くと、**押すボタンによって必須入力の検査があったり無かったりする**。
  実測では、明細を 1 行足して空のまま「下書き保存」（標準）を押すと「必須項目です」で止まり、
  「計上する」（スクリプト）を押すと素通りして DB の NOT NULL 制約まで到達した
- **なぜ困るか**: `IsRequired` は**デザイン JSON の宣言**であり、保存の経路によって
  効いたり効かなかったりするとは読めない。しかも**効かないほうが、スクリプトを足した
  「より作り込んだ」経路**なので、作り込むほど守りが薄くなる。
  マニュアルの `ScriptGuidelines.md` は `this.ValidateInput()` → `this.Submit()` の順を例示しているが、
  「`Submit()` は検証しない」とは書かれていないため、例示を読み落とすと静かに穴が開く
- **提案**: 次のいずれか。① `this.Submit()` の既定で `ValidateInput()` を走らせる
  （素通ししたい場合の引数を用意する）② `designcheck` が
  「`Submit()` を呼ぶメソッドに `ValidateInput()` が無い」を指摘する
  ③ 少なくとも `_script_catalog.md` の `Submit` の説明に明記する
- **回避策**: `this.Submit()` の前に `this.ValidateInput()` を必ず書く。
  書き忘れを自作の静的検査（`lint_design.py`）で止める
- **出典**: [qa/01 F-15](../qa/01_CLB静かな失敗.md)・[qa/03 L-16](../qa/03_テストで漏らした実例.md)（2026-08-28 実測）

### FB-007【高】保存が DB に拒まれると、DB の生のエラーメッセージが利用者のトーストに出る

- **発見日**: 2026-08-28
- **CLB バージョン**: ランタイム 1.3.20 / デザイナ 1.3.20 / Extras 0.5.0
- **症状**: 保存が DB の制約に当たると、`ModuleSubmitResult.ExceptionMessage` に
  データベースドライバの例外メッセージがそのまま入り、CLB がそれをトーストに表示する。
  実測で画面に出たのは
  `SQLite Error 19: 'NOT NULL constraint failed: journal_lines.account_id'.` である
- **なぜ困るか**: **テーブル名・列名・DB 製品名が業務利用者の画面に出る。**
  読み手（本アプリでは経理担当者と税理士）には意味が分からず、しかも
  **内部のスキーマが漏れる**。アプリ側で防ぎ切るのが本筋だが、防ぎ漏れたときの
  既定の見え方が「内部表現をそのまま出す」なのは安全側ではない
- **提案**: `ExceptionMessage` のうち**データアクセス層由来のもの**は、
  既定で定型文（「保存できませんでした」）に置き換え、原文はサーバのログに残してほしい。
  原文をそのまま出すかどうかをアプリ側で選べる設定でもよい
- **回避策**: 保存を包む自前の関門で `ExceptionMessage` を検査し、
  DB 由来と分かるものを利用者の語に差し替える
- **出典**: [qa/01 F-16](../qa/01_CLB静かな失敗.md)・[qa/03 L-16](../qa/03_テストで漏らした実例.md)（2026-08-28 実測）

### FB-008【中】一覧の列の `ClassName` が `<td>` にしか付かず、`<th>` を揃えられない

- **発見日**: 2026-08-28
- **CLB バージョン**: ランタイム 1.3.20 / デザイナ 1.3.20 / Extras 0.5.0
- **症状**: `ListElement.ClassName` に付けたクラスは**データセル（`<td>`）にだけ**適用され、
  見出しセル（`<th>`）の class は空のままになる。そのため金額列を右詰めにしても、
  **見出しだけ左寄せのまま残る**。
  あわせて、セルの中身は `<td><div style="display:flex"><span>値</span></div></td>` で描かれるため、
  `text-align: right` は `<span>` まで継承されるものの、`<span>` が**内容ぶんの幅しかない
  flex 項目**なので見た目が変わらない（効かせるには `justify-content: flex-end` が要る）
- **なぜ困るか**: 会計・販売のような**金額列を持つ業務アプリでは、右詰めは既定の要求**である。
  `nth-child` で `<th>` を狙う回避策は、列の増減で黙ってずれる（静かな失敗になる）。
  また `text-align` が「効いているのに見た目が変わらない」ので、
  DevTools で計算値を見ても原因にたどり着けず、調査に時間がかかる
- **提案**: ① `ListElement.ClassName` を `<th>` にも付けてほしい
  ② あわせて、セル内側のラッパー（`display:flex`）に `text-align` が届かないことを
  `_specs/AppCss.md` に明記するか、`justify-content` まで含む右詰めの作法を例示してほしい
- **回避策**: `.<クラス> > div { justify-content: flex-end; }` を `app.css` に書く。
  見出しは揃えられないので、**列見出しは左寄せのまま**にする
- **出典**: [qa/01 D-15・D-16](../qa/01_CLB静かな失敗.md)（2026-08-28 実測）

### FB-009【高】明細行の親 FK が `LinkField` だと、追加した行が静かに消える

- **発見日**: 2026-08-30
- **CLB バージョン**: ランタイム 1.3.20 / デザイナ 1.3.20 / Extras 0.5.0
- **症状**: ヘッダ＋明細（`ListField` による 1:N）で、**子の親 FK を `LinkFieldDesign` にすると、
  「追加」した行が保存されない**。しかも
  **`/api/module_data/submit` が 1 本も飛ばない**——エラーもトーストも出ず、
  画面には行が残ったままなので、**リロードして初めて消えたと分かる**。
  `designcheck` は findings 0。**読み取りは正しく動く**（既存の行は
  `SearchCondition` の逆引きでちゃんと出る）ので、壊れているのは**追加だけ**である。
  `IsRequired` を外しても変わらない（切り分け済み）
- **なぜ困るか**: **`Docs/AppPatterns/header_detail.md` 自身が「候補から選ばせたい設計なら
  `LinkField` でもよい」と書いている。** 読んだとおりに作ると、静かに壊れる。
  しかも**相手の名前を一覧に出したい**という要求はごく普通に起きる——
  `IdField` の FK は識別子しか出せないので、名前を出すには一覧をクエリモジュールに
  作り替えるしかなく、その判断が**実装して実機で動かすまで分からない**
- **提案**: ① `LinkField` を親 FK にできるようにする（親の保存時に識別子を差し込む）か、
  ② できないなら**`designcheck` が指摘する**（「`ListField` の逆引き先の FK が `IdField` でない」）。
  ③ 少なくとも `header_detail.md` の「`LinkField` でもよい」を訂正し、
  **`IdField` 以外では追加が保存されない**ことを明記してほしい
- **回避策**: 親 FK は `IdFieldDesign` ＋ `IsManualInput: false` にする。
  相手の名前を一覧に出したいときは、その一覧をクエリモジュール（`DbTable` 空）で作って
  SQL で JOIN する
- **出典**: [qa/01 D-17](../qa/01_CLB静かな失敗.md)（2026-08-30 実測）

### FB-012【中】権限で閉じたモジュールの読み取りが、`403` ではなく `500` と英語で返る

- **発見日**: 2026-09-02
- **CLB バージョン**: ランタイム 1.3.20
- **症状**: `UserReadCondition` を満たさない利用者が `POST /api/module_data/list` を投げると、

- **提案**: 権限の拒否は `403` を返してほしい。文言も日本語の既定を用意してほしい
- **回避策**: 無い（サーバの認可層で、アプリ側から包める場所が無い）

### FB-013【高】`MaxFractionDigits` が「拒む」ではなく「黙って切り捨てる」

- **発見日**: 2026-09-04
- **CLB バージョン**: ランタイム 1.3.20
- **症状**: `NumberFieldDesign` に `MaxFractionDigits: 0` を設定した欄へ小数を打つと、
  **警告もトーストも無く切り捨てられる**。`1.5`→`1` / `1.9`→`1` / `2.5`→`2` / `1234.5`→`1234`。
  **四捨五入ではなく切り捨て**で、値そのものが変わる（表示の書式ではない。合計欄にも切り捨て後が出る）。
  **同じ欄の `Min: 1` は拒む**——`-1` は「最小値より小さい値です」で止まり、保存されない。
  **1 つの欄の 2 つの設定で、守り方が違う。**
- **なぜ困るか**: **会計では 1 円のずれが致命的である。** しかも
  **貸借の両側で切り捨てが起きると合計は合ってしまう**ので（`1234.5 / 1234.5` → `1234 / 1234`）、
  貸借一致の検証を通り、**欠落が誰の目にも触れないまま帳簿に載る**。
  利用者は「打った値と違う値が保存された」ことに気づけない。
- **提案**: **`MaxFractionDigits` を超える入力は、`Min` / `Max` と同じように拒んでほしい**
  （「小数は入力できません」）。少なくとも**拒むか切り捨てるかを選べる**ようにしてほしい。
  「切り捨てる」が既定であること自体が、金額を扱うアプリでは危険側の既定である。
- **回避策**: `OnInput` で打鍵ごとに小数点を見て断る（未実装）。画面に「円未満は入力できません」と先に出す。
- **出典**: [qa/01 A-10](../qa/01_CLB静かな失敗.md)（2026-09-04 実測）

### FB-014【中】権限で拒まれた画面が真っ白になり、「画面が無い」と区別できない

- **発見日**: 2026-09-04
- **CLB バージョン**: ランタイム 1.3.20
- **症状**: 権限の無い PageFrame を開くと、トースト「ページフレームへのアクセス権限がありません」が
  出るだけで**画面は真っ白**。サイドバーも戻る導線も無く、**トーストが消えると理由も分からない白い画面**が残る。
  **存在しないフレーム名（`/Nope/JournalEntry`）でも同じ文言**が出る。
- **なぜ困るか**: ① 利用者が**自分がどこにいるか分からず、戻る手段も無い**
  ② **URL の打ち間違いを「自分に権限が無い」と誤解する**——原因が違う 2 つが同じ文言になっている
  ③ 文言が内部表現（「ページフレーム」）。利用者は「ページフレーム」を知らない
- **提案**: ① 拒んだときの**行き先を指定できる**ようにしてほしい（玄関へ返す）
  ② **「権限が無い」と「その画面が無い」を別の文言にしてほしい**
  ③ 文言を差し替えられるようにしてほしい（FB-010 と同じ要望）
- **回避策**: 無い。**CLB がフレームの手前で止めるので、アプリのスクリプトが走らない。**
- **出典**: [qa/01 F-36](../qa/01_CLB静かな失敗.md)（2026-09-04 実測）

### FB-015【中】入力検証の文言が内部表現（「最小値より小さい値です」）

- **発見日**: 2026-09-04
- **CLB バージョン**: ランタイム 1.3.20
- **症状**: `Min` を満たさない値を入れると、欄の下に **「最小値より小さい値です」**、
  トーストに「不正な入力があります」が出る。**止まること自体は正しい。**
- **なぜ困るか**: **利用者は「最小値」が何かを知らない。** 金額の欄なら
  「金額は 1 円以上で入力してください」であるべきで、**どう直せばよいかが文言から分からない**。
- **提案**: **欄ごとに検証の文言を差し替えられる**ようにしてほしい
  （`Min` / `Max` / `MaxLength` などの標準検証すべて）。
- **回避策**: `OnValidateInput` で自前に検証して自前の文言を出す（欄の数だけ書くことになる）。
- **出典**: [qa/01 A-10](../qa/01_CLB静かな失敗.md)（2026-09-04 実測）

### FB-016【中】検索条件を載せた URL が壊れていると、画面全体が死ぬ（抜け道が無い）

- **発見日**: 2026-09-04
- **CLB バージョン**: ランタイム 1.3.20
- **症状**: クエリモジュールの一覧が検索のたびに URL へ書く `?q=…`（圧縮した検索条件）を
  壊した状態で開くと、**Blazor 既定の英語のバー `An unhandled error has occurred. Reload`**
  が出て本文が真っ白になる。実測は `/Main/GeneralLedger?q=THIS_IS_NOT_VALID`。
- **なぜ困るか**: 3 つ重なっている。
  1. **`Reload` が効かない**——同じ URL を読み直すので同じ所へ戻る。
  2. **サイドバーで別の画面へ移っても白いまま**。URL は変わるがサーキットが死んでいて再描画されない。
     **利用者はブラウザごと読み直すしかない**が、それを画面が教えない。
  3. **`?q=` を書いているのは CLB 自身**である。ブックマークや共有ができるのは良い設計だが、
     **メールで折り返されて切れた URL・古いブックマーク・手で触った URL** がそのままこれに当たる。
- **提案**: **`q` の復元に失敗したら、条件を捨てて既定の一覧を出してほしい**
  （壊れた条件は「条件なし」と同じに倒す）。せめて例外にせず、
  アプリ側で受け取れるフック（`OnSearchConditionRestoreFailed` のようなもの）が欲しい。
- **回避策**: **見つかっていない。** 復元は CLB がフレームを組み立てる段で走るので、
  アプリのスクリプトは 1 行も動かない（FB-014 と同じ層の問題）。
- **出典**: [qa/01 F-38](../qa/01_CLB静かな失敗.md)（2026-09-04 実測）

### FB-017【中】標準の `SubmitButtonFieldDesign` は、サーバが返した失敗の文言に「更新に失敗しました」を重ねる

- **発見日**: 2026-09-10（2 枚出ること自体は 2026-08-30 から。原因の切り分けがこの日）
- **CLB バージョン**: ランタイム 1.3.20
- **症状**: `ModuleDataIO.SubmitAsync` の差し替えが保存を止める（例外を投げる、または `ModuleSubmitResult.ExceptionMessage` に
  文言を載せて返す）と、**標準の `SubmitButtonFieldDesign` はその文言のトーストに続けて「更新に失敗しました」をもう 1 枚出す**。
  スクリプトから `this.Submit()` / `this.Delete()` を呼んだときは文言だけが出る。
  親の差分がある保存でも、明細（`ListField` の子）だけの保存でも同じ。結果に行ごとの `SourceId` を付けて返しても同じ。
- **なぜ困るか**: 利用者には 1 つの失敗が 2 回見える。関門の文言が「入力内容は悪くない。別の人が消した」と言っているのに、
  直後の定型文が「失敗」だけを残す。同じ画面で、押すボタンによって枚数が変わる。
- **提案**: サーバが文言を返したときは、標準のボタンでも**その文言だけを出してほしい**（スクリプトの `Submit()` と同じ扱い）。
- **回避策**: 標準の保存ボタンをやめ、スクリプトのボタンで `ValidateInput()` → `Submit()` を呼ぶ（本プロジェクトの「計上する」がこの形）。
  画面の作りを変えることになるので、採るかは検討中（[docs/04 §5](../04_実装計画と現在地.md)）。
- **出典**: [qa/01 F-42](../qa/01_CLB静かな失敗.md)（2026-09-10 実測）・[qa/04](../qa/04_実機操作テスト.md) の C-01 ⑤・C-05・C-06
