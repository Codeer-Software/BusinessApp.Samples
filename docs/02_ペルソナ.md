# ペルソナ — 株式会社アルタイルシステムズ（架空）

> 本アプリの機能・データモデル・デモデータはすべてこの会社を基準に設計する。
> 選定理由（上位方針）: CLB の買い手＝ソフトを作る会社。デモの聴衆とペルソナが一致し、「自分ごと化」が最速で起きる。

## 1. 会社概要

| 項目 | 内容 |
|---|---|
| 社名 | 株式会社アルタイルシステムズ（Altair Systems Inc.） |
| 所在地 | 東京都（本社のみ、単一拠点） |
| 設立 | 2009年（現在18期目。UI の年度表記は「第18期（2026年度）」形式＝fiscal_years.label） |
| 資本金 | 3,000万円（非上場・オーナー経営） |
| 従業員 | 55名（正社員50・契約5） |
| 年商 | 約8.5億円 |
| 決算期 | **3月決算（会計期間 4/1〜3/31）** |
| 税務 | 課税事業者（本則課税）・**税抜経理方式**・適格請求書発行事業者（T+13桁登録済み） |
| 会計基準 | 中小企業の会計に関する基本要領（収益認識基準は不適用。受託=検収基準） |

## 2. 事業構成（売上比率）

| 事業 | 比率 | 売上計上の実務 |
|---|---|---|
| 受託開発（一括請負） | 60% | **検収基準**。中〜大型案件は中間検収あり。前受金・仕掛品（未成業務支出金）が発生 |
| SES／準委任 | 25% | 月次の稼働報告→翌月請求。精算幅（140-180h）による超過/控除精算あり |
| 自社 SaaS（勤怠管理サービス） | 15% | 月額サブスク＋年額一括前払いプランあり → **年額分は繰延収益（前受収益）の月次按分**が必要 |

## 3. 組織

**部課2階層**（ADR-0044。部の下にオプションで課を置く。全5部が第一課/第二課を持つ）:

```
代表取締役（オーナー）
├─ 総務部（6名）: 部長1・部長代理1／第一課（経理2）・第二課（総務労務・情シス2）
├─ 営業部（5名）: 部長1・部長代理1／第一課・第二課（営業3）
├─ 開発1部（受託・20名）: 部長1・部長代理1／第一課・第二課（PM・エンジニア18）
├─ 開発2部（受託/SES・18名）: 部長1・部長代理1／第一課・第二課（PM・エンジニア16）
└─ SaaS事業部（5名）: 部長1・部長代理1／第一課・第二課（開発・CS3）
```

- 部門コード: 総務(10)／営業(20)／開発1(31)／開発2(32)／SaaS(40) の5部＋全社共通(00)。各部の課は `10-1` `10-2` のような枝コード。**伝票の部門は部ノードのみ**（課は候補に出ない）。
- 役職は 部長・部長代理（部の director 行）／第一課長・第二課長（課の manager 行）／一般（member 行）の5層。
- 承認系統: 一般社員 → **自分の課の課長** → 部長（課長空席時は walk-up で自動繰上げ）→ 全滅時は経理代替（ADR-0044）。適用テンプレート（課長のみ/部長のみ/＋総務）は承認ルート判定マスタ（ADR-0023）が金額・費目で決める。

## 4. アプリの利用者像

> アプリ上の権限は**3軸分離**（正典: `10_部品アーキテクチャ.md`・ADR-0043/0044）: ①機能権限＝ユーザー管理画面の直接フラグ（営業機能/経理機能/経費精算/工数入力/システム管理者）、②組織所属＝部課2階層＋部門メンバー行、③承認構造＝課長/部長行からの walk-up 解決。**部門メンバー行の追加・削除は機能の見え方に影響しない**。以下は利用者タイプの人数感。

| 利用者タイプ | 人数感 | 主な操作 |
|---|---|---|
| 一般社員 | 〜50名 | 経費申請、工数入力、自分の申請状況の確認 |
| 承認者（is_approver=課長10・部長5・部長代理5＋テンプレ個人指名者） | 〜20名 | 申請の承認/差戻し、自部門の予実閲覧 |
| 部長（is_director。部の director 行から導出） | 10名 | 上記に加え案件マスタの登録・変更（SES 精算条件は経理のみ＝ADR-0046） |
| 経理（総務部のうち経理機能フラグ保有者） | 2〜6名 | 仕訳入力・帳票・締め・請求/入金・マスタ管理（アプリの中心ユーザー） |
| 経営（代表・総務部長） | 2名 | ダッシュボード閲覧（全社損益・案件別損益・資金繰り） |

## 5. 現状の痛点（本アプリが解決するもの）

1. **案件別の損益がリアルタイムに見えない。** 会計ソフト（弥生）は科目別集計のみ。案件別は経理が月末に Excel で工数×単価を手集計 → 翌月中旬にやっと判明し、赤字案件の手当てが常に手遅れ。
2. **工数原価が会計とつながっていない。** 勤怠・工数は別システム。人件費の案件配賦が「どんぶり」。
3. **SaaS 年額プランの繰延処理が Excel 管理。** 前受収益の月次按分を経理が手作業で仕訳化しており、ミス・漏れが怖い。
4. **経費精算が紙とメール。** 領収書のり付け→部長ハンコ→経理が弥生へ手入力の二度手間。月末に集中して残業の温床。
5. **資金繰りが経営者の勘。** 受託の入金は検収ずれで凸凹が激しく、賞与月・納税月の残高不安が常にある。
6. **SES の精算計算が属人化。** 精算幅（140-180h）の超過/控除計算を営業が個別 Excel で行い、請求ミスが年数回起きる。
7. インボイス対応で、フリーランス外注（免税事業者が数名残る）の**経過措置の控除計算（2026年10月から70%）**を手管理するのが不安。

## 6. デモデータの基準値（フェーズAで作成するサンプルの前提）

- 会計年度: 第17期（2025-04-01〜2026-03-31、締め済み）と第18期（2026-04-01〜、進行中）。
- 月間仕訳数: 200〜400件程度（年間約 3,000〜4,000件）を想定したデータ量で性能も確認する。
- 主要取引先: 得意先10社（受託5・SES3・SaaS法人2）、仕入先/外注先10社（うち免税事業者2）。
- 進行中案件: 受託4件（うち1件は赤字傾向）・SES 8名分・SaaS 契約120社（デモでは集約管理）。
