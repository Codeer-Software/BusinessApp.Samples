# 取引先設計

> **取引先は会計マスタではない**（[ADR-0029 §6](decisions/0029-所有は相手抜きで存在するかで導き粒度は決断で決める.md)）。
> 会計をやめても存在するものであり、会計コアは**使うだけ**である。
> だから会計ドメインの文書（[10](10_会計ドメイン設計.md)）ではなく本書が持つ。
> さらに**独立したアプリ部品として分ける**と決めた
> （[ADR-0025](decisions/0025-取引先を部品として分ける.md)。2026-08-27）。本書はその部品の設計書である。
>
> 制度そのものの説明と出典は
> [取引先の識別番号と公表システム](research/2026-08-25_取引先の識別番号と公表システム.md) にある。
> 本書は**設計上の決定**だけを書く。

## 0. 部品の構成（実装済み。2026-08-27）

**現在形の正典はここ。** 決めた経緯と理由は [ADR-0025](decisions/0025-取引先を部品として分ける.md)。

| 層 | 実体 | 依存 |
|---|---|---|
| CLB | `PageFrames/Partners.frm.json`（`IsApplicationRoot: false`）＋ `Modules/Partners/`（`Partner` / `PartnerInvoiceRegistration` / 一覧の `PartnerRegistrationList` ＋ その `.Query.sql` / 玄関の `PartnerHome`） | **会計へ戻るリンク 1 本**（下の「取り出すとき」） |
| 純粋 | `BusinessApp.Partners` | **なし**（NuGet も参照もゼロ） |
| サーバ | `BusinessApp.Partners.Server` | `Partners`・`ServerSupport`・CLB |
| 検査 | `BusinessApp.Partners.Tests` / `.Server.Tests`（行・分岐 100% ＋ ミューテーション） | — |

**保存の入口は `PartnerSubmitPipeline` 1 本。** 会計と一緒に載せるときは
`AccountingSubmitPipeline` がこれを 1 本呼ぶ。**取引先の関門が増えても会計側を直さなくてよい**
——直さなければならない形にすると、別ホストへ載せた取引先だけ関門が 1 つ足りないまま通る。

### 取り出すとき（会計コア抜きで載せるとき）

**C# は何も直さなくてよい**（会計コアへの参照がゼロなので、そのまま持ち出せる）。
**CLB は 2 か所を直す**——この 2 つは、一緒に載せるアプリとしての利便のために入れてある。

1. `Partners.frm.json` の `IsApplicationRoot` を `true` にする。
   **`true` のフレームが 1 枚も無いと、ルート URL が非 root のフレームへ黙って落ちる**
   （CLB 仕様リファレンス CommonMistakes #54）。`lint_design.py` の D-13 が 0 件を検出する
2. サイドバーの「会計へ戻る」リンクを外す。会計フレームが無いので行き先が無くなる

- **依存は会計コア → 取引先の一方通行。** 逆はコンパイラが禁じ、両側から機械が見ている——
  会計側は `ModuleDependencyTests`（参照は `BusinessApp.Partners` ただ 1 本）、
  取引先側は `PartnerDependencyTests`（純粋層は参照ゼロ・サーバ層は会計コアを参照しない）
- **DB は分けない**（[ADR-0025 §5](decisions/0025-取引先を部品として分ける.md)）。会計は `partners` を読むだけで、
  書き込みは `PartnerSubmitGate` / `PartnerRegistrationSubmitGate` だけを通る
- **共有インフラ `BusinessApp.ServerSupport`** に `DbValue`（DB 値の変換）と
  `DatabaseTimeZone`（オフセットを持たない DATETIME を書き読みするタイムゾーン）を置く。
  会計でも取引先でもない、この DB の作法である。
  **次にここへ出すのは `DbTransactionScope`** で、条件は**取引先が書き込みの経路
  （[ADR-0016](decisions/0016-画面から呼ぶサーバ処理はWebAPIに置く.md) の Web API）を持ったとき**である。
  いまは会計側にしかなく取引先から手が届かないので、**先に写しを作らないこと**——
  同じ 6 行が 2 か所にあると、片方だけ直しても全テストが緑になる（qa/02 R4-04 で一度踏んだ）
- **CLB のモジュールはデザイン全体で共有される。** PageFrame の分割はナビゲーションの分割であって
  隔離ではなく、会計の画面（振替伝票・仕訳帳・元帳）は `Partner` を Lookup と JOIN で名指しする

## 1. 何を持つか

### 1-1. 判断の基準

**取引先マスタは会計コアより上位の存在で、他のどこにも依存しない**（開発者の整理。2026-08-25。
部品間の依存の向きの規則は [ADR-0029 §2](decisions/0029-所有は相手抜きで存在するかで導き粒度は決断で決める.md) が正典）。
だから「会計コアが使いたいものを持つ」のではなく、**取引先マスタ自身が持つべきものを持つ**。

| | 判断 |
|---|---|
| **持ってよい** | 取引先マスタ単独で意味が決まり、他部品でも同じ意味で使うもの（名称・所在地・法人番号・種別） |
| **持たない** | 特定の部品の業務が決めるもの（与信限度・回収サイト・営業担当・仕入条件） |

迷ったら「**経費精算アプリと営業アプリが同じ意味で使うか**」を問う。

ただし**本プロジェクトで作るのは会計コアと、それが使う範囲の取引先部品**である
（[ADR-0025 §7](decisions/0025-取引先を部品として分ける.md)）。会計に関係しない部分まで作り込まない。
「持ってよい」と「今作る」は別である。

### 1-2. 列

| 列 | 必須 | 内容 |
|---|---|---|
| `code` / `name` / `name_kana` / `is_active` | ○ | 既存 |
| `address` | | 所在地。**1 列で持つ。** 都道府県・市区町村に分割しない（設計判断: スコープに分割を使う機能が無く、入力が重くなるだけ。需要が出たら見直す） |
| `entity_type` | 画面○ | **法人（設立登記法人）／個人事業者／人格のない社団等／その他** |
| `corporate_number` | | 法人番号（13 桁）。**任意**（§2-3）。DB は桁と数字だけを見る。**検査用数字（チェックデジット）は保存の関門が見る**（§1-5） |
| `parent_partner_id` | | 名寄せの手動キー（§2-2）。自己参照・連鎖・循環はすべて拒む（§2-5） |

**`display_order` は持たない**（2026-08-28 の**設計判断**。開発者は「消しましょう」と同意している）。マスタのテンプレートから写しただけである——
**取引先の初期データはそもそも 1 本も無く**（`Designer/seed/` にあるのは組織・部門・税区分・勘定科目）、
**どの行にも値が入っていない**。一覧の並び順キーには指定してあるが（`Partners.frm.json`）、
全行が空なので実質コード順に並んでいる。詳細画面には入力欄が出ている（2026-08-28 に実物で確認）。
勘定科目・部門・税区分と違い、取引先は数百件に育つもので**人が並び順を手で維持することはあり得ず**、
探し方はコード順・カナ順・検索である。画面から外し、DB の列も消す。

**種別が 2 値では足りない。** 人格のない社団等は法人番号を持ちうるが**公表は代表者の同意がある場合のみ**で、
法人とも個人事業者とも扱いが違う。

**種別の必須は画面で守り、DB は NULL 可にする**（2026-08-25 実装時の決定）。
列より前からある行と「まだ分類していない」を、既定値の偽の分類で埋めないため
（`posted_by` と同じ規律）。NULL は「未分類」。**名寄せの解決順序（§2-2）に種別は関与しない**——
未分類でも法人番号があれば法人番号で束なり、無ければ結果として手動キーの経路に落ちるだけである。
（**種別は「親に付けてよい相手か」の入力の関門としては見る**。§2-5。解決の側では見ない。）
なお**個人事業者に法人番号は指定されない**（制度事実）ので、矛盾する組は DB の CHECK が拒む。

### 1-3. 個人番号（マイナンバー）は持たない

番号法 20 条は、**19 条各号に該当する場合を除いて**個人番号の収集・保管を禁じている。
除外の中心は「**個人番号関係事務**を処理するために必要な限度で扱うとき」で、
本プロジェクトの周辺だと**個人事業者への報酬・料金等の源泉徴収**がこれに当たる。
しかし**源泉徴収の事務は会計コアの外**であり（[03_機能スコープ](03_機能スコープ.md)）、
**取引先の名寄せは個人番号関係事務ではない**（[リサーチ §2](research/2026-08-25_取引先の識別番号と公表システム.md)）。
名寄せのために個人番号を利用すれば **30 条 2 項の目的外利用**になり、本人が同意しても認められない。
[企画概要 §6](01_企画概要.md) も「マイナンバー」を明示的に狙わないものに挙げている。

**つまり会計コアには、個人番号を適法に収集できる場面が無い。**
**列を作らないこと自体が最良の安全管理措置である。** 任意列にすると誰かが入れる。

### 1-4. 住所の写しは仕訳に作らない

スコープ内で帳簿に相手方の住所が要るのは**入場券等の回収特例で 1 回 3 万円以上**の 1 類型だけである
（他の類型は [03_機能スコープ](03_機能スコープ.md) がスコープ外にしている）。

**明細の「内容」欄に書く運用**とし、`partner_address_snapshot` は作らない。
1 類型のために仕組みを作るより軽い。**帳簿に書く欄は③（資産又は役務の内容）**であり、
経過措置の適用を受ける旨も同じ欄に書く（[11 §5・§8](11_消費税設計.md)）。

振替伝票の入力画面に注意書きを出す（実装済み。2026-08-26）。

> 入場券等の回収特例（1 回 3 万円以上）に当たる仕入れは、明細の「内容」欄に取引先の住所を記載してください。

**計上済みの伝票では出さない。** もう直せない伝票に入力の指示を出しても、次の手が無い。

### 1-5. 素性の画面と保存の関門（実装。2026-08-26）

**種別・法人番号・所在地・名寄せの親を取引先の画面に出した**（一覧は種別・法人番号・所在地）。

**種別は画面で必須**（§1-2 の決定）。既存の行は未分類のまま残るが、**その行を直そうとした時点で
分類を求める**——DB は NULL 可のままなので、触っていない行を偽の値で埋めることはない。

`PartnerSubmitGate` が次を止める（**この表が正典**。件数は書かない——数えるたびに腐る）。
**多くは DDL の CHECK やトリガが最後には拒むもの**であり、関門はその手前に置く網である
（DB まで届かせると、利用者に見えるのは DB の言葉で書かれた失敗になる）。

| 止めるもの | なぜ画面の手前で止めるか |
|---|---|
| 法人番号の**書式**（数字 13 桁） | DB も同じものを見るが、拒み方が利用者の語にならない |
| 法人番号の**検査用数字** | **DB は見ない**（§1-2 の決定）。ここが唯一の関門である。打ち間違えた番号を通すと、それが名寄せの自然キーになる（§2-2）——別の法人に化けて束なるか、束なるべきものが束ならないかのどちらかで、**どちらも画面には何も出ない**。算式は[リサーチ §1-1](research/2026-08-25_取引先の識別番号と公表システム.md) |
| **個人事業者に法人番号**を入れること | 制度事実（§1-2）。**差分に片方しか無ければ、保存されている値で補って判定する**——CLB は変更された項目しか送ってこない（[qa/01](qa/01_CLB静かな失敗.md) F-11）ので、片方だけ直した保存で検査をやめると「先に個人事業者にしておいて、あとから法人番号を足す」で素通りする |
| **自分自身を名寄せの親**にすること | 選択肢の一覧に自分が出るので、実際に起こる |
| **個人事業者と法人系を名寄せで束ねる**こと | §2-5 |
| **名寄せの親が 2 段以上つながる**こと | §2-5 |

## 2. 名寄せ

### 2-1. なぜ要るか

経過措置の控除限度額が「**一の免税事業者等ごと**」の集計だからである
（[11 §5](11_消費税設計.md)）。同じ相手の拠点・店舗・屋号が別レコードだと合算されない。

> **制度上の「一の免税事業者等」の同一性判定（屋号違い・相続・合併など）は未確認である**
> （[消費税リサーチ の未確認事項](research/2026-08-23_消費税インボイス制度.md)）。
> 本節が決めているのは**実装上の突合手段**であって、制度の解釈ではない。

**登録番号は名寄せに使えない。** 対象は免税事業者等であり、**免税事業者は登録番号を持たない**。

### 2-2. 2 つのキー

| キー | 性質 | 対象 |
|---|---|---|
| **法人番号** | **自然キー**。同じ値なら同一法人。人が束ねる操作が要らない | 法人 |
| **`parent_partner_id`** | **手動キー**。人が明示的に束ねる | 個人事業者・法人番号が取れない相手 |

**解決の順序は「法人番号があればそれ、無ければ親を辿る、それも無ければ自分」。**
したがって**法人に `parent_partner_id` は要らない**。

**両方あって食い違ったら、法人番号を優先し、警告する。** 黙って片方を採ると人の入力ミスが見えなくなる。

### 2-3. 法人番号を必須にしない

- **外国法人**は国内に事務所等が無ければ指定されない（**一次情報は未確認**。リサーチ §5）
- **人格のない社団等**は代表者の同意がないと公表されず、調べようがない
- 伝票入力中に取引先をその場で作る場面では、まず分からない

**必須にすると入力が止まり、迂回のためのダミー値が入る。** 任意にして、未入力を警告する。

### 2-4. 氏名で自動的に束ねない

**表記ゆれが避けられない。** 候補を提示するのはよいが、機械が束ねてはならない。

### 2-5. 親に付けられる相手の規則（[ADR-0028](decisions/0028-名寄せの親は同一人格の表明であり深さ1に固定する.md)）

**親は「この 2 者は同じ事業者である」という表明**であり、それ以外の意味を持たない。
規則はすべてここから導かれる。

| 規則 | 止める場所 |
|---|---|
| **自分自身は親にできない** | 関門 ＋ DDL の `CHECK` |
| **個人事業者と、法人・人格のない社団等は互いに親にできない** | 関門 |
| それ以外の種別違いは**通す**（未分類・「その他」・**法人 × 人格のない社団等**） | ——（公表システムは法人と人格のない社団等を区別しない。[ADR-0028 §1](decisions/0028-名寄せの親は同一人格の表明であり深さ1に固定する.md)） |
| **親が、さらに親を持っていてはいけない**（深さ 1 の森。連鎖も循環も作れない） | 関門 ＋ DDL のトリガ |
| **自分が誰かの親になっているなら、自分に親を付けられない**（同上） | 関門 ＋ DDL のトリガ |
| **無効（`is_active = 0`）な取引先も親にできる** | ——（`ParentPartner` の候補を `IsActive` で絞らない） |
| **法人番号を持つ取引先に親を設定してもよい** | ——（解決では参照されない。食い違いはフェーズ 3 の解決処理が警告する） |

- **無効な取引先を親にできるのは、`is_active` が「入力時の候補に出すか」の意味だから**
  （[08_マスタ台帳 §1](08_マスタ台帳.md)）。名寄せの親は入力の候補ではない。
  逆向き（親になっている取引先を無効にできないようにする）は採らない——
  子を全部付け替えないと無効化できなくなる
- **深さ 1 に固定したので、解決は 1 段で済む**（法人番号 → 親 → 自分）。
  循環の検知も「誰が代表か」の規則も要らない

## 3. 適格請求書発行事業者の登録

### 3-1. 有効期間つきの別テーブルで持つ

登録は**取消・失効・再登録**があり、1 列では「その時点でどうだったか」を表せない。
`partners` に列を足さず、`partner_invoice_registrations` を作る。

**弥生会計の本体は登録番号の入力欄そのものを持たず、摘要か仕訳メモに書くよう案内している**
（[調査](research/2026-08-28_市販会計ソフト比較_登録番号の呼び名.md)。**調べたのは弥生 1 社だけ**）。
**本プロジェクトは違う選択をする**——計上時に明細へ写す記録が要り
（§4・[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)）、
**摘要に書く運用では「どの登録に基づいて計上したか」が後から辿れない**からである。

**引く日付は `journal_lines.tax_point`**（課税仕入れを行った日）。計上日でも取引日でもない。

### 3-2. 列（確定。2026-08-25）

公表システムの提供項目（[リサーチ §3-2](research/2026-08-25_取引先の識別番号と公表システム.md) で
リソース定義書の項目一覧を確認）に対応させて、次で確定した（`Designer/ddl/006_partner_registrations.sql`）。

| 列 | なぜ要るか・対応する提供項目 |
|---|---|
| `registration_no` | 登録番号（registratedNumber）。**書式は「T ＋ 数字 13 桁」（計 14 桁）で確認済み**（リサーチ §3-3）。DB は書式を検査せず、入力画面・取込を作るときに**アプリ側で検査する**（13 桁部分が法人番号と同一かは未確認のままなので、法人番号との突合には使わない） |
| `valid_from` | 登録年月日（registrationDate） |
| `ended_on` / `end_reason`（`expired` / `revoked`） | `expired` ＝ 失効年月日（expireDate）由来、`revoked` ＝ 取消年月日（disposalDate）由来。**日付 1 列＋理由 1 列**で持つ。公表システムの提供も**履歴 1 行につきいずれかの日付**なので、この形と一致する（リサーチ §5-6 で実質確認。2026-08-25）。**それぞれが指す法的事象——届出による取りやめ・職権・事業廃止など——の対応は未確認**。提供された日付をそのまま持ち、**「その日を含むか」の判定はフェーズ 3 で制度を確認してから**確定させる（保留リスト）（当初案の `valid_to` をやめたのは、±1 日の解釈をデータに焼き込まないため）。登録より前に終わる行は CHECK が拒む（**同日はあり得るか未確認なので許している**） |
| `source`（`manual` / `nta_api` / `nta_download`） | **手で入れた値を自動同期が黙って上書きしないため** |
| `confirmed_on` | この行を人が最後に確かめた日（監査用） |
| `nta_updated_on` | 公表システム側の更新年月日（updateDate）。差分取得の基準 |
| `published_name` | 氏名又は名称（name）の写し。**公表名とマスタ名はずれる**（略称で登録している等）。突合結果が残り、名寄せの手がかりにもなる。個人のダウンロード提供では削除される項目があるため（どの項目かは未確認）空がありうる |

**前後の空白は落として保存する**（`InvoiceRegistrationNumber.Normalize`。法人番号も同じ）。
貼り付けで紛れ込むだけで利用者の意図ではないからで、**落とさないと同じ番号が 2 通りの文字列で
保存されて突合が壊れる**。**小文字の `t` と全角数字は落とさずに拒む**——
そちらは利用者が入れたつもりのものだからである（[21 §0](21_画面の原則.md)）。

同じ登録の二重取込は `UNIQUE (partner_id, registration_no, valid_from)` が拒む
（**登録年月日そのものが誤りだった場合の訂正の配信のされ方は未確認**。取込の設計時に
実データで確かめる。リサーチ §5-7）。

### 3-2-1. 同じ登録番号を別の取引先が持つことは正常である（排除しない）

**開発者の判断**（2026-09-05）。**登録番号は人格に紐づくので、同じ法人を支店ごとに
別の取引先として登録すれば、登録番号は必ず同じになる。** 排除しえない。

- 実データがそうなっている——`T1234567890123` を `P001` と `S0001` が
  期間の重なる形で持っている（2026-09-05 の探索的テストで見つけた。[qa/04](qa/04_実機操作テスト.md)）。
  この 2 件は法人番号も同じ（`8700110005901`）で、**同じ法人の別レコード**として筋が通っている
- **§2-2 の法人番号と同じ扱いである。** 同じ値なら同一法人であって、束ねる操作は要らない
- `PartnerRegistrationSubmitGate` の検査がすべて取引先ごとなのは**正しい**。
  取引先をまたぐ重なりを止める関門は置かない

**ただしフェーズ 3 で数えるときに効く。** [11 §5](11_消費税設計.md) の経過措置の相手方別上限は
**「一の免税事業者等ごと」**に掛かるので、**取引先レコード単位で数えると、支店ごとに分けた分だけ
上限が増えて控除が過大になる**。**名寄せで解決したあとの単位で数える**こと（§2-2 の解決の順序）。

### 3-3. 登録状況は税額計算を支配しない

**計算を支配するのは利用者が選んだ税区分である**（[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)）。
相手が適格請求書発行事業者でも、登録番号のない区分記載請求書等しか保存していなければ
**一律に経過措置が適用される**（選択制ではない）。適用は「受け取った書類」で決まる。

登録状況の使い道は**入力支援・警告**と、**計上時に明細へ写す記録**（§4。[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md) の「判定の根拠の記録」）に限る。

### 3-4. 手入力の画面（実装は 2026-08-26。呼び名と導線は 2026-08-31 に変えた）

**画面での呼び名**（開発者の決定。2026-08-29。**「登録番号」が法令（消法 57 の 4 ①。
[消費税リサーチ §9](research/2026-08-23_消費税インボイス制度.md)）と国税庁の資料
（[リサーチ §3-2](research/2026-08-25_取引先の識別番号と公表システム.md)）の語だから**）。

補い方の考え方は [21 §5](21_画面の原則.md)、用例の調査は

**このアプリは取引先に法人番号も持つ**（§1-2）。裸の「登録番号」を使うのは

`PartnerInvoiceRegistration`。**最低限**である——
取引先・登録番号・登録年月日・取消・失効年月日・取消・失効の理由・公表名・最終確認日だけを持つ。

**入力は別画面で行い、取引先の詳細には確定した履歴だけを見せる**
（画面の骨格——「埋め込みの一覧を直接編集させ、編集したとたん本物になる仕様は無理がある。
編集は別画面で行い、『登録』の成功で戻り、失敗なら何も起こらない」——は**開発者の提案**（2026-08-31）。

**履歴は行ごとに「終わり」をあとから記録する操作があり、対象の行を選ぶ入口が要るから**）。
それまでの埋め込み編集の経緯は git の本節の履歴にある）。

  その行を開いて行う

### 3-5. 登録の不変条件（確定。2026-09-02）

**1 つの取引先の登録の履歴が守る規則。** 破ると、計上時の写し（§4）が「どれを写すか
決められない」で止まるか、誤った番号が永久に焼き込まれる。**テストの観点もこの表から導く。**

| # | 不変条件 | どこが守るか |
|---|---|---|
| R-I1 | 終わりには必ず理由がある（`ended_on` と `end_reason` は対） | DDL の CHECK ＋ 関門（言葉で断る） |
| R-I2 | 登録より前には終われない（`ended_on >= valid_from`。同日は許す——§3-2） | DDL の CHECK ＋ 関門。**CHECK は生の文字列比較のまま**（`date()` 包みへの作り直しはフェーズ 6 の取込設計と一緒に——保留リスト） |
| R-I3 | 同じ日から始まる登録は 1 件（qa/02 R26-20） | DDL の一意索引（`date()` 包み）＋関門 |
| R-I4 | **期間は重ならない。ただし隣接は許す**（下の定義） | 関門＋ DDL のトリガ（2026-09-02 に追加） |
| R-I5 | 終わりのない行（現に有効な登録）は**高々 1 件で、必ず最も新しい行**（R-I4 の帰結） | 同上 |
| R-I6 | 既存の行の取引先は変えられない（§3-4） | 関門 |
| R-I7 | 登録番号の書式は「T ＋ 数字 13 桁」（§4-2） | 関門 |
| R-I8 | 行は削除できない。取消・失効は「終わり」の記録で表す（**手入力に対して確定**。公表システムの差分の**処理区分 99＝登録簿からの削除**（[リサーチ §3-3](research/2026-08-25_取引先の識別番号と公表システム.md)）をどう表すかはフェーズ 6 の論点——保留リスト） | `CanDelete = false` ＋ 関門（画面の形は守りではない——qa/01 F-24） |
| R-I9 | 新規の行の取引先は実在する（2026-09-02 追加） | 関門が言葉で断る。最後は DB の外部キー |

**R-I4 の定義**（登録年月日の早い行を A、遅い行を B とする）:

- A に終わりが無い（`ended_on` が NULL）のに B がある → **拒む**（有効な登録が続いているのに次が始まる）
- B の登録年月日が A の終わりより前 → **拒む**（真の重複）
- B の登録年月日が A の終わりと**同じ日 → 許す**（隣接。どちらの制度解釈でも決定的に引ける——下の説明。**再登録の正常形かは未確認**（[2026-08-26 リサーチ](research/2026-08-26_登録の効力を失う日.md)））
- B の登録年月日が A の終わりより後 → 許す（間に未登録の期間がある）

**隣接を許すのは、計上時の引き当て（`InvoiceRegistrationHistory.InEffectOn`）が
「終わりの日を含み、同日に 2 件当たったら新しいほうを採る」と決めているから**である。

**関門は「保存後にできあがる履歴」で判定し、DB（一意索引・トリガ）は文単位で判定する。**
このずれのため、**複数行の期間を 1 回の保存で同時に編集する操作は、最終状態が正しくても
文の順序によっては DB が途中状態で拒みうる**（SQLite に遅延制約は無い。2026-09-02 のレビュー指摘）。
**画面は 1 行ずつ保存するのでこの形は出ない。** 複数行を 1 保存で送る取込（フェーズ 6）の
設計時に、実際の保存の順序で確かめて倒し方を決める。
取消・失効の日を有効期間に「含むかどうか」の制度解釈はフェーズ 3 送り（§3-2）なので、
隣接の 1 日はどちらの解釈でも決定的に引ける形にしてある。

**編集の許容**（保存後の行に対して）:

| 対象 | 可否 | 理由 |
|---|---|---|
| 取引先 | **不可** | R-I6 |
| 登録番号・登録年月日 | 可 | 誤記の訂正。**マスタを直しても計上済みの写しは動かない**（[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)）ので過去の帳簿は変わらない |
| 取消・失効年月日・理由 | 可（追記が本来の操作） | 登録の「終わり」は保存のあとに起きる出来事である |
| 公表名・最終確認日 | 可 | 公表システムで再確認するたび更新する |
| 行そのもの | 削除不可（R-I8） | 誤って確定した余分な行は、**内容を正しい行に編集して使う**。行を消す手を作るかは保留のまま（qa/02 R29-12） |

## 4. 計上時に仕訳へ写すもの

[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md) のとおり、**サーバが計上時に写す**。
利用者には入力させない。

| 写すもの | 理由 |
|---|---|
| `partner_name_snapshot` | 帳簿の法定記載事項①（消法 30 ⑧） |
| **計上時点の登録番号** | 法定記載事項ではないが、**CSV の入出力と監査追跡が「当時の値」を要求する**。現在のマスタから引くと、登録を取り消した相手で当時と違う値が出る |

明細に取引先が無い行には**伝票の取引先**の値を写す。**計上済みは直さない。**

### 4-1. 引く日をどう決めるか（実装。2026-08-26）

| 決めごと | どうするか | なぜ |
|---|---|---|
| 引く日付 | `journal_lines.tax_point`。**入っていなければ伝票の取引日** | `tax_point` は「引き渡しが取引日と違う取引」のための上書きである。上書きが無いなら取引の日に行われたと読むのが素直。**いまの振替伝票の画面は `tax_point` を入力させない**ので、「無ければ写さない」にすると写しが永久に空になる（計上済みは不変なので後から埋め直せない。[qa/03 L-12](qa/03_テストで漏らした実例.md)） |
| 終わりの日そのもの | **含める**（`ended_on == tax_point` の登録も引く） | 取消年月日・失効年月日が**効力の最終日か、効力を失った初日か**は一次情報で確認できていない（§3-2 が**フェーズ 3 送り**と決めた論点。2026-08-26 に国税庁の公表サイト運営方針まで当たったが確定できず）。**ここは根拠の記録であって制度上の判定ではない**ので、含める側に倒す——境界の 1 日で番号を落とすと後から補えないが、残っていれば解釈が決まったときに読み替えられる |
| 同じ日に始まる登録が 2 件 | **止める**（計上させない） | どちらを写しても 5 割の確率で誤った番号が**永久に**残る。ただし**入力の時点で止める**のが本筋なので、登録の保存の関門が先に弾く（§3-4） |
| 前の登録が終わった日に次が始まる | **新しいほうを採る** | 再登録では境界日に候補が 2 件になる。これは異常ではない |

規則は `InvoiceRegistrationHistory.InEffectOn`（純粋関数）が 1 か所で持つ。
**SQL 側では絞り込まない**——境界の条件が 2 か所に分かれると、片方だけ直したときに
「画面では有効なのに写しが空」という形で静かにずれる。

### 4-2. 登録番号の書式は保存の関門が見る（実装。2026-08-26）

DB は書式を検査しない（§3-2 の決定）ので、**`PartnerRegistrationSubmitGate` が唯一の関門**である。
止めるのは 2 つだけ。

1. **書式**（「T」＋数字 13 桁。半角のみ・大文字のみ）。壊れた番号を通すと、計上のときに
   そのまま明細へ焼き込まれ、計上済みは不変なので直せない
2. **同じ取引先に同じ日から始まる登録が 2 件できること**（上の表の 3 行目を、
   計上の場面ではなく入力の場面で止めるため）

**画面のスクリプトでは検査しない**（[ADR-0008](decisions/0008-CLBとCSharpライブラリの責務分担.md)）。
取込（フェーズ 6）も同じ入口を通るので、ここに置けば経路が増えても検査が外れない。
