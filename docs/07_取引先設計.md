# 取引先設計

> **取引先は会計マスタではない**（[ADR-0019](decisions/0019-マスタは会計が生んだ概念かで分ける.md)）。
> 会計をやめても存在するものであり、会計コアは**使うだけ**である。
> だから会計ドメインの文書（[04](04_会計ドメイン設計.md)）ではなく本書が持つ。
>
> 制度そのものの説明と出典は
> [取引先の識別番号と公表システム](research/2026-08-25_取引先の識別番号と公表システム.md) にある。
> 本書は**設計上の決定**だけを書く。

## 1. 何を持つか

### 1-1. 判断の基準

**取引先マスタは会計コアより上位の存在で、他のどこにも依存しない**（開発者の整理。2026-08-25）。
だから「会計コアが使いたいものを持つ」のではなく、**取引先マスタ自身が持つべきものを持つ**。

| | 判断 |
|---|---|
| **持ってよい** | 取引先マスタ単独で意味が決まり、他部品でも同じ意味で使うもの（名称・所在地・法人番号・種別） |
| **持たない** | 特定の部品の業務が決めるもの（与信限度・回収サイト・営業担当・仕入条件） |

迷ったら「**経費精算アプリと営業アプリが同じ意味で使うか**」を問う。

ただし**今回作るのは会計コアだけのアプリ**なので、会計に関係しない部分まで作り込まない。
「持ってよい」と「今作る」は別である。

### 1-2. 列

| 列 | 必須 | 内容 |
|---|---|---|
| `code` / `name` / `name_kana` / `is_active` | ○ | 既存 |
| `address` | | 所在地。**1 列で持つ。** 都道府県・市区町村に分割しない（設計判断: スコープに分割を使う機能が無く、入力が重くなるだけ。需要が出たら見直す） |
| `entity_type` | 画面○ | **法人（設立登記法人）／個人事業者／人格のない社団等／その他** |
| `corporate_number` | | 法人番号（13 桁）。**任意**（§2-3）。DB は桁と数字だけを見る。検査数字の検証はアプリ側 |
| `parent_partner_id` | | 名寄せの手動キー（§2-2）。自己参照は DB が拒む。循環はアプリ側（フェーズ 3 の解決ロジック） |

**種別が 2 値では足りない。** 人格のない社団等は法人番号を持ちうるが**公表は代表者の同意がある場合のみ**で、
法人とも個人事業者とも扱いが違う。

**種別の必須は画面で守り、DB は NULL 可にする**（2026-08-25 実装時の決定）。
列より前からある行と「まだ分類していない」を、既定値の偽の分類で埋めないため
（`posted_by` と同じ規律）。NULL は「未分類」。**名寄せの解決順序（§2-2）に種別は関与しない**——
未分類でも法人番号があれば法人番号で束なり、無ければ結果として手動キーの経路に落ちるだけである。
なお**個人事業者に法人番号は指定されない**（制度事実）ので、矛盾する組は DB の CHECK が拒む。

### 1-3. 個人番号（マイナンバー）は持たない

番号法 20 条が**収集・保管そのものを禁じ**ており、取引先の名寄せは 9 条 4 項の個人番号関係事務に
当たらない。本人が同意しても認められない（30 条 2 項）。
[企画概要 §6](01_企画概要.md) も「マイナンバー」を明示的に狙わないものに挙げている。

**列を作らないこと自体が最良の安全管理措置である。** 任意列にすると誰かが入れる。

### 1-4. 住所の写しは仕訳に作らない

スコープ内で帳簿に相手方の住所が要るのは**入場券等の回収特例で 1 回 3 万円以上**の 1 類型だけである
（他の類型は [03_機能スコープ](03_機能スコープ.md) がスコープ外にしている）。

**明細の「内容」欄に書く運用**とし、`partner_address_snapshot` は作らない。
1 類型のために仕組みを作るより軽く、[06 §8](06_消費税設計.md) が
「類型に該当する旨は摘要に記録する」と決めているのと揃う。

振替伝票の入力画面に注意書きを出す。

> 入場券等の回収特例（1 回 3 万円以上）に当たる仕入れは、明細の「内容」欄に取引先の住所を記載してください。

## 2. 名寄せ

### 2-1. なぜ要るか

経過措置の控除限度額（税込 1 億円）が「**一の免税事業者等ごと**」の集計だからである
（[06 §1](06_消費税設計.md)）。同じ相手の拠点・店舗・屋号が別レコードだと合算されない。

**登録番号は名寄せに使えない。** 対象は免税事業者等であり、**免税事業者は登録番号を持たない**。

### 2-2. 2 つのキー

| キー | 性質 | 対象 |
|---|---|---|
| **法人番号** | **自然キー**。同じ値なら同一法人。人が束ねる操作が要らない | 法人 |
| **`parent_partner_id`** | **手動キー**。人が明示的に束ねる | 個人事業者・法人番号が取れない相手 |

**解決の順序は「法人番号があればそれ、無ければ親を辿る、それも無ければ自分」。**
したがって**法人に `parent_partner_id` は要らない**。

**両方あって食い違ったら、法人番号を優先し、警告する。** 黙って片方を採ると人の入力ミスが見えなくなる。

### 2-3. 法人番号を必須にしない

- **外国法人**は国内に事務所等が無ければ指定されない（**一次情報は未確認**。リサーチ §5）
- **人格のない社団等**は代表者の同意がないと公表されず、調べようがない
- 伝票入力中に取引先をその場で作る場面では、まず分からない

**必須にすると入力が止まり、迂回のためのダミー値が入る。** 任意にして、未入力を警告する。

### 2-4. 氏名で自動的に束ねない

**表記ゆれが避けられない。** 候補を提示するのはよいが、機械が束ねてはならない。

## 3. 適格請求書発行事業者の登録

### 3-1. 有効期間つきの別テーブルで持つ

登録は**取消・失効・再登録**があり、1 列では「その時点でどうだったか」を表せない。
`partners` に列を足さず、`partner_invoice_registrations` を作る。

**引く日付は `journal_lines.tax_point`**（課税仕入れを行った日）。計上日でも取引日でもない。

### 3-2. 列（確定。2026-08-25）

公表システムの提供項目（[リサーチ §3-2](research/2026-08-25_取引先の識別番号と公表システム.md) で
リソース定義書の項目一覧を確認）に対応させて、次で確定した（`Designer/ddl/006_partner_registrations.sql`）。

| 列 | なぜ要るか・対応する提供項目 |
|---|---|
| `registration_no` | 登録番号（registratedNumber）。**書式は DB で検査しない**（「T ＋ 13 桁」は一次情報で未確認。リサーチ §5。確認後にアプリ側で検査する） |
| `valid_from` | 登録年月日（registrationDate） |
| `ended_on` / `end_reason`（`expired` / `revoked`） | `expired` ＝ 失効年月日（expireDate）由来、`revoked` ＝ 取消年月日（disposalDate）由来。**日付 1 列＋理由 1 列**で持つ（提供側は日付 2 項目。**同一の登録で両方が値を持つことがあるかは未確認**で、あるなら 2 列に分ける。リサーチ §5）。**それぞれが指す法的事象——届出による取りやめ・職権・事業廃止など——の対応も未確認**。提供された日付をそのまま持ち、**「その日を含むか」の判定はフェーズ 3 で制度を確認してから**実装する（当初案の `valid_to` をやめたのは、±1 日の解釈をデータに焼き込まないため）。登録より前に終わる行は CHECK が拒む（**同日はあり得るか未確認なので許している**） |
| `source`（`manual` / `nta_api` / `nta_download`） | **手で入れた値を自動同期が黙って上書きしないため** |
| `confirmed_on` | この行を人が最後に確かめた日（監査用） |
| `nta_updated_on` | 公表システム側の更新年月日（updateDate）。差分取得の基準 |
| `published_name` | 氏名又は名称（name）の写し。**公表名とマスタ名はずれる**（略称で登録している等）。突合結果が残り、名寄せの手がかりにもなる。個人のダウンロード提供では削除される項目があるため（どの項目かは未確認）空がありうる |

同じ登録の二重取込は `UNIQUE (partner_id, registration_no, valid_from)` が拒む
（**訂正区分で登録年月日そのものが訂正された場合の扱いは未確認**。取込の設計時に見直す。リサーチ §5）。

### 3-3. 登録状況は税額計算を支配しない

**計算を支配するのは利用者が選んだ税区分である**（[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)）。
相手が適格請求書発行事業者でも、登録番号のない区分記載請求書等しか保存していなければ
**一律に経過措置が適用される**（選択制ではない）。適用は「受け取った書類」で決まる。

登録状況の使い道は**入力支援・警告**と、**計上時に明細へ写す記録**（§4。[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md) の「判定の根拠の記録」）に限る。

**行の不存在は「調べて未登録だった」と「まだ入力していない」を区別しない**（2026-08-25 の決定）。
区別する列（未登録と確認した日）は、警告の文言設計（フェーズ 3）で必要になったら考える。
それまで警告は「登録情報が入っていません」のように、**不存在を未登録と断定しない言い方**にする。

## 4. 計上時に仕訳へ写すもの

[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md) のとおり、**サーバが計上時に写す**。
利用者には入力させない。

| 写すもの | 理由 |
|---|---|
| `partner_name_snapshot` | 帳簿の法定記載事項①（消法 30 ⑧） |
| **計上時点の登録番号** | 法定記載事項ではないが、**CSV の入出力と監査追跡が「当時の値」を要求する**。現在のマスタから引くと、登録を取り消した相手で当時と違う値が出る |

明細に取引先が無い行には**伝票の取引先**の値を写す。**計上済みは直さない。**
