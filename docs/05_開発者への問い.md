# 開発者への問い

> **開発者の答えが無いと先へ進まないこと**を、判断に要る材料ごと 1 か所に置く文書。
> **運用の規則は [30 §11](30_作業のルール.md) が持つ**（誰がいつ書き、答えはどう伝わり、いつ消すか）。ここは問いの本体だけ。
> **急ぎの順に並べる**——期限のフェーズが近い順 → 同じ期限の中では「決まらないと止まるもの」がある問いを先 → 期限の無いもの。
> 番号 `Q-nn` は付けた順で、**使い回さない**（並びと番号は一致しない。消えた番号は欠番のまま）。
> 答えが出て ADR か設計文書に載ったら、その問いは消す（本文は git log が持つ）。
> **本書の推奨はすべて Claude の判断である。** 開発者の決定は、ここではなく ADR・設計文書に書く（[00 §4-11](00_ドキュメント規約/本文.md)）。
> 制度・法令に触れる箇所で「Claude の読み」と書いたものは、リサーチで裏を取っていない——**法令の当てはめは開発者が最も確かな確認先**（[CLAUDE.md §2](../CLAUDE.md)）。
> 行数の目安（[00 §5](00_ドキュメント規約/README.md)）は本書に当てない——長さは未決の数で決まる。

## Q-40 遡及効のある無効・取消しに、伝票の「取消」（反対仕訳）を使わせるか

| | |
|---|---|
| **急ぎ** | **フェーズ 3 で返還等の税区分と経過措置の関門を作る回**（取消の確認文を直すのはその前でもよい） |
| **決まらないと止まるもの** | 取消の確認文（`JournalEntry.mod.cs`）・[10 §5](10_会計ドメイン設計.md)・[06 の W-10](06_利用者の作業.md)・[qa/04 の A-14](qa/04_実機操作テスト.md) の文言。返還等の設計（決定 9）は進む |
| **どこの話か** | [10 §5](10_会計ドメイン設計.md)（取消は記帳の誤りを正すためのもの）、[ADR-0066](decisions/0066-経過措置の上限は行ごとの適用の指定と計上時の関門で守る.md) の決定 9 と当てはめ 2 の取消の行 |
| **既に決まっていること** | **返品・値引き・割戻し・合意解除は返還等として当期で扱う**（決定 9）。**遡及効のある無効・取消しは別**（開発者。2026-09-19。消税基本通達 14-1-11——課税資産の譲渡等が無効・取消しとなった場合は「なかったものとする」。なお書は判明した日に 38 ① を適用することを認めるが、それは 38 ① の話で、他への類推は微妙） |

**状況。** 開発者の考えは「無効・取消しの場面で取消を使わせる」——民法上も通達上も、遡及効とは遡ってなかったことにするものだから。
「取消は記帳の誤りを正すための操作」に限っていたところに、遡及効のある無効・取消しを含めるだけで済むなら、それでよい、という意見。
**Claude が実物を当たった結果**（2026-09-19）——

- **前期の伝票も取り消せる。** 締め済みの検査（I-04）は反対仕訳の計上日だけを見る。反対仕訳は計上日が今日、取引日と課税仕入れの日は原仕訳と同じ、会計年度は今日の年度で作られる（`JournalReversal`・`AmendmentRules`）。取り消せないのは下書き・取消伝票・期首残高と繰越と決算振替だけ
- **帳簿は自然。** 前期の費用の打ち消しが当期の損益に出る（前期損益修正と同じ姿）。残高も当期で戻る。前期の繰越は動かない
- **上限の累計は前期が減る**（課税仕入れの日を写すため）。「なかったものとする」と一致する
- **消費税の側に決めることが 1 つ。** 反対仕訳の税行は課税仕入れの日が前期なので、税額を課税仕入れの日で集計すれば前期の申告の数字が変わる。遡及効からはそれが正しく、前期分は更正の請求か修正申告になる。**仕入れ側に 14-1-11 の なお書 に当たる緩和があるかは、消税基本通達の第 11 章・第 12 章（国税庁の目次から辿れる 17 ページ）に「無効」「取消し」の語が無いことまで確かめた**（2026-09-19。`curl` で原文を取って機械で探した）。第 14 章の売上げ側の 14-1-11 だけである
- **直す文言は 3 か所。** 10 §5、画面の確認文（「返品・契約解除・値引があったときは、元の伝票を取り消さずに、新しい伝票で記してください」）、06 の W-10 と qa/04 の A-14
- **注意点。** 取消を無効・取消しに開くと、通常の返品にも取消を使う誘惑が増える。期をまたぐと前期の数字が動くので、確認文は「返品・値引き・合意解除は新しい伝票」を言い続ける必要がある

**問い。** ①**取消の対象を「記帳の誤り」と「遡及効のある無効・取消し」の 2 つにしてよいか**（開発者の考えどおり）。
②**確認文の書き分け**——「返品・値引き・合意解除は新しい伝票。遡って無効・取消しとなった取引は取り消す」でよいか。「契約解除」の語をどちらに置くか。
③**前期の伝票を取り消したとき、前期の消費税の申告に影響する旨を確認文で告げるか**（[21 §1](21_画面の原則.md) の「押す前に見せる」）。

**Claude の推奨。** ①よい（機械は元々区別していない。線を広げるだけ）。②その書き分け。「契約解除」は合意解除の意味で返還等の側に置く。③告げる（1 文で足りる）。

**関連**: [10 §5](10_会計ドメイン設計.md)・[ADR-0066](decisions/0066-経過措置の上限は行ごとの適用の指定と計上時の関門で守る.md)・[ADR-0015](decisions/0015-訂正は取消と再計上の組で表し更新履歴方式を採らない.md)。

## Q-41 登録事業者の適格請求書でない請求書に、経過措置を適用できるようにするか——決定 7（登録事業者の行には「適用する」を立てられない）を保つか、登録状況を既定値と警告に限るか

| | |
|---|---|
| **急ぎ** | **フェーズ 3 で経過措置の関門を作る回**（決定 7 の関門を作る前） |
| **決まらないと止まるもの** | 決定 7 の関門の実装と、[14 §3](14_適格請求書発行事業者の登録.md) の現在形 |
| **どこの話か** | [ADR-0066](decisions/0066-経過措置の上限は行ごとの適用の指定と計上時の関門で守る.md) の決定 7、[14 §3](14_適格請求書発行事業者の登録.md)、[11 §5](11_消費税設計.md)、[消費税リサーチ §1-4](research/2026-08-23_消費税インボイス制度.md) の 3 |
| **既に決まっていること** | 決定 7（2026-09-18）。**2026-09-19 に開発者が再検討中**——決まるまで決定 7 は動かさない |

**状況。** 開発者の決定 7 は「経過措置は条見出し等に鑑みれば免税事業者等を対象としており、適格請求書発行事業者には適用すべきでないだろう」という考えに基づいていた。
しかし**インボイスQ&A 問 113-2 は、適格請求書発行事業者の適格請求書でない請求書（登録番号のない区分記載請求書等）の保存があれば経過措置を「一律に」適用すると明言している**（[消費税リサーチ §1-4](research/2026-08-23_消費税インボイス制度.md) の 3。条文も「できる」ではなく「する」規定）。
開発者の問い——「登録事業者であっても経過措置適用を行うようにし、登録事業者であっても上限までの残額を表示したり、その他、経過措置に係る機能を使えるようにしたほうがいいんでしょうか？ しかし、いったいどんな設計になるのでしょうか、そしてそんなアプリが本当に使いやすいのでしょうか」。

**Claude の整理**（2026-09-19）。**アプリは請求書を見ていない。** 税額を決めるのは利用者が選ぶ税区分で、登録状況は既定値・警告・計上時の写しに使う——これは 14 §3 が元々書いていた線である。

| 案 | 何をするか | 利点 | 欠点 |
|---|---|---|---|
| **A. 決定 7 を保つ** | 登録事業者の行には「適用する」を立てられない（関門） | 通常の実務ではこれで足りる | **問 113-2 の場面で正しく記帳できない。** 利用者は全額控除（過大）か控除なし（過少）のどちらかを選ばされる。制度より狭い |
| **B. 登録状況は既定値と警告に限る** | 既定値は「登録事業者なら適用しない、未登録なら適用する」。利用者はどちらの向きにも倒せる。**登録事業者の行に「適用する」を立てたら警告**（「この取引先は登録事業者です。適格請求書があるなら経過措置ではなく全額控除です」）。上限の累計・残り枠・一覧は、行に「適用する」が立っていれば相手の登録状況に関係なく同じに動く | 制度の全部を記帳できる。**関門は「法令上あり得ない状態」（上限超え）だけに残り、書類で決まることを止めない**という線が一貫する。使いやすさは変わらない——登録事業者の行で「適用する」に触れなければ、警告も残り枠も出ない | 誤って「適用する」を立てると控除が過少になる（法令違反ではない） |
| C. B に加えて、登録事業者の行の「適用する」に理由の印を要る | 「適格請求書なし」の印を行に持たせる | 帳簿で場面が分かる | 旨の記載は制度上同じなので、印は制度が要求していない。欄が増える |

**Claude の推奨。 B。** 理由——①「会計ロジックの不具合の絶無」は、制度が認める記帳をできなくすることも不具合である。②設計は決定 7 を「関門」から「既定値と警告」に格下げするだけで、累計・分割・一覧は何も変わらない。③使いやすさは、通常の利用者が触れない行には何も出ない、という形で守れる。
**逆向き（未登録の相手に全額控除の税区分を選ぶ）も同じく警告**にすると、線が揃う（登録簿の更新遅れで登録済みの相手が未登録に見える場面があり、機械では止められない）。

**関連**: [ADR-0066](decisions/0066-経過措置の上限は行ごとの適用の指定と計上時の関門で守る.md)・[14 §3](14_適格請求書発行事業者の登録.md)・[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)。

| **既に決まっていること** | **普通預金は「その他の債権」に入り、照会は要らない**（開発者の決定。2026-09-16。旧 Q-18）。**記載事項は法税規則 別表二十四（二）に準じる**（[ADR-0042](decisions/0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の決定 6。2026-09-06。「預金の口座別に、取引の年月日、事由、支払先及び金額」。**この読みを保つか（六）で読むかが、本問の ①**）。**取引先は行ごとに選べ、伝票の取引先は既定値**（開発者の決定。[ADR-0062](decisions/0062-明細の取引先は行ごとに選べるようにし伝票の取引先は既定値にする.md)）。**初期データで「取引先を要する」を立てるのは 6 科目で、広げるのは利用者**（開発者の決定。2026-09-11。[15 §1-2](15_記帳の枠組み.md)）。**E1 ハ・ニ の書類はスコープ外**（開発者の決定。2026-09-16。旧 Q-19。[40 の E1](40_優良な電子帳簿の対応表.md)） |

**状況。** 旧 Q-18 の答えで開発者は「**『相手方』を補助科目で管理するのみという仕様はかなり気持ちが悪いです。
可能であればそれ以外の手法の検討をお願いします**」と述べた（2026-09-16）。

**いまの設計はこうである**（[40 §4-1](40_優良な電子帳簿の対応表.md) の 1 行目）——普通預金の行では、
**口座＝補助科目**（開発用 DB では `みずほ銀行 本店` のような補助科目で口座を区分する——[qa/04](qa/04_実機操作テスト.md) の B-11。口座別に補助科目を持つ運用に依存する）、
**事由＝摘要**、**支払先＝取引先**（明細か伝票の取引先の実効値。`JournalEntry.PartnerOf`）。
**「取引先を要する」は 6 科目にしか立てていない**ので、**普通預金の行は取引先が空のまま計上できる**。

**「相手方」の読みが 2 つあり、どちらを指しているかで直し先が変わる。**

| 読み | 相手方は誰か | いまの設計では |
|---|---|---|
| A. 法税規則 別表二十四（二）に準じる（[ADR-0042](decisions/0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の決定 6。2026-09-06） | **支払先**——入出金の相手（外注先・得意先・給与の受取人） | **取引先**（欄はあるが、普通預金の行には要していない） |
| B. 同（六）その他の債権として読む（**Claude の読み**——開発者の 2026-09-16 の「その他の債権に該当」は電帳規則 5 ① の対象帳簿の話で、記載事項をどの区分で読むかには触れていない） | **債権の相手方＝金融機関**（預け先） | **補助科目の名前だけ**。**`sub_accounts` に取引先への参照列は無い**（`Designer/ddl/004_masters.sql`——設計上の事実）ので、法人番号も名寄せも、取引先で引く検索（[40 の D1](40_優良な電子帳簿の対応表.md)）も届かない |

**Claude は、開発者の言葉は B を指していると読んだ**——A の支払先は補助科目では管理していないので、
「補助科目で管理するのみ」と言えるのは B の相手方だけである。**違っていたら教えてほしい。**
**B を採るなら [ADR-0042](decisions/0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の決定 6 の後半（（二）に準じる）を動かすことになる**——本問はそれを問う。

**手法の案**（Claude の検討。2026-09-17）。

| 案 | 何をするか | 利点 | 欠点 |
|---|---|---|---|
| **① 金融機関を取引先に登録し、口座の補助科目が取引先を参照する** | `sub_accounts` に任意の `partner_id` を足す（口座の補助科目だけが使う）。**明細も伝票も取引先が空なら、補助科目の取引先を実効値に採る**。帳簿には金融機関の名前が写る | **相手方が実体（取引先）になる**——法人番号・名寄せ・取引先で引く検索が効く。**入力は増えない**（口座を選べば相手方が決まる）。**A の支払先を伝票か明細に選んだときはそちらが写る**ので、（二）に準じる読みも壊れない | **支払先（A）と金融機関（B）が 1 つの取引先の欄を争う**——両方は写せない。金融機関が写るのは、支払先が無い行（利息・手数料・口座間振替）だけになる。**実効値の規則は 1 か所ではない**（2026-09-17 に開いて数えた）——C# は `JournalEntry.PartnerOf` の 1 か所だが、**DDL のトリガ**（`trg_journal_entries_partner_presence_when_posted`。`COALESCE` の式が 2 つ）、**帳簿と一覧の SQL 3 本**（`JournalEntryList`・`JournalBook`・`GeneralLedger`。**取引先の絞り込みは `COALESCE` を使わず `l.partner_id = @p OR (l.partner_id IS NULL AND e.partner_id = @p)` にほどいてある**——[qa/01 H-09](qa/01_CLB静かな失敗.md)。`COALESCE` のままなのは空値検索と一覧の「複数」の数え、表示列は `COALESCE(NULLIF(写し,''), lp.name, ep.name)`）、**取引先の「使用中」の判定**（`009_partner_meaning.sql`。実効値ではなく「明細か伝票のどちらかに載っていれば使用中」の 2 つの `EXISTS`）が、それぞれ別の形で同じ既定値の規則を持つ。**全部に補助科目の取引先を足し、SQL はほどいた形を保ったまま `sub_accounts` を JOIN する**（H-09 を踏み直さないため）。**スキーマ変更 1 本**（[ADR-0020](decisions/0020-スキーマは現在形の正典で持ち変更は差分で配る.md)）。**計上時の写し（[ADR-0060](decisions/0060-勘定科目・補助科目・部門の名前も計上時に写す.md)）に影響が無いかを確かめる** |
| ② 普通預金に「取引先を要する」を立て、金融機関を取引先として行ごとに選ぶ | 初期データの `requires_partner` を普通預金にも立て、利用者が普通預金の行の取引先に金融機関を選ぶ | スキーマ変更なし。**[ADR-0062](decisions/0062-明細の取引先は行ごとに選べるようにし伝票の取引先は既定値にする.md) の行ごとの取引先がそのまま使える** | **毎行、金融機関を選ぶ手間**（既定値の仕組みが無い）。**支払先（A）は普通預金の行には載らない**（相手の行に載る）。**期首残高・繰越の免除（[15 §1-2](15_記帳の枠組み.md) の宿題 1）が普通預金にも掛かる** |
| ③ いまのまま（A の読みで足りるとする） | 口座＝補助科目、支払先＝取引先。**普通預金に「取引先を要する」を立てるかは利用者に任せる** | 変更なし | **開発者が「気持ちが悪い」と述べた形そのもの**。B の読みでは相手方が実体で無い |

**Claude の推奨は ①。** 優先順位は「**明細の取引先 → 伝票の取引先 → 補助科目の取引先**」——
既定値の連なりを 1 段深くするもので、[ADR-0062](decisions/0062-明細の取引先は行ごとに選べるようにし伝票の取引先は既定値にする.md) の「伝票の取引先は既定値」を崩さない。
**これで A と B のどちらの読みでも列は埋まる。** ただし**「相手方は必ず金融機関」（B を厳格に読む）なら ② のほうが正しい**——
**どちらの読みを採るかは開発者に決めてほしい**（法令の当てはめは開発者が最も確かな確認先——[CLAUDE.md §2](../CLAUDE.md)）。
**① を採るなら、有価証券（法税規則 別表二十四（七）の相手方——[40 §4-1](40_優良な電子帳簿の対応表.md)）にも同じ形が使える**（銘柄の補助科目が証券会社を参照する）。

**一覧の載せ先。** 「条文上は相手方が要る科目」の一覧（候補は [40 §4-1](40_優良な電子帳簿の対応表.md) の表の直下）は
E1 ニ の雛形に載せると決めていた（開発者の決定。2026-09-11）が、雛形はスコープ外になった（旧 Q-19）。

| 案 | 中身 |
|---|---|
| **a. 勘定科目マスタの注記に 1 文で載せる**（推奨。**ただし「一覧を示す」の縮小である**） | `Account.mod.json` の「取引先を要する」の欄には注記が既にある（[ADR-0062](decisions/0062-明細の取引先は行ごとに選べるようにし伝票の取引先は既定値にする.md) の帰結 4）。**そこに「法税規則 別表二十四が相手方・支払先を求める区分（債権債務・収入・経費）に当たる科目には立てる」を 1 文で足す**（[21 §1](21_画面の原則.md) の「画面に書いていない規則は、凡例に 1 文で書く」）。**科目名の一覧は画面に書かない**——利用者の科目体系は初期データと違いうるから（Claude の判断）。**候補の表そのものは [40 §4-1](40_優良な電子帳簿の対応表.md) に残す** |
| b. 利用者向けの文書をリポジトリに置く | 操作説明書に近づく——**開発者がスコープ外と決めたもの**と線が引きにくい |
| c. 載せない | 開発者の 2026-09-11 の案 A のうち「一覧を利用者に示す」の側を、雛形と一緒に取り下げることになる |

**やってほしいこと。** ①相手方の読み（A か B か、両方か）②手法（①〜③のどれか、または別の形）③一覧の載せ先（a〜c）。
**いつ**——フェーズ 4 で [ADR-0059](decisions/0059-期首残高と繰越と決算振替は仕訳として持ち閉鎖残高勘定は作らない.md) の入口条件 1 を解く回まで。

## Q-27 行セットの差分で殺す掃引を、コミット前フックに載せてよいか

| | |
|---|---|
| **急ぎ** | 期限なし。ただし**いま載せないなら、クエリの SQL を触った人が手で流すのを忘れたときに誰も気づかない** |
| **決まらないと止まるもの** | 止まらない。手で流せる（`pwsh -NoProfile -File tools/clb/sql_sweep.ps1 -Mode Rows`）。**計器の配線が腐っていないことは、いまも `dotnet test` の傘下で毎回見ている** |
| **どこの話か** | コミット前フックの段（[tools/README](../tools/README.md) の表）と `tools/clb/sql_sweep.ps1` |
| **既に決まっていること** | **載せない理由は速さではなかった**——[ADR-0056](decisions/0056-SQLミューテーションはクエリのSQLを1箇所ずつ壊し行動テストだけで赤になるかを見る.md) 決定 7 の逐語は「**生き残りが多いうちは、毎回流しても上限を通るだけで誰も読まない**」。同 決定 7 は「**減らしてから、載せるかを開発者に諮る**」と続けている。**前例がある**——[ADR-0012 §8](decisions/0012-テスト方針とカバレッジのゲート.md) の Stryker は、当初「フェーズの区切りで」としたものを**実測の速さを見て開発者の判断で毎回実行へ変えた** |

**状況が変わった。** 2026-09-15 に **B 案（行セットの差分で殺す掃引）** が入った（[ADR-0058](decisions/0058-行セットの差分で殺す掃引は入力コーパスを持たず行動テストが流した入力をその場で当てる.md)）。

- **速さ**: `-Mode Rows` は**端から端まで 7.4 秒**（ビルド込み。掃引そのものは 5 秒）。
  **A 案（`-Mode Tests`）は 6 分 13 秒**なので、**こちらは載せる話にならない**
- **生き残り**: **15 件まで落ち、全部に説明が付いている**（型 A の範囲比較 10・型 B の並び順 4・`CASE` の `DISTINCT` 1。
  内訳は ADR-0058 の実測）。**「誰も読まない」という理由は、もう当たらない**
- **ラチェットは読むものではなく鳴るものである。** 緑のときは何も読まなくてよく、
  **説明の付かない点が 1 つ増えた日にだけ止まる**
- **フック全体の重さから見ると誤差**である。`dotnet stryker` の段は 5 プロジェクトで数分かかる

**選択肢**

| 案 | 中身 | 短所 |
|---|---|---|
| **A（推奨）** | **`-Mode Rows` を 1 段足す**（`dotnet test` の段の後）。`-Mode Tests` は今までどおり手動 | 文書だけのコミットでも 7 秒余分にかかる。**python と dotnet の両方に依存する段が 1 つ増える** |
| B | 載せない（現状のまま）。区切りで手で流す | **流し忘れに誰も気づかない。** いまも [31 §6](31_検証のルール.md) の文章だけが守っている |
| C | `-Mode Rows` も `-Mode Tests` も載せる | **毎回 6 分**。コミットのたびに待たされ、**フックを迂回する習慣ができる**——いちばん避けたい形 |

**Claude の推奨は A。** **7 秒で、流し忘れという人の失敗が 1 つ消える。**
**B の危険は具体的である**——2026-09-14 に `JournalEntryList` の行動テストが
「SQL の絞り込みを 1 つも撃っていない」状態で通っていた（[qa/03 の L-47](qa/03_テストで漏らした実例.md)。
**入れてから 11 日である**——日数の出どころは git log で、L-47 には書いていない）。
**あれを見つけたのは掃引を手で流した回**であって、**流さなければ今も気づいていない。**
**ただし見つけたのは `-Mode Tests` である。** `-Mode Rows` でも同じ点が生き残りに出たはずだ、というのは
**Claude の読みで、当時の検体で回して確かめてはいない**——
根拠は「**どのテストもその引数を束縛していないなら、どの入力でも行は変わらない**」という理屈だけである。

**やってほしいこと。** A・B・C のどれかを教えてほしい（A なら Claude が
`tools/git-hooks/pre-commit` と [tools/README](../tools/README.md) の段の表を直す）。**いつ**——期限なし。
