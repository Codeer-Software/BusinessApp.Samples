# 開発者への問い

> **開発者の確認を要すること**を、判断に要る材料ごと 1 か所に置く文書。**2 種類ある**——
> **①答えが無いと先へ進まないもの** と **②Claude が自分で決めて実装し、後から諮るもの**（[34 §1-1](34_開発者とClaudeの分担.md)）。
> **運用の規則は [30 §11](30_作業のルール.md) が持つ**（誰がいつ書き、答えはどう伝わり、いつ消すか）。ここは問いの本体だけ。
> **急ぎの順に並べる**——期限のフェーズが近い順 → 同じ期限の中では「決まらないと止まるもの」がある問いを先 → 期限の無いもの。
> 番号 `Q-nn` は付けた順で、**使い回さない**（並びと番号は一致しない。消えた番号は欠番のまま）。
> 答えが出て ADR か設計文書に載ったら、その問いは消す（本文は git log が持つ）。
> **本書の推奨はすべて Claude の判断である。** 開発者の決定は、ここではなく ADR・設計文書に書く（[00 §4-11](00_ドキュメント規約/本文.md)）。
> 制度・法令に触れる箇所で「Claude の読み」と書いたものは、リサーチで裏を取っていない——**法令の当てはめは開発者が最も確かな確認先**（[CLAUDE.md §2](../CLAUDE.md)）。
> 行数の目安（[00 §5](00_ドキュメント規約/README.md)）は本書に当てない——長さは未決の数で決まる。

## Q-66 ブラウザで利用者を切り替える（ログインする）ことを Claude がしなくなった——全件の回に要る `admin`・`soumu_ippan` の項目をどうするか

| | |
|---|---|
| **急ぎ** | **次に §3 の全件を流す回の前**（フェーズ 3 の区切り、または最後の全件から 3 日——[qa/04 §1](qa/04_実機操作テスト.md)） |
| **決まらないと止まるもの** | **全件のうち、`soumu_bucho` 以外の利用者で流す画面の項目**——[qa/04 §3-6](qa/04_実機操作テスト.md) の権限の項目の多く（PRM-08〜PRM-16）・MST-30 の ① など。**毎回実施する項目は止まらない**（PRM-17 は HTTP だけで流せた——下） |
| **どこの話か** | [31 §3](31_検証のルール.md)（開発用アカウントのログイン）・[qa/04 §3 の前書き](qa/04_実機操作テスト.md)（どの利用者で流すか） |
| **既に決まっていること** | **開発者は、localhost の開発用アカウントについて、Claude がログイン・ログアウトしてよいと許可している**（2026-09-05・2026-09-19。31 §3） |

**状況。** **2026-09-24 から、ブラウザの欄にパスワードを入れることを Claude はしない**——ブラウザを操作する道具（Claude in Chrome）の安全の決まりで、**利用者が許可していても変わらない**（31 §3 に書いた）。
**そのため、ブラウザの利用者を Claude が切り替えられない。** ブラウザがいまログインしている `soumu_bucho` のままでは流せない項目が出る。

- **この回（保存の関門の断りを束ねた回）は、MST-30 の ①（利用者の画面の離脱確認。`admin` でしか開けない）が未達になった**——関門を持たない画面で、この回の変更は届かない（Claude の読み）。**それを記録に書いてマージした**
- **PRM-17（Web API を直に叩く）は、ブラウザを使わず HTTP だけで `admin` にログインして流せた**（手順は qa/04 の PRM-17 の行）

**選択肢は 3 つある。**

| # | 選択肢 | 分かっていること |
|---|---|---|
| ① | **全件の回の前に、開発者がブラウザを必要な利用者でログインしておく**（Claude は項目を利用者ごとにまとめ、切り替えの回数を減らして頼む） | 開発者が居る時間にしか全件が終わらない。**切り替えのたびに開発者の手が要る**（全件では `soumu_bucho` → `soumu_ippan` → `admin` の 3 回ほど） |
| ② | **利用者ごとに別のブラウザ（または別のプロファイル）を用意し、開発者がそれぞれに 1 度ログインしておく**——Cookie が別になるので、Claude は道具で接続先のブラウザを選ぶだけで利用者を切り替えられる | **Claude の道具が複数のブラウザへの接続と切り替えを持っていることは、道具の一覧で見た**（`list_connected_browsers`・`switch_browser`）。**複数のブラウザで実際に動くか・ログインがどれだけ保つかは確かめていない** |
| ③ | **画面を通らない項目は HTTP で流し、`soumu_bucho` 以外の画面の項目は開発者が居るときにまとめて流す** | 権限の項目の多く（PRM-08〜PRM-16）は画面の到達と表示を見るので、HTTP では代えられない |

**Claude の推奨は ②**（Claude の判断）。**一度用意すれば、自律作業の中で全件が回る**——①と③は、開発者の不在が長い日に全件が止まる。
**②を採るなら、先に Claude が 1 本試す**（開発者が 2 つ目のブラウザに 1 つの利用者でログインしたあと、Claude が接続を切り替えて画面を開けるか）。**動かなければ①に戻る。**

**やってほしいこと。** ①〜③ のどれか。②なら、どのブラウザ（またはプロファイル）をどの利用者にするかと、ログインしておいてほしい時期。
**いつ**——次に §3 の全件を流す回の前。

| | |
|---|---|

**言葉**——**本体行**は、利用者が打つ明細の行（消耗品費など）。**消費税行**は、税抜経理で本体行からシステムが作る仮払消費税等・仮受消費税等の明細の行（[11 §2](11_消費税設計.md)）。

**状況。** **いまの振替伝票は、金額をそのまま税抜の本体行として保存している**（消費税行はまだ無い）。
消費税行を作るには、**利用者がどちらの金額を打つのか**を決める必要がある——

- **税込で打つ**（内税）: 「消耗品費 1,100 ／ 現金 1,100」と打てば、保存で「消耗品費 1,000・仮払消費税等 100」に割る。**貸借は打った時点で合う**。
  **帳簿積上げの計算の形（支払対価 × 10/110）と同じ向き**である（[消費税リサーチ §5-2](research/2026-08-23_消費税インボイス制度.md)）
- **税抜で打つ**（外税）: 「消耗品費 1,000 ／ 現金 1,100」と打ち、保存で「仮払消費税等 100」を足す。**打つ時点では貸借が合わない**（相手の 1,100 は利用者が暗算する）。
  **税抜の小計と消費税が別に書かれた請求書はこちらの向き**（ペルソナの外注費・SES の請求書がそうだというのは **Claude の想定**——[02](02_ペルソナ.md) は請求書の書式に触れていない）

**freee・弥生・PCA は「行＋その行の税額」で持ち、行ごとに計算して丸める**（原文で確かめた。**マネーフォワードは行ごとと読めるが、明記した文は見つからなかった**。2026-09-24 に調べた。[市販ソフト比較](research/2026-09-24_市販会計ソフト比較_消費税額の入力と計算単位.md)）。
**入力の形は社によって違う**——

| 社 | 入力の形 | 選ぶ単位 |
|---|---|---|
| freee | **税込が原則**。取引の画面に内税／外税の切替 | **本文に無い**（取引の画面に切替がある） |
| マネーフォワード | 経理方式で決まる——税込／税抜（内税）＝税込額を打ち、仮払消費税は行にせず残高として計上する／税抜（別記）＝仮払消費税の行を手で起こす。**外税入力は見当たらない** | 会計年度 |
| 弥生 | 内税／外税／別記 | **科目の既定 → 仕訳の行ごとに変えられる** |
| PCA | 内税／外税／税計算しない | **既定は補助科目＞勘定科目＞会社の順に効き**（補助科目の設定がいちばん優先）、**仕訳の貸借ごとに変えられる** |

**選択肢は 3 つある。**

| # | 選択肢 | 分かっていること |
|---|---|---|
| ① | **行ごとに「内税／外税」を選べる。既定は会社か勘定科目に持つ**（弥生は科目の初期値、PCA は補助科目＞勘定科目＞会社） | **欄が 1 つ増える**（W-01 の手数）。**既定を合わせておけば、ふだんは触らない**。**DB には打った形（内税か外税か）と打った金額も持つ**——下書きを開き直したとき、**打った字が画面に戻る**ようにするため（税抜で持つ `amount` だけでは、税込で打った 1,100 が 1,000 に化けて見える） |
| ② | **税込だけ**（freee の原則・マネーフォワード） | **欄が増えない。** **困るのは税込の合計が書かれていない証憑だけ**——税率ごとの税抜額と税額しか無い請求書では、利用者が足し算して税込を打つ |
| ③ | **税抜だけ**（いまの DB の形のまま） | **打つ時点で貸借が合わない**——相手の行の金額を利用者が暗算するか、保存してから直すことになる。**税込しか分からない額（レシートなど）はそもそも打てない**。**調べた市販の 4 社のどれもこの形だけではない** |

**税額が請求書と合うかは、入力の形より、売り手の丸め方と帳簿の端数処理が同じかで決まる**（Claude が Python で計算した。2026-09-24。税抜の金額 0〜20 万円の全部、10%・8%）——
- **売り手の丸め方と帳簿の端数処理が同じなら**、税抜で打っても税込で打っても、行ごとに計算すれば**請求書の税額と一致する**（税込で打った行は、税込額から逆算した税額——税込 × 10/110 を丸めたもの——になる）
- **違えば、どちらの形でも請求書と 1 円ずれる行が多く出る**（例: 売り手が四捨五入・帳簿が切捨てなら、10% の金額の半分）
- **2 つの形どうしが食い違うのは、そのうちの一部の組だけ**——売り手が切捨て・帳簿が四捨五入のとき、10% で 10 件に 1 件、8% で 25 件に 1 件（例: 税抜 1,005 円・税額 100 円・税込 1,105 円の請求書は、税込で打つと 100 円、税抜で打つと 101 円）

**Claude の推奨は ①**（Claude の判断）。**既定を内税にしておけば、ふだんの手数は ② と同じ**で、
**税込の合計が書かれていない証憑だけ外税に切り替えられる**——ペルソナは両方を扱うと **Claude は想定している**（レシート・交通費は税込で毎日、家賃・リース・SES の月次請求は税抜の小計＋消費税で毎週——頻度は [06](06_利用者の作業.md) の W-01・W-04）。
**② との差は「欄が 1 つあるか」と「足し算を利用者にさせるか」**で、**税額は、売り手と帳簿の丸め方が同じならどちらでも同じ**（上の計算）。**② を選んでも筋は通る**——手数の少なさを取るなら ② である。
**③ は採らない**（打つ時点で貸借が合わないのは、W-01 の「続けて何枚も入れる」に正面から逆らう）。
**請求書の税額と帳簿の税額が 1 円ずれるのは、①②のどちらでも起きる**——売り手の丸め方が帳簿と違う・1 枚の請求書を部門ごとに複数行へ分けた、など。**そのときは税額の上書き（W-14。消費税行を作る回に入れる——[04](04_実装計画と現在地.md)）で直す。**
**丸める単位**（行ごとか、1 回の課税仕入れごとか）**はこの問いとは別に、消費税行を作る回に決める**——帳簿積上げは「課税仕入れの都度」（[11 §4](11_消費税設計.md)）。
[03 §D](03_機能スコープ.md) の「税率ごとに 1 回の端数処理／行ごとに切り捨てない」は、適格請求書の側の規則だと **Claude は読む**（11 §4 がそう書き分けている）。

**①を採るときに Claude が決めること**（開発者の答えは要らない——[34 §1-1](34_開発者とClaudeの分担.md) の「それ以外の疑問」）:
既定を持つ場所（会社か勘定科目か）、税額の端数処理の設定の置き場、画面での税額の見せ方（行の「税額」列か、消費税行を並べるか）、
下書きの間に消費税行を作るか計上のときに作るか。**決めた案は ADR にして後から諮る。**

**やってほしいこと。** ①〜③ のどれか。
**いつ**——消費税行を作る回の着手前（**Claude はそれまで入力の形に依らない部分を進める**）。

**市販**: freee の仕訳帳は、仮受消費税の行にも本体行の税区分を付けて出す（[市販ソフト比較](research/2026-09-24_市販会計ソフト比較_消費税額の入力と計算単位.md)）。**取引先まで写すかは確かめていない。**

（**消費税行に取引先を持たせない**案は、`PartnerOf` が伝票の取引先に落とすので ② と同じ結果になる。**本当に空にするには「消費税行は伝票の取引先に落とさない」という例外を、`PartnerOf` と帳簿の SQL・トリガに入れる必要がある**——選択肢から外した。）
**Claude の推奨は ①**——**帳簿の法定記載事項（消税法 30 ⑧ 一 イ の相手方）は課税仕入れについて言うもので、仮払消費税等の行そのものに課されているかは Claude の読みでは明らかでない**（条文の当てはめは未確認）。**ただ、同じ取引の 2 行で相手が違うと帳簿を読む人が迷う**、という実務の理由で ① を推す。

**やってほしいこと。** ①か②か。**いつ**——消費税行を作る回の着手前（止めない）。

**(b) 外し方**——**税区分の 2 行（TS8・TP8）と税率の表の 1 行を消し、2 つの表の CHECK が許す値から `legacy_8` を除いた**（[12 §1](12_マスタ台帳.md) の「削除はさせない」の例外。参照が無いことを数えて——何を適用の前に、何をあとに数えたかは [11 §1-1-1](11_消費税設計.md)）。
**別の道もあった**——**CHECK に `legacy_8` を残し、TS8・TP8 を `is_active = 0` にし、税率の行も残す**。この道なら、**[11 §1-1-1](11_消費税設計.md) の①の形（外す前の形）で戻すときは有効に戻すだけで済み、表の作り直しが要らない**。

**(c) ペルソナがいま旧税率の取引を持つか**——**(a) の前提**である（「後から足せる」は、足すまでに旧税率の伝票が計上されないときにだけ成り立つ）。
**2019-10-01 以後にも旧税率が出る経路として、自己レビューで Claude が二次情報から 2 つ挙げた**——①資産の貸付けの経過措置 ②リースの分割控除（経過措置ではない経路）。**条文も国税庁の原文も開いておらず、要件と日付も確かめていない**（中身は [税率リサーチ §3](research/2026-09-23_消費税の税率と地方消費税の税率.md)）。

**あわせて**——2019 年の改正には工事の請負等の経過措置もあった、と同じ二次情報は言う（確かめていない。[税率リサーチ §3](research/2026-09-23_消費税の税率と地方消費税の税率.md)）。**次の改正に同じ措置が置かれるかは分からない。置かれれば、ペルソナの受託開発（[02](02_ペルソナ.md) §2）が当たりうる**（Claude の推測）。そのときは改正前の税率を使う仕組みが要る（[11 §1-1-1](11_消費税設計.md) の「足すときに決めること」）。

**(d) 画面に置いたもの**（2026-09-25。Claude の判断）——**税区分の画面の「登録」ボタンの下に、旧税率の区分が無いことと、旧税率の取引のために「軽減税率」の税区分を作ったり名前を変えたりしないことを置いた**（字は `TaxCategory.mod.json` の `RateKindNotesLabel`）。
**届くのは、税区分を作る・直す人（経理責任者）だけである**——税区分の画面は「設定とマスタ」にあり、経理責任者にしか開かない（[qa/04](qa/04_実機操作テスト.md) §3 の権限の表）。**伝票で既存の「軽減税率」の区分を選ぶ道（経理担当）は、何も止めていない。** 効き目も確かめていない。
**次の一手は書いていない**——このアプリの中に正しく入れる道が無いからで、[21 §2-3](21_画面の原則.md) の例外（押す前に見せる注意では、次の一手を書かない選択がある）を当てた（Claude の当てはめ）。
**経理担当に届く手は 3 つある**（Claude の整理）——①税区分の名前に対象を足す（いまの「課税仕入（軽減税率）」を、例えば「課税仕入（軽減税率・飲食料品等）」に）②振替伝票の「入力の決まり」に 1 行 ③あとで作る関門の警告（例: 既定の税区分が標準税率の科目で「軽減税率」を選んだとき）。
**いまはどれも足していない**（Claude の判断。2026-09-25）——①消費税行も本番の記帳もまだ無く、(c) の期限までに誤りが額に出る時期が無い ②(c) の答えが「持たない」なら要らず、「持つので足す」なら要るのは案内ではなく旧税率の区分である ③いまの「入力の決まり」は「計上する」ボタンより上にあり（Q-52 の ② の入れ替え前）、1 行足すと押す前に越える字が増える ④名前を変えるなら seed と移行で配り直すことになり、この回の主題（外す）を越える。
**税区分の画面にだけ置いたのは、区分を作る人に当てるためである**——(c) の答えを待つ間に旧税率のつもりの区分が作られて伝票に使われると、答えが出たあとに 1 枚ずつの訂正になる。
**(c) の答えが「持つが、このアプリでは足さない（申告のときに税理士が調整する など）」なら、要るのは伝票の側の案内である**——そのときは ①〜③ から選ぶ。

**やってほしいこと。** (a) この判断（後から足せるので外す）でよいか (b) 外し方（行を消し、CHECK から除いた）でよいか
(c) **ペルソナが 17・18 期に旧税率の取引を持つか**（確かめる材料——事務所の賃貸借の締結日と賃料改定の条項、税率が変わる前に引渡しを受けたリースを分割で控除しているか）。上の ①② の読みが合っているか。
(d) **(c) の答えが出るまで、旧税率の案内を税区分の画面だけに置き、経理担当に届く手（名前・「入力の決まり」・関門の警告）は足さない**——これでよいか。
**いつ**——消費税行を作る回の着手前（止めない）。

## Q-61 返還等の専用の税区分を付けた明細の行で、税率表から税率を取り出すとき、どの日を使うか

| | |
|---|---|
| **急ぎ** | **返還等の税区分を作る回まで**（フェーズ 3） |
| **決まらないと止まるもの** | **止まらない**——**いま配っている税率表の行は期間がすべて同じ**なので、どの日で取り出しても同じ値になる。**次の税率改正の行を足した日に初めて分かれる** |
| **どこの話か** | [11 §1-1](11_消費税設計.md) の例外の段落と保留リスト・[11 §5-7](11_消費税設計.md) |
| **既に決まっていること** | **返還等の行の基準日は取引日（＝返還等を受けた日）**（ADR-0066 の決定 9 の 4。**11 §5-7 はこの扱いを「当期説」と呼ぶ**——返還等を受けた課税期間で差し引く、の意味で、学説の名ではない）。**控除の割合は税区分が持ち、日付では取り出さない**（決定 9 の 3） |

**言葉**——**基準日**は、その明細の税率・控除割合を税率表や控除割合の表から取り出すときに使う日（[11 §5-2](11_消費税設計.md)）。
ふつうの明細では `tax_point`（課税仕入れの日を取引日と別に入れる欄）、無ければ取引日を使う。**返還等の行は `tax_point` を見ず、取引日に固定する**（利用者の入力で当期説を覆させないため）。

**状況。** **消税法 32 ① 一 は、返還等の税額を今の税率の分数で直接書いている**——「百十分の七・八（…軽減対象課税資産の譲渡等に係るものである場合には、百八分の六・二四）を乗じて算出した金額」
（逐語は [条文リサーチ §7](research/2026-09-11_インボイス経過措置の附則条文.md)。開発者の提示。2026-09-13）。
**だから、返還等を受けた日（取引日）の税率で計算するのが本則の読み**である（Claude の読み）。
**税率が改正されたとき、改正前の課税仕入れの返還等に旧い税率を当てるかは、税率を改めた法律の附則（経過措置）が決める**と Claude は読むが、**その附則は開いていない**（Claude の読み。条文は未確認）。
**一方で、返還等の行は元の課税仕入れの日を持っていない**（別建ての伝票で、`tax_point` を見ない）。

**選択肢**:
① **取引日で取り出す**（いまの形のまま。**本則の読みに合う**。改正をまたぐ返品に経過措置があれば、そのときに ② の区分を足す）
② **税区分で税率も固定する**（「仕入返還・経過措置 80%・標準 10%」のように、返還等の専用の税区分が税率まで持つ。改正のたびに区分を足す）
③ **元の課税仕入れの日を、税率を取り出すためだけに別の欄で持つ**（基準日には使わない）

**Claude の推奨は ①**（Claude の判断）——**本則は今の税率で書いている**ので、日付を 1 つも増やさずに済む。**改正をまたぐ経過措置は、改正が来たときに附則を開いて ② の形で足せる。**

**やってほしいこと。** ①前提の読み（本則は返還等を受けた日の税率。旧い税率を当てるかは改正法の附則しだい）が正しいか ②①〜③ のどれか。**いつ**——返還等の税区分を作る回まで。

| 2 | **例外①: 取引先の意味の凍結と、取引先の値の断りを束ねない** | **画面から踏める**（MST-41）——使用中の取引先の「取引先コード」を変え、同時に「取引先名」を 101 文字にして「登録」すると、1 回目は「コードは変えられない」だけ、コードを戻した 2 回目に「取引先名は 100 文字以内」 | 凍結は会計コアの関門、取引先の値は取引先部品の関門が見ている。**束ねるには、取引先部品に「理由だけを集めて返す」公開メソッドを足し、会計コアから凍結した欄を渡す必要がある**。**事実**: 取引先部品は「取引先だけのデプロイは可能な形に」する約束がある（[ADR-0025](decisions/0025-取引先を部品として分ける.md)。取引先だけのホストはまだ無い）。**Claude の判断**: 足すメソッドはその約束の一部になり、後から変えにくい |
| 3 | **例外②: 入れ子になった関門どうしの理由を束ねない**（仕訳 → 自社情報 → マスタ → 取引先部品 → その中の登録番号 → 取引先。`AccountingSubmitPipeline`・`PartnerSubmitPipeline`） | **画面からは起きない**（画面の 1 回の保存が 2 つの段に同時に届くのは例外①だけ——デザインを読んだ Claude の読み。登録番号の一覧は取引先の詳細から作れない——`Partner.mod.json` の `CanCreate` 等が `false`）。**いまは API だけ**。**取込（フェーズ 6）は未設計**で、複数のモジュールを 1 回で送る形にするかはそのとき決まる | 画面の利用者に届く場面が無いのに、入れ子の関門の検査を 1 つの呼び出しに合わせ直す費用がかかる |
| 4 | **1 つの欄の中の 2 つ目の誤りは言わない**（前からある Claude の決め。[ADR-0047](decisions/0047-マスタのコードは空白を落とす以外書き換えず字種で断る.md) の決定 10——開発者の指示「即エラー。次へ進まない」を**欄ごとの指示と読んだのは Claude**。同 ADR は「10〜12 は Claude の決めで、開発者は述べていない」と書く） | コード「-A--B」は、1 回目に先頭の記号を言い、直した 2 回目に連続を言う。コードが空・書式違いなら重複は言わない | 同じ欄の直し先は 1 つなので、1 つ直せば次が見える。**開発者の逐語が欄ごとを指すのか、関門全体を指すのか（それなら (a) で、2026-09-20 に退けられた形）は読みが割れうる** |

**選択肢は 3 つある。**

| # | 選択肢 | 分かっていること |
|---|---|---|
| ① | **このままでよい** | **2 回目に回るのは、1 つの保存で 2 つの違反が重なったときだけ**。例外①は、使用中の取引先のコードを変える（改名ではない）操作と、ほかの欄の違反が重なったときに限る（**稀だというのは Claude の見込み**で、測っていない） |
| ② | **例外①も束ねる**（取引先部品に公開メソッドを足す） | **取引先部品の公開 API が 1 つ増える**。例外②と 1 は残る |
| ③ | **1（前提の崩れた検査は飛ばす）と 4 をやめ、従っても通らない一手も並べて全部言う** | **逆を言う一手が 1 通に並ぶ**（上の個人事業者の例）。利用者は、どちらに従えば通るかを自分で見分けることになる |

**Claude の推奨は ①**（Claude の判断）。**残る 2 回目は、どれも 2 つの違反が同じ保存で重なったときだけ**で、1 通に全部を言うために部品の公開 API を広げる（②）か、逆を言う一手を並べる（③）ほうが、利用者と部品の両方にとって重いと見た。
**区別の基準**（Claude の判断）——1 と 4 は、並べると一手どうしが逆を言うか、同じ欄の直し先が 1 つなので**並べる意味が薄い**。
**例外①は、2 つの一手が両立する（コードを戻し、取引先名を短くする）のに、費用で分けている**——開発者の「初めから言ってくれ」にいちばん近いのはここなので、**迷うなら例外①から見てほしい。**

**やってほしいこと。** ①〜③ のどれか。**いつ**——次に保存の関門を触る回まで（止めない）。

## Q-67 補助科目を持つ勘定科目の「補助科目を使う」をオフにしたいとき、要らない補助科目をどう片づけるか——あわせて、ADR-0038 §3 の「オフの科目は補助科目を持てない」は明細の話か、マスタの話か

| | |
|---|---|
| **急ぎ** | **次にマスタの保存の関門を触る回まで**（**止めない**）。**2 つの性格がある**——①（いまの形。マスタの読み）は **Claude の読みで入れ、後から諮る**もの、推奨の②は**入れる前に諮る**もの（[34 §1-1](34_開発者とClaudeの分担.md)） |
| **決まらないと止まるもの** | **止まらない** |
| **どこの話か** | [ADR-0038](decisions/0038-使用中のマスタは意味を変えられない.md) §3・[12 §2](12_マスタ台帳.md)・[06](06_利用者の作業.md) の W-33（勘定科目・部門・税区分を保守する作業） |
| **既に決まっていること** | **開発者の決定（2026-09-05）**——補助科目は 2 値で、「オンの科目だけが補助科目を持て、そのとき必須。オフの科目は持てない」（ADR-0038 §3 の箇条の字。§3 の見出しは「補助科目は 2 値。オフなら「持てない」」）。3 値にしない理由は「持てるが任意の実務上の需要が思い当たらず、一部の明細だけ補助科目なしを許すと『全補助科目の合計＝科目の残高』が崩れる」。**別の決まりとして、マスタは削除させず、無効化する**（[12 §1](12_マスタ台帳.md)。経緯は ADR-0006 → ADR-0019） |

**言葉**——**「補助科目を使う」**は勘定科目の画面のチェックボックス（列は `uses_sub_account`）、**「有効」**は補助科目の画面のチェックボックス（`is_active`。オフにすると伝票の候補に出ない）。
**未使用**は、計上済みの明細が無いこと（下書きは数えない。ADR-0038 §1）——**使用中の科目は「補助科目を使う」そのものを変えられない**（同 §2）ので、この問いは未使用の科目の話である。
**マスタの側の関門**は、勘定科目・補助科目の保存を断る関門（`MasterSubmitGate`）。**計上の関門**は、伝票を計上するときに断る関門で、**「補助科目を使う」がオフの科目の明細に補助科目を付けたままでは計上できない**（2026-09-08 から。DB のトリガも同じことを見る）。

**Claude の読み。** **決定の字には、明細の話かマスタの話かの明示が無い。材料は両側にある。**
**明細と読む材料**——理由はどれも明細の話で（一部の明細だけ補助科目なしを許さない）、「そのとき必須」も明細でしか意味が通らない。
**マスタと読む材料**——決定の前日（2026-09-04）に Claude が書き、ADR-0038 §3 が引いている [qa/03 L-27](qa/03_テストで漏らした実例.md) は、通ってしまう経路に
「補助科目マスタの勘定科目の候補が絞られていない」「補助科目マスタに保存の関門が無い」を数え、「補助科目を**持てる**か」を科目と補助科目の関係（マスタ）の意味で使っている。§3 の箇条の「オンの科目だけが補助科目を持て」も同じ字である。
**マスタにも置けない**（オフの科目の下に補助科目の行を置けない）**と読んだのは Claude である**——2026-09-08 に ADR-0038 の追記（「マスタ側は残っている」）でそう書き、2026-09-09 に補助科目の側の関門を置いた。**開発者がどちらの読みだったかは、記録に無い。**

**状況。** **2026-09-24 に、マスタの読みの穴を塞いだ**——それまでは補助科目の側からしか見ておらず、補助科目を持つ未使用の勘定科目の「補助科目を使う」をオフにできた（帳簿は計上の関門が守っていた）。
**無効の補助科目も数える**（1 件でもあれば断り、断りに件数を出す）。補助科目は画面から削除できないので、**オフにしたい利用者に残る道は「補助科目を、オンの別の勘定科目へ移す」だけ**である。
そこで困ることが 4 つある（Claude の自己レビューで、06 の利用者の作業から見る観点が挙げた）——

1. **移し先の科目も、同じ理由でオフにできなくなる**（連鎖する）
2. **移し先の科目の補助科目の一覧に、無関係な行が残る**（無効にすれば伝票の候補には出ない）
3. **オンの科目がほかに無いと、移し先が無い**——置き場のためだけにオンの科目を作ることになる（初期データでオンなのは普通預金・当座預金・定期預金の 3 つ）
4. **移し先に同じコードの補助科目があれば、コードも変える**（一意なのは勘定科目とコードの組）

**選択肢は 3 つある。**

| # | 選択肢 | 分かっていること |
|---|---|---|
| ① | **このまま**（無効も数え、移して片づける） | 上の 4 つが残る。**マスタの読みの文言にいちばん近い**（Claude の読み） |
| ② | **数えるのを「有効な補助科目」と「明細（下書きを含む）が参照する補助科目」に絞る**。あわせて、オフの科目の下で「有効」をオンに戻す更新を断る | 利用者の一手は「要らない補助科目の『有効』をオフにする」だけになり、移す必要が無くなる（**下書きが参照していれば、先にその下書きを直す**）。**参照の無い無効の行は、残高にも明細にも現れない**——決定の理由（全補助科目の合計＝科目の残高、一部の明細だけ補助科目なしを許さない）は崩れない（Claude の読み）。**明細の読みなら、決定の範囲の中である**（Claude の読み） |
| ③ | **明細が参照しない補助科目は、削除できるようにする** | 12 の「削除はさせない。無効化する」を補助科目だけ改める。**削除の画面と関門が要る**（参照の有無を見る）。**市販ソフトが未使用の補助科目の削除と、補助科目を持つ科目の切り替えをどう扱うかは調べていない**（[32 §2](32_調査のルール.md)） |

**Claude の推奨は ②**（Claude の判断）。**決定の理由を崩さずに、上の 4 つが全部消える。** ③は削除という新しい操作を足すぶん重い。
**①では、ほかにオンの科目が無いと（上の 3）、置き場のためだけにオンの科目を作らせ、その科目もオフにできない**（上の 1）——
W-33 は必須の作業で、必須の作業は [30 §4-1](30_作業のルール.md) の 100% の側に置く（[06 §3](06_利用者の作業.md)。06 §3 の意味の欄は Claude の言い換え）。
**② は、開発者の決定がマスタの話だったならそれを緩める。どちらだったか記録に無いので、答えを待つ。**

**やってほしいこと。** ①〜③ のどれか。**あわせて、ADR-0038 §3 の決定は明細の話だったか、マスタの話だったか。**
**マスタの話だったなら、ADR-0038 §4（関門で拒み、DDL のトリガでも拒む）がこの規則にも及ぶか**——いまは関門だけが守り、Claude は §4 を意味の凍結についての決定と読んで及ばないとしている（[12](12_マスタ台帳.md) の保留リスト。及ぶなら DB のトリガを置く）。
**材料は両側にある**——及ばないと読む材料は、§4 の文例が科目区分を変えられないという断りであること。**及ぶと読む材料**は、§3 の明細の側を関門とトリガの 2 層で実装したこと（ADR-0038 の 2026-09-08 の追記）と、
意味の凍結ではないコードの書式の規則を「ADR-0038 §4 と同じ形」で 2 層に置いた先例（[12 §2-1](12_マスタ台帳.md)）。
**いつ**——次にマスタの保存の関門を触る回まで（止めない）。

**いまの設計はこうである**（[40 §4-1](40_優良な電子帳簿の対応表.md) の 1 行目）——普通預金の行では、

**事由＝摘要**、**支払先＝取引先**（明細か伝票の取引先の実効値。`JournalEntry.PartnerOf`）。
**「取引先を要する」は 6 科目にしか立てていない**ので、**普通預金の行は取引先が空のまま計上できる**。

**「相手方」の読みが 2 つあり、どちらを指しているかで直し先が変わる。**

| 読み | 相手方は誰か | いまの設計では |
|---|---|---|
| A. 法税規則 別表二十四（二）に準じる（[ADR-0042](decisions/0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の決定 6。2026-09-06） | **支払先**——入出金の相手（外注先・得意先・給与の受取人） | **取引先**（欄はあるが、普通預金の行には要していない） |
| B. 同（六）その他の債権として読む（**Claude の読み**——開発者の 2026-09-16 の「その他の債権に該当」は電帳規則 5 ① の対象帳簿の話で、記載事項をどの区分で読むかには触れていない） | **債権の相手方＝金融機関**（預け先） | **補助科目の名前だけ**。**`sub_accounts` に取引先への参照列は無い**（`Designer/ddl/004_masters.sql`——設計上の事実）ので、法人番号も名寄せも、取引先で引く検索（[40 の D1](40_優良な電子帳簿の対応表.md)）も届かない |

**Claude は、開発者の言葉は B を指していると読んだ**——A の支払先は補助科目では管理していないので、
「補助科目で管理するのみ」と言えるのは B の相手方だけである。**違っていたら教えてほしい。**
**B を採るなら [ADR-0042](decisions/0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の決定 6 の後半（（二）に準じる）を動かすことになる**——本問はそれを問う。

**手法の案**（Claude の検討。2026-09-17）。

|---|---|---|---|
