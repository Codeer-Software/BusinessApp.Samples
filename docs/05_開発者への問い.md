# 開発者への問い

> **開発者の答えが無いと先へ進まないこと**を、判断に要る材料ごと 1 か所に置く文書。
> **運用の規則は [30 §11](30_作業のルール.md) が持つ**（誰がいつ書き、答えはどう伝わり、いつ消すか）。ここは問いの本体だけ。
> **急ぎの順に並べる**——「決まらないと止まるもの」がある問い → 期限のフェーズが近い順 → 期限の無いもの。
> 番号 `Q-nn` は付けた順で、**使い回さない**（並びと番号は一致しない。消えた番号は欠番のまま）。
> 答えが出て ADR か設計文書に載ったら、その問いは消す（本文は git log が持つ）。
> **本書の推奨はすべて Claude の判断である。** 開発者の決定は、ここではなく ADR・設計文書に書く（[00 §4-11](00_ドキュメント規約/本文.md)）。
> 制度・法令に触れる箇所で「Claude の読み」と書いたものは、リサーチで裏を取っていない——**法令の当てはめは開発者が最も確かな確認先**（[CLAUDE.md §2](../CLAUDE.md)）。
> 行数の目安（[00 §5](00_ドキュメント規約/README.md)）は本書に当てない——長さは未決の数で決まる。

## Q-06 廃止済みの消税軽減通達の差し替え先——候補の表を作った。6 行それぞれに「合っている／違う」を付けてほしい

| | |
|---|---|
| **急ぎ** | **フェーズ 3（消費税）の着手前。急ぐ**（[80 §4](80_参照法令一覧.md) の ①） |
| **決まらないと止まるもの** | 軽減税率の当てはめ。[消費税リサーチ §10](research/2026-08-23_消費税インボイス制度.md) が**廃止済の通達 2・5・8・9・11・12 を 6 か所で引いている**ので、根拠が無いまま設計に入ることになる |
| **どこの話か** | [80 §2](80_参照法令一覧.md) の「消税軽減通達」の行（令和5年10月1日廃止）と、消費税リサーチ §10 |
| **既に決まっていること** | 制度で迷ったら推測せず開発者に聞く（[CLAUDE.md §2](../CLAUDE.md)・[32 §1](32_調査のルール.md)）。通達は e-Gov で引けないと見ている（**裏は未確認**。80 §4 の ③） |

**状況。** リサーチ §10 は「消税軽減通達の 2・5・8・9・11・12」を根拠に 6 つのことを書いているが、その通達は廃止されている。
書いてあること自体が間違いになったのではなく、根拠の置き場が動いただけに見える（**Claude の読み**——旧の項と候補の項は、本文の冒頭で引く条文が違う。旧 2 は改正法附則 34 ①一、5−9−1 は消税法 別表第一 一）。

**Claude がしたこと（2026-09-10）。** 国税庁のページで、廃止された通達の別冊の項の見出しと、消費税法基本通達 第5章第9節「軽減対象課税資産の譲渡等」の項の見出しを突き合わせた。
**旧 2〜14 が 5−9−1〜13 に 1 つずつずれて並び、6 か所とも同名の項がある**（「令５課消２−９により追加」の注記——廃止の発遣文書と同じ番号——は 13 本中 11 本にあり、候補のうち 5−9−7 には無い）。
**見出しの文言が同じ項を対応させただけで、本文は読み比べていない。** 見たのは 5−9 の 1 ページだけで、軽減 Q&A と基本通達の他の節は当たっていない。 表は [消費税リサーチ §10](research/2026-08-23_消費税インボイス制度.md) に置いた（出典 URL つき）。

| 本表の箇所 | 旧の根拠（廃止済） | 候補（消税基本通達） |
|---|---|---|
| 飲食料品の範囲 | 軽減通達 2「食品の範囲」 | **5−9−1**「食品の範囲」 |
| 一体資産の 2/3 判定 | 軽減通達 5「一体資産に含まれる食品に係る部分の割合…」 | **5−9−4**（同名） |
| 外食の飲食設備 | 軽減通達 8「飲食に用いられる設備」 | **5−9−7**（同名） |
| 飲食設備の設置者が異なる場合 | 軽減通達 9 | **5−9−8**（同名） |
| 持ち帰りの判定 | 軽減通達 11 | **5−9−10**（同名） |
| ケータリング | 軽減通達 12「給仕等の役務を伴う飲食料品の提供」 | **5−9−11**（同名） |

**やってほしいこと。** 6 行それぞれについて、**候補の項が本当に同じ内容を引き継いだ項か**を見て、合っていれば ○、違えば正しい根拠を教えてほしい
（本文の読み比べは法令の当てはめなので開発者に残る）。○ なら Claude がリサーチ §10 の 6 か所と 80 §2 の行を差し替える。

**関連**: [80 §4](80_参照法令一覧.md) ①・[消費税リサーチ §10](research/2026-08-23_消費税インボイス制度.md)。

## Q-05 「取引先を要する」科目の顔ぶれ——外注費を「仕入れ」に当ててよいか。6 科目で足りるか、条文どおり広げるか

| | |
|---|---|
| **急ぎ** | **実データを入れる前**（この列は一方通行で、計上済みの明細がある科目では外せない。開発機は再シードできるので、期限はフェーズ 7 のデモデータ——それより前に利用者が使うなら、その前） |
| **決まらないと止まるもの** | 初期データ（`Designer/seed/004_accounts.sql`）と [40 §4-1](40_優良な電子帳簿の対応表.md) の表の確定。E1 ニ の雛形に書く「取引先が要る科目」の一覧 |
| **どこの話か** | 勘定科目の `requires_partner`（取引先を要する）。規則は [10 §6-2](10_会計ドメイン設計.md) |
| **既に決まっていること** | 属性と関門を置くこと、立てる科目は「売掛金・買掛金・売上げ・仕入れ」（開発者。2026-09-06）。科目コードへの当てはめは Claude |

**状況。** 初期データは **1300 売掛金・2100 買掛金・4010〜4030 売上高 3 本・5010 外注費** の 6 科目。
**このペルソナに仕入高の科目は無く、外注費を「仕入れ」に当てた**——それでよいかが第一の問い。

**条文どおりなら 6 では足りない。** 法税規則 別表二十四は科目名ではなく性質で切っており
（（四）（五）は「売掛金と同様の性質を有するもの」、（六）は相手方、（十二）（十四）は相手方・支払先。逐語は [対象帳簿リサーチ §2](research/2026-09-06_優良な電子帳簿の対象帳簿と記載事項.md)）、
残っている候補は次のとおり。

| 別表二十四 | 候補の科目 |
|---|---|
| （六）その他の債権債務 | 未収入金・未払金・立替金・仮払金・貸付金・預り金・仮受金・借入金／普通預金（（二）に準じるかは Q-18 の照会待ち） |
| （十二）その他の収入 | 受取利息・受取手数料・雑収入 |
| （十四）その他の経費 | **電帳規則 5 ① の括弧書きが除く賃金・給料手当・法定福利費・厚生費を外した全部** |
| （十一）売上 | 売上値引・戻り高 |

**全部に立てると、行ごとに取引先を選ばない限り経費を計上できなくなる。**

**戻せないのは「外す」向きだけ**——立てるのはいつでもでき、計上済みの明細がある科目では外せない（[10 §6-2](10_会計ドメイン設計.md)）。
だから **「立てすぎていないか」を先に、「広げるか」をその次に**聞きたい。
**どの案でも効く事実が 1 つ**——[10 §6-2 の宿題 1](10_会計ドメイン設計.md)。決算振替・繰越・期首残高には相手方が無いので、
**いま立ててある損益科目（売上高 3 本・外注費）は、その種別を作った瞬間に締められなくなる**。免除の軸をフェーズ 4 で決める必要があり、広げるほど免除の範囲も広がる。

| 案 | 何をするか | 利点 | 欠点 |
|---|---|---|---|
| **A. 6 科目のまま。広げるのは利用者に任せる** | 初期データは 6。E1 ニ の雛形に「条文上は相手方が要る科目」の一覧を載せ、利用者が自分の科目に立てる | 使い勝手を製品が決めつけない。立てるのは画面からいつでもできる | 立て忘れた科目の帳簿は、相手方の欄が空きうる（摘要で補う） |
| B. 条文どおり全部に立てる | 候補を全部 1 にする | 帳簿の記載事項を製品が保証する | 行ごとに取引先が要る。取引先マスタが肥大する。宿題 1 の免除も広がる |
| C. 債権債務（六）まで | 未収入金・未払金・立替金・仮払金・貸付金・預り金・仮受金・借入金を足す | 相手方が本質的な科目だけ広がる | 線の根拠が「性質」ではなく「手間」になる |

**Claude の推奨は A。** 根拠は 2 つ——①「どの科目に立てるか」は利用者の科目体系に依るので、製品が一律に決めるより雛形で示すほうが合う（[ADR-0042](decisions/0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の論法）。
②行ごとに相手方を要する入力は手数が増える（**Claude の想定**。[02](02_ペルソナ.md) は経費の内訳を書いていないので、ペルソナの経費が何かは分からない）。

**関連**: [40 §6](40_優良な電子帳簿の対応表.md)（元の置き場）・[seed の README](../Designer/seed/README.md)・[10 §6-2](10_会計ドメイン設計.md)。同じ列について Claude が承認なしで決めた 5 つは Q-11 の表。

## Q-04 ADR-0051（利用者に見せる文言は型で決める）を承認するか

| | |
|---|---|
| **急ぎ** | **次に関門を足す回の前**（フェーズ 3 の消費税の関門） |
| **決まらないと止まるもの** | 止まらない（main に入って動いている）。ただし覆すなら、乗るコードが増える前のほうが安い |
| **どこの話か** | [ADR-0051](decisions/0051-利用者に見せる文言は型で決め想定外の例外は保存の入口で定型文にする.md)。`BusinessApp.ServerSupport` の `RejectedException` と `AccountingSubmitPipeline.SubmitAsync` |
| **既に決まっていること** | 差し戻しは 1 種類の見た目で見せる（[ADR-0023](decisions/0023-利用者への差し戻しは1種類の見た目で見せる.md)）。関門は例外で止める（[ADR-0008](decisions/0008-CLBとCSharpライブラリの責務分担.md)） |

**状況。** 開発者向けの例外文言（「仮 ID … に本物の ID が 2 つ対応している」など）がそのまま画面に出る経路があった（[R57-35](qa/02_自己レビュー記録.md)）。
2026-09-10 に次の 3 つを決めて実装し、main に入れた（**Claude の判断。開発者は未承認**）。

1. **利用者に見せてよい差し戻しは、すべて `RejectedException` の派生にする**（5 種。規約テストが 2 部品の例外の派生を全数取って確かめる）
2. **保存の入口は、それ以外の例外をすべて定型文（「保存できませんでした。…」）に差し替えて、原文をログへ回す**
3. **差し戻しは例外のまま CLB へ渡す**（`ModuleSubmitResult.ExceptionMessage` で返す形は、一度作って戻した——トーストは 1 枚にならず（枚数はボタンで決まる。[qa/01 F-42](qa/01_CLB静かな失敗.md)。2 枚のまま受け入れた——[21 §2-6](21_画面の原則.md)）、巻き戻しを CLB 固有の挙動に頼ることになる）

**Claude の推奨は承認。** 型で線を引けば、関門を足す人が「画面に出る文言か」を毎回考えなくてよい。
覆すなら代わりの線引きが要る（文言の中身では判定できない）。ADR に「検討したが採らなかった案」を 3 つ書いてある。

**関連**: [qa/02 ラウンド 71](qa/02_自己レビュー記録.md)・[qa/01 F-42](qa/01_CLB静かな失敗.md)。

## Q-12 計上検証の「警告」をどこへ届けるか

| | |
|---|---|
| **急ぎ** | **フェーズ 4**（不変条件をまとめて触る回。[04 §5](04_実装計画と現在地.md) の「摘要の必須を不変条件に足すか」と同じ回） |
| **決まらないと止まるもの** | 止まらない。ただし**それまで警告は誰にも届かない**——無効にした科目・部門・取引先・補助科目のまま取消が通っても、利用者は気づかない |
| **どこの話か** | `ViolationSeverity.Warning`。取消・訂正で「止めない」と決めた検査（[10 §6-3](10_会計ドメイン設計.md) の表）が警告に落とすが、本番コードはどこもそれを読んでいない |
| **既に決まっていること** | 取消は止めない（利用者に直す手立てが無い。Q-11 の表）。届け先は決めていない |

**状況。** 「止めない」は「警告に落とす」の意味で作ったが、計上の側は Error だけを読む。自己レビュー（[R69-13](qa/02_自己レビュー記録.md)）が「既存の穴を取引先で 1 種類広げた」と指摘した。
**警告が出る経路は 2 つで、通る道が違う**——取消は Web API（`JournalAmendmentEndpoint`。[ADR-0016](decisions/0016-画面から呼ぶサーバ処理はWebAPIに置く.md)）、
訂正の再計上は「計上する」の標準の保存経路（`this.Submit()` → `AccountingSubmitPipeline`）。

| 案 | 何をするか | 利点 | 欠点 |
|---|---|---|---|
| **A. 「取り消す」の応答に載せ、画面で黄色のトーストにする** | Web API の応答に `warnings` を足し、`JournalEntry.mod.cs` がトーストにする | 利用者がその場で気づく。帳簿は変えない | **取消しか覆わない**——訂正の再計上（保存の成功）に文言を載せる経路は未計測。トーストを読み飛ばすと残らない |
| B. 計上済みの伝票に注記として残す | 列を足し、詳細と帳簿に出す | 両方の経路を覆う。後から見返せる | 計上済みの伝票に列を足す（[ADR-0004](decisions/0004-優良な電子帳簿への準拠と仕訳の不変性.md) の不変性は保てるが、スキーマが動く） |
| C. ログにだけ書く | サーバのログ | 実装が最小 | 利用者には届かない（いまと同じ） |

**Claude の推奨は A を取消に当て、再計上の側は「保存の成功に文言を載せられるか」を実測してから決める**（[qa/01](qa/01_CLB静かな失敗.md) の型——想像で決めない）。
警告の中身は「無効な相手を使った」で、利用者が直後にできることは「マスタを有効に戻す」か「気にしない」の 2 つしかない。
B は帳簿に出す価値のある情報になった時点で考える。
