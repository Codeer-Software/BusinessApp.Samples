# 開発者への問い

> **開発者の答えが無いと先へ進まないこと**を、判断に要る材料ごと 1 か所に置く文書。
> **運用の規則は [30 §11](30_作業のルール.md) が持つ**（誰がいつ書き、答えはどう伝わり、いつ消すか）。ここは問いの本体だけ。
> **急ぎの順に並べる**——期限のフェーズが近い順 → 同じ期限の中では「決まらないと止まるもの」がある問いを先 → 期限の無いもの。
> 番号 `Q-nn` は付けた順で、**使い回さない**（並びと番号は一致しない。消えた番号は欠番のまま）。
> 答えが出て ADR か設計文書に載ったら、その問いは消す（本文は git log が持つ）。
> **本書の推奨はすべて Claude の判断である。** 開発者の決定は、ここではなく ADR・設計文書に書く（[00 §4-11](00_ドキュメント規約/本文.md)）。
> 制度・法令に触れる箇所で「Claude の読み」と書いたものは、リサーチで裏を取っていない——**法令の当てはめは開発者が最も確かな確認先**（[CLAUDE.md §2](../CLAUDE.md)）。
> 行数の目安（[00 §5](00_ドキュメント規約/README.md)）は本書に当てない——長さは未決の数で決まる。

## Q-12 計上検証の「警告」をどこへ届けるか

| | |
|---|---|
| **急ぎ** | **フェーズ 4**（不変条件をまとめて触る回。[04 §5](04_実装計画と現在地.md) の「摘要の必須を不変条件に足すか」と同じ回） |
| **決まらないと止まるもの** | 止まらない。ただし**それまで警告は誰にも届かない**——無効にした科目・部門・取引先・補助科目のまま取消が通っても、利用者は気づかない |
| **どこの話か** | `ViolationSeverity.Warning`。取消・訂正で「止めない」と決めた検査（[15 §1-3](15_記帳の枠組み.md) の表）が警告に落とすが、本番コードはどこもそれを読んでいない |
| **既に決まっていること** | 取消は止めない（利用者に直す手立てが無い。Q-11 の表）。届け先は決めていない |

**状況。** 「止めない」は「警告に落とす」の意味で作ったが、計上の側は Error だけを読む。自己レビュー（[R69-13](qa/02_自己レビュー記録.md)）が「既存の穴を取引先で 1 種類広げた」と指摘した。
**警告が出る経路は 2 つで、通る道が違う**——取消は Web API（`JournalAmendmentEndpoint`。[ADR-0016](decisions/0016-画面から呼ぶサーバ処理はWebAPIに置く.md)）、
訂正の再計上は「計上する」の標準の保存経路（`this.Submit()` → `AccountingSubmitPipeline`）。

| 案 | 何をするか | 利点 | 欠点 |
|---|---|---|---|
| **A. 「取り消す」の応答に載せ、画面で黄色のトーストにする** | Web API の応答に `warnings` を足し、`JournalEntry.mod.cs` がトーストにする | 利用者がその場で気づく。帳簿は変えない | **取消しか覆わない**——訂正の再計上（保存の成功）に文言を載せる経路は未計測。トーストを読み飛ばすと残らない |
| B. 計上済みの伝票に注記として残す | 列を足し、詳細と帳簿に出す | 両方の経路を覆う。後から見返せる | 計上済みの伝票に列を足す（[ADR-0004](decisions/0004-優良な電子帳簿への準拠と仕訳の不変性.md) の不変性は保てるが、スキーマが動く） |
| C. ログにだけ書く | サーバのログ | 実装が最小 | 利用者には届かない（いまと同じ） |

**Claude の推奨は A を取消に当て、再計上の側は「保存の成功に文言を載せられるか」を実測してから決める**（[qa/01](qa/01_CLB静かな失敗.md) の型——想像で決めない）。
警告の中身は「無効な相手を使った」で、利用者が直後にできることは「マスタを有効に戻す」か「気にしない」の 2 つしかない。
B は帳簿に出す価値のある情報になった時点で考える。

**関連**: [15 §1-3](15_記帳の枠組み.md)・[qa/02 R69-13](qa/02_自己レビュー記録.md)。

## Q-13 取引を記さない伝票（取消・期首残高・決算振替・繰越）に、法税規則 55 ① と別表二十四はどう当たるか

| | |
|---|---|
| **急ぎ** | **フェーズ 4**（期首残高・決算振替・繰越を作る回） |
| **決まらないと止まるもの** | 期首残高・繰越の伝票の「内容」欄に何を入れるか。摘要の必須（[10 §4-2-1](10_会計ドメイン設計.md)）をそれらにも当てるか |
| **どこの話か** | [10 §4-1](10_会計ドメイン設計.md)・[ADR-0045 決定 3](decisions/0045-振替伝票1枚には1つの取引だけを記す.md)・[ADR-0048](decisions/0048-伝票の複製は取引の内容だけを写す.md) |
| **既に決まっていること** | 「伝票は 1 取引を 1 伝票とする」（開発者。2026-09-08。逐語）。それ以外は決まっていない |

**状況。** **「取消・期首残高・決算振替・繰越は経済事象ではなく帳簿の上の振替なので、法税規則 54・55 が数える『取引』に当たらない」は Claude の読み**で、諮っていない。
**期首残高と繰越で、何が「内容」（55 ①・別表二十四）を満たすのかも決まっていない。**

| 論点 | Claude の読み |
|---|---|
| 取消伝票は「取引」か | 当たらない（原仕訳の反転で、経済事象を記していない）。**ただし訂正の再計上は当たる**（取引を記し直す） |
| 期首残高・繰越の「内容」 | 「前期繰越」のような固定の摘要で足りる（相手方も給付も無い） |
| 決算振替の「内容」 | 「損益振替」「利益処分」の固定の摘要で足りる |

上の読みでよいか、違うなら何を記すべきかを教えてほしい。

**関連**: [40 §4-1](40_優良な電子帳簿の対応表.md)。元の置き場は README の保留リスト（本文は git log）。

## Q-14 勘定科目・補助科目・部門の名前も、取引先と同じく計上時に写すか

| | |
|---|---|
| **急ぎ** | **マスタに手を入れる回**（[12](12_マスタ台帳.md) の論点。フェーズ 4 の帳簿を出し切る回までに） |
| **決まらないと止まるもの** | 止まらない。ただし科目・補助科目・部門を改名すると、計上済みの伝票と帳簿の表示が動く |
| **どこの話か** | `journal_lines` の科目・補助科目・部門（写しを持たない）。取引先は `partner_name_snapshot` を持つ |
| **既に決まっていること** | **取引先は写す**——帳簿（[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)）も伝票の画面（[ADR-0037](decisions/0037-計上済みの伝票は画面でも計上時の姿を見せる.md)。開発者の決定。2026-09-02）も計上時の姿を見せる。**科目・補助科目・部門は決めていない** |

**状況。** 取引先の写しは消税法 30 ⑧ の帳簿記載事項が根拠で、名称で写すのは本プロジェクトの選択（ADR-0018 の注記）。
科目・補助科目・部門の名前は、[40 §4-1](40_優良な電子帳簿の対応表.md) の当てはめでは**別表二十四（六）（十二）（十四）の「名称を付して区分し」と（二）の「口座別に」に当たりうる**ので、
「法定記載事項ではない」とは言い切れなくなった（2026-09-06。**Claude の読み**）。写しを持たないまま改名すると、計上済みの伝票と帳簿の名前が動く。

| 案 | 何をするか | 利点 | 欠点 |
|---|---|---|---|
| **A. 取引先と同じ扱いにする** | 明細に科目名・補助科目名・部門名の写しを足し、計上時に焼く。画面も ADR-0037 と同じ切り替え | 帳簿と伝票が計上時の姿で揃う。改名の影響が消える | 列が 3 つ増える。マイグレーションと帳簿クエリの書き換え |
| B. 写さない | 改名は「意味を変える」に当たるとして止める（[ADR-0038](decisions/0038-使用中のマスタは意味を変えられない.md) の線を名前まで広げる） | 列を足さない | 誤字の訂正もできなくなる。ADR-0038 §2 は名前を「変えてよい列」に置いている |
| C. コードだけを写す | 名前は写さず、コードで区分を固定する | 列が小さい | 名前が動く問題は残る |

**Claude の推奨は A**（帳簿の記載を計上時の姿で固定した ADR-0018・ADR-0037 の方針に合わせる。**設計判断であって法令の当てはめではない**）。

**関連**: [40 §6](40_優良な電子帳簿の対応表.md)（元の置き場）・[ADR-0038 §2-1](decisions/0038-使用中のマスタは意味を変えられない.md)・[qa/02 R34-12](qa/02_自己レビュー記録.md)（取引先の側。ADR-0037 で閉じた）。

| | |

| **急ぎ** | **フェーズ 4**（帳簿を出し切る回） |
| **決まらないと止まるもの** | [03](03_機能スコープ.md) の「含めない」に書けるか。優良な電子帳簿の F1'（対象帳簿の**全て**）の当てはめ |

## Q-16 登録番号の行を、画面から消す手を作るか

| | |
|---|---|
| **急ぎ** | **フェーズ 6**（公表システムからの取込を設計する回。取込が「削除」の差分を受けたときの形と同じ根） |
| **決まらないと止まるもの** | 止まらない。それまで、誤って足した余分な行は内容を編集して使い回す |
| **どこの話か** | 取引先の詳細の登録番号の一覧（`PartnerInvoiceRegistration`。`CanDelete: false`。[14 §5](14_適格請求書発行事業者の登録.md) の R-I8） |
| **既に決まっていること** | 取消・失効は終わりを記録して残す（[14 §4](14_適格請求書発行事業者の登録.md)）。**正しく入力された行の話**で、入力の誤りを消せないことまでは決めていない |

**状況。** 入力の導線を取引先の詳細 1 本にしたことで逃げ場が消えた（[R29-12](qa/02_自己レビュー記録.md)）。

| 案 | 何をするか | 利点 | 欠点 |
|---|---|---|---|
| A. 作らない | いまのまま。余分な行は編集して使う | 不変性が単純 | 本当に余分な行は永久に残る |
| **B. 計上済みの仕訳が写していない行だけ消せる** | 関門と DDL のトリガで「その行を写した計上済み明細が無い」を条件に削除を許す | 誤入力を消せる。帳簿の写しは守られる | 条件つき削除の形が 1 つ増える |
| C. 取消・失効で終わりを記す | 「誤入力」という終わり理由を足す | 行の削除禁止を保つ | 帳簿に「誤入力の登録番号」が履歴として残る |

**Claude の推奨は B。** 写しが無い行は帳簿のどこにも出ていないので、消しても帳簿は変わらない（**設計上の事実**）。要件への当てはめ（優良な電子帳簿の訂正・削除の履歴に当たらないか）は **Claude の読み**で、確かめてほしい。

**関連**: [14 §4](14_適格請求書発行事業者の登録.md)・[14 の保留](14_適格請求書発行事業者の登録.md)（処理区分 99）。

## Q-21 明細の「取引先」を一覧に出して行ごとに選ばせるか——それとも伝票の取引先 1 つで固定し、相手が違えば伝票を分けるか

| | |
|---|---|
| **急ぎ** | 期限なし。ただし**フェーズ 4（期首残高）までには決める必要がある**（下の答え 2） |
| **決まらないと止まるもの** | 止まらない。ただし**相手方の違う行が同じ伝票にある**と、帳簿にその行の相手方でない名前が焼き付く（[15 §1-2](15_記帳の枠組み.md) の宿題 2。計上時の写しなので後から直せない——[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)） |
| **どこの話か** | 振替伝票の明細（`JournalLine`）。**「取引先」の欄と詳細レイアウトはある**が、明細の一覧（列は 行・貸借・勘定科目・補助科目・部門・金額・税区分・内容）に列が無く、伝票の画面から行の詳細へは遷移しない（`CanNavigateToDetail: false`）。**画面から選べるのは伝票の「取引先」だけ** |
| **既に決まっていること** | 1 枚の伝票には 1 つの取引を記す（開発者の決定。[ADR-0045](decisions/0045-振替伝票1枚には1つの取引だけを記す.md)——「取引」の単位は法税規則 55 ① の取引で、**相手方の数には触れていない**）。帳簿には明細の取引先が空なら伝票の取引先が載る（[10 §4-1](10_会計ドメイン設計.md)・[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)） |

**開発者の 3 つの問い**（2026-09-13）**に答える。** 調べた結果、**Claude の推奨を B から A へ改める**——
理由は答え 1 の ② と答え 2 の ③ で、**前の推奨が挙げていた唯一の反例が、一次情報に照らすと半分しか成り立っていなかった**。

### 答え 1. 行ごとに違う取引先にしたい場面は、どれほどあるか

**① 日々の入力では、ほとんど無い。**
`requires_partner` が立っているのは **6 科目**（売掛金・買掛金・売上高 3 本・外注費。`Designer/seed/004_accounts.sql`）で、
通常これらが同じ伝票に 2 行以上出るのは **売掛金↔売上高** と **買掛金↔外注費** の組だけ。**どちらも相手方は必ず同一**である。
起きうるのは**カード決済の経費**（未払金＝カード会社／費用＝加盟店）と**振込手数料の立替払**くらいで、どちらも頻度が低い。
**手形の裏書は起きない**（科目が初期データに無く、[ADR-0011](decisions/0011-手形貸付借入の補助簿を持たない.md) が電子交換所の廃止まで押さえている）。
**経費精算の一括計上も起きない**（別部品からの投入は個別取引の単位。[40 §3-3](40_優良な電子帳簿の対応表.md) の C2）。

**② 振込手数料の例は、3 通りのうち 1 通りでしか成り立たない**（**これが前の推奨の誤り**）。
インボイスQ&A（令和8年5月改訂）問 29 は「取引当事者間の契約関係等により、次のように対応が分けられます」として **3 本を並列に**挙げる
（`https://www.nta.go.jp/taxes/shiraberu/zeimokubetsu/shohi/keigenzeiritsu/pdf/qa/29.pdf`。確認日 2026-09-13）。

| ルート | 帳簿に載る相手方 | 伝票の取引先と |
|---|---|---|
| 1 売上値引 | **得意先** | **一致する** |
| 2 買手からの代金決済上の役務提供の対価 | **得意先** | **一致する** |
| 3 買手が金融機関へ立替払 | **金融機関** | **一致しない** |

**2 通りでは相手方は得意先**で、伝票の取引先と一致する。**国税庁はどれが望ましいとは書いていない**（問 29・30 を確認）。
問 30 は「**経理処理を支払手数料としつつ、消費税法上、売上げに係る対価の返還等とすることもできます**」と述べ、
「**支払手数料のコードを売上げに係る対価の返還等と分かるように別に用意する**」対応を例示している。

**③ しかし市販ソフトは、例外なく行ごとである**（[リサーチ](research/2026-09-13_市販会計ソフト比較_明細の取引先.md)）。
**位置まで確認できた 6 製品はすべて行ごと**（freee・MF・弥生 Next・PCA hyper・TKC、および補助科目で代替する弥生デスクトップ・PCA DX）。
**伝票ヘッダにだけ持つ製品は 1 つも確認できなかった。**
**freee は「貸方と借方に別々の取引先を入れたい場合」を振替伝票の利用用途として明記**しており、
**TKC は本プロジェクトの `requires_partner` とほぼ同じ仕組み**（科目ごとの取引先別元帳管理＋その科目では必須）**を明細行に置いている**。

### 答え 2. 伝票の取引先を 1 つに固定すると、実務上困るか

**① 今日の設定では、伝票は 1 枚も増えない**（答え 1 の ①）。ここまでは B 案で回る。

**② ただし「伝票を分ける」という対策は、貸借にまたがる場合には使えない。**
1 つの仕訳の借方と貸方に別の相手方が要るとき、**貸借一致の要請があるので伝票を分けられない**。

```
普通預金   99,340 / 売掛金 100,000   ← 相手方: 得意先
支払手数料    660 /                   ← 相手方: 金融機関（上のルート 3）
```

2 枚にするには**仮払金などの経由勘定**を挟むしかなく、帳簿に**実在しない残高の出入り**を作る。
**「分ける」が成り立つのは独立した複数の取引を 1 枚に書いた場合（まとめ書き）だけ**で、それは [ADR-0045](decisions/0045-振替伝票1枚には1つの取引だけを記す.md) が既に禁じている。
**つまり B 案の「分ける」は、ADR-0045 が既に消した問題にしか効かない。**

**③ フェーズ 4 の期首残高が気になる。ただしこれは未決に乗った見立てで、決め手にはできない**
（**自己レビューで降格した。2026-09-13**）。

- 売掛帳・買掛帳は**専用画面を作らず、総勘定元帳を取引先で絞ったものが兼ねる**（[03](03_機能スコープ.md)）。
  **それを取引先別の帳簿として成立させるには、期首残高も取引先ごとに要るのではないか**——というのが Claude の見立てである
- **しかし [15 §3](15_記帳の枠組み.md) は期首残高を「科目・補助科目・部門の単位で持つ」と書いており、取引先の軸は無い。**
  さらに [15 §1-2](15_記帳の枠組み.md) の宿題 1 は「**決算振替・繰越・期首残高には相手方が無い**」として、
  **免除の軸をフェーズ 4 に決める**と既に置いている——**これは A 案でも要る論点で、B 案固有の詰みではない**
- **「期首残高伝票は全体で貸借一致する 1 枚」という前提にも根拠が無い**（I-11 は「期首残高は貸借一致し、B/S 科目のみ」と
  集合について言っており、DDL の貸借一致は伝票単位である）

**重要度**——日常の入力は「仕事が回らないレベル」ではない（下の対策で回る）。
**③ は「フェーズ 4 で取引先別の期首残高を作ると決めたときに、B 案だと書けない」という条件つきの話**であり、
**その「決めたとき」がまだ来ていない。**

**対策と手数**（日常の入力の側）

| 対策 | 手数 | 裏づけ |
|---|---|---|
| **振込手数料を売上値引で処理する** | **伝票は増えない**（科目を売上値引・戻り高にするだけ） | 問 29 のルート 1。**1 万円未満は適格返還請求書の交付義務が免除される**（消税法 57 の 4 ③ ただし書・消税令 70 の 9 ③ 二。恒久措置であることは 2023-10-01 施行の版を e-Gov で機械検算。**制度の正典は [消費税リサーチ](research/2026-08-23_消費税インボイス制度.md)**） |
| 支払手数料の補助科目で相手を表す | 伝票は増えないが、**その科目の全明細で補助科目が必須になる**（[15 §1](15_記帳の枠組み.md) の 2 値） | 問 30 が「別のコードを用意する」対応を例示。消税基本通達 11-6-1 は相手方を記号・番号で表すことを無条件に許す |
| 明細の「内容」欄に支払先を書く | 伝票は増えない。**本プロジェクトが既に採っている型**（回収特例の住所を内容欄に書く運用） | [13 §1-4](13_取引先設計.md)・[11 §8](11_消費税設計.md)・[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md) |
| 経由勘定で 2 枚に分ける | **伝票 1 → 2 枚 ＋ 仮勘定の行 2 本。実在しない残高が出る** | — |

### 答え 3. A 案にするコスト

**結論——DB・ドメイン・写し・帳簿 SQL は 1 行も変えなくてよい。足りないのは画面の列 1 本である。**

**もうあるもの**（コードを開いて確かめた）

- **DB**: `journal_lines.partner_id`（FK・索引つき）・`partner_name_snapshot`・`registration_no_snapshot`。
  DDL のトリガも**既に `COALESCE(l.partner_id, NEW.partner_id)` の実効値で判定**している
- **ドメイン**: `JournalEntry.PartnerOf(line) => line.PartnerId ?? PartnerId` が実効値を 1 か所で持ち、関門も写しも同じものを見る
- **サーバ**: 目録の読み込みが**明細の取引先も既に拾っている**（`AccountingMasterLoader`）。複製・取消・訂正・読み書きとも行の取引先を往復させている
- **帳簿 SQL**: 表示・検索・空値検索が、すべて実効値で揃っている
- **デザイナ**: 明細の `Partner` フィールドと詳細レイアウトは**もうあり、定義は伝票側と完全に一致**している

**足すもの**

| # | どこ | 何を |
|---|---|---|
| 1 | `JournalLine.mod.json` の `ListLayouts[""].Elements` | **列を 1 本足す**（いまは 8 本） |
| 2 | 同 `DataOnlyFields` | `PartnerNameSnapshot` を入れる。**入れないと必ず空になる**（[qa/01 F-34](qa/01_CLB静かな失敗.md)。2026-09-03 に実際に踏んだ） |
| 3 | 同 `OnAfterInitialization` ＋ `JournalLine.mod.cs` | 計上済みの行で写しを見せる（[ADR-0037](decisions/0037-計上済みの伝票は画面でも計上時の姿を見せる.md) を明細にも当てる） |
| 4 | 伝票の凡例・関門の文言・`lint_design.py` の理由文 | 「画面から選べるのは伝票の取引先だけ」が嘘になるので直す（4 か所） |

**テスト**: 新規 8〜14 本 ＋ 既存の修正 2〜3 本。**文言を変えると `JournalSubmitGateTests` が既存のまま赤になる**（全文で固定しているため）。
**サーバ側テストのヘルパ `InsertLine` に `partnerId` 引数が無い**ので、そこも足す。
**実機**: 既存の台本 9 件を書き換え、新規 5〜8 件。**2〜3 周**（見た目 → 実効値と帳簿 → 写しの表示）。

**技術的な未知はほぼ無い**——「一覧の行の中で `DisplayText` を差し替えられるか」は、

**明細の一覧には条件つき必須の印を置けない**（実機で確かめて戻した記録がある。[`Designer/Project.md`](../Designer/Project.md)）ので、**伝票の凡例で言う**。

**B 案のコストも書いておく。** B は**実質的に現状維持**（凡例に 1 文）で最小である。

| 案 | 中身 | 評価 |
|---|---|---|
| **A（推奨）** | 明細の一覧に「取引先」の列を足し、行ごとに上書きできるようにする（伝票の取引先が既定） | **市販 6 製品と同じ形。コストは画面の列 1 本。フェーズ 4 の期首残高を解ける** |

| ~~C~~ | B ＋ 取引先を要する科目の行が 2 行以上あるとき警告 | **採らない。** 通常の売上（売掛金／売上高）も外注費（外注費／買掛金）も**ちょうど 2 行**なので、**ほぼ全部の伝票で鳴る** |

1. **B の「相手が違えば伝票を分ける」が、貸借にまたがる場合に成り立たない**（答え 2 の ②）。
   成り立つのはまとめ書きの場合だけで、それは ADR-0045 が既に消している。**これは論理の話で、未決に乗っていない**
2. **市販 6 製品が例外なく行ごとである**（答え 1 の ③）。**違う形を採るなら、6 製品が揃って採っていない理由が要る**

**期首残高（答え 2 の ③）は決め手に数えない**——フェーズ 4 の未決に乗っているうえ、
[15 §1-2](15_記帳の枠組み.md) の宿題 1 は逆（期首残高には相手方が無い）を示唆している。
**当初この 2 つ目に置いていたが、自己レビューで降格した**（2026-09-13）。

**B を採っても「誤った名前が焼き付く」は消えない**ことも申し添える——
写しは `requires_partner` を見ずに**全行**へ実効値を焼くので、B では伝票の取引先が全行に焼かれる。
**B が消すのは「利用者が直す手立て」であって、誤記そのものではない**（[15 §1-2](15_記帳の枠組み.md) は「空欄より誤記のほうが悪い」と書いている）。

**やってほしいこと。** A・B のどちらかを教えてほしい。**いつ**——期限なし。ただし**フェーズ 4 の着手前**までに。

## Q-25 検索欄に入れた末尾の空白を、どこで落とすか（いまはどこも落としていない）

| | |
|---|---|
| **急ぎ** | 期限なし。ただし**帳簿の検索は利用者が毎日触る導線**で、症状が「該当なし」としか出ない |
| **決まらないと止まるもの** | 止まらない。いまも検索はできる（末尾に空白を入れたときだけ 0 件になる） |
| **どこの話か** | 4 つのクエリモジュールの文字入力欄。いずれも `ShouldTrimAfterEdit: false` |
| **既に決まっていること** | **コードは保存時に前後の空白を落とす**（[ADR-0047](decisions/0047-マスタのコードは空白を落とす以外書き換えず字種で断る.md)）。**検索欄については決めていない** |

**状況。** 登録番号や摘要の検索欄に `T1234… ` と**末尾の空白**を入れると、
`LIKE '%T1234… %'` になって **0 件**になる。画面には「該当なし」としか出ないので、
**利用者は「無い」と判断する**（[qa/01](qa/01_CLB静かな失敗.md) の静かな失敗の形）。
**貼り付けで空白が付くのはよくある**。

| 案 | 何をするか | 利点 | 欠点 |
|---|---|---|---|
| **A（推奨）. 画面のフィールドで落とす** | 検索欄の `ShouldTrimAfterEdit` を `true` にする（4 モジュール分） | **入れた値が見た目でも直る**ので、利用者に何が起きたか分かる。SQL は触らない | デザイン JSON を 4 か所（変更点が散る） |
| B. SQL で落とす | `trim(@p_keyword)` を各条件に入れる | 1 ファイルずつで閉じる | **画面には空白が残る**ので、次に押したときの挙動が読めない。条件式が 1 段深くなる |
| C. 何もしない | いまのまま | 変更ゼロ | 症状が「該当なし」なので、**利用者は自分の入力を疑わない** |

**Claude の推奨は A**（**設計判断であって制度の話ではない**）。
**ただし「検索欄は全部そうする」という規則にするかどうかは開発者に決めてほしい**——
決めれば [21_画面の原則](21_画面の原則.md) に 1 行置いて、以後の画面に自動で効く。

**関連**: [qa/02 のラウンド 91](qa/02_自己レビュー記録.md)（この問いが出た回。**動かさないと決めた**）。
