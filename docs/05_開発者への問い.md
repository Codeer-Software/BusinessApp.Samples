# 開発者への問い

> **開発者の確認を要すること**を、判断に要る材料ごと 1 か所に置く文書。**2 種類ある**——
> **①答えが無いと先へ進まないもの** と **②Claude が自分で決めて実装し、後から諮るもの**（[34 §1-1](34_開発者とClaudeの分担.md)）。
> **運用の規則は [30 §11](30_作業のルール.md) が持つ**（誰がいつ書き、答えはどう伝わり、いつ消すか）。ここは問いの本体だけ。
> **急ぎの順に並べる**——期限のフェーズが近い順 → 同じ期限の中では「決まらないと止まるもの」がある問いを先 → 期限の無いもの。
> 番号 `Q-nn` は付けた順で、**使い回さない**（並びと番号は一致しない。消えた番号は欠番のまま）。
> 答えが出て ADR か設計文書に載ったら、その問いは消す（本文は git log が持つ）。
> **本書の推奨はすべて Claude の判断である。** 開発者の決定は、ここではなく ADR・設計文書に書く（[00 §4-11](00_ドキュメント規約/本文.md)）。
> 制度・法令に触れる箇所で「Claude の読み」と書いたものは、リサーチで裏を取っていない——**法令の当てはめは開発者が最も確かな確認先**（[CLAUDE.md §2](../CLAUDE.md)）。
> 行数の目安（[00 §5](00_ドキュメント規約/README.md)）は本書に当てない——長さは未決の数で決まる。

## Q-36 普通預金の「相手方」をどう持つか——補助科目で管理するのみの形を改めるか。あわせて「条文上は相手方が要る科目」の一覧の載せ先

| | |
|---|---|
| **急ぎ** | **フェーズ 4**（[ADR-0059](decisions/0059-期首残高と繰越と決算振替は仕訳として持ち閉鎖残高勘定は作らない.md) の入口条件 1——取引先を要する科目・補助科目の 2 値の免除を、期首残高・繰越に対してどう引くかを決める回。[15 §1-2](15_記帳の枠組み.md) の宿題 1）。**普通預金の行に取引先を要するかは、その免除の軸と一緒に決めないと 2 度直す** |
| **決まらないと止まるもの** | 止まらない。ただし**（六）で読むなら、普通預金の元帳が法税規則 別表二十四の「相手方」を満たすと言い切れない**まま、[40 §4-1](40_優良な電子帳簿の対応表.md) の 1 行目が「一部済」で残る。**一覧の載せ先が無いと、[15 §1-2](15_記帳の枠組み.md) の開発者の決定（2026-09-11。案 A——E1 ニ の雛形に一覧を載せて利用者に示す）の「示す」の側が果たせない**（雛形が消えても「示す」が残ると読むのは Claude——15 §1-2） |
| **どこの話か** | [40 §4-1](40_優良な電子帳簿の対応表.md) の 1 行目（普通預金）と表の直下の候補の表・[15 §1-2](15_記帳の枠組み.md)・[12 §2](12_マスタ台帳.md) の補助科目の行（「口座・契約・相手先が増えたとき」に足すマスタ）・`Designer/ddl/004_masters.sql` の `sub_accounts`・勘定科目マスタの「取引先を要する」の注記（`Account.mod.json`。[ADR-0062](decisions/0062-明細の取引先は行ごとに選べるようにし伝票の取引先は既定値にする.md) の帰結 4） |
| **既に決まっていること** | **普通預金は「その他の債権」に入り、照会は要らない**（開発者の決定。2026-09-16。旧 Q-18）。**記載事項は法税規則 別表二十四（二）に準じる**（[ADR-0042](decisions/0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の決定 6。2026-09-06。「預金の口座別に、取引の年月日、事由、支払先及び金額」。**この読みを保つか（六）で読むかが、本問の ①**）。**取引先は行ごとに選べ、伝票の取引先は既定値**（開発者の決定。[ADR-0062](decisions/0062-明細の取引先は行ごとに選べるようにし伝票の取引先は既定値にする.md)）。**初期データで「取引先を要する」を立てるのは 6 科目で、広げるのは利用者**（開発者の決定。2026-09-11。[15 §1-2](15_記帳の枠組み.md)）。**E1 ハ・ニ の書類はスコープ外**（開発者の決定。2026-09-16。旧 Q-19。[40 の E1](40_優良な電子帳簿の対応表.md)） |

**状況。** 旧 Q-18 の答えで開発者は「**『相手方』を補助科目で管理するのみという仕様はかなり気持ちが悪いです。
可能であればそれ以外の手法の検討をお願いします**」と述べた（2026-09-16）。

**いまの設計はこうである**（[40 §4-1](40_優良な電子帳簿の対応表.md) の 1 行目）——普通預金の行では、
**口座＝補助科目**（開発用 DB では `みずほ銀行 本店` のような補助科目で口座を区分する——[qa/04](qa/04_実機操作テスト.md) の BOK-11。口座別に補助科目を持つ運用に依存する）、
**事由＝摘要**、**支払先＝取引先**（明細か伝票の取引先の実効値。`JournalEntry.PartnerOf`）。
**「取引先を要する」は 6 科目にしか立てていない**ので、**普通預金の行は取引先が空のまま計上できる**。

**「相手方」の読みが 2 つあり、どちらを指しているかで直し先が変わる。**

| 読み | 相手方は誰か | いまの設計では |
|---|---|---|
| A. 法税規則 別表二十四（二）に準じる（[ADR-0042](decisions/0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の決定 6。2026-09-06） | **支払先**——入出金の相手（外注先・得意先・給与の受取人） | **取引先**（欄はあるが、普通預金の行には要していない） |
| B. 同（六）その他の債権として読む（**Claude の読み**——開発者の 2026-09-16 の「その他の債権に該当」は電帳規則 5 ① の対象帳簿の話で、記載事項をどの区分で読むかには触れていない） | **債権の相手方＝金融機関**（預け先） | **補助科目の名前だけ**。**`sub_accounts` に取引先への参照列は無い**（`Designer/ddl/004_masters.sql`——設計上の事実）ので、法人番号も名寄せも、取引先で引く検索（[40 の D1](40_優良な電子帳簿の対応表.md)）も届かない |

**Claude は、開発者の言葉は B を指していると読んだ**——A の支払先は補助科目では管理していないので、
「補助科目で管理するのみ」と言えるのは B の相手方だけである。**違っていたら教えてほしい。**
**B を採るなら [ADR-0042](decisions/0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の決定 6 の後半（（二）に準じる）を動かすことになる**——本問はそれを問う。

**手法の案**（Claude の検討。2026-09-17）。

| 案 | 何をするか | 利点 | 欠点 |
|---|---|---|---|
| **① 金融機関を取引先に登録し、口座の補助科目が取引先を参照する** | `sub_accounts` に任意の `partner_id` を足す（口座の補助科目だけが使う）。**明細も伝票も取引先が空なら、補助科目の取引先を実効値に採る**。帳簿には金融機関の名前が写る | **相手方が実体（取引先）になる**——法人番号・名寄せ・取引先で引く検索が効く。**入力は増えない**（口座を選べば相手方が決まる）。**A の支払先を伝票か明細に選んだときはそちらが写る**ので、（二）に準じる読みも壊れない | **支払先（A）と金融機関（B）が 1 つの取引先の欄を争う**——両方は写せない。金融機関が写るのは、支払先が無い行（利息・手数料・口座間振替）だけになる。**実効値の規則は 1 か所ではない**（2026-09-17 に開いて数えた）——C# は `JournalEntry.PartnerOf` の 1 か所だが、**DDL のトリガ**（`trg_journal_entries_partner_presence_when_posted`。`COALESCE` の式が 2 つ）、**帳簿と一覧の SQL 3 本**（`JournalEntryList`・`JournalBook`・`GeneralLedger`。**取引先の絞り込みは `COALESCE` を使わず `l.partner_id = @p OR (l.partner_id IS NULL AND e.partner_id = @p)` にほどいてある**——[qa/01 H-09](qa/01_CLB静かな失敗.md)。`COALESCE` のままなのは空値検索と一覧の「複数」の数え、表示列は `COALESCE(NULLIF(写し,''), lp.name, ep.name)`）、**取引先の「使用中」の判定**（`009_partner_meaning.sql`。実効値ではなく「明細か伝票のどちらかに載っていれば使用中」の 2 つの `EXISTS`）が、それぞれ別の形で同じ既定値の規則を持つ。**全部に補助科目の取引先を足し、SQL はほどいた形を保ったまま `sub_accounts` を JOIN する**（H-09 を踏み直さないため）。**スキーマ変更 1 本**（[ADR-0020](decisions/0020-スキーマは現在形の正典で持ち変更は差分で配る.md)）。**計上時の写し（[ADR-0060](decisions/0060-勘定科目・補助科目・部門の名前も計上時に写す.md)）に影響が無いかを確かめる** |
| ② 普通預金に「取引先を要する」を立て、金融機関を取引先として行ごとに選ぶ | 初期データの `requires_partner` を普通預金にも立て、利用者が普通預金の行の取引先に金融機関を選ぶ | スキーマ変更なし。**[ADR-0062](decisions/0062-明細の取引先は行ごとに選べるようにし伝票の取引先は既定値にする.md) の行ごとの取引先がそのまま使える** | **毎行、金融機関を選ぶ手間**（既定値の仕組みが無い）。**支払先（A）は普通預金の行には載らない**（相手の行に載る）。**期首残高・繰越の免除（[15 §1-2](15_記帳の枠組み.md) の宿題 1）が普通預金にも掛かる** |
| ③ いまのまま（A の読みで足りるとする） | 口座＝補助科目、支払先＝取引先。**普通預金に「取引先を要する」を立てるかは利用者に任せる** | 変更なし | **開発者が「気持ちが悪い」と述べた形そのもの**。B の読みでは相手方が実体で無い |

**Claude の推奨は ①。** 優先順位は「**明細の取引先 → 伝票の取引先 → 補助科目の取引先**」——
既定値の連なりを 1 段深くするもので、[ADR-0062](decisions/0062-明細の取引先は行ごとに選べるようにし伝票の取引先は既定値にする.md) の「伝票の取引先は既定値」を崩さない。
**これで A と B のどちらの読みでも列は埋まる。** ただし**「相手方は必ず金融機関」（B を厳格に読む）なら ② のほうが正しい**——
**どちらの読みを採るかは開発者に決めてほしい**（法令の当てはめは開発者が最も確かな確認先——[CLAUDE.md §2](../CLAUDE.md)）。
**① を採るなら、有価証券（法税規則 別表二十四（七）の相手方——[40 §4-1](40_優良な電子帳簿の対応表.md)）にも同じ形が使える**（銘柄の補助科目が証券会社を参照する）。

**一覧の載せ先。** 「条文上は相手方が要る科目」の一覧（候補は [40 §4-1](40_優良な電子帳簿の対応表.md) の表の直下）は
E1 ニ の雛形に載せると決めていた（開発者の決定。2026-09-11）が、雛形はスコープ外になった（旧 Q-19）。

| 案 | 中身 |
|---|---|
| **a. 勘定科目マスタの注記に 1 文で載せる**（推奨。**ただし「一覧を示す」の縮小である**） | `Account.mod.json` の「取引先を要する」の欄には注記が既にある（[ADR-0062](decisions/0062-明細の取引先は行ごとに選べるようにし伝票の取引先は既定値にする.md) の帰結 4）。**そこに「法税規則 別表二十四が相手方・支払先を求める区分（債権債務・収入・経費）に当たる科目には立てる」を 1 文で足す**（[21 §1](21_画面の原則.md) の「画面に書いていない規則は、凡例に 1 文で書く」）。**科目名の一覧は画面に書かない**——利用者の科目体系は初期データと違いうるから（Claude の判断）。**候補の表そのものは [40 §4-1](40_優良な電子帳簿の対応表.md) に残す** |
| b. 利用者向けの文書をリポジトリに置く | 操作説明書に近づく——**開発者がスコープ外と決めたもの**と線が引きにくい |
| c. 載せない | 開発者の 2026-09-11 の案 A のうち「一覧を利用者に示す」の側を、雛形と一緒に取り下げることになる |

**やってほしいこと。** ①相手方の読み（A か B か、両方か）②手法（①〜③のどれか、または別の形）③一覧の載せ先（a〜c）。
**いつ**——フェーズ 4 で [ADR-0059](decisions/0059-期首残高と繰越と決算振替は仕訳として持ち閉鎖残高勘定は作らない.md) の入口条件 1 を解く回まで。

## Q-45 フロントマターの `audience` は何のためのフィールドか——「読者」か「観点」か

| | |
|---|---|
| **急ぎ** | **期限は無い**（開発者が 2026-09-20 に「ちょっと今は保留にしましょう」と述べた） |
| **決まらないと止まるもの** | 止まらない。**ただし [00 §4-13](00_ドキュメント規約/本文.md)（他者に通じる表現を用いる）に反したまま**である——**このリポジトリの中でだけ意味を持つ 4 つの値が、定義なしに全文書へ付いている** |
| **どこの話か** | [00 §3-1](00_ドキュメント規約/フロントマター.md) の必須フィールドの表、全文書のフロントマター |
| **既に決まっていること** | **値は `開発` `運用` `営業` `テスト` から 1 つ以上**（[00 §3-1](00_ドキュメント規約/フロントマター.md)）。**それ以外は何も決まっていない**——意味も、誰が付けるかも、どう使うかも書かれていない |

**状況。** 2026-09-20 に §4-13 を書くとき、Claude が `audience` を「読者」と読み、
「`営業` を宣言した文書では開発の用語を前提にしない」という規則を建てた。
**開発者は「営業的観点が入った文章ではあるが、読者はあくまで開発者ではないか」と読み、規則は取り下げた。**
**フィールドに定義が無いので、どちらの読みも成り立つ。**
いま `開発` 以外を宣言しているのは 13 文書（`[開発, 営業]` が 7、`[開発, テスト]` が 7、`[開発, 営業, テスト]` が 1。重複あり）。

**問い。** ①`audience` は**誰が読むか**を表すのか、**どの観点を含むか**を表すのか。
②その意味で、いまの 13 文書の値は正しいか。③このフィールドは何の役に立っているか
（**読み手が `status` のように「読まなくてよい」を判断する材料になっているか**）。

**Claude の推奨。** **まず ③ から決めてほしい。** 役に立っていないなら、意味を決めるより外すほうが安い
（[00 §3-1](00_ドキュメント規約/フロントマター.md) の必須フィールドを 1 つ減らせる）。
役に立っているなら、**①の答えを §3-1 に 1 行ずつ書く**のがいちばん安い（値はそのまま使える）。
**名前を変える案（`audience` → `perspective`）は採らない**——全文書の書き換えと `lint_docs.py` の対応が要るわりに、得るものが名前だけである。
