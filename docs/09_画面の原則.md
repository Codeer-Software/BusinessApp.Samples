# 画面の原則

> **読み手は利用者である**——経理担当・経理責任者・経営者・顧問税理士（[02_ペルソナ](02_ペルソナ.md)）。
> 本書は**画面が満たすこと**と**なぜそうするか**だけを書く。
> **CLB での書き方**（JSON のキー・CSS クラス・幅の数値）は
> [`Designer/Project.md`](../Designer/Project.md) のレイアウト規約が持つ。
> 踏むと静かに壊れる挙動は [qa/01](qa/01_CLB静かな失敗.md)。

**この文書の育て方**

- **原則だけを置く。** CLB の書き方は Project.md、実際に踏んだ穴は qa/01 が持つ
- **「なぜ」の無い項目を足さない。** 理由が書いていない規則は、例外に出会った人が判断できない
- **厳選して書く。** 文書に残さなければ守られないもので、かつ、全体に適用すべきものだけを書く。
  **原則が増えるほど 1 件あたりの重みが下がるから**。
- 原則が覆るときは ADR を起こす。ここを黙って書き換えない
- **まだ実機で確かめていない項目は、「きっと利用者が使いやすいだろう」という想像である。**
  **最終的な判断は開発者が触って下す**（開発者の指示。2026-09-05）。触って使いにくければ外す。
  それでも書くのは、**想像を言葉にしておかないと、触ったときに何を確かめればよいか決まらない**から
- **ここに書いてあるのは「こうする」であって「こうなっている」ではない。**
  実装の現在地は [05 §2](05_実装計画と現在地.md)、これから直すものは [05 §3](05_実装計画と現在地.md) が持つ
  （実例: 2026-08-30 の朝まで、**検索条件は全モジュールが閉じたまま**だった——
  決めてから実装が追いつくまでに日が空く）

## 0. 勝手に直さない。直すなら知らせる

**アプリが入力を書き換えるなら、書き換えたことを利用者に伝える**（開発者の指示。2026-09-05。
**大事なのは会計ルールを守ることと、利用者を驚かせないこと**）。

- 黙って直すのがいちばん悪い。**実例**: CLB の `MaxFractionDigits: 0` は `1234.5` を
  **警告なしで `1234` に切り捨てる**（[qa/01 A-10](qa/01_CLB静かな失敗.md)）。
  貸借の両側で起きると合計は合ってしまうので、**1 円の欠落が誰の目にも触れない**
- **拒めるなら拒む**（押す前に見せる。§1）。拒まずに直すなら、**直した事実と直した後の値を見せる**
- 前後の空白を落とすような**利用者の意図でない混入の除去**は、黙って直してよい
  （[登録番号と法人番号が既にそうしている](07_取引先設計.md)——07 §3-2）。
  **境目は「利用者が入れたつもりのものを変えるか」**である

## 1. 制限は、押す前に見せる

**データ登録の規則・制限は、登録ボタンを押してエラーが出て初めて分かるのではなく、
可能な限り登録画面にあらかじめ示す**（開発者の指示。2026-08-29。
**差し戻しは利用者にとって作業のやり直しであり、防げるものは防ぐべきだから**）。

- **必須の欄は、入力前に必須と分かるようにする**（ラベルの赤い `*` と凡例。
  書き方は [Project.md](../Designer/Project.md)）。**色だけに頼らない**
- **選べないものを候補に出さない。** 無効にしたマスタは入力候補から外す
  （有効／無効の意味は [08_マスタ台帳](08_マスタ台帳.md)）。
  **ただし、その欄が何を選ばせる欄かを先に決めてから絞る**——**例外は各設計文書が持つ**
  （実例は [07 §2-5](07_取引先設計.md)）
- **書けない状態の画面は、書けないと見て分かるようにする。** 計上済みの伝票は閲覧専用にし、
  「押せるのに拒まれる」ボタンを残さない
- **読めない相手の候補欄を出さない。** その利用者が読めないデータ（[ADR-0033](decisions/0033-読み取りはそのアプリの役割を持つ人だけに開く.md)）を
  選ばせる欄は、**欄ごと消す**。候補が空の欄を残すのは「選べないものを候補に出さない」の裏返しで、
  利用者には「選ぶべきものが見つからない」としか見えない
- **形式・書式の制約はプレースホルダーを活用する**（桁数・書き出しの文字など）。
  **具体的な値はここに書かない**——正典は各設計文書である
  （登録番号と法人番号なら [07 §1-2・§3-2](07_取引先設計.md)）
- その他、登録時のルールで利用者に示すべきものは箇条書き等で示す（利用者にとって自明なものは不要。
  最もユーザビリティが向上する示し方と内容を都度検討する。）。

**ただし、すべてを先出しできるわけではない。** 貸借の一致・締め済み期間・二重取消のように
**保存の瞬間にしか判定できないもの**は関門で止める（§2）。
**先出しは関門の代わりではない。**関門は必ず置く——画面の先出しは経路が増えると外れる
（取込・API。関門の置き場は [ADR-0008](decisions/0008-CLBとCSharpライブラリの責務分担.md)、
実例は [07 §1-5](07_取引先設計.md)）。差し戻しの見せ方は §2。

## 2. 利用者に見せる文言（常に守る）

**画面・トースト・エラー・一覧の見出しと選択肢——利用者の目に入る文字はすべて対象である。**
差し戻しのときだけの話ではない。次の 5 つを常に守る。

**差し戻しはトースト 1 種類の見た目で見せる**（[ADR-0023](decisions/0023-利用者への差し戻しは1種類の見た目で見せる.md)）。
関門ごとに見た目を変えない。

### 2-1. 「です・ます」調に統一する

「〜できない。」ではなく「〜できません。」。
文書とコード内のコメントは「だ・である」調でよい（読み手が開発者と Claude だから）。

### 2-2. 内部表現を出さない

列挙子の英語名（`Reversal`）・クラス名・列名・違反コードを文言に混ぜない。
種別なら「取消」、状態なら「計上済み」と、**利用者の語で書く**。

### 2-3. 次にどうすればよいかを書く

「取り消せません」で終わらず、「取り消せるのは通常の伝票と訂正だけです」まで書く。

### 2-4. 改行を入れない

トースト内の文字列は改行できない（CLB の仕様。[qa/01 D-12](qa/01_CLB静かな失敗.md)）。
複数の項目は**件数と番号**で区切る——`計上できません（2 件）。①…②…`。

### 2-5. 日付は `yyyy/MM/dd` で書く

**部品が違っても揃える**（開発者の決定。2026-09-02。**CLB の日付欄はブラウザ標準の
`<input type="date">` で、日本語環境では `2026/09/02` と表示される**——
欄と文言で書式が違うと、同じ日付が別のものに見えるから）。時刻を添えるなら `yyyy/MM/dd HH:mm`。

**画面に置く日時のフィールドには、書式を明示して書く**（2026-09-02 に足した）。
CLB の `DateTimeFieldDesign` は `Format` が空だと既定が出て、**秒まで並ぶ**——
仕訳帳の「入力年月日」が `2026/08/24 18:56:09` になっていた（[qa/01 D-40](qa/01_CLB静かな失敗.md)）。
`lint_design.py` の **D-30** が、レイアウトに置いた日時の欄に `yyyy/MM/dd HH:mm` を要求する。
**日付だけの欄（`DateFieldDesign`）は書かなくてよい**——ブラウザ標準の `<input type="date">` で、
日本語環境では `yyyy/MM/dd` に見える。

**機械に渡す値はこの規則の外**である。SQL に渡す ISO の日付は
`ToString("yyyy-MM-dd", CultureInfo.InvariantCulture)` と**明示して**書く——
文字列補間（`$"{date:...}"`）は利用者に見せる文言の書き方として予約し、
`CSharpStyleTests` がそこだけを見張る（[ADR-0021](decisions/0021-CSharpは読みやすさを損なわない範囲で最新の記法に揃える.md)）。

## 3. 一覧と帳簿の見せ方

- **検索条件は既定で開く。** CLB の一般則は「閉じて一覧を多く見せる」
  （`ClaudeCodeForDesigner/Docs/LayoutGuidelines.md` の `IsExpanderDefaultOpened: false`）だが、
  **本プロジェクトは違う選択をする**（Claude の判断。**会計データは件数が多く、
  一覧を開いて最初にやることは絞り込みだと見込んでいるから**。既定で閉じているのは
  「絞らない」を既定にしていることになる）。**利用者の実際の使い方は計測していない**
**この節の「帳簿」は仕訳帳・総勘定元帳・補助元帳を指す。振替伝票の一覧は含まない**（最後の項目）。

- **帳簿は既定で絞らない。**「現在の会計年度で初期表示する」案は採らない
  （開発者の決定。2026-08-28。**「あるはずの仕訳が出ない」という誤解のほうが重いから**）。
  検索条件が既定で開いているので、絞りたければ年度の欄はすぐ見える
- **帳簿を並べ替えさせない**（**本プロジェクトの判断**）。
  **制度が定めるのは「記載」の順序であって、画面の並べ替えではない**——
  電帳法側に並び順の統一規定は無い（[電帳法リサーチ](research/2026-08-23_電子帳簿保存法.md) の一問一答 問 21・問 22）。
  それでも崩させない根拠は帳簿ごとに違う——**総勘定元帳・補助元帳**は
  [ADR-0022](decisions/0022-明細を並べる帳簿はクエリモジュールで作る.md)（累計がその並び順で積んだ値そのもの）、
  **仕訳帳**は**法人税法施行規則 55 ①**（**青色申告法人**が対象。「取引の**発生順に**」記載する）に
  画面の既定の並びを合わせてある。個人事業者は所得税法施行規則 58 ①・59 で条が別である
  （条文・施行日・確認日は[仕訳と伝票の用語のリサーチ](research/2026-08-25_仕訳と伝票の用語.md)）
- **入力のための一覧と、帳簿は別物である。** 前者は下書きを含み、後者は計上済みだけを出す
  （[ADR-0017](decisions/0017-仕訳と伝票の呼び分け.md)。作り方は
  [ADR-0027](decisions/0027-入力の一覧はラップモジュールとクエリモジュールで作る.md)）

## 4. 桁・揃え・色

- **金額列は右詰め・3 桁カンマ区切り・桁を揃える。** 桁をそろえて大小を比べるためである。
  フォーム入力欄は左詰めのまま、列見出しは左寄せのまま
- **数値でも識別子は左詰め**（科目コード・伝票番号・取引先コード）。識別子は先頭から読むものであり、
  大小を比べない
- **一覧の ○/— フラグ列は中央寄せ。** 記号は 1 文字で、左右に寄せると列見出しから離れて読みにくい
- **ボタンの色は 3 値だけ**（開発者の決定。2026-08-30。**前回プロジェクトの結論をそのまま引き継ぐ**——
  悩んだ末の選択なので、適切でない例が実際に出るまで尊重する）

  | | 使うところ |
  |---|---|
  | **Primary（青）** | **前進アクション**。保存・登録・確定・起票・生成・申請・承認・複製・出力・開く |
  | **Danger（赤）** | **元に戻しにくい／巻き戻す操作**。削除・却下・取消・状態の巻き戻し |
  | **Secondary（灰）** | **ダイアログのキャンセル・閉じるだけ。業務アクションには使わない**（**いまは書ける場所が無い**——`MessageBox` はラベル文字列しか受け取らない。[qa/01](qa/01_CLB静かな失敗.md)） |

  - **この 3 値以外は使わない**（CLB の `ButtonVariant` には `Outline*` や `Text` もあるが、使わない）
  - **操作の重要度や主・副を色で表さない。** 1 画面に青が複数並ぶことは許す
  - **押せないボタンを灰色にしない。** 無効なボタンは **(a) 非表示にして理由をラベルで示す**か、
    **(b) アクション色のまま半透明にする**（書き方は [Project.md](../Designer/Project.md)）
  - **「訂正する」は赤**（開発者の決定。2026-08-30）。誤りを直す前進にも読めるが、
    **押すと取消を 1 本計上する**ので、上の表の赤（例示に「取消」がある）に当たる。
    **「両方に読める操作は赤」という一般則は置かない。** 決めたのはこの 1 件だけで、
    次に迷う操作が出たときは、**その操作が実際にすることを表に当てて**決める

  **なぜ 3 値か・なぜ灰と黄を使わないかは
  [ADR-0030](decisions/0030-ボタンの色は3値に限る.md)**（前回プロジェクトの実態調査と UX テストの結果）

## 5. 用語

- **用語は [ADR-0017](decisions/0017-仕訳と伝票の呼び分け.md) に従う。**
  入力の単位は「振替伝票」、帳簿は「仕訳帳」
- **画面で「仕訳」と単独で書かない**（伝票 1 件か明細 1 行かが読み手に決まらない）
- **原則は法令用語等を用いるが、利用者が迷うと思われる場面では適切に補う。**
  例:「登録番号」は法令用語だが（[07 §3-4](07_取引先設計.md) が出典を持つ）、
  何ら文脈がない場所では何を指しているか分かりにくいため、
  サイドメニューなどでは「登録番号（インボイス）」と情報を補う。
  ただし、取引先登録画面では「登録番号」と裸で使う。取引先登録という文脈があり、利用者は理解できると考えられるため。
  都度判断となり、最終判断は開発者に従うが、Claudeも「利用者から見た理解しやすさ」を常に意識し設計・実装する。

## 6. 機械で守っている範囲

**ここに書いてあることは、ほとんど人が見るしかない。**

**何が機械で守られているかの一覧は、ここに書かない**（検査を足すたびに書き直すことになり、必ず腐る）。
**正典は検査のコードそのもの**である——`tools/clb/lint_design.py`（見ているものの一覧は
[qa/01](qa/01_CLB静かな失敗.md)）と、`dotnet test` の規約テスト。
**「これから足すもの」の一覧はもう無い**（フェーズ 2.5 の D で一巡した。2026-09-02）。
**気づいた時点で検査に足す。** 足さないと決めたものは、理由を[qa/02](qa/02_自己レビュー記録.md) に残す。

**守られている範囲は、思っているより狭い。** 実例——文言の検査は
**C# の文言リテラルの改行コード**を見ているだけで、
**トーストの文言を組み立てる CLB の `*.mod.cs` は 1 行も見ていない**。
「機械が見ているはず」を前提に §1〜§5 を省かない。

関門を足したときは**一度わざと壊して鳴ることを確かめる**
（[ADR-0021 §4](decisions/0021-CSharpは読みやすさを損なわない範囲で最新の記法に揃える.md)）。
