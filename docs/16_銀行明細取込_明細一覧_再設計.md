> 対象: 【会計】銀行 > 明細取込（BankImport）・明細一覧（BankStatementLine）と、その関係先（仕訳ルール MatchingRule・残高照合 BankReconciliation・仕訳 JournalEntry）。

## 1. 現状の問題

### 1.1 データと画面の全体像（前提）

- 明細は 1 テーブル `bank_statement_lines` に集約され、`status` 列で区別される:
  `preview`（プレビュー）→ `pending`（未起票）→ `journalized`（起票済）／`excluded`（対象外）
- 「明細取込」画面は表示専用モジュール（BankImport）で、同テーブルを status で絞った 2 つのリスト（プレビュー / 未起票）を持つ。
- **ユーザーの理解どおり、プレビューリストは「DB に status='preview' で登録済みのレコード」の表示**である（取込ボタンの時点で DB に INSERT されている。重複キーで再取込を防ぐための設計）。

### 1.2 不具合（実測＋コード根拠）

| # | 症状 | 根本原因 |
|---|---|---|
| B-1 | プレビュー/未起票リストの行削除が保存されない（保存を押すと復活） | 行削除はメモリ上の行リストから消えるだけ。保存処理 `SaveListEdits()` は「いまメモリにある行」を1行ずつ Submit する方式なので、**消えた行を DELETE する者がいない**。リロードで DB から復活する |
| B-2 | プレビューで削除・編集しても「この内容で登録」に反映されない（削除した行が登録され、編集前の値で登録される） | `ConfirmImport_OnClick` は**画面のリストを見ずに DB を直接検索**（status='preview' 全行）して pending に遷移させる。メモリ上の編集・削除は完全に無視される |
| B-3 | プレビューリストの編集を保存する手段がそもそも無い | `SaveListEdits()` は未起票リスト（PendingLines）だけを対象にしており、**プレビューリスト（PreviewLines）用の保存経路が存在しない** |
| B-4 | 「AIで相手科目を推定」を押すと保存ボタンなしで DB が更新される | 推定結果を行に代入して**その場で `Submit()`** している。ユーザーが確認・修正してから確定する導線（「AI は下書き、確定は人間」）と矛盾 |
| B-5 | 状態セレクトが自由編集できる | 一覧の「状態」列が編集可能なドロップダウン（候補は preview/pending/journalized/excluded の全4値）。**手で「起票済」にすると仕訳が無いのに起票済になる**など、状態機械を UI から破壊できる。ADR-0026「状態遷移はボタンに一元化・状態フィールドは表示専用」の全アプリ規約に、この画面だけ違反している |
| B-6 | 明細の原本列まで編集できる | 一覧レイアウトで**日付・摘要・出金・入金・残高も編集可能**。明細は銀行データの写し（原本）であり、書き換えると残高照合の意味が崩壊する |
| B-7 | 「対象外」にすると行き止まり | 対象外にした行は取込画面の未起票リスト（status='pending' 絞り）から消える。明細一覧には出るが、**明細一覧は削除ボタンしか無い**（CanUpdate: false / 詳細画面なし）。誤って対象外にした明細を未起票に戻す正規の手段が無い |
| B-8 | 明細一覧の物理削除が無条件 | **起票済の明細も削除できる**。削除しても生成済み仕訳は残るため、①明細→仕訳のトレーサビリティが切れる ②残高照合が「帳簿にはあるが明細に無い」状態になり差異が出る ③重複キーが解放され同じ明細を再取込→再起票（二重仕訳）できてしまう |
| B-9 | ボタンの配置が操作対象と対応していない | 「この内容で登録」等が CSV 欄の下にまとまっており、どのリストに効くボタンか読み取れない（ユーザー指摘） |

一言でまとめると、**「リスト上の編集・削除（メモリ）と DB の同期規律が設計されておらず、状態遷移と原本保護のガードも無い」**。個別修正ではなく保存セマンティクスから決め直す。

## 2. あるべき仕様

### 2.1 設計原則（3つ）

1. **保存は明示・一括**: リスト上の編集・削除・対象外化はすべてメモリ上の変化とし、**保存系ボタンを押した瞬間にまとめて DB に反映**する。行削除の即時 DB 反映はしない（ユーザー決定 2026-07-21）。
2. **状態遷移はボタンだけが行う**（ADR-0026 準拠）: 状態列は表示専用。ユーザーが起こせる遷移は「未起票 ⇄ 対象外」のみ。preview→pending（登録）と pending→journalized（起票）はシステムの遷移。
3. **明細は原本**: 日付・摘要・金額・残高・口座・重複キーは取込後は読み取り専用。ユーザーが編集できるのは**相手科目（候補）だけ**。

### 2.2 状態機械（唯一の正）

```
（CSV取込）──→ preview ──「この内容で登録」──→ pending ──「候補科目で一括起票」──→ journalized
                  │                              │  ↑
                  │「全てのプレビューを取り消す」    │  │「未起票に戻す」（明細一覧の詳細から）
                  │ または行削除＋保存             ↓  │
                  └──→ （物理削除・キー解放）      excluded
                                                 pending の行削除＋保存 → 物理削除・キー解放
```

| 遷移 | 誰が | どこで | 備考 |
|---|---|---|---|
| → preview | システム | 取込ボタン | 重複キーで既存スキップ |
| preview → pending | システム | 「この内容で登録」 | 暗黙保存を含む（§2.4） |
| preview → 削除 | ユーザー | 行削除＋保存 / 全て取り消す | 重複キー解放＝貼り直し可 |
| pending → excluded | ユーザー | 行の「対象外」チェック＋保存 | 唯一の日常的な状態操作 |
| excluded → pending | ユーザー | 明細一覧の詳細画面「未起票に戻す」 | 誤操作の差し戻し（B-7 解消） |
| pending → journalized | システム | 「候補科目で一括起票」 | 仕訳リンク付与 |
| pending → 削除 | ユーザー | 明細一覧の詳細画面「削除」 | キー解放。取込ミスの後始末用 |
| journalized → （不変） | — | — | 削除・編集とも不可。訂正は仕訳側の赤黒で行い、明細はそのまま残す（照合の証跡） |

- 「状態」列はどの画面でも**表示専用**にする（B-5 解消）。
- excluded の削除は許可（対象外＝帳簿対象外の記録なので消す意味は薄いが、ゴミ掃除は妨げない）。ただし残高照合は「明細が存在する日」を突合するため、**対象外行も残高照合の材料である**ことを削除確認ダイアログで注意喚起する。

### 2.3 画面構成とボタン配置（ユーザー案を採用）

```
【明細取込】
  口座選択 ／ 明細CSV貼り付け欄
    └─ [明細を取り込む]
  ── プレビュー（未登録）リスト ──────────────
  編集可: 相手科目（候補）　行削除: ○（保存で確定）
    └─ [プレビューの変更を保存] [この内容で登録] [全てのプレビューを取り消す]
  ── 未起票の明細リスト ─────────────────
  編集可: 相手科目（候補）・「対象外」チェック　行削除: ×（削除は明細一覧の詳細から）
    └─ [未起票明細の変更を保存] [AIで相手科目を推定] [候補科目で一括起票]
```

- 未起票リストの行削除ボタンは**廃止**する。理由: 「削除」と「対象外」の使い分けが紛らわしく、登録済み明細の削除は例外操作（取込ミス）なので、例外操作は明細一覧の詳細画面（§2.6）に寄せる。プレビューは未登録の作業中データなので行削除を残す。
  - ※未起票でも行削除を残したい場合は実装可能（プレビューと同じ差分同期で消える）。採否はレビューで決める。→ **Q2**
- 「対象外」チェック列（BooleanField）を未起票リストに追加し、チェック＋保存で excluded へ遷移する（状態セレクト直編集の代替。ADR-0026 の「遷移はボタン/明示操作」に整合）。

### 2.4 保存セマンティクス（各ボタンの DB への作用）

原則: **DB を書くのは「保存」「登録」「起票」「取り消す」の4系統だけ**。参照・推定系はメモリのみ。

| ボタン | メモリ→DB 同期 | 内容 |
|---|---|---|
| 明細を取り込む | INSERT のみ | 新規行を preview で作成（既存の編集には触れない）。**未保存のプレビュー変更がある場合は警告**（§2.7） |
| プレビューの変更を保存 | 差分同期 | プレビューリストの編集反映＋削除行の DELETE |
| この内容で登録 | 差分同期＋遷移 | **暗黙に「変更を保存」を実行してから** preview→pending。画面で消した行・直した科目がそのまま登録される（B-2 解消） |
| 全てのプレビューを取り消す | DELETE | preview 全行を物理削除（キー解放）。確認ダイアログ付き |
| 未起票明細の変更を保存 | 差分同期＋遷移 | 科目修正の反映＋「対象外」チェック行を excluded へ |
| AIで相手科目を推定 | **なし** | 候補未設定の未起票行（メモリ上の現在値で判定）に推定値をメモリ代入するだけ。保存するまで DB は変わらない（B-4 解消）。破棄したければ保存せずリロード |
| 候補科目で一括起票 | 暗黙保存＋遷移 | **暗黙に「変更を保存」を実行してから**、候補設定済みの pending を起票。画面と DB の食い違い起票を防ぐ |

### 2.5 差分同期の実装方式（B-1 の恒久対策）

「削除ボタンを押したらリストから消え、保存で初めて DB に反映」は次の方式で実現する（実現可能・既存知見の組み合わせ）:

1. リストをリロードするたびに、**ロード済み行の ID 集合をスクリプト変数に記録**する（スナップショット）。
2. 保存時に「スナップショットにあるが、いまメモリに無い ID」= ユーザーが削除した行 → 1行ずつ `Delete()`（明細は子なしモジュールなので物理削除が確実に効く。Project.md 2026-07-19 知見）。
3. メモリに残っている行は 1 行ずつ `Submit()`（未変更行は送信データなしで無害）。
4. 同期後にリロードし、スナップショットを取り直す。

- **DB 全行との突き合わせにしない**ことが重要（リストに LimitCount があるため、「DB にあるが画面に無い＝削除」と誤判定して**表示されていないページの行を消す**事故になる）。スナップショット方式なら「一度画面に出た行」しか削除対象にならない。
- 補助ガードとして、リストの LimitCount は現行 200 → **null（全件）**にする。月次の明細件数（数十〜数百）なら実用上問題なく、「201件目が画面に出ず起票されない」系の取りこぼしも同時に消える。

### 2.6 明細一覧（BankStatementLine）の再設計

役割を「**全状態の監査ビュー＋例外操作の入口**」と定義し直す:

- 一覧: 全列**表示専用**。検索（口座・状態・日付）は現行維持。**一覧の削除ボタンは廃止**（B-8 解消）。
- **詳細画面を新設**（現行 DetailLayouts は空）: 行クリックで遷移し、状態に応じたボタンを出す（ADR-0026 パターン）:
  - pending: 「対象外にする」（赤）／「この明細を削除」（赤・確認ダイアログ＋キー解放の注意書き）
  - excluded: 「未起票に戻す」（青）／「この明細を削除」（赤）
  - journalized: 操作ボタンなし。仕訳番号を表示し「訂正は仕訳側で赤黒訂正」の案内ラベル
  - preview: 「取込画面で作業中の明細です」の案内のみ（操作は取込画面で）
- 相手科目（候補）の編集は**詳細画面では不可**とする（候補をいじる作業は取込画面の未起票リストに一本化。二箇所で編集できると保存規律が再び曖昧になる）。→ 異論あれば **Q3**

### 2.7 細部仕様

- **未保存変更の警告**: 未保存の編集・削除がある状態で「明細を取り込む」「AIで相手科目を推定」以外の画面遷移をしたら変更は破棄される（CLB のリスト再読込の標準動作）。少なくとも「明細を取り込む」実行時はプレビューの未保存変更を検知して確認ダイアログを出す（変更検知が CLB API で困難な場合は、取込時に必ず暗黙保存する案に倒す。実装時に実測して決める）。
- **プレビュー放置警告**（他担当者の作業中プレビューの検知）: 現行仕様を維持。
- **AI推定・ルールの対象判定**: 「候補が未設定」はメモリ上の現在値で判定（保存前の手入力を上書きしない）。
- **推定元（rule/ai）表示**: 現行維持。手修正したら推定元を「手入力」に変える（新値 manual を候補に追加）。
- **重複キー**: 現行方式を維持（日付|摘要|出金|入金|連番）。削除＝キー解放＝再取込可能、を各削除ダイアログに明記する。
- **権限**: 現行どおり経理・sysadmin のみ（UserWriteCondition 設定済み）。
- **残高照合・明細一覧の CSV ダウンロード・冪等スキップ**: 仕様変更なし（B-8 の削除制限により、照合の穴と二重起票経路がむしろ塞がる）。

## 4. 未決事項（レビューで決めたい点）

- **Q1**: 原本列（日付・摘要・金額・残高）の読み取り専用化に異論はないか。「銀行CSVの文字化け・変な摘要を直したい」ニーズがあるなら、プレビュー段階（登録前）のみ編集可にする折衷案もある。
- **Q2**: 未起票リストの行削除ボタンは廃止（削除は明細一覧の詳細に集約）でよいか。それとも未起票でも行削除＋保存を許すか。
- **Q3**: 相手科目（候補）の編集場所は取込画面に一本化（明細一覧の詳細では編集不可）でよいか。
- **Q4**: 「全てのプレビューを取り消す」の名称（現行は「プレビューを取り消す」）。全件消えることが名前から分かるユーザー案を採用予定。
