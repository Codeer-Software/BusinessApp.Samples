# Claude Code の自動モードの分類器と、許可の規則の効き方

## 調査の目的

**実機操作テストの手順が `sql` CLI（`tools/clb/sql.ps1`）で開発機の DB に書く呼び出しが、ときどき拒まれる。**
拒んでいるのは Claude Code の**自動モード**（道具の呼び出しを、人の代わりに分類器という別のモデルが判じ、危ないと見たものを拒む権限モード）である。
開発者が 2026-09-24 に「私のほうで何か設定することでこれを許可させられるなら言ってください」と尋ねたので、**何を設定すれば何が変わるか**を公式文書で確かめた。
**この調べを使った問いは旧 Q-63**（2026-09-25 に開発者が答えて閉じた。自動モードの答えは下の「開発者に示した手と、開発者が入れた設定」、別のタブへの切り替えの答えは [qa/04 §3](../qa/04_実機操作テスト.md) の前書き）。

## 何を見たか

- **Claude Code の公式文書 2 本**（確認日 2026-09-24。**Claude が WebFetch で全文を取って読んだ**）
  - **「権限モードの文書」** = [Choose a permission mode](https://code.claude.com/docs/en/permission-modes)——とくに「How the classifier evaluates actions」「When auto mode falls back」
  - **「自動モードの設定の文書」** = [Configure auto mode](https://code.claude.com/docs/en/auto-mode-config)——とくに「Where the classifier reads configuration」「Route all shell commands through the classifier」
- **このリポジトリの設定**——`.claude/settings.json`（追跡している）の `permissions.allow` を、Claude がスクリプトで数えた（2026-09-24）
- **実機操作テストの記録**（[2026-09](../qa/04_実機操作テスト/2026-09.md)）に残っている、拒まれた呼び出しの一覧
- **このマシンの Claude Code の版は 2.1.281**（`claude --version`。2026-09-24）——下で版の条件が付く事実は、どれもこの版で当たる

**見ていないもの**: 分類器の既定の規則の全文（**2026-09-25 に `claude auto-mode defaults` を流し、各欄の本数を数え、`soft_deny` のうち「Modify Shared Resources」の文だけを読んだ**——`allow` 17・`soft_deny` 70・`hard_deny` 1・`environment` 21。**`soft_deny` の「Modify Shared Resources」の文は `database records` を名指している**。全文はリポジトリに写していない）・分類器が個々の呼び出しをどう判じたか（判定の中身は外から見えない）。

## 確かめた事実（公式文書）

**許可の規則と分類器の順序**（権限モードの文書の「How the classifier evaluates actions」）:

- 許可・確認・拒否の規則（`permissions.allow`・`ask`・`deny`）に当たる呼び出しは、分類器より先にその場で決まる。例外は、保護されたパス（Claude Code 自身が守るパス。本リポジトリの `tools/claude/protected_paths.json` とは別）への書き込み・`requiresUserInteraction` の MCP の道具・1 回ごとに許可するドメインを伴うシェルのコマンドなど
- **自動モードに入ると、任意のコードを実行できる広い許可の規則は外れる。** 文書が挙げる例は「Blanket `Bash(*)` or `PowerShell(*)`」「Wildcarded interpreters like `Bash(python*)`」「Package-manager run commands」「`Agent` allow rules」「`Monitor` allow rules」。**「Narrow rules like `Bash(npm test)` stay in effect」**。自動モードを出ると外した規則は戻る
- 分類器が拒むと、Claude は理由を受け取って別の手を探す。理由は多くの場合、当たった規則の名前（例 `[Data Exfiltration]`）である

**拒まれたあと**（権限モードの文書の「When auto mode falls back」）:

- 拒まれた呼び出しは `/permissions` の「Recently denied」に載り、**`r` で手動の承認つきで打ち直せる**（対話のセッション）
- **分類器が 3 回続けて拒むか、セッションで合計 20 回拒むと、自動モードは止まり、承認を求める形に戻る**（回数は変えられない。**許可された呼び出しが 1 つ挟まると、続けての数は 0 に戻る**）
- 文書は、拒否が続くのは多くの場合「classifier is missing context about your infrastructure」だと書く

**分類器の設定 `autoMode` をどこから読むか**（自動モードの設定の文書の「Where the classifier reads configuration」）:

- **分類器は、Claude が読むのと同じ CLAUDE.md を読む**——文書の字は「an instruction like "never force push" in your project's CLAUDE.md steers both Claude and the classifier」
- **`autoMode` の欄（`environment`・`allow`・`soft_deny`・`hard_deny`。中身は自然文）を読むのは 3 か所だけ**——開発者のホームの `~/.claude/settings.json`・組織の管理設定・起動時の `--settings` の指定（と Agent SDK）
- **リポジトリの中の設定ファイル**（`.claude/settings.json` と、追跡しないマシン固有の設定ファイル）**に書いた `autoMode` は読まない**。理由は文書の字で「a checked-in repo or a build step could otherwise inject its own allow rules」。**追跡しないほうのファイルを読まなくなったのは v2.1.207 から**
- `autoMode.allow` に書いた文は、分類器の中で「soft_deny」の規則への例外として働く。**`"$defaults"` を入れずに書くと、その欄の既定の規則が全部消える**（文書の警告）
- `/permissions` の「Auto mode」タブから足せる（v2.1.246 から）。保存先は `~/.claude/settings.json`

**狭い許可の規則の危うさ**（自動モードの設定の文書の「Route all shell commands through the classifier」）——「a narrow rule can still let a destructive argument through without the classifier seeing it, for example a script path or flag the rule's prefix didn't anticipate」。
**`autoMode.classifyAllShell` を `true` にすると、シェルの許可の規則を全部止め、どのコマンドも分類器に掛ける。**

**サブエージェント**（権限モードの文書の「How auto mode handles subagents」）——サブエージェントの各呼び出しも、親と同じ規則で分類器に掛かる。

## このリポジトリの設定（2026-09-24 に数えた）

- `.claude/settings.json` の `permissions.allow` には **`Bash(pwsh:*)` がある**。**`PowerShell(pwsh …)` の形の許可は無い**（`PowerShell(Get-ChildItem:*)` などコマンドレットの許可はある）
- `sql.ps1` を名指した許可の規則は無い

## 記録に残っている、拒まれた呼び出し（事実）

**[記録](../qa/04_実機操作テスト/2026-09.md) の 2026-09-21 と 2026-09-24 の節から。**

- **2026-09-21**: `[Console]::OutputEncoding = …; pwsh …` と前置きを繋いだ `sql` CLI の書き込みが拒まれ続け、**3 回続けて止まったあと、その担当の呼び出しが全部承認待ちになった**（上の「3 回続けて」の動き）。**打ち方を Bash の道具の `pwsh` 単独に変えると、5 本とも通った**
- **2026-09-24**: Claude（主のセッション）が Bash の道具で打った `UPDATE`（MST-13 の DDL の側）と `DELETE`（CNC-02）が「Irreversible Local Destruction」で拒まれた。**同じ日の全件の回では、サブエージェントが打った手順の書き込み 20 本あまりが 1 本も拒まれなかった**。PRM-14 の `UPDATE app_users …` は **PowerShell の道具**で打って「Modify Shared Resources」で拒まれた
- **2026-09-24**: **読み取りの `SELECT` とブラウザの操作（`navigate` を含む）も拒まれた回がある**（「Modify Shared Resources」、理由の書かれない拒否）。書き方を変えて打ち直すと通った

## Claude の読み（確かめていない）

- **`Bash(pwsh:*)` は、文書の「Wildcarded interpreters」に当たると読む**——`pwsh` は PowerShell の実行系で、後ろに何でも書ける。**当たっているなら、自動モードでは `pwsh …` の呼び出しは毎回分類器に判じられていた**ことになり、**通ったり拒まれたりしたのは分類器の判定の揺れ**である
- **2026-09-21 の記録の読み**（「前置きを繋いだので `Bash(pwsh:*)` の前方一致が外れた」）**とは両立しない**——上の読みが当たっているなら、前置きを外して通ったのも分類器の判定だったことになる。**どちらが当たっているかは確かめていない**（当時の版は記録に無い）
- **PowerShell の道具には、自動モードかどうかに関わらず `pwsh` を許す規則が 1 本も無い**——PRM-14 が拒まれたのは、道具の違いが効いた可能性もある
- **`Bash(pwsh -NoProfile -File tools/clb/sql.ps1:*)` のような規則が「狭い」側に数えられるか**は、文書の例（`Bash(npm test)`）からの類推である。**`-Query` に何でも書けるので、分類器から見れば中身の見えない書き込みの口になる**
- **2026-09-25 の承認待ちは、上の「3 回続けて拒むと承認を求める形に戻る」に当たったと読む**——ただし**記録にある拒否は 2 回**で、3 本目は拒否ではなく承認待ちになった。3 本目の判定が 3 回目に数えられたのか、セッションの合計 20 回に当たったのかは分からない
- **開発者が入れた ② が効いたかは確かめていない**——同じ日に打ち方も変えた（[qa/04 §2-0](../qa/04_実機操作テスト.md)）うえ、拒否はもともと揺れる。書き込みで確かめられるのは、次に手順どおりの書き込みを打つ回

## 確認できなかったこと

- **分類器が何を見て拒んだか**（同じ種類の書き込みが、呼び出しごとに通ったり拒まれたりした理由）——判定の中身は外から見えない
- **2026-09-21 の Claude Code の版と、そのときのモード**——記録に無い

## 開発者に示した手と、開発者が入れた設定（2026-09-25）

**旧 Q-63 で開発者に示した手**（2026-09-24。Claude がまとめた）——
①`.claude/settings.json` の `permissions.allow` に `sql.ps1` を名指した規則を足す（狭い規則に数えられれば分類器を通らない。**`-Query` の中身を分類器が見なくなり、DDL の印を置く呼び出しや `PRAGMA writable_schema` のような裏口の SQL まで分類器の外に出る**。[34 §1-4](../34_開発者とClaudeの分担.md) の操作制限を緩める決定）
②`~/.claude/settings.json` の `autoMode.allow` に、開発用の DB であることを述べる文を足す（分類器は外さず、その文を判断の材料にする。自然文なので必ず通るとは限らない。`"$defaults"` を必ず入れる。34 §1-4 の操作制限の定義の外の設定だが、書くのは開発者）
③CLAUDE.md に `sql.ps1` の用途を 1 文書く（分類器も CLAUDE.md を読む。CLAUDE.md は開発者が書く文書）
④何もしない

**Claude が ② を推した理由**——分類器を外さずに、公式文書が拒否の続く原因として挙げる「環境の文脈の欠け」を補う形だから。**② で拒否が残るなら ① を検討する**（Claude の判断）。

**開発者の決定（2026-09-25）——② を選び、自分で入れた**。逐語は「あなたの提案どおりの値を `~/.claude/settings.json` に書き込んで保存しました。（つまり②を実行しました。）これで駄目だったらまた対策を考えましょう。」
**入った文**は、`"$defaults"` に続けて、開発機のローカル SQLite（データソース `BusinessAppSQLite`）への `sql.ps1` の `SELECT`・`UPDATE`・`DELETE` を許し、開発用の DB で `db_snapshot.ps1` で退避できることを述べる文である（Claude が会話で出した案のとおり。**旧 Q-63 の例文より広い**——読み取りが拒まれたので `SELECT` を足し、退避の道具を名指した）。**文の中身は、2026-09-25 に自己レビューの担当がファイルを読んで確かめた**。**`INSERT` は文に入っていない**——手順には `INSERT` を打つ項目がある（MST-21・JNL-23・AMD-12）。

**同じ日の観測**（事実。[記録](../qa/04_実機操作テスト/2026-09.md) の 2026-09-25）——
- **入れる前**: 読み取りの `SELECT` が 2 回続けて「Modify Shared Resources」で拒まれ、並列で出ていた 3 本目が承認待ちで約 7 分止まった。直前に手順どおりの `UPDATE` が 2 本打たれていた
- **入れたあと**: Claude が流し直した MST-26 で、前に拒まれた部門名の `type` が通った。同じ日の別のタブの試し（35 分）では、拒まれた呼び出しは 0 だった。**そのときの `sql` CLI は読み取り（単独・直列）だけで、書き込みはまだ打っていない**
