> **切り出せるのは、登録が取引先そのものとは別の実体だから**である——**有効期間つきの別テーブル**で持ち、

## 1. 有効期間つきの別テーブルで持つ

登録は**取消・失効・再登録**があり、1 列では「その時点でどうだったか」を表せない。
`partners` に列を足さず、`partner_invoice_registrations` を作る。

**弥生会計の本体は登録番号の入力欄そのものを持たず、摘要か仕訳メモに書くよう案内している**
（[調査](research/2026-08-28_市販会計ソフト比較_登録番号の呼び名.md)。**調べたのは弥生 1 社だけ**）。
**本プロジェクトは違う選択をする**——計上時に明細へ写す記録が要り
（[13 §4](13_取引先設計.md)・[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)）、
**摘要に書く運用では「どの登録に基づいて計上したか」が後から辿れない**からである。

**引く日付は `journal_lines.tax_point`**（課税仕入れを行った日）。計上日でも取引日でもない。

## 2. 列（確定。2026-08-25）

公表システムの提供項目（[リサーチ §3-2](research/2026-08-25_取引先の識別番号と公表システム.md) で
リソース定義書の項目一覧を確認）に対応させて、次で確定した（`Designer/ddl/006_partner_registrations.sql`）。

| 列 | なぜ要るか・対応する提供項目 |
|---|---|
| `registration_no` | 登録番号（registratedNumber）。**書式は「T ＋ 数字 13 桁」（計 14 桁）で確認済み**（リサーチ §3-3）。DB は書式を検査せず、入力画面・取込を作るときに**アプリ側で検査する**（13 桁部分が法人番号と同一かは未確認のままなので、法人番号との突合には使わない） |
| `valid_from` | 登録年月日（registrationDate） |
| `ended_on` / `end_reason`（`expired` / `revoked`） | `expired` ＝ 失効年月日（expireDate）由来、`revoked` ＝ 取消年月日（disposalDate）由来。**日付 1 列＋理由 1 列**で持つ。公表システムの提供も**履歴 1 行につきいずれかの日付**なので、この形と一致する（リサーチ §5-6 で実質確認。2026-08-25）。**それぞれが指す法的事象——届出による取りやめ・職権・事業廃止など——の対応は未確認**。提供された日付をそのまま持ち、**「その日を含むか」の判定はフェーズ 3 で制度を確認してから**確定させる（保留リスト）（当初案の `valid_to` をやめたのは、±1 日の解釈をデータに焼き込まないため）。登録より前に終わる行は CHECK が拒む（**同日はあり得るか未確認なので許している**） |
| `source`（`manual` / `nta_api` / `nta_download`） | **手で入れた値を自動同期が黙って上書きしないため** |
| `confirmed_on` | この行を人が最後に確かめた日（監査用） |
| `nta_updated_on` | 公表システム側の更新年月日（updateDate）。差分取得の基準 |
| `published_name` | 氏名又は名称（name）の写し。**公表名とマスタ名はずれる**（略称で登録している等）。突合結果が残り、名寄せの手がかりにもなる。個人のダウンロード提供では削除される項目があるため（どの項目かは未確認）空がありうる |

**前後の空白は落として保存する**（`InvoiceRegistrationNumber.Normalize`。法人番号も同じ）。
貼り付けで紛れ込むだけで利用者の意図ではないからで、**落とさないと同じ番号が 2 通りの文字列で
保存されて突合が壊れる**。**小文字の `t` と全角数字は落とさずに拒む**——
そちらは利用者が入れたつもりのものだからである（[21 §0](21_画面の原則.md)）。

同じ登録の二重取込は `UNIQUE (partner_id, registration_no, valid_from)` が拒む
（**登録年月日そのものが誤りだった場合の訂正の配信のされ方は未確認**。取込の設計時に
実データで確かめる。リサーチ §5-7）。

### 2-1. 同じ登録番号を別の取引先が持つことは正常である（排除しない）

**開発者の判断**（2026-09-05）。**登録番号は人格に紐づくので、同じ法人を支店ごとに
別の取引先として登録すれば、登録番号は必ず同じになる。** 排除しえない。

- 実データがそうなっている——`T1234567890123` を `P001` と `S0001` が
  期間の重なる形で持っている（2026-09-05 の探索的テストで見つけた。[qa/04](qa/04_実機操作テスト.md)）。
  この 2 件は法人番号も同じ（`8700110005901`）で、**同じ法人の別レコード**として筋が通っている
- **[13 §2-2](13_取引先設計.md) の法人番号と同じ扱いである。** 同じ値なら同一法人であって、束ねる操作は要らない
- `PartnerRegistrationSubmitGate` の検査がすべて取引先ごとなのは**正しい**。
  取引先をまたぐ重なりを止める関門は置かない

**ただしフェーズ 3 で数えるときに効く。** [11 §5](11_消費税設計.md) の経過措置の相手方別上限は
**「一の免税事業者等ごと」**に掛かるので、**取引先レコード単位で数えると、支店ごとに分けた分だけ
上限が増えて控除が過大になる**。**名寄せで解決したあとの単位で数える**こと（[13 §2-2](13_取引先設計.md) の解決の順序）。

## 3. 登録状況は税額計算を支配しない

**計算を支配するのは利用者が選んだ税区分である**（[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)）。
相手が適格請求書発行事業者でも、登録番号のない区分記載請求書等しか保存していなければ
**一律に経過措置が適用される**（選択制ではない）。適用は「受け取った書類」で決まる。

登録状況の使い道は**入力支援・警告**と、**計上時に明細へ写す記録**（[13 §4](13_取引先設計.md)。[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md) の「判定の根拠の記録」）に限る。

## 4. 手入力の画面（実装は 2026-08-26。呼び名と導線は 2026-08-31 に変えた）

**画面での呼び名**（開発者の決定。2026-08-29。**「登録番号」が法令（消税法 57 の 4 ①。
[消費税リサーチ §9](research/2026-08-23_消費税インボイス制度.md)）と国税庁の資料
（[リサーチ §3-2](research/2026-08-25_取引先の識別番号と公表システム.md)）の語だから**）。
**「インボイス番号」は使わない**（用例が見つからず、法令・国税庁の語ともずれるから）。

| 場所 | 呼び名 |
|---|---|
| メニュー・ページの題（**文脈が無い**） | **登録番号（インボイス）** |
| 取引先の画面の中のフィールド（**文脈がある**） | **登録番号** |

補い方の考え方は [21 §5](21_画面の原則.md)、用例の調査は
[市販会計ソフト比較 — 登録番号の呼び名](research/2026-08-28_市販会計ソフト比較_登録番号の呼び名.md)。

**このアプリは取引先に法人番号も持つ**（[13 §1-2](13_取引先設計.md)）。裸の「登録番号」を使うのは
**取引先の画面の中だけ**にとどめ、それ以外では必ず補う。

`PartnerInvoiceRegistration`。**最低限**である——
取引先・登録番号・登録年月日・取消・失効年月日・取消・失効の理由・公表名・最終確認日だけを持つ。

**入力は別画面で行い、取引先の詳細には確定した履歴だけを見せる**
（画面の骨格——「埋め込みの一覧を直接編集させ、編集したとたん本物になる仕様は無理がある。
編集は別画面で行い、『登録』の成功で戻り、失敗なら何も起こらない」——は**開発者の提案**（2026-08-31）。
「追加ボタン 1 つ ＋ 行ごとの編集リンク」の形は Claude の提案を**開発者が承認**（2026-09-02。
**履歴は行ごとに「終わり」をあとから記録する操作があり、対象の行を選ぶ入口が要るから**）。
それまでの埋め込み編集の経緯は git の本節の履歴にある）。

- **取引先の詳細には、閲覧専用の履歴一覧と「登録番号を追加する」ボタンを置く。**
  登録 → 取消 → 再登録という**履歴が複数行あることが、取引先の画面で見える**。
  一覧の**行ごとに編集リンク**を置く——失効の記録・公表名や確認日の更新・誤記の訂正は、
  その行を開いて行う
- **編集画面（`PartnerInvoiceRegistration` の詳細）では、取引先は表示のみ。**
  利用者が選ぶ欄は無い（新規は親から識別子を渡す）。**「登録」ボタンで確定**——
  関門に拒まれたらエラーを出して何も起こらない。成功したら取引先の詳細へ戻る
- **既存の登録の取引先は変えられない**（関門 `RejectRepoint`。2026-08-31）。
  変えられると A 社の履歴に穴が空き、B 社に他人の登録番号が生え、
  **すでに計上済みの明細に焼き込まれた写し（[13 §4](13_取引先設計.md)）と食い違う**。
  関門は取引先を**型を問わず差分から読む**（API を直に叩く経路と取込（フェーズ 6）が同じ入口を通るため）
- **独立した一覧は「見るため」に残す**（取込の結果を一括で確かめるのに要る。フェーズ 6）。
  **この一覧はクエリモジュール（`PartnerRegistrationList`）である**——親 FK を `IdFieldDesign` に
  すると参照先の名前を出せなくなるため（[qa/01 D-17](qa/01_CLB静かな失敗.md)）。
  [ADR-0022](decisions/0022-明細を並べる帳簿はクエリモジュールで作る.md)・[ADR-0027](decisions/0027-入力の一覧はラップモジュールとクエリモジュールで作る.md) と同じ判断で、
  **一覧の中身が素の姿と違うならクエリモジュール**にする。取引先名は取引先の詳細へのリンクにし、
  **出所**（手入力か取込か）も列に出す
- **取引先と登録を同じ保存で新規作成する経路は塞いである**（2026-08-26 に先行して塞いだ）。
  取引先の識別子が仮のままでも、**送られてきた文字列のまま突き合わせる**ので二重登録を止められる
  （`PartnerRegistrationSubmitGate`）

- **出所（`source`）と公表システム側の更新年月日（`nta_updated_on`）は画面に出さない。**
  手入力の行は DB の既定（`source = 'manual'`）が入る。
  取込（フェーズ 6）を作るときに、区別を見せる必要が出てから足す
- **削除できない**（`CanDelete = false`）。取消・失効は「終わり」を記録して残すものであって、
  行ごと消すものではない

**行の不存在は「調べて未登録だった」と「まだ入力していない」を区別しない**（2026-08-25 の決定）。
区別する列（未登録と確認した日）は、警告の文言設計（フェーズ 3）で必要になったら考える。
それまで警告は「登録情報が入っていません」のように、**不存在を未登録と断定しない言い方**にする。

## 5. 登録の不変条件（確定。2026-09-02）

**1 つの取引先の登録の履歴が守る規則。** 破ると、計上時の写し（[13 §4](13_取引先設計.md)）が「どれを写すか
決められない」で止まるか、誤った番号が永久に焼き込まれる。**テストの観点もこの表から導く。**

| # | 不変条件 | どこが守るか |
|---|---|---|
| R-I1 | 終わりには必ず理由がある（`ended_on` と `end_reason` は対） | DDL の CHECK ＋ 関門（言葉で断る） |
| R-I2 | 登録より前には終われない（`ended_on >= valid_from`。同日は許す——§2） | DDL の CHECK ＋ 関門。**CHECK は生の文字列比較のまま**（`date()` 包みへの作り直しはフェーズ 6 の取込設計と一緒に——保留リスト） |
| R-I3 | 同じ日から始まる登録は 1 件（qa/02 R26-20） | DDL の一意索引（`date()` 包み）＋関門 |
| R-I4 | **期間は重ならない。ただし隣接は許す**（下の定義） | 関門＋ DDL のトリガ（2026-09-02 に追加） |
| R-I5 | 終わりのない行（現に有効な登録）は**高々 1 件で、必ず最も新しい行**（R-I4 の帰結） | 同上 |
| R-I6 | 既存の行の取引先は変えられない（§4） | 関門 |
| R-I7 | 登録番号の書式は「T ＋ 数字 13 桁」（§7） | 関門 |
| R-I8 | 行は削除できない。取消・失効は「終わり」の記録で表す（**手入力に対して確定**。公表システムの差分の**処理区分 99＝登録簿からの削除**（[リサーチ §3-3](research/2026-08-25_取引先の識別番号と公表システム.md)）をどう表すかはフェーズ 6 の論点——保留リスト） | `CanDelete = false` ＋ 関門（画面の形は守りではない——qa/01 F-24） |
| R-I9 | 新規の行の取引先は実在する（2026-09-02 追加） | 関門が言葉で断る。最後は DB の外部キー |

**R-I4 の定義**（登録年月日の早い行を A、遅い行を B とする）:

- A に終わりが無い（`ended_on` が NULL）のに B がある → **拒む**（有効な登録が続いているのに次が始まる）
- B の登録年月日が A の終わりより前 → **拒む**（真の重複）
- B の登録年月日が A の終わりと**同じ日 → 許す**（隣接。どちらの制度解釈でも決定的に引ける——下の説明。**再登録の正常形かは未確認**（[2026-08-26 リサーチ](research/2026-08-26_登録の効力を失う日.md)））
- B の登録年月日が A の終わりより後 → 許す（間に未登録の期間がある）

**隣接を許すのは、計上時の引き当て（`InvoiceRegistrationHistory.InEffectOn`）が
「終わりの日を含み、同日に 2 件当たったら新しいほうを採る」と決めているから**である。

**関門は「保存後にできあがる履歴」で判定し、DB（一意索引・トリガ）は文単位で判定する。**
このずれのため、**複数行の期間を 1 回の保存で同時に編集する操作は、最終状態が正しくても
文の順序によっては DB が途中状態で拒みうる**（SQLite に遅延制約は無い。2026-09-02 のレビュー指摘）。
**画面は 1 行ずつ保存するのでこの形は出ない。** 複数行を 1 保存で送る取込（フェーズ 6）の
設計時に、実際の保存の順序で確かめて倒し方を決める。
取消・失効の日を有効期間に「含むかどうか」の制度解釈はフェーズ 3 送り（§2）なので、
隣接の 1 日はどちらの解釈でも決定的に引ける形にしてある。

**編集の許容**（保存後の行に対して）:

| 対象 | 可否 | 理由 |
|---|---|---|
| 取引先 | **不可** | R-I6 |
| 登録番号・登録年月日 | 可 | 誤記の訂正。**マスタを直しても計上済みの写しは動かない**（[ADR-0018](decisions/0018-帳簿の記載事項は計上時に写して固定する.md)）ので過去の帳簿は変わらない |
| 取消・失効年月日・理由 | 可（追記が本来の操作） | 登録の「終わり」は保存のあとに起きる出来事である |
| 公表名・最終確認日 | 可 | 公表システムで再確認するたび更新する |
| 行そのもの | 削除不可（R-I8） | 誤って確定した余分な行は、**内容を正しい行に編集して使う**。行を消す手を作るかは保留のまま（qa/02 R29-12） |

## 6. 引く日をどう決めるか（実装。2026-08-26）

| 決めごと | どうするか | なぜ |
|---|---|---|
| 引く日付 | `journal_lines.tax_point`。**入っていなければ伝票の取引日** | `tax_point` は「引き渡しが取引日と違う取引」のための上書きである。上書きが無いなら取引の日に行われたと読むのが素直。**いまの振替伝票の画面は `tax_point` を入力させない**ので、「無ければ写さない」にすると写しが永久に空になる（計上済みは不変なので後から埋め直せない。[qa/03 L-12](qa/03_テストで漏らした実例.md)） |
| 終わりの日そのもの | **含める**（`ended_on == tax_point` の登録も引く） | 取消年月日・失効年月日が**効力の最終日か、効力を失った初日か**は一次情報で確認できていない（§2 が**フェーズ 3 送り**と決めた論点。2026-08-26 に国税庁の公表サイト運営方針まで当たったが確定できず）。**ここは根拠の記録であって制度上の判定ではない**ので、含める側に倒す——境界の 1 日で番号を落とすと後から補えないが、残っていれば解釈が決まったときに読み替えられる |
| 同じ日に始まる登録が 2 件 | **止める**（計上させない） | どちらを写しても 5 割の確率で誤った番号が**永久に**残る。ただし**入力の時点で止める**のが本筋なので、登録の保存の関門が先に弾く（§4） |
| 前の登録が終わった日に次が始まる | **新しいほうを採る** | 再登録では境界日に候補が 2 件になる。これは異常ではない |

規則は `InvoiceRegistrationHistory.InEffectOn`（純粋関数）が 1 か所で持つ。
**SQL 側では絞り込まない**——境界の条件が 2 か所に分かれると、片方だけ直したときに
「画面では有効なのに写しが空」という形で静かにずれる。

## 7. 登録番号の書式は保存の関門が見る（実装。2026-08-26）

DB は書式を検査しない（§2 の決定）ので、**書式を守れるのは `PartnerRegistrationSubmitGate` だけ**である
（**止める範囲の正典は §5 の表**——この関門は R-I1〜R-I9 をすべて見る）。
この節が言うのは、そのうち **2 つをここで止める理由**である。

1. **書式**（「T」＋数字 13 桁。半角のみ・大文字のみ。R-I7）。壊れた番号を通すと、計上のときに
   そのまま明細へ焼き込まれ、計上済みは不変なので直せない
2. **同じ取引先に同じ日から始まる登録が 2 件できること**（R-I3）。§6 の表の 3 行目を、
   計上の場面ではなく**入力の場面で**止めるためである

**画面のスクリプトでは検査しない**（[ADR-0008](decisions/0008-CLBとCSharpライブラリの責務分担.md)）。
取込（フェーズ 6）も同じ入口を通るので、ここに置けば経路が増えても検査が外れない。
