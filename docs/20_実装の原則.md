# 実装の原則

> **[21_画面の原則](21_画面の原則.md)・[22_層と実行場所](22_層と実行場所.md) と並ぶ、2x 帯（原則）の 1 冊**
> （開発者が 2026-08-26 に指示し、2026-09-05 に [CLAUDE.md](../CLAUDE.md) のスリム化と合わせて起こした）。
> **コードをどう書くか**の原則だけを置く。作業の進め方は [30](30_作業のルール.md)、検証は [31](31_検証のルール.md)、
> CLB での書き方は [`Designer/Project.md`](../Designer/Project.md)、
> 踏むと静かに壊れる挙動は [qa/01](qa/01_CLB静かな失敗.md) が持つ。

**この文書の育て方**（21 と同じ）

- **原則だけを置く。** 個別の判断は ADR、CLB の書き方は Project.md
- **「なぜ」の無い項目を足さない。** 理由が書いていない規則は、例外に出会った人が判断できない
- **厳選して書く。** 原則が増えるほど 1 件あたりの重みが下がる
- **ここに書いてあるのは「こうする」であって「こうなっている」ではない。**
  実装の現在地は [04](04_実装計画と現在地.md)。**原則と現況を混ぜて読まない**
- **まだ確かめていない項目は想像である。** 確かめたら、確かめたと書く
- 原則が覆るときは ADR を起こす。ここを黙って書き換えない

## 1. ロジックは C#、CLB は薄いプレゼンテーション層

**会計の計算・検証・集計は、外部依存ゼロの C# ライブラリ（`AccountingCore`）に置き、ユニットテストで守る。**
スクリプトに書いてよいのは、画面上の値の出し入れと C# サービスの呼び出しだけ。
**理由は CLB スクリプト（`*.mod.cs`）がツリーウォーク型インタプリタで、静的検査がほぼ効かないこと**——
論拠は [ADR-0008](decisions/0008-CLBとCSharpライブラリの責務分担.md) が持つ。
**本来なら画面が持つロジックも、テストできる側（`AccountingCore.Server`）に置く**——
それがこのプロジェクトの制約である。

**どの層に何を置き、どこで実行するかは [22_層と実行場所](22_層と実行場所.md) が持つ**
（層・プロジェクト・フォルダ・どの層に置くか・どこで実行するか・Web API・依存の向き）。
**ここは原則だけを置く。**

## 2. 制度値をハードコードしない

税率・控除割合・閾値・耐用年数は、**有効期間つきのルールデータ**として持つ
（各マスタへの当てはめは [12_マスタ台帳](12_マスタ台帳.md)）。
**仕訳には適用したルールの版を固定して保存し、後日マスタを更新しても過去を再計算しない。**

## 3. マジックナンバーを使わない

**意味を持つ数値をコードに直接書かない**（開発者の指示。2026-09-05）。名前の付いた定数にする。

**理由は「読む人が『この 100 は何か』を推測しなくて済む」こと**である。
**だから境目もそこで決まる**——`value >= 1m`（1 円未満は無い）や `BETWEEN 1 AND 12`（月）のように
**その場で読めば意味が分かる数値は、そのまま書いてよい。** 名前を付けても情報が増えない。

**複数の場所に要る値は、読めても定数にする。** それは §4 の話になる。

## 4. 重複定義を避ける。已むを得ないなら、機械で突き合わせる

**同じ事実を 2 か所に置かない**（開発者の指示。2026-09-05）。
**ただし C# と CLB で別々に定義せざるを得ない場合は許容する**——
CLB のデザインは JSON、DDL は SQL テキストで、**どちらも C# の定数を読めない**からである。

**許容するときは、必ず機械で突き合わせる。** 人が揃えると、いつか片方だけ直る。

**先例が 2 つある。2 者でも 3 者でも同じ形である。**

- **`EnumConsistencyTests`**——**DB の `CHECK` の値・CLB のデザイン enum・C# の列挙子**の
  **3 者一致**（`AccountingRole` がその例）。C# 側を持たない行は 2 者一致で守っている
- **`Designer/migrations/baseline/`**——`ddl/` の凍結コピーを**同値テスト**で守る（[ADR-0020](decisions/0020-スキーマは現在形の正典で持ち変更は差分で配る.md)）

**当てはまる場面と、いま守れているか**（2026-09-05 に実物と突き合わせた）

| 値 | どこに要るか | いま |
|---|---|---|
| 選択肢（列挙） | DB の `CHECK`・CLB のデザイン enum・C# の列挙子 | **守れている**（`EnumConsistencyTests`） |
| 桁と長さ | DB の `GLOB '[0-9]…'` やトリガ・CLB のプレースホルダ（`MaxLength` は黙って切るので使わない。[qa/01 A-13](qa/01_CLB静かな失敗.md)）・C# の定数 | **守れている**（`FieldLengthConsistencyTests`。2026-09-09。法人番号は 2026-09-11 にプレースホルダ側へ）。**法人番号 13 桁・マスタのコード 20 文字・文字の欄 10**（[12 §2-2](12_マスタ台帳.md)・[10 §4-2-1](10_会計ドメイン設計.md)。2026-09-14）。**上限を置いていない欄は理由つきの表で持ち、デザインを総当たりして漏れを赤くする** |
| コードの字種と形 | DDL のトリガ・C# の `MasterCode` | **守れている**（`MasterCodeGuardTests` が符号位置を総当たりする。2026-09-09）。**画面のプレースホルダは対象外**——`MasterCode.FormatDescription` の 4 か所目の写しだが、突き合わせていない |
| 使用中のマスタの意味を決める列 | C# の `MasterMeaningGate.Guarded`・DDL のトリガの `UPDATE OF`・CLB のデザイン JSON（`DbColumn`・`DisplayName`・並び） | **守れている**（`MasterMeaningGateTests`。2026-09-07） |

**金額の上限は、この表に載せない**——`journal_lines.amount` の上限を決めているのは
`CHECK` ではなく**格納型**（SQLite の 64 ビット INTEGER）であり、**重複した定義が存在しない**からである。

## 5. 使われないコードを残さない

**「いつか要るかもしれない」で書いた分岐は、書いた瞬間から腐る**（開発者の指示。2026-09-07。
**一度も動いていないコードが正しく動く保証はどこにも無いのに、
「昔からあるコードだから大丈夫だろう」と思われて残り続け、使った日に不具合が出るから**）。

- **一度もコミットしていないなら、書かない。** 一度コミットしたなら、**消してよい**——
  必要になったら履歴から取り出せる
- 判断の基準は「**その経路が実行されるか**」である。**関門やテストが毎回通す経路は「使われている」**
  （例: `trash.ps1` の `-DryRun` は、コミット前フックの自己検査が毎回通す）
- **「効果を観測していない」は消す理由にならない。** 関門のコードは**事故のときにしか効果が出ない**ので、
  この物差しを当てると関門は必ず痩せる。**判定に効く分岐を消すなら、
  その経路がこの repo で起こりえないことを先に示す**
- 例外は、**分岐そのものが「印字して終わる」ものだけ**（間違えても誤った動作をしない）

**実例**（2026-09-07。**一度消して、戻した**）。`trash.ps1` の worktree の 2 根解決を
「一度も動いていない」として落とした。**動いていなかったのは効果のほうで、コードは毎回走っていた。**
しかも `.claude/worktrees/` は実際に使う作業形態で
（サブエージェントに隔離した作業をさせるときに切る。守りの当てはめは
[ADR-0044](decisions/0044-削除はごみ箱送りに一本化しrmを機械で止める.md)）、
落とした結果**worktree から本体のリポジトリを消せる穴が開いた**（自己レビューで実証）。
**同じ回にシンボリックリンクの実体解決も落としたが、そちらは残したまま**——
このリポジトリにリンクは 1 つも無く、経路そのものが起こらないからである。

## 6. 利用者に見せる文字列と、機械に渡す文字列を書き分ける

**機械に渡す値は、書式を明示して書く**（Claude の判断。2026-09-13。書式そのものは [21 §2-5](21_画面の原則.md)）。
SQL に渡す ISO の日付は `ToString("yyyy-MM-dd", CultureInfo.InvariantCulture)` と書く。

**理由は、書式指定そのものを「利用者に見せる文言」の書き方として予約したこと**である。
そう決めると `CSharpStyleTests` は**書式指定を見張るだけで**、
**利用者に見せる日付が `yyyy/MM/dd` から外れたら鳴る**（[ADR-0021](decisions/0021-CSharpは読みやすさを損なわない範囲で最新の記法に揃える.md)）。
**見張るのは文字列補間（`$"{date:...}"`）と `ToString("…")` の両方である**——
補間だけを見ていると、いちばん自然な逃げ道が空く。
**外れるのは `CultureInfo` を明示した形だけ**で、それがそのまま「機械に渡す値」の印になっている。

## 7. 空の値は 1 通りに持つ（空値検索の前提）

検索機能は「記録事項がない電磁的記録」も探せなければならない（電帳通達 8-13。[リサーチ](research/2026-08-23_電子帳簿保存法.md) §3.5）。そのために**「無い」は NULL で表し、空文字を保存しない**。混在すると空値検索が `is null or = ''` になり、書き漏らした側が静かに取りこぼす。
**画面の設定だけでは 1 通りに揃わない**（CLB の既定は空文字保存で、`Null` にしても空白だけの入力は
空文字のまま残る。[qa/01 A-11・A-12](qa/01_CLB静かな失敗.md)）。だから**保存の入口が、受け取った空文字を
NULL に寄せてから渡す**——**関門ではなく `BlankTextNormalizer`**（プレゼンテーション層。[22 §2-1](22_層と実行場所.md)）で、
`AccountingSubmitPipeline` が呼ぶ。**いま会計コアの入口にしか無い**ので、
**取引先だけを別ホストへ載せると足りなくなる**（`PartnerSubmitPipeline` が自分でそう警告している。qa/03 L-14）。
**帳簿のクエリ側は空文字も拾う二重の守り**を残す（`is null or = ''`）——
関門を通らない経路（CSV 取込・投入 API。フェーズ 6）が入るまで、法定検索を守るのはこちらである。
