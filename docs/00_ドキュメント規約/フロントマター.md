# ドキュメント規約 §3 — フロントマター

> [ドキュメント規約（総則）](README.md)の一部。**節番号は 3 冊を通して一意**なので、
> 他の文書からは `00 §3-3` のように節だけで指してよい。

## 3. フロントマター

全対象文書の先頭に YAML フロントマターを置く。

```yaml
---
title: 会計ドメイン設計              # 見出しと同じでよい
status: current                     # current | superseded | historical（3値のみ）
scope: 会計コア                      # 対象領域（部品名 / 業務名 / 全体）
audience: [開発]                    # 開発 | 運用 | 営業 | テスト（複数可）
updated: 2026-08-23                 # 内容を変えた日
supersedes: []                      # この文書が置き換えた文書のパス
related: [decisions/0004-仕訳の不変性.md]
---
```

### 3-1. 必須フィールド

| フィールド | 規則 |
|---|---|
| `title` | 短い名詞句。見出しと揃える |
| `status` | `current` / `superseded` / `historical` の 3 値のみ（§3-2） |
| `scope` | 対象領域。部品名（会計コア・証憑 …）／`全体` |
| `audience` | `開発` `運用` `営業` `テスト` から 1 つ以上 |
| `updated` | **フロントマター以外の行を変えたら**更新する（体裁だけの変更でも動かす。**新規追加と改名も含む**）。日付をまたいで持ち越したら今日に直す。**機械が検査する**（[§6](README.md)） |

### 3-2. `status` の判定

**`status` が肝である。`current` 以外は「読まなくていい」と最初の数行で判断できる。**

| 値 | 意味 | 中身の扱い |
|---|---|---|
| `current` | 現在の仕様・計画・手順。読めば今の姿が分かる | **常に現在形に保つ**（[§4](本文.md)） |
| `superseded` | 後継がある。`related` に後継を必ず書く | **消さない・直さない**（判断の経緯が失われる） |
| `historical` | 当時の記録として価値がある（実施記録・レポート） | **消さない・直さない**（記録なので現在形化しない） |

`superseded` と `historical` の違いは「後継があるか」。

**`research/` は `historical` ではない。** 制度リサーチは実装のたびに引く現役の文書なので `current` に保ち、
制度が変わったら**本文を書き換える**（[§5](README.md) の「引くもの」）。

### 3-3. ADR（`decisions/`）の特則

ADR は判断ログである。**当時の判断とその理由を、いつでも同じ形で読めること**に価値があるので、
**書き換えない。** `status` は決定の生死で決める。

| 状況 | `status` |
|---|---|
| 決定が現在も有効（大半） | `current` |
| 後継 ADR が決定を覆した（**一部でも**） | `superseded`（`related` に後継 ADR） |
| 検討して見送った記録 | `historical` |

**一部だけを覆すときも、元 ADR は全体を `superseded` にする**（開発者の決定。2026-08-26。
**部分的に直すと「current なのに一部は嘘」という、最も見分けの付かない状態ができるから**）。
最新の判断は**新しい ADR** に書く——元 ADR の内容を引き継ぎ、**どこを変えたか**と**なぜ変えたか**を足す。
元 ADR を部分的に直して `current` のまま置かない。それは「当時の判断ログ」ではなく「今の方針」であり、
**`current` なのに一部は嘘**という状態が [§6](README.md) のコード参照の検査を空振りさせる。

**書き換えないが、追記はしてよい**（[§4-3](本文.md)）。**判断が変わっていないのに事実だけが動いたとき**——
実装で名前が変わった・数値を締め直した・時期の見込みが外れた——は、
**日付つきの注記**（`> **YYYY-MM-DD 追記**: …`）を足して知らせる。
判断が変わったなら注記ではなく後継 ADR を起こす。

**体裁と参照の修理は書き換えてよい。** 節番号の重複・欠番、他文書への参照が指す先のずれ、
リンク切れは、**判断ログの中身ではない**ので直す。直したことは注記しなくてよい
（git log が持つ）。中身に触れるなら注記か後継 ADR である。
**ただし「参照先が `superseded` になった」は、ずれではない**——当時その ADR に依拠した事実は
動いていないので、張り替えずに注記で示す（Claude の判断。2026-08-28。**張り替えた実例を
自己レビューで差し戻したときに決めた**。[§4-10](本文.md)・[qa/02 R19-05](../qa/02_自己レビュー記録.md)）。

**既知の例外**: [ADR-0008](../decisions/0008-CLBとCSharpライブラリの責務分担.md) は
[ADR-0022](../decisions/0022-明細を並べる帳簿はクエリモジュールで作る.md) に一部を覆されているが
`current` のまま据え置いている。本規則を決める前に書かれたもので、
作り直すコストに見合わないため（開発者の判断。2026-08-26）。**次からはこの形にしない。**

**ADR は行数にこだわらない**（[§5](README.md) のとおり行数警告と管理指標の対象外）。判断の理由が 1 本に
まとまっていることを優先する。ただし**「1 ADR 1 論点か」を確かめる**——2 つの論点を抱えた ADR は、
片方が覆されたときに丸ごと写し直すことになる。

### 3-4. 任意フィールド

| フィールド | 使う文書 | 意味 |
|---|---|---|
| `verified: 2026-08-23` | `tests/` 配下 | **最後に実機で通した日**。`updated`（文書を直した日）とは別物 |
| `growth: append` | 台帳・ログ型 | 追記専用で必ず育つ文書。行数警告を免除する代わりに分割方針を本文に持つ |
| `expires: <終了条件>` | 一時文書 | 移行計画・レポートなど、役目を終える予定があるもの（[§4-4](本文.md)） |
