# ドキュメント規約 §4 — 本文の書き方

> [ドキュメント規約（総則）](README.md)の一部。**節番号は 3 冊を通して一意**なので、
> 他の文書からは `00 §4-6` のように節だけで指してよい。
> **分割のとき既存の番号は動かしていない**（他文書が節を名指しして参照しており、
> 動かすとその全部が別の節を指すため。2026-08-28）。

## 4. 本文の書き方

### 4-1. `current` の文書は常に現在形に書き換える

追補・読み替え表・注記で積み上げない。**過去との差分ではなく、今どうなっているかを書く。**

### 4-2. ヘッダに更新履歴を積まない（禁止）

```
✗ > 更新: 2026-08-23 ADR-0005 を反映 ／ さらに更新: 2026-09-01 UI 改訂
```

これは**ファイル内読み替え表**であり、本文が旧記述のまま取り残される事故を必ず起こす。

- 変更の**経緯**は ADR に書く → `related:` でリンクする
- 変更の**日付**は `updated:` が持つ
- 本文は**書き換える**

### 4-3. 古い情報は消す。追記で肥大化させない

**既定の更新方法は「追記」ではなく「書き換え」である。** 文書を触るたびに、
「この文書に、もう事実でない記述・重複した記述が残っていないか」を確認して**消す**。

- **消すことをためらわない。** すべて Git 管理下にあり履歴から復元できる。「念のため残す」は肥大化の最大の原因である
- **追記が正しいのは 2 種類だけ** — ADR（判断ログ）と、`growth: append` を付けた台帳・ログ型文書。
  それ以外の文書に追記していたら、それは書き換えを怠っているサインである
- **定期棚卸し**: フェーズの区切り・大きな機能追加のたびに `current` を一覧し、「250 行超」「もう `historical` でよいもの」「同じ事実を二重に書いているもの」を整理する
- **実装の経過を記録する文書を作らない。** 何をしたかは git log、なぜそうしたかは `decisions/`、
  CLB の踏み抜きは `qa/` と `CLB改善提案/` が持っている。「実装履歴」文書はそれらの劣化コピーになり、必ず最大の文書に育つ

### 4-4. 「後で直す」を本文に書かない

保留は本文ではなく**保留リスト**に積む。置き場所は**その保留を負う文書の末尾**
（どの文書にも属さないものは対象ディレクトリの `README` 末尾）。書式は
**日付・内容・いつ決めるか**の 3 つで、期限のない保留を置かない。

```
- 2026-08-23 ADR-0007: 10_会計ドメイン設計 に補助元帳の節を追加（フェーズ 2 の着手前）
```

**決まったら保留リストから消す。** 決定は ADR か仕様書へ移し、**打ち消し線で残さない**
（経緯は git log と ADR が持つ。§4-3）。

**期限を他の文書の中に置かない**（**Claude の判断。2026-09-09。開発者は未承認**——
[README](../README.md) の保留リストで諮っている）。**保留は、それを負う文書が自分の末尾で持つ**（上の「置き場所」）。
**他文書と時期を合わせたいときは、自分の側に書いたうえで「〜と同じ回に」と添える。**
**預け先が空になっても、預けた側で気づけるようにするため**である。
実例: [qa/02 の R40-21](../qa/02_自己レビュー記録.md) は 4 件の期限を
「**80 §4 の宿題と一緒に、フェーズ 3 の着手前の回で拾う**」と [80 §4](../80_参照法令一覧.md) に預けている。
**2026-09-09 に 80 §4 の宿題は 5 件から 2 件に減った**——**0 件になっていたら、預けた側の期限は宙に浮いていた**
（**実際に落ちた事例はまだ無い**。落ちる前に規則にした）。

**保留リストと未決事項の項目を、番号で参照しない。** 番号は消すたびに振り直されるので、
他の文書から `#4` と指した参照は必ず腐る。指すときは**論点の名前**を書く。

読み替え表との違いは、**これが解消される前提の一時リスト**であること。
`lint_docs.py` は `current` 文書の未処理マーカーを警告する。除外されるのは、保留リストの節、
コードブロックの中、行末に `lint-docs:ignore` を書いた行、および `decisions/` と `research/`
（自身の未確認事項を本文で列挙するのが正しい姿の文書）。

### 4-5. 一時文書には終了条件を書く

移行計画・レポートのように**役目を終える予定がある文書**は、作る時点で `expires:` に終了条件を書く。
条件を満たしたら即 `historical` にする。

### 4-6. 同じ事実を 2 箇所に書かない

書くならリンクする。とくに**マスタ化された値**（税率・控除割合・閾値）を複数の文書に直書きすると、
マスタを変えた瞬間に全部が嘘になる。コードで「制度値をハードコードしない」と定めているのと
同じ規律を文書にも適用する。

### 4-7. 呼称は 4 語で固定する

**4 語（利用者・開発者・Claude・CLB 開発元）の定義は
[CLAUDE.md §3](../../CLAUDE.md) が正典である。** ここは文書を書くときの当てはめだけを書く
（定義を写すと片方が古くなる。§4-6）。

- **「ユーザー」と書いてよいのは、固有名詞・API 名・製品名の一部だけ**
  （`AppUser`・`CurrentUser`・User Secrets・ユーザー定義関数・OS のユーザー名）
- **CLB でアプリを作る人たちには語を決めていない。** 言及が要るときは
  そのまま「CLB で開発する人たち」と書く
- 既存文書の混在は一括置換せず、触った文書から直す。
  **`decisions/` は判断ログなので遡って直さない**（[§3-3](フロントマター.md)）

### 4-8. 公開リポジトリに書いてはいけないもの

このリポジトリは GitHub のパブリックリポジトリへ公開する。

- **絶対パスを書かない。** リポジトリ直下は `<REPO_ROOT>` と表記する
- **ユーザー名・ホスト名・個人のメールアドレスを書かない**
- **接続文字列・API キー・トークン・パスワードを書かない**（秘密は .NET User Secrets）。**禁止の本体と例外は [CLAUDE.md](../../CLAUDE.md) §5 が持つ**
- 検査: `python tools/docs/lint_secrets.py`（コミット前に流す）

### 4-9. 制度・法令の記述には出典と確認日を付ける

税率・控除割合・期限・要件を書くときは、**必ず一次情報（国税庁・e-Gov・財務省・ASBJ 等）の URL と
確認日**を併記する。記憶や推測で書かない。制度は毎年変わるため、出典と確認日が無い記述は
半年後に信用できなくなる。

**条文は e-Gov、解説は行政機関の作成資料のみを信じる。それら以外は根拠にしない**
（開発者の指示。2026-08-26。文言は 2026-08-27 に開発者が明確化）。

- **法令の二次資料（法令集サイト・解説記事）を根拠にしない**（改正が頻繁で、古い版でも見分けが付かない。実例: 二次資料が法税規則 54 を「別表二十一」と示したが**正しくは別表二十四**）
- **最終改正・更新が今年でない資料は、まず疑う**（法税規則は 2026 年だけで 7 回以上施行）
- **e-Gov は施行日で条文が切り替わる。** 見た版の**施行日**も URL と確認日に添える
- 国税庁の一問一答・Q&A、省庁の法令解説、個人情報保護委員会のガイドライン等、
  **行政機関の作成資料は e-Gov に準ずる根拠**として使ってよい。
  ただし**ほぼ毎年改定される**ので**版（発行年月）を必ず控える**
- **少しでも怪しければ開発者に聞く**（[32_調査のルール §1](../32_調査のルール.md)）

### 4-10. `current` の本文から `superseded` へリンクしない

**リンクは読者をそこへ連れて行く。** `current` を読んでいる人がリンクをたどり、覆された決定を
現在の方針だと思ってしまう。だから**本文のリンクは後継へ張る**（`lint_docs.py` が error にする。
[§6](README.md)）。**「参照していたら error にする」は開発者の提案**（2026-08-28）。
**リンクに限ること・下の免除の範囲・連鎖を追わないことは Claude の判断**で、同日に開発者が承認した。

- **散文で番号や題名を挙げるのは咎めない**（「当時の三層の表は ADR-0019 §1 にある」）。連れて行かないから。
  **コードのコメントは逆に散文の言及も咎める**（[§6](README.md)）——実装と一緒に読まれ、たどる先が無いため
- **`decisions/` では張り替えない。** ADR は判断ログで、当時どの ADR に依拠したかは記録そのものである
  （[§3-3](フロントマター.md)）。**前身へのリンクは `ignore` で残し、後継は日付つき注記で示す**
- **対象外**: フロントマター（`supersedes:` / `related:` は関係を記録する場所）／コードフェンスの中／
  自分が `supersedes:` に挙げた前身（**後継は前身を語ってよい**）／
  ADR 台帳 `decisions/README.md`（全 ADR を載せるのが仕事）／
  `historical`（見送った記録は当時の記録として引くのが正しい）
- 経緯としてリンクが要る行には `<!-- lint-docs:ignore 理由 -->` を書く
  （表示に出ない HTML コメント。コードでは行末に `lint-docs:ignore`）。
  **この印はその行の検査を全部止める**ので、1 行に複数のリンクを置いた行では使わない
- **連鎖は追わない。** 前身特権で通ったリンクの先がさらに `superseded` でも咎めない
  （開発者の判断。2026-08-28。「**デメリットが目立ち始めたら検討すればよい**」——
  必要になってから作ればよく、連鎖をたどること自体にも意味がある、という理由）
- **参照リンク（`[x][y]`）とオートリンク（`<path>`）を使わない。** 検査の正規表現が拾わず、
  [§6](README.md) のリンク切れ検査も同時に盲目になる

### 4-11. 「開発者の指示・決定」には理由を添える

**「開発者の指示。2026-08-28」とだけ書かない。なぜそう決めたのかを同じ場所に書く**
（開発者の指示。2026-08-28。**理由のない指示・決定はしない主義であり、
後から見直したときに最も知りたいのは理由だから**）。

- 「誰が言ったか」は判断の重みを示すので、**引き続き書いてよい**
- 足りないのは「なぜ」のほう。**1 行でよい**——
  `（開発者の決定。2026-08-26。部分的に直すと「current なのに一部は嘘」ができるから）`
- **「開発者の決定」と書いてよいのは、開発者が答えた範囲までである。**
  そこから導いた敷衍・当てはめは、**同じ節の中で分けて書く**
  （2026-09-08。**2 日で 2 回、答えをもらっていない話まで開発者の判を押した**——
  [qa/02](../qa/02_自己レビュー記録.md) の R50-24・R51-01）。
  **書き分けの実例は [ADR-0042](../decisions/0042-優良な電子帳簿の対象帳簿は記載事項で数え帳簿の名前で数えない.md) の理由節**
  （「以下は開発者の見解を Claude が整理したものである」）と
  [ADR-0045](../decisions/0045-振替伝票1枚には1つの取引だけを記す.md) の決定節。
  **逐語が短いときは逐語を書く**——読者が範囲を自分で測れる
- **既存の記述は遡って直す必要はない**（数が多く、当時の理由を思い出せないものもあるため。
  開発者の判断。2026-08-28）。理由を思い出せるものを触ったついでに足すのは構わない

### 4-12. 節番号は識別子である。使い回さない

**節番号は採番であって順序ではない**（開発者の決定。2026-08-30。
**番号を使い回すと、古い参照が黙って別のものを指すから**）。

| | 規則 |
|---|---|
| **足す** | 原則、その階層で使った**最大の番号 +1** を取り、**末尾に置く**（中間に挿すときは §4-12-1） |
| **消す** | **`### N. 削除` を残す。詰めない**（日本の法令が「第○条 削除」とするのと同じ作法） |
| **使い回す** | **しない。** 一度使った番号を、別の内容に付け直さない |
| **節を別の文書へ出す** | 移送先で**新しい番号**を取り、**移送元に `削除` の見出しを残す**（下の書式） |
| **文書を分冊する** | **番号を保ち、`削除` も置かない**（本規約を 3 冊に割った形。**番号空間を 3 冊で共有**しており、どの冊が何を持つかは[総則](README.md)の表が着地点になる） |

**`削除` を置くのは、番号が使用中であることを見せるためと、古い参照の着地点を作るためである。**
番号が黙って飛んでいるのは「詰めた」疑いがあり、`削除` があればそうでないと分かる。
**書式は見出し 1 行だけ**——`### 2-4. 削除` に、移した先があれば行き先を markdown リンクで添える
（実物は [ADR-0027](../decisions/0027-入力の一覧はラップモジュールとクエリモジュールで作る.md)）。

**例外は [CLAUDE.md](../../CLAUDE.md) だけ**——`削除` を残さず番号を詰める（付け直す）（開発者の決定。2026-09-06。
**毎回のタスクの前に必ず読むファイルなので、`削除` すら無駄であり、参照の張り替えは必要なコストと割り切るから**）。
**張り替え漏れを機械は拾えない**——番号を詰めると旧番号は必ず実在する別の節に着地し、`check_section_references`（見出しの実在しか見ない）は鳴らない。**§4-12-1 の 3 手順を手で通す。**

**番号が消える／動くときは、下の 3 手順で参照を洗う。** 実際に事故が起きたのは**削除**のほうである
（[qa/03 L-18](../qa/03_テストで漏らした実例.md)。`削除` を置いても、**古い参照が指す先が
「削除」になるだけ**で、直す必要は消えない）。

**§4-4（保留リストを番号で参照しない）とは処方が逆である。** 危険は同じ（番号が別のものを指す）が、
保留リストは**番号を振り直す前提で、参照する側を禁じる**。節番号は**番号を凍結して、参照を守る**。
**保留リストに `削除` は置かない。** なお [10](../10_会計ドメイン設計.md) の I-17 も、
番号を再利用しないという点で同じ考え方に立つ。

#### 4-12-1. 番号が消える／動くときの参照の洗い方

1. **`git grep -n "§"` で追跡下の全ファイルを洗う。** `--include` で絞らない——
   **`BusinessApp/` を除外しない**（自前の C# が入っている。[§2](README.md) の「対象外」は文書規約の話）
2. **その文書を指す形を全部拾う**——ファイル名（`docs/21_画面の原則.md §3`）・短縮番号（`21 §3`）・
   `ADR-0021 §4-3`・**自文書内の裸の `§3`**。表記ゆれ（空白の有無）も見る
3. **直したら、旧番号での参照が 0 件になることを確かめる**

**機械が助けるのは一部だけである。** `lint_docs.py` の `check_section_references` は
「リンクの札に節を書く形」・`docs/10 §1`・`docs/21_画面の原則.md §2`・`21 §3`・`CLAUDE.md §5` の
5 形を拾い、**指し先にその節が実在するか**を見る。**この 5 形なら、節が消えた・
文書ごと番号が消えた取り残しは鳴る。**

**鳴らないものが 3 つある。手順 1〜3 は、この 3 つのために要る。**

1. **旧番号が別の実在する節・文書に着地したとき。** 番号を詰めたときと、
   文書の番号を付け替えたときがこれに当たり、リンクも節も生きたまま**別の内容**を指す
   （理由と処方は [qa/03 L-18](../qa/03_テストで漏らした実例.md)）
2. **上の 5 形以外の書き方。** 手順 2 が挙げた `ADR-0021 §4-3` と**自文書内の裸の `§3`**、
   および `08 が現在形を持ち` のような**散文の裸の番号**は、どの形にも当たらない
3. **検査の対象外のファイル。** 拡張子と除外の一覧は [§6](README.md)。
   とくに `Designer/migrations/` は凍結ゆえ対象外で、**旧番号が残るのが正しい**

#### 4-12-2. どうしても中間に挿すとき

**順序に意味がある文書では、中間への追加を認める**（開発者の判断。2026-08-30）。
**§4-12 の表の「使い回さない」より、こちらが優先する。**
ただし**ずれる節すべてに §4-12-1 を通す**。
**中間への挿入は、末尾に足すより高くつくと分かったうえで選ぶ。**
